## 论文概况

- **标题**: oo7: Low-overhead Defense against Spectre Attacks via Binary Analysis
- **作者**: Guanhua Wang, Sudipta Chattopadhyay, Ivan Gotovchits, Tulika Mitra, Abhik Roychoudhury
- **来源**: arXiv:1807.05843v3
- **核心贡献**: 提出一套**仅基于二进制代码**的静态分析框架，自动检测 Spectre 漏洞（含变体），量化泄露风险，并以最小性能开销完成修复。

## 核心威胁模型与检测条件

oo7 将 Spectre 漏洞（Variant 1）抽象为三条关键指令组成的三元组 **<CB, IM1, IM2>**：

| 符号 | 含义 | 角色 |
|------|------|------|
| **CB** (Conditional Branch) | 受不可信输入控制的条件分支 | 触发推测执行的入口 |
| **IM1** (Instruction Memory 1) | 依赖污点数据的 **加载指令** | 在推测窗口内读取秘密数据 |
| **IM2** (Instruction Memory 2) | 地址依赖 IM1 返回值的 **内存访问指令** | 将秘密数据编码进微架构状态（缓存） |

### 典型漏洞代码模式

```c
void victim_function_v01(size_t x) {
    if (x < array1_size) {          // CB: 受攻击者控制的 x 控制分支
        // IM1 (access to array1)    // 推测执行时越界读取 array1[x]
        // IM2 (access to array2)    // 依赖 IM1 结果访问 array2，将秘密编码进缓存
        temp &= array2[array1[x] * 256];
    }
}
```

**攻击原理**：攻击者先用合法 `x` 训练分支预测器，再传入越界 `x`。CPU 推测执行 `if` 分支，`array1[x]` 读到秘密，`array2[...]` 将秘密映射到缓存行。推测失败后架构状态回滚，但缓存状态保留，攻击者通过侧信道（如 Flush+Reload）恢复秘密。

### 形式化检测条件 Φ<sub>spectre</sub>（公式 1）

```
br(CB) ∧ load(IM1) ∧ mem(IM2) ∧
τ(CB) ∧ τ(IM1) ∧ τ(IM2) ∧
Δ(CB, IM1) ≤ SEW ∧ Δ(CB, IM2) ≤ SEW ∧
Dep(IM1, IM2)
```

- `br(inst)`：inst 为分支指令
- `mem(inst)` / `load(inst)`：内存访问 / 加载指令
- `τ(inst)`：指令被污点着色（操作数含不可信数据）
- `Δ(inst1, inst2)`：两指令间最短指令距离，不可达为 ∞
- `SEW` (Speculative Execution Window)：目标平台推测窗口大小（受 ROB 容量限制）
- `Dep(IM1, IM2)`：IM2 地址计算数据依赖 IM1 返回值

## oo7 方案整体流程

### 分析阶段：污点传播与三元组定位

#### 跨过程污点分析
- **源点**：网络、文件、命令行参数、环境变量等不可信输入。
- **传播规则（值到值 V2V）**：
  - 计算指令：任一操作数被污 → 结果被污
  - Load：源地址值被污 → 目标寄存器被污
  - Store：源寄存器被污 → 目标内存值被污
- **指针到值（P2V）临时开启**：仅在发现污点分支 CB 后，为定位 IM1/IM2 允许“地址被污 → 加载值被污”传播；超出 SEW 立即关闭。这避免了全局 P2V 导致的污点爆炸。

#### 三阶段检测器（Algorithm 1）
检测器沿控制流图前向遍历，维护 `Step ∈ {STEP_CB, STEP_IM1, STEP_IM2}` 状态机：

| 状态 | 触发条件 | 动作 |
|------|----------|------|
| **STEP_CB** | 遇到 `τ(CB) ∧ br(CB)` | 记录 CB，切换 P2V=ON，Step=STEP_IM1 |
| **STEP_IM1** | 在 SEW 内遇到 `τ(IM1) ∧ load(IM1)` | 记录 IM1，Step=STEP_IM2 |
| **STEP_IM2** | 在 SEW 内遇到 `τ(IM2) ∧ mem(IM2) ∧ Dep(IM1,IM2)` | 记录 IM2，输出三元组 <CB,IM1,IM2>，重置检测器 |
| **超出 SEW** | `Δ(CB, current) > SEW` | 自动重置检测器，防止跨窗口误报 |

> **跨过程支持**：分析在调用边界处进行上下文敏感的污点传播（参数、返回值、全局变量），不将库函数视为黑盒，从而捕获 `victim_function_v03` 这种跨函数漏洞。

### 修复阶段：精准插桩

仅在检测出的 **CB 指令后、IM1 指令前** 插入缓解措施，避免全局插桩带来的性能崩溃。

## 关键技术细节

### 记号定义汇总（表 1）

| 记号 | 定义 |
|------|------|
| `br(inst)` | inst 为分支指令 |
| `mem(inst)` | inst 为内存访问指令 |
| `load(inst)` | inst 为加载指令 |
| `τ(inst)` | inst 被污点着色 |
| `Δ(inst1, inst2)` | 指令间最小距离，不可达为 ∞ |
| `Dep(inst1, inst2)` | inst2 数据依赖 inst1 |
| `val(x)` | 地址 x 处存储的值 |
| `SEW` | 推测执行窗口 |

### Spectre 变体识别：间接分支

- **威胁**：攻击者训练间接分支预测器（`jmp rax` / `jmp [rax]`），使推测执行跳转至恶意代码片段（Spectre v2 风格）。
- **oo7 对策**：若间接分支目标寄存器/内存被污点着色 → 直接判定为漏洞，无需寻找 IM1/IM2 三元组。

### 泄露量评估：取值集合分析

- **原理**：IM1 的下标（如 `array1[x]`）指向秘密数据；统计 `x` 在所有调用上下文中的取值区间并集，减去合法数组长度即为最大可泄露字节数。
- **示例**：`x ∈ (50, 200] ∪ [20, 20]`，`array1_size = 100` → 最大泄露 151 字节。
- **实现**：二进制层面的 Value-Set Analysis (VSA)，支持跨函数调用上下文合并。

## 三种修复手法对比

| 手法 | 原理 | 性能开销 | 内存开销 | 自动化程度 | 适用场景 |
|------|------|----------|----------|------------|----------|
| **Fence 指令** | CB 后插入 `lfence`/`mfence` 序列化流水线，阻断推测执行 | 低～中（仅热点分支） | 无 | 全自动 | 通用二进制、性能敏感路径少 |
| **NOP 填充** | CB 与 IM1 间插入 `SEW - Δ(CB, IM1)` 条 NOP，使 IM1 落在推测窗口外 | 极低（NOP 吞吐极高） | 代码膨胀 ≤ 数 KB | 全自动 | SEW 固定、代码尺寸不敏感场景 |
| **冗余数据填充** | 在 `array1` 与秘密区间插入足够大的哑元数组，攻击者读到的全是填充值 | **零**（无指令插入） | 高（需预留填充区） | **半自动**（需人工确认敏感数组边界） | 内存充裕、极致性能要求场景 |

> **注意**：冗余数据填充需人工标识“基本数组”与“秘密区”边界，oo7 仅负责根据泄露量计算填充长度。

## 检测挑战与 oo7 的应对（基于论文 2.2 节实例分析）

论文通过 `f()` / `f'()` 与 `g()` / `h()` / `long()` 的组合（图 1）系统阐述了四大检测挑战：

| 挑战 | 现象 | oo7 对策 |
|------|------|----------|
| **不能仅靠语法检测** | `f()` 中两处 `if` 语法相似，但 `h()` 返回值不受污点控制，第一处无漏洞 | 污点分析 `τ(inst)` 过滤无污点分支 |
| **不能仅做过程内分析** | `f()` 第二处漏洞跨越 `g()`、`h()`；过程内保守假设会误报 `h()` 返回值 | 跨过程污点传播，精确建模参数/返回值/全局变量 |
| **不能仅用现有测试技术** | 符号执行仅沿程序顺序执行，满足 `y < array1_size` 约束，漏报推测路径 | 显式建模推测窗口 SEW，允许在分支条件为假时沿真分支继续分析 |
| **必须模拟微架构特性** | `f'()` 中 `long()` 撑大指令距离，IM1/IM2 超出 SEW，实际不可利用 | 引入 `Δ(CB, IM) ≤ SEW` 硬约束，自动剔除超窗口候选 |

**推测窗口建模细节**：
- SEW 由处理器重排序缓冲区（ROB）大小决定，对应指令数上限。
- oo7 在 CFG 上按指令数计算最短路径 `Δ`，超出 SEW 即判定安全。
- 图 1(f) 中 `long()` 执行指令数 > SEW，导致 `Δ(CB, IM1) > SEW`，检测器复位，避免误报。

## 与现有防御机制的关联

- 与 [[linux-kernel-hardening-mechanisms]] 中的 **侧信道缓解**（如 `retpoline`、IBRS/IBPB、KPTI）互补：内核级缓解覆盖全系统，oo7 提供**应用层二进制精准修补**，二者可组合部署。
- 污点分析思想可借鉴 [[sourcerercc-code-clone-detection]] 中的倒排索引与启发式过滤，加速大规模二进制污点传播。

## 总结与启示

1. **精准性源于约束**：推测窗口 SEW 与数据依赖 `Dep(IM1,IM2)` 双重约束大幅降低误报。
2. **二进制级优势**：无需源码、符号表，适配遗留固件/闭源库。
3. **分层修复策略**：Fence 兜底、NOP 低开销、填充零开销，按部署约束灵活选择。
4. **可扩展性**：污点引擎与检测器解耦，易迁移至 ARM/RISC-V 等新架构（仅需调整 SEW 与指令语义）。

> **后续工作方向**：结合动态轮廓引导污点传播剪枝、探索硬件辅助（Intel PT / ARM SPE）加速推测窗口建模、将泄露量评估集成至编译期优化流水线自动插桩。
