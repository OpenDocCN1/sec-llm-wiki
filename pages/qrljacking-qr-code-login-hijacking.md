## 攻击概述

**QRLJacking**（Quick Response Code Login Jacking）是一种针对基于二维码的快速响应登录系统的会话劫持攻击技术。由埃及安全研究人员提出，并被 OWASP 收录为专项攻击类型。攻击核心在于：攻击者预先初始化一个合法的二维码会话，将其嵌入高仿真度的钓鱼页面，诱导受害者扫码后，攻击者即可劫持受害者的登录会话，获取账户控制权及敏感信息（GPS 定位、设备 IMEI、SIM 卡信息等）。

> 原文来源：301在路上微信公众号《一种针对二维码登陆的新型攻击方式？》，发表于 2016 年。详见 [[301-zai-lushang-wechat-archive-201508-202208]] 中 2016 年 QRLJacking 条目。

## 攻击原理

### 二维码登录认证流程

1.  用户在 PC 端打开支持二维码登录的网站（如微信网页版、WhatsApp Web、Line 网页版）。
2.  网站后端生成唯一的二维码会话 ID，并通过 WebSocket/长轮询等机制等待移动端扫码确认。
3.  用户使用手机 App 扫描二维码，App 将会话 ID 与当前登录账户绑定，完成授权。
4.  PC 端检测到授权成功，建立用户会话，实现免密登录。

### QRLJacking 利用机制

攻击者利用**二维码会话 ID 可预测/可复用**及**用户无法直观区分二维码归属**的特性，构造以下攻击链：

| 阶段 | 操作描述 |
|------|----------|
| **1. 会话初始化** | 攻击者在自己控制的浏览器中打开目标网站，获取一个有效的二维码会话 ID 及对应二维码图片。 |
| **2. 会话保活** | 编写脚本定期刷新/重用该会话 ID，防止因超时失效（部分验证码有存活期，需同步更新）。 |
| **3. 钓鱼页面构造** | 克隆目标网站登录页面（高相似度），将攻击者持有的二维码图片嵌入页面对应位置。 |
| **4. 社工诱导** | 通过钓鱼邮件、即时通讯软件等方式将钓鱼链接发送给受害者。 |
| **5. 受害者扫码** | 受害者误信页面真实性，使用已登录的手机 App 扫描二维码完成授权。 |
| **6. 会话劫持** | 攻击者浏览器端检测到授权成功，立即获得受害者账户的完整会话控制权。 |

## 实施条件与难点

### 必备条件

1.  **自动刷新的二维码脚本**：需同步目标网站二维码更新机制，保证钓鱼页面二维码始终有效。
2.  **高仿真钓鱼页面**：需复刻目标站点登录页的 UI、交互逻辑、域名外观（可配合同形异义域名、短链接等手段）。
3.  **有效的社工诱导手段**：需让受害者在信任上下文中点击链接并执行扫码操作。

### 现实约束（文章作者视角的“鸡肋”点）

- **前置依赖强**：必须受害者**主动扫描**攻击者提供的二维码，纯技术手段无法强制触发。
- **时效性要求高**：二维码会话通常有严格过期时间（如 30~60 秒），攻击者需实时同步，工程实现复杂度非零。
- **目标范围受限**：仅针对**已在手机端登录 App**且**习惯使用扫码登录 PC 端**的用户群体。

> 尽管存在上述约束，但正如文章结尾所言：XSS 漏洞早期也被低估，QRLJacking 作为一种新型会话劫持面，随着二维码登录普及，其威胁面可能被重新评估。

## 影响范围

- **微信网页版**（web.wechat.com）
- **WhatsApp Web**（web.whatsapp.com）
- **Line 网页版**
- 其他采用“扫码授权”模式的 OAuth/SSO 系统（企业内部 OA、云盘、邮箱等）

## 防御与缓解建议

### 客户端/用户侧

1.  **验证域名**：扫码前务必确认浏览器地址栏为官方域名，警惕同形异义域名（如 `vvx.wechat.com` vs `wx.wechat.com`）。
2.  **关注 App 提示**：微信、WhatsApp 等 App 在扫码授权时会弹窗显示“登录地点/设备类型”，若显示异常（如陌生城市、非本人设备），应立即取消授权。
3.  **开启登录设备管理**：定期检查并清理不再使用的已登录设备（微信：设置 → 账号与安全 → 登录设备管理）。
4.  **避免在非受信环境扫码**：公共场所、他人分享的链接、不明来源的二维码均不应扫描登录。

### 服务端/开发侧

1.  **绑定会话上下文**：二维码会话 ID 与发起页面的 Client Fingerprint（IP、User-Agent、Canvas 指纹等）强绑定，检测到异常变更即失效会话。
2.  **短周期+一次性二维码**：大幅缩短二维码有效期（≤30 秒），且每次刷新生成全新会话 ID，防止攻击者长期复用。
3.  **扫码确认页增强**：在移动端授权页显示请求来源 IP、地理位置、设备型号等上下文信息，引导用户识别异常。
4.  **引入二次验证**：高敏感操作（首次新设备登录、修改安全设置）要求输入手机验证码/生物特征确认。
5.  **监控异常扫码模式**：同一会话 ID 在短时间内被多次扫描、或来自高风险 IP 的扫码请求，触发风控拦截。

## 小结

QRLJacking 揭示了**“扫码登录”这种看似安全的免密认证方式，在会话绑定环节存在信任假设缺失**。攻击成本主要在于**钓鱼页面制作与社工诱导**，而非纯技术漏洞利用。随着二维码登录成为主流，防御重点应转移到**会话上下文绑定、用户侧风险感知提升、风控实时拦截**三个维度，而非单纯依赖“二维码随机生成即安全”的错误认知。
