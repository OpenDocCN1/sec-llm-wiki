## 概述

**SourcererCC**（Source Code Clone Detector）是针对大规模代码库设计的 Token 级代码克隆检测工具，发表于 ICSE 2016。它解决了现有工具在通用性与规模上的两大痛点：

- **通用性不足**：多数工具仅适用于特定场景或语言
- **规模受限**：无法处理亿行级代码库

SourcererCC 的核心优势：
- **克隆类型覆盖全**：精确检测 Type-1（完全相同）、Type-2（变量/字面量替换）、Type-3（语句增删修改）三类克隆
- **语言无关**：仅依赖词法 Token，可直接应用于 C/C++、Java、C# 等语言
- **单机即可运行**：无需分布式集群，单工作站即可完成亿行代码检测
- **高效精准**：召回率与精度均优于 CCFinderX、Deckard、iClones、NiCad 等主流工具，检测时间随规模近线性增长

## 核心原理

### 基本概念

| 概念 | 定义 |
|------|------|
| **代码块** | 括号内的一系列语句、局部类和变量声明，由若干 Token 组成：$B = \{t_1, t_2, ..., t_n\}$ |
| **项目** | 由若干代码库组成：$P = \{B_1, B_2, ...\}$ |
| **Token** | 编程语言的关键字、常量及标识符；用 `(token, frequency)$ 表示，frequency 为全局出现次数 |
| **候选块** | 对给定代码块进行比较的其他所有代码块 |
| **克隆对/克隆类** | 相似的代码段对 / 一组相似的代码段 |

### 相似度度量

采用 **Overlap 系数** 作为相似度函数：

$$
sim(B_1, B_2) = |tokens(B_1) \cap tokens(B_2)|
$$

给定阈值 $\theta$，目标是找出所有满足 $sim(B_1, B_2) \ge \theta \cdot \min(|B_1|, |B_2|)$ 的克隆对。

### 整体流程

检测分两大阶段：

1. **部分索引构建**：仅对部分 Token 建立**倒排索引**（Token → 包含该 Token 的代码块列表及位置），类似搜索引擎技术，大幅加速检索
2. **克隆检测**：候选块筛选 → 克隆对验证，核心在于两阶段启发式过滤

## 算法细节

### Token 排序策略

所有代码块内的 Token 按**全局出现频率从小到大排序**（稀有 Token 优先）。此排序为两阶段启发式奠定基础。

---

### 第一阶段启发式过滤（前缀过滤）

**原理**：若两集合重叠度高，其前缀子集必有交集。

给定代码块 $B_1, B_2$（长度均为 $t$），若 $sim(B_1, B_2) \ge \theta \cdot t$，则由前 $k = t - \lceil \theta \cdot t \rceil + 1$ 个 Token 组成的前缀子块至少匹配 1 个 Token。

**索引构建算法（Algorithm 1）**：
1. 对每个代码块按全局 Token 频率重排
2. 计算需索引的前缀长度 $k$
3. 建立倒排索引：存储 `<Token, (BlockID, Position)>`

**局限性**：当两块实际重叠 Token 数不足阈值但前缀仍有交集时，仍会被误判为候选块（产生假阳性）。

---

### 第二阶段启发式过滤（位置界过滤）

**原理**：利用 Token 在有序序列中的位置关系，计算最大可能重叠上界，提前剪枝。

设 $B_1$ 中第 $i$ 个 Token 为 $t$，将 $B_1$ 分为前缀 $B_1[1..i]$ 与后缀 $B_1[i+1..t]$。若当前已匹配 $m$ 个 Token，则最大可能重叠为：

$$
upper\_bound = m + \min(|B_1| - i, |B_2| - pos_{B_2}(t))
$$

若 $upper\_bound < \theta \cdot \min(|B_1|, |B_2|)$，直接排除该候选块。

**检测算法（Algorithm 2）**：
- 维护 `candSimMap` 记录候选块已匹配 Token 数
- 遍历查询块的前缀 Token，在倒排索引中查找候选块
- 应用第二阶段界值剪枝，仅保留通过的候选块

---

### 最终验证阶段（Algorithm 3）

对通过两阶段过滤的候选块，逐 Token 精确比对：

1. 跳过已参与过滤的前缀 Token
2. 利用已排序特性，双指针线性扫描计算真实重叠数
3. 仅当真实重叠满足阈值时确认为克隆对

## Type-3 克隆检测原理

SourcererCC **忽略 Token 在代码块中的相对位置**，仅基于 Token 集合重叠度判断。这种“词袋”特性使其：
- **优势**：自然兼容语句增删、顺序调整等 Type-3 变体
- **劣势**：丢失语义/控制流信息，**不适合直接用于漏洞检测**等需语义理解的场景

## 实验评估

### 数据集与基线

| 维度 | 选择 |
|------|------|
| 数据集 | IJaDataset 2.0（Java）、C/C# 项目 |
| 召回率基准 | BigCloneBench、Mutation & Injection 框架 |
| 精度验证 | 专家人工标注 BigCloneBench 结果 |
| 对比工具 | CCFinderX（仅 Type-1/2）、Deckard、iClones、NiCad（均支持 Type-1/2/3） |

### 关键结果

- **召回率**：在 Java、C、C# 三语言上均显著优于四款基线工具（Mutation 框架与 BigCloneBench 双指标验证）
- **精度**：专家验证 **91%**
- **检测时间**：随输入规模近线性增长，单机处理亿行代码仅需数小时，比基线工具快 1-3 个数量级

## 总结与定位

| 维度 | 评价 |
|------|------|
| **创新点** | 两阶段启发式过滤（前缀过滤 + 位置界剪枝）将复杂度从 $O(n^2)$ 降至近线性 |
| **适用场景** | 大规模代码库去重、重构机会挖掘、跨项目代码复用分析、恶意代码变种检测 |
| **局限性** | 无语义感知，不适合漏洞克隆检测；Token 级粒度可能漏报高度重构的 Type-4 克隆 |
| **工程价值** | 单机部署、多语言零配置、工业级性能，已在多个开源项目中集成应用 |
