## 概述

2016年2月7日（除夕前夕），微信在朋友圈推出限时公测功能**“红包照片”**：用户发布照片后自动覆盖动态模糊滤镜，好友需发送 2–10 元红包才能查看清晰原图。功能上线数小时内，乌云社区白帽子 **@路人甲** 发现**模糊处理仅在客户端渲染层实现，服务端未对原图进行任何加密或访问控制**，导致攻击者可通过抓包获取原图 URL 或直接读取本地缓存绕过红包支付查看完整照片。腾讯安全团队在漏洞提交后快速确认并承诺修复，当晚功能即暂时下线。该案例成为国内移动端 **客户端侧访问控制缺失** 与 **厂商漏洞响应协同** 的经典教学案例。

## 漏洞背景与功能逻辑

### 红包照片产品设计

| 步骤 | 用户侧行为 | 客户端表现 |
|------|------------|------------|
| 1 | 发布者在朋友圈上传照片 | 照片上传至微信 CDN，生成唯一资源标识 |
| 2 | 好友浏览朋友圈 | 客户端请求图片资源，**本地叠加动态模糊滤镜** 渲染“雾蒙蒙”预览图 |
| 3 | 好友点击预览图 | 滤镜随机揭示一小块清晰区域，诱导发送红包 |
| 4 | 好友完成红包支付 | 客户端移除滤镜，直接展示原始清晰图片 |

**核心缺陷**：步骤 2–3 中，**原始高清图片已在步骤 2 全量下载至本地**，滤镜仅为前端渲染时的视觉遮罩，服务端未实施“支付后下发解密密钥”或“延迟下发原图”逻辑。

## 漏洞技术细节

### 攻击面分析

```text
正常流程：CDN → 加密传输 → 客户端内存（完整图片） → 滤镜渲染 → 屏幕显示
攻击流程：CDN → 加密传输 → 客户端内存/磁盘缓存（完整图片） → 绕过渲染层 → 直接访问
```

### 两条利用链路

| 利用方式 | 关键操作 | 门槛 |
|----------|----------|------|
| **网络层抓包** | 1. 开启 Burp Suite / Charles 代理<br>2. 触发朋友圈图片加载<br>3. 在 HTTP 响应体中提取 `Content-Type: image/jpeg` 的完整图片数据 | 需配置代理、安装 CA 证书，中等 |
| **本地缓存提取** | 1. 进入微信缓存目录 `/data/data/com.tencent.mm/MicroMsg/{hash}/image2/`<br>2. 直接复制对应哈希命名的图片文件 | Root 权限或 ADB backup，低 |

**关键证据**（白帽子抓包截图）：
- HTTP 响应头无 `Cache-Control: no-store` 等防缓存指令
- 响应体即为原始 JPEG 数据，无加密、无分片、无水印

| CWE 分类 | 说明 |

## 漏洞披露与厂商响应全过程

### 时间线

| 时间节点 | 事件 | 备注 |
|----------|------|------|
| 2016-02-07 17:00 左右 | 微信灰度推送“红包照片”功能 | 仅限当日体验，18:00 计划自动下线 |
| 2016-02-07 17:30 | 白帽子 @路人甲 发现绕过逻辑，提交乌云漏洞报告 | 报告标题：《微信朋友圈绕过红包限制直接查看照片》 |
| 2016-02-07 18:00 前后 | 腾讯安全团队确认漏洞，标记为“已知问题” | 回复：“今天的微信朋友圈红包也只是预热，后续我们将尽快修复此问题” |
| 2016-02-07 18:30 | 微信服务端下线红包照片功能入口 | 朋友圈恢复正常主题，原发布照片不可访问 |
| 2016-02-08（除夕夜） | 功能修复后正式上线 | 新版本在支付红包后才下发原图/解密密钥 |

### 腾讯响应亮点

1. **响应时效**：从白帽子提交到官方确认 **< 30 分钟**，符合 [[bug-bounty-program-history-evolution]] 中“高成熟度 SRC”标准。
2. **定性准确**：明确承认“已知问题”，未推诿至“设计权衡”或“预热版不算漏洞”。
3. **业务决策果断**：在春节营销关键期**主动下线**有缺陷功能，体现“安全>业务”原则。
4. **公开致谢**：在乌云平台公开回复，鼓励后续红包业务安全测试，强化 [[white-hat-enterprise-collaboration-guide]] 中“信任机制”建设。

## 安全启示与最佳实践

### 移动端访问控制设计原则

| 原则 | 错误做法 | 正确做法 |
|------|----------|----------|
| **服务端授权** | 客户端持有完整资源，靠 UI 控制可见性 | 资源默认加密/分片，**支付成功后下发密钥/剩余分片** |
| **最小权限下发** | 全量下发原图再本地滤镜 | 预览图单独生成低分辨率/高斯模糊版本，**原图永不落盘** |
| **缓存策略隔离** | 统一缓存目录，无加密 | 敏感资源**内存级缓存+进程销毁即清理**，或 AES-256 加密落盘 |
| **审计与监控** | 无异常下载检测 | 埋点上报“未支付触发原图请求”，触发风控熔断 |

### 白帽子协作规范参考

- **漏洞报告要素**：复现步骤（含抓包/缓存路径）、影响范围（全量用户/灰度版本）、POC 视频/截图、修复建议（延迟下发/服务端授权）。
- **厂商响应 SLA**：确认 < 1h、分级 < 4h、修复上线 < 24h（P0），参考 [[security-vendor-incident-response-behavior]] 中“天融信 TOS 1 小时确认修复”正向案例。
- **激励机制**：腾讯 SRC 按风险等级发放赏金，配合“白帽子成长体系”积分，避免 [[whitehat-arrest-baihe-case]] 类“提交漏洞反被刑拘”负面事件。
