**\# 0**

![](../Images/66c775030e5bd1ea715781b55a2d2e4e.png)

今天上午刷 Twitter 时，突然看到一条使用 Chrome 0-day 进行弹计算器的，并且放出了 Exploit： 

![](../Images/e6b7b03707b980b2de3967263190affa.png)

一开始以为这个漏洞包括 Chrome 沙箱逃逸的，后来看了一下发现只是 V8 引擎的一个漏洞，而且这个漏洞实际上已经被补掉了，只是相应版本的 V8 目前还没同步到线上稳定版的 Chrome 中，因此还存在被利用的风险（不过一般 Chrome 的沙箱默认开启，不手动关掉就没啥问题）。 

  

下午稍微看了下相关的补丁，发现这个漏洞还是相对比较好理解，所以决定分析一下。 

  

**\# 漏洞**

  

首先，这个漏洞在这个提交中被修复： 

  

*   https://chromium.googlesource.com/v8/v8/+/02f84c745fc0cae5927a66dc4a3e81334e8f60a6
    

  

进去看一下可以发现，补丁的内容非常简单，而且有相应的注释： 

![](../Images/a155ba20433a8f7825b707bc0c7e5424.png)

具体的内容是将 ChangeInt32ToInt64 相关的图节点字节码编译成机器码选择机器指令的时候，原先会考虑目标值是否为有符号数，而进行选择 Movl 还是 Movsxlq，可以从注释中推测前者是零扩展，而后者是符号扩展。 

  

接下来我们看一下提供的 Exp，这里仅截取与漏洞相关的主要部分： 

![](../Images/683ee940ae0aa0b922003eb6c2d40f8e.png)

通过将这个函数进行 JIT 编译之后，可以通过返回的 arr 数组对 cor 实现越界读写。那么这个函数在被 JIT 之后发生了什么呢？我们可以使用 Turbolizer 来查看对应生成的节点，首先关注 Exp 中 \_arr\[0\] ^ 0 部分，一般情况下，整数与 0 异或会得到原数字，但是由于这里 \_arr\[0\] 是无符号整数，与 0 异或之后会得到一个有符号整数，因此生成的节点图如下： 

![](../Images/314795186ffb8eef26f6c321821df5a5.png)

可以看到 \_arr\[0\] 与 0 异或之后得到有符号的 32 位整数，之后为了进行加法运算，通过 ChangeInt32ToInt64 节点将 32 位整数转换成 64 位整数，从而引入了漏洞相关的代码。本来由于 Word32Xor 返回的是有符号整数，因此这里的 ChangeInt32ToInt64 节点在转换成机器码的过程中不应该出现问题。但是由于 V8 引擎中的 JIT 是一个多阶段不断优化的过程，之前说到，整数与 0 异或会得到整数本身，因此 TurboFan（编译引擎）在遇到 Word32Xor 并发现右操作数为常量 0 时，会在 EarlyOptimization 阶段将改节点优化掉，从而得到如下图： 

![](../Images/533197957564e350dbea21808577095d.png)

可以看到，传递给 ChangeInt32ToInt64 节点的值直接从 LoadTypedElement 节点获得，而该节点从 \_arr 中加载的元素为无符号数。这时，漏洞的成因也就明确了，在后续将 ChangeInt32ToInt64 节点转换成机器码的过程中，由于传进来的值为无符号数，因此选择 kX64Movl 对应的机器码，而该机器码会进行零拓展，从而得到 64 位有符号数 0x80000000（Exp 中的变量 x）。这时，变量 x 再通过 Exp 代码中的一系列操作，在执行到作为 new Array() 的参数时，可以得到 x 的值为 1。因此，正常情况下，new Array 将返回一个空数组，而通过 JIT 触发漏洞之后，new Array 返回的数组长度为 1。 

  

但是只分析到这里还是无法对这个漏洞进行利用，第二个关键的部分是 Exp 代码中的 arr.shift() 代码，正常情况下，该语句会返回数组中的第一个元素，并将数组的长度减 1。照理来说，即使前面触发了漏洞，返回了一个长度为 1 的数组，经过这句话之后，也只是将数组的长度变为 0，不会有太大的问题。 

  

问题还是出在 TurboFan 的优化过程中。V8 的 TurboFan 在转化内置函数时，一般会将其转换到直接调用一些事先编译好的内置代码，来加快执行速度。但是有一些情况下，会进行判断，如果满足某个条件，则会执行 Fast Path，不进入内置代码执行（可以查看 JSCallReducer::ReduceArrayPrototypeShift 函数代码）： 

![](../Images/9495170cd797ec50dc1b4cc9bd8b847b.png)

因此，如果当前数组长度小于 kMaxCopyElements 的值（100）的时候，会执行 Fast Path。而 Fast Path 实际上是就是获得第一个元素，然后根据数组长度进行循环，将数组中元素的位置进行挪动，并在挪动完成之后，将数组长度的字段减 1，如下图，其中红框部分为更新长度字段部分： 

![](../Images/dc96087a5cba297e6851dea5fd6465ac.png)

但是，由于 JIT 的过程会不断根据推测的值对操作进行优化、消除冗余步骤，TurboFan 在优化过程中（LoadElimination 阶段），会根据所推测的具体数值，判断当前数组的长度为常量 0，而常量 0 减去 1 会得到定值 -1，因此可以将图中大部分的操作直接消除，最后更新长度字段部分如下： 

![](../Images/787c91991c84eb7d52b43629138ed090.png)

因此，当我们对通过 new Array 创建的数组使用 shift 函数时，最终会使得当前数组的长度变成 -1（0xffffffff），如下图（这里值为 0xfffffffe 是因为 V8 对值存储的特性）： 

![](../Images/52c7ed86f92d7d9945ad30008368feb0.png)

在完成这些之后，实际上我们可以获得一个很大的数组，从而实现越界读写。   

  

接下来的利用就比较直白，在构造可越界数组（victim\_arr）的同时构造一个浮点型数组（float\_arr），通过 victim\_arr 的越界写改写 float\_arr 的长度字段，从而可以得到一个实现任意越界读写的 float\_arr，然后我们借助 WASM 将 Shellcode 写到可读写内存区域中，从而实现任意代码执行。
