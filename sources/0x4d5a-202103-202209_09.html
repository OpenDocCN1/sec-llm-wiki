关于PE不落地执行技术的思考

原文：http://mp.weixin.qq.com/s?__biz=Mzg5MjU2NTc1Mg==&mid=2247483721&idx=1&sn=5ce84fc04adbedce1a40a348d28e7a10&chksm=c03d60def74ae9c8f98368780a3bd3040495ee9ca8d13e27297a383c0fe434ca24bfe0e7bc6e&scene=126&sessionid=1681657974#rd

本文阐述主流的PE不落地执行技术，简述其思路步骤，并分享一些细节原理的研究。

PE内存执行个人认为可以分为以下三大类：

1.PE加载器：除了常规的PE加载器，还有RDI，sRDI和pe2shellcode (如Donut / pe2shc）等，它们的核心都是PE加载器。2.Section相关：包括Process Doppelganging, Process Ghosting等，它们的核心都与进程创建时的Section内核对象有关。3.镂空傀儡进程，复用进程创建流程：代表是Process Hollowing和Transacted Hollowing

1. 技术点概述

1.1 Process Hollowing

Process Hollowing是一个非常经典的技术，我见过几种不同的实现，但核心都是以下几步

1.创建挂起的傀儡进程2.Unmap原有的Section View（非必须）3.写入payload的PE头4.依次写入并展开payload的Section5.执行重定位6.修改PEB的ImageBase7.修改OEP8.恢复主线程

1.2 Process Doppelganging

Process Doppelganging利用TxF不落地的创建Image Section，步骤为：

1.创建NTFS Transaction2.在TxF中创建文件或者覆写文件，写入payload3.通过文件句柄创建IMAGE SECTION4.关闭文件句柄5.回滚NTFS Transaction6.通过Section创建进程7.写入PEB的ProcessParameters和Environment8.创建主线程

1.3 Process Ghosting

Process Ghosting的后几步与Process Doppelganging相同，区别在于前三步通过设置DELETE PENDING file来不落地的创建Image Section

1.创建文件2.设置文件句柄的FILE_DISPOSITION_INFORMATION.DeleteFile = TRUE3.写入payload4.通过文件句柄创建IMAGE SECTION5.关闭文件句柄6.通过Section创建进程7.写入PEB的ProcessParameters和Environment8.创建主线程

1.4 Process Herpaderping

和Process Doppelganging / Process Ghosting其实没有太大区别，略过

1.5 Transacted Hollowing

Transacted Hollowing是Process Hollowing和Process Doppelganging的结合，它的步骤是：

1.创建NTFS Transaction2.在TxF中创建文件或者覆写文件，写入payload3.通过文件句柄创建IMAGE SECTION4.关闭文件句柄5.回滚NTFS Transaction6.创建挂起的傀儡进程7.将第三步创建的SECTION映射到傀儡进程中8.修改傀儡进程PEB的ImageBase9.修改傀儡进程的OEP

1.6 PE Loader

流程分为：

1.为PE Image分配内存2.依次写入PE头和节3.处理重定位表4.处理导入表5.处理延迟导入表6.恢复节的DEP属性7.执行TLS回调8.执行EntryPoint

2. 关于上述技术的思考

2.1 Process Hollowing

回顾Process Hollowing的流程，它是在恢复主线程执行前进行镂空操作，而在镂空的过程中需要手动的做节展开和重定位，但不需要处理导入表。

原因是：操作系统加载PE过程中的导入表和重定位处理流程是发生在主线程执行之后的，通过ProcessHacker等工具可以观察到进程以挂起方式创建时，只会加载自己本身和NTDLL两个模块，分析内存也会发现此时还没有做重定位

（此处因为没有搜索到相关资料，所以猜测操作系统的PE Loader处理导入表和重定位表的功能是通过APC或进程挂靠等机制实现的，所以也就解释了为什么在主线程恢复执行之后）

2.2 Process Doppelganging

Process Doppelganging是通过TxF来不落地创建IMAGE Section。

回顾其流程，我们只需要将PE不落地转换为IMAGE Section，就可以通过NtCreateProcessEx创建进程。但前提是创建的Section必须是IMAGE Section，而使用NtCreateSection指定SEC_IMAGE时必须传入文件句柄，且该文件句柄对应的文件是一个合法PE文件。

于是通过TxF可以通过CreateTransaction在不落地的情况下获取到一个合法的PE文件句柄，然后传递给NtCreateProcessEx。这里的不落地是真正的不落地，TxF在没有Commit前是完全通过内存的，通过ProcMon监控无法看到写创建文件或写文件事件。

2.3 Process Ghosting

Process Ghosting的思路与Process Doppelganging如出一辙，但是通过DELETE Pending file实现近似不落地创建IMAGE Section。

首先讲讲什么是DELETE Pending，Windows删除文件有两种方法[1]：

1.创建文件时设置FILE_DELETE_ON_CLOSE2.有文件句柄的情况下，通过设置文件句柄FILE_DISPOSITION_INFORMATION.DeleteFile = TRUE

（当然Windows有一个API叫DeleteFile，但它只接受一个字符串文件名，它的实现是通过上文第二种方法ReactOS - DeleteFileW[2]）

为什么说Process Ghosting是近似不落地，因为通过Process Hacker等内核层监控是可以看到写文件行为的

2.4 NtCreateProcessEx

该API通过一个Section句柄创建进程，与其相关的进程不落地技术都是通过了Windows进程创建流程中的BUG，或者说Feature来躲避监控。

通过该API创建进程，只需要一个PE文件句柄，和一个通过其创建的IMAGE Section。该文件句柄可以设置NO SHARE MODE，可以通过TxF使其仅存在于内存，可以设置DELETE PENDING状态，在创建Section后可以立即覆写混淆磁盘上的源PE文件。

2.5 Transacted Hollowing

Transacted Hollowing是Process Hollowing和Process Doppelganging的结合，综合了两者的优点

回顾一下两者的优缺点分别是：


Process HollowingProcess Doppelganging
优不需要处理PEB；可以模拟傀儡进程(e.g. 文件签名)不需要做重定位
缺需要做重定位；PE处于Private虚拟内存需要处理PEB；创建的进程异常

（解释一下Process Doppelganging创建的进程异常是什么意思，即创建后在tasklist和任务管理器里看到的进程名不同，Process Hacker里看到的进程源PE文件不存在等种种有别与正常进程的特点。）

而Transacted Hollowing则很好的结合了两者[3]，它通过TxF不落地创建IMAGE Section，然后将该Section映射到傀儡进程里进行镂空。

Transacted Hollowing不需要做重定位，因为NtMapViewOfSection在映射IMAGE Section时会尝试映射到ImageBase，失败后会返回STATUS_IMAGE_NOT_AT_BASE并标记，并在主线程resume后自动进行重定位。而且因为是IMAGE Section，所以映射到进程空间里是MEM_IMAGE属性。

2.6 Sysmon Process Tampering

Sysmon 8.0之后引入了Process Tampering - Event ID 25[4]，根据描述，它应该能检测所有内存镜像和磁盘文件不相同的进程，但经过测试我发现它只能检测到Process Hollowing, Process Doppelganging, Process Ghosting和Process Herpaderping，但无法检测到Transacted Hollowing。

MSDN写Process Tampering有以下两种检测类型：

1.Image is locked for access2.Image is replaced

按理说TYPE 2是能够检测Transacted Hollowing的，但我测试多次都无法检测到，所以该技术目前还是个非常好的选择。

2.7 PE Loader

本节讲讲PE Loader的三个trick

2.7.1 处理延迟导入表

诸如MemoryModule之类的PE Loader项目没有处理延迟导入表，这会导致某些PE跑不起来，代表例子就是cmd.exe，因为cmd.exe的cmdext.dll是通过延迟导入加载的

2.7.2 处理api set schema

如果自实现GetProcAddress，那么必须要处理api set schema[5]，不然会出现下面的情况

当导入kernel32!InitializeProcThreadAttributeList时，它是一个forwarded export，指向api-ms-win-core-processthreads-l1-1-0!InitializeProcThreadAttributeList，接着通过LoadLibrary加载api-ms-win-core-processthreads-l1-1-0这个虚拟DLL时，它会转发到kernel32，接着就开始无限循环。

而实际上这个函数位于kernelbase，解决方法是通过指定base module去解析api-ms-win开头的虚拟DLL，会直接指向kernelbase。

有个叫DarkLoadLibrary的项目用一种非常奇葩的方法[6]实现，它不解析api set schema，通过fallback至kernel32, kernelbase和ntdll来寻找目标函数所处的真实DLL。如果以上三个DLL里都没找到，就fallback回用NTDLL!LdrGetProcedureAddress来获取函数地址。为什么会有最后一步回退至NTDLL!LdrGetProcedureAddress，因为还有dbghelp!MiniDumpWriteDump这样的forwarded export它无法处理。

2.7.3 将PE Image分配到MEM_IMAGE内存

常规的方法都是通过VirtualAlloc分配虚拟内存，但这样的内存块是MEM_PRIVATE属性，如果具有执行属性的话会显得非常可疑。

所以可以将其分配到MEM_IMAGE内存中，具体方法就不赘述了，读到这里的读者一定是明白的。
