PPL机制：绕过与利用

0. 概述

本文将介绍Windows系统的PPL (Protected Process Light) 机制，并介绍与PPL相关的两种手法，分别是：

1.绕过PPL的保护访问目标进程，例如Dump设置了RunAsPPL的LSASS进程2.利用PPL对抗AV/EDR，保护自身恶意代码，躲避内存扫描

这两种手法都基于@itm4n的PPLDump[1]项目，本文最后会简要分析该漏洞原理

1. 什么是PPL

1.1 kernel32!OpenProcess

介绍PPL前先介绍一些基础知识，了解的读者可以跳过


HANDLE OpenProcess(  [in] DWORD dwDesiredAccess,  [in] BOOL  bInheritHandle,  [in] DWORD dwProcessId);


kernel32!OpenProcess函数的第一个参数指定了打开进程句柄的访问权限，在红队Dump LSASS进程内存时，一般会设置PROCESS_QUERY_INFORMATION | PROCESS_VM_READ两个权限，具备这两个权限的句柄才可以通过kernel32!ReadProcessMemory来读取虚拟内存。(当然，前提是当前进程的令牌里有SeDebugPrivilege权限，具有该权限的进程可以向其它进程请求所有访问权限)

但在高版本Windows 10上，默认LSASS进程是设置了RunAsPPL的 (reg query HKLM\SYSTEM\CurrentControlSet\Control\Lsa /v RunAsPPL)。此时即使是再高的权限，也无法以上述两种访问权限打开LSASS的句柄，而是会返回Access Denied

1.2 Protected Process

Windows Vista和Windows Server 2008引入了Protected Process，它最初是用来做DRM的，也就是保护音视频文件版权

直观理解：被设置为Protected Process运行的进程无法被未设置Protected Process运行的进程访问。受保护的进程仅能以PROCESS_QUERY_LIMITED_INFORMATION / PROCESS_SET_LIMITED_INFORMATION / PROCESS_TERMINATE / PROCESS_SUSPEND_RESUME权限打开句柄

1.3 Protected Process Light

Windows 8.1和Windows Server 2012 R2引入了PPL，它与Protected Process的不同之处在于，它有了级别的概念


typedef enum _PS_PROTECTED_TYPE {    PsProtectedTypeNone = 0,    PsProtectedTypeProtectedLight = 1,    PsProtectedTypeProtected = 2} PS_PROTECTED_TYPE, *PPS_PROTECTED_TYPE;
typedef enum _PS_PROTECTED_SIGNER {    PsProtectedSignerNone = 0,      // 0    PsProtectedSignerAuthenticode,  // 1    PsProtectedSignerCodeGen,       // 2    PsProtectedSignerAntimalware,   // 3    PsProtectedSignerLsa,           // 4    PsProtectedSignerWindows,       // 5    PsProtectedSignerWinTcb,        // 6    PsProtectedSignerWinSystem,     // 7    PsProtectedSignerApp,           // 8    PsProtectedSignerMax            // 9} PS_PROTECTED_SIGNER, *PPS_PROTECTED_SIGNER;


进程会被设置保护类型 (PP或PPL)，签名方。有以下可用的值


PS_PROTECTED_SYSTEM (0x72) PS_PROTECTED_WINTCB (0x62) PS_PROTECTED_WINTCB_LIGHT (0x61)PS_PROTECTED_WINDOWS (0x52)PS_PROTECTED_WINDOWS_LIGHT (0x51) PS_PROTECTED_LSA_LIGHT (0x41) PS_PROTECTED_ANTIMALWARE_LIGHT (0x31)PS_PROTECTED_AUTHENTICODE (0x21) PS_PROTECTED_AUTHENTICODE_LIGHT (0x11)PS_PROTECTED_NONE (0x00)


对于Ring3层的进程，WinTcp是最高优先级的Signer，可以看到Ring3关键的系统进程都是以PsProtectedSignerWinTcb-Light运行的

关于PP和PPL，有以下两个原则：

1.PP始终比PPL级别高2.PROTECTED_TYPE相同的情况下，比较Signer级别

由以上两个原则可以推导出常见场景：

1.PP进程始终可以访问PPL进程，反之不可以，无关Signer级别2.PROTECTED_TYPE相同的情况下，一个进程可以访问Signer级别比自身低或等于自身的进程3.无保护的进程无法访问PP或PPL进程

这也就解释了为什么在LSASS RunAsPPL设置的情况下，无法通过procdump或mimikatz来Dump其内存

2. 绕过PPL

现行有两种绕过PPL访问目标进程的方案

2.1 Ring0层修改EPROCESS

Ring0层EPROCESS结构体代表了一个内核对象，PPLKiller和mimikatz的mimidrv都是通过加载驱动到内核层，然后patch该结构体上的Protected标志位来将目标进程的保护给取消的

这种加载驱动的方法有一个硬伤，就是无论如何驱动文件都需要落地

2.2 从保护级别大于等于目标进程的进程空间中进行访问

这种方法的代表是PPLDump项目，它是通过DefineDosDevice在做impersonate时的一个逻辑漏洞来修改了KnownDLLs，然后将恶意DLL加载进了受保护进程内存空间，在受保护进程中对受保护的LSASS进程进行访问

KnownDLLs目录保存的实际是Section对象，所以可以将DLL不落地转换为内存中的Section，了解过Process Doppelganging / Process Ghosting技术的读者应该能立刻明白我在说什么。该项目就是利用了这种技术，即通过Transaction+写文件来不落地获取了文件句柄，然后通过NtCreateSection在内存中创建Section

后面会详细讲解该漏洞原理

3. 利用PPL

免杀中如何绕过内存查杀一直是一个问题，通过将恶意代码跑在PPL进程内，可以避免被AV/EDR扫描内存

把shellcode注入到Windows Defender服务进程MsMpEng.exe中，它的PPL级别是PsProtectedSignerAntimalware-Light

把shellcode注入到wininit.exe进程中，它的PPL级别是Ring3层最高的PsProtectedSignerWinTcb-Light


以上两个注入都是在Windows10 21H1中进行的

但是很遗憾，跑在这两个服务里的shellcode都无法创建进程 (返回Error code 87 Invalid Parameters)，也就导致了CS里大部分命令用不了，但文件系统操作都没问题。（如果哪位大佬知道原因恳请后台留言告诉我）

4. PPLDump原理

上述两种手法都是通过PPLDump[1]这个项目实现的，@itm4n写了不少类似的EXP，而且很有分享精神

关于PPLDump漏洞原理，@itm4n的这篇文章[2]讲的非常详细，建议看原文。（本来想写一下，但觉得太复杂，还是算了）

EXP的执行步骤：

1.Elevate to SYSTEM, otherwise we will not be able to create objects inside \GLOBAL??.2.Create the object directory \GLOBAL??\KnownDlls to mimic the actual \KnownDlls directory.3.Create the symbolic link \GLOBAL??\KnownDlls\FOO.dll, where FOO.dll is the name of the DLL we want to hijack. Remember that what matters is the name of the link itself, not its target.4.Drop the SYSTEM privileges and revert to our administrator user context.5.Create a symbolic link in the current user’s DOS device directory called GLOBALROOT and pointing to \GLOBAL??. This step must not be done as SYSTEM because we want to create a fake GLOBALROOT link inside our own DOS directory.6.This is the centerpiece of this exploit. Call DefineDosDevice with the value GLOBALROOT\KnownDlls\FOO.dll as the device name. The target path of this device is the location of the DLL but I will get to that in the next part.

漏洞的核心在于CSRSS服务在处理RPC函数DefineDosDevice时存在一个逻辑错误，导致在执行关键操作时没有进行impersonate，进而在服务的安全上下文中进行了KnownDLLs目录的操作，最后启动了services.exe这个PPL级别为WinTcb-Light的进程，其加载了KnownDLLs目录里我们伪装的EventAggregation.dll，最终攻击者就可以在services.exe的进程空间里执行任意操作
