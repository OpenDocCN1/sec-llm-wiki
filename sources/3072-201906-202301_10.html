国外某站JWT漏洞挖掘

什么是JWT

JWT一般被用来在身份提供者和服务提供者间传递被认证的用户身份信息，以便于从资源服务器获取资源，也可以增加一些额外的其它业务逻辑所必须的声明信息，该token可直接被用于认证，也可被加密。


JWT的原理

JWT 的原理是，服务器认证以后，生成一个 JSON 对象，发回给用户，就像下面这样。

{"name": "lily","role": "admin","expired": "20180101"}

以后，用户与服务端通信的时候，都要发回这个 JSON 对象。服务器完全只靠这个对象认定用户身份。为了防止用户篡改数据，服务器在生成这个对象的时候，会加上签名。


JWT结构

JWT的结构如下"Base64(Header).Base64(Data).Base64(Signature)"


比如:

AAAAAAAAA.BBBBBBBBB.CCCCCCCCC


JWT提供的安全机制如下：

1. 加密方式 （Encryption）

2. 签名 （Signature）


而保证签名（Signature）完整性的算法有如下几种：

1. RSA

2. HMAC

3. Elliptic curves

4. None


上面加粗的部分是个伏笔

背景

全文假设站点为redacted.com，该网站使用基于 cookie 的身份验证和授权机制来验证服务器端的合法请求。


上图是为了说明问题伪造的包，其中存在用户身份参数“c=1234567”。


挖掘过程

几乎所有的电商站点都有增加，修改和移除用户地址的功能，这个虚拟的站点也不例外。


该站点的两个修改地址的接口如下：


1.在用户个人资料部分（https://www.redacted.com/profile/address）


2. 在完成订单的最后步骤。(https://www.redacted.com /checkout/adv/address/view) —一个隐藏的 JSON 接口。


开发人员一般对比较明显的接口做的校验比较严格，所以理所当然的，第一个接口并没有能利用成功


之后尝试修改第二个接口的customer_id，仍然没有成功


之后不断验证以尝试找到服务器端用来做校验的依据。


最后发现是通过cookie中的如下值来验证session的:


ud= XXXXXXX;c= CUSTOMER_ID;XSSRF-TOKEN= XXXXXXXX;sessid= XXXXXXXXXX;

GET /checkout/adv/address/view HTTP/1.1
