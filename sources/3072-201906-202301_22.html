1 栈溢出原理

我们知道在不考虑GS等编译选项的情况下，函数栈帧的情况如图所示，最简单的栈溢出即利用局部变量覆盖返回地址，从而截获EIP拿到程序的控制权，接下来的两个漏洞都是这一原理

2 MS06-040

该漏洞的触发处是netapi32.dll中的NetpwPathCanonicalize()函数

动态调试

我们先通过POC来定位漏洞指令

  1. #include <windows.h>
  2. typedef void (*MYPROC)(LPTSTR, char *, int, char *, long *, bool);  //定义函数指针

  4. int main() {
  5.     char path[0x320]; 
  6.     char can_path[0x440]; 
  7.     int maxbuf=0x440; 
  8.     char prefix[0x100]; 
  9.     long pathtype=44;

  11.     HINSTANCE LibHandle; 
  12.     MYPROC Trigger;
  13.     char dll[ ] = "./NETAPI32.DLL";   
  14.     char VulFunc[ ] = "NetpwPathCanonicalize"; 
  15.     LibHandle = LoadLibrary(dll); //拿句柄
  16.     Trigger = (MYPROC) GetProcAddress(LibHandle, VulFunc); 
  17.     memset(path,0,sizeof(path)); 
  18.     memset(path,'a',sizeof(path)-2); 
  19.     memset(prefix,0,sizeof(prefix)); 
  20.     memset(prefix,'b',sizeof(prefix)-2); 
  21.     (Trigger)(path,can_path,maxbuf,prefix ,&pathtype,0); 
  22.     FreeLibrary(LibHandle);
  23.     return 0;
  24. }

可以看到此时程序跑飞，EIP已经被控制。我们重新加载程序并在NetpwPathCanonicalize()函数入口处下断点，单步调试

可以从OD中看到，该函数通过wcscpy先复制了一串b到栈中，然后通过wcscat函数将Unicode字符"\"连接在了之后，最后通过wcscat将一串a连接到了之后，此时观察栈中数据可以发现EBP和返回地址都已经被覆盖。继续单步执行程序跑飞

静态分析

通过IDA反编译我们可以看到该函数有两次长度检查，但是用的都是计算宽字节字符的wcslen，也就是意味着我们传入的ASCII字符可以达到0x411 * 2个，这也是漏洞产生原因

exploit布局

从之前的调试可以知道缓冲区起始地址为0x0012F284，函数返回地址为0x0012F6A0，所以exploit的思路就是在程序返回时跳回缓冲区中。观察各个寄存器的值我们发现ecx是指向缓冲区的，所以函数返回地址应该设置为call ecx/jmp ecx指令的地址，通过OD的搜索插件很容易得到相关的地址，如图

3 CVE-2010-3333

该漏洞是Microsoft Word 2003 sp3中的一个栈溢出漏洞，漏洞存在于mso.dll模块中

动态调试与静态分析以及POC构造

打开Microsoft Word 2003 sp3，用windbg附加到进程，然后载入POC

程序崩溃，通过最后一条指令地址和windbg的信息，我们知道它是mso.dll模块中的某个函数，用IDA中找到其所在函数

重新加载word 2003 sp3，附加进程后，在该函数入口下断点

单步步入，逐步来到了漏洞指令处

观察此时寄存器值可以发现eax值和esi所指向的字符串都是我们在POC中可控的，如图

结合最后一条指令，可以知道我们复制到edi的数据和长度都是可控的，而edi此时所指的位置就是在栈中，且距离返回地址0x14个字节（通过windbg算出），所以通过覆盖返回地址可以轻松劫持EIP

如上图EIP被劫持成功，程序已经去执行我们的shellcode了。注意这里之所以在返回地址与shellcode中还有0x14个字节的距离，是因为该函数返回时的指令是ret 14h而我们选择的跳板为jmp esp，程序在jmp esp时会多跳14个字节
