｜相关知识

eBPF (Extended Berkeley Packet Filter) 由 cBPF (Classic Berkeley Packet Filter) 衍生而来，是一项可在内核虚拟机中运行程序的技术。使用eBPF无需修改内核源码，或者插入驱动，对系统的入侵性相对没那么强，可以安全并有效地扩展内核的功能。

eBPF 使用类似 x86 的虚拟机指令，基础指令为 8 字节，其编码格式为：

扩展指令在基础指令基础上增加 8 个字节的立即数，总长度为 16 字节。伪指令是内核代码中定义的方便理解记忆的助记符，通常是对真实指令的包装。

eBPF 寄存器

eBPF 共有 11 个寄存器，其中 R10 是只读的帧指针，剩余 10 个是通用寄存器。

R0: 保存函数返回值，及 eBPF 程序退出值 R1 – R5: 传递函数参数，调用函数保存 R6 – R9: 被调用函数保存 R10: 只读的帧指针

eBPF 整体架构

eBPF程序虽然是有内核的虚拟机负责执行的，但是eBPF程序的编写确实完全由用户定义的，因此这也是之前eBPF模块成为一个理想的内核提权攻击面的根本原因。 eBPF程序通过BPF系统调用，cmd为BPF_PROG_LOAD就可以将eBPF程序发送给内核，还可以通过cmd为BPF_MAP_CREATE系统调用创建一个map数据结构，这个map数据结构就是用户侧运行的程序与内核中运行的eBPF程序进行数据交互的地方。其简要原理图为：

由 https://github.com/torvalds/linux/commit/3f50f132d8400e129fc9eb68b5020167ef80a244 commit 引入32位操作运算，但range_within函数未更新对32位的判断，导致jmp32操作被裁剪，判断结果错误，造成提权漏洞。

漏洞代码：

/* check %cur's range satisfies %old's */
static bool range_within(struct bpf_reg_state *old,
    struct bpf_reg_state *cur)
{
 return old->umin_value <= cur->umin_value &&
        old->umax_value >= cur->umax_value &&
        old->smin_value <= cur->smin_value &&
        old->smax_value >= cur->smax_value;
}

漏洞调用链：

do_check->states_equal->func_states_equal->regsafe->range_within

func_states_equal 函数用于检查两个寄存器的状态是否一致，如果一致，该条路径下就能一直安全地执行到bpf_exit

* Similarly with registers. If explored state has register type as invalid
 * whereas register type in current state is meaningful, it means that
 * the current state will reach 'bpf_exit' instruction safely
 */
static bool func_states_equal(struct bpf_func_state *old,
                              struct bpf_func_state *cur)
{
        struct idpair *idmap;
        bool ret = false;
        int i;

        idmap = kcalloc(ID_MAP_SIZE, sizeof(struct idpair), GFP_KERNEL);
        /* If we failed to allocate the idmap, just say it's not safe */
        if (!idmap)
                return false;

        for (i = 0; i < MAX_BPF_REG; i++) {
                if (!regsafe(&old->regs[i], &cur->regs[i], idmap)) // regsafe 返回true
                        goto out_free;
        }

        if (!stacksafe(old, cur, idmap))
                goto out_free;

        if (!refsafe(old, cur))
                goto out_free;
        ret = true;
out_free:
        kfree(idmap);
        return ret;
}

range_within 只检查了64位的范围，如果新的范围在旧范围内，则返回true。未考虑32位的范围变化，所以可能导致32位的情况下，判断错误。如下：

old:s32_min_value=0x80000000,s32_max_value=0x00003030,u32_min_value=0x00000000,u32_max_value=0xffffffff
cur:s32_min_value=0x00003031,s32_max_value=0x7fffffff,u32_min_value=0x00003031,u32_max_value=0x7fffffff

上述范围在64位情况下，新范围在旧范围内，返回true，但是32位的新范围却不在旧范围内，但漏洞代码却造成新范围的判断结果和旧范围的判断结果一致，认为新范围更窄，是安全的，因此新范围的分支被裁剪了，没有进行判断。

ALU Sanitation机制

ALU sanitation机制一直在进行更新，其目的是为了阻止verifier漏洞的利用，原理是在runtime运行时检查BPF指令的操作数，防止指针运算越界导致越界读写，其实是对verifier静态范围检查起到了补充的作用。

最开始的patch：

    if (insn->code == (BPF_ALU64 | BPF_ADD | BPF_X) ||
            insn->code == (BPF_ALU64 | BPF_SUB | BPF_X)) {
            const u8 code_add = BPF_ALU64 | BPF_ADD | BPF_X;
            const u8 code_sub = BPF_ALU64 | BPF_SUB | BPF_X;
            struct bpf_insn insn_buf[16];
            struct bpf_insn *patch = &insn_buf[0];
            bool issrc, isneg;
            u32 off_reg;

            aux = &env->insn_aux_data[i + delta];
            if (!aux->alu_state ||
                aux->alu_state == BPF_ALU_NON_POINTER)
                continue;

            isneg = aux->alu_state & BPF_ALU_NEG_VALUE;
            issrc = (aux->alu_state & BPF_ALU_SANITIZE) ==
                BPF_ALU_SANITIZE_SRC;

            off_reg = issrc ? insn->src_reg : insn->dst_reg;
            if (isneg)
                *patch++ = BPF_ALU64_IMM(BPF_MUL, off_reg, -1);
            *patch++ = BPF_MOV32_IMM(BPF_REG_AX, aux->alu_limit - 1);
            *patch++ = BPF_ALU64_REG(BPF_SUB, BPF_REG_AX, off_reg);
            *patch++ = BPF_ALU64_REG(BPF_OR, BPF_REG_AX, off_reg);
            *patch++ = BPF_ALU64_IMM(BPF_NEG, BPF_REG_AX, 0);
            *patch++ = BPF_ALU64_IMM(BPF_ARSH, BPF_REG_AX, 63);
            *patch++ = BPF_ALU64_REG(BPF_AND, BPF_REG_AX, off_reg);

alu_limit 即最大绝对值，就是该指针可以进行加减的安全范围。在该指令之前必须加上如下指令，off_reg表示与指针作运算的标量寄存器，BPF_REG_AX是辅助寄存器。

上述patch为了保证off_reg在合理范围[0, alu_limit-1]内，一旦超过该范围就会认为发生了越界，将off_reg置为0。

例如令alu_limit=8 时，此时map指针相加的偏移规定的范围为[0,7]，超过该范围就会将偏移置0.

绕过缓解

绕过上述patch的方法只需令alu_limit=0，那么得到的范围就会是[0,0xffffffff]，map指针实际相加的偏移可以是任意值，绕过越界判断。

但早期eBPF又引入了三个补丁用于修复ALU的侧信道安全问题，但同时也进一步检查了越界问题。

（1）限制指针加减 偏移只能在map大小范围内

https://lore.kernel.org/lkml/20210322121920.198372959@linuxfoundation.org/

*patch++ = BPF_MOV32_IMM(BPF_REG_AX, aux->alu_limit);
*patch++ = BPF_ALU64_REG(BPF_SUB, BPF_REG_AX, off_reg);
*patch++ = BPF_ALU64_REG(BPF_OR, BPF_REG_AX, off_reg);
*patch++ = BPF_ALU64_IMM(BPF_NEG, BPF_REG_AX, 0);
*patch++ = BPF_ALU64_IMM(BPF_ARSH, BPF_REG_AX, 63);
*patch++ = BPF_ALU64_REG(BPF_AND, BPF_REG_AX, off_reg);

这种绕过只需要累加在map大小范围内的偏移，使其偏移总和能够越界即可。

       BPF_ALU64_IMM(BPF_MUL, BPF_REG_0, 0x110), //r0检查为0，实际为0x110

https://github.com/torvalds/linux/commit/7fedb63a8307dda0ec3b8969a3b233a1dd7ea8e0

表示如果该寄存器在运行时超出边界，则指针运算不会使用该寄存器，导致上述绕过失效。

利用栈偏移进行绕过，我们先开辟一个栈空间，通过漏洞混淆偏移，让检查时为-0x60，实际为-0x50，并如下图所示，在fp-0x50处存入map ptr指针，在fp-0x60处存入用户传入的数据。这样我们取用户数据时实际是将map ptr 取出，达到了泄露指针的效果。反之如果fp-0x50存入的是指针，fp-0x60存入用户数据，那么后续就会将用户数据当成指针进行操作，可以实现任意地址的读写操作。

（3）限制指针加减 偏移为立即数时，实际运行取检查时立即数的大小

https://git.kernel.org/pub/scm/linux/kernel/git/bpf/bpf.git/commit/?id=801c6058d14a82179a7ee17a4b532cac6fad067f

在runtime时会用立即数替换掉 verifier 认定为常数的寄存器。例如，BPF_ALU64_REG(BPF_ADD, BPF_REG_2, EXPLOIT_REG) ，EXPLOIT_REG被verifier认定为0，但运行时为1，则 将该指令改为 BPF_ALU64_IMM(BPF_ADD, BPF_REG_2, 0)，导致上述绕过失效。

这些补丁严格检查了指针越界的情况，使得指针和混淆的数相加后根据实际运行时的值来检查而不是verifier时的值，这样依靠栈偏移混淆指针的做法也失效了。我们的绕过思路如下：

Poc如下：

        BPF_JMP_IMM(BPF_JEQ, BPF_REG_0, 1, 2),   //r0=1 check -> actual:0x0
        BPF_ALU64_IMM(BPF_ADD, BPF_REG_7, -0x110), 
        BPF_JMP_IMM(BPF_JA, 0, 0, 3),
        BPF_ALU64_IMM(BPF_ADD, BPF_REG_7, 0x110), 
        BPF_MOV64_IMM(BPF_REG_0, 17),
        BPF_JMP_IMM(BPF_JGE, BPF_REG_0, 10, -5),
        ......

检查过程如下：

  // 根据漏洞，检查时r0=1, 实际为0 
  31: (15) if r0 == 0x1 goto pc+2 // 所以检查时，根据r0=1，进入分支
  32: (07) r7 += -272                               <-----
  33: (05) goto pc+3                                      |
  34: (07) r7 += 272  //<--- r7= r7+0x110                 |  
  35: (b7) r0 = 17    //<----                             |
  36: (35) if r0 >= 0xa goto pc-5 // 跳转到32，r7=r7-0x110 -
      
  // 所以检查时到这一步，r7还是之前的map_ptr，下面的运算没有问题
  37: (79) ......

检查阶段的执行流程如下，首先r0被认为是1，则直接跳到指令【34】，而【32】和【33】指令被认为是不可能执行的（dead code），变成goto -1。之后通过指令【36】跳转回去执行流程，又将之前的dead code ”激活“，但此时压入栈中要检查的状态是从指令【36】跳转过来的，而不是从指令【30】顺序执行下来的。整体检查过程来看：r7为map 指针，但在检查流程中只是减去0x110，又加上0x110，其值没有发生变化。

实际运行时：

  31: (15) if r0 == 0x1 goto pc+2 // 实际运行时，根据r0=0，进入分支
  32: (07) r7 += -272    // r7= r7-0x110                           
  33: (05) goto pc+3     //  -------------------      
  34: (07) r7 += 272                           |
  35: (b7) r0 = 17                             |
  36: (35) if r0 >= 0xa goto pc-5              |
  37: (79) ......               //  <----------   // 直接跳到这一步，此时r7=map_ptr-0x110

实际运行时，r0为0，进入指令【32】，此时指令【32】的状态不为goto -1，为从指令【36】跳转过来的状态，可以通过检查， 由此减去0x110，获得越界指针r7，就可以正常进行越界读写，完成利用。

然而eBPF之后又引入了新补丁将不可能执行的分支也检查了，不设置成goto -1，导致这一绕过方法也失效了。而最近绕过的方法是CVE-2022-23222利用中使用到的，通过BPF_FUNC_skb_load_bytes_relative (bpf_skb_load_bytes ) 这个 helper 函数实现从 sk_buff 里拷贝数据到栈上，该操作不会触发 ALU sanitation，所以用假的 len 欺骗静态验证器即可。
