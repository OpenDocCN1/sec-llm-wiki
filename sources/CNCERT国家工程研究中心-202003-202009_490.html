1、C&C木马样本分析存在的挑战

木马在网络安全领域借指一类恶意程序，这一程序能够在目标主机或其他类型系统中执行，以便攻击者占领目标并获取其控制权。这一类程序往往伪装成合法程序，很难被计算机系统的使用者发现和识别。木马根据不同的用途会集成各不相同的恶意功能，例如键盘监控、用户帐号窃取、文件窃取等。但不论木马具备什么功能，在正常工作过程中，必然要与外界进行通信以便传输数据。

C&C即Command and Control，即命令和控制协议。木马在工作过程中与远程操作人员开启的控制端或者其他“同伴”之间通信的协议，这一协议设计的初衷是实现木马远程控制指令下达。木马往往采用C/S通信模型进行通信。即木马作为服务器端或者客户端软件，等待远程控制端连接或者主动连接远程控制端。被控系统内的木马程序通过C&C协议与控制者通信，从而实现对于目标主机的控制。

在实现过程中，木马C&C协议主要有以下几个特点：常用协议是标准协议，有公开的标准，但是木马协议没有公开标准，属于私有协议；木马协议通常要考虑到利用尽量少的资源，所以设计的比常用的应用协议更为简单和髙效，往往采用非文本协议传输，对直接协议分析造成了很大的困难；虽然木马使用了私有协议，但是由于对抗防火墙等网络防御系统，木马有时会选用特定的标准协议对其C&C协议进行封装，达到难以被识别的效果。

通过以上我们可以发现一个恶意软件的核心功能都在C&C部分设计实现，因此木马二进制样本分析最困难也是最重要的部分就是木马的C&C协议逆向。由于我们运行木马无法提供正确的控制指令，只能执行一部分C&C指令，导致无法覆盖样本所有的执行空间。特别是在工业控制系统中，由于无法提供木马运行的工控环境，样本无法执行。因而我们借助动态符号执行来分析代码，以协助人工分析，尽快明白C&C木马功能与原理，找出对应的防护手段。

2、动态符号执行原理

符号执行的关键思想就是，把输入变为符号值，那么程序计算的输出值就是一个符号输入值的函数。简而言之，就是一个程序执行的路径通常是true和false条件的序列，这些条件是在分支语句处产生的。在序列的位置如果值是true，那么意味着条件语句走的是then这个分支；反之如果是false就意味着程序执行走的是else分支。

那么，如何形式化地表示符号执行的过程呢？程序的所有执行路径可以表示为树，叫做执行树。接下来我们就以一个例子来阐述通过符号执行遍历程序执行树的过程。

左边的代码中，testme()函数有3条执行路径，组成了右图中的执行树。直观上来看，我们只要给出三个输入就可以遍历这三个路径，即图中绿色的x和y取值。符号执行的目标就是能够生成这样的输入集合，在给定的时间内探索所有的路径。

为了形式化地完成这个任务，符号执行会在全局维护两个变量。其一是符号状态σ，它表示的是一个从变量到符号表达式的映射。其二是符号化路径约束PC，这是一阶公式，用来表示路径条件。在符号执行的开始，符号状态σ会先初始化为一个空的映射，而符号化路径约束PC初始化为true。σ和PC在符号执行的过程中会不断更新。在符号执行结束时，PC就会用约束求解器进行求解，以生成实际的输入值。这个实际的输入值如果用程序执行，就会走符号执行过程中探索的那条路径，即此时PC的公式所表示的路径。

经典的符号执行技术并不真实的执行目标测试程序，而是通过分析程序指令语义，以符号值模拟执行的方式来进行程序分析，这导致符号执行在诸多场景下极其占用计算机的计算资源和存储资源，严重限制了符号执行技术的发展和实际应用的效率。动态符号执行则改进了传统经典的符号执行技术，在符号执行分析的过程中加入了具体执行的机制，从而使得符号执行技术能够在动态实际执行的过程中进行应用，也在一定程度上减少了模拟执行过程中需要消耗的计算资源和存储资源。

动态符号执行的本质是将实际执行的路径信息与符号执行技术相结合，用具体的输入数据执行程序，并在程序运行的过程中，通过程序插桩的手段收集路径分支处的约束条件，然后对收集到的约束条件集合中的某一个进行取反操作，再调用约束求解器对取反后的约束条件集合进行求解，从而生成另一条执行路径下的测试用例并重复上述过程直至遍历测试对象的全部执行路径。

3、动态符号执行工具angr

由利福尼亚大学圣塔芭芭拉分校开发的二进制程序漏洞挖掘平台，系统架构与BAP类似，由python开发，利用了VEX中间语言，使用符号执行引擎，是较完整的程序分析平台。angr在实际应用过程中展现出来的分析和挖掘漏洞的效果较好，并多次在各类信息安全竞赛和自动化漏洞挖掘挑战赛中表现出色。我们以此为工具，以一个具体的例子来介绍基于符号执行的恶意代码协议分析方法。

4、分析实例

由于符号执行工具angr特别复杂，为了弄明白怎样利用它来进行安全分析。我们用C语言编写一段代码，并把它编译为二进制程序。代码如下所示：

#include <stdio.h>#include <stdlib.h>#include <string.h>#include <time.h>// Type#define T_FILESYSTEM 0x64bbe900#define T_CMD 0xee697065// File System Order#define FSO_CREATE 0xaff80c17#define FSO_WRITE 0xc6e6ef6b#define FSO_DELETE 0x1f01d4d4#define FSO_READ 0x14c47592// Object Type#define OT_FILE 0x6e0978af#define OT_FOLDER 0x690c6b0e// Cmd order#define CO_BASH 0x698b87a6#define CO_NEW_USER 0xc678c002// User#define U_CURRENT 0xe8723ad9#define U_ROOT 0xfe42ed2btypedef struct {    int type;    int fs_order;    int object_type;    int cmd_order;    int user;    char args[256];} c2_order;c2_order c2_resp;
void call_home(){    // Create foder    c2_resp.type = T_FILESYSTEM;    c2_resp.fs_order = FSO_CREATE;    c2_resp.object_type = OT_FOLDER;    strcpy(c2_resp.args, "/home/931/._ssh");}void exec_order(){    if (c2_resp.type == T_FILESYSTEM) {        if (c2_resp.fs_order == FSO_CREATE) {            if (c2_resp.object_type == OT_FILE) {                printf("Creando fichero: %s\n", c2_resp.args);            } else if (c2_resp.object_type == OT_FOLDER) {                printf("Creando carpeta: %s\n", c2_resp.args);            }        } else if (c2_resp.fs_order == FSO_WRITE) {            printf("Escribiendo fichero: %s\n", c2_resp.args);        } else if (c2_resp.fs_order == FSO_DELETE) {            if (c2_resp.object_type == OT_FILE) {                printf("Borrando fichero: %s\n", c2_resp.args);            } else if (c2_resp.object_type == OT_FOLDER) {                printf("Borrando carpeta: %s\n", c2_resp.args);            }        } else if (c2_resp.fs_order == FSO_READ) {            if (c2_resp.object_type == OT_FILE) {                printf("Leyendo fichero: %s\n", c2_resp.args);            } else if (c2_resp.object_type == OT_FOLDER) {                printf("Leyendo carpeta: %s\n", c2_resp.args);            }        }    } else if (c2_resp.type == T_CMD) {        if (c2_resp.cmd_order == CO_BASH) {            if (c2_resp.user == U_CURRENT) {                printf("Ejecutando bash como usuario actual: %s\n", c2_resp.args);            } else if (c2_resp.user == U_ROOT) {                printf("Ejecutando bash como root: %s\n", c2_resp.args);            }                    } else if (c2_resp.cmd_order == CO_NEW_USER) {            printf("Creando usuario: %s\n", c2_resp.args);        }    }}int main(int argc, char *argv[]){    call_home();    exec_order();    return 0;}

前两个参数用来限定angr进行符号分析的范围，以免分析整个二进制文件而浪费时间。第三个参数包括一系列地址，这些地址代表我们比较感兴趣的路径。第四个参数表示服务端接收数据的buffer。他代表随着那个数据的不同，目前程序会进入由参数3标记的执行路径。

从第一张图的反汇编代码可以看到我们分析的目标代码起始地址为0x0804844D,这个用来设置参数START_ADDR。我们需要跟踪的目标地址保存在FIND_ADDRS列表中。例如0x08048483处的汇编指令“push str.Creando_file: __ s”被添加到列表中。BUFF_ADDR表示接收的缓冲区变量。最后运行脚本可以得到如下的结果：

第一个节点表示如果C&C想要执行代码块，必须给它输入“00 E9 BB 64 D4 D4 01 1F AF 78 09 6E 00 00 00 00 00 00 00 00”。实际上这个功能代码在0x80485050处，下面的表示到达这个节点的路径约束。需要说明的是“angr”运行在指令层，所以输出的indexs都表示为位。他表示输入buffer的大小为20个字节 ，也就是20*8=160bit（c2_resp_0_160[159:128]）。

第一个约束表示输入的第四个DWORD必须包含0x64bbe900(C代码中的T_FILESYSTEM)，但是第三个字节却有三个约束：它不等于0xaff80c17和0xc6e6ef6b，必须包含 0x1f01d4d4。实际上只需要第三个约束就可以了。但是angr在进行符号执行时，需要避免进去其他的分支（if语句），而仅有第三个约束并不能阻止其进入其他的分支。我们回去看C代码，就会发现第三个字节表示“fs_order”，它首先与常量FSO_CREATE和FSO_WRITE进行比较，然后与FSO_DELETE比较，当两者相等的时候才进入deltion分支。

这些信息可以帮助我们来理解C&C的通信协议，在动态分析的时候可以伪装成攻击者，设定特定的攻击指令，调试特定的代码块。angr也有助于我们在分析恶意样本的时候遍历C&C的执行空间。
