# 整形溢出漏洞

在计算机中，整形是一个特定的变量类型。经过不同的CPU架构的编译器处理后，整形和指针所占字节一般是相同的。因此，在32位系统中，一个整数占32位；而在64位系统中，一个整数占64位。 但是，仅这样做是不够的。因为这样做无法表示负数，所以需要引入一种机制，即通过一个变量的最高位来决定数值的正负。如果最高位置1，那么这个变量就解释为负数；如果只置0，那么这个变量就解释为正数。在高级语言中通常分为有符号和无符号正数型。 一般开发人员在写程序时，对整形数仅考虑范围，不考虑安全需求。对不同用途的整形数，其安全要求也不相同。例如，在32位系统中，无符号整型数（unsigned int）的范围是0~0xffffffff，不仅要保证用户提交的数据在此范围内，还要保证对用户数据进行运算和存储后，其结果仍然再次范围内。在实际应用中，开发人员可能会忽略这个问题。把它当做一个有符号整形数据（int）使用。 整形溢出从成因的角度可以分为三大类，分别是存储溢出、计算溢出和符号问题。

## 存储溢出

存储溢出是最简单的一类，他是由不同的数据类型存储整形数造成的。

```
1.  `int len1=0x10000;`
    
2.  `short len2=len1;`
    
```

由于len1和len2的数据类型的长度不一样，len1是32位的，len2是16位的，在进行赋值操作后，len2无法容忍len1的全部位，导致与预期不一致，即len=2等于0。 同样，把短类型变量赋给长类型同样存在问题，如: short len2=1; int len1=len2; 以上代码的执行结果并非总是如预期那样使len1等于1，在很多编译器编译的程序时，结果会使len1等于0xffff0001，这实际上是一个负数。当len1的初始值等于0xffffffff时，把short类型的len2赋给len1，只能覆盖其低16位，这自然造成了安全隐患。

## 运算溢出

运算过程中造成整数溢出是常见的情况，有很多著名的漏洞都是由这种整形数溢出导致的。起原理就是在对整形数变量进行运算的过程中没有考虑其边界范围，造成运算后的数值超出了其存储空间，如：

```
1.  `bool func（char *userdata, short datalength）`
    
2.  `{`
    
3.  `    char *buff;`
    
4.  `    ......`
    
5.  `    if(datalength != strlen(userdata))`
    
6.  `    return false;`
    
7.  `    datalenght = datalenght*2;      //short类型运算超界将使下面的拷贝发生溢出`
    
8.  `    buff = malloc(datalenght);`
    
9.  `    strncpy(buff,userdata,datalength)`
    
10.  `}`
     
```

## 符号问题

整数型分为有符号整数和无符号整数，因此符号问题也可能造成安全方面的隐患。在一般情况下，对长度变量都要求使用无符号整形数，如果开发人员忽略了符号，那么在进行安全检查时就可能出现意想不到的情况。符号一起的溢出，最典型的例子是eEye发现的Apache HTTP Server分块编码漏洞。

分块编码（chunked encoding）传输方式是HTTP1.1中定义的Web用户向服务器提交数据的一种方式，当服务收到chunk编码方式的数据时会分配一个缓冲区来存放数据，如果提交的数据大小未知，那么客户端会以一个协商好的分块大小向服务器提交数据。

Apache服务器默认提供了对分块编码的支持。Apache使用了一个有符号变量来存储分块长度，同时分配了一个固定大小的栈缓冲区来分块数据。处于对安全的考虑，再将分块数据复制到缓冲区之前，Apache会对长度进行检查，如果分块长度大于缓冲区长度，Apache将最多只复制缓冲区的长度，否则将根据分块长度来复制数据。然而，在进行上述检查时，没有将分块长度转换成无符好型来比较，因此，如果攻击者将分块长度设置成负值，就会绕过上述安全检查，Apache会将一个超出（至少0x80000000字节）的分块数据复制到缓冲期中，而这会造成缓冲区溢出。

整形溢出的产生是由赋值类型的大小不匹配造成的。防范整形溢出，需要开发人员养成良好的安全编程习惯，严格检查变量的赋值。
