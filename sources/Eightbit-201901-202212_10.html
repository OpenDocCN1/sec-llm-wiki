0x1 内核UAF

内核UAF的原理与应用层UAF相同，残留的堆指针可以再堆块被释放后依旧允许我们对堆块进行操作。与应用层的UAF不同，内核UAF不再致力于通过堆操作实现任意位置堆块的申请，而是尝试让某些结构正好落在我们释放的堆块空间上，从而实现对该结构的控制。想要理解和掌握内核UAF的基础利用，首先需要对内核堆分配和回收机制有清楚的认识，Linux内核堆分配的算法采用伙伴算法和slub算法，其中伙伴算法以页为单位，但由于大多数情况下我们需要的空间并不以页为单位，多数情况是几个或几十个字节，于是需要另一套系统完成对小内存的管理，即slub系统，这里就不解释这个slub系统，如果不清楚的可以参考linux 内核 内存管理 slub算法（https://blog.csdn.net/lukuen/article/details/6935068）。

0x2 tty_struct劫持

内核UAF一般会有两种利用思路，这里我们首先介绍第一种，uaf控制 tty_options结构。

tty_operations，即tty设备操作关联函数表。在 /dev下有一个伪终端设备 ptmx ，在我们打开这个设备时内核中会创建一个 tty_struct结构体，与其他类型设备相同，tty驱动设备中同样存在着一个存放着函数指针的结构体。

  1. struct tty_struct {
  2.         int     magic;
  3.         struct kref kref;
  4.         struct device *dev;
  5.         struct tty_driver *driver;
  6.         const struct tty_operations *ops;
  7.         int index;
  8. //......

因此，如果我们可以通过 UAF 劫持 /dev/ptmx这个设备的 tty_struct结构体与其内部的 tty_operations函数表，那么在我们对这个设备进行相应操作（如write、ioctl）时便会执行我们布置好的恶意函数指针，道理类似于got表劫持。其中 tty_operations函数表如下：

利用UAF，我们有如下思路：

明显在ioctl中存在uaf，在write函数中存在溢出。因此有如下利用思路：

  1. 打开LKM申请的设备，调用ioctl申请0x2e0大小的堆空间再释放，形成UAF，这里之所以申请0x2e0是为了和 tty_struct匹配；

  1. 打开ptmx，内核通过 alloc_tty_struct() 分配 tty_struct的内存空间，此时该空间即是之前我们释放的堆空间

  2. 定义一个 fake_tty_operations，写入提权函数地址

  3. 使用第一次打开设备获取的指针直接修改 tty_struct，因为 tty_struct[3]->tty_operations，而 tty_operations[12]->tty_operations.unlocked_ioctl

  4. 执行call ioctl，最终效果为 ioctl->unlocked_ioctl->get_root

这里要注意需要设置ptmx权限令普通用户可以访问，可以在init文件中参考以下代码：

  1. mkdir -p /dev/pts
  2. mount -vt devpts -o gid=4,mode=620 none /dev/pts
  3. chmod 666 /dev/ptmx

于是有如下exp：

对于cred结构体，如果uid,gid为0的话，就等于获得root权限，那么想要利用uaf修改cred就需要吧cred结构变成堆块。当fork一个子进程时，内核会给cred分配空间，如果这块堆空间是我们释放之后区域，我们也就获得了cred结构体的控制权。于是有如下思路：

  1. fd1打开申请的设备；

  2. fd1申请0xa8的堆块，再释放掉，这里0xa8正好是cred结构大小；

  3. fork一个进程，则slub系统会把之前device_buf分配给cred；

  4. 利用fd1残留指针则可以实现对该空间的写入，将其gid和uid置0即可实现提权到root；
