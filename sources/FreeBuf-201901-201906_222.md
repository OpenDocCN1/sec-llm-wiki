# Nmap在VMware NAT网络下探测主机存活误报的分析

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MjM5NjA0NjgyMA==&mid=2651074626&idx=4&sn=8bf31db325f631ec4d4e6a4400100709&chksm=bd1fa2c98a682bdfba5fc168ac027b7cbf2be2e0c4e148c3b17f372e124885475e12fbed1a05&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=MjM5NjA0NjgyMA==&mid=2651074626&idx=4&sn=8bf31db325f631ec4d4e6a4400100709&chksm=bd1fa2c98a682bdfba5fc168ac027b7cbf2be2e0c4e148c3b17f372e124885475e12fbed1a05&scene=27#wechat_redirect)

## 起因

**昨天，在某安全交流群，看到关于Nmap扫描的讨论，对一个段做主机存活扫描，发现主机全部存活。**

![](../Images/772353f364f8cadddb487659421b2710.png)

扫描源主机是安装在虚拟机上的Kali，网络连接为NAT模式，使用-sP参数对192.168.0.0/24网段扫描，探测存活主机，返回结果为256个IP全部在线，而实际情况是该网段只有几个IP存活，使用Ping命令，其它不在线的IP是Ping不通的。

![](../Images/ae8bf54c3a91744c6335fa3a94a450df.png)

## 分析

难道是Nmap出错了？带着这个疑问，我查阅了Nmap的官方文档，Nmap使用`-sn`参数指定只做主机存活发现（以前的一些版本中使用`-sP`，新版本中`-sn`和`-sP`都可以使用，为同一参数），不做端口扫描。Nmap默认的主机存活发现使用了以下四种方式：

```none
ICMP echo requestTCP SYN to port 443TCP ACK to port 80ICMP timestamp request
```

只要其中一个主机存活的特征存在，Nmap判断为主机存活。

Linux下默认Ping命令使用的ICMP echo请求，现在Ping不通，那第一种请求是没有主机存活特征的，问题可能在后面的三种请求。

抓个包分析吧。

![](../Images/6445636966d2669144fb03b9bb8a04f4.png)

扫描源IP为10.10.10.128，筛选了其中一个不存在的IP 192.168.0.10。ICMP echo请求ICMP timestamp请求没有响应，但奇怪的是，到80端口的ACK请求，有一个RST标志的响应，窗口大小是32767。

正常情况下，数据包发送到一个不存在的IP，不会收到任何响应。

TCP连接端口未监听、请求超时、异常关闭等几种情况会发送RST标志的响应。IP存在，但端口关闭，收到ACK标志的包时，会返回一个RST标志的包，内容为Seq=1，Win=0，Len=0。

这里返回了一个RST标志的包，而且窗口大小不为0，Nmap认为该端口开放（参考Nmap的TCP Windows Scan），也就是这个包导致了Nmap对主机存活的误判断。这个包是哪来的呢？网络结构很简单，除了VMware的NAT外，没有其它网络设备，说明这个包是NAT返回的。

## 解决

现在已经知道了引起Nmap误判断的原因是VMware的NAT，那用什么方法来避免呢？**方法一：**只使用ICMP echo请求探测（-PE）探测主机时，添加-PE参数，nmap只发送一个ICMP echo请求。

```none

nmap -sn -PE -n 192.168.0.0/24
```

现在可以扫描出准确的主机存活信息了。

![](../Images/70aed8e0f842eb716316826902480830.png)

> `-n`参数禁用域名解析，避免浪费大量实在在域名解析等待上。

过滤其中一个存活的IP192.168.0.102，Nmap发送一次IMCP echo请求，收到102的ICMP响应后，判断主机存活，不在发送其它数据包。

![](../Images/948f8e820a1e95d75e0f3741dda64387.png)

不存活的IP192.168.0.106，发现两次ICMP echo请求，仍未收到106的ICMP响应，则判断为主机不存活。

![](../Images/595bc538206af61a16ee485643a9723c.png)

不过这种方式存在一个问题，Nmap最多发送两次ICMP echo请求，主机禁Ping或者丢包时造成漏报。

**方法二：**VMware虚拟机网络连接方式改为桥接

既然问题是VMware的NAT引起的，那就索性不用NAT了，改成桥接，这也是VMware官方的建议。

![](../Images/032138d5a6acf2c151cf29cf6853c303.png)

其实，VMware网络连接使用桥接模式，好处不只是解决了Nmap对主机存活的误判断，也避免了无法traceroute和操作系统判断不准确的问题，可以直接创建反弹shell监听端口，网络性能上也优于NAT。

影响操作系统判断的原因，这里提一下，经过VMware NAT返回的数据包，TTL永远是128，即使对方操作系统是Linux。

![](../Images/27e1eace05cd05f7079da28e37aa3aa5.png)

下图是两种网络连接模式，使用`-O`参数探测操作系统是的结果对比。

![](../Images/2a477bcd04baf49e191f63fd0c6dc091.png)

所以，作为渗透测试的虚拟机，还是直接用桥接网卡吧。
