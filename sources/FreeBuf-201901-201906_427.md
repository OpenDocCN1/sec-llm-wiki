# ES文件浏览器CVE-2019-6447漏洞分析

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MjM5NjA0NjgyMA==&mid=2651073610&idx=2&sn=4d4f2e4a710b6451ebe2a55a25877273&chksm=bd1fbec18a6837d79fe8e0648f4807deaa076bf0a8fdb8f6d2cacd29c793d2dee4a707c6135a&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=MjM5NjA0NjgyMA==&mid=2651073610&idx=2&sn=4d4f2e4a710b6451ebe2a55a25877273&chksm=bd1fbec18a6837d79fe8e0648f4807deaa076bf0a8fdb8f6d2cacd29c793d2dee4a707c6135a&scene=27#wechat_redirect)

## 漏洞名称

> ES File Explorer Open Port Vulnerability - CVE-2019-6447

## 漏洞简介

**ES文件浏览器在启动时创建了一个HTTP服务器，在本地打开了59777端口。攻击者通过构造指定的payload可以获取用户手机文件，安装apk等操作。**

## 影响范围

4.1.9.7.4 and below（部分版本可能不支持，也可能和应用市场有关）

## 漏洞分析

  

从fs0c131y所给出的信息来说CVE-2019-6447影响的ES应用版本为4.1.9.7.4以下，但是在某些版本的应用该漏洞却无法利用，例如从华为和google play商店下载的ES就无法顺利复现该漏洞，向59777端口发送payload一直会回复500 ERROR报错，下面将详细对该漏洞进行分析。

### 4.1.9.4版本应用分析

以下是选择了4.1.9.4版本的ES文件浏览器进行了分析，该版本ES能够成功利用该漏洞。

![](../Images/300f58472e8cc73864ea36aa2cd95aa9.png)

首先对APK解包后发现存在三个DEX文件。

![](../Images/aaf045e03fc7d9ecf637f983858167e6.png)

先简单看了下lib中的库发现应用没有加壳，用grep筛查以下59777确定相关代码可能在classes2.dex中。

把classses2.dex反编译后，全局搜索command发现存在漏洞的类在com/estrongs/android/f/a之中,而触发漏洞的函数为com/estrongs/android/f/a.a。

![](../Images/db7e4380d7c0902f5e5e2c6d1ef92b17.png)

简单看下来a.class,b.class,c.class可能都和该漏洞的服务相关，其中a.class继承了c.class。

![](../Images/b0c5f02512a4422153d91c94ac0f5fcf.png)

![](../Images/79682f392346864b55b6ee565ad8864d.png)

下面来看下整个漏洞的触发过程，由于混淆代码不管是丢进jeb中还是smali阅读起来都比较费力，为此我们可以先动态的将程序跑一边后记录trace，分析android trace文件来查看函数调用栈（利用TraceReader读取）。

记录trace的方法如下：

![](../Images/ac4b6854bef9c09918a75ee6f2dc4b56.png)

![](../Images/289600eb86088fa698a87ed1d9e9da4c.png)

在DDMS上成功打开Trace之后，我们就要去构造payload去触发该漏洞，漏洞具体利用payload见github（https://github.com/fs0c131y/ESFileExplorerOpenPortVuln）。

  

```none
curl --header "Content-Type: application/json" --request POST --data "{\"command\":getDeviceInfo}" http://192.168.13 7.10:59777 -vvv
```

把tracer文件丢到TraceReader查看调用栈，可以发现程序进入com/estrongs/android/f/c$a.run()V来处理了我们的请求，注意这里的类的实例化对象其实是a.class而不是c.class。：

![](../Images/96489b35fc415995d3e9d8f89f3f67a0.png)

首先接受socket然后读到buffer中提取数据

![](../Images/e206e04ce931de0f68784aaf60f77217.png)

然后判断是不是post数据，如果是post请求则对content-type进行解析，当所有的前置解析完成后最后程序会来到label\_189处

![](../Images/a13becacf49634f31fe41af8e7d431e9.png)

label*189中，执行了v2*7 = this.a.a*parse*url*other*data(v9, v10, v11, v6, v7);来进一步解析并执行相应的command。

![](../Images/05696c2a9a6e8e24d2c40f631a62fc4c.png)

这里有一个问题，如果JEB直接双击来跟踪函数会跳转到自己类中的函数，而实际真正调用的是a.class(com/com/estrongs/android/f/a)中的函数a*parse*url*other*data（这里我对混淆函数名重命名了实际上原本的函数名是a）。

下图是JEB错误跳转到函数的位置，实际上我们应该分析的是a.class中的a*parse*url*other*data：

![](../Images/a2eb0e1723a7109c11fb42a1573b32eb.png)

继续追踪下去来到就来到了我们一开始漏洞触发的地方（com/estrongs/android/f/a.a）：

![](../Images/43ba0270ecc6b809c39bd873c4c373d7.png)

关于这个地方的分析其实有很多文章以及做过了，这里就不再过多提及了。

解析对应的command调用对应的功能函数后返回json：

![](../Images/f306d2dd76a777363df251e1cf53989c.png)

最后进入com/estrongs/android/f/c$a.a(Ljava/lang/String;Ljava/lang/String;Ljava/util/Properties;Ljava/io/InputStream;)V将response写回。

![](../Images/c1e41187c3ef666be60b1255057ea182.png)

该函数将输出的结果写入到OutputStream中然后将其返回。 ![](../Images/d640baaca9fe1fd86329e089e07c544b.png)

该ES版本整个漏洞的触发流程大致就如上所示。

这里有一个需要注意的地方，如果是不存在漏洞的ES应用v2\_7是为null的也就会进入this.a("500 Internal Server Error", "SERVER INTERNAL ERROR: Serve() returned a null response.");中，这也是很多应用市场上的ES应用都会到报500错误的原因。

### 4.1.6.6.1版本应用分析

以下将对4.1.6.6.1版本ES文件管理器进行分析，该版本的ES文件管理器没有顺利触发漏洞。

![](../Images/e325954a47e2e373e8a23a850056947f.png)

直接curl个看看，500报错了。

![](../Images/c91bce1366086d5f19fa36754537370d.png)

拆包静态看一遍，代码基本上还是在f包中，但是多了很多其他的类，a.class依然是ESHttpServer实现的地方。

![](../Images/466088032005a6a7c4c51317b6f0314e.png)

![](../Images/8ddded896f7c65108d560c6beaeeba73.png)

再curl一个包抓取一下调用栈。

```none
curl --header "Content-Type: application/json" --request POST --data "{\"command\":getDeviceInfo}" http://192.168.0\. 122:59777 -vvv
```

![](../Images/45e1e3bc2d18bfbad7dd817510b928c4.png)

错略比对发现在这个版本的ES中多了一些函数，可能是做了某一些的校验逻辑。

静态分析代码，发现前面的逻辑和之前app差不多，但是在执行完com.estrongs.android.f.h.a(Ljava/lang/String;Ljava/util/Properties;)V后又调用了bJ。

![](../Images/594a21d90b0915e5bd527e6c9fa5f88c.png)

![](../Images/a3b1031a8447005b003bf69667fd6cb0.png)

跟入bJ，bJ验证了了url并且ap.a()方法检测当前环境是否处于WIFI环境下。

![](../Images/356ce62a64eba8a7d5a7d97db9d307f9.png)

![](../Images/faed3c223d3e2874b0dd37a2a1cdac3e.png)

继续往下跟踪，我们来到问题点!bp.q() || !f.e(v8)) && !f.a(v8, v2*5)这里返回了true导致flag*object为null值所以服务器返回了500。

![](../Images/591a7cb5b56a94b1a50d85d8072d32b2.png)

bq.q()为true或者f.e以及f.a为true才能进入逻辑

跟踪进入bq.q()，要满足bp.p()和cw.e()都为true。

而FexApplication.a().getSystemService("uimode").getCurrentModeType() == 4成立的时候bp.p()才能为true，根据官方文档4的uimode为UI*MODE*TYPE\_TELEVISION。

![](../Images/61f77f38b6f60176f9fca257bcf72fd7.png)

![](../Images/ffab6f10ea988d9dee288a3eb08ef3c1.png)

在cw.e中需要满足一定的界面长宽需求

boolean v0\_1 = Math.sqrt(Math.pow((((double)v0.heightPixels)) \* 1 / (((double)v0.densityDpi)), 2) + Math.pow((((double)v0.widthPixels)) \* 1 / (((double)v0.densityDpi)), 2)) >= 20 ? true : false;

![](../Images/b9a0492359168231c2fbd5b4db30b237.png)

而另外的f.e(v8)，f.a(v8, v2\_5)函数则负责校验了我们的ip。

![](../Images/03958e4600fecaa8db4fc7524be8e9c3.png)

此外存在另外一种情况是当我们的ip为127.0.0.1时候flag\_object能不为null，但首先你要满足v4=null这个先觉条件。

![](../Images/60f7d92473ab2debf4aa82c3bd16c1af.png)

查看v4 = as.bJ(v9)，之前已经说过bJ函数负责校验了url，我们再重新回到bJ发现return null好像不太可能，v9不管uri如何构造都会以'/'开始。

![](../Images/93752123f99e0839bd90fdde6fa91b6e.png)

也就是说在应用市场上的ES版本不管是走if((!bp.q() || !f.e(v8)) && !f.a(v8, v2*5))还是走if(v4 != null && as.I(v4) != 0)似乎都不能出发到flag*object = v8\_1.a(v9, v10, v11, v6, v7)的逻辑，这样该漏洞就没法触发，但说不定还有其他的绕过方法，希望大家能够多多补充。
