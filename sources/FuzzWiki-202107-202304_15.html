Part.1

引言

      API即应用程序接口，由一组定义和协议组合而成，它为软件开发和现代应用程序带来了许多便利和好处。例如可以公开获取、标准化接口、文档完备、调用简单。在当前的许多应用程序中，通过API共享的一些数据是非常机密的，它必须保持安全和加密，但是，总有一些黑客在寻找一个API 漏洞来获取机密信息。为了应对API的安全问题，必须找到API中的潜在隐患。模糊测试作为当前主流的漏洞挖掘方法，在API的漏洞发现中得到了应用。从表现形式来看，现有的API主要分为了函数级API及web server中的Web API两大类。函数级API指的是应用程序本身对外提供的功能接口，如操作系统向上层应用程序提供的各种接口，第三方库对外提供的各种功能接口等。Web API一般指提供WEB服务的server对外提供的数据、资源请求接口。API模糊测试的核心原理是以自动化方式或半自动化的方式使用随机或者错误的数据注入到函数的参数中，判断监视软件的异常，从而来发现漏洞。

       本文主要对API模糊测试领域的现有工具及方法进行梳理和总结，首先按照测试对象的不同，对现有的函数API及Web API测试工具及其特点进行了总结。在此基础上，对现有的代表性工具和方法的基本原理进行详细介绍。

Part.2

API Fuzz工具汇总

      我们将现有的API模糊测试方法分为两类，一类是Web API模糊测试，主要针对于网络服务接口；一类是函数级API模糊测试，对于内核态或普通应用层的函数接口都可以进行测试。下面对这两类测试工具进行了汇总。

Web API模糊测试工具

       对于Web应用程序，其API一般指定如何通过网络访问服务和数据，在移动、社交和云应用程序都有很广泛的应用。不同的Web API也有不同风格的架构，如SOAP、RPC、GraphQL、REST等。现有的Web应用程序大多使用REST架构，因此，REST API是本文主要讨论的目标。

       由于REST API请求和响应是通过HTTP传输的，所以可以使用HTTP模糊测试工具来进行API Fuzz。现有方法的基本思路是，首先捕获并随机模糊或重放HTTP流量，然后解析HTTP请求/响应及其内容（如嵌入的JSON数据），来找到错误。这些工具大多是基于突变的黑盒模糊器，普遍对接口参数粗糙地选取预定义的特殊值进行变异，甚至有些采用对模糊候选值全遍历的手段，这导致数据变异后的测试用例数量非常多，模糊测试的效率较低。近年来，随着有状态的REST API模糊测试工具Restler的提出，它能在无需预先记录HTTP流量的情况下智能地生成请求序列，研究者开始转向研究有状态的REST API模糊测试工具。表1总结了REST API模糊测试工具。

Part.3

API Fuzz研究进展

REST API模糊测试

REST API将定义一系列由统一资源标识符（URL）区分的资源。然后可以使用基于HTTP动词的语义的操作来操作这些资源，例如GET、POST、DELETE和PUT。在处理HTTP请求期间，API可能需要从数据库读取/写入数据，并与其他web服务通信。测试REST API我们不仅需要为不同的端点编写HTTP消息，还需要选择正确的查询参数，以及正文有效载荷消息。

 REST API规范可以由JSON、OpenAPI、API Blueprint、RAML描述，但OpenAPI是目前为止最受欢迎的REST API规范。一般来说，REST API是无状态的，但由于调用此接口返回的是状态信息，因此，REST API Fuzz的测试手段通常为大量构造特殊的请求报文，通过观察被测对象的响应报文及系统表现情况，来捕获漏洞。

对于REST类型的API进行模糊测试的大致流程为：首先确定REST API为待测目标，将不同的REST API规范作为输入向量，根据待测目标和输入向量找到合理的策略生成模糊数据。进行模糊测试之后，我们需要对REST API进行监测，观察响应状态码或者代码覆盖率。

我们通过测试生成方法将REST API模糊测试分为三类，一类是采用依赖于手工定义模型的黑盒方法，一类则尝试使用使用搜索算法的白盒方法来生成测试，最后一类是自动化的黑盒算法。虽然，在当前的研究中也有灰盒方法模糊REST API，它将通过程序插装跟踪代码覆盖率，并引导模糊程序最大化代码覆盖率，但是它受到支持的特定编程语言的限制，我们不作讨论。

手工定义模型的黑盒方法

Chakrabarti[1]和Kumar在他们的工具中提出了一种测试REST API的方法，称为Test-the-REST（TTR）。它是一种黑盒的、基于规范的测试，它输入的测试用例是基于XML的测试规范语言编写的，需要手工构造。手动模型定义是他们提案的主要缺点，尽管如此，他们每天都能发现大量的bug。  

基于Chakrabarti等人提出的TTR，由Fertig[2]等人提出了一种模型驱动的方法MDT。该方法需要使用领域特定语言(DSL)描述现有的API，虽然也是需要手工定义模型，但与TTR相比需要了解的测试知识较少。Earle[3]等人使用了类似的方法，他们创建了一个JSON库，将JSON数据特征化为JSON架构从而生成测试用例。测试工具QuickCheck提供了一个通用的状态机，它通过遵循JSON 架构中的链接来自动浏览web服务。同样，这是一种需要手动定义模型的方法。

自动化的白盒方法

与之前提到的建议相反，Arcuri[4]等人提出了一种完全自动化的白盒测试方法，其中使用进化算法自动生成测试用例。他们提出了一个非常强大的工具Evomaster，与黑盒技术相比，它在测试RESTful服务内部更深层次的逻辑方面更有效，因为它可以搜集和使用有关服务目标的更多信息来指导测试用例生成。但它的缺点是需要开发人员阅读API文档，并且只能为基于Java\Scala\Kotlin的RESTful服务提供工具。

自动化的黑盒方法

当我们在访问一些服务时，常常是通过REST API远程访问，我们并不能知道其服务的完整代码，为了解决白盒方法的局限性和手工定义模型的低效性，完全自动化的黑盒方法逐渐成为REST API 研究的主要方法。本质上，这些方法使用随机测试数据来测试API 。包括随机和默认值、输入数据字典、测试数据生成器、API之前的响应观察到的数据。

Hamza[5]等人提出了一个四个步骤的方法。首先通过解析JSON(或YAML)文件，从定义文档中提取OpenAPI模型。第二步从OpenAPI模型中提取参数示例，然后将它们用作测试用例的输入数据。第三步通过推断API操作的测试用例定义，创建一个TestSuite模型，最后，将TestSuite模型转换成一个可执行的JUnit代码。该方法就是使用随机值来测试API。

最近，Atlidakis[6]等人提出了第一个有状态的REST API模糊器RESTler。模糊化的过程与Hamza的方法相似，但主要是使用输入数据字典进行模糊。对于接口测试，应用程序中的函数需要以正确的顺序调用，REST API也不例外。只有按照正确的顺序发送请求，才能生成有意义的测试用例，从而提高代码覆盖率。RESTler能够推断请求类型之间的自动依赖关系并且能由服务响应反馈来指导测试的动态生成，以避免服务拒绝依赖组合和避免无效的请求序列。但RESTler只能从用户定义的固定值字典中选择相同类型的其他值来替换body值，为了改进此方法，Godefroid[7]提出了一种能智能地生成嵌入在REST API请求中的数据负载的方法。该方法包括一系列模糊技术，包括结构化模式模糊规则、各种规则组合、搜索启发式等。


图 1 Restler


受RESTler的启发，Karlsson[8]等人提出了QuickREST，对于给定的OpenAPI规范，它可以生成用于基于属性的测试数据生成器。基于属性的测试主要思想是生成输入数据，并在使用该输入执行被测系统时检查已定义的属性是否保持不变。这种方法可以快速验证和测试OpenAPI，但不会向测试目标发送请求。

尽管黑盒模糊具有不受编程语言限制的优势，但盲目、随机和发散的突变会使某些路径难以触发。为了使黑盒模糊测试过程能够识别变异的影响，Tsai[9]等人结合灰盒方法提出了新的模糊程序HsuanFuzz。该方法在REST API黑盒模糊测试中添加“测试覆盖率级别”，并对其进行反馈，以了解突变效果和输入是否合适，从而进行有意义的突变以生成新值，改善了普通黑盒测试的缺点。

2022年，Liu[19]等人提出一种基于模型的测试。Morest将其OpenAPI规范作为输入来构建RPG，这是RESTful API和模式之间关系的新表示。在构建初始RPG后，Morest使用它生成调用序列，并用实际请求替换调用序列中的API调用。然后将生成的测试用例反馈给目标RESTful服务，Morest将收集响应。

函数级API模糊测试

内核API函数模糊测试

内核本身可以分为两种类型的代码:核心内核代码和设备驱动程序。前者是通过系统调用(sycall)接口访问的，open()、execve()系统等等。后者，在posix兼容的系统上，通常通过ioctl接口访问。

在操作系统中，用户应用程序常常利用系统调用（sycall）接口访问系统资源。这些应用程序本身一般调用高级API函数，而API函数会在内部请求系统调用。因此，对于内核中的API函数模糊测试，API中传递的参数类型和依赖关系是研究的关键策略之一。Choi[11]等人创建了一个名为NTFUZZ的工具，它可以静态分析调用系统的二进制文件（dll文件），通过对系统调用参数也就是API函数中传递的参数执行类型感知变异。因为系统调用参数通常是嵌套的，并且彼此依赖，若不对系统调用类型进行识别就难以生成有意义的测试用例。

图3 内核API函数fuzz


对于内核驱动程序，ioctl是设备控制接口函数。对于该接口，Corina[12]等人提出了DIFUZE以实现接口感知的模糊。DIFUZZ对内核驱动程序代码执行自动的静态分析，在用户空间中合成正确结构的输入，以恢复ioctl接口的有效的命令和相关的数据结构。它使用这个恢复的接口来生成ioctl调用的输入，可以从用户空间程序将ioctl调用分派到内核。

库中API函数模糊测试

模糊测试最开始是针对发现C/C++语言，通过模糊C和C++库，我们发现了许多不规范及代码中的各类漏洞。要对库进行模糊化，编写一个有效的支持API的fuzzer需要深入理解目标库。而针对不同的编程语言，如java、Rust、javascript等等有不同的库。

Kyriakos[13]等人提出FuzzGen方案，它从系统中已有使用库的代码出发，通过对整个系统进行分析，先确定哪些是API，再从控制流和数据流两方面整理出抽象API依赖图(A2DG)。这个过程需要确定每个参数的可能值和类型，并分析参数之间的依赖关系。最后，基于依赖图生成libFuzzer的桩代码，从而进行不需人工干预、能较好地平衡宽度和深度的模糊测试。

图4 FuzzGen实现概述


FUDGE[14]是与FuzzGen[13]同时独立开发的，是自动生成模糊驱动程序的最新成果。FUDGE利用单个库消费者来推断库的有效API用法，以合成模糊器。然而，这两个方法有两个主要区别：首先，FUDGE从单个库使用者中提取API调用序列及其上下文（称为“片段”），然后使用这些片段创建模糊驱动程序，然后使用动态分析对其进行测试。FuzzGen没有从库使用者中提取短片段，而是将使用者最小化为只包含库调用、它们的依赖检查和依赖参数流。其次，FUDGE从提取的代码片段中创建了许多小的模糊驱动程序。相比之下，FuzzGen将多个消费者合并到一个可以合成任意长度序列的图中。与FUDGE相比，FuzzGen 更大、更通用，关注复杂的API交互，而不仅仅是短的API序列。

图5 FUDGE架构


由于缺乏模糊目标，现有的模糊测试工具并不直接适用于库 API。针对这一问题，Jiang[15]等人提出了一种新型的自动化模糊目标生成方法，通过API依赖图遍历对 Rust 库进行模糊测试。该方法使用带剪枝和反向搜索的BFS生成有效的API调用序列，并对序列进行细化以获得最佳API序列集。对于JavaScript库中的API函数，Hodován[16]等人也引入了一种图表示，对JavaScript引擎的API进行建模，并通过在这些图上执行随机遍历来生成测试用例。

Harrison[17]等人提出了一种新的基于数据流图的模糊化技术，其中库API交互被表示为数据流图。GraphFuzz使用了图形突变，将每次突变都作用于一个生成的数据流图，主要方法如下图所示，包含拼接、剪切、交叉链接、交换等等。

Part.4

结语

本文对API模糊测试进行了一个基本的概述，首先介绍了API模糊测试的特点和难点，然后对现有的API模糊测试的工具进行总结，最后分析了API模糊测试的研究进展。由于API要求输入数据在语义上是复杂的，函数中参数情况具有多样性，API模糊测试依然面临着一些挑战：

API函数的参数之间存在着参数间依赖问题，参数间依赖关系是API操作的两个或多个输入参数之间的约束。如果存在参数间的依赖，变异时需要对参数做出一些限制。

API函数之间存在着上下文依赖的问题，如内存管理函数malloc和free，free函数的参数必须是malloc函数的返回值。也就是说，如果操作的输入参数基于上一个操作的响应，我们需要等待上一个操作完成执行，只有以正确的顺序调用，才能生成有意义的测试用例，从而提高代码覆盖率。

在API模糊测试中，每个API都需要手工测试和编写测试用例，这样会花费大量的时间。自动化生成测试用例需要考虑识别API规范并自动推断API操作序列和参数间的约束等问题。
