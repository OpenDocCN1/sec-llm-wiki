1.简单理解协议

Http是无状态的,所以如果你下次登录服务器是不会有意识到又是你在访问,那如何保存登录状态？这里有很多技术可以实现,不过核心还是存储。注册后 常见是保存在数据库 对比成功就返回相应页面，如果B站不想让已经登录过的用户再次输入账号 密码这里假设需要重新输入账号密码,就需要存储,就简单的可以设置让用户记住账号密码,如浏览器账号 密码,如果你的电脑被攻破,那很危险,即使没有这个,也需要解决HTTP无状态的问题,浏览器要想办法每一 次请求加入账号密码保持登录 可以实现每次HTTP都自动带数据给服务器技术：Cookie 浏览器发起HTTP->服务器进行set-Cookie(名和值)Cookie设置 Cookie有名和值属性,服务器会把里面的内容填充完整->Cookie发给浏览器后 保存起来 浏览器以后发的 每一个请求都会带这个Cookie, 说白了就是保存的数据,也就是说如果把用户名和密码放在Cookie是很不 完全的 于是就有了Session会话 浏览器访问服务器就是会话的开始,模糊的是会话的时间,因为有可能是按错而已,因此不同网站对于每个 用户的会话都设定了时间和唯一ID（Session ID）时间就是结束的时间,因为是服务器自己定义的东西,因 此一般会保存到数据库里面。首先使用用户密码发送->B站服务器核对正确->服务器创建Session ID和会话结束时间(没规律的字符串)- >服务器把Session ID和时间发送到浏览器->这里就有了Cookie设置Cookie,并且把Session ID加入 Cookie里

再把会话结束时间对应设置成这个Cookie 的有效期->浏览器拿到Cookie保存 浏览器这时候没有保存用户名密码保存的Session ID也是没有规律的字符串 这个Cookie里也就Session ID最重要,如果黑客拿到Session ID怎么办.意义不大,因为Session ID无规律字 符串,不能通过Session ID推断出账号密码,服务器发送Cookie之前是会对这个含有Session ID的Cookie进 行签名,如果黑客修改了Session ID他就会变成识别不了的字符串,所以浏览器保存Cookie后利用Cookie 的核心特点,也就是每个请求,都会自动发送Cookie到相应服务器哪里,换句话说,浏览器的下次访问,下下次 访问都会自动发送这个Session ID给服务器知道Cookie有效期失效后,浏览器一般就会自动删除这个 Cookie会话就结束了,那么在Cookie失效后用户就得重新输入了。为了避免服务器超载和服务器分享,数据库崩溃等就出现了JWT json web token 用户第一次登录 ->生成jwt服务器不需要保存jwt只需要保存jwt的密文 接着把jwt发给浏览器可以让浏览器以cookie||storage的形式保存下载这也用户每次发送请求都会把这 个jwt发送给服务器这也就不需要重新输入账号密码了和session很类似这个token只不过存在用户哪儿 JWT由三部分组成

JWT由三部分组成 header.算法 payload 数据有效期类 signatrue 签名

1.1.什么是Session

Session会话：客户端A访问服务器,服务器存储A的数据value,吧key返回给客户端A，客户端A下次 带着Key(session ID)来访问服务器,服务器就能给出客户端A的数据。如果负载均衡,客户端A访问了 另一个服务器,那个服务器没有客户端A的数据。

1.2.什么是Cookie

Cookie:客户端A访问服务器,服务器返回Cookie给客户端A,客户端A存储Cookie,下次需要带着 Cookie访问服务器,服务器返回相应的数据。

1.3.什么是Token

Token令牌:客户端A访问服务器,服务器给了客户端token,客户端A拿着token访问服务器,服务器验 证token,返回数据。

1.4.session和cookie的区别

数据存放位置不同: Session数据时存放在服务器中的,Cookie存放在浏览器当中。安全程度不同: Cookie放在服务器中不是很安全,Session放在服务器中,相对安全。性能使用程度不同: Session放在服务器上,访问增多会占用服务器的性能,考虑减轻服务器性能方面,应使用 Cookie。数据存储大小不同: 单个Cookie保存的数据不能超过4K,Session存储在服务端,根据服务器大小来定。

1.5.token和session的区别

token是开发定义的,session是Http协议规定的。token不一定存储,session存在服务器中。token可以跨域,session不可以跨域,它是与域名绑定的。

1.6.什么是同源策略

同源策略是一种约定,它是浏览器最核心也是最基本的安全功能,同源策略会阻止一个域的javascript 脚本和另一个域的内容进行交互,是用于隔离潜在恶意文件的关键安全机制,如果缺少同源策略浏览 器的安全使用会受到很大的影响,可以说是Web是构建在同源策略的基础之上的,浏览器只是针对同 源策略的一种实现。

同源的定义

当一个请求url的协议、域名、端口三者之间任意一个与当前页面url不同即为跨域。同源策略目的就是为了保证用户信息的安全,防止恶意的网站窃取用户数据,如果网页之间不满足同源的要 求,那么他们之间: 

  1. 不能共享Cookie、localstorage、IndexDB

2. 不能获取DOM

3. AJAX请求不能发送

同源策略作用举例:

  1. 双十一到了,你打开了某网站www.waterhorse.top,登陆成功,你准备买东西了。

2. 你的好朋友给你发了一个网站www.weixian.com，你打开了 

3. 你在浏览着www.weixian.com，由于没有同源策略的限制,浏览器会自动将Cookie附加在HTTP请求 头字段Cookie中,这样,这个不法网站就相当于登陆了你的账号,如果这是你的银行卡账号！！！

4. 这也就是CSRF(跨站请求伪造)攻击。

1.7跨域问题

同源策略存在带来的问题就是跨域。

跨域访问限制的流程:

同源策略,是由Netscape提出的一个著名的安全策略 所有支持javascript的浏览器都会使用这个策略 所谓的同源指的是,域名,协议,端口相同。当一个浏览器两个ab页面分别打开,百度和谷歌的页面,就会检查是否同源,只有和百度同源的脚 本才会被执行,如果非同源,name在请求数据中,浏览器会在控制台中报一个错误,提示拒绝访 问。同源策略是浏览器的行为,是保护本地数据不被JavaScript代码获取回来的数据污染,因此拦截 的是客户端发出的请求回来的数据接收,即请求发送了,服务器响应了,但是无法被浏览器接收。

跨域访问限制的作用

  1. 浏览器发送跨域请求

2. 接收response数据 

3. 检查响应头 

  1. 如果响应头中没有允许跨域访问的配置,则不加载,并报出响应异常。

2. 如果响应头中有允许跨域访问的设置,正常加载数据。同源策略并不是浏览器不让请求发出去,或者后端拒绝返回数据,实际情况是请求正常发出去了,后端也正 常响应了,只不过数据到浏览器后浏览器不去作用加载而是丢弃了。

跨域问题的解决

CORS(Cross-Origin Resource Sharing)跨域资源共享机制

简称为跨域访问,允许Web应用服务器进行跨域访问控制,从而使跨域数据传输得安全进行,CORS需 要浏览器和服务器同时支持,目前,所有浏览器都支持该功能(IE浏览器要求版本IE10或以上) 整个CORS通信,都是浏览器完成,不需要用户参与,对于开发者来说,CORS通信与同源的AJAX通信没有 差别,代码完全一样,浏览器一旦发现 AJAX 请求跨域，就会自动添加一些附加的头信息，有时还会多 出一次附加的请求，但用户无感知。因此,实现CORS通信的关键是服务器,只要服务器实现了CORS接口,即可跨域通信。

CORS使用场景

用户在使用浏览器的情况下会使用到CORS,因为控制访问权限的是浏览器而非服务器,因此使用其他 客户端的时候无需关心任何跨域问题 CORS的主要应用是实现在浏览器端使用AJAX直接访问COS的数据或上传下载数据，而无需通过用 户本身服务器中转。

CORS原理

浏览器判断后端有没有返回CORS头(Access-Control-Allow-Origin),发现没有就认为后端不允许跨 域,即认为返回的数据不可靠。所以只要后端能够返回浏览器需要的请求头,即可跨域(响应数据不会被同源策略抛弃) 浏览器将AJAX请求分为两类 简单请求 特殊请求

简单请求

只要同时满足以下两大请求,就属于简单请求：1. 请求方法是以下三种方法之一: HEAD GET POST 2. HTTP的头信息不超出以下几种字段：Accept Accept-Language Content-Language Last-Event-ID Content-Type：只限于三个值 application/x-www-form-urlencoded , multipart/form-data , text/plain

当浏览器发现发起的ajax请求时简单请求时,会在请求头携带一个字段:origin 刚才讲了,CORS需要客户端和服务器同时支持,上面的操作,算是客户端的支持行为(IE10以下不行)

Origin中会指出当前请求属于那个域(协议+域名+端口),服务会根据这个值决定是否允许其跨域。如果服务器允许跨域,需要在返回的响应头中携带下信息(服务端支持)

Access-Control-Allow-Origin:可接受的域,是一个具体域名或者*(任意域名)。Access-Control-Allow-Credentials：是否允许携带Cookie,默认情况下,CORS不会携带Cookie,除非 这个值是True。关于Cookie 要想操作Cookie,需要满足3个条件: 服务的响应头中需要携带Access-Control-Allow-Credentials：并且为True 浏览器发起ajax需要指定withCredentials 为true 响应头中的Access-Control-Allow-Origin一定不能为*，必须是指定的域名 这样就能支持跨域了。

1.8什么是HTTP-only

微软公司的Internet Explorer 6 SP1引入了一项新的特性。这个特性是为Cookie提供了一个 新属性，用以阻止客户端脚本访问Cookie。　　　　

如果cookie中设置了HttpOnly属性，那么通过js脚本将无法读取到cookie信息，这样能有效的 防止XSS攻击，窃取cookie内容，这样就增加了cookie的安全性。

1.9什么是内容安全策略(CSP)

跨站脚本攻击(XSS) 在某些情况下,同源策略的限制性如果太强,其实是不太友好的,比如大型网站的子域之间的数据传递, 开发过程中的一些调试等,但是人类利用一些技术,从而放宽策略 但是,XSS攻击可通过欺骗网站提供而已代码和计划好的内容来绕过同源策略:通过寻找将恶意脚本注 入网页,攻击者可以获得对敏感页面内容,会话Cookie以及浏览器代表用户维护的各种其他信息的提 升访问权限。盗cookie 强制发邮件 

CSP内容安全策略: 

为了缓解很大一部分潜在的跨脚本问题,浏览器的拓展程序系统引入了内容安全策略(CSP)这种的一般概 念,简单来说这一技术就是:

开发者明确告诉客户端(制定比较严格的策略和规则),那些外部资源是可以加载和执行的,即使攻击 者发现漏洞,但是没办法注入脚本的。

开发人员可以使用这种工具以各种方式锁定其应用程序,降低内容注入漏洞(如XSS)的风险,并降低其应用 程序执行的权限。

2.OAuth2.0授权流程

什么是OAuth2.0

OAuth2.0是一个授权协议,它允许软件应用代表(不是充当)资源拥有者去访问资源拥有者的资源,应 用向资源拥有者请求授权,然后取得令牌(token),并用它来访问资源。


服务器安装系统,这台服务器就是管理用户的数据,如果他是微信,他就是保存的聊天数据,如果是豆瓣就是 豆瓣评分 ,在oAuth中叫资源服务器,什么是资源？数据或者文件都是资源。交互的入口就是各种各样的API接口了,可能是APP可能是网页,要获取数据的数据就包含对应的Userid用 户编号，然后API查询用户ID编号返回对应的资源。你可以发送,那攻击者也可以冒充。他通过一些方式 获取Userid或者不是他应该访问的数据,这是需要避免的 那oAuth是怎么解决的？


Auth2.0概括了四种决策 1. 资源服务器 对应了保存用户数据的后端系统 2. 客户端(APP，网页) 3. 授权服务器 通常指第三方搭建用于接收用户授权的服务器 4. 用户(资源拥有者) 拥有了自己在平台的数据

以常见的豆瓣为例 假设我在当前页面点击微信,由微信生成二维码,在手机上就显示是否授权,点击同意,同时看到的数据都是 之前我们拥有的 首先用户在豆瓣的首页上点击微信登录：作为豆瓣的网页他进行一个跳转或者新的请求分发,分发给微信 的授权服务器,微信生成二维码数据,二维码交给用户看,用户扫码。同意以后由豆瓣首页向授权服务器申请Access Token 是整个oAuth中的灵魂,当豆瓣向授权服务器申请 Access Token 的时候,之前作为这个用户他已经经过授权所以由服务器生成Access Token是有规则的长字符串 这个Access Token随着响应返回给客户端,客户端收到Access Token进行缓存,如果是APP返回到本地的 某个文件中,如果是网页返回到Cookie或者localstory第三方可能缓存到数据库中,无论返回到哪里 ,如果 要获取用户当前数据,除了包含userid以外还要包含Access Token,这个Access Token发给API后API先进 行Access Token校验,依照oath使用模式不同,校验Access Token 的方式也不同,如果校验通过后API执行 原有的业务,把对应的userid 的数据返回。在这个过程中Access Token被称为令牌是一个有格式特殊有失效性的字符串,当授权服务器把Access Token颁发以后他会包含每一次请求中向服务器发送,aouth标准化了整体响应和请求和整体的流程, 他实现了技术和标准

两者的区别是完全不同的概念,1是一个标准化的执行流程2.本身是具有特殊格式的长字符串用于生成 Access Token,JWT只是在其中Access Token的方法 什么情况下Oauth使用 需要第三方认证的时候需要搭建Oath2.0
