想象一下如果需要保护 Web 应用生产环境，而实现这一点你需要考虑与所有不同 Web 服务器的后端技术栈一对一集成。这样的工作不仅需要懂得WAF，也要有足够的专业知识理解 Nginx、Apache、IIS 和 Tomcat 等应用系统。每个受保护的后端技术栈带来的复杂性，使得您很有可能永远也无法完成该项目。此外，即便技术准备足够成熟，您也将在操作和维护中陷入困境；通过对技术栈一对一集成实现应用快速保护，事实上是不可能的。

幸运地是，上述这些做法都不是 Imperva 实现应用保护的标准操作。我们的解决方案已经演变为相当简化的流程；我们的方案在实现有效保护的同时，并不需要考虑后端技术栈的实现。换言之，无需与技术栈中不同的 Web 服务器一对一地集成。

上述个场景引出了一个问题——为什么如今 API 安全的集成策略如此复杂？今天的大多数企业客户都在API端点发现中投入了过多的精力。这个过程通常会涉及与各层网络以及不同 API 网关间的集成，使得 API 发现变成了复杂而花费精力的任务。考虑到如今API 服务事实上成为了应用交付中不可或缺的一部分，API端点发现过程不应该如此复杂。

实现API 安全保护的复杂性，在很大程度上被一些只做API安全的供应商扩大化了。这类供应商努力寻找一种无需依赖其他系统提供的日志的方法，无缝提供 API 安全性。为了全面掌握API数据，供应商迫使企业将其方案与应用环境中各种组件集成，包括 API 网关、负载均衡器和网络聚合器。然而，这种设计理念是有缺陷的。所有流量的阻塞点，才是获取API服务信息的最佳位置，可以同时捕获应用程序和 API 数据。

以下是围绕 API 安全制定集成和运营策略的要点：

● 1\. 如果不直接与所有流量对接，就无法捕获所有 API 流量。企业应遵循简单高效的设计理念，直接在全部流量的瓶颈处进行整合。

● 2. 如果无法在网络边缘捕获 API 访问流量，那么次佳的选择不是依赖于不同组件（例如 API 网关）的集成策略。服务网格已经为您提供了有效使用内置代理来捕获所有流量（包括 API）的方法。

● 3. 如果能够直接集成 API 网关来让您从 Shape IT 了解影子 API，那么 API 发现功能实际上是多余的。鉴于 API 网关可以看到通过它发送的所有流量，只需付出有限的努力，您应该就能够生成所有 API 端点的列表。不应该通过一个本不必要的集成来实现。

**转变设计理念**

**imperva.com/zh**

  

通过发现和分类实现对 API 端点的可见性，这个过程应该遵循与应用安全相同的设计理念。可以率先从面向互联网开放的 API 开始，并且通过在网络和应用堆栈的边缘创建一个无缝集成点来完成，提供足够的保护，避免服务受不良行为者的侵害。

接下来，扩展您的安全策略以包含内部 API，也称为东-西方向 API。如果您有一个基于服务网格的现代应用程序栈，那么可以实现无缝集成。这种集成可以通过代理设置，例如 Kubernetes 中的 Envoy，它内置在服务网格中。

最后，请记住 API 服务已经存在了几十年。不受供应商忽悠，认为API端点是新兴的服务界面。API 一直是应用程序开发（以某种形式）的一部分，最初的 XML RFC 规范促生了 1998 年发布的 SOAP。虽然API如今已经发展出不同的版本，例如 RESTful 和 GraphQL，但您不必开发完全脱离了整体应用保护的新策略。最好的方法是选择能够在应用安全层之上构建 API 安全性的服务提供商。这种方法大大减少了集成的麻烦，帮助您充分了解面临的风险，并提供了一种整合、有效的方法来限制 API 暴露。

  

  

**加快实现API安全保护的最佳实践**

**imperva.com/zh**

  

为了提高保护暴露 API 的能力，以结果为导向的设计理念很重要。这种方法意味着您可以在不过度扩展团队的情况下实现 API 安全性。可以参考以下最佳实践来衡量选择的解决方案。

  

**#1. 不需要改变代码**

为保护您公开的 API，供应商不应当要求任何形式的代码更改。如果要求在持续交付和持续集成 (CI/CD) 生命周期内更改代码以支持安全解决方案，会引入不必要的复杂性。为安全功能引入这些代码更改，可能会导致新的问题，或者导致 API 安全产品的兼容风险，此外代码更改还会减慢 CI/CD 的速度。您应该避免选择需要更改底层代码以实现 API 可见性的安全解决方案。

  

**#2.无冲突部署**

基础架构和安全团队应该能够在不依赖开发人员的情况下实现强大的 API 安全控制。开发人员和安全团队之间的协作可以通过无冲突的部署方式得到增强，因为安全团队可以通过自动发现和分类为开发团队提供对 API 端点的可见性。这种可见性包括能够为开发人员提供及时更新的 API 规范文件，以及在CI/CD过程中提供额外代码分析的选项。

  

**#3. 毫不妥协的实时保护**

不应该有任何依赖关系限制对暴露 API 的实时保护。要实现这一点，仅通过与其他边缘安全解决方案集成，执行准实时或排队的操作是不够的。这个功能要求很关键。每当 API 安全合作伙伴声称解决方案将减少您的平均修复时间时，您了解清楚为什么新方案不能像的应用保护框架那样提供实时的保护。

  

**#4. 不需要改变代码**

不要误以为 API 安全的实现可以脱离Web 应用程序防火墙 (WAF)。不需要与 API 网关直接集成，就能够发现和保护您的 API服务。WAF 不并是一项“过时的技术”，在 API 保护方面仍然具有不可估量的价值。看看 OWASP API 安全性 Top 10 漏洞就知道了；企业级WAF 产品能够为其中六类漏洞提供保护。借助通过 WAF 在应用程序安全框架上构建的原生集成 API 安全服务，可以利用高级 WAF 功能快速保护企业 API 端点。

  

WAF 产品的选用，对于通过WAAP平台集成实现API保护的方案至关重要。
