如何利用RASP自动减轻安全漏洞的威胁

DevOps 如今正在为软件开发加油助力，自动化、代码重用和第三方库已经成为应用程序开发周期中不可或缺的重要组分。 但是，当业务和功能的开发速度超过必要的安全保障时会发生什么？想象一下，如果帮开发提速的工具本身成为了安全漏洞，又该如何是好？

这些新的攻击量令人束手无策：边界保护和端点安全等传统安全机制，要么无法部署，要么不起作用。同时我们看到，即便是具有丰富安全编码经验的组织，也很难管理软件供应链和开发流程中的风险。

代码依赖

据估计，约有 90% 的安全事件的成因是针对软件设计或代码中的缺陷和漏洞的攻击。如今，构成您软件的大部分都不是你自己的代码——多达 97% 的企业代码库是开源的，平均有 203 个依赖项。从正面角度看，这加速 DevOps 和数字化转型；然而，越来越多的攻击者们，也能够方便地寻找到您正在使用的相同代码中的漏洞。根据 GitHub 的说法：任一个活跃的代码项目，明年有高达 59% 的可能性会给您推送安全警报。

将编译器、API、构建系统和其他技术堆栈因素也考虑在内，您就会看到一个规模巨大且错综复杂的系统。在这种环境下，管理应用程序的漏洞是一项巨大的挑战。您如何知道该优先解决哪些问题？如何得知您使用的哪些应用处于危险之中？您有多少应用程序的开发是基于开源、第三方软件或您无法控制的其他来源？您是否有响应预案及操作时间，能够暂停目前的工作流以修补关键应用程序中的零日漏洞？当您以很快的迭代速度部署软件时，如何保护这些代码免受攻击？

根据 Code Complete，每 1,000 行代码平均有 1-25 个错误。解决代码中的安全问题，您打算从哪里开始？

认清差距

在软件运行时这种动态的环境中，传统的安全方法是无效的。边界安全、静态/动态分析以及端点安全方案都依赖于更新，无法防范零日漏洞或缺乏对应用程序攻击的可见性。例如，SolarWinds 攻击中使用的后门代码无法通过静态分析检测到，因为它不包含任何错误。

Web 应用程序防火墙 (WAF) 保护您免受来自网络外部的 Web 流量的威胁。然而，如果在受信任网络中的软件 (例如 Exchange Server) 遭到破坏，WAF 将无法保护您，因为访问该服务的流量并不通过 WAF。代码分析器工具在查找错误和漏洞方面做得很好，但您仍然需要手动修改代码消除漏洞威胁——这个过程可能需要几个月的时间。

积极的安全模型允许您锁定软件，使其无法做不该做的事情。应用程序只在缺省安全的配置下运行，这样可以保护整个软件堆栈，包括开源和第三方依赖项。运行时应用程序自我保护 (RASP) 实现的就是一种积极的安全模型，它使得交付的代码在执行中符合安全标准，降低了风险，并让您有更多时间修补/修复漏洞，而不会中断工作流。

先行缓解，稍后修补

RASP 方案，能够帮助安全团队跟上 DevOps 的步伐，同时为团队提供更多的灵活性和时间来管理和修复漏洞。无论您的应用程序处于何处，底层环境如何，RASP都可以伴随在应用程序内部运行。 即使边界防御措施被破坏，同时应用程序包含漏洞，RASP 也可以做到控制应用程序正常执行、阻止攻击并向安全团队发出警报。 这样，RASP 可以很好地作为 WAF 方案的补充； 后者将已知的不良流量拒之门外，而 RASP 则减轻了未知漏洞所带来的风险。

RASP 可防止零日漏洞和 OWASP 前 10 名应用程序安全威胁、注入和弱点。保障以下几类应用程序的缺省安全：

·       活跃的应用程序

·       遗留应用程序

·       第三方应用程序

·       API 和微服务

·       云应用

·       容器和虚拟机

RASP 与应用程序代码紧密耦合，与黑白名单 (阻止/允许列表) 机制不同，RASP 使用上下文感知来检测威胁，并确保请求中的有效负载无法利用到应用程序代码的任何未知部分。 在您的应用程序中拥有这样的“眼睛” ，开启了一个由内而外的全新视角，可以让安全团队深入了解攻击企图、易受攻击的代码位置，同时锁定攻击中用户账号、请求来源等指标——在未来，也可以借助RASP 实现更好的应用程序开发，提供增强的威胁洞察力。
