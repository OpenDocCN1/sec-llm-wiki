# 软件供应链攻击的5种方法，第3部分：恶意的账号接管

本篇是有关软件供应链攻击的系列文章的最后一部分。 之前我们讨论了四种臭名昭著的供应链攻击方法，即攻陷程序供应商、第三方程序利用、开源代码库利用和依赖关系混淆，并深入了解了这些方法如何威胁软件供应链，从而将极大的风险传递给信任并依赖他们的用户。 今天，我们将讨论供应链攻击的一种经典场景：恶意的账号接管。

**恶意的账号接管**

“恶意接管账号”是另一类供应链攻击的手段，或许也是各类方法中技术含量最低的，这是另一个攻击者利用我们对软件供应链安全性假设的情形。从很多角度看来，“恶意接管账号”与前面讨论的“依赖关系混淆”攻击非常接近。由于几乎所有应用程序中都或多或少使用了开源软件，因此，“恶意接管账号”虽然简单，但出人意料地有效。

此类攻击的一个有据可查的例子发生在2018年底，Node.js开发人员使用了一个处理事件流的npm包 “event-stream”。该工具包最早发布于近10年前，每周下载估摸有2百万次，由其原始所有者忠实地维护了很多年。

开源项目通常由原始开发人员自己来维护，也可能由一小部分贡献者在空闲时间无私地维护。可能是一项不足为道且无偿的工作，但对很多开源项目参与者而言，为社区的改善做出贡献并获得一定的认可，也是一种回报。

经过多年处理功能改进，错误修复和新版本发布之后，社区中的另一位成员与“event-stream”项目原始所有者接洽，表示愿意接管该项目。出于信任，原作者将项目的控制权移交给了新成员，然后转去做其他项目。在几周内，恶意代码被附加到项目中，通过自动构建工具下载，并部署在数量未知的软件应用程序中。

在上述这个例子中，发布到公网的恶意代码是专门设计用来从Copay比特币钱包中窃取凭据的。像后门程序和其他恶意软件一样，这段攻击代码使用加密来混淆其真实操作，然后将窃取的凭据数据发送到远程服务器。如果不是因为攻击者编写的代码出了些小错误，两个多月后终于引起了Node.js代码库管理员的察觉，那么这些恶意代码很可能会在“event-stream”程序包中保留更久。

软件开发过程完全基于软件供应链值得信赖的假设，这种意识存在巨大风险。开源软件届通行的规则是任何人都可以创建项目或做出贡献，然而并没有制定正式的审核程序。尽管可以使用构建工具的很多检查功能来减轻此类安全风险，但这些检查功能要么太深奥复杂，要么不够实用，无法持续使用以保障应用安全。

**总结**

显然，开源代码、自动化软件构建工具的广泛应用以及灰产经济诱因的结合，使对软件供应链的攻击变得越来越有效且异常具有吸引力。那我们不禁要反问：为什么现有的安全控制措施无法减轻这种风险？

如今，在软件开发生命周期和供应商管理中，现有的过程控制完全依赖于耗时，容易出错的手动流程和自我证明机制，因此无法始终如一地保证有效。用技术手段实现控制，往往会会遗漏真正要关注的方面。对于Web应用程序防火墙，检查重点是入站流量。对于端点安全系统存在的问题可能是：未安装到应用程序的部署环境中，或者被故意配置为“允许”来自受信任应用程序的特权活动。代码扫描技术能够发现无意的常见错误，但无法识别有意的恶意软件。

是的，我们可以对供应商和补丁程序管理流程进行改进；也可以对端点安全系统和代码扫描工具进行改进；甚至可能在开源社区中达成共识，以更统一的方式审查开源项目、创建者和所有权所有权链。但逐步做这些改进的同时，我们该如何应对眼下的安全威胁？

如果使用软件应用程序的组织必须承担与之相关的所有风险，那么他们必须有一种简单的方法来减轻这些风险，而无需特殊的专业知识或软件供应商的参与。如果有“一劳永逸”技术控制手段，可以在任何部署环境中，应用于任何应用程序，将大大降低与软件供应链相关的风险。
