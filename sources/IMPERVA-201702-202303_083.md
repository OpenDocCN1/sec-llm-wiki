# 在AWS RDS服务上DIY数据安全方案的风险

**通过 AWS RDS服务，可以轻松DIY数据库服务供应**

越来越多的企业开始使用数据库即服务（DBaaS），这种趋势是显而易见的。DBaaS的灵活性可以用来更快地将新产品和服务推向市场，同时降低了数据库操作的成本和复杂性，这两方面优势都可以大大节省时间和资金投入。  

Amazon Web Services（AWS）是DBaaS的流行选择，它能够让启动新数据库变得如此容易且便宜。AWS RDS平台会自动处理所有重要的详细信息，安装和配置。 业务团队和DevOps团队无需等待IT部门来安装和配置新数据库，他们完全可以自己动手操作，而无需另外学习DB相关领域的专业知识。

**那么DBaaS上的安全实现也可以DIY么？**

AWS RDS使得配置和使用数据库变得如此简单，容易带来这样的错觉：RDS有着同样方便简单的方案，可以实现其上数据库服务的安全与合规。

毕竟，AWS平台本身非常安全。 另外，还辅助提供了几种安全增强工具和服务。 从理论上讲，这些工具和服务可用于组成DBaaS的安全解决方案。

在完整解答上述问题之前，我们讨论一下实现AWS RDS数据库安全解决方案，需要哪些功能。

**DIY方案与安全合规要求的差距**

大部分情况下，AWS平台本身是非常安全的，但是您放在其基础架构上的数据却不是。亚马逊条款中明确表示，维护安全及合规是用户自己的责任。

AWS RDS中提供的数据库类型（例如MySQL，PostgreSQL，Microsoft SQL，Oracle，MariaDB和Amazon Aurora）包括一些重要的安全措施，包括用户访问权限设置，数据加密以及数据库快照等。但请注意，默认情况下这些安全功能并未全部启用，因此必须确保正确地配置，使用和管理。 启用这些功能的是必不可少的前提，但这些并不足以确保符合安全与合规的最佳实践。

正如我们在上一篇博客文章中介绍的那样，仍然存在一些重要的安全性和合规性挑战，由使用云数据库服务组织来解决：

**● 可见性：**梳理组织架构内AWS账号下所有数据库的，并知道哪些数据库包含敏感的，与合规有关的数据

**● 持续监控：**监视所有数据库（更重要的是监视每个数据库中的实际敏感数据），并保持对可能影响安全或合规的任何行为的洞察

**● 追溯问责：**能够以5个重要维度(何时、何地、人员、访问对象、原因)跟踪和报告数据库访问事件

**DIY数据库安全方案的缺陷**

我们在上文提到过一些组织尝试使用DIY方法，试图由AWS平台的服务以及三方公司提供的工具，拼凑一套安全系统，旨在提供能够弥合上述差距的安全解决方案。

例如，部分方案选择是将所有数据库日志活动定向到AWS CloudWatch，然后使用AWS Lambda无服务计算进行事件分析并触发后续操作； 另一部分解决方案将所有数据库事件数据发送到SIEM平台，配置特定事件过滤器以及(日志处理)工作流以管理安全事件。

这些方法都缺少两个非常重要的元素。

**● 无法及时跟进：**面对每个新的数据库，必须手动调整并重新配置DIY系统。 在现实环境中，移动和删除数十个甚至百个数据库的，可能涉及使用多个AWS账户。业务及对应服务需要持续配置或更改，人为操作将始终落后于更改的速度，从而给未受保护的数据带来不必要的风险。

**● 接口不堪重负：**DIY解决方案使您难以照顾到整个数据仓库。由于设计限制及定义的分散，通常缺少统一的视图来管理数据库服务。 使用不同的工具和界面来查看数据库清单，观察安全状态，对事件做出响应，运行报告等；很可能导致响应时间变慢，风险事件被遗漏，更不消说还需要对已经过度劳累的安全人员进行了大量的额外的培训和努力。

**DIY数据库安全项目既冒险又艰难**

在实践中，尝试进行DIY安全项目的组织大大低估了所需的成本和投入，并且在许多案例中，所有的努力最终都被彻底放弃了。 以下我们列举分析了导致这些结局的具体原因：

● **缺乏专业知识：**数据安全实施团队通常并不是数据库技术栈或安全合规要求领域的专家。

**● 比预期更大的投入：**许多组织在安全实施中都发现项目范围逐步蔓延：往往会发现有额外的需求，或者意识到问题远比预期的复杂

**● 隐形成本：**所采用的技术组件的价格高得惊人，更不用说补充专业程序员和操作员的额外成本了

**● 项目不是一次性的：**需要持续的维护和现代化工作来解决问题，并跟上技术发展的步伐

**● (安全)并不是项兼职工作：**事实往往证明，将数据安全工作分配给已经负责其他任务的团队，附带的工作量太大了

**● 总之，经历过DIY数据库安全的公司会发现****：**先前认为以合理的投入能够达成的工作，最终被证明是一个庞大的，持续的项目。主要问题是其中大多数人低估了任务所需的成本和精力，并且根本没有时间、技能或持续水平的投入来取得安全方案的成功

**DIY方法会在需要它时实际发挥作用吗？**

当然，最重要的问题是安全方案是否按设计要求完成使命。构建似乎有效的解决方案是一回事，而当严重安全事件发生时，能够完全依靠方案解决问题则是完全不同的事情。

衡量成功的最佳指标也许就是金钱。综合违规调查所需的工作量、信息泄露的惩戒与罚款，以及因业务信誉受损而造成的收入损失而言，违规行为会导致巨额经济损失。参考2020年全年统计，在美国，平均每起数据泄露事件造成的损失为819万美元，需要花费约280天的时间解决。

安全团队需要掌控全局，以快速觉察和响应安全事件。很多DIY数据库安全性解决方案，使“及时获取所需的有效信息”的环节变得困难复杂甚至不可能。可能对企业范围内的一些数据库，安全团队甚至无法获知它们有否存储敏感信息。响应团队必须查看几种不同的工具来了解一个安全事件，何时发生、究竟发生了什么、哪些数据遭受影响、谁应该为此负责。发现和解决关键事件所花费的时间越长，带来的成本就越高；任何减少安全事件响应时间的方法，都可能带来巨大的投资回报。
