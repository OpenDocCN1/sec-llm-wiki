# 结合WAF以及RASP：纵深防御最佳实践

**WAF构建的防御层似乎足够强大，为什么还需要RASP方案？**简单的答案是：没有任何一个单独的安全产品，可以针对所有威胁向量提供保护。全面完备的IT安全策略，应当包含适当的风险控制措施，实施这些措施可以在最大程度上提高效率，并在整个过程中进行集成分析。Imperva WAF（Web应用程序防火墙）是用于保护应用程序的分层纵深防御策略的重要组成部分。它允许合法流量访问在其后的应用程序，同时阻止不良流量，从而防范严重威胁的攻击，例如针对“OWASP Top 10”列表中的漏洞进行未经授权的数据渗透。Imperva同样也提供RASP（运行时应用程序自保护）方案。听起来可能与WAF类似，RASP也旨在检测和阻止某些请求载荷，以避免对SQL注入和跨站脚本等漏洞的利用。但随着Imperva对RASP产品的最新增强，引入语言无关保护的特性以及对云原生的支持，它与WAF方案差异与特点逐渐显现。值得我们仔细研究一下WAF和RASP的安全架构的结合，是否能在支持关键资产和数据保护方面体现综合优势。**Web****应用防火墙**Web应用防火墙WAF位于应用程序的前方，检查传入的HTTP请求流量，试图检出已知的攻击负载和判别异常的使用模式。当检测到可疑的攻击负载或使用模式时，可以设定WAF报告该HTTP请求，或者同时报告并阻止请求。除了提供实时警报和报告外，WAF还可以批量阻止IP地址，并提供规则集的自定义功能。Imperva的WAF方案可将已知的不良流量与正常流量区分开来，确保您的应用程序不会处理与预期功能无关的信息或请求。降低应用程序基础架构的成本，也是采用该类解决方案的另一个好处。大多数WAF的不利之处在于：必须持续对其进行调整，以期保持阻止漏洞利用功能的有效性。另外，在对应用开启保护之前，有效攻击载荷的识别通常是被动的，这会造成漏报或引起有害误报。特别是在采用了敏捷开发实践，通常需要实现快速迭代的移动应用程序环境中，这样的问题尤其严重。**运行时应用自防护（RASP）**RASP方案实现方式与WAF大不相同，防护的实现方式是在服务器层级将自身插入应用程序，与应用程序代码紧密耦合。Imperva的RASP方案使用语义理论安全（LangSec）的上下文感知技术来检测威胁，并确保特定的恶意HTTP负载无法利用到应用程序代码。RASP技术仅在应用尝试使用（请求）数据时，才在应用程序上下文中检验完整的（通常在传输阶段是经过转换或混淆的）有效负载。这种实现方式上的变革，带来的收益是降低了误报率，同时增强了漏洞的可见性，包含了对先前未知弱点的发现。RASP不需要持续维护或进行重大调整。它在应用关键位置提供安全增强，补充了WAF及其他应用安全方案组件的不足。尽管SDLC的策略可能会强制要求，在应用程序投入生产之前纠正使用安全测试工具（例如：动态代码检查DAST）发现的漏洞，但通常情况下，业务压力意味着应用程序带着已知问题发布。应用程序代码很难做到没有错误，而且由于开发人员通常没有经过严格的安全培训。因此，在应用程序层级，提供针对漏洞利用的默认保护，这样的解决方案确实非常迫切且必要。RASP方法的优点数不胜数，它能够提供应用程序感知和上下文相关的保护。从这个角度看，它可以轻松地集成到软件开发生命周期（SDLC）中，能够防止0-day攻击，并且有效地保护遗留的旧版应用程序。**WAF与RASP结合案例****攻击检测**WAF等置于应用程序前方的安全方案，针对已知攻击提供出色防护，WAF基于签名策略的方式非常适合检验已知漏洞的利用负载。但是应用程序代码的频繁更改和第三方库的使用，意味着应用环境处于不断变化之中，边缘防护方案不得不被动响应这种变化，否则可能会带来漏报或意外误报的风险。在这种情况下，基于语义安全LangSec的RASP方案，能够在应对未知漏洞利用载荷时发挥作用。Imperva RASP解决方案不需要签名，以与应用程序及其支持组件相同的方式评估每个有效请求负载，识别攻击尝试，提供应用程序缺省安全。RASP是仅在应用关键位置实现的安全增强解决方案，可以最大程度减少误报。为构建完备的安全体系架构，纵深防御策略需要在不同的节点实施不同的控制。如果攻击能够穿透某一层的控制，在另层使用相同类型的控制方案将毫无意义。**阻止更多攻击流量**随着越来越越多的组织机构逐渐向云基础架构过渡，传统的网络边界已基本消失，因此根据网络连接的源头分辨敌友的难度越来越大。在大多数WAF部署中，检查的重点是“南-北向”或“由外向内”的流量。与之对比的是，RASP方案通常是面对的是“东-西向”或“由内而外”的流量。WAF主要致力于将不受信任的外部人员拒之门外。RASP可以防范受信的内部人员或自治微服务，对应用和业务造成伤害。**将安全融入到DevOps体系**在许多组织中，WAF通常由专门的专业化团队维护——在外部，通过Imperva或其他类似的安全服务提供商托管；在内部，通过安全运维团队中的WAF管理员维护。但是，随着IT行业不断向“云”方向演进，运营团队与开发团队正在加速整合。开发运维一体化DevOps意味着，与持续集成/持续交付管道的集成，是设置和实施安全控制的默认机制。RASP方案能够很自然地融入这个模型中，因为它可以被当作应用程序的一部分来看待。随着IT团队和黑产对手构成的不断变化，深度防御策略必须是动态的。安全必须成为DevOps实践的日常部分……然而训练有素的安全人员，并不像研发和运维一样，似乎永远不够用。那为什么不在这个（安全与DevOps结合的）场景中，借鉴研发的最佳实践，利用研发的技术，借助研发人员呢？在评估RASP与WAF的优劣，试图确定哪个方案更好的过程中，我们会发现RASP和WAF方案事实上是互补的。WAF阻止已知的不良流量，同时RASP在应用程序的上下文中提供了适当位置的安全增强。两种不同的安全方法可以同时运用，提供了纵深防御解决方案，成为坚实安全策略的一部分，对抗当今许多不同形式的攻击。在纵深防御中，我们还可以采用诸如Imperva 应用安全方案之类的组合：Web应用程序防火墙（WAF），DDoS保护，高级Bot管理和RASP提供保护和多传感器分析，提供完整的解决方案组合，多层级地监控和保护应用程序访问。
