在Windows系统中，最重要的就是它的API，这是无法绕过的坎，除非你不用windows；就连前面我们介绍的“反射型DLL注入”技术对抗也只是绕过了LoadLibrary这个关键API，这样的方法不具有通用性，且难度高；所以有人就从另一个层面想“招法”，就是这里我们介绍的API混淆；以Github中的一个例子，我进行研究验证整理后发出来，有些结果同作者一致，但有些不一样，至于为什么，我也在文进行了一些尝试性说明，不保证正确；还是发出来，大家共同研究研究。

作者在文章开头提出了一个很好的设想：“This's pretty forward, let's say I've used VirtualProtect and I want to obfuscate it with Sleep,the tool will manipulate the IAT so that the thunk that points to VirtualProtect will point instead to Sleep.Now at executing the file, windows loader will load Sleep instead of VirtualProtect, and moves the execution to the entry point.From there the execution will be redirected to the shellcode , the tool put before, to find the address ofVirtualProtect and use it to replace the address of Sleep which assigned before by the loader”。

作者文地址：https://github.com/d35ha/CallObfuscator

 

一、混淆工具及样本

文中涉及到了一个用于混淆函数的工具：CallObfuscator，作者提供了源代码，可以编译成exe文件；并提供了一个用于测试的C文件，截图方便说明作者的意图：

很简单，里面就两个函数：GetLastError、SetLastError；要操作混淆的就是这两个函数。

①混淆工具：CallObfuscator。

②样本分别为混淆前的文件test.exe，混淆后的文件sample_test.exe。

 

使用格式为：CallObfuscator text.exe sample_test.exe GetLastError,GetACP SetLastError,Beep

这里我要将GetLastError混淆成GetACP、将SetLastError混淆成Beep。

替换不影响程序函数的功能。

2、发现端倪

这是我们用APIMonitor来查看的结果，两者出现了不同，在这点上和作者得出的结论是不同的，可能是APIMonitor先进了从而认出了混淆的存在；也可能是没有认出来而丢弃了。

 

三、结论

可以说，这个混淆函数名的工具还是非常成功的，现有市面上的工具都是基于IAT来识别的，混淆恶意程序的重要函数名还是可以达到伪装效果的，从发现来看APIMonitor也是识别不成功的，直接来个不显示了。

 这个危害其实挺大的，有关成果还在继续研究中，敬请关注！
