前言

现在的老板们骚操作多，很多公司每个月都会有定额的福利，但需要拿发票去报销才能拿，于是就会有很多朋友碰到这样的问题：

•由于日常生活中不会经常出去吃饭、打车或是买一些价格较高的物品，导致每个月收集到的发票都极为零散，而且有些是纸质发票、有些是电子发票，整理起来极其麻烦。•由于收集到的发票都是小额发票，而且各种类型都有，在有特定类型限制（比如说餐饮类多少、交通类多少）的情况下，需要将发票分门别类地整理好，并计算出该类型的总额，对着计算器一张一张敲金额敲到头疼。•如果每个月收集的发票会比较多的话，还可能会出现一张发票开了多次、发票抬头或税号错误的情况，一不留神可能就得重新找发票补上空缺金额。而且多了的发票还得流转到下个月继续使用，管理已使用和未使用的发票又是件麻烦事。•电子发票现在还无法实现纯数字化处理，所以整理好发票之后还得打印出来才行，一张一张打开、打印点到手酸。•等等...

其实不单单是我们，财务在处理这种事情的时候其实也很头疼，他们会碰到这样的问题：

•有些人的发票金额没凑够，但报销单上写的却是完整的福利金额。•有些人的抬头或税号填错了，但他们自己却没有核对过。•有些人有部分发票的类型不符合要求，但他们却混着给了过来。•为了方便整理，电子发票要求按规定格式命名并打包发给财务，但有些人给的发票名很混乱，或者发票号之类的打错了。•等等...

这些其实都是很机械化的操作，但毕竟是涉及到钱的问题，必须得要严谨，所以我们和财务都需要对发票一个一个地进行查看、核实，无形之中大家都浪费了很多时间在做这些没有多大意义的事情上。

那么，有没有什么办法能解决呢？有，用发票管理工具就好了...吗？

理想与现实

如果你有调研过这种工具的情况的话，你会发现，虽然这种工具在专业的财务工具中基本都有，但由于对发票的处理只是财务工作的一部分，所以他们往往不会将这部分独立出来，而是作为自家产品的一个子功能。

但问题在于，这些产品往往年费高昂或是需要按照使用人数付费，对于中小企业而言，其实是没有必要为了这一个功能而付费的。毕竟...我们换位思考一下，作为一个企业的老板、股东，在人员不多的情况下，人工处理各种事务对财务来说不会有太大的负担，而对于其他员工来说，每个月就处理一次，还有钱拿，压根就不会说什么，那为什么还要为这种东西付钱呢？

而作为员工，即使自己觉得太麻烦了想省点事，为这种工具掏钱也仍然是没必要，毕竟这钱出了之后每个月也就用那么一两次，太亏了。

免费工具？

所以...有免费的发票管理工具吗？当然有，但问题更多，拿比较典型的在线工具举例，最直接、最明显的就是会涉及到隐私问题，毕竟你买了啥东西，在发票上可是一清二楚的，而这发票还是能精确到公司和个人的，你愿意舍弃掉这部分隐私吗？

还有是否付费使用也是个问题，免费的话别人服务器资源收不回来随时可能关站，加上这种工具使用频率很低，挂广告也不现实；

而付费的话，功能上总得比较有特色吧？得要人愿意买吧？如果定价太低，人家可能根本收不回开发各种特殊功能、推广等所花的时间成本，如果定价太高...和前面所说的中小企业的情况一样，你会愿意出钱吗？

自己开发太麻烦？

很显然，市场环境和现实情况导致这种工具变成了一种两极分化明显的状态，要么好用但需要花钱（还比较贵）、要么免费但不好用（还可能有别的问题），但我们如果想要把这部分时间节省下来干点别的事的话，一个趁手的工具是必须有的，怎么办呢？只能自己写。但自己写的话似乎最核心的发票识别不太好搞？

别担心，这种时候我们大可直接使用现成的东西来解决，比如我们可以使用华为云的增值税发票识别API来解决识别问题。

下面我们就来基于这个API和一些现成的库快速开发一个自己用的发票管理工具吧，这样既能完美满足自己的需求，又能基本不需要花钱，何乐而不为呢？这个工具最后会作为一个开源项目放到GitHub上，偷懒的朋友可以到时候直接基于这个开发自己需要的功能。

自己动手，丰衣足食

明确需求

首先，我们需要明确一下需求，根据前面的那些问题（痛点）可以得出，这个工具至少需要做到以下功能：

1.发票自动识别、入库，避免人工一张一张输入进工具的操作。2.发票分类，用于区分不同类别的发票要求。3.发票总额计算，用于方便地凑到指定金额。4.去重，避免出现多张一样的发票。5.抬头、税号检测，避免出现开票开错抬头或税号的情况。6.自动排除已使用的发票，避免重复使用到旧的发票。7.批量打印，不然还得一张一张点开打印。8.自动导出已使用的发票并规范化命名，以方便财务收集。

注：由于国家已经在大力推进电子发票的普及，纸质发票只会越来越少了，现在深圳这边即使日常消费较多，一个月下来也就最多几张。所以我们其实没必要刻意去处理，只需要把比较方便处理的电子发票弄好就行了。

那么怎么开发比较省事呢？需求1是直接调用华为云API的；2如果搞成纯自动的太麻烦了，做成半自动的（仅自动识别已知一定是某个类型的发票）显然是最适合、时间性价比最高的，所以需要有个界面来完成；3和2一样，也是半自动就好了，也需要个界面；4、5、6都是简单的CRUD和逻辑判断操作，随便怎么搞都行；7需要操作PDF做合并；8就是文件操作而已，也是随便怎么搞都行。

很显然，这些功能用Python来开发是最适合的了，GUI（图形界面）和PDF都有成熟且方便的库可以快速实现、操作，加上我们可以直接使用华为云的发票识别API来解决核心的识别问题，这些功能压根就不是事儿，干就完了！奥力给！

飞速开发

我们先从最能提升体验的GUI部分开始做起。这里我选择使用Django来做，因为Django自带了一个后台管理系统（名为Django Admin），它可以自动地将UI跟数据库中的数据建立关联并以可定制化的方式展现出来，省去了大量画UI、写接口、写调接口代码的时间。对于发票管理这种没有啥性能要求、追求快速开发的情况而言，使用这种现成的框架来进行开发显然是最优的选择。

打开Pycharm新建一个项目，选择Django，然后选好路径、选好虚拟环境，直接点击创建，Pycharm就会自己调用Django新建项目的命令把各种目录和配置建好了。

接下来我们创建一个“应用”用来做我们的发票管理界面，在项目目录下打开命令行输入python manage.py startapp manager，Django就会自己新建一个manager目录出来，并往里面填充进样例代码。

然后我们打开manager目录下的models.py文件，开始写我们的数据模型。在Django中，基本的数据模型只需要继承models.Model写一个类，并把它的属性一个一个设定好就行了，属性会自动与数据库表中对应名字的字段对应上，同时也会自动在Django Admin中显示出来。

下面我定义了一个只有我们所需的关键信息的发票类（模型），然后在里面加上了是否已使用和发票类型两个属性，方便实现其他功能。

class Invoice(models.Model):    # 发票号码（唯一ID）    id = models.CharField(verbose_name="发票号码", primary_key=True, max_length=100)    # 货物或应税劳务、服务名称（开票内容）    description = models.CharField(verbose_name="开票内容", max_length=100)    # 开票日期    create_date = models.DateField(verbose_name="开票日期")    # 购买方名称（公司名）    company_name = models.CharField(verbose_name="公司名", max_length=100)    # 购买方纳税人识别号（税号）    company_id = models.CharField(verbose_name="税号", max_length=100)    # 价税合计（发票金额）    price = models.FloatField(verbose_name="发票金额")    # 是否已使用    used = models.BooleanField(verbose_name="已使用", default=False)
    type_transportation_fee = "交通费"    type_dining_fee = "餐饮费"    type_not_selected = "未选择"    categories = [        (type_transportation_fee, "交通费"),        (type_dining_fee, "餐饮费"),        (type_not_selected, "未选择"),    ]    # 所属类型    category = models.CharField(        verbose_name="发票类型",        max_length=100,        choices=categories,        default=type_not_selected    )

这部分代码中的verbose_name是在Django Admin中展示用的名字，如果没有设置的话，Django会默认使用属性名拿出来展示。

其他的参数都很直观，应该不用我过多地解释了吧？理解不了含义的话可以看一下Django的官方文档（https://docs.djangoproject.com/zh-hans/3.1/topics/db/models/），里面会有详细的说明。

注：由于发票类型每个公司要求的可能都不一样，而我目前已知常见的只有交通费和餐饮费两种，所以这里就直接写死了。如果你有别的类型，也可以直接按着加上，或是把category改成ForeignKey然后再加个category类（模型）以增强扩展性，但实际上这种简单需求完全没必要搞那么复杂，代码里复制粘贴一下直接写死就好了。

然后我们在manager目录下找到admin.py，导入models中的发票模型，并写上一行admin.site.register，这样这个发票模型就可以在Django Admin中展示和操作了。

接着我们还需要把这个manager应用给“激活”起来，在invoice_manager目录下的settings.py文件中找到INSTALLED_APPS，并加上一个'manager.apps.ManagerConfig'，这个操作的目的是将manager应用加入到invoice_manager项目启动时的模块加载列表中。如果没有加载的话，manager里的代码是不会被运行的。

“激活”完应用之后可以顺便把这个文件最下面的LANGUAGE_CODE和TIME_ZONE改一下，分别改成zh-hans和Asia/Shanghai。这两个参数，一个是将Django服务端的语言设定为中文，一个是把Django服务端的时区设定为北京时间。如果没有修改的话，默认是英文和UTC时间，看着挺难受的。

在“激活”了应用之后，我们就可以执行python manage.py makemigrations manager和python manage.py migrate命令，将数据库初始化好、把模型对应的表创建起来了。

注：关于makemigrations和migrate这两个命令更具体的用途和用法，建议直接看官方文档（https://docs.djangoproject.com/zh-hans/3.1/topics/migrations/），里面讲得很详细，这里就不再赘述了。

现在我们就可以打开Django Admin看看了，在Pycharm中直接在右上角选择项目名那个运行配置并点击运行即可，不需要手输python manage.py runserver命令，很方便。

如果不出意外的话，你就可以在http://127.0.0.1:8000/看到一个祝贺页面了，接着访问http://127.0.0.1:8000/admin/就能看到Django Admin的界面。

但是，我们的电子发票都是PDF格式的，这个API目前还只支持常见的图片格式，不支持直接拿个PDF去识别，所以我们还需要将发票PDF转换一下格式才行。

不过没有关系，通过搜索引擎我们可以得知，有一个叫Wand的图像处理库可以很轻松地将PDF转换成各种图片格式，我们直接用它来解决就好了。

从Wand的官方文档（https://docs.wand-py.org/en/0.6.3/）中找到安装说明，按着直接装就好了。

注意需要安装依赖 —— ImageMagick（https://imagemagick.org/script/download.php#windows），Windows的话在安装时记得勾选"Install development headers and libraries for C and C++ "选项。

然后有一个文档中没有明确指出的点需要注意一下，Wand在处理PDF文件时需要依赖一个名为Ghostscript（https://www.ghostscript.com/download/gsdnld.html）的东西对PDF进行解析，没有安装的话在运行时是会报错的。这个Ghostscript在Windows下就下载安装包之后一路下一步就好了，没啥需要特殊处理的。

接着，我们根据文档上的样例，就可以写出这样的一段代码：

class InvoiceAdmin(admin.ModelAdmin):    list_display = ("id", "description", "create_date", "company_name", "company_id", "price", "used", "category")    list_filter = ["company_name", "company_id", "category", "used"]    search_fields = ["id", "description"]
admin.site.register(Invoice, InvoiceAdmin)

这里我配置了三个配置项，分别是list_display、list_filter和search_fields，它们分别表示“需要展示的字段”、“可以用来筛选的字段”和“关键词搜索时会去搜索的字段”。

简单配置过后，我们刷新一下页面，就能看到一个改头换面的表格和花里胡哨的搜索、筛选项了：
