引言 
热更新技术，类似的技术还有称为热修复技术、插件化技术，我们在《信息安全技术　移动互联网应用程序（App）SDK安全指南（征求意见稿）》中找到其是这样定义的：
热更新（Hot Fix），通过动态下发和加载代码，使App或SDK在不重新下载和安装的情况下，改变其原有代码逻辑或资源文件。
我们认为，热更新技术的初始目的是用于应用或者 SDK 开发者在不需要重新提交应用审核的情况下，在用户无感下就能实现紧急软件问题的修复。成熟且稳定的热更新技术需要较高的技术实现成本及技术能力壁垒，所以当前主流的热更新技术开源框架大多由大型互联网公司开发并开源，并广泛用于移动互联网生态下的其他应用或者 SDK 开发者。
本研究报告是我们对移动互联网应用生态下应用使用热更新技术的趋势介绍，以及在这种趋势下隐含的应用安全风险问题，并期望以此引发业界对热更新技术滥用的讨论。

应用热更新技术应用趋势 

国内应用生态下应用热更新技术应用态势


我们以市场上TOP1000用户量的应用中抽取的500余款 APP 进行热更新框架使用情况和动态下发和加载代码情况的统计分析。

这里我们是对业界比较公开知名的开源热更新框架进行识别和统计，具体列表见“附录”。从统计结果来看，其中有57%的应用使用了主流的热更新框架，并且有少量应用同时使用了多款热更新框架。从使用数量来看，以掌阅的 ZeusPlugin、腾讯的 Tinker、美团的 Robust 和360的 RePlugin 使用最为广泛。

我们对应用代码中使用了系统 ClassLoader 类相关 API 的应用数量进行统计，该类 API 主要用于实现在运行时动态加载代码模块，从历史分析情况来看，运行时动态加载代码通常都会联网获取模块配置信息并能够通过云端更新模块文件，所以我们这里认为使用动态加载 API 的应用和使用动态下发和加载代码的应用差异不大。从结果来看，应用中存在动态下发和加载代码的数量高达83%。

从上述的统计分析来看，热更新框架和动态下发和加载代码的热更新技术已经被广泛应用于当前的移动互联网应用生态。
然而，即使是应用或者 SDK 开发者广泛使用热更新框架或相关热更新技术，但其通常并未明示用户使用的目的，以及是否在动态下发的功能模块和插件中涉及收集用户个人信息行为。我们在大部分应用的隐私政策协议中，均未明确提及应用或者接入的第三方 SDK 中使用了热更新技术的目的，以及明确告知用户应用或者第三方 SDK 在应用运行时会获取其他可执行文件；在应用的设置中也不存在供用户开启和关闭热更新功能的设置选项。

海外应用生态下热更新技术现状


对于海外的Android 和 iOS 应用生态来看，Google Play 在很早就明令禁止通过 Google Play 分发的应用，不得采用 Google Play 更新机制以外的其他任何方式修改、替换或更新应用本身行为，并且，应用不得从 Google Play 以外的其他来源下载可执行代码。

而 Apple Store 应用审查机制在后续也添加了对热更新技术使用的明确禁止。

并且，国外知名安全厂商 FireEye曾就 iOS 上热更新技术使用的安全风险进行了深度分析。
国外知名手机厂商品牌三星在其 Galaxy Store应用分发指南上也明确规定“应用程序不得启用或支持自动更新功能”。

应用热更新技术风险问题 
我们一直非常关注应用热更新技术及其使用的情况，是因为热更新技术常常作为安全威胁对抗所使用的核心技术手段之一，其可以用于逃避安全检测、应用安全审查等。那么为什么说应用热更新技术的泛滥使用是存在安全风险的？
我们认为，大部分应用热更新技术是在应用的运行时以用户无感的情况下实现的，其下发的模块是由当时的云端策略所决定，并且可以达到完全更改应用原始的运行状态和代码模块，若再结合云控配置、用户画像或者用户归因的技术，理论上可以实现千人千面的效果。而对于终端防御来说，难以确定性的预测每个用户设备的实际运行状态，所以存在安全风险。

案例二 利用云控配置结合动态加载技术

我们发现某个应用启动后，会拉取云端配置，其中的 hotfix_jar_url 参数用于指定代码模块的下载地址，其后从该地址下载并加载运行，而该代码模块承载了应用的部分核心功能实现。

从上述的实现方式来看，其存在如下的安全风险问题：
（1）应用开发者能够完全控制和变更下发的代码模块获取地址和模块文件内容造成实际运行时的逻辑功能无法预测；
（2）如果存在不安全的配置获取和代码模块下载校验方式，可能还存在被恶意劫持的风险。

建议与总结 
从上述分析研究来看，在国内的移动互联网应用生态下，热更新技术的使用已经达到非常普遍的现状，并且也存在着热更新技术滥用的问题。
本着生态良赢治理的目的，我们认为对于热更新技术的生态治理不宜采用快速一刀切的策略，而是可以采取“定向治理，逐步治理和规范，最终实现生态统一管控”的生态治理思路。
其中，定向治理，是优先治理通过热更新技术实现恶意或者安全风险行为，例如在插件中侵害用户权益，违规收集个人信息行为，恶意广告弹窗，甚至是恶意代码行为等。
逐步治理和规范，一方面是对于非必要的应用或者 SDK 使用热更新技术应当给予时间窗口进行整改和技术方案调整，对于热更新技术的具体实现方式给予一定的规范，我们认为热更新的实现方式在原始应用安装包中应该有迹可循，例如加载入口是固定的，调用接口是固定的，插件的名称和数量是明确的；另一方面应用或者 SDK 应当向用户明示使用热更新技术的目的，下发模块的功能作用以及关键云控配置参数的使用目的，如果下发模块还涉及收集用户个人信息相关，还需要额外在隐私政策协议中明确告知用户下发的具体模块信息及其收集的用户个人信息范围和目的，另外应用或者 SDK还应当提供用户是否开启和关闭热更新功能的设置入口。
生态统一管控，是对热更新技术的使用，必要性约束以及技术声明给予标准化的实现指引文件，手机终端厂商和应用市场应当加强对上架应用使用热更新技术的审核力度，并且可以采取在终端系统策略或者应用运行时引入检测和监测能力，另外也可以提供标准化和统一的线上更新渠道和接口，从而实现更新渠道的统一安全管控机制，避免开发者实现自有的热更新技术而引入的管控混乱问题。

最后，我们发布此研究报告也是期望引发生态各方对于当前广泛使用的热更新技术的滥用现象的讨论，并且最终协同多方一起实现对应用热更新技术滥用所带来的生态安全问题的治理和净化。
