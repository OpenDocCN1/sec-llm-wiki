由于给了源码，Web 服务，很明显的SSRF漏洞，而且还有回显：

![](../Images/6af86e28466fb6a9a7b27a29152aa66e.png)

这里的SSRF请求是用jodd-http这个第三方库完成的，跟进下 jodd-http 组件在处理url的解析逻辑：

jodd.http.HttpRequest#set

![](../Images/5e2b74362f1be9e825eb2f441d76fab3.png)

发现它会用空格把url做分割，并将空格前面的部分当作http请求方法。

并且它会把最后会把url解析出来的东西进行组装，构建socket连接，这个过程没有处理特殊字符的问题，导致可以注入换行符：

jodd.http.HttpRequest#buffer

  

![](../Images/4dd9d5efda482a85467c7bc40d0d2e5b.png)

所以这里的SSRF表面上看起来只是个单纯的HTTP GET SSRF，实际上可以指定任意HTTP请求方法，并且可以注入换行符。

  

除了 Web 服务外，还本地启了个 RMI server：

![](../Images/acfc219d12dbe5a8739f171373c88d08.png)

  

同时依赖组件里有缺陷库 Commons Collections 3.2.1：

![](../Images/e7b7fd3f6f4578cddeecf8759ad5329c.png)

因此思路就是通过 SSRF 攻击 RMI，利用 RMI 进行反序列化，完成远程代码执行。

  

根据Moritz Bechler在2018年的研究，JDK 6u191/7u181/8u171 之前的版本，RMI 默认会开启 HTTP tunnel 的特性。简单来说就是客户端可以通过 HTTP POST 请求与 RMI 服务端进行交互，Post Body 部分就是常规的 JRMP 数据包。

  

参考：

https://github.com/mbechler/serjs

https://mbechler.github.io/2018/05/21/Java-CVE-2018-2800/

2.$this->format被篡改导致的格式化字符串漏洞

PHP(vspprintf)的格式化字符串漏洞利用比较特殊，它提供了

很多结合PHP特点的格式，这里我们需要利用%Z这个格式。

我们看到vspprintf在遇到%Z的时候会把其对应参数传入zend\_make\_printable\_zval

功能为强制将对应参数转化成zend\_string的类型

![](../Images/647c96dce0a7997eea3a5e244e83d2ed.png)

然后如果参数本身不是zend\_string类型的话，会被传入zval\_get\_string\_func

![](../Images/5448e968879a9aa7ec60ef8af638f66d.png)

如果参数的类型是zend\_object的话，会调用其handlers中的函数

我们可以在格式化字符串的栈内找到一个指向可控位置的指针，然后

在可控地址上布置伪造的zval结构，将type伪造成OBJECT(\\x08)，然后

让zval的object地址为另一可控地址，在对应地址上布置fake zend\_object，

然后同样对其handlers进行构造，从而最终可以控制RIP(cast\_object地址可控)
