# ELF样本脱壳

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzUyMTUwMzI3Ng==&mid=2247484488&idx=1&sn=cf6e120abc869f5b2f38ac53bdf8866e&chksm=f9db530bceacda1d99eb38eeaefc222224fc372b60304e5e6f3d8b64155e92eec10f673bc71a&scene=126&sessionid=1681654987#rd](http://mp.weixin.qq.com/s?__biz=MzUyMTUwMzI3Ng==&mid=2247484488&idx=1&sn=cf6e120abc869f5b2f38ac53bdf8866e&chksm=f9db530bceacda1d99eb38eeaefc222224fc372b60304e5e6f3d8b64155e92eec10f673bc71a&scene=126&sessionid=1681654987#rd)

ELF是Linux下可执行文件的文件格式，对于该环境下的恶意样本来说，自然也会有相应的壳进行保护，加壳的作用要么是压缩文件体积或者是隐藏相关的静态特征。而一般常见的压缩壳，例如UPX，如果是原始的UPX加壳就会比较简单，我们可以利用Linux环境下的官方UPX程序直接静态脱壳，得到原始文件。如果遭遇到魔改的UPX壳或者类UPX壳，简单的方法暂时不可用，需要手工或者半自动对其进行调试脱壳。

  

最近居家办公的时候大佬同事给我提供了一份Linux环境下的恶意文件，后续立马简单分析了下发现是Rootkit等恶意文件类型，不过在首先静态分析时遇到的较多情况是恶意文件本身添加了UPX压缩壳，所以静态分析获取的结果并不是很明显，肯定需要对其脱壳。因为UPX是比较简单的壳，三下两除二就搞定了，笔者对Linux环境下的恶意样本分析经验尚欠缺，于是这次将过程进行记录以及学习扩展做好相应的笔记，后续可以复用。

  

  

第一种情况是64位环境的原版UPX脱壳

存在加壳的恶意文件如下，DIE检测到了UPX3.95。

如果要图简单的话可以直接利用Linux环境下的官方UPX进行直接静态脱壳，这里不再记录，利用IDA远程调试Linux可执行文件的配置过程比较简单这里同样不再记录。

  

如果是动态学习脱壳，需要在IDA分析得到的以下函数里找到关键位置下好断点。

慢慢寻找后会发现这个函数会调用 sys\_mmap 和 sys\_mprotect 来进行初始化，我们可以直接在该函数最后的位置jmp r13指令下断点，然后启动进程进入动态调试。

![](../Images/1b55e63da6a17889c98b468101452273.png)

  

执行完上述指令后直接跳转来到第一个函数，我们需要进入函数内部。

![](../Images/f39b2dec4444d0a89617f52a6a1a5807.png)

  

进入函数内部后接着会发现有三次向上跳转的逻辑，不用停留，继续往下调试。

![](../Images/836918e311c310c84e889ca40c14d668.png)

  

最后来到jmp的远跳转，如下。

![](../Images/1323e9e9e61a5e9a37f892188a5902c8.png)

  

执行完远跳跃后出现了三行指令，继续执行会看到 IDA 提示 RIP 被更改了，表示就要跳回到入口点\_start 了。（所以对于UPX也可以在sys\_munmap函数下断点）  

![](../Images/ec3bf1d05e7cd1eaac5a169e20fe1a79.png)

  

上述指令执行前，我们还可以在右侧的模块地址处右键跳转至该模块起始地址，会发现Entry Point已经被修改为462520h地址。

![](../Images/fde74f48a3c074834806a738a76a4352.png)

  

最终我们来到了OEP位置，如下。

![](../Images/2c5f5a29a1f437c09d62c255ded102b0.png)
