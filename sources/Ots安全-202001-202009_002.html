驾驶员剖析

换句话说，驱动程序不过是一个可加载的内核模块，这意味着，除非编写为完全独立的驱动程序，否则它将需要某些用户土地对象与之交互。在任何真正的功能开始之前，用户模式应用程序必须获取驱动程序的有效句柄，这是与ring0通信的安全方法。




设备对象

稍后我们将看到，用户应用程序调用CreateFileAPI以获取有效的句柄。这个函数接受一个符号链接，在我们的例子中是一个DEVICE_OBJECT元素。该设备对象由驱动程序本身创建为可用于任何用户应用程序的通信通道，并且毫不奇怪，如果访问控制不当，它可能会增加攻击面。

实际的设备对象由I / O管理器控制，一旦发出有效请求，它将向用户模式应用程序返回有效句柄。

获取驱动程序句柄


DriverEntry和驱动程序对象

每个驱动程序中都存在的DriverEntry是程序的入口点。这可以看作是“主要”驱动程序功能，类似于用户模式应用程序的经典主要功能。

该函数接受的第一个参数DriverEntry是一个DRIVER_OBJECT结构。然后，将由内核创建但未完全初始化的该结构传递给DriverEntry例程。加载后，驱动程序可以使用其自身的功能填充结构。第二个参数RegistryPath只是指向注册表中字符串的指针，我们可以在其中将配置参数键传递给驱动程序。

NTSTATUS DriverEntry(_In_ PDRIVER_OBJECT DriverObject, _In_ PUNICODE_STRING RegistryPath) {
    UNREFERENCED_PARAMETER(RegistryPath);
    NTSTATUS status;

    // device object
    UNICODE_STRING devName = RTL_CONSTANT_STRING(L"\\Device\\uf0DeviceObject");
    PDEVICE_OBJECT DeviceObject;
    NTSTATUS status = IoCreateDevice(DriverObject, 0, &devName, FILE_DEVICE_UNKNOWN, 0, FALSE, &DeviceObject);
                
    // symlink
    UNICODE_STRING symLink = RTL_CONSTANT_STRING(L"\\??\\uf0SymLink");
    status = IoCreateSymbolicLink(&symLink, &devName);
}

从上面的代码片段中，我们还可以注意到DriverEntry例程如何负责创建DeviceObject和符号链接，该链接最终提供给用户应用程序以便与驱动程序进行通信。请注意，Io驱动程序IoCreateDevice和都使用了这两个API 的前缀IoCreateSymbolicLink，它们暗示是I / O Manager领域的成员。


主要功能

需要由驱动程序初始化的函数实际上称为Dispatch Routines，它是结构的MajorFunction成员内部的函数指针数组DRIVER_OBJECT。该数组描述了驱动程序支持的功能：在最常见的功能的简短列表下面（更多信息在此处）

IRP_MJ_CREATE (0)
IRP_MJ_CLOSE (2)
IRP_MJ_READ (3)
IRP_MJ_WRITE (4)
IRP_MJ_DEVICE_CONTROL (14)
IRP_MJ_INTERNAL_DEVICE_CONTROL (15)
IRP_MJ_PNP (31)
IRP_MJ_POWER (22)

我们可以将它们中的每一个视为用户模式标准功能的内核模式对应物。例如，IRP_MJ_CREATE是相当于CreateFile，IRP_MJ_CLOSE的CloseFile等。

为了我们的开发目标，现在将重点转移到IRP_MJ_DEVICE_CONTROL用作“函数分派器”以执行大多数内部驱动程序功能上。我们可以注意到，每个主要功能IRP名称中都有一个前缀：这是由于这些功能是为处理不同类型的IRP而设计的。太酷了吗？但是到目前为止，我们还没有提到有关IRP的信息，对吧？


IRP和IOCTL

正如我们前面所看到的，通过导出的DLL函数和I / O管理器可以完成从用户土地代码与驱动程序的交互，这是管理往返驱动程序的请求的最终权限。根据每个请求，I / O管理器会制作一个I / O请求打包程序（IRP），该程序是MSDN上部分记录的不透明结构。驱动程序将检索寻址到其自身的IRP数据包，并在完成例程后将其发送回IoManager。

绕过SMEP和其他内核利用缓解措施

与Windows7相反，Windows 10采用了几种内核级别的漏洞利用缓解措施，例如：

  • 内核模式代码签名（KMCS）

  • 主管模式执行预防（SMEP）

  • 内核地址空间布局随机化（KASLR）

除了最新的两项，CFG和VBS，我们还将研究如何绕过或避免其他四项缓解，其中SMEP似乎是最不容易克服的。

中小企业

已经有大量关于SMEP的文献，因此我们可以将其概括为缓解措施，以阻止从内核模式上下文执行的任何用户登陆shellcode。在典型的内核利用场景中，一旦通过Ring0漏洞（即在驱动程序中）获得了对指令指针的控制，就可以像跳转令牌一样方便地跳转到用户级的shellcode，而不是编写更复杂的内核端代码。。

SMEP在CR4控制寄存器的第20位实现，每当从内核上下文执行驻留在用户模式下的代码时，都会对其进行检查。



如果是这样，0x000000fc则会显示一个错误检查以及阻止任何利用尝试的“尝试执行NOEXECUTE内存”。尽管有所缓解，但自那时以来，Economou / Nissim描述的这种流行的旁路技术已得到广泛使用，在此我们也不例外。

计划是在跳到我们的shellcode 之前使用from的一些ROP小工具ntoskrnl禁用SMEP位。实际上，我们只需要两个小工具即可实现我们的目标：一个将所需的CR4值加载到通用寄存器中，第二个将该值加载到cr4本身中。

 pop rcx ; ret             # save the desired value into cr4
 [target cr4 value]
 mov cr4, ecx ; ret        # load the new value into cr4

KASLR

来自中等完整性进程，例如非特权用户的命令外壳，我们可以使用方便的Psapi EnumDeviceDrivers API获取内核的基址nt。我们将需要基地址来计算稍后绕过SMEP所需的ROP小工具。这并不是真正的绕过，因为KASLR旨在主要保护低完整性进程，例如浏览器：在这种情况下，无法从这种完整性查询Psapi或NtQuerySystemInformation。但是，在像我们这样的标准本地EoP场景中，可以忽略KASLR。

2004年-面临新的障碍？

作为最后的练习，我考虑到2020年9月将漏洞利用移植到最新的Windows 10官方正式版本2004。起初，我认为只是重新计算小工具偏移量的问题，然后这只是小菜一碟。恰恰相反：没有启用VBS 0xfc，尽管CR4 20位已关闭，但我仍在进行错误检查。很有意思的是，我看到它可以在其他CPU /管理程序上正常工作。我决定不花更多时间在此问题上，但是根据利用虚拟机管理程序或在其下运行的硬件设置，此漏洞利用似乎无效。经过测试后，请随时与我们联系：我想了解更多并找到共同的分母:)


高威的想法

WHQL流程不能证明所讨论的驱动程序没有错误：正如Eclypsium记录的那样，那里大量未打补丁的已签名驱动程序令人jaw 目结舌。从好的方面来说，HVCI和VBS阻止了所有这些攻击，因为它们将在寄存器级别检测到任何篡改，例如，破坏CR4控制寄存器。从最新的Windows 10 20H1开始，VMWare提供了虚拟化基础安全性支持，我们可以预测攻击面将很快变得更小。
