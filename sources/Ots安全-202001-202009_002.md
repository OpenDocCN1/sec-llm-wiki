## 驾驶员剖析

换句话说，驱动程序不过是一个可加载的内核模块，这意味着，除非编写为完全独立的驱动程序，否则它将需要某些用户土地对象与之交互。在任何真正的功能开始之前，用户模式应用程序必须获取驱动程序的有效句柄，这是与ring0通信的安全方法。

  

###   
  
设备对象

稍后我们将看到，用户应用程序调用`CreateFile`API以获取有效的句柄。这个函数接受一个*符号链接*，在我们的例子中是一个`DEVICE_OBJECT`元素。该设备对象由驱动程序本身创建为可用于任何用户应用程序的通信通道，并且毫不奇怪，如果访问控制不当，它可能会增加攻击面。

实际的设备对象由I / O管理器控制，一旦发出有效请求，它将向用户模式应用程序返回有效句柄。

![](../Images/c34588d54bb2198c1aba43c4a2a9ce2d.png)

*获取驱动程序句柄*

### DriverEntry和驱动程序对象

每个驱动程序中都存在的DriverEntry是程序的入口点。这可以看作是“主要”驱动程序功能，类似于用户模式应用程序的经典*主要*功能。

该函数接受的第一个参数`DriverEntry`是一个`DRIVER_OBJECT`结构。然后，将由内核创建但未完全初始化的该结构传递给DriverEntry例程。加载后，驱动程序可以使用其自身的功能填充结构。第二个参数`RegistryPath`只是指向注册表中字符串的指针，我们可以在其中将配置参数键传递给驱动程序。

```
NTSTATUS
```

### 主要功能

需要由驱动程序初始化的函数实际上称为Dispatch Routines，它是结构的*MajorFunction*成员内部的函数指针数组`DRIVER_OBJECT`。该数组描述了驱动程序支持的功能：在最常见的功能的简短列表下面（更多信息在此处）

```








IRP_MJ_CREATE (0)
```

我们可以将它们中的每一个视为用户模式标准功能的内核模式对应物。例如，`IRP_MJ_CREATE`是相当于`CreateFile`，`IRP_MJ_CLOSE`的`CloseFile`等。

为了我们的开发目标，现在将重点转移到`IRP_MJ_DEVICE_CONTROL`用作“函数分派器”以执行大多数内部驱动程序功能上。我们可以注意到，每个*主要功能*`IRP`名称中都有一个前缀：这是由于这些功能是为处理不同类型的IRP而设计的。太酷了吗？但是到目前为止，我们还没有提到有关IRP的信息，对吧？

  

### IRP和IOCTL

正如我们前面所看到的，通过导出的DLL函数和I / O管理器可以完成从用户土地代码与驱动程序的交互，这是管理往返驱动程序的请求的最终权限。根据每个请求，I / O管理器会制作一个I / O请求打包程序（IRP），该程序是MSDN上部分记录的*不透明*结构。驱动程序将检索寻址到其自身的IRP数据包，并在完成例程后将其发送回IoManager。

如前所述，一旦用户模式应用程序获得了有效的驱动程序句柄，它就可以通过发送IRP来开始与驱动程序进行交互，IRP最终包含一个将调用特定驱动程序例程的IOCTL代码。整个过程可以简化如下：

## 显微镜下的MSIO64.sys

戴着新的工具带，我们可以找到在寻找驱动程序漏洞时要查找的内容的一般方法：在处理这些漏洞时，我建议您检查以下几点：

*   驱动程序允许低特权用户直接与其交互。
    
*   任一`MmMapIoSpace`或`ZwMapViewOfSection`存在于导入地址表（IAT）。
    
*   它具有一些自定义`memmove`或众所周知的不安全功能
    

*注意：这只是一个非常基本的起点，可以肯定地进行扩展。*

## 利用MSIO64.sys

现在我们知道了如何在Ring0中控制指令指针，我们可以继续开发概念的不同证明。我们将使用的shellcode是一个标准的令牌窃取，旨在通过*窃取* SYSTEM进程的令牌来提升当前（或另一个）进程特权。就像我说的那样，我不会过多介绍Windows 7，但是，尽管如此，它还是使我对进程还原在内核领域的重要性有一些卓著的见解。然后，在进入Windows10领域之前，我将在此主题上花一些时间。

  

### Windows 7的

在Windows 7上玩了一段时间之后，我最终设法使整个shellcode正常工作-但是-并非没有很大的代价：我找不到一种稳定的方法来恢复原始执行流程并释放其余的代码。调用堆栈。每次尝试都会导致残酷的错误检查。  
然后，我戴上*尝试用力的*眼镜，并想出了一些“假设”。这里的问题是，在不停止整个系统的情况下，我们不能让这个过程直截了当地崩溃。我们必须找到一种方法来恢复执行或使线程无害。  
然后，我开始调整shellcode / exploit，以便将被盗的SYSTEM令牌复制到任意进程，例如另一个打开的cmd提示符，该提示符可以作为命令行参数传递。这样，由于在进行错误检查时我们已经提高了目标进程的特权，因此我们可以稍微关心初始进程的命运。是的，但是我们如何防止BSOD发生呢？突然，我想起了马特·米勒（Matt Miller）写了一篇有关Ring0有效载荷的很酷的论文，因此我对此表示信任，并很快获得了回报。在许多其他有趣的有效载荷，是相当惊人发现，我找到了解决办法包括了只有两个字节，即`\xEB\xFE`或`JMP 0x0`：这个技巧很老套，不仅仅限于内核shellcode。在提高了目标进程的特权之后，通过在shellcode的末尾附加这些指令，我们将使原始线程永远旋转，而不会使它崩溃。无论如何，这都不是一个优雅的解决方案，但它至少在Windows 7上有效（可能具有更好的监视程序的Windows 10最终会检测到浪费的内核线程并召集错误检查）。

要利用此漏洞，我们只需要在用户空间的缓冲区中分配窃取shellcode的令牌，并且由于Windows 7基本上没有内核缓解措施，因此我们的利用仅需用shellcode的指针覆盖返回地址。

### **Windows 10 1907年**

#### 绕过SMEP和其他内核利用缓解措施

与Windows7相反，Windows 10采用了几种内核级别的漏洞利用缓解措施，例如：

*   内核模式代码签名（KMCS）
    
*   主管模式执行预防（SMEP）
    
*   内核地址空间布局随机化（KASLR）
    
*   内核补丁保护（KPP，也称为补丁防护）
    
*   控制流防护（CFG）
    
*   基于虚拟化的安全性（VBS）
    

除了最新的两项，CFG和VBS，我们还将研究如何绕过或避免其他四项缓解，其中SMEP似乎是最不容易克服的。

在对最新，最出色的Windows 10版本进行测试之前，我决定先在1709（又名Redstone 3）上进行尝试，因为它在缓解和旁路技术方面得到了很好的证明。

回到缓解措施，让我们将它们一一列出，并采用特定的绕过或回避措施。

  

#### **KMCS**

好吧，该驱动程序已经签名，因此实际上没有真正的绕过之路:)但是我们可以指出，阻止加载未签名的驱动程序可能是阻止普通邪恶驱动程序的初始障碍，但并不能进一步保证防止有错误的签名驱动程序从加载。

  

#### **中小企业**

已经有大量关于SMEP的文献，因此我们可以将其概括为缓解措施，以阻止从内核模式上下文执行的任何用户登陆shellcode。在典型的内核利用场景中，一旦通过Ring0漏洞（即在驱动程序中）获得了对指令指针的控制，就可以像跳转令牌一样方便地跳转到用户级的shellcode，而不是编写更复杂的内核端代码。。

SMEP在CR4控制寄存器的第20位实现，每当从内核上下文执行驻留在用户模式下的代码时，都会对其进行检查。

  

  

![](../Images/ba45224f95520e2232c83470ea993c90.png)

如果是这样，`0x000000fc`则会显示一个错误检查以及阻止任何利用尝试的“尝试执行NOEXECUTE内存”。尽管有所缓解，但自那时以来，Economou / Nissim描述的这种流行的旁路技术已得到广泛使用，在此我们也不例外。

计划是*在*跳到我们的shellcode *之前*使用from的一些ROP小工具`ntoskrnl`禁用SMEP位。实际上，我们只需要两个小工具即可实现我们的目标：一个将所需的CR4值加载到通用寄存器中，第二个将该值加载到cr4本身中。

```
 pop rcx ; ret             # save the desired value into cr4
```

原始cr4值可能会有所不同，具体取决于主机系统/管理程序以及支持的CPU功能。就我们而言`1506f8`：

```
0: kd> .formats cr4
```

要获得我们的*SMEP绕过*值，我们只需要翻转第20位，即`1`上面代码段中最左边的设置即可。然后得出的值为`506f8`。现在，我们可以搜索小工具，并使用rp ++从`ntoskrnl.exe`正在测试的版本中查找所需的，我们很高兴。就是这样-是的-至少在Redstone 3上，绕过SMEP很容易。

####   

#### **KASLR**

来自中等完整性进程，例如非特权用户的命令外壳，我们可以使用方便的Psapi EnumDeviceDrivers API获取内核的基址`nt`。我们将需要基地址来计算稍后绕过SMEP所需的ROP小工具。这并不是真正的绕过，因为KASLR旨在主要保护低完整性进程，例如浏览器：在这种情况下，无法从这种完整性查询Psapi或NtQuerySystemInformation。但是，在像我们这样的标准本地EoP场景中，可以忽略KASLR。

  

#### **KPP**

内核补丁保护如果AKA Patch Guard检测到任何关键的内核结构被篡改，它将对我们发出吠声和蓝屏。是的，因为我们正在处理CR4寄存器，所以挑衅KPP的机会就摆在桌面上了。但是，我们知道KPP是在随机的时间间隔触发的，因此，如果我们足够快地恢复原始CR4值，就可以完全避免触发任何蓝屏。

WHQL流程不能证明所讨论的驱动程序没有错误：正如Eclypsium记录的那样，那里大量未打补丁的已签名驱动程序令人jaw 目结舌。从好的方面来说，HVCI和VBS阻止了所有这些攻击，因为它们将在寄存器级别检测到任何篡改，例如，破坏CR4控制寄存器。从最新的Windows 10 20H1开始，VMWare提供了虚拟化基础安全性支持，我们可以预测攻击面将很快变得更小。
