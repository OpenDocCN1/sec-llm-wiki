最近，国外安全研究人员Andrew Danau偶然发现了在举旗竞赛期间php-fpm组件处理特定请求的错误（CTF：捕获标志）：特定的构造请求可能导致php-fpm处理Nginx + PHP产品组合在Web应用程序开发中占有很高的市场份额，因此该漏洞具有广泛的应用范围。影响范围。

漏洞概述

PHP-FPM在特定的Nginx配置中具有任意代码执行漏洞。特别是：
使用Nginx + PHP-FPM构建的服务器使用nginx.conf类似于以下配置：

1   location ~ [^/]\.php(/|$) {
2        fastcgi_split_path_info ^(.+?\.php)(/.*)$;
3        fastcgi_param PATH_INFO       $fastcgi_path_info;
4        fastcgi_pass   php:9000;
5        ...

Nginx中的fastcgi_split_path_info将在处理存在'\ n'（％oA）的path_info时将传递给PHP-FPM的PATH_INFO保留为空（PATH_INFO =“），影响键指针的方向，从而导致后续path_info [0]的受控零位置= 0操作。通过构造对特定长度和内容的请求，您可以覆盖特定位置数据，插入特定环境变量并导致generationsCode执行。

由此，我们可以得出结论，request-> env-> data-> pos的方向直接影响我们的环境变量Key（在其中写入Value），并且只要我们控制char * pos的方向，我们可能会覆盖现有的数据。但是，要实现RCE，存在以下要求和限制：

  1. 指针向前受当前fcgi_hash_seg空间结构的影响。太短的char * pos不能为零，并且太长的char * pos被分配给新的fcgi_hash_seg空间。（传递“ like” http://127.0.0.1/Somefile_exits/AAAAA.php/也会导致指向向后移动）

  2. path_info [0] = 0只能将单个字节（最好是最低位）清零，否则将导致过多的指针位置偏移。

  3. 鉴于条件2应该以最小的0位覆盖，然后是合格的可覆盖环境变量。

  4. 覆盖的位置环境变量的键必须与预期要写入的键相同：要读取的var，hash_value和var_len。

  5. 当执行FCGI_PUTENV（请求，'ORIG_PATH_INFO'，orig_path_info）时，分别写入ORIG_SCRIPT_NAME，orig_script_name（ORIG_SCRIPT_NAME / index.php / PHP_VALUE \ nAAAAAA）。

因此，我们可以：

  1. 通过控制query_string的长度，path_info恰好位于新fcgi_hash_seg的数据中，此时我们只需要移动8 + 8 + 8 + len（“ PATH_INFO \ 0”）+ N = 34 + N以完成对char * pos的篡改，满足条件1,2的要求。

  2. 通过自定义http标头，操纵请求标头的长度可将环境变量的预期替代放置在特定位置（0x_u_00 + len（“ ORIG_SCRIPT_NAME”）+ len（“ /index.php/”）。要求3,5为（在NGINX中，HTTP中的请求标头以“ HTTP_XXX”的形式传递到PHP-FPM中，然后写入到request-env中）

  3. Exp作者提供了EBUT，这是一个自定义标头，其环境变量名称HTTP_EBUT的长度和hash_value等于PHP_VALUE，在后续处理中将尝试读取PHP_VALUE（ini = FCGI_GETENV（请求，'PHP_VALUE'）；条件4下的要求是遇见。

另外，鉴于逻辑的PATH_INFO重估部分主要处理PATH_INFO与实际path_info不同的情况，因此开头提到的nginx配置项在某些情况下会出现URL，例如http：// localhost / index / info。可以启动php / test？a = b来构建以下场景

影响范围

使用前面提到的配置，此漏洞影响以下版本的PHP：
7.1.x <7.1.33 
7.2.x <7.2.24 
7.3.x <7.3.11

错误修复

可以通过向Nginx添加配置try_files％uri = 404php来设置cgi.fix_pathinfo = 0选项，以暂时避免漏洞影响。您还可以选择使用正式发布的更新进行全面修复。
