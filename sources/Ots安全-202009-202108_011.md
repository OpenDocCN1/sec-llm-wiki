ZecOps 移动 EDR 研究团队调查了最近公布的 wifid 中的 WiFi 格式字符串错误是否在野外被利用。

**介绍**

城里有一个新的 WiFi 漏洞。你可能已经看到它，但没有意识到它的含义。最近披露的“非危险”WiFi 漏洞很强大。

  

此漏洞允许攻击者感染手机/平板电脑而无需与攻击者进行\*任何\*交互。这种类型的攻击被称为“0-click”（或“zero-click”）。该漏洞仅部分修补。

1\. WiFiDemon 0-Click 攻击的先决条件：

*   需要使用自动加入打开 WiFi（默认启用）
    
*   易受攻击的 0-click iOS 版本：自 iOS 14.0
    
*   iOS 14.4 修复了 0-Click 漏洞
    

  

解决方案：

*   在撰写本文时更新到最新版本 14.6 以避免 WiFiDemon 的 0 单击形式的风险。 
    
*   考虑通过设置->WiFi->自动加入热点->从不禁用WiFi自动加入功能。
    
*   使用ZecOps Mobile EDR对您的移动/平板电脑安全进行风险和危害评估，以防您怀疑自己成为攻击目标。
    

  

**2\. WiFi 0Day 格式字符串攻击的先决条件：**

与最初的研究出版物不同，在撰写本文时，WiFi 格式字符串在加入恶意 SSID 时似乎是远程代码执行 (RCE)。 

  

**解决方案：**

*   不要加入未知的 WiFi。
    
*   考虑通过设置->WiFi->自动加入热点->从不禁用WiFi自动加入功能。
    
*   使用ZecOps Mobile EDR对您的移动/平板电脑安全进行风险和危害评估，以防您怀疑自己成为攻击目标。
    
*   在撰写本文时，即 7 月 4 日，此漏洞仍为 0day。连接到特制 SSID 时，iOS 14.6易受攻击。 
    
*   等待苹果官方更新并尽快应用。
    

  

**Wi-Fi  Demon**

wifid 是一个系统守护进程，它处理与 WIFI 连接相关的协议。Wifid 以 root 身份运行。大多数处理功能在 CoreWiFi 框架中定义，并且这些服务无法从沙箱内访问。wifid 是一个敏感的守护进程，可能会导致整个系统受到损害。

  

最近，研究员 Carl Schou ( @vm\_call ) 发现 wifid 在处理 SSID 时存在格式字符串问题。

https://www.forbes.com/sites/kateoflahertyuk/2021/06/20/new-iphone-bug-breaks-your-wifi-heres-the-fix

  

最初的推文表明，这个 wifid 错误可能会永久禁用 iPhone 的 WiFi 功能以及热点功能。这种“WiFi”拒绝服务 (DoS) 正在发生，因为 wifid 将已知的 wifi SSID 写入磁盘上的以下三个文件：

*   /var/preferences/com.apple.wifi.known-networks.plist
    
*   /var/preferences/SystemConfiguration/com.apple.wifi-networks.plist.backup
    
*   /var/preferences/SystemConfiguration/com.apple.wifi-private-mac-networks.plist
    

每次 wifid 重新生成时，它都会从文件中读取错误的 SSID 并再次崩溃。即使重新启动也无法解决此问题。  

但是，根据《福布斯》，可以通过以下步骤“修复”此错误：

“修复方法很简单：只需转到设置 > 常规 > 重置 > 重置网络设置即可重置网络设置。”

此错误目前影响最新的 iOS 14.6，Apple 尚未针对此错误发布任何修复程序。

  

**进一步分析声明：这只是拒绝服务**

紧接着另一位研究员Zhi@CodeColorist 发表了一篇快速分析。

https://blog.chichou.me/2021/06/20/quick-analysis-wifid/

  

**他的结论是：**

“对于可利用性，它没有回显，其余参数似乎不可控。因此，我认为这种情况不可利用。毕竟，要触发此错误，您需要连接到该 WiFi，其中 SSID 对受害者可见。网络钓鱼 Wi-Fi 门户页面也可能更有效。”

  

**情节变厚**

我们检查了ZecOps Mobile Threat Intelligence（https://www.zecops.com/），看看这个漏洞过去是否被利用过。我们注意到我们的两个 EMEA 用户有一个与此错误相关的事件。值得注意的是，我们只能访问我们的云数据，无法检查其他本地客户端——因此我们可能会错过其他事件。

  

我们问自己： 

1.  为什么一个意识到危险威胁的人会连接到一个名称如此奇怪的网络“%s%s...”。——不太可能。
    
2.  为什么攻击者会带一个战术小组来瞄准 VIP，结果却是造成 DoS——这仍然没有意义。
    

  

**可远程利用，0 次点击，在幕后！**

进一步的分析表明：

*   攻击者不需要强迫用户连接。此漏洞可以作为 0click 启动，无需任何用户交互。受害者只需打开您的 WiFi 即可触发易受攻击的代码。
    
*   这不是 DoS，而是最近修补的 0-click format-strings 漏洞和恶意 SSID format-strings 0-day 漏洞的实际 RCE 漏洞。
    

这个 0 单击错误已在iOS 14.4上进行了修补，并归功于“匿名研究人员”的协助。尽管这是一个有效的 0 单击错误，但未分配 CVE。

**技术细节：零点击 WiFi 漏洞分析 – WiFiDemon**

让我们更深入地了解此漏洞背后的技术细节：

*   考虑到以 0 次点击触发此漏洞的可能影响，以及潜在的 RCE 影响，我们深入调查了 wifid 漏洞。
    
*   当我们在与我们的客户端类似的旧版本上测试此格式字符串错误时，我们注意到 wifid 在未连接到任何 wifi 时具有有趣的日志。
    

![](../Images/6bbdbab5d2ce6aeef376622e0c2545cc.png)

这些日志包含 SSID，这表明它可能受到相同格式字符串错误的影响。 

  

我们对它进行了测试，瞧，它受到相同格式字符串错误的影响——这意味着这是一个零点击漏洞，可以在没有最终用户连接到一个奇怪的命名 wifi 的情况下触发。

  

此日志与常见的智能设备行为有关：自动扫描并加入已知网络。

  

**零点击 - 即使屏幕关闭**

当用户正在积极使用手机时，iPhone 每约 3 秒扫描一次 WiFi 以加入。此外，即使用户的手机屏幕已关闭，它仍会扫描 WiFi，但频率相对较低。接下来扫描的等待时间会越来越长，从~10秒到1+分钟。 

  

只要打开WiFi就可以触发这个漏洞。如果用户连接到现有的 WiFi 网络，攻击者可以发起另一次攻击以断开/取消关联设备，然后发起这种 0-click 攻击。断开设备与 WiFi 的连接是有据可查的，我们不会将其作为本博客范围的一部分进行介绍。

  

这个 0-click 漏洞很强大：如果恶意接入点有密码保护，并且用户从不加入 wifi，则不会将任何内容保存到磁盘。关闭恶意接入点后，用户的WIFI功能将正常。用户几乎不会注意到他们是否受到攻击。

  

**利用此漏洞**

我们进一步分析了这个漏洞是否可以被利用，以及如何：

![](../Images/0a39a328e5dfe5fbb3ab9eba46906e7e.png)

这篇文章假设读者了解格式字符串错误的概念以及如何利用它们。然而，这个bug与“传统的”printf格式字符串bug略有不同，因为它使用了Apple实现的\[NSString stringWithFormat:\]，出于安全原因，Apple取消了对%n的支持。这就是攻击者如何能够利用传统格式字符串错误来写入内存。

  

**你在哪？– %@ 很方便！**

由于我们无法使用%n，我们寻找另一种方法来利用这个 0-click N-Day 以及 1-click 0-day wifid 漏洞。另一种可能的用途是%@，它是 Objective-C 唯一使用的。

  

由于 SSID 长度限制为 32 个字节，我们最多只能在单个 SSID 中放置 16 个转义字符。然后我们放置的Escape字符会处理栈上对应的数据。

  

一个潜在的利用机会是，如果我们可以找到一个已经在堆栈上释放的对象，那么我们可以找到一个spray方法来控制该内存的内容，然后使用%@将其视为Objective-C对象，就像典型的 Use-After-Free 可能导致代码执行。

  

**步骤 1：在堆栈上寻找可能的喷涂机会**

首先，我们需要设计一种自动方法来检测是否可以调整堆栈上的数据。lldb 断点处理脚本完全符合这个目的。在格式字符串错误之前设置断点并链接到 lldb 脚本，该脚本将自动扫描并观察堆栈中的变化。

![](../Images/b4f66d3351190389f0aa9af81a0b084c.png)

**第 2 步：找到一种有效的喷涂方法**

那么我们就需要一个可以空中干扰wifid内存的spray方法。 

  

一个有趣的策略称为Beacon Flooding Attack。它广播无数的 Beacon 帧，并导致许多接入点出现在受害者的设备上。

  

要执行信标泛洪攻击，您需要一个价值约 10 美元的无线加密狗和一个 Linux 虚拟机。安装相应的加密狗固件和一个名为 mdk3 的工具。有关详细信息，请参阅这篇文章：https://medium.com/infosec-adventures/beacon-flooding-attack-a4baadc2242b。

![](../Images/998ef78a368e25ef0f546b8919201efe.png)

作为信标帧强制字段的一部分，SSID 可以存储最多 32 个字节的字符串。wifid 为每个检测到的 SSID 分配一个字符串对象。您可以从日志中观察到这一点。这是我们可以用于喷雾的最明显的东西。

![](../Images/24f5b501ba11794c7ffde7e93bb9b821.png)

现在将调试器连接到 wifid 并开始使用可以轻松识别的 SSID 列表淹没设备。打开 iOS wifi 功能并等待它开始自动扫描可用的 WiFi。断点将被触发并检查堆栈以查找喷雾痕迹。下面是 lldb 脚本的输出：

![](../Images/52fcc38cd2b1618d4bdc3771846fa1b1.png)

引起我们注意的是存储在堆栈 + 偏移量 0x18 处的指针。由于SSID最多可以存储32个字节，最短的格式字符串转义字符比如%x会占用两个字节，也就是说我们最多可以用一个SSID达到栈上存储的16个指针的范围。因此，第四个转义字符可以达到堆栈 + 偏移量 0x18。并且测试结果告诉我们，这个偏移量的数据可以通过我们喷洒的内容来控制。

![](../Images/14ba0a32892fa22abbeab708cd4270db.png)

**步骤 3 – 测试远程控制代码执行流程的能力**

所以在接下来的测试中，我们保持 Beacon Flooding Attack 运行，同时我们构建了一个名为“DDDD%x%x%x%@”的热点。请注意%@是第四个转义字符。不出所料，wifid 一读到名字就会崩溃，只要热点还在，它就会自动重生并再次崩溃。

  

检查崩溃，似乎x15寄存器很容易受到影响。

![](../Images/9317d4208f9ded184a2719f65d011c6a.png)

现在分析它在哪里崩溃。由于%@格式说明符的作用，它试图打印 Objective-C 对象。

![](../Images/d3281d7bcd19899bc9c9bff98e237a03.png)

以黄色突出显示的代码块是所需的代码执行流程。x0 是存储在堆栈 + 偏移量 0x18处的指针。我们尝试通过喷雾来控制其内容，并将情况引向典型的 Use-After-Free 场景。x9是x0指向的数据。它代表 isa 指针，它是objc 对象数据结构的第一个成员。正如您在图中所见，控制x9对于到达底部的objc\_msgSend调用至关重要。通过更多的测试，我们确认stack + offset 0x18确实会受到喷雾的影响。

![](../Images/c2c02671929dc3a5fd2d23acf81a95d6.png)

![](../Images/369f2e591cd8dcb20f0e875250d9da13.png)

![](../Images/91d6f32fff1eab55c704520dda098857.png)

现在事情变得更加熟悉了。将受控/伪造的 Objc 对象传递给objc\_msgSend以实现任意代码执行。下一个挑战是找到一种方法来喷射充满 ROP/JOP 负载的内存。

  

**第 4 步 - 实现远程代码执行**

wifid 处理许多无线功能。无线喷涂大内存留给读者作为练习。在本地，该漏洞可用于构建部分沙箱逃逸，以帮助实现越狱。
