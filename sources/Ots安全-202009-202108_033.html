CVE-2021-22555 是 Linux Netfilter 中一个已有 15 年历史的堆越界写入漏洞，其功能强大到足以绕过所有现代安全缓解措施并实现内核代码执行。它被用来打破kCTF 集群的 kubernetes pod 隔离，并获得了 10000 美元的善款（谷歌将匹配并将捐款翻倍至 20000 美元）。

介绍

在BleedingTooth之后，这是我第一次研究 Linux，我也想找到一个提权漏洞。我开始以看旧的漏洞一样CVE-2016-3134和CVE-2016-4997这启发了我到grep的memcpy()和memset()在Netfilter的代码。这导致我找到了一些有问题的代码。


漏洞

当IPT_SO_SET_REPLACE或者IP6T_SO_SET_REPLACE被称为在兼容模式，这需要CAP_NET_ADMIN能够然而，在一个用户+网络命名空间来获得能力，结构需要从用户转换为内核以及32位到64位，以便由本地函数进行处理。自然，这注定是容易出错的。我们的漏洞是在xt_compat_target_from_user()wherememset()中调用了一个target->targetsize在分配过程中没有考虑的偏移量- 导致一些字节越界：

// https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/net/netfilter/x_tables.cvoid xt_compat_target_from_user(struct xt_entry_target *t, void **dstptr,unsigned int *size){const struct xt_target *target = t->u.kernel.target;struct compat_xt_entry_target *ct = (struct compat_xt_entry_target *)t;int pad, off = xt_compat_target_offset(target);u_int16_t tsize = ct->u.user.target_size;char name[sizeof(t->u.user.name)];
  t = *dstptr;memcpy(t, ct, sizeof(*ct));if (target->compat_from_user)    target->compat_from_user(t->data, ct->data);elsememcpy(t->data, ct->data, tsize - sizeof(*ct));  pad = XT_ALIGN(target->targetsize) - target->targetsize;if (pad > 0)memset(t->data + target->targetsize, 0, pad);
  tsize += off;  t->u.user.target_size = tsize;  strlcpy(name, target->name, sizeof(name));  module_put(target->me);strncpy(t->u.user.name, name, sizeof(t->u.user.name));
  *size += off;  *dstptr += tsize;}

该targetsize不是由用户控制，但人们可以通过名字选择用不同的结构尺寸不同的目标（如TCPMSS，TTL或NFQUEUE）。越大targetsize，我们在偏移量上的变化就越大。但是，目标大小不得为 8 字节对齐以实现pad > 0. 我发现的最大可能是NFLOG我们可以选择一个最多 0x4C 字节的偏移量（可以通过在struct xt_entry_match和之间添加填充来影响偏移量struct xt_entry_target）：

struct xt_nflog_info {/* 'len' will be used iff you set XT_NFLOG_F_COPY_LEN in flags */__u32  len;__u16  group;__u16  threshold;__u16  flags;__u16  pad;char    prefix[64];};

请注意，缓冲区的目标是分配的，GFP_KERNEL_ACCOUNT并且大小也可以不同：

// https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/net/netfilter/x_tables.cstruct xt_table_info *xt_alloc_table_info(unsigned int size){struct xt_table_info *info = NULL;size_t sz = sizeof(*info) + size;
if (sz < sizeof(*info) || sz >= XT_MAX_TABLE_SIZE)return NULL;
  info = kvmalloc(sz, GFP_KERNEL_ACCOUNT);if (!info)return NULL;
memset(info, 0, sizeof(*info));  info->size = size;return info;}

但是，最小大小是 > 0x100，这意味着该对象可以分配的最小slab 是kmalloc-512。换句话说，我们必须找到分配在 kmalloc-512 和 kmalloc-8192 之间的受害者来利用。


开发

我们的原语仅限于越界写入四个字节的零到 0x4C 字节。有了这样一个原语，通常的目标是：


  • 参考计数器

  • 不幸的是，我在前 0x4C 字节中找不到任何带有引用计数器的合适对象。

  • 空闲列表指针

  • CVE-2016-6187：逐个利用 Linux 内核堆是关于如何利用空闲列表指针的一个很好的例子。然而，这已经是 5 年前的事了，与此同时，内核CONFIG_SLAB_FREELIST_HARDENED启用了保护空闲列表指针的选项。

  • 结构体中的指针

  • 这是最有前途的方法，但是写入四个字节的零太多了。例如，指针 0xffff91a49cb7f000 只能转换为 0xffff91a400000000 或 0x9cb7f000，这两个指针都可能是无效指针。另一方面，如果我们使用原语在相邻块的最开始写入，我们可以写更少的字节，例如2个字节，例如将指针从0xffff91a49cb7f000转为0xffff91a49cb70000。


在处理一些受害者对象时，我注意到我永远无法struct xt_table_info在内核 5.4 上可靠地分配它们。我意识到它与GFP_KERNEL_ACCOUNT标志有关，因为其他分配的对象GFP_KERNEL_ACCOUNT没有这个问题。Jann Horn 证实，在 5.9 之前，使用单独的 Slab 来实施会计。因此，我们在利用链中使用的每个堆原语也应该使用GFP_KERNEL_ACCOUNT.


系统调用msgsnd()是一个众所周知的堆喷射原语（使用GFP_KERNEL_ACCOUNT），并且已经被用于多个公共漏洞利用。尽管如此，msg_msg令人惊讶的是，它的结构从未被滥用。在这篇文章中，我们将演示如何滥用这种数据结构来获得释放后使用原语，而后者又可用于泄漏地址和伪造其他对象。巧合的是，在我 2021 年 3 月进行研究的同时，Alexander Popov 还在四字节力量中探索了完全相同的结构：在 Linux 内核中利用 CVE-2021-26708。


探索 struct msg_msg

使用 发送数据时msgsnd()，有效载荷被分成多个段：

// https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/ipc/msgutil.cstatic struct msg_msg *alloc_msg(size_t len){struct msg_msg *msg;struct msg_msgseg **pseg;size_t alen;
  alen = min(len, DATALEN_MSG);  msg = kmalloc(sizeof(*msg) + alen, GFP_KERNEL_ACCOUNT);if (msg == NULL)return NULL;
  msg->next = NULL;  msg->security = NULL;
  len -= alen;  pseg = &msg->next;while (len > 0) {struct msg_msgseg *seg;
    cond_resched();
    alen = min(len, DATALEN_SEG);    seg = kmalloc(sizeof(*seg) + alen, GFP_KERNEL_ACCOUNT);if (seg == NULL)goto out_err;    *pseg = seg;    seg->next = NULL;    pseg = &seg->next;    len -= alen;  }
return msg;
out_err:  free_msg(msg);return NULL;}

其中用于头struct msg_msg和struct msg_msgseg有：

// https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/include/linux/msg.h/* one msg_msg structure for each message */struct msg_msg {struct list_head m_list;long m_type;size_t m_ts;    /* message text size */struct msg_msgseg *next;void *security;/* the actual message follows immediately */};
// https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/include/linux/types.hstruct list_head {struct list_head *next, *prev;};
// https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/ipc/msgutil.cstruct msg_msgseg {struct msg_msgseg *next;/* the next part of the message follows immediately */};

in 的第一个成员是指向队列中另一条消息struct msg_msg的mlist.next指针（这与next指向下一个段的指针不同）。这是一个完美的腐败候选人，你将在接下来学习。

最后，我们在主消息中创建一些漏洞（在我们的例子中是每 1024 个），并触发易受攻击的setsockopt(IPT_SO_SET_REPLACE)选项，在最好的情况下，它将struct xt_table_info在其中一个漏洞中分配对象：

[图 3：xt_table_info在块之间分配的A会破坏下一个指针]

我们选择用零覆盖相邻对象的两个字节。假设我们与另一个主要消息相邻，我们覆盖的这些字节是指向次要消息的指针的一部分。由于我们为它们分配了 1024 字节的大小，因此我们有 1 - (1024 / 65536) 机会重定向指针（我们失败的唯一情况是指针的两个最低有效字节已经为零）。


现在，我们可以希望的最好情况是被操纵的指针也指向一个次要消息，因为结果将是两个不同的主要消息指向同一个次要消息，这可能导致释放后使用：

【图4：由于指针损坏，两条主消息指向同一个次要消息】

但是，我们如何知道哪两个主要消息指向同一个次要消息？为了回答这个问题，我们用 [0, 4096) 中的消息队列索引标记每个（主要和次要）消息。然后，在触发损坏后，我们遍历所有消息队列，查看所有使用msgrcv()with 的消息MSG_COPY并查看它们是否相同。如果主消息的标签与次消息的标签不同，则表示它已被重定向。在这种情况下，主要消息的标签代表假消息队列的索引，即包含错误次要消息的队列。，错误辅助消息的标签代表真实消息队列的索引。知道这两个索引，实现释放后使用现在很简单 - 我们即使用并释放它从真实消息队列中获取辅助消息：msgrcv()

[图 5：释放带有过时引用的辅助消息]

请注意，我们仍然有对假消息队列中已释放消息的引用。


绕过 SMAP

使用 unix 套接字（可以使用 轻松设置socketpair()），我们现在喷射大量大小为 1024 的消息并模仿struct msg_msg标头。理想情况下，我们能够收回之前释放的消息的地址：

【图6：假冒struct msg_msg的代替释放的二级消息】

请注意，这mlist.next是 41414141，因为我们还不知道任何内核地址（启用 SMAP 时，我们无法指定用户地址）。没有内核地址是至关重要的，因为它实际上会阻止我们再次释放块（稍后您将了解为什么需要这样做）。原因是在 期间msgrcv()，消息与作为循环列表的消息队列断开链接。幸运的是，我们实际上处于实现信息泄漏的良好位置，因为struct msg_msg. 即，该字段m_ts用于确定返回用户空间的数据量：

// https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/ipc/msgutil.cstruct msg_msg *copy_msg(struct msg_msg *src, struct msg_msg *dst){struct msg_msgseg *dst_pseg, *src_pseg;size_t len = src->m_ts;size_t alen;
if (src->m_ts > dst->m_ts)return ERR_PTR(-EINVAL);
  alen = min(len, DATALEN_MSG);memcpy(dst + 1, src + 1, alen);
  ...return dst;}

消息的原始大小仅为1024-sizeof(struct msg_msg)字节，我们现在可以人为地增加到DATALEN_MSG=4096-sizeof(struct msg_msg). 因此，我们现在将能够读取超出预期的消息大小并泄漏struct msg_msg相邻消息的标头。如前所述，消息队列被实现为一个循环列表，因此，mlist.next指向主消息。


知道主消息的地址，我们可以struct msg_msg使用该地址重新制作假消息next（意味着它是下一个段）。然后可以通过读取多个字节来泄漏主消息的内容DATALEN_MSG。mlist.next来自主消息的泄漏指针揭示了与我们的 fake 相邻的次要消息的地址struct msg_msg。从该地址中减去 1024，我们终于得到了假消息的地址。


实现更好的免费使用

现在，我们可以struct msg_msg使用泄漏的地址作为mlist.next和mlist.prev（意味着它指向自己）重建假对象，使假消息可以通过假消息队列释放。

请注意，当使用 unix 套接字进行喷射时，我们实际上有一个struct sk_buff指向假消息的对象。显然，这意味着当我们释放假消息时，我们仍然有一个陈旧的引用：


[图 8：释放带有过时参考的假消息]

这个陈旧的struct sk_buff数据缓冲区是一个更好的释放后使用场景，因为它不包含头信息，这意味着我们现在可以使用它来释放平板上的任何类型的对象。相比之下，struct msg_msg只有前两个成员是可写指针（需要取消消息链接）时，才能释放对象。


寻找受害者对象

攻击的最佳受害者是在其结构中具有函数指针的对象。请记住，受害者也必须分配有GFP_KERNEL_ACCOUNT.


与 Jann Horn 交谈时，他建议struct pipe_buffer在 kmalloc-1024 中分配对象（因此辅助消息是 1024 字节）。该struct pipe_buffer可以很容易地分配pipe()有alloc_pipe_info()一个子程序：

// https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/fs/pipe.cstruct pipe_inode_info *alloc_pipe_info(void){  ...  unsigned long pipe_bufs = PIPE_DEF_BUFFERS;  ...  pipe = kzalloc(sizeof(struct pipe_inode_info), GFP_KERNEL_ACCOUNT);  if (pipe == NULL)    goto out_free_uid;  ...  pipe->bufs = kcalloc(pipe_bufs, sizeof(struct pipe_buffer),           GFP_KERNEL_ACCOUNT);  ...}

虽然它不直接包含函数指针，但它包含一个指向struct pipe_buf_operations函数指针的指针：

// https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/include/linux/pipe_fs_i.hstruct pipe_buffer {  struct page *page;  unsigned int offset, len;  const struct pipe_buf_operations *ops;  unsigned int flags;  unsigned long private;};
struct pipe_buf_operations {  ...  /*   * When the contents of this pipe buffer has been completely   * consumed by a reader, ->release() is called.   */  void (*release)(struct pipe_inode_info *, struct pipe_buffer *);  ...};

绕过 KASLR/SMEP

当一个写入管道时，struct pipe_buffer填充。最重要的是，ops将指向anon_pipe_buf_ops驻留在 .data 段中的静态结构：

// https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/fs/pipe.cstatic const struct pipe_buf_operations anon_pipe_buf_ops = {  .release  = anon_pipe_buf_release,  .try_steal  = anon_pipe_buf_try_steal,  .get    = generic_pipe_buf_get,};

由于 .data 段和 .text 段之间的差异总是相同的，拥有anon_pipe_buf_ops基本上可以让我们计算内核基地址。

提升权限

我们struct pipe_buffer用一个假的ops指向一个假的来回收陈旧的struct pipe_buf_operations。因为我们知道它的地址，所以这个假结构被放置在相同的位置，显然，这个结构应该包含一个恶意函数指针，如release。

【图11：struct pipe_buffer用假货回收的Freed struct pipe_buffer】

漏洞利用的最后阶段是关闭所有管道以触发释放，从而启动 JOP 链。寻找 JOP gadgets 很困难，因此目标是尽快实现内核堆栈枢轴以执行内核 ROP 链。


内核 ROP 链

我们将 RBP 的值保存在内核中的某个暂存地址处，以便稍后恢复执行，然后调用commit_creds(prepare_kernel_cred(NULL))安装内核凭据，最后调用switch_task_namespaces(find_task_by_vpid(1), init_nsproxy)将进程 1 的命名空间切换到init进程之一。之后，我们恢复 RBP 的值并返回以恢复执行（这将立即free_pipe_info()返回）。


逃离容器并弹出一个根shell

回到用户空间，我们现在拥有更改 mnt、pid 和 net 命名空间的 root 权限，以逃离容器并脱离 kubernetes pod。最终，我们弹出一个 root shell。
