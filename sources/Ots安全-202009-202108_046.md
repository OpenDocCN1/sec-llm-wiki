介绍

Microsoft Windows 图形设备接口+，也称为 GDI+，允许各种应用程序在视频显示器和打印机上使用不同的图形功能。Windows 应用程序不直接访问设备驱动程序等图形硬件，但它们与 GDI 交互，然后 GDI 又与设备驱动程序交互。这样，就有了一个 Windows 应用程序的抽象层和一组通用的 API 供所有人使用。

  

由于其格式复杂，GDI+ 有各种漏洞的已知历史。我们 McAfee 不断地模糊测试各种开源和闭源软件，包括 Windows GDI+。在过去几年中，我们向 Microsoft 报告了各种 Windows 组件（包括 GDI+）中的各种问题，并收到了针对它们的 CVE。

  

在这篇文章中，我们详细分析了我们使用 WinAFL 发现的一个此类漏洞的根本原因分析：CVE-2021-1665 – GDI+ 远程代码执行漏洞。此问题已于 2021 年 1 月作为 Microsoft 补丁的一部分得到修复。

  

什么是 WinAFL？

WinAFL 是流行的 Linux AFL 模糊器的 Windows 端口，由 Google Project Zero 的 Ivan Fratric 维护。WinAFL 使用 DynamoRIO 使用动态二进制检测，它需要一个称为线束的程序。线束只不过是一个简单的程序，它调用我们想要模糊的 API。

EMF 文件格式：

EMF 也称为增强型元文件格式，用于独立存储图形图像设备。EMF 文件由各种长度可变的记录组成。它可以包含各种图形对象的定义、绘图命令和其他图形属性。

![](../Images/650cc8aaac2a978afb5e9102194646bf.png)

信用：MS EMF 文档。

通常，一个 EMF 文件由以下记录组成：

1.  EMF Header – 这包含有关 EMF 结构的信息。
    
2.  EMF 记录——这可以是各种可变长度的记录，包含有关图形属性、绘制顺序等的信息。
    
3.  EMF EOF 记录- 这是 EMF 文件中的最后一条记录。
    

  

EMF 文件格式的详细规格可以在 Microsoft 站点的以下 URL 中查看：

https://docs.microsoft.com/en-us/openspecs/windows\_protocols/ms-emf/91c257d7-c39d-4a36-9b1f-63e3f73d30ca

执行流程总结：

1.  在“ Builtline::BuildAllLines”函数内部，有一个while循环，程序在其中分配了0x60字节的内存。然后它调用“ Builtline::BuiltLine”
    
2.  该“Builtline :: BuiltLine”功能将数据迁移到新分配的内存，然后将其称之为“ BuiltLine :: GetUntrimmedCharacterCount ”。
    
3.  “ BuiltLine::GetUntrimmedCharacterCount ”的返回值被添加到循环计数器中，即ECX。此过程将重复进行，直到循环计数器 ( ECX ) < 字符串长度 ( EAX )，此处为 0x14。
    
4.  循环从 0 开始，因此它应该在0x13 处终止，或者应该在“ GetUntrimmedCharacterCount”的返回值为0时终止。
    
5.  但是在易受攻击的DLL 中，由于循环计数器增加的方式，程序不会终止。这里，“ BuiltLine::GetUntrimmedCharacterCount”返回0，它被添加到循环计数器（ECX）并且不会增加ECX值。它分配 0x60 字节的内存并创建另一行，破坏数据，后来导致程序崩溃。循环执行了21次而不是20次。
    

  

详细：

1\. 在“ Builtline::BuildAllLines”内部将分配0x60或96字节的内存，在调试器中如下所示：

![](../Images/65d3adf58ca02678d50c67ac4881ba45.png)

2\. 然后调用“ BuiltLine::BuiltLine ”函数并将数据移动到新分配的内存中：

![](../Images/398e3ce8ef965f601f08e9d3dd4af72a.png)

3\. 这发生在 while 循环中，并且有一个对“ BuiltLine::GetUntrimmedCharacterCount ”的函数调用。

4\. “ BuiltLine::GetUntrimmedCharacterCount ”的返回值存储在0x12ff2ec位置。该值将为 1，如下所示：

![](../Images/47fee4b549c22a6b375149212f074634.png)

5\. 此值被添加到 ECX：

![](../Images/e13f5b59dbcfe7ca85838fecfd00a70f.png)

6\. 然后检查确定是否ecx< eax。如果为真，它将继续循环，否则将跳转到另一个位置：

![](../Images/45af4c19481a342997bb01d285c68bd9.png)

7、现在在易受攻击的版本中，如果“ BuiltLine::GetUntrimmedCharacterCount ”的返回值为0，则循环不存在，这意味着这个0将被添加到ECX中，这意味着ECX不会增加。因此循环将使用0x13的“ ECX ”值再执行 1 次。因此，这将导致循环执行 21 次而不是 20 次。这是这里问题的根本原因。

  

同样经过一些调试，我们可以弄清楚为什么EAX包含 14。它是从 POC 文件中读取的偏移量：0x174：

![](../Images/0c6dc2b0dcaf99901defd2124abf5dab.png)

如果我们还记得，这是EmfPlusDrawString记录，0x14是我们之前提到的长度。

稍后，程序使用“ FullTextImager::Render ”函数破坏 EAX 的值，因为它读取未使用的内存：

![](../Images/005b58c8947f34854346a9a190657dc5.png)

这将作为参数传递给“ FullTextImager::RenderLine ”函数：

![](../Images/8ffd1328d500c9c4dc0790b267588294.png)

稍后，程序将在尝试访问此位置时崩溃。

![](../Images/07206d9865a82fe8645fdbae9b1e524c.png)

我们的程序在处理EMF 文件中的EmfPlusDrawString记录时崩溃，同时访问了无效的内存位置和处理字符串数据字段。基本上，程序没有验证“ gdiplus!BuiltLine::GetUntrimmedCharacterCount ”函数的返回值，这导致采用不同的程序路径破坏寄存器和各种内存值，最终导致崩溃。

  

这个问题是怎么解决的？

正如我们通过查看上面的补丁差异发现的那样，添加了一个检查来确定“ gdiplus!BuiltLine::GetUntrimmedCharacterCount ”函数的返回值。

![](../Images/888656bcf4fd771cf4d6ceeb376d0aa6.png)

如果返回的值为 0，则对包含计数器的xor 的EBX进行编程，并跳转到为内置对象调用析构函数的位置：
