# 【漏洞分析】CVE-2021-26892：MICROSOFT WINDOWS EFI 系统分区上的授权绕过

点击上方蓝字“Ots安全”一起玩耍

2020 年 10 月，研究员 Abdelhamid Naceri（也称为 halov）向 ZDI 提交了一个独特的漏洞。Windows 10 中的此漏洞允许低权限用户清除 UEFI 启动所需的任意文件。攻击甚至可以从低完整性级别进行。

  

这个案子有很多谜团，我将解释我能够解释的部分。

  

该漏洞被识别为ZDI-21-330 / CVE-2021-26892，并于 2021 年 3 月由微软修补。

  

**背景**

当任何计算机系统从冷态启动时，处理器执行的第一条指令来自固件。尽管我们想快速过渡到执行存储在磁盘（例如操作系统）上的指令，但冷启动时这些指令字节在内存中尚不可用。因此处理器必须从执行固件指令开始。固件提供了从磁盘检索操作系统启动指令并最终跳转到操作系统所需的指令。

  

UEFI 是一种固件。对 UEFI 的深入处理超出了本文的范围，但出于我们的目的，我们需要知道 UEFI 固件将查找包含称为EFI 系统分区或 ESP。此分区使用固件可以解析的 FAT 文件系统的变体之一进行格式化。在这个文件系统中，固件希望找到一个扩展名为 的文件.EFI，称为引导加载程序，它可以从中读取继续启动操作系统所需的进一步步骤。通常.EFI存在对应于不同架构的多个文件。UEFI 固件还能够处理多个可用引导设备的情况。

  

**EFI 系统分区和安全性**

众所周知，FAT 文件系统不记录文件的 ACL 或任何其他安全信息。如果 FAT 文件系统安装在 Windows 上，则每个文件实际上都有一个空的安全描述符，使该文件既可全局读取又可全局写入。显然，这对于 EFI 系统分区来说是不可接受的。如果 ESP 上的文件是全局可写的，那么任何用户通过删除启动所需的关键文件来损坏系统都将是微不足道的。非特权用户甚至可以通过将.EFI文件替换为包含恶意指令的文件来安装 bootkit 。

  

因此，Windows 做了一些幕后工作来对 ESP 的访问施加特殊限制。首先，默认情况下 EFI 分区不会挂载到任何驱动器号。如果非管理用户尝试将其安装到驱动器号，访问将被拒绝。即使管理员将它挂载到驱动器号（事实上，有一个特殊的命令行语法用于挂载 EFI 分区：）mountvol F: /S，非管理用户仍然无法访问已挂载的驱动器。

  

**绕过 ESP 授权限制**

尽管有这些限制，研究人员发现低权限用户，即使以低完整性运行，仍然可以获得对 EFI 系统分区上文件的一些访问权限。

卷 GUID 可以通过卷的枚举使用FindFirstVolume和FindNextVolumeAPI 获得。通过这种方式，攻击者可以获得 EFI 分区内任意文件的句柄，只要路径是可预测的，这很常见。我做了一个实验并调用GetSecurityInfo了结果句柄，正如预期的那样，我收到了一个空的安全描述符，表明该文件是全局可读和可写的：O:WDG:WDD:NO\_ACCESS\_CONTROL。即便如此，Windows 也不会按照此安全描述符所暗示的方式运行。尝试打开文件进行读取或写入（GENERIC\_READ或GENERIC\_WRITE）被拒绝。

  

尽管如此——这是研究人员的主要发现——攻击者仍然有办法获得有限数量的写访问权限。诀窍是调用CreateFile时根本不请求任何访问权限（既不是GENERIC\_READ也不是GENERIC\_WRITE），而是指定CREATE\_ALWAYS. 此标志要求如果目标文件存在，则应立即将其截断为零长度。不知何故，这种组合超越了 Windows 为 ESP 实现的授权逻辑。尽管结果句柄上的访问掩码不允许攻击者向文件写入任何字节，但 Windows 仍会在CreateFile调用期间根据请求截断文件。通过清除关键.EFI文件的内容，攻击者可以使系统无法启动。

  

**漏洞再现困难**

在分析这个案例时，我惊讶地发现它无法在某些管理程序平台上重现。我发现它可以在裸机和 HyperV 上复制。但是，在 ESXi 上，即使安全描述符作为全局可写的 出现O:WDG:WDD:NO\_ACCESS\_CONTROL，截断.EFI文件的尝试也会失败并显示ERROR\_ACCESS\_DENIED. 我无法解释裸机和 ESXi 之间的行为差异。

  

**结论**

在试验此漏洞时，最好备份.EFI将被删除的文件，尤其是在裸机上运行时。成功复制会导致完全无法启动机器。

  

提交这个 bug 的研究员 (halov) 是 ZDI 程序的频繁贡献者，我们希望在未来继续看到他总是有趣的研究。
