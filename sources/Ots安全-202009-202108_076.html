这是我（与许多其他人一样）如何独立构建 CVE-2021-22204 概念证明 (PoC) 的叙述性演练。这段旅程中包括我遇到的死胡同，以及我一路走来的思考过程。其中大部分是在其他 PoC 和文章发表之前完成的，但是当我意识到它们时，我很高兴在自己的过程中从这些其他报告中获得灵感。


背景

ExifTool是一个 Perl 库和命令行界面 (CLI) 应用程序，用于读取、写入和编辑各种图像和文档格式的元数据。例如，它可用于从 JPG 图像中删除标识元数据。它被 GitLab 使用，这就是最初发现此问题的方式，并且可能还有许多其他 Web 应用程序。


以下是NIST 国家漏洞数据库 (NVD) 中CVE-2021-22204跟踪页面的片段：


ExifTool 7.44 及更高版本中 DjVu 文件格式中的用户数据中和不当会导致在解析恶意图像时执行任意代码。


此外，OSS-security 邮件列表中引用的电子邮件说：


该错误可以从多种有效文件格式触发。


有趣的！我们在一个可能被广泛使用的库中执行任意代码，可以从各种不同类型的输入访问。可以想象这对于接受用户上传的图像或文档的 Web 应用程序可能带来的危险。

让我们看看我们是否能弄清楚这里发生了什么。


初步调查

CVE-2021-22204的漏洞报告包含指向GitHub中 ExifTool 修复版本差异的链接。看了diff，或者只是看了网上的其他评论，我们发现DjVu Perl模块中ParseAnt函数有如下变化，用于解析DjVu注解字段：

-            # must protect unescaped "$" and "@" symbols, and "\" at end of string-            $tok =~ s{\\(.)|([\$\@]|\\$)}{'\\'.($2 || $1)}sge;-            # convert C escape sequences (allowed in quoted text)-            $tok = eval qq{"$tok"};+            # convert C escape sequences, allowed in quoted text+            # (note: this only converts a few of them!)+            my %esc = ( a => "\a", b => "\b", f => "\f", n => "\n",+                        r => "\r", t => "\t", '"' => '"', '\\' => '\\' );+            $tok =~ s/\\(.)/$esc{$1}||'\\'.$1/egs;

此代码是处理ParseAnt 中用双引号“字符包裹的文本的案例的一部分。因此，如果注释是asdf(hjkl”1234”，则此函数会将字符串处理为1234。对(字符以及其他处理有递归，但这似乎不是漏洞的一部分。


查看差异，我们看到旧版本在$tok 上进行了搜索和替换以对其进行清理，然后在$tok上运行eval以实现对某些转义的处理，例如\n。但是，新版本使用搜索和替换来仅处理预期的 C 转义，并完全删除eval。从不完全清理的漏洞分类和被删除的eval来看，我们可以看出我们要在这里专注于获取代码执行。


就其核心而言，eval用于像这样的不受控制的输入是非常危险的，因此任何使用像这样的eval 的代码都应该经过彻底审核，或者更好地进行重构，使其根本不需要eval。


检查 Regex 和 Eval 的特性

Perl 语法和正则表达式可能会变得有点难看。这是正在发生的事情的语法不兼容的细分：

$tok =~ # apply search/replace regex to $tok, saving modified version in $tok s # search/replace regex# syntax: s/match pattern/replace pattern/modifiers# (can use {} as pattern delimiters instead of / if we want)
 { \\(.) | ( [\$\@] | \\$ ) } # what to match, and capture groups in parentheses (if match, save input found in parentheses)# match any single character which is preceded by a '\', saving that character in capture group 1 OR# capture the following match in capture group 2:#    a '$' character OR#    a '@' character OR#    a '\' character at the end of the line (or before a trailing newline, thanks Jakub!)
 { '\\'.($2 || $1) } # what to replace each match with# IF there is a match THEN replace the matching text with# a '\' character followed by:#    capture group 2 if it exists ($ character, @ character, or '\' at end of line) OR#    capture group 1 (any character that was escaped by a '\')# (because of the matching regex, one of these must exist)
 sge; # modifiers# s: treat entire input as single line# g: match on any occurrence in input, not just first# e: eval the replace string

我们还应该指出这个正则表达式之前的for (;;)循环，它也处理一些”和\字符，这对于清理很重要：

for (;;) {# get string up to the next quotation mark# this doesn't work in perl 5.6.2! grrrr# last Tok unless $$dataPt =~ /(.*?)"/sg;# $tok .= $1;my $pos = pos($$dataPt);last Tok unless $$dataPt =~ /"/sg;    $tok .= substr($$dataPt, $pos, pos($$dataPt)-1-$pos);# we're good unless quote was escaped by odd number of backslasheslast unless $tok =~ /(\\+)$/ and length($1) & 0x01;    $tok .= '"';    # quote is part of the string}

这部分在补丁中没有变化，但仍然影响输入的解析方式。基本上，它会抓取输入字符串的其余部分，直到下一个”未被转义。这很重要，因为 eval 的结构是这样的：

$tok = eval qq{"$tok"};

在 Perl 中，字符串插值是在”字符内的字符串上完成的，而不是对'字符内的字符串进行的。所以，“我的$字符串”将有内容$串插了进去，而“我的$字符串”不会。为了更容易地在插入的字符串中包含”，您可以使用qq{ ... }。这个 eval 接受$tok，将它包裹在” 中以使其成为一个字符串，并评估该字符串。如果$tok包含”、$ 或 @，则会带来插值风险，因此我们提前将其过滤掉。


简而言之，这种清理（几乎）确保在我们评估之前：

  • 所有$字符都被转义

  • 所有@字符都被转义

  • 没有未转义的”字符可以跳出qq{“$tok”}

  • 保留所有其他转义字符，例如\n或\t。


虽然这看起来很严格，但显然这里仍然存在差距。否则，就不会有漏洞。

死胡同和杂项。技巧

在尝试绕过消毒功能之前，我尝试了许多不同的方法。在本节中，我们将讨论我尝试过的各种方法，以及它们是否有效。我建议在此处阅读该函数的最新易受攻击版本。这花了我一周的大部分时间来完成。


首先，我将易受攻击的函数复制到我自己的 Perl 脚本中，这样我就可以只针对易受攻击的代码进行测试，而不必担心 ExifTool 的其余部分。这对于分析和理解漏洞的根本原因很有用。使用此测试脚本，我尝试了以下操作：


手动尝试不同的转义序列

由于eval，处理的转义序列比预期的多得多。例如，\x41会产生一个A字符，而像\U这样不太知名的转义符也能工作。\c是我以前不知道的，它处理“控制”转义序列。例如，\ch在终端中的操作类似于 Ctrl+h，删除前一个字符。我测试并可以验证这是否影响了我们的$tok字符串，但我无法弄清楚如何使用它来将任何特殊字符偷偷经过消毒。


这个 ` \c ` 转义最终成为关键，直到后来我才明白这一点。

没有 $ 或 @ 的字符串插值


我找不到任何不需要$或@ 的转义符。像${ …code…}这样的东西似乎是我们获得代码执行的最佳选择。我希望像反引号这样的东西会起作用，但没有运气。


用 ( 递归将两个良性字符串组合成一个邪恶字符串来欺骗它


即使使用(进行递归， eval 也只发生在”字符内的字符串的基本情况下，而不是递归调用函数的组合结果。


Perl -T 污点跟踪

Perl 支持使用-T进行基本的污点跟踪，这听起来很有希望作为安全控制和分析此错误的一种方式。如上面链接的文档中所述：


您不能使用从程序外部派生的数据来影响程序外部的其他东西——至少，不是偶然的。


但是使用-T运行我们的测试程序，我们真正得到的只是一个警告，即eval正在受污染的内存上运行，这是我们已经知道的。我希望这个功能可以对我的清理正则表达式进行某种分析，但它是一个比这简单得多的功能。


Perl正则调试

也许我只是不太了解正则表达式？我们可以调试正则表达式以查看有关如何编译状态机和处理输入以查找匹配项的详细信息。我们可以使用-Mre=debug为整个脚本启用此功能，但这也会调试我们不感兴趣的正则表达式。相反，我们可以只使用 use re 'debug';包装我们感兴趣的正则表达式。之前并且没有重新“调试”；之后只调试我们感兴趣的代码。


这确实有助于我们观察正则表达式，因为它在我们的输入上运行。然而，它并没有真正帮助我找到任何绕过正则表达式匹配的魔法字符，或者任何其他被证明有用的东西。


使用原始 ASCII/字节进行模糊测试

在这一点上，我感到非常难倒。我想我只会向它扔字节和 ASCII，直到我得到一些有希望的东西。生成随机字节很容易，生成 ASCII 并不难。添加额外的逻辑也很容易，例如“对于 ASCII 字符，有 25% 的机会转义 ASCII 字符”或“有 50% 的机会生成特殊字符”以帮助生成可能更有趣的字符串。


为了正确进行模糊测试，我们需要能够复制任何发现。保存我们尝试的所有输入是不可行的，因此我们以print("seed: ",rand(),"\n");开始我们的脚本。一种叫法。一旦我们知道特定运行的种子，我们总是可以通过重用相同的种子来复制它，只要我们不改变使用rand() 的任何方式。我们还想减少打印语句，而不是使用警告；. 通过这种方式，我们可以使用perl ./fuzz.pl &> fuzz_log.txt记录有关发现和性能的有趣输出，而不会过度膨胀我们的输出。


这就是使用 Git 跟踪更改特别有用的地方，因为如果没有在该运行中执行的确切代码，用于运行的种子将毫无用处。


就其本身而言，这并没有真正发挥作用，但后来非常有帮助。

使用 Data::Compare 对 vuln/fixed 版本进行差分模糊测试


由于ParseAnt函数发生了变化，也许我们可以比较易受攻击的版本与固定版本的行为有何不同，以帮助我们找到什么样的输入会导致代码执行？让我们也将固定函数复制并粘贴到我们的代码中。然后，我们将相同的输入提供给ParseAnt 的任一版本，并使用来自 CPAN的Data::Compare模块比较结果数据结构。我们还可以使用内置的Data::Dumper以人类可读的方式打印数据结构。


不幸的是，处理转义的方式有足够的差异，我们有大量的输入产生不同的数据结构。所以，我们并没有真正从中学到任何东西。


解决方案

我厌倦了在ParseAnt上缺乏进展。似乎很明显必须有某种方法可以让代码在eval 中执行，但我知道的唯一方法需要$或@字符，这些字符似乎很可能被严格转义。看来”字符也处理得当。必须有一些神奇的输入来取消逃避，但我没有想法。


在这一点上，我把它分解成简单的问题。比如，“我们可以只在 eval 上执行代码吗？”。经过手动实验，我确定这是可能的：

好吧，这还不错。我们可以只使用“来结束字符串并直接执行。但是如果我们对完整的ParseAnt函数使用它，这会中断：

$ perl ./test_regex.pl main::ParseAnt() called too early to check prototype at ./test_regex.pl line 24.eval: ";exit(41);"XXX token after: ;exit(41);$ echo $?0

使用”是我们获取易受攻击代码所需要做的全部工作，因此我们添加的唯一可能破坏我们简单漏洞利用的是for (;;)循环处理”字符。与其手动再次尝试完整的问题，我想我会重用我之前的 fuzzer 组件，但稍作修改。


这种清理似乎可以在正确的位置使用一些正确的字符来绕过，这应该可以通过蛮力来实现。如果我只是找到正确的字符添加到我的有效负载的开头和结尾，我最终会执行它。这将使用特殊的退出代码退出 fuzzer，所以我知道我成功了，而不是因为其他原因而崩溃。

正是在这一刻，我意识到我在五天前在perlop 文档中读到了这个确切的内容。我一直在用它来解开 Perl 字符串插值中更晦涩的部分：

幸运的是chr(28)，ASCII 中的“文件分隔符”字符，似乎不会导致 Perl 字符串插值的问题。多么有用的巧合啊！\c\$看起来已经转义到正则表达式，但变为$。同样，\c$变成\c\$，然后变成$。我们现在可以将我们的魔法插值字符隐藏到我们的 eval 中并执行代码。


Fuzzer 事后改进

以下是我在模糊器工作后的一些想法，关于它如何更快地找到工作输入：

  • 嵌套输入的

机会有一些机会在前置/附加生成的字符串中生成匹配的嵌套字符。如果{出现在前置字符串中，有机会将}放入附加字符串中。

  • 更智能的转义

不是只用\随机转义任何 ASCII 字符，而是有机会用\c、\x和其他带参数的转义来转义。

  • 更智能的随机数生成器 (RNG) 状态管理

如果我们想要复制部分运行，则定期将 RNG 状态转储到文件中以减少开销。这样，我们不仅可以从头开始重新启动，还可以在找到有趣的输入之前不久重新启动。


制作 DjVu 文件

现在剩下要做的就是将此有效负载包装在 DjVu 文件中，以便正确处理。我最初尝试使用djvused 等工具手动设置注释，但我无法保留所需的转义。在将字符串放入文件之前，djvused似乎在对字符串中的字符进行转义。这一定是 ExifTool 首先处理 c 样式转义的原因。它似乎也从未创建未压缩的 ANTa 块，只是压缩了 ANTz 块，因此简单的十六进制编辑也不容易。


果然，通过djvlibre的来源以及它如何保存注释，内容是通过一个make_c_string函数传递的，该函数似乎对某些字符进行了转义。因为使用djvused似乎很容易，所以我想我只需要构建一个自定义的libdjvlibre.so而不进行转义，并使用我的修改版本和LD_LIBRARY_PATH。


在这一点上，我意识到了第一个公开的 PoC 和文章。我发现Jakub Wilk 的 PoC简单得多，而且是我自己的 PoC 的更好起点。


这是我结束的快速而肮脏的 PoC，使用 Jakub 创建 DjVu 文件的更简单的方法，我发现了\c绕过：
