**浏览器控制台中的错误**

*   请求的资源上不存在“Access-Control-Allow-Origin”标头。
    

  

*   跨域请求被阻止：同源策略不允许读取example.com 上的远程资源
    

  

*   CORS 策略阻止了从源“ localhost:3000”获取“ example.com ”的访问权限。
    

  

我相信您已经在浏览器的控制台中看到了这些错误之一或变体。如果你还没有——别担心，你很快就会了。所有开发人员都有足够的 CORS 错误。

  

这些在开发过程中的弹出窗口可能很烦人。但事实上，在 Web 服务器配置错误、Web 上的敌对行为者以及推动 Web 标准向前发展的组织的世界中，CORS 是一种非常有用的机制。

  

但是让我们回到最初...

  

**一开始是第一个子资源**

子资源是请求嵌入到文档中或在其上下文中执行的 HTML 元素。1993年，<img>引入了第一个子资源。通过引入<img>，网络变得更漂亮了。而且更复杂。

![](../Images/d8f4842b81f7610c9f4ec08ff2e308c8.png)

你看，如果你的浏览器渲染一个带有 的页面<img>，它实际上必须从源中获取该子资源。当浏览器从不位于相同方案、完全限定主机名或端口的源中获取所述子资源时——这是一个跨源请求。

  

**起源与跨起源**

源由三元组标识：方案、完全限定的主机名和端口。例如，http://example.com和https://example.com是不同的起源——第一个使用http方案，第二个使用https. 此外，默认http端口为 80，而默认端口为https443。因此，在此示例中，尽管主机相同 ( example.com) ，但两个来源在方案和端口上有所不同。

  

你明白了——如果三元组中的三个项目中的任何一个不同，那么来源就不同。

  

**作为练习，如果我们将**https://blog.example.com/posts/foo.html原点与其他原点进行比较，我们将得到以下结果：

![](../Images/3213186c758aa96e9645d80766933c16.png)

一个跨源请求意味着，例如，一个资源（即页面）http://example.com/posts/bar.html会尝试从https://example.com源渲染一个子资源（注意方案改变！）。

  

**跨域请求的诸多危险**

现在我们定义了同源和跨域是什么，让我们看看有什么大不了的。

  

当我们介绍<img>到网络时，我们打开了闸门。不久后，网上有<script>，<frame>，<video>，<audio>，<iframe>，<link>，<form>等。这些子资源可以在加载页面后被浏览器获取，因此它们都可以是同源请求或跨域请求。

  

让我们进入一个想象中的世界，在那里 CORS 不存在并且 Web 浏览器允许各种跨域请求。

  

想象一下，我的网站上evil.com有一个带有<script>. 从表面上看，它看起来像一个简单的页面，您可以在其中阅读一些有用的信息。但是在 中<script>，我有特制的代码，可以向银行的DELETE /account端点发送特制的请求。加载页面后，将执行 JavaScript，并且 AJAX 调用会访问银行的 API。

![](../Images/28fbf6dbc4872e353270df9bc372c63d.png)

令人兴奋 - 想象一下，当您阅读网页上的一些信息时，您会收到一封来自银行的电子邮件，说明您已成功删除帐户。我知道我知道...如果在银行做任何事情都那么容易的话。我离题了。

  

为了让我的邪恶<script>发挥作用，作为请求的一部分，您的浏览器还必须从银行网站发送您的凭据（cookie）。这就是银行服务器如何识别您并知道要删除哪个帐户。

  

让我们看一个不同的、不那么邪恶的场景。

  

我想检测为Awesome Corp工作的人，他们的内部网站在intra.awesome-corp.com. 在我的网站上，dangerous.com我得到了一个<img src="https://intra.awesome-corp.com/avatars/john-doe.png">.

  

对于没有与 活动会话的用户，intra.awesome-corp.com头像将不会呈现 - 它会产生错误。但是，如果你登录了Awesome Corp.的内网，一旦你打开我的dangerous.com网站，我就会知道你可以访问。

  

这意味着我将能够获得一些关于你的信息。虽然对我来说发动攻击肯定更难，但您可以访问 Awesome Corp. 的知识仍然是潜在的攻击媒介。

![](../Images/4de6a13a5b5777dd478cd826bde99a71.png)

虽然这两个例子过于简单，但正是这种威胁使得同源策略和 CORS 成为必要。这些都是跨域请求的不同危险。有些已经得到缓解，有些则无法 缓解——它们植根于网络的本质。但是对于已经被压制的大量攻击媒介——这是因为 CORS。

  

但在 CORS 之前，有同源策略。

  

**同源策略**

同源策略通过阻止对从不同源加载的资源的读取访问来防止跨源攻击。此策略仍允许某些标签（例如<img>）嵌入来自不同来源的资源。

  

同源策略由 Netscape Navigator 2.02 于 1995 年引入，最初旨在保护对 DOM 的跨域访问。

  

尽管同源策略的实现不需要遵循确切的规范，但所有现代浏览器都实现了某种形式的规范。该政策的原则在互联网工程任务组 (IETF) 的RFC6454 中进行了描述。

  

同源策略的实现是用这个规则集定义的：

![](../Images/cbc62762b1a8e54d1dd93d97ea4d745f.png)

同源策略解决了许多挑战，但它的限制性很强。在单页应用程序和媒体密集型网站的时代，同源并没有为这些规则的放松或微调留出很大的空间。

  

CORS 的诞生目标是放宽同源策略并微调跨源访问。

  

**输入 CORS**

到目前为止，我们介绍了什么是源、它是如何定义的、跨源请求的缺点是什么以及浏览器实现的同源策略。

  

现在是时候熟悉跨源资源共享 (CORS) 了。CORS 是一种允许通过网络控制对网页上子资源的访问的机制。该机制将子资源访问分为三类：

1.  跨域写入
    
2.  跨域嵌入
    
3.  跨域读取
    

  

在我们继续解释这些类别中的每一个之前，重要的是要认识到，尽管您的浏览器（默认情况下）可能允许某种类型的跨域请求，但这并不意味着该请求将被服务器接受。

  

跨域写入是链接、重定向和表单提交。在浏览器中激活 CORS 后，这些都是允许的。还有一个叫做预检请求的东西，它可以微调跨域写入，所以虽然默认情况下可能允许某些写入，但这并不意味着它们可以在实践中通过。我们稍后再研究。

  

跨域嵌入功能都可以通过加载子资源：<script>，<link>，<img>，<video>，<audio>，<object>，<embed>，<iframe>等等。这些都是默认允许的。<iframe>是一个特殊的——因为它的目的是在框架内加载不同的页面，它的跨源框架可以通过使用X-Frame-options标题来控制。

  

当涉及到<img>其他可嵌入的子资源时——触发跨域请求是它们的本质。这就是为什么在 CORS 中区分跨域嵌入和跨域读取，并区别对待它们的原因。

  

**跨域读取**是通过 AJAX /fetch调用加载的子资源。这些默认情况下在您的浏览器中被阻止。有一种在页面中嵌入此类子资源的解决方法，但此类技巧由现代浏览器中存在的另一种策略处理。

  

如果您的浏览器是最新的，则所有这些启发式方法都已在其中实现。

**预检请求**

如果我们更深入地查看我们的开发人员控制台，特别是在 Network 选项卡中，我们实际上会注意到两个请求代替了我们发送的请求：

![](../Images/09e16e44cf16b2deeeb9d29bf7599c18.png)

值得注意的是，第一个请求的 HTTP 方法为OPTIONS，而第二个请求的 HTTP 方法为POST.

  

如果我们探索这个OPTIONS请求，我们会看到这是一个在发送我们的POST请求之前由我们的浏览器发送的请求：

![](../Images/61519381272e39d4c07f4dfa8e1edc80.png)

有趣的是，即使对OPTIONS请求的响应是 HTTP 200，它仍然在请求列表中标记为红色。为什么？

  

这是现代浏览器所做的预检请求。对 CORS 认为复杂的请求执行预检请求。复杂请求的标准是：

*   使用比其它方法的请求GET，POST或HEAD
    
*   包含除Accept,Accept-Language或以外的标头的请求Content-Language
    
*   具有的请求Content-Type比其它标头值application/x-www-form-urlencoded，multipart/form-data或text/plain
    

  

因此在上面的例子中，虽然我们发送了一个POST请求，但浏览器由于Content-Type: application/json头部的原因认为我们的请求很复杂。

  

如果我们要更改我们的服务器来处理text/plain内容（而不是 JSON），我们可以解决对预检请求的需求：

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
require "kemal"
get "/" do  "Hello world!"end
get "/greet" do  "Hey!"end
post "/greet" do |env|  body = env.request.body
  name = "there"  name = body.gets.as(String) if !body.nil?
  "Hello, #{name}!"end
Kemal.config.port = 4000Kemal.run
```

  

现在，当我们可以发送带有Content-type: text/plain标头的请求时：

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
fetch(  'http://localhost:4000/greet',  {    method: 'POST',    headers: {      'Content-Type': 'text/plain'    },    body: 'Ilija'  }).then(resp => resp.text()).then(console.log)
```

现在，虽然不会发送预检请求，但浏览器的 CORS 策略将继续阻止：

![](../Images/184d88c396d4b2a7979078719740ed18.png)

但是因为我们制作了一个不归类为complex的请求，我们的浏览器实际上不会阻止该请求：

![](../Images/5ff29ccf4216b994f55de0579aba9497.png)

简单地说：我们的服务器被错误配置为接受text/plain跨域请求，没有任何其他保护，我们的浏览器对此无能为力。但是，它仍然做了下一件最好的事情——它不会将我们打开的页面/标签暴露给该请求的响应。因此，在这种情况下，CORS 不会阻止请求 -它会阻止响应。

  

我们浏览器的 CORS 策略认为这是一种有效的跨域读取，因为尽管请求是作为 发送的POST，但Content-type标头值使其本质上与GET. 默认情况下，跨源读取是被阻止的，因此我们在网络选项卡中看到了被阻止的响应。

  

不建议像上例那样处理预检请求。事实上，如果您希望您的服务器必须优雅地处理预检请求，它应该实现OPTIONS端点并返回正确的标头。

  

在实现OPTIONS端点时，您需要知道浏览器的预检请求会特别查找响应中可能出现的三个标头：

*   Access-Control-Allow-Methods – 它指示响应的 URL 支持哪些方法用于 CORS 协议。
    
*   Access-Control-Allow-Headers - 它指示响应的 URL 支持哪些标头，用于 CORS 协议。
    
*   Access-Control-Max-Age- 它表示可以缓存Access-Control-Allow-Methods和Access-Control-Allow-Headers标头提供的信息的秒数（默认为 5）。
    

  

让我们回到之前发送复杂请求的示例：

*   
*   
*   
*   
*   
*   
*   
*   

```
fetch(  'http://localhost:4000/greet',  {    method: 'POST',    headers: { 'Content-Type': 'application/json' },    body: JSON.stringify({ name: 'Ilija'})  }).then(resp => resp.text()).then(console.log)
```

我们已经确认，当我们发送这个请求时，我们的浏览器会检查服务器是否可以执行跨域请求。为了让这个请求在跨域环境中工作，我们必须首先将OPTIONS /greet端点添加到我们的服务器。在其响应标头中，新端点必须通知浏览器可以接受来自 origin 的POST /greet带有Content-type: application/json标头 的 请求https://www.google.com。

  

我们将通过使用Access-Control-Allow-\*标题来做到这一点：

*   
*   
*   
*   
*   
*   
*   
*   

```
options "/greet" do |env|  # Allow `POST /greet`...  env.response.headers["Access-Control-Allow-Methods"] = "POST"  # ...with `Content-type` header in the request...  env.response.headers["Access-Control-Allow-Headers"] = "Content-type"  # ...from https://www.google.com origin.  env.response.headers["Access-Control-Allow-Origin"] = "https://www.google.com"end
```

如果我们启动我们的服务器并发送请求：

![](../Images/ce663347da941956415e39fe64188191.png)

我们的请求仍然被阻止。即使我们的OPTIONS /greet端点确实允许请求，我们仍然看到错误消息。在我们的网络标签中有一些有趣的事情发生：

对OPTIONS /greet端点的请求成功！但是POST /greet通话还是失败了。如果我们看一下POST /greet请求的内部结构，我们会看到一个熟悉的景象：

![](../Images/973aad5116d11688c29edcff4c6b2758.png)

事实上，请求确实成功了——服务器返回了一个 HTTP 200。预检请求确实有效——浏览器确实发出了POST请求而不是阻止它。但是POST请求的响应不包含任何 CORS 标头，因此即使浏览器确实发出了请求，它也会阻止任何响应处理。

  

为了让浏览器也处理来自POST /greet请求的响应，我们还需要向POST端点添加一个 CORS 标头：

*   
*   
*   
*   
*   
*   
*   

```
post "/greet" do |env|  name = env.params.json["name"].as(String)
  env.response.headers["Access-Control-Allow-Origin"] = "https://www.google.com"
  "Hello, #{name}!"end
```

通过添加Access-Control-Allow-Origin标头响应标头，我们告诉浏览器https://www.google.com打开的选项卡也可以访问响应负载。

  

如果我们再试一次：

![](../Images/d76de1e035fd09ca283465bd6497ca00.png)

我们会看到POST /greet确实得到了我们的回应，没有任何错误。如果我们看一下 Network 选项卡，我们会看到两个请求都是绿色的：

![](../Images/5f0fa835f8c65572047c21b258a34c64.png)

通过在我们的预检端点上使用正确的响应头OPTIONS /greet，我们解锁了我们服务器的POST /greet端点，以便跨不同来源访问。最重要的是，通过在POST /greet端点的响应上提供正确的 CORS 响应标头，我们释放了浏览器来处理响应而没有任何阻塞。

  

**跨域读取**

正如我们之前提到的，默认情况下会阻止跨源读取。这是故意的 - 我们不希望从我们源范围内的其他源加载其他资源。

  

比如说，我们GET /greet在 Crystal 服务器中有一个操作：

*   
*   
*   

```
get "/greet" do  "Hey!"end
```

从我们的标签已经www.google.com呈现，如果我们试图fetch在GET /greet我们将得到阻止CORS端点：

![](../Images/4c9f67c72927f061e54e9f9844dc1bab.png)

如果我们更深入地查看请求，我们会发现一些有趣的事情：

![](../Images/9d44e3f19087c71e3c70447fc4185e48.png)

事实上，就像以前一样，我们的浏览器确实让请求通过了——我们得到了一个 HTTP 200。但它并没有将我们打开的页面/标签暴露给该请求的响应。同样，在这种情况下，CORS 不会阻止请求 -它会阻止响应。

  

就像跨域写入一样，我们可以放宽 CORS 并使其可用于跨域读取 - 通过添加Access-Control-Allow Origin标题：

*   
*   
*   
*   

```
get "/greet" do |env|  env.response.headers["Access-Control-Allow-Origin"] = "https://www.google.com"  "Hey!"end
```

当浏览器从服务器获取响应时，它会查看`Access-Control-Allow-Origin`标头并根据其值决定是否可以让页面读取响应。鉴于本例中的值是`https://www.google.com`我们在示例中使用的页面，结果将是成功的：

![](../Images/3649acbc731b03e3075ff7cef773a434.png)

这就是浏览器如何保护我们免受跨域读取并尊重通过标头发送的服务器指令。

  

**微调 CORS**

**一些最佳实践**

在结束之前，让我们先介绍一些跨域资源共享 (CORS) 的最佳实践。

  

**所有人免费**

一个常见的例子是，如果您拥有一个向公众显示内容的网站，该网站没有付费墙，或者需要身份验证或授权，您应该能够设置Access-Control-Allow-Origin: \*其资源。

  

\*在以下情况下，该值是一个不错的选择：

*   无需身份验证或授权
    
*   资源应该可供广泛的用户无限制地访问
    
*   将访问资源的来源和客户多种多样，您不了解或根本不在乎
    

这种配置的一个危险前景是当涉及到在专用网络上（即在防火墙或 VPN 后面）提供的内容时。当您通过 VPN 连接时，您可以访问公司网络上的文件：

![](../Images/96c0c8b616997860fc26e965d7c96cb4.png)现在，如果攻击者作为网站托管dangerous.com，其中包含指向 VPN 内文件的链接，他们可以（理论上）在他们的网站上创建一个可以访问该文件的脚本：

![](../Images/da6b055025e45dc867ea9c604cb1d8bf.png)

虽然这种攻击很困难，并且需要大量关于 VPN 和其中存储的文件的知识，但它是我们必须意识到的潜在攻击媒介。

  

**把它留在家里**

继续上面的例子，假设我们想为我们的网站实施分析。我们希望用户的浏览器向我们发送有关用户在我们网站上的体验和行为的数据。

  

一种常见的方法是在浏览器中使用 JavaScript 使用异步请求定期发送该数据。在后端，我们有一个简单的 API，它接收来自用户浏览器的这些请求，并将数据存储在后端以供进一步处理。

  

在这种情况下，我们的 API 是公开的，但我们不希望任何网站将数据发送到我们的分析 API。事实上，我们只对来自呈现我们网站的浏览器的请求感兴趣——仅此而已。

![](../Images/4216660338fbf93662ee1ef5ca04088d.png)

在这种情况下，我们希望我们的 API 将Access-Control-Allow-Origin标头设置为我们网站的 URL。这将确保浏览器永远不会从其他页面向我们的 API 发送请求。

  

如果用户或其他网站试图在我们的分析 API 中填充数据，我们 APIAccess-Control-Allow-Origin资源上设置的标头不会让请求通过：

![](../Images/f91531773b149742d27a70938be1a4f7.png)

**NULL 起源**

另一个有趣的案例是null起源。当呈现本地文件的浏览器访问资源时，就会发生这种情况。例如，来自本地机器上静态文件中运行的某些 JavaScript 的请求将Origin标头设置为null.

  

在这种情况下，如果我们的服务器现在允许访问源的资源null，那么它可能会阻碍开发人员的工作效率。null必须有意在 CORS 策略中允许来源，并且仅当您的网站/产品的用户是开发人员时。

  

**如果可以，请跳过 cookie**

正如我们之前在 中看到的Access-Control-Allow-Credentials，默认情况下不启用 cookie。要允许跨域发送 cookie，就像返回Access-Control-Allow-Credentials: true. 这个标头会告诉浏览器他们被允许在跨域请求中发送凭证（即 cookie）。

  

允许和接受跨域 cookie 可能很棘手。您可能会将自己暴露在潜在的攻击媒介中，因此仅在绝对必要时才启用它们。

  

当您确切知道哪些客户端将访问您的服务器时，跨源 cookie 效果最佳。这就是 CORS 语义不允许我们设置Access-Control-Allow-Origin: \*何时允许跨域凭据的原因。

  

虽然Access-Control-Allow-Origin: \*andAccess-Control-Allow-Credentials: true组合在技术上是允许的，但它是一种反模式，绝对应该避免。

  

如果您希望您的服务器被不同的客户端和来源访问，您可能应该考虑构建 API（使用基于令牌的身份验证）而不是使用 cookie。但是，如果沿着 API 路径走下去不是一种选择，那么请确保实施跨站点请求伪造 (CSRF) 保护。
