#### 介绍

这篇文章是该漏洞故事的第二部分，该漏洞可以被利用为供应链攻击，并且可以用于黑客攻击全球数百万的软件开发人员。

我们将描述有关CVE-2020-26233的所有详细信息，该漏洞会影响适用于Windows的Github CLI工具（也称为gh）中Git Credential Manager Core 2.0.280以下的所有版本。

#### 问题说明

这个问题类似于我们在博客中发现并发布的Github for Desktop远程执行代码，但是这次另一个组件受到了影响：Git Credential Manager Core。

默认情况下，当Git克隆带有子模块的存储库时，它首先克隆存储库的顶层，然后递归地克隆子模块。但是，这样做时，它会从顶层目录中启动一个新的Git进程。

如果将名为git.exe的恶意可执行文件放置在存储库的根目录中，则在尝试读取配置时，Git凭据管理器核心将调用此二进制文件。克隆过程正常进行，并且没有视觉迹象表明运行了恶意二进制文件，而不是原始的git可执行文件。

自2020年11月我们的第一份报告以来，Github创建了一个库SafeExec，以缓解Windows中二进制文件搜索顺序差异带来的风险。

快速回顾一下，Windows首先检查当前文件夹中是否存在给定的二进制文件，并且只有在找不到该二进制文件时，才遍历％PATH％环境变量中的目录，直到找到有问题的可执行文件为止。

在gh版本1.2.1中，引入了*safeexec.LookPath*函数，从理论上讲，当通过滥用Windows路径搜索顺序来克隆新存储库时，不允许执行远程代码。

![](../Images/30d361cd863634b9920b02bde44bb679.png)

仔细研究后，我们的安全工程师Vitor Fernandes发现了一个旁路，可以像以前一样利用该旁路来实现RCE。

在漏洞发现过程中，Blaze注意到，在创建新的私有存储库时，仍然有可能执行远程代码执行，这是因为在克隆命令*git.exe config credential.namespace之后*，没有使用*safeexec.LookPath*函数，因此Windows将回*退到*其默认值，并在当前克隆的存储库中搜索git.exe二进制文件：

#### 利用漏洞

要利用此问题，需要执行以下步骤：

1.  a）创建一个新的存储库或将文件添加到现有存储库的能力；
    
2.  b）将Windows可执行文件上载到此存储库，并将其重命名为git.exe；
    
3.  c）等待受害者分叉存储库
    
4.  d）享受你的贝壳
    

在下面的示例中，calc.exe被重命名为git.exe并被推送到存储库中：

#### 修补程序和解决方法

GCM Core版本2.0.289包含针对此漏洞的修复程序。它也捆绑在Windows 2.29.2（3）的Git中。

\[1\]中建议的解决方法指示用户避免使用--recurse-submodules命令行开关递归地克隆不受信任的存储库。

提交5b4a08dcb9bc63f8da5f966b4e47d73edf87f3b7引入了对此漏洞的修复程序。
