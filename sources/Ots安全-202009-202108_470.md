在参与过程中，我们发现其基础结构核心部分存在各种漏洞，这些漏洞可能使攻击者完全破坏客户和员工的应用程序，启动能够自动接管受害者的iCloud帐户的蠕虫，并检索内部的源代码。Apple计划充分利用Apple使用的工业控制仓库软件，并接管具有访问管理工具和敏感资源能力的Apple员工会议。

总共发现55个漏洞，其中11个严重严重性，29个高严重性，13个中严重性和2个低严重性报告。我们出于汇总目的评估了这些严重性，并且取决于CVSS和我们对与业务相关的影响的理解。

截至2020年10月6日，这些发现中的绝大多数已得到修复并得到认可。通常会在1-2个工作日内对它们进行补救（其中一些修复会在4-6个小时之内完成）。

## 介绍

当我在7月左右某个时间滚动浏览Twitter时，我注意到有一篇博客文章被分享，一位研究人员因发现身份验证绕行而获得苹果公司10万美元的奖励，该绕行使得他们可以随意访问任何Apple客户帐户。这让我感到惊讶，因为我以前了解到，Apple的漏洞赏金计划仅授予影响其物理产品的安全漏洞，而没有为影响其Web资产的问题付款。

读完这篇文章后，我进行了一次Google快速搜索，找到了他们的程序页面，其中详细说明了Apple愿意为“对用户有重大影响”的漏洞支付费用，而不管资产是否在范围内明确列出。

这引起了我的注意，因为这是一个有趣的机会，可以研究一个似乎范围广泛且有趣的新程序。当时我从未从事过Apple Bug赏金计划，因此我真的不知道该期待什么，但决定为什么不试试我的运气，看看能找到什么。

为了使该项目更有趣，我向过去与之合作过的黑客发送了一些消息，并询问他们是否愿意在该程序上共同努力。即使不能保证支出，也不能保证程序的工作原理，但每个人都说可以，我们开始在Apple上进行黑客攻击。

## 侦察

入侵Apple的第一步是弄清楚实际目标是什么。Ben和Tanner都是这里的专家，所以他们开始弄清楚我们可以访问的所有Apple拥有的东西。他们扫描的所有结果都在仪表板中建立了索引，该仪表板包括HTTP状态代码，标头，响应正文以及Apple拥有的各个域下可访问的Web服务器的屏幕快照，我们将在参与过程中参考这些屏幕。

![](../Images/d8d5e0ca2b61bf5177595ac233480851.png)

简而言之：苹果的基础设施规模巨大。

他们拥有整个17.0.0.0/8 IP范围，其中包括25,000个Web服务器，其中apple.com下拥有10,000个Web服务器，另外7,000个唯一域，最重要的是拥有自己的TLD（点苹果）。我们的时间主要花费在17.0.0.0/8 IP范围，.apple.com和.icloud.com上，因为那是有趣的功能所在。

列出所有Web服务器后，我们开始在更有趣的服务器上运行目录暴力破解。

自动扫描的一些直接发现是...

*   受Cisco CVE-2020-3452本地文件读取1天（x22）影响的VPN服务器
    
*   破碎页面上的错误消息中泄漏的Spotify访问令牌
    

这些过程获得的信息有助于理解授权/身份验证在整个Apple中的工作方式，存在的客户/员工应用程序，使用的集成/开发工具以及各种可观察到的行为，例如使用某些Cookie或重定向到某些应用程序的Web服务器。

在完成所有扫描之后，我们认为我们对Apple基础架构有了一个总体了解，我们开始针对单个Web服务器，这些Web服务器本能地比其他服务器更容易受到攻击。

这开始了一系列发现，这些发现在我们的整个参与过程中一直持续，并逐渐增加了我们对Apple计划的了解。

## 通过身份验证和授权绕过Apple杰出教育者计划的全面妥协

我们花费大量时间进行黑客入侵的第一批服务之一是“苹果杰出教育者”网站。这是一个仅限邀请的Jive论坛，用户可以在其中使用其Apple帐户进行身份验证。这个论坛的有趣之处在于，一些注册到该应用程序的Jive核心功能是通过Apple构建的自定义中间件页面移植的，目的是将其身份验证系统（IDMSA）连接到通常使用用户名/密码身份验证的底层Jive论坛。。

![](../Images/cfa99c03b1eb46b7a2e67d5348bf40ab.png)

这样做是为了使用户可以轻松地使用其现有的Apple帐户向论坛进行身份验证，而不必处理创建其他用户帐户的问题。您只需使用“使用Apple登录”并登录到论坛即可。

不允许访问论坛的用户的登录页面是一个应用程序门户，您在其中提供了有关您自己的信息，论坛主持人对该信息进行了评估以供批准。

![](../Images/9aaad15ebff9825ec3bd346ae1ba0fcc.png)

当您提交使用该论坛的应用程序时，您几乎提供了帐户的所有值，就像您正常注册到Jive论坛一样。这将使Jive论坛根据IDMSA cookie知道您是谁，因为它将您属于Apple帐户的电子邮件地址绑定到了该论坛。

在应用程序内要注册使用该论坛的页面上隐藏的值之一是“ password”字段，其值为“ *\### INvALID＃％！3* ”。当您提交包含用户名，名字和姓氏，电子邮件地址和雇主的应用程序时，您还提交了一个“密码”值，该值然后秘密地绑定到您来自页面上隐藏输入字段的帐户。

观察到隐藏的默认密码字段后，我们立即想到了一种方法，可以手动对应用程序进行身份验证并访问论坛的批准帐户，而不必尝试使用“使用Apple登录”系统登录。我们对此进行了调查，因为我们每个人在单独注册时的密码都相同。

如果有人使用此系统提出申请，并且存在可以手动进行身份验证的功能，则只需使用默认密码登录到他们的帐户，然后完全绕过“使用Apple登录”登录即可。

乍一看，您似乎似乎无法手动进行身份验证，但是经过几次Google搜索后，我们发现了一个“ cs\_login”端点，该端点用于使用用户名和密码登录Jive应用程序。当我们手动形成测试HTTP请求以对Apple Distinguished Developers应用程序进行身份验证时，我们发现它尝试通过显示错误的密码错误来对我们进行身份验证。当我们使用以前使用的自己的帐户时，该应用程序出现错误，并且由于我们尚未获得批准，因此不允许我们进行身份验证。如果要进行身份验证，我们将必须找到已批准成员的用户名。

![](../Images/1e528d4aa9a06b5fdbbde0fee8db14d4.png)

此时，我们将HTTP请求加载到Burp Suite的入侵者中，并尝试通过登录名和默认密码强行使用1到3个字符的用户名。

大约两分钟后，我们收到302响应，指示使用我们之前找到的默认密码成功登录了具有3个字符用户名的用户。我们进去了！从这一点出发，我们的下一个目标是对具有提升权限的人员进行身份验证。我们截取了一些访问权限的屏幕快照，然后单击“用户”列表以查看哪些用户是管理员。我们登录到列表中看到的第一个帐户，以试图证明我们可以通过管理功能实现远程代码执行，但是，仍然存在一些障碍。

![](../Images/39f3683a23c2dc8ac5319ba43e77d9a7.png)

尝试以admin帐户浏览到“ / admin /”（Jive管理员控制台）时，该应用程序将重定向为登录，就好像我们尚未通过身份验证一样。这很奇怪，因为它是Jive应用程序的自定义行为，而且我们之前都没有人观察到这一点。我们的猜测是，Apple限制了基于IP地址的管理控制台，以确保永远不会完全破坏该应用程序。

我们尝试的第一件事之一是使用X-Forwarded-For标头绕过假设的限制，但不幸的是，此操作失败了。我们接下来尝试做的是加载另一种形式的“ / admin /”，以防应用程序具有访问管理员控制台的特定于路径的黑名单。

在再执行几个HTTP请求之后，我们发现“ GET / admin; /”将使攻击者可以访问管理控制台。我们通过设置Burp Suite规则自动执行此绕过操作，该规则在HTTP请求中将“ GET / POST / admin /”自动更改为“ GET / POST / admin; /”。

![](../Images/76b1d6ce00e85797c503c0bc32e316c5.png)

当我们最终导航并加载管理控制台时，立即很清楚，有些事情是不对的。我们无法使用演示远程代码执行的常规功能（没有模板，插件上传或标准的管理调试功能）。  

![](../Images/1f16309db37716ce463aa94c36ccb48b.png)

在这一点上，我们停止思考我们在哪里，并且意识到我们通过身份验证的帐户可能不是应用程序的“核心”管理员。我们继续进行并通过了2-3个帐户的身份验证，然后最终以核心管理员身份进行身份验证，并看到了可以远程执行代码的功能。

![](../Images/919bce6485177a851b855a080d72a358.png)

攻击者可能（1）使用隐藏的默认登录功能通过手动身份验证来绕过身份验证，然后（2）通过在请求中发送修改后的HTTP路径来访问管理控制台，最后（3）使用一个完全破坏应用程序许多“嵌入RCE”功能中，例如插件上传，模板化或文件管理。

总体而言，这将使攻击者能够...

*   在ade.apple.com网站服务器上执行任意命令
    
*   访问内部LDAP服务以管理用户帐户
    
*   访问苹果大部分内部网络
    

至此，我们完成了报告并提交了所有内容。

## 通过身份验证旁路完全破坏了DELMIA Apriso应用程序

在黑客入侵苹果公司时，我们曾想过很多事情，即他们是否拥有与产品制造和分销有关的任何可访问服务。事实证明，有一个名为“ DELMIA Apriso”的应用程序，它是第三方“ Global Manufacturing Suite”，提供了各种仓库解决方案。

![](../Images/2db32c53befe1ce1189dfc3675611b62.png)

遗憾的是，该技术似乎没有太多可用的交互方式，因为您只能从可用界面中“登录”和“重置密码”。

![](../Images/8f3065222a533ab7ffa9737d104ad663.png)

尝试在有限数量的页面上找到漏洞后，发生了一件奇怪的事情：我们通过一个名为“ Apple No Password User”的用户身份验证，该用户基于网站右上方的栏。  

![](../Images/ccb934c1a9bb1c2e2b058a97b8d68f3b.png)

发生的事情是，通过单击“重置密码”，我们被临时认证为具有“权限”才能使用该页面的用户。

### 通过样式标签混淆存储XSS

### 通过超链接混淆存储XSS

后来，我发现了另一个跨站点脚本漏洞，以类似方式影响邮件。

我将始终对这类半HTML应用程序进行检查的一件事是它们如何处理超链接。自动将未标记的URL转换为超链接似乎很直观，但是如果未正确清理或与其他功能组合使用，则可能会变得混乱。由于依赖于正则表达式，innerHTML和可以在URL旁边添加的所有接受的元素，因此这是寻找XSS的常见位置。

此XSS的第二个有趣功能是完全删除某些标签，例如“ <script>”和“ <iframe>”。这很整洁，因为某些东西将依赖于字符，例如空格，制表符和换行符，而remove标记留下的空白可以提供这些字符而无需告知JavaScript解析器。这些差异使攻击者可以混淆应用程序，并潜入可以调用XSS的恶意字符中。

我花了一段时间来研究这两种功能（自动超链接和某些标签的完全删除），直到决定将两者结合起来并尝试观察它们的表现方式。令我惊讶的是，以下字符串破坏了超链接功能并混淆了DOM：

```
https://www.domain.com/abc#<script></script>https://domain.com/abc
```

在通过电子邮件本身发送以上内容之后，将内容解析为以下内容：

```
<a href="https://www.domain.com/abc#<a href=" https:="" www.domain.com="" abc="&quot;" rel="noopener noreferrer">https://www.domain.com/abc</a>
```

最初看起来很有趣，但要利用它会有点困难。在标记内定义属性很容易（例如src，onmouseover，onclick等），但是要提供这些值很困难，因为我们仍然必须匹配URL正则表达式，这样就无法避免自动超链接功能。最终在不发送单引号，双引号，括号，空格或反引号的情况下有效负载如下：

```
https://www.icloud.com/mail/#<script></script>https://www.icloud.com/onmouseover=location=/javascript:alert%28document.domain%29/.source;//
```

有效负载是在DOM中产生的：

```
<a href="https://www.icloud.com/mail#<a href=" https:="" www.icloud.com="" onmouseover="location=/javascript:alert%28document.domain%29/.source;//&quot;">https://www.icloud.com/onmouseover=location=/javascript:alert%28document.domain%29/.source;//</a>
```

并给了我们这个美丽的警报提示：

![](../Images/278d5c968b3928002d51b62082ec7aa2.png)

该有效负载来自@Blaklis\_的CTF解决方案。我原本以为这可能是无法利用的XSS，但似乎总是存在针对边缘案例XSS的解决方案。

我最好的解释是（1）加载初始URL时，“ <script> </ script>”中的字符在自动超链接过程中是可接受的，并且没有破坏它，然后（2）删除了脚本标签创建了一个空间或某种空隙，这些空间或空隙在不关闭初始超链接功能的情况下重置了自动超链接功能，最后（3），第二个超链接添加了额外的引号，该引号用于打破href和创建onmouseover事件处理程序。

第二个XSS的影响与第一个XSS相同，不同之处在于，用户必须通过将鼠标置于电子邮件正文中的某个位置来触发onmouseover事件处理程序，但是可以简化此部分以使其更容易触发。整个电子邮件的超链接。

*   在受害者的浏览器中静默执行任意HTML和JavaScript

由于应用程序是内部应用程序，而我们不是真正的攻击者，因此在每次发现时都在此停止。这些应用程序将使攻击者至少能够泄露大量有关Apple内部物流和员工/用户的敏感信息。

## 结论

当我们刚开始这个项目时，我们不知道我们会花三个多月的时间来完成它。最初，这原本是一个附属项目，我们会不时进行，但是由于大流行的所有额外空闲时间，我们每个人最终都花了数百个小时。

总体而言，苹果对我们的报告反应非常快。我们提交的更重要的报告仅在提交和修复之间有四个小时的时间。

由于没有人真正了解他们的错误赏金计划，因此，我们投入了大量的时间几乎进入了未知的领域。苹果与安全研究人员合作已有一段有趣的历史，但看来他们的漏洞披露计划是朝着与黑客合作以保护资产并允许有兴趣的人查找和报告漏洞的正确方向迈出的重要一步。

写这篇博客文章是一个有趣的过程，因为我们不确定如何实际去做。坦白说，我们发现的每个错误都可能变成了包含大量随机信息的完整文章。苹果公司使用的身份验证系统相当复杂，用1-2个句子引用它，就好像我们在欺骗某人的信息一样。关于苹果基础设施中的许多元素，例如iCloud，苹果商店和开发者平台，也可以说同样的话。

截至10月8日，我们已针对各种漏洞共收到32笔付款，总计288,500美元。

但是，Apple似乎分批付款，并可能在接下来的几个月中为更多问题付款。

我们已获得Apple安全团队（product-security@apple.com）的许可，以发布此内容，并由其自行决定。此处披露的所有漏洞均已修复并重新测试。未经苹果许可，请勿泄露与苹果安全有关的信息。
