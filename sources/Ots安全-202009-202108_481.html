就在几天前，FortiGuard Labs捕获了一个网络钓鱼活动，其中以电子邮件附件形式发送的恶意Microsoft Excel文档正在传播Dridex的新变体。Dridex是一种特洛伊木马恶意软件，也称为Bugat和Cridex，它能够从受感染的计算机中窃取受害者的网上银行和系统信息。

我对Excel文档以及恶意宏在Excel文档中下载的Dridex有效负载文件进行了深入分析。在这篇文章中，我提供以下信息：宏如何下载Dridex有效负载，Dridex有效负载文件如何启动，其用于执行反分析的技术，它从受害人的计算机中收集了什么信息以及如何收集这些信息。信息将发送到其C2服务器。

在Regsvr32.exe中解压缩Dridex并导出功能

Dridex在regsvr32.exe进程中执行，该进程是Microsoft Windows的命令行实用程序进程，用于在操作系统注册表中注册和注销DLL和ActiveX控件。下载的Dridex有效负载文件是这些DLL文件之一。图2.1是在“ regsvr32.exe”中运行Dridex的进程树的屏幕截图。

图2.1。在regsrv32.exe中运行Dridex的进程树

Regsvr32.exe加载Dridex有效负载文件并调用其DllEntryPoint（）函数以执行初始化工作。 

它具有7B600H大小的加密数据块，包括数据和代码。将其解密并提取到新创建的内存缓冲区中。然后，它跳转到解密的代码，其地址已加载到EAX中。整个过程看起来像一个解压缩过程。图2.2显示了将要跳转到提取的代码时的代码上下文。

图2.2。执行提取的代码之前的代码

执行代码可以将完整的PE文件（即Dridex核心模块）解密并提取到内存中。然后将PE文件部署到可执行空间中。该过程就像Windows OS加载要执行的EXE文件的方式一样，包括但不限于将部分复制到相对虚拟地址（RVA），加载导入的API，调整重定位数据等等。

完成上述所有工作后，最终通过一段ASM代码调用提取的PE的Entry Point函数，如图2.3所示。它使用ASM代码“ push edx”和“ retn”，此处类似于“ jmp edx”。

图2.3。跳转到提取的Dridex核心模块的入口点

 经过上述两次解压缩后，Dridex核心模块现已退出。

遍历核心Dridex，您会发现其中有两个导出函数–“ DllEntryPoint（）”和“ DllRegisterServer（）”。“ DllEntryPoint（）”是图2.3中所称的那个。  

可以通过“ regsvr32.exe”注册的每个DLL文件都必须提供一个名为“ DllRegisterServer（）”的导出功能。MSDN（Microsoft开发人员网络）说，此功能“指示进程内服务器为此服务器模块中支持的所有类创建其注册表项。”

请记住，我们仍然在“ regsvr32.exe”最初调用的函数DllEntryPoint（）中。在核心Dridex的Entry Point函数中，它执行一些初始化工作。当“ regsvr32.exe”从该函数接收到“ 1”时，表示初始化工作已成功完成。然后，“ regsvr32.exe”调用API GetProcAddress（）来查找具有名称的“ DllRegisterServer（）”的导出函数地址。图2.4是当“ regsvr32.exe”调用API GetProcAddress（）以从核心Dridex获取导出函数“ DllRegisterServer（）”时截取的屏幕截图。

图2.4。“ regsvr32.exe”调用GetProcAddress（）获得DllRegisterServer（）

Dridex中使用的反分析技术

Dridex开发人员将其所有恶意工作放入DllRegisterServer（）函数中，该函数可以视为其他正常进程的Main（）函数。

在核心Dridex中观察到许多反分析技术，以防止对其代码进行分析。在本节中，我将介绍其中一些。

隐藏的API 

大多数Windows API函数都是隐藏的，在调用之前将对其进行检索。这给静态分析带来了更多困难。一个函数（在本文中称为GetAPIByHash（））通过其哈希码检索API。

图3.1检索API RegEnumKeyW（）的示例

图3.1显示了使用需要两个参数的GetAPIByHash（）检索API RegEnumKeyW（）的示例。第一个是名为“ ADVAPI32.DLL”的模块的XORed CRC32码的哈希值（68EFDF75h）（全部为大写），常数为6AECC489h。第二个是名为“ RegEnumKeyW”的API的XORed CRC32代码的哈希值（0A7373679h），常数为6AECC489h。 

在这种情况下，“ RegEnumKeyW”的CRC32码为CDDBF2F0H，将其与常数6AECC489h异或等于0A7373679h。

GetAPIByHash（）枚举指定模块中的所有API，以通过比较传入的哈希码参数来发现API。匹配时，它将以EAX返回API地址。

字符串已加密

整个核心Dridex都对密钥字符串进行了加密。因此，分析人员无法通过简单地在其存储空间中搜索键字符串来找到其行为。就像隐藏的API一样，字符串在使用前会被解密。图3.2是解密Unicode字符串“ POST”的示例。函数813B00是具有三个参数的解密函数。ECX是要解密的字符串的索引（“ GET”为0，“ POST”为1）。8296D0指向加密字符串的缓冲区。

生成调用API的异常

如前所述，该恶意软件不仅具有隐藏的API，而且在调用这些隐藏的API时还会使用技巧。再次参考图3.1，它的底部有ASM代码“ int 3”，它会生成一个异常，代码为80000003（BREAKPOINT陷阱）。它中断执行并等待直到异常被处理。

Dridex设法在其Entry Point函数中设置了一个异常处理程序（像Try…Catch块这样的本地函数）。为此，它调用API RtlAddVectoredExceptionHandler（）以将本地函数添加为异常处理程序。这样，每当Dridex导致任何异常时，都会首先调用此局部函数来处理它。 

调用本地异常处理程序时，在参数中它是一个数据_EXCEPTION_RECORD，该数据包含异常信息和具有异常处所有寄存器的值的上下文结构，其中EAX寄存器保存了被调用的API。然后，它将EAX值压入堆栈并修改其他寄存器的值，例如EIP和ESP。在函数的末尾，它返回0FFFFFFFFh（-1），代表 EXCEPTION_CONTINUE_EXECUTION，告诉系统使用修改后的值还原整个寄存器。最后，它从异常行的下一行开始运行该过程，在该行中将使用带有自变量的参数从堆栈中调用该API，所有这些都已在异常发生之前被压入堆栈。

这是Dridex如何使用异常调用API的完整机制。图3.3显示了本地异常处理程序功能。

图3.3本地异常处理程序功能的视图

除此之外，如果Dridex由执行单步跟踪的调试器附加，则它可以生成EXCEPTION_SINGLE_STEP异常（代码80000004）。本地异常处理程序可以识别此异常，并修改寄存器的值以使Dridex崩溃，以保护自身免受分析和调试。 

将收集的信息发送到C2服务器

在DllRegisterServer（）函数中，Dridex从受害者的计算机收集信息，然后将信息发送到其C2服务器。在本节中，我将解释Dridex如何做到这一点。

首先，它获取受害者的用户名和完整的计算机名。然后，它从系统注册表中读取Windows安装时间。将以上值放在一起，并用它们制成MD5值。数据包的第一部分（2Fh长）由数据长度+计算机名称+ MD5值组成。然后，它将通过调用API GetVolumeInformationW（）获得的VolumeInformation数据（20h长的十六进制值）附加到数据包缓冲区中。以下数据是常量字值“ 29 3B”和来自API GetVersion（）的组合系统版本的双字。“ 18F8C844h”是附加到分组的分组ID。有关更多信息，请参考图4.2。

Dridex从受害者的系统注册表中收集所有已安装的软件信息。它导航到子项“ HKEY_LOCAL_MACHINE \ SOFTWARE \ Microsoft \ Windows \ CurrentVersion \ Uninstall”，并枚举所有子项，并从中读出它们的值DisplayName和DisplayVersion。在“卸载”下，具有所有已安装的软件注册表信息，供卸载时使用。

例如，读取的7-Zip信息为“ 7-Zip 18.05（18.05）”，如图4.1所示。

图4.1已安装的7-Zip子项信息

长度（以网络字节顺序排列的双字）和整个收集的软件信息将被附加到数据包中。

数据包的最后一部分来自受害者的系统环境变量。为此，Dridex调用API GetEnvironmentStringsW（），该API返回指向包含环境变量的内存块的指针。然后将它们格式化并在收集到的软件信息之后附加到数据包中。 

图4.2显示了数据包的轮廓，其中带红色下划线的值是按照网络字节顺序排列的数据长度，用蓝色竖线分隔的值是我之前已经解释过的数据字段。

图4.2。Dridex从我的测试机收集数据

整个收集的数据将使用RC4算法进行加密，以在传输过程中对其进行保护。这意味着最终的数据包将以整个密文数据的dword CRC32值开头，然后将是密文。

图4.3以二进制形式显示硬编码的C2服务器IP和端口

如图4.3所示，Dridex的这种变体具有四个以二进制形式进行硬编码的C2服务器。Dridex重复向他们发送最终数据包，直到收到HTTP状态为“ 200 OK”的响应数据包为止。

为此，它将调用以下API：InternetOpenA（），InternetConnectW（），HttpOpenRequestW（），HttpSendRequestW（）和InternetReadFile（），所有这些均由GetAPIByHash（）检索。

到目前为止，我们还没有收到来自那些C2服务器的“ 200 OK”响应。因此，我们不知道此Dridex广告系列还有什么其他任务。我们将继续对其进行监控。
