**概述**

SIGRed，CVE-2020-1350，是 Microsoft Windows DNS 服务中的一个漏洞，于 2020 年 7 月 14 日披露。它是由 Check Point Research \[1\]的 Sagi Tzadik 发现的，他发布了一篇关于补丁发布当天的错误。该漏洞的 CVSS 评分为 10.0，这是最高级别的严重性。在 Windows 上，DNS 服务器是域控制器，其管理员是域管理员组的一部分。默认情况下，域管理员组是已加入域的所有计算机上的管理员组的成员，包括域控制器\[8\]. 如果仔细利用，攻击者可以在易受攻击的系统上远程执行代码并获得域管理员权限，从而有效地破坏整个公司基础设施。这篇文章详细介绍了已发布的概念证明 \[2\]中使用的利用方法。

  

**漏洞**

CVE-2020-1350 是一个整数溢出漏洞，在处理格式错误的 DNS SIG资源记录时会导致基于堆的缓冲区溢出。SIG记录是一种DNS 资源记录，包含记录集的数字签名（一个或多个具有相同名称和类型的 DNS 记录）\[10\]。为了利用 SIGRed，攻击者可以配置一个“邪恶”域，其NS记录指向恶意 DNS 服务器。当客户端向受害者服务器发出“邪恶”域的 DNS 查询时，受害者服务器将查询其上方的 DNS 服务器。DNS 服务器将返回一条 NS 记录，表明恶意 DNS 服务器是该域的权限，并且该记录将被受害者缓存。之后，当客户端向受害者发送域的 DNS SIG查询时，受害者服务器将查询恶意 DNS 服务器。恶意 DNS 服务器将发送格式错误的 DNS SIG记录作为响应。

![](../Images/6ce567cb84a2624e81cae94fe88d23f0.png)

攻击者如何利用 SIGRed

  

该漏洞存在于函数dns!SigWireRead（在 DNS 服务二进制文件dns.exe 中）中，该函数用于缓存来自另一个 DNS 服务器的 DNS SIG记录响应。

![](../Images/34fdd20990068613a5a39eb0507bcabb.png)

反编译易受攻击的函数，dns!SigWireRead

参考易受攻击函数dns!SigWireRead的反编译中的第11行。函数RR\_AllocateEx为 size 参数传递了一个 16 位无符号整数。可以发送 DNS SIG记录响应，使得计算的大小大于 0xFFFF，这会触发整数溢出。

  

**触发漏洞**

由于数据包大小的限制，仅通过发送具有非常大签名的SIG记录是不可能触发漏洞的。事实上，通过 UDP 触发漏洞是不可能的，因为通过 UDP 的 DNS 消息的最大允许大小是 512 或 4096 字节，具体取决于服务器是否支持EDNS0。在任何一种情况下，仅仅触发漏洞都是不够的。使用 DNS 截断\[9\]，恶意 DNS 服务器可以告诉受害者服务器通过 TCP 重试请求。TCP 上的 DNS 消息的总大小限制为 64KB (0xFFFF)。这仍然不足以触发漏洞，因为消息限制包括标题空间和原始查询。

  

**DNS 名称压缩**

DNS 名称可以并且经常被压缩在 DNS 消息中。通过在 TCP 上操纵 DNS 消息中名称的压缩，可以在不增加 DNS 消息总大小的情况下膨胀sigName.Length 。

![](../Images/1410b510ae433995daccab4a61bf7ed3.png)

DNS 消息包中的 DNS 名称压缩

  

在上面的示例中，0xC0 字节（在上面的绿色框中突出显示）设置了最高有效两位。这表明后面的 14 位表示 DNS 名称的偏移量，相对于 DNS 消息的开头。在上图中的示例中，它是从消息开头开始的 0xC 字节（在蓝色框中突出显示）。

  

DNS 名称编码如下：单个字节表示 '.' 之前的字符数。字符，以空字节结尾。例如，www.google.com可能被编码为：

![](../Images/15401976f0defd01c994ed02bc7d7b15.png)

这表示名称由 3 个字节、一个句点、6 个字节、一个句点和三个以空字符结尾的字节组成的字符串。

  

在上面的数据包捕获中所描绘的情况下，偏移量指向 0x1，因为请求的域从“9.”开始。因此，如果我们将后面的 14 位从 0x0C 更改为 0x0D，DNS 名称偏移量将指向 0x39，表示 DNS 名称的下一部分向前 0x39 字节，延伸到数据包的签名部分。这样，我们可以欺骗 Windows DNS 服务计算出的 DNS 名称大小远大于用于表示 DNS 名称的实际字节数。

  

从dns!SigWireRead的反编译中可以看出，传递给RR\_AllocateEx的总大小计算为：signatureLength + sigName.Length + 0x14。DNS 名称的最大长度为 0xFF 字节。假名长度的额外字节足以触发漏洞，并且还保持在最大消息大小 65KB 以下！

**在不崩溃的情况下触发漏洞**

该漏洞利用最耗时的部分是理解操作堆的正确方法。本节将重点介绍堆修饰的细节，以避免崩溃并控制堆缓冲区的释放和分配。

  

**WinDNS 堆管理器**

首先有必要了解 WinDNS 服务是如何管理堆内存的。WinDNS 服务管理自己的内存池\[3\]。如果请求的缓冲区大小超过 0xA0 字节，它将向 Windows 本机堆管理器 ( HeapAlloc ) 请求内存。否则，它将使用内存池存储桶（大小为 0x50、0x68、0x88 和 0xa0）。每个桶中的缓冲区存储在一个单链表中。如果所选桶中没有更多可用的缓冲区，则会从本机堆请求一个内存块，划分为单独的缓冲区，然后添加到相应桶的列表中。对于大小为 0x50、0x68、0x88 和 0xA0 的缓冲区，分别请求大小为 0xFF0、0xFD8、0xFF0 和 0xFA0 的内存块。

![](../Images/6ab4dd5d8a68a27d73fee6869e538b0d.png)

dns!eMm\_Alloc 的近似反编译

当其中一个内存桶中的缓冲区被释放时，它们不会返回到 Windows 本机堆。相反，它们会被添加回该存储桶的可用缓冲区列表中。缓冲区是在后进先出 (LIFO) 基础上分配的，这意味着要释放的最后一个缓冲区将是下一个要分配的缓冲区。

**在 memcpy 期间避免分段错误**

我在编写漏洞利用程序时遇到的第一个问题是，在将大型签名memcpy到分配的基于堆的缓冲区中时发生分段错误。我必须确保将整个溢出字节复制到有效的内存地址中。

  

在调查堆布局时，我发现 Windows 原生堆管理器在大小为 0x41FD0-0x41FF0 的“内部”堆段内分配了桶内存块。根据我的观察，这些堆段仅包含用于 WinDNS 内存桶的内存块。因此，如果我们确保溢出缓冲区的大小小于 0xA0，我们可以确定它将在这些块之一内。

![](../Images/69f4ab4d2149cb866c90840983247cb4.png)

堆喷射后包含 WinDNS 内存块的堆段

  

该缓冲区将位于大小约为 0x41ff0 的堆段内。所需的总字节数略大于 0xFFFF。因此，整个溢出结束于有效内存地址的概率相对较高。

  

**打个洞**

如果我们可以在许多连续堆段的中间触发释放缓冲区，重新分配它并溢出缓冲区，我们就可以保证我们到达有效内存地址的机会。这是堆利用中的常用技术。

  

在这种情况下，我们可以通过向受害者客户端进行查询并让我们的恶意 DNS 服务器返回一个带有短 TTL（生存时间）的响应来释放缓冲区。同样，我们可以通过分配长 TTL 来确保缓存的记录缓冲区不会被释放。过期记录每约 2 分钟释放一次。

![](../Images/26c858fe1b6fd42d557e332660d2ac9d.png)

恶意 DNS 服务器控制 TTL，可用于堆修饰

  

在堆中挖一个洞并重新分配它的过程有几个基本步骤：

*   向受害者服务器多次查询恶意域的子域。
    
*   恶意 DNS 服务器会给受害者一个响应，受害者将其缓存在堆内存中（堆喷射）。
    
*   恶意 DNS 服务器将为除一个之外的所有子域分配一个长 TTL（生存时间），该子域将被赋予一个短 TTL。
    
*   WinDNS 每约 2 分钟释放一次过期记录的缓冲区，因此我们等待缓冲区被释放。
    
*   再次查询SIG记录刚刚过期的子域；这一次恶意DNS服务器会给出格式错误的响应来触发溢出。
    
*   因为缓冲区是 LIFO 分配的，所以新的记录缓冲区将与内存中过期的SIG记录具有相同的地址。
    

![](../Images/9900e792b745c3045ded5a873179310d.png)

在堆中打一个洞以避免 SEGFAULT

**避免由于覆盖堆上的其他对象而导致的崩溃**

虽然我能够在  memcpy期间可靠地避免分段错误，但我仍然遇到了许多其他由于覆盖堆上的对象而导致的崩溃。

![](../Images/3213065d5a498dfbef6a51f552a62dd2.png)

由于覆盖缓存树节点而崩溃

‍ 我决定在WinDbg中查看溢出缓冲区附近分配了哪些类型的缓冲区。

![](../Images/c63979822878e33eaced4a3ffa8363d2.png)

Windbg 中的内存分配跟踪

‍ 我可以看到大小为 0xFF0 和 0xFA0 的新 WinDNS 内存块被分配在我溢出的堆缓冲区附近。后者是堆喷射的结果（大小为 0xA0 的记录缓冲区）。但是大小为 0xFF0 的块呢？这些包含大小为 0x88 的缓冲区，用于存储与 DNS 记录缓存相关的对象，该缓存被保存为二叉树。我正在覆盖缓存树对象并在遍历树时导致崩溃。

  

此时溶液变得清澈。请记住，溢出的缓冲区位于仅由其他 WinDNS 托管内存块共享的堆段内。这意味着被覆盖的对象的大小 <= 0xA0 并适合 WinDNS 管理的内存桶之一。我们知道，这些内存桶中的缓冲区永远不会释放回本机堆，而是返回到相应桶大小的空闲缓冲区列表中。因此，我们可以通过强制分配许多大小为 0x88 的缓冲区来清理堆并释放它们。一旦它们被释放，它们将被返回到空闲缓冲区列表中，从而避免了分配新堆内存的需要。然后，我们可以用许多不会被释放的缓冲区喷洒堆，以确保我们溢出的缓冲区将位于远离我们不想覆盖的对象的新堆段中。

![](../Images/53fad445eb1a4e20473b0c2e19f486ab.png)

堆修饰以避免覆盖重要的堆对象

**了解你的环境**

因为我们喷了堆，所以会分配很多新的内存块。这些缓冲区被连续添加到空闲列表中，这意味着它们是按连续顺序分配的。因此，进行 DNS SIG记录查询的顺序将是它们出现在堆上的顺序。因此，我们确切地知道溢出期间将覆盖哪些记录。

**控制缓冲区释放**

  

以前，我们通过简单地给它们一个短 TTL 并等待它们过期并被释放来释放我们选择的记录缓冲区。这很好，但至少等待两分钟是个问题。不是因为我们不耐烦，而是因为它使我们对重新分配的控制更少。能够触发缓冲区的立即释放将很有用。

  

当从缓存中检索RR\_Record对象以响应查询时，在返回响应之前首先检查字段dwTTL和dwTimeStamp 。这是因为记录的 TTL 可能已经过期。请记住，记录缓存仅每 2 分钟清理一次。清理之间的记录可能已过期。我们可以通过简单地将假RR\_Record对象中的dwTTL和dwTimeStamp字段清零并发送相应子域的查询来滥用它。这将导致缓冲区被释放。

  

**控制缓冲区分配**

现在控制缓冲区分配是直截了当的。由于 WinDNS 缓冲区是 LIFO 分配的，一旦我们释放了一个缓冲区，它将是下一个要分配的存储桶大小。更好的是，因为我们还控制WINDNS\_BUFF结构中的值，所以我们可以伪造原始缓冲区的大小！这意味着我们可以在我们控制的堆区域中分配不同大小的对象。

**泄漏内存**

**泄漏堆地址**

我们现在可以通过执行以下操作来泄漏堆中的地址：

*   触发释放假的RR\_Record。
    
*   给被释放的上面的假RR\_Record一个大的wRecordSize。
    
*   使用伪造的大wRecordSize向受害者发送子域的SIG查询。
    
*   响应将超过缓冲区的实际大小，并在其下方包含已释放记录的WINDNS\_FREE\_BUFF结构数据。这会在pNextFreeBuff字段中泄漏一个有效的堆地址。
    

  

![](../Images/dd9d9c4947acf217c4992b4060fbf592.png)

使用伪造的 RR\_Record 对象泄漏堆指针

太好了，我们获得了第一个内存泄漏！但是，我们实际上并不知道泄露的指针相对于我们控制的堆区域的位置。如果我们能得到溢出缓冲区的地址就更好了。为此，我们可以简单地释放两个假的RR\_Record对象，并泄漏我们最后释放的缓冲区的WINDNS\_FREE\_BUFF。释放缓冲区时，指向在写入pNextFreeBuff字段之前已释放的缓冲区的指针。

![](../Images/76b1d366aaee18b0fe7dece4e5d59118.png)

泄漏指向堆的可控部分的指针

**任意读取**

最后，我们拥有任意读取原语的所有部分。

请注意，我们已经能够通过覆盖  已分配的DNS\_timeout对象中的pFreeFunction指针来执行代码。在函数dns!Timeout\_CleanupDelayedFreelist中，为CoolingDelayedFreeList中的每个超时对象调用pFreeFunction中的函数地址。此列表包含表示准备释放的记录的DNS\_Timeout对象。幸运的是，DNS\_Timeout对象包含传递给此函数的一个参数的字段。

我们可以在分配超时对象覆盖这些字段后再次触发漏洞。

现代版本的dns.exe使用 Control Flow Guard (CFG) \[4\]进行编译。绕过 CFG 的一种已知方法是破坏堆栈\[11\]上的返回地址并使用 ROP \[7\]方法执行。但是，我们目前还没有稳定的方式来写入堆栈。相反，我们可以找到用于原语的有效调用目标（即dns.exe中的函数）。一个合适的候选者是dns!NsecDnsRecordConvert，它采用一个参数\[3\]。

  

NsecDnsRecordConvert的参数应具有以下结构：

![](../Images/9288afe9e4d9c4ee90ce7b8fbf2f59eb.png)

在这个函数内部，分配了一个缓冲区并调用了Dns\_StringCopy。这就是读取原语所在的位置。由于我们控制传入的函数参数及其内容，我们可以将pDnsString字段设为我们要读取的地址。在DNS\_StringCopy内部，分配了一个缓冲区，并复制了pDnsString指向的数据（直到一个空字节）。![](../Images/dea0d244b5c9f06f9951713853611692.png)

dns的反编译！NsecDnsRecordConvert

因为我们还控制wSize，所以我们控制分配的缓冲区的大小。因此，我们强制将新缓冲区分配到我们控制的堆区域中。数据复制完成后，我们使用与之前相同的方法泄漏内存。

![](../Images/c6b34e75a95e067831f3ccec993e80ff.png)

**任意读取原语**

‍我们读取的msvcrt.dll的地址。我选择了dns!\_imp\_exit，其中包含msvcrt!exit的地址。这将破坏msvcrt.dll的 ASLR 。有了这个，我们可以计算出msvcrt!system的地址。

  

注意：Dns\_StringCopy期望复制一个以 null 结尾的字符串。如果地址的最低有效字节为 0x00，则计算字符串的大小将为 1，并且不会复制地址。在我获得的样本中，这不是问题，但我没有测试msvcrt.dll的所有可能版本。

  

**远程代码执行**

现在所有部分都已准备就绪，可以远程执行代码了。我们可以再次触发DNS\_Timeout对象的分配。然后，我们用msvcrt!system和pFreeFuncParam覆盖pFreeFunction并使用包含有效负载命令的内存的堆地址。为了获得反向 shell，我选择使用mshta.exe从攻击者托管的 HTTP 服务器执行 HTA shell。我发现这是最简单的解决方案，但还有许多其他可能性。该漏洞也可以被重新设计以使用任何其他函数而不是system。
