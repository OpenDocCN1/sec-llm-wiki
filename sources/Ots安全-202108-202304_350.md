保护应用程序并不是最简单的事情。一个应用程序有许多组件：服务器端逻辑、客户端逻辑、数据存储、数据传输、API 等等。有了所有这些组件的安全，构建一个安全的应用程序似乎真的令人生畏。

  

值得庆幸的是，大多数现实生活中的漏洞都有相同的根本原因。通过研究这些常见的漏洞类型、它们发生的原因以及如何发现它们，您可以学会预防它们并保护您的应用程序。

每种语言、框架或环境的使用都会使应用程序暴露于一组独特的漏洞中。修复应用程序漏洞的第一步是知道要寻找什么。

**原型污染**

JavaScript 是一种具有许多特质的独特语言。将其与其他主流语言区分开来的这些特征之一是如何在 Javascript 中创建对象。Javascript 中的对象不是从类中实例化，而是从现有对象或“原型”继承其属性。

  

从安全角度来看，这意味着如果攻击者可以修改原型对象及其属性，那么原型对象就可以影响从该原型创建的所有对象的属性。这可能导致从浏览器中的跨站点脚本 (XSS) 攻击到 Node.js 应用程序中的远程代码执行 (RCE) 攻击。在此处了解这些攻击的工作原理以及如何防止它们。

  

**跨站点脚本包含**

跨站点脚本包含攻击也称为 XSSI。当恶意站点包含来自受害者站点的 Javascript 以从脚本中提取敏感信息时，就会发生这些攻击。

  

同源策略（SOP）通常控制数据跨域访问。但是 SOP 不限制 javascript 代码，并且允许 HTML <script> 标签从任何来源加载 Javascript 代码。这是一个非常方便的功能，允许跨域重用 JavaScript 文件。但是这个特性也带来了安全风险：攻击者可能能够通过加载受害者的 JS 文件来窃取用 JavaScript 文件编写的数据。

  

例如，假设一个网站通过 Javascript 文件为登录用户存储和传输敏感数据。如果用户在同一浏览器中访问恶意站点，则恶意站点可以导入该 JavaScript 文件并访问与用户会话相关的敏感信息，这一切都归功于存储在浏览器中的用户 cookie。在此处查看此漏洞的示例并了解如何防止它们。

  

**不安全的 Puppeteer 设置**

不安全的 Puppeteer 设置是 Node 应用程序的另一个问题。Puppeteer 是一个 Node 库，它允许应用程序以编程方式控制 Chrome 或 Chromium 的无头构建。Puppeteer 通过模仿用户可以在浏览器中执行的活动来帮助自动化用户测试。例如，您可以自动测试表单提交、键盘输入和许多其他用户操作。

  

对 Puppeteer 运行的浏览器进行沙箱处理很重要，因为无头浏览器可能可以访问磁盘或内部网络。在这篇文章中阅读如何做到这一点。

  

**安全配置错误**

不安全的 Puppeteer 设置本质上是一种安全配置错误。还有许多其他类型的安全错误配置可能会危及 Node 应用程序的安全性。其中可能包括使用默认凭据、使用错误的 HTTP 安全标头、通过错误消息暴露敏感系统信息或禁用内置安全措施。在此处了解 Node 应用程序中一些最常见的安全错误配置。

  

**远程代码执行**

远程代码执行漏洞 (RCE) 是攻击者可以在您的机器上执行其代码时发生的一类漏洞。发生这种情况的一种方式是通过代码注入漏洞。它们是一种远程代码执行，当用户输入直接连接到执行代码时发生。应用程序无法区分用户输入的位置和可执行代码的位置，因此应用程序将用户输入作为代码执行。攻击者将能够通过应用程序执行任意 Javascript 代码。

  

防止代码注入的最简单方法之一是以允许列表的形式实现健壮的输入验证。在此处阅读有关如何实施白名单以及应避免使用哪些 Javascript 方法以防止 RCE的信息。

  

**代码注入**

代码注入也是一种注入问题。当应用程序无法正确区分不受信任的用户数据和代码时，就会发生注入。当 Javascript 代码中发生注入时，会导致代码注入。但注入漏洞也以其他方式表现出来。

  

**SQL 注入**

例如，在 SQL 注入攻击中，攻击者通过注入数据来操纵 SQL 命令。当应用程序没有正确验证用户输入时，攻击者可以插入 SQL 语言的特殊字符来扰乱查询逻辑，从而执行任意 SQL 代码。在此处了解有关这些 SQL 注入攻击如何工作的更多信息。

  

SQL 注入允许攻击者代码更改应用程序 SQL 查询的结构，以窃取数据、修改数据或可能在底层操作系统中执行任意命令。防止 SQL 注入的最好方法是使用参数化语句，这使得 SQL 注入几乎不可能。在本文中了解如何使用参数化语句。

  

**日志注入**

您可能会执行系统日志记录以监控网络中发生的恶意活动。但是你有没有想过你的日志文件条目可能对你撒谎？与其他系统文件一样，日志文件可能会被恶意行为者篡改。攻击者经常修改日志文件以在攻击期间掩盖他们的踪迹。日志注入是攻击者可以更改您的日志文件的方式之一。当攻击者欺骗应用程序在您的日志文件中写入虚假条目时，就会发生这种情况。

  

当应用程序不清理写入日志的输入中的换行符“\\n”时，通常会发生日志注入。攻击者可以利用换行符将新条目插入应用程序日志。攻击者可以利用日志中的用户输入的另一种方式是，他们可以将恶意 HTML 注入日志条目，以尝试在查看日志的管理员的浏览器上触发 XSS。

  

为了防止日志注入攻击，您需要一种方法来区分真实日志条目和攻击者注入的虚假日志条目。一种方法是在每个日志条目前加上额外的元数据，如时间戳、进程 ID 和主机名。您还应该将日志文件的内容视为不受信任的输入，并在访问或操作之前对其进行验证。

  

**邮件注入**

许多 Web 应用程序会根据用户的操作向用户发送电子邮件。例如，如果您订阅了新闻媒体上的提要，该网站可能会向您发送包含提要名称的确认信息。

  

当应用程序使用用户输入来确定将电子邮件发送到哪些地址时，就会发生邮件注入。这可以让垃圾邮件发送者使用您的服务器向用户发送大量电子邮件，或者使诈骗者能够通过您的电子邮件地址进行社会工程活动。在此处了解攻击者如何实现邮件注入以及如何防止它。

  

**模板注入**

模板引擎是一种用于确定网页外观的软件。这些以模板语言（如 Jinja）编写的 Web 模板为开发人员提供了一种通过将应用程序数据与 Web 模板相结合来指定应如何呈现页面的方法。Web 模板和模板引擎一起允许开发人员在 Web 开发期间将服务器端应用程序逻辑与客户端表示代码分开。

  

模板注入是指注入到网页模板中。根据受感染应用程序的权限，攻击者可能能够利用模板注入漏洞读取敏感文件、执行代码或提升他们在系统上的权限。

  

**正则表达式注入**

正则表达式或正则表达式是描述文本中搜索模式的特殊字符串。有时，应用程序让用户提供自己的正则表达式模式，以供服务器执行或使用用户输入构建正则表达式。正则表达式注入攻击或正则表达式拒绝服务攻击 (ReDoS) 发生在攻击者为正则表达式引擎提供需要很长时间评估的模式时。您可以在我的帖子中找到这些模式的示例。

  

值得庆幸的是，通过不从用户输入生成正则表达式模式，以及构建设计良好的正则表达式模式，其所需的计算时间不会随着文本字符串的增长而呈指数增长，可以可靠地防止正则表达式注入。您可以在此处找到这些先发制人措施的一些示例。

**标头注入**

当 HTTP 响应标头是从不受信任的输入动态构建时，会发生标头注入。根据漏洞影响的响应标头，标头注入可能导致跨站点脚本、开放重定向和会话固定。

  

例如，如果Location标头可以由 URL 参数控制，则攻击者可以通过在参数中指定他们的恶意站点来导致开放重定向。攻击者甚至可以在受害者的浏览器上执行恶意脚本，或者通过标头注入向受害者发送完全受控的 HTTP 响应来强制受害者下载恶意软件。更多关于这些攻击如何工作的信息。

  

您可以通过避免将用户输入写入响应标头、从用户输入中去除换行符（换行符用于创建新的 HTTP 响应标头）以及使用允许列表来验证标头值来防止标头注入。

  

**会话注入**

会话注入是一种标头注入。如果攻击者可以操纵他们的会话 cookie 的内容，或者窃取其他人的 cookie，他们可以欺骗应用程序认为他们是其他人。攻击者可以通过三种主要方式获取他人的会话：会话劫持、会话篡改和会话欺骗。

会话劫持是指攻击者窃取别人的会话 cookie 并将其用作自己的。攻击者经常通过 XSS 或 MITM（中间人）攻击窃取会话 cookie。会话篡改是指攻击者可以更改其会话 cookie 以更改服务器解释其身份的方式。当会话状态在 cookie 中进行通信并且 cookie 未正确签名或加密时，就会发生这种情况。最后，当会话 ID 是可预测的时，攻击者可以“欺骗”会话。如果是这种情况，攻击者可以伪造有效的会话 cookie 并以其他人的身份登录。防止这些会话管理陷阱需要多层防御。

  

**主机头中毒**

Web 服务器通常在同一个 IP 地址上托管多个不同的网站。HTTP 请求到达某个 IP 地址后，服务器会将请求转发到 Host 标头中指定的主机。尽管 Host 标头通常由用户的浏览器设置，但它仍然是用户提供的输入，因此不应被信任。

如果 Web 应用程序在使用 Host 标头构造地址之前未对其进行验证，则攻击者可以通过 Host 标头发起一系列攻击，例如 XSS、服务器端请求伪造( SSRF) 和 Web 缓存中毒攻击。例如，如果应用程序使用 Host 标头来确定脚本的位置，则攻击者可以提交恶意 Host 标头以使应用程序执行恶意脚本：

scriptURL = "https://" + properties.getProperty("host") + "/script.js";

**敏感数据泄露**

当应用程序未能正确保护敏感信息时，就会发生敏感数据泄漏，从而使用户可以访问他们不应该获得的信息。这些敏感信息可能包括有助于攻击的技术细节，例如软件版本号、内部 IP 地址、敏感文件名和文件路径。它还可能包含允许攻击者对应用程序进行源代码审查的源代码。有时，应用程序会泄露用户的私人信息，例如他们的银行帐号、电子邮件地址和邮寄地址。

应用程序泄露敏感技术细节的一些常见方式是通过描述性响应标头、带有堆栈跟踪或数据库错误消息的描述性错误消息、系统文件系统上的打开目录列表以及在 HTML 和模板文件中显示注释。您可以在此处了解如何防止 Node 应用程序中的数据泄漏。

  

  

**身份验证绕过**

身份验证是指在执行敏感操作或访问敏感数据之前证明自己的身份。如果在应用程序上没有正确实施身份验证，攻击者可以利用这些错误配置来访问他们不应该能够访问的功能。有关如何在 Node 中正确配置身份验证的更多详细信息，请阅读本教程。

  

**访问控制不当**

身份验证绕过问题本质上是不正确的访问控制。当应用程序中的访问控制实施不当并且可以被攻击者绕过时，任何时候都会发生不当的访问控制。但是，访问控制不仅仅包括身份验证。虽然身份验证要求用户证明他们的身份：“你是谁？”，但授权要求应用程序“允许此用户做什么？”。适当的身份验证和授权共同确保用户无法访问超出其权限的功能。

为用户配置授权有多种方式：基于角色的访问控制、基于所有权的访问控制、访问控制列表等。

  

**目录遍历**

目录遍历漏洞是另一种不恰当的访问控制。当攻击者可以通过操纵用户输入字段中的文件路径来查看、修改或执行他们不应访问的文件时，就会发生这种情况。../此过程涉及通过将字符或其他特殊字符添加到文件路径来操作应用程序用于引用文件的文件路径变量。该../序列指的是 Unix 系统中当前目录的父目录，因此通过将其添加到文件路径中，您通常可以访问 web 目录之外的系统文件。

攻击者通常可以使用目录遍历来访问敏感文件，如配置文件、日志文件和源代码。为了防止目录遍历，您应该验证插入文件路径的用户输入，或者避免直接引用文件名并使用间接标识符。

  

**任意文件写入**

任意文件写入漏洞的工作方式与目录遍历类似。如果应用程序将文件写入底层机器并通过用户输入确定输出文件名，则攻击者可能能够在他们想要的任何路径上创建任意文件，或覆盖现有的系统文件。攻击者可能能够更改密码文件或日志文件等关键系统文件，或将他们自己的可执行文件添加到脚本目录中。

  

减轻这种风险的最佳方法是不根据任何用户输入创建文件名，包括会话信息、HTTP 输入或用户控制的任何内容。您应该控制每个创建的文件的文件名、路径和扩展名。例如，您可以在用户每次需要生成唯一文件时生成一个随机的字母数字文件名。您还可以在创建文件之前去除用户输入的特殊字符。在这篇文章中了解这些技术。

  

**拒绝服务攻击**

拒绝服务攻击或 DoS 攻击会破坏目标机器，使合法用户无法访问其服务。攻击者可以通过耗尽所有服务器资源、崩溃进程或一次发出过多耗时的 HTTP 请求来发起 DoS 攻击。

  

拒绝服务攻击很难防御。但是有一些方法可以通过让攻击者尽可能地困难来最小化您的风险。例如，您可以部署提供 DoS 保护的防火墙，并通过设置文件大小限制和禁止某些文件类型来防止基于逻辑的 DoS 攻击。您可以在此处找到有关防止拒绝服务攻击的更详细步骤。

  

**加密漏洞**

加密问题可能是应用程序中可能发生的最严重的漏洞之一。加密漏洞是指未正确实施加密和散列。这可能导致广泛的数据泄漏和通过会话欺骗绕过身份验证。

开发人员在网站上实施加密时常犯的一些错误是：

*   使用弱算法
    
*   使用错误的算法达到目的
    
*   创建自定义算法
    
*   生成弱随机数
    
*   将编码误认为加密
    
*   可以在此处找到加密安全指南。
    

  

**批量分配**

“批量赋值”是指一次为多个变量或对象属性赋值的做法。当应用程序自动将用户输入分配给多个程序变量或对象时，就会出现批量分配漏洞。这是许多旨在简化应用程序开发的应用程序框架中的一个功能。

  

但是，此功能有时允许攻击者随意覆盖、修改或创建新的程序变量或对象属性。这可能导致身份验证绕过和程序逻辑操作。要防止批量分配，您可以使用正在使用的框架禁用批量分配功能，或者使用白名单仅允许对某些属性或变量进行分配。

  

**打开重定向**

网站通常需要自动重定向其用户。例如，当未经身份验证的用户尝试访问需要登录的页面时，就会发生这种情况。网站通常会将这些用户重定向到登录页面，然后在他们通过身份验证后将其返回到原来的位置。

  

在开放式重定向攻击期间，攻击者通过向用户提供来自合法站点的 URL 来欺骗用户访问外部站点，该 URL重定向到其他地方。这可以让用户相信他们仍然在原始网站上，并帮助诈骗者构建更可信的网络钓鱼活动。为了防止开放重定向，您需要确保应用程序不会将用户重定向到恶意位置。例如，您可以通过验证重定向 URL来完全禁止异地重定向。还有许多其他方法可以防止打开重定向，例如检查请求的引用者，或使用页面索引进行重定向。但是因为验证 URL 很困难，开放重定向仍然是现代 Web 应用程序中的一个普遍问题。

  

**跨站请求伪造**

跨站点请求伪造(CSRF) 是一种客户端技术，用于攻击 Web 应用程序的其他用户。使用 CSRF，攻击者可以发送假装来自受害者的 HTTP 请求，代表受害者执行不需要的操作。例如，攻击者可能会在未经您许可的情况下更改您的密码或从您的银行账户转账。

  

与开放重定向不同，有一种防止 CSRF 的万无一失的方法：使用CSRF 令牌和 SameSite cookie的组合，并避免使用 GET 请求进行状态更改操作。

  

**服务器端请求伪造**

SSRF 或服务器端请求伪造是攻击者能够代表服务器发送请求时发生的漏洞。它允许攻击者“伪造”易受攻击的服务器的请求签名，从而在网络上占据特权位置，绕过防火墙控制并获得对内部服务的访问权限。

  

根据给予易受攻击服务器的权限，攻击者可能能够读取敏感文件、进行内部 API 调用以及访问隐藏管理面板等内部服务。防止 SSRF 漏洞的最简单方法是永远不要根据用户输入发出出站请求。但是，如果您确实需要根据用户输入发出出站请求，则需要在发起请求之前验证这些地址。

  

**信任边界违规**

“信任边界”是指不受信任的用户输入进入受控环境的位置。例如，在服务器验证之前，HTTP 请求被认为是不受信任的输入。

  

存储、传输和处理可信和不可信输入的方式应该有明显的区别。当不尊重这种区别并且可信和不可信数据相互混淆时，就会发生信任边界违规。例如，如果受信任和不受信任的数据存储在同一个数据结构或数据库中，应用程序将开始混淆两者。在这种情况下，不受信任的数据可能会被错误地视为已验证。
