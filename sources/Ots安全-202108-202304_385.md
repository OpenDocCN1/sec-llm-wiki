# 汽车劫持 未经授权的硬件攻击

用于与汽车中的各种 ECU（电子控制单元）交互，UDS（统一诊断服务）服务被汽车制造商广泛部署。这种通用的高级协议用于提取 ECU 状态、配置它们甚至更新它们的固件。当实施缺乏 ECU 内部的加密支持时，安全级别会显着降低。这篇简短的博客文章介绍了一种利用所有诊断功能对未经授权的测试人员进行的硬件攻击。

  

**安全访问**

出于完整性和安全性的明显原因，与 ECU 的关键交互必须仅授予授权人员。为此，UDS 标准中提供了一项专用服务：著名的安全访问请求。基于质询/响应身份验证，底层协议取决于构造函数。在研究案例中，挑战由附加到汽车的各种关键标识符的随机数发出，作为种子发送给用户（在UDS世界中称为Tester）。然后，测试者根据这个用密钥加密的种子发回响应。当答案与 ECU 内计算的值不匹配时，测试仪仍然在有限的允许命令范围内。相反，当 ECU 验证答案时，基本上所有可用的交互都是可能的。利润。

  

当构造函数实现反暴力技术时，暴力破解密钥特别耗时，或者只是痛苦。无论如何，也必须以某种方式发布特定于构造函数的身份验证算法。

  

另一方面，当UDS服务器将身份验证响应检查委托给一个辅助芯片时，身份验证绕过可能更容易，它通过线路以明文形式与之通信。在研究案例中，运行 UDS 服务器的主芯片要求辅助芯片通过SPI链接验证测试仪的响应。

![](../Images/e4c8855c8862eb800f05088ff6b32ee2.png)

辅助芯片和主芯片之间的最终消息 (4) 是身份验证验证过程中的一个单一故障点：如果它可以强制为“OK”值，则主芯片被欺骗并认为测试仪是合法的。

  

**串行链路协议 MiTM**

主芯片上的软件被认为是一个白盒（软件可用），而不是附属芯片。我们对辅助芯片的唯一了解是它在 ECU 板上的位置、制造商参考、其文档（可在 Internet 上公开获取）。身份验证算法和密钥未知。

  

这种芯片封装使所有引脚完全可以与电子探针一起使用（与BGA系列相反）。

  

另一方面，这个辅助芯片有多个引脚，具有两个、三个或更多功能，这意味着一个引脚可以用于ADC、CAN、PWM、SPI，无论根据内部配置：专用于SPI链接的引脚是在启动时动态定义，而不是硬连线。让我们发现它们。

  

**定位销**

知道SPI链接——根据定义——基于时钟信号，所有引脚都被盲目地探测，直到找到一个周期性地连续跳动八次的信号。

![](../Images/ff7e2c642af2ca8bfa099ae1e31860ee.png)

SPI时钟信号

Bingo，即具有八个边沿的信号，对应于要传输的八位，以 4.8 MHz 的频率跳动。在 MCU 文档的帮助下，查看此时钟引脚会发现哪些引脚承载MOSI和MISO信号。

![](../Images/d16eb3e7d9ec846906ea53a5c24aee3f.png)

上面的摘录显示MOSI（主机到从机）线发送三个字节，而MISO（从机到主机）同步发送其自己的有效负载\[1\]。缩小此信号样本显示软件协议将数据封装在 128 字节帧内。这将通过对主控芯片上的协议栈的分析来确认。进一步缩小显示 128 字节的SPI帧以更高的速率间隔 300us 的休息期。这似乎是主机能够输出字节的最高带宽。信不信由你，观察到的最大吞吐量大约为 1.7Mb/s，与现在的通信带宽相比，这是相当慢的。

  

该SPI引脚绝对位置。伟大的。让我们在从验证响应上翻转一两个位并欺骗主。

  

**翻转一两个位，容易吗？**

TL;DR：这取决于谁。

从技术上讲，我们试图在SPI链路上设置 MiTM（中间人）攻击，尤其是在上游链路上，从从设备到主设备（MISO信号）。从第一种方法来看，MiTM 设备由耦合到从SPI发射器的从SPI接收器和其间的一些计算组成。

![](../Images/d58f4e2b14d873d4f77a61fc0cc15df3.png)

MiTM 设备对从从芯片发出的MISO信号进行反序列化，逐字节分析流，并根据其内部状态将相同或修补的字节推回到其上游链路，由主时钟控制。是的，但是……实际上，您知道哪个简单的芯片包含一个处理器和一个从 SPI接口吗？当处理器耦合到SPI接口时，它通常希望成为主设备，而不是从设备。实际上，它存在一些廉价的现成设备，通常是可以完成这项工作的Arduino板或基于STM32的系统。在功能上，它集成了一个处理器和一个从SPI接口。让我们去编码。

  

等等...记住第一个SPI时钟样本图中每个字节之间的 520ns 。廉价处理器是否运行得足够快以处理由SPI接收接口触发的中断、处理几个字节并在下一个字节的第一位开始发出之前加载SPI发送寄存器？

  

根据经验，在理想的执行条件下，基于 1.3GHz ARM 的 SoC 花费大约 100ns 处理外部中断：没有操作系统、专用于此中断的单核、预热缓存、最短的汇编代码中断处理路径。任何数据或代码缓存未命中都会使这个数字爆炸。不用说，处理器和外围控制器之间的 I/O 内存访问不采用相同的内存优化总线。相反，I/O 总线（例如到SPI接口）甚至可能比内存总线慢得多。

  

在这些情况下，使用廉价的 SoC 在粗略的 500ns 时序窗口内读取传入字节、处理它、写入下一个字节似乎不可靠。任何延迟的传输都会破坏协议并且是致命的。

  

有人会争辩说，SoC 可以轻松实现 1Gb/s（甚至更高）的吞吐量，而这种情况在持续阶段仅限于 - 荒谬 - 1.7Mb/s 的最大值。但是这些高吞吐量绕过处理器执行路径，依赖于专用于一堆内存副本的外部引擎，也称为 DMA（直接内存访问）。该解决方案在研究中是负担不起的，因为 - 至少 - 必须在 128 字节SPI帧之一中即时修补一个字节，这意味着最少的处理。

  

比赛结束？不，解决方案存在于以下四个字母中：FPGA。

  

**硬件设计**

FPGA（现场可编程门阵列）是一种高度可配置的集成电路，包含许多基本逻辑块。使用时钟为几纳秒的组合逻辑，该解决方案在这种时间受限的上下文中实现位翻转似乎是合理的。

  

另一方面，作为一个软件开发者，这个硬件解决方案是相当令人不安的，需要选择：

*   一种介于所谓的 VHDL 和 Verilog 之间的编程语言，
    
*   FPGA 创始人，如 Xilinx 和 Intel（前 Altera），暗示其特定的设计工具（名为 Vivado 和 Quartus），
    
*   最终的 FPGA 开发板。
    

编程语言的选择没有经过科学论证：在网上快速搜索教程的菜鸟会发现用 VHDL 编写的实现示例比用 Verilog 编写的要多。请注意，此结果从根本上受搜索关键字的影响，很容易产生倒排结果。尽管如此，为项目选择的编程语言是 VHDL。

  

对于创始人来说，选择主要来自经验。事实上，之前的一项研究暗示 Vivado 工具套件留下了与工具套件整体缓慢相关的令人讨厌的感觉。此外，一位有经验的人向我声称，Quartus GUI 比其竞争对手更加用户友好。很好，所有基本元素都可用于启动至少基于 Quartus 套件中 VHDL 的 FPGA 设计。最后看FPGA板，开始编码。

  

在第一种方法中，中间人设备必须在正确的时间“只”注入一点或几位，覆盖原始从响应。从原理上讲，它可以表示为SPI链路上的一个简单换向器，在大脑的控制下激活，不断监视传入的比特流以检测覆盖点。

![](../Images/5803148c1f079b00097d646cc20cbd1a.png)

可以肯定的是，这个被称为多路复用器的基本电子组件，即使是一个微不足道的两入口单向多路复用器，也可以在 VHDL 中快速实现，即使对于软件开发人员也是如此。此外，还应快速实现寻找 16 位模式（上图中的“ xy ”）的比较功能。最后，在 VHDL 中实现的从SPI组件，反序列化和重新序列化字节，至少在 GitHub 项目\[2\]上也可用。只需将它们混合在一起，它就可以完成工作。

  

唉，这种初步的做法，绝对是太高级了。

  

首先，研究两个实体之间使用的专有协议很快就会发现，每个 128 字节的SPI帧都包含一个 24 位的 CRC（循环冗余校验）尾部。在工业界，为了检测一个或多个虚假位分裂，这是一个相当不错的主意，但对于 MiTM 设备的快速设计来说却很烦人。修改SPI有效载荷中的单个位意味着重新计算整个帧的 CRC，否则主芯片会系统地丢弃该帧。对于完全未经实验的 VHDL 设计人员来说，在 VHDL 中实现 CRC24（或 CRC16 或任何 CRC）并不明显。存在多个 CRC24，具体取决于所选的多项式项\[3\]。Google 再次成为您的朋友：一个网站\[4\]提供世界上所有 CRC 的 VHDL（和 Verilog）实现。只需指定输入宽度、输出格式和多项式项，以及 JavaScript 生成的 VHDL 源代码的利润。事实上，在本项目的后面，CRC 计算特别容易在硬件中实现。

  

为了缩短故事时间（并避免构造函数的信息泄露），这里没有开发内部对偶CRC16计算，也没有开发一些SPI帧末尾的隐蔽填充字节，也没有将内部协议嵌入底层协议中标头和有效载荷分布在几个SPI帧上。

  

简而言之，VHDL 设计开发花费的时间比预期的要长得多，这是由于最初来自未经实验的硬件设计人员未识别出的问题，但部分补偿了与 VHDL 开发相关的丰富文档\[5\]。

  

**设计模拟**

正如所有初学者手册中所述，由于 Quartus 套件提供了重要的 VHDL 仿真器，因此该设计已经逐个实体地进行了验证。首先通过对单个字节进行反序列化和重新序列化，然后获取整个 128 字节的SPI帧，然后在单个帧上计算和检查 CRC，依此类推，直到在流中的正确位置修补正确的字节数百个SPI帧。顺便说一下，测试平台中使用的一个很棒的功能是能够从 CSV 格式的文件中读取数据（用作测试向量）。初始采样工具（Saleae）记录了主从之间大约两分钟的通信，产生了超过2K的SPI CSV 格式的帧，准备注入测试平台，大大简化了对真实向量的测试。

![](../Images/d24631bbfec3b42b91b7ceaa358de3c4.png)

最终设计检测测试平台的 331 个SPI帧（从实际从机活动中捕获）中的安全访问响应，即时修补，修复所有 CRC。理论上至少。该设计内部时钟频率为 100MHz，可轻松处理时钟频率为 4.8MHz 的每个传入位。感谢Quartus。

  

**结论**

不幸的是，分配给这项研究的有限时间与当前廉价的 FPGA 板交付延迟不兼容。电子零件市场面临压力，这种攻击无法在博客文章的时间范围内真正发挥作用。

  

然而，由于对这个特定汽车 ECU 的两个部分之间的通信协议有部分了解，主要的诊断安全访问保护可以通过使用标准工具编程的廉价硬件部分绕过。

  

第一次设计和逻辑模拟为下一个挑战开启了新的视角，这意味着硬实时 MiTM 攻击！
