介绍

两年前，我们发布了CARPE DIEM，这是一个 Apache HTTPd 本地根漏洞。今天我们发布了一个影响 PHP-FPM 的类似漏洞的详细信息。相似不仅因为它们具有相同的影响并影响相同类型的目标，还因为它们源自相同的问题：不安全的共享内存使用。然而，原始是不同的，因此，剥削也是如此。


该漏洞允许低权限用户（例如www-data）使用 PHP-FPM 中的漏洞将其权限提升为 root，该漏洞已存在 10 年。


PHP-FPM (FastCGI Process Manager) 是官方的 PHP FastCGI 服务器。它与HTTP 服务器（如Apache 或 NGINX）结合使用来处理 PHP 文件。它通常通过 UNIX 套接字或 TCP 端口 9000 侦听连接。当 HTTP 服务器需要运行 PHP 文件时，它会将文件路径、PHP 变量和配置等参数转发给 PHP-FPM，后者将发回响应。


如果您想知道自己是否容易受到攻击：如果您使用的是Apache和 PHP，那么您可能正在使用 PHP-FPM。如果您使用NGINX和PHP，你正在使用PHP-FPM。如果您使用的是 PHP-FPM，那么您很容易受到攻击。


漏洞概述

低权限进程可以通过共享内存读写主进程使用的指针数组，以root身份运行。攻击者可以利用此问题将主进程内存中的 32 位整数从 0 更改为 1，或者清除内存区域。通过多次利用原语，可能会触及另一个错误，使主进程执行代码，从而提升权限。


PHP-FPM 概述

PHP-FPM 的行为由其配置控制；我们将使用标准配置来解释它是如何工作的。天啊。


主要流程和工人

PHP-FPM 是一个 FastCGI 服务器。主进程通常作为 运行root，管理特权较低的 ( www-data, nobody) 工人。当收到请求时，主进程将其转发给空闲的工作人员进行处理。工人发回响应。系统是“按需”的：如果每个工人都忙于处理一个请求，主进程可以产生一个或几个新的工人。反之，如果流量不大，主进程可以杀掉worker来节省资源。如果一个工作进程以某种方式崩溃或退出，主进程会产生一个新进程来代替它。默认情况下，PHP-FPM 以 2 个 worker 启动，最多可以处理 5 个并发请求（即5 个并发 worker）。


记分牌

为了了解每个工人在做什么，每个工人管理一个记分板 ( struct fpm_scoreboard_proc_s) 1。这些结构包含一个 PID、worker 的当前状态（它是在处理请求还是空闲？它正在处理哪个 PHP 文件？），以及一些统计信息（使用的内存和 CPU 时间）。

主记分牌

其中一个字段很有趣：结构的最后一个字段procs，是一个指向前面描述的子记分板的指针数组。当根进程需要访问一个子记分板时，它会引用这个数组并取消引用它的元素。


这意味着主进程可以访问子记分板，尽管它们由工作人员维护。怎么会这样 ？


工控机通过 SHM

当 PHP-FPM 启动时，它会创建一个共享内存映射来存储子记分板。与主进程一起，每个工作人员都可以读取和修改此映射中的数据。这似乎不安全：作为一名工人，您可以例如修改其他工人的记分牌，并假装他们很忙，这可以对应用程序进行 DOS 操作。然而，这并不是戏剧性的。


这是什么：主记分牌也位于 SHM 中。fpm_scoreboard_s.procs[]因此，任何工作人员都可以写入 中的指针。当根进程尝试使用子记分板时，我们可以让它在 SHM 之外读取或写入，就在它自己的内存中！


作为快速测试，您可以scoreboard->procs[0]从工作进程设置为未映射的地址，并在主进程尝试取消引用时几乎立即看到它崩溃。


使用 PHP 沙箱逃逸错误，就像这里描述的那样，可以完全控制工人的内存，并使用它来修改fpm_scoreboard_s.procs[]指针，以使主进程使用假fpm_scoreboard_proc_s结构。


然而，与 Apache HTTPd 漏洞不同的是，没有简单的方法可以从这个 bug 到达任意函数调用。事实上，我们实际上无能为力！我们将在下一节中讨论这一点。


流程记分牌管理和坏原语

为了理解我们可以用这些指针做什么，我们需要了解 PHP-FPM 在关闭和创建 worker 期间如何管理子记分板。


PHP-FPM 在运行时维护一个正在运行的子进程（工人）的链表，每个子进程都由一个fpm_child_s结构表示。它们存储在堆上（libc 的，而不是 PHP 的）。


此外，PHP-FPM 希望收集有关其正在运行的 worker 的一些统计信息。因此，当它启动时，主进程会在共享内存中分配主记分板 ( fpm_scoreboard_s) 和数量fpm_scoreboard_proc_s等于最大工人数（默认为 5）的结构。然后它fpm_scoreboard->procs[]用指向这些的指针填充数组。


在它产生一个新工人之前，主进程需要为它找到一个记分板来使用。为此，选择一个未使用的子记分板，将其标记为已使用，并将其链接到工作人员。


当工人死亡时，它不再需要子记分板。PHP-FPM 通过另一个结构找到它的索引，然后擦除整个结构。


这两个操作都发生在主进程中，作为 root。它们分别由以下函数完成：fpm_scoreboard_proc_alloc()和fpm_scoreboard_proc_free()。让我们快速检查一下这两个函数的代码。

为了加快分配过程，该字段scoreboard->free_proc会跟踪最后释放的子记分板。当需要分配一个子记分牌时，首先会检查这个索引。


包含每个子记分板地址的数组scoreboard->procs[]位于共享内存中：它可以被任何工作进程修改。此外，分配子记分板的过程可以通过创建多个并发请求轻松触发为工作人员，并且可以通过杀死工作人员来释放子记分板。


因此，我们可以作为攻击者触发这些函数：我们可以使用它使主进程将 32 位整数从 0 更改为 1（使用2），或者清除一个巨大的内存区域（使用5）。


一个例子

假设我们想0x555600000038在主进程的堆中的地址处设置一个整数为1。原来是0。


我们设置scoreboard->procs[2]为0x555600000028( usedis at offset 0x10)，并杀死关联的工人。fpm_scoreboard_proc_free(scoreboard, 2)被调用，并且由于scoreboard->procs[2]->used( 0x555600000038) 为零，它只是设置scoreboard->free_proc为2并返回。


然后，在产生一个新工人之前，fpm_scoreboard_proc_alloc()被调用。它检查scoreboard->procs[scoreboard->free_proc]->used，看到它是零，并将其设置为一。然后它设置scoreboard->free_proc为2+1=3并返回。


但是，如果由于某种原因，地址处的整数0x555600000038恰好不为零，则影响就大不相同了。fpm_scoreboard_proc_free()检查scoreboard->procs[2]->used，看到它是非零的，因此调用memset(0x555600000028, 0, 1168)，破坏了地址周围（大部分是之后）的内存的重要部分。


这是一个有风险的原语：由于内部 PHP-FPM 结构的尺寸很小，1168 代表一个巨大的尺寸。如果我们以某种方式搞砸了，我们可能会破坏重要数据，并可能使主进程崩溃。


然而，我们得到了我们的原语：我们把一个元素scoreboard->procs[]指向我们想要的任何地方，并杀死相关的工人。根据其used字段的值，它将被设置为1，或者清除它周围的 1168 个字节。


从现在开始，这些原语将分别命名为set-0-to-1和clear-1168-bytes原语。


沙箱

从现在开始，我们假设我们已经使用PHP 沙箱转义（例如 SplDoublyLinkedList::offsetUnset）在工作人员中完成了读/写。我们可以通过发送多个并发请求来强制创建工作线程，并通过向其发送SIGKILL信号来杀死任何工作线程。


我们希望从工作进程中的完全读写访问升级到根进程中的代码执行。


为此，我们有一些事情要做：


  • 由于工作进程是从主进程分叉出来的，因此它们共享相同的内存映射（ASLR 无关紧要）。

  • 它们的堆也很相似：尽管在一个 worker 产生时会发生很多 allocs/deallocs，我们仍然可以通过读取主进程的子进程的内存来了解主进程的堆的内容。

  • 最后，如果我们在利用过程中以某种方式使子进程崩溃，主进程将重新启动它。


但是，我们也有一些问题：

  • 原语很糟糕：如果used没有我们期望的值，我们将销毁 1168 字节的内存，而不是仅仅将一位从 更改0为1；通常，这意味着崩溃。如果主进程崩溃，那么您和网站的游戏就结束了。即使我们设法不搞砸，我们也可以清除一个巨大的内存范围或将零变为一。这没什么可做的。

  • 在fork 之后，worker 会释放很多结构，因为它们只被主进程使用。如果新生成的 worker 在生成时不知何故具有不正确的堆状态，它将退出或崩溃。因此，主进程将产生一个新的，仍然是一团糟的工人。这将再次退出。这将无限期地持续下去，并导致 DOS。

  • 为了控制我们的原始人，我们将不得不快速连续地产生和杀死工人。如果普通用户在不方便的时候浏览网站，他可能会搞砸我们的漏洞利用，这可能会导致 root 进程崩溃。

总之，破坏主进程的方法有很多，获得代码执行的方法并不多。


裁剪原语

尽管我们对主进程的内存布局有一个不错的了解，但我们不能总是 100% 确定给定的 32 位整数为零。因此，我们的两个原语可能会混淆，我们可能会导致进程崩溃。


为了避免这种情况，我们首先杀死一个工人，然后scoreboard->procs[]只有在fpm_scoreboard_free_proc()被杀死后才更改元素。这可以通过监视 的值轻松完成，该值scoreboard->free_proc在函数结束时更改。然后，一旦fpm_scoreboard_free_alloc()被调用，我们就重置指针（同样，我们可以free_proc对此进行监控）。


通过一些涉及记分牌结构和超出文章范围的额外技巧，我们可以保证，虽然我们并不总是赢得比赛，但我们永远不会破坏任何东西。


我们的set-0-to-1原语变得更好了一点：我们不能再memset()错误地触发，并且减少了一种破坏 PHP-FPM 的方法。其他人来了。


到达堆：设置 catch_workers_output

现在我们的set-0-to-1原语是安全的，我们需要找到它的用途。就其本身而言，它没有多大用处：例如，我们可以破坏长度或块大小，但我们不能在主进程中创建任意数据（共享内存段除外）。换句话说，也许我们可以做更大的东西，但我们不能让它包含我们控制的数据。


因此我们需要一种向主进程发送数据的方法，并且在工作池配置中有一个完美的解决方案：

pwndbg> p *fpm_worker_all_pools->config$2 = {name = 0x559e247bf020 "www",prefix = 0x0,user = 0x559e247b73d0 "www-data",group = 0x559e247b73f0 "www-data",listen_address = 0x559e247b73a0 "/run/php/php7.4-fpm.sock",listen_backlog = 511,listen_owner = 0x559e247b7440 "www-data",listen_group = 0x559e247b7460 "www-data",listen_mode = 0x0,listen_allowed_clients = 0x0,process_priority = 64,process_dumpable = 0,pm = 2,...rlimit_files = 0,rlimit_core = 0,chroot = 0x0,chdir = 0x0,catch_workers_output = 0, // <-----------------decorate_workers_output = 1,clear_env = 1,security_limit_extensions = 0x559e247b7480 ".php .phar",env = 0x0,php_admin_values = 0x0,php_values = 0x0,apparmor_hat = 0x0,listen_acl_users = 0x0,listen_acl_groups = 0x0}

里面有很多东西，但一个看起来很有趣：catch_workers_output。它的用途是将工作人员的输出聚合到单个日志文件中php-fpm.log。


因此，在设置时，如果工作人员写入stdout或stderr，则数据将发送到根进程，该进程将其缓冲直到遇到换行符。发生这种情况时，该行将存储到日志文件中，并刷新缓冲区。此缓冲区默认为固定大小1024，并分配在堆上。


catch_workers_output默认为关闭( 0)。我们使用原语将其设置为1。我们现在可以在主进程的堆中发送几乎任意的数据；我们只需要写入工人的stderr。


够好了 ？

现在我们可以在根进程的堆中发送（almost)）任意数据，并且有两个原语，我们可以很容易地进行堆攻击。例如，通过使用set-0-to-1原语，我们可以更改块大小；通过使用其他原语，我们可以清除 tcache 指针 LSB ...


一个例子：我们可以使用 3 个 worker 来强制分配 3 个连续的日志缓冲区，并按照选定的顺序释放它们。由于它们都适合 tcache，我们可以使用我们的clear-1168-bytes原语覆盖第一个块的指针的 LSB ，我们会有一个很好的起点。


然而，这种攻击和许多其他攻击一样，在某些时候依赖于不稳定的堆。如果一个合法的客户端在这个时间点发送一个请求，它可能会产生非常糟糕的影响：崩溃，DOS，......


即使使用不同的方法，结论仍然是相同的：无论理论上的利用策略有多好，如果在利用的关键阶段处理合法请求（及其潜在错误），则很可能发生崩溃。我们需要找到一种方法将服务器留给我们自己。


限制工人数量

每当一个新的 worker 从主进程中分叉出来时，它就会摆脱不需要的结构。这种结构包括所有工人的zlog_stream和buffer。它还将分配新的东西，这将触发malloc_consolidate(). 在我们的每一个利用思路中，堆在很短的时间内都处于无效状态：一个块头可能是无效的，一个条目可能在 tcache 中出现两次......假设此时产生了一个工人。它继承了坏堆，尝试使用它……然后 libc 发出错误并引发SIGABRT. 通常我们不会关心：PHP-FPM 会重新启动它崩溃的子进程。但是，由于我们启用了catch_workers_output，错误消息被发送回主进程，它应该创建一个日志缓冲区来接收错误。主进程中的堆也被破坏了，主进程也最终崩溃了！


即使工作进程无声地崩溃，主进程也会在做任何其他事情之前重新生成它。它会再次崩溃，导致进程的生死循环。


因此，我们需要一种方法来阻止主进程产生工人。请记住，在生成工作线程之前，主进程将确保子记分板可供其使用。一个明显的想法是将->usedevery的标志设置scoreboard->procs[]为1。然而，当主进程反复产生新的工作人员时，这证明真的很难：您需要在结构被清空后立即设置它。幸运的是，fpm_scoreboard_proc_free()和fpm_scoreboard_proc_alloc()不同的表现一点点：

如果你的代码再看看，你会发现，fpm_scoreboard_proc_free()检查那used是优越于零，同时fpm_scoreboard_proc_alloc()检查，这是不同的从零。因此，设置used为-1阻止这两个功能执行任何操作。


这允许我们阻止工人产生，从而限制工人的最大数量。例如，在默认配置下，它允许5名并发工人最多，如果我们将used要-1在3分的记分板，PHP-FPM将只能够产卵2。


此外，当我们杀死一个工人时，我们甚至可以先发制人地将其used标志设置为-1，确保 PHP 不会立即重新生成一个。


另一个结果是，我们现在可以针对 5 个最大并发工作人员的默认配置定制我们的漏洞利用。如果目标 PHP-FPM 服务恰好允许更多，我们将把这个数字限制回 5。我们可以构建一个与配置无关的漏洞利用。


封闭式FD

由于我们对 的修补程序catch_workers_output，当 PHP-FPM 以非常高的速度产生工作人员时，可能会发生竞争条件，即应该接收 CGI 请求的fd在使用之前关闭。这会导致 worker 立即退出（如果它无法接收请求，那么活着还有什么意义），导致主进程重新生成它。但是，立即重生会产生完全相同的问题，并且工作人员再次退出。无限循环。幸运的是，这可以通过使用与上述相同的技术阻止工人的生成片刻来解决。

一旦我们启用，这些错误就会变得烦人catch_workers_output：它们被写入stderr，因此被转移到主进程，主进程将创建日志流和缓冲区来存储它们。由于这些堆块是我们唯一可以控制的，因此我们希望将它们保留给我们自己。


幸运的是，在将 PHP 错误写入 FD 之前，会发生很多事情。这是工作进程中的示例堆栈跟踪，它产生错误：

ZCG(some_key)扩展到accel_globals.some_key. 这个accel_globals结构是从主进程继承而来的，并且包含许多空字段，比如ZCG(record_warnings) 1和ZCG(warnings) 2。通过将两者设置为1使用我们的set-0-to-1原语，每个工作进程将继承值。因此，任何PHP错误将导致persistent_error_cb()输入if块，并且最终会调用erealloc()与1在其第一个参数，从而崩溃工人。由于工作程序在写入stderr之前崩溃，因此主进程永远不会收到错误，并且没有分配堆块。


使用所有这些调整，我们能够优雅地控制哪个 worker 执行什么，产生多少 worker，并阻止 PHP 错误破坏我们的漏洞利用。


无问题的开发策略

把所有这些问题都抛在脑后，我们已经准备好找到一个有效的开发思路。还记得上一节讨论的重叠块攻击吗？


在实践中，这要困难得多：由于我们对 进行了热修复catch_workers_output，PHP-FPM 没有机会设置与工作人员交互所需的 FD。因此，一些工作人员只能使用stdout将数据发送到主进程，而其他工作人员只能使用stderr。其他人不能发送任何东西。更糟糕的是，有时，工人代表他人写作。这使得拥有三个连续的块变得非常困难。而这只是我们攻击的第一个要求。


管理流：zlog_stream

为了管理主进程中的stderr缓冲区，PHP-FPM 为每个 worker 分配了另一个结构：zlog_stream. 它包含缓冲区的地址、大小、写入其中的字符数等。


让我们多看一点。

当一个工作者将它的第一个字节发送到 stderr 时，它zlog_stream被创建。起初，没有分配缓冲区：stream->buf.dataisNULL和stream->buf.sizeis 0。光标的位置stream->len也为零。


当stderr不是空行时，日志流会创建一个缓冲区来存储发送的字符。发送test\n结果有以下变化：

现在我们对日志流有了一个基本的（但足够的）概述，让我们深入研究负责将数据附加到缓冲区的代码。


无法访问的堆溢出

如前所述，每当工作人员写入stderr 时，主进程实现的第一步是创建一个zlog_stream结构（如果尚未完成）。


此后，它从相应的 FD 中读取，并调用zlog_stream_str()，如果读取到某些内容，则调用zlog_stream_buf_append() 1：

static ssize_t zlog_stream_buf_append(        struct zlog_stream *stream, const char *str, size_t str_len) // [1]{    int over_limit = 0;    size_t available_len, required_len, reserved_len;

让我们回顾一下参数：stream负责工人的日志流，str包含写入的字节stderr，并str_len写入的字节数。


如果尚未向缓冲区写入任何内容（stream->len为零），则zlog_stream_prefix_ex()调用。如果stream->buf.data尚未分配，则完成，大小为stream->buf_init_size(1024)。在此之后，stream->msg_prefix被添加到消息的开头，并相应地len增加2。


然后，PHP-FPM 验证存储数据所需的总大小未超过全局最大值zlog_limit 3。这是一个等于 1024 的整数。就这么简单：stream->buf.data永远不能在 中写入超过 1024 个字节。


然后调用zlog_stream_buf_copy_cstr() 4：

static inline ssize_t zlog_stream_buf_copy_cstr(        struct zlog_stream *stream, const char *str, size_t str_len) /* {{{ */{if (stream->buf.size - stream->len <= str_len /* [5] */ && !zlog_stream_buf_alloc_ex(stream, str_len) /* [6] */) {return -1;    }

如果缓冲区5 中没有足够的剩余大小，则重新分配6。我们输入最后一个函数，zlog_stream_buf_alloc_ex()：

如您所见，发生了一个可怕的错误：缓冲区在 的函数中（重新）分配needed，而stream->len完全忽略了。这会导致父函数的memcpy()调用7溢出，其范围为stream->len + str_len，而缓冲区的大小为str_len。


但是，如前所述，当stderr的第一个字节进入主进程时，将添加前缀，从而创建大小为1024 2的缓冲区。紧随其后的代码片段禁止我们将多个1024字节写入缓冲区；这可以防止我们在正常情况下触发溢出。


伪造流，获得根

堆溢出

我们还有一件事要做：我们心爱的set-0-to-1原语。


我们可以欺骗stream->len和stream->buf.size使用它，但zlog_limit作为一个上限。因此，当他们是零，我们只能给他们的3个可能的值之一：1，0x100，和0x101（因为0x10000 > zlog_limit）。


假设我们将两者都设置为L，并将N字节写入标准错误（使用L + N < zlog_limit - 2）。有时候是这样的：

  1. zlog_stream_buf_append(stream, str, N).

  2. zlog_stream_prefix_ex()没有被调用，并stream->buf.data保持NULL。

  3. required_len < zlog_limit，因此available_len = N。

  4. zlog_stream_buf_copy_cstr(stream, str, N) called。

  5. 由于两者buf.size和len是相等的，检查总是为真。

  6. zlog_stream_buf_alloc_ex(stream, N)被调用，并分配N字节。

  7. memcpy(stream->buf.data + L, str, N)被调用，L字节溢出。

因此，我们可以创建一个任意大小的日志缓冲区N，并在其后溢出L( 1,0x100或0x101) 字节。


但是，堆中包含的对象非常小；这些溢出大小对于我们的喜好来说要么太小，要么太大。我们需要更进一步。首先，我们利用L=1，我们得到以下log_stream结构：

stream->buf.data = malloc(N)stream->buf.size = Nstream->len = N + 1

然后，我们可以在 的第三个字节上再次应用原语buf.size。我们得到：

stream->buf.data = malloc(N)stream->buf.size = 0x10000 | Nstream->len = N + 1

然后，如果我们M向stderr写入额外的字节，我们有：


  1. zlog_stream_buf_append(stream, str, M).

  2. zlog_stream_prefix_ex() called

  3. required_len < zlog_limit，因此available_len = M。

  4. zlog_stream_buf_copy_cstr(stream, str, M) called。

  5. 由于buf.size既大又len小，支票总是假的。

  6. zlog_stream_buf_alloc_ex(stream, N)not called

  7. memcpy(stream->buf.data + 1 + N, str, M)被调用，1 + M字节溢出。

我们现在有一个 size 溢出M + 1，在size的缓冲区上N，两个变量几乎是任意的。


任意写

创建日志流将产生一个zlog_stream块 ( 0x80) 和一个msg_prefix块 ( 0x40)。我们可以为任何工人创建一个。我们创建尽可能多的，并寻找一个流块（称为@overflowed），它紧跟在流块或 msg 前缀块之前@replaced。我们还选择了另一个日志流，我们将其命名为@corrupted。

通过将set-0-to-1原语应用于@corrupted->buf.sizeand @corrupted->len，我们可以N通过向的stderr发送N字节来分配任意大小的块。我们使用它来分配位置。现在指向之前的块。@corrupted@replaced@corrupted->buf.data@overflowed

我们现在最后一次应用原语，因此它@corrupted->buf.size增加了0x10000。我们现在可以写越界，即覆盖@overflowed。我们可以buf.data指出任何事情！但是，我们只能做一次。


因此，我们@overflowed->buf.data指出@corrupted。通过写入@overflowed的stderr，我们可以修改@corrupted( zlog_stream) 及其缓冲区指向的地址。然后我们可以写入@corrupted's stderr来写我们想要的东西，我们想要的地方。

这样，我们有一个写入另一个的日志流：我们得到了循环的任意写入。从那里，我们可以修复配置、堆，最后覆盖函数指针以获得代码执行。
