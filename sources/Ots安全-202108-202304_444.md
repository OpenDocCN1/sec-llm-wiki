**v8 中的属性访问**

错误本身发生在与属性访问相关的优化（JIT 编译）代码中，尤其是全局属性访问。属性访问在 v8 中是一个相当复杂的系统，它在过去导致了许多可利用的错误。（例如，这个也在野外被利用的bug和这个 bug。）负责属性访问的代码大致在三个不同的层中实现：

*   像SetProperty和这样的方法中最通用GetProperty的object.cc
    
*   在目录中实现的内联缓存实现ic
    
*   JSNativeContextSpecialization优化阶段的 JIT 优化实现，主要是通过方法实现ReduceNamedAccess的，它使用的方法，以及LoadElimination阶段
    

这些代表了 v8 中大约三个不同级别的优化。由于属性访问是 Javascript 中的常见操作，因此该子系统进行了大量优化。为了实现这些优化，相当多的元数据与每个属性相关联，设置属性不仅涉及更改属性的值，还涉及为元数据分配适当的值，然后用于在优化的 JIT 代码中进行假设. 因此，重要的是每一层都以一致的方式更改元数据，以便优化代码中的假设不会变得无效。在非常高的层次上，此漏洞是 JIT 编译的代码设置与元数据不一致的属性值的结果，然后导致其他 JIT 编译的代码做出的假设变得无效。

  

我现在将介绍与此错误相关的属性元数据。

  

**对象贴图、贴图稳定性和贴图过渡**

映射（或隐藏类）的概念对于 Javascript 解释器来说是相当基础的。它表示对象的内存布局，对于优化属性访问至关重要。由于已经有很多关于这个主题的好文章，例如Mathias Bynens 的“ JavaScript 引擎基础：形状和内联缓存”和Camillo Bruni 的“ V8 中的快速属性”，我将不再详细介绍。从安全的角度来看，地图之所以重要，原因如下：

1.  Maps 保存有关对象内存布局的信息，这些信息用于加速属性访问。
    
2.  优化的代码通常依赖于对输入对象的映射所做的假设。如果这些假设变得无效，那么优化后的代码可能会访问错误内存位置中的属性或用错误的类型表示属性。

新地图 ( MapB) 已经存在，因此地图 forx/obj.x简单地过渡到MapB. 在这种情况下，MapA本来就不稳定。

  

因此，当全局变量或对象属性的映射发生变化时，可能会发生以下两种情况之一：

1.  变量/属性被重新分配，在这种情况下原始地图的稳定性保持不变。
    
2.  地图在没有重新分配的情况下被更改，在这种情况下，原始地图 ( MapA) 变得不稳定，要么是因为添加了新的过渡，要么是因为它已经不稳定。
    

  

这个观察对于检查优化的 JIT 代码的有效性很重要。优化代码在对对象的映射进行假设时，需要确保映射不发生变化。这通常涉及检查以下内容：

1.  这个对象是对全局变量的访问还是对属性的访问？
    
2.  这个变量/属性可以以可能改变其映射的方式重新分配吗？
    
3.  如果问题二的答案是false并且地图是稳定的，那么当地图变得不稳定时确保代码去优化。否则，地图可能会更改而无需重新分配。
    
4.  如果问题三的答案是true或者地图已经不稳定，那么要么放弃优化代码，要么插入CheckMap代码以确保地图保持不变。
    

  

对于问题二，GlobalPropertyDependency通常用于全局变量访问。如果使用通用路径（即使用SetProperty）重新分配相关全局变量，则它将优化代码标记为无效并取消优化。通过内联缓存重新分配（除非有缓存未命中，这将恢复到通用路径）和 JIT 优化路径不会导致去优化，因为这些代码有其他检查来确保属性的地图和其他相关元数据不要换。

  

为确保相关映射保持稳定，DependOnStableMap使用 ，如果相关映射变得不稳定，它会去优化代码。

  

在 JIT 编译器的许多地方，假设在没有通过通用路径重新分配变量/属性的情况下，稳定映射无法更改。

**获得代码执行**

首先，我应该解释 v8 中称为指针压缩的优化。在 v8 中，大多数引用仅作为堆中完整 64 位指针的低 32 位存储，而高 32 位保持不变并缓存在寄存器中。这些较低的 32 位地址称为压缩指针。因此，v8 中的任意读/写实际上由两个不同的部分组成：第一个是对任何压缩指针地址的任意读/写，第二个是对任何绝对地址的任意读/写。

  

请注意，v8 堆是一个非常简单的线性堆。对象是连续线性分配的。因此，例如，如果我按以下顺序创建对象：

**结论**

在这篇博文中，我分析了 CVE-2021-30632 并介绍了 v8 中的属性访问子系统。优化属性访问时所做的许多假设，以及属性访问的不同实现（通用、内联缓存和 JIT）意味着必须格外小心以确保对象状态的一致性。这个子系统中的漏洞通常很微妙，即使是有经验的审计员也很难发现。我希望这种分析对对该子系统感兴趣的研究人员有所帮助，并有助于使其更加安全。
