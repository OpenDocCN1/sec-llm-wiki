点击上方蓝字“Ots安全”一起玩耍

这篇博文描述了我在 2020 年 10 月至 2021 年 1 月期间对 SAP J2EE Engine 7.50 的研究。第一部分描述了我如何着手寻找一个纯粹的 SAP 反序列化小工具，它允许利用 SAP 的 P4 协议进行开发，以及如何纯粹是巧合，我发现了一个完全不相关但至关重要的漏洞，这在第二部分中进行了概述。

假设读者熟悉 Java 反序列化，并且应该对 Java 中的远程方法调用 (RMI) 有基本的了解。


序幕

2016 年，我第一次开始研究 Java Exploitation 的主题，或者更准确地说：对 Java 对象的不安全反序列化的利用。由于我的专业历史，看一下用 Java 编写的 SAP 产品是有意义的。自然，SAP NetWeaver Java 的 P4 协议引起了我的注意，因为它是一种类似于 RMI 的远程管理协议，类似于 Oracle WebLogic 的 T3。2017年5月，我发表了一篇博文关于使用 Jdk7u21 小工具获取 RCE 的漏洞利用。那时，SAP 很久以前就已经提供了修复程序。从那时起，这个话题就没有让我一个人呆着。虽然几乎每个月都有针对 Oracle 的 Java 服务器产品的新反序列化小工具，但让我惊讶的是没有人听说过具有类似影响的 SAP 反序列化小工具。更重要的是，因为每个了解 SAP 软件的人都知道他们随每个产品提供的大量代码。在我看来，他们完全不可能完全免疫过去六年 Java 世界中最突出的错误类。2020 年 10 月，我终于找到了时间和精力开始新的狩猎。令我非常失望的是，搜索最终没有成功。一个产生类似于著名的 ysoserial 项目的 RCE 的小工具仍然看不到。然而在 1 月份，我发现了一个完全不受保护的 RMI 调用，它最终产生了对 J2EE 引擎的管理访问权限。除了它可以通过 P4 调用这一事实之外，它与反序列化主题没有任何共同之处。即使只是偶然发现，它仍然是非常关键的，并允许危害底层 J2EE 服务器的安全性。

该漏洞被归档为 CVE-2021-21481。2021 年 3 月 9 日，SAP 提供了修复程序。SAP 注释 3224022 描述了详细信息。


P4 和 JNDI

清单 1 显示了一个使用 P4 连接到 SAP J2EE 服务器的小程序：

import java.security.KeyStore;import java.util.Properties;
import javax.naming.Context;import javax.naming.InitialContext;
import com.sap.engine.services.keystore.interfaces.KeystoreManagerWrapper;
public class Sample {
public static void main(String[] args) throws Exception  {Properties p = new Properties();  p.put("java.naming.factory.initial", "com.sap.engine.services.jndi.InitialContextFactoryImpl");  p.put("java.naming.provider.url", "p4://10.10.100.11:50004);  p.put("java.naming.security.principal", "Administrator");  p.put("java.naming.security.credentials", "xxxxxxxx");  Context ctxt = new InitialContext (p);
  KeystoreManagerWrapper keysMngr = (KeystoreManagerWrapper) ctxt.lookup ("keystore");  KeyStore keystore = keysMngr.getKeystore("whatever");  }}

该代码与称为P4的专有协议有关的唯一提示是以P4://. 除此之外，一切都由 P4 RMI 调用封装（对于那些想要刷新他们关于 JNDI 的记忆的人）。此外，幕后发生的事情与 RMI 有什么关系并不明显。但是，如果您更仔细地检查所涉及的 Java 对象的类型，您会发现它keysMngr是类型 com.sun.proxy.$Proxy（实现接口KeystoreManagerWrapper）并且 keysMngr.getKeystore()是一个普通的 RMI 调用。参数（要实例化的密钥库的名称）将被序列化并发送到服务器，该服务器将返回一个序列化的密钥库对象（在这种情况下它不会，因为没有“无论如何”的密钥库）。同样不明显的是， 的实例化InitialContext需要在后台进行各种 RMI 调用，例如RemoteLoginContext允许使用提供的凭据处理登录的对象的实例化。

理论上，这些 RMI 调用中的每一个都是一个接收器，可以向其发送反序列化小工具。在我上面提到的漏洞利用中，内部的第一个调用new InitialContext()用于发送 Jdk7u21 小工具（java.lang.String顺便说一下，而不是对象）。


现在，由于 Jdk7u21 小工具不再可用，而我正在寻找仅由 SAP 类组成的小工具，我不得不与一个非常烦人的限制作斗争：类加载器分段。SAP J2EE 了解各种类型的软件组件：接口、服务、库和应用程序（可以由 Web 应用程序和 EJB 组成）。部署组件时，您必须声明对组件所依赖的其他组件的依赖关系。通常，Web 应用程序依赖于 2-3 个服务和库，这些服务和库也与其他服务和库有一些依赖关系。在这个依赖链的底部是核心组件。


现在，我所说的限制是依赖管理极大地影响了组件可以看到哪些类：它可以精确地看到它所依赖的所有组件的所有类（当然还有 JDK 类），但不能更多。如果您的类作为上述密钥库服务的一部分提供，则它只能从密钥库服务声明为依赖项的组件中解析类。

图 1：keystore 服务与所有子类和父类加载器的依赖关系

这对小工具开发产生了巨大的影响。假设您发现一个小工具，其类来自组件 X、Y 和 Z，但这些组件之间没有依赖关系，此外，没有任何组件依赖于所有这些组件。然后，无论您的小工具将在哪个类加载器上下文中被反序列化，类路径中至少会缺少 X、Y 或 Z 之一，并且反序列化将以ClassNotFoundException. 通过使用与GadgetProbe 项目中描述的方法类似的方法， 我发现在上述漏洞中反序列化 Jdk7u21 小工具时，只有大约 160 个可见的非 JDK 类实现 java.io.Serializable. 不适合构建漏洞利用。回到清单 1，如果我们发送一个小工具而不是字符串“whatever”，我们可以从图 1 中看出来自十个组件的类（在“直接父加载器”下面列出的那些）将在类路径中。发送任意可序列化对象而不是字符串“whatever”的代码可能如下所示（而不是keysMgr.getKeystore()）：

不管类加载器的挑战如何，我都渴望了解服务器中存在多少可序列化的类。核心层的类、服务和库的数量大约有10万个，这还不算应用程序代码。我很快意识到我需要比 Eclipse 的分析功能更智能的东西来处理这样的数量。所以我开发了自己的工具，它使用OW2 ASM 框架分析 Java 字节码。它将对象和接口继承依赖项、方法、方法调用和属性写入 SQLite DB。事实证明，在 100,000 个类中，大约有 16,000 个实现了 java.io.Serializable. RDBMS 方法非常方便，因为它允许构建复杂的查询，例如

我发现的第一个有趣的类之一是使用private void readObject(java.io.ObjectInputStream). 四年前的直接打击至少可以在 2020 年取得可观的成功。请记住：Oracle JRE 在 2019 年 JRE 1.8.0_191 版本中解析 LDAP 引用时终于关闭了远程类加载。如果这是可利用的，至少对于具有过时 JRE 的系统来说，它会开辟一条攻击途径。我的 SAP J2EE 运行在 2015 年的 JRE 版本 1.8.0_51 之上，所以 JNDI 注入应该有效，但令我惊讶的是，它没有。原因可以在以下方法getObjectInstance中找到javax.naming.spi.DirectoryManager：

突出显示的调用getObjectFactoryFromReference是攻击者需要到达的地方。该方法使用URLClassLoader攻击者提供的代码库解析 JNDI 引用。然而，正如人们很容易看到的那样，如果getObjectFactoryBuilder()返回一个非空对象，则代码在以下 if 子句的两个分支中的任何一个中返回，并且getObjectFactoryFromReference永远不会到达对下面的调用。而这正是发生的事情。SAP J2EE 注册ObjectFactoryBuilder类型为com.sap.engine.system.naming.provider.ObjectFactoryBuilderImpl. 该类将尝试根据factoryName-attribute查找工厂类并完全忽略codebaseJNDI 引用的-attribute。底线是 JNDI 注入可能永远不会在 SAP J2EE 中起作用，这将消除 Java 反序列化攻击上下文中最重要的攻击原语之一。


CVE-2021-21481

在离开我如何搜索反序列化小工具之后，我现在想介绍真正的漏洞，它与 Java 反序列化完全无关。它是 CWE-749: Exposed Dangerous Method or Function 的普通实例。让我们回到清单 1。我们可以看到 JNDI 上下文允许按名称查询接口，在我们的示例中，我们KeyStoreManager通过名称“keystore”查询 接口。有几次，我已经尝试为使用 P4 的 SAP J2EE 引擎管理找到一个可用的富客户端。每次我不成功，我都相信这样的客户不存在，或者至少不是每个人都可以使用。

但是，无论何时安装 SAP J2EE 引擎，默认情况下都会启用 P4 端口，并在与 HTTP(s) 服务相同的网络接口上进行侦听。因为我完全专注于反序列化，很长一段时间我都忘记了可以通过 JNDI 上下文收集多少信息。例如，获取所有绑定很简单：

SAP J2EE Engine 的配置设置按层次结构组织。对象的位置可以通过路径指定，就像文件系统中文件的路径一样。上面的代码JUpgradeIF_Stub通过查询名称为“MigrationService”的 JNDI 上下文获取对 的引用，Configuration通过调用获取对象 的实例，openCfg()然后沿着路径向下走到叶节点。在那里找到的元素可以导出到存储在服务器文件系统中的存档（调用export(String path)）。如果仔细选择，服务器上的本地路径将指向 Web 应用程序的根文件夹。在那里，download.zip 可以简单地通过 HTTP 下载。如果您想自己检查，UME 配置存储在 cluster_config/system/custom_global/cfg/services/com.sap.security.core.ume.service/properties.

您可能会说“嘿！我需要成为管理员才能做到这一点！有什么危害？”。没错，我也是这么想的。但您既不需要成为管理员，也不需要通过身份验证。下面的代码工作得很好：

但是，调用时会出现权限异常 keysMngr.getKeystore()（因为getKeystore()确实有权限检查）。但是JUpgradeIF.openCfg()在 SAP 修复之前错过了检查。


此时，即使没有 SAP 特定知识，攻击者也可能造成重大伤害。例如，用档案充斥服务器的文件系统，导致资源耗尽 DoS 条件。


凭借一点内幕知识，您可以获得管理员访问权限。在配置树中，有一个名为TicketKeystore的密钥库。其加密密钥对用于签署 SAP 登录票证。如果您窃取了密钥库，您可以为管理员用户签发一张票并以完全管理员权限登录。还有各种其他密钥库，例如用于 XML 签名等（更不用说这个存储库中有大量东西的事实。没有人可能知道您可以访问的所有安全敏感内容......）


这些信息应该足以理解 CVE-2021-21481。配置中密钥库的确切位置以及通过 HTTP 下载存档的相对本地路径留给读者作为练习。
