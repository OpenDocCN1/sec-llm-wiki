**概述**

上周五，我在 Jira 数据中心 (CVE-2020-36239) 中看到了针对关键 RCE的Atlassian 安全公告，因此我决定尝试为其开发概念验证漏洞利用。这最终花了我大约 5 个小时。这篇简短的博客文章详细介绍了我创建 POC 的过程。我还包括了我犯的一些错误和死胡同，这些在 POC 文章中经常遗漏。

  

这是为修补的漏洞创建 POC 的一个很好的练习，因为我能够在不区分补丁的情况下做到这一点。我学到了更多关于利用 RMI 的知识，以及 JEP 290 中的变化。

  

**调查错误建议**

阅读公告的详细信息，很明显该漏洞仅影响数据中心，而不是独立服务器模式。它影响了一个名为 Ehcache 的组件，它似乎是一个基于 Java 的缓存，它以某种方式支持 RMI 进行通信。可利用性需要连接到端口 40001 和可能的 40011。这似乎是 Ehcache 正在侦听的端口，如果它正在侦听非标准端口，它也可能容易受到攻击。该咨询包含大量有用的详细信息，例如：

ysoserial gitter上的一篇文章让我看到了这篇非常有帮助的文章。根据文章，在 JEP290（影响我正在运行的 JDK 版本）之后，JDK 为 RMI 注册表和 DGC（JRMP 使用）内置了过滤器。这些过滤器只允许反序列化特定的类。所以这就解释了为什么没有一个常规的 Ysoserial 小工具可以通过 RMIRegistry 漏洞利用。

  

继续阅读，我发现仍然可以使用绕过 gadget或通过将任意对象传递给 RMI 服务器来利用反序列化问题，只要存在接受非原始类型的方法。我想我会尝试任意对象方法，如果我不能让它工作，稍后再回到旁路小工具。

**寻找合适的小工具**

这确实执行了 DNS 查找，所以我知道我走在正确的道路上。接下来，我尝试使用 ysoserial gadget 对接口进行暴力破解，以找到允许代码执行的接口，RMItaste 使用“-gen bruteforce”参数支持该接口。

虽然它确实返回了相当有希望的消息Remote method has been invoked with payload: Spring2 notepad.exe，但不幸的是没有 notepad.exe 即将到来。

  

我开始怀疑这个漏洞是否需要一个自定义的 Java 反序列化小工具，这可能很难找到和利用。在开始这条路线之前，我更仔细地阅读了该工具的输出，并注意到它没有包括所有的 ysoserial 小工具！这是因为暴力破解的小工具列表是硬编码在 RMItaste 源中，而不是从 ysoserial jar 中动态发现的。

  

稍后我进行了快速的 bash，我尝试了 ysoserial 必须提供的每个有效负载，结果生成了 notepad.exe！作为旁注，calc.exe 没有产生，即使有一个有效的漏洞利用。我认为这是因为它现在是一个 UWP 应用程序？
