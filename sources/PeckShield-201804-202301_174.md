# EOS越界漏洞的分析与重现

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzU3MTU2NTU1MA==&mid=2247483680&idx=1&sn=4f7b6b895cc4bd5bf11850e85c3db822&chksm=fcdf75a1cba8fcb79edb249261092076a89b359339b0622fd6357576a1c15b62e5f110b02162&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=MzU3MTU2NTU1MA==&mid=2247483680&idx=1&sn=4f7b6b895cc4bd5bf11850e85c3db822&chksm=fcdf75a1cba8fcb79edb249261092076a89b359339b0622fd6357576a1c15b62e5f110b02162&scene=27#wechat_redirect)

今天，奇虎360在其Blog中发布了EOSIO软件包中nodeos程序的一个越界漏洞，此漏洞被利用后可以触发远程代码执行（RCE，Remote-Code-Execution）攻击。考虑到此漏洞的重要性，而且EOS主网即将上线，PeckShield的安全专家立即对nodeos的代码库进行了分析，并成功重现了Blog中所提到的，通过构造恶意智能合约致使EOS客户端崩溃的问题。

我们快速的回顾下此漏洞。图1展示了相关的WASM合约处理逻辑，第75行由不可信的合约二进制中解析出了本地变量offset，红圈部分第78行的代码引用了offset变量从而导致了越界问题。

![](../Images/f2eae46169e44b0171b0392c334ef2b2.png)

  

图1:存在漏洞的WASM合约处理逻辑

  

您可能也发现了在第76行有一个assert()函数调用，用来保证第77行-79行的循环访问的元素索引不会超过table向量的实际大小（module->table.initial）。然而，如修复bug时所提交的log所提到的（图2），assert()函数仅在调试模式才生效，在生产版本中并无效果。

![](../Images/4aad1b6f0fc1aa7559311c935d284a5d.png)

  

图2：修复WASM合约处理逻辑的代码

  

这就解释了为什么只需简单的将assert()改为FC\_ASSERT()即可修复问题。在理解了这个漏洞的内在逻辑后，我们构造了一个名为malice\_eos\_contract.cpp的恶意智能合约，并成功重现了\[1\]中所提到的崩溃。

首先，使用如下命令来将合约编译成WAST格式：

```


```
eosiocpp -o malice\_eos\_contract.wast malice\_eos\_contract.cpp
```


```

![](../Images/367b976ebad40318fd3f0383529cc16a.png)

  

图3：WAST格式的构造的malice\_eos\_contract合约

  

之后，构造一个非常大的offset值，也就是-1，来触发越界写入（如图3）。

![](../Images/0a10257da8b612b194f541be79901509.png)

  

图4:由于非法访问而崩溃的nodeos进程
