**1、什么是热修复**

  

```
    在业务无需重启的情况下实现对漏洞紧急修复。热修复一般用于0day漏洞。

```

  

**2、热修复必要性以及特点  
**

****2.2 **热修复的必要性  
**  

    RASP天然具备对命令执行、反序列化等漏洞的防护能力，因为RASP是在应用程序内部hook关键函数，只关注执行行为，不关注漏洞是什么组件触发的。理论上在hook方法足够的情况下，是不需要进行热修复的。

    然而，实际生产环境下RASP存在多方面不足：  

*   **hook的函数做不到全面，存在绕过的可能**。
    
    这里以命令执行为例子，常见的命令执行调用栈如下  
    
      
    

![](../Images/113d51215cf9ea11ddfb6cfe9b1b7ae7.png)

  

    在Java层面，hook方法越靠近底层，越难以绕过。因此对于命令执行，RASP一般会选择hook住 java.lang.UnixProcess（jdk8以下）和 java.lang.ProcessImpl （jdk9以上）这两个类中的方法。  

    然而对于OS层面的native方法很难hook（这里很难不是说不能实现，实现方式比较繁琐），并且native方法可以通过jdk的unsafe工具类+反射来调用，配合反序列化任意代码执行可以完美绕过RASP检测。  

  

```

```

*   **RASP熔断逃生机制，使得部分hook方法在高负载情况下失效**。
    
      
    

RASP依赖宿主jvm运行，首要的基本原则是不能影响业务代码的正常执行，这就需

要严格控制RASP运行时的性能，当业务性能恶化时，必须有熔断逃生机制，

这意味着RASP安全防护作用大大削弱，即起不到防护作用。以open-rasp为例子，  

当系统负载高于一定值时，RASP放行所有hook点检测。  

  

**2.2 热修复的前提**  

  

   热修复的首要基本条件是可以在**JVM运行时动态增加hook类**（令人遗憾的是目前绝大部分安全产品不具备这个特性）

```

**一般的漏洞修复的研发、部署流程：**


```

修改RASP代码 -----> 验证测试功能 ----->  发布RASP到业务机器上 ----->

 通知业务方重启java进程 -----> RASP新功能生效

  

    如果是面对小规模机器(几百台)，上面的流程没有什么问题；机器数量达到1万之后，等待全部业务完成全部服务的重启，基本上要一周时间，达不到24小时完成全部服务修复止血的目标。

  

**2.3 热修复的优势**  

  

*   在没有可用方案或者方案存在绕过时，只需要知道攻击或者绕过的细节即能够立即堵住漏洞；  
    
*   避免研发工程师进行大范围的频繁迭代升级，给研发工程师提供漏洞修复的缓冲时间，不会打乱研发升级节奏，提升了研发工程师幸福感。

    由于JNDI对log4j来说是以插件形式存在，所以有统一的执行入口，由堆栈图可知RASP可以从几处进行拦截处理，其中“InitialContext.java:417”为原生底层方法，如果在这里增加修复策略，需要考虑正常业务的调用，有误杀的风险和过滤正常业务时的性能影响。所以可用的点为“JndiManager.java:172” 。  

  

优点：  
1\. 由于不需要匹配任何参数，无需担心性能问题；  
2\. 只有解析后的内容使用了JNDI才会触发，无需担心各种变种payload，无对抗成本；  
3\. 只针对log4j2自身使用JNDI的场景，不影响应用正常使用JNDI能力。
