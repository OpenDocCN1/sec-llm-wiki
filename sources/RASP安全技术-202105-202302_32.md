![](../Images/03425630f120e276e1ee80ae3aef7f1e.png)

  

  

RASP与服务紧密结合，处在安全防护的最后关键一环

  

**2、RASP 研发难点**

  

**2.1 侵入性大**

  

      相对于WAF、HIDS等安全产品来说，侵入性最大。从隔离级别来看WAF、HIDS 和 RASP与业务进程的隔离级分别为主机隔离、进程隔离、类加载器隔离，RASP与业务隔离级别是最低的。如果RASP本身出现异常或者故障，将直接对业务造成严重影响。

  

**2.2 部署难**

  

**2.2.1 部署安装量大**

  

       RASP需要部署在每台主机上，面对的是全公司的服务器，少则几百台，多则几十万，整个部署、运维压力很大。

  

**2.2.2 频繁迭代升级**

  

     RASP自身的功能需要进行频繁的迭代升级，包括功能迭代、修复自身bug、虚拟补丁等。

  

**2.3 性能问题**

  

       由于需要将检测流程插入到请求链路中，在运行时产生不属于业务流程本身的逻辑，这样会增加业务执行的流程长度，从而使得服务请求响应时间变长。以Java语言的RASP来说这里的影响可以分为几个方面：内存增长、GC频繁、服务请求延迟、CPU波动等四个方面。

  

**2.4 多语言支持**

  

      针对不同的语言，RASP底层的实现是完全不一样的，都需要重新基于语言特性进行专门的开发，而且需要了解语言的底层如编译、性能优化等知识，开发难度很大。多语言：Java、Go、Nodejs、python、php 等

  

  

**3、JRASP研发部署实践**

  

**3.1  针对侵入性大的实践**

  

*   与传统的RASP架构不同，JRASP 采用**分体式架构**, 将非必要进入业务进程的逻辑（如插件升级、配置监听等）单独抽取成独立Daemon进程，最小化对业务的侵入及资源占用, 提高可用性及稳定性；
    
      
    
*   JRASP 抛弃了之前开源和商业RASP产品大而全的方案，专注解决掉入侵相关的风险，其中 Java Agent 只完成核心功能如字节码转换、入侵检测逻辑等。
    

  

**3.2 针对性能问题实践**

  

**3.2.1  内存占用**

  

       由于JRASP采用分体式架构，非必要的逻辑放在单独进程进行，极大的降低了JVM堆空间消耗，使得 Java 堆空间增长控制在100M以内。

  

**3.2.2 CPU波动**

  

*   一方面，**服务最低峰****自动注入**，CPU消耗极低；
    
*    另一方面，premain 和 agentmain **两种启动方式相结合**，将RASP 消耗 CPU 的较大的操作放在JVM启动前进行。
    

  

**3.2.3 请求延时**

  

*    检测逻辑先触发 JIT 编译优化，待检测方法调用效率达到最优化后，才加入业务执行流程中，从而降低服务请求延时。
    
      
    

**3.3  针对部署实践**

  

*   JRASP 提供一键安装部署包，适配宿主机/容器化部署，安装非常方便，降低部署运维难度；
    
      
    
*   JRASP的守护进程、Java Agent 核心包、安全检测插件都已经实现热更新，管理端新建配置即可以实现升级，无需SRE配合操作。
    
      
    

**3.4  多语言支持**

目前已经开源的有Java RASP，Go语言RASP开源进行中...

  

**4、阻断实践**

**4.1 阻断功能实现**

1.  采集业务运行时特征（通俗点就是运行时读写了哪些文件，加载了哪些类、执行了什么SQL、命令等）；
    
2.  正常行为加入到白名单中，然后开启白名单阻断模式，收集白名单能够有效解决误拦截风险，避免因为误拦截导致的严重事故 （sql白名单、文件读访问白名单、命令执行白名单等）。
