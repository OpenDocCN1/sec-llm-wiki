## 继续测试Blind XXE

我想通过访问内部文件和内部网络试试能不能找到关键信息。  
为了证明影响，我展示一下怎么判断文件存在。

![](../Images/295cdbef487aabd750dadb0ed1a21c60.png)

这表示文件存在并且可以由XML解析器读取，但是并不是有效的DTD，所以解析器错误，我们没有得到任何输出。  
我们还可以认为后端解释器是`Java的SAX Parser`，因为这个错误貌似与`org.xml.sax.SAXParseExceptionpublicId`有关。  
这个好玩，因为Java在涉及到XXE时有许多特点，我们稍后会指出。

![](../Images/e3f85715eb9f1d11d9f85ba1f6017bc1.png)

好耶 - 这意味着我们可以枚举内部的服务。但仍然不是我想要的那种很酷的结果，你懂的，但至少还有一些值得提交的东西。这种类型的`Blind XXE`实际上似乎与SSRF漏洞的行为类似：  
可以有内部的HTTP请求，但无法读取响应结果，很难受。

我在想是否可以应用任何其他与SSRF相关的技术呢？  
以便更好地利用这个`Blind XXE`漏洞。  
要检查的一件事是是否支持其他协议，包括https，gopher，ftp，jar，scp等。我尝试了没有结果的那些，但是它们导致了其他有用的错误消息，例如：

它将用户提供的协议打印回错误消息中。让我们记下来以后再说。

通过SSRF漏洞进一步加强相同性，我们是否可以访问任何内部Web应用程序？。由于我所定位的公司似乎与一个相当广泛和多样化的开发人员合作，GitHub有很多对`x.company.internal`格式的内部主机的引用。我发现了一些看起来比较有用的内部资源，例如：

*   wiki.company.internal
    
*   jira.company.internal
    
*   confluence.company.internal
    

考虑到前面阻止我的传出流量的防火墙，我想验证内部流量是否也被阻止，或者内部网络是否更受信任呢。

![](../Images/e6c3d71673879ee8f28b52052a8a0b8a.png)

nice！

我们之前看到过此错误消息，表明所请求的资源已被读取，但是呢格式不正确。这意味着允许内部网络流量，我们的内部请求成功！

所以这就是我所处的位置。使用`Blind XXE`漏洞，可以向许多内部Web应用程序发起盲请求，枚举文件系统上存在的文件，并枚举在所有内部主机上运行的服务。

## 继续搞事

通常，在没有任何形式的响应反馈的情况下攻击内网Web应用程序几乎是不可能的。不过还好咯，Jira中存在一个已知的SSRF漏洞，有漏洞报告的。

![](../Images/ecb9735a7d8ad4d955d285c3d5f240f6.png)

等下，有东西来了。  
![](../Images/ba70da0b786a82eca013e3aaf19455ef.png)

成功的证明可以连通服务器，然后下面就使用经典的XXE攻击方法，在VPS上放一个`evil.xml`

```text


<！ENTITY％file SYSTEM“file：///”>
```

![](../Images/d8212238153f4e982579cd1e82d55df8.png)

Awesome！  
列出了服务器目录内容。  
`%file`就是模糊匹配。  
而且这种不全的协议，也算是一个新的点。

![](../Images/f840ffb19c7d56155d31911ad86ea2f2.png)

换句话说，可以在第一次出现冒号之前去读取文件:，但不能再读取。绕过此方法然后强制在错误消息中显示完整文件内容的方法是在文件内容之前去添加一个冒号。这将忽略`无协议`的错误，因为第一个冒号之前的字段将为空，即未定义。

payload像这样：

```text


<!ENTITY % file SYSTEM "file:///etc/passwd">
```

![](../Images/3973d335df68b2a4ab3b691f7fb5cfe9.png)

为了让漏洞影响更大，看是不是root权限。

![](../Images/53979b401f8067f1cf24ec53193a6b9a.png)  
woc！运气太好了，Root。
