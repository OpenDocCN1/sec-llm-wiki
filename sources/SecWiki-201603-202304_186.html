我是如何从Github信息泄露中获取10K漏洞悬赏的？

每天都会有API keys，passwords和用户数据被上传到Github上。

攻击者使用这些keys登陆服务器，窃取个人信息，甚至会消费高昂的AWS费用。Github敏感信息泄露可能会造成一个公司成千上万的损失。在Github上收集一个公司的开源情报信息已经成为一个安全研究者的强大工具。NC State的研究人员对此也写了一篇学术论文[1]。

这篇文章是为漏洞悬赏猎人和甲方安全团队而写的。分享了上传到Github的敏感信息常见类型以及如何快速发现它们的一些启发性方法。本文中的技术同样适用在GitHub Gist[2]

使用这些技术，在过去的一年里，我从HackerOne[3]获得了将近$10,000的赏金，甚至都没有访问悬赏项目的Web地址。我提交了30多个Github信息泄露的报告，其中包括8家财富500强的公司。

我还写了一个开源的工具GitHound[4]用于自动化的在Github上查找敏感信息。Githound不限制用户或者组织，它可以遍历整个GIthub，使用代码查找作为项目的入口，使用上下文，正则和一些其他的技巧去获取敏感信息。

GitHub Code Search

在讨论自动化工具和漏洞悬赏方法之前，我们先聊聊代码搜索。

Github提供了强大的代码搜索功能[5]扫描整个公开的Github项目(省略了某些内容，比如forks和非默认分支)。查询n内容可以是简单的uberinternal.com，也可以是像这样的Authorization: Bearer多个字符串。搜索内容可以是特定的文件(filename:vim_settings.xml)和特定的语言(language:SQL)。搜索内容还可以包含一些 布尔字符[6]比如NOT和>。

了解到Github的搜索机制之后，设计搜索工具来获取敏感信息。可以从网上找到GIthub搜索工具，但是最好的还是你自己开发的。

比如：搜索:filename: vim_settings.xml(try it![7])，目标是 IntelliJ settings files[8]。有意思的是，这个vim_settings.xml文件包含最近复制粘贴的Base64编码字符串。我使用这种搜索技巧从一个漏洞悬赏中获得了$2400，SaaS API keys和用户信息被泄露在vim_settings.xml。

vim_settings.xml中仅仅包含近期复制粘贴的字符串，但是我们可以从项目的提交历史中去找整个的复制粘贴内容。将这个项目下载下来，并运行这个14行的脚本[9]。你就可以获取用户的复制粘贴行为。GitHound也可以查找和扫描base64编码字符串来获取敏感信息，甚至在历史提交版本中。

可以看到，使用Github搜索提交[10]，我们很快可以扫描到500,000个修改vim_settings.xml的提交记录。

漏洞悬赏猎人的搜索方法

Github大范围搜索可以发现敏感信息，但是我们该如何搜索一个特定公司的敏感信息？Github上面有上百万个仓库项目，甚至更多的文件。我们需要一些策略方法来缩小搜索范围。

在开始获取敏感信息之前，先确定目标。

我发现最好的开始方法是去找域名或子域名来标识公司的基础结构。

搜索company.com可能不会获得什么有用的结果。因为有很多公司发布了审核后的开源项目，并且不可能包含敏感信息。但是使用子域名就不一样了，比如jira.company.com以及更加通用的二级和更低的域名。查找模式比单个的域名更有效。corp.somecompany.com, somecompany.net, 或 companycorp.com更有可能出现在一个员工的配置文件中。

下面的域名枚举工具会帮助你来更好的获取开源情报。

•Subbrute[11] Python编写的用来暴力枚举子域名•ThreatCrowd[12] 输入一个域名，通过大量的OSINT技术来查找相关联的域名。•Censys.io[13] 输入域名，查找SSL证书

GitHound也可以帮助你发现子域名。添加自定义的正则表达式\.company\.com，使用GitHound的--regex-file参数。

找到要搜索的主机或者模式后，在使用自动化工具之前，我通常会在Github上进行搜索。我通常会问自己几个问题。

•搜索结果是多少? 如果页面超过了100页，我喜欢找一个更好的匹配方式。(Github代码搜索结果限制是100页)•搜索结果是什么? 如果搜索的结果大部分是开源项目和公开API的话，我会优化搜索来规避这些。

•改变搜索语言会发生什么?language:Shell 和language:SQL可能会有意外惊喜。•搜索结果是否会出现其他的域名和主机？前几页的搜索结果通常会包含对其他域名的引用。比如搜索jira.uber.com可能会发现另一个域名的存在，uberinternal.com。


我会花大量的时间在这几步。

明确定义和准确的搜索内容起到关键的作用。使用合理的查询关键字会使自动化工具和手工查询事半功倍。

一旦我根据上面描述的方法找到了有用的内容之后，我会使用GitHound工具的--dig-files和--dig-commits参数来查看其整个的项目和历史。

echo "uberinternal.com" | ./git-hound --dig-files --dig-commits  echo "uber.com" | ./git-hound --dig-files --language-file languages.txt --dig-commits  echo "uber.box.net" | ./git-hound --dig-files --dig-commits

GitHound 也会找到一些简单搜索方法无法发现的文件，比如.zip或.xlsx文件。但是，自动化工具也会遗漏一些用户信息、敏感代码和用户名/密码组合，所以我也会手工的检查下结果。通常，这也会获取更多的子域名和其他有用的匹配模式，启发我使用更多的搜索方式。记住一点开源情报信息是一个递归的过程。

这个过程总会有收获。泄露的信息通常是下面的几类。按照影响严重性排序。

1: SaaS API keys 公司很少对API添加白名单域名限制，AWS、Slack、Google和其他的API keys是重要敏感信息，它们通常在config files, bash history files和scripts被发现。

2:服务/数据库凭证 这些通常在防火墙后面，在公司内网里面。因此影响较小。它们通常在config files, bash history files和scripts被发现。

3: 客户/员工信息 这些信息通常在XLSX、CSV和XML文件里，信息内容可能是账单信息和员工绩效考核。

4:数据脚本 - SQL查询、R 脚本和Jupyter项目可能泄露敏感信息。这些项目可能含有"测试数据"的文件。

5:主机名/元数据 - 这是搜索常见的结果。很多公司不认为这是一个漏洞，但是可以完善一下便于将来的搜索。

特定API的工作流程

可以指定特定的API提供程序和端点来构造搜索关键字。这种对公司创建自动化检测用户的API key特别有用。了解一下一个API key的上下文和语法，可以有效降低搜索范围。

了解了特定API后，我们可以设置匹配API key的正则表达式在API上下文中匹配。然后在其内部数据库或API端点去检测其有效性。

假设一家公司(HalCorp)为用户提供了一个API来读写起账户。通过创建我自己的HalCorp账户，我发现这个API keys的格式是[a-f]{4}-[a-f]{4}-[a-f]{4}。

Python  import halapi  api = halapi.API()  api.authenticate_by_key('REDACTED')    REST API with curl  curl -X POST -H "HALCorp-Key: REDACTED" https://api.halcorp.biz/userinfo

利用这些信息，我们可以为HalCorp API响应编写Github dorks。

Python  "authenticate_by_key" "halapi" language:python    REST API  "HALCorp-Key"


使用类似GitHound[14]这样的工具,我们可以使用正则表达式去匹配Api key来获取字符串并将其输出到一个文本里。

echo "HALCorp-Key" | git-hound --dig-files --dig-commits --many-results --regex-file halcorp-api-keys.txt --results-only > api_tokens.txt

现在我们有了一个文件包含潜在API tokens。我们可以针对数据库来检测其有效性。(如果你没有经过许可，不建议这么做)

通过对HalCorp的案例，我们可以写一个shell脚本来读取输入，检测api.halcorp.biz/userinfo接口并输出结果。

cat api_tokens.txt | bash checktoken.bash

建议

尽管人们对Github泄露敏性信息的意识有所提高，但每天还是有大量的敏感信息被公布在Github上。

Amazon Web Services 可以通知其用户他们的API key是否被公布在网上[15]。Github增加了一个安全特性[16]来扫描公开的项目中的通用密钥。这些方法只是起到表面的作用。为了解决源码中泄露密钥，我们必须更新API框架和开发方式，来防止API keys被存储在Git/SVN项目中。像这样的Vault[17]软件可以安全的存储生产的密钥。比如像Google Cloud Platform这样的API提供者，已经更新他们的库强制将API keys存储在默认的文件中。

完全的避免敏感信息泄露是一件困难的事情。如何去全方位的检测用户信息？如果是一个word文档、Excel、或者更加复杂的文件？这个领域需要深入研究以及其解决方案。
