由于最近的Solidity更新，许多ERC20 Token合约中存在一个严重错误。


ERC基础知识

ERC20标准是迄今为止以太坊平台上最常用的Token标准。

ERC20被定义为一个接口，用于指定哪些功能和事件必须在智能合约中实现为符合ERC20。

ERC20合约的转移功能应该返回什么？

在ERC20的开发过程中，对于ERC20合约的传递函数的正确返回值进行了长时间的讨论。这次讨论基本上有两个阵营。

  1. 一方认为，如果转移功能在调用合约中不允许错误处理，转移函数应该返回false。

  2. 另一方声称，如果未能确保安全，ERC20应该恢复交易。这个问题从未真正解决，现在这两种行为都被认为是符合ERC20的。最常见的行为是在发生故障时恢复，特别是在OpenZeppelin通过这种方式实现了ERC20 Token后。

所有这些与我想描述的实际错误没有多大关系，或许能提供一些东西帮助你理解。

The Bug

事实证明，ERC20 Token的很大一部分以另一种方式表现在传输函数的返回值上。

这些Token 合约（我们称之为BadTokens）的传递函数不返回任何东西。

他们遵守的界面如下所示：

(https://gist.githubusercontent.com/lukas-berlin/4f0be8c6fc48b23429e44155eb3e4627/raw/5b88fdba730a10ef625b8d101cb8d29f996cf2e8/BadERC20)

此接口不符合ERC20标准，这意味着实现此接口的合约不是ERC20 Token。

拥有Token标准的一个重要特点是使其他智能合约能够通过通用接口与许多不同的Token合约进行交互。

有许多不同的合约使用ERC20 Token的这一特性。分散的交易所可以发送代币，众包合约可以接受ERC20代币作为付款等等。

现在有趣的问题是，如果期望ERC20接口的合约试图与不符合ERC20的BadToken进行交互，会发生什么？

我们来看看这个场景：

(https://gist.githubusercontent.com/lukas-berlin/04f4b88c14cd1e05a7a9158ed6b1c9a2/raw/80a2e0b1e05194afcc62b08584b1623b25796693/BadTok)

在Solidity中，函数选择器从其函数名称和输入参数的类型派生而来。

selector = bytes4（sha3（“transfer（）”））

函数的返回值不是函数选择器的一部分。因此，在函数转移（）没有返回值和 功能转移（）返回（布尔）具有相同的功能选择，但他们仍然是不同的。如果你会尝试

contract BadToken is Token {                      
   function transfer() {}         
}   

由于缺少返回值，编译器不会接受transfer（）函数作为Token接口的实现。所以GoodToken是Token接口的实现，BadToken不是。

如果我们仍然调用会发生什么？

调用合约向BadToken发送一个外部调用，它处理调用，进行传输并且不返回布尔返回值。

调用合约现在查找内存中的返回值，但由于Token没有写入返回值，因此它会将此内存位置中找到的任何内容作为外部调用的返回值。

这已经非常糟糕了：将恰好在内存空间中的数据作为返回值并不是一个好主意。

纯属巧合，这个问题在过去并没有出现，因为调用者预期返回值的内存空间与内存空间重叠，调用的函数选择器被存储在内。

EVM将其解释为返回值“真”。所以，纯粹的运气，EVM的行为就像程序员所期望的那样。

但对于较新的智能合约，情况并非如此。

什么改变了？

自去年10月份拜占庭硬叉以来，EVM有一个新的操作码，称为RETURNDATASIZE。该操作码存储（如名称所示）外部呼叫返回数据的大小。这是一个非常有用的操作码，因为它允许在函数调用中返回动态大小的数组。

此操作码在Solidity 0.4.22更新中采用（当设置为默认情况下的后拜占庭模式时）。

现在，代码会在外部调用后检查返回值的大小，并在返回数据比预期短时恢复事务。这比从某个内存空间读取数据更安全。但是这种新行为对我们的BadTokens来说是一个巨大的问题。

谁受到影响？

为了了解这个问题有多广泛，我列出了在Etherdelta上列出的ERC20 Token

并检查了他们在Etherscan上验证的API。

因此，我发现了130个受影响的Token合约：

(https://gist.githubusercontent.com/lukas-berlin/f587086f139df93d22987049f3d8ebd2/raw/1f937dc8eb1d6018da59881cbc633e01c0286fb0/Tokens%20missing%20return%20values%20in%20transfer)

Binance Coin $ 1.587.146.847 
OmiseGO $ 1.127.641.627

但是这个列表中也有很多中小型Token。

有什么风险？

如上所述，最大的风险是，智能合约编译为solc≥0.4.22，期望ERC20接口，将无法与我们的BadTokens进行交互。

这可能意味着即使合约具有转移ERC20 Token的功能，发送给此合约的Token也将永久卡在那里。处理ERC20 Token的合约会遇到很多不同的情况。

一个例子是，您将无法使用与您的BadToken一起编译solc≥0.4.22的分散式交易所。

这怎么会发生？

这个问题显然是Token合约中的一个错误。Solidity的变化只会将这个bug带到daylight。为什么有这么多BadTokens的原因之一是OpenZeppelin在他们的框架中实现了错误的接口。2017年3月17日至2017年7月13日期间，界面出错：

https://github.com/OpenZeppelin/openzeppelin-solidity/blob/52120a8c428de5e34f157b7eaed16d38f3029e66/contracts/token/ERC20Basic.sol

因此，大多数BadTokens使用了ERC20接口的OpenZeppelin错误实现。

那么现在怎么办？

有两种方法可以解决这个错误，我认为这些方法需要并行处理。

一方面，受影响的Token合约团队需要修复他们的合约。这可以通过重新部署Token合约或通过更新合约来完成，如果Token合约有一些更新已编入合约的合约的能力。

另一种可能性是将Token合约封装在一个调用不良传递函数并返回一个良好传递函数的契约中。这种封装有不同的建议。

例如

(https://gist.githubusercontent.com/axic/85f12e78885a5336f2806357b1ba6ea1/raw/6ef3eaadaf7bb0ece55f35fd5e432caa91f5e7d3/ERC20SafeTransfer.sol)

 另一方面，编写处理ERC20 的合约的开发人员需要注意这个错误，以便他们能够预测BadTokens的意外行为并处理它们。

这可以通过预期BadERC20接口并在调用之后检查返回数据来确定我们是否调用GoodToken或BadToken。

结论

我认为目前没有理由恐慌，因为分散交易所和其他大合约的更新周期相当长。尽管如此，这个bug还是需要尽快解决。
