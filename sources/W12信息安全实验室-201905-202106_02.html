SafeSEH 安全的异常处理程序

同样需要编译器和系统双向开启后才能发挥最大的安全性。当然，此功能主要用于x86目标中，x64已经对异常处理程序进行类似操作。

微软自WindowsXP SP2中引入此功能，但是因为当时的程序在编译时大部分都没有支持 SafeSEH ，所以导致了 SafeSEH 直到 Vista 才开始真正的发挥效益。

主题逻辑并不复杂，主要是在调用 SEH 回调之前对回调地址进行检查。检查逻辑大概为：

  1. 地址在加载模块的内存范围内

    1. 并未标志 NO_SEH 标志

    2. 存在 SafeSEH 表

      1. 异常处理函数地址在表中 ✔

        ✨ 此时可以通过删除/修改 SafeSEH 表来进行绕过，以进入是否有 DEP 的另一个判断，但是这就可能需要另一个漏洞帮助

    3. 不存在 SafeSEH 表，且未标记 ILOnly 标志 (IL:.net 中间语言 Intermediat Language )

      1. 未开启 DEP ✔

  2. 地址不在加载模块的内存范围内

    1. 位于不可执行页面上

      1. 未开启 DEP ✔

        ✨ 可以通过将 Shellcode 布置到堆中利用此条进行绕过，前提是未开启 DEP

    2. 可执行页面上

      1. 允许加载模块内存外的地址执行✔

SMEP

Upervisor Mode Execution Prevention

是一种基于硬件的CPU缓解机制，专门针对内核漏洞攻击而实现的。

由于内核中存在 NonPagedPoolNx 的规则，在提权的过程中已经无法通过内核中的数据执行实现了。

但是出现了一些绕过方式，例如在用户态申请空间并写入Shellcode 然后将地址传入内核中，之后使用内核的上下文运行Shellcode。

于此，出现了SMEP，简单来说就是内核态不允许执行用户态代码。以 CPL 和 PTE 来判断。

PTE 在上一篇有提到过，而 CPL 则是当前特权级别，通过存放在 CS 和 SS 寄存器中的段选择子的高2位实现。

Safe Unlink 

直接放段代码：

// 原int remove(ListNode *node){    node->blink->flink = node->flink;    node->flink->blink = node->blink;    return 0;}
// SafeUnlink:int safe_remove(ListNode *node){    if((node->blink->flink == node) && (node->flink->blink == node)){        node->blink->flink = node->flink;        node->flink->blink = node->blink;        return 1;    }    else{        // pointer is corrupted and flow goes to exception        return 0;    }}

其会在Unlink前通过节点回溯的方式检查节点是否正常。

PTR Page Table Randomization

页表地址随机化，在保护模式下，页表是实现读写执行权限的根本，如果页表位置固定，那么将会有利于恶意代码更改权限。

所以为了实现对页表的保护，微软在w10 1607后实现了PTE base随机化

ACG Arbitrary Code Guard

在申请虚拟内存时检查申请的是否是同时拥有 W 和 X 的内存，如果是的话则返回

 STATUS_DYNAMIC_CODE_BLOCKED 

主要尝试实现动态阻止以下行为：

  1. 现有代码被修改

  2. 执行数据段代码

PIE 

Position Independent Executables

位置无关可执行程序。需要在编译时开启，与ASLR不同，PIE影响的是.bss .text .data段的地址，并且实际上并没有做随机处理。

真正的操作是将绝对地址改为了相对变址寻址，放两段汇编代码，看其中的call部分即可发现区别

FORTIFY FORTIFY_SOURCE(Linux)

Linux下可以通过 man 查看帮助文档：

man 7 feature_test_macros | grep -A 20 "_FORTIFY_SOURCE (since glibc 2.3.4)"

原文如下：

FORTIFY_SOURCE (since glibc 2.3.4)               Defining this macro causes some lightweight checks to be performed to               detect some buffer overflow errors when employing various string  and               memory  manipulation  functions  (for  example, memcpy(3), memset(3),               stpcpy(3), strcpy(3), strncpy(3), strcat(3), strncat(3),  sprintf(3),               snprintf(3),  vsprintf(3),  vsnprintf(3), gets(3), and wide character               variants thereof).   For  some  functions,  argument  consistency  is               checked;  for example, a check is made that open(2) has been supplied               with a mode argument when the specified flags include  O_CREAT.   Not               all problems are detected, just some common cases.
               If  _FORTIFY_SOURCE  is  set to 1, with compiler optimization level 1               (gcc -O1) and above, checks that shouldn't  change  the  behavior  of               conforming  programs  are  performed.  With _FORTIFY_SOURCE set to 2,               some more checking is added, but some conforming programs might fail.
               Some of the checks can be performed at compile time (via macros logic               implemented  in header files), and result in compiler warnings; other               checks take place at run time, and result in a run-time error if  the               check fails.

需要在编译时使用

-D_FORTIFY_SOURCE=1/2 来使用此机制：

    =1 ：仅在编译时进行检查，是否有可能导致溢出的代码

    =2 ：在运行时进行检查，是否可能导致溢出

检查的函数包括：

memcpy(3), memset(3), stpcpy(3), strcpy(3), strncpy(3), strcat(3), strncat(3),  sprintf(3),snprintf(3), vsprintf(3), vsnprintf(3), gets(3), 以及相应的宽字符函数

在 =2 的情况下主要原理为：

;在编译时将call   8048320 <strcpy@plt>   ;更改为 call   8048370 <__strcpy_chk@plt>  ;并提前在栈中压入缓冲区大小
