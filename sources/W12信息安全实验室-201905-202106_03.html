DEP Data execution protection

Windows 下最为早期的漏洞缓解机制之一， DEP 防止在内存的非可执行部分中执行任意代码，它迫使研究人员采取其他的利用方法。

DEP 在内核模式和用户模式下的实现非常相似，因为 DEP 是通过页表条目在分页内存的基础上强制执行的。PTE(Page Table Entry) 的高位部分几个负责为指定范围的虚拟地址强制执行各种权限和属性。虚拟内存的每个块称为页(通常为4Kb)，通过 (byte* PTE)[1] 标记整个页块的读写执行权限。而 DEP 则保证了不能同时存在写和执行。

 👆 CR3 寄存器/一级页表 PDE /二级页表 PTE

在Linux中的实现也与Windows相同，使用页表实现对数据不可执行的限制

ASLR/kASLR

Address space layout randomization

Win.


Windows 在Windows Server 2008，Windows 7，Windows Vista，Windows Server 2008 R2，Windows 10 1809，默认情况下启用ASLR,但它仅适用于动态链接库和可执行文件。

需要系统及程序双向开启，在程序通过

NT→Optional→DLL_CHARACTERISTICS→IMAGE_DLLCHARACTERISTICS_FORCE_INTEGRITY

来进行关闭或者开启

    同时，在WinXp Sp2之后，TEB和PEB也都进行了随机化

Linux.


Linux在Kernal 2.6.12 引入

Linux ASLR分为三级

0

没有随机化

1

保留的随机化，栈、mmap()分配的空间、共享库以及VDSO将被随机化

2

完全的随机化，除了上面已经随机的，对brk()分配的内存空间也进行随机

可以简单的使用

cat /proc/sys/kernel/randomize_va_space

来查看等级

使用

echo 2 > /proc/sys/kernal/randomize_va_space

来完全开启随机化

    可以使用 ldd 来查看程序运行地址情况

ASLR 的出现给 ROP 的攻击造成了很大的麻烦，大幅提高了 ROP 的利用难度。

CFG/kCFG Control Flow Guard

控制流执行保护，微软在Windows 10和Windows 8.1 Update 3中默认启用

具体实现是通过在间接调用前插入一段代码以检查调用地址是否为合法地址。所以CFG的实现需要联合 系统、编译器、用户层库以及内核模块共同实现。

Security Cookie(W) / Stack Protector(L)


Security Cookie(GS For VS)

经常逆VS编译的应该能很频繁的看到一个函数名为 __security_cookie 包括在开头和结尾。GS的开启就会对函数的入口和出口代码都添加针对安全cookie检查的指令。

push    ebpmov     ebp,espsub     esp,0x10mov     eax,[__security_cookie]mov     [ebp-0x4],eax;...用户逻辑代码add     esp,0xCxor     eax,eaxmov     ecx,[ebp-0x4]call    __security_check_cookie;...收栈

主要原理是在进入函数的时候多压入栈一个安全cookie，然后在出栈的时候进行检查，如果返回地址被溢出覆盖，则安全cookie也应该被溢出覆盖导致不同。


Stack Protector(For Linux)

又称之为 Stack Canary（栈金丝雀）因为在很久以前的煤矿井内没有一氧化碳检测器，于是矿工会带着对一氧化碳比较敏感的金丝雀一同下矿，用作报警。

与GS的实现基本相同，在栈内而外压入Cookie(Canary)，如果返回地址被覆盖则会检测到，以触发栈保护。
