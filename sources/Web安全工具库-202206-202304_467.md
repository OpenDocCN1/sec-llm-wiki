# 姿势1:CSRF Token Tracker

CSRF Token Tracker是个插件,可以在BApp Store下载安装

![](../Images/f3073b071668e11935b15634f217d646.png)

这种方式可以说是最简单的,但是不适用姿势2和姿势3中的案例  
现有一个请求参数是user\_token  

![](../Images/8f883dace4f6f7cb81b1979274a96e3d.png)

只需要在插件中添加  

![](../Images/ce22fdc934391f62de703b96fe794443.png)

注意这里有个坑(搞了好久)  
比如你想在repeater模块测试一下重新发送请求会不会修改密码  

![](../Images/62b1e336f40f1a59dc8a31e9fca9aee9.png)

发现返回的结果仍然是302  
这里是需要有一个有效的,没有使用过的user\_token去请求的!  
然后再去重放请求包就都会自动更新token了  
总结一句就是你第一次用有效的token重放请求包就永远有效(自动更新token了)  
你第一次用无效的token重放请求包就永远无效

# 姿势3:宏+Extractor

在这个案例中前两种姿势均无效  
下载安装插件

![](../Images/9b050e101cc5c7bf7ba511fd50e27351.png)

先看下两个请求包  
第一个请求包就是获取token的

![](../Images/c6a596f29ae895d22086e8b615f99321.png)

第二个就是带着token去访问

![](../Images/235b54404db2f221b98c9b71c25d3a8b.png)

看过这两个请求包应该就明白了  
这次token是在请求头中  
而定义宏的时候会让你选择更新token的地方  
这个地方却没有更新请求头的功能  
所以姿势2在这里就失效了  

![](../Images/b9137b6e9b0ddd4274f6f630a47b40af.png)

首先定义宏获取token  
这个宏只需要要确保在请求2之前会执行请求1  
相比于姿势2的步骤简单一点

![](../Images/4a379e2d66126b803cd3f7a69202f49c.png)

![](../Images/a43ae05c4cc787698cd24398bb392fef.png)

![](../Images/e8b8a396f4076f23ca439bd278dd4c89.png)

到这里宏就配置好了  
在repeater重放请求2然后再logger+=里面查看  
确保每次都会在请求2前自动执行请求1就是正常的

![](../Images/70dba5a2b38f197329ac60d7a09ff1d2.png)

然后配置插件Extractor  
把两个请求包都发送到Extractor

![](../Images/72d08b929566b688f0de9333a4272a53.png)

![](../Images/66135b60365abc4a20d46cf8db583d5b.png)

![](../Images/b7690a87a1986d5da0788dfb21dcd170.png)

此时回到repeater模块重放发现token就有效了

![](../Images/8735b29fa1a0434dc076416833d7e0fe.png)

再次回到logger++看发生了什么  
看到第87个请求获取的token值为407667d008b147199d174681a655aea0

![](../Images/4e99d9685e1e0b2b87bf5000c3a7f975.png)

第88个请求包的accessToken值也是407667d008b147199d174681a655aea0

![](../Images/8086239bdd77019fdf62ccefce977159.png)

总结一下姿势3的思路  
宏负责在请求2前发送请求1  
Extractor插件负责匹配和替换token
