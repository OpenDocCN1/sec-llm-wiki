2、SSRF理解
SSRF(Server-Side Request Forgery:服务器端请求伪造) 是一种由攻击者构造请求，最终由服务端发起请求的一个安全漏洞。大白话来说，SSRF漏洞只是一个起到类似中间请求转发的框架，需要结合其他各种脆弱点才能发挥出期待的效果。
通常情况下，我们利用SSRF漏洞攻击的目标是从外网无法（直接）访问的内部系统。正因为攻击请求是由服务端发起的，能够请求到与它相连而与外网隔离的内部系统，我们顺势利用服务端在内网或对自我的信任性，达到内网探测、内网系统漏洞利用的目的。

3、SSRF成因

SSRF 形成的原因大多是由于服务端提供了从其他服务器获取数据的功能且没有对目标地址做过滤与限制或过滤不严格。比如从指定URL地址获取网页文本内容，加载指定地址的图片，下载等等。

  • 肉眼可见的现象特征

URL中出现的诸如如下一系列加载远程或本地文件/请求等特征的地方

url=img=im=target=pic=domain=src=source=link=share=u=file=......

  • 业务功能特征

URL分享网页内容、转码服务、在线翻译、图片加载与下载、收藏功能、未公开的api以及其他调用URL的功能。

  • 代码层面特征

各大语言在使用上面提到的这些功能时，都有可能会产生SSRF漏洞，比如：

5.2、SSRF漏洞判断

  1. 排除法
    对于url=http://x.x.x.x/xxx.jpg这类形式的URL，可以通过burp重放或者burp拦截记录，确认后面指向的url是否在自己本地请求了，如果是在本地请求了，那么不存在漏洞。

  2. dnslog请求判断
    通过url=http://xxx.dnslog.cn/ 请求dnslog，查看是否有请求记录，来判断是否有此漏洞。若没有收到请求记录，也不能完全断定为没有漏洞，也有可能服务器不出网。然后再用各种协议进行尝试，通过业务功能特点判断可能会使用什么函数。

  3. 各种协议开始往上怼测试，尤其是常用的协议http、dict、file、php伪协议、gopher、telnet、ssh2、smb等。

tips：
比如http协议尝试请求本地127.0.0.1的网站服务，常见的80、8080以及看到的互联网业务系统目前正使用的端口，根据页面的回显判断是否服务器端发出了本次请求（仅适用于有回显的情况）。
5.3、SSRF内网探测
常用来测探内网的协议为dict，若有页面回显及端口存活与否的特征区分，可批量对内网进行端口探测。其他能探测端口的协议还有telnet、ssh2、ftp、http等，不过都有局限性，只能探测特定协议的端口，或者端口存活，但是没有回显的情况下，会漏报（dict也有这个问题），比如3389没有回显。
tips：
虽然有的端口没有回显，但是存活的端口和不存活的端口，对于请求响应的时间是不一样的，存活的端口会立马响应，不存活的端口会有那么1-2秒的等待时间（实际环境中还需根据实际情况进行判断）。

5.3.1 dict协议
dict使用比较简单，格式为dict://ip:port/的形式，比如dict://127.0.0.1:80/，如下图，代表端口存活。将请求包放在burp中，改变ip和port，对请求内容排序，可对内网进行ip、port存活探测。

5.3.2 file协议
在使用其他协议判断无果，或者已经判断确有SSRF漏洞后，可以尝试使用file协议读取服务器本地文件，格式为file:///etc/passwd或file:///c:/windows/win.ini ，注意这里file后面是必须要跟三个/，然后再跟目录（后边直接跟目录名即可，不管是否是跟目录，比如Linux系统）。

tips:
有的网站对于权限限制比较严，可能会出现只能读取（本）网站目录下文件，而无法读取网站目录外其他任何目录下文件的情况。

●命令2：
网上流传的方法，先将常规的反弹shell的命令在自己搭建的环境中请求一次，使用socat命令进行端口转发，捕捉请求时实际产生的命令结果，然后将结果进行处理，转换为gopher协议格式，再进行请求

exp形成过程：1Linux系统要使用socat命令，端口转发并捕获到程序时实际的请求包，可以使用Linux命令直接安装。格式为：socat -v tcp-listen:3333,fork tcp-connect:127.0.0.1:6379，前面的3333端口是转发端口，可以自定义，后面6379是实际请求的端口；2到redis的cli执行程序目录下，一般就是在redist的src目录下，执行./redis-cli -h 192.168.2.128 -p 3333 进入到redis命令执行界面；3再将常规的反弹shell命令一步步执行完4进入到redis命令执行界面后，仅将执行的反弹shell命令的转发结果复制出来，转换为gopher协议的格式，并进行二次URL编码；转换规则(可以直接用下面的转换脚本)：1如果第一个字符是>或者< 那么丢弃该行字符串，表示请求和返回的时间。2如果前3个字符是+OK 那么丢弃该行字符串，表示返回的字符串。3将\r字符串替换成%0d%0a4空白行替换为%0a5本地环境请求那次的结果中，$num指的是紧挨着的两个\r之间的字符个数，所以这个poc其实可以通用，只不过若要改其中的某些内容，则相对应的这个后面的数字也要改，例如：



附命令2中提到的结果转换脚本：注：脚本来源于网络收集（懒），可到参考链接中查看

#coding: utf-8#author: JoyChouimport sys
exp = ''
with open(sys.argv[1]) as f:    for line in f.readlines():        if line[0] in '><+':            continue        # 判断倒数第2、3字符串是否为\r        elif line[-3:-1] == r'\r':            # 如果该行只有\r，将\r替换成%0a%0d%0a            if len(line) == 3:                exp = exp + '%0a%0d%0a'            else:                line = line.replace(r'\r', '%0d%0a')                # 去掉最后的换行符                line = line.replace('\n', '')                exp = exp + line        # 判断是否是空行，空行替换为%0a        elif line == '\x0a':            exp = exp + '%0a'        else:            line = line.replace('\n', '')            exp = exp + lineprint(exp)
命令2中的坑点：

网上不少说直接把反弹shell的命令写成bash脚本，然后对端口转发进行抓包，将脚本执行的结果直接进行转换就能用。实际玩的时候发现，用bash脚本执行虽然也能写入到cron计划任务中，但是因为\n在脚本执行的时候，没有被正确解析为换行，导致反弹shell命令那一行有垃圾字符，最终计划任务执行时无法成功反弹shell。

这里是先进入到redis自己的命令执行程序中，然后再直接执行redis命令，也只要进入到redis程序后执行的命令即可。其实对比这两种情形的结果，差别就是在\n这里有没有被正确解析为换行符。
