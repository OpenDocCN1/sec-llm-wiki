1、客户端程序安全性检测

1.1.数字签名检测

进入jdk目录下执行命令：

jarsigner.exe -verify -verbose -certs APK路径

输出结果为“jar 已验证”时，表示签名正常；还需检测签名的CN及其他字段是否正确标识客户端程序的来源和发布者身份。

1.2.反编译检测

将apk重命名为zip，解压缩得到 classes.dex 文件（有时可能不止一个dex文件，但文件名大多类似）

当有多个dex文件时使用dex2.1 执行进行反编译，命令：

d2j-dex2jar.bat apk文件名

可以转化所有dex文件到一个jar包中

使用 jd-gui 打开生成的 jar 文件  ，查看代码是否经过混淆：发现代码未经混淆，是不安全的。

1.3.应用完整性校验

使用apktool反编译，命令

java -jar apktool_2.5.0.jar d -f apk apk名称 -o 文件名

当apk中存在加密后的dex文件时会报错，需要加–only-main-classes参数

之后修改一个资源文件，推荐找到logo之类的图进行（容易确认）。（解析AndroidManifest.xml文件的application节点，获取android:icon属性，得到图标资源文件名，一般位于/drawable-hdpi目录下。）

然后在重新打包成未签名的apk文件：

 java -jar apktool.jar b -f 待打包的文件夹 -o apk路径

用 SignApk，对未签名的 APK 文件进行签名：

 java -jar signapk.jar certificate.pem key.pk8 待签名apk 签名后输出

将签了名的 APK 安装、运行、确认是否存在自校验，此处app正常启动，无自校验。

1.4.debug调试

客户端软件 AndroidManifest.xml 中的 android:debuggable="true"标记如果开启，可被 Java 调试工具例如 jdb 进行调试，获取和篡改用户敏感信息，甚至分析并且修改代码实现的业务逻辑；设置为false，表示不存在该漏洞。 


1.5.应用程序是否可备份

打开反编译后的 AndroidManifest.xml 文件；检查应用 AndoridManifest.xml 文件中的配置是否为：android:allowBackup="false"，表示不存在该漏洞


1.6.应用权限检测

打开反编译后的 AndroidManifest.xml 文件，将应用权限和业务功能需要权限做对比，检查申请应用权限是否大于业务需要权限，是否存在安全隐患。


1.7.so库函数接口检测

从安装包中提取So文件后，使用IDA对So文件进行反编译，发现源码逻辑未混淆。


2、组件安全测试

环境搭建

下载wifi adb到模拟器安装，win10使用adb连接

adb端口转发

adb forward tcp:31415 tcp:31415

 (31415为dozer占用的端口号)

使用adb安装代理 apk 到模拟器 。 

下载dorzer安装到电脑和模拟器（drozer使用python2.x编写不支持python3.x）。

添加python库。

pip install protobuf pyOpenSSL Twisted service_identity

切换到drozer安装目录下，执行

drozer console connect


小插曲：配置drozer连接时报错，Missing parentheses....查找资料说是由于环境变量为python3，需要手动改变临时环境变量，手动改变之后依然报错。卸载重新安装python2，选择add python.exe to path,执行成功（重装大法好！）。

开始检测，首先获取要检测的包名：

run app.package.list -f app名称

查看可expored的组件

run app.package.attacksurface app包名

2.1.Activity组件安全检测

run app.activity.info -a app包名

第三方支付相关组件必须是可导出的。）

使用drozer中的activity调用模块尝试启动上述activity：

run app.activity.start --component app包名 调用的activity

发现app成功启动

2.2.Broadcast Receiver组件安全检测

run app.broadcast.info -a app包名


存在可导出的Receiver组件，可以导致Receiver被劫持、绕过、本地认证，造成拒绝服务，导致程序崩溃等。

2.3.ContentProvider组件安全检测

run scanner.provider.finduris -a app包名

存在可访问的content,导致应用数据的泄露。

2.4.Service组件安全检测

run app.service.info -a app包名


存在可以导出的service。可能被恶意应用提供获取重要信息，没有声明任何权限的应用即可在没有任何提示的情况下启动该服务，完成该服务所作操作，对系统安全性产生极大影响。

3、敏感信息安全测试

3.1.检查私有目录文件权限

对 android 的每一个应用，android 系统会分配一个私有目录，用于存储应用的私有数据。此私有目录通常位于“／data／data／应用名称／”。

查看相关文件的权限配置。正常的文件权限最后三位应为空（类似“rw-rw----” ），即除应用自己以外任何人无法读写；目录则允许多一个执行位（类似“rwxrwx—x” ）。


3.2. 检查客户端程序存储在手机中的 SharedPreferences 配置文件  

在检查完权限之后，通常是对本目录下的文件内容（一般是 xml）进行检查，看是否包含敏感信息。 

3.3.sqlite数据库文件安全检验

手机进行root之后， 在私有目录及其子目录下查找以.db 结尾的数据库文 件。对于使用了 webView 缓存的应用，会在 databases 子目录中保存 webview.db 和 webviewCache.db，如图所示。其中有可能会记录 cookies 和提交表单等信息。使用数据库查看工具即可查看这些文件中是否有敏感信息。

3.4.检查apk包中是否保存有敏感信息

有些时候，客户端程序 apk 包中也是是保存有敏感信息的，比如检查 apk 包中各 类文件是否包含硬编码的的敏感信息等（反编译 so 库和 5.逆向 classes.dex，检查 apk 包中各类文件是否包含硬编码的的敏感信息。对可执行文件可通过逆向方法寻找，也可以直 接使用 16 进制编辑器查找。）。

3.5.logcat日志

安装应用后对app进行使用，使用adb导出日志，查看是否包含敏感信息：

adb shell logcat -d >d:/a.txt

4、密码软键盘安全性测试（适用于支付类APP）

4.1.键盘劫持

测试客户端程序在密码等输入框是否使用自定义软键盘。安卓应用中的输入框默认使用系统软键盘，手机安装木马后，木马可以通过替换系统软键盘，记录手机银行的密码通常来说，只有使用系统输入法的编辑框才能够进行键盘码记录。如果是自制的软键盘，则可以尝试进行触摸屏记录。不使用系统输入法，且按键随机分布的软键盘是安全的.

安装安卓按键记录工具，选择使用并查看是否有记录。

4.2.随即布局软键盘

当客户端软键盘未进行随机化处理时为低风险；当客户端软键盘只在某一个页面载入时 初始化一次而不是在点击输入框时重新进行随机化也为低风险 。

4.3.屏幕录像

客户端使用的随机布局软键盘是否会对用户点击产生视觉响应。当随机布局软键盘对用户点击产生视觉响应时，安卓木马可以通过连续截屏的方式，对用户击键进行记录，从而获得用户输入；攻击者可以在用户进入登录页面，在输入密码的同时，进行连续截图，即可记录用户 输入的密码。如果没有防截屏，那么即使是随机分布的、没有视觉反馈的软键盘也会被记录  。 

使用adb执行：

adb shell /system/bin/screencap -p 路径（安卓设备中）

查看是否有截图。

5、进程保护测试

5.1.内存访问和修改

需要 root 权限，可以使用 MemSpector 查看、搜索和修改客户端内存数据是否存在敏感信息。（不知道为啥，没检测到运行。）


5.2.反调试检测

可通过 ptrace 挂载等方式控制客户端代码执行流程，对金融类 APP 用户的个人财产造成威胁.

需要开启调试，但 apk中的 AndroidManifest.xml 中debuggable基本为false，直接修改打包会出错，

借助工具mprop修改手机应用为可调试状态，首先查看一下手机debugabble的值，0为不可调试。

adb shell su -c "getprop ro.debuggable"

使用adb将mprop（我这里用的v7版本）上传到/data/local/tmp目录：

 adb push mprop /data/local/tmp

添加执行权限：

adb shell su -c "chmod 755 /data/local/tmp/mprop"

修改debugabble值为1

adb shell su -c "setprop ro.debuggable 1"


然后查看模拟器/手机的cpu型号

adb shell getprop ro.product.cpu.abi


利用ida自带的32位android_server进行调试，上传android_server，修改android_server权限并启动服务

接下来就可以进行反调试检测，使用jadx-gui逆向apk包，获得包名和入口函数名


利用adb shell am start -D -n 包名/入口函数，来通过调试模式打开APP

设置PC端需要转发23946端口

使用ida进行远程调试,选中Debuggerz中的Attach里的Remote ARMLinux/Android debugge


设置好Debug options,并且设置hostname


点击ok后找到对应的包名



成功进入ida调试进程，证明APP缺少反调试检测，攻击者还可以利用调试技术，在运行时的App内存中注入恶意代码，达到截获运行时数据的目的，此举可能导致用户的隐私信息被窃取。

6、通信安全测试

6.1.证书有效性

使用GDA查看证书信息，查询开发者证书是否规范。

6.2.关键数据加密和校验

测试客户端程序提交数据给服务端时，密码、收款人信息等关键字段是否进行了加密， 防止恶意用户嗅探到用户数据包中的密码等敏感信息。 

6.3.访问控制

测试客户端访问的 URL 是否仅能由手机客户端访问。是否可以绕过登录限制直接访问 登录后才能访问的页面，对需要二次验证的页面（如私密问题验证），能否绕过验证。 

6.4.客户端更新安全性

使用代理抓取检测更新的数据包，尝试将服务器返回的更新 url 替换为恶意链接。看 客户端是否会直接打开此链接并下载应用。在应用下载完毕后，测试能否替换下载的 apk 文件，测试客户端是否会安装替换后的应用。

返回数据包经过加密，无风险。 

6.5.短信重放攻击

检测应用中是否存在数据包重放攻击的安全问题。是否会对客户端用户造成短信轰炸的困扰。尝试重放短信验证码数据包是否可以进行短信轰炸攻击
