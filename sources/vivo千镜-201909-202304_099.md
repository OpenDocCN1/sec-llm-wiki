**Javascript 逆向分析技巧**  

在进行 Android 移动应用安全评估时，我们经常会遇到前端相关内容，例如 H5 网页、快应用、WebView 等，而这些项目对应需要重点关注的内容就是 Javascript。由于 Javascript 最终是运行在用户的浏览器上，所有的代码都是透明的，只需通过简单的抓包或浏览器开发者工具就能获取到对应代码，所以一般开发者在发布前端应用前都会对 js 代码进行加固、混淆等操作，加大逆向分析的难度。

  
**如何获取 Javascript 代码**  
![](../Images/59d645f5585bab359ec9684ace8c26a8.png)**浏览器开发者工具**  
  
**【电脑端网页】**

对于一个获取一个网站 js 代码，最简单的方法就是通过浏览器的开发者工具（F12）去查看，这里以 Chrome 为例。

![](../Images/60235dbcfe742ec4bb70eb360ff69006.png)

访问网站，打开 F12，选中 Sources 页签，左边导航栏 Page 显示的就是当前页面的静态内容，其中包含该网页的 css、js、图片、字体等内容，我们可以直接在开发者工具中进行查看，一般打包后的代码都会经过压缩混淆，点击 Pretty-print 按钮可将代码格式化。

  
**【Android 端网页（WebView）】**

对于 WebView，首先可以观察该 WebView 是否开启可调试选项

（setWebContentsDebuggingEnabled(true)），如果开启，则代表该页面可被调试，这时在地址栏中输入 chrome://inspect 可以查看到该页面，点击 inspect 即可像正常网页一样进行调试

![](../Images/0d3389ae522ce68b6f23bbc535f7c157.png)

如果没开启调试，可以将对应地址复制到电脑端浏览器打开，这时候需要注意，移动端网站的服务器可能会检测访问者的 User Agent，直接访问可能会遇到 403 Forbidden 的情况，这时可以在开发者工具 Network conditions 页签中设置自定义 UA。

  ![](../Images/a684701565856beb637374079739eba4.png)

  

PS：上述介绍的方法仅限于在开发者工具中查看，如果想下载内容，可以安装 Save All Resources 扩展程序，该插件可以下载 Sources 页签下的所有内容。

  ![](../Images/58b38438115f47b6c8f8226c06268579.png)

![](../Images/59d645f5585bab359ec9684ace8c26a8.png)**抓包**  
  

  

抓包也是获取移动端网站代码的一种比较常见的方法，因为打开网站前，必须要先将网站加载出来，这时候只要劫持流量，就可以拿到对应代码了，本文就不再赘述抓包方法了，想了解的同学可以关注之前发布的文章。下图是用 mitmproxy 抓取网站 js 的截图。

  

![](../Images/60e3ab31cdb42cf9f32a6a817a8f9ec9.png) 

  
**如何分析 Javascript 代码**  
![](../Images/59d645f5585bab359ec9684ace8c26a8.png)**肉眼调试**  

在安全评估中，获取到一段 js 代码后，首先需要分析的就是代码的特征，先看看这段代码在发布前进行过哪些操作（混淆、加密等等）。

  

**0****1****源码**  
  
  

首先，如果拿到的代码里面有很多熟悉的单词，这段代码很大几率就是源码（可能是开发在 webpack 打包时没有关闭 source map 选项），可以直接用开发者工具或者 IDE 调试；

![](../Images/0c03d836641f1697592f4fabaed77e59.png)

  
  

  

**0****2****压缩混淆代码**  
  
  

如果拿到的代码里面大部分是 a, b, c，而且只有一行，这种是比较正常的情况，因为开发者为了节省网络加载 js 时间，会把 js 进行压缩，这个操作一般不会改变代码原有的逻辑，只是将变量进行了重命名。遇到这种情况只需要将代码格式化一下，分析时将关键变量自己进行重命名，或者利用反混淆工具跑一遍，分析起来也不会太困难，下图是使用 jsnice 工具反混淆的一段代码（反混淆并不能还原代码，只是让代码分析起来更简单）。

  

![](../Images/a30849c46e9037d2e12e49286831b8e9.png)

  

  
  

  

  

**0****3****十六进制变量**  
  
  

如果拿到的代码即没有熟悉的字眼，也没有 abcd，而是像下图这种的：

  

![](../Images/c20cb04e480e20f6cf26c2f2e13031a0.png) 

  

这种代码一般进行了混淆、加密、反调试、平坦化、防格式化等一系列操作，分析难度较大。

  
  

**这种代码的特征：**  

1、变量以下划线加一个十六进制命名

2、第二行像是一个加密 / 编码后的数组

3、有很多以字符串为 key，函数为 value 的对象属性

![](../Images/59d645f5585bab359ec9684ace8c26a8.png)**实际分析**  

  

对于上述的第三种情况，肉眼调试已经解决不了问题了，尝试用开发者工具真实调试一下。Chrome 中打开一个新的页签，将代码复制到开发者工具的 Snippets 中运行。  

  

![](../Images/188e751f95ca129df6d14421a0bd835c.png)

  

直接运行发现，系统的 CPU 占用率非常高，一段时间后控制台打印出报错，看来是没运行成功。这时猜测该代码做了防格式化操作，试试把代码还原成原来的一行再执行。

  

![](../Images/3778e55ea58e91cfbe49c29d967beb0e.png) 

可以看到，一旦运行就会一直弹出断点，无法调试，所以进一步思路就是尝试尽可能地还原代码，再静态分析其逻辑。上面提到，这段代码有一个密文数组，可以从这里入手。因为 js 最终都是运行在浏览器上，即使加密了，运行前也是需要解密的，通过观察发现，这个数组只有一个函数使用到了，而对应函数多处被调用，可以猜测这个函数就是解密函数。如下图，黄色部分为数组，0x50e3 引用了数组，且被多处调用。

  

![](../Images/35073881bf377e563f673d945ae04fdb.png)

  

下面先来看看 0x50e3 做了什么：

  

![](../Images/a287cd53c7b0baa89fe019fff92719cd.png)

  

  
  
**通过分析**

0x50e3 首先将第一个入参加上 0x 变成十六进制字符串，再转换成对应数字，然后作为索引从密文数组取值，最终返回解密的结果。

所以我们的思路就是，将所有调用到 0x50e3 的地方全部跑一遍，就可以获取到解密后的结果了。

下面尝试用 python 模拟环境尝试对数组进行解密，并将调用 0x50e3 函数的地方替换成解密后内容。这里使用到 PyExecJS 库，该库可以执行一段 js 代码并获取返回结果。需要注意的是这里我们只需要 0x50e3 以及之前的代码，0x50e3 没有调用到后面的代码，可以先注释掉，防止影响运行效果。

  

![](../Images/e61ea61e18f7dfd1859f53d3113f9d29.png) 

这段代码的原理是利用正则寻找调用了 \_0x50e3 的地方，将参数提取出来，然后利用 execjs 调用 \_0x50e3 并将执行结果替换加密过的代码。

控制台输出内容如下：

  

![](../Images/b529f514e5b7882d6576248473d14844.png) 

  

可以看到，数组内容其实是一些变量名和函数名，替换回去后再进行静态分析就容易多了。

  

**解密后的代码有以下几个特征：**  
**1、 原代码的内容被抽离，存在对象里面，以5为字母字符串为 key，加大分析难度**

![](../Images/22fd3aafe18e1b9abc1ced873d53415c.png)

PS：对于这种情况，可以使用脚本读入对象，然后逐个解析替换回去，此处就略过了。

![](../Images/a3afb1f78112514bc7ffefbdcd93f00c.png)

![](../Images/082273557a85e71e6b7893cef562fb72.png)

![](../Images/fccb181d689929ad27c0e900e700eee4.png)

![](../Images/a3f248b7e391bfd87ef86359c6bfa3b1.png)  
继续分析  

下面来看看为什么格式化后代码会报错。

  

![](../Images/debb8f6b8d763bb85b60b726ae0c876d.png) 

通过简单的浏览可以发现，代码的开头有一段函数定义，这段代码实际定义了一段正则表达式，去匹配 removeCookie，我们先看看正则写了什么，将 16 进制转换成字符后实际上是以下内容（\\x20 是空格，为了方便理解这里不作转换）：

  

\\w+\\x20\*\\(\\)\\x20\*{\\w+\\x20\*\['|"\].+\['|"\];?\\x20\*} 

  

我们再看看 removeCookie 的内容：  

  

![](../Images/a151a4bb06592256b3d9e51869c6c5de.png) 

  

需要注意的是，代码中匹配的内容为 removeCookie 的 toString，这里并不是 removeCookie 执行的结果 'dev'，在 js 中函数的 toString 方法返回的是函数体内容，所以结果是 function () {\\n return 'dev'\\n}，可以看到是匹配不上的。

  

![](../Images/0f4fe350aedc9afae037fa1121007f7e.png)

   

  

但这个是我们格式化后的代码，如果回到格式化前呢（把 \\n 去掉）？

  

![](../Images/7aee0086df384d2310409581c3efa007.png) 

  

这回匹配上了，所以正则匹配的结果取决于代码是否被格式化过，我们继续看下面的代码：

  

![](../Images/0c02a1f819efc6fdeaad8bcf47210f9a.png) 

  

如果匹配上了，则执行 else if 的 getCookie，反之执行 setCookie，而 setCookie 就是导致资源消耗的罪魁祸首，最终使程序报错（参考上文报错信息）。

PS：这里的 else 是无效分支，属于控制流平坦化操作，是用来增加肉眼调试难度的。

所以我们可以将格式化后的 "removeCookie" 还原回去，来绕过正则检测，或者直接点把整段代码删掉。

  

这时候再运行代码，就会发现回到代码是一行时候的情况，一直弹出断点，说明代码格式化的检测被成功绕过了！

  

那断点是怎么回事呢？

![](../Images/7d29d1aa86293542bdbc211d1daf1b8d.png)继续往下分析![](../Images/e16e0648b174ac4b3a8987f071581265.png)

  

![](../Images/f42e9147417e355c6148540a3eb28db2.png) 

这段代码，用脚本将对应的值都替换一下，等价于以下代码：

  

![](../Images/eb1a6963f0ab52b82b19d64b1e72eb55.png) 

这段代码中，可以看到一番嵌套分支后，其实最终简化后相当于执行：

  

(function (param1) {  
    return Function('Function(arguments\[0\]+"' + param1 + '")()')  
})('bugger')('de')

  

而这段代码，首先会将 'bugger' 传入 param1，构造字符串 Function(arguments\[0\]+"bugger")()，再传入 Function 的构造方法创建方法，最后返回值为方法

  

function () {  
    Function(arguments\[0\] + "bugger")()  
}

  

而第二步即将字符串 "de" 传入上述方法，得到 Function("debugger")()，即立即执行 debugger，这就有了上文一直弹出断点的场景。

  

![](../Images/9f16fb971fa08cdb16ae97cd8dafe330.png) 

至此，只需要删除这段代码，反调试也就不存在了，剩下的步骤，可以采用开发者工具调试或者人工静态分析，即可得出该 js 的逻辑。

**方法重定义**

– 替换常用方法，例如 console.log

  
  
  
**死循环 debugger**

– 只要打开调试工具则触发断点

  
  
  
**判断代码是否被格式化**

– 只要打开调试工具则触发断点

  
  
  
**Chrome 开发者工具检测**

– chrome 开发者工具打开后，通过 console.log 打印 div 时会尝试获取 div 的 id，可通过重写 id 的 getter 方法进行检测
