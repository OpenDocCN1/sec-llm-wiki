# 【科普向】Android本地SQL注入的dos攻击方式

**说在前面**

Android平台使用SQLite存储数据，所以SQL注入问题非常常见，在没有其他漏洞辅助的情况下利用比较困难，无法形成有效攻击，并且漏洞利用只能篡改或窃取本地数据库中的数据。如今的开发人员安全意识较高，敏感数据存储非常谨慎，能够通过SQL注入进行的利用少之又少，本文主要讲述如何通过资源消耗的SQL注入攻击导致手机死机，以及在尝试的过程中遇到的问题。

**尝试过程**![](../Images/a562c51be3990c3ae93f3957ef7c9747.png)

初次接触本地SQL注入问题，思考良久，把服务端的SQL注入利用方式套用到本地SQL注入的场景，发现都不适合或者太过于鸡肋。

  

但是下面的这段代码可以触发内存消耗的现象：

LENGTH**(**randomblob**(**100000\*xxxxx此处省略xxxxx**\***00000000**))**

对漏洞利用了解的同学应该比较熟悉此利用代码，可以通过解析此SQL语句消耗内存，达成资源消耗型dos攻击。

  

批量发现SQL注入点，使用此payload进行测试，共发现3类不同现象：

1、返回错误提示：out of memory (code 7 SQLITE\_NOMEM)2、消耗内存导致应用重启3、消耗内存导致手机死机那么下面就分析一下，出现不同现象的原因！

  

**OOM**

为什么会出现OOM（out of memory）报错？

难道SQLite支持内存上限配置？

  

将错误码输入到google进行搜索为什么会出现这类报错，结果如下：

![](../Images/ef72d2441f2aeb76412a437fdcea3e0d.png)

官方错误码描述，SQLITE\_NOMEM结果代码表示SQLite无法分配完成操作所需的内存，对sqlite3\_malloc()或sqlite3\_realloc()的内部调用失败。但是通过这段描述还是无法确认是什么原因导致内存申请失败。然后去查看logcat是否存在错误日志，其中一条提示：

**failed to allocate 100000000 bytes of memory**

![](../Images/5781435317eb79b76c953cefeb42fec9.png)

根据提示调整100000000这个数值，当缩小至100000时，报错消失并可以查看到返回结果。通过不同输入对比输出，发现输出长度和输入有关。

输入：

run app.provider.query content://com.xxx.xxxx.provider/usualcity --projection "1"

![](../Images/60dd8107466f4b1dd421c82e1e068927.png)

  

输入：

run app.provider.query content://com.xxx.xxxx.provider/usualcity --projection "LENGTH(randomblob(100000))"

![](../Images/dbe917c677e18b6a2abca7310b2b0860.png)

不断扩大输入的值，输出返回结果就是增加，导致输出缓冲区数据长度过大超过缓冲区最大值，以致于内存申请报错。

此类问题为误报，不符合我们的预期结果，只是因为输入值导致输出值超出了缓冲区的限制。

  

**消耗内存导致应用重启**

可以直观的看到android.process.media应用程序的内存占用量增长迅速，并在达成5.5G后应用进程重启。

![](../Images/d88e12c29919974ea0ca3c9b9efc96d1.png)

对于终端用户的体验影响非常小，仅仅会导致桌面应用程序重新加载。

![](../Images/700463a1aaf91c0d36f87c1d656cebc9.png)

那么是什么原因导致应用程序重启，但却没有占用全部内存导致手机死机呢？

![](../Images/d96c49c6d94e855fdb2d8f69e89bd0bd.png)

通过logcat分析日志发现框架中存在一个进程会监控应用程序，还发现当应用程序的内存使用值超过阈值时，此进程会将应用程序杀掉，日志如下图所示。这个杀掉应用程序、pid为1509的进程叫做system\_server，system\_server是Android框架的基础进程，很多服务都集成在这个进程中。通过日志可以看出应用进程首先监控程序，然后杀掉程序，最后自动重启。

  

总结分析，此类攻击场景同样不能达成我们预期目标。  

![](../Images/f75948a6bf1615d86c6b0c17d391f2e9.png)

  

**消耗内存导致手机死机**

通过不断地测试，最终发现通过内存消耗导致手机死机的攻击现象，唯有强制重启才能使手机恢复正常运行。此类攻击现象的攻击方式和第二类（消耗内存导致应用重启）没有区别，唯一的区别是被攻击应用程序的运行权限，可以看到第二类现象的用户为u0\_a28，id为10028的普通用户，可以导致手机死机的应用程序的用户为system，id为1000。

![](../Images/7ede4206adfb5e2ff1429645afcbd864.png)

攻击现象如下图所示：

![](../Images/9a1e6a8c785f5d2443676f2c5dffb6c8.png)

出现死机现象的原因是监控程序没有针对system权限的应用程序进行监控，占用大量的内存导致手机无法正常运行。

  

**总结**![](../Images/a562c51be3990c3ae93f3957ef7c9747.png)

Android框架对应用使用的内存存在限制，/system/build.prop配置文件中配置了dalvik.vm.heapsize参数，测试手机中的参数配置为512M，但是除了java内存堆之外还存在native内存堆，Android框架对native内存的使用没有限制，并且SQLite运行在native层（请查看下图中的Java Heap和Native Hep的数值对比，Java堆的内存使用很低），申请使用的内存为native堆的内存，所以可以忽略java层的内存限制达成dos攻击。
