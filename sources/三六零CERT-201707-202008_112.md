## 1.2 利用t3协议进行恶意序列化

在编写利用的过程中，需要发送两部分的数据

*   请求包头，也就是
    
    ```
    t3 
    ```
    
    以`\n`结束
    
*   序列化数据部分，序列化部分的构成方式有两种：
    

*   第一种生成方式为，将前文所述的weblogic发送的JAVA序列化数据的第二到九部分的JAVA序列化数据的任意一个替换为恶意的序列化数据。
    
*   第二种生成方式为，将前文所述的weblogic发送的JAVA序列化数据的第一部分与恶意的序列化数据进行拼接
    

必须先发送`T3`协议头数据包，再发送`JAVA`序列化数据包，才能使`weblogic`进行`JAVA`反序列化，进而触发漏洞。如果只发送`JAVA`序列化数据包，不先发送`T3`协议头数据包，无法触发漏洞

# 0x03 防御机制

## 3.1 JEP290机制

JEP290机制是用来过滤传入的序列化数据，以提高安全性，其核心机制是序列化客户端需要实现`ObjectInputStream`上的`ObjectInputFilter`接口（低于`jdk9`的版本是在`sun.misc`这个`package`下，而`jdk9`是在 `java.io` 这个`package`下），利用`checkInput`方法来对序列化数据进行检测，如果有任何不合格的检测，`Filter`将返回`Status.REJECTED`

jdk9向下增加jep290机制的jdk版本为

```
Java™ SE Development Kit 8, 
```

这里使用测试版本`jdk8u221` 图上的流程已经很明显了，我们来看看如果被`jdk`拦截是什么样子的，这里我随便用了`CommonsCollections`的`gadget`做测试，使用的测试版本`jdk8u221`

### 3.1.1 filterCheck

最终的拦截调用是 `readOrdinaryObject->readClassDesc->readNonProxyDesc->filterCheck`

![](../Images/c6f7cf65139c1555572a6fb2abb33f89.png) 这里的`ObjectInputFilter`类型变量`serialFilter`，`serialFilter`的值是作为 `JEP290`对序列化数据进行检测的一个格式(里面包含需要做检测的默认值，用分号隔开。包名后面需要带星号，包名或者类名前面带感叹号的话表示黑名单，没有则表示白名单)

具体细则 ![](../Images/1640e37b172a8c061fc93220414fe843.png)

这里的`serialFilter`值如下


### 3.1.2 serialFilter赋值过程

![](../Images/f686687a86323f979929ca64c518ad59.png)

![](../Images/ab4e4e04f359523c924940b2f7293955.png) 为初始化前，`FilterProperties`和`BlacklistProperties`都为`null`，都返回`false`， 于是跟进`processDefaultConfiguration`方法

![](../Images/fbb2b0376ff605e9a1e8321a589510a0.png)

接着调用`getDefaultFilterScope`判断当前jdk，我们测试版本是`8u221`，返回`GLOBAL` ![](../Images/f67553778ccecbf5d903513ae315fb47.png) 接着是`constructSerialFilter`，开始对`serialFilter`进行赋值，主要是对`serialFilter`的格式进行统一 黑名单主要来自`DEFAULT_BLACKLIST_CLASSES`和`DEFAULT_BLACKLIST_PACKAGES`， ![](../Images/ca478cc67fc3882aab73f552b71f7873.png) `serialFilter`的赋值结束后，会通过反射调用`ObjectInputFilter.setSerialFilter`，对`ObjectInputFilter`接口的`serialFilter`赋值 ![](../Images/ff9f608760e558aeda8f10b5d327d6dd.png) 再之后，就是上文的`ObjectInputFilter.checkInput`的调用了 具体的检测过程如下 ![](../Images/9e180da75b7a40ac59e747f4e2549dbe.png) 这就是在jep290的机制下的weblogic配合jdk `ObjectInputFilter` 的一个检测过程，就是一个基于类/包的黑名单检测，还是存在绕过的可能性，比如最近的 `CVE-2020-2555` 的 `gadgets`，可以参考 CVE-2020-2555 漏洞分析

### 3.2.2 resolveClass

在普通的java反序列化的过程中会调用`resolveClass`读取反序列化的类名，所以我们可以通过重写`ObjectInputStream`对象的`resolveClass`方法即可实现对反序列化的校验，来看`weblogic`是如何实现的

根据错误日志，定位到`weblogic.rjvm.InboundMsgAbbrev$ServerChannelInputStream`。

我们看到反序列化的点 ![](../Images/ee8f95e452c8ba8f08d14be4431dbe91.png) 这里将类型转换为`ServerChannelInputStream`，该类继承了`ObjectInputStream` ![](../Images/92646654f677bad7a3e8374663fc10e7.png)

并且重写了`resolveClass` ![](../Images/2e9b66dbfe6c584a8b13c5479c9c4e89.png) 在反序列化的时候，就会优先调用重写的`resolveClass` ![](../Images/f1d942694bf0370c3b4ec488e963144a.png)

接着跟进`checkLegacyBlacklistIfNeeded` ![](../Images/aa3c3a4e896725ae773c34bcff9ba6b9.png) 这里首先会判断`isJreFilteringAvailable`属性(jep290机制下该值为`true`，所以不会用这种方法进行检测)，然后会调用`isBlacklistedLegacy`判断反序列化类是否在黑名单里 ![](../Images/02af385344955016bf37008091d02a6d.png)
