# 【最新漏洞预警】CVE-2022-26133 Atlassian Bitbucket Data Center反序列化漏洞

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=Mzg3MTU0MjkwNw==&mid=2247489213&idx=1&sn=aad8e7ab5235736107ec3ae89c543440&chksm=cefdafa9f98a26bfa7ec4d02f4384feb52a555ba308a82bcf76cbd001a1bb0f944c6b3ee126b&scene=126&sessionid=1681277847#rd](http://mp.weixin.qq.com/s?__biz=Mzg3MTU0MjkwNw==&mid=2247489213&idx=1&sn=aad8e7ab5235736107ec3ae89c543440&chksm=cefdafa9f98a26bfa7ec4d02f4384feb52a555ba308a82bcf76cbd001a1bb0f944c6b3ee126b&scene=126&sessionid=1681277847#rd)

**漏洞信息**

  

Bitbucket Data Center是Atlassian的Git存储库管理解决方案，它为需要高可用性和大规模性能的企业提供源代码协作。

  

近日爆出Atlassian BitBucket Data Center存在CVE-2022-26133未授权反序列化漏洞，问题所在的服务位于5701 Hazelcast接口，经过测试发现在开启集群授权License后漏洞可用。

  

![](../Images/6eec68e81b4b7bd764b34bc4cebb4dae.png)

  

影响版本为：

  

*   All 5.x versions >= 5.14.x
    
*   All 6.x versions
    
*   All 7.x versions < 7.6.14
    
*   All versions 7.7.x through 7.16.x
    
*   7.17.x < 7.17.6
    
*   7.18.x < 7.18.4
    
*   7.19.x < 7.19.4
    
*   7.20.0
    

  

**环境搭建  
**

  

搭建7.18.2 windows版本测试环境，安装的时候选择\`Data Center instance\`：

  

![](../Images/1fc7fc982cc9c03e2a387b29c5ec6c01.png)

  

在\`\_start-webapp.bat\`中添加xdebug选项进行远程调试：

  

![](../Images/2ef624fcf2b529a29493d98d54ff3f46.png)

  

**cluster授权问题  
**

  

\`Bitbucket Data Center\`使用\`Hazelcast\`进行内存数据缓存，它是一个分布式内存数据存储和计算平台，作为内存数据存储，\`Hazelcast\`通过将数据存储在内存中，让您可以更快地访问数据。

  

\`Hazelcast\`默认情况下开启端口 5701 ，Bitbucket通过\`EnterpriseNodeExtension\`启动\`HazelCast\`实例，通过\`getSocketInterceptorConfig\`获取Socket配置：

  

![](../Images/bc2479eea16443867936f2d43b19b4c2.png)

  

在\`NetworkConfig\`中可以看到默认的端口为\`5701\`：

  

![](../Images/2b521af95878326afddb03ee6e6f97ae.png)

  

使用telnet或nc默认访问\`5701\`端口，提示\`Clustering is not enabled\`，之后TCP连接被强制断开：

  

![](../Images/0d2c14938d9ccea4770bf93aeb4f2236.png)

  

调试代码可知使用\`isClusteringEnabled\`检查是否具有\`Cluster\`授权：

  

![](../Images/2e59a28049165c2029d7bcc820dc9ad2.png)

  

注意看\`clusterEnabled\`字段，这里的license并没有授权：

  

![](../Images/ca001dc3cbc06399eab264e0adb0f492.png)

  

  

使用Idea的Evaluate功能将修改为\`clusteringEnabled=True\`：

  

![](../Images/558f4dda2f8a26b29bc7c691398aa16b.png)

  

之后便能正常访问该接口了：

  

![](../Images/da25ca679858018f80844bdc27b94998.png)

  

**触发点分析  
**

  

问题代码并不太复杂，\`BitBucket Hazelcast\`接收到TCP连接后，首先执行\`ClusterJoinSocketInterceptor.onAccept\`函数：

  

![](../Images/9d6c921471479bc4ad6371c88ecced59.png)

  

然后动态调用\`DefaultClusterJoinManager.accept\`函数：

  

![](../Images/e2662d7ae114625a13cdd6be0963b6ac.png)

  

在\`checkAcceptingClusterConnections\`函数中检查系统状态和\`Cluster\`模式是否可用（在上一节中调试过）：

  

![](../Images/db966de425bb9cc45a48aff65bbdebfa.png)

  

接下来继续执行\`this.clusterAuthenticator.authenticate(request)\`：

  

![](../Images/1b647ffa8f64ab047f07567bc0a9ed9f.png)

  

执行\`com.atlassian.stash.internal.cluster.SharedSecretClusterAuthenticator.runMutualChallengeResponse\`函数，\`SharedSecretClusterAuthenticator\`为BitBucket自行实现的一个身份认证代码：

  

![](../Images/d392dbc6be00de65e4eba214c78018da.png)

  

\`receiveObject\`处存在反序列化调用：

  

![](../Images/ae3ba1afd49cf51a86a77345d4b3c046.png)

  

执行\`receiveObject\`前需通过\`verifyGroupName\`检查：

  

![](../Images/04e2a51f79c8e124ed3e2dd0ccd407e1.png)

  

比较幸运的是判断\`groupName\`前服务端会通过\`out.writeUTF\`会返回自身\`groupName\`，这样我们就可以探测服务器的名称了。之后如果报文中读取不到\`RemoteGroup\`的话TCP会一直保持连接：

  

![](../Images/96dea6bee1fd0c74214ff1bddc7aebee.png)

  

**漏洞利用  
**

  

首先是获取目标服务器的\`groupName\`，使用wireshark捕获返回\`groupName\`报文，分析可知格式为\`4字节长度+字符串\`格式：

  

![](../Images/20d7ed9ef438949e334907dcd2e6e69d.png)

  

发送\`\\x00\\x00\\x00\\x01\\x31\`字节数据，服务器成功读取到\`remoteGroup\`并断开了TCP连接：

  

![](../Images/3c58ce358fddbec37ec9b3910c4bb3bb.png)

  

对于反序列化利用报文，虽然请求失败，依然可以从返回的数据中推测反序列化头以\`\\xff\\xff\\xff\\x9c\`开头：

  

![](../Images/4d628cef2b6ff8196e2a49c9d8144b67.png)

  

得到反序列化请求格式如下：

  

*   

```

```

![](../Images/e43121665a69d36cfefdf15c1487319d.png)
