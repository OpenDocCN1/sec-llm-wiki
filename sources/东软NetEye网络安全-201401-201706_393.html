魔高一尺还是道高一丈？

从软件溢出漏洞首次证明可以被利用以来，相关的攻击及防御技术不断发展。为对抗最初的覆盖函数返回地址的攻击，GS保护技术被提出。通过在函数返回地址前加入cookie来检测函数返回地址被覆盖。随后，绕过GS的办法被提出，包括利用SEH结构、利用虚函数表、修改cookie值等。为了防止攻击者执行堆或栈中的代码，DEP（数据执行保护）技术应运而生，使得堆或栈等数据区域不具有可执行属性。为绕过DEP保护，ROP攻击技术又现江湖，通过重用进程空间中的可执行代码来完成攻击。ROP攻击时，需要确切知道某一指令在内存中的位置。为对抗ROP攻击，ASLR（地址空间格局的随机化）技术诞生，它随机化各个代码段在内存中的加载基址，使得ROP攻击无法在固定地址找到需要的指令。而通过调用暂不支持ASLR的DLL文件或通过内存泄露的方式，依然可以在固定地址找到需要的指令。


在这些防护技术的保护下，大多数的漏洞无法被利用。即便少部分漏洞可以被利用也变得愈发困难，利用方法也越来越与漏洞形式本身相关。随着时间的推移，还会有更多的攻击及保护技术相应产生。永哥觉得吧，在攻防的世界里，就是魔高一尺道高一丈，魔再高一尺，道再高一丈的无限循环。下面永哥将针对几种常见的攻击及绕过方法逐一介绍。


栈溢出的产生

通常，某一函数内部所定义的数组等局部变量，其所占用的空间会从栈上分配。这时在栈空间中，该数组buffer所在内存地址，会与存有该函数返回地址的空间相近，且数组buffer的位置会更靠近低址。如果在函数返回前，向该buffer写入过多的数据，会导致该函数的返回地址被覆盖。那么函数返回时，程序流程就会被劫持。


栈溢出的产生多发生在下面几种情况：

当memcpy()将过多的数据复制到目的buffer空间中；

sprintf()格式化后的字符串长度大于buffer大小；

scanf()函数所输入的数据大于buffer的长度；

另外，各种形式的字符串拷贝函数或指令也可能导致栈溢出的产生。


栈溢出的利用

当DEP未开启时，栈具有可执行权限。通过栈溢出覆盖返回地址，可控制函数返回至“jmp esp”指令处，因为ret指令执行后，esp加4，此时esp所指向的内存刚好为可以控制的内存，可将任意指令放置在此处。随后jmpesp将程序流程转向此处，最终实现任意指令的执行。


如PCMan's FTP Server 2.0 - Remote Buffer OverflowExploit漏洞部分攻击脚本：

EIP ="\xDB\xFC\x1C\x75" #751CFCDB JMP ESP USER32.DLL

NOP ="\x90" * 10

s.send("\x41"* 2010 + EIP + NOP +SHELLCODE +'\r\n')"


可看到，send()发送的数据第2010~2013字节为EIP，目的是控制函数的返回地址。而EIP的值为JMP ESP指令的地址，当函数返回后，eip为0x751CFCDB,esp则指向了NOP所在处。JMP ESP执行后，eip便指向了NOP处，将NOP+SHELLCODE当作代码开始执行。


防御覆盖函数返回地址

为防止覆盖函数返回地址的攻击，编译器提供了/GS编译选项，开启该选项后，编译器会在函数入口和函数结束处，插入一小段代码，用于在栈中插入cookie，插入的cookie会在局部变量和返回地址之间，函数返回时，再比较该值是否被改变。因此，这种方法便能够检测由局部变量溢出导致函数返回地址被覆盖的情况。


对抗GS保护

在Windows程序中程序运行时发生的错误可由SEH结构提供解决办法。通过覆盖SEH结构，则可以在GS检测之前获得EIP。

SEH即结构化异常处理，当程序运行发生错误时，系统会从最近一次添加的SEH结构中找到异常处理函数，调用该异常处理函数。


通常SEH结构位于栈上，与局部变量紧邻。如果局部变量中的buffer发生溢出，便会覆盖掉SEH结构，当程序发生错误时，系统会从被覆盖过的SEH结构中取得错误的异常处理过程地址并调用，产生与栈溢出覆盖掉函数返回地址类似的攻击效果。

如Kolibri WebServer 2.0 - GET Request SEH Exploit漏洞部分攻击脚本。

buffer ="\x90"*(buff-20-32-4)

buffer+= egghunter

buffer+= "\x90"*20

buffer+= "\xEB\xBA\x90\x90"

buffer+= "\xC2\x15\x40" #/p/p/r kolibri.exe


eggshell= "dogedoge"+shellcode


evil= (

"GET/"+buffer+" HTTP/1.1\r\n"

"Host:"+eggshell+"\r\n"

"User-Agent:kepo\r\n"

"Connection:close\r\n\r\n")


溢出后，\xC2\x15\x40覆盖了原有的异常处理函数指针，pop,pop后的ret指令从栈中取得的地址会落在"\x90"*20范围内，将eip转入buffer内，跳转指令执行后，egghunter被执行。


防御Shellcode直接执行

前面介绍的攻击方法在控制EIP后，将指令流程直接转移到了攻击者输入的数据内，而大多数程序正常运行时，数据内不会包含程序指令。因此，数据执行保护（DataExecution Prevention，DEP）被提出，由CPU和操作系统配合，将数据所在的堆、栈等内存部分设为不可执行权限，来防止直接跳转至Shellcode的攻击。


对抗DEP

当DEP开启时，栈空间不具有可执行权限，放置在栈上的代码也就无法被执行。此时利用可以采用ROP的方式。函数返回时，ret指令会从栈中取得函数返回后的地址，而栈溢出后可以控制栈中的内容，也就可以控制每个ret指令返回时所返回的地址。ROP攻击时，返回地址处的指令通常由两部分组成：前一部分是正常的指令，这些指令序列通常完成恶意功能的一小部分。紧接着的便是程序跳转指令，如ret,jmpeax,call eax，这些指令会直接或间接的从栈上取得地址，再将程序转入该地址处。这样，通过后一部分指令的连接便可将众多的前一部分的指令序列串连起来，串连后的指令即可完成完整的恶意功能，即通过不可执行栈中的数据来指引CPU按顺序执行一系列已经于内存中且可执行的程序代码来达到攻击效果。


多数情况下，ROP攻击时，会将程序流程转向VirtualProtect()，等设置内存属性的函数，给内存增加可执行权限。再执行该内存中的Shellcode，以简化攻击。

BOOLVirtualProtect(

LPVOIDlpAddress, // 目标地址起始位置

DWORDdwSize, // 大小

DWORDflNewProtect, // 新的保护方式

PDWORDlpflOldProtect // 保存修改前的保护方式

防御ROP攻击

在ROP攻击中，需要提前知道某些指令在内存中的代码，这样才能在攻击时，在内存中准确找到将要执行的指令。这成为了ROP攻击的一个弱点。操作系统抓住了这一弱点，在程序准备运行时，随机化各模块在当前进程空间中的加载基址。使得攻击者无法确定栈、堆、可执行程序本身以及动态链接库的实际地址。使需要知道指令固定地址的ROP攻击失效。这项技术即地址空间格局的随机化（AddressSpace Layout Randomization，ASLR）。


对抗ASLR

有些DLL在编译时并未支持ASLR，在加载了这些DLL的进程空间中，依然可以准确的在特定位置找到需要的指令来进行ROP攻击。

别外一种方法便由程序内部函数指针等信息，来间接的找到函数所在的地址，从而确定可执行模块所在的地址。当随机化被开启时，若程序提供内存分配的功能，可尝试分配大量内存，这些内存便有很大的概率覆盖攻击者所假定可以控制的内存地址，从而可在固定地址找到特定的数据。


防御漏洞攻击的建议

使用版本较新的操作系统，如windows7. 在上述保护机制的保护下，溢出的利用已越来越困难。


对于未知的漏洞利用形式，可以安装微软提供的EMET。它提供更加全面的保护机制，来阻止绝大多数的溢出攻击。


最后永哥建议大家安装一些安全防护工具或者使用入侵检测系统，也可以有效的防止系统受到基于已知威胁的攻击。
