01

什么是

Webassembly

Webassembly是一种低级的类汇编语言，具有紧凑的二进制格式，可以接近原生的性能运行。

它设计的目的不是为了手写代码，而是为诸如C/C++和Rust等源语言提供一个高效的编译目标，以便它们可以在Web上运行。它也被设计为可以与JavaScript共存——通过使用WebAssembly的JavaScript API，你可以把WebAssembly模块加载到一个JavaScript应用中并且在两者之间共享功能。

简而言之，Webassembly提供了一条途径，使得以各种语言编写的代码都可以以接近原生的速度在Web中运行。

在这种情况下，以前无法以此方式运行的客户端软件都将可以运行在Web中。

02

Webassembly的诞生

虽然JavaScript足够强大从而能够解决人们在当今网络上遇到的绝大部分问题，但是当试图把JavaScript 应用诸如3D游戏、虚拟现实、计算机视觉、图像/视频编辑以及大量的要求原生性能的其他领域的时候，我们不可避免地遇到了性能问题。

一方面是由于这些业务逻辑越来越复杂、代码量越来越大，还有一个原因是JavaScript这门语言本身的缺陷。

上图为Microsoft Edge浏览器的JavaScript引擎ChakraCore的结构示意图。我们可以看到在JIT(Just-in-time)的帮助下，引擎会对执行次数比较多的function进行优化，但是由于JavaSrcipt的特性——没有静态变量，在优化的过程中，JIT同样增加了很多开销。

比如如上图所示，虽然只是一个很简单的循环，但是由于JavaScript的动态类型，所以每一次循环迭代，JIT都会检查数据类型。同时，如果在某一轮循环中，sum或arr的类型发生变化（比如整数相加和字符串连接就是两种完全不同类型的操作），那么JIT必须放弃之前对这行代码所做的优化。

为了解决这些问题，Webassembly的前身——asm.js诞生了。asm.js是JavaScript的严格子集，同Webassembly一样，asm.js并不是用来给程序员一行一行撸的代码，asm.js是一个编译目标。

虽然asm.js强制使用静态类型，避免了JavaScript引擎一些难以优化的机制和模式（主要是垃圾回收和类型判断），但是asm基于JavaScript的文本格式导致代码尺寸偏大，在互联网上传输成本过高，同时parse 性能不够理想。 

在这样的背景下，在Mozilla、Google、Microsoft、Apple等厂商巨头联手推动下，对asm.js进行二进制化的Webassembly也就应运而生了。


与其说Webassembly是一门编程语言，倒不如说它是一份新的字节码标准。 

Webassembly 字节码是一种抹平了不同 CPU 架构的机器码，Webassembly 字节码不能直接在任何一 种 CPU 架构上运行， 但由于非常接近机器码，可以非常快的被翻译为对应架构的机器码，因此 WebAssembly 运行速度和机器码接近，这听上去非常像 Java 字节码。


相对于 JavaScript，WebAssembly 有如下优点： 

体积小：由于浏览器运行时只加载编译成的字节码，一样的逻辑比用字符串描述的JavaScript文件 体积要小很多。

加载快：由于文件体积小，再加上无需解释执行，WebAssembly 能更快的加载并实例化，减少运 行前的等待时间。

兼容性问题少：WebAssembly 是非常底层的字节码规范，制订好后很少变动，就算以后发生变 化,也只需在从高级语言编译成字节码过程中做兼容。可能出现兼容性问题的地方在于JS和 WebAssembly 桥接的JS接口。


Webassembly 目前可以通过 Emscripten SDK 生成，下图是 WebAssembly 的编译原理：

上图展示了以 C / C++ 代码为例生成 WebAssembly 的过程。

首先通过LLVM ，将C/C++ 源代码编译为LLVM bytecode。

其次，通过EMscripten 中的后端编译器，将LLVM bytecode生成asm.js 格式的文件。由于asm.js 是JavaScript的严格子集，并且比通常的JavaScript代码运行速度更快。这意味着使用C/C++编写的源代码，哪怕用户设备不支持WebAssembly特性，也可以回退到JavaScript 运行并得到一致的结果。

最后，asm.js 会通过另一个编译器生成为WebAssembly 的.wasm 文件。

Webassembly与逆向

随着Webassembly的流行，ctf中也出现了越来越多相关的题目，接下来我们以去年国赛的一道题目简单介绍一下如何静态分析Webassembly。

手撕Webassembly字节码与手撕机器码难度相当，几乎是不可能完成的任务，所以我们需要一些“小小” 的帮助。

WABT(The WebAssembly Binary Toolkit)是由官方开发的一套用于Webassembly相关工作的工具箱，可以为我们的逆向工作提供很大的便利。


04

反汇编

这里的反汇编指的是将.wasm 文件转换为.wat 文件。

Webassmbly标准规范了两种格式，一种是.wasm文件的紧凑二进制格式，这是Webassembly代码的常规输出格式；第二种是.wat文件的文本格式，它与汇编语言相似，设计为方便人类阅读。

也就是说Webassembly要求一个程序段具有两种可相互转化的等价表达式。这两者可以理解为机器码与汇编的关系：传输和运行时使用二进制格式，展现给人的时候用文本格式，这样就同时保留了两者的优点。

我们可以使用WABT工具箱中的wasm2wat将 .wasm 文件转换为.wat 文件。

如果说源代码比较简单的话，我们可以通过阅读.wat文件理清程序的逻辑。

但是显然这道在wat格式下有3万多行文本的程序不属于这个范畴。

优化

这样的代码显然是无法阅读的，我们需要做一些优化。

一种比较简单的优化方式就是：用gcc编译之后再用ida反编译。

将之前反编译得到的where_u_are.c和where_u_are.h，以及WABT工具包内的wasm-rt.h，wasm-rt- impl.c，wasm-rt-impl.h放在同一个文件夹内。

使用gcc只编译不链接这些文件。

将得到的.o 文件丢进ida里，可以看到代码逻辑已经比较清楚了。
