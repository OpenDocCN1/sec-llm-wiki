01

简介

早期的英国矿井工人每次下井时都会带上一只金丝雀来探查井下的气体是否有毒，有毒气体会使得敏感的金丝雀停止鸣叫甚至死亡，从而使工人们得到预警。基于这种思想引出了 stack canary 这种古老而又有效的栈溢出保护机制。

Canary不管是设计还是实现思想都比较简单高效，即在初始化栈帧是在栈底设置一个随机的canary值，栈帧销毁前测试该值是否“死掉”，即是否被改变，若被改变则说明栈溢出发生了，程序进入异常处理，以免漏洞利用成功。


02

实现原理

在GCC中使用canary

在使用GCC编译程序时可以添加以下参数来设置canary：

    -fstack-protector 启用保护，不过只为局部变量中含有数组的函数插入保护
    -fstack-protector-strong 启用保护，不过只对满足一定筛选原则的函数插入保护
    -fstack-protector-explicit 只对有stack_protect attribute关键字的函数开启保护
    -fstack-protector-all 启用保护，为所有函数插入保护
    -fno-stack-protector 禁用保护


具体实现

 

插入canary后的函数栈帧结构如图所示，可以看到在EBP和函数的局部变量之间插入了一个随机数canary（根据经验该随机数的位置距离EBP会有一定的偏移，以实际调试为准）。

那么这个随机数又是从哪里得到的呢？我们看一下具体汇编。     可以看到第四条和第五条指令执行的就是一个将canary入栈的过程，其中fs:28h处存放的就是canary。

fs段寄存器指向一些与进程信息相关的结构（对于不同的程序来讲并不一样，这里不展开讨论），其28h偏移处的值为canary,那么自然就存在一种攻击方式--通过覆盖fs:28h处的值来伪造canary。

接下来我们来看一下函数是如何验证canary的。     可以看到验证的流程也很简单，只是将栈中的canary取出与fs:28h处的值进行比较，如果相等再正常结束，如果不相等的话则意味着发生了栈溢出，执行__stack_chk_fail函数进行异常处理。

__stack_chk_fail函数的内容也很简单，我们来看一下代码。

void __attribute__ ((noreturn)) __stack_chk_fail (void){  __fortify_fail ("stack smashing detected");}__stack_chk_fail函数执行了__fortify_fail函数。void __attribute__ ((noreturn)) internal_function __fortify_fail (const char *msg){  /* The loop is added only to keep gcc happy.  */  while (1)    __libc_message (2, "*** %s ***: %s terminated\n",                    msg, __libc_argv[0] ?: "<unknown>");}

__fortify_fail通过__libc_message函数来输出错误信息，其中__libc_argv[0]这个参数很重要，它指向了运行的程序名称（并且一般也存在于栈上，那么我们就可以通过覆盖掉__libc_argv[0]的值来打印出我们想要的内容，即stack smash技巧）。


03

攻击方式

上面我们简单的介绍了canary的实现机制，接下来就让我们来了解一下有哪些针对canary的攻击方法吧！

泄露canary

泄露canary是最简单也最容易想到的一种攻击方式。

canary的最低字节为\x00, 本意是为了保证canary可以截断字符串（因为常见的输出函数如puts等都以\x00作为终止标志）。但我们可以通过覆盖掉canary的最低字节来使这个截断作用失效，从而打印出高位的canary值。

这种利用方式需要合适的函数流程，即第一次读入造成溢出之后，后面存在输出函数可以将canary的值打印出来，并且往往还需要第二次溢出来控制函数返回地址。 

one-by-one 爆破canary

 对于 canary，不仅每次进程重启后的 canary 不同 ，而且同一个进程中的每个线程的 canary 也不同。但是，如果使用fork函数来开启子进程交互，由于fork函数会直接拷贝父进程，因此每次创建的子进程的canary值是相同的。这也就意味着我们可以无限次重复利用该进程，那么我们自然很容易想到逐个字节将canary爆破出来。

由于canary验证机制的特点：如果检查到canary不匹配则利用__stack_chk_fail输出错误信息，匹配则正常退出，因此我们可以逐步从低字节到高字节覆盖canary进行尝试。     上图为一个常见的使用fork函数生成子进程的模块。


stack smash

我们在之前介绍过如果函数检查到canary值被修改，就会终止程序输出错误信息， 而一般来说我们并不会关心报错信息。而stack smash技巧就是利用打印错误信息来得到我们想要的内容。如果我们利用栈溢出覆盖argv[0]为我们想要输出的字符串的地址，那么我们就可以通过__fortify_fail函数来输出我们想要的信息。

例题可参考 2015 年 32C3 CTF readme 。


劫持_stack_chk_fail 函数

我们同样在前面介绍过canary异常处理逻辑会进入到__stack_chk_fail函数中，而__stack_chk_failed 函数是一个普通的延迟绑定函数，因此可以通过修改 GOT 表劫持这个函数。

参见 ZCTF2017 Login 。


覆盖TLS中存储的canary值

线程局部存储（Thread Local Storage）是一种机制，通过该机制分配变量，以便每一个现存的线程都有一个变量实例。它主要是为了避免多个线程同时访存同一全局变量或者静态变量时所导致的冲突，尤其是多个线程同时需要修改这一变量时。

为了解决这个问题，我们可以通过TLS机制，为每一个使用该全局变量的线程都提供一个变量值的副本，每一个线程均可以独立地改变自己的副本，而不会和其它线程的副本冲突。从线程的角度看，就好像每一个线程都完全拥有该变量。而从全局变量的角度上来看，就好像一个全局变量被克隆成了多份副本，而每一份副本都可以被一个线程独立地改变。

这个机制在不同的架构和操作系统上的实现不同，在glibc实现中，TLS的指针保存于一个segment register fs(即fs段寄存器)中，TLS的结构tcbhead_t定义如下：

typedef struct{  void *tcb;                      dtv_t *dtv;  void *self;         int multiple_threads;  int gscope_flag;  uintptr_t sysinfo;  uintptr_t stack_guard;            //canary  uintptr_t pointer_guard;  ...} tcbhead_t;

我们可以看到该结构体中存在有canary的值，也就是说每次我们实际上都是从该结构体中的固定偏移处（28h)取出canary的值（fs寄存器指向了该结构体）。

但是glibc在TLS的实现上存在问题。在为栈分配内存后，glibc在内存的高地址初始化TLS，而栈向下增长，TLS位于栈的顶部，也就是说现在我们不需要泄露出canary的值，而是直接栈溢出足够多的数据来覆盖TLS中的tcbhead_t.stack_guard即可绕过canary。

参见 StarCTF2018 babystack
