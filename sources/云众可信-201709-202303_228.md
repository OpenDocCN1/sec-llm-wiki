恶意代码分析的核心是分析恶意代码的行为。这些行为可能是启动另一段恶意代码，可能是让恶意代码能够在内存中驻留，也可能是执行一些破坏行为，还可能是其他的行为。无论是哪一种行为，都有很多种实现方式，而迅速识别恶意代码使用何种技术实现了何种行为是每一位恶意代码分析人员的必备技能。

在本系列接下来的文章中，我们将一起分析恶意代码的行为，分析这些行为是如何实现的。今天，就让我们从如何启动一段恶意代码开始。

**2.用户操作启动**

让一个可执行程序运行起来最简单的方式是用户对着文件双击、敲下回车或者右键打开。如果这个文件是恶意文件，那么我们就要想办法诱导用户运行这个文件；如果这个文件是正常的文件，那么我们就要想办法在启动正常文件的时候启动恶意程序。

**2.1.文件伪装**

为了让用户双击运行程序，攻击者会对可执行程序进行一些伪装，诱导用户点击运行程序。对可执行程序进行伪装主要是对图标、文件名进行伪装。

**2.1.1.更改文件图标**

对于lnk文件来说，更改文件图标的方式很简单，右键——属性——快捷方式——更改图标——选择shell32.dll中的图标。windows系统自带的图标主要存放在C:\\Windows\\System32\\shell32.dll中，你也可以从网上下载图标文件更改图标：

![](../Images/cef3178e34eb4078b5d26020bc6d3925.png)

对于exe文件来说，更改图标就要麻烦一点，exe的图标数据是放在资源段中的，更改图标需要借助专业的工具——ResourceHacker。在ResourceHacker中打开exe文件，然后点击AddBinary or Image Resource 按钮选择要添加的图标文件。

![](../Images/a364b817c3ed9fb947e73c9f6e239c57.png)

**2.1.2.更改文件名**

最简单的修改方式是将 "evil.exe"修改为"evil.jpg.exe"，系统默认的配置会隐藏exe的后缀名，用户看到的文件名就是"evil.jpg"而不是"evil.jpg.exe"，这样用户就会以为自己打开的是一张图片，而实际运行的是exe文件。

另一种更改方式是将文件的扩展名由 ".exe" 变成 ".scr"。scr是屏保程序的后缀名，它就是一个exe文件。然而许多用户对".scr"不熟悉，可能上当受骗。

更改文件名最高级的技术要属利用RLO技术欺骗了。RLO（Right-to-Left）控制符是Unicode控制符的一种，可以使得字符显示从右至左的顺序，例如字符“123”，使用RLO控制符后就会显示为“321”。Windows系统在解析文件名时，当遇到unicode控制符时，会改变文件名的显示方式，利用这一特性，可以将exe、scr、com等可执行文件伪装成doc、jpg、txt、ppt等。例如：我有一个名为“testagpj.scr”的exe文件，我利用RLO技术重命名：

**2.2.文件关联**

当我们对着一个文件双击、敲下回车或者右键打开时，这个文件就启动打开了。一个word文档会由office程序打开，一个avi视频则会由视频播放软件打开，不同类型的文件由不同的应用程序打开。我们都知道是操作系统控制应用程序打开文件的，但操作系统又是如何知道应该使用哪个应用程序打开哪种类型的文件的？这里就不得不提文件关联机制了。

**2.2.1.文件关联注册表**

windows文件关联机制是由注册表实现的。当我们打开一个文件时，操作系统首先根据后缀名查找注册表HKEY\_CURRENT\_USER\\Software\\Microsoft\\Windows\\CurrentVersion\\Explorer\\FileExts\\，查看该后缀名对应哪一个应用程序；如果找不到对应的项或应用程序，则会去查找HKEY\_CURRENT\_USER\\Software\\Classes；如果还是找不到，就会查找HKEY\_LOCAL\_MACHINE\\Software\\Classes；如果最后都没找到，就会弹出对话框让用户自主选择打开方式。

![](../Images/65f3ea3c8a6bcb9fdeb402cd579165ec.png)

**2.3.exe启动过程**

刚刚提到了exe文件的打开方式，默认键值为：“%1”%\*。这是什么鬼，这并没有表明谁启动了exe文件啊。实际上，这个键值是传递给Windows程序管理器(Explorer.exe)的，由Explorer.exe启动exe。

当双击某个exe图标时，Explorer.exe进程的一个线程会侦测到这个操作，它根据注册表中的信息取得文件名，然后Explorer.exe 调用 CreateProcess 函数，CreateProcess 内部调用NtCreateProcess创建这个exe的进程。

**2.3.1.CreateProcess创建进程**

  

CreateProcess 创建进程的过程如下图所示：

![](../Images/af6e12280032fc5c1bbb09e530d6f0a6.png)

阶段1：解析、验证和转换参数。CreateProcess会进行参数检查，检查进程创建标志(CreationFlags)、桌面检查（lpStartupInfo->lpDesktop）等参数；并将部分参数从Windows子系统格式转换为NT格式，例如将字符串参数“C:\\\\WINDOWS\\\\XXX”转为Nt格式文件路径“\\\\Device\\\\HarddiskVolume1\\\\WINDOWS\\\\XXX”。若CreationFlags包含DEBUG\_PROCESS | DEBUG\_ONLY\_THIS\_PROCESS标志位，则调用DbgUiConnectToDbg创建调试对象，并调用DbgUiGetThreadDebugObject获取该调试对象。做完各项检查转换后后调用NtCreateUserProcess进入ring0，创建进程的主要工作是在ring0中进行的。

阶段2：打开将要被创建进程的文件映像并创建了一个内存区对象(只是现在还没有将映像文件映射到该内存区)，同时做兼容性检查。调用ZwCreateSection创建文件映像，文件映像已经实现了内存对齐，同时在ZwCreateSection内部调用MiVerifyImageHeader完成对PE格式的校验和解析。在进行兼容性检查时会进行几个判断，比较重要有如下几个判断：

·如果是64位程序运行在32位系统中或损坏无效的exe文件，则退出创建进程的过程；

·如果是正常的windows的exe程序，则会查找注册表HKLM\\SOFTWARE\\Microsoft\\Windows NT\\CurrentVersion\\Image File ExecutionOptions中是否有一个子键与可执行映像的文件名或扩展名相同；如果有，则调用PspAllocateProcess查找该键是否有Debugger的值，该值里存放的是调试器程序；如果存在，则会以调试状态重新调用CreateProcess打开该exe程序，同时设置调试器为Debugger里的值；

·如果是后缀为.exe、.com、.pif的MS-DOS程序，则会创建MS-DOS支持进程Ntvdm.exe；支持进程Ntvdm.exe是在注册表HKEY\_LOCAL\_MACHINE\\SYSTEM\\CurrentControlSet\\Control\\WOW\\cmdline中指定的；

·如果映像是win16(Windows3.1)支持的可执行文件，则会启动虚拟DOS机（VDM）进程运行它。如果CreateProcess中没有指定CREATE\_SEPARATE\_WOW\_VDM和CREATE\_SHARED\_WOW\_VDM标志，则会判断HKLM\\SYSTEM\\CurrentControlSet\\Control\\WOW\\DefaultSeparateVDM的值，DefaultSeparateVDM指定每个Win16应用程序是否在其自己的内存空间中运行自己的ntvdm.exe和wowexec.exe实例；

阶段3：初始化进程的过程，主要调用的是PspAllocateProcess。该过程包括创建进程内核对象，完成映像地址到虚拟内存地址的映射，建立PEB，将Ntdll.dll映射到进程中，调用PspInsertProcess将新进程对象插入Windows活动进程列表的末尾等。

阶段4：创建初始线程，以及它的栈和执行环境、windows执行体线程对象。至此，NtCreateUserProcess完成返回。

阶段5：执行特定于WINDOWS子系统的初始化后处理。这里所有必须的执行体进程和线程对象已经创建完毕，接着就会检查windows是否允许运行这个可执行文件，是否导入了禁止的API，是否需要创建令牌，检查运行权限(UAC)等；同时初始化第一个线程的Windows子系统。

阶段6：如果没有指定CREATE\_SUSPENDED，这里就会调用NtResumeThread唤醒初始线程正在恢复，以便它可以开始运行；

阶段7：完成进程初始化，正式开始执行。在新进程和线程环境中，完成地址空间的初始化，运行映像加载器(LdrInitializeThunk)例程，初始化加载器、堆管理器、NLS表TLS、FLS数组、临界区结构、加载DLL(并用DLL\_PROCESS\_ATTACH功能代码调用DLL的真正入口点)；最后调用RtlUserThreadStart使用实际的映像入口点和启动参数的地址来调用应用程序的入口点。在程序运行过程中如果发生异常，则会调用UnhandledExceptionFilter启动异常处理机制。在异常处理过程中，如果没有额外的异常处理程序，则会查询注册表HKEY\_LOCAL\_MACHINE\\SOFTWARE\\Microsoft\\WindowsNT\\CurrentVersion\\AeDebug，如果存在Debugger键，则会启动Debugger所指向的程序（被称为JIT调试器）附加调试崩溃进程。

![](../Images/915bf4b4000b7813d5176be2ddbc9421.png)

**2.3.3.映像劫持**

系统在创建exe进程的过程中，会检查HKLM\\SOFTWARE\\Microsoft\\Windows NT\\CurrentVersion\\Image File ExecutionOptions中相关进程的Debugger的值，如果存在会启动调试器，攻击者可以修改该Debugger的内容为恶意程序，这种技术就被称为映像劫持。

利用映像劫持技术，可以在正常进程启动的过程中启动恶意程序。

映像劫持的实现就是对注册表的操作，一般可以使用RegSetValue设置注册表，其使用demo：

| char RegName\[\] = "SOFTWARE\\\\Microsoft\\\\Windows NT\\\\CurrentVersion\\\\Image File Execution Options";char szBuf\[MAX\_PATH\];HKEY hKey = NULL;strcpy(szBuf, "%windir%\\\\Hacked.exe");RegOpenKey(HKEY\_CURRENT\_USER, RegName, &hKey);RegSetValueEx(hKey, //subkey handle"Debugger", //value name0, //ReservedREG\_EXPAND\_SZ, //value type(LPBYTE)szBuf, //pointer to value datastrlen(szBuf) + 1); //length of value dataRegCloseKey(hKey); |
| --- |

对注册表的操作，就是要先调用RegOpenKey打开相关项，然后使用一系列“Reg”开头的API进行注册表操作，最后还要调用RegCloseKey关闭注册表。

**2.3.4.Dos支持进程**

系统在创建dos进程的过程中，会使用HKLM\\SYSTEM\\CurrentControlSet\\Control\\WOW\\cmdline中的支持进程Ntvdm.exe，攻击者可以修改该项，用恶意程序替换支持进程。修改注册表的方式和前面的方式类似。

**2.3.5.JIT调试**

exe程序在运行过程中可能产生异常，攻击者可以设置注册表项HKEY\_LOCAL\_MACHINE\\SOFTWARE\\Microsoft\\WindowsNT\\CurrentVersion\\AeDebug，添加JIT调试器，在程序异常时自动运行Debugger程序。

![](../Images/4e655a25a510eacbe58c9f6650368833.png)

该注册表中，Debugger键表示JIT调试器；Auto键表示附加是否需要确认，默认0，表示需要确认；UserDebuggerHotKey是设置一个快捷键用来发送一个DebugBreak()调用。

**2.3.6.dll劫持**

在进程启动过程中，进程会将需要的DLL加载到其内存空间中，但是程序中并没有记录DLL文件的路径，程序是如何找到这些DLL并加载的呢？Windows提供了一个目录搜索顺序，程序将会根据这个搜索顺序查找DLL并加载。

在WinXP之前的系统中，DLL文件的搜索顺序：

1.  应用程序所在目录
    
2.  当前工作目录
    
3.  32位Windows系统目录(GetSystemDirectory获取System32文件夹)
    
4.  16位Windows系统目录(System文件)
    
5.  Windows目录(GetWindowsDirectory获取)
    
6.  PATH环境变量中的目录
    

在这种情况下，如果我有一个恶意的dll文件，将这个dll命名为系统dll的名字（eg：kernel32.dll），并将其放在应用程序所在目录，那么程序在加载dll的过程中就会加载恶意dll而不是系统dll。

为了对抗这类攻击，微软给出了两个解决方案。

第一个解决方案——SafeDllSearchMode，安全DLL搜索模式。从WindowsXPSP2开始，SafeDllSearchMode默认开启。该模式启用后，DLL文件的搜索顺序变为：

1.  应用程序所在目录
    
2.  32位Windows系统目录(GetSystemDirectory获取System32文件夹)
    
3.  16位Windows系统目录(System文件)
    
4.  Windows目录(GetWindowsDirectory获取)
    
5.  当前工作目录
    
6.  PATH环境变量中的目录
    

SageDllSearchMode并不能完全防止dll劫持的存在，因为恶意dll可能被放在应用程序所在目录。而且SageDllSearchMode很容易关闭，只需要设置注册表HKEY\_LOCAL\_MACHINE\\System\\CurrentControlSet\\Control\\SessionManager\\SafeDllSearchMode的值为0就禁用了SafeDllSearchMode。

第二个解决方案——KnownDLLs。KnownDLLs是注册表HKEY\_LOCAL\_MACHINE\\SYSTEM\\CurrentControlSet\\Control\\SessionManager\\KnownDLLs下的一系列常见的系统dll，如kernel32.dll、lpk.dll、shell32.dll。系统在启动时，会读取KnownDLLs里的值，在之后的进程加载这些KnownDLLs里的dll时，会优先搜索系统目录，其次才是应用程序目录。

![](../Images/cf54f65d38a67fa9b7f3e6c663ce116c.png)

但KnownDLLs对dll的保护也不是不能破坏的，创建HKEY\_LOCAL\_MACHINE\\SYSTEM\\CurrentControlSet\\Control\\SessionManager\\ExcludeFromKnownDlls，并指定具体dll名称，重启后就可以使KnownDLLs列表中同名的dll保护失效。

虽然这两种技术并不能杜绝dll劫持，但SageDllSearchMode和KnowDLLS技术结合起来，可以有效防止对系统dll的劫持。

**3.非PE类文件启动恶意代码**

文档类文件、脚本类文件、lnk文件等类型的文件（几乎所有类型的文件）都可以启动恶意代码，要细细说来那就多了，这个说多了反而显得啰嗦，何况在本系列之前的章节直接间接都有介绍，这里就不赘述了。

**4.恶意进程启动恶意代码**

一般来说，恶意代码攻击过程中，最先运行的程序只是Downloader或Dropper，由它们释放真正的恶意程序(payload)并运行恶意程序。关于它们如何投放payload的部分，我们之后的章节再介绍，这里我们分析一下，它们是如何运行payload的。

**4.1.创建进程**

在一个进程中启动另一个新进程，最简单的方式是调用WindowsAPI函数创建新进程。最常用的三个API是WinExec、ShellExecute和CreateProcess。

从功能上看，这三个API不仅能创建进程，还能执行CMD命令等，但功能复杂度上 CreateProcess> ShellExecute> WinExec。WinExec只用于可执行文件，使用WinExec函数执行文件和在Windows“开始”菜单的“运行”中键入命令在效果上是一致的；ShellExecute可以打开任意类型文件，非可执行文件自动通过关联的程序打开。同时，WinExec必须有GetMessage或超时之后才返回，CreateProcess和ShellExecute都是直接返回的。

**4.1.1. WinExec**

  

函数原型：

| UINT WinExec(\_In\_ LPCSTR lpCmdLine,\_In\_ UINT uCmdShow ); |
| --- |

  

**参数：**

lpCmdLine：指向要执行的应用程序的命令行字符串（文件名加上可选参数）。如果lpCmdLine中不包含目录路径，则系统按照以下顺序搜索可执行程序：应用程序所在目录->父进程的当前工作目录->32位Windows系统目录(

GetSystemDirectory获取System32文件夹)->16位Windows系统目录(System文件)->Windows目录(GetWindowsDirectory获取)->PATH环境变量中的目录。

uCmdShow：如果被执行的文件会显示一个窗口，那么此参数指定窗口的显示方式，使用ShowWindow()中的dwCmdShow参数。参数速查：

![](../Images/8828c43f09678c6a9bbd6f793ea941d8.png)

**返回值：**

  

如果成功，返回值大于0x1F；

如果失败，则返回一下错误值之一：

| 值 || 含义 |
| --- | --- |
| 0 || 系统内存或资源不足 |
| #define ERROR\_BAD\_FORMAT 11L || exe文件无效 |

**4.2.跨session创建进程**

  

至此介绍的3个API创建的进程都是当前登录用户的，其所有的消息队列都可以被当前窗口下运行的所有进程访问，例如可以用SetWindowsHookEx()钩子挂住消息队列进行各种操作。  

还有三个API，CreateProcessAsUser、CreateProcessWithTokenW和CreateProcessWithLogonw，他们也能创建进程，创建的方式和CreateProcess相似，然而其创建的却可能是另一个用户的进程，消息循环属于另一个用户，因此也无法用SetWindowsHookEx()去钩，即使用全局钩子也钩不到回应。

系统是根据什么判断进程是哪个用户的？这就要引入session(会话)的概念了。

**4.2.1.会话**

用户登陆到windows系统之后，不管该用户是本地登陆的，还是远程登陆，系统都会为这个用户分配一个新的sessionid(SID，会话ID)。每个用户都有自己的session，用户创建的进程都会处于自己的session中，不同的session中存在着会话隔离，具体表现：

①不同session之间不能通过窗口互发消息；

②一个session中不能直接使用另一个session的显示资源，比如不能直接在session0中向session1中弹出窗口；

③一个session中不能直接使用另一个session的显示资源，不能读写另一个session中的文件；

④不同session之间不能直接共享内核对象的访问权；

当然session间也不是完全不能通信的，可以通过管道、SOCKET、内存映射、全局命名空间(并设置访问控制)等方式实现不同session间通信。

  

**4.2.2.CreateProcessAsUser、CreateProcessWithTokenW和CreateProcessWithLogonw**

  

CreateProcessAsUser、CreateProcessWithTokenW和CreateProcessWithLogonw这三个API创建的新进程都是在由指定标记表示的用户的安全上下文中运行，既可以创建本session的进程，也就是可以创建其他session的进程。  

CreateProcessAsUser和CreateProcessWithToken都是使用用户token创建进程的，而CreateProcessWithLogonw使用的是用户账户和密码:

**4.3.加载dll**

有些恶意代码存放在dll文件中，程序加载dll从而执行恶意代码。

**4.3.1.隐式链接和显示链接**

加载dll的方式主要有两种：一种是“隐式链接”(ImplicitLinking)，程序在启动的时候一同加载dll，程序终止时再释放占用的内存；一种是“显式链接”，程序使用dll时主动加载dll，使用完毕后主动卸载。

隐式链接加载dll的方式又叫静态调用，我们在编写exe程序的时候，就需要指明要调用的dll：

| #include"..\\dll.h"#pragmacomment(lib,"dllTest.lib") |
| --- |

之后我们就可以随便调用这个dll的导出函数了。我们可以在编译生成的exe文件导入函数表里，查看这个exe导入了哪些函数，哪些dll。

显式链接又叫动态调用，如果要调用Dll中的function，至少需要经历3个步骤：

| HINSTANCE hDll; //DLL句柄lpAddFun addFun; //函数指针hDll = LoadLibrary(TEXT("dllTest.dll")); //第一步，加载DLL  
if (hDll != NULL){addFun = (lpAddFun)GetProcAddress(hDll, "add"); //第二步，返回函数指针if (addFun != NULL){int result = addFun(2, 3); //第三步，通过函指针调用其functioncout << result << endl;}FreeLibrary(hDll); // 卸载dll} |
| --- |

显式链接调用dll中的每个function，都需要通过GetProcAddress()获取函数地址，比较麻烦。但显式链接非常灵活，如果丢失了这个dll，程序仍能继续运行；隐式链接则会报错，导致程序无法继续运行。

在上面代码中出现的几个核心API的介绍：

| HMODULE LoadLibrary(\_In\_ LPCTSTR lpFileName //指定要载入的dl文件名称);//返回值:成功则返回库模块的句柄;零表示失败,会设置GetLastError;BOOL FreeLibrary(\_In\_ HMODULE hModule //指定要卸载的dl句柄);//返回值:非零表示成功;零表示失败,会设置GetLastError;FARPROC GetProcAddress(\_In\_ HMODULE hModule, // DLL模块句柄\_In\_ LPCSTR lpProcName // 函数名);//返回值:成功则返回函数地址;失败则返回NULL,会设置GetLastError; |
| --- |

  

**4.3.2.延时加载**

显式链接和隐式链接各有利弊，于是就有了融合了两者优点的加载方式——延时加载。

**4.3.3.DllMain**

跟exe有个main或者WinMain入口函数一样，DLL也有一个入口函数，就是DllMain（DllMain就是一个名字，是编译器生成的，可以任意改变，有的时候也叫DLLEntry）。DllMain是可以选的，有些dll是没有DllMain函数的。

**4.4.内存加载**

在前文我们介绍exe启动的时候，提到了映像加载器，但并没有详细介绍，主要是为了留在这里介绍。

许多恶意程序会模拟映像加载器的行为，把exe、dll等PE文件直接加载到恶意程序的内存中去执行。为和映像加载器区分，笔者称之为PE加载器。

PE加载器工作的基本流程：

①获取要被加载的PE文件的映像文件大小；

②在进程中申请一个可读、可写、可执行的内存块；

③把PE文件按照映像对齐大小映射到内存中；

④根据PE结构的重定位表，进行重定位(有些exe是没有重定位表的)；

⑤根据PE结构的导入表，加载所需的DLL（使用LoadLibrary）；

⑥获取导入函数地址写入IAT（使用GetProcAddress）；

⑦修改PE文件加载基址ImageBase；

⑧根据PE结构，获取PE的入口地址，进入入口地址执行；

  

PE加载器实现的源码较长，这里就不放了，网上有很多实现PE加载代码，可以自行学习。

**6.Windows服务**

windows服务指由SCM(ServiceControlManager,windows服务管理器)启动的进程。Windows服务的实现需要三个部件：服务（Service）程序、SCP(ServiceControlProgram,服务控制程序)、SCM。运行服务时，需要由SCP执行启动命令。SCP向SCM提出服务控制请求（启动/停止/重启/暂停），SCM向服务程序传递控制命令，并接收其返回的值。

**6.1.SCM**

SCM—服务管理器，就是%SystemRoot%\\System32\\Service.exe。

**6.3.服务程序**

服务程序也只是简单的Windows可执行程序，但是它提供了一些功能，这些功能可以被注册为服务。一般我们说服务程序就是指服务宿主程序，就是Service注册表下ImagePath值对应的进程。但是服务和服务宿主程序不是一一对应的，因为一个程序可以提供很多功能，也就可以被注册为多个服务了。如下图所示，不同的服务对应的进程ID是一样的，说明同一个进程启动了多个服务：

svchost后面带了-k的参数，这样的服务的注册表键还必须有一个名为ServiceDll的注册表值，它位于Parameter子键下面，其中指向了真正实现该服务的DLL文件：

![](../Images/9a75f411282e277e9e5460a9b170df10.png)

除了svchost.exe，更多的服务是由“简单的”Windows可执行程序提供的。一个“简单的”Windows可执行程序要想提供服务功能，必须具有以下能力才行：

①至少有一个功能是服务；

②能够告诉SCM“我的这个功能是服务”；

③这个功能必须能够与SCM通信，接收来自SCP的指令，向SCM反馈自己的状态；

④能够根据SCP的要求执行相应的动作，如SCP要求服务停止运行，服务要能被终止；

接下来我们依次分析，这些能力是如何实现的。

在一个程序中会有很多的功能函数，其中提供服务的函数我们可以定义为ServiceMain1()、ServiceMain2()等等。

在程序的main函数里，我们就要告诉服务管理器ServiceMain1、ServiceMain2是提供服务的函数。我们调用StartServiceCtrlDispatcher与SCM通信，通知SCM哪些函数是服务。StartServiceCtrlDispatcher向SCM提供了一个列表，列表中标记了服务的名称以及提供服务的函数地址；随后，它等待SCM发来的启动服务的命令，创建相应的服务线程，由服务线程调用服务的入口点函数，并实现服务的命令循环。StartServiceCtrlDispatcher会一直等待来自SCM的命令，只有当该进程中所有的服务都停止时它才会将控制返回该进程的main函数。

在服务的入口点（ServiceMain1、ServiceMain2）第一个动作就是调用RegisterServiceCtrlHandler函数，RegisterServiceCtrlHandler接收一个函数指针，此函数指针指向的函数用于处理各种来自SCM的命令，此函数指针被称为控制处理器。RegisterServiceCtrlHandler并不与SCM通信，它只是把控制处理器告诉StartServiceCtrlDispatcher，StartServiceCtrlDispatcher与SCM通信，接收命令发给控制处理器，控制处理器进行相应操作。

接着，服务的入口点继续初始化该服务。同时调用SetServiceStatus函数定期给SCM发送状态消息，告诉SCM自己的状态。当入口点完成了初始化，服务线程就进入一个循环，等待客户应用的请求。

**6.4.创建或修改服务**

根据上面的知识，我们只需要创建或修改一个服务，让服务中含有恶意代码，启动这个服务就可以启动恶意代码了。笔者总结了三种方式创建或修改服务。

第一种方式，直接设置注册表。可以修改Service注册表已有的服务，将ImagePath或ServiceDll键值修改为恶意程序；也可以在Service表中新建一个服务，设置ImagePath或ServiceDll键值为恶意程序。将Start键值修改为0x02，实现自启动服务。这样系统在重启后会自动运行恶意服务。

第二种方式，实现自定义的SCP程序。在SCP程序中调用API修改服务或创建服务，最后调用StartService启动服务。

第三种方式，利用windows自带的SCP工具——sc.exe。利用控制台命令实现服务的创建和修改。

**6.5.session 0隔离**

恶意代码喜欢把自己注入系统服务进程或伪装成系统服务进程，但所有的服务全都是运行在session0中，而用户进程却不是，这就导致了一些问题。

在WindowsXP、WindowsServer2003，以及更老版本的Windows操作系统中，服务和应用程序使用相同的会话（Session）运行，而这个会话是由第一个登录到控制台的用户启动的。该会话就叫做Session0，如下图所示，在WindowsVista之前，Session0不仅包含服务，也包含标准用户应用程序。

![](../Images/86bece01d0e3587632d0bac99cc8ccb1.png)

将服务和用户应用程序一起在Session0中运行会导致安全风险，因为服务会使用提升后的权限运行，而用户应用程序使用用户特权（大部分都是非管理员用户）运行，这会使得恶意软件以某个服务为攻击目标，通过“劫持”该服务，达到提升自己权限级别的目的。

从Vista开始Session0 中只包含系统服务，将服务与应用程序隔离提高系统的安全性。其他应用程序则通过分离的Session运行，并需要运行在用户登录系统时创建的后续session中，如第一个登录用户创建session1，第二个用户创建session2，以此类推。

![](../Images/c64c2f312829fcd0920774712510fd76.png)

除了将系统服务所在的session与应用程序所在的session进行隔离，系统还限制session0不支持用户UI界面。服务不能直接与用户的桌面进行交互。

Session都是与窗口站关联起来的，普通session关联的窗口站是可见的（窗口站命名为WinSta0），而session0关联的窗口是不可见窗口站（窗口站命名为Service-0x0-xx$）。而所有的服务都是在session0中，所以服务的窗口站是不可见的，如果一个服务弹出一个对话框，就会因为用户无法看到该对话框，无法进行交互（键盘/鼠标消息不可达），导致该服务一直处于挂起状态。

处于session0的进程，无法与普通用户通信，不能通过Windows消息机制进行通信，更不能创建普通的用户进程。于是恶意代码程序就要想办法突破session0隔离。

**7.可移动设备启动7.1.autorun.inf**

Windows提供了可移动设备自动播放功能，在可移动存储介质的根目录下的autorun.inf文件就负责自动播放的功能。如下图所示只要插入可移动设备就会运行setup.exe：

![](../Images/df9eb02394041a242c052d8f7cb58239.png)

这种运行是在用户不知情的情况下运行的，在很长一段时间里，利用autorun.inf进行攻击非常流行。

为了对抗这种攻击，微软在2011年给出了解决方案，禁用USB的自动运行（没有禁用CD/DVD的自动运行）。

微软的措施在很大程度上阻断了这种攻击，但因为微软没有禁用CD/DVD的自动运行，攻击者还可以利用CD/DVD进行攻击。另一方面，攻击者想出了将USB设备（U盘）伪装成CD/DVD设备的方式实现自动运行，这种伪装需要使用专业的工具改造USB设备，详细可以参考《USB自动渗透手法总结》(超链接:https://www.freebuf.com/sectool/158784.html)。

在《USB自动渗透手法总结》一文中还介绍了另一种很有意思的攻击，使U盘伪装成一个USB键盘，并通过虚拟键盘输入集成到U盘固件中的指令和代码进行攻击，插入U盘后便有一个无形的键盘输入指令进行恶意操作。

  

**8.第三方程序启动8.1.路径搜索顺序**

windows在执行一个程序的时候，是按照如下目录搜索程序的：

*   应用程序所在目录
    
*   父进程的当前工作目录
    
*   32位Windows系统目录(
    
*   GetSystemDirectory
    
*   获取System32文件夹)
    
*   16位Windows系统目录(System文件)
    
*   Windows目录(GetWindowsDirectory获取)
    
*   PATH环境变量中的目录
    

  

有的时候我们运行一个程序，输入不带后缀的文件名也可以运行程序，这是因为windows在搜索可执行文件时如果发现根据文件名找不到该文件，windows会自动为其添加环境变量PATHEXT中后缀，从左往右遍历后缀。

![](../Images/90664a2ab993c5fd1f1ee473f9ce5a35.png)

在注册表开机启动项中，有些程序是受信任的程序，攻击者会把注册表中的程序扩展名删掉。然后，将的恶意程序复制到相应目录下，并将扩展名改为.com。当机器重启时，后缀名是.com的恶意程序就会自动运行：

![](../Images/de123c600f21bd74b57cc94cb7776617.png)

这种修改还有一个“好处”是Autoruns（安全软件）不会检测出启动项被修改成恶意程序了，因为Autoruns并不检测扩展名，而是直接解析.exe文件。
