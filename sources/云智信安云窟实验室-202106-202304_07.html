Mythic使用和分析

环境安装

有详细的官方文档：

https://docs.mythic-c2.net/installation


实际使用命令：

// 下载主体程序
$ git clone https://github.com/its-a-feature/Mythic

// 安装payload
sudo ./mythic-cli install github https://github.com/MythicAgents/Apollo

// 安装C2配置文件
sudo ./mythic-cli install github https://github.com/MythicC2Profiles/http

// 启动Mythic
./mythic-cli start

等待启动命令运行完成。查看当前状态：

./mythic-cli status

框架

参考官方文档，Mythic主要分为3部分，Mythic Server、Payload、C2 Profiles。Mythic Server主要起到整体控制作用联合作用，Payload负责生成payload可执行文件。C2 Profiles是C2的配置文件。它们分别运行在不同的docker容器中，方便维护。


Mythic Server

把mythic_server容器中的源码复制出来，分析一下服务端的逻辑


先看一下源码框架


__init__.py

初始化应用用到的参数，最后初始化用sanic启动的web服务。紧接着就是路由分配了。


routes/

这个目录下主要是应用的基础功能，通俗讲就是页面有按钮的部分。包括认证、选项、报告、登陆功能、文件服务、websocket等等。


api/

这部分是C2的逻辑部分，主要是后端运行的和后端应用交互的部分。文件名基本可以知道文件的作用。


Payloads

这部分负责生成payload可执行文件，使目标上线。官方给出多种选择，称为agent。使用的时候，根据自己需求，选择一个即可。

https://github.com/MythicAgents/

拿apollo举例，源码主要包括两部分，agent_code（agent端的源码，最终编译成可执行文件）和mythic（agent命令相对的py源码文件）

agent_code/

每种payload的这部分都不一样，可能用不同的代码语言，可能执行方式不同。最终都会生成在目标机可运行的文件。这个是用C#编写，最终编译成exe可执行文件。上传到目标机运行即可。


cd命令


mythic/

这部分代码主要是agent的命令配合Mythic服务端。

目录下的agent_functions为python源码，用来从服务端向agent发送要执行的命令。


browser_scripts目录为js文件，主要作用是在浏览器端处理命令执行后返回的内容。


C2 Profiles

C2 Profiles是C2的配置文件。官方一共给出了6种。

https://github.com/MythicC2Profiles

类型

描述

tcp

基于 TCP 网络套接字的 P2P 通信

http

这是一个名为 http 的 Mythic C2 配置文件。 它只是提供了一种从网络中获取 HTTP 消息并将它们转发到 Mythic 服务器的方法。

websocket

这是一个名为 websocket 的 Mythic C2 Profile。 它为代理提供了一种通过静态 websocket 连接进行连接的方法，然后在单个连接中进行标准的信标流量。

smb

命名管道的 P2P 通信

dns

这是一个名为 dns 的 Mythic C2 配置文件。 它实现了一个 DNS 服务器，用于侦听来自代理的 TXT 查询。

dynamichttp

这是一个名为 dynamichttp 的 Mythic C2 Profile。 它只是提供了一种从网络中获取 HTTP 消息并将它们转发到 Mythic 服务器的方法。

使用体验

不得不说，跟CobaltStrike相比，差远了。上线的agent没有删除功能。发送exit命令后，也不会掉。这点很尴尬


再之后，怎么滴都不上线了。尝试了好几种payload和C2 Profile都没有反应。（服务端监听的端口可以正常访问）


很多命令无法执行，可能跟使用的payload有关。



总的来说，感觉Mythic挺复杂的，用到了很多组件，启动的时候，还需要启动一堆docker容器。C2本来不应该是短小精悍吗？
