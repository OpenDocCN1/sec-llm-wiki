之前写过一篇《实践证明K8S环境真的需要入侵检测或防御》，说的是用EPK监控容器内部的攻击，攻击用的是cve-2017-5638，实际监控效果并不好，

本周从另外一个角度来实践监控这个攻击的发生，就是从K8S内部监控容器的异常通信，

像上周blog中做packetbeat容器镜像一样，首先得做一个监控容器的镜像，其实就是以ubuntu的镜像为基础，安装上docker，然后还是以DaemonSet的方式启动这个监控容器，yaml模板如下，

apiVersion: apps/v1  
kind: DaemonSet  
metadata:  
  name: monitor  
  namespace: kube-system  
  labels:  
    k8s-app: monitor  
spec:  
  selector:  
    matchLabels:  
      name: monitor  
  template:  
    metadata:  
      labels:  
        name: monitor  
    spec:  
      hostNetwork: true  
      hostPID: true  
      containers:  
      - name: monitor  
        image: monitor:0.1  
        imagePullPolicy: IfNotPresent  
        securityContext:  
          privileged: true  
        volumeMounts:  
        - mountPath: /var/run  
          name: docker-sock  
      volumes:  
        - name: docker-sock  
          hostPath:  
            path: /var/run  
      terminationGracePeriodSeconds: 30  

这个监控容器启动后，可以进到内部查看一下，

![](../Images/bb7325972d01d4e5f464383ce77f66d5.png)

想要监控靶机容器，就得先能看整个宿主机里的容器信息，找到靶机容器的id，然后通过容器id找到靶机容器在宿主机里的pid，

docker inspect 0266612583da | grep Pid，

有了pid，就可以在监控容器内部查看靶机容器的通信会话了，

nsenter -t 4911 -n cat /proc/net/tcp，

还是在外面对靶机容器进行攻击，  

![](../Images/576a78871fe3722099c8ca421a3df095.png)

监控效果有点儿复杂，我放到最后详细解释一下，

![](../Images/22d33c2086c4bdbef82fc35d8f9e1650.png)

上面的数据是攻击前的，下面是攻击后的，能够看到靶机容器里多了一个会话，数据翻译过来就是，靶机向外面一个地址的4444端口做了主动连接，而且一直维持，这个就是异常。
