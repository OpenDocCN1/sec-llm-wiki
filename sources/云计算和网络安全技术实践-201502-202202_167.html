之前做过Networking-SFC+NSH的实践，但是nsh的流表出不来，就放弃了，最近有高人解决了这个问题，原来是Networking-SFC项目自己埋的bug，问题解决方法的知识产权不是我的，不方便扩散，但倒是可以把效果发出来看看，

跟以前的验证方案一样，希望从外网ping普通虚机，流量被通过nsh流表引到安全服务虚机上，

命令跟以前一样，

openstack sfc port pair create --ingress p1 --egress p1 --service-function-parameters correlation=nsh pp1，
openstack sfc port pair group create --port-pair pp1 ppg1，
openstack sfc flow classifier create --protocol icmp --logical-source-port 676b5b92-cc8d-4448-b62d-a67d9c5358a1 fc1，
openstack sfc port chain create --port-pair-group ppg1 --flow-classifier fc1 --chain-parameters correlation=nsh pc1，

不同的是这回能看到nsh流表了，

先说第二条，意思是从服务虚机接口出来的包，要做nsh解封装，然后再正常转发，然后看第一条，从网关口进来的icmp流量，要做nsh封装，然后去组1，

组1这条说的是，把目的mac改成服务虚机接口的，然后去表5，

表5里看到目的mac是服务虚机接口的，把vlan加上（这个地方感觉有点儿问题，vlan_id应该是4才对），然后去表10，

表10里倒是正确的看vlan是4，mac是服务虚机的，nsh封装不动，把vlan去掉再发给服务虚机的接口，

抓包验证一下看看，流量被正确的引过来了，但是看不明白包结构，

保存成pcap文件，用wireshark看吧，

一目了然，原始二层报文被用eth+nsh封装了，目前实验的服务虚机不支持nsh，无法正确处理报文，所以只能看到请求报文，

虽然nsh验证成功了，但是还是没整明白跟非nsh封装的好处在哪里，还是不支持跨网段引流和一个服务虚机接口共享给多条服务链，这个恐怕还是要Networking-SFC项目去发展解决了，问题是，一个主动埋bug的项目，能指望吗？
