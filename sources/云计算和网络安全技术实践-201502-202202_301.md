# 如何在云环境中给vIPS回放威胁特征包

最近太忙，都没有时间研究啥新攻击工具的使用，为了不跳票，本期就分享一个本周为工作需要研究的在云环境中给vIPS回放威胁特征包的方法。

对于IPS的威胁识别效果，我个人是非常注重搭建真实的攻防环境来测试的，但是实际情况下要测试的威胁种类太多，一个一个搭建真实的攻防环境太费时间和精力，而且还不一定都能搭建出真实的攻防环境，无奈还是得选择回放威胁特征包的方法。当然这也不是啥丢人的事，NSSLAB测试都是这么干的。

有过硬件IPS威胁识别率测试经验的同学应该知道，就是拿测试仪或PC机直接往硬件IPS的接口上一连，直接回放事先准备好的一堆cap特征包就可以了，在云环境中这种方法就行不通了，因为在云环境中从虚拟机接口出来的报文都会先经过源MAC和IP检查，再通过vSwitch的二层交换（按目的MAC寻址）才能把数据包送到目的地，我们手里的cap特征包都是在现网环境中抓取的，源目的MAC和源目的IP都不是本地环境的，导致直接从vPC回放出来的特征包从接口一出来就被丢掉了。

怎么办，很容易想到的办法就是把手里的cap特征包中的源目的MAC和源目的IP都改成符合当前测试环境的，然后再回放，在网上搜到了两款开源软件tcprewrite和bittwiste，都能干这个事，下面就在OpenStack环境中验证一下，

![](../Images/58f912c4c3cfefa85de76e3b824c868a.png)  
需要验证的方案是，用tcprewrite或bittwiste把既有的BACKDOOR.binghe.3.3.cap文件中的源MAC和IP都改成ubuntu1的，目的MAC和IP都改成ubuntu2的，然后在ubuntu1上回放新的pcap文件，在ubuntu2上抓包验证。

在上面环境中，ubuntu1的MAC和IP分别为fa:16:3e:25:8d:44和10.0.0.3，ubuntu2的MAC和IP分别为fa:16:3e:2d:37:b2和10.0.0.4，在ubuntu1上先装好tcprewrite和bittwiste软件，

BACKDOOR.binghe.3.3.cap文件原始报文如下，

![](../Images/f4be7f8380da36e539ce5d73ba9d1f17.png)

先用tcprewrite改源目的MAC，

tcprewrite --enet-dmac=fa:16:3e:2d:37:b2 --enet-smac=fa:16:3e:25:8d:44 -i BACKDOOR.binghe.3.3.cap -o BACKDOOR.binghe.3.3-change-mac.pcap，

修改过源目的MAC的报文如下，

![](../Images/f3a94bfcf82a38b24b6072192e1153a6.png)

再用bittwiste改源目的IP，

bittwiste -I BACKDOOR.binghe.3.3-change-mac.pcap -O BACKDOOR.binghe.3.3-change-mac-ip.pcap -T ip -s 10.0.0.3 -d 10.0.0.4，

修改过源目的IP的报文如下，

![](../Images/77863ceb2c9386fc18ae5ac132e1d5e6.png)最后用tcpreplay回放修改过MAC和IP的pcap报文，同时在ubuntu2上抓包，

tcpreplay -i eth0 BACKDOOR.binghe.3.3-change-mac-ip.pcap，

在ubuntu2上抓到的报文如下，

![](../Images/0399cff3da10e935e49fc2a2d4bfb802.png)  
试验成功，怎么把vIPS串在ubuntu1和ubuntu2之间，请参考前两期内容。
