春节后第一篇，姗姗来迟。其实这期的内容上周末就写了，因为有个问题没考虑清楚，就没推送，这两天把问题搞清楚了，稍微改了点儿，本周推送也还好。

看到标题可能有人会问，怎么又回到以前的风格了，没办法，这个主题至少两篇连载，想来想去也只能这么命名。

闲言少叙，看干货。

用最新的Liberty版本，因为我喜欢它的拓扑图。用官方推荐的linuxbridge是不行的，需要改成openvswitch，参考一下以前的OpenStack实践，在安装时注意把neutron-plugin-linuxbridge-agent换成neutron-plugin-openvswitch-agent，以及所有的linuxbridge相关配置都要改成openvswitch的，不愿意看ubuntu的主题，把它卸载掉，apt-get remove --purge openstack-dashboard-ubuntu-theme，实验拓扑如下，

![](../Images/038e25d05d69650df33456ce7ad8a20f.png)  
从图上你应该能看明白，我是要把进出web虚拟机的流量都镜像给monitor虚拟机的port接口，这里的web虚拟机直接用的OpenStack御用的cirros，而monitor虚拟机则用的ubuntu server，做个试验，足够了。

在计算节点上ovs-vsctl show看看都有哪些接口，

![](../Images/28a3e130dee67b8040710b28aaae414f.png)  
其中qvo0b4dfea6-8c是web虚拟机的接口，qvo242208ba-1f是monitor虚拟机的port接口，

怎么做流量镜像，很简单，

ovs-vsctl \\  
  -- --id=@m create mirror name=mymirror \\  
  -- add bridge br-int mirrors @m \\  
  -- --id=@qvo0b4dfea6-8c get port qvo0b4dfea6-8c \\  
  -- set mirror mymirror select\_src\_port=@qvo0b4dfea6-8c select\_dst\_port=@qvo0b4dfea6-8c \\  
  -- --id=@qvo242208ba-1f get port qvo242208ba-1f \\  
  -- set mirror mymirror output-port=@qvo242208ba-1f

然后从外面ping web虚拟机，再ssh到monitor虚拟机上抓包，没抓到！

brctl show一下你就明白为啥了，

![](../Images/33bdfc86cbd694cd132b9d4838d0599a.png)  
因为安全组的driver用的neutron，虚拟机的接口并不是直接连到ovs上的，而是为每个接口都用linux bridge做了一次桥接，镜像过来的流量到了ovs上的接口，走普通的交换模式，当然不会把报文转发给跟它桥接在一起的虚拟机的接口，

这怎么办，想了一天，只能把bridge配置成hub模式，brctl setageing qbr242208ba-1f 0，再抓包就有了，

![](../Images/3989e281a86e32d7b30a075e47ee9d12.png)  
这就完了吗，细心点儿你会发现抓到的包都是没有vlan tag的，再稍微明白点儿ovs原理，你会有疑问，ovs定义的被镜像流量是怎么样的，是从一个接口进来之后+从一个接口出去之前，还是从一个接口进来之前+从一个接口出去之后，如果是前者，抓到的包应该是带vlan tag的。

看了上面的抓包结果，你就能下结论说这是后者吗，非也，你要去实践验证，

把监听接口配置成trunk模式，ovs-vsctl set port qvo242208ba-1f vlan-mode=trunk，然后再抓一次包，

![](../Images/f69d9035a77ad98f80736f3206951346.png)  

vlan tag出来了，原来是当监听接口是access模式时把转发过来报文中的vlan tag给剥掉了。

打完收工，下期给你们看怎么破掉二次桥接的方式，直接把流量镜像到虚拟机接口的方案，这就是我说的连载的意思。
