摘要

思科Talos安全团队披露称，开源项目PDFium中的TIFF图像解码器功能中存在一个“差一错误”读/写漏洞。PDFium是由谷歌开发的一款PDF开源转换器，存在漏洞的版本用于Chrome 60.0.3112.101及之前版本中。

  

  

  

## **概述**

  

谷歌Chrome浏览器是当前使用最广泛的浏览器，而一个特别构造的PDF能触发该漏洞从而造成内存损坏问题，甚至是信息泄露问题，也有可能造成代码执行问题。该问题已在Chrome62.0.3202.62版本中修复。受害者要触发这个漏洞，需要在浏览器中打开一个恶意PDF。  

该漏洞由思科Talos安全团队的研究员Aleksandar Nikolic发现。

## **漏洞具体详情**

  

PDFium是由谷歌开发的一款PDF开源转换器，用于Chrome网络浏览器、在线服务和其它独立的应用程序中。Talos-2017-0432/ CVE-2017-5133是一个“差一错误”读/写漏洞，存在于PDFium的TIFF图像解码器功能中。该漏洞已在最新的git版本以及最新的Chromium地址清洁器版本(asan-linux-release-498039) 中验证。

负责解码压缩TIFF图像流的代码中存在一个堆缓冲溢出漏洞。该漏洞产生的原因在于负责解析像素数据的功能。在解析flate解码图像流时，函数TIFF\_PredictLine功能实现：

> void TIFF\\\_PredictLine(uint8\_t\* dest\_buf,
> 
>                    uint32\_t row\_size,
> 
>                    int BitsPerComponent,
> 
>                    int Colors,
> 
>                    int Columns) {
> 
>  
> 
>  
> 
> int BytesPerPixel = BitsPerComponent \*Colors / 8;
> 
>  if(BitsPerComponent == 16) {
> 
>  for(uint32\_t i = BytesPerPixel; i < row\_size; i += 2) {
> 
>   uint16\_t pixel =
> 
>       (dest\_buf\[i - BytesPerPixel\] << 8) | dest\_buf\[i - BytesPerPixel +1\];
> 
>   pixel += (dest\_buf\[i\] << 8) | dest\_buf\[i + 1\];
> 
>   dest\_buf\[i\] = pixel >> 8;
> 
>   dest\_buf\[i + 1\] = (uint8\_t)pixel;

 

在上述代码的循环中，它一直都会从dest\_buffer中读取4个字节，即使缓冲的长度少于4个也不例外。这就可能引发堆“差一错误”读取，随后紧接着是“差一错误”写入。然而，要访问易受攻击的代码，需要满足多个条件。在之前的函数TIFF\_Predictor中，我们看到：

> bool TIFF\_Predictor(uint8\_t\*& data\_buf,
> 
>                   uint32\_t& data\_size,
> 
>                   int Colors,
> 
>                   int BitsPerComponent,
> 
>                   int Columns) {
> 
> int row\_size = (Colors \* BitsPerComponent \*Columns + 7) / 8;                        \[1\]
> 
> if (row\_size == 0)
> 
>  return false;
> 
> const int row\_count = (data\_size + row\_size- 1) / row\_size;
> 
> const int last\_row\_size = data\_size %row\_size;                                       \[2\]
> 
> for (int row = 0; row < row\_count;row++) {
> 
>  uint8\_t\* scan\_line = data\_buf + row \* row\_size;
> 
>   if((row + 1) \* row\_size > (int)data\_size) {
> 
>    row\_size = last\_row\_size;                                                        \[3\]
> 
>   }
> 
>  TIFF\_PredictLine(scan\_line, row\_size, BitsPerComponent, Colors,Columns);        \[4\]
> 
> }
> 
> return true;

 

在\[1\]中，row\_size的计算结果是8的倍数。在\[2\]中，最后一排的数据大小也进行了计算，而输入数据可能并不是row\_size字节的倍数。当最后一排使用时（如果下一排不在数据大小中），row\_size被设为last\_row\_size，如\[3\]。在\[4\]中，易受攻击的函数TIFF\_PredictLine被rowsize的计算结果所调用。如果我们将缓冲大小和last\_row\_size正确地排成一行，那么结果会导致最后一排的大小为3，而Tiff\_PredictLine实际上从这个数据缓冲中读取/写入的是4，从而导致出现读/写“差一错误”。

如下是能够触发该漏洞的一个样本PDF：

> %PDF-1.6
> 
>  
> 
> 47 0 obj
> 
> <</DecodeParms
> 
>      <<        /Columns 2
> 
>      /Colors 1
> 
>               /BitsPerComponent 16
> 
>               /Predictor 2>>
> 
>      /Filter/FlateDecode
> 
>      /W\[0 0 0\]>>
> 
> stream
> 
> ...
> 
> endstream
> 
> endobj
> 
> startxref 30
> 
> %%EOF

 

以上流中的内容仅需满足一个条件即可：它必须解析为某个长度，从而使之前提到的\[2\]中的计算结果为3。满足这些条件以及之前提到的某些条件的最小长度是23。”Columns”、”Color” 的值和未压缩流的长度可进行相应调整以控制缓冲的大小、循环的数量以及所访问的字节，最终让相应的值通过我们提到的函数。

根据底层分配器和其它变量，利用这个漏洞虽然不一定会引发信息泄露或内存覆写问题，但结合其它漏洞一定会进一步引发内存损坏问题。
