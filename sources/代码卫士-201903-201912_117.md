CVE-2015-8562是一个 PHP 对象注入漏洞，已在3.4.5版本中修复，不过它非常依赖于并不实际被所有环境所信任的 PHP 版本。和 CVE-2015-8562 相比，这个新发现的 0day 完全独立于变得越来越可靠的环境；仅影响 3.0.0 至 3.4.6 版本。不过这个新 0day 的有趣之处在于它的利用。当前关于对 PHP 对象注入漏洞的更高级且手动利用的文章不是很多，而本文补充的正是这一点。

**会话如何运作**

![](../Images/e749ec6a9f63a5498a7364aa208788bb.png)

Joomla 会话以 PHP Objects 的形式存储在数据库中且由 PHP 会话函数处理。它是一种有意思的攻击向量，因为未认证用户的会话也可存储，因此对象注入 (Object Injection) 能够导致未认证的远程代码执行 (RCE) 后果。 ‘libraries/joomla/session/storage/database.php’中定义的函数 read()和 write()由session\_set\_save\_handler()设置，作为‘libraries/joomla/session/session.php:\_\_start’ session\_start() 调用的读和写处理程序。如下例子说明了未认证用户在数据库中存储的典型 Joomla （3.4.6版本之前）会话 (at table\_session)：

![](../Images/00d72f6366aa5754e1d8dd2d967997ca.png)

虽然定义了很多对象，但最有意思的地方在于会话处理输入参数的方式。如果我们使用参数进行常规操作，则这些参数和动作的结果信息将存储在会话对象中，如下所示：

![](../Images/26f7120c0170f7b2677fa3b46842cd43.png)

当我们在 Joomla中执行 POST 请求时，通常会有303重定向将我们重定向至结果页。**这是利用的重要事项**，因为第一个请求（含参数）将只会导致 Joomla 执行动作并存储（例如调用write() 函数）会话，之后303重定向将进行检索（如调用read() 函数）并将信息显示给用户。

Write 函数接受2个参数，即session\_id（来自 cookie）和序列化对象。在将数据存储到数据库之前，会用‘\\0\\0\\0’替换‘\\x00\\x2a\\x00’(chr(0).’\*’.chr(0))，原因在于 MySQL 无法保存 Null 字节，而在序列化对象中， $protected 变量被赋予‘\\x00\\x2a\\x00’前缀。从另一方面来看，当读取时， read 函数会用‘\\x00\\x2a\\x00’替换‘\\0\\0\\0’，重构原始对象。这种替换的主要问题在于它用3个字节替换了6个字节。

![](../Images/0f33bf49cbbb6c68cc8dedfdd21323e1.png)

这种行为始于 3.0.0 版本并一直影响到 3.4.6 版本。从 3.4.7 版本开始，该代码虽然仍然存在，但会话是 base64 编码形式存储在数据库中。
