# 高质量软件真的物有所值吗？

Martin Fowler，世界软件开发大师，敏捷开发方法的创始人之一，在面向对象分析设计、UML、模式、XP和重构等领域都有卓越贡献，现为软件开发咨询公司ThoughtWorks的首席科学家。他的多部著作《分析模式》、《UML精粹》和《企业应用架构模式》等都已经成为脍炙人口的经典。

  

软件开发项目中常出现的一个矛盾是花时间改进软件质量和集中精力发布更有价值功能之间的抉择。通常，交付功能的压力占上风，导致开发人员抱怨没有时间改进架构和代码质量。  

 

Betteridge通过一句谚语提出了标题法，指出任何以问号结束的标题或题目的文章都可以用“否”来概括。了解我的人应该不会怀疑我颠覆该法则的想法。但这篇文章更进一步，它颠覆了问题本身。该问题假定了质量和成本之间存在权衡取舍的关系。本文将解释为何这种权衡不适用于软件领域：实际上高质量软件的成本更低。

 

虽然我大部分的文章针对专业的软件开发人员，但在本文中我不再假定读者具备任何有关软件开发机制的知识。我希望本文能对所有思考软件工作的人都具有价值，尤其是那些作为软件开发团队客户的商业领袖们。

**我们习惯于权衡质量和成本。**

![](../Images/d364d3ac0cecb30f2d8340480dd834d5.png)

就像本文开头提到的那样，我们都习惯了权衡质量和成本。换新手机时，我可以选择处理器更快、屏幕更好、内存更多但价格昂贵的款式；或者我可以放弃其中的某些质量，从而花更少的钱。但这并非铁律，有时候我们可以找到物美价廉的商品。更常见的情况是，我们对质量的看法不一致，比如有些人并没有注意到这个屏幕优于其它屏幕。但多数时候，质量更高成本也更高的假设是成立的。  

 

**软件质量涵盖多个方面。**

![](../Images/d364d3ac0cecb30f2d8340480dd834d5.png)

如果要谈论软件质量，那么首先需要解释软件质量是什么。这是第一个复杂的问题：软件质量涵盖很多方面。比如我可以考虑用户界面是否能够更容易地让我完成任务，使我效率提升并减少困难？我可以考虑稳定性是否包含引发错误和挫折的缺陷？我也可以考虑架构问题，如源代码模块是否明确，能让程序员轻松找到并理解本周需要处理哪些代码？  

 

虽然以上三方面并无法涵盖全部的软件质量问题，但足以说明一个重要观点。如果我是软件的客户或者用户，那么我并不关心我们称之为质量的某些方面。用户可以判断用户界面是否友好，高管能够知道软件是否让员工效率提升，用户和客户将会注意到缺陷问题，尤其是数据损坏或导致系统暂时无法运行时。但客户和用户无法感知软件的架构。

 

因此我将软件质量分为外部质量（如用户界面和缺陷）以及内部质量（架构）。这个分类认为，用户和客户能够看到软件产品外部质量的高低，但无法辨别内部质量孰优孰劣。

 

**乍一看，内部质量对客户无关紧要。**

![](../Images/d364d3ac0cecb30f2d8340480dd834d5.png)

用户和客户无法看到内部质量，但这重要吗？我们假设瑞贝卡和我都编写了一款用于追踪并预测航班延误的应用程序。我们应用程序的主要功能都是一样的，用户界面优雅且基本不包含什么缺陷。二者的唯一区别在于瑞贝卡的内部源代码整洁有序，而我的一团糟。另外还有一个区别：我的售价6美元，她的售价10美元。  

 

由于客户无法看到源代码，而源代码也不会影响应用程序的操作，那么人们为什么要多花4美元购买瑞贝卡编写的软件呢？总体而言，不值得花更多的钱获得更高的内部质量。

 

换一种说法就是，把钱用在提高外部质量上是合理的，而用在改进内部质量上没有意义。用户可以判断出是否花更多的钱来获得更好的用户界面，因为他们能够评估出某个用户界面是否更好即值更多的钱；但用户无法看到软件的内部模块化结构，更不用说哪种结构更优。既然如此，为何要把钱花在没有效果的东西上呢？既然如此，那么软件开发人员为何要投入时间和精力改进软件的内部质量呢？

 

**高水平的内部质量使软件增强工作更容易开展。**

![](../Images/d364d3ac0cecb30f2d8340480dd834d5.png)

那么，软件开发人员为什么要在内部质量方面大费周折呢？程序员大部分时间都在修改代码。即使在一个新的系统下几乎所有的编程都是在现有的代码库中完成的情况下也不例外。当我想要增加一个新的软件功能时，我首先要做的就是弄清楚该功能如何适应现有的应用流，然后更改流并添加新功能。通常我需要使用已存在于应用程序中的数据，因此需要理解代码的表示内容、它如何和周围的数据关联以及增加新功能需要哪些数据。  

 

以上提到的都是关于我如何理解现有代码的内容，但软件很难理解这些东西。逻辑可能纠缠不清、数据难以追踪、6个月前用于指代的名称对于托尼而言很好理解，但于我而言它们就和托尼离职的原因一样扑朔迷离。开发人员将这些问题称为“cruft”，即当前代码和理想代码之间的差距。

 

人们常把cruft比作技术债务。增加新功能的额外成本就像支付利息，而清理cruft就像支付本金。虽然这个比喻很贴切，但它确实让很多人想当然地认为cruft要比实际更容易衡量和控制。

  

![](../Images/5a30c6b2cdd522b070406b030aa5e039.png)

内部质量的一个主要特征是，它能让我摸清应用程序如何运作以便增添内容。如果软件被很好地划分为多个单独的模块，那么我就不必读取所有50万行代码，而是快速在几个模块中找到几百行代码。如果我们将精力放在清晰的命名上，那么我就能快速理解代码的各个部分的用途，而不必通过细节查找蛛丝马迹。如果数据明确地遵循底层业务的语言和机构，那么我就能容易地理解它和我从客户服务代表获得的需求之间存在何种关联。cruft增加了我理解如何修改的时间，同时增加了出错几率。如果我发现了这些错误，但因为我必须理解错误是什么以及如何应对，那么又增加了时间成本。如果我没发现这些错误，那么就会出现生产缺陷，从而后续不得不花费更多的时间来处理这些缺陷。

 

我所做的修改也会影响后续工作。我可能找到了增加这新功能的快速方法，但这一过程违背程序的模块化结构，从而增加cruft。如果我使用了这一过程，那么今天我可能会更快地解决问题，但在未来的数周或数月时间里，任何处理这段代码的人员都会被拖累。一旦团队的其他人都做出了同样的决定，那么修改应用程序的容易路径将会快速累积cruft，导致每一次小改动都会耗费数周时间。

 

**客户确实在意快速推出新功能。**

![](../Images/d364d3ac0cecb30f2d8340480dd834d5.png)

现在我们了解了为何对于用户和客户而言内部质量至关重要的原因。更高的内部质量让新功能的增添变得更容易，从而以更快的速度以更低的成本推出。虽然当下瑞贝卡和我的应用程序是一样的，但在数月之后，瑞贝卡更高的内部质量能让她每周都增添新功能，而我却不得不为推出某个新功能而披荆斩棘于cruft问题。我无法和瑞贝卡的速度比拼，而不久之后她的软件要比我的更具特色。之后我的所有客户都会弃我而去投奔瑞贝卡，即使她可能会提高价格也无法阻挡这一趋势。

  

![](../Images/920bc162a51db32ed229cf72a1dd5f32.png)

  

**可视化内部质量的影响。**

![](../Images/d364d3ac0cecb30f2d8340480dd834d5.png)

  

内部价格的根本作用在于它降低了未来做出修改的成本。但编写良好的软件需要投入更多的精力，它确实会在短期内影响成本。

这就是内部质量差的后果。刚开始进展迅速，但随着时间的流逝越来越难以增加新功能。即使是小小的改动也要求程序员理解难以理解的庞大代码。修改时会发生意外错误，从而导致测试时间延长以及需要修复的缺陷。

 

专注于内部质量就是要减少生产力的降低。确实某些产品会产生相反的效果，基于之前的工作可以更容易地构建新的功能。这种愉快的场景很罕见，因为它要求一支技术精湛、训练有素的团队来完成。不过的确偶尔能见到这种情况。

  

  

![](../Images/7c690a0592eb012a0b49c83378666b07.png)

  

这里的微妙之处在于，低下的内部质量要比高水平的内部质量在短时间更具生产力。在此期间，质量和成本之间存在某种权衡。显然，问题是，多久之后二者会交汇呢？

 

此时，我们解释一下使用可视化伪图的原因。我们无法衡量某软件团队交付的软件质量。这种无法衡量产出继而无法衡量生产力的情况使得我们无法给出内部质量低下（同样难以衡量）所造成后果的可靠统计数据。无法衡量产出在很多专业工作中是很常见的情况，比如我们如何衡量律师或医生的生产力呢？

 

我评估交汇点的方法是征求技术精湛的开发人员的意见。而他们的答复让很多人大跌眼镜。开发人员认为质量低下的代码在几周内的时间里就能严重拖慢进展。因此内部质量和成本之间的权衡取舍空间并没有多少。即便是微小的软件工作也会从良好的软件实践中获益，当然我的经验也能够证明这一点。

 

**即使最好的团队也制造cruft。**

![](../Images/d364d3ac0cecb30f2d8340480dd834d5.png)

很多非开发人员倾向于认为只有开发团队粗心大意犯错时才会产生cruft，但实际上即使是最优秀的团队也不免在工作过程中制造某些cruft。

 

我和我们团队最优秀的一名技术团队领导有一次聊到一个故事，我想通过它来阐述上面提到的观点。他刚刚完成了一个被认为是非常成功的一个项目。客户对交付的系统很满意，对于系统能力、构造时间和成本都很满意。我们的团队对于项目的工作经验持积极态度。这名技术领导非常高兴，但承认系统的架构实际上并没有那么好。我问他，“怎么会呢，你可是我们最好的架构师之一啊。”他的回答和所有有经验的软件架构师一样，“虽然我们做出了良好决策，但现在才明白我们本应该构建它的方法。”

 

很多人，包括软件行业的一些人，都将构建软件比作建造大教堂或摩天大楼的过程，不然我们为何要把资深程序员称为“架构师”呢？但要知道我们是在物理世界未知的不确定世界中构建软件。软件客户只是拥有产品功能的粗略想法，而且是在软件构建之后尤其是发布早期版本之后才了解得更多。软件开发的构建模块——语言、库和平台——每隔几年就会快速变化。这就像在物理世界中客户通常会在大楼构建完成和入住之后会添加新地板并改变楼层平面图那样，而混凝土的基本属性每隔几年就会改变。

 

 

鉴于这种变化，软件项目一直都在创新。我们几乎无法通过之前已解决的问题来理解当下遇到的麻烦。当我们构建解决方案时自然会更多地了解问题，因此我常常会听到很多团队说构建软件一年左右的时间后才真正理解了软件的架构。即使是最好的团队也会在软件中制造出cruft。

 

不过区别在于，最好的团队在创建更少cruft的同时也会清除足够的cruft，以便能够继续快速地添加功能。他们花费时间创建自动测试以便能够快速发现问题并花费更少的时间解决问题。他们经常进行重构以便在积重难返前解决问题。持续集成将团队因工作目的不同造成的cruft最少化。这就像清理厨房灶台和设备。烹饪时不可能做到一尘不染，但如果不快速清理，污渍就会变干难以清除，而下次进入厨房时，所有的污渍导致无法继续烹饪。

 

**高质量软件的成本更低。**

![](../Images/d364d3ac0cecb30f2d8340480dd834d5.png)

总结一下：  

*   忽视内部质量导致cruft的快速累积。
    
*   cruft拖慢功能开发进程。
    
*   即使是优秀的团队也制造cruft，但维系高水平的内部质量能够掌控这一状况。
    
*   高水平的内部质量将cruft最少化，使团队能够投入更少的精力、时间和成本增添新功能。
    

 

遗憾的是，软件开发人员通常无法很好地解释这种情况。我无数次遇到开发团队会表示，“由于耗时太长，他们（管理层）不让我们编写高质量代码。”开发人员通常需要通过适当的专业性来证明对代码质量的关注是值得的。但这种道德主义论证意味着，高质量是有代价的，而这又使他们的论点失效。令人厌烦的是，粗制滥造的代码让开发人员的日子不好过，同时也让客户花更多的钱。当思考内部质量时，我强调的是我们只应将其视为经济学论点。高水平的内部质量减少了未来增添功能的成本，说明花时间编写良好的代码实际上会降低成本。

 

这就是为何说文章开头的问题忽略了重点。高水平内部质量软件的“成本”是负数。权衡成本和质量是我们在日常生活中做出多数决策时用到的，但它对软件的内部质量而言毫无意义。（它对外部质量确实有用，如精心设计的用户体验。）由于成本和内部质量之间的关系是不常见的反直觉关系，因此通常人们一时难以消化。但理解这一点对于以最高的效率开发软件至关重要。
