漏洞详述


该漏洞存在的原因在于 Adobe Reader 处理 PDF 文件尾 (trailer) 的方式不正确。问题在于，当处理 ID 标签的数组值时，该应用程序不会预测超过0x100 字节。了解了这一点再加上一些 JavaScript，攻击者就能够暴力 Annots.api 的基地址 (base address)。

我们讨论的到底是什么？

按照 Adobe 的文档说明，该尾由一个或更多个键值对组成。

方法 f_AcroDocGetFileID 返回 PDF 中文件ID 的实际大小，即使传递的缓冲区参数是 NULL 且缓冲区大小的参数小于文件ID的实际大小。之后这个值用于设置 originalIDLen 和 modifiedIDLen 属性，而无需检查该值是否大于0x100 字节。

当应用程序试图将 origionalID 复制到基于堆的缓冲区时，它会使用新的 0x400 字节大小，而不是预期的0x100字节，并允许用户泄漏栈中的数据。结果，可利用基于栈的缓冲区界外读取漏洞，通过 Collab.documentToStream() API 调用泄漏 Annots.api 的基地址。



总结


由于 PDF 格式如此普遍，因此 Adobe Reader 是一个常见的攻击目标。本文说明了信息泄漏漏洞，Adobe 最近还修复了可导致远程代码执行的其它漏洞。在现代应用程序中执行代码通常需要执行多个步骤，而泄漏内存地址通常是完整利用链的第一步。结合利用本漏洞以及可导致代码执行和沙箱逃逸后果的漏洞，即可形成完整攻陷。用户应尽快打补丁。
