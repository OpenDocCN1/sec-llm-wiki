# 有时，你离成功的 exploit 只差一个信息泄漏：通过 ID tag 找到它

![](../Images/9bd196a41466a1b6afecfdaff80a3587.png)漏洞详述

  

该漏洞存在的原因在于 Adobe Reader 处理 PDF 文件尾 (trailer) 的方式不正确。问题在于，当处理 ID 标签的数组值时，该应用程序不会预测超过0x100 字节。了解了这一点再加上一些 JavaScript，攻击者就能够暴力 Annots.api 的基地址 (base address)。

我们讨论的到底是什么？

如果在编辑器中打开PDF文档，那么大概率我们会在底部看到一个文件尾 (File Trailer)，如下：

  

![](../Images/a4fa0616f3a1db844661d6d7428da24b.png)

  

按照 Adobe 的文档说明，该尾由一个或更多个键值对组成。

  

![](../Images/dca5f84ab4aa38b657911691a6473346.png)

  

我们感兴趣的一个键值对是 ID，它是“由两个字符串组成的一个数组，构成文件的文件标识符。”概念验证如下，它包含非常长的数组值：

  

![](../Images/ea493352941c3243d7c2ab18e22e38a2.png)

  

  

当应用程序遇到文件尾中的一个ID键会发生什么？在解析 ID 键的过程中，Reader 将调用一个函数，返回 ID 数组值的大小并使用这个值填充如下结构：

  

![](../Images/f9615e0a3276e25cf4c6c24ebfe90115.png)

  

伪代码如下：

  

![](../Images/385e1e52159ebf632392637dcbe4423d.png)

  

  

方法 f\_AcroDocGetFileID 返回 PDF 中文件ID 的实际大小，即使传递的缓冲区参数是 NULL 且缓冲区大小的参数小于文件ID的实际大小。之后这个值用于设置 originalIDLen 和 modifiedIDLen 属性，而无需检查该值是否大于0x100 字节。

在调试程序中我们可以看到，栈上的参数和我们在调试程序中看到的情况一致。

  

![](../Images/9c0e127c3b3e6c997f1b2af4e81510f3.png)

  

当函数返回时，结构如下：

![](../Images/e01667f8cdc712f9d799e934279646ab.png)

  

注意 @eax 中的返回大小。这里的问题在于，在将值存储到 this->originalIDLen 和 this->modifiedIDLen 之前并未检查并确定其是否大于0x100。

此时，该结构设置了无效的长度值。稍后通过调用 Collab.documentToStream() 起作用，它会调用一个 memcpy 调用，如下：

  

![](../Images/6f77df38f8b3dcbce3d5a91a50f2403b.png)

  

当应用程序试图将 origionalID 复制到基于堆的缓冲区时，它会使用新的 0x400 字节大小，而不是预期的0x100字节，并允许用户泄漏栈中的数据。结果，可利用基于栈的缓冲区界外读取漏洞，通过 Collab.documentToStream() API 调用泄漏 Annots.api 的基地址。

  

![](../Images/32a939e4125f4eb45cca5e75fd2c4e00.png)

  

![](../Images/9bd196a41466a1b6afecfdaff80a3587.png)总结

  

由于 PDF 格式如此普遍，因此 Adobe Reader 是一个常见的攻击目标。本文说明了信息泄漏漏洞，Adobe 最近还修复了可导致远程代码执行的其它漏洞。在现代应用程序中执行代码通常需要执行多个步骤，而泄漏内存地址通常是完整利用链的第一步。结合利用本漏洞以及可导致代码执行和沙箱逃逸后果的漏洞，即可形成完整攻陷。用户应尽快打补丁。
