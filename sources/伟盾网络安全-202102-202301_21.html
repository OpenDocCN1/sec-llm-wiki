0x02 漏洞简介


Apache Shiro<=1.4.1版本，当开启了rememberMe功能的时候，cookie的加解密使用了易受攻击的AES-128-CBC加密算法，由于该加密算法存在缺陷，导致攻击者可以构造恶意iv并且根据服务器返回结果来加密恶意数据，最终绕过解密算法，反序列化恶意对象执行命令。

01 常规解密流程分析


这里我们依然是使用DES加密算法来做，和AES是一样的，问题主要是出在CBC加密模式，使用了填充才会导致该问题。和加密算法无关，所以两个都可以用来做示例，不影响漏洞原理的理解。


首先我们还是来看一张图，看一下常规的解密流程，如图


这里我们可以看到，正常的解密流程是正向的，第一次通过密文块1解密，得到中间值，然后将中间值和初始向量iv异或得到明文分组块1。第二次解密，是对密文块2进行解密，得到中间值，然后将中间值和密文块1进行异或后得到明文分组块2。第三次解密，对密文块3进行解密，得到中间值，然后再将中间值和密文块2进行异或，得到最后一个明文分组3。


看完分析，我们可以发现，除了第一次解密是中间值和iv异或得到明文，其他的时候，都是将中间值和前一个密文块进行异或进而得到明文分组，以此类推，所以我们可以通过分析写出相应的解密测试案例。

02 加密一个数据块恶意数据


这个我在上一篇文章就有讲过，其实也不难理解，当只有一个密文数据块的时候，我们通过枚举iv的值来求得密文块的中间值。常规解密流程是中间值异或iv即可得到明文，但是想要串改密文解密结果，我们必须反其道而行之，通过我们想要解密的恶意数据异或中间值，就可以得到我们生成的恶意iv，因为解密是在服务端执行的，密文不变的情况下，中间值也是不会改变的，所以当我们修改初始iv为我们的恶意iv时，服务端就会将中间值和恶意iv进行异或，进而得到我们想要的解密结果。

首先第一个问题，如何生成多个恶意密文数据块？这个问题一开始困扰了我很久，因为人的主观意识就是，知道了第一块恶意密文是如何生成的，所以就会把第一块生成的经验带入下一次密文生成。


已知第一块恶意密文生成是通过原始密文快解密后获得中间值，然后将中间值和恶意明文数据异或，进而得到恶意密文块，那么第二块恶意密文快应该是由谁和谁异或来生成我们想要的恶意密文块呢？其实前面也分析了，肯定是要将中间值和第二块恶意数据异或来得到第二块恶意密文，可是我们这个中间值从哪来，由谁而产生的，我们并不是很清楚。

然后我又去看各种文章，关于如何通过padding oracle漏洞来生成我们自己的恶意密文，使其最终解密结果为我们预期的恶意数据。不看还好，越看越迷糊，不过也不是没有收获，至少知道了如何生成密文数据块。


这里我们再回顾一下上面关于解密的那张图，之前我们是从正向解密流程去分析的，现在我们需要转换下思路，逆向分析解密流程。首先，我们可以看到密文快3通过解密后得到中间值，然后中间值和密文快2进行异或，从而得到明文分组块3。这里用我们上面加密一个恶意数据块的思路去理解，我们依然是对密文快3进行解密得到中间值，但是我们中间值不是和密文块2进行异或了，而是要和恶意数据块进行异或，异或之后得到的是恶意iv，在这里可以理解为密文块2，相当于覆盖了原来的密文块2，这么说大家应该可以理解吧。然后我们要想使得第2个明文分组块解密结果为我们想要的数据，这时就得重复上一步的操作，对密文块2进行解密，注意！这时的密文块2可不是原来的密文块2了，是我们恶意数据和第1块密文的中间值异或得到的结果。所以我们应该解密的是异或之后的值，再通过枚举iv来得到该密文块的中间值，然后再将中间值和第2块恶意数据异或，来得到第1块密文，之后反求初始iv也是重复上面的步骤，将异或得到值作为密文去解密。


还有要注意的是，我们的完整密文是从后往前拼接而成的，密文块3为初始密文的密文块3，然后将密文块2再放在密文块3的前面，之后再将密文块1放置在密文块2的前面，最后再将iv放置在密文块1的前面，这个时候我们就可以得到完整的密文了。


这里说说我理解上的第二个坑吧，我通过上面的步骤，计算出了完整的密文，但是解密的时候，我代入得是生成初始密文的初始iv "12345678"，所以导致每次解密结果都为null，也就是解密失败，没有解密成我想要的值。


之后，我又去看了几遍网上的分析文章，才发现原来我理解错了，因为网上的文章都是以目标是一个服务端为前提，而且服务端接收到密文会将前8个字节作为iv，然后对8个字节后面的内容进行解密，所以我应该将完整的密文的前八个字节截取下来，作为解密时用的iv，再将8个字节往后的内容作为需要解密的密文，然后服务端key不变，这样子就可以将我们自己生成的恶意密文，解密成我们想要的内容了。

    public static byte[] encrypt(byte[] plaintext, byte[] key, byte[] iv) {
        byte[] ciphertext = null;
        try {
            SecretKeyFactory keyFactory = SecretKeyFactory.getInstance("DES");
            //创建密钥对象
            DESKeySpec keySpec = new DESKeySpec(key);
            SecretKey secretKey = keyFactory.generateSecret(keySpec);
            //创建iv对象
            IvParameterSpec ivParameterSpec = new IvParameterSpec(iv);
            //指定使用DES加密算法，CBC模式，PKCS5Padding填充方式
            Cipher cipher = Cipher.getInstance("DES/CBC/PKCS5Padding");
            //初始化cipher对象，Cipher.ENCRYPT_MODE代表这个cipher是用来加密的

            //加密
            ciphertext = cipher.doFinal(plaintext);
        } catch (Exception e) {
            e.printStackTrace();
        }
        return ciphertext;
    }

0x04 小结


其实shiro的padding oracle也正是利用了这个原理，来逆向生成恶意密文数据，只不过是转换了一个思想，我们自己写测试模型，是将iv和密文分开来的，而shiro则是将iv和密文拼接在一起的，然后加上rememberMe前缀，一起发送到服务器进行解密，服务器是会区分rememberMe前缀的cookie的iv和我们拼接的恶意密文的iv的，所以就会形成我们上面的测试结果，通过截取恶意iv来对恶意密文进行解密，最终得到的结果也就是我们想要的恶意数据，最后经过反序列化执行命令。
