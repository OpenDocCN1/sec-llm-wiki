Grim Finance 攻击事件分析

1. 前言

北京时间 2021 年 12 月 19 日，Grim Finance 官方称平台被黑客攻击并盗走价值超过 3000 万美元的代币。

2. 分析

攻击事件如下图所示，该次攻击事件的问题点在于 depositFor() 函数，攻击者利用该函数进行重入攻击。

2.1 基础信息

  • 攻击合约：0xb08ccb39741d746dd1818641900f182448eb5e41
  • 攻击 tx：0x19315e5b150d0a83e797203bb9c957ec1fa8a6f404f4f761d970cb29a74a5dd6
  • 漏洞合约：0x660184ce8af80e0b1e5a1172a16168b15f4136bf

2.2 流程

  1. 攻击者通过闪电贷借款 30 BTC 和 9200000 WFTM，并通过 PancakePair 将贷款得到的代币拿去添加流动性获得 0.0476 Spirit-LP。
  1. 攻击者将上一步获取的 Spirit-LP 质押后获得 GB-BTC-FTM（图中框出来的交易是多次重入后最后一次重入）。
  1. 攻击者通过重入漏洞多次调用质押函数进行质押获得 GB-BTC-FTM（攻击原因会在下面进行分析），一共进行了 8 次重入攻击。
  1. 攻击者将解除流动性获取 41 BTC 和 1280000 WFTM。
  1. 最后攻击者归还闪电贷借出代币和闪电贷手续费。

2.3 细节

该次攻击事件重点在于 GrimBoostVault 合约的 depositFor() 函数，其代码如下：

function depositFor(address token, uint _amount,address user ) public { // 质押 _amount 数量的 token 代币，将 LP 代币铸给 user

        uint256 _pool = balance();
        IERC20(token).safeTransferFrom(msg.sender, address(this), _amount);
        earn();
        uint256 _after = balance();
        _amount = _after.sub(_pool); // Additional check for deflationary tokens
        uint256 shares = 0;
        if (totalSupply() == 0) {
            shares = _amount;
        } else {
            shares = (_amount.mul(totalSupply())).div(_pool);
        }
        _mint(user, shares);
    }

合约的主要功能是在用户将 token 质押转入合约后，计算合约余额的差值，再将计算后的差值进行质押证明代币数量计算，并发送给用户相应的质押证明代币。

由于该函数 token 地址并没有做固定限制，也没有对该 token 进行校验，而 depositFor() 函数中会用到 token 合约地址中的 safeTransferFrom 方法，那么攻击者可以控制 token 合约地址，将 safeTransferFrom 方法改为再次调用 GrimBoostVault 合约的 depositFor() 函数，这样就可以进行多次重入攻击（可以在 Debug 中看到重入），在最后一次重入攻击时传入之前添加流动性获得的 Spirit-LP 进行正常的代币质押，这也就是上面流程中的第二步。也就是说第 8 次重入攻击是第 1 次正常执行流程（可以拿递归函数来理解），第 8 次重入代码执行完后执行第 7 次重入，以此类推直到第 1 次重入。

_pool 和 _amout 都由 balance() 影响，而前 7 次重入传入的 token 并不是代币地址，而是攻击合约地址，所以根据 balance() 函数的内容其值不会改变。

由于 8 次重入中 _pool 和 _amount 的值都没有变，而 shares = (_amount.mul(totalSupply())).div(_pool);，也就是说 shares 只受到 totalSupply 影响，而每次重入后再执行 5-14 行代码会导致 totalSupply 增加，这样 shares 的值也会随着每次的重入越来越大，即 totalSupply 增大使得 shares 增大，shares 增大又会使得下次的 totalSupply 增大，从而获得额外的 GB-BTC-FTM。

3. 总结

通过分析该次攻击事件，问题主要是在 depositFor() 函数传入的 address token 可控，导致攻击者可以多次重入造成合约的余额存在较大差值，从而 mint 过多的 shares。该合约如果要修复的话，可以将 token 写死在代码中，所以说在写智能合约时一定要对所有传入参数进行校验，否则很可能出现外部攻击。
