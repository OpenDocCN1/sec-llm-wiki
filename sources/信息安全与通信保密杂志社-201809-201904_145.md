摘要：目前网络上有海量的攻击流量时刻威胁着Web应用的安全。要想直接对攻击流量进行有效搜集并分析难度很大，而要想通过搭建靶机的方式来搜集也十分费时费力且效率低下。针对上述问题，采用符号执行技术，在开源符号执行引擎PyExZ3的基础上，运用循环优化方法和对符号执行基础类型的完善，弥补了PyExZ3的不足，使得改进后的原型系统能够高效可靠地对绝大部分基于Python的Web攻击脚本进行自动化分析。

**0 引 言**

随着网络技术及其应用的快速发展，Web应用在人们日常生活中扮演着越来越重要的角色，如购物、社交、银行服务、搜索等。但是，SQL注入、缓冲区溢出、文件上传、信息泄露、跨站脚本、越权访问等Web攻击对用户造成了极大的困扰。随着传统操作系统的日益成熟，应用漏洞成为了攻击者攻击的焦点，严重威胁Web应用的安全性。Web应用的安全性一直以来都受到安全从业人员的广泛关注，对Web应用的安全评估、Web应用防火墙（简称WAF）的研究也在不断发展\[1\]。但是，如何获取用于评估Web应用的安全性和验证WAF有效性的攻击流量一直困扰着广大安全研究人员。如果对受测试的Web应用/设备进行真实攻击，可能会留下后门，造成难以预计的不良后果；如果直接从网络中搜集，难度极大且存在大量噪声；如果通过搭建靶机的方式搜集攻击流量，费时费力，成本巨大，且同样要进行真实攻击，可能会对网络造成难以预计的影响。

  

针对上述情况，本文采用基于Python的符号执行引擎PyExZ3对Python Web攻击脚本进行动态分析，无需搭建靶机环境，无需进行真实攻击，就可以自动提取完整的Web攻击流量。PyExZ3是一款基于Microsoft开发的Z3 SMT实现的开源符号执行引擎，可利用动态符号执行技术对Python脚本进行动态分析。动态符号执行技术可以遍历脚本不同的分支，获得更多的行为特征。相对地，在使用符号执行遍历分支的过程中，可能会面临路径爆炸的难题，产生大量无效分支，导致迟迟难以发现目标分支。

  

因而，本文将首先对符号执行技术进行简单介绍；其次说明为应对路径爆炸问题做出的改进，以及对原有的PyExZ3符号执行引擎的改进；再次，介绍以改进后的原型系统作为工具，对Web攻击流量进行采集和分类的方法；最后，通过使用改进后的原型系统对Python Web攻击脚本进行动态符号执行分析，证明了开发的原型系统满足预设目标，实现了对Web攻击流量的高效采集和分类。

  

**1　背景**

**1.1　符号执行概述**

符号执行技术是在分析源代码的过程中将代码中的变量替换为符号值，模拟程序执行流程，通过构建单元代码的控制流图选择代码路径，当遇到分支语句时，提取并存储不同分支的约束条件，使用约束求解器求解进入某一分支所要满足的条件，最后根据路径调度算法对控制流图中的所有路径进行遍历分析。

  

自2005年以来，符号执行技术已经成为自动化测试领域的重要技术之一\[2\]。例如：贝尔实验室提出的一种自动化软件测试工具DART（Directed Automated Random Testing）\[3\]，大量用于软件测试、逆向工程等领域；伊利诺亚大学提出的单元测试工具CUTE（Concolic Unit Testing Engine for C），用于处理程序中出现的动态数据结构指针符号化的情况\[4\]；斯坦福大学实现的自动化软件测试工具KLEE及其前身EXE（Execution generated Executions）\[5\]，用于分析LLVM中间代码\[6\]。此外，还有加州大学伯克利分校的CREST、IBM的Apollo、加州大学圣芭芭拉分校的angr和Microsoft的PyExZ3等符号执行引擎。

  

上述的符号执行引擎可以分为三类：第一类是用来分析二进制机器码的，如angr；第二类是用来分析LLVM中间代码的，如KLEE；第三类是针对特定语言的专用符号执行引擎，如PyExZ3\[7\]。

  

**1.2　Python专用符号执行引擎PyExZ3**

PyExZ3是Microsoft开发的一款针对Python语言的开源符号执行引擎，包含函数加载模块、路径探索模块、求解器封装模块和基础符号类型模块。其中，求解器模块使用Microsoft研究院设计开发的Z3约束求解器\[8\]。PyExZ3具有不错的分析性能，同时也存在一些不足。首先，PyExZ3目前只能对整型变量进行符号执行，不支持对字符串等其他类型的变量进行符号执行；其次，PyExZ3的求解性能依赖于Z3求解器，但一些约束求解问题在当前计算理论发展的程度下无法求解，会产生一系列问题。目前主要关注的问题有：路径爆炸问题和约束求解问题。

  

路径爆炸问题。PyExZ3默认使用DFS路径搜索算法，容易产生路径爆炸问题。因为程序在每一个判断分支处都会产生两个不同的约束，类似树状结构，所以符号执行要探索的路径分支以指数级增长，尤其在遇到循环分支时，会产生大量分支路径，从而形成路径爆炸。路径爆炸对于内存有限的计算机设备而言，不可能遍历程序所有可执行路径，会导致程序代码覆盖率不足的问题。虽然目前已经提出了一些解决方案，如启发式函数算法、缓存中间结果、剪枝冗余路径等，但都不能从根本上解决路径爆炸问题。

  

约束求解问题。Z3求解器的约束求解效率决定了PyExZ3符号执行引擎的性能。随着程序结构和场景的日益复杂，求解复杂度不断上升。对于大规模的复杂约束求解问题，会给约束求解器提出很大的挑战，求解效率会大幅下降。同时，由于一些非线性约束求解问题的出现，求解器无法准确求解，导致求解失败。由于约束求解问题在理论上没有根本解决，故对于所有的约束求解器都存在这个问题，是当前符号执行发展的瓶颈之一\[9\]。

  

**2　改进PyExZ3符号执行引擎**

  

在对Web攻击流量进行采集的过程中，需要对字符串类型变量进行符号执行。所以，扩展了PyExZ3符号执行的基础类型。同时，针对它可能深陷循环而产生路径爆炸的情况，采用新型循环优化分析方法以提高其分析性能。本原型系统用于采集Python语言编写的Web攻击脚本所释放的攻击流量，会对Python脚本进行预处理，以优化原型系统对Web攻击流量采集的效率。

  

**2.1　扩展符号执行的基础类型**

PyExZ3目前只支持对整型变量进行符号执行，但PyExZ3基于的Z3约束求解器支持对整型、浮点型、字符串、数组、字典类型等变量进行符号执行。所以，对PyExZ3符号化类型的字符串集扩展，只需要探索字符串类型变量的约束条件集，交给Z3求解器求解即可\[7\]。

  

设计SymbolicStr类和Z3String类来实现对字符串类型的符号执行。对于字符串符号化处理主要包括三部分：对字符串长度有约束的情况、对字符串内容有约束的情况和对子字符串有约束的情况。SymbolicStr类中实现了对这三种情况的处理。首先，判断需要符号化的变量，如果需要符号化的变量是字符串类型，则通过SymbolicStr类对字符串符号化变量进行初始化，初始化为“0”；其次，使用ExplorationEngine类探索代码路径，通过Predicate类提取每一个判断分支的正反两个约束条件，然后通过Constraint类进行存储（Constraint存储了可以到达某一具体分支的所有约束条件）；最后，Z3String类通过继承Z3Expression类，将约束条件转化为Z3表达式，由PathToConstraint类交给Z3约束求解器进行求解。

  

其中，SymbolicStr类创建了符号化的字符串类型变量，并包含与符号化字符串处理相关的函数，如获取字符串长度函数getLength()、字符串分割函数split()和字符串中字符的替换函数replace()等。Z3String类继承了Z3Expression类，把符号化字符串类型的约束转化为Z3约束求解器可识别的表达式。针对字符串类型的符号执行框图如图1所示。

  

![](../Images/f9890d6e7f00d112ae719031186d7a52.png)

  

SymbolicStr类具有符号长度属性，可以根据路径条件的不同调整字符串长度。例如，if len(str)==5，将代码中长度相关的约束条件转化为一个操作数数量为1、操作符为“str.len”的expression类实例，判断语句根据长度属性会提取正反两个约束进行下一步遍历，同时原型系统也会动态调整符号化字符串str的长度。

  

SymbolicStr类对字符串内容约束的处理。Z3求解器包含了对符号化字符串内容的求解，所以只要转化并传递所有约束条件即可。

  

SymbolicStr类具有子字符串属性，利用split()可以分拆、保存、拼接原始符号化的字符串。例如：有str、str1和str2三个字符串，满足str=str1+str2，当遇到控制判断语句：if(str==“targetString”)，原型系统可以给出一个满足条件的解{a=“target”,b=“String”}，而不仅仅只是{c=“targetString”}。这种特性可以使原型系统的符号对象具有良好的传递性。

  

**2.2　非线性约束的循环优化方法**

当符号执行在遇到循环时，由于循环中包含符号变量，无法确定具体的执行次数。如果对于每一次迭代都生成两条路径，就会引起路径爆炸问题。目前，对于符号执行中的路径爆炸问题没有很好的解决方法。针对上述问题，研究人员尝试提出了多种解决方案，如基于路径分析的启发式循环检测算法，通过排除干扰路径来解决路径爆炸问题；通过设置循环次数上限的方式解决路径爆炸问题。PyExZ3是通过限制循环最大次数来解决路径爆炸问题的。这种方法比较粗暴，且依然会产生大量无用分支，因为这些分支依然会存在于待处理分支列表中。同时，由于设置了循环次数上限，也有可能导致符号执行结果的不精确。

  

上述第一种方法只有在符号变量的约束条件是线性时才有效，当符号变量的约束条件是非线性时候不能有效降低路径爆炸带来的影响；第二种方法比较粗暴，会损失精度。鉴于此，提出一种针对循环中出现非线性约束情况的优化方法。作为实际问题的抽象，以奇偶归一问题进行说明：

  

def test(x):

while(x>1):

    if(x%2==1):

            x=3\*x+1

        else:

            x=x/2

        return x

  

当程序执行到第2行，生成约束x＞1 ；在第3行遇到判断语句时，生成约束x>1&&x%2==1和x>1&&x%2!=1；以此类推，假设第4行的语句执行了a 次，分别为J1,J2,…,Ja ，第6行的语句执行了b 次，分别为K1,K2,…,Kb ，在第n 次执行循环时，其中一条路径约束为{xn-1>0}&&{xJ1%2==1}&&…&&{xJa%2==1}&&{xK1%2==1}&&…&&{xKb%2==1}。显然，这是一个非线性约束，约束求解器无法识别并求解，将堆积大量待求解约束，故当循环中遇到非线性约束时会产生路径爆炸问题。

  

在上述例子中，检测出约束条件是一个高次方程f(x) 。针对这种情况，可以采用牛顿法对非线性约束进行迭代拟合，将f(x) 在x=0 处泰勒展开：

取其中的线性部分，然后再继续迭代，过程如图2所示。

  

![](../Images/f5371b4298d3a13d2951cef902c93082.png)

  

依次在xk,xk+1,… 处迭代，其值就是符号变量在当前循环中的值。迭代次数越多越精确，但也会耗费太多时间，故可以设定最大迭代层数\[10\]。

  

**2.3　针对Web攻击流量采集的优化**

本原型系统的使用场景是分析Web攻击脚本。网络上的Web攻击脚本规范不一，很难用统一的标准来加载脚本的目标函数。针对这个情况，在对Web攻击脚本进行符号执行前，先对其进行预处理优化。优化主要集中在三个方面：调整符号执行变量、统一脚本函数入口和统一Python脚本语言版本。

  

2.3.1　调整符号执行变量

  

在Web攻击脚本中，有些情况是无法直接进行符号执行的。例如，通过构造请求来实现攻击，构造请求的变量不会出现在函数参数列表中，所以无法对其进行符号执行；有些变量虽然在函数的参数列表中，但是并不需要进行符号执行，如IP地址、端口号等变量。

  

针对这些情况，设计了调整符号执行变量的方法对脚本进行优化。

  

优化规则1：对需要进行符号执行但不在函数参数列表中的变量，首先删除函数体中该变量的构造代码，然后在函数列表中添加同名变量；

  

优化规则2：对不需要进行符号执行但却在函数参数列表中的变量，首先在函数参数列表中删除该变量，然后在函数体内或者函数体外（全局变量）构造同名变量的值；

  

优化规则3：对于其他不需要进行符号执行但依赖于外部交互的变量，首先删除函数体中该变量的构造代码，然后为同名变量指定一个值。

  

举例一个简单的POST请求，具体操作如下：

  

import sys,urllib,urllib2

def getDataFromPOSTRequest(url):

#构造POST参数

wd=input(“search word:”)

data=urllib.urlencode(\[(‘wd’,wd)\])

#构造request

req=urllib2.Request(url)

fd=urllib2.urlopen(req,data)

res=“”

#读取相应结果

while True:

    data=fd.read(1024)

    if not len(data):

        break

    res=res+data

\# do something with res

…

  

这个例子中，需要进行预处理优化的有如下几个变量：wd 、url 、req 、fd 、data 、res 。

  

（1）对于wd ，依赖用户输入，根据优化规则3，需要把这一行删除，然后指定一个wd 值；

  

（2）对于url  ，不需要进行符号执行但是在函数参数列表中，根据优化规则2，首先在函数参数列表中删除这个变量，然后在函数体内（外）构造同名变量的值；

  

（3）对于req  、fd 、data  ，fd  通过req  请求获得了一个类文件描述符，将内容写入缓存data data中，根据优化规则3，需要删除函数体中req  、fd  、data  的构造代码，并为其指定一个值；

  

（4）对于res  ，根据优化规则1，首先需要删除函数体中res  的构造代码，然后在函数列表中添加变量名为res  的参数。

  

经过预处理优化后的脚本如下：

  

import sys,urllib,urllib2

url=“http://www.baidu.com”

def getDataFromPOSTRequest(res):

wd=“aaa”

data=urllib.urlencode(\[(‘wd’,wd)\])

req=urllib2.Request(url)

fd=urllib2.urlopen(req,data)

#do something with res

…

  

通过预处理优化后，原型系统就可以在保留获取到的网络数据流的同时，对目标变量进行符号执行，以获取完整的网络流量。

  

2.3.2　统一脚本函数入口

  

Web攻击脚本由于规范不统一，原型系统无法准确获取脚本中的核心攻击函数，导致不能对其进行符号执行。因此，首先需要对脚本的核心攻击函数入口进行统一。目前采用的方法是对脚本进行扫描，依次寻找exploit()、run()和main()，将它们统一为exploit()。如果exploit()存在，则不做调整；如果不存在，查找是否有run()；如果run()存在，则函数名修改为exploit()，并把所有调用run()的地方进行替换；如果没有run()，就查找是否有main()；如果main()存在，则函数名修改为exploit()，并把所有调用main()的地方进行替换；如果没有main()则报错，转至人工查看。

  

2.3.3　统一脚本语言版本

  

本原型系统是用Python3实现。但是，在网络上用Python语言编写的Web攻击脚本中，有的用Python2实现，有的用Python3实现。两个版本的Python之间存在兼容性问题，导致原型系统无法对Python2编写的Web攻击脚本进行符号执行。针对这个问题，通过使用Python3的官方工具2to3将Python2脚本转化为Python3脚本。对于少数转化失败或者转化出错的Python2脚本，需转至人工查看原因。

  

**3　Web攻击流量的采集和分类**

  

利用上述原型系统对Web攻击脚本进行流量采集，同时根据各个攻击阶段的不同特征，对攻击流量进行分类，并存储入库。

  

**3.1　Web攻击流量的采集**

先将Web攻击脚本进行预处理，统一脚本语言版本，调整符号执行变量，统一函数入口，并把脚本中的IP地址和端口号设置成特定的值，便于之后的流量采集，然后通过流量的目的IP、目的端口、源IP、源端口进行过滤采集流量。因为在符号执行过程中会遍历代码的所有分支，所以会产生多次流量。针对这种情况，选取其中流量最多的进行采集。因为攻击失败后攻击脚本会直接退出，所以流量会比攻击成功的流量少。

  

**3.2　Web攻击流量的按阶段分类**

为了能够更细致地操控Web攻击流量，将其运用于网络靶场中，需要对Web攻击流量按阶段分类存储。

  

3.2.1　分类方法

  

在真实的Web攻击中，攻击过程大致可以分为4个阶段：检测、扫描、攻击、驻留。

  

根据上述的四个攻击阶段，需要先提取各个阶段的Web攻击流量特征，然后通过这些流量特征对采集的Web攻击流量按阶段分类。目前，主要的流量识别技术有以下三类\[11\]：基于深层包检测（Deep Packet Inspection，DPI）的流量识别技术、基于行为特征的流量识别技术和基于流特征的流量识别技术。这三类流量识别技术都只能针对协议进行区分，但在本项目中，仅根据协议的不同并不能对流量进行有效分类，如图3所示。

  

![](../Images/2d84b5b716e5362bba867887e415afdb.png)

  

可见，只是对协议进行区分显然不行。针对这种情况，结合实际使用场景，提出流量的尺度特征分析和流量的连接特征分析，从而对不同阶段的流量进行区分，具体执行流程如图4所示。

  

![](../Images/b02cb83951ff9c9c52262acdf795e1f5.png)

  

（1）流量的尺度特征

  

网络流量的尺度特征最早是用来作为DDos攻击的检测。然而，由于网络业务流量种类的繁多，网络流量的尺度特征检测一直存在争议。但在本项目中，只针对Web攻击流量的四个阶段的尺度特征进行提取，很好地规避了上述问题。

  

网络流量在总体分布和包长分布上具有明显特征。在总体分布上，它具有的自相似特征和多分形特征已经得到研究者们的普遍认可；在包长分布上，它的包长分布呈现出明显的双峰特征。在网络攻击的不同阶段，攻击流量包长将发生一定变化，所以可将流量的尺度特征作为不同阶段的流量特征的表现之一\[12\]。

  

根据研究表明，网络流量在不同的分析尺度上体现出了不同的行为特征。在大时间尺度下（1 s及以上）表现出平稳自相似特征，在小时间尺度下（1 s以下）的特征还存在争议，但多数研究表明是呈现长相关特性（自相关过程具有长相关特性）。目前，自相似模型是最能描述网络流量长相关的模型。自相关模型是指在从微秒到小时的范围内，流量由一系列正常流量和一系列突发期流量组成。突发期是由一些突发的子周期组成，而这些子周期又由更小的突发子周期组成。数据流在不同时间尺度上都表现出相似的特征\[13\]。在本项目中，虽然时间尺度属于大时间尺度，但由于流量分布较为稀疏，因此采用小时间尺度的分析方法，采用长相关特征分析，使用自相似模型。检测阶段通常是ping包，包长较短；扫描阶段需要获取目标主机上安装的服务及服务版本号，所以需要提交表单，故包长比检测阶段长；攻击阶段通常要添加有效载荷，包长较长；驻留阶段通常是远程执行代码，故包长比攻击阶段短。具体地，把检测阶段流量和攻击阶段流量作为“正常”流量，把扫描阶段流量和驻留阶段流量作为“突发期”流量，使用一阶分形进行检测。

网络流量的尺度特征最早是用来作为DDos攻击的检测。然而，由于网络业务流量种类的繁多，网络流量的尺度特征检测一直存在争议。但在本项目中，只针对Web攻击流量的四个阶段的尺度特征进行提取，很好地规避了上述问题。

（2）流量的连接特征

  

通过对实际流量的分析发现，在不同阶段，网络流量的连接数也有一定的特征。在检测和扫描阶段，需要对目标系统的IP地址段、开放端口、所用的服务类型、服务版本信息等进行尝试连接和扫描因此在这两个阶段会有很多发包，但是收包会很少。在攻击和驻留阶段，通过前期检测和扫描阶段，已经获得了攻击目标和攻击点，所以对于每一组连接，发包和收包基本都是对应的。所以，通过对网络流量中源IP地址、目的IP地址、端口号等信息的分析和过滤，可以获得流量的全部连接特征，得知哪些流量是属于前期的尝试扫描流量并没有收到相应的回应流量包，哪些流量是属于后期的执行攻击流量能够收到相应的回应流量包。

  

根据流量的连接特征分析，可以把检测、扫描阶段和攻击、驻留阶段区分开，再通过流量的尺度特征分析进一步把检测和扫描阶段、攻击和驻留阶段区分开，并打上标记。

  

3.2.2　存储入库

  

根据上述的对Web攻击脚本的预处理优化、符号执行和对流量的按阶段分类，获得了Web攻击脚本的名称、攻击类型、对应的漏洞编号和各个阶段的流量。采用MySQL数据库存储这些信息，其中对于各个阶段的流量只保存具体的流量信息并保证其时序性，对于流量之间的时间间隔信息并不保存，因为时间间隔存在一定的随机性，会随着网络状况的变化而变化。具体过程如图5所示。

  

![](../Images/74a4c622d469cfab47287f4f98cf15e8.png)

  

通过使用OSX Sierra系统下的MySQL管理工具Sequel Pro对MySQL数据库进行管理，使用的数据库版本为MySQL 5.7.21，创建表名为WebAttackFlow的数据表：

  

CREATE TABLE \`WebAttackFlow\`(

\`id\` INT NOT NULL AUTO\_INCREMENT,

\`script\_name\` VARCHAR(100) NOT NULL,

\`attack\_type\` VARCHAR(1000) NOT NULL,

\`vulnerability\` VARCHAR(100) NOT NULL,

\`testingFlow\` VARCHAR(5120) NOT NULL,

\`scaningFlow\` VARCHAR(5120) NOT NULL,

\`attackFlow\` VARCHAR(5120) NOT NULL,

\`residentFlow\` VARCHAR(5120) NOT NULL,

PRIMARY KEY(\`id\`)

)ENGINE=InnoDB DEFAULT CHARSET=utf8;

  

其中：id为编号，是自增量；script\_name为脚本名称；attack\_type为攻击类型；vulnerability为相应漏洞编号；testingFlow为检测阶段流量；scaningFlow为扫描阶段流量；attackFlow为攻击阶段流量；residentFlow为驻留阶段流量。

**5　结　语**

  

本文基于PyExZ3提出了一种能够对Web攻击流量进行高效采集和分类的方法。原型系统在PyExZ3基础上通过对基础符号类型的扩展、对非线性约束循环的优化和针对Web攻击脚本的预处理优化三种方式，实现了对攻击流量的采集，解决了传统Web攻击流量采集过程中出现的诸多问题，如搭建靶机环境费时费力，无法控制对靶机进行攻击后产生的潜在不良后果等。同时，根据Web攻击不同阶段的流量特征，实现了对攻击流量的高级分类，以获取Web攻击在不同阶段的流量信息并加以存储。后续需要进一步分析不同阶段的Web攻击流量的特征，以提高对攻击流量高级分类的准确性，同时要对更多的基于Python的Web攻击脚本所释放的攻击流量进行采集和分类，为之后搭建网络靶场打下基础。

  

本原型系统只能针对Python语言编写的Web攻击脚本所释放的攻击流量进行采集和分类，不适用于其他脚本语言。针对其他脚本语言的符号执行功能，不是扩展本原型系统就能够完成的，需要针对特定语言另行搭建专用的流量采集分类系统。因此，完善对多语言的支持也是后续工作的努力方向之一。
