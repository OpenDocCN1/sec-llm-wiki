【网安学术】基于KEELOQ的RKE系统软件设计及遥控不灵敏分析

摘要：介绍了RKE的系统架构和KEELOQ数据加密、解密的具体过程，在此基础上设计了一套安全有效的通信协议，并设计出能够满足性能要求的发送端和接收端软件。发送端对前导码、同步头、64 bit数据、停止位和防护周期进行编码发送，接收端则根据接收到的数据解码验证。在对设计的RKE系统进行实车验证的过程中发现，设计存在遥控不灵敏的问题。于是，运用鱼骨图分析法找出出现问题的可能原因，并对这些可能原因进行验证。通过大量实测数据波形分析找到了根因，并提出了延长前导码和修改同步头的方案，最终解决了遥控不灵敏的问题。

0 引 言

车辆远程遥控进入系统（Remote Keyless Entry 以下简称RKE）作为汽车的标配，不仅给用户带来了方便，还关系到汽车的安全。RKE采用任何人都可以使用的公共信道高频信号进行数据传输。这种信号是公开的，可能被截获[1]，因此要求每次发出的编码信息不同，无规律可循。本文采用的KEELOQ滚动码是一种抗扫描、抗截获、多变化、安全性高的新型加密技术，安全可靠[2-3]。同时，根据发送端和接收端设计软件，针对RKE系统中出现遥控不灵敏的问题进行分析和解决。


1　RKE系统架构


汽车RKE系统包含了遥控发射和遥控接收两部分。遥控接收部分在车内部，遥控发射端位于遥控钥匙内。通常的RKE的工作方式如图1所示。用户按下钥匙扣上的按钮开关即可触发系统工作，唤醒RKE钥匙扣内部的CPU，CPU则发送数据流到射频（RF）发射机。数据流通常包括前导码、同步头、命令码和滚动码等信息，采用用户自己定义的发送速率发射出去。在车内的RKE射频接收机捕捉射频信号并解调，传送数据流给CPU，由CPU对数据进行译码并发送指令到对应指令模块做出对应的动作。



2　KEELOQ加密技术研究


2.1　KEELOQ的核心组成元件


2.1.1　制造商代码


制造商代码用于产品的辨别，由制造商自行决定此代码（不可泄露的原始密码）。遥控器的制造商代码必须与接收解码器相同。不同的制造商拥有不同的制造商代码。


2.1.2　序号


每一编码IC或遥控器的序号均不相同，用来识别遥控器与接收器之间的关系。即使使用者同时有两支遥控器来控制同一接收器，其序号也不相同（但制造商代码必须相同）。


2.1.3　编码密码


利用制造商代码及序号产生8 Byte的编码密码，将这8 Byte的编码密码烧录在芯片内部的EEPROM中。这8 Byte的编码密码是用来产生跳码的密码。


2.2　KEELOQ运算规则


KEELOQ算法的核心思想是用8 Byte编码密码和4 Byte（4 bit按键值、16 bit同步计数值、10 bit识别码和2 bit溢出指示）明文加密得到4 Byte密文，或者用8 Byte编码密码和接收到的4 Byte密文解密还原出原4 Byte明文。在KEELOQ算法演算过程中，4 Byte明文y31～0和4 Byte密文y31～0会存储在数据寄存器中，8 Byte密钥k63～0则存放在密钥寄存器。


KEELOQ数据加密过程模型图，如图2所示。首先定义一个非线性表，这个非线性表有5 bit输入码，1 bit输出码。在4 Byte明文中，取5 bit数据——y31、y26、y20、y9、y1，通过NLF（Nonlinear Logic Function）运算产生一个输出码，如式（1）所示。输出码与明文中的y16、y0以及编码密码中的k0进行异或运算后，生成1 bit加密数据码。每生成1 bit加密数据码，明文中的数据右移1位，加密数据码作为明文移位的输入，编码密码则循环右移1位。重复上述步骤528次后，得到4 Byte的输出密文。数据解密的过程和加密过程类似，这里不再赘述。




2.3　KEELOQ实现机制


采用KEELOQ方法实现数据编码和解码，其通信过程需严格按照下述过程进行。首先，要求编码端和解码端都要有非易失性存储空间，以存储8 Byte密钥（用于编解码，可编程且不被发送不可泄露）、28 bit序列号（用于区分不同的编码端）、16 bit同步计数值、10 bit识别码和4 Byte种子码（安全模式下用来生成密钥）。


当用户有按键操作时，KEELOQ编码端将4 bit功能键、10 bit识别码、16 bit同步计数值和2 bit溢出位组合成4 Byte明文，按照图2的NLF运算规则加密成4 Byte密文，再加上4 Byte固定码（28 bit序列号、4 bit功能键），组合成一组8 Byte的编码数据，然后经PWM调制发送出去。密钥的组成如图3所示。



为了增加安全性，需要引入额外的动态信息作为加密的输入。一般RKE系统都使用同步滚码机制作为动态密钥。这个同步滚码就是一个按键的计数值，每次按键计数加1。这样每次加密的数据都可以保持动态滚动变化[4]，使得每次发送的4 Byte密文都是唯一的、不规则的且不重复，故称之为滚动码，以有效防止密码捕捉和密码拷贝。由于8 Byte的编码组合达到264=1.84×1019，因而可以有效防止密码扫描。


解码端接收到8 Byte密文数据后，首先匹配编码端和解码端的28 bit序列号一致后，按照KEELOQ解码运算规则还原出4 Byte明文，再校验明文中的识别码和功能键是否正确，最后判断同步计数值是否合理增加。确认成功后，根据功能键定义，控制相应执行机构动作。


3　软件设计


3.1　发射端软件设计


发送数据采用曼彻斯特编码方式。在曼彻斯特编码中，每比特的中间有一个跳变，位中间的跳变既作时钟信号，又作数据信号，从低到高跳变表示“0”，从高到低跳变表示“1”[5]。


本文软件设置每比特数据的周期为600 μs，占空比为50%，RF数据内容如图4所示。每次按键会发送4帧数据，每帧数据由前导码、3 ms低电平同步头、8 Byte有效数据（含命令码+ID+滚动码+4 Byte加密生成的校验码）和帧间防护周期组成。前导码为8 Byte的0x55。为增加第一帧唤醒接收器的概率，第一帧的前导码需要发送17 Byte的0x55。 



对于发射模块软件，当发射端MCU检测到有按键按下时，则系统被唤醒，并把当前的遥控按键值、滚动码值、序列号存储下来；当300 μs定时中断到来时，就对存储EEPROM中的按键值、滚动码值、序列号和编码密码进行KEELOQ加密生成32 bit密文，并依次发送前导码、同步头、64 bit数据、停止位和防护周期。发送完毕后，同步计数值加1同时关闭射频发射器，系统重新进入睡眠模式。具体软件框图如图5所示。 



3.2　接收端软件设计


为了保证系统有较小的静态电流，接收端绝大部分时间也处在睡眠状态。BCM每隔100 ms使能RF数据接收端6 ms，检测是否有遥控命令到来。当接收到一个有效的射频信号时，射频接收器置位唤醒标志位唤醒CPU，依次接收同步头和64 bit数据。CPU分析数据，解密接收到的数据，验证数据的合法性。如果合法，则执行相应的动作；不合法，则不予理睬。在数据接收过程中，只要发现数据不正常，就回到睡眠模式。整个接收模块的状态迁移、迁移条件分别如图6和表1所示。




在整个RF状态迁移图中，S2和S5的软件设计较为复杂，下面以S2和S5的软件设计为例来做说明。


S2为验证前导码函数，流程如图7所示。当系统在睡眠状态时，RF_ON会每隔100 ms打开一次接收数据，开启时间为6 ms。整个检测函数由底层50 μs定时中断调用。当RF_ON被打开时，数据进来会有一定的延时，通过示波器的波形分析得知延时时间在1.8 ms左右，故软件在分析数据时做了2 ms的延时处理，之后设置 ，因为 即可开始前导码波形检测。前导码的周期为600 ms，占空比为50%，外界环境可能会对其波形有一定的干扰。为了提高系统的容错性能，允许前导码波形有一定的畸变，即解析出来的半周期波形在200～400 ms内，整周期波形在400～800 ms内都判定为正常。当接收到4个周期正常波形的前导码时，认为前导码有效，有遥控命令进来，MCU被唤醒，退出休眠状态。

4　试验与结果分析


RKE在设计时要求的有效距离为30 m。实车测试发现，RKE在要求的有效距离内存在无法唤醒BCM或唤醒BCM但不执行相应命令的情况。虽然这种现象在测试过程中只是偶尔出现，但说明系统在设计上存在不足。下面针对这一问题做详细的分析验证。


4.1　原因分析


RKE作为BCM的一个重要模块，其设计制造较为复杂。图9的鱼骨图从RKE的设计、生产、测试和工作环境等环节，列出了可能会造成遥控不灵敏的因素。经过逐一的确认排查，最终确定4个可能影响因素：（1）RKE与BCM唤醒周期匹配不佳；（2）同步头数据错误；（3）天线焊接露出PCB长度；（4）RF模块接收数据不佳。 



4.2　原因验证及改善


4.2.1　RKE前导码与BCM唤醒周期匹配不佳


当RKE无法可靠唤醒睡眠状态下的BCM时，很可能是前导码不能被正确接收。用示波器分别测试发射器数据发送脚和接收器数据接收脚波形，结果如图10所示。可以看出，发送的前导码和接收的前导码均没有被干扰，理论上可以可靠唤醒BCM，与实际测试的遥控不灵敏不符。所以，可以确定不是前导码数据被干扰的问题。

 


BCM睡眠时每100 ms扫描一次唤醒源，每次扫描时间为6 ms，如图11所示。当检测到有唤醒源时，则结束睡眠；否则，继续睡眠模式。RKE作为BCM的唤醒源之一，在6 ms的唤醒扫描时间内，当检测到连续4个周期600±200 μs，占空比为50±16.67%的RKE前导码时，就唤醒BCM。



提高可靠性有两个方案。方案一是将BCM睡眠唤醒周期从106 ms修改为81.6 ms，前导码可以覆盖整个睡眠唤醒周期，保证每次100%唤醒，但这将导致BCM睡眠时的静态电流增加。方案二是将RKE发射端前导码时间增长至106 ms，其后果是RKE使用者可能会感觉到BCM反应有延迟，因为RF是在接收完前导码后才处理具体的命令数据。


当汽车停止工作时，有些电子设备仍然在工作，只是进入了睡眠模式消耗较少的电流，这个电流称为静态电流。静态电流较大时，消耗的能量多，容易造成蓄电池亏电发动不了车辆。因此，汽车上的每一个电控单元又有严格的静态电流限制。本BCM系统允许最大静态电流为8 mA。当睡眠唤醒时间从106 ms缩短到81.6 ms时，静态电流为9.7 mA，超出了规定值。静态电流增大是客户比较不能接收的，而增长前导码没有带来明显的延时感。因此，最终选择方案二解决RKE唤醒不灵敏的问题。优化后的前导码波形如图12所示。



4.2.2　同步头数据错误


以上分析解决了RKE不能可靠唤醒BCM的问题。实际测试中还发现，有时RKE唤醒了BCM，但是BCM没有执行相应的动作，即前导码后面的数据不能被正确解析。通过大量的测试发现：（1）接收的数据3 ms低电平的同步头经常会受到外界干扰，如图13所示，同步头中含有干扰杂波。（2）同步头后面的第一个比特数据占空比失真，如图14所示。在一个比特周期600 μs的数据中，曼彻斯特编码方式的占空比为50%，软件解析数据时对高、低电平的容错为±100 μs，即认为高、低电平在200～400 μs范围内为正常数据，可以被解析，否则放弃该帧数据，重新进入睡眠模式。由图14可知，低电平为160 μs（小于200 μs），导致数据无法被解析。 




曼彻斯特码在传输代码信息的同时，也将时钟同步信号一起传输到对方。每位编码中有一跳变，不存在直流分量，因此具有自同步能力和良好的抗干扰性能。同步头没有设置为曼彻斯特码，而是设置为3 ms低电平，主要目的是区别前导码和命令数据部分，被干扰的部分刚好就是同步头和其后的第一位数据。为了使数据不被干扰，同步头也采用曼彻斯特编码方式。考虑到同步头要有较好的识别性，所以将同步头数据设置为0xaa55，对应二进制数为1010 1010 0101 0101，如图15所示。

 


4.2.3　天线底部露出PCB长度


天线焊接露出PCB长度设计理论要求不大于3 mm，但在实际生产中并没有管控，导致天线残桩长度不一致，如图16所示，天线残桩大于3 mm。天线残桩高度须越短越好，因为PCB板底部的钣金地平线可以有效吸收无线波，造成信号损失。另外，残桩越长，离车上固定BCM的钢板筋越近，如图17所示，对信号的屏蔽作用就越强，可能会影响遥控距离。




选取几个接收不灵敏的BCM，改变天线残桩长度进行验证测试，结果如表2所示。



从表2可以看出，对于同一个BCM，当天线残桩变短后，遥控距离会有所提升。但是，测试发现依然存在遥控不灵敏的现象。所以，天线残桩不是导致问题点的根本原因。然而，这次对比实验提醒设计人员，在以后的生产中要严格管控天线残桩长度，以提高RKE遥控距离的一致性。


4.2.4　RF模块接收数据不佳


在遥控钥匙出现不灵敏时，通过接收器芯片上的RF_Data引脚记录数据波形，发现RF模块接收的数据不佳，如图13、图14所示。同步头和其后一个比特数据出现破码，很可能是外部干扰信号造成的。发射器将RF信号转换为声表面波，在基片表面上传播，经过一定延迟后，接收器将声信号转换为电信号输出。滤波过程是在电到声和声到电的转换中实现的，而声表面波（SAW）滤波器利用压电单晶的压电效应和逆压电效应，实现声学信号和电学信号间的转化[6]。所以，可以在RF接收端增加SAW（Surface Acoustic，Wave）滤波器过滤杂波，但会增减设计成本。考虑到增加前导码时间和优化同步头已经解决了遥控不灵敏的问题，是否采用增加SAW滤波器的方案，需依据具体情况具体分析。


5　结　语


RKE系统设计过程较复杂，影响因素众多，需要一定的技术积累和沉淀。本文通过对

KEELOQ加密技术的分析，给出了系统密钥的产生和解码过程，具有保密性高、使用方便和成本低的特点。针对所设计的RKE系统出现遥控不灵敏问题，先通过鱼骨图分析法列出所有可能影响因素，再通过初步确认分析找出最可能的几个影响因素，然后对这些因素进行详细实验验证。记录下遥控不灵敏时的数据波形，通过对这些数据波形的分析找到根本原因，并提出相应的改善措施：（1）延长前导码时间，使之和BCM唤醒周期匹配，确保RKE在设计的有效范围内能可靠唤醒BCM；（2）同步头数据由3 ms低电平优化为0xaa55，提高RKE系统的抗干性能，减少发送的数据被外界干扰导致破码的可能，使数据能被正确解析。实践表明，以上两个方案最终解决了遥控不灵敏问题。
