**智能家居系统中的不同实体之间的通信研究**

**—USENIX Security 2019论文解读**

作者：绿盟科技格物实验室 张星

论文标题：  

Discovering and Understanding the Security Hazards in the Interactions between IoT Devices, Mobile Apps, and Clouds on Smart Home Platforms

论文作者：

Wei Zhou, University of Chinese Academy of Sciences; Yan Jia, Yao Yao, Lipeng Zhu, Le Guan, Yuhang Mao, Peng Liu and Yuqing Zhang

相关链接：

https://www.usenix.org/conference/usenixsecurity19/presentation/zhou

**1\.  摘要**智能家居系统一般可以看作由三个实体组成，设备、云端和APP，三者之间两两可以通信，由于其通信在大多数时候都是处于加密状态的，并且不同实体之间的交互也较为复杂，所以在此之前，并未有对于这些实体间的交互的系统性研究。研究人员更多关注于固件、隐私保护、认证、权限模型等方面的研究，在交互方面，只有对于三星SmartThings平台的研究，也并未推广到其它的平台。论文作者对5个广泛使用的智能家居平台进行了研究，包括三星SmartThings、TP-LINK KASA、小米米家、阿里Alink和京东Joylink。通过固件分析、流量劫持、黑盒分析等技术，对智能家居系统的不同实体之间的交互细节进行了分析。结合分析的情况，推测出了三个实体的状态转移图，三个实体的不同状态可以组成一个三元组。作者对其中的不同状态组合进行了研究，通过模拟真实设备与云端通信，对可能存在的问题进行了验证。

作者发现智能家居平台并没有在实体的状态转移时进行严格的权限验证；三个实体在有些时候可能会处于非法的状态组合，有可能带来一些风险；云端对于交互请求的权限检查不够充分。而这些情况，导致智能家居平台可能存在5大风险：

**( 1 ) 敌手可以远程用一个自己控制的虚拟设备替换受害者的真实设备。**

**( 2 ) 敌手可以远程控制受害者的真实设备。**

**( 3 ) 敌手可以通过虚拟设备远程解除一个授权用户和真实设备的绑定关系。**

**( 4 ) 敌手可以利用虚拟设备误导云平台，占用还没有被售出的真实设备的身份，将其绑定到敌手的账户，当用户和真实设备进行绑定时，由于设备已经处于绑定状态，则用户绑定失败。**

**( 5 ) 敌手可以通过虚拟设备发送升级请求到云端，从而规模化获取设备固件。**

这些风险想想有些“可怕”，作者是如何做到这些的呢？下面让我们来为您一一揭晓。

**2\.  智能家居平台介绍**首先，我们来系统了解下智能家居平台。图 2.1 是一个典型的智能家居平台的架构，包括设备、云端和APP三部分。设备又可以根据组网形式分为两类，第一类是直接与云端相连的设备，如智能电视、智能音箱等，它们可以通过WiFi接入家庭宽带从而入网；第二类是一些低功耗的设备，如门禁传感器等，它们通过ZigBee、蓝牙等协议与一个网关相连接，而网关通过WiFi接入家庭宽带从而入网。论文主要关注第一类设备。

云端按照业务功能可以分为三部分，第一部分是设备身份管理模块，用于对设备的身份进行管理，比如设备ID的生成、设备与用户的绑定关系等等；第二部分是设备控制模块，用于接收来自APP的控制指令，并下发到相应的设备；第三部分是家庭自动化模块，用于执行一些预置的条件触发操作，如温度传感器发现室内温度高于30摄氏度，自动下发打开空调的命令等。

![](../Images/01d40153060c3840a367dc97a47e7b81.png)

图 2.1  智能家居平台架构

在设备的正常使用中，每个设备都会有一个唯一性的身份标识信息，我们将其称之为设备ID（uuid）。通过对五大智能家居平台的研究，作者又依据设备ID的生成方法不同，将这五大平台分成了两类，如表 2.1 所示。

Type I平台：在设备注册环节，通过云端产生设备ID，并发送给设备，由设备将其存储起来。在设备绑定和解绑操作中，设备的权限检查由云端完成。

Type II平台：设备ID通过硬编码的方式在设备出厂前由厂商预置到设备中，授权检查由设备执行，当设备向云端发送设备绑定和解绑信息时，云端直接执行。注意，这样的设计蕴含了一个假设，厂商认为，真实设备不会“骗人”，设备ID“看起来”是一串很长的乱码，无法被攻击者伪造，所以默认为设备发送的信息都是真实的。在本文之前，这样的假设看起来也是合理的。

**3\.  威胁模型和可行性分析**

3.1**威胁模型**

敌手的目标是利用不同实体交互中的设计漏洞来控制设备或者监控/操作来自设备的数据。论文假设敌手有能力搜集交互必备的信息，包括设备身份信息和合法性信息，如表 3.1 所示。针对不同的平台，搜集这些信息的难度也有差异。对于Type II平台，假设敌手可以在攻击前能够本地访问到受害者的设备，而对于Type I平台，则不需要这样的假设。

3.2**可行性分析**

下面，我们来分析下搜集设备身份信息和合法性信息的可行性。

设备通过设备ID来进行唯一性标识，因此，如果要通过虚拟设备来模拟真实设备，首先需要获取受害者的设备ID。对于Type I平台，设备ID由云端生成，经作者验证，得出了设备ID取决于设备身份信息的结论，如表 3.1 所示，敌手需要将所需的身份信息搜集完整。对于Type II平台，设备ID硬编码在受害者设备中，因此，敌手需要本地访问到受害者设备才有可能获取设备ID。虽然这个假设看起来很强，但是，一旦硬编码的设备ID被泄露，受害者设备将会在未来一直存在被远程攻击的风险。另外，一些平台还会使用合法性信息作为附加的认证需求。

根据这些信息获取方式的不同，作者将其分为三类。

**公开信息（P）：**这类信息包括设备型号、设备芯片号（CID）等信息。作者还发现，有些平台的合法性信息是不同设备共享的，例如，阿里的Alink平台，合法性信息由两个看似机密的字符串组成，称为Key和Sign，但是这样的信息在阿里和合作制造商的GitHub都可以找到。

**可猜测信息（G）**：这类信息可以通过暴力破解的方式进行猜测，比如MAC地址。MAC地址的前三个字节标识制造商，通常是固定的，而制造商一般会分配一段连续的MAC地址给特定型号的产品，因此，可以通过对后三个字节遍历来发现更多的设备。另外，如果敌手在受害者设备所在的局域网中，可以通过嗅探的方式获取设备的MAC地址。

**硬编码信息（H）：**这类信息被硬编码到Type II平台的设备中，是一长串看似随机的字符串，通常难以预测。敌手需要本地访问到受害者设备才有可能获取到这样的信息。在实际场景中，这样的可能性也是存在的，比如设备有可能被二次出售，自如、Airbnb等租房平台提供的房屋中如果存在这样的设备，也是有可能被敌手访问到的。这些信息不一定需要通过对设备拆解、固件提取分析才能获取，比如在设备发现阶段，设备ID有可能在设备和APP之间传播；设备ID有可能存储在APP的日志中等。

**4\.  分析方法**为了保护用户隐私，智能家居平台通常会对不同实体之间的通信进行加密。因此，本研究最关键的内容是对通信的解密，只有这样，才有可能研究不同实体之间的交互。**Cloud-APP通信：**云端和APP之间的通信可以通过中间人攻击来解密。中间人攻击的前提是需要用敌手证书来取代云端的证书。经过对多个APP的分析，作者发现APP通常将云端证书以硬编码的方式存储在APK文件中，并没有借助Android的可信存储功能。当替换APK文件中的硬编码证书后，由于完整性检查失败，会导致APK无法运行。作者的解决方案是，通过root其手机，安装了Xposed（https://github.com/Fuzion24/JustTrustMe）。Xposed可以hook证书检查函数，从而在不破坏APP完整性的前提下动态改变证书。

**Device-APP通信：**经对多个APP进行分析，作者发现，JoyLink和米家使用一个对称加密算法来保护设备和APP之间的通信。通过分析APK文件，可以提取出通信密钥。三星SmartThings在设备和APP之间也采用TLS的通信方式，可以使用解密云端和APP通信的方法。

**Device-Cloud通信：**设备和云端通过TLS通信。作者对设备固件进行了静态分析，发现，单纯替换云端证书不可行，会导致固件的完整性检查失败。经过分析，作者发现大部分设备的完整性检查是通过CRC实现的，因此，在更新了CRC的值后，固件成功启动。

具备了前文所说的基础，之后就是模拟设备与云端进行通信，进行一些测试了，比如表 3.1 中的设备身份信息和合法性信息，就是通过测试得到的。具体而言，作者主要进行了三方面的测试：

**( 1 ) 每个实体是否在维护一个状态机；**

**( 2 ) 三个实体的状态三元组是否一直保持合法状态；**

**( 3 ) 认证所涉及的参数。**

由于已经对不同实体之间的交互进行了解密，对于交互的模拟则变得较为容易了。对于提供设备侧SDK的平台，如三星、京东和阿里，可以直接借助SDK，调整相关参数实现对于真实设备的模拟。对于使用私有SDK的平台，如小米和TP-LINK，则需要分析清楚交互流程，然后写代码实现了。

5\.  发现的设计缺陷

利用上文提到的分析方法，作者共发现了四类设计缺陷，如图 5.1 所示。

**F1：Insufficient State Guard。**作者发现这三个实体并没有正确实现状态机机制，例如，当云端处于状态4-运行状态（图 2.2 ）时，理论上来讲，其只应该接受状态更新请求和设备解绑请求，但是，作者发现其同样可以接受其它类型的请求。根据请求的不同，这一缺陷又可以细分为三类。

**F1.1：本缺陷针对Type I平台，**在获取到相关的设备身份信息后，敌手可以借助虚拟设备将注册请求发送给云端，云端会返回相应的设备ID。

**F1.2：本缺陷针对Type II平台，**敌手可以借助虚拟设备发送设备绑定请求给云端，从而实现敌手账号和受害者设备的绑定。在Type II平台中，设备绑定请求由设备发送，云端无条件接受。

**F1.3：即便云端处于状态4-运行状态，**云端也可以接受设备登录请求。这个是缺陷F3的前置条件。

**F2：非法的状态组合。**作者发现三个实体有时会处于意想不到的非法状态组合。例如，理想情况下，当用户不再使用一个设备后，他/她应该复位和解绑设备，从而使得三个实体都恢复到初始状态。然而，对于Type I平台来说，如果用户在解绑设备时，不对设备进行复位操作的话，设备与云端的连接将会继续保持，作者将这样的设备称为dangling设备。这时，由于云端位于状态1-等待设备注册状态，如果敌手远程发送一个设备注册请求，云端进入状态2-等待绑定状态，敌手继续发送绑定设备请求，云端会接受该请求，从而进入状态4-运行状态（状态3-等待设备登录状态会被跳过，因为受害者的设备和云端一直处于连接状态）。至此，敌手可以通过云端发送控制命令给设备了。

**F3：未授权设备登录。**云端可以接受虚拟设备登录请求，从而实现虚拟设备和受害者的连接（经由云端），之后，敌手可以借助虚拟设备看到受害者的设备使用习惯，甚至可以伪造数据给受害者。

**F4：未授权设备解绑。**理想情况下，只有设备的所有者才能够解绑设备。当解绑操作来自APP时，即对应这种情况。但是，对于Type I平台，设备侧也可以发送设备解绑命令。而这时的设备解绑命令不包含任何用户的信息。这将导致敌手可以通过虚拟设备伪造设备解绑请求，受害者账号和设备的绑定关系在受害者不知情的情况下被撤销了。

6.1**实验准备**

作者对5个平台的多个设备进行了实验验证，如图 6.1 所示，涉及智能插座，摄像头，灯泡，扫地机器人等。

![](../Images/a33960d2750d330a01854af5e1d97c61.png)

图 6.1  实验用到的设备

针对Type I和Type II平台，作者分别选取了一个例子来说明如何获取设备身份信息和合法性信息。Type I平台的例子是阿里Alink的飞利浦智能插座，Type II平台的例子是TP-LINK的WiFi灯泡。

对于Alink的设备，前文已经提到可以通过GitHub来对合法性信息进行搜集。Alink使用型号、MAC地址和芯片ID来作为身份标识信息。对于型号和芯片ID，对于特定的设备类型，其是固定的，可以从APP的日志信息中提取。对于MAC地址，可以通过暴力破解的方式获得。作者购买了两个测试设备，其中一个的MAC地址是3C:2C:94:0B:56:69，经过21,692次尝试，即可命中第二台设备的MAC地址，3C:2C:94:0B:AB:25。更进一步，作者对MAC地址后三个字节进行了遍历，分别用于进行设备注册，在获取设备ID后，执行设备ID和用户的绑定操作。如果设备ID已经和其它账户绑定，云端则会拒绝绑定请求。最终，作者发现7,181个设备的ID已经被真实用户所绑定。这意味着这7,181个设备都是潜在的可被攻击的对象。

对于TP-LINK设备，身份信息和合法性信息都是硬编码的，作者通过在设备和APP之间进行中间人攻击，获取到了这些信息。

6.3**其它危害分析**

除了远程设备替换和劫持，作者又分析了三种可能的危害。

**( 1 ) 远程设备DoS**

如果敌手可以解绑设备，那么目标设备将不能被操作，实现了对于设备的DoS攻击。

**( 2 ) 非法设备占用**

对于设备ID已经和其它账户绑定，云端则会拒绝绑定请求的情况，假设敌手可以预测未出售的设备ID，并且用虚拟设备与云端通信对其进行绑定，则设备出售后，用户将无法和其进行绑定。这类攻击针对Type I平台，因为其身份信息是可预测的。

**( 3 ) 固件窃取**

IoT制造商可能会采用多种技术来对其产品进行保护，防止敌手从硬件中提取固件（或增大固件提取难度）进行分析。但是，通过虚拟设备，敌手可以构造OTA升级请求，从而窃取设备固件。实验的效果比较惊人，作者模拟了1,355款阿里的设备，543款京东的设备，118款小米设备，23款三星设备，18款TP-LINK设备，从中获取到63个阿里设备的固件镜像，37个京东设备的固件镜像，89个小米设备的固件镜像，16个TP-LINK的固件镜像。这种方式，大幅降低了获取设备固件的难度。

**7\.  小结**

作者对五个智能家居平台的不同实体（设备、云端、APP）之间的交互进行了研究，发现了在交互层面的设计缺陷，并进行了实验验证。交互层面的问题的完整修复，需要开发人员重新对整体的智能家居体系架构进行思考，从而设计出最优的方案。但是，整体架构的改变成本很高，在这里，笔者建议，可以考虑引入风控机制，将同一设备的外网IP、内网IP，设备登录次数等信息考虑进来，在发生一些异常情况时，及时进行告警甚至是阻断，将大部分的分析、判断、处置工作都交由云端来进行。
