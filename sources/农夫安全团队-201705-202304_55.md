1. **子域劫持问题**

当公司域名创建指向第三方服务的DNS解析记录（CNAME记录）时，可能会发生子域名接管/劫持攻击，然而，如果公司忘记了第三方申请使用过的子域名，会让它很容易被另一方劫持。如果另一方是攻击者，通过这样做，他们可以破坏或重定向用户到另一个位置。 这种攻击实际上是不可追踪的。

![](../Images/298a9137a2129cbe5ae1e7703ef41520.png)

在这种情况下，我能够劫持一个指向一个不存在的CyrdFrand（CF）域的公司的子域；幸运的是，AWS（亚马逊）存在的一些问题导致任何人都可以劫持已过期或未使用的子域名。   

  

2. **CloudFront 是什么？**

![](../Images/d03185a19080f72f3186ced5b2f61c93.png)

Amazon CloudFront是一种用于内容分发网络（CDN）的Web服务，它加速了静态和动态Web内容的分发，例如HTML，javascript，CSS，PHP和图像文件。许多站点和组织将其用于加速服务，以便在用户本地服务器上更快地分发内容。如果想了解有关该服务的更多信息，请阅读亚马逊的开发人员文档：

https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Introduction.html

 

3. **发现漏洞**

在进行常规的信息搜集时，发现了我的第一个子域劫持，通常我都会使用子域名爆破工具来搜集子域名信息，然后使用nmap在一些常用端口上查找web应用程序，接下来我才开始进行测试子域名劫持。

 

我发现检查子域名劫持漏洞的最简单方法是首先搜集子域名列表，然后查看子域名是否通过使用cname记录添加到第三方，访问域名的时候返回404 找不到的错误。

在这种情况下，我遇到了一个解析为CloudFront域的域名，该域名出现以下错误：“CloudFront（CloudFront）生成的请求无法满足的错误”，类似于下图所示：

![](../Images/b1714be371ca2a020b0d582543541b4d.png)

在识别厂商可能不再使用的CF域时，此错误是相对常见和标准的错误。通过使用dig命令的方式，可以进行快速测试以找出跳转到这种页面的子域名。

  

4. **dig 用法**

在下面的示例中，对目标域进行简单测试将返回类似以下的输出：

\# dig example.com

; <<>> DiG 9.10.3-P4-Debian <<>> example.com

;; global options: +cmd

;; Got answer:

;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 25169

;; flags: qr rd ra; QUERY: 1, ANSWER: 9, AUTHORITY: 0, ADDITIONAL: 1

 

;; OPT PSEUDOSECTION:

; EDNS: version: 0, flags:; udp: 512

;; QUESTION SECTION:

;example.com. IN      A

 

;; ANSWER SECTION:

example.com. 3599 IN  CNAME   example.cloudfront.net.

example.cloudfront.net. 59 IN    A       x.x.x.238

example.cloudfront.net. 59 IN    A       x.x.x.251

example.cloudfront.net. 59 IN    A       x.x.x.127

example.cloudfront.net. 59 IN    A       x.x.x.253

example.cloudfront.net. 59 IN    A       x.x.x.6

example.cloudfront.net. 59 IN    A       x.x.x.114

example.cloudfront.net. 59 IN    A       x.x.x.22

example.cloudfront.net. 59 IN    A       x.x.x.106

 

;; Query time: 144 msec

;; SERVER: 8.8.8.8#53(8.8.8.8)

;; WHEN: Tue Oct 10 12:55:44 EDT 2017

;; MSG SIZE  rcvd: 229

 

从输出中，我们感兴趣的基本内容是请求返回的部分，特别是如果存在CNAME别名解析。 识别这个记录的一个简单方法是使用grep进行筛选：

 

\# dig example.com  | grep CNAME

example.com. 3027 IN  CNAME   example.cloudfront.net.

 

**5.如何使用CloudFront的和安装程序**

现在，如果我们发现自己处于一个指向不存在的CF域的域名，该怎么办？ 好吧，如果它是一个bug赏金或渗透测试的范围，它可能值得我们去尝试劫持它。 以下是接管CF域的步骤和要求。

  

6. **aws方面**

我们要做的第一件事是注册一个亚马逊网络服务（AWS）帐户，一旦你有了一个免费的帐户，那么我们就可以开始测试了。

前往CloudFront注册去注册一个免费账号。选择创建分发并选择Web作为交付方法，如下面的两个屏幕截图所示。

![](../Images/a710653883dfb23c0ea5ccb985e9f63b.png)

![](../Images/d8acbc63327b81e042b533c514c644dc.png)

点击开始后，我们将看到一个与此非常类似的界面：

![](../Images/3c4bcccf1cc6d26a4d9af5e166e97f1b.png)

第一个红色框是我们放置要声明的CF域的位置。 完成此操作后，向下滚动到“分发设置”区

域：

![](../Images/c78a2b340cfdb600f48a3f752472e7b3.png)

在“别名解析（CNAME）”部分中，输入我们要接管的子域，从上面信息搜集的阶段确定目标。 将其余部分的设置保留为默认值，然后单击创建，创建完毕以后，它应该看起来像这样：

![](../Images/b03245c82b19a8f5a5bb2fd9aeef66a3.png)

下一步是将新创建的CF域指向我们的内容作为源地址。 这是通过添加源地址来完成的，只需选择分布然后导航到源地址选项卡并选择创建源地址，不用担心是否已经有源地址，我们也可以选择编辑它。

![](../Images/c159db623147105ce05a469cf9ffd676.png)

输入我们拥有的“原始域名”中的S3存储容器或网络域为其提供ID，这可以是我们想要的任何内容，将其他所有内容保留为默认值，然后选择“创建”。 如果成功，我们现在应该拥有自定义域的来源。

![](../Images/f958799f1450244e8f0db60f6ec3eb31.png)

最后导航到CF的主页，如果一切顺利，我们应该看到新创建的分发处于进行中状态。 这意味着CF正在将我们的内容加载到其系统中并且正在逐渐部署接管内容，请注意，这可能需要一个小时左右才能显示在目标域上，但是我们可以通过直接浏览到CF域来进行检查。

![](../Images/7d5493180a6f3c3bb5baa0f1af497d35.png)

如果第一个URL是我们声明的CF域，则第二个URL是我们的服务器或S3存储容器，最后一个链接是我们正在接管的域或子域。

  

7. **域名或内容**

一旦你在CF方面完成了基本设置，接下来就是创建接管页面的步骤。 这可以有效地成为我们想要在S3存储容器或我们自己的Web服务器上托管的任何内容。 通常我会使用以下代码

<!DOCTYPE html>

<html>

<head>

    <title>Sub-domain Takeover ZephrFish</title>

</head>

<body>

    <h1>Sub-domain Hijack/Takeover Proof of Concept by INSERT HANDLE HERE</h1>

    <script>

    document.write("Sub-domain Hijack/Takeover Proof of Concept " + document.domain + " by ZephrFish")

    </script>

</body>

</html>

 

它是一个带有一点JavaScript的静态页面，用于显示正在被劫持/被劫持的域。 现在，如果我们没有VPS或服务器，不用担心，这是AWS非常给力的地方，我们可以创建一个S3存储容器。 只需导航到AWS控制台，然后选择S3，然后创建一个存储容器，将其设置为公共存储并上传一个index.html，然后将S3存储容器设置为CF中的源地址，我们就已经成功接管该子域名了。
