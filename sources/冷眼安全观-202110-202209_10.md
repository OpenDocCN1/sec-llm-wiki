## **1.1   合规、安全、自证需求是安全审计的源头**

日志审计最初多是从信息系统运营机构自身安全的需要出发，以帮助用户获悉信息系统的安全运行状态、识别针对信息系统的攻击和入侵、以及来自内部的违规和信息泄露或者能够为事后的问题分析和调查取证提供必要的信息为目的。随着国家相关法律法规和行业标准的颁布，基本上都将日志审计纳入合规与内控机制建设的范围，例如：（1）《网络安全法》第二十一条（三），明确要求“采取监测、记录网络运行状态、网络安全事件的技术措施，并按照规定留存相关的网络日志不少于六个月”，**虽然本法并未明确什么是网络日志；**（2）GB/T 22239-2008《信息安全技术信息系统安全等级保护基本要求》对于二级及以上信息系统，在网络安全、主机安全和应用安全等基本要求中明确要求进行安全审计，并简单阐述了日志应该记录的对象：

1.  应制定重要设备的配置和操作手册，依据手册对设备进行安全配置和优化配置等；
2.  应详细记录运维操作日志，包括日常巡检工作、运行维护记录、参数的设置和修改等内容；
3.  应指定专门的部门或人员对日志、监测和报警数据等进行分析、统计，及时发现可疑行为；
4.  应严格控制变更性运维，经过审批后才可改变连接、安装系统组件或调整配置参数，操作过程中应保留不可更改的审计日志，操作结束后应同步更新配置信息库；
5.  应严格控制运维工具的使用，经过审批后才可接入进行操作，操作过程中应保留不可更改的审计日志，操作结束后应删除工具中的敏感数据；
6.  应严格控制远程运维的开通，经过审批后才可开通远程运维接口或通道，操作过程中应保留不可更改的审计日志，操作结束后立即关闭接口或通道；
7.  应保证所有与外部的连接均得到授权和批准，应定期检查违反规定无线上网及其他违反网络安全策略的行为。

（3）公安部发布的《互联网安全保护技术措施规定》的第七条（三），要求建立“记录并留存用户登录和退出时间、主叫号码、账号、互联网地址或域名、系统维护日志的技术措施”；第八条要求“记录、跟踪网络运行状态，监测、记录用户各种信息、网络安全事件等安全审计功能”。**该规定其实并没有系统阐述日志的内涵、审计的目的；**（4）作为行业标准，中国人民银行2002年发布的《商业银行内部控制指引》第一百二十六条指出“商业银行的网络设备、操作系统、数据库系统、应用程序等均当设置必要的日志。日志应当能够满足各类内部和外部审计的需要”，**日志、审计的内涵及外延其实也是缺乏定义的，给合规要求留出太多操作空间。****只是很遗憾，还没有在国内权威机构文件中，看到广泛遵循的日志、审计明确定义。**

## **1.2   安全资产权限管理机制局限性产生的风险管控要求**

虽然已经有了各类授权模型，DAC、MAC、ACL、RBAC、ABAC，但在现实环境中，由于权限管控功能和配置复杂度限制，各类操作系统、应用软件、数据库都很难做到针对每一个用户对其对一个数据库表项、字段、指令参数等资源的操作权限的细致定义，实际授权经常超越其工作职责所需的权限，因此，需要通过审计来察觉恶意利用权限管理机制缺陷、超范围访问数据、执行敏感操作指令的行为。数据库就是一个典型案例，加之开启日志记录功能将明显降低其处理能力，因此，业界推出数据库审计产品，并得到了广泛应用。

# **第2章    日志是什么**

## **2.1   名词定义的常用方法**

在李庆臻编著的《科学技术方法大辞典》一书中（科学出版社，1999），解释了“定义”的基本方法。他强调定义方法是揭示概念内涵的逻辑方法，通过某概念所反映的对象的本质属性来说明该概念。从逻辑结构上看，定义包括三个部分：①被定义项，即其内涵需要明确的概念;②定义项，即用来说明被定义项的概念;③定义联项，用来联结被定义项和定义项的联结词。例如，“所谓商品，即指为了交换而生产的劳动产品”，在这个定义中，“商品”是被定义项，“为了交换而生产的劳动产品”是定义项，“所谓…即指…”是定义联项。定义的方法有许多种，如真实定义、语词定义、关系定义、发生定义、功用定义、递归定义等方法。在科学研究、社会实践中经常使用的一种定义方法，是通过找出被定义项的邻近的属和种差来下定义。另一种是语词定义的方法，即明确一个语词表达什么概念。在科学著作或议论文中，语词通常是用来表达概念的，因此给某些语词下定义是明确概念的一种重要方法。要正确运用定义的方法还必须遵守定义的逻辑规则，如“定义必须相称”、“定义项不得包含被定义项”、“定义项必须清楚明白”、“定义项一般不能用否定形式”等。在思维实践中，定义方法起着重要作用：第一，通过定义可以把对事物的认识总结和巩固下来;第二，定义能将各种各样的事物区别开来;第三，定义还用于检查人们所用的概念是否明确;第四，对于科学原理的形成、制定以及理论宣传、教育、传授知识等方面也有着重要作用。

## **2.2   个人理解的日志定义及其关键属性**

带日志二字的场景有很多，比如航海日志、飞行日志、公司经营日志、信息系统运维日志、用户登录日志等等。因为本文关注的是计算机、网络、信息系统，所以，我们仅仅限于主机、网络、应用、数据库等信息系统的重要组成部分中的登录、访问、变更操作相关的活动记录，因此敏感信息的访问、下载、改变、添加，重要参数、文件的变更，重要指令及其执行，无论是系统自动执行还是系统用户执行，都属于需要记录的内容。而系统重要组件、功能的运行状态，也需要记录，以利于系统运行分析、故障排查。动词意义上的日志（Logging），是以回溯、排查违规可疑行为、证明合规为目的，针对所有敏感访问、特别是改变一个系统、属性、数据状态的重要活动关键过程的记录行为。**名词意义上的网络及信息系统日志（****Log****，****Audit Log****或者****Audit Trail****），个人理解就是按照时间顺序记录下的改变信息或者系统状态的一个个活动及其属性信息，关注的是“主体”“改变”“客体”的“过程”，而结果本身不是重点。****日志关注的要素应具备几个关键属性：**

1.  **时间顺序**
2.  **改变了敏感数据或者文件的****CIA****特性**
3.  **使用了某种功能**
4.  **改变了系统的完整性，如命令、文件、参数等**

本文以维基百科、Solarwinds、华为、ISO27001关于日志的解释为例，从另一个方面去理解日志的含义，并佐证我们的理解是否准确。

## **2.3   常见日志记录方式及其优缺点比较**

合法用户或者盗用合法用户账号的非法用户在尝试登录各类设备、应用系统、数据库，进行合规、违规操作甚至黑客行为时，设备本身具有100%感知、记录能力优势，理论上，基于设备自身日志进行审计是最佳方案。但在现实当中，由于基于设备自身的日志记录取决于设备在设计之初是否进行了敏感操作行为的梳理、建立了记录功能、进行了启用参数配置、与日志审计系统建立采集关系，记录能力不被恶意关闭，并且日志记录在发出之前不被恶意行为者破坏，不会出现网络故障……，需要强有力的运营维护体系建设才能得到有效保障。因此，任何一种情况都可能导致部分敏感操作或者全部操作不能被日志审计系统采集到。在设备量较大、维护能力低下的运营机构，依靠设备自身日志成为建立日志审计系统的噩梦。**为此，很多厂商、甲方将希望寄托在网络流量日志解决方案上面，进行全流量采集存储、分析，但是这种技术方案的巨大缺陷显而易见，未来更加不可持续：**

1.  只能监测采集探针覆盖范围，所有东西向、南北向全覆盖的前提是所有交换机的链路均纳入监测访问，成本巨大。即便如此，在服务器本地登录、操作仍然无法覆盖。
2.  流量加密已经成为事实上的主流；
3.  应用层的敏感操作如何识别？理论上，通过安全公司、信息系统提供商携手合作可以解决识别问题，但在实践上，由于信息系统业务逻辑的多样性、复杂性、变动极度频繁，完全不可行。

既然两种技术各有利弊，需要甲方根据自身的维护能力、业务复杂性、流量是否加密等情形，进行优化选择。

## **2.4   Logging (software)——维基百科日志定义及分类**

https://en.wikipedia.org/wiki/Logging\_(software)In computing, a log file is a file that records either events that occur in  an operating system or other software runs,\[1\] or messages between different users of a communication software. Logging is the act of keeping a log. In the simplest case, messages are written to a single log file.A transaction log is a file (i.e., log) of the communications between a system and the users of that system, or a data collection method that automatically captures the type, content, or time of transactions made by a person from a terminal with that system. For Web searching, a transaction log is an electronic record of interactions that have occurred during a searching episode between a Web search engine and users searching for information on that Web search engine.Many operating systems, software frameworks and programs include a logging system. A widely used logging standard is syslog, defined in Internet Engineering Task Force (IETF) RFC 5424). The syslog standard enables a dedicated, standardized subsystem to generate, filter, record, and analyze log messages. This relieves software developers of having to design and code their own ad hoc logging systems.

### **2.4.1  Event logs**

Event logs record events taking place in the execution of a system in order to provide an audit trail that can be used to understand the activity of the system and to diagnose problems. They are essential to understand the activities of complex systems, particularly in the case of applications with little user interaction (such as server applications).

It can also be useful to combine log file entries from multiple sources. This approach, in combination with statistical analysis, may yield correlations between seemingly unrelated events on different servers. Other solutions employnetwork-wide querying and reporting.

### **2.4.2  Transaction logs**

Most database systems maintain some kind of **trasaction log**, which are not mainly intended as an audit trail for later analysis, and are not intended to be human-readable. These logs record changes to the stored data to allow the database to recover from crashes or other data errors and maintain the stored data in a consistent state. Thus, database systems usually have both general event logs and transaction logs.

#### **2.4.2.1 Transactionlog analysis**

The use of data stored in transaction logs of Web search engines, Intranets, andWeb sites can provide valuable insight into understanding the information searching process of online searchers. This understanding can enlighten information system design, interface development, and devising the information architecture for content collections.

### **2.4.3  Message logs**

Internet Relay Chat(IRC), instant messaging (IM) programs, peer-to-peer file sharing clients with chat functions, and multiplayer games(especially MMORPGs) commonly have the ability to automatically save textual communication, both public (IRC channel/IMconference/MMO public/party chat messages) and private chat between users, as message logs. Message logs are almost universallyplain text files, but IM and VoIP clients (whichsupport textual chat, e.g. Skype) might save them in HTML files or in a custom format to ease reading or enable encryption.

#### **2.4.3.1 Internet Relay Chat (IRC)**

In the case of IRC software, message logs often include system/server messages and entries related to channel and user changes (e.g. topic change, user joins/exits/kicks/bans, nickname changes, user status changes),making them more like a combined message/event log of the channel in question,but such a log isn't comparable to a true IRC server event log, because it onlyrecords user-visible events for the time frame the user spent being connected to a certain channel.

#### **2.4.3.2 Instant messaging**

Instant messaging and VoIP clients often offer the chance to store encrypted logs to enhance the user's privacy. These logs require a password to be decrypted and viewed, and they are often handled by their respective writing application.

### **2.4.4  Server log**

A **server log** is a log file (or several files) automatically created andmaintained by a server consistingof a list of activities it performed.

A typical example is a web server log which maintains a history of page requests. The W3C maintains a standard format (the Common Log Format) for web server log files, but other proprietary formats exist. More recent entries are typically appended to the end of the file.

### **2.5.1  什么是审计日志？**

**审计日志（****AuditLog****）**，也称为**审计跟踪（Audit Trail****）**，本质上是**事件和变化**的记录。网络上的 IT 设备会根据事件创建日志。审核日志**是这些事件日志的记录，通常与一系列活动或特定活动有关。**审计日志并不总是以同样的方式运行。事实上，它们因设备、应用程序和操作系统而异。但通常，他们**通过记录谁执行了活动、执行了哪些活动以及系统如何响应来捕获事件**。

**审计****日志****注意到系统内的几乎每一个更改，提供系统操作的完整记录。**因此，审计日志对于想要检查网络上的可疑活动或诊断和排除故障问题的管理员和审计人员来说是一种宝贵的资源。这些审核日志可以让管理员对哪些行为正常以及哪些行为不正常进行宝贵的洞察。例如，日志文件事件将显示尝试的活动以及是否成功。当确定系统组件是否配置错误或可能失败时，这很有用。

审计跟踪可以是手动记录或电子记录，尽管该术语通常指数字记录。日志审核可以像基本文件或数据库表一样简单，但它需要一些结构来避免混淆。**有些人可能会使用审核日志审查模板，这将为您提供一个经过尝试和测试的结构和格式。**这意味着您只需要输入您的日志。如果您认为审核日志审核模板可能适合您，则在线访问审核日志示例，或者应嵌入您的审计软件中。

审计日志的一个问题是它们很脆弱。**如果日志审计被错误配置、损坏或以某种方式损坏，则变得毫无用处，**因此了解审计记录的基本知识非常重要。审计日志管理和事件日志审计的最基本形式，如手动梳理您的记录，设备逐设备-只适合小型企业。如果你想要一些可扩展的，强大的，不太容易人为错误，那么日志审计软件是必要的。

### **2.5.2  审计日志的优势**

审计日志为 IT 团队和企业都提供了优势。

#### **2.5.2.1 提高安全性**

审核日志有助于安全性，因为它们**提供所有 IT ****活动的记录，包括可疑活动。**审计日志可以帮助监控数据和系统，防止任何可能的安全漏洞或漏洞，并根除内部数据滥用。审计日志甚至可用于认证正在遵守的文档协议并跟踪欺诈活动。

**事件日志审核对网络安全也很重要，因为它提供的记录可以作为**证据**。全面和深入的日志审计****可以****在法律战中产生所有差异，并保护您的企业免受责任。**

#### **2.5.2.2      证明合规性**

从外部来说，审计日志**对于证明****符合**HIPAA和**PCI DSS****等常见法规**至关重要**。**审计日志作为官方记录，企业可以用来证明他们遵守法律。对于许多企业来说，有必要定期与审计师共享日志，尤其是在出现问题时。使用审计日志遵守法规可以保护企业免受重大罚款和处罚。

#### **2.5.2.3      获得洞察力**

网络工程师、服务台工作人员、开发人员和管理员**可能会在内部使用日志审核来提高绩效、提高责任心和保持系统稳定**。日志文件提供活动的历史可见性，因此更改不会被忽视。

审计日志记录了某人访问特定文档或文件的频率，这可以为公司提供宝贵的见解。您可以使用日志审核了解用户活动，这些活动可用于提高效率、安全性和性能。

#### **2.5.2.4      风险管理**

拥有稳健的风险管理策略对任何企业都很重要。审计日志在风险管理中起着关键作用，**因为它们向合作伙伴、客户和监管机构展示正在采取措施防止问题发生之前。**这可能向投资者展示提供可靠且低风险的投资机会。

### **2.5.3  日志记录的内容**

首先，当事件发生时，应该了解要审计哪些字段。日志中包含的信息应提供事件的上下文、"谁、什么、在哪里、何时"和其他任何相关内容。以下领域至关重要：

1.  **组**（即活动发起地的团队、组织、部门或帐户）
2.  **行为人**（即负责该操作的帐户的 uuid、用户名或 API 令牌名称）
3.  **事件名称**（即特定事件的标准名称）
4.  **描述**（即人读，可能包括指向其他应用页面的链接）
5.  **当**（即服务器NTP同步时间戳）
6.  **地点**（即原籍国、设备识别号或IP地址）
7.  **操作**（即对象是如何更改的）
8.  **操作类型**（即创建、读取、更新或删除）

必须记录以下内容：用户 ID、登录和注销日期和时间、访问尝试失败和成功、终端身份、访问过的网络、访问的文件、系统配置更改、系统实用程序使用、安全相关事件、例外、网络连接更改或故障、更改安全设置的尝试以及激活反恶意软件等保护系统。这些组件有助于访问控制监控，允许您在发生事故时调查审计跟踪。

**确保同步时间戳是日志审计管理的另一个关键要素**。如果没有使用通用格式的日志时间戳字段，几乎不可能进行顺序分析。NTP，时间协议，应同步为所有服务器，设备和应用程序，因为这是许多标准的合规性要求。

**日志文件安全****性也很重要。**日志审核是任何意图隐藏其活动证据或想要泄露和损坏数据的人的主要目标。为了防止这种情况发生，最好配置审核日志，以便为日志建立强大的访问控制限制。这通常包括限制可以更改日志文件的用户数量。加密审计日志的所有传输也是最佳实践。

## **2.7   ISO27001-2013**

12.4 日志和监视

目标：记录事态和生成证据。

12.4.1 事态记录

控制措施应产生记录用户活动、异常情况、故障和信息安全事态的事态日志，并保持定期评审。事态日志应在需要时包括：

a）用户ID；

b）系统活动；

c）日期、时间和关键事态的细节，例如登录和退出；

d）若有可能，设备身份或位置以及系统身份；

e）成功的和被拒绝的对系统尝试访问的记录；

f）成功的和被拒绝的对数据以及其他资源尝试访问的记录；

g）系统配置的变更；

h）特殊权限的使用；

i）系统实用工具和应用程序的使用；

j）访问的文件和访问类型；

k）网络地址和协议；

l）访问控制系统引发的警报；

m）防护系统的激活和停用，例如防病毒系统和入侵检测系统；

n）应用系统中用户执行的交易记录。

事态记录成为自动监视系统的基础，该系统可以提供综合报告并且能够针对系统安全提供告警。其他信息事态日志包含敏感数据和个人身份信息，应采取适当的隐私保护措施（见18.1.4）。可能时，系统管理员不应有删除或停用他们自己活动日志的权利（见12.4.3）。

12.4.2 日志信息的保护

控制措施记录日志的设施和日志信息应加以保护，以防止篡改和未授权的访问。实施指南应实施控制措施以防止日志信息被未授权更改以及日志设施出现操作问题，包括：

a) 更改已记录的消息类型；

b) 日志文件被编辑或删除；

c) 超越日志文件介质的存储容量，导致不能记录事态或过去记录事态被写覆盖。

一些审计日志可能需要被存档，以作为记录保持策略的一部分或由于收集和保留证据的要求（见16.1.7）。系统日志通常包含大量的信息，其中许多与信息安全监视无关。为帮助识别出对信息安全监视目的有重要意义的事态，应考虑将相应的消息类型自动地拷贝到第二份日志和/或使用适合的系统实用工具或审计工具执行文件查询及规范化。需要保护系统日志，因为如果其中的数据被修改或删除，可能导致一个错误的安全判断。实时复制日志到系统管理员和操作员控制范围外的系统，可用于日志防护。

12.4.3 管理员和操作员日志

控制措施系统管理员和系统操作员的活动应记入日志，保护日志并定期评审。实施指南特权用户账户持有人可操作其直接控制下的信息处理设施日志。因此，为保持特权用户的可稽核性，保护和评审日志是必要的。其他信息对在系统和网络管理员控制之外进行管理的入侵检测系统可以用来监视系统和网络管理活动的符合性。

12.4.4 时钟同步

控制措施一个组织或安全域内的所有相关信息处理设施的时钟应使用单一参考时间源进行同步。实施指南应记录时间表示、同步和精确的内部及外部要求，这些要求符合法律、法规及合同要求，同时也符合标准一致性或内部监视要求。应定义标准参考时间用于组织内。应记录和实施组织从外部源获取参考时间的方法以及如何同步内部时钟并保证可靠性。其他信息正确设置计算机时钟对确保审计记录的准确性是重要的，审计日志可用于调查或作为法律、纪律处理的证据。不准确的审计日志可能妨碍调查，并损害这种证据的可信性。链接到国家原子钟无线电广播时间的时钟可用于记录系统的主时钟。可以用网络时间协议保持所有服务器与主时钟同步。

# **第3章    安全审计的含义及定位**

安全审计是将传统的审计应用于网络与信息系统中所衍生出的新概念。

安全审计通过对审计日志相关数据、文件、记录的分析，结合对相关人员的询问，判断关键活动过程是否符合相关规定，是将具体活动与既定规程进行匹配、判断的行为，本质上与经济领域的审计没有区别。

## **3.1   安全审计的特征**

以规则匹配为核心特征的安全审计和安全事件管理还是存在重大区别：

1.  安全审计（LogAudit或者说SIM）侧重的是合法的账号被尝试登陆的情况，对无论是合法的用户以合法账号还是任何非授权人员以非法方式获取合法账号并以合法账号之名，在限定的权限范围内或者未严格限定的范围中具体的活动情况；
2.  安全事件管理（SEP），侧重的是攻防概念，覆盖任何漏洞攻击、获取账号权限之后利用合法的账号密码进行非法行为。

## **3.2   什么是审计——百度百科**

审计（独立性的经济监督活动）\_百度百科(baidu.com)

**审计作为一种监督机制，其实践活动历史悠久，但人们对审计的定义却众说纷纭。公认具有代表性且被广泛引用的是****美国会计学会1972****年在其颁布的《基本审计概念公告》中给出的审计定义，即****“****审计是指为了查明有关经济活动和经济现象的认定与所制定标准之间的一致程度，而客观地收集和评估证据，并将结果传递给有利害关系的使用者的系统过程****”****。**

**经济活动和经济现象的认定**

经济活动和经济现象是审计的对象，也就是审计的内容。经济活动和经济现象的认定代表着被审单位对本单位经济活动的合法合规性或有效性及经济现象（如会计资料）的真实公允性的一种看法。本书第四章将深入探讨这一问题。

**收集和评估证据**

证据是审计人员用来确定被审单位经济活动合法合规性或有效性及经济现象真实公允性的各种形式的凭据。收集充分、有力的审计证据是审计工作的核心。从一定意义上说，审计就是有目的、有计划地收集、鉴定、综合和利用审计证据的过程。

**客观性**

客观性是指不偏不倚，实事求是，这是对审计人员的职业道德要求。审计人员只有客观地收集和评估证据、作出审计结论、报告审计结果，才能达到审计目标，也才能使审计工作令审计意见的利害关系人信服。

**所制定的标准**

所制定的标准是审计的依据，即判断被审单位的经济活动合法合规与否、经济效益如何、经济现象真实公允与否的尺度，如国家颁布的法律、规章和标准，职业团体制定的会计准则（如美国财务会计准则委员会FASB发布的《财务会计准则公告》），企业制定的各种消耗定额、计划、预算等。

**传递结果**

向依赖和利用审计意见的组织和人员传递结果是通过编制审计报告进行的。编制审计报告是审计工作的最后步骤。审计报告的格式有些是标准化的，如年度会计报表审计报告；有些则是非标准化的，如职员舞弊专项审计报告。在有些情况下，审计人员甚至还可以采取口头的非正式形式报告审计结果。

**系统过程**

审计须按照公认的规范（如美国注册会计师协会AICPA颁布的十条公认审计准则及审计准则公告，统称为“GAAP (General Accepted Accounting Principles)”）要求，遵循一定的程序进行，以保证审计的质量，提高审计的效率。

## **3.3   什么是审计——维基百科**

 **审计（英语：****auditing****）是对资料作出证据搜集及分析，以评估企业财务状况，然后就资料及一般公认准则之间的相关程度作出结论及报告。**审计就有关经济活动及事件之声明主张，与有关之既定准则之相符程度，以有系统的方式客观地搜集并评估相关证据，作为审定相符程度之依据，并将审核结果传达予利害关系人。进行审计的人员必需有独立性及具相关专业知识。审计准则公报由于各国之情形及需求不同，各国之审计准则公报常有差异。常见的财务审计有以下四种：

1.  运作审计（作业审计）：检讨组织的运作程序及方法以评估其效率及效益。
2.  履行审计（遵行审计）：评估组织是否遵守由更高权力机构所订的程序、守则或规条。
3.  财务报表审计：亦称为**核数**、**查核**、**查账**，评估企业或团体的财务报表是否根据公认会计准则编制，一般由独立会计师进行。对财务报表进行查核，搜集充分且适当之证据，以针对财务报表之编制“是否符合一般公认会计原则，且足以允当表达”表示意见，表示意见之作业由超然独立之会计师进行，提供与受查单位及利害关系人决策之依据。
4.  资讯科技审计：评估企业或机构的资讯系统的安全性，完整性、系统可靠性及一致性。

## **5.1   端点设备日志记录能力**

日志审计的前提是先有日志。因此，日志审计的基础是网络设备、主机操作系统、应用软件、中间件、数据库自身具备对需要留痕的各类账号登录、敏感数据访问、敏感操作的记录能力，或者融合通过网络全流量记录功能记录、还原远程访问的能力，一起实现记录日志的能力。

由于加密流量逐步成为主流，非标准化的应用层菜单、与业务高度相关的敏感操作类型也难以通过第三方进行识别、记录，因此，各类端点设备自身记录能力决定了日志审计的最终成效。

引导用户在梳理不同设备、应用、数据库的敏感操作、登录访问列表的基础上，提出网络、主机、应用、数据库、中间件、云平台、容器、云原生等资产类型的安全日志记录功能要求，推动厂商在规划、开发环节落实，确保入网之前满足所有审计的要求。

 

以下给出一种基于标准化工作模板的操作系统、应用系统、数据库不同层面的敏感操作梳理方式，供大家参考。

### **5.1.1  敏感操作梳理说明**

| **填表说明** |
| --- |
| **序号** || **XX****系统敏感操作及相关日志梳理表** |
| 1 || 该表格用于梳理某厂家的某信息系统的敏感操作以及和敏感操作对应的日志记录。 |
| 2 || “设备类型”明确本系统具体包含的设备种类。 |
| 3 || “敏感操作分类”包括1.账号和权限管理，2.用户登录、登出，3.修改日志配置，4.访问和操作客户信息，5.访问和操作客户业务订购关系，6.其他修改关键配置或影响系统稳定运行的操作等6类。 |
| 4 || “敏感操作概述”，按照主谓宾结构分为“操作者”、“操作”和"操作对象"三个方面。其中：（1）操作者，如所有用户、超级用户、普通用户、第三方用户等；（2）操作，如增加、删除、修改、查询、导入、导出、批量导入、批量导出、重启、关闭、加载、卸载等;（3）操作对象，包括账号、客户信息、配置文件、系统进程等，但应使用系统中该对象的具体名称并说明含义，如“iLog文件，话单文件”。避免使用“客户信息”、“计费话单”等概念性的类属名词。 |
| 5 || 敏感操作描述，非必填项。对于需要对该操作进一步补充具体信息的填写到本栏。 |
| 6 || “敏感操作对应的风险”项目描述对应“敏感操作类型”操作场景和该操作可能造成的风险，应结合该系统功能的特殊性，将可能造成的后果描述具体化。 |
| 7 || “应用层是否能够记录”，在系统侧是否有能力形成该操作的日志。对于应用系统侧没有日志记录，且堡垒主机也无法记录的情况，该行后面的内容不用填写。 |
| 8 || （1）“日志采集方式”，包括SYSLOG、SFTP、FTP、JDBC/ODBC、SNMP，堡垒主机。  
 （2）堡垒主机特指管控平台中集中接入控制的设备，其具备将维护人员操作及操作返回的结果，以文本或录像的方式进行记录的能力。  
 （3）SFTP和FTP方式需要填写“日志文件名称”、“日志存储位置”，其他方式不需要填写“日志文件名称”和“日志存储位置”。  
 （4）堡垒主机方式，不需要填写“开启日志记录的配置指令/方法”  
 （5）对于存在多种日志采集方式的可以一一列举。 |
| 9 || “开启日志记录的配置指令/方法”，描述如何配置开启应用系统该类敏感操作日志记录功能所需的配置流程和指令，以及验证系统已开启该日志记录功能的方法。 |
| 10 || “日志存储位置”：描述日志文件在系统中具体保存的位置。 |
| 11 || “适用版本”，普遍适用各种现网版本，填写“通用”。否则，枚举具体适用的版本。 |
| 12 || “应用原始日志样本”，从原始日志中至少选择3个具有代表性的。 （堡垒主机方式不用填） |
| 13 || “原始日志字段/变量值解释说明”，分字段依次逐一解释。每个字段的解释包括以下四个方面的内容：序号，字段名，长度或分隔符，含义。1、序号，按照该字段在每条日志中出现的顺序标号，从1起始；2、字段名，如果日志文件中已包含字段名，则遵循日志文件的命名，否则按照该字段的用途给出命名。3、长度或分隔符，提供该字段的长度或与下一字段的分隔符。4、含义：文字说明该字段记录信息的准确含义。结合“应用原始日志样本”中的样本给出至少3个具体解释的例子。（堡垒主机方式不用填） |
| 14 || 日志筛选策略，如果该类日志中或堡垒主机记录的操作指令中还包括敏感操作之外的内容，需要填写日志筛选策略，从便于系统确认那些日志对应该敏感操作。日志筛选策略是由字段名，取值和逻辑与、或组成的表达式。如(字段名1=“关键字1”OR“关键字2”OR……)AND（字段名2=“关键字3”OR“关键字4”OR……），（操作命令1=“关键字1”AND参数1=“关键字2”）OR（操作命令2=“关键字3”AND参数2=“关键字4”） |

## **5.2   端点设备日志记录功能参数配置**

以windows系统日志管理功能为例，缺省设置为仅记录密码错误登录请求，如果想记录成功登录，需要在安全管理功能中进行配置。

其实，这不是个案，在其它网络设备、主机操作系统中，也存在此类设备有记录能力但需要进行配置才能生效、启用的情况。在非标准化的应用系统中，更是常见。

## **5.3   采集接口启用**

在建立集中化的日志审计平台后，需要人工或者远程登录设备，配置各类设备syslog、ODBC、JDBC等接口，或者部署专用Agent，将日志源源不断地上报到集中化平台。

即便在完成接入后，由于网络故障、设备升级、参数配置变更等原因引起接口失效，相关设备与日志审计平台“失联”，在日常运维中也是常态，需要采取自动化监测、智能分析技术定位“失联”设备，提示管理员迅速解决问题。

需要结合资产接入/退服管控流程，确保新增资产及时纳入审计平台，退服资产从审计平台中删除或者冻结，不再占用分析、处理资源。

## **5.4   强大的自动化分析能力**

毫无疑问，海量日志分析需要强大的高效处理能力，部署大数据分析基础平台，这一点是大多数厂商在白皮书、技术交流中经常特别强调的。但是决定日志审计平台效能的关键指标，即能否全面、准确、及时发现异常登录、操作的能力，应该获得更多关注。

## **5.5   与运维白环境结合是降低误报率的根本途径**

与人员工作职责、应用访问设计目的密切相关的标准，一般以文本方式进行描述，需要量化为机器可读、可理解的策略，才能作为审计参照的“基准”。而安全审计最为关注的敏感操作，如账号权限变更、远程应急、非忙时系统升级、敏感数据访问下载、网络与主机和应用中的控制类参数变更、系统宕机等场景，如果仅仅依赖设备日志、网络流量日志进行判断，自然导致大量的误告警、浪费运维人员的精力。

**上述敏感操作管控，本身就是网络与信息系统运营部门日常严格限制的内容，有明确的管理规章制度，并通过流程审批、4A等身份管理系统、堡垒机、金库管理进行“事前审批、事中实时审计”，因此，在设备中产生的对应日志，结合这些系统中的记录，就可以将基于用户账号登录前提下的可疑操作分析极大地简化，极大地降低误告警比率。**

以下以修改设备、意愿系统关键配置参数或影响系统稳定运行的操作为例，说明业务、维护场景和基于场景的访问操作异常判定原则，供大家体会。

**正常操作具备的特征：**

（1）  有明确的操作需求授权方，如业务部门、国家相关部门（如防火墙策略变更需求）、关键参数制作规定发文、维护部门形成工单；

（2）  有成文的操作依据，如工单业务联络函、申请审、批单；

（3）  有较为固定的操作人，如只能是相关系统维护人员几个固定的帐号，绝对不允许第三方进行操作，日常巡检帐号只有查看权限；如有较为固定的操作终端和访问路径，通过IAM、堡垒机访问，固定的维护终端，机房内部操作，有进入机房登记和相关摄像等物理安全设备；

（5）  频次较为规律；

（6）  维护专业后台有权限，但绝对不能执行的关键配置数据变更等的操作（正常情况下都是业务部门通过前台执行），如业务费率数据等，有些测试帐号会在系统开通、网络调整等特殊阶段执行一些操作；

（7）  常见操作时间段维度

**参照正常操作特征，基于上述维度的各类组合建立审计策略：**不满足其中之一或者几个的组合，形成一个或者多个策略，共同确定一个违规行为。

## **5.6   与主动防御系统结合是降低告警的根本途径**

**安全审计基本上可以说是被动行为，是在合规、违规、攻击行为发生之后进行的审核动作。因此，降低事件发生可能性是根治告警量大的根本方法，无论是部署4A、基于零信任理念的下一代4A、绕行控制机制、强认证技术以及提升边界访问控制机制有效性，都将大幅度降低恶意攻击者进入系统的可能性、极大地遏制内部人员违规的意愿，提升违法成本。攻防兼备、以攻为守，才是日志审计的上上策。**
