# 利用Docker将从Heroku迁移至AWS

在 DoorDash，如果没有一个稳健的基础设施来支撑后端系统，我们将不能提供快速可靠的物流服务。不管我们的算法和应用程序如何完美，没有足够的服务器资源来运行他们一切都将无意义。最近我们发现基于 Heroku 的基础设施已经无法满足我们的需求，需要升级到 AWS。借助现在最为火热的 Docker 技术，我们可以在更短的时间更轻松完成这次迁移。

由于 Heroku 在使用上的简单和便利，我们最早将 DoorDash 的应用在上面运行。通过这种方式我们无需关注复杂的底层基础设施，可以将更多的精力集中在开发产品的新功能上。但是使用这种 PaaS 服务并不是没有代价的，随着流量的上升，我们开始遇到 Heroku 上的一些严重问题：  
**性能：** 最为紧迫的一个问题是 Heroku 的服务实例（dynos）的性能表现十分平庸。每一个 dynos 都会消耗大量 CPU 和内存资源（考虑到 Heroku 在一个 EC2 上运行多个 dynos 实例，这点就不奇怪了）。即使在对 Django 应用进行了极度的优化后，我们仍然需要运行比预期更多的 dynos，而且我们不知道接下来需要如何进行扩展。  
**成本：** 使用 Heroku dynos 计算资源的成本十分昂贵。租用一个拥有 1G 内存的 Heroku 2x dyno 价钱大概可以租用一个拥有 3.75G 内存的 Amazon c3.large EC2 实例。  
**可靠性：** 出人意料的是 Heroku 平台一直有着稳定性方面的问题。Heroku 部署 API 几乎每周都会有两次无法提供服务。曾将甚至有一次半天无法提供服务导致我们的一个紧急的线上修复无法进行，造成了客户对我们服务的不信任。  
**控制：** 使用 Heroku，将会失去对服务器的细粒度控制。在服务器中安装用户定制的软件十分困难，并且无法 SSH 到一台主机并对 CPU 和内存问题进行排查。

为了解决这些问题，我们必须从 Heroku 迁移到别的服务商。一个合理的选择是升级到 AWS 的 EC2。Amazon EC2 虚拟服务器提供了更为多样的 CPU 和内存配置，完整的 root 访问权限，以及更低的成本。

AWS 看上去是个有吸引力的解决方案，但是从一个像 Heroku 这样更高层的管理平台进行迁移是一个有挑战的任务。简单来说，需要有大量的管理工作来组建一个服务器的集群和代码的持续部署平台。为了自动化服务器的安装步骤，通常需要安装一个类似于 Chef 或者 Puppet 这样的配置管理软件。但是这类工具通常太重并且需要掌握特定领域的语言。我们需要编写脚本来安装所有的第三方依赖，自动进行配置。此外为了测试代码还需要利用 Vagrant 来建立本地开发环境。所有这些复杂的工作都让我们头疼。

Docker

我们在寻找一个能够迁移到 AWS 上的简单方法的时候一次次听到了一个称为 Docker 的新型虚拟化技术。Docker 可以帮助你把一个应用及其完整的依赖装入一个 container 环境中，并可以在任何 Linux 系统上运行。由于 Docker 是一个可工作系统状态的完整镜像，他可以做到“一次构建，处处运行”。

Docker 容器内封装了 Linux 虚拟文件系统以提供和虚拟机相同的移植性和隔离性。两者最大的区别在于资源使用率，一个虚拟机需要运行一个完整的操作系统，而容器之间可以共享同一个机器上的 Linux 内核，只需要对应用及其依赖进行虚拟化。因此容器量级十分轻，可以在几秒内启动，而虚拟机通常需要几分钟。关于容器更技术方面的解释可以参考 RightScale 的文章。

实现

在了解了 Docker 之后，我们相信可以利用它来加速迁移到 AWS 的过程。我们的计划是在 Amazon EC2 上部署 Docker 容器运行 Django 应用。通过这种方式我们可以用配置 Docker 容器环境来取代配置复杂的 EC2 环境。

构建 Docker 镜像

第一步需要构建一个容纳应用的 Docker 镜像。（解释一下先关术语，Docker 镜像是一个容器的模板，容器是一个镜像运行的实例）。这就意味着我们要编写一个 Dockerfile 配置文件。和 Chef 或者 Puppet 这类需要特定领域语言的复杂配置不同，Dockerfile 的语法十分接近 Bash 命令，并且十分易于理解。

Docker 镜像由不同的层组成，每个镜像都可以成为其他镜像的底层镜像。简单来说你可以利用一个流行的 Ubuntu 或者 CentOS 的镜像为基础进行构建。这些“基镜像”可以在公共的仓库 Docker Hub 中找到，里面包含了很多已经配置好的镜像。

对于我们的 Django 应用来说，主要的工作在于如何将第三方的 Python 依赖正确安装（尤其是那些 C 语言扩展）以及建立复杂的软件栈（例如 web 服务器以及数据库连接池）。通常来说这些步骤十分乏味并包含了大量的试错，但是能够在本地测试所有的环境是十分有益处的。下一次我们就无需任何时间即可建立一个全新的 Docker 容器，这可以极大加快我们的开发步骤。

准备 Docker 环境

第二步是要在 EC2 中建立起 Docker 的运行环境。为了节约时间，我们决定利用 AWS Opsworks 这个包含了内建 Chef 的工具来管理 ECS 实例。尽管我们还是使用到了 Chef，但是并不需要太复杂的配置，因为大部分的配置工作都已经在 Docker 镜像的配置中完成了。

我们的代码部署流程十分简洁，主要是利用 Docker image 服务器从最新的代码库中构建 Docker 镜像并分发到系统实例上，只需要写几个简短的 Chef 脚本来下载最新的 Docker 镜像，并启动一个新的 Docker 容器。![](../Images/c3f74429da0a714a064f2c09451af52e.png)  
我们的 Docker 容器部署流程。

结果

从一开始的设想到最后的实现，从 Heroku 到 AWS 的迁移花费了两个工程师一个月的时间。这包括了学习 Docker，AWS 以及 Chef，将所有东西进行集成与测试的时间。最令我们开心的是一旦我们可以在本地正常运行一个容器，即可在生产环境同样正确的运行。因此我们可以在迁移到过程中实现零故障。

通过使用 Docker + AWS 的环境性能与 Heroku 相比有了两倍的提升。DoorDash 的平均 API 响应时间从 220ms 降到 100ms 以内。后台任务的运行时间也降为原来一半。由于 EC2 硬件的稳定，我们只需要使用一半数目的服务器，基础设施的费用因此大幅下降。对于整个软件栈的控制也极大的帮助了我们，例如我们可以通过 Nginx 在应用服务器前端建立反向代理服务来提高 web API 的吞吐量。

结论

无需多言，我们对迁移到 AWS 的决定十分满意，而 Docker 是我们能够实现快速迁移的关键因素。我们可以提高服务器的性能并获得对软件栈的更多控制，而无需额外的管理开销。能够在本地运行和生产完全相同的环境是一个巨大的收益。另一个收益是可迁移性 —— 和被绑定在一家服务提供商上相比，未来我们可以轻松的在多个服务商之间迁移。

Docker 是一个强大的技术可以让开发者控制如何部署应用，并且极大的削减了 Heroku 这样 PaaS 平台的优势。我们期待着未来还能用它做出些什么来。

—— Alvin Chow
