# 从工具选取到实施部署，数人云教你跑百万压测

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=Mzg5Mjc3MjIyMA==&mid=2247542433&idx=2&sn=ea140f6906c4229fc5485263d5c55a5d&chksm=c03b6cb2f74ce5a4f4b09a69b65f4054f40ff2cce61b03e5279237b3b9f86b03bb7019abd880&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=Mzg5Mjc3MjIyMA==&mid=2247542433&idx=2&sn=ea140f6906c4229fc5485263d5c55a5d&chksm=c03b6cb2f74ce5a4f4b09a69b65f4054f40ff2cce61b03e5279237b3b9f86b03bb7019abd880&scene=27#wechat_redirect)

不久前，数人云联合清华大学交叉信息研究院OCP实验室完成了百万并发压力测试。数人云DCOS提供了整个压测环境的安装部署和运行环境，最终通过10台OCP服务器成功承载了百万并发HTTP请求。3月27日，数人云在京召开“百万并发”线下分享活动，数人云运维负责人庞铮在活动中分享了数人云百万压测实践，公布了此次压测实践的结果以及整套部署流程和方案，把数人云DCOS在此次实验中的真实表现与参会者一一分享。

此次实验设立的目标是在物理资源最小值的情况下完成100万并发处理，整个实验历时一周。庞铮认为，通过此次实验，最大化验证了基于Mesos和Docker技术的数人云DCOS承载高压的能力。在此次实验完成后，数人云把快速进行百万压力测试实验的方法及代码已经开源出来向业内公开，在业界非常有参考价值。

**实验组成：OCP 硬件集群+数人云**

清华大学交叉信息学院的OCP实验室是中国唯一的一座OCP认证的实验室，自2015年9月开始，数人云和清华大学交叉信息研究院助理院长徐葳博士合作在OCP实验室开展数据中心方面的相关研究工作。数人云在数十台OCP服务器上部署了数人云DCOS，并进行了广泛的性能测试。

OCP项目旨在以开源硬件推动IT基础设施不断发展，构建服务器和数据中心。OCP用开源硬件方案解决了数据中心的硬件问题，随之而来的问题是如何解决硬件上的软件和系统的问题。而数人云正是利用开源软件的技术，在硬件、VM、IaaS 上建立了一套软件层面的DCOS（数据中心操作系统）。

本次实验OCP硬件配置如下：

CPU 类型：主频2.20

*   双 CPU 24核 转发端
    
*   双 CPU 20核 加压端
    
*   双 CPU 16核 承压端
    
*   内存：DDR3 1600 / 128G
    

网络：万兆网络

在底层OCP硬件集群之上，数人云解决了软硬件环境隔离、硬件资源抽象、快速部署、弹性伸缩、自动容错以及故障检查六大问题。数人云用开源的容器虚拟化技术，将系统和软件环境打平，把软件层所有的系统依赖软件全都封装在Docker里面。服务器基础环境无需配置上面承载服务的复杂依赖环境，而把应用程序和依赖环境都封装在容器里，在需要迁移的时候非常方便，应用程序的可移植性得到大大提高，非常便于迁移和扩展。

### **如何做百万压测**

前文已经说到，本次实验的目标是在物理资源最小值的情况下完成100万并发处理。庞铮遇到了以下几个挑战：首先，如何加压到100万？也就是说，用什么加压方法？第二，最终需要多少物理资源？架构中每种模块的处理能力是怎样的？

![](../Images/f29df6388a28a525116f902a6f1be296.png)  

红框内是此次压测实验用到的工作集群，而红框外面的是本次实验的辅助功能集群。需要注意的是，10台OCP服务器承载100万HTTP请求中的10台硬件指的是转发端加上承压端的机器，不包括加压端的机器，因为在真实场景中加压端是访问用户本身。

加压工具选择：数人云庞铮最终选择的加压工具是分布式压测工具Locust+Tsung。

Locust是一个简单易用的分布式负载测试工具，主要用来对网站进行负载压力测试。

Tsung是基于Erlang的一个开源分布式多协议的负载测试工具，支持HTTP、WebDAV、SOAP、PostgreSQL、MySQL、LDAP和Jabber/XMPP。

基础部署：

第一步：实验用OCP硬件上架、上电、网络构建、系统安装；  
第二步：本次使用的系统是CentOS 7.1，需要升级内核升级到3.19；  
第三步：使用Ansible部署机器其他底层用软件，包括安装 Docker 1.9.1（ext4+overlay），打开系统默认约束(文件句柄，系统内核和中断优化)等。

部署数人云：

装了标准的系统以及 Docker之后，机器就可以装数人云了。庞铮在现场展示了数人云集群平台的建立步骤，在两分钟之内完成安装。

![](../Images/5d43261ccea0b9d6394a7027934f2414.png)  
数人云DCOS安装完之后，就可以发布压测应用了。首先发布承压端，庞铮选择了Nginx+Lua的组合，它们是高压系统的常用组合，也是数人云秒杀项目原生模组，并可做到客户端获取动态无缓存数据保证压测准确性。

![](../Images/184daf6c3dfe471f7a856cd8d35e1939.png)  

在秒杀模块中，Time是自动从服务器取到的时间戳，events是秒杀服务的数据；event1是秒杀活动的项目，48万是秒杀活动需要持续多少时间。

在数人云上部署程序分三个步骤，首先是项目Docker化，然后调用数人云的API，最后是功能检测。

![](../Images/3b9907daf2291c247b28b5bf454adfdc.png)  

API调用是这样写的：第一个是config.cfg抽象环境变量，然后是get\_token.sh获取验证，最后是nginx\_test.sh发布脚本。

![](../Images/a538b9f43e1470d48103811acb972494.png)

左边是Nginx 优化方案，也取自网络方案。右边是Lua 自带优化，对Lua的处理能力至关重要。

![](../Images/a08346a99bf34bb039b1117d95e42af6.png)

运行nginx\_test.sh脚本后就能得到发布结果，在这里可以通过数人云界面查看发布的应用名、运行状态、发布时间以及集群发布数量，还可以看到一些发布脚本里的参数。

![](../Images/2811e49f2a7389b8629636c4b6c37b91.png)

承压端发布完成后，就可以开始部署加压端。庞铮指出，Locust具有分布式、安装简单以及Web-UI界面三个特点。

### ![](../Images/39025de2688ea950a73a05a001b70dd3.png)

### **选择Loc****ust在进行测试****过程中遇到的问题**

Locust不能对多个服务端进行压测，所以庞铮在它的上面加了Mesos-DNS,用来汇聚压力提供统一的接口给Locust slave。Locust的压测用力文件是tasks.py，每个slave都需要在启动前先去config server拉一下tasks.py。

紧接着就是转发层HA，再接下来就是Nginx，这些全都由数人云发布。

测试Locust步骤

*   测试单核性能：约等于500/s处理
    
*   测试单机性能：40核超线程，约等于1w/s处理  
    

通过测试，庞铮发现Locust有三个缺点，那就是单核加压能力低、支持超线程能力差，以及在大量slave节点连接的情况下，Master端不稳定。

![](../Images/7114a5fb0afcc0be692fe7affc7d7076.png)  

如上图可以看到，压测资源分为两个组，A组20个物理核机器有20台，slave能压到的能力是20 W/S。B组16个物理核机器有15台，可以压到12W/S，整个加压组的能力为32 W/S。

![](../Images/f645a284c350acb4a8c1820daa52eb5c.png)  

#### **压测第一步**

得到承压单机Nginx+Lua（HOST）能力是19.7w/s。

![](../Images/04cbaf43a79350305c99380e3e7bab2d.png)  

在考虑 HA 的优化，然后是单台测试，最终选择了keepalive。

![](../Images/0d1649c0fa4e9dd6bf3a47f9bd94f0e8.png)  
![](../Images/60ec6e572d759ec524b7932b6f0ec989.png)  
![](../Images/b0f4cfa6804ba51ca85ad7d6a05d1170.png)  

#### **压测第二步**

单机非超线程最后测出来的结果是22.7万，95%做到一秒之内的响应。庞铮发现，Ha的排队现象非常多，可持续加压能力非常差，几分钟之内就出现严重的堵塞。同时，CPU有几个是持满的，说明它的分配不均匀，有一些模块是需要有统一的模块调度，导致HA无法持续保持高性能处理。

![](../Images/9f2699d68bca5346eeb9b4795262ad9e.png)  
![](../Images/b8ddddf6761c8c0a1172622fbaf527d4.png)  
![](../Images/d2315f580c10e920bab08ec57f0e1b03.png)  

单机超线程比非超线程有一些衰减，测出来的结果是21.9万，95%可以做到一秒内响应，但HA的排队请求少很多，CPU的压力也平均了很多，测试结果非常稳定。

![](../Images/e6217d1ef26c1add8cefb1ee9e6ccc37.png)  
![](../Images/b67918fed0f55549d45b86de754cebf6.png)  
![](../Images/f824d41fc83f74a43c51dfe871e1c1f4.png)  

HA超线程的非Docker，测出的结果是27万。Docker情况下确实有一定衰减，可以明显的看到99%的请求在一秒之内处理了，已经可以达到企业级使用的标准。

现在，已知加压总能力是32w/s，单机 Nginx + Lua 是19w/s，转发层单机 Haproxy 最大能力 27w/s，那么，单机 Nginx + Lua NAT模式的能力是怎样的呢？

![](../Images/875e2a4fd48f92aa087d6ce73c9a2ffe.png)  
![](../Images/9eba904594679fc0ec798a40fbdd7006.png)  

可以看出之前单机Nginx HOST网络模式下发测试结果是19.7万。Nginx模式加了HA再加NAT模式，衰减之后是14.3万，CPU压力几乎是100%。

![](../Images/44e82656a384eadd78b49f75ab503a87.png)  

由于之前使用的 Locust对于超线程支持以及本身性能问题，无法在现有硬件资源基础上达到需求，改用Tsung进行测试。
