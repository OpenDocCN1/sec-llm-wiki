Pod优先级、抢占

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  

Pod优先级、抢占功能，在Kubernetes v1.8引入，在v1.11版本进入beta状态，并在v1.14版本进入GA阶段，已经是一个成熟的特性了。  
顾名思义，Pod优先级、抢占功能，通过将应用细分为不同的优先级，将资源优先提供给高优先级的应用，从而提高了资源可用率，同时保障了高优先级的服务质量。  
我们先来简单使用下Pod优先级、抢占功能。  
集群版本是v1.14，因此feature PodPriority默认是开启的。抢占模式的使用分为两步：  

1.  定义PriorityClass，不同PriorityClass的value不同，value越大优先级越高。
    
2.  创建Pod，并设置Pod的priorityClassName字段为期待的PriorityClass。
    

  
创建PriorityClass

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  

如下，先创建两个PriorityClass：high-priority和low-priority，其value分别为1000000、10。  
需要注意的是，要将low-priority的globalDefault设置为了true，因此low-priority即为集群默认的PriorityClass，任何没有配置priorityClassName字段的Pod，其优先级都将设置为low-priority的10。一个集群只能有一个默认的PriorityClass。如果没有设置默认PriorityClass，则没有配置PriorityClassName的Pod的优先级为0。  

```
1.  `apiVersion: scheduling.k8s.io/v1`
    
2.  `kind: PriorityClass`
    
3.  `metadata:`
    
4.  `  name: high-priority`
    
5.  `value: 1000000`
    
6.  `globalDefault: false`
    
7.  `description: "for high priority pod"`
    
8.  `---`
    
9.  `apiVersion: scheduling.k8s.io/v1`
    
10.  `kind: PriorityClass`
     
11.  `metadata:`
     
12.  `  name: low-priority`
     
13.  `value: 10`
     
14.  `globalDefault: true`
     
15.  `description: "for low priority pod"`
     
```

  
创建后查看下系统当前的PriorityClass。  

```
1.  `kubectl get priorityclasses.scheduling.k8s.io`
    
2.  `NAME                      VALUE        GLOBAL-DEFAULT   AGE`
    
3.  `high-priority             1000000      false            47m`
    
4.  `low-priority              10           true             47m`
    
5.  `system-cluster-critical   2000000000   false            254d`
    
6.  `system-node-critical      2000001000   false            254d`
    
```

  
可以看到，除了上面创建的两个PriorityClass，默认系统还内置了system-cluster-critical、system-node-critical用于高优先级的系统任务。  
设置Pod的PriorityClassName

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  

为了方便验证，这里使用了扩展资源。为节点x1设置了扩展资源example.com/foo的容量为1。  

```
1.  `curl -k --header "Authorization: Bearer ${token}" --header "Content-Type: application/json-patch+json" \`
    
2.  `--request PATCH \`
    
3.  `--data '[{"op": "add", "path": "/status/capacity/example.com~1foo", "value": "1"}]' \`
    
4.  `https://{apiServerIP}:{apiServerPort}/api/v1/nodes/x1/status`
    
```

  
查看下x1的allocatable和capacity，可以看到x1上有1个example.com/foo资源。  

```
1.  `Capacity:`
    
2.  ` cpu:                2`
    
3.  ` example.com/foo:    1`
    
4.  ` hugepages-2Mi:      0`
    
5.  ` memory:             4040056Ki`
    
6.  ` pods:               110`
    
7.  `Allocatable:`
    
8.  ` cpu:                2`
    
9.  ` example.com/foo:    1`
    
10.  ` hugepages-2Mi:      0`
     
11.  ` memory:             3937656Ki`
     
12.  ` pods:               110`
     
```

  
我们先创建Deployment nginx，它会请求1个example.com/foo资源，但是我们没有设置PriorityClassName，因此Pod的优先级将是默认的low-priority指定的10。  

```
1.  `template:`
    
2.  `    spec:`
    
3.  `      containers:`
    
4.  `      - image: nginx`
    
5.  `        imagePullPolicy: Always`
    
6.  `        name: nginx`
    
7.  `        resources:`
    
8.  `          limits:`
    
9.  `            example.com/foo: "1"`
    
10.  `          requests:`
     
11.  `            example.com/foo: "1"`
     
```

  
然后再创建Deployment debian，它并没有请求example.com/foo资源。  

```
1.  `  template:`
    
2.  `    spec:`
    
3.  `      containers:`
    
4.  `      - args:`
    
5.  `        - bash`
    
6.  `        image: debian`
    
7.  `        name: debian`
    
8.  `        resources:`
    
9.  `          limits:`
    
10.  `            example.com/foo: "0"`
     
11.  `          requests:`
     
12.  `            example.com/foo: "0"`
     
13.  `        priorityClassName: high-priority`
     
```

  
此时两个Pod都可以正常启动。  
**开始抢占**  
我们将Deployment debian的example.com/foo请求量改为1，并将priorityClassName设置为high-priority。  

```
1.  `  template:`
    
2.  `    spec:`
    
3.  `      containers:`
    
4.  `      - args:`
    
5.  `        - bash`
    
6.  `        image: debian`
    
7.  `        name: debian`
    
8.  `        resources:`
    
9.  `          limits:`
    
10.  `            example.com/foo: "1"`
     
11.  `          requests:`
     
12.  `            example.com/foo: "1"`
     
13.  `        priorityClassName: high-priority`
     
```

  
此时，由于集群中只有x1上有1个example.com/foo资源，而且debian的优先级更高，因此scheduler会开始抢占。如下是观察到的Pod过程。  

```
1.  `kubectl get pods -o wide -w`
    
2.  `NAME                      READY   STATUS    AGE     IP             NODE       NOMINATED NODE`
    
3.  `debian-55d94c54cb-pdfmd   1/1     Running   3m53s   10.244.4.178   x201       <none>`
    
4.  `nginx-58dc57fbff-g5fph    1/1     Running   2m4s    10.244.3.28    x1         <none>`
    
5.  `// 此时Deployment debian开始Recreate`
    
6.  `debian-55d94c54cb-pdfmd   1/1     Terminating   4m49s   10.244.4.178   x201       <none>`
    
7.  `debian-55d94c54cb-pdfmd   0/1     Terminating   5m21s   10.244.4.178   x201       <none>`
    
8.  `debian-55d94c54cb-pdfmd   0/1     Terminating   5m22s   10.244.4.178   x201       <none>`
    
9.  `debian-55d94c54cb-pdfmd   0/1     Terminating   5m22s   10.244.4.178   x201       <none>`
    
10.  `// example.com/foo不满足，阻塞`
     
11.  `debian-5bc46885dd-rvtwv   0/1     Pending       0s      <none>         <none>     <none>`
     
12.  `debian-5bc46885dd-rvtwv   0/1     Pending       0s      <none>         <none>     <none>`
     
13.  `// scheduler判断将x1上的Pod挤出后可以满足debian Pod的需求，设置NOMINATED为x1`
     
14.  `debian-5bc46885dd-rvtwv   0/1     Pending       0s      <none>         <none>     x1`
     
15.  `// sheduler开始挤出Pod nginx`
     
16.  `nginx-58dc57fbff-g5fph    1/1     Terminating   3m33s   10.244.3.28    x1         <none>`
     
17.  `// Pod nginx等待。优先级低啊，没办法。`
     
18.  `nginx-58dc57fbff-29rzw    0/1     Pending       0s      <none>         <none>     <none>`
     
19.  `nginx-58dc57fbff-29rzw    0/1     Pending       0s      <none>         <none>     <none>`
     
20.  `// graceful termination period，优雅退出`
     
21.  `nginx-58dc57fbff-g5fph    0/1     Terminating   3m34s   10.244.3.28    x1         <none>`
     
22.  `nginx-58dc57fbff-g5fph    0/1     Terminating   3m37s   10.244.3.28    x1         <none>`
     
23.  `nginx-58dc57fbff-g5fph    0/1     Terminating   3m37s   10.244.3.28    x1         <none>`
     
24.  `// debian NODE绑定为x1`
     
25.  `debian-5bc46885dd-rvtwv   0/1     Pending       5s      <none>         x1         x1`
     
26.  `// 抢占到资源，启动`
     
27.  `debian-5bc46885dd-rvtwv   0/1     ContainerCreating   5s      <none>         x1         <none>`
     
28.  `debian-5bc46885dd-rvtwv   1/1     Running             14s     10.244.3.29    x1         <none>`
     
```

  
君子：Non-preempting PriorityClasses

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  

Kubernetes v1.15为PriorityClass添加了一个字段PreemptionPolicy，当设置为Never时，该Pod将不会抢占比它优先级低的Pod，只是调度的时候，会优先调度（参照PriorityClass的value）。  

```
1.  `apiVersion: scheduling.k8s.io/v1`
    
2.  `kind: PriorityClass`
    
3.  `metadata:`
    
4.  `  name: high-priority-nonpreempting`
    
5.  `value: 1000000`
    
6.  `preemptionPolicy: Never`
    
7.  `globalDefault: false`
    
```

  
所以我把这种PriorityClass叫做“君子”，因为他只是默默凭本事（Priority）排队，不会强抢别人的资源。官网给出一个适合的例子是 data science workload。  
对比Cluster Autoscaler

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  

云上Kubernetes在集群资源不足时，可以通过Cluster Autoscaler自动对Node扩容，即向云厂商申请更多的Node，并添加到集群中，从而提供更多资源。  
但这种做法不足的地方是：  

*   云下场景不易实施
    
*   增加Node要多花钱
    
*   不是立即的，需要时间
    

  
如果用户能够比较明确的划分应用的优先级，在资源不足的时候通过抢占低优先级Pod的资源，可以更好的提高资源利用率、提高服务质量。
