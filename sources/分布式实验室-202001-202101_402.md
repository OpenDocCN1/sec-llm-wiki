exporter相关部署

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  
安装exporter：  

```
1.  `[[root@controller2 opt]# https://github.com/prometheus/mysqld_exporter/releases/download/v0.10.0/mysqld_exporter-0.10.0.linux-amd64.tar.gz`
    
2.  `[root@controller2 opt]# tar -xf mysqld_exporter-0.10.0.linux-amd64.tar.gz`
    
```

  
添加MySQL账户：  

```
1.  `GRANT SELECT, PROCESS, SUPER, REPLICATION CLIENT, RELOAD ON *.* TO 'exporter'@'%' IDENTIFIED BY 'localhost';`
    
2.  `flush privileges;`
    
```

  
编辑配置文件：  

```
1.  `[root@controller2 mysqld_exporter-0.10.0.linux-amd64]# cat /opt/mysqld_exporter-0.10.0.linux-amd64/.my.cnf`
    
2.  `[client]`
    
3.  `user=exporter`
    
4.  `password=123456`
    
```

  
设置配置文件：  

```
1.  `[root@controller2 mysqld_exporter-0.10.0.linux-amd64]# cat /etc/systemd/system/mysql_exporter.service`
    
2.  `[Unit]`
    
3.  `Description=mysql Monitoring System`
    
4.  `Documentation=mysql Monitoring System`
    
5.  
    
6.  `[Service]`
    
7.  `ExecStart=/opt/mysqld_exporter-0.10.0.linux-amd64/mysqld_exporter \`
    
8.  `         -collect.info_schema.processlist \`
    
9.  `         -collect.info_schema.innodb_tablespaces \`
    
10.  `         -collect.info_schema.innodb_metrics  \`
     
11.  `         -collect.perf_schema.tableiowaits \`
     
12.  `         -collect.perf_schema.indexiowaits \`
     
13.  `         -collect.perf_schema.tablelocks \`
     
14.  `         -collect.engine_innodb_status \`
     
15.  `         -collect.perf_schema.file_events \`
     
16.  `         -collect.info_schema.processlist \`
     
17.  `         -collect.binlog_size \`
     
18.  `         -collect.info_schema.clientstats \`
     
19.  `         -collect.perf_schema.eventswaits \`
     
20.  `         -config.my-cnf=/opt/mysqld_exporter-0.10.0.linux-amd64/.my.cnf`
     
21.  
     
22.  `[Install]`
     
23.  `WantedBy=multi-user.target`
     
```

  
添加配置到Prometheus server：  

```
1.  `- job_name: 'mysql'`
    
2.  `    static_configs:`
    
3.  `     - targets: ['192.168.1.11:9104','192.168.1.12:9104']`
    
```

  
测试看有没有返回数值：  

```
1.  `http://192.168.1.12:9104/metrics`
    
```

监控相关指标

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  
在做任何一个东西监控的时候，我们要时刻明白我们要监控的是什么，指标是啥才能更好的去监控我们的服务，在MySQL里面我们通常可以通过以下指标去衡量MySQL的运行情况：MySQL主从运行情况、查询吞吐量、慢查询情况、连接数情况、缓冲池使用情况以及查询执行性能等。  
**主从复制运行指标****主从复制线程监控**  
大部分情况下，很多企业使用的都是主从复制的环境，监控两个线程是非常重要的，在MySQL里面我们通常是通过命令：  

```
1.  `MariaDB [(none)]> show slave status\G;`
    
2.  `*************************** 1. row ***************************`
    
3.  `               Slave_IO_State: Waiting for master to send event`
    
4.  `                  Master_Host: 172.16.1.1`
    
5.  `                  Master_User: repl`
    
6.  `                  Master_Port: 3306`
    
7.  `                Connect_Retry: 60`
    
8.  `              Master_Log_File: mysql-bin.000045`
    
9.  `          Read_Master_Log_Pos: 72904854`
    
10.  `               Relay_Log_File: mariadb-relay-bin.000127`
     
11.  `                Relay_Log_Pos: 72905142`
     
12.  `        Relay_Master_Log_File: mysql-bin.000045`
     
13.  `             Slave_IO_Running: Yes`
     
14.  `            Slave_SQL_Running: Yes`
     
```

  
#SlaveIORunning、SlaveSQLRunning两个线程正常那么说明我们的复制集群是健康状态的。  
MySQLD Exporter中返回的样本数据中通过mysqlslavestatusslavesql\_running来获取主从集群的健康状况。  

```
1.  `# HELP mysql_slave_status_slave_sql_running Generic metric from SHOW SLAVE STATUS.`
    
2.  `# TYPE mysql_slave_status_slave_sql_running untyped`
    
3.  `mysql_slave_status_slave_sql_running{channel_name="",connection_name="",master_host="172.16.1.1",master_uuid=""} 1`
    
```

  
**主从复制落后时间**  
在使用show slave status里面还有一个关键的参数SecondsBehindMaster。SecondsBehindMaster表示slave上SQL thread与IO thread之间的延迟，我们都知道在MySQL的复制环境中，slave先从master上将binlog拉取到本地（通过IO thread），然后通过SQL thread将binlog重放，而SecondsBehindMaster表示本地relaylog中未被执行完的那部分的差值。  
所以如果slave拉取到本地的relaylog（实际上就是binlog，只是在slave上习惯称呼relaylog而已）都执行完，此时通过show slave status看到的会是0。  

```
1.  `Seconds_Behind_Master: 0`
    
```

  
MySQLD Exporter中返回的样本数据中通过mysqlslavestatussecondsbehind\_master来获取相关状态。  

```
1.  `# HELP mysql_slave_status_seconds_behind_master Generic metric from SHOW SLAVE STATUS.`
    
2.  `# TYPE mysql_slave_status_seconds_behind_master untyped`
    
3.  `mysql_slave_status_seconds_behind_master{channel_name="",connection_name="",master_host="172.16.1.1",master_uuid=""} 0`
    
```

  
**查询吞吐量**  
说到吞吐量，那么我们如何从那方面来衡量呢？  
通常来说我们可以根据MySQL的插入、查询、删除、更新等操作来衡量。  
为了获取吞吐量，MySQL有一个名为Questions的内部计数器（根据MySQL用语，这是一个服务器状态变量），客户端每发送一个查询语句，其值就会加一。由Questions指标带来的以客户端为中心的视角常常比相关的Queries计数器更容易解释。作为存储程序的一部分，后者也会计算已执行语句的数量，以及诸如PREPARE和DEALLOCATE PREPARE指令运行的次数，作为服务器端预处理语句的一部分。可以通过命令来查询：  

```
1.  `MariaDB [(none)]> SHOW GLOBAL STATUS LIKE "Questions";`
    
2.  `+---------------+-------+`
    
3.  `| Variable_name | Value |`
    
4.  `+---------------+-------+`
    
5.  `| Questions     | 15071 |`
    
6.  `+---------------+-------+`
    
```

  
MySQLD Exporter中返回的样本数据中通过mysqlglobalstatus\_questions反映当前Questions计数器的大小：  

```
1.  `# HELP mysql_global_status_questions Generic metric from SHOW GLOBAL STATUS.`
    
2.  `# TYPE mysql_global_status_questions untyped`
    
3.  `mysql_global_status_questions 13253`
    
```

  
当然由于Prometheus具有非常丰富的查询语言，我们可以通过这个累加的计数器来查询某一段时间内的查询增长率情况，可以做相关的阈值告警处理、例如以下查询2分钟时间内的查询情况：  

```
1.  `rate(mysql_global_status_questions[2m])`
    
```

  
当然上面是总量，我们可以分别从监控读、写指令的分解情况，从而更好地理解数据库的工作负载、找到可能的瓶颈。通常，读取查询会由Com\_select指标抓取，而写入查询则可能增加三个状态变量中某一个的值，这取决于具体的指令：  

```
1.  `Writes = Com_insert + Com_update + Com_delete`
    
```

  
下面我们通过命令获取插入的情况：  

```
1.  `MariaDB [(none)]> SHOW GLOBAL STATUS LIKE "Com_insert";`
    
2.  `+---------------+-------+`
    
3.  `| Variable_name | Value |`
    
4.  `+---------------+-------+`
    
5.  `| Com_insert    | 10578 |`
    
6.  `+---------------+-------+`
    
```

  
从MySQLD Exporter的/metrics返回的监控样本中，可以通过globalstatuscommands\_total获取当前实例各类指令执行的次数：  

```
1.  `# HELP mysql_global_status_commands_total Total number of executed MySQL commands.`
    
2.  `# TYPE mysql_global_status_commands_total counter`
    
3.  `mysql_global_status_commands_total{command="create_trigger"} 0`
    
4.  `mysql_global_status_commands_total{command="create_udf"} 0`
    
5.  `mysql_global_status_commands_total{command="create_user"} 1`
    
6.  `mysql_global_status_commands_total{command="create_view"} 0`
    
7.  `mysql_global_status_commands_total{command="dealloc_sql"} 0`
    
8.  `mysql_global_status_commands_total{command="delete"} 3369`
    
9.  `mysql_global_status_commands_total{command="delete_multi"} 0`
    
```

  
**慢查询性能**  
查询性能方面，慢查询也是查询告警的一个重要的指标。MySQL还提供了一个Slowqueries的计数器，当查询的执行时间超过longquerytime的值后，计数器就会+1，其默认值为10秒，可以通过以下指令在MySQL中查询当前longquery\_time的设置：  

```
1.  `MariaDB [(none)]> SHOW VARIABLES LIKE 'long_query_time';`
    
2.  `+-----------------+-----------+`
    
3.  `| Variable_name   | Value     |`
    
4.  `+-----------------+-----------+`
    
5.  `| long_query_time | 10.000000 |`
    
6.  `+-----------------+-----------+`
    
7.  `1 row in set (0.00 sec)`
    
```

  
当然我们也可以修改时间：  

```
1.  `MariaDB [(none)]> SET GLOBAL long_query_time = 5;`
    
2.  `Query OK, 0 rows affected (0.00 sec)`
    
```

  
然后我们而已通过SQL语言查询MySQL实例中Slow\_queries的数量：  

```
1.  `MariaDB [(none)]> SHOW GLOBAL STATUS LIKE "Slow_queries";`
    
2.  `+---------------+-------+`
    
3.  `| Variable_name | Value |`
    
4.  `+---------------+-------+`
    
5.  `| Slow_queries  | 0     |`
    
6.  `+---------------+-------+`
    
7.  `1 row in set (0.00 sec)`
    
```

  
MySQLD Exporter返回的样本数据中，通过mysqlglobalstatusslowqueries指标展示当前的Slow\_queries的值：  

```
1.  `# HELP mysql_global_status_slow_queries Generic metric from SHOW GLOBAL STATUS.`
    
2.  `# TYPE mysql_global_status_slow_queries untyped`
    
3.  `mysql_global_status_slow_queries 0`
    
```

  
同样的，更具根据Prometheus慢查询语句我们也可以查询到他某段时间内的增长率：  

```
1.  `rate(mysql_global_status_slow_queries[5m])`
    
```

  
**连接数监控**  
监控客户端连接情况相当重要，因为一旦可用连接耗尽，新的客户端连接就会遭到拒绝。MySQL默认的连接数限制为151。  

```
1.  `MariaDB [(none)]> SHOW VARIABLES LIKE 'max_connections';`
    
2.  `+-----------------+-------+`
    
3.  `| Variable_name   | Value |`
    
4.  `+-----------------+-------+`
    
5.  `| max_connections | 151   |`
    
6.  `+-----------------+-------+`
    
```

  
当然我们可以通过修改配置文件的形式来增加这个数值。与之对应的就是当前连接数量，当我们当前连接出来超过系统设置的最大值之后常会出现我们看到的Too many connections（连接数过多），下面我查找一下当前连接数：  

```
1.  `MariaDB [(none)]> SHOW GLOBAL STATUS LIKE "Threads_connected";`
    
2.  `+-------------------+-------+`
    
3.  `| Variable_name     | Value |`
    
4.  `+-------------------+-------+`
    
5.  `| Threads_connected | 41     |`
    
6.  `+-------------------+-------`
    
```

  
当然MySQL还提供Threads\_running这个指标，帮助你分隔在任意时间正在积极处理查询的线程与那些虽然可用但是闲置的连接。  

```
1.  `MariaDB [(none)]> SHOW GLOBAL STATUS LIKE "Threads_running";`
    
2.  `+-----------------+-------+`
    
3.  `| Variable_name   | Value |`
    
4.  `+-----------------+-------+`
    
    `| Threads_running | 10     |`
    
5.  `+-----------------+-------+`
    
```

  
如果服务器真的达到maxconnections限制，它就会开始拒绝新的连接。在这种情况下，Connectionerrorsmaxconnections指标就会开始增加，同时，追踪所有失败连接尝试的Aborted\_connects指标也会开始增加。  
MySQLD Exporter返回的样本数据中：  

```
1.  `# HELP mysql_global_variables_max_connections Generic gauge metric from SHOW GLOBAL VARIABLES.`
    
2.  `# TYPE mysql_global_variables_max_connections gauge`
    
3.  `mysql_global_variables_max_connections 151`
    
```

  
表示最大连接数：  

```
1.  `# HELP mysql_global_status_threads_connected Generic metric from SHOW GLOBAL STATUS.`
    
2.  `# TYPE mysql_global_status_threads_connected untyped`
    
3.  `mysql_global_status_threads_connected 41`
    
```

  
表示当前的连接数：  

```
1.  `# HELP mysql_global_status_threads_running Generic metric from SHOW GLOBAL STATUS.`
    
2.  `# TYPE mysql_global_status_threads_running untyped`
    
3.  `mysql_global_status_threads_running 1`
    
```

  
表示当前活跃的连接数：  

```
1.  `# HELP mysql_global_status_aborted_connects Generic metric from SHOW GLOBAL STATUS.`
    
2.  `# TYPE mysql_global_status_aborted_connects untyped`
    
3.  `mysql_global_status_aborted_connects 31`
    
```

  
累计所有的连接数：  

```
1.  `# HELP mysql_global_status_connection_errors_total Total number of MySQL connection errors.`
    
2.  `# TYPE mysql_global_status_connection_errors_total counter`
    
3.  `mysql_global_status_connection_errors_total{error="internal"} 0`
    
4.  `#服务器内部引起的错误、如内存硬盘等`
    
5.  `mysql_global_status_connection_errors_total{error="max_connections"} 0`
    
6.  `#超出连接处引起的错误`
    
```

  
当然根据prom表达式，我们可以查询当前剩余可用的连接数：  

```
1.  `mysql_global_variables_max_connections - mysql_global_status_threads_connected`
    
```

  
查询MySQL拒绝连接数：  

```
1.  `mysql_global_status_aborted_connects`
    
```

  
**缓冲池情况**  
MySQL默认的存储引擎InnoDB使用了一片称为缓冲池的内存区域，用于缓存数据表与索引的数据。缓冲池指标属于资源指标，而非工作指标，前者更多地用于调查（而非检测）性能问题。如果数据库性能开始下滑，而磁盘 I/O 在不断攀升，扩大缓冲池往往能带来性能回升。  
默认设置下，缓冲池的大小通常相对较小，为128MB。不过，MySQL建议可将其扩大至专用数据库服务器物理内存的80%大小。我们可以查看一下：  

```
1.  `MariaDB [(none)]> show global variables like 'innodb_buffer_pool_size';`
    
2.  `+-------------------------+-----------+`
    
3.  `| Variable_name           | Value     |`
    
4.  `+-------------------------+-----------+`
    
5.  `| innodb_buffer_pool_size | 134217728 |`
    
6.  `+-------------------------+-----------+`
    
```

  
MySQLD Exporter返回的样本数据中，使用mysqlglobalvariablesinnodbbufferpoolsize来表示：  

```
1.  `# HELP mysql_global_variables_innodb_buffer_pool_size Generic gauge metric from SHOW GLOBAL VARIABLES.`
    
2.  `# TYPE mysql_global_variables_innodb_buffer_pool_size gauge`
    
3.  `mysql_global_variables_innodb_buffer_pool_size 1.34217728e+08`
    
```

  
Innodbbufferpoolreadrequests记录了正常从缓冲池读取数据的请求数量。可以通过以下指令查看：  

```
1.  `MariaDB [(none)]> SHOW GLOBAL STATUS LIKE "Innodb_buffer_pool_read_requests";`
    
2.  `+----------------------------------+-------------+`
    
3.  `| Variable_name                    | Value       |`
    
4.  `+----------------------------------+-------------+`
    
5.  `| Innodb_buffer_pool_read_requests | 38465 |`
    
6.  `+----------------------------------+-------------+`
    
```

  
MySQLD Exporter返回的样本数据中，使用mysqlglobalstatusinnodbbufferpoolread\_requests来表示：  

```
1.  `# HELP mysql_global_status_innodb_buffer_pool_read_requests Generic metric from SHOW GLOBAL STATUS.`
    
2.  `# TYPE mysql_global_status_innodb_buffer_pool_read_requests untyped`
    
3.  `mysql_global_status_innodb_buffer_pool_read_requests 2.7711547168e+10`
    
```

  
当缓冲池无法满足时，MySQL只能从磁盘中读取数据。Innodbbufferpoolreads即记录了从磁盘读取数据的请求数量。通常来说从内存中读取数据的速度要比从磁盘中读取快很多，因此，如果Innodbbufferpoolreads的值开始增加，可能意味着数据库的性能有问题。可以通过以下只能查看Innodbbufferpool\_reads的数量：  

```
1.  `MariaDB [(none)]> SHOW GLOBAL STATUS LIKE "Innodb_buffer_pool_reads";`
    
2.  `+--------------------------+-------+`
    
3.  `| Variable_name            | Value |`
    
4.  `+--------------------------+-------+`
    
5.  `| Innodb_buffer_pool_reads | 138  |`
    
6.  `+--------------------------+-------+`
    
7.  `1 row in set (0.00 sec)`
    
```

  
MySQLD Exporter返回的样本数据中，使用mysqlglobalstatusinnodbbufferpoolread\_requests来表示：  

```
1.  `# HELP mysql_global_status_innodb_buffer_pool_reads Generic metric from SHOW GLOBAL STATUS.`
    
2.  `# TYPE mysql_global_status_innodb_buffer_pool_reads untyped`
    
3.  `mysql_global_status_innodb_buffer_pool_reads 138`
    
```

  
通过以上监控指标，以及实际监控的场景，我们可以利用PromQL快速建立多个监控项。可以查看两分钟内读取磁盘的增长率的增长率：  

```
1.  `rate(mysql_global_status_innodb_buffer_pool_reads[2m])`
    
```

  
**简单的告警规则**  
除了相关模板之外，没有告警规则那么我们的监控就是不完美的，下面列一下我们的监控告警规则。  

```
1.  `groups:`
    
2.  `- name: MySQL-rules`
    
3.  `  rules:`
    
4.  `  - alert: MySQL Status `
    
5.  `    expr: up == 0`
    
6.  `    for: 5s `
    
7.  `    labels:`
    
8.  `      severity: warning`
    
9.  `    annotations:`
    
10.  `      summary: "{{$labels.instance}}: MySQL has stop !!!"`
     
11.  `      description: "检测MySQL数据库运行状态"`
     
12.  
     
13.  `  -alert: MySQL Slave IO Thread Status`
     
14.  `    expr: mysql_slave_status_slave_io_running == 0`
     
15.  `    for: 5s `
     
16.  `    labels:`
     
17.  `      severity: warning`
     
18.  `    annotations: `
     
19.  `      summary: "{{$labels.instance}}: MySQL Slave IO Thread has stop !!!"`
     
20.  `      description: "检测MySQL主从IO线程运行状态"`
     
21.  
     
22.  `  -alert: MySQL Slave SQL Thread Status `
     
23.  `    expr: mysql_slave_status_slave_sql_running == 0`
     
24.  `    for: 5s `
     
25.  `    labels:`
     
26.  `      severity: warning`
     
27.  `    annotations: `
     
28.  `      summary: "{{$labels.instance}}: MySQL Slave SQL Thread has stop !!!"`
     
29.  `      description: "检测MySQL主从SQL线程运行状态"`
     
30.  
     
31.  `  -alert: MySQL Slave Delay Status `
```
