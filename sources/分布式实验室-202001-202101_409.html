方案调研


Kubernetes Service config

http-svc：


  1. apiVersion: v1
  2. kind: Service
  3. metadata:
  4.   labels:
  5.     app: cyh-nginx
  6.   name: http-svc
  7.   namespace: cyh
  8. spec:
  9.   ports:
  10.   - name: http
  11.     port: 80
  12.     protocol: TCP
  13.     targetPort: 80
  14.   selector:
  15.     app: cyh-nginx
  16.   sessionAffinity: None
  17.   type: ClusterIP

https-svc：

  1. apiVersion: v1
  2. kind: Service
  3. metadata:
  4.   labels:
  5.     app: cyh-nginx
  6.   name: https-svc
  7.   namespace: cyh
  8. spec:
  9.   ports:
  10.   - name: https
  11.     port: 443
  12.     protocol: TCP
  13.     targetPort: 443
  14.   selector:
  15.     app: cyh-nginx
  16.   sessionAffinity: None
  17.   type: ClusterIP

准备两个Service是为了Ingress Controller配置路由路由到不同的SVC上，进而选择不同的后端（80/443）。

HAProxy Ingress Controller

http-ingress config：

  1. apiVersion: extensions/v1beta1
  2. kind: Ingress
  3. metadata:
  4.   annotations:
  5.     ingress.kubernetes.io/config-backend: ""
  6.     ingress.kubernetes.io/ssl-redirect: "false"
  7.     kubernetes.io/ingress.class: haproxy
  8.   labels:
  9.     app: cyh-nginx
  10.   name: http-ingress
  11.   namespace: cyh
  12. spec:
  13.   rules:
  14.   - host: cyh.test.com
  15.     http:
  16.       paths:
  17.       - backend:
  18.           serviceName: http-svc
  19.           servicePort: 80
  20.         path: /

https-ingress config：

  1. apiVersion: extensions/v1beta1
  2. kind: Ingress
  3. metadata:
  4.   annotations:
  5.     ingress.kubernetes.io/config-backend: ""
  6.     ingress.kubernetes.io/ssl-passthrough: "false"
  7.     ingress.kubernetes.io/ssl-redirect: "false"
  8.     kubernetes.io/ingress.class: haproxy
  9.   labels:
  10.     app: cyh-nginx
  11.   name: https-ingress
  12.   namespace: cyh
  13. spec:
  14.   rules:
  15.   - host: cyh.test.com
  16.     http:
  17.       paths:
  18.       - backend:
  19.           serviceName: https-svc
  20.           servicePort: 443
  21.         path: /
  22.   tls:
  23.   - hosts:
  24.     - cyh.test.com
  25.     secretName: cyh-nginx-crt

应用之后查看HAProxy Ingress的关键配置如下：

  1. ........
  2. acl host-cyh.test.com var(txn.hdr_host) -i cyh.test.com cyh.test.com:80 cyh.test.com:443 
  3. ........
  4. use_backend cyh-http-svc if host-cyh.test.com

上述配置是http-ingress先创建，https-ingress后创建的结果。从上述的配置可以看出，要想实现http和https分流需要通过acl进行判断当前的请求是http请求还是https请求，如：

  1. ........
  2. acl host-cyh.test.com var(txn.hdr_host) -i cyh.test.com cyh.test.com:80 cyh.test.com:443 
  3. acl https-cyh.test.com var(txn.hdr_host) -i cyh.test.com cyh.test.com:80 cyh.test.com:443  
  4. ........

  6. use_backend https-ingress-443 if from-https https-cyh.test.com
  7. use_backend cyh-http-svc if host-cyh.test.com

理想是丰满的，现实却是残酷的。当前HAProxy Ingress并没有类似：

  1. ingress.kubernetes.io/config-frontend: ""

的annotations。但我们能否可以通过HAProxy Ingress ConfigMap自定义frontend acl及usebackend规则呢。其实也不行，经验证当ConfigMap上配置frontend acl及usebackend规则时，HAProxy reload将会抛出如下WARNING：

  1.  rule placed after a 'use_backend' rule will still be processed before.

这意思就是ConfigMap上配置的frontend acl及use_backend和已有的冲突了不会生效；即使进去查看haproxy.conf文件确实配置上了，但其实HAProxy使用的配置已被加载至内存，可以参考haproxy-ingress-issue-frontend[1]。另外也可以从HAProxy Ingress Controller的源码：

洞悉frontend的配置都是代码直接控制。并没有自定义入口。为此HAProxy Ingress无法实现http和https分流。

Nginx Ingress Controller

负载均衡服务器除了HAProxy，还有应用广泛的Nginx。对Nginx Ingress Controller的Ingress方案调研了一番能做切入点的只有：

  1. nginx.org/location-snippets
  2. nginx.org/server-snippets

这两组合来自定义Location和Server，但Location只能根据path来匹配，都是"/" 路径这样并不合适，为此此方案并未验证；其实也是过于复杂。本文在此介绍另外的很简单的方案：NGINX VirtualServer and VirtualServerRoute[2]。NGINX VirtualServer and VirtualServerRoute是在Nginx Ingress Controller release 1.5版本才开始支持，VirtualServer and VirtualServerRoute熟悉F5的比较清楚，Nginx VirtualServer and VirtualServerRoute的引入是为了替代掉Nginx Ingress，它具备更了Nginx Ingress不具备的能力：流量拆分和基于内容的高级路由，这些能力在Nginx Ingress层面是自定义资源。安装Nginx Ingress Controller请参考：Installation with Manifests[3]，当前是1.6.3版本。创建Nginx VirtualServer and VirtualServerRoute资源实现http和https分流。

cyh-nginx-virtualserverroute.yaml：

  1. apiVersion: k8s.nginx.org/v1
  2. kind: VirtualServer
  3. metadata:
  4.   name: cyh-nginx-virtualserver
  5.   namespace: cyh
  6. spec:
  7.   host: cyh.test.com
  8.   tls:
  9.     secret: cyh-nginx-crt
  10.   upstreams:
  11.   - name: http-svc
  12.     service: http-svc
  13.     port: 80
  14.   - name: https-svc # nginx upstream name,但并非实际nginx config中生成的upsteam名称
  15.     service: https-svc # kubernetes service name
  16.     tls: # https 必须开启enable，否则会报400，也就是使用http协议访问https，开启了这才会在proxy_pass处使用https
  17.       enable: true
  18.     port: 443
  19.   routes:
  20.     - path: / # nginx location 配置
  21.       matches:
  22.       - conditions: # 条件匹配进行基于内容的高级路由，流量权重的设置用Split。
  23.         - variable: $scheme # 变量或者header，cookie，argument参数等，此处$scheme 表示http或https
  24.           value: "https" # 当$scheme是https时走https-svc的后端,默认其他流量均走http
  25.         action:
  26.           pass: https-svc
  27.       action:
  28.         pass: http-svc

应用后，来看看实际Nginx的配置：

/etc/nginx/conf.d/vs_xxx.conf：

  1. upstream vs_cyh_nginx-virtualserver_http-svc {
  2.     zone vs_cyh_nginx-virtualserver_http-svc 256k;
  3.     random two least_conn;
  4.         server 172.49.40.251:80 max_fails=1 fail_timeout=10s max_conns=0;        
  5. }
  6. upstream vs_cyh_nginx-virtualserver_https-svc {
  7.     zone vs_cyh_nginx-virtualserver_https-svc 256k;
  8.     random two least_conn;
  9.         server 172.x.40.y:443 max_fails=1 fail_timeout=10s max_conns=0;        
  10. }
  11. map $scheme $vs_cyh_nginx_virtualserver_matches_0_match_0_cond_0 {
  12.         "https" 1;
  13.         default 0;
  14.     } # https 路由匹配
  15. map $vs_cyh_nginx_virtualserver_matches_0_match_0_cond_0 $vs_cyh_nginx_virtualserver_matches_0 {

  17.         default @matches_0_default;
  18.     } # 默认路由匹配
  19. server {

  21.     server_name cyh.test.com;

  24.     ssl_certificate_key /etc/nginx/secrets/cyh-cyh-nginx-crt;
  25.                    server_tokens "on";
  26.                        location / {
  27.         error_page 418 = $vs_cyh_nginx_virtualserver_matches_0;
  28.         return 418;
  29.     }        
  30.     location @matches_0_match_0 {
  31.                                 proxy_connect_timeout 60s;
  32.         proxy_read_timeout 60s;
  33.         proxy_send_timeout 60s;
  34.         client_max_body_size 1m;
  35.                     proxy_buffering on;
  36.                                 proxy_http_version 1.1;
  37.         set $default_connection_header close;
  38.         proxy_set_header Upgrade $http_upgrade;
  39.         proxy_set_header Connection $vs_connection_header;
  40.         proxy_set_header Host $host;
  41.         proxy_set_header X-Real-IP $remote_addr;
  42.         proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  43.         proxy_set_header X-Forwarded-Host $host;
  44.         proxy_set_header X-Forwarded-Port $server_port;
  45.         proxy_set_header X-Forwarded-Proto $scheme;
  46.         proxy_pass https://vs_cyh_nginx-virtualserver_https-svc;
  47.         proxy_next_upstream error timeout;
  48.         proxy_next_upstream_timeout 0s;
  49.         proxy_next_upstream_tries 0;
  50.             }
  51.         location @matches_0_default {
  52.                                 proxy_connect_timeout 60s;

  54.         proxy_send_timeout 60s;

  60.         proxy_set_header Connection $vs_connection_header;
  61.         proxy_set_header Host $host;
  62.         proxy_set_header X-Real-IP $remote_addr;
  63.         proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  64.         proxy_set_header X-Forwarded-Host $host;
  65.         proxy_set_header X-Forwarded-Port $server_port;
  66.         proxy_set_header X-Forwarded-Proto $scheme;
  67.         proxy_pass http://vs_cyh_nginx-virtualserver_http-svc;

  69.         proxy_next_upstream_timeout 0s;
  70.         proxy_next_upstream_tries 0;
  71.             }
  72.     }

使用Nginx Ingress Controller VirtualServer and VirtualServerRoute基于内容高级路由和流量拆分一切都变得如此简单。其实Nginx Ingress Controller VirtualServer and VirtualServerRoute从http和https分流还可以延伸至基于内容的高级路由或流量拆分（比如：当有一个预发布环境和正式环境来测试一项新特性需要根据用户进行流量拆分，张三流量放到新特性的预发布环境，而其他的人员流量仍然导到正式环境）都变得如此简单。关于Nginx Ingress Controller VirtualServer and VirtualServerRoute更多使用请参考：VirtualServer and VirtualServerRoute Resources[3]。

结束语


当然除了Nginx Ingress Controller VirtualServer and VirtualServerRoute的方案外，还可以采用传统的HAProxy TCP转发或LVS TCP转发，只需要将两者的VIP与Kubernetes的Endpoints绑定即可，这两种方案本文不进行介绍。
