# 图解 Kafka

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=Mzg5Mjc3MjIyMA==&mid=2247544365&idx=1&sn=32458840fc6639fa0693eb1b9e09bd95&chksm=c03b643ef74ced288df7c8b9fff19ff4fba19253028f84a05f7fa5b99e674dd6eb3d40355cca&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=Mzg5Mjc3MjIyMA==&mid=2247544365&idx=1&sn=32458840fc6639fa0693eb1b9e09bd95&chksm=c03b643ef74ced288df7c8b9fff19ff4fba19253028f84a05f7fa5b99e674dd6eb3d40355cca&scene=27#wechat_redirect)

![](../Images/5276214ed8b93f60a764a5888bd7f0ff.png)

  

Kafka 是主流的消息流系统，其中的概念还是比较多的，下面通过图示的方式来梳理一下 Kafka 的核心概念，以便在我们的头脑中有一个清晰的认识。

  

基础

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  

Kafka 是一套流处理系统，可以让后端服务轻松的相互沟通，是微服务架构中常用的组件。  
![](../Images/0efd8a140f22eaaf64294c11da9734c8.png)

  

生产者消费者

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  

生产者服务 Producer 向 Kafka 发送消息，消费者服务 Consumer 监听 Kafka 接收消息。  
![](../Images/6896ca983a7cdf6c4345790985606d78.png)  
一个服务可以同时为生产者和消费者。  
![](../Images/46b81b9ddb8c3b3e378319ae991afd16.png)

  

Topics 主题

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  

Topic 是生产者发送消息的目标地址，是消费者的监听目标。  
![](../Images/3f3cdbbec4b3d0e86826007c13eae313.png)  
一个服务可以监听、发送多个 Topics。  
![](../Images/897c2734d81df80e57e428408f27a523.png)  
Kafka 中有一个【consumer-group（消费者组）】的概念。  
这是一组服务，扮演一个消费者。  
![](../Images/aa3a868d21f51a012a707c70b8ff32ed.png)  
如果是消费者组接收消息，Kafka 会把一条消息路由到组中的某一个服务。  
![](../Images/90f035ba1df42410bd1759ca1961643c.png)  
这样有助于消息的负载均衡，也方便扩展消费者。  
Topic 扮演一个消息的队列。  
首先，一条消息发送了。  
![](../Images/495f6041005572a3993c48294afdaa84.png)  
然后，这条消息被记录和存储在这个队列中，不允许被修改。  
![](../Images/0c39003e3eaedca763efd1b873a6fe7e.png)  
接下来，消息会被发送给此 Topic 的消费者。  
但是，这条消息并不会被删除，会继续保留在队列中。  
![](../Images/0da5306cdd1dd9f85b64e30e209b9e4f.png)  
继续发送消息。  
![](../Images/36c6e711cb4f07ecc3185d7d1c836a17.png)  
像之前一样，这条消息会发送给消费者、不允许被改动、一直呆在队列中。  
（消息在队列中能呆多久，可以修改 Kafka 的配置）  
![](../Images/59f90871fb8190b5bd3c7e9da7a91373.png)  
![](../Images/309c1f11ccd16382021bc1bd609a26f3.png)

  

Partitions 分区

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  

上面 Topic 的描述中，把 Topic 看做了一个队列，实际上，一个 Topic 是由多个队列组成的，被称为【Partition（分区）】。  
这样可以便于 Topic 的扩展。  
![](../Images/f3aa848576c6c0157f54044c6847762c.png)  
生产者发送消息的时候，这条消息会被路由到此 Topic 中的某一个 Partition。  
![](../Images/5b3b8c42d4265ffb47926d43290d522f.png)  
消费者监听的是所有分区。  
![](../Images/83e1da9f7b2fc7c31905c3c9ee4fc679.png)  
生产者发送消息时，默认是面向 Topic 的，由 Topic 决定放在哪个 Partition，默认使用轮询策略。  
![](../Images/07f46c8accbc22502e7ed41d1611795a.png)  
也可以配置 Topic，让同类型的消息都在同一个 Partition。  
例如，处理用户消息，可以让某一个用户所有消息都在一个 Partition。  
例如，用户1发送了3条消息：A、B、C，默认情况下，这3条消息是在不同的 Partition 中（如 P1、P2、P3）。  
在配置之后，可以确保用户1的所有消息都发到同一个分区中（如 P1）。  
![](../Images/839bd11f13b63238b2e1486d5327de9a.png)  
这个功能有什么用呢？  
这是为了提供消息的【有序性】。  
消息在不同的 Partition 是不能保证有序的，只有一个 Partition 内的消息是有序的。  
![](../Images/0c9d9fdf8694ae80559b31eed0d03cd1.png)  
![](../Images/13418b3f1cc13b4f703c5105b9944ed9.png)

  

架构

![](../Images/1708fdcac61cedac5979fc1b01e5ac23.png)

  

Kafka 是集群架构的，ZooKeeper是重要组件。  

![](../Images/ce80bd0caec2ece979a0aa7642afc60e.png)

  
ZooKeeper 管理着所有的 Topic 和 Partition。  
Topic 和 Partition 存储在 Node 物理节点中，ZooKeeper负责维护这些 Node。  

![](../Images/2508763c68898d53fb20ff413ac8fe6d.png)

  
例如，有2个 Topic，各自有2个 Partition。  

![](../Images/180b708e8a3d7d69b2fe262d99b00152.png)

  
这是逻辑上的形式，但在 Kafka 集群中的实际存储可能是这样的：  

![](../Images/45d0b282f49b9b127328da5298c091ff.png)

  
Topic A 的 Partition #1 有3份，分布在各个 Node 上。  
这样可以增加 Kafka 的可靠性和系统弹性。  
3个 Partition #1 中，ZooKeeper 会指定一个 Leader，负责接收生产者发来的消息。  

![](../Images/d137f4082c2d28c7eab0814fc9e41af9.png)

  
其他2个 Partition #1 会作为 Follower，Leader 接收到的消息会复制给 Follower。  

![](../Images/e1745b0730631e1f40d041577c8c98fc.png)

  
这样，每个 Partition 都含有了全量消息数据。  

![](../Images/3c99d5de152b0b50164df300678a0126.png)

  
即使某个 Node 节点出现了故障，也不用担心消息的损坏。  
Topic A 和 Topic B 的所有 Partition 分布可能就是这样的：  

![](../Images/9a54edf620089a090652b2127f3fee93.png)
