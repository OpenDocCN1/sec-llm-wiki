# 工程师必须提高写作能力

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=Mzg5Mjc3MjIyMA==&mid=2247561991&idx=1&sn=60925ecda3cecf6af8d9cbad0d02d704&chksm=639ec0244351839b932930f3df8de977dd7caace4f01c40cc1e5174e57b0bc7909d676f01130&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=Mzg5Mjc3MjIyMA==&mid=2247561991&idx=1&sn=60925ecda3cecf6af8d9cbad0d02d704&chksm=639ec0244351839b932930f3df8de977dd7caace4f01c40cc1e5174e57b0bc7909d676f01130&scene=27#wechat_redirect)

本篇文章主要介绍和说明作为一名软件开发人员有效写作的一些方法和技巧。

有效写作是一种超能力，这是不可否认的。作为一名软件工程师，你写了很多代码，写的大部分东西都是给电脑看的。然而，企业由人组成。

![](../Images/a24e08d066cbe89cd18a38f25484b03b.png)

我们有很多人远程办公，这对我们的写作能力提出了更高的要求。如果几年前我们可以坐在办公椅上向前挪几米，和同事谈论一些事情，现在我们通常会给他们写邮件。有时我们会在几个小时后，甚至几天后才收到回复。当往返时间以小时为单位计算时，你需要考虑写什么以及如何写，以避免一天后收到回复 “你是什么意思？”。

**作为一名工程师，有效的沟通意味着要增加你写作的清晰度。**

******#01******

**简式写作**  

在每个开发工程师的生活中，第一个无处不在的主要写作就是聊天 ——Slack、Discord、Telegram、WhatsApp 等。无论平台是什么，信息交换 —— 书写和阅读 —— 都很快。

不过，在 Slack 上写消息并不是工程师的工作，写代码解决问题才是。即时通讯工具更多地被视为在团队中完成工作所必需的工具，而不是其他任何东西。由于这种情况，有一种省略细节或缩短信息的趋势，有时以牺牲可读性为代价。

让我们看几个例子：

![](../Images/23b740097378756c178a65dffce4187e.png)

在 DM 或者私人对话中聊天 

![](../Images/b30946cfc1b08f4cb2901f6c977a3d61.png)

在公共场合或者团队中与多人聊天

在这两种情况下，左边的例子就是我所说的 “低清晰度写作”。上下文很少，太依赖代词，指代不清。内容并不具有同理心 —— 读者必须花费更多的精力来理解说了什么：

*   “它” 是什么？
*   “她” 是谁？
*   “工作不正常” 是怎么回事？
*   “糟糕的时间” 到底是什么意思？
    

另一方面，右边的例子试图让读者做更少的工作，尽管这会让作者花费了更多的时间。写作者显然已经考虑过人们会如何阅读这个信息。

特别是在左边的 “团队” 的例子中，甚至不清楚作者想要传达什么。这是一个声明，我必须承认吗？含糊不清，我应该继续提问吗？作者是在寻求帮助还是在开玩笑？

然而，在右边，作者不厌其烦地告诉读者：

*   他们看到了什么症状（假设他们后来粘贴了异常）；
*   他们为解决问题做了哪些努力；以及
*   他们需要帮助。
    

熟悉问题的人将能够立即提供帮助，而不是先了解消息作者要表达什么意思。

******#02******

**稍长一点儿的写作**  

许多工程师每天进行的第二类写作是各种笔记 —— 对拉取请求的评论、对设计文档的反馈、提议和 RFC、代码评论等等。通常，这种类型的写作是 “离线” 阅读，速度较慢。高清晰度和同理心的规则在这里也适用。

长篇写作给你一个机会，让你更深入地探究你为什么要说这些话。这是一个教育、教学、帮助理解和提升水平的机会。

![](../Images/0a6db129f34bb11f7933cc83405c7eab.png)

在上面左边的例子中，我写的注释完成了它的工作 —— 它声明引入的端点不是 RESTful 的，并且在实现中有一个 bug。这个检视评论本身没什么问题，虽然有点冷。

右边是我实际写的评论。因为我知道上下文和接收者，所以我花了一些时间来解释错误的实现是如何崩溃的，并阐述了如何通过使它更符合 RESTful 来 “正确地” 修复它。这看起来有点矫枉过正。当然，如果你向一个行业老手提供这样的反馈，你会得到一些奇怪的表情。这就是为什么理解上下文和为读者写作是很重要的。

现在，我不是说你应该在每次坐下来做公关评论或对设计文档提供反馈时都写论文。通常，留下一些简短、清晰的便条是完全没问题的。但是要注意，如果你花 10 分钟而不是 2 分钟写一个回复，读者可能会受益匪浅。

******#03******

**长篇写作**  

这类写作很难给出战术建议。文档的长度可以从一页到几千字不等，这通常是结构和流程真正开始起作用的地方。

许多组织负担不起（或者根本看不到）雇佣一个技术作家，所以编写清晰、有用、准确的文章的任务就落在了你 —— 开发人员身上。这反过来又要求你成为自己的编辑。

虽然这也适用于短篇写作，但我建议考虑一下长篇写作，尤其是作为一种手段。你写得越清晰易懂，杠杆就越长。

![](../Images/2e5f57c425797b2c2764e524d5e21853.png)

这里有一个具体的例子：

假设你运行一个 Web 服务，它有很多用户。该服务由一个 API 提供支持，你决定向你的用户开放该 API，以便他们能够构建自己的集成并以编程方式与你的服务进行交互。

API 文档的质量将带来巨大的影响，这种杠杆作用将是双向的。

真正有用的文档是让用户感到满意的 API 使用者减少支持请求和显著增加服务使用率之间的区别。满意的用户会带来更多的满意用户。

API 文档只是一个例子，其他文本如规范、设计文档、特性和项目推介也是如此。

******#04******

**为什么写作很重要**  

我们都写东西。大多数时候，我们写的东西并不具有影响力 —— 回复一封随意的电子邮件，在 Discord 上与朋友开个玩笑，给一个远方亲戚寄张生日卡。

在专业环境中，这开始变得重要，而且非常重要。当你写的东西被你的同事、你的经理或你经理的经理阅读时，如果你写的东西清晰、简洁、有感情，会对每个人都有帮助。

![](../Images/2dc36071545e2b391574f40b8bc37cfb.png)

我们公司越发展，我越相信高质量的写作。

说过的话会被遗忘。书面文字被分享、保存，并成为公司文化的基础。

**清晰度低，浅层书写是一阶正，二阶负**

一级积极 —— 你很快就完成了写作，可以继续下一个任务。它更有效率…… 对你来说。

二阶否定 —— 读者将不得不花费更多的精力去揣摩你想说什么。结果可能从沮丧到业务损失不等。

![](../Images/24edfe9dae3641c81cb1cbfd04cf265e.png)

三张关于同理心的幻灯片，来自 Michael Covington 关于写作、思考和学习的演讲。

**清晰度高，同理心写作是一阶负，二阶正**

一级负面 —— 你将不得不花费更多的精力让你的文章更容易理解。你将不得不努力克服你自己的困惑和理解上的漏洞。你必须弄清楚你写作的适当密度是多少。

不过，这不是关于你的…… 是关于他们的。

二阶积极 —— 不仅仅是一个人从你的额外努力中受益，如果十个人阅读你的好作品会怎么样？一百？一千？公司老总看了怎么办？在工作中或在你的组织中认真对待。写作，努力取悦读者，随着时间的推移，将会合成一个庞大的优质写作体，使每个人受益。这是一个字面上的双赢：

*   你的读者获得了更好的理解和水平
*   你的组织受益于更好的知识共享和更高的生产率
*   你能更好地传达你的想法，改善你的职业轨迹
    

写一些你会在另一端欣然阅读的文章。
