分布式事务的挑战及常见解法

事务构成了大多数现代应用的数据库工作负载的重要部分。当需要为一个不断增长的企业扩大运营规模时，将这些工作负载分布在多个硬件系统上，以实现横向扩展、高可用性和容错，往往是计划的一个重要部分。
但是，数据库事务是如何分布的，在分布事务性工作负载方面有哪些挑战和方法？
本文我们将讨论这个问题，让我们从一个更简单的问题开始：在数据库的背景下，什么是事务？（如果你已经知道这些东西，可以跳过这一节，开始研究实际分布数据库事务的挑战）。

#01

什么是事务（在数据库中）？

在数据库中，事务是一组我们想在数据上执行的操作。通常情况下，事务是一个全有或全无的过程 —— 我们希望所有的操作都能成功完成，或者如果这不可能，就把整个事情取消。
举个简单的例子，想象一下从一个网上商店购买东西。如果一个客户购买了价值 20 美元的东西，我们可能想从他们的账户中减去 20 美元（这是一个操作），并将 20 美元加入我们的账户（这是另一个操作）。但我们不希望其中一个操作完成而另一个操作失败。所以我们把它们打包成一个事务，只有当两个操作都成功完成时，我们的数据库才会提交更改。

#02

什么是分布式事务？

分布式事务是一组我们想在数据上执行的操作，但它被提交到多个硬件上。因此，我们不是把与我们的 20 美元事务相关的变化写到一个单实例数据库的硬盘上，而是把这些变化写到几个不同的数据库节点。这些节点一般在不同的地方，并通过网络连接。

#03

为什么使用分布式事务？

分布式事务之所以被使用，是因为将数据库分布在多个节点上，甚至可能分布在多个区域上，有很大的优势。这些优势包括：

  • 直截了当的横向扩展。要给数据库增加更多的能力，你可以简单地增加节点，而不是在一台机器上升级硬件。这通常比较容易，而且通常也比较便宜。
  • 更高的可用性。如果你的数据库分布在多个节点上，一个节点发生故障，一般来说，其他节点可以继续为你的工作负载提供服务，让你的应用程序继续不受影响。相反，如果你的整个数据库是在一台机器上，而这台机器离线或遇到错误，你的应用程序将停止运作，直到机器被修复。
  • 更好的用户体验。如果配置得当，分布式数据库通常可以提供卓越的性能，因为有多台机器能够分担负载。在多区域配置中，数据也可以在地理上靠近最需要它的用户，降低用户访问应用程序时的延迟。
实际上，分布式数据库的优势非常显著，以至于在规模超过一定规模后，分布式数据库基本上是必需的。
然而，分布式数据库确实给处理事务的方式增加了一些复杂性，而事务是大多数公司关键任务工作负载的一个重要部分。

#04

分布式事务和一致性挑战

分布式事务比单实例数据库上的事务更复杂，因为我们需要某种方式来确保每个数据库节点与其他节点的一致性。

下图说明了分布式事务的一个潜在问题。想象一下，我们有一个应用程序试图向三个独立的数据库节点提交一个事务（也许在这三个节点上复制了相同的数据，或者该事务影响了多条记录，而不同的记录被存储在不同的节点上）。
在图中，事务被成功写入前两个节点，但未能写入第三个节点 —— 可能是由于网络断开或节点本身的错误。这就引入了一个不一致的状态 —— 前两个节点和第三个节点对哪些数据是正确的 "意见不一致"。
不用说，数据库中的不一致性可能会导致各种问题，特别是对于那些使用事务的工作负载（例如支付处理系统）而言更是如此。
那么，我们怎样才能确保我们的数据库即使在多个节点上被分割时也能保持一致呢？有各种各样的方法，每一种都有自己的优势和劣势。让我们来看看分布式事物的一些可行的例子。

#05

分布式交易模式：真实的例子

两阶段提交模式

我们先来看看一个非基础的、简单的方法。
两阶段提交模式的工作原理是分两个阶段同步数据库节点，其中每个节点必须先准备提交，然后执行提交。只有当这两个阶段都成功完成时，事务才会被完成。下面是它在一个简单的双节点配置中的示意图。


这种方法是可行的，可以确保两个数据库节点保持一致。然而，它确实有一些明显的缺点。
首先，它需要在两个阶段完成时锁定两个节点的资源。当这些资源被锁定时，它们就不能被其他数据库操作所访问，这在规模上很快就会成为性能瓶颈。
第二，每增加一个节点，它就会变得更复杂，而且它的容错性也不强。如果一个节点发生故障，即使所有其他节点都在线并且能够提交交易，交易也会失败。这就否定了分布式数据库的主要优势之一，因为只要有一个节点发生故障，系统最终就会被卡住。
主动 - 被动复制
在分布式系统中处理事务的另一种方法是使用主动 - 被动设置，由一个或多个只读副本支持的单一节点提供写操作。
这种方法比两阶段模式有一些明显的优势。首先，如果配置得当，它可以有更多的容错性 —— 如果主动节点发生故障，其中一个被动节点可以被切换为主动节点，以便继续运行（切换一般需要时间，可能会导致短暂的服务中断，但它可以被自动化，以尽量减少停机时间）。
然而，这种方法也有一些缺点。同样，我们也错过了一些首先使用分布式系统的原因。写作工作负载不能在机器之间共享，它们必须全部由活动节点处理。因此，尽管（在上面的配置中）数据库有三个节点，但其写入性能仍然受到单个活动节点的性能限制的瓶颈。
它也可能不容易扩展。增加额外的被动节点相对简单，但是增加主动节点就需要某种系统来解决主动节点之间出现的一致性问题。
让我们看看一个系统的例子，这个系统正是为了解决这个问题而建立的。
多活分布式事务
可以说，处理分布式事务的最佳方法是使用多活系统，其中所有的数据库节点都是活动的，能够同时为读和写提供服务。
我们在这里用 CockroachDB 作为例子，因为在现实世界中能够做到这一点的系统少之又少。在 CockroachDB 中，所有的数据库节点都是活跃的，可以提供读和写的服务。活动节点之间的一致性问题是由 Raft 共识算法解决的。简而言之，只要大多数节点同意，事务就可以被提交，这意味着即使一个节点（或者根据你的配置，多个节点、AZ，甚至整个区域）瘫痪，你的数据库也可以保持运行。
重要的是，数据库软件会自动处理将交易路由到不同节点的复杂性，并在节点被添加和删除时确保一致性。从应用开发者的角度来看，CockroachDB 与单实例 Postgres 数据库的处理方式基本相同。
多活方法最终实现了分布式数据库的真正承诺，它允许轻松的横向扩展、高可用性和容错，所有这些都不需要牺牲一致性。因此，使用 CockroachDB 的多活系统在 DoorDash 和 Netflix 等应用的后端都有体现。
这种方法的不利之处实际上就是从头开始自己实现它会非常复杂。实际上，采用多活动系统意味着选择或迁移到像 CockroachDB 这样的数据库，它从一开始就为此功能构建的。（然而，CockroachDB 兼容 Postgres 线，支持 AWS DMS，甚至还提供了一个自动工具，方便从 PostgreSQL、MySQL、Oracle 和 Microsoft SQL Server 数据库转换模式进行迁移）。
