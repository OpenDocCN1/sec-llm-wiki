# 苹果自研的GPU出了低级Bug，不应该

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=Mzg5Mjc3MjIyMA==&mid=2247547705&idx=1&sn=744f9196135c84c14acca1bf62a71565&chksm=c03b712af74cf83c29766e304cba6b4ed44fd36fae6237e44e991620ded54870b417b2ed7383&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=Mzg5Mjc3MjIyMA==&mid=2247547705&idx=1&sn=744f9196135c84c14acca1bf62a71565&chksm=c03b712af74cf83c29766e304cba6b4ed44fd36fae6237e44e991620ded54870b417b2ed7383&scene=27#wechat_redirect)

2020年末，苹果推出了采用自家GPU架构AGX的M1芯片。据称该架构源自Imagination的PowerVR系列。之后，我们就一直在对AGX开展逆向工程，并为其构建开源图形驱动程序。去年一月，我用自己的代码渲染出了一个三角形，但其中却潜藏着本不该存在的bug：

这款驱动无法渲染大量几何图形。

旋转一下立方体没有问题，多边形较少的其他几何图形也可以，但更精细的模型就总是渲染失败。用户看到的结果是：GPU只渲染了模型中的一部分，然后报错。

![](../Images/1ffdb35197b455266c75ac07306eac99.png)

只局部渲染完成的兔子

很难确定渲染能力的极限究竟在哪里。而且影响因素不只是几何复杂性，同一个几何体用简单着色器就能成功渲染，但使用复杂着色器时也会出错。

这意味着使用复杂着色器渲染精细几何图形会“耗时过长”，并导致GPU超时。也许目前的驱动只能渲染超时前已经完成的部分。

但结合硬件架构，我又觉得这种解释不太靠谱。

我们可以简单测试这个假设，因为我们完全能够在着色器中控制时间：

```
for

 (int i = 0; i < LARGE\_NUMBER; ++i) {
```

再次试用着色器后，我们发现……

*   如果着色器设定了用于防止无限循环的时间限制，但这个时长是非常非常高的，我们这只兔子的渲染时间根本不可能达到极限。
    
*   超时引发的错误和我们驱动渲染过多几何图形时的错误并不一样。
    

所以上述猜测确实不对。

于是我们决定开展更多实验。通过修改着色器并查看中断位置，我们发现错误其实来自着色器中的同一部分：各顶点插值的数据量。现代图形API允许我们为每个顶点指定“varying”数据，例如颜色或表面法线。

之后，当硬件渲染各个三角形时，这些“varying”就会在三角形上进行插值、为片段着色器提供平滑输入，从而高效实现Blinn-Phong着色等常见图形技术。

综合起来，最重要的应该就是顶点数量（代表几何复杂度）x每顶点数据量（「着色」复杂度）。此乘积代表的是“各顶点的数据总量”，就是说如果各顶点的总数据量过大，GPU就会报错。

为什么呢？

在硬件处理各个顶点时，顶点着色器会生成各顶点数据。这些数据必须被传递到某处，具体取决于硬件架构。下面我们来看看常见的GPU架构。（这些解释针对现代GPU工作原理进行了大幅简化，但已经足够支撑咱们这篇简单的探讨文章。）

传统的即时模式渲染器会直接将渲染结果传递至帧缓冲区内。它们首先为三角形的各个顶点运行顶点着色器，之后为三角形内的各个像素运行片段着色器。各个顶点的“varying”数据几乎直接在着色器间传递，这就让即时模式渲染器拥有了非常高效的复杂场景处理能力。

但它也有自己的缺点：直接渲染至帧缓冲区会涉及大量内存访问，借此不断写入片段着色器结果、并在混合时读取这些结果。即时模式渲染器更适用于那些配备专用显存的独立、高功耗桌面GPU。

相比之下，基于图块的延迟渲染器则将渲染分为两条通道。首先，硬件运行整个帧的所有（而非单一模型）顶点着色器，之后再将帧缓冲区划分成一个个小块，再由被称为tiler的专用硬件确定各个块中包含哪些三角形。最后，硬件会对各个图块运行所有相关片段着色器，再将最终混合结果写入内存。

Tiler减少了帧缓冲区所需要的内存流量。当硬件对单一图块执行一次渲染时，它会为帧缓冲区中相应的图块保留一份“缓存”副本（被称为「图块缓冲区」）。图块缓冲区很小，只有几KB上下，但访问速度却很快。

向其中写入的成本很低，而且跟直接渲染器不同，它的混合操作几乎不消耗资源。考虑到访问主内存会严重影响性能，而且移动版GPU也没有独立显存，所以tiler就特别适合ARM Mali、Imaginations PowerVR以及苹果AGX等移动版GPU。

没错，AGX是一款移动版GPU，当初是专门为iPhone产品设计的。M1芯片虽然直接面向高性能台式机，但其统一内存与tiler GPU仍然保留着最初的手机设计特性。Tiler在桌面上运行良好，但也有一些缺点。

首先，在一帧开始之初，图块缓冲区的内容并未定义。如果应用程序需要保留当前帧缓冲区的内容，则驱动程序必须从主内存处加载帧缓冲区并将其存储在图块缓冲区内。这个过程相当影响性能。

其次，因为一切顶点着色器都必然先于片段着色器运行，所以硬件需要一个缓冲区来存储所有顶点着色器的输出。一般来说，这需要的数据比GPU的内存容量大得多，所以这个缓冲区也只能放置在主内存中。同样相当影响性能。

这就明白了。因为AGX的本质是个tiler，所以需要一个包含各个顶点数据的缓冲区。如果我们使用的各顶点数据过多并溢出缓冲区，就会报错。

……那么，我们要怎么分配更大的缓冲区呢？

在某些tiler上，例如Arm Mali GPU的某些较早版本，用户空间驱动会计算这个“varying”缓冲区有多大并进行分配（其实这个主意相当糟糕。从新型Valhall架构开始，Mali已经在采用更有效的varying分配方式。）。为了修复错误，我们可以尝试增加所分配的全部缓冲区的大小，确保其容纳得下各顶点数据。

迷雾渐散。

通过认真观察苹果Metal驱动程序的作用，我们发现自己也能编写一个Metal程序来绘制可变数量的几何图形，并跟踪Metal在运行程序时所执行的一切GPU内存分配操作。如此一来，我们了解到增加绘制的几何图形数量并不会增加已分配缓冲区的大小。事实上，除了绘图命令中的“顶点数”这一个字段，它也不会影响被提交给内核的命令缓冲区中的任何内容。

我们知道这个缓冲区的存在。既然它不是由用户空间分配的（至少目前我们认为不是），但肯定是由内核或固件来分配。

于是我们萌生了个有趣的想法：也许我们根本就不必指定缓冲区的大小，也许溢出也无所谓，只要有办法处理溢出就行。

马上开始验证。通过查阅AGX的少量公开文档，我们从一份WWDC演示材料中了解到：

Tiled Vertex Buffer存储着Tiling阶段的输出，其中包括转换后的顶点数据……

但如果该缓冲区已满，则可能导致局部渲染。所谓局部渲染，是指GPU拆分渲染通道以刷新该缓冲区的内容。

明白了！我们要找的缓冲区，也就是“Tiled Vertex Buffer”，确实可能溢出。为此，GPU会停止接受新的几何图形、仅渲染现有几何图形，之后重新开始渲染。

由于局部渲染有损于性能，所以Metal应用程序开发者需要深入研究来优化自己的应用程序。应该会有对应的性能指标来体现这个问题吧。又是一番检索，我们找到了两条：

*   局部渲染的数量。
    
*   参数缓冲区所使用的字节数。
    

“参数缓冲区”？这又是什么东西？

还记得AGX脱胎于PowerVR的传闻吗？PowerVR优化指南中解释道：

所谓参数缓冲区（PB），是一份包含从应用程序传入的各个顶点的指针的列表。它与顶点数据一道被存储在系统内存中。

每个varying都会在参数缓冲区内占据额外的空间。

Tiled Vertex Buffer就是参数缓冲区，参数缓冲区在PowerVR中被称为PB、在苹果这边则被称为TVB。但在苹果的内部开发文档中，参数缓冲区仍然沿用PB名称。

所以，当PowerVR发生参数缓冲区溢出时，会发生什么？

一份早期PowerVR演示材料提到，当参数缓冲区被塞满时“渲染将被刷新”，意味着“在执行连续的tile渲染时，必须从帧缓冲区只检索刷新后的数据”。换句话说，只会执行局部渲染。

回到苹果M1这边，看起来硬件似乎无法执行局部渲染。让我们再看一遍错误的渲染结果。

![](../Images/1ffdb35197b455266c75ac07306eac99.png)

  

还是那只局部渲染的兔子

请注意，模型中的某些部分已经被正确渲染。在黑色背景之下，可以清晰看到这些蓝色的已渲染效果。让我们再捋捋整个逻辑顺序。

首先，硬件为兔子运行顶点着色器，直至参数缓冲区溢出。这一步是对的，毕竟能看到有部分几何图像已经正确渲染完成。

第二，硬件对部分几何图形进行光栅化，并运行片段着色器。这也是对的，因为可以看到图中出现了正确的阴影效果。

第三，硬件将局部渲染刷新到帧缓冲区。这肯定是对的，否则我们应该只能看见纯黑的背景。

第四，硬件为兔子的其余几何体运行顶点着色器。这应该也没毛病，因为其配置与原始顶点着色器相同。

第五，硬件对其余几何体进行光栅化和着色，再跟原先的局部渲染混合。因为AGX是个tiler，所以为了保留现有局部渲染，硬件需要将其加载回图块缓冲区。我们不知道这一步是怎么做到的。

最后，硬件把渲染结果刷新到帧缓冲区。这跟前面提到的第三步应该是相同的操作。

唯一有问题的步骤，就是在局部渲染之后如何将帧缓冲区加载回图块缓冲区。一般来说，驱动程序会提供两个“额外的”片段着色器。其一负责在开始时清除图块缓冲区，另一个在结束时清除图块缓冲区。

如果应用程序需要保留现有帧缓冲区内容，而非写入明确的某种颜色，那么“加载图块缓冲区”程序就会读取帧缓冲区以重新加载内容。这个处理过程需要大量代码，但我们的驱动程序完全可以搞定。

再认真观察，可以看到AGX需要更多的辅助程序。

这里的“存储”程序提供了两次。我们在最初启动硬件时就注意到了这个问题，但并不清楚为什么会发生重复。但在忽略掉具体副本、查看错误内容时，原因就很明确了：其中一个程序负责刷新最新渲染结果，另一个则刷新局部渲染结果。（为什么会重复？我没有进一步观察过Metal在使用不同程序时的表现。但对于前端缓冲区渲染，必须先把局部渲染刷新至临时缓冲区才能正常起效。当然，大家也可以在这种情况下使用双缓冲。）

……如果把帧缓冲区加载到图块缓冲区中，结果又会如何？

当局部渲染可以正常完成时，就一定对应着两个“加载”程序。其一负责写入确切颜色、或者加载帧缓冲区，具体视应用程序设置而定；其二则始终加载帧缓冲区。

……始终加载帧缓冲区，就是说即使在帧开头已经有了清晰的图像，也可以加载回局部渲染？

这个问题的答案其实不难验证。Metal肯定是要求程序绘制出相同的兔子图像，所以我们可以编写一个Metal应用程序来绘制兔子、再塞满GPU内存，之后用一个始终加载黑色的辅助加载程序来替换掉当前的辅助加载程序。

![](../Images/3e85164a18543e33b7659ad32675f857.png)

Metal绘制出的兔子，这时候的内存已经被塞满了

如此一来，Metal也出现了类似的错误，看来根源就在这里。回顾我们自己的驱动程序代码，可以发现我们并没有为局部渲染加载指定任何程序。所以只要参数缓冲区没有溢出、不使用局部渲染，那么显示效果就一切正常；而一旦涉及局部渲染，缺少辅助加载程序就意味着GPU会间接引用空指针并引发错误。真相由此大白。

模仿Metal，我们也编写出自己的程序，负责在局部渲染后加载回图块缓冲区……

![](../Images/8c76c8dafa55ac78962b33d40c01f7a7.png)

修复后的兔子渲染图

……但这样仍没有完全修复渲染效果！这GPU真是要人亲命。错误虽然消失了，但前几帧的渲染仍然不太正确，可以证明局部渲染还是不正常。注意上图中兔子脚的部分。

但奇怪的是，在几帧之后渲染效果就“自动修正”了，表明参数缓冲区已经不再溢出。也许参数缓冲区的大小可以调整（通过内核或固件），而系统会在几帧之后增大参数缓冲区以响应溢出。这种设计机制有其道理：

*   硬件本身无法直接分配太大的参数缓冲区空间。
    
*   参数缓冲区溢出会造成巨大的性能影响，因为局部渲染会占用巨额内存带宽。
    
*   过度分配参数缓冲区会浪费内存，影响应用程序对简单几何图形的渲染效果。
    

而初始参数缓冲区较小，再根据溢出逐步增大是一种更加平衡的作法，既减少了GPU的内存占用量、也最大限度降低了局部渲染的发生几率。

再说回我们的渲染错误。我们的程序实际上用到两个缓冲区，一个是颜色缓冲区（帧缓冲区）、另一个则是深度缓冲区。深度缓冲区并非直接可见，但可以通过“深度测试”来确定，即丢弃掉被其他近端像素遮挡的远端像素。大家可以这样理解，局部渲染机制丢弃的是几何图形、深度测试丢弃的则是像素。

这就解释了兔子身上为什么会发生像素缺失。深度测试受到局部渲染的影响而被迫中断。为什么？因为深度测试取决于深度缓冲区，所以深度缓冲区必须在局部渲染后才能进行存储，并在恢复时再加载回来。于是我们把自己的驱动程序跟Metal驱动的跟踪机制进行比较，最终偶然发现了能够成功执行深度缓冲区刷新的配置。

到这里，我们的兔子终于正常了。
