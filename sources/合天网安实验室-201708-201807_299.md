**

![](../Images/3391c7671abf0bc777a39f0b853ef0fe.png)

本人前几天，刚参加一场线下安全赛，特其中一台靶机攻击过程分享下其中的坑。

靶机IP ：172.16.1.107

Web 访问似乎没什么有价值的东西

![](../Images/563d992ce264d5b13139a6fc9493f018.png)

  

Nmap 看下是否有其他收获?

![](../Images/8587f4387e489f7e0dc5b809c5cf6ebf.png)

  

咋一眼看过去除了 80 端口的 web 以为就没其他端口了，尝试着进行全端口扫描发现，还是一样。

  

后来仔细进行 nmap -sV 扫描，还有一个 82 端口，尝试 web 访问。

![](../Images/6e7c4487a9e257fbd9beca8c6c563ff5.png)

  

存在一个 ucenter home 的站点，首先考虑了是否存在当前 cms 的漏洞

![](../Images/ac32405118becb1ec9b1c5f1286852a9.png)

  

后来一想，如果单纯是 cms 的漏洞，何必需要之前 80 端口上的 IIS 列目录。

  

分别将两个站点内容对比下，发现 80 端口上的 logo.gif 文件与 82 站点的 logo 一致。

![](../Images/d5f9c561c32325c1fee659d0414f092d.png)![](../Images/bf7a690ad697d6929b98f9b2c3ea42c7.png)![](../Images/0d38714ce4a764fe89602f4e56dd6b44.png)

  

那么现在可以肯定 80 的 IIS 站点肯定是 82 主站的图片存放位置。

  

**看到 IIS 想起了 IIS 存在写入漏洞，拿出工具扫描一番**

![](../Images/8d79a71b390c058f7939ee7d1631b00b.png)

  

看来存在漏洞,尝试上传 asp webshell

![](../Images/34884695e8d674f03bbc3b7742c9d0bf.png)

  

上传成功，接下来 move 一下就好了。

![](../Images/36e1be638b2b0ecd890d1d33e6b0e1a4.png)

  

Shell.asp 创建成功。

![](../Images/d933451454cae8c03f3ba1c19203c13b.png)

  

尝试访问 404，未找到该文件……

![](../Images/53e424b01761623d314e946368d550d3.png)

  

后来考虑到估计就是 IIS 的 80 端口不允许我们访问。

  

这些想起前面的82端口主站是跟80端口有联系。

![](../Images/e03452c0973ba523111c87f388e19b44.png)![](../Images/2e1efaa867f35ccc4069768e18caddae.png)

  

80 无法访问，那就借助 82 端口，

82 端口是 PHP 站点，那么直接上传 php webshell 就好了，

![](../Images/63edcc0a31209e9f3e02218bbaffc835.png)![](../Images/927c8d361a3366c626652874ae22a5f0.png)

  

**菜刀连接成功**

![](../Images/be3d24bfc4b94bc31ff7d62c386e9ca5.png)

  

发现 FLAG 值一个

![](../Images/91f99e401140383b8a7782484b1c5eaf.png)

  

从目录结构来看，是appserv搭建，权限不够看来得提权

![](../Images/f79a1e7996e449c784e08da242365f67.png)![](../Images/1144fb02eb98379a2e4441f23b36fe05.png)

  

在 web 根目录底下发现连接数据库配置文件，可尝试进行数据库提权。

![](../Images/1b114e2ed08244b40a50220e4370b802.png)

  

进行 udf 提权，上传 udf.php 文件。

![](../Images/10e70935d6c1fcf171727d44f1b67e6f.png)

  

如果这边对 udf 提权原理不熟悉，可能不好提权，有个坑

  

**UDF提权条件**

(1) Mysql 版本大于 5.1 版本 udf.dll 文件必须放置于 MYSQL 安装目录下的 lib\\plugin 文件夹下。

  

(2) Mysql 版本小于 5.1 版本。udf.dll 文件在 Windows2003 下放置于 c:\\windows\\system32，在 windows2000 下放置于 c:\\winnt\\system32。

  

**当前版本当然大于 5.0，mysql 数据库底下没有 lib 目录**

所以需要在 appserv mysql 目录下的 lib 目录新建一个 plugin 目录

  

然后在用 udf 提权脚本导入 udf.dll 然后再创建 system shell 函数

![](../Images/5d5ca8e3ecc40d4ec57b74eedb51ee2a.png)

  

Mysql 数据库底下发现存在一个 FLAG 数据库，把数据库下载下来，扔到本地的 PHPstudy 的 mysql/data 文件夹底下环境中，本地去查看 FLAG值

![](../Images/91c44ddddee1210db5912a5826df4c9b.png)![](../Images/1e9625df8b5f534f1bfee29779fd36d9.png)

  

最近看到一篇 mysql 数据库利用的总结博文，挺全面的，如下：

http://blog.51cto.com/simeon/1981572

后来考虑到数据库提权还是挺麻烦的还不如使用 exp 更快。

  

经过多个 exp 尝试，发现 ms15-077 可以提权成功。

![](../Images/15f979a7bf656dc7f10a43252d389e62.png)

  

修改 administrator 密码  

![](../Images/bbdc0caf49156bafe739e462cfd6f189.png)

  

接下去开 3389 远程桌面，被拒绝访问了，应该不是权限问题，而是语句问题，尝试更换别的。

![](../Images/d20fdb0d9d62d11648142ed9af892062.png)![](../Images/82a0294a1c80605174931e9372087d0a.png)

  

最终上传了个 kai3389.exe 成功开启

![](../Images/7b12d4bc707631816f27cf2665712a82.png)

  

远程桌面连接发现桌面大大的一个 FLAG，记事本打开看见乱码，虽然可以 FLAG{},但是内容是乱码，估计不是最终值，都是 % 估计是 url 编码  

![](../Images/2d5f3b81dd5a3392bc587edbd46d3f77.png)

  

Url解密得到一串base64值，再进行base64解码

![](../Images/7d3e4fc8a6c85eacf5552d41715493e2.png)![](../Images/fd9d4df8ab49a281547faffac091d712.png)

  

至此整个靶机入侵提权成功。
