# 浅谈root账号安全管理

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzI2MjQ1NTA4MA==&mid=2247487620&idx=1&sn=09fae4325ae5120c5034a67db64867b7&chksm=ea4bbac3dd3c33d53ffed89a20c2af13b896d58c880de0d87a09d698564a9892aba847b3def6&scene=126&sessionid=1681322324#rd](http://mp.weixin.qq.com/s?__biz=MzI2MjQ1NTA4MA==&mid=2247487620&idx=1&sn=09fae4325ae5120c5034a67db64867b7&chksm=ea4bbac3dd3c33d53ffed89a20c2af13b896d58c880de0d87a09d698564a9892aba847b3def6&scene=126&sessionid=1681322324#rd)

曾有人问了一个关于root账号管理的问题：之前由于安全团队没有介入，导致都使用root账号安装应用。现在安全团队感觉这样风险很大，也不符合各种合规要求，虽然和运维团队商量了很久，但他们仍旧不知道如何改变现状。在这种情况下，有没有办法破局？

  

**1 问题分析**

  

这是个历史遗留问题，关键是动生产，特别是稳定性要求高的情况下，整改风险也大。有些系统可能根本就不能非root启动，还需要运维排查权限点，单点处理。存量可以通过特权账号登陆监控来慢慢清理，但是root权限管理一定不是用监测来解决。**监测是监控异常，运维滥用root的本质是自动化能力不足，性质是规范不明确，流程不合规**。还是要通过**与运维负责人一起明确规范，严格执行开始。短期回收root集中管理，长期做好白屏化，让运维不依赖root权限**。大家目标一致，自发执行，绝不是做彼此的watch dog。

 

# **2 解决方案**

  

**和运维对接好，通过流程要求把增量卡住，存量逐步推动**。有这么几个方案可以参考：

*   **非root账号启动**是基本运维原则，运维部门一定要认可，达成与安全一致的目标；
    
*   **母盘基线统一账号、目录、启停脚本**，root无法启用服务（除非显示申明）；
    
*   **root密码托管**，使用堡垒机、LDAP等等方案，集中管理root账户，运维日常不持有root权限；
    
*   也可以**考虑采用密钥的方式登录，然后私钥由安全组统一管理**。在堡垒机上分配，禁止root远程登录。这是一个好办法，但涉及改动公私钥证书改动也很大；
    
*   使用**堡垒机审计和阻断特殊命令**，万一出问题事后也可以审计；
    
*   如果有发布系统，配合发布系统统一改成发布系统的特殊权限账号，增量存量都控制了；
    
*   如果是中间件等组件，配合运维一个一个集群搞，能拿权限的敏感组件把危险的指令给干掉，比如Redis。
    

 

# **3 追根溯源**

  

基础设施安全第一天没做好，确实就背上了历史包袱。感觉最终解决之道还是基础设施安全，**先把资产管理做好，要有统一的自动化运维平台，减少堡垒机的访问需求，然后统一常见组件的安装包安全配置**。

  

此外靠新发布应用的机会，把root权限降到非root权限比较稳妥，再做好访问控制加固和监测来辅助。增量的机器和应用需要做好准入，需要梳理好应用发布流程及是否依赖root，一般是没这个场景，然后把新应用降级到非特权账号启动。
