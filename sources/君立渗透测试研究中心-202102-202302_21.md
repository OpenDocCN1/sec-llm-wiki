## 前言

菜鸡如我，在学习代码审计的过程中很长一段时间处于各种 WEB 漏洞的原理也知道了一些常见的绕过等利用方式。

但是当给我一个 CMS 让我审计的时候，往往觉得无所适从、无从下手。

因为很多的代码审计的教程都是告诉人们在哪个位置有个怎样的漏洞，这属于结论式的审计，而非过程式的思路、方法。

所以计划写一个代码审计系列的，主要侧重分享一些我个人在进行代码审计的时候的方法、思路，工作流程等。希望能对跟我过去一样拿到一套源码之后感觉无可名状、无从下手、无所适从的小伙伴有一点帮助。

  

## 一、 个人审计的一个基本流程

通常大家提到代码审计，总会说两个东西：

l黑盒测试

l白盒审计

但是实际上真正在进行审计时你会发现其实还有很多都是一些别的东西。

下面以最近审计的 TuziCMS 为例，分享一下我拿到这个 CMS 之后是如何一步一步的找出漏洞来的，虽然漏洞质量不是很高，但是考虑到作为入门教程可能反而刚刚好。

  

### 1\. 目标源码相关信息收集

不管是渗透测试还是代码审计，信息收集总是跑不了，但是当对一套源码进行代码审计时我们应该重点关注哪些信息呢？

下面是我个人在拿到一套源码之后的一些比较关注的点，这里主要是抛砖引玉：

  

A. 目标源码所使用的 架构、语言、组件

也就是目标源码是靠哪些东西开发的。

在这一步通常需要具体到细化的版本组件情况，以及这些组件对应版本的相关历史漏洞。

### 2\. TP3 相关审计基础（熟悉审计 TP 框架相关的可跳过本部分内容)

对于本次审计的 TuziCMS 的相关历史漏洞, 由于其是基于 Thinkphp 3.2 二次开发的，所以我们先来回顾一下审计 Thinkphp3 系列相关的一些基础知识，同时顺便侦察一下本次审计的 CMS 中相关的内容

##### 审计思路

通常来说，对于基于 TP3 或者说基于任何框架开发的源码，在审计的时候我们主要关注的是两个方面的问题：

l一 是框架自身的漏洞

l二 是源码开发者自己写的代码中的漏洞

通常来说，一个广泛使用的开发框架的安全性要远比普通开发者写的代码安全得多，所以一般我们重点关注的应该是开发者自己写的代码中的问题，但是往往也有一些开发者较为缺乏安全意识，导致所使用的框架本身的漏洞成了漏网之鱼。

  

##### TP3 相关基础

在审计任何基于框架相关的源码时，我们都需要对源码所使用的框架有一定的了解，那么框架相关的帮助文档往往自然是我们不可或缺的参考资料。

TP3 的帮助文档：http://document.thinkphp.cn/manual32.html#var\_output

帮助文档往往是用来查的而不是通读的，所以我们在看帮助文档时必须要有一个重点，带着问题去看。

那么从代码审计的角度来看，大家觉得我们需要从帮助文档中了解哪些东西呢？或者说我们需要从帮助文档中找到哪些问题的答案呢？

下面是我个人目前对这个问题的一个答案。

##### 需要帮助文档解决的问题：

\# A. 这个框架的配置文件是哪些？开发者又应该如何去调用这个框架来对源码进行相应的配置？  
\# B. 基于这个框架开发的源码大概会有怎样的 URL 模式？也就是说它的 URL 以及输入参数通常是怎么一个形式？从一个 URL 中我们怎么知道它访问的实际上是哪一个代码文件又代入了哪些参数呢？  
\# C. 如果按照 M-V-C 模式开发的框架，那么这个框架处理 M-V-C 各个部分的代码又分别是哪些，它的目录结构作用大致是怎样的呢？哪一部分是处理数据操作的，哪一部分又是处理视图的，哪一部分又是来连接模型与视图的呢？同时在基于此框架开发的源码中，开发者自己的代码大概是在哪一部分呢？  
\# D. 这个框架是如何进行输入输出处理的？开发者在调用框架来进行输入输出时又应该是怎样的代码形式？  
\# E. 这个框架有没有考虑安全性，具体针对常见的漏洞又是怎么设计安全规则的呢？  
\# F. 这个框架是如何处理与数据库的交互的？开发者在调用框架处理与数据库的交互时大概是怎样的代码形式？  
\# G. 这个框架是如何处理与文件的交互的？如果开发者调用这个框架中的代码来进行文件操作是怎样的代码形式？  
\# H. 个框架中有对序列化与反序列化进行处理吗？如果开发者调用这个框架中的代码来处理序列化与反序列化那么又应该是怎样的代码形式呢？这个框架中有哪些公开的 POP 链或反序列化链呢？

###### 0xB TP 中的 四种 URL 路由模式

\# 0. 普通模式 （普通模式即传统的 GET 传参的方式来指定当前访问的模块和操作，通常 URL 形式如下：）  
http://域名/项目名/?m=模块名&c=控制器名&a=操作方法名&var=参数  
eg. http://localhost/index.php?m=home&c=user&a=login&var=value  
\# 1. PATHINFO 模式（默认模式，想传入多个参数可以通过使用 键1/值1/键2/值2 的方式，通常 URL 形式如下：）  
http://域名/项目名/入口文件名/模块名/方法名/参数键1/参数值1/餐宿键2/参数值2  
eg. http://localhost/index.php/home/user/login/var/value/  
同时 PATHINFO 模式下，依然可以采用普通 URL 模式的参数方式:  
eg. http://locahost/index.php/home/user/login/?var=value  
并且 PATHINFO 模式中可以通过修改配置 URL\_PATHINFO\_DEPR 来更改 PATHINFO 参数的分隔符。例如配置如下：  
'URL\_PATHINFO\_DEPR'\=>'-',  
则 URL 变为：  
http://localhost/index.php/home-user-login-var-value  
\# 2. REWRITE 模式（REWRITE 模式是在 PATHINFO 的基础上添加了重写规则的支持，通常用于去掉入口文件名以便 SEO 优化，需要额外配置 WEB 服务器的重写规则才能生效, 假如配置服务器重写规则为去掉入口，则 URL 形式如下）  
http://域名/模块名/控制器名/方法名/键1/值1  
\# 3. 兼容模式（兼容模式主要用于不支持 PATHINFO 的特殊环境，通常 URL 形式如下:）  
http://域名/?s=/模块名/控制器名/方法名/参数键/参数值  
eg. http://locahost/?s=/home/user/login/var/value

###### 0xD TP3 中的输入输出处理及开发者的调用形式

输入处理及调用形式

TP 的帮助文档中给出了两种允许开发者接收输入的方式：

l使用传统的 $\_GET\['param'\]  $\_POST\['param'\] 的形式

l通过 TP 框架中的 I 方法 (同时帮助文档中也提示了不建议使用传统方式，因为没有统一的安全处理机制，这就说明I 方法在设计时就考虑到了安全性的问题）

下面我们来具体看一下 I 方法：

l调用格式：

I('变量类型.变量名/修饰符'， \['默认值'\]， \['过滤方法'\]，\['额外数据源'\])  
\# 其中变量类型可通过传统的形式的小写字母来指定:  
eg. I('get.id')  等价于 $\_GET\['id'\] 

l输入过滤：

\# 1. I 函数在未指定过滤方式时会采用默认的过滤机制：  
默认会使用配置文件中的 'DEFAULT\_FILTER'\=> 'htmlspecialchars'  
\# 2. TP3.2.3 版本开始支持正则匹配过滤，   
\# eg.  
I('get.name', '', '/^\[A-Za-z\]+$');     \# 表示过滤字符  
\# 3. 不采取任何过滤机制接收输入的方式：  
I('get.name', '', '')  或 I('get.id', 0, false)

l修饰符：

\# TP3.2.3 版本开始， I 函数支持通过修释符的方式来指定变量类型, 会通过修饰符将参数强制转换为指定的类型  
\# eg.  
I('get.id/d')   I('get.name/s')  I('post.ids/a')

通过对输入处理机制的学习，我们可以知道基于 TP 框架开发的代码一般默认至少都会通过 htmlspecialchars 的过滤处理，那么在对此类源码的输入点进行审计的时候，我们可以重点关注哪些方面或者哪些代码形式的输入调用呢？

\# 1. 禁用了过滤机制的 I 函数调用  
I('get.id', 0, '')             \# 正则匹配模式：^I\[(\](\[\\s\\S\])\*\\'\\'\[)\]$  
I('get.name', '', false)       \# 正则匹配模式：^I\[(\]\\'(\[\\s\\S\])\*false\[)\]$  
\# 2. 通过传统的接收输入的方式的

  

输出处理流程及调用形式 

相较于框架的输入处理机制也许不那么重要一点，主要容易导致的是 XSS/SSTI 一类的漏洞

所谓输出，在 WEB 中也就是生成的网页内容，通常 MVC 模式的源码主要是通过视图的方式来控制，一般在 Control 层控制内容，然后在 View 层来处理具体的显示。

在 TP 中的输出机制也是 MVC 模式中常见的在控制层中先处理完内容然后通过传递给模板来进行渲染的方式来生成具体显示的 html。

具体来看整个的模板渲染输出机制主要是这么一个流程：

\# 0. 首先定义某个模板文件， 通常文件路径及文件名格式为:  
视图目录/\[模板主题\]/控制器名/操作名+模板后缀  
eg. 定义 User 控制器的 add 操作的模板：    \# ./Application/Home/View/User/add.html  
\# 通过修改配置可以控制默认的视图层的路径 'DEFAULT\_V\_LAYER' => 'Template\_Path'  
eg. 修改视图路径配置后，上边的模板文件变更为：# ./Application/Home/Template/User/add.html  
\# 然后还可以通过修改配置 ‘define('TMPL\_PATH', './Template') 来改变所有模块的模板目录  
\# 也可以在模块配置文件中设置 'VIEW\_PATH'=>'./Theme/' 的方式来单独定义某个模块的视图目录  
\# 然后还可以通过修改配置 'TMPL\_TEMPLATE\_SUFFIX' => '.tpl' 的方式来修改模板文件的后缀名  
eg. 修改完后缀名后，上边的模板文件就应变成:  \# ./Applicaiton/Home/Template/User/add.tpl  
  
\# 1. 然后想要输出某个变量的话，首先需要控制器传递变量给模板, 具体地，TP 中提供了无论何种变量类型都统一使用的 assign 方法来进行对于模板变量的赋值  
$this\->assgin('name', $value);  等价于 $this\->name = $value;  
\# 同时此时模板文件中需通过对应形式 {$name} 来指定如何渲染。  
  
\# 2. 模板变量赋值之后通过 display 方法来对模板进行渲染输出  
\# 调用格式： diplay('\[模板文件\]'，'\[字符编码\]', '\[输出类型\]')  
eg. 不带任何参数，自动定位到当前操作的模板文件     \# $this->display();  
eg. 指定当前模板下面的 edit 模板               \# $this->display('edit');  
eg. 调用 Member 模块下的 read 模板           \# $this->display('Member:read');     
eg. 指定渲染输出时的编码和类型                \# $this->display('read', 'utf-8', 'text/xml')  
eg. 指定模板文件进行渲染                    \# $this->display('./Templcate/Public/menu.html');

###### 0xG TP3 中是如何处理与文件的交互的：

## 二、TuziCMS 审计过程

### 0\. 检查安装逻辑

将程序分成安装前及安装后进行分析，通过在安装时监控文件的改动可知系统判断是否安装是通过常规的 install.lock 锁文件。

对于系统的安装逻辑来说主要可能引起的是重装漏洞，造成重装漏洞的主要为三种情况：

l代码中并未判断安装锁程序是否存在就进入了安装程序

l代码中判断了安装锁是否存在，但是并没有用 exit 或 die 推出 PHP程序，而是只用了 header 函数来指定 location, 又或者说这个判断逻辑只是在某个步骤如 step1 判断的，而安装程序是分开进行的，那我们可以尝试跳过 step1 而直接进入step2/3/4 等等 

l代码中判断了安装锁是否存在，并且是在开头判断的，如果存在就使用 exit 或 die 退出 PHP 程序，这时候如果我们想重装就只有一个办法，就是删除/修改安装锁文件，这个就要具体看代码怎么写的，如果只是判断文件是否存在的话那么我们就得去找一个文件删除漏洞、而如果是靠文件内容来判断的，我们则需要找一个可以修改锁文件内容的点。

### 3\. 总结

首先是我们从这些漏洞之间可以找到一条对这个 CMS 明确的拿 shell 的方法：

1.首先通过前台的用户管理的注入那里拿到管理员的hash 或者通过 manage 后台的登录那儿同样有的注入来使用万能密码进后台

2.然后通过后台的缓存管理等功能处抓包改参数来写 shell 到配置文件里边去

3.然后访问配置文件的 php 来 getshell 

然后是总结一下本次审计过程中的小技巧：

lTP 中快速查找不安全的输入方式的正则表达式： ^I\[(\]\\'(\[\\s\\S\])\*false\[)\]$ 

lTP3 版本中常见的几个注入漏洞以及缓存漏洞的调用代码形式

l用 diff 快速查找版本改动

lTP 框架中从模板文件的输出位置中快速排除能否导致 XSS 的地方（是否输出在标签内而非 html 中)

最后的关键还是分析这个 CMS 会出现这些安全问题的原因：

l首先肯定的是这个开发者安全意识不强，或者是觉得他自己的这个项目不重要了（虽然还在卖企业授权码就是了）

l然后就是很多人都会犯的通病： 使用了存在漏洞的组件，同时又没有采取相关的补丁措施

那么发散一下，一个刷 CNVD 的思路：

提取存在漏洞的框架组件的特征（比如说文件 md5 或者关键字)，然后通过 github 来想办法搜索使用了这些相关框架组件的项目
