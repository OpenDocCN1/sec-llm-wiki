背景

![](../Images/09ec9b813a2dca4d0ef07c5c9a1b6cf5.png)

  

Android系统在安装APK程序的时候，首先会检验APK的签名，如果发现签名文件不存在或者校验签名失败，则会拒绝安装提示安装失败，所以Apk应用程序在发布之前必须要进行签名。

  

Apk签名主要解决两个问题：1.确定消息的来源确实是其申明的那个人;2.通过签名可以保证信息在传递的过程中不被第三方篡改，即使被篡改了，也可以进行校验。

  

![](../Images/44459f5af513c9e6bc1d2b07b010d726.png)

APK的签名是什么？

![](../Images/c3dcd193b45c172b3d836a28c53742be.png)![](../Images/f95cc868228dfea3b0013535594a4ba8.png)  
![](../Images/09ec9b813a2dca4d0ef07c5c9a1b6cf5.png)

  

签名就是摘要与非对称密钥加密相相结合的产物，摘要就像内容的一个指纹信息，一旦内容被篡改，摘要就会改变，签名是摘要的加密结果，摘要改变，签名也会失效。Android中的签名也是这个道理，如果APK签名跟内容对应不起来，Android系统就认为APK内容被篡改了，从而拒绝安装，以保证系统的安全性。

  

  

![](../Images/44459f5af513c9e6bc1d2b07b010d726.png)

Apk签名方案版本

![](../Images/c3dcd193b45c172b3d836a28c53742be.png)![](../Images/f95cc868228dfea3b0013535594a4ba8.png)  
![](../Images/09ec9b813a2dca4d0ef07c5c9a1b6cf5.png)

  

通过几次的迭代发展，apk的签名方案已经发展到3个版本了；

1.最原始签名方案V1；

2.为了提高验证速度和覆盖度在 android系统7.0版本中引入的 签名方案V2；

3.为了实现密钥轮转在android系统 9.0版本中 引入签名方案 V3。

  

  

![](../Images/44459f5af513c9e6bc1d2b07b010d726.png)

原始签名方案解析

![](../Images/c3dcd193b45c172b3d836a28c53742be.png)![](../Images/f95cc868228dfea3b0013535594a4ba8.png)  
![](../Images/09ec9b813a2dca4d0ef07c5c9a1b6cf5.png)

  

Apk 本质上就是个zip文件，通过对Apk解压缩后，在Apk目录下的 META-INFO文件夹中，可以看到包含 MANIFEST.MF、CERT.SF、CERT.RSA 三个文件。这三个文件是在签名时进行创建，在安装Apk时用于验证签名。下面我就对这三个文件进行详细解析：

![](../Images/dfb73255df3ab53720c49dd5bfe9187c.png)

** MANIFEST.MF文件**

它的作用：用于记录Apk中每一个文件所对应的摘要信息，防止某个文件被篡改。

它的内容：当打开 MANIFEST.MF文件时候，可以看到文件内容是这种格式：

  

Manifest-Version: 1.0

Built-By: Generated-by-ADT

Created-By: Android Gradle 2.9.1

  

Name: res/drawable-hdpi-v4/tracepoint\_tip.png

SHA1-Digest: UqNwQcd9oLGpVfILjkVOtNQmySA=

  

Name: res/layout/activity\_new\_base\_layout.xml

SHA1-Digest: Uw3jXiCR9Msf9C6P0Mjcmh2/A/E=

  

其中前三行记录了基础信息，后面每一块都对应了 Apk 中一个原始文件的数据摘要，摘要算法是 SHA-1。在 MANIFEST.MF 文件没被篡改的情况下，可以用于保证Apk中的其他文件不被篡改。用于保证 MANIFEST.MF 文件本身不被篡改就是依赖CERT.SF 文件了。

  

** CERT.SF文件**

它的作用：用于记录 MANIFEST.MF文件的摘要，以及 MANIFEST.MF 文件中每个数据块的摘要。防止 MANIFEST.MF 被篡改。

  

CERT.SF 的文件内容如下：

Signature-Version: 1.0

SHA1-Digest-Manifest: m4hofJv2im9b2HQo/h6VPKRnzqE=

Created-By: 1.0 (Android)

  

Name: res/drawable-hdpi-v4/tracepoint\_tip.png

SHA1-Digest: UqNwQcd9oLGpVfILjkVOtNQmySA=

  

Name: res/layout/activity\_new\_base\_layout.xml

SHA1-Digest: Uw3jXiCR9Msf9C6P0Mjcmh2/A/E=

  

第一行 Signature-Version 记录了签名版本;

第二行 SHA1-Digest-Manifest 记录了整个 MANIFEST.MF 文件的摘要;

后面每一块都是 MANIFEST.MF 中对应数据块的摘要;

  

例如CERT.SF文件中对应的这一段:

Name: res/drawable-hdpi-v4/tracepoint\_tip.png

SHA1-Digest: UqNwQcd9oLGpVfILjkVOtNQmySA=

其中【UqNwQcd9oLGpVfILjkVOtNQmySA= 】就是 MANIFEST.MF 中这一段的摘要（包含换行符）：

Name: res/drawable-hdpi-v4/tracepoint\_tip.png

SHA1-Digest: UqNwQcd9oLGpVfILjkVOtNQmySA=\\r\\n

CERT.SF 如果没被篡改，就能用于验证清单文件 MANIFEST.MF 是否被篡改。用于保证 CERT.SF文件不被被篡改需要依赖CERT.RSA文件。

  

** CERT.RSA文件**

它的作用：就是为了验证CERT.SF 文件是否被篡改。

它的内容：它包含了【对 CERT.SF 文件的签名】和【包含公钥的开发者证书】。

  

  

  

**V1签名的流程**

1\. 计算每一个原始文件的 SHA-1 摘要，写入到 MANIFEST.MF 中;

2\. 计算整个 MANIFEST.MF 文件的 SHA-1 摘要，写入到 CERT.SF 中;

3\. 计算 MANIFEST.MF 中，每一块的 SHA-1 摘要，写入到 CERT.SF 中;

4\. 计算整个 CERT.SF 文件的摘要，使用开发者私钥计算出摘要的签名;

5\. 将签名和开发者证书(X.509)写入 CERT.RSA 。

  

**V1签名校验的流程**

1\. 取出 CERT.RSA 中包含的开发者证书;

2\. 通过系统的根证书（CA证书）验证这个开发者证书是否可信;

3\. 如果开发者证书可信，用证书中的公钥解密 CERT.RSA 中包含的签名;

4\. 计算 CERT.SF 的签名;

5\. 对比 (3) 和 (4) 的签名是否一致;

6\. 如果一致，用 CERT.SF 去校验 MANIFEST.MF 是否被修改;

7\. 如果没有被修改，再用 MANIFEST.MF 中的每一块数据去校验每一个文件是否被修改。

  

  

**V1签名方案如何防止篡改**

假如攻击者通过修改了其中某一个文件，那么他必须修改 MANIFEST.MF 中对应文件的摘要，否则这个文件校验不通过；接着还得修改 CERT.SF 中的摘要，否则摘要校验不过；还得重新计算 CERT.SF 的签名，否则签名校验不通过;但是计算签名需要私钥，私钥在开发者手中，攻击者没有私钥，所以就无法签名。

  

  

**V1签名方案存在的问题**

校验速度慢：需要对 apk 中的每个文件都计算摘要并验证，如果文件很多，校验时间会很长。完整性不够：V1 签名只会校验 Zip 文件中的部分文件，例如 META-INFO 文件夹就不会参与校验。

V2签名方案解析

![](../Images/c3dcd193b45c172b3d836a28c53742be.png)![](../Images/f95cc868228dfea3b0013535594a4ba8.png)  
![](../Images/09ec9b813a2dca4d0ef07c5c9a1b6cf5.png)

  

V2 签名是在 Android系统7.0之后引入的，它解决了 V1 签名校验时速度慢的问题，同时对完整性的校验扩展到整个安装包。

  

在使用v2签名方案进行签名时，会在APK文件中插入一个APK签名分块，该分块位于zip中央目录部分之前并紧邻该部分。在APK签名分块内，签名和签名者身份信息会存储在APK签名方案v2分块中，保证整个APK文件不可修改

** V2 签名的校验**

Android 7.0 及以上在校验时，会先判断是否具有 V2 签名，如果有 V2 签名信息，那么就会进行 V2 签名的校验流程，不再验证V1签名了。

如何判断是否有V2签名？根据Zip文件格式的规则，我们可以找到中央目录区的起始位置。读取从起始位置开始往回的16个字节，判断这16个字节的值是否为 "Apk Sig Block 42"，如果是，则对应上了魔数，说明有 V2 签名。后续就是解析 V2 签名块的流程了。用公钥和签名对蓝色区域验证，验证通过后，用 「APK数据摘要集」对APK每一块做验证。

  

![](../Images/44459f5af513c9e6bc1d2b07b010d726.png)

 V3 签名方案解析

![](../Images/c3dcd193b45c172b3d836a28c53742be.png)![](../Images/f95cc868228dfea3b0013535594a4ba8.png)  
![](../Images/09ec9b813a2dca4d0ef07c5c9a1b6cf5.png)

  

V3 的签名方案，它的签名块格式和V2签名格式完全一样，只是 V2 的签名块信息存放在 ID = 0x7109871a 的数据块中，而 V3 的签名信息存放在 ID = 0xf05368c0 的数据块中。

在这个新的数据块中，记录了旧的签名信息和新的签名信息，以密钥转轮的方案，做签名的替换和升级。这意味着我们可以更改 APK 的签名。
