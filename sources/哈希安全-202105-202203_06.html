0x00 官方说明

  • https://www.djangoproject.com/weblog/2021/jul/01/security-releases/


  1. 漏洞披露于2021年7月1日。

  2. 漏洞影响了3.1.x和3.2.x的版本

  3. 当QuerySet.order_by()接收到恶意的输入会导致SQL注入。


0x01 漏洞成因

翻开代码：找到https://github.com/django/django/blob/3.2.4/django/db/models/sql/query.py，的Blame，可以找到这条PR：https://github.com/django/django/pull/12669/files，可以看到以下关键的修改：


Git commit message上的#31426编号对应链接为：https://code.djangoproject.com/ticket/31426，有关于这次改动更详细的一些讨论。查看这次ticket的相关讨论可以发现是原本想增加order_by()对于uuid的支持被否认，但发现十二年前的正则表达式未对输入的列名存在性进行校验从而转为对正则表达式进行重构。


  1. 在新加的代码我们可以看到1898行删去了正则表达式的匹配，直接导致item变量脱离了正则表达式的束缚，导致可以注入包含引号分号空格等任何字符。


我们构建一个简易的程序测试一下以上所说的漏洞成因。


核心代码如下：


对于或者GET参数中order_by传入order_by方法

可以看到order_by中的值直接被拼接进了SQL语句中。


至于为什么多了双引号，我们可以看到下面这几行代码：

https://github.com/django/django/blob/3.2.4/django/db/models/sql/compiler.py#L343

这几行代码是对field转换成SQL，self.quote_name_unless_alias(table)是对表名进行转义，在表名两端加上了引号，防止SQL注入，而对于变量col，直接就拼接进了SQL中。


所以会在表名俩边多出了双引号。


这样未经过滤的列名直接就被拼接进了SQL，导致了SQL注入的产生。

0x02 利用条件

结合上述据说我们可以得出这三个条件：

  1. Django Version ∈ [3.1, 3.1.13) ∪ [3.2, 3.2.5)

  2. 一个可控的order_by()参数

  3. 正确的表名及正确的列名


比较贴近现实的一种场景是：

发现了一个Django报错页面，得到版本信息在范围内（条件一），接下来找到一处可控的order_by()注入点（条件二），然后可以从报错页面得到对应的表名及列名（条件三）。


0x03 修复

https://github.com/django/django/commit/a34a5f724c5d5adb2109374ba3989ebb7b11f81f

官方的修复方案是继续把正则表达式加上了，防止不应该出现的字符出现。

至于为什么不校验列的存在性，我想可能是因为功能需要，无法进行校验，下面的字符串写着功能：Passing column raw column aliases to order_by()，功能就是为了传递原始的列别名。
