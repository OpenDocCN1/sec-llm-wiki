# Django order\_by() SQL注入分析（CVE-2021-35042)

### 0x00 官方说明

### 

![](../Images/2834b71d0290ae53f5e76e45081a743a.png)

*   *https://www.djangoproject.com/weblog/2021/jul/01/security-releases/*
    

  

1.  漏洞披露于2021年7月1日。
    
2.  漏洞影响了3.1.x和3.2.x的版本
    
3.  当QuerySet.order\_by()接收到恶意的输入会导致SQL注入。  
    

  

0x01 漏洞成因

翻开代码：找到*https://github.com/django/django/blob/3.2.4/django/db/models/sql/query.py*，的Blame，可以找到这条PR：*https://github.com/django/django/pull/12669/files*，可以看到以下关键的修改：

  

![](../Images/69b4b47ca6f60682e781057bbadd4ff0.png)

![](../Images/0db79b33d7512ede9f915c8e7571e522.png)

![](../Images/c1bd11b3d40371b22b19beceb8f270d8.png)

Git commit message上的#*31426编号*对应链接为：*https://code.djangoproject.com/ticket/31426*，有关于这次改动更详细的一些讨论。查看这次*ticket*的相关讨论可以发现是原本想增加*order\_by()*对于*uuid*的支持被否认，但发现十二年前的正则表达式未对输入的列名存在性进行校验从而转为对正则表达式进行重构。  

  

1.  在新加的代码我们可以看到1898行删去了正则表达式的匹配，直接导致item变量脱离了正则表达式的束缚，导致可以注入包含引号分号空格等任何字符。
    
      
    

我们构建一个简易的程序测试一下以上所说的漏洞成因。

  

核心代码如下：

![](../Images/3831a98629d996611df6c4c7b67cc209.png)  

对于或者GET参数中order\_by传入order\_by方法  

可以看到order\_by中的值直接被拼接进了SQL语句中。

![](../Images/02ca003818882315184d1807f1837e96.png)

  

至于为什么多了双引号，我们可以看到下面这几行代码：

![](../Images/f1c58240f16c75d75abb2c9b7bc7c42f.png)

*https://github.com/django/django/blob/3.2.4/django/db/models/sql/compiler.py#L343*

这几行代码是对field转换成SQL，self.quote\_name\_unless\_alias(table)是对表名进行转义，在表名两端加上了引号，防止SQL注入，而对于变量col，直接就拼接进了SQL中。  

  

所以会在表名俩边多出了双引号。

  

这样未经过滤的列名直接就被拼接进了SQL，导致了SQL注入的产生。

0x02 利用条件

结合上述据说我们可以得出这三个条件：

1.  Django Version ∈ \[3.1, 3.1.13) ∪ \[3.2, 3.2.5)
    
2.  一个可控的order\_by()参数  
    
3.  正确的表名及正确的列名
    

  

比较贴近现实的一种场景是：

发现了一个Django报错页面，得到版本信息在范围内（条件一），接下来找到一处可控的order\_by()注入点（条件二），然后可以从报错页面得到对应的表名及列名（条件三）。

  

0x03 修复

![](../Images/7cd0fa98b2172b82ea5a76fb18501ec4.png)

*https://github.com/django/django/commit/a34a5f724c5d5adb2109374ba3989ebb7b11f81f*

官方的修复方案是继续把正则表达式加上了，防止不应该出现的字符出现。

至于为什么不校验列的存在性，我想可能是因为功能需要，无法进行校验，下面的字符串写着功能：Passing column raw column aliases to order\_by()，功能就是为了传递原始的列别名。
