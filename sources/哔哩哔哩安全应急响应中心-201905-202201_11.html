 前言


   第三方组件具有开放、共享、自由等特性，在软件开发中扮演着越来越重要的角色，也是软件供应链的重要组成部分，它的使用大大提高企业中软件研发的效率、缩短上线时间，能有效降低开发成本。但这些组件，可能会存在一些安全问题，所以对开发使用的这些组件进行监控，是很有必要的。之前我们写过一篇文章《漫谈SDL之三方库漏洞检测与CICD》，文章介绍了如何在CI/CD流程中接入第三方组件漏洞检测工具。紧接上一篇文章，再介绍一下我们使用的检测工具的检测原理以及后续漏洞修复的运营工作。目前我们公司使用的是自研第三方组件检测工具，现在整个工具正处于起步阶段，所以这篇文章也是起到一个抛砖引玉的作用，欢迎大佬们来分享交流关于第三方组件漏洞检测工具的见解。


 工具的检测原理

对第三方组件进行检测，首先需要获取到全面、准确、最新的组件清单，包括应用名、组件名、组件版本、owner。

应用中使用组件信息的获取，可以通过在仓库中配置yml文件，让开发在每次commit提交代码的时候，提取里面的相关信息。

yml文件的内容（以java-maven项目为例）：

1.  stages:2.    - build3.   4.  variables:   # 定义用到的变量5.    PROJECT_NAME: xxx.test6.    # 依赖文件在项目根目录则填写依赖文件名称即可，若依赖文件不在根目录，则需要写上相对路径7.    DEPEND_FILE: pom.xml8.    LANGUAGE:java9.  10.  build:11.    stage: build12.    tags:13.      - shared-shell14.    script: 15.      # 执行操作：发送依赖文件pom及对应的commit id 、owner，传给三方库漏洞检测服务进行检测及通知owner16.      - file=` $DEPEND_FILE `17.      - echo {\”owner\":\"$GITLAB_USER_EMAIL\"，\"app_name\":\"$PROJECT_NAME\",\"branch\":\"$CI_COMMIT_BRANCH\",\"commit_id\":\"$CI_COMMIT_SHA\",\"lang\":\"java\",\"app_from\":\"git\",\"data\":\"$file\",\"build_task_id\":\"$CI_JOB_ID\"}18.    only:19.      - branches20.      - tags

在yml文件中，需要配置PROJECT_NAME、仓库中依赖文件的路径、当前仓库使用的语言，在开发commit提交代码时，检测工具会从yml文件中信息获取当前仓库使用的语言、仓库的依赖文件、PROJECT_NAME来解析当前项目中整个组件的使用情况，且能通过CI/CD，获取到本次提交的owner、分支，这样子，就构成了组件清单。


在获取到组件清单之后，需要比对目前使用的组件版本是否有存在漏洞。目前我们使用的漏洞数据库是从CNVD上面爬取到的漏洞信息（每日爬取更新）。因为组件受影响版本在不断更新，所以一个组件可能会存在多个漏洞，开发看起来未免有些繁杂。因此为了更加清晰直观，当前工具检测是通过漏洞名单（在配置中添加相应的受影响组件的最新CNVD编号）的方式来进行检测。在开发commit提交代码后，会通过依赖文件获取到组件信息，再和漏洞名单中的漏洞影响版本进行比对。如果使用的组件版本和漏洞名单中的漏洞影响版本相符的话，则通知相应的owner当前仓库使用的组件版本存在安全漏洞。


工具的运营

   以上就是我们工具的检测流程，那么检测工具在用户提交代码后，将检测结果展示在pipelines中，但因为目前还没有做阻塞流程的机制，修复漏洞的提示往往没有得到足够的重视，所以我们将漏洞具体信息通过办公通讯工具进行通知。当开发进行提交代码操作后，立刻对依赖文件进行扫描。如果存在漏洞，则将漏洞通知到提交代码的开发同事的通讯工具，并且会提供漏洞信息，包括项目名称（方便定位漏洞位置）、项目存在漏洞的组件、组件使用的版本、存在的漏洞、以及这个组件漏洞的影响范围。

然而在推动的过程中，发现通过办公通讯工具通知，修复效率却没有呈现明显提升。所以我们尝试将漏洞录入到漏洞管理平台中，漏洞管理平台按照目前定制的漏洞修复规范，指派给对应开发并对漏洞修复时效进行要求，漏洞超期也会有相应的延期升级机制。
录入到漏洞管理平台之后，开发的修复效率明显提高。除此之外，也可以考虑让开发参与到安全排查的工作，对漏洞进行一个修复监控。还是说回CI/CD流程，在合并代码的时候，可以考虑将第三方组件的检测结果附到MR的评论处，这样开发管理员也能在通过合并请求来看到目前的漏洞情况。这样不仅仅是在安全这边对漏洞修复进行管控，在开发这边同样能有一个督促修复的效果，双管齐下提高修复的效率。

或者在流程完善之后，选择直接在构建时检测到组件漏洞，如果存在有组件漏洞未修复的情况，则对构建进行阻塞，要求通过组件扫描零漏洞才可构建成功。
这样，就可以实现一个第三方组件漏洞从发现到修复的整个流程的闭环。
以上内容就是目前我们对SDL中第三方组件安全检测的一些理解。其中也遇到很多坑，后续也将不断完善检测机制，如添加二次依赖检测机制、添加cve漏洞库等。关于文章内容有任何建议或想法，欢迎公众号后台留言讨论~
