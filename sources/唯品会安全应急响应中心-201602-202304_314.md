**情况描述**

3月20号，Struts 又发布了 S2-046 漏洞公告，地址为：

https://cwiki.apache.org/confluence/display/WW/S2-046

官方描述为当使用 Jakarta Multipart parser 进行上传的时候，会导致远程命令执行。接下来，有人在网上公布了 S2-046 的一些细节，https://community.hpe.com/t5/Security-Research/Struts2-046-A-new-vector/ba-p/6949723#.WNCE7vl97IX

  

![](../Images/2db0ff74873dc4839ae276a4ba620a90.png)

列出了此漏洞触发需要满足的三个条件：

1、struts.multipart.parser需要为jakarta-stream；

2、http请求头中的 Content-Length 需要大于 2GB；

3、文件名包含 OGNL 表达式；

注：笔者分析发现第二条原文作者写得有些偏差，应该是 2M 才对，后面会有分析说明。

  

  

**漏洞验证**

有人在 github 上提供了靶机程序，我们直接下载下来使用即可。

https://github.com/pwntester/S2-046-PoC

构造了以下的 poc ，成功复现了漏洞。其中 OGNL payload 直接使用 S2-045 的即可。

  

![](../Images/5b8b147e9af81ed13d79edd12f658615.png)

  

**漏洞分析**

当然了还是从 Struts 的入口开始跟踪，以下是调试跟踪栈，运行流程是从下至上。

![](../Images/94a428eac0b26b74d79657be5b5917bf.png)

跟踪到 org.apache.struts2.dispatcher.multipart.JakartaStreamMultiPartRequest.processUpload(HttpServletRequest request, String saveDir)，

  

![](../Images/b355c4dcdfce1a1bc9f22f8b8999c673.png)

看到 282 行请求的数据长度是否允许，跟踪进去，可以看到是判断 ContentLength 是否小于 maxSize，而 maxSize 为 2097152。

  

![](../Images/cba23b40cf629b90c3ce8614df97c8b6.png)

那么 maxSize 是在哪里设置的呢。查看靶机程序的 struts.xml 的配置代码中没有发现有对 maxSize 做设置，那么 maxSize 应该是 Struts 的默认设置。

找到 org.apache.struts2 包下的 /org/apache/struts2/default.properties 文件，可以看到默认设置为 2097152 即 2M 而不是 2G。当然了在实际生产环境中程序员会重新设定这个值，所以我们 payload 中的 ContentLength  尽量设得长一点。

  

![](../Images/2f302db9dcb6c110a27d78e0dfde2271.png)

同时我们还看到了 Struts 默认的 struts.multipart.parser 为 jakarta，而不是 jakarta-stream。

 

继续往下跟踪

  

![](../Images/36b05050d5bb38b505fdea3e8a06cd30.png)

发现只有当 requestSizePermitted 为 false， 即我们的 ContentLength 大于 maxSize 的时候，会将输入流的 filename 放入错误消息中，而 filename 为我们的 payload。继续跟踪就到了以下位置：

  

![](../Images/0bde1f57d993a4b11e487ac21b7fd288.png)

是不是很熟悉，跟 S2-045 一样了，会触发命令执行。

  

![](../Images/74a6d68e67af554b24a4aa3a085fd01b.png)

  

**另一个 poc**

有意思的是，有人在 github 上公布了另外一个 poc，完全不用设置 ContentLength 。

  

![](../Images/8c62b7a6c36693a9642a9c82ce0146cd.png)

地址：https://gist.github.com/frohoff/a3e24764561c0c18b6270805140e7600。

下面我们就来分析一下：

Poc 中在 OGNL payload 后面加入了一个空字符和一个任意字符，而 ContentLength  是正常的。

也就是说这个 poc 触发的时候，跟上面的 poc 会走不同的流程。

继续跟踪到 org.apache.struts2.dispatcher.multipart.JakartaStreamMultiPartRequest.processUpload 中

  

![](../Images/e85ace7d32bf1092d382db2f78fddd4e.png)

其不会走 if 代码块，而是直接进入 processFileItemStreamAsFileField，跟进

  

![](../Images/7c7a02d187dfea2c5be3a15d17899b25.png)![](../Images/ff5fb17cb541e510cd9466ad5f50c5a3.png)

会对流的文件名做检查，继续跟进，奇葩逻辑来了。

  

![](../Images/42d732609dfd896809490fff9e0361eb.png)

通过方法描述，我们可以了解到方法功能为对文件名做检查，如果包含 NUL 字符就抛出一个异常，否则正常返回文件名。

还记得吗，我们的 poc 中是包含 NUL 字符的，那么肯定会抛出异常。看一下 189 行，得知抛出的异常包含了完整的文件名。而 Struts 对错误消息是进行 OGNL 解析的，从而导致命令执行。

  

![](../Images/4f77158652d52ef4f591f7a750e08abf.png)

**吐槽一下：**

这个 checkFileName 为什么是抛出异常而不是返回 NUL 字符之前的文件名呢。如果以后其他的应用使用这个方法时候，同时对错误消息进行 OGNL 解析的话，都会造成命令执行的，这是一个坑。（checkFileName 在 commons-fileupload 包中）

  

![](../Images/ade2a45625769c2fdc2f7fda6537b298.png)
