0x01     各种漏洞挖掘方法的比较

  

上一篇我们说过一些常见的漏洞挖掘方法，而这些方法各有优点和缺点。下面我们来对比一下这些方法，让大家能够了解这些方法，授之以鱼不如授之以渔。

  

以下方法相关文献自行google,bing,baidu进行搜素。

  

 **1、模糊测试(fuzzing)** 

  

**优点：**对比其他测试方法，使用范围广，FUZZ的数据是动态执行的且不存在静态分析技术中那样的大量误报率，FUZZ实现比较简单。

  

**缺点：**由于FUZZ数据都是随机产生的，会有大量的数据是无效的，FUZZ的周期较长，FUZZ的覆盖率低。

  

\[文献参考：Fuzzing技术综述\]

  

**2、符号执行** 

  

**优点：**代码覆盖率高，不需求使用太多测试用例，更能产生高纬度的测试用例，测试时间短。

  

**缺点：**程序设计难度大，需要分析汇编指令的语义或需要静态分析技术支撑。

  

\[文献参考：

基于动态符号执行的二进制程序缺陷发现系统，基于符号执行的二进制代码漏洞发现\]

  

**3、模型检验**

  

**优点：**自动化建模，检测范围大，可用于多种系统的安全属性检测，特别适用于工控系统和协议。

  

**缺点：**非验证型安全漏洞检测不适用。

  

\[文献参考: 模型检验技术在软件漏洞自动挖掘中的应用\]

  

**4、污点分析** 

  

**优点：**误报率低，可与符号执行深度结合，可在编译阶段进行深度挖掘，如有源代码状态下属于高效的漏洞挖掘方法。

  

**缺点：**需要源代码的支持。

  

\[文献参考: 基于动态污点分析的二进制程序导向性模糊测试方法\]

0x02我们应该选择什么样的挖掘方式

  

      对于选择挖掘方法并没有一个同意的固定的规定，需要结合多方面的参考和漏洞挖掘者本身的技能水平和方法论的研究程度进行合适的选择。在这里我可以给大家一些建议，让大家能够有个横向的参考。但是需要切记真理（只有高效挖掘漏洞的方法才是好方法）

  

**1、有源代码：**  

污点分析->符号执行->深入分析（阅读源码，断点调试）

  

为何这样的步骤，首先，我们需要高效的寻找漏洞，越能提高效率的方法就需要优先使用，直到无法找到漏洞或者无法满足需求的时候，我们才需要人工的介入。

 

**2、无源代码：**

理解程序->Fuzzing->符号执行

  

在无源代码情况下的程序，我们就需要理解程序后再进行挖掘，我们这个系列所讲的就是无源代码状态下的漏洞挖掘。

 

0x03什么是污数据

  

污数据的早期定义---任何不符合规定的数据都是污数据；

污数据的当前定义---在高纬度下的数据且不符合规定的数据都是污数据；

  

大家对当前定义可能有些模糊，我主要讲一下当前定义是什么：

在以前软件安全相对薄弱的时候对数据的定义和解析都是比较简单的，数据结构也是简单的，大多数程序和数据都是耦合状态的，所以污数据的生成对于数据结构的理解并不需要太在意和太明确，只要能够生成不符合程序输入输出的标准数据就是一条污数据。

但当今的软件安全已经有一个很明显的提升，有着复杂的数据结构和复杂的加密方式，使得我们需要更加关注高纬度的数据——那种符合程序的输入输出又能让程序不理解的数据。

这听起来比较矛盾但又不矛盾，我们要产生能让程序理解的数据，但又要让程序无法执行或异常的数据。

对于任何中挖掘方法，我们所需要的是污数据的命中率，命中率越高，挖掘效率也就越高，相对的，更能挖掘到有价值的漏洞。

现在，我们已经知道了怎么发送数据包给服务器，那我们就可以进行FUZZING测试了。

  

数据包的构造流程:

  

1：AAAA(Mac)BBBB(Mac)CCCC(Mac)DDDD(Mac)EEEE

2：在每个字符后面添加\\x00

3：进行Base64编码

4：在编码后的头部加入177

  

伪代码：

  

x0 = "\\x00"

datas = ""

for x in data:

    datas = datas + x + x0

datas = "177" + base64.b64encode(datas)

c = connect(‘127.0.0.1:7211’)

c.send(datas)

 

到这里基本上可以进行数据包的伪造发送了，那我们应该如何进行fuzzing呢？

通过以上的认知，我们知道(Mac)是分隔符，我们不易进行替换，其他的数据我们都可以进行替换，那我们要替换成什么数据呢？

首先我们得明确我们的目的，需要发现什么类型的漏洞。

从目前来看，我们需要从被控端向控制端发送第一个消息，那我们可以从这个入口点出发，思考下他可能存在的漏洞：

  

1：拒绝服务

2：缓冲区溢出

3：鉴权

  

我们可以再思考下，是否还存在其他的问题可以产生其他的漏洞？

在那些场景下会产生那些漏洞，这才是我们真正需要考虑的也是挖洞思想的核心。

 

纵观整个程序的运行过程，我们可以得出一个结论:

1：被控端链接控制端缺少鉴权：
