**背  景**

Shellcode是软件漏洞利用过程中的一小段机器代码，它被攻击者用来控制目标机器。Shellcode的编写这方面被讨论的不是太多，原因是好多shellcode都是现成的，我们直接拿过来用就行了。最近在研究内核漏洞利用时，发现内核漏洞利用的shellcode更多的是用来完成提权功能的，例如，一个ring3的程序触发漏洞之后执行内核shellcode，此时shellcode只是把ring3程序提权成system进程。但是如果我们有一个可以远程攻击的系统漏洞（例如：CVE-2019-0708远程桌面漏洞），此时我们更希望shellcode能完成RCE/反弹shell的功能，而并不仅仅是让一个ring3程序获得ring0权限。调研发现，17010永恒之蓝漏洞的shellcode是有RCE功能的，该shellcode在内核执行之后，通过windows的APC（异步过程调用）机制在内核向应用层线程注入了代码来完成任意代码执行。国外有人对该shellcode进行了整理并发在了github上，链接如下：

https://github.com/worawit/MS17-010/blob/master/shellcode/eternalblue\_kshellcode\_x86.asm

本篇文章主要分为两个部分，一是对该shellcode的调试分析，二是该shellcode经过简单修改后时可以在xp上运行，但是运行后有时会卡死系统，我会针对这个问题进行定位分析，并给出解决方案。![](../Images/900940727440a189da863910930dea92.png)**调试分析**![](../Images/2dcd16be649673903ac54a8f59e7d323.png)

**Shellcode大体分为七部分来完成RCE：**  

**1、hook sysenter入口函数kifastercallentry**Windows2000以前用int 2e作为中断指令进入内核发起系统调用。从Windows2000以后，为了避免int 2e指令对模式切换的巨大开销，Intel引入了一对新的指令——sysenter/sysexit，实现了快速的模式切换，所以也叫快速系统调用。执行sysenter进入内核之后，入口函数就是kifastercallentry。

Sysenter使用三个MSR(Model Specific Register)寄存器来指定跳转目标地址和栈位置。操作系统在内核模式下通过rdmsr/wrmsr特权指令来设置这三个寄存器，当然必须在系统初始化时(第一次系统调用发生以前)完成。

| MSR寄存器 || MSR地址 || 含义 |
| --- | --- | --- |
| IA32\_SYSENTRY\_CS || 174h || 低16位值制订了特权级0的代码段和栈段的段选择符 |
| IA32\_SYSENTRY\_ESP || 175h || 内核栈指针的32位偏移 |
| IA32\_SYSENTRY\_EIP || 176h ||  目标例程的32位偏移(Kifastcallentry地址)  
 |

我们若通过rdmsr指令读出kifastercallentry函数的地址，然后替换kifastcallentry函数地址为shellcode地址，那么就实现了劫持系统调用。

**2、查找ntkrpamp.exe模块地址**

由于kifastercallentry函数位于ntkrpamp.exe模块中，所以我们知道了kifastcallentry函数的地址后，减去一个固定偏移就可以获得ntkrpamp.exe模块的地址了。但是由于不同版本模块汇编代码不同，所以固定偏移也不相同。函数地址减去固定偏移的方法受版本的影响比较大。该shellcode采用了一种不依赖模块版本获取模块地址的方法。由于模块地址是按0x1000对齐的，所以函数地址按0x1000对齐之后，每次减去0x1000，然后比较是否到达“MZ”，那么就一定可以定位到模块基地址。

**6、遍历ethread 对象，对线程尝试APC注入**

所谓APC（asynchronous procedure call）,翻译过来，即为异步过程调用，是windows提供的一种向目标线程注入一段代码，并且让代码异步执行的机制。每个线程有2个APC队列，分为内核APC队列和用户APC队列。线程处于alertable状态该APC才可以被调度执行。关于APC机制详解如下：

https://anhkgg.com/win-apc-analyze1/

shellcode首先通过KeInitializeApc函数初始化一个APC对象，然后通过KeInsertQueueApc函数将APC对象注入到目标线程中。

**shellcode死循环分析**  
![](../Images/2dcd16be649673903ac54a8f59e7d323.png)在调试的过程中，我们发现该shellcode在windows xp sp3 执行时，有时会卡死系统。在单核系统是表现为cpu占用率100%，在多核系统上表现为其中一核cpu被占满。那么为什么会发生这种情况呢？

我对shellcode做了调试分析，定位到了卡死的原因，卡死就发生在\_insert\_queue\_apc\_loop：代码块上。

```
_insert_queue_apc_loop:    ; move backward because non-alertable and NULL TEB.ActivationContextStackPointer threads always be at frontmov ebx, [ebx+4]…    mov eax, KEINSERTQUEUEAPC_HASH    call win_api_direct    ; if insertion failed, try next thread    test eax, eax    jz _insert_queue_apc_loop        mov eax, [ebp+DATA_KAPC_OFFSET+0xc]      ; get KAPC.ApcListEntry    ; EPROCESS pointer 4 bytes    ; InProgressFlags 1 byte    ; KernelApcPending 1 byte    ; if success, UserApcPending MUST be 1    mov ecx,[ebp+DATA_KAPC_OFFSET+8]    ;ecx points to _kthread    xor edx,edx    mov dl,byte [ecx+0x4a]             ;dl = UserApcPending;    cmp dl,1                            ;cmp UserApcPending is 1    jz _insert_queue_apc_done    ; manual remove list without lock    mov [eax], eax    mov [eax+4], eax    jmp _insert_queue_apc_loop

```

该代码块会遍历目标进程（lsass.exe）的所有线程，若有合适线程被APC注入，那么循环就会退出；若没有合适线程被APC注入，那么循环就不会退出。遍历进程（lsass.exe）的所有线程是通过遍历lsass.exe对应内核对象的ThreadlistHead来实现的。ThreadlistHead 是个循环链表，如果该链表的所有线程都不满足条件，那么遍历就会死循环。一种可行的解决方案是当前shellcode只是遍历特定进程lsass.exe的所有线程，如果所有线程都不能APC注入成功，那么就会死循环，我们修改shellcode，多选择几个进程（如smss.exe,spoolsv.exe,csrss.exe等），然后分别遍历他们的线程，若有线程满足APC注入条件，那么循环就会退出，这么多进程的线程只要有一个线程处于alertable状态，那么APC注入就会成功，shellcode就不会卡死系统。
