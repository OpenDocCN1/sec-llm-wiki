墨云科技尖峰安全实验室在最近对浏览器进行漏洞fuzz时，发现了一个IE11浏览器的类型混淆的漏洞。目前该漏洞已经被修复了，笔者对这个漏洞进行了分析和利用，终于在win7sp1（32bit）+IE11上实现了代码执行，利用环境是win7sp132bit+IE11(KB3124275)，现在把漏洞的细节分享给大家。  

  

  

漏洞说明  

这个漏洞的poc有2个html文件，我们要先加载A页面，然后A页面再通过一个js跳转去加载B页面，这样漏洞才能触发。  

A页面的poc代码非常简单,如下：

  

          m0 = new WeakMap();

 try{m0.set(window, "b");}catch(e){}

         Object.freeze(window);

 window.location.href = "http://127.0.0.1/poc3.html";  

  

  

我们首先创建了一个weakmap对象，Weakmap是用来保存键/值对的。我们可以使用set方法来相weakmap对象里添加很多键/值对。例如：

  

Weakmap.set(“name1”,”mike”);

Weakmap.set(“name2”,”john”);  

  

  

这样我们就给weakmap对象添加了2个键/值对。  

Poc中，我们添加了一个window对象到”b”的键值对。在底层，这表现为给window对象的property域添加了一个自定义属性 weakmapkeymap。

当我们通过js跳转加载另一个页面时，window对象的属性会被设置为undifined，然后还会将weakmapkeymap指针设置为null。

  

if (!keepProperties)

        }

一般情况下，this->SetInternalProperty(InternalPropertyIds::WeakMapKeyMap, nullptr, PropertyOperation\_Force, nullptr);会将weakmapkeymap指针置0，但是poc中的**Object.freeze()** 方法可以冻结一个对象。冻结对象是指那些不能添加新的属性，不能修改已有属性的值。这导致该函数并没有将指针置0.还会指向undifined对象，该对象大小是0x10字节，这个对象被残留给了下一个页面。

我觉得漏洞形成的根本原因是在某些极端情况下，浏览器上一个页面的某些结构对象会遗留到下一个页面，这导致浏览器处理逻辑产生错误。

B页面的poc代码也非常简单

  

m1 = new WeakMap();

try{m1.set(window, "aaaa");}catch(e){}  

  

  

执行m1.set(window, "aaaa");时，IE11首先检查window对象的属性中weakmapkeymap指针是否为0，若不为0，这表明weakmap已经给window对象添加过键值对了，此时就使用该指针指向的对象（weakmapkeymap对象）来更新 键/值对。Poc中 ，指针不为0,但是指针指向的对象是undifined对象，所以也就造成了类型混淆。

下面的代码是给对象添加weakmap键值对的代码。

  

void JavascriptWeakMap::Set(DynamicObject\* key, Var value)

    {

        WeakMapKeyMap\* keyMap = GetWeakMapKeyMapFromKey(key);

 

        if (keyMap == nullptr)

        {

            keyMap = AddWeakMapKeyMapToKey(key);

        }

  

        keyMap->Item(GetWeakMapId(), value); //poc中keymap对象被混淆了

        keySet.Item(key, true);

    }

那么我们怎么样在undifined对象后面放置上可控数据呢？  

在Chakra的堆管理中，只有大小相同chunk才会位于一个同一个heapblock中（0x1000字节），不同size的chunk位于不同的heapblock中。这类似系统堆开启LFH时的情形。 

所以我们布置在undifined对象后面的结构也必须是0x10字节的。

比较理想的情况是把 string的字符串或者 array的数据放在undifined的后面，但是呢，这2个都不能被我们所用。  

如下图所示，chakra堆管理为不同的结构采用不同的堆管理器。有smallnormalheapblock，smallleafheapblock等等。这些smallnormalheapblock，smallleafheapblock就相当于独立的堆管理器，在申请，释放内存时都互不干扰。  

Undefined对象是在smallnormalheapblock堆管理器中申请的内存。String的字符串申请是在smallleafheapblock中。array对象虽然是在smallnormalheapblock中申请的，但是结构大小大于0x10字节，所以我们也不能用。

但是inernalarray的数据貌似我们也不能控制，其实没有关系。原因是该漏洞把internalarray当成了recycler对象。Recycler对象是一个很大的结构，控制堆块申请的一些关键指针，都位于recycler对象偏移0x4000+的地方。我们只需要控制internamarray偏移0x4000+后面的数据就行，这是完全可以做到的   

在chakra堆管理中，相同size 的chunk位于同一个heapblock中，该heapblock的大小只有0x1000字节，与该heapblock相邻的下一个heapblock就可以容纳不同size 的chunk。 所以recycler偏移0x4000的内存处，我们可以放置任意对象。
