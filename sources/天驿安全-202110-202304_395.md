## 0x01 起因

朋友给某甲方做渗透测试，奈何甲方是某知名保险，系统太耐艹，半天不出货兄弟喊我来一块来看，于是有了本文  

## 0x02 客户端RCE一处

朋友把靶标发给我看了下，除了两个下载链接啥也没有

![](../Images/e80348e68297e1bf92b6fdccae44cf6a.png)

  

链接下载下来的东西如图，看了下目录里面还有JRE，那么很显然，这客户端exe就是个JAVA启动命令执行套壳

  

![](../Images/b0d67c5c684898a2d9f2cff961aea84e.png)

  

随后打开program文件夹，逆了一下里面的Jarfull\_path前面定义为用户更新时输入的路径

![](../Images/0aed3cd7ea41e5744adbfb31795fc730.png)

  

那么很简单了full\_path可控，诱导用户安装更新时路径出输入注入命令即可

  

D:\\software  && ping hacker's IP

  

![](../Images/65a24e1c5d4bfb67df006e78a959240b.png)

  

## 0x03 发现Webservice Soap接口

光这一个水来的客户端RCE肯定是不够的，接下来继续挖掘服务端看了看没别的功能点，我就简单FUZZ了一下这个系统三级目录

![](../Images/71eb568d9aa53bb163032764b076b635.png)

  

最后FUZZ出来了一个webservice接口http://\*\*\*\*.xxxxxx.cn/xxxx/service

![](../Images/528a9c7eaf9d4cdd8b9bc5d7ca64be9d.png)

  

拼接出其wsdl接口  
http://\*\*\*\*.xxxxxx.cn/xxxx/service/BusinessService?wsdl但导入SoapUI或AWVS的调试模块进行调试时却发现其导入失败

![](../Images/153bf69eea996f3fa676f4869ca34e37.png)

  

仔细看了下WSDL返回的信息。。。妈的WSDL Import Location和Soap Address Location都是内网域名

  

![](../Images/f56690a26d30e562856d044e35b1bc19.png)

  

不过幸运的是，该系统的外网域名拼接路径后也可以访问到这个WSDL接口但是自动化的Soap接口调试工具是“看见什么就import什么”，这可让人犯了难

  

## 0x04导入SoapUI

思考了一会，突然想起来BurpSuite可以把RequestBody和ResponseBody的值进行替换，hhh，那我们就有办法导入了在Burpsuite的Porxy Option中增加Match&Replace规则将WSDL Import Location和Soap Address Location处对应的内网域名都替换为外网域名

  

![](../Images/17488f2f9d668c03cbc41895681e8df3.png)

  

随后在SoapUI中设置Proxy

  

![](../Images/247ec833471170c4a45d7757d95a054c.png)

  

打开代理，再次添加WSDL，ResponseBody的内网域名成功被替换，WSDL导入成功~

  

![](../Images/49ca2fe6c5d4a651200aa8d245e4051e.png)

  

## 0x05 XXE挖掘

导入接口后，发现有参数为dataXML，心中暗喜XXE估计是送上门了

![](../Images/78b1cd15578c9823e52c3724aa0e7e8e.png)

  

直接BurpSuite中利用XXE OOB测试

  

![](../Images/66bcf7addfbede2adaa8ace2d9908e4b.png)

  

OOB成功，XXE到手，收摊~
