固件分析

NOR 和 NAND 都从板上移除并丢弃。下面的所有数据都是用binwalk和 hex editor 找到的。路由器固件基于 OpenWRT 并不是什么秘密。这是 SpaceX 的官方存储库：
https://github.com/SpaceExplorationTechnologies/starlink-wifi
当然，GitHub 存储库仅包含 GPL 代码，没有任何驱动路由器的 SpaceX 专有组件。
分析转储，我发现 SpaceX 遵循典型的 QCA 模式，但有一些细微差别。系统从烧录到 SoC 中的主引导加载程序 (PBL) 启动。该 PBL 正在 NOR 闪存的零地址处寻找辅助引导加载程序 (SBL)。SBL 初始化硬件（CPU、DDR）并启动主引导加载程序（u-boot）。
u-boot 的目的是支持系统特定的任务，例如启动环境、固件恢复和操作系统启动。这是 Starlink NOR 的简化布局：

2、黑客破解starlink路由器二代固件提取及分析

新一代Starlink终端于2021年底发布。Dishy天线现在是方形的，完全重新设计的室内机结合了WiFi路由器和电源。新的设计应该更划算，所以路由器上没有AUX网口，只有WiFi。后来 SpaceX 发布了一个官方以太网适配器，可以恢复端口。老实说，我不喜欢这种解决方案。我还没有新的路由器，所以我不知道设备内部是否有任何设计限制。此外，正面还有一张从地球到火星的轨道转移椭圆图。报道说前玻璃面板很难拆。

线缆拆解

可能 SpaceX 有一些使用统计数据显示大多数用户只使用 WiFi。我设法找到了适配器并对这个简单的设备进行了逆向工程。只是为什么不🙂

Starlink 以太网适配器具有以太网端口、Dishy 专有端口和 Dishy 专有连接器。

在新的 Dishy 设计中引入了新的防水连接器。以前他们使用标准以太网。

基本上，这个适配器连接着 Dishy 终端和 WiFi 路由器。

用一字螺丝刀很容易打开塑料盖。里面不多：

识别 eMMC 测试点

嵌入式多媒体卡 (eMMC) 包含闪存和控制器，与 SD 卡非常相似。UT 包含一个带有封装标记 JY976 的 Micron eMMC 芯片，Micron 提供了一个方便的工具来将这些封装标记解码为实际部件号：
https ://www.micron.com/support/tools-and-utilities/fbga 。
有问题的 eMMC 芯片的部件号为 MTFC4GACAJCN-1M，并在 BGA-153 封装中包含 4GB 闪存。
在大多数情况下，我们会拆焊这样的 eMMC 芯片，重新焊球并使用 BGA 插槽将其丢弃。然而，在这种情况下，我们首先尝试在线倾倒 eMMC，以尽量减少损坏我们的 UT 和 eMMC 芯片的可能性。
eMMC 芯片与 SD 卡的相似之处在于它们共享相似的接口；eMMC 芯片最多支持 8 条数据线，而 SD 卡最多支持 4 条数据线。eMMC 芯片和 SD 卡都支持仅使用一条数据线，但代价是读/写速度较低。
要在线读取 eMMC 芯片，我们必须识别时钟 (CLK)、命令 (CMD) 和数据 0 (D0) 信号。主 SoC 上方的 10 个测试点引起了我们的注意，因为 10 个测试点可能是 CMD、CLK 和 8 条数据线。此外，所有这些测试点都连接了一个 30 欧姆的串联电阻，这对于 eMMC 连接来说是比较常见的。我们将一根短线焊接到每个测试点，使我们能够在 UT 启动过程中创建逻辑分析仪捕获。使用这样的捕获可以相对简单地识别所需的信号。CLK 信号将是唯一的重复信号，CMD 是时钟开始翻转后首先激活的信号，而 D0 是发送数据的第一条数据线。幸运的是，确定剩余的 7 条数据线对于转储 eMMC 内容是不必要的。

在线倾倒 eMMC

要转储 eMMC 芯片，我们可以将读取器（支持 1.8V IO）连接到已识别的测试点。存在主要针对电话维修的商业阅读器，并且应该可以很好地用于此目的（例如 easy-JTAG 和 Medusa Pro）。或者，您可以使用带有集成电平转换器（例如https://shop.exploitee.rs/shop/p/low-voltage -emmc 适配器）。如果您周围有一些零件，您也可以自己制作一些东西。下图显示了连接到 TI TXS0202EVM 电平转换器分线板的标准 USB SD 卡读卡器。
我们只为 eMMC 供电以防止主 SoC 干扰。eMMC 可以通过附近的两个去耦电容供电，3.3V 由 SD 卡读卡器提供，1.8V 由实验室电源提供。一旦一切都正确连接，我们就可以创建磁盘映像以供以后分析。
请注意，在电路中读取 eMMC 并不总是一件容易的事。稍长的电线已经可以阻止读取成功。在这种情况下，它相当简单，即使连接了这些相对较长的电线，系统似乎也能正常运行。

#define ECC_DAT_SIZE        (ECC_BLOCK_SIZE - NPAR - 1)

 

#define ECC_BLOCK_TYPE_DATA '*'

#define ECC_BLOCK_TYPE_LAST '$'

#define ECC_BLOCK_TYPE_FOOTER   '!'


最后归结为，在这个实现中，一个受 ECC 保护的内存块以魔术头值SXECCv开头，后跟一个版本字节 ( 1)。这个神奇的值标志着 ECC 保护数据的开始，也标志着头块的开始。标头块本身包含（除了魔法值和版本字节）、215 字节的数据、星号 ( *) 和 32 字节的 ECC 代码字。


头块后面是多个数据块。这些数据块中的每一个都是 255 字节长，包含 222 字节的数据，后跟一个星号 ( *) 和 32 字节的 ECC 代码字。最后一个数据块包含一个美元符号 ( $) 而不是星号，然后是最后一个页脚块。此页脚块以感叹号 ( !) 开头，后跟 ECC 受保护内存块（4 字节）中的数据字节数和这些数据字节的 MD5 摘要。


至此应该清楚为什么 Binwalk 没有成功提取内核、initramfs 和 FDT。Binwalk 能够获取指示特定文件开始的魔法值，但文件的每个块都有阻止 Binwalk 提取它的附加数据。在使用 Binwalk 提取图像之前，我们使用了一个简单的 Python 脚本来删除额外的 ECC 数据。同样，我们现在也可以使用 dumpimage 来获取有关 FIT 图像的更多信息。

开发硬件

开发硬件经常落入坏人之手[6, 7]。SpaceX 的工程师考虑了这种情况，似乎试图主动检测不再受其控制的未融合开发硬件。开发硬件的地理围栏只能在某些预定义的区域工作，其中大部分显然是 SpaceX 的位置。如果在这些预定义的地理围栏之外使用开发硬件，SpaceX 可能会收到通知。
