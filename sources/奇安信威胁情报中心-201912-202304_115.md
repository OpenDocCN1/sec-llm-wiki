# CVE-2022-30190：Microsoft Windows 支持诊断工具 (MSDT) 远程代码执行漏洞利用分析

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzI2MDc2MDA4OA==&mid=2247501333&idx=1&sn=e2f6c8cec8f591d41c85678431efb147&chksm=ea663162dd11b87482799fc2e4518b5bc5bc0bd9c746bafc57995400a42ba024eae81d560bc2&scene=126&sessionid=1681277454#rd](http://mp.weixin.qq.com/s?__biz=MzI2MDc2MDA4OA==&mid=2247501333&idx=1&sn=e2f6c8cec8f591d41c85678431efb147&chksm=ea663162dd11b87482799fc2e4518b5bc5bc0bd9c746bafc57995400a42ba024eae81d560bc2&scene=126&sessionid=1681277454#rd)

  

  

  

综述

  

近期，安全社区通过VirusTotal发现一个通过Office远程加载特性访问HTML页面进而利用ms-msdt协议在Word文档中执行恶意PowerShell的0day漏洞利用文档。其实该漏洞早在4月12日就已经被相关安全人员通过VT发现并提交给微软，其利用上和去年的CVE-2021-40444有很多相似之处，通过OLE的方式远程拉取一个恶意HTML，该HTML中通过msdt协议绕过了Office自带的保护视图。后续通过分析发现微软实际上之前已经尝试修复该问题，但是依旧存在rtf文件格式的绕过，最后通过msdt协议中的一处powershell注入导致最终的代码执行。

  

  

漏洞分析

  

样本通过构造一个ole对象远程拉取恶意的html文件，这里的加载方式和CVE-2021-40444类似。  

![](../Images/b12c1dd3d6890ebf1ed8cb8306d6096e.png)

Html文件如下所示，其中使用了ms-msdt协议，该协议是Microsoft Support Diagnostics Tool 的缩写，它是一种实用程序，用于排除故障并收集诊断数据以支持专业人员分析以解决问题，其可以调用本地脚本，而不触发office的保护视图，从而导致代码执行，如下所示样本执行的代码通过base64编码。

![](../Images/8c8eb113e6908f6cbc3e8e157504044c.png)

编码的数据如下所示，这里猜测其中实际执行的exe应该是通过某种方式部署到了目标机器中（目前未知）。

![](../Images/7d9d0c4d723a8d3cee3862902edd12f3.png)

这里构造poc就很简单了，替换换成模板注入的html即可，这里确保你的远端exp 存在这个路径下http://127.0.0.1:8080/www/RDF842l.html

![](../Images/283c32c5b1ac9ea6e8e3c05da27a8b0e.png)

如下所示，确保RDF842l.html保存路径如下所示：

![](../Images/1e1dc43a3e375d8bce1b4e886bb00e91.png)

打开对应的52945af1d.docx，即可触发代码执行，这里的测试环境是office 2019

![](../Images/4626fec2a015c6fb95d4fc8ce1dbea51.png)

可以看到在触发漏洞的时候，word会通过注册表选项查找对应的md-msdt这个协议，用于处理脚本中的ms-msdt后续的字段可以看到最终其实找到的就是执行代码的msdt.exe这个程序。

![](../Images/47323b9267078d5957e0c397a2f832d9.png)![](../Images/72d3a07a0a9327eb76a4475d048ce2a7.png)

当你把office升级到大版本2205后，漏洞将不再触发，需要注意目前只有2019/2021提供自动更新功能。

![](../Images/0e3e128df988560453775dac725f214a.png)

通过该功能可更新到大版本2205，该版本不受影响。

![](../Images/085d40b01ba92647a5a6994352ee92b3.png)

如下所示，可以看到完全不会触发协议的访问，因为其中利用的特殊的 Office 远程 OLE 对象自动加载方式已经被作为非安全问题修复（没有CVE编号）。但是攻击者依然可以使用 rtf 格式样本来实现自动触发漏洞。

![](../Images/b87bea98570b1ede41ead7681ee98460.png)

其构造方式只需要将之前的docx文档按rtf另存一份即可。

![](../Images/340d201bd9190e86c64654d5dda72133.png)

分析发现计算器是由sdiagnhost.exe这个程序启动的。

![](../Images/16f48875439a55c65bea493dd9024e16.png)

分析sdiagnhost.exe发现其是通过CScriptedDiagNativeHost::RunScript函数来启动的calc。

![](../Images/4b8c6818cb712bc2bfcfd514126610d7.png)

这里通过函数名可以猜测是用于调用本地的脚本，调试发现其参数传递了一个ps1脚本：

C:\\Windows\\diagnostics\\system\\PCW\\TS\_ProgramCompatibilityWizard.ps1

对应的参数就是构造的exp中的IT\_BrowseForFile = /../../$(calc).exe，这是最简的exp，在sdiagnhost.exe中没有任何相关的参数过滤操作。

![](../Images/0eeae99bd1fae0e0a8f41515a2443c46.png)

来看TS\_ProgramCompatibilityWizard.ps1脚本可以看到通过注释发现其功能为” 如果在这些位置没有找到快捷方式，我们将转到浏览文件屏幕”，获取的IT\_BrowseForFile保存在selectedProgram，并通过Test-Selection校验。

![](../Images/d331ba5131069b097c75ff063f44bac2.png)

Test-Selection逻辑如下，首先判断其路径是否为空，之后依次为test-path -literalpath $appPath及判断是否以exe/msi后缀结尾，这也就是为什么我们exp中最后必须是.exe，.msi也是可以的。

![](../Images/18eedff84ac9538af35e88fc521f72bf.png)

这里来看test-path -literalpath $appPath，可以看到其用于判断一个路径，如下所示这里/../../也是合法的，因此exp中需要构造至少/../../，否则你就需要提供一个真实合法的路径。

![](../Images/6cadeabf11fc5cd99a747c69fd7c307f.png)

可以看到我们传入的参数实际上看着是有判断$()注入情况的。

![](../Images/c7ad150dd18c9fb007225e9a840fb735.png)

最终应该是以下位置的代码导致代码执行，这里$appName/$selectedProgram都来自于攻击者的输入，而这两个参数通过阅读代码可知，$selectedProgram是没有经过$检测的，而$appName有，详细我们可以通过修改脚本日志输出来看看具体的问题。

![](../Images/5090ddbba37e7cc5e1791aced3907dcf.png)

通过查询也可知，这里疑似最终代码调用的cmdlet并不能直接通过powershell跑，其只能通过漏洞触发的路径有msdt.exe – > sdiagnhost.exe->TS\_ProgramCompatibilityWizard.ps1 来调用。

![](../Images/db1332f5841d9f485440d0a5774b9cff.png)

当我们需要修改TS\_ProgramCompatibilityWizard.ps1脚本进行日志输出的时候发现，无法修改这个文件，这里可以通过修改其对应访问策略来使得其他用户也能修改该文件，从而有助于我们的调试。

首先将selectedProgram获取的值输出，并在selectedProgram经过Test-Selection检测后同样输出，看是否有什么变化。

![](../Images/ee976bf4fb6daf96dbbd2f26e25ca04f.png)

之后经过while循环后的selectedProgram输出，看有什么变化，同样将关键参数appName输出，看看这里的Replace是否真正起到了过滤的作用。

![](../Images/e6e8dbb348f2085c0e1fac40d9505adb.png)

在关键代码执行前输出appName/selectedProgram这两个参数，并通过注释掉Update-DiagRootCause这行代码来确定真正触发代码执行的位置是否是这里。

![](../Images/27c662e9f73703eae5f2d62f5f213b3c.png)

通过测试后发现Update-DiagRootCause这行代码注释后，漏洞无法触发，即该调用导致了最终的代码执行，而其传入的参数日志输出如下所示，可以看到selectedProgram全程都是/../../$(calc).exe，没有经过过滤，而appName经过replace之后的值为$(calc)，并不是我们期待的\`$(calc)，那这里到底是appName/selectedProgram导致了代码执行？

![](../Images/4493fb813c8ea6b3a59fcdd0cfaec523.png)

我们尝试对这个两个变量进行控制。

![](../Images/c68aa110a7527b9a091f50d42f2c217d.png)

如下所示可以看到运行后，二者只要用一个正常，漏洞都能触发，即导致漏洞的是$appName /$selectedProgram这两个参数，由于对其过滤不严格，从而导致了powershell的代码注入。

![](../Images/d1e02134aac69442c58d9e3a06a36711.png)

如下所示可以看到gui下的攻击入口其实就是下图的位置

![](../Images/9d0c9f8f96c12977a45b8de67102534e.png)

这里将其替换为/../../$(calc).exe

![](../Images/363d0d434ba40c2252a775e7eb8dc5bb.png)

将直接代码执行

![](../Images/5e4e0e9074398506720d76915fb71e0d.png)

该样本通过ole对象拉取恶意html的动作会导致office落地文档直接被查杀。

![](../Images/4b8ed56a4add56a7e451037daa2332c2.png)
