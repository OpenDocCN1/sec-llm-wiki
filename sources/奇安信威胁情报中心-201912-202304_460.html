一、Mozi概述

自2019年9月份开始，我们在物联网威胁数据平台中，持续发现一类特别的物联网恶意样本，并监测到它在境内开始出现大规模传播的趋势。该恶意样本以Mozi.a和Mozi.m命名，分别运行在ARM CPU和MIPS CPU架构的物联网设备上，并以P2P的通讯方式进行命令控制和广泛传播。该类样本是继“.i”命名的Hajime家族[1]之后，我们发现的第二个大规模物联网P2P僵尸网络。截至到2020年2月27日，物联网威胁数据平台共捕获该恶意程序的各类变种1281个，监测发现的感染地址共有105234个。

其中，Mozi在中国境内的感染趋势如下图所示：

图2  Mozi境内感染趋势图-动态图

二、Mozi样本统计分析

对捕获到的1281个样本进行统计分析发现,其中791个样本支持ARM CPU架构,命名为“Mozi.a”；490个样本支持MIPS CPU架构的，命名为“Mozi.m”。如下图所示：

图3  CPU架构分布图

其中997个样本采用了加壳技术对抗分析。与其他常见的IoT恶意样本加壳方式一样，Mozi也主要采用UPX压缩方式进行加壳，并且使用了多种对抗方式防止分析人员对恶意样本进行解压脱壳。如下所示：

图4  样本加壳分布图

对样本静态分析结果进行统计发现，Mozi样本主要采用telnet弱口令和漏洞利用进行传播。内置列表中的弱口令多达78个，利用的漏洞有12个。其中漏洞利用列表如下:

表1  Mozi漏洞利用列表 

样本的主要恶意行为是DDos攻击，其攻击模块复用了Gafgyt家族的部分攻击代码，支持HTTP、TCP、UDP等常见的DDos攻击。

三、样本逆向分析

我们结合人工分析和在仿真环境下的动态运行行为对 Mozi 的功能实现进行深入分析。下面分执行流程和通信协议两个部分来介绍。

3.1 Mozi样本执行流程分析

Mozi 样本运行后，首先绑定本地端口0x3991（即14737端口），可以用 netstat 命令在仿真环境下查看其监听端口情况，如下图所示。

图5  Mozi 监听本地端口

然后，对/proc目录下所有PID的exe软链接所指向的路径进行遍历，并查找是否包含指定路径的进程，若存在则杀掉相关进程。

图6  遍历/proc 进程

通过读取/proc/net/tcp或者/proc/net/raw，查找对应网络连接端口为1536和5888的进程并杀掉进程。

图7  遍历网络连接

判断系统是否存在python命令文件，若存在则修改进程的名称为sshd，否则修改为dropbear。

图8  修改进程名称

通过设置iptables禁用22,23,2323端口。

图9  通过 iptables 禁用本地端口

随后其会随机从程序硬编码的port列表中选择端口，并配置iptables允许相关端口的网络通信。

图10  通过 iptables 允许通信端口

Mozi 内置了一个16位的密钥和初始的配置信息，其首先用密钥异或解密该配置信息。

图11  解密配置信息

配置信息解密的结果如下所示。

图12  解密后的配置信息

Mozi 程序会将解密后的配置信息写入同路径下的文件，其中硬编码了一个URL：http://ia.51.la/go1?id=19894027&pu=http%3a%2f%2fbaidu.com/，该域名推测是一个网络流量统计服务提供商，其中id字段可能是分配给使用者的 id 标识。

图13  写入的配置文件内容

Mozi 配置信息中采用中括号包裹的配置项名称和值的形式，这里首先会解析配置中的[hp]，[ver]，[count]配置项参数值。

图14  解析配置参数

首先判断解析的[count]参数值是否为http链接，如果是，则判断是否包含[idp]，然后发起一个http请求。

图15  [count]参数解析

图16  发起 http 请求

Mozi程序基于修改的 DHT 协议（即 Bitorrent）实现命令控制网络的构建，DHT 协议首先需要将自身加入到节点网络，从而能够进行相邻节点列表的获取和通信，所以在初始加入节点网络时，会内置初始的节点列表。Mozi内置的节点地址如下图所示。

图17  初始节点列表

当接入到节点网络后，进入到循环的请求和响应逻辑。

图18  请求和响应

在Mozi主函数中后续还会对目标网络设备进行登录凭据的暴力破解，以及漏洞扫描和利用过程，一旦成功，则会触发从本地下载对应的 Mozi 主体执行文件到远程设备中并执行起来，从而实现广泛传播。

图19  暴力破解和漏洞利用
3.2 Mozi 通信协议分析

在本节将详细分析 Mozi 定制化的 DHT 协议实现原理。

1）节点信息构造

首先需要构造自身节点相关信息，以便用于后续的节点加入和通信中使用。

图20  构造自身节点相关信息

Mozi内置了一个节点version的生成算法，其将"1:v4:JBls"字符串的最后4字节进行如下方式修订：

| 1byte 随机字符 | 1byte magic字符 | 剩下两个字符通过算法计算得到 |

图21  节点version生成

剩下两个字符的计算算法如下图。

图22  生成算法

然后其会对内置硬编码的初始配置信息（长度为528字节）进行验证，这里验证算法使用的是椭圆曲线算法，验证后对配置信息进行异或解密。

处理[hp]配置参数，[hp]配置的是用于生成节点id的前缀，默认为88888888，前缀用于替换节点id生成的一个硬编码字符串序列"123888d1:ad2:id2bo"，也就是说替换之后变成"88888888:ad2:id2bo"。

图23  生成节点id

例如我们在仿真环境下运行Mozi时，返回的数据包可以看到对应的节点id形如上述所说。

图24  节点id示例

2）节点网络加入

按照 DHT 协议，节点需要首先发送ping请求给初始节点来获取相邻节点列表。在前面的分析中也提到过Mozi中内置了8个初始节点，端口为6881。

图25  初始节点列表

如果初始的配置信息中包含了[nd]参数，则会按照[nd]参数值作为节点 id 标识发送ping消息。

图26  发送 ping消息

如下图示例，我们可以看到 Mozi 在初始连接时udp连接了212.129.33.59：6881，其发送的 ping 请求，节点 id 的前缀为88888888。

图27  ping消息数据包

3）请求和响应

当加入节点网络后，则进入循环请求和响应其他节点的通信流程。这里实现了一个响应包解析函数用于解析返回的数据。其首先搜索返回数据中是否存在1:v4:，并且会将这里的版本信息给保存起来，用于后续对其进行校验。

图28  获取远程节点 version 信息

相比DHT协议标准的解析函数实现来说，Mozi在尾部增加了自定义的响应包筛选策略。

图29  标准DHT响应解析

图30  Mozi 自定义响应解析

例如，当响应包中未出现1:y1:q时，并且长度大于99则为Mozi 自定义的配置更新和命令控制请求。其会执行 switch..case 语句的 case 7逻辑中。

当 Mozi 加入节点网络后，会发送 find_node 请求获取相邻的节点列表。例如下图示例为向67.215.246.10节点发出的 find_node 请求和响应，从前缀可以发现都是 Mozi 节点。

图31  Mozi  find_node请求数据包

4）配置更新和命令控制

这里我们主要分析 Mozi自定义的命令控制通信部分，也就是switch..case为7的情况。其首先对接收的配置信息进行校验，校验通过后则进行异或解密和解析。这里的校验逻辑和前面分析的校验逻辑相同，都是使用椭圆曲线算法。

图32   获取配置和校验

然后解析[cpux]、[ssx]、[ss]、[sv]的配置参数值。

图33  配置参数解析

和初始逻辑一样，其同样会解析[hp]、[ver]和[count]配置参数，并且还支持命令控制的参数：

[atk]参数实现ddos攻击；

[dr]参数实现下载和执行；

[ud]参数实现自身程序更新。

图34   下发控制命令

其也可以在[rn]配置参数中指定需要执行的shell命令，并将结果返回。

图35  下发shell命令
