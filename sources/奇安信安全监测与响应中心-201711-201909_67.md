## **0x02 漏洞分析**

**eBPF** (extended Berkeley Packet Filter)

eBPF 构架

![](../Images/bea79a070ebf0cbb8a77704d23715695.png "img")

ebpf 是一个用于过滤(filter)网络报文(packet)的架构。内核通过bpf\_*prog\_*load() 来载入用户层传入的伪代码，通过某事件来触发内核执行这些伪代码，伪代码通过内核的verifier 机制来确认注入的代码无害，在\_\_bpf\_*prog\_*run() 中将这些伪代码进行执行，同时通过bpf 的map 机制以key-value 的形式穿件数据库，用户层和内核层共享map 中的数据，大大的提升了效率。

详情：https://www.ibm.com/developerworks/cn/linux/l-lo-eBPF-history/index.html

**漏洞情况：**

用户层的代码提交给BPF 时，经过verifier 检查，

问题出现在bpf verifier 上面，verifier 在检验用户层传入的\_prog 是否合法时，

在check\_alu\_op 函数处有如下代码：

```

insn->imm 赋值给regs的imm 成员是，两者的数据类型都是有符int 类型，这不会出错。

再看下，在prog 通过了verifier 检查后, \_prog 在\_\_bpf\_prog\_run 函数得到执行，在解析JMPJNE\_K 指令时有如下比较：

DST 为宏，定义为：

```
1.  `#define DST regs[insn->dst_reg]`

```
1.  `u64 regs[MAX_BPF_REG], tmp;`

```
1.  `#define IMM insn->imm`

insn 为bpf\_insn 结构， 可以注意到 regs 为无符64 位整型，insn->imm 为有符32位整形，无符号64位数与有符32位数去比较，就会发生符号扩展，从而可能导致比较结果不在计算范围内，导致漏洞出现。

```

观察upstream44.c 的pwn() 函数，提权的思路为 首先通过获取frame pointer , 然后通过addr & ~(0x4000 - 1) 来获取current 结构，从current 结构获得 task\_struct 地址，从而获取cred 指针，获取到uid 指针，最后修改uid 来提权。

具体过程如下：

**获取frame pointer**

首先exp 创建长度为3 的map\_array , 使用bpf\_prog\_load 将prog 字节码载入内核，使用socketopt 绑定sockets的过滤器为\_prog ，接着进入提权阶段，首先更新map 的三个元素分别为(1, 0, 0)，通过writemsg 来触发eBPF 过滤使\_prog 字节码得到执行。

将mapfd 赋值给r9, r9 又被赋值给r1, r2 = fp -4, 将fp - 4 地址的值设置为0, 随后进入bpf\_map\_lookup\_elem函数来获取map 的第一个元素，

```
1.  `static u64 bpf_map_lookup_elem(u64 r1, u64 r2, u64 r3, u64 r4, u64 r5)`
    
2.  `{`
    
3.  ` /* verifier checked that R1 contains a valid pointer to bpf_map`
    
4.  ` * and R2 points to a program stack and map->key_size bytes were`
    
5.  ` * initialized`
    
6.  ` */`
    
7.  ` struct bpf_map *map = (struct bpf_map *) (unsigned long) r1;`
    
8.  ` void *key = (void *) (unsigned long) r2;`
    
9.  ` void *value;`
    
10.  
     
11.  ` WARN_ON_ONCE(!rcu_read_lock_held());`
     
12.  
     
13.  ` value = map->ops->map_lookup_elem(map, key);`
     
14.  
     
15.  ` /* lookup() returns either pointer to element value or NULL`
     
16.  ` * which is the meaning of PTR_TO_MAP_VALUE_OR_NULL type`
     
17.  ` */`
     
18.  ` return (unsigned long) value;`
     
19.  `}`
     
```

函数返回为指针，保存到r0 虚拟寄存器中，指向该元素，

```
1.  ` │0xffffffff81177226 <__bpf_prog_run+1942> add rax,0xffffffff81176400 │`

3.  `B+ │0xffffffff81177231 <__bpf_prog_run+1953> mov QWORD PTR [rbp-0x270],rax │`
