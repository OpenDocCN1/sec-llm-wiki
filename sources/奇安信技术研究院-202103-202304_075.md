在软件安全问题中，相比开发者蓄意植入的后门木马，无意之中引入的软件漏洞带来的威胁更为普遍。仅仅依靠程序员本身的安全意识很难保障代码的安全性，尤其是现代软件工程的模块化结构特点，导致代码质量本身也参差不齐，如同木桶效应一般，任何一个防护薄弱的代码模块，都可能被攻击者利用，导致软件甚至整个系统被攻破。

  

为缓解各种攻击，业界也一直在应用软件、操作系统、甚至物理硬件等各个层面增加各种安全机制，缓解各种常见且成熟的攻击手段。例如，通过栈保护机制GS校验调用栈，加大栈溢出的实现难度；通过数据执行防护（Data Execution Prevention，DEP）机制，使攻击者注入数据区域中的Shellcode 代码不可执行；通过地址随机化（Address Space Layout Randomization，ASLR）机制，使攻击者难以预测关键资源地址，从而无法通过硬编码地址进行漏洞利用等。但这些保护机制往往需要可执行程序开启某些代码特性进行配合，例如ASLR就需要程序在编译时开启重定位节（relocated section）。

  

相对健全的安全机制，可以在出现漏洞时加大漏洞利用的技术难度，降低漏洞带来的安全威胁，从而显著提高软件的安全性。如Internet Explorer（IE）11上出现的远程代码执行高危漏洞（MS16-063），因为受到控制流保护机制（Control Flow Guard，CFG）的保护，在Windows 8及更高版本操作系统上的利用难度就更大。但在实际环境中，由于兼容性等各种各样的原因，很多安全机制在大量应用软件甚至系统软件中并未被实际启用，为评估各种安全机制的落地应用情况，我们针对Windows、macOS、Android等主流操作系统中的基础软件、应用程序等进行了系列测量和分析。

**1. Windows系统软件安全性测量**

  

我们分析的系统软件包括Windows XP、Windows 7x64、Windows 10x64这3个系统中的基础应用、动态链接库等系统自带的所有PE文件，以及VisualC++Runtime等官方提供下载安装的运行库文件。代码安全特性测试结果如表3-3所示。

**表3-3 Windows系统软件代码安全特性测量**

![](../Images/8b24104bb4cb51f51d715db1a9746108.png)

  

整体来看，对于重要性较高的机制，在越新版本的操作系统上，系统软件的安全机制启用率越高。例如对栈溢出结合代码注入这种历史上最常见的漏洞攻击方法，ASLR与DEP机制能够进行有效防护。开启这两种安全特性的系统程序，在Windows XP上仅占23%，在Windows 7上则上升到90%左右，到Windows 10已超过99%。此外，还有如CFG、RFG等新的保护机制也随着操作系统的更新而出现并逐渐普及，因此从安全性的角度来讲，操作系统的版本越新，安全防护的等级自然也越高。

  

但是从另一个角度来讲，由于系统安全存在木桶效应，因此任何一个短板都可能成为整个系统的隐患。从测量分析结果可以发现，系统软件支持和采用的安全机制虽然越来越多，但离完全普及还有一定距离。即使是ASLR等非常必要的安全特性，在最新的Windows 10操作系统上也未能达到100%的普及。

  

**2. Windows第三方应用安全性测量**

  

我们选择国内十多个热门软件下载市场，从中选择排名靠前的第三方应用程序作为分析目标，对总量超过30万款的第三方软件进行了安全性分析和测量。如系统软件的分析方法，我们统计了全量软件对各种安全机制的支持情况，另外，我们根据应用软件的发行时间，单独统计了近3年内发现的第三方软件对各种安全机制的支持情况，如表3-4所示。

**表3-4 应用软件的安全机制测量**

![](../Images/a4a34cedd74ef7bb9dd1241c97538006.png)

  

分析结果表明，与系统软件相比，第三方应用软件上各类安全机制的采用情况较差，这可能与程序兼容性、开发者安全意识、软件工程规范程度等多种因素有关。但类似GS/NX/ASLR等可以显著提高漏洞攻击门槛的必要安全防护机制，普及程度也远不及系统软件，再加上第三方软件本身的数量庞大，因此这些第三方软件容易成为攻击者的突破口，需要引起网络安全管理者的注意。

  

此外，对比全量软件的分析结果和近3年发行软件的分析结果可以看出，安全防护机制的采用比例整体呈上升趋势。事实上，部分较新的安全机制，如RFG/CFG等，上升相对缓慢，但DEP等实用性较强的安全机制却能得到较好普及。各种安全机制逐年上升的比例如图3-8所示。 

![](../Images/90dccd245672b1b1334943bb20a0e6cb.png)

**图3-8 市场软件安全防护机制变化趋势**

  

上图的分析结果中，一个值得关注的现象是，很多第三方应用没有对自身代码进行签名，采用了Authenticode的软件占比不到60%。在现实环境中大部分恶意代码没有签名，虽然代码签名不能代替安全检测，但如果能提高合法程序的签名普及率，将有助于防止合法软件被恶意软件假冒和伪造。

  

02

**macOS系统**

macOS中虽然使用了系统完整性保护（System Integrity Protection，SIP）等安全机制保证应用程序在终端运行时的安全性，但程序自身安全特性的配合仍然是必要的，macOS中比较主流的安全机制包括以下几种。  

  

△Stack Canary：栈溢出保护机制。通过在栈中加入Canary Value，当发生栈溢出时对其进行修改，从而能够快速检测出缓冲区溢出攻击。

  

△NX（No-eXecute）：内存区域不可执行机制。其基本原理是将数据所在内存页标识为不可执行，处理器无法将此类内存页中的数据作为代码执行，这种技术可防止多数的缓存溢出式攻击。

  

△PIE（Position-Independent Executables）：位置无关的可执行文件。该机制和Windows下的ASLR机制类似，程序开启地址随机化选项意味着程序每次运行的时候加载地址都会变化，这主要是为了解决二进制本身地址已知的问题，可用来防御ROP（Return Oriented Programming，面向返回的编程）攻击。

  

△ Restrict：如果在程序中包含Restrict segment段，则在加载链接库时会强制进行签名校验。

  

△ Code Signature：开发者对代码的签名机制，支持系统对程序来源进行校验。

  

△ ARC（Automatic Reference Counting）：自动引用计数。在编译时提供了对Objective-C和Swift编程语言的自动内存管理代码，使开发者无须考虑retain和release操作。

  

本节我们通过分析近年来各版本macOS系统安装包中的程序，评估了这些安全机制在系统程序中的覆盖情况。评估结果如图3-9所示，根据分析结果可以看到，macOS系统自带可执行文件、链接库中使用以上安全机制的情况并不理想。其中部分安全机制的开启比例较高，例如NX；另一部分安全措施随系统版本的迭代开启的比例在增加，例如StackCanary；但大部分措施的开启比例仍然未达到较高的数值，例如PIE。

03

** Android系统**

近年来，移动智能终端与传统PC设备的严格界限已经变得模糊，移动智能终端不仅融入了整体网络空间和软件空间中，甚至比传统PC设备占据了更大的比例，其安全问题的数量和重要性自然也与日俱增。然而，以目前的Android安全生态来看，评估Android安全性的方案还远不够完善，并且不同地域的不同手机制造商之间也存在着很大差别。在2020年7月召开的Android Security Symposium线上会议中，有研究人员提出了建设侧重于评估Android设备安全性的数据库，收集了各个设备上诸如平均更新补丁频率、安全补丁等级、保证的最长补丁延迟等信息用作参考指标。  

  

在Android生态快速发展、其安全问题的重要性与日俱增的现实情形下，我们也针对Android系统中的一些安全问题进行了测量。测量对象主要包括从Google、华为、三星、OPPO、OnePlus等各个厂商官方发布渠道获取的4,356个AndroidROM、从ROM镜像中提取的大量系统程序，以及144,886个预装App。ROM镜像数量和比例如图3-10所示。 

![](../Images/2f0ffbf2d6e01991aeeef56f66a50b78.png)

**图3-10  收集的各厂商Android固件**

  

与Windows、macOS等桌面平台类似，在Android系统程序中，我们首先对地址随机化、数据不可执行等安全机制的覆盖情况进行了测量和分析。然后，针对Android系统本身的特殊性，即各个厂商采用的系统对AOSP补丁的依赖性，我们对Android固件的安全补丁的及时性进行了分析评估。

  

由于Android系统底层采用Linux内核，安全机制也比较通用，因此我们重点选择了其中最重要也最典型的5种漏洞缓解措施进行分析。

  

△ Stack Canary：往栈里添入Canary信息，通过比对Canary来判断是否存在栈溢出攻击，类似于Windows中的GS机制。

  

△NX：将数据所在内存页标记为不可执行，以阻止Shellcode在数据页上执行命令，类似于Windows中的DEP机制。

  

△ PIE：位置无关的可执行文件，用于内存地址随机化，用于缓解ROP等攻击。

  

△ RELRO（Relocation Read-Only）：设置符号重定向表为只读，或在程序启动时就解析并绑定所有动态符号，用于缓解GOT（Global Offset Table）攻击。

  

△Fortify：GCC在编译时对一些危险的函数，比如字符串或内存操作函数插入额外代码进行检查，用于缓解缓冲区溢出攻击。

  

针对上述5种安全机制，我们从收集的Android ROM镜像内提取系统程序（ELF文件）进行了大规模测量，发现各安全机制的整体覆盖率呈阶梯上升。首先，以其中最具代表性的Stack Canary和Fortify两种机制为例，我们按照ROM镜像的发布时间，针对这两种安全机制的覆盖情况进行评估，如图3-11所示。 

![](../Images/c09ff603a526ee027ef48a9f6de97f74.png)

**图3-11 Android ROM镜像中的Canary和Fortify覆盖情况**

  

图中的横坐标代表ROM镜像的发布时间，纵坐标是安全机制启用的占比，从左往右可以看出安全机制的启用有明显的阶梯状。另外一个特别有趣的现象是，在2018年7月到2019年6月这个时间段，有明显的“安全低谷”存在，即这两种安全机制因为某些原因关闭了一段时间。经过我们人工确认分析，该低谷时期涉及的更新包，其Android版本均为9.0，而这个时间段也近似于Google发布Android9.0的更新包的起始时间和最后一个更新包的截止时间。因此可以认为，在Android9.0项目的整个周期内，相关的ROM镜像版本都存在一定的安全防护机制弱化的情况。

  

除Stack Canary和Fortify以外，另外3个安全机制（NX、PIE、RELRO）的覆盖情况比较理想，绝大部分二进制程序有启用，几乎已经成为标配，统计结果如图3-12所示。

![](../Images/8d96836c029df272199d611accec1e0d.png)

**图3-12 Android ROM镜像中的NX、PIE、RELRO覆盖情况**

  

我们进一步对相同手机厂商的不同产品线对应的ROM进行了分析，发现其安全性也存在差异。以Google代号为fugu（Nexus Player）和shamu（Nexus 6）的两款设备为例，这两个设备同属Google厂商，且维护周期相似，均在2014年11月到2017年10月期间内，因此我们选择它们作为比较目标。如图3-13所示，可以看到shamu的更新频率较fugu明显更高，并且以ROM镜像内程序的Fortify机制启用百分比来看，两者的启用情况也有较大的差异。此外，fugu在2017年9月发布了Android 8.0 Oreo更新后，ROM镜像内程序的Fortify安全机制启用率反而有了小幅下降。

![](../Images/07cca0e83e81866f134acedddfe72272.png)

**图3-13  设备代号fugu和shamu的Fortify启用情况**  

  

除此之外，相同产品线、同时维护的不同Android版本安全性也不同。以设备代号volantis的产品为例，该设备在更新过程中有明显的阶梯性，如图3-14所示。2014年11月到2015年9月的版本为Android 5.1.1，2015年9月到2016年7月的版本为Android 6.0.0，2016年7月到2017年9月的版本则是Android 7.0.0。这3个阶段的ROM镜像内程序的Fortify安全机制启用率百分比分别为32.62%、55.75%、78.22%，而在同一个Android版本内，各项安全机制的启用百分比并没有明显的变化，跨Android版本则产生了显著区别。实际上从图3-14中可以看出，不止是Fortify机制，在Android 6到Android 7的版本升级过程中，各项安全机制启用百分比都有了明显的提高。因此，就安全机制启用情况来看，Android大版本的更新对安全性提升来讲是比较重要的。 

![](../Images/88a5b825148613dafb1aa99696b8f82b.png)

**图3-14  设备代号volantis的不同Android版本的安全机制启用情况**

  

另外，对于Android系统的安全性，除传统的各种安全机制以外，还有两个比较重要的问题：一个是针对App本身的安全配置是否恰当，因为相比系统ELF可执行程序来讲，Android应用更多是以App的形式传播、部署和应用；另一个是AOSP补丁更新是否及时，因为Android系统底层代码大多依赖AOSP，其安全性也比较依赖AOSP补丁，这也是Android系统比较独特的软件供应链安全问题。关于这两个问题，我们都会在3.6节进行详细的分析和说明。
