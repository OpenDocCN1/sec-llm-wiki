我们在上一篇探讨了mcheck , 感觉这个机制不错，虽然不够完善，但还是有点用处。

打算按照之前内存泄露的套路，探讨hook+backtrace的方式。

先看堆块内存损坏的场景：

  1. 这个比内存泄露要复杂。因为不光是申请释放这么简单，还要对memset, memcpy,strcpy, snprintf之类操作内存的函数挂钩。glibc并不像malloc,free提供内置的hook，所以只能使用LD_PRELOAD的方式挂钩。
  2. 像memset, memcpy，strcpy, strncpy之类的函数，有时候在编译选项里直接内联了，就算自身代码不内联，引入的库使用这些函数内联了，所以，这些函数有时候还hook不了。其实valgrind也有这问题
  3. 就算是hook了，使用glibc的malloc出来的内存块，堆块前后边界没什么特征来确保是否被损坏了。有兴趣的请看第一篇所讲的结构体，那些size和prev_size不完全准确。
  4. 当程序崩溃时，根本就不知道当时申请的地址是什么，也更加不知道它前面的地址是什么。
  5. 这个方案在运行时可以会影响程序稳定性。

第三点，再回忆mcheck方案，对它能够检测堆块的头尾部完整性就非常奇怪了。因为它有mprobe函数，能够检测堆块的头部，尾部完整性。

看一下它的代码malloc/mcheck.c，发现有这个结构

struct hdr
{
  size_t size;                  /* Exact size requested by user.  */
  unsigned long int magic;      /* Magic number to check header integrity.  */
  struct hdr *prev;
  struct hdr *next;
  void *block;                  /* Real block allocated, for memalign.  */
  unsigned long int magic2;     /* Extra, keeps us doubleword aligned.  */
};

再看mcheck.c的源码， 就是对要申请的内存块都加上这个头部，每次在申请或释放时就根据这个头部检查一下完整性。

这个机制和Windows的gflags很像，但windows下的机制更巧妙些。

如果是利用mcheck机制继续扩展，叠加到hook+backtrace的方案或uprobes方案会怎样呢？感觉可行。

试一下把思路转换一下：

打开mcheck, 每次申请或释放内存都把所有申请过的内存检查一遍，如果有问题，立马打印出来申请时的调用栈。

那么hook+backtrace就成了每次在申请或释放时，就检查一下所有申请过的内存，用mprobe来检查，如果有问题，立马把申请时的调用栈打印出来。

看起来可行，但仔细考虑一下，就发现大有问题。

  1. mprobe只能是本身进程调用，那么，本进程要检查堆块完整性时，得先分配大量内存来缓存堆块地址和调用栈的map。这个大小和数量是无法预知的。
  2. 如果按照之前定位内存泄露的方式，把堆块地址和调用栈的映射关系发送给一个名为monitor的管理进程，monitor怎么根据这些堆块地址来检查它的完整性。毕竟这些堆块并不属于monitor，而是属于被检测进程的，管理进程要做这种完整性检查必须要做读取被检测进程的mem(位于/proc/<pid>/mem)，根据这个文件读取出相应地址的内容。当然用ptrace的PTRACE_PEEKDATA会更简单一些，但这些对于一个开发者来说，难度很大。同时把mprobe自己实现一把。对于完整性已经被破坏的地址，就把它的申请调用栈打印出来

从上面思考来说，第2种方式是可行的。

但还存在一个问题，由上面的方案，已经找到会导致堆块损坏的申请内存调用栈，但由这些申请调用栈申请的内存，会在代码某些地方的操作导致堆块损坏，那么是代码哪些地方呢？

一般呢，大多程序员都会很傻逼地走读代码，希望在屎山中找出有问题的代码。如果有问题的地方是在第三方库呢，他们就立马歇菜了。毕竟没有源代码，只有汇编啊。

如果读过张银奎老师写的《软件调试》，就会知道应该使用数据断点了。在GDB里叫watchpointhttps://sourceware.org/gdb/current/onlinedocs/gdb/Set-Watchpoints.html#Set-Watchpoints

假设，会导致堆块损坏的申请调用栈为S，那么思路就如下（使用GDB)

  1. 在S栈调用malloc的代码打断点
  2. 当断点命中后，申请到的内存为ptr，根据mcheck.c里的边界，假设ptr的尾部地址为ptr_tail，那么给ptr_tail打上数据断点watch ptr_tail
  3. 继续运行，然后打开音乐播放器，听一下陈百强的歌《等》
  4. 当程序命中了数据断点时，就是损坏堆块的代码行了。这时候使用bt来获取整个栈。

上面使用watch的方法，可以覆盖自身代码和第三方库，不需要进行代码检视。

归纳一下思路，主要是两个阶段：

  • 获取申请调用栈
  1. 每次申请时，把获得的内存地址和调用栈发送到monitor进程。monitor进程一接收到这些信息，立马读取被检测进程的内存，对所有已经申请过的地址进行检测，一旦有被破坏，打印出申请调用栈。使用ptrace自实现mprobe
  2. 每次释放时，把释放的地址发送到monitor进程，monitor进程也同样把所有申请过的地址进行检测，一旦有破坏，打印出申请调用栈；同时把释放地址相应的项删除。
  • 定位破坏时的调用栈
    1. 在第一阶段获得的申请调用栈上对调用malloc处的代码或指令地址打断点
    2. 断点命中，对申请到的内存块尾部打数据断点
    3. 运行程序直至命中数据断点，获得破坏时调用栈

    有朋友如果不懂第一阶段的实现，这也很正常的。毕竟这涉及到调试和代码注入的知识。
