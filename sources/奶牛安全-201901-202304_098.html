进一步劝退警示，现在讲述用eBPF+uprobes机制来定位内存泄露

上一篇Linux内存泄露定位3：hook+backtrace篇已经讲述到hook+backtrace来定位内存泄露的问题，从方案来看，貌似已经是最终方案了。但从实际角度来看，hook+backtracer的方案：

  1. 开发成本较高
  2. 因为hook是侵入式，很容易造成程序不稳定。如果程序在生产环境下不小心打开hook，可能导致事故，需要有人祭天。

那么有没有其它方案呢？

最近几年，在Linux社区eBPF特火，有句话叫” 为人不识eBPF,就懂内核也枉然“。eBPF起源于BPF，起初用于包分析，后来扩展到进程各种行为实时捕获，性能分析等，在4.x内核后，增加到kprobes，uprobes。由于eBPF提供了一个Jit的虚拟机，可以在内核里执行，从4.13内核后，这个功能非常稳定。同时为了能够更好地使用，提供了一个BCC工具集，这个工具集在https://github.com/iovisor/bcc。

这个工具集的tools目录有一个文件，叫memleak.py,有兴趣的同学，看一下它的源码。

它的基本思路：

  1. 给malloc, calloc, realloc, valloc, pvalloc, aligned_alloc挂uprobe和uretprobe的hook，主要作用是获取这些函数刚开始执行时的参数和这些函数执行完之后的返回值，建立返回地址和调用栈的map。原理和__malloc_hook,__realloc_hook差不多
  2. 给free挂uprobe,uretprobe的hook，用来删除释放地址相关的信息。原理也和__free_hook差不多
  3. 打印出泄露的信息。

操作文档可以参考：https://github.com/iovisor/bcc/blob/master/tools/memleak_example.txt

整体思路和上一篇文章都差不多，而且比上一篇来说，并不是侵入式实现，实现会更加优雅。

它的缺点是：

  1. 要求系统的内核在4.13+
  2. 执行的系统也要安装开发工具和内核头文件
  3. 编写这些代码对人员要求极高，真正起作用代码是C，还要懂内核。虽然它号称python, lua,go支持，但这些语言只是支持对接eBPF虚拟机输出，可以解析它的结果。目前有些企业招聘python, lua, go之类语言工程师，竟然要求懂eBPF。真的想卷死人啊。

试一下例子，mem.c:

#include <unistd.h>
#include <stdlib.h>

char* alloc(size_t n )
{
    return malloc(n);
}

char* alloc1(size_t n)
{
    return alloc(n);
}

char* alloc2( size_t n)
{
    return alloc1(n);
}

char* alloc3(size_t n)
{
    return alloc2(n);
}

int main()
{
    sleep(10);
    char* a = 0;

    for ( size_t i = 8; i < 10; i++ )
    {
        a = alloc3(i);
    }

    sleep(10);

    return 0;
}

这前后，要加一个sleep(10)，否则是采集不到内存泄露的结果，甚至提示找不到malloc`之类的符号

运行一下

cc -g -o mem mem.c
sudo python3 /usr/share/bcc/tools/memleak -c ./mem
