> 从malloc/free原理来讲述方案

从上一篇来看，`mtrace`就是一个叉烧功能，没什么用。但已经尝试了`valgrind`和`mtrace`，似乎没什么好的办法了。

在这种情况，应该仔细思考一下问题`什么是内存泄露`。

**内存泄露**无非就是申请的内存没有释放。而**定位内存泄露**就是找出这些没有释放的内存。

那如何做呢？是不是在每次申请内存都记录一下，每次释放时，也记录一下，然后再把这两种记录进行一个对比，把相同的去掉，剩下就是没释放的。

但如果是这样做，必须要在各个调用`malloc/realloc/calloc/free`的代码都要加上这样的代码。这种工作量会非常大，如果是第三方库呢？难道直接改机器码？

上一篇在介绍`mtrace`时, 就有这样的介绍：

> The  mtrace()  function  installs  hook  functions for the memory-allocation functions (malloc(3), realloc(3) memalign(3), free(3)).
> 
> These hook functions record tracing information about memory allocation and deallocation.
> 
> The tracing information can be used to discover memory leaks and attempts to free nonallocated memory in a program.

也就是说`glibc`提供了相应的`hook`，可以安装这些`hook`来跟踪内存申请和释放。

在https://www.gnu.org/software/libc/manual/html\_node/Hooks-for-Malloc.html 列举了这些hook函数：

> **\_\_malloc\_hook** ：每次`malloc`调用就会调用它
> 
> **\_\_realloc\_hook**：每次`realloc`调用就会调用它
> 
> **\_\_free\_hook**：每次`free`调用就会调用它 、

同时也有相应的例子来如何使用这些hook函数。

再回忆一下`mtrace`的叉烧点：它只能拿到调用`malloc/realloc/free`之类函数的调用者。像`getifaddrs`， `strdup`， `inet_ntoa`这些函数也是调用`malloc/free`的，但它们同时也是内存泄露的重灾区。目前很多代码静态扫描工具都是在拼命找这些。如果使用`mtrace`，效果还不如这些静态扫描工具。

所以，要定位**内存泄露**，不光要找出那些泄露的内存地址和申请内存时的调用者函数，还要找到申请内存时的整个调用栈。

之所以使用这些hook函数，不是`mtrace`，是可以定制申请时的行为，获取申请内存时整个调用栈。

那有没有获取整个调用栈的函数呢？

在https://www.gnu.org/software/libc/manual/html\_node/Backtraces.html ，有三个函数有这种功能：

> **backtrace**: 可以获取到整个调用栈的返回地址，就是一串16进制的数字，要解读它，需要进行地址到函数的转换，可能需要`dladdr`之类来进行解码
> 
> **backtrace\_symbols**: 把`backtrace`的结果翻译成可读，就和`GDB`命令`bt`结果差不多。
> 
> **backtrace\_symbols\_fd**: 和`backtrace_symbols`功能差不多，但把结果发到`fd`去。

按照它们的说明，如果在一个大型程序里实现，程序里有大量申请释放的操作，那么`backtrace/backtrace_symbols`产生的结果光是记录就是非常耗费内存，会占用不少进程本身的内存。

所以，可以考虑使用`backtrace/backtrace_symbols_fd`的组合，通过`fd`发送到另外一个程序进行分析。

那么，整体的思路就是这样:

*   程序初始化：
    

1.  先保存旧的`__malloc_hook`, `__realloc_hook`, `__free_hook`，再安装新的
2.  同时去连接**监控进程**监听的`socket`获取`fd`

*   `__malloc_hook`:
    

1.  被调用时，先恢复到旧的`hook`
2.  调用`malloc`申请内存
3.  获取申请的内存`addr`后，调用`backtrace/backtrace_symbols_fd`, 把`addr`和栈发到**监控进程**
4.  重新设置`hook`为自定义的函数

*   `__realloc_hook`:
    

1.  被调用时，先恢复旧的`hook`
2.  把参数`ptr`通过`fd`发到**监控进程**
3.  调用`realloc`获取新内存
4.  获取申请的内存`addr`后，调用`backtrace/backtrace_symbols_fd`, 把`addr`和栈发到**监控进程**
5.  重新设置`hook`为自定义的函数

*   `__free_hook`:
    

1.  被调用时，先恢复旧的`hook`
2.  把参数`ptr`通过`fd`发到**监控进程**
3.  释放内存
4.  重新设置`hook`为自定义的函数

*   监控进程：
    

*   维护一个map, 每个元素就是<内存地址，申请调用栈>的对。
*   当接收到内存申请的数据，就往map新增一个数据
*   当接收到内存释放的数据，就从map删除一个数据
*   当对端进程退出时，就开始统计这个map有多少剩余元素，并把它打印出来。剩余的元素就是内存泄露的数据和申请调用栈。

这个方案，如果实现，会非常准确地定位内存泄露。它的实现相对而言是比较复杂。可以写成一个公共的库和监控服务，如果通过`ld.so.preload`或`LD_PRELOAD`的方式，可以监控任何一台机器所有进程的内存泄露问题。

这个方案还有一点不足，就是`backtrace_symbols_fd`：

1.  有些符号信息它不一定获取得了
2.  它把地址翻译成符号的过程可能非常消耗CPU，也会占额外内存
3.  它只对elf文件有效

**监控进程**获取到对端进程的/proc//maps，可以通过计算代码偏移量的方式，从加载的二进制文件获取调用栈所对应的符号位置。这一块对码农的要求就比较高。
