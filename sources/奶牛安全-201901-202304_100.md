> 更深一层讲述定位内存泄露的手段

从上一篇文章[Linux内存泄露定位1：valgrind篇](http://mp.weixin.qq.com/s?__biz=MzU4NjY0NTExNA==&mid=2247486481&idx=1&sn=e4eafc70e7a4d0860ca7fd5eef6050ff&chksm=fdf96704ca8eee1219afe01d894056f7ad000e1c07510afbed3fb3ca698e5a3102dd07fadc59&scene=21#wechat_redirect)，可以知道`valgrind`是类似`JVM`的方式来进行内存泄露。虽然它很好用，但用过的朋友都知道，它非常慢。这种沙箱类的技术，需要对很多函数进行打桩，是非常消耗性能。而且，由于它并不是为了针对内存泄露实现的，代码一复杂，往往跑不出结果来。

再者，`valgrind`是通过代码打桩技术，如果程序本身对`malloc`加钩，实现内存池，它有可能对程序本身的功能有影响。

那么，`glibc`本身有没有内置的对内存泄露的功能呢？

根据`man 3 mtrace`的介绍

> The  mtrace()  function installs hook functions for the memory-allocation functions (malloc(3), realloc(3) memalign(3), free(3)).  These hook functions record tracing information about memory allocation and deallocation.  The tracing information can be used to discover **memory  leaks**  and  attempts to free nonallocated memory in a program.

也可以从https://www.gnu.org/software/libc/manual/html\_node/Tracing-malloc.html的介绍，它好像是可以定位内存泄露的。

这个是什么结果，可以说是一点用处都没有。而且，这个`memtrace`程序还是用`-g`选项编译出来，有调试符号，却识别不了。

是的，虽然用`objdump -d memtrace`出来这样的结果

```










0000000000001149 <func>:
```

按照`4K`大小内存页的方式，也可以知道是`func`这个函数调用`malloc`申请的内存没有释放，但这种定位是没有意义的。就像`strdup`也调用了`malloc`，但真正导致内存泄露往往是调用`strdup`函数的调用者或者整个栈有逻辑错误。

所以，结论是：

**`mtrace`是一个废物**。
