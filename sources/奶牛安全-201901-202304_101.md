上面代码命名为`mem.c`, 以`debug`模式编译后

```

cc -g -o mem mem.c
```

运行一下`valgrind`

```

valgrind --leak-check=full ./mem
```

出来结果如下：

```























==4060== Memcheck, a memory error detector
```

从

```



==4060== 17 bytes in 2 blocks are definitely lost in loss record 1 of 1
```

看，它的结果很准确，是在`mem.c`的第10行出现问题。

再重新编译一下`mem.c`，不用`debug`模式（去掉`-g`选项）

```

cc  -o mem mem.c
```

用同样命令运行，得到如下结果

```























==78104== Memcheck, a memory error detector
```

这下可是看不出是哪一行代码出现问题，只能从`by 0x10916E: main (in /home/buckxu/code/test/mem)`猜了。那看一下在`main`函数的汇编吧， `objdump -d mem`的结果

```





















0000000000001149 <main>:
```

按照4K内存页对齐，`0x10916E`对应的地址也是`16E`结尾(**不懂的同学请《linker and loader》或《程序员的自我修养**)，从这两行来看，

```


    116a:       e8 c1 fe ff ff          call   1030 <malloc@plt>
```

再考虑代码打桩，应该就是`116a`( 并不是`116e`，可是打桩里大小端)。

从这里看，`valgrind`在定位内存泄露时，能够把泄露的申请栈打印出来，可以很好地定位代码，虽然在没调试符号情况下非常复杂而已。

再看一下它的原理,

```




buckxu@kali:~/code/test$ ps aux|grep mem
```

可见，并没有`mem`这个程序在跑，而只有`valgrind.bin`这个程序在跑

看一下`valgrind`这程序的加载结果

```




















































buckxu@kali:~/code/test$ cat /proc/79024/maps
```

可见，它加载了`mem`这个程序，还在`libc`前面的地址加载了`/usr/libexec/valgrind/vgpreload_core-amd64-linux.so`和`/usr/libexec/valgrind/vgpreload_memcheck-amd64-linux.so`

同时，也从这一行

```

00109000-0010a000 r-xp 00001000 08:09 23724328                           /home/buckxu/code/test/mem
```

看到`mem`的代码基地址是`0x109000`，那么用`0x10916E`减去`0x109000`，刚好是`0x16E`，正好是之前`objdump -d mem`里`main`函数调用`malloc`那一行。

再看`valgrind`打开的文件

```












buckxu@kali:~/code/test$ ls -l /proc/79024/fd
```

可见，它是把`mem`当作文件来做，和`JAVA`虚拟机执行`jar`包一样，就是`valgrind`作为一个虚拟机，读取二进制文件的内容，进行指令解析并执行。
