`--privileged`标志引入严重安全隐患，且`POC`依赖于使用该标志启动的`Docker`容器。当使用这个标志，容器可以完全访问所有设备，也不受`seccomp`, `AppArmor`和`Linux`功能的限制。

不要使用`--privileged`运行容器。`Docker`包括独立控制容器权限的粒度设置。在各种案例中，这些至关重要的安全设置经常被遗忘。明白这些选项如何工作来加固容器是非常必要的。

在接下来的章节，将详细介绍“容器逃逸”的工作原理，它依赖的非安全设置和开发者应该做什么。

## 该技术的要求

事实上，`--privileged`提供的权限远远超过通过此方法退出停靠容器所需的权限。在现实中，“唯一”的要求是：

1.  在容器以`root`身份运行
2.  容器应该使用`SYS_ADMIN`功能运行
3.  容器必须缺少`AppArmor`配置文件，或允许`mount`系统调用
4.  第一版`cgroup`的虚拟文件系统在容器以可读写模式加载

`SYS_ADMIN`功能允许容器可以使用`mount`系统调用。`Docker`默认以一组受限的功能启动容器，且基于安全风险考虑不会启用`SYS_ADMIN`能力。

并且，`Docker`默认使用`docker-default`的`AppArmor`策略启动容器，即使容器使用`SYS_ADMIN`运行，这个策略也会禁止使用`mount`系统调用。

一个容器如果使用下列标记启动`--security-opt apparmor=unconfined --cap-add=SYS_ADMIN`，它就很容易受到这种技术的攻击。

## 使用cgroups传送PoC

`Linux cgroups`是`Docker`用于隔离容器的原理之一。`PoC`滥用第一版`croups`中的`notify_on_release`功能，以完全授权的超级用户身份运行利用漏洞攻击。

当一个`cgroup`最后一个任务结束（退出或附加到另一个`cgroup`)，在`release_agent`文件提供的一个命令会执行。它的目的是为了清除那些弃用的`cgroup`。一旦执行，这个命令是以完全授权超级用户身份在宿主机上运行。

> 1.4 `notify_on_release`是做什么的？
> 
> 如果一个`cgroup`启用了`notify_on_release`标志，当这个`cgroup`最后一个任务结束（退出或附加到其它`cgroup`)，且它最后一个子`cgroup`被删除，然后内核会运行该层次根目录下的`release_agent`文件内容指定的命令，提供弃用`cgroup`的目录（相对于`cgroup`文件系统的挂载点）。这使得弃用`cgroup`的自动清理。系统启动时，根`cgroup`的`notify_on_release`的默认值是禁用(0)。其它`cgroup`该标志在创建时的默认值是它们父`cgroup`的`notify_on_release`设置。一个`cgroup`层次`release_agent`路径默认值为空。
> 
> \--来自https://www.kernel.org/doc/Documentation/cgroup-v1/cgroups.txt

## 分散PoC

既然已经知道使用这个技术的要求，也已经完善了`PoC`，现在一行一行地详细介绍它的工作原理。

要触发这个攻击，需要一个`cgroup`，在它上面可以创建一个`release_agent`文件和通过杀死里面所有进程来触发`release_agent`操作。最简单方法是挂载一个`cgroup`控制器和创建一个子`cgroup`。

要达到这个目的，创建一个`/tmp/cgrp`目录，挂载`RDMA cgroup`控制器和创建一个子`cgroup`（这里命令它为`x`）。

如果在挂载时遇到`mount: /tmp/cgrp: special device cgroup does not exist`，这是因为设置里没有`RDMA cgroup`控制器。把`rdma`改为`memory`。这里使用`RDMA`是因为原初的`PoC`是使用它。

> `cgroup`控制器是全局资源，可以使用不同许可挂载多次，每个挂载的变动都会传递给另外的。

可以看到`x`子`cgroup`创建，查看一下它的目录

```
root@b11cf9eab4fd:/
```

接着，通过把1写到`x cgroup`的`notify_on_release`文件来启用它的释放通知。同时将`RDMA cgroup`释放代理设置为执行`/cmd`脚本(稍后我们将在容器中创建该脚本)，方法是将主机上的`/cmd`脚本路径写入`release_agent`文件。为此，从`/etc/mtab`获取容器在主机上的路径。

这些在容器上增加和修改的文件在宿主机上展示，也可以从两边来修改它们：从容器里的目录和在宿主机的目录。

操作如下

```

请注意将在宿主机上创建的`/cmd`脚本的路径：

```

现在，创建`/cmd`脚本，以便它将执行`ps aux`命令，并通过指定输出文件在宿主机上的完整路径把结果保存到容器上的`/output`中。最后，打印`/cmd`脚本以查看其内容：

## 安全地使用容器

`Docker`默认限制容器。放松这些限制会产生安全问题，即使没有达到`--privileged`的权限。认识到每种附加权限的影响和总体限制权限到最小需求是非常重要的。

下面是容器安全的建议：

*   不要使用`--privileged`标志或者在容器内部挂载`Docker socket`。`Docker socket`允许启动容器，所以它很容易完全控制宿主机，比如，使用`--privileged`标志运行另外一个容器。
*   不要在容器里以`root`身份运行。使用另外一个用户或另外一个用户命名空间。没有重新映射用户命名空间，`root`在容器和在宿主机是一样的，只是稍微由`Linux`命名空间，功能和`cgroups`限制。
*   丢弃所有`Linux`功能(`--cap-drop=all`)，只启用那些必需的(`--cap-add=`)。许多工作并不需要任何`Linux`功能，启用它们只会增加潜在风险
*   使用`no-new-privilegeds`安全选项防止进程获取更多权限，比如通过`suid`二进制文件
*   限制容器的资源。资源限制可以防止宿主机遭受`DoS`攻击。
*   调整`seccomp`, `AppArmor`（或`SELinux`)配置来限制容器可用的操作和系统调用到最小化程度
*   使用`Docker`官方镜像或者基于它们创建自己的镜像，不要继承或使用有后门的镜像。
*   经常打补丁来重建镜像
