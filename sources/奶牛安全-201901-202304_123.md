## 概述

本文是分析微软Windows地址本堆缓冲出溢出漏洞。微软已经在2021.2.9号二月补丁日发布了这个漏洞的建议。本文会深入这些细节：微软windows地址本是什么，漏洞本身和构建使它崩溃的POC的过程。

## Windows地址本

Windows地址本是微软Windows系统的一部分，也是一个服务，给用户提供由微软或第三方应用访问或修改的中心化联系列表。Windows地址本维护一个本地数据库和接口来查找和修改联系人的信息，也可以通过LDAP查询网络目录服务。Windows地址本是在1996年引入，随后被Vista的联系人和Win10的人们替代。

Windows地址本提供了一个API，使得其它应用可以直接使用它的数据库，和用户界面服务让服务可以直接访问和修改联系人信息。当微软替换了提供地址本功能的应用程序，新的替代者使用旧的功能和保证向后兼容。Windows地址本功能位于Windows 10应用程序(包括Outlook和Windows Mail)使用的几个Windows库中。通过这种方式，现代应用程序可以利用Windows地址本，甚至可以从旧版本的Windows导入地址本。

## CVE-2021-24083

处理联系人的嵌套属性时，`wab32.dll`内的`SecurityCheckPropArrayBuffer()`函数中存在堆缓冲区溢出漏洞。基于网络的攻击媒介引诱用户打开精心编制的.wab文件，该文件包含WAB记录中的恶意复合属性。

## 漏洞

接下来的漏洞分析是基于Windows 10 x64运行的地址本联系人DLL（wab32.dll）10.0.1901.388版本。

Windows通讯簿联系人DLL(即wab32.dll)提供对通讯簿API的访问，多个应用程序使用它与Windows通讯簿交互。联系人DLL处理与联系人和身份管理相关的操作。其中，联系人DLL能够导入从早期版本的Windows地址簿导出的地址簿(即WAB文件)。

早期版本的Windows通讯簿以.wab文件的形式维护身份和联系人数据库。虽然当前版本的Windows在默认情况下不再使用.wab文件，但它们允许从早期安装的Windows通讯簿导入WAB文件。

有很多种导入WAB文件到Windows地址本的方法，但据观察，应用程序依赖于Windows联系人导入工具(即C：\\Program Files\\Windows Mail\\wabmi.exe)来导入地址本。

## WAB文件格式

WAB文件格式是一个未公开私有，包含个人身份的文件格式。个人身份同时也会包含联系人，每个联系人会包含一个或多个属性。

虽然WAB文件格式没有公开，但它早已经被第三方组织部分逆向了。下面结构是由公开的第三方软件和wab32.dll汇编里混合提取出来的。因此，结构定义，字段名和字段类型有可能存在不准确。

WAB文件有下列结构

```











Offset      Length (bytes)    Field                   Description
```

没有特别指出，所有多字节字段都是以小字节端表示。所有字符串都是unicode，用UTF16-LE格式编码。

`Magic Number`字段包含下面16个字节：``9c cb cb 8d 13 75 d2 11 91 58 00 c0 4f 79 56 a4`。有些来源列举字节序列为`81 32 84 C1 85 05 D0 11 B2 90 00 AA 00 3C F6 76`为WAB文件有效的`magic number`，实验发现，替换为这些字节序列会阻止Windows地址本处理该文件。

每个`Table descriptor`字段有下列结构

```







Offset    Length    Field    Description
```

下面是一些已知`table descriptor`的例子

*   文本记录（类型：0x84d0)：一个包含unicode字符串的记录
*   索引记录（类型：0xFA0): 一个可以包含多个WAB记录描述符的记录。

每个文本记录有如下结构

```



Offset   Length (bytes)    Field          Description
```

每个索引记录有如下结构

```


Offset      Length (bytes)    Field        Description
```

索引记录每个条目有一个偏移量指向一个WAB记录

## WAB记录

一个WAB记录用来描述一个联系人。它包含存储在属性中的电子邮件地址和电话号码等字段，这些字段可以是字符串、整数、GUID和时间戳等各种类型。每条记录有如下结构

```




Offset      Length   Field              Description
```

下面字段是相关的：

*   `RecordProperties`是一串记录属性结构
*   `PropertyCount`表明有多少个属性在`RecordProperties`

记录属性可以是简单，也可以是复合的。

## 简单属性

简单属性有如下结构

```


Offset      Length (bytes)    Field       Description
```

简单属性的`Tags`少于0x1000，包括下面这些

```



Tag Name        Tag Value    Length      Description
```

> 注意事项：
> 
> *   上面提及的列举并不全，更多`Tag`定义请看https://docs.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxcdata/0c77892e-288e-435a-9c49-be1c20c7afdb
> *   `PtypBinary`的值有`Count`字段前缀，计算16比特的字
> *   除了上面，下列属性也存在，它们在WAB用处未知
> 
> *   `PtypEmbeddedTable`(0x0000000D): 属性值是一个COM对象
> *   `PtypNull`(0x00000001): 占位符
> *   `PtypUnspecified`(0x00000000): 该属性类型可匹配任何类型

## 复合属性

复合属性有如下结构

```



Offset  Length     Field             Description
```

复合属性的`Tag` 是大于等于0x1000的，包含如下

```









Tag Name                Tag Value
```

每个复合属性的`Value`字段包含`NestedProCount`个相应类型的简单属性。

在定长属性情况下（`PtypMultipleInteger16`, `PtypMultipleInteger32`, `PtypMultipleGuid`, and `PtypMultipleTime`），复合属性的`Value`字段包含`NestedPropCount`个相应简单属性的`Value`字段。

比如，在一个`NestedPropCount`为4的`PtypMultipleInteger32`的结构

*   `Size`一直为16
*   `Value`包含4个32位数字

在变长属性情况下（`PtypMultipleString8`, `PtypMultipleBinary`, and `PtypMultipleString`)，复合属性的`Value`字段包含着`NestedPropCount`个相应简单属性的`Value`字段和`Size`字段。

比如，在一个`NestedPropCount`为2的`PtypMultipleString`结构，有两个unicode编码的字符串“foo”和“bar”：

*   `Size`是`14 00 00 00`
*   `Value`字段包含着下列两个字节串的连结

*   `foo`编码成4字节长度：`06 00 00 00 66 00 6f 00 6f 00`
*   `bar`编码成4字节长度：`06 00 00 00 62 00 61 00 72 00`

## 技术细节

一个畸形的地址本以WAB文件方式被导入，这个漏洞就会出现。当一个用户尝试导入到一个WAB文件到Windows地址本，`WABObjectInternal::Import()`会被调用，它会接着调用`ImportWABFile()`。对于 WAB文件中每个联系人，`ImportWABFile()`进行了下列嵌套调用：`ImportContact()`, `CWABStorage::ReadRecord()`, `ReadRecordWithoutLocking()`, 最后 到`HrGetPropArrayFromFileRecord()`。最后一个函数接收一个文件指针作为参数，读取联系人头部信息，抽取出`PropertyCount`和`DataLen`。`HrGetPropArrayFromFileRecord（）`接着调用`SecurityCheckPropArrayBuffer()`对导入文件进行安全检查和`HrGetPropArrayFromBuffer()`读取联系人属性到一个属性数组。

`HrGetPropArrayFromBuffer()`严重依赖`SecurityCheckPropArrayBuffer()`安全检查的准确性。然而`SecurityCheckPropArrayBuffer()`无法对某些属性类型进行安全检查。特别地，`SecurityCheckPropArrayBuffer()`会跳过对属性`Tag`为未知的嵌套属性的内容的检查，而`HrGetPropArrayFromBuffer()`不进行任何安全检查继续处理所有嵌套属性。因此，有可能蒙骗函数`HrGetPropArrayFromBuffer()`解析未检查的联系人属性。解析完这样属性，`HrGetPropArrayFromBuffer()`会溢出一个堆缓冲区。

## POC

为了从一个良性WAB文件生成一个恶意WAB文件， 从Windows地址本的实例中导出一个有效的WAB文件。Windows XP的Outlook Express有导出联系人到WAB文件的功能。

良性的WAB文件变成恶意WAB，可能通过改变它里面的联系人，使它拥有这样特性：

*   一个嵌套属性包含如下

*   大于或等于0x1002
*   大于0x1007
*   不等于0x1014,0x101e,0x101f和0x1102
*   减去0x1040，再和0xFFFFFFF7进行字节与操作的结果不为0
*   不等于0x1002,0x1003,0x1004,0x1005,0x1006,0x1007,0x1014,0x1040,0x1048
*   一个未知或不可处理类型的tag，如0x1058，有如下条件：
*   `NestedPropCount`大于`Size`
*   复合属性的`Value`应该为空

*   一个简单属性包含如下：

*   属性tag不等于0x1e, 0x1f, 0x40,0x48。比如0x0
*   `Size`应该 大于0x18*`NestedPropCount`来溢出`_SPropValue`数组缓冲区
*   一个不指定个数的尾字节串，用来溢出`_SPropValue`数组

最后，当攻击者诱使毫无戒心的用户导入精心构造的WAB文件时，就会触发漏洞，从而实现代码执行。攻击尝试失败很可能会导致Windows地址本导入工具崩溃

由于ASLR的存在和缺少脚本引擎，我们无法从该漏洞获取Windows 10中的任意代码执行。
