## 检测

如果一个管理员怀疑有`webshell`蛰伏在他们系统或只是进行巡检，需要检查下列内容。

首先，服务的访问和错误日志应该筛选`webshell`通用关键词。这包括文件名和参数名。下面例子允许你在`Apache HTTP`服务的访问日志的URL搜索字符串`file`

```

root@secureserver:/var/www/html# cat /var/log/apache2/access.log | awk -F\" ' { print $1,$2 } ' | grep "file"
```

必须在文件系统(通常是Web服务器根目录)中搜索文件或文件名中的通用字符串。

```

root@secureserver:/var/www/html/demo# grep -RPn "(passthru|exec|eval|shell_exec|assert|str_rot13|system|phpinfo|base64_decode|chmod|mkdir|fopen|fclose|readfile) *\("
```

搜索长字符串，这可能是编码过的代码。有些后门有成千上万行代码。

```

oot@secureserver:/var/www/html/demo# awk 'length($0)>100' *.php
```

搜索那些近期来修改过的文件。比如下面例子，搜索前一天修改的`*.php`文件，不过，推荐搜索所有文件变动，毕竟`webshell`可以嵌入到一个图像文件或其它文件。

```

root@secureserver:/var/www/html/# find -name '*.php' -mtime -1 -ls
```

监控网络里不寻常的流量和连接

```

root@secureserver:/var/www/html/demo# netstat -nputw
```

分析`.htaccess`文件的修改。下面是一个攻击者可能对`.htaccess`文件做的修改

```



# The AddType directive maps the given filename extensions onto the specified content type
```

## 防护

以下是针对`webshell`应采取的防护措施的非详尽列表。

1.  如果不使用，禁用潜在危险的`PHP`函数，如`exec`,`shell_exec`,`passthru`,`system`,`show_source`,`proc_open`, `pcntl_exec`, `eval`和`assert`
2.  如果确实有必要使用这些函数，那么确保未授权用户无法访问这些脚本。另外，使用`escapeshellarg`和`escapeshellcmd`来确保用户输入不会注入`shell`命令，导致命令注入漏洞
3.  如果`web`应用使用上传表单，确保它们是安全并且只允许白名单的文件类型上传
4.  决不相信用户输入
5.  不要盲目使用那些在论坛或网站上找到的代码
6.  在`WordPress`情况下，避免安装那些不必要的第三方插件。如果需要使用一个插件，确保它是名声好且经常更新
7.  禁止`PHP`在敏感目录下执行，如图片或上传目录。
8.  锁定`web`服务用户的权限

## 结语

正如我们已经看到的，编写和使用`webshell`并不困难。不幸的是，许多`Web`服务器的配置，使得即使一个简单的脚本也足以造成重大破坏。这就是为什么有数以千计的公开可用的`webshell`的主要原因。由于存在如此之多的变体，入侵检测和入侵防御系统(IDS/IPS)很难检测到它们，特别是当它们使用特征来检测此类`webshell`时。有些`webshell`非常复杂，即使用行为分析也几乎不可能检测到它们。这意味着防止攻击的最好方法是从一开始就阻止它们被上传。
