# 技术分享|代码签名的安全注意事项

代码签名（或软件签名）为可信计算环境提供技术支撑，能有效保障软件在开发、构建、分发、维护过程中可信任、不被篡改。基于代码签名实现白名单机制，能有效减少白名单的生成和维护成本。同时签名系统自身的安全性也至关重要，如果自身不安全，会导致整个信任链不安全，带来严重的安全问题。根据我国等保4级的技术要求，在安全计算环境相关章节，提到“应构建从操作系统到上层应用程序的信任链，以实现系统运行过程中可执行程序的完整性检验，防范恶意代码等攻击，并在检测到其完整性受到破坏时采取措施恢复，例如采用可信计算等技术”，代码签名技术就是一种实现该信任链的技术方案。

NIST（美国国家标准和技术研究院）在2018年1月26日发布了《Security Considerations for Code Signing》的技术白皮书，介绍了代码签名的技术基础、基本架构和安全风险，为代码签名系统提供安全指导，原文可以在NIST的官方网站查找下载：https://csrc.nist.gov/publications。

本文对该技术白皮书进行了翻译，介绍给国内的安全工作者。

\-------------------------------------------------------------

**1前言**

最近的安全相关事件表明，在软件的开发、构建、分发和维护阶段，需要一个安全的软件供应链来保护软件产品（或者称为代码）。特别值得关注的是安装和更新软件，对于平台的安全性起着关键作用，必须以安全和自动的方式分发和更新各种软件产品，包括固件，操作系统、移动应用程序和应用程序容器映像，以防止伪造和篡改。保护软件的一种有效且常见的方法是对软件应用数字签名。数字签名既提供数据完整性验证，以证明代码未被修改，还提供源代码验证，以标识签名时谁控制了代码。当使用者验证签名时，他就可以确信软件来源正确，并且传输过程中未被篡改。

本白皮书针对正在实施代码签名系统或审查现有系统安全性的软件开发人员和产品供应商，旨在提高系统安全性，提高客户对代码真实性和完整性的信心。系统集成商和管理员可能会担心在其系统上安装并运行的应用程序的可信赖性，他们可以从代码签名解决方案中获得想要的信息，以保护他们的软件供应链。

本白皮书介绍了当今广泛部署的典型代码签名解决方案的功能和架构，描述了几种典型的代码签名用例，并确定了在将代码签名解决方案应用于这些用例时可能出现的一些安全问题。最后，本文提供了规避这些安全问题的方案建议，并提供了更多信息资源作为参考。正确应用这些建议将有助于确保软件供应链的安全。

NIST计划开发进一步的指导以帮助组织评估、部署或管理代码签名系统。本文档中描述的一些粗粒度的建议下一步将会进行细化，成为代码签名的实践指导。

**2基础知识**

本节简单描述一下代码签名过程是如何工作的，整个工作过程中有三个基本角色：开发者、签名者和验证者。

开发者负责编写、构建和提交将要签名的代码。开发者维护一个安全的开发环境，包括源代码库，在完成开发和测试流程后将代码提交给签名者。

签名者负责管理用于签署软件的密钥。这个角色可以和开发人员属于同一个组织，也可以是独立公正的第三方。该过程的安全性依赖于私钥的保护，所以签名者必须在保证安全的设备上生成代码签名的私钥/公钥对。在许多情况下，签名者通过证书签名请求将公钥提供给证书颁发机构（CA）。CA将确认签名者的身份，并提供与签名者绑定的签名证书。任何人都可以使用与此证书关联的公钥来验证使用此密钥对签署的代码的真实性和完整性。如果没有使用CA，则必须使用可信的带外机制来分发公钥。

签名人通过技术和程序控制确保只有授权代码被签署。当开发人员提交代码进行签名时，签名人将验证他们的身份和权限以请求签名。签名者也可能采取额外的步骤来验证代码是否可信。最终，可能需要代码签名系统的两个或多个可信代理来批准请求，并生成数字签名。在某些情况下，还可以将签名代码提供给时间戳授权机构，以标记代码签名的时间。

验证者负责验证代码签名。验证者可能是与签名代码相同的开发者提供的软件组件（例如：用于签名固件更新），或者也可能是由平台提供的共享组件（例如：操作系统）。

**3.1 代码签名系统（CSS）**  

CSS接收准备签名的代码，对提交者进行身份验证和授权，并生成签名。为了生成这些签名，CSS有一个或多个私人签名密钥，必须严格保护这些私钥，防止被窃取或未经授权的使用。

**3.2认证机构（CA）**

通常CSS利用CA来对签名者的身份进行身份验证。CA根据证书政策颁发证书给签署人，证书政策规定了CA在签发证书时遵循的安全控制和实践，并对证书主题施加要求。NIST机构间报告（Interagency Report）7924 定义了一个可以参考的证书策略，它制定了颁发代码签名证书的CA的大部分要求。另外还有诸如CA/Browser Forum和CA Security Council等行业组织已经发布了用于签发代码签名证书的要求文件。

**3.3时间戳认证（TSA）**

一些代码签名体系结构使用TSA来标记签名时间。使用TSA时，签名会发送给TSA，TSA会将自己的签名和签名时间应用于软件包。TSA独立于CSS运行，并保持时钟与权威时间源同步。如果签名密钥在代码签名时有效，即使密钥在验证时已过期或密钥在签名之后某个时间受到损害，这也不会影响原来签名的有效性。

**3.4 验证者**

验证者负责验证签名者以及签名者使用的任何证书和时间戳，还管理用于验证证书的信任锚。签名者或独立方可能负责开发验证组件。

**3.5信任锚（Trust Anchors）**

管理验证组件的一个关键任务是管理用于验证签名的信任锚，它用于验证代码签名证书。信任锚是数据对象，通常是公钥，它们被安装并安全地存储在验证平台上。信任锚的可信度基于其安装、存储和管理的方法。信任锚一般不用于直接验证代码，但通常是签署代码签名CA证书的根CA的公钥。如果丢失个人代码签名CA或代码签名者拥有的私钥，通过信任锚可以提供恢复的手段。信任锚必须以足够安全的方式进行存储，如果相应的私钥遭到破坏，将导致整个平台容易受到攻击而且无法修复。

**4 典型用例**

CSS系统的实现及策略制定取决于实际的用例，本节介绍四个典型用例：固件签名、驱动程序签名、可信应用程序商店和应用程序软件签名。请注意，这些例子仅用于示例说明; 它们既不反映每个用例的所有实例，也不包含所有代码签名用例。

**4.1固件签名**

固件的安全分发是软件供应链的一个例子，其中代码签名的所有工作通常由单一组织负责：软件开发、授权签署代码、CSS的管理、以及最后的验证。典型的工作流程包括一组开发人员，在将代码传递给构建系统之前，他们在版本控制系统中跟踪提交的代码。在开发过程中，CSS可能会使用开发或测试密钥签署非生产版本，这些签名将仅用于测试，不会用于验证实际发布的代码。

当代码准备打包发布时，开发人员将其提交给签名部门。授权审批人（可能有多个审批人）根据组织政策检查代码，并提交代码批准签名。CSS检查这一套数据（代码，批准和元数据）以确定是否满足所有要求，然后对该软件包使用生产密钥进行签名。密钥可以针对每个项目单独设置，所有生产密钥都需要集中安全保存，比如位于硬件安全模块（HSM）中，每个相应的公钥安全地安装在固件所针对的平台上的验证器组件中。

**4.2驱动签名**

设备驱动程序是运行在计算机系统内核附近的特权进程，用于控制硬件组件并与之通信。典型的个人电脑具有多个具有相关驱动程序的硬件设备。虽然驱动程序通常由相关硬件供应商开发，但代码签名的所有其他工作仍然由中央认证机构进行控制。虽然细节不尽相同，但设备驱动程序通常由预配置的中央可信授权机构签署。对于操作系统（OS）的驱动程序，批准和签名过程通常由OS供应商执行。固件级驱动程序（例如统一可扩展固件接口（UEFI）驱动程序）通常依赖于中央第三方签名服务，由原始设备制造商（OEM）管理信任锚。在这个例子中，驱动程序开发人员不会获得他们自己的代码签名密钥和证书。相反，他们将代码提交给中央可信机构（例如操作系统供应商或OEM厂商），后者验证开发人员的身份并为提交的驱动程序提供签名。如果后续发现驱动程序不可信或恶意，则可信机构有机制撤销已经颁发给该开发机构或人员的签名。

**4.3可信应用商店**

现在计算设备通常使用应用程序商店向用户分发签名的应用程序，包括由第三方开发的软件。不同的平台以不同的方式执行代码签名，但在大多数情况下，应用程序商店由操作系统或平台供应商维护运营，只分发经过审查的应用程序（请参见NIST的SP 800 -163 ）。虽然单个开发人员可能拥有自己的签名密钥，无论是为了开发目的还是为了向商店进行身份验证，用于签署应用程序的私钥受商店的控制，该商店在CSS上提供服务。开发人员将他们的应用程序提交给商店，并在应用程序进行审核之前验证其身份。如果一切顺利，商店就会对应用程序进行签名并发布，以供下载。设备可以配置为仅安装由应用商店控制的密钥签名的应用。

**4.4应用软件签名**

操作系统通常支持独立供应商开发和分发应用程序。根据系统的配置，有效的代码签名可能是安装的先决条件，或者操作系统可能只允许已签名的应用程序对受保护的系统资源进行访问。要让这些签名被操作系统接受，应用程序开发人员必须从操作系统供应商信任的CA获取代码签名证书。操作系统供应商可能为此运营一个CA，或者与商业CA合作提供此服务。开发人员生成一个代码签名密钥对，并从CA请求一个公钥密钥。CA在颁发证书之前验证开发人员的身份，开发人员使用其私钥签署为该OS开发的任何应用程序。这些签名确定了开发人员的身份，并允许操作系统验证应用程序未被篡改。 开发人员也可以从TSA获取时间戳，这样即使在证书过期后操作系统也能够验证签名。操作系统可以确定应用程序的出处，系统管理员或用户可能会询问是否信任开发人员的代码，因为操作系统供应商不会审查应用程序。当然，如果某个开发人员曾经提交过恶意代码，受信任的CA将会拒绝向他颁发证书，以保证后续签名代码的安全可信。

**5 CSS面临的威胁**

本节列举了CSS的一些潜在威胁。

私人签名密钥的盗用：没有被正确保护的私人签名密钥有被盗风险，被盗后就可能被攻击者用于签署任意代码。一些代码签名系统对已签名的软件没有有效的撤销机制，这也会加剧这种威胁的严重性。

颁发未经授权的代码签名证书：用于颁发代码签名证书的CA私钥缺乏保护或用于颁发这些证书的审核程序过弱，可能允许攻击者获取一个或多个未经授权的代码签名证书。

错误放置的证书或密钥：如果一些证书或密钥从来不打算用于代码签名，就不应该放置在验证程序的信任库里面。在某些情况下，验证者可能允许用户将信任扩展到不值得信任的证书或签名者，从而产生错误的验证结果。

签署未经授权或恶意代码：代码签名程序可能允许恶意或未经授权的代码被无意识地签名，可能的原因包括：合法错误、糟糕的管理、内部人员攻击、成功侵入软件/固件开发或代码签名系统。同样，对开发系统或代码签名基础设施本身的入侵可能导致恶意代码被签名。

使用不安全的密码学：如果使用比较弱或不安全的密码算法或密钥生成方法，使用现在的密码分析技术或强力攻击方式可能恢复私钥或获取欺诈性证书。在未来随着新的密码分析技术、新的漏洞，或量子计算机的发展，可能使先前部署的系统不再安全。

**6安全建议**

本节介绍如何通过在开发、构建、分发和维护阶段保护代码来提高软件供应链的安全性。

识别和认证（I＆A）可信用户：实施I＆A计划，充分识别能够签署代码或提交代码进行签名的用户。

授权可信用户：确定谁有权提交代码进行签名，维护一个列表并定期审查，指定谁可以提交代码以及他们可以提交哪些代码（例如：他们可以提交哪些项目）。考虑要求两个人批准用于签名或使用多因素认证的代码。

CSS进行角色分工：分离运行CSS的关键角色并将其分配给不同的人，特别是将CSS的管理角色与授权的代码提交者的角色分开。

建立检视、审查和批准代码的政策和程序：签名代码说明组织接受该固件或软件，所以签署代码之前，组织应检视和审查代码以确保其值得信赖。组织现有的安全软件开发和构建流程应该支持这些程序。

使用强大的加密技术：使用设计良好的、经过测试和维护的加密库，并选择NIST批准的哈希和签名算法。

保护签名密钥：必须保持签名密钥的保密性，它们应该被隔离在具有最小应用程序和连接的机器上。如果可能的话，密钥应该以最少的功能存储在HSM中（例如签名）。

使用单独的CSS进行开发：如果代码需要定期签名进行开发验证，创建一个物理或逻辑上不同的CSS，这些CSS将在开发过程中使用并且不用于签署生产代码。在这种分离的场景，开发密钥和生产密钥应使用不同的根密钥。

隔离和保护CSS：CSS是一个基础安全系统，应作为关键资产加以保护。尽最大可能将CSS与生产网络（以及任何外部网络）隔离开来。

利用审计系统定期审查日志：审核签名密钥的使用情况，定期查看日志以查找密钥的异常使用情况。制定保护机制，不允许CSS覆盖历史日志。

利用信誉良好的CA：如果使用CA来建立对签名者和公钥的绑定的信任，则可以使用安全CA或从信誉良好的CA购买证书。如果没有使用CA，则通过单独拥有私人签名密钥来建立信任。在这种情况下一定要重点保护好签名密钥，因为以后将很难进行密钥的更新。

利用有信誉的TSA：如果使用TSA来提供代码签名时间，则需要确保运营一个安全的TSA，或者使用有信誉的TSA的服务。

管理信任锚：在许多情况下，可以更新信任锚。但是应该注意只有在适当授权的情况下，信任锚才会发生变化。信任锚不能随意更改，必须按照定义明确的过程进行更新。

管理代码版本：如果需要阻止回退，则应将代码版本作为包中元数据的一部分进行签名，并在验证过程中由验证者进行验证。只有当提供的代码版本比系统上已经存在的代码版本更新时，才会继续进行升级更新。

验证证书：如果使用CA，验证者必须能够确定包含公共签名验证密钥的证书是有效的。它应检查证书上的签名是否有效并来自授权的CA， 还应检查包括有效期和密钥使用字段的关键字段。

验证时间戳：如果签名代码包含时间戳，验证者必须能够确定时间戳由其信任的TSA签署，并且要验证代码签名时间戳的有效性。

验证签名：验证者必须能够验证签名并确定与签名关联的公钥可以链接回授权签名者。请注意在某些情况下没有CA，必须根据公钥确定授权。

检查证书撤销：有时证书需要在有效期结束前撤销。 验证者应该能够检查证书吊销或具有用于更新信任锚的安全机制。

**7 总结**

本白皮书介绍了用于保护软件供应链的代码签名解决方案的安全注意事项。代码签名可以确保软件是真实的，并且在开发、构建、分发和维护阶段没有被篡改，并且验证者可以在运行时验证这些属性。代码签名解决方案的核心组件包括CA、TSA、CSS和验证程序，文中介绍了几个典型的签名用例，定义了相关的部署模型。
