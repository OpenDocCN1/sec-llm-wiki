## 工作背景

2008 年，随着 Hydra IRC bot 的披露，针对嵌入式 Linux 系统的恶意软件被首次发现。随后，业界揭开了 psyb0t、Chuck Nor ris、Carna、Tsunami、Aidra、Dofloo、Gafgyt、Elknot、XOR.DDoS、Wifatch、The Moon、LUABot、Remaiten、NewAidra 和 Moose 等更多针对 IoT 的恶意家族的面纱。2016 年 Mirai 源码的发布催生了非常多的变种，而最初的 Mirai 依靠默认用户名与密码进行传播，但现在更多依赖未修复的漏洞。

由于实际情况与 Mirai 当时已经发生了巨大的变化，业界需要系统地研究 IoT 恶意软件的生命周期，例如 IoT 恶意软件如何感染系统、如何部署有效载荷、如何持续存在于系统上、如何滥用资源以及如何运作其基础设施。

系统地整理了 25 篇研究传统恶意软件的论文，IoT 恶意软件语料库可以在 https://badthings.info 上找到。（注：在会议召开后应该就会正常上线）

![](../Images/42658bad48de45a2ad3a79c389caa049.png)

从如何感染系统（攻击系统的方式）、如何部署载荷（攻击后释放的代码）、如何持久化、如何滥用资源、如何运作基础设施几个角度来比较 IoT 恶意软件与桌面恶意软件、移动恶意软件的异同。

![](../Images/af490a046612c61f592c478e67f2258b.png)

### 静态分析

静态分析部分旨在提取样本文件的目标架构、链接方法（静态与动态）、反分析技术、加壳、内嵌硬编码域名/IP地址、感染向量。

主要使用 binutils 套件中的 readelf、objdump、objcopy、strings 和 hexdump 进行静态分析，根据文件头识别目标架构、字节顺序和链接信息。

#### 标签合并

利用 AVClass 对 VirusTotal 的检出标签进行合并

#### 反分析技术

反分析技术使用四种方法进行检查：

1.  检查 ELF 文件中标记可读可写可执行的节头中的第一个 LOAD (PT\_LOAD) 段，这种反分析技巧通常用于隐藏程序的入口点和中断分析工具
    
2.  遍历每个段和节来检查 ELF 文件中是否有与程序入口点重叠的假节头，检查每个段是否与入口点地址重叠，这种反分析技巧使用可写可执行段覆盖虚假数据段
    
3.  检查一个或多个动态符号表 (SHT\_DYNSYM) 的节头来检查 ELF 文件中是否存在假动态符号表，检查每个段并查找动态表（DT\_SYMTAB）之后的动态符号表，并检查动态符号表是否与动态表重叠（虚拟地址+大小在段之外），这种反分析技巧通常为混合函数符号的动态链接二进制文件插入虚假动态符号表
    
4.  迭代每个段并检查节头字段 e\_shoff、e\_shentsize、e\_shnum、e\_shstrndx 是否为零值。这种反分析技巧删除了有关节头的关键信息，使其无法解析（Linux 内核加载执行 ELF 文件时不使用节头，但分析工具往往依赖节头）
    

#### 加壳

对于 UPX 加壳文件，还会检查 UPX 标头，这并不会影响文件执行，但会影响使用 UPX 标准程序进行脱壳。

#### 内嵌硬编码域名/IP地址

首先使用正则提取 IP 地址/域名，再进行后续处理：

*   对于域名再利用 tldextract 提取域名
    
*   对于 IP 地址再删除所有 bogon 和无效 IP 地址

> 最初 IPv4 地址未分配完时，有伪造这些来源的数据包。后续完成分配后便不应该再过滤 bogon 只过滤 Martian 这种保留地址类，例如 https://ipinfo.io/bogon

#### 感染向量

通过枚举路由器与其他 IoT 设备供应商来获取相关 Yara 规则，爬取 NVD 数据并识别 PoC 代码和常见漏洞的 CVE 信息。一共使用 200 多个 Yara 规则来识别感染向量

### 动态分析

*   全系统仿真：构建特定于架构的虚拟机来执行每个样本并收集其系统调用和网络流量信息，每个样本运行 1 分钟。使用 strace 和其他工具对系统调用/网络行为进行跟踪
    
*   二进制仿真：使用 Zelos 模拟 ELF 文件的指令和系统调用来跟踪系统调用，该方式可以跳过 sleep 调用快速表现恶意行为
    

再利用公开可获得的各种恶意软件的源码，补充用于对执行流程和函数符号进行匹配识别。

全系统仿真与 85% 的二进制仿真能够匹配，其余因为 ABI 不匹配或者无法在二进制仿真中运行而无法比较。在全系统仿真的 30 秒内，95% 的恶意软件都会表现出网络行为。（注：如果创建了至少三个进程、调用了至少 100 个系统调用、则认为恶意软件正常执行了）

#### 基础设施分析

同时收集虚拟机 72 小时背景流量，用于进行流量清洗，过滤发现出站流量与 DNS 请求。

按次数进行统计，首先使用 Tranco 过滤，其次手动检查剔除良性域名，最后利用域名与 IP 的二部图关系过滤良性域名（例如：A lustrum of malware network communication: Evolution and insights）

### 如何部署 Payload

发现的样本至少 15% 都使用了加壳，能够直接脱壳 78% 的样本。有 3.3 % 使用了比加壳更先进的反分析技术来妨碍脱壳

IoT 的恶意软件必须考虑设备异构的问题，不同的处理器、不同的 C 运行库（uclibc、musel、glibc）、不同的内核版本都要纳入考量。所以很多恶意样本都会分析设备名称、CPU 和内存以检查正确的环境。通常来说，Payload 都会使用 Shell 命令，例如，调用 uname、whoami、lsof、crontab 和 os-release 等 shell 命令来收集有关设备的信息，也有依赖于脚本解释器（如 Python 和 Lua）的 Payload。如果无法识别设备的架构，可能会针对不同的架构测试不同的变种。

### 如何持久化

大多数嵌入式设备都将 rootfs（文件系统）挂载为只读 (RO），这样做有可以减少闪存的损耗，降低了系统文件损坏的风险等好处。但设备上必须有一些进程需要对密钥、配置文件等进行写访问，嵌入式设备一般会指定一个非易失性数据区域和一个易失性临时文件系统区域。恶意软件也必须考虑到 IoT 设备的这种特性，才能维持自己的持久化。

可以通过将自身安装为服务、启动脚本、系统模块或后门程序来实现持久化，有些样本也会尝试重新挂载具有读写权限的文件系统，例如使用 mount -o re mount。即使使用易失性内存区域，也会使用 tmpfs 路径进行持久化。在系统重新启动时，tmpfs 路径将被擦除，也会清除 IoT 恶意软件。

为了延长感染时间，IoT 恶意软件会禁用设备上的 watchdog 进程。嵌入式设备上的 watchdog 进程是一个特权进程，它通过强制设备重新启动到干净状态来缓解软件故障。IoT 恶意软件会通过将 "Magic Close" 写入 /dev/FTWDT101\_watchdog、/dev/misc/watchdog 或 /dev/watchdog 路径处来禁用 watchdog 进程。

#### 其他行为

恶意软件还可能尝试删除文件系统的根目录、dbus 设备、清空 MMC 内存、删除通用 IO 引脚上的配置设备、删除 Linux 设备表等破坏性操作。

### 案例一：代码重用与演进

很多 IoT 恶意软件样本实际上未能在全系统仿真中运行，这些样本即使在真实物理缓解下执行也会崩溃。研究发现根源在于编译面向 ARMv6 和 MIPS-EL 架构的 Mirai 代码时，要求编译器 strip 就会复现这个问题。

![](../Images/910c0b7d380c1f7c98d5d95f03eb194b.png)

Mirai 的源码中用于存储进程名的缓冲区常读仅为 20 字节，故而在恶意软件试图隐藏进程名时就会报错。而有些样本修复了这个问题，转而使用可变长度缓冲区即可解决。

### 案例二：破损 DNS

Mirai 源码中保有一个导致 DNS 查询格式错误的初始化错误。由于未初始化存储 DNS 查询的缓冲区，会被内存中的随机字节填充查询。该漏洞影响所有的 Mirai 变种，这可能也促使 IoT 恶意软件更多依赖 IP 而不是域名进行 C&C 通信。

### 案例三：部署 Payload

分别调查了 iwantallthesmoke.club 和 str3sser.com 两个案例。

#### str3sser.com

*   str3sser.com 通过 Namecheap 于 2018 年 6 月 29 日注册，并且近六个月处于非活动状态。
    
*   2018 年 12 月 27 日，域名解析记录更改为指向 Cloudflare。创建了两个 A 记录（104.27.181.96 和 104.27.181.96）和两个 NS 记录（liz.ns.cloudflare.com 和 jobs.ns.cloudflare.com）。由于 DNS 请求量较少，推测这些记录用于上线前的测试。
    
*   79 天后，域名的 A记录（35.241.225.135 和 35.205.247.152）和 NS 记录（dns1.registrar-servers.com 和 dns2.registrar servers.com）更改为指向 Google Cloud。
    
*   14 天后 A 记录变更 IP 地址 (72.5.65.111)，两天后所有者创建了五个指向 OpenDNS 基础结构 (146.112.61.107) 的子标签（cuteguyss、est1976、apneager、chivethethrottle 和 aq），然后域名就下线了。
    
*   后来域名一直处于休眠状态，直到过期。
    

#### iwantallthesmoke.club

*   iwantallthesmoke.club 通过 Namecheap 于 2019 年 1 月 10 日注册。
    
*   一天后增加 A 记录(185.141.24.211)指向 Sailor 的 VPS
    
*   第二天，域名首页显示 "me nah wan go jail"
    
*   第三天，通过 Passive DNS 发现 11 次请求，后续休眠了五天
    
*   在 2019 年 1 月 21 日，该域名更新了 A 记录（89.46.223.195）指向另一个 VPS（Zare.com）
    
*   在三天后，请求就归零了
    
*   第七天，域名也已经失效了。
    

该域名仅仅运营了六天时间，该域名是关联的五个域名之一。另外四个域名指向的 IP 地址 89.46.223.195 也托管了类似的 Payload，这表明有效域名进行了轮换。但恶意软件用来 C&C 的硬编码 IP 地址与使用的五个域名解析的 IP 地址并不相关。

## 工作思考

在野的 IoT 恶意软件大量重用代码，这可能使得检测起来更为容易。同时也能看出，多态和反分析技术都可以有效进行检测逃避。未来，IoT 恶意软件应该也会参考桌面恶意软件与移动恶意软件的经验，变得对抗性越来越强。

*   设备所有者应该尽可能地禁用公网暴露的服务、更改默认凭据。当设备无响应或者服务质量下降时，可以重启设备实现对恶意软件的清除。但可以看出，随着持久化更加普及，想通过重启来清除恶意软件可能会越来越难
    
*   设备供应商应该通过设备遥测检测系统异常、固件限制 Shell 命令、容器化限制跨进程交互、进程白名单限制、限制公网暴露的服务等措施尽可能减少攻击面
    
*   ISP 运营商应该封堵或者重定向 IP 来控制感染，更积极的方法是让 ISP 拦截 Payload 投递或者 C&C 通信。最好的情况下是能够提供良性的 Payload，在不需要用户参与的情况下透明地清理/禁用易受攻击的服务
