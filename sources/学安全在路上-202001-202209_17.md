# Kerberos认证流程

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzI3MjI0NDEzMg==&mid=2247484052&idx=1&sn=7ee680ff0d552ab0592192ccd5e40303&chksm=eb34ce5fdc4347492e851d17d76925fbfa309787f183f6817692c362cf63d611dab85a2e8705&scene=126&sessionid=1681654688#rd](http://mp.weixin.qq.com/s?__biz=MzI3MjI0NDEzMg==&mid=2247484052&idx=1&sn=7ee680ff0d552ab0592192ccd5e40303&chksm=eb34ce5fdc4347492e851d17d76925fbfa309787f183f6817692c362cf63d611dab85a2e8705&scene=126&sessionid=1681654688#rd)

    Kerberos 是一个用于验证用户或主机身份的身份验证协议，Kerberos 协议在开放和不安全的网络上提供一种可靠的认证，但需要网络中的主机本身是可信的，即可信主机在不可信网络上的认证，微软 Kerberos 协议的实现遵循 RFC 的标准。与NTLM不同的是，NTLM认证是基于请求的客户端与需要访问服务端，Kerberos多了一个信托机构，客户端认证是通过信托机构完成的。  
RFC文档：https://www.rfc-editor.org/info/rfc4120

## 名词介绍

  
Kerberos认证涉及到几个新的名词，先做一个介绍：

| 角色 || 作用 |
| --- | --- |
| Domain Controller（DC） || 域控制器，简称DC，一台计算机，实现用户、计算机的统一管理。 |
| --- | --- |
| Key Distribution Center（KDC） || 秘钥分发中心，简称KDC，默认安装在域控里，包括AS和TGS。 |
| Authentication Service（AS） || 身份验证服务，简称AS，用于KDC对Client认证。 |
| Ticket Grantng Service（TGS） || 票据授予服务，简称TGS，用于KDC向Client和Server分发Session Key（临时秘钥）。 |
| Active Directory（AD） || 活动目录，简称AD，用于存储用户、用户组、域相关的信息。 |
| Ticket Grantng Ticket（TGT） || 票据许可票据，由KDC颁发，使用 KDC 一个特定账户tgtkbr的 NTLM-Hash加密的票据，用于客户端申请服务票据。 |
| Service Ticket（ST） || 由KDC认证通过后颁发的服务票据，客户端最终用来访问服务端的票据 |
| Privilege Attribute Certificate（PAC） || 特权访问证书，PAC 中包含的是用户的 SID、用户所在的组等一些信息，DC通过PAC查询对应的用户SID来判断用户是否有权限访问服务。 |
| Client || 客户端，指用户。 |
| Server || 服务端，可能是某台计算机，也可能是某个服务。 |

  

## 基本过程

  
由浅入深，先介绍Kerberos认证的粗略过程：

![](../Images/460ef16735d633784287dd26a687598a.png "null")

未命名绘图 的副本.png

  
1、Client 想要访问服务端的某个服务（SMB、FTP等等），输入的账号密码账号密码将先被交给域控的KDC中的AS服务，AS通过查询AD域判断是否存在用户。  
2、AS若判断用户存在，则交由TGS生成TGT发送给Client 。  
3、Client 将收到的TGT再次发送给TGS  
4、Client 继续拿着 TGT 请求 DC 访问 Server Service，TGS 通过 Client 消息中的 TGT，判断 Client 是否有访问权限。如果有，则给 Client 有访问 Server 的权限 Ticket，也叫 ST（Service Ticket）。  
5.Client 得到 ST 后，再去访问 Server，且该 ST 只针对这一个 Server 有效。  
6.最终 Client 获得Server Service的访问权限。  

以上是Kerberos认证粗略的过程，通过上面的描述可以对Kerberos认证流程有一个基本的认识。

### AS\_REQ & AS\_REP

![](../Images/c8869b5026aec0f5a12e03b4d2bd4c4d.png "null")

1.png

  
该阶段主要是 Client 和 AS 的认证，通过认证的客户端将获得Ticket Grantng Ticket（TGT）。  
KRB\_AS\_REQ是Client发起认证的第一步，是Client发起的请求；KRB\_AS\_REP是Kerberos认证的第二步，是域控回复Client的响应。  
**第一步：**  

当域内某个客户端用户 Client 试图访问域内的某个服务，于是输入用户名和密码，此时客户端本机的 Kerberos 服务会向 KDC 的 AS 认证服务发送一个 AS\_REQ 认证请求。请求的凭据是 Client 的哈希值 NTLM-Hash 加密的时间戳（pre-authorization-data）、 Client-info以及Server-info 等数据，以及一些其他信息。这个请求就是AS\_REQ。

```
AS_REQ {    Client-NTLM-Hash(timestamp);    Client-info:用户名、主机名    Server-info:服务名}
```

**第二步：**  

当 Client 发送身份信息给 AS 后，AS 会根据AS\_REQ中携带的CLient-info先向活动目录 AD 询问域内是否有此 Client 用户。如果有的话，就会取出它的 Client-NTLM-Hash，对 AS\_REQ 请求中加密的时间戳进行解密，如果解密成功，则证明客户端提供的密码正确。如果时间戳在五分钟之内，则预认证成功。然后会返回给Client包含三部分的内容。**第一部分是：** AS 会生成一个临时秘钥 Session-Key AS，并使用客户端 Client - NTLM-Hash 加密 Session-key AS 作为响应包的一部分内容。**第二部分是：**TGT：使用 KDC 一个特定账户krbtgt的 NTLM-Hash 对 Session-key AS、时间戳、Client-info 进行的加密。这个特定的**krbtgt用户**是在创建域时系统自动创建的一个账号，其作用是密钥发行中心的服务账号，其密码是系统随机生成的，无法正常登陆主机。然后将这两部分以及 **第三部分：PAC** 等信息回复给 Client，即 AS\_REP 。  
此 Session-key AS 用于确保客户端和 KGS 之间的通信安全。

```
KRB_AS_REP {    Client-NTLM-Hash(Session-Key AS);    TGT:kbrtgt(timestamp1+client-info+Session-Key AS);    PAC;}
```

备注：  
AS-REP 中最核心的东西就是 Session-key 和 TGT。我们平时用 Mimikatz、kekeo、rubeus 等工具生成的凭据是 .kirbi 后缀，Impacket 生成的凭据的后缀是 .ccache。这两种票据主要包含的都是 Session-key 和 TGT，因此可以相互转化。  
至此，Kerberos 认证的KRB\_AS\_REQ & KRB\_AS\_REP两步完成。

### KRB\_TGS\_REQ & KRB\_TGS\_REP

![](../Images/4fa31081326fb32688fe77b0b8e3d502.png "null")

2.png

  
该阶段是 Client 和 TGS 的认证，通过认证的客户端将获得 ST 服务票据。  
**第三步：**  

客户端 Client 收到 AS 的回复 AS\_REP 后分别获得了 TGT 和加密的 Session-Key AS。它会先用自己的 Client-NTLM-Hash 解密得到原始的 Session-Key AS，然后它会在本地缓存此 TGT 和原始的 Session-Key AS，当需要访问某台服务器上的服务时，就需要凭借这张 TGT 认购凭证向 KGS 购买相应的 ST 服务票据。  
Client会使用解密出来的 Session-Key AS加密Client-info、Server-info以及时间戳。由于Client没有kbrtgt的NTLM-Hash，所以会将TGT原封不动的发送给KGS。这两部分称为KRB\_TGS\_REQ。

```
KRB_TGS_REQ {    Session-Key AS(Client-info+Server-info+timestamp2);    TGT:kbrtgt(timestamp1+client-info+Session-Key AS);}
```

**第四步：**  

TGS 收到该请求，用 kbrtgt 用户的 NTLM-hash 先解密 TGT 得到 Session-key AS、时间戳、Client-info 以及 Server-info。再用 Session-key AS 解密第一部分内容，得到 Client-info、时间戳。然后将两部分获取到时间戳进行比较，如果时间戳跟当前时间相差太久，就需要重新认证。TGS 还会将这个 Client 的信息与 TGT 中的 Client 信息进行比较，如果两个相等的话，还会继续判断 Client 有没有权限访问 Server，如果都没有问题，认证成功。认证成功后，KGS 会生成一个 Session-key TGS，并用 Session-key AS 加密 Session-key TGS 作为响应的一部分。  
此 Session-key TGS 用于确保Client和Server之间的通信安全。  
另一部分是使用服务器 Server 的 NTLM-Hash 加密 Session-key TGS、时间戳以及 Client-info 等数据生成的 ST。然后 TGS 将这两部分信息回复给 Client，即 TGS\_REP 。

```
KRB_TGS_REQ {    Session-Key AS(Session-Key TGS);    ST:Server-NTLM-Hash(Session-key TGS+client-info+timestamp3);}
```

至此，Client 和 KDC 的通信就结束了，然后是Client和 Server 进行通信。

```
KRB_AP_REQ {    Session-Key TGS(client-info+Timestamp4)    ST:Server-NTLM-Hash(Session-key TGS+client-info+Timestamp3);  PAC；}
```

**第六步：**  

Server 收到 AP\_REQ 请求后，用自身的 Server NTLM-Hash 解密了 ST，得到 Session-Key TGS，再解密出Client-info、时间戳等数据。然后与 ST 的Client-info、时间戳等进行一一对比。时间戳有效时间一般时间为8小时。通过客户端身份验证后，服务器 Server 会拿着 PAC 去询问 DC 该用户是否有访问权限，DC 拿到 PAC 后进行解密，然后通过 PAC 中的 SID 判断用户的用户组信息、用户权限等信息，然后将结果返回给服务端，服务端再将此信息域用户请求的服务资源的 ACL 进行对比，最后决定是否给用户提供相关的服务。通过认证后 Server 将返回最终的 AP-REP 并与 Client 建立通信。  

至此，客户端获取到了Server Service 访问权限，Kerberos认证结束。

## 常见安全问题

  

### 域内用户枚举

由于AS\_REQ请求中的Client-Info包含用户名，AS通过用户名在AD中查找是否存在用户名判断用户请求是否合法，那么就可以通过尝试发送不同用户名AS\_REQ来爆破域内用户名。  

![](../Images/288394b6b1fe4b8d9f545b60116a4651.png "null")

image.png

  

### 白银票据

上述的Kerberos认证第6步中，Server service 收到Client发来的AP\_REQ后会使用PAC询问DC ST票据是否是DC颁发且用户是否存在访问Server权限，进而决定是否为客户端提供服务。实际上该步骤不是必须，有的环境可以通过配置不使用PAC，省去使用PAC询问DC这一步。这也导致了白银票据的问题。  
查看AP\_REQ报文，实际上Server Service本身 并不知道Session-key TGS的具体内容，是通过Server-NTLM-Hash来解密得到的。那么假如我们拥有Server-NTLM-Hash，我们完全可以伪造一个AP\_REQ来欺骗Server Service ，在未开启PAC验证的情况下访问服务。  

![](../Images/fea439437a2fbf1f66a2046dc6fc1808.png "null")

报文.png

  

### 黄金票据

域认证过程中，AS\_REP会使用krbtgt用户哈希来生成TGT票据，假如我们拥有了krbtgt用户哈希，参考白银票据，那么我们就可以任意构造TGS\_REP来申请任意用户、任意权限的ST，因为 Krbtgt 只有域控制器上面才有，所以使用黄金凭据意味着你之前拿到过域控制器的权限，黄金凭据可以理解为一个后门。

### AS\_REQ Roasting

AS\_REQ & AS\_REP 认证的过程是 Kerberos 身份认证的第一步，该过程又被称为预身份验证。预身份验证主要是为了防止密码脱机爆破。  
而如果域用户设置了选项 "Do not require Kerberos preauthentication"（该选项默认没有开启）关闭了预身份验证的话，攻击者可以使用指定的用户去请求票据，向域控制器发送 AS\_REQ 请求，此时域控会不作任何验证便将 TGT 票据和加密的 Session-key 等信息返回。因此攻击者就可以对获取到的加密 Session-key 进行离线破解，如果爆破成功，就能得到该指定用户的明文密码。  
这种攻击方式被称作 AS-REP Roasting 攻击。
