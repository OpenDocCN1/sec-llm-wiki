经过一番百度之后终于了解到了一种xss攻击手段叫做flash xss。那么为什么取名为flash xss呢？是因为flash有可以调用js的函数，也就是可以和js进行通信。因此这些函数如果使用不当也是会造成xss的。

常见的可触发xss的危险函数有：getURL、navigateToURL、ExternalInterface.call、htmlText、loadMovie等等。

要想知道这一关的是不是属于flash xss，只需要对引用的swf文件进行反编译然后进行源码分析。这里我说使用的对此类文件进行反编译的工具是jpexs-decompiler（项目地址：https://github.com/jindrapetrik/jpexs-decompiler）。下载之后进行安装

首先我们需要理解的就是这里ExternalInterface.call()的运行机制。从反编译的代码中我们可以看到通过LoaderInfo获取的id的值是充当了ExternalInterface.call()的第二个参数。

源文件中有很多处都调用了ExternalInterface.call()，并且其中id都是作为第二参数的位置。ExternalInterface.call(a,b)在运行时其实就相当于js中的函数名(参数)。

以上图为例，如果我们提交的参数为id=1的话，在这里的实际情况就是

ZeroClipboard.dispatch(id)

结合通篇的反编译代码来看，这里的id的值两边是要加”的，所以就是 ZeroClipboard.dispatch(“1”)

了解了这一点后之前的payload就不难理解了

id=xss"))}catch(e){alert(/xss/)}//%26width=123%26height=123

传入到swf文件中就是这样的

ExternalInterface.call("ZeroClipboard.dispatch","xss"))}catch(e){alert(/xss/)}//","complete",clipText);

从运行机制理解的话就是

private function clickHandler(param1:Event) : void { System.setClipboard(clipText); ExternalInterface.call(ZeroClipboard.dispatch("xss"))}catch(e){alert(/xss/)}//","complete",clipText)); }

可以看到后面的代码都被//注释掉了，所以把多余的去掉就会变成这样

private function clickHandler(param1:Event) : void { System.setClipboard(clipText); ExternalInterface.call(ZeroClipboard.dispatch("xss"))}catch(e){alert(/xss/)}

关键的一点就在于这个"xss"。因为这里的\将后面的”已经转义了，就只是一个单纯的符号而已，无法达到闭合的效果。这里的ExternalInterface.call()运行时由于前面少了一个真正可以闭合的"就会报错，所以后面抛出异常的catch就会生效，于是执行后面的alert(/xss/)。

接着再来说下//后面的%26width=123&26height=123，%26其实是&的url编码格式，那为啥非得写%26呢，来看看源文件的代码

可以看到服务器端只通过get方式接收两个参数的值，如果这里继续用&来传递参数的话服务器端也不会接收。但是如果是通过url编码之后的%26的话，服务器端就会将其后的所有字符当做是arg02参数的值，然后将其添加到<embed>标签的src属性值中去。可能这样在网页源码中显示会是有的字符经过html字符实体编码的，但是不会影响swf文件的取值的。
