自动化挖洞的想法


    我最近有一些自动化挖洞的想法，我把这些想法写成了一个工具，那个工具的名字就叫赏金鸡，因为这个工具就像会下金蛋的鸡，将那些枯燥无味的事情自动化。我想展示我最近所做的一些事情，并分享我的方法。我会尽量简化和解释很多想法。自动化挖洞可以分为自动化信息收集和自动化漏洞扫描。信息收集得越完善，越有可能挖到漏洞。所以自动化挖洞的第一步就是自动化的信息收集。


    在开始我自己的想法之前，我是先了解了一下安全社区的一些自动化信息搜集的工具，看看它们有啥优点和缺点，这能给我自己实现带来一些灵感。




对一些自动化信息收集工具简单分析



lazyrecon


1.lazyrecon介绍

    首先是lazyrecon，lazyrecon他是知名bb猎人nahamsec写的，它是一个结合多个信息收集工具的脚本，该工具用的是bash编写，可以说是自动化信息收集工具。


2.安装Lazyrecon所需要的工具和环境

git clone https://github.com/nahamsec/bbht.gitcd bbhtchmod + x install.sh./install.sh


3.安装lazyrecon

git clone https://github.com/nahamsec/lazyrecon.gitcd lazyrecon


4.使用方法

./lazyrecon.sh -d domain.com

domain.com 是目标域名

我这里的域名是yahoo.com ，图下已经对yahoo开始信息收集了。


运行完毕后可以发现多了一个yahoo的文件夹


现在进入yahoo的文件夹中，发现里面有一个文件夹写着日期，这里有一个好处是如果你定期扫描目标的资产，用日期的情况下可以做数据对比，从而分析更多的信息，可以准确的跟踪资产。日期文件夹是各种信息收集的结果（最终结果）


这里它还会贴心的生成一个html结果方便你对结果进行查看和管理。


5.总结

lazyrecon是一个结合多个工具的流程脚本，他把任务分发给每一个工具进行处理和分析。

优点：

  1. 模块化的分割，lazyrecon它是把任务分给多个工具进行工作，不会一个工具崩了导致整个工具运转不了

  2. 可以输出运行结果，它可以方便自己手动测试。

  3. 代码开源，我们可以通过它的脚本代码知道他是如何去结合多个工具进工作的，并且我们可以获取工具的思路，对自己的工具进行定制化。


缺点

1.不容易和其他工具进行联动，如果想将它的结果移交给另外一个扫描器，可能要手动的处理结果。它由于是bash编写的，有些优化的工作无法完成。同样用bash编写的自动化信息收集工具还有sniper。

3.总结

写到这里可以开始总结了，不得不说这个是一个很全面的信息收集器，这个工具有个很有意思的地方是将攻击面抽象为图，把节点表示资产。

优点：

  1. 可以监控你所扫描的整个项目，这有利于你大致了解信息的彼此关系，然后进一步分析

  2. 在扫描的过程中输出结果，方便自己手动去测试，因为如果直接输出最终结果有些，信息点会被忽略。

  3. 对目标延展性强可以更深入的迭代，可以发现很多目标，从而扩大攻击面

  4. 代码开源，我们对其代码进行分析总结出实现的方法，然后扩展性强的代码来编写自己定制的扫描器。

缺点：

  1. 模块没有分割，因为整个扫描器是用ruby写的，只要有一个地方出了问题整个扫描器就会错误，在我测试的时候经常会出现访问不到或者崩掉。

对xsstrike的简单分析



为什么选择分析xsstrike


除了能够自动化信息收集，自然地，我们也需要一个能够自动化扫描漏洞的工具。拿寻找xss漏洞中简单的反射xss来说，如果给出一个有漏洞的url，是否保证找出这个url的反射xss漏洞，当扫描队列里面有成千上万的url的时候，是否能够做到尽可能避免漏报和误报。对于反射xss来说，如果能判断出反射点所处的上下文，那么就能大大减少误报的出现。


举个例子，当反射点出现在一个html属性里面，被双引号包裹起来，哪怕你的荷载<svg/onload=alert()>完全没有过滤，也是毫无用处，因为最关键的字符是双引号，只有在这个反射点的地方双引号没有被过滤或者html实体编码，才表示能够打破上下文，表示有漏洞。很多xss工具误报严重就是因为没有进行上下文的分析。经过简单地排查，我选择了xsstrike这款工具。并花了一整个下午的时间分析它的代码实现，测试这个工具。

dom xss检测



首先用正则表达式re.findall(r'(?i)(?s)<script[^>]*>(.*?)</script>将所有script标签提取出来，分别对每个script标签进行处理，把script标签的内容一行一行分隔开来，再把每一行通过'var '分隔符分开，利用正则表达式找到输入点，输出点以及可控变量。输入点的寻找的关键代码在下面

sources=r'''document\.(URL|documentURI|URLUnencoded|baseURI|cookie|referrer)|location\.(href|search|hash|pathname)|window\.name|history\.(pushState|replaceState)(local|session)Storage'''pattern = re.finditer(sources, newLine)

利用正则表达式对每行匹配，如果匹配到了，还会对这行拆分的各个部分进行判断是否在该部分存在匹配值以及一个变量，如果同时满足这两个条件，这个匹配值就是输入点，同时把这个变量加入可控变量集合。

输出点除了没有这种判断外逻辑类似。寻找可控变量的时候，首先需要进行一个if语句判断，

if len(parts) > 1:


这个语句对应了前面的代码，

parts = line.split('var ')


表明这一行中有变量的定义。这一行被'var '分割为几个部分，对每个部分进行查看，如果这个部分存在一个输入点，那么这个部分定义的变量就是可控变量，另外如果已经找到的可控点出现在这个部分，那么这个部分定义的变量也是可控变量。通过下面这个简单的正则表达式就可以把变量找到，

re.search(r'a-zA-Z$_]a-zA-Z0-9$_]+', part)

因为re.search只会匹配第一个符合的，然后把这个可控变量加入可控变量集合，所有找到的输入点输出点可控变量都会对他们进行上色高亮处理。不过这种通过正则表达式寻找dom xss漏洞的方式不光容易误报还容易漏报。比如下面这个教科书一样简单的例子它都检测不出来，

var hash = location.hash;if(hash){var url = hash.substring(1);location.href = url;}

因为它的输出点的正则表达式没有location.href，这种情况就容易导致漏报。

把location.href改成document.location，它就能成功检测到了，我真是太机智了。

还有就是输入点和输出点不一定有关联性，这就导致了误报。所以这种检测方式只能作为辅助使用。回到scan这个函数

if highlighted:logger.good('Potentially vulnerable objects found')logger.red_line(level='good')for line in highlighted:logger.no_format(line, level='good')logger.red_line(level='good')

如果找到了dom xss漏洞，就将结果输出。

xss荷载生成



简单来说，它荷载生成的方式不够灵活。我个人觉得，只要检测上下文是否能被特殊字符打破，如果可以，就认为是有漏洞的，最后发送一个假荷载即可，假荷载只是用来展示上下文，不代表实际情况，这样可以大大加快扫描速度。所以我把它荷载生成的代码给去掉了，只检测是否可以打破上下文，比如上下文在js中，比如var="反射点"，我只要检查"符合在这个上下文是否被过滤，如果没有，就认为有漏洞，生成一个"-alert()-"荷载，但这个荷载不会被实际请求看看是否被过滤，只是用来指出上下文，是个伪荷载，或者检查</sCriPt/x>是否被过滤，如果没有，生成伪荷载查</sCriPt/x><svg/onload=alert()>也认为存在漏洞，然后发送到邮箱，其实微信也是可以的，不过有时候老是会响个不停。剩下的那些关于爬虫的代码我没有去看，因为我心中比较理想的爬虫的实现是那种动态爬虫。
