# 1、PTR（反向域名解析）

## 1.1 简介

PTR 记录或更恰当的反向 PTR 记录是将 IP 地址解析为其关联主机名的过程。这与将主机名解析为 IP 地址（A记录）的过程完全相反。例如，当您 ping一个名称时`mail.mydomain.com`，它将使用 DNS 解析为 IP 地址，例如192.168.1.5. 反向 PTR 记录则相反；它查找给定 IP 地址的主机名。在上面的示例中，IP 地址的 PTR 记录192.168.1.5将解析为`mail.mydomain.com`。

## 1.2 原理

查找 PTR 记录的最常见用途是垃圾邮件过滤器。这个想法背后的概念是，使用假域名发送电子邮件的垃圾邮件发送者通常不会在 ISP DNS 区域设置适当的反向 PTR。垃圾邮件过滤器使用此标准来检测垃圾邮件。如果域名没有一个适当的反向PTR记录设置然后有机会的垃圾邮件过滤软件MIGHT从您的邮件服务器阻止电子邮件。

## 1.3 PTR设置

您很可能需要联系您的 ISP 并请求为您的邮件服务器 IP 地址创建反向 PTR 记录。例如，如果您的邮件服务器主机名mail.mydomain.com然后要求您的 ISP192.168.1.5在其反向 DNS 区域中设置反向 PTR 记录（您的互联网公共 IP 地址）。即使拥有自己管理的正向查找 DNS 区域，反向 DNS 区域由所在的ISP 运营商处理。

# 2、SPF（发件人策略框架）

## 2.1 简介

SPF，全称为 Sender Policy Framework，即发件人策略框架，以IP地址认证电子邮件发件人身份的技术，是非常高效的垃圾邮件解决方案。

### 1.背景

![](../Images/d60c1a740dbc16882bbd82cb7bc93587.png)

今天我的月光族表弟想要模仿我寄信给爷爷跟他要零用钱，他可以自己架起一个email server，然后伪造一封信纸（`header.From`）与信封袋（smtp.MailFrom）上均写着goodboy@gmail.com的信件并寄出。爷爷的email server 看到这封信不疑有他就送进爷爷的信箱里，导致爷爷成功被骗，转了一笔钱给表弟。单纯从SMTP 机制来看，outlook.com眼中的信件写着来自gmail.com，那就姑且相信他。

为了防范这种假冒寄信人的攻击，2014 年4 月RFC 7208 正式提出一套名为**Sender Policy Framework（SPF）**的电子邮件验证机制。这个机制的原理就是要求每个网域发一笔DNS 纪录，其中记载着这个网域所授权的email server 的IP 位置，也就是

**SPF：昭告天下『这些IP 位置是我信任且核可的信件来源』**

当收件方email server 要进行验证时，MDA 就会去查询 smtp.MailFrom这个网域的DNS 纪录，然后检查此信件的来源IP 是否在SPF 纪录中。

### 2.SPF记录原理

SPF 记录实际上是服务器的一个 DNS 记录，假设邮件服务器收到了一封邮件，来自主机的 IP 是173.194.72.103，并且声称发件人为email@example.com。为了确认发件人不是伪造的，邮件服务器会去查询example.com的 SPF 记录。如果该域的 SPF 记录设置允许 IP 为173.194.72.103的主机发送邮件，则服务器就认为这封邮件是合法的；如果不允许，则通常会退信，或将其标记为垃圾/仿冒邮件。

**主流邮件服务提供商是不会接收从未配置SPF的服务器发来的邮件。**

## 2.3 操作方法

### 1.简介

严格来说，SPF 数据应该创建为 SPF 记录。但是鉴于很多 DNS 服务商不支持 SPF 记录，甚至有的邮件服务器也不支持 SPF 记录，因此也可以创建为一条 TXT 记录。目前，你应该至少创建一条 TXT 记录。

因为本质上 SPF 的作用是为一个域名指定合法的发件 IP，所以你需要知道自己使用的邮件服务器的发件 IP 是什么。如果使用第三方的域名邮箱服务（比如腾讯的域名邮箱），那么他们应该有相应的文档提示该怎么填写。

### 2.操作方法

SPF 是 TXT 类型的 DNS 记录，可以在其中列出 IP 地址或 MX 域

```
mydomain.com.   3600    IN  TXT "v=spf1 mx -all"
```

云厂商配置如下

![](../Images/e92f6b9811d4902a3080350e3b464726.png)

SPF 记录意味着`mydomain.com`允许从MX 记录中定义的所有服务器发送以`someone@mydomain.com`电子邮件

`-all`意味着禁止从所有其他服务器发送电子邮件。如果它对您来说太严格，您可以~all改用这意味着软失败

### 3.允许IP发送邮件

```
mydomain.com.   3600    IN  TXT "v=spf1 ip4:111.111.111.111 ip4:111.111.111.222 -all"
```

# 3、DKIM

## 3.1 简介

### 1.情景

![](../Images/d60c1a740dbc16882bbd82cb7bc93587.png)

表弟发现攻击失败，只好另寻他法。他灵光一闪，发现虽然不能假冒gmail.com寄信，那他可以拦截我寄给爷爷的信，然后把里面的栏位跟资讯改掉，这样就可以冒充我的身份又通过SPF 验证啦！于是表弟窜改我的信件，把内容改成零用钱请求，又成功骗到爷爷了。

### 2\. 攻击防范

为了防范这种攻击，2011 年首次提出的RFC 6376（后来又在RFC 8301 与RFC 8463 修订）定义了DomainKeys Identified Mail（DKIM）这个机制。

DKIM：使用数位签章的概念来防止邮件伪造与窜改，透过公私钥加密验证的特性来确保讯息的完整与真实性。

寄信方的email server 会产生一组公私钥，公钥会用DNS 纪录发布出去让收信方可以用来解密。在寄信时使用私钥加密header 的某些栏位与body，并将产生的杂凑（hash）做为签章附上，此签章称为DKIM signature。要加密的栏位由email server 指定，不过必须包含header.From（否则寄件人的身份就没有保障啦）。

收信的email server 进行验证时，如同SPF，MDA 会去查询寄信网域的DNS 纪录，找到对应的公钥后解密签章内容来比对是否一致。

## 3.2 DKIM原理

DKIM 允许组织以收件人可以验证的方式对消息负责。该组织可以是消息的直接处理者，例如作者的、原始发送站点的或传输路径上的中间人。但是，它也可以是间接处理程序，例如为直接处理程序提供帮助的独立服务。DKIM 定义了一个域级别的电子邮件数字签名认证框架，通过使用公钥密码学，并使用域名服务作为其密钥服务器技术（RFC4871）。它允许验证消息的签名者及其内容的完整性。DKIM 还将提供一种机制，允许潜在的电子邮件签名者发布有关其电子邮件签名做法的信息；这将允许电子邮件接收者对未签名的邮件进行额外的评估。DKIM 对电子邮件身份的认证可以辅助全球控制“垃圾邮件”和“网络钓鱼”。

一个人或组织有一个"身份"——也就是说，一组将他们与任何其他身份区分开来的特征。与此抽象相关联的可以是用作参考或"标识符"的标签。这是事物与事物名称的区别。DKIM 使用域名作为标识符，指代负责人或组织的身份。在 DKIM 中，此标识符称为签名域标识符 (SDID)，包含在 DKIM-Signature 标头字段d= 标记中。请注意，同一个身份可以有多个标识符。

![](../Images/64b580b82859c66b891f5824553ce3d7.png)

签章如下图所示，标签中 v 为版本、a代表加密方式。d s q三者一起用来查询公钥，表示查询域名为<selector>.\_domainkey.<domain>（图中就是brisbane.\_domainkey.example.net）的DNS TXT 纪录。h代表指定的header 栏位，加密后的结果会放在b，而bh（body hash）则是body 本身经过杂凑后的结果

# 4、DMARC

## 4.1 简介

### 1.情景

![](../Images/d60c1a740dbc16882bbd82cb7bc93587.png)

表弟拿不到零用钱，很是挫败。于是他绞尽脑汁终于想到：既然我不能仿冒gmail.com也不能拦截真的信件，那我就自己架一个email server、申请一个合法网域cousin.com，然后寄一封信纸（header.From）上写goodboy@gmail.com的信给爷爷就好啦！虽然信封袋（smtp.MailFrom）上写的是cousin.com，但反正爷爷在outlook 里看到的也只有header.From，他哪知道不是真的从gmail.com来的。而且，不管是SPF 还是DKIM 验证的都是 smtp.MailFrom 的网域，我本来就是cousin.com又没造假，休想挡我财路。

## 4.2 攻击防范

好在2015 年3 月时RFC 7489 出现，提出了一个可以保护爷爷的方法，名为**Domain-based Message Authentication, Reporting and Conformance（DMARC）**

DMARC 结合了SPF 与DKIM，形成三人联防，缺一不可，同时强化信纸与信封袋的一致性。

DMARC 主要有两个功能，其一是指示了当SPF 与DKIM 验证失败时该采取的行为，称为policy；第二则是确保信纸与信封袋上标示的寄件人来自同一个网域（也就是比对header.From跟smtp.MailFrom），称为alignment。

## 4.3 名词解释

**注：DMARC 严重依赖 SPF 和 DKIM 记录，需确保已发布正确且最新的 SPF 和 DKIM 记录**

DMARC 记录是 TXT 类型的 DNS 记录

### 1.简化记录

```
v=DMARC1; p=none; rua=mailto:dmarc@mydomain.com
```

### 2.详细记录

```
v=DMARC1; p=reject; sp=none; adkim=s; aspf=s; rua=mailto:dmarc@mydomain.com; ruf=mailto:dmarc@mydomain.com
```

### 3.解释

*   ✅v=DMARC1标识 DMARC 协议版本，目前仅DMARC1可用，并且v=DMARC1必须首先出现在 DMARC 记录中。
    
*   ✅adkim指定 DKIM 的对齐模式。有 2 个选项可用：
    

*   r: 宽松模式 ( adkim=r)
    
*   s: 严格模式 ( adkim=s)
    

*   ✅aspf指定 SPF 的对齐方式。有 2 个选项可用：
    

*   r: 宽松模式 ( aspf=r)
    
*   s: 严格模式 ( aspf=s)
    

*   ✅p指定组织域的策略。如果收到的电子邮件未通过 DMARC 机制检查，它会告诉收件人服务器该怎么做。有 3 个选项可用：
    

*   none( p=none)：域所有者要求不对邮件传递采取任何具体措施。
    
*   quarantine( p=quarantine)：域所有者希望邮件接收器将未通过 DMARC 机制检查的电子邮件视为可疑电子邮件。根据邮件接收器的功能，这可能意味着“放入垃圾邮件文件夹”、“标记为可疑”或“将电子邮件隔离在某处”，甚至更多。
    
*   reject( p=reject)：域所有者希望邮件接收器拒绝在 SMTP 事务期间未通过 DMARC 机制检查的电子邮件。
    
*   如果您确定您的所有电子邮件都是由 SPF 记录中列出的服务器发送的，或者具有正确的 DKIM 签名，p=reject则强烈建议您这样做。
    
*   根据RFC 7489， "v"和"p"标签必须存在并且必须按该顺序出现。所以请始终将"p"标签紧跟在"v"标签之后。例如 v=DMARC1; p=reject; aspf=s; ...可以，但不是v=DMARC1; aspf=s; p=reject; ...。
    

*   ✅sp为所有子域指定策略。这是可选的。可用选项与 相同p。
    
*   ✅rua指定一种传输机制来提供聚合反馈。目前仅mailto:支持。这是可选的。
    
*   ✅ruf指定将报告特定于消息的故障信息的传输机制。目前仅mailto:支持。这是可选的。

### 1.设置SPF

**在设置DMARC记录之前，必须保证已经设置SPF记录**

```

```

*   ✅主机记录为：`_dmarc`
    
*   ✅记录值为：`v=DMARC1; p=quarantine; rua=mailto:dmarc_report@yourdomain.com; ruf=mailto:dmarc_report@yourdomain.com`
