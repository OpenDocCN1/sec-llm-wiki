OS X 字体解析漏洞分析

原文：http://mp.weixin.qq.com/s?__biz=MzA5ODA0NDE2MA==&mid=206537544&idx=3&sn=3a53ee26054e1fb139ce255bc86b18a2&chksm=192cb3272e5b3a3108a64cade04da55377d519aab1a88807b3c13e9a2ff4b8d79bfec6c72e6c&scene=27#wechat_redirect

苹果公司在OSX 10.10.4更新中修补了大量由雅虎Pentest团队报告的安全漏洞。在研究各种OS X框架的过程中，笔者将注意力投向了OS X字体解析模块并利用了一个星期的时间模糊测试和逆向OSX本地库。通过研究发现了6个CVE，其中5个在OS X和iOS系统中均存在。

由于文件格式的复杂性和多样性，客户端字体解析往往成为很好的攻击目标。例如，TrueType自带图灵完备的指令集（可以在这里了解更多相关内容）。OTF和冷门的PostScript文件格式虽然复杂但OS X系统依然支持这些格式。

字体解析中的许多缺陷是使用不可信的长度值造成的，这些值直接提取自未经验证的文件。举个例子，在CoreText（一种底层字体布局框架）中，ArabicLookups::AddLookup函数（如下所示）从字体文件的内存映射中读取一个长度值，将其累加到一个出界指针上。该指针值存于rdi寄存器中，且随后在ResolveLookup函数中被解引用。


loc_D27E3:
mov eax, ecx
mov ax, [rdx+rax*2+2]
rol ax, 8
movzx edi, ax
add rdi, rdx
mov rsi, r8
mov rdx, r9
call __ZL13ResolveLookupPKN3OTL11LookupTableEPKvS4_ ; ResolveLookup(OTL::LookupTable const*,void const*,void const*)

Apple Type Services进程负责管理字体。官方文档关于该进程的描述：“ATS服务器进程管理MAX OS X的字体数据库。它负责激活和停用字体，维持和缩放字形轮廓，维护字体缓存数据，并在客户端和字体使用程序间传递字体可用性信息。”正是由于ATS解析字体文件，使得ATS成为了极佳的客户端攻击目标。

在ATS中发现的漏洞之一与攻击者控制调用memcpy函数的size参数有关。堆栈跟踪的片段如下所示：


Thread 0 Crashed:: Dispatch queue: com.apple.main-thread
0 libsystem_platform.dylib 0x00007fff91599fc9 _platform_memmove$VARIANT$Unknown + 41
1 libTrueTypeScaler.dylib 0x00007fff943a2daa CreateScalerVariationBlock(fsg_SplineKey*, memoryContext*, unsigned int, FontVariation const*) + 281
2 libTrueTypeScaler.dylib 0x00007fff943a1e2f AssureStrikeBlocks(fsg_SplineKey*, memoryContext*, cacheStrike*, TStrikeDescription const*) + 121
3 libTrueTypeScaler.dylib 0x00007fff943a6879 TTGetStrikeSpecs + 129
4 libFontParser.dylib 0x00007fff910882a0 TConcreteFontScaler::GetFontInfo(FPFontInfo*) const + 48

为达到这部分代码，AssureScalerFontBlock函数必须在[rax+10h]位置获得一个null值。最终调用ScalarGetTableParts()从字体文件中读取一个整数值，将该值字节交换以满足字节序，然后存放于[rcx+50h]。


mov ecx, [rcx+50h] # read from file, set in ScalarGetTableParts
imul ecx, eax
lea edx, [rdx+rcx*2+40h]
mov [r14+28h], edx # edx is a controlled length
...
mov r12d, [r14+28h]
sub r12d, [r14+18h] # 44h
...
movsxd rdx, r12d # size_t
call _memcpy
