# 【技术分享】从hw打点到编写python版webshell提权

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzA5ODA0NDE2MA==&mid=2649747215&idx=1&sn=e82520267ac87397db00a78609ab5b39&chksm=888cdf60bffb567636457cb60fcb11c597b2532121c1583318554baddc8a41ee38e7337a65f4&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=MzA5ODA0NDE2MA==&mid=2649747215&idx=1&sn=e82520267ac87397db00a78609ab5b39&chksm=888cdf60bffb567636457cb60fcb11c597b2532121c1583318554baddc8a41ee38e7337a65f4&scene=27#wechat_redirect)

![](../Images/20fdfac51f300645b78664430b6a7027.png)

 

摸到一个某信息管理平台

![](../Images/ef3d4f79d81f48abb213a11f9da90a31.png)

![](../Images/52f0a7ffbab9ed93b68c2da85ec2b49b.png)

开局一个登录框，那么尝试sql注入和弱口令爆破，从返回包中可以看出存在用户名枚举  

![](../Images/97b0d68d71ec659df852a70e7c5046ae.png)

尝试注入测试发现后端存在检测，试了几十个常见的测试手机号还无法枚举到用户名后，遂放弃此路

![](../Images/e3f812dd9ac254266fd68aaec580a78f.png)

通过报错页面的信息，和url格式，我当时判断的是这是一个 java mvc模型的站点，也给后面埋了个坑  

![](../Images/f56389fdda892430d876c629f99b125b.png)

于是开始翻看静态资源，熟悉的文件名格式，确认过眼神，这是vue的资源

![](../Images/8a4fde15f73b134d856e73f882044ee7.png)

根据以往的经验，VUE项目的关键代码存在于生成的以app开头的js文件中，所以通常遇到vue项目的目标，只需翻看其app开头的js文件，即可通过其内容大致了解到它的功能点。

![](../Images/546885d9ee0335e25579b4db7387a4fb.png)

于是打开那个app开头的js文件，我个人是非常喜欢将js代码粘贴到Pycharm里面，然后按 Ctrl + Alt + L 来格式化代码，再慢慢的审阅寻找线索。

经过仔细的查看js代码，发现一处疑似后台主页的跳转url

![](../Images/838f52440f163bbdb419c8d5c852c083.png)

直接粘贴至浏览器打开，进到了一个后台页面

![](../Images/61b1ff4537910e8930a5841ea1edb292.png)

在熟悉它里面的功能点时，发现这只是一个框架页面，跟后端交互获取数据时仍需要验证用户身份

于是我灵机一动，猜测 url的company\_id提交的可能就是用户凭证，所以直接在Pycharm使用字符串查找功能查找，没想到真的找到了一串md5值，看起来像是凭证，大喜之后将其补上到url后再访问

![](../Images/597c8c59a5142069f10753a9e209ce2d.png)

![](../Images/3f844a2eab70ab8078c7daefb02335a6.png)

获得了一个用户身份的后台（看右边的成员和部门那里已经与前面不同）  

![](../Images/887d261858de2df8b850db7f6463253d.png)

但继续摸功能点后，发现只是个测试用户的身份

![](../Images/cb74ef278ced23b4232f489723fc9258.png)

找到一处上传点，但是上传过去发现没有数据包响应

![](../Images/d42c5300269cac8a30843c5860b08857.png)

于是查看浏览器控制台信息，发现是被同源策略给限制了，那么这里通过功能点直接上传是行不通的，除非你通过他的域名访问，我这里反查了ip查不到对应的域名

![](../Images/0081dc3029bd2c207ce6ea27691e2072.png)

这个时候可以手动构造文件上传表单， 然后浏览器打开上传

![](../Images/32ece9daec6aa8d9aa4718840d12e6fd.png)

发包过去之后，是我天真了

![](../Images/57aaffb654fa4354e4cc278dbb6a1ff2.png)

报了一个404回来，开始怀疑人生当中，不过后面想了想，我刚才访问的是82端口，提交上传的接口是8082端口，难不成这里面有问题？本着死磕到底的精神，我颤抖的手敲了敲键盘，在burp的重放功能那将8082端口改为了82端口，再尝试发包

![](../Images/beb1ce605b9f0130aff0de5a69f42abe.png)

回包果真不一样了，貌似是被后端接受了，但是却没有返回上传成功的文件路径，我怀疑是没有上传成功

![](../Images/210083cd6bcc113f3aba7657d872c226.png)

于是掏出了我的大\*，不对，是我的祖传字典，用于测试上传文件对象的键名

![](../Images/8d8a810a5cc763e8812b4c4ff958545a.png)

我晕，原来上传的文件对象键名就是 file

![](../Images/648f0fcb97447ed65d1daae279f97acd.png)

将文件字典键名改为file, 文件名改为 .jsp后缀再上传，成功上传了

![](../Images/0a5765d48c5347f55ad88ab010a47855.png)

于是赶紧上传个冰蝎的webshell,发现被拦了，难不成存在waf ？

![](../Images/b480aed721938c1ecd450a0d2170b7f7.png)

![](../Images/8fb71afac65f20417ea496011571cb43.png)

那么先上传个打印字符串的短小代码，发现上传成功了也顺利访问了可是却不解析？？？

![](../Images/8cf7f61d1c634a7f68d727166178ba60.png)

我尼玛直接怀疑人生，这不是tomcat应用服务器吗，怎么可能不解析jsp

![](../Images/929e0d6bc6c5778d938dfad92e71cee0.png)

后面在测试其他文件名时，

![](../Images/32f84130ddff33f27e8e9b6e231f19ee.png)

发现解析php，这就离谱，tomcat + php还有这种搭配？麻烦搞懂的朋友告诉我

![](../Images/e927cf825d0ec365fb34f26c0b554d41.png)

![](../Images/24ea839061f785371a6d4a3ffca38c47.png)

蚁剑链接之，发现是 apache权限，内核3.10

![](../Images/4b9a4d05547e77256a3877fac5d2b85c.png)

其实这个时候通常都是上代理打内网的了，不过后面遇到了更诡异的事，我上传了frp 客户端做代理时，发现连接到服务端后几十秒就断了，再查看文件时，权限已经变成了 000

![](../Images/1129c12d9d7d05498b1b236a808a1db2.png)

看来是应该有某种防护软件？这是块硬骨头啊

![](../Images/586481d4f1da72b5edbe5186408d0fe4.png)

然后开始打算提权，一般提权通用性比较高的就是内核提权，但是不太建议这种提权方式，因为溢出类的内核提权都有一定的偶然性，容易把服务器打宕机

查看了下进程，很惊喜的发现python 以root权限运行了一个程序，有着django开发经验的我一眼就看出了这就是django,

![](../Images/371720115f33be70d0215e32b69432d0.png)

然后访问其8000端口，是一个 swagger 接口页面。

![](../Images/24e3804b5c1d0e3d690b1c1f88b08b45.png)

这时随便访问个不存在的路由

![](../Images/c5e99e6ea4ff9048dd5af30f0b17e219.png)

通过报错信息得知这真的是django，并且开起了debug功能，开启后修改源代码会自动重启应用

![](../Images/f469e47826ac6791148a1f2b3511ab1d.png)

心中大喜直接奔去寻找这个django项目的目录，很巧的是项目目录里的所有文件都具有777的权限，所以能改写视图函数，我添加了红框中的代码，大致意思就是当访问 test/ 路由时，返回字符串 “Hello Django”

![](../Images/10b17ae11e6e76e132a6c64d3f1b42c6.png)

再去浏览器访问 test 路由，成功执行了我自定义的视图函数

![](../Images/519ad667d51649cb06c226a926b4e918.png)

于是这时候 python 版的webshell就出来了

![](../Images/4839781b490f667dfa55e696c99a0b53.png)

去查看执行效果，ok提权成功

![](../Images/af6fdf8539bbcda3e5f69a061bdc382a.png)

当我开始漫游时，问题又出现了，应该是流量特征太明显被 waf 拦了

![](../Images/ed21e027b0303ebd4df3cf113600a7ff.png)

![](../Images/6921f6c1f5a07af6b30297c3b7a85280.png)

然后我又把视图函数改了下，添加base64编码传输

![](../Images/0b3270dd7de3a14c7c72d26be1ddbde4.png)

完美

![](../Images/7614bcbc8d577842f29ffecde93bb14b.png)

随便几行代码写了个方便点的利用工具

![](../Images/bcc94a1d1c5faf1c744a914c52ed552d.png)

本次外网打点到此结束，如有打码不严请勿复现

![](../Images/48d9c906443613a33811e2d2e6cf27c6.png)![](../Images/bafb0a02e258fabc527d81540257dffa.png "虚线阴影分割线")
