# 【技术分享】对利用了微软签名文件的Sigloader分析

** 前期提要**

在日常看威胁情报中发现一种利用Microsoft数字签名DLL文件的恶意软件，并且查询了披露出来的ioc信息发现没有杀软报毒，遂进行了分析。报告链接（https://www.lac.co.jp/lacwatch/report/20210521\_002618.html）

![](../Images/9ddc2727772d09e3d0ff82d8f8f6d357.png)

![](../Images/31727c7478ee980d3bb25c5b5d88af42.png "报告中的IOC")

![](../Images/28cd2ec9a40ee5cda9340662bcd20e94.png "查询的IOC")

 

**样本概要**

我从中选取了1个loader（1E750c5cf5c68443b17c15f4aac4d794）跟1个滥用微软签名的有效载荷文件（2F2E724DD7D726D34B3F2CFAD92E6F9A）

Loader就是一个没有签名的dll

![](../Images/3c515c5f4263bb47619ed14a283bfb61.png "Loader")

查看带有载荷的文件，发现确实有微软签名，但是文件有做过修改原始文件应该是UXLibRes.dll

![](../Images/c1b1b7975497fda25fbac2ca70c13e2d.png)

![](../Images/09f64e385e543709ab4af185a5169079.png "含有签名的载荷文件")

 

**样本分析**

Loader的主要的功能实现就是sub\_180001858函数，跟进这个函数

![](../Images/c4278f83859600dcdceed9fd23b7e55e.png)

sub\_180001858函数首先获取当前进程的默认堆的句柄，然后从堆中分配一块分配0x58字节的内存并初始化为0，然后调用了一个解密函数传入加密函数的地址以及函数名称的长度作为参数进行解密，解密出的函数如下

![](../Images/be26b9e3a2cecf7ca506433019ef5380.png)

![](../Images/cc90448224e0e7a31d2569a5bd24c4b5.png)

解密函数主要就是传入了秘钥随机数以及加密数据，加密数据长度进行计算

![](../Images/ee55ca7a7ebadc3f2c85b8cb175a1146.png)

![](../Images/1e29d5778477e713bcef9da9a4002256.png)

进行了循环判断堆指针指向的值是否为空

![](../Images/82767984b7dd1ca3af66b75e45f1563c.png)

进入sub\_180001000函数首先就有个if判断里面有2个判断条件，第一个是判断datalen-1的值是否小于等于0xEA,datalen-1值为0x4d第一个成立第二个是利用了RtlcomputerCrc32函数对datalen+4地址的数据块进行crc32计算，算出来的值与dword\_1800168EC保存的数据进行比较验证数据块是否正常。Crc计算出来的值包括数据长度这些已经硬编码在数据块中

![](../Images/4f310c1a1769e60ada5069ddfc18787c.png)

![](../Images/e410a1de23896985dc8194cc1f9de8c6.png)

还是调用相同的解密函数传入秘钥随机值加密数据加密数据的长度进行解密

![](../Images/156da8abfea0cf4810cad768e11fb63e.png)

![](../Images/c750c1e7d056a1f0cbeb06afae494e05.png)

datalen解密前的数据

![](../Images/15b1b5816f396d66634d3fe49c6d4b25.png)

datalen解密后的数据可以看到KBDTAM131.DLL字符串已经出来了

![](../Images/12a3c26f4c75ac21f24760e7644f4fdf.png)

分配新的堆空间heapPointer\_1

![](../Images/c0c072643c1af6032dcffbcf6e006fe6.png)

判断datalen数据块的长度满足就进行数据拷贝，拷贝了24个字节到新分配的堆空间

![](../Images/1846459e227c27b06d31ea5bd2d2c3b8.png)

![](../Images/ad9f80eef97c55b454a92e9112e78887.png)

新分配了一块堆空间heapPointer\_2用来存放KBOTAM131.DLL字符串

![](../Images/339b1fcc5a646ac2791e3cb49fa6709a.png)

![](../Images/28258a78bb23e747d68faed5f1452403.png)

将KBOTAM131.DLL后面的所有数据拷贝到堆空间heapPointer\_1中

![](../Images/e660ccc444ae4dd3acf0e3a96ce3453e.png)

![](../Images/d1206ef7fbd076756d7305bd14e9b592.png)sub\_180001000函数主要就是解密了datalen数据块然后将数据块的值拷贝新的2个堆空间中  
解密后的datalen数据块

![](../Images/20916d17520a58892c78d531eef3ef30.png)

堆1原始数据

![](../Images/08a1080225f5bdb587df9160fb707b0c.png)

拷贝后堆1数据

![](../Images/ae9068f2194934b89f3a268850504ef3.png)

堆2原始数据

![](../Images/8c93df99763c04fb6cc182b28a7a9e0a.png)

拷贝后的堆2数据

![](../Images/031feee813691916ef4c9d91a529a1b1.png)

sub\_180001000函数执行返回后就是对新开辟的堆1偏移16的空间的值判断是否数据已经解密并且修改，然后获取了新EtwEventWrite函数的地址然后通过VirtualProtect修改内存属性修改了函数的前4个字节。

![](../Images/805ae7da4ba4b6b136fdf88db2bb5e4c.png)

![](../Images/5813c8486ce8724b2e34dc56255549ca.png)

![](../Images/3af79f4704642b9f68d8231c32ed2832.png)

然后继续根据堆1偏移4的值来判断用户名是否是system，这里由于值为0该判断条件里面的内容并未执行

![](../Images/84cc6f917bff7f9e9065db518af9d547.png)

然后又对堆1偏移8的值进行了判断条件是或由于第一个条件值为0直接执行了下面的函数并未调用CreateMutex函数，CreateMutex函数跟进去如下图所示

![](../Images/14f13c305543ba701c884a582c28d4ea.png)

![](../Images/dbac2d7559a1189499a85b6f87c9788c.png)

下面就是主要的loader的执行方式了，通过DecodeData读取并解密含有载荷的有微软签名的dll然后申请内存空间创建线程执行

![](../Images/619eb531e3534bcd04c472b20ffa681f.png)

跟进DecodeData函数里面一开始是判断堆1偏移20的空间的值是否为0，这里是为0的没执行获取当前模块名字的函数，然后执行else传递堆1偏移24空间地址里面的值，该值正好是堆2空间的指针，从堆2中获取KBDTAM131.DLL并设置为当前环境变量然后通过获取当前模块名称，并通过一系列路径的操作函数来拼接出KBDTAM131.DLL的绝对路径

![](../Images/542d4a90c60926ea618d63e5503e9c54.png)

![](../Images/78c2d2b7363ab896ff6222d54fa5e46e.png)

![](../Images/f5b5a566408f8bf56b119c057a4fdd5c.png)

![](../Images/3aa71d9a86d68227d639dd4775822c6f.png)

这里主要就是打开带微软签名的文件然后读取里面文件偏移为0x2E10的地方读取0x3F00字节的数据，读取出来后存到新的堆空间堆3中.这里又可以发现最开始解密出来的堆1空间里面的偏移32代表了读取载荷的大小也就是0x3fa00,偏移36代表了载荷的偏移位置. 2个地址的数据相加来判断恶意签名文件大小

![](../Images/3827fef0490b9aef49a7161c20a71425.png)

![](../Images/a5f11875203d578d9a12e4c181af217b.png)

继续使用之前的解密算法传入了密钥，,堆1偏移44的地址，微软签名文件中读取的加密载荷,载荷的长度进行运算

![](../Images/23b658b2c4bd0a6719da1b53fac5620b.png)

![](../Images/1e086f77a8a33188fb2aa4dfb383c8e8.png)

![](../Images/b556772207c471ad9d84f7b3014fe37b.png)

然后又使用RtlcomputerCrc32对解密出来的数据进行计算然后与硬编码在堆1空间偏移40地址的值进行比较，我这里是校验不通过的可能是loader跟载荷文件不对应导致的可以修改zf标志位来绕过校验返回1就可以了

![](../Images/694f0becb6eae240aec9a22126fdb42e.png)

![](../Images/b477fba079197e1d682d635d18749aca.png)

![](../Images/94ce8913abe8a033c8acf48b5c1ba1e3.png)

解密后的文件简单看了下是CS的beacon反射加载dll,ioc与报告中一致

![](../Images/b1aeea28786be4b58eae11e1717ecb13.png)

![](../Images/baf6a1e7c34831f0a89cbc7957400da9.png)

![](../Images/93416c0ba04e6a3b77dea45e61766228.png)  
主线程后续会判断堆1偏移12里面的值来进行自删除的操作删除最外层的loader

![](../Images/b7885088fff8ce2064b91b1c8b2795c8.png)

![](../Images/b285a5eeced0ce6a3449b459ebecb9da.png)

 

**总结**该loader的加载方式并不复杂,读取带有微软签名的载荷文件解密创建线程执行，loader本身也是被各大厂商查杀，只是拥有白签名的载荷确实能躲避大部分杀软的查杀。
