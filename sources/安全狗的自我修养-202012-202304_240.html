Shellcode 是现代恶意软件的主要组件之一。它最初是为了利用漏洞并在目标进程上运行代码而发明的。最近，它更多地被用作恶意软件组件来破坏简单的检测和分析。在APT攻击中使用的多阶段，高度混淆的shellcode是非常常见的。

尽管有很多很好的静态和动态分析工具和服务可用于观察恶意软件行为，但某些恶意软件可能具有一些仅在特殊条件下才会显现的隐藏行为。一些恶意软件可能会检查虚拟环境的存在。需要工具来更深入地分析这些威胁。

在本文中，我们想讨论一种使用仿真框架分析 shellcode 威胁的方法。

方法：使用内存工件

这里介绍的方法是使用内存工件作为 shellcode 仿真的基础。Shellcode 本质上是位置独立的，并且在大多数情况下对每个进程的特定环境是中立的。许多模拟 shellcode 的实现依赖于内置的内存结构。但是，理论上所有必要的内存组件都可以通过进程转储镜像轻松获得。相关的内存结构，如 TEB/PEB、加载的模块映像列表甚至 DLL 代码都应该驻留在进程镜像中。

ShellCodeEmulator是使用 Unicorn 框架进行仿真并使用 Windows 进程转储图像作为内存工件源的框架。

目标Shellcode

为了演示这种方法的工作原理，这里有一个非常简单的 Windows x64 shellcode 示例，其 SHA1 哈希值为 33312f916c5904670f6c3b624b43516e87ebb9e3。

PEB 访问

shellcode最重要的部分是访问PEB结构的部分。PEB 是一个进程环境块，其中存储了与进程相关的信息。PEB 通过 'gs:[rdx]' 内存位置访问。'rdx' 设置为 0x60，GS:60 是 PEB 指针所在的位置。

“Ldr”指针具有以下数据结构，它包含有关加载的 DLL 模块的信息。通过这种结构，您可以访问 DLL 的基地址。该结构的“InLoadOrderModuleList”成员具有已加载模块的链表。

基本上，shellcode 依赖于 PEB.ldr 结构遍历来定位 API。在这种情况下，它将检索第一个模块的基地址（通常是 kernel32），并通过比较 API 哈希值找到 WinExec API 的位置。最终，shellcode 将通过调用检索到的 API 指针来运行外部进程 (calc.exe)。

GDT（全局描述符表）和独角兽框架

为 shellcode 提供执行环境的第一个挑战是构建虚拟 FS/GS 分段。在 Unicorn 框架上，您需要构建虚拟 GDT 整体。并且每个条目的选择器值需要写入每个段寄存器。

下面显示了 GDT 条目的结构。您需要为具有适当值的每个段创建此条目。

从gdt.py中，GDT 入口构建代码如下所示。

class Layout:
    def create_gdt_entry(self, base, limit, access, flags):        gdt_entry = limit & 0xffff        gdt_entry |= (base & 0xffffff) << 16        gdt_entry |= (access & 0xff) << 40        gdt_entry |= ((limit >> 16) & 0xf) << 48        gdt_entry |= (flags & 0xff) << 52        gdt_entry |= ((base >> 24) & 0xff) << 56        return struct.pack('<Q',gdt_entry)


完整的 GDT 构建代码如下所示。基本上，它使用 create_gdt_entry 来构建每个 GDT 条目并将 GDT 条目索引值分配给每个段，并将选择器值写入每个段寄存器。

def setup(self, gdt_addr = 0x80043000, gdt_limit = 0x1000, gdt_entry_size = 0x8,                 fs_base = None, fs_limit = None, gs_base = None, gs_limit = None, segment_limit = 0xffffffff):        gdt_entries = [self.create_gdt_entry(0,0,0,0) for i in range(0x34)]                if fs_base != None and fs_limit != None:            gdt_entries[self.fs_index] = self.create_gdt_entry(fs_base, fs_limit , A_PRESENT | A_DATA | A_DATA_WRITABLE | A_PRIV_0 | A_DIR_CON_BIT, F_PROT_32)        else:            gdt_entries[self.fs_index] = self.create_gdt_entry(0, segment_limit, A_PRESENT | A_DATA | A_DATA_WRITABLE | A_PRIV_3 | A_DIR_CON_BIT, F_PROT_32)
        if gs_base != None and gs_limit != None:            gdt_entries[self.gs_index] = self.create_gdt_entry(gs_base, gs_limit, A_PRESENT | A_DATA | A_DATA_WRITABLE | A_PRIV_3 | A_DIR_CON_BIT, F_PROT_32)        else:            gdt_entries[self.gs_index] = self.create_gdt_entry(0, segment_limit, A_PRESENT | A_DATA | A_DATA_WRITABLE | A_PRIV_3 | A_DIR_CON_BIT, F_PROT_32)
        gdt_entries[self.ds_index] = self.create_gdt_entry(0, segment_limit, A_PRESENT | A_DATA | A_DATA_WRITABLE | A_PRIV_3 | A_DIR_CON_BIT, F_PROT_32)        gdt_entries[self.cs_index] = self.create_gdt_entry(0, segment_limit, A_PRESENT | A_CODE | A_CODE_READABLE | A_PRIV_3 | A_EXEC | A_DIR_CON_BIT, F_PROT_32)        gdt_entries[self.ss_index] = self.create_gdt_entry(0, segment_limit, A_PRESENT | A_DATA | A_DATA_WRITABLE | A_PRIV_0 | A_DIR_CON_BIT, F_PROT_32)
        self.emulator.memory.map(gdt_addr, gdt_limit)        for idx, value in enumerate(gdt_entries):            offset = idx * gdt_entry_size            self.emulator.memory.write_memory(gdt_addr + offset, value)                self.emulator.register.write_register(UC_X86_REG_GDTR, (0, gdt_addr, len(gdt_entries) * gdt_entry_size-1, 0x0))        self.emulator.register.write_register(UC_X86_REG_FS, self.create_selector(self.fs_index, S_GDT | S_PRIV_0))        self.emulator.register.write_register(UC_X86_REG_GS, self.create_selector(self.gs_index, S_GDT | S_PRIV_3))        self.emulator.register.write_register(UC_X86_REG_DS, self.create_selector(self.ds_index, S_GDT | S_PRIV_3))        self.emulator.register.write_register(UC_X86_REG_CS, self.create_selector(self.cs_index, S_GDT | S_PRIV_3))        self.emulator.register.write_register(UC_X86_REG_SS, self.create_selector(self.ss_index, S_GDT | S_PRIV_0))


过程映像

现在 shellcode 模拟的基本要求已经完成，下一步是从进程转储映像中提供适当的内存数据。只需从 notepad.exe 获取内存转储即可。如果 shellcode 检查特定进程的进程名称或进程环境，您可能希望对这些进程进行转储。它将为仿真提供更具体的内存环境。例如，使用 Process Explorer 从 64 位 notepad.exe 获取内存转储并将其保存为 notepad64.dmp。

ShellcodeEmulator 使用 PyKD 从进程转储映像中解析和提取适当的组件。提取的组件包括 PEB 和 LDR 结构以及加载的 DLL。当 shellcode 从 DLL 调用某些 API 时，将模拟提取内存中的代码。您可以为 shellcode 将运行的潜在 API 放置代码执行钩子，以观察和修改行为。如果您不拦截任何 API 调用，最终仿真将在遇到系统调用指令时停止。目前 ShellcodeEmulator 还没有为系统调用指令提供仿真层。

Shellcode模拟器

您需要在装有 Python 3.x 的系统上安装 git。

pip install git+https://github.com/ohjeongwook/ShellCodeEmulator


ShellCodeEmulator 依赖于windbgtool，您可以使用以下命令进行安装。

pip install git+https://github.com/ohjeongwook/windbgtool --upgrade

用法

安装后，你可以提供'-d' 提供进程转储映像文件名的选项。

ShellcodeEmulator 的当前实现侧重于用于 Windows shellcode 的非常常见的 API，但它可以通过修改代码轻松扩展。

结论

ShellcodeEmulator 是一个基本框架，可以轻松扩展以支持多种不同类型的 shellcode 仿真。因为它不依赖硬编码的 PEB 或模型结构，您可以轻松地为不同的 shellcode 设置不同的内存环境。一些 shellcode 可能需要一个特殊的环境，您可以通过提供与配置文件匹配的适当内存转储轻松地提供环境。广泛的 API 仿真仍在进行中，但作为一种研究工具，它很容易使用，可以作为仿真的一个很好的例子，Unicorn 框架可以应用于现实生活中的防御分析工作。
