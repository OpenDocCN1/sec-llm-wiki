    我们回顾下其它注入方式(需要其它注入源码可以直接联系作者。)，比如在windows用户层中用远程线程注入方式来讲，原理是首先在进程中远程申请一块可以读写执行的内存空间，然后把我们要注入的模块或者路径(取决于是否有实体文件。)写到这段内存中，然后开一个远程线程把线程的入口指向这块地址的首地址。在windows内核中也可以这么实现，毕竟上层的api在内核中肯定有对应的底层接口(上层只是封装而已)。

    然而我这里讲的是在linux内核中实现模块注入，在linux中肯定有也类似的远程线程注入，但是这里不讲这种，讲的是另一种思路修改RIP指向。

    具体思路是，先在被注入的进程中同样申请一段可以读写执行的内存空间，然后把模块路径名称保存到这段空间中(这里用的是有实体文件方式注入)，到这里我们先把这个被注入的进程挂起备份寄存器，最后我们把rip指向我们的loader函数，最后恢复进程执行。

    loader函数可以是自己实现的so加载器，也可以直接调用现成的函数，我这里就是用的现成的loader函数(__libc_dlopen_mode通过符合查找得到)。

    开始实现代码逻辑，由于用的是驱动所以最好写一个控制接口(学习linux驱动开发教程可以联系作者。)，代码如下:

long device_ioctl(struct file *f, unsigned int cmd, unsigned long arg) {    long status = SUCCESS;    switch (cmd)    {    case IOCTL_INJECT:         status = inject_so(arg);        break;        default:        status = SUCCESS;        break;    }
}

查找__libc_dlopen_mode函数地址，这里得解析elf文件格式，代码如下：

void* get_symbol_address(struct task_struct* task, void* module_base_address, const char* symbol_name) {    Elf64_Ehdr elf_header;    unsigned long dynamic_tables;    unsigned long symbol_string_table;    unsigned long symbol_table;    void* symbol_address;    ssize_t result;    unsigned long offset = (unsigned long)module_base_address;
    result = mem_read(task, (char*)&elf_header, sizeof(Elf64_Ehdr), offset);    if (sizeof(Elf64_Ehdr) != result) {        return NULL;    }    offset += elf_header.e_phoff;    result = get_dynamic_section(task, elf_header.e_phnum, (unsigned long)module_base_address, offset, &dynamic_tables);    if (SUCCESS != result) {        return NULL;    }        symbol_string_table = (unsigned long)get_dynamic_table(task, DT_STRTAB, dynamic_tables);    symbol_table = (unsigned long)get_dynamic_table(task, DT_SYMTAB, dynamic_tables);
    if (NULL == (void*)symbol_table || NULL == (void*)symbol_string_table) {        return NULL;    }    symbol_address = find_symbol(task, symbol_string_table, symbol_table, symbol_name);    if (NULL == symbol_address) {        return NULL;    }    return symbol_address + (unsigned long)module_base_address;}
