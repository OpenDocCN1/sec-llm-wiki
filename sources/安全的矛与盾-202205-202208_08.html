前言

大家都知道jsp中可以用\uxxxx或者\uuuuuuxxxx这种格式来对恶意代码进行混淆，并且还可以用注释+换行unicode的方式进行恶意代码的逃逸。那么是什么造成了这种情况呢，带着问题我们从Javac层面看一看原因是什么。

搭建Javac调试环境

使用源码来调试的原因主要是源码里有变量名以及注释等，方便理解。

git clone https://github.com/arthur-zhang/javac-source-code-reading

解决办法是手动把tools.jar加为库文件

支持变形Unicode的原因

在源码中进行一番查找，我们可以找到解析unicode编码的地方在 com.sun.tools.javac.parser.UnicodeReader#convertUnicode 这里，ch是当前扫描的字符，bp是当前扫描到的位置，unicodeConversionBp是用来记录上一个unicode的位置。关键步骤的作用已经在代码中给出：

protected void convertUnicode() {        if (ch == '\\' && unicodeConversionBp != bp) {//当前字符是'\'且不是上一个unicode的位置            bp++; ch = buf[bp];//读取下一个字符            if (ch == 'u') {                do {                    bp++; ch = buf[bp];//继续读下一个字符                } while (ch == 'u');//只要'\'的下一个字符是u，就会一直走到while循环                int limit = bp + 3;//记录unicode的最后一个位置                if (limit < buflen) {                    int d = digit(bp, 16);                    int code = d;                    while (bp < limit && d >= 0) {//这里的主要功能是读取\u00xx中xx的内容，并且转为对应的char字符。                        bp++; ch = buf[bp];                        d = digit(bp, 16);                        code = (code << 4) + d;                    }                    if (d >= 0) {                        ch = (char)code;//转为对应的char字符                        unicodeConversionBp = bp;                        return;                    }                }                log.error(bp, "illegal.unicode.esc");            } else {                bp--;                ch = '\\';            }        }    }

因此我们的第一个问题就解决了：能支持\uuuuu这种的原因是javac使用了while循环来扫描，循环的判断逻辑是只要\的后面是u就会一直往下读取。

注释+换行绕过的原因

还有一种利用姿势是用 //+\u000d换行的写法进行代码的逃逸，如下面这个例子：

public class test {    public static void main(String[] args) throws Exception {        //\u000djava.lang.Runtime.getRuntime().exec("whoami");    }}

表面上java.lang.Runtime.getRuntime().exec("whoami");是在注释符的后面无法执行，但实际上由于前面存在\u000d转义字符，导致后面的代码逃逸了出来。实际编译的时候是下面的代码形式：

public class test {    public static void main(String[] args) throws Exception {        //        java.lang.Runtime.getRuntime().exec("whoami");    }}

javac后的class文件也可以印证我们的说法

至于为什么这样可以绕过呢，javac对于注释的核心处理代码在这里 com.sun.tools.javac.parser.JavaTokenizer#readToken

可以看到这里也进入了一个do while的循环：只要当前的ch!=CR或者LF或者没有读取到最大长度都会继续读取，最后把pos跟bp之间的字符都当作注释。这里的pos是进入token读取之前记录的一个起始值。其中我们代码中用到的\u000d也就是CR，关于token读取过程中一些特殊的字符解释如下：

public interface LayoutCharacters {
    /** Tabulator column increment.     */    final static int TabInc = 8;
    /** Standard indentation for subdiagnostics     */    final static int DiagInc = 4;
    /** Standard indentation for additional diagnostic lines     */    final static int DetailsInc = 2;
    /** Tabulator character.     */    final static byte TAB   = 0x9;
    /** Line feed character.     */    final static byte LF    = 0xA;
    /** Form feed character.     */    final static byte FF    = 0xC;
    /** Carriage return character.     */    final static byte CR    = 0xD;
    /** End of input character.  Used as a sentinel to denote the     *  character one beyond the last defined character in a     *  source file.     */    final static byte EOI   = 0x1A;}

那么为什么这里的换行可以是一个unicode转义过后的换行，而非一个真正的换行呢？接着往下看，代码会走到com.sun.tools.javac.parser.UnicodeReader#scanCommentChar 

protected void scanCommentChar() {        this.scanChar();        if (this.ch == '\\') {            if (this.peekChar() == '\\' && !this.isUnicode()) {                this.skipChar();            } else {                this.convertUnicode();            }        }
    }

又调用了com.sun.tools.javac.parser.UnicodeReader#scanChar

protected void scanChar() {        if (this.bp < this.buflen) {            this.ch = this.buf[++this.bp];            if (this.ch == '\\') {//如果为\开头则进行unicode转换                this.convertUnicode();            }        }
    }

我们可以看到，Javac在扫描字符的时候，底层只提供最后转换的结果，并不会告诉上层这个char到底是真正的一个字符还是从unicode转过来的。所以绕过的原因也就很清楚了：Javac在读取注释的过程中会判断下一个字符是否是CR回车字符，而不会判断这个回车到底是从Unicode转过来的还是真正的一个回车符号，所以就产生了恶意代码的逃逸。debug过后可以看到我们的comment里面到换行就加了个0x1a结束了，没有把恶意代码计入到注释里面。

一个奇怪的发现

在瞎几把摸索之后，发现了一个奇怪的现象 在//\u000d后面随便加一个\uabcd

public class test {    public static void main(String[] args) throws Exception {        java.lang.Runtime.getRuntime().                //\u000d\uabcdexec("whoami");    }}

直接用javac解析会报错，这个当然是符合预期的



<%    Runtime.getRuntime().            //\u000d\uabcdexec("calc");%>

在jsp下面居然成功解析了？？

一开始是以为java版本的原因，后来换到了同样的版本还是不太一样。又去找了一下jsp翻译过后的java文件，tomcat也没有做特殊的处理。
