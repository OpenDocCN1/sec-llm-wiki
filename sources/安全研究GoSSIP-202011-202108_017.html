今天上午的课程由清华大学计算机系的白家驹老师带来，白老师的研究方向为系统软件可靠性、操作系统和程序分析，具体利用动态分析和静态分析技术来自动检测系统软件的缺陷。在操作系统和系统安全会议和期刊上已发表20余篇学术论文，包括ACM TOCS、ACM ASPLOS、USENIX ATC和USENIX Security等顶级会议和期刊。其研究团队所设计的程序分析工具，在主流操作系统（包括Linux、FreeBSD和Zephyr等）中发现了数千个真实缺陷，并在华为、蚂蚁金服和腾讯等公司中得到实际部署和使用，在缺陷检测方面效果良好。

作为一名非常Geek的研究人员，白老师从典型的系统软件（内核、数据集、驱动等）出发，引出fuzz工具在系统软件方面的相关挑战，并针对其中两个挑战（怎么去fuzz异常处理代码，以及如何去fuzz协议栈）进行了详细的阐述。对于异常处理代码方面的fuzzing，具有输入异常和偶发异常两种类型，分别与用户输入空间和系统状态资源相关联。白老师团队通过调研发现，目前fuzz工具在异常处理代码方面，对检测偶发异常类型的漏洞存在不足。对于现存的fuzz工具，在利用软件异常注入的时候，大多采用是上下文不敏感（context-insensitive）的方式，这就存在一个问题：在特定的一些上下文中会遗漏bug。因此，白老师团队基于上下文敏感的软件异常注入，提出了名为FIFUZZ的工具，在实验的效果和可扩展性上的表现都不错。

然后，白老师介绍了针对TCP协议栈的fuzz工作，指出在TCP协议栈中，考虑到其复杂性，导致执行过程中容易出错，会出现很多的异常并需要做相应处理。其中TCP协议栈中常见的bug包括内存bug和语义bug两类。经过调研发现，目前的工具在语义bug的检测上表现欠佳，其主要原因是：1）现存的fuzz工具只能生产数据包或者系统调用来测试（要么数据包，要么syscall），没有考虑两者的依赖关系，或者只有简单的关系。2）现存的fuzz工具利用代码覆盖去找覆盖的状态，但是没有考虑状态的迁移顺序。3）没有对语义规则做过多的考虑。因此白老师团队提出的fuzz工具首先考虑到了数据依赖的问题，在输入的序列当中基于数据依赖的方法对序列中的各项（数据包和syscall）做变异操作（增删改替换）。然后提出了基于数据迁移的fuzzing方案，记录变化前后的代码状态覆盖信息，利用差分的方法得出数据的迁移方向。最后利用差分测试方法测试语义，其思想是不同的TCP协议栈在处理相同输入时，应当给出一致或相似的输出。

最后，白老师介绍了他们研究团队目前正在研究的相关方向，包括并发的fuzzing，分布式系统或者分布式系统协议的fuzz、QUIC协议栈的fuzzing，Robotic software fuzzing等。

下午的课程来自两名G.O.S.S.I.P成员——来自中科大的吕云龙和来自蜚语安全的方屹，他们为大家带来的是名为《追踪非标准内存破坏漏洞》的课程。首先，吕云龙总结了静态分析发现漏洞的两种常见方法：基于成对关系的挖掘和基于函数语义的挖掘，但这两种方法的存在着无法揭露结构体信息，以及对于非标准内存函数，无法基于成对关系的假设的问题。因此他们打破了成对检查的方法，提出了NLP-assisted function Identification：通过函数原型推断出函数的功能，其中，函数原型对应的功能有三：简易性、可行性和鲁棒性；他们使用了自然语言处理的方法，提取出候选函数；并进行数据流跟踪，得到函数摘要，生成函数表征；最后，基于函数摘要，完成漏洞检测。在实验部分，他们选择了内核态和用户态的程序进行检测，并有较高的准确率，能够发现多个问题。

接下来，方屹为大家准备了一堂非常实际的动手课程，如何利用CSA（Clang Static Analyzer）这个开源的带符号执行引擎的静态分析工具来编写自己的代码缺陷检查工具。CSA基于clang，用于分析C/C++/Objective-C代码，可以检测代码中的安全问题。分析目标在于为函数建立扩展图，并在扩展图基础上搜索目标程序属性。方屹在课程中介绍了CSA的检查器Checker——符号执行的客户端，将符号执行的结果发送给Cheker进行分析，并带大家尝试使用Checker，如何使用Checker检测非标内存破坏。
