今天给大家推荐的是一篇来自USENIX Security 2021的关于漏洞检测的文章--"Static Detection of Unsafe DMA Accesses in Device Drivers"。

直接内存访问（Direct Memory Access，DMA）是提高硬件I/O性能的常用方法，并在现有设备驱动中广泛应用。本文作者发现以下两种情况DMA访问是不安全的：

  1. 如果没有正确对数据进行同步，存储在CPU cache与硬件寄存器的缓冲区数据可能会不一致，进而导致非预期的硬件行为（不一致DMA访问）

  2. 恶意或者不受信任的硬件设备可以向系统内存写入恶意数据，当驱动未经正确验证使用数据时，可能会触发安全问题（缓冲区溢出或者非法指针访问）（未检查的DMA访问）

本文作者设计了一种静态分析方法，并实现了名为SADA的检测工具，以自动和精确的检测设备驱动中上述不安全DMA访问的问题。作者使用5.6版本的Linux代码对SADA进行了实验评估，并且发现了284处不安全DMA访问。其中121处可以触发buffer overflow，36处可以触发非法指针访问进而造成任意内存读写。作者将其报告Linux驱动开发者，其中的105个已经被确认。

DMA buffer可以分为两种：

  1. Coherent DMA buffer：CPU和硬件设备同时可以访问buffer，一般存在于整个驱动的生命期，无需在代码逻辑中同步数据。但是存储在特定的memory（cache-coherent）中。

  2. Streaming DMA buffer：CPU和硬件设备无法同时访问buffer，一般是动态映射或者取消映射。硬件和CPU cache存储的数据可能是不一致的，需要在代码逻辑中进行数据同步。

其简要流程如下：

  1. 根据DMA buffer mapping（or allocation）函数，定位存储DMA buffer的变量（大多位于结构体中）。利用成员变量敏感的别名分析来定位所有的DMA buffer变量别名，同时记录其对应的结构体以及成员变量。

  2. 针对不一致DMA访问，SADA会根据代码上下文来检测DMA buffer是否同步；针对未检查DMA访问，SADA使用静态污点分析来检查被访问数据是否会对数据流或者控制流产生不安全影响。对于两种模式，记录打破规则的代码路径。

  3. 利用Z3作为SMT solver，验证第2步记录的代码路径可达性。具体方法为逐指令翻译为Z3语句，遇到分支添加约束。对于未检查访问，会分别根据具体模式添加触发bug的约束。最终有解即表示路径可达。
