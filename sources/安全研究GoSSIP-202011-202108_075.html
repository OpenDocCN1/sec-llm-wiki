Session 5A: Fuzzing

One Engine to Fuzz ’em All: Generic Language Processor Testing with Semantic Validation

来自佐治亚理工学院的研究人员提出并实现了针对多种程序语言处理器的通用fuzz框架PolyGlot。通过将PloyGlot用于针对9种程序语言的21个语言处理器，作者发现了173个新的bug，其中18个获得了CVE，113个已得到修复。

程序语言处理器的角色是将开发者编写的高级语言转换为机器代码，该过程需要保证源代码和编译后代码的语义一致性。但由于语言处理器中存在的bug，可能会将正确的源代码转换为故障代码，导致安全漏洞。本文作者研究的fuzz就是针对程序语言处理器的bug。

如图1所示，编译过程包括前端的语法解析和后端的语义行为，对应地，这两阶段会分别进行语法检查和语义检查。在fuzz过程中，只有通过语法与语义检查的测试用例才是有意义的。现有fuzzer，或是着眼于语法正确性而导致缺乏语义正确性，或是只针对单一语言进行语义检查导致难以迁移。

本文的研究则是要设计通用的fuzzing框架，使得能够针对不同的语言处理器生成语法与语义正确的测试用例。作者设计的PloyGlot结构如图3所示，以BNF语法、语义注释和种子作为输入，将源代码翻译为中间语言IR，然后在IR级别进行变异，接着修复其中的语义错误，最后运行得到的测试用例。整个过程中包含了两个亮点：

  1. 设计了一个IR来中和不同程序语言的差异，将特定语言的语法和语义特征转换为通用形式；

  2. 为了实现生成的高级语言的有效性，作者设计了constrained mutation和semantic validation两种技术。前者基于输入的语法来进行变异，后者在变异的基础上进行增量式的语义检查，即修复变异部分的潜在语义错误。

详细的设计和实现不予以展开，接着来看评估过程。除了开头提到的bug发现情况，作者还对fuzz的性能指标进行了测试。通过将PolyGlot与三个通用的fuzzer（AFL、QSYM和Nautilus）、两个特定语言的fuzzer（针对C的CSmith和针对JavaScript的DIE）进行比较，作者得到了以下图表的数据。结果显示，PloyGlot在bug类型的覆盖、测试用例的正确性和代码覆盖率这三方面都有显著优势。

STOCHFUZZ: Sound and Cost-effective Fuzzing of Stripped Binaries by Incremental and Stochastic Rewriting

对没有符号信息的binary进行Fuzzing非常困难。现有的技术要么依赖于硬件和昂贵的动态二进制翻译引擎(比如qemu)，要么做出不切实际的假设(比如二进制文件中没有内联数据)。本文提出STOCHFUZZ，生成不同版本的重写二进制程序，然后通过模糊测试来判断重写的有效性，该过程最终收敛于正确重写的二进制程序上。

STOCHFUZZ的结构如上图所示，由五个组件组成：

  1. 概率分析器：概率分析器计算给定二进制文件中每个地址是数据还是指令的概率

  2. 增量和随机重写器：重写器根据计算出的概率通过采样以不同形式重写二进制程序。

  3. 程序分派器：程序分派器选择一个重写的版本执行，要么针对正常的执行请求随机执行，或者从策略上考虑根本原因诊断

  4. 执行引擎：执行引擎是AFL的变体，执行给定的二进制文件并监视崩溃

  5. 崩溃分析器：如果崩溃是有意的，将会触发增量重写，否则，将分析根本原因，如果是重写错误就将会自动修复。

在STOCHFUZZ中会对二进制文件进行重写，如果是最开始的hlt指令导致的段错误，那么就认为是还没有进行反汇编或者重写的代码区域，把这种crash认为是有意的，就会进行增量重写。由重写导致的错误或者程序中的潜在错误被认为是无意的crash，遇到这种crash之后STOCHFUZZ将会清除不确定的重写然后观察崩溃是否消失来确定是否由重写错误引起，如果是的话会进行重写的修复。

另外，STOCHFUZZ的概率分析器也设定了一系列的规则用来计算某个地址是数据还是指令的概率。

在实验评估部分，本文采取了Google Fuzzing Test Suite(FTS)测试套件和包含了内联数据的FTS套件变形，以及为了和RetroWrite对比设置了满足RetroWrite的条件的测试环境。

在FTS套件中，STOCHFUZZ比afl-qemu、ptfuzzer、e9patch、ddisasm有更高的可靠性，后四者都存在失败的情况。

并且发现bug的时间也在大多数情况下与afl-gcc可比。表现了STOCHFUZZ的稳健性和有效性。

在有内联数据的测试条件下，STOCHFUZZ仍然有与afl-gcc可比的性能，虽然因为处理一些重写错误会导致效率降低一些。

并且在RetroWrite的无内联数据，包含符号等测试条件下，STOCHFUZZ也与RetroWrite有相似的表现。

NTFUZZ: Enabling Type-Aware Kernel Fuzzing on Windows with Static Binary Analysis

kernel fuzzing通常会利用系统调用的类型信息。由于Windows的系统调用大多是私有的且没有官方文档，利用类型信息方法对Windows kernel fuzzing并不奏效。
本文作者针对上述问题，实现了一个自动推断系统调用类型信息的静态分析工具，并在此基础上实现了名为NTFUZZ的类型感知的针对Windows kernel fuzzing框架。利用此框架，作者发现了11个新的的kernel bug。

简化的Windows架构如图所示，系统进程和用户应用会通过一系列API来调用syscall与kernel通信，其中就包括文档未记录的API。作者观察到，虽然有大量的syscall没有文档记载，但是这些syscall会通过已知的系统API，通过内部的函数调用链最终调用。因此可以通过静态分析，从已知的系统API分析推测未知syscall的类型信息。
下图可以很好的说明问题，NtUserRegisterWindowMessage是未知的系统API，而RegisterWindowMessage是有文档记录的系统API。通过RegisterWindowMessage我们可以推断NtUserRegisterWindowMessage的参数为UNICODE_STRING*类型，且利用此信息可以构造输入使len为奇数进而绕过对指针范围的检查。

作者实现的NTFUZZ的架构如下图所示，整个框架分静态分析器和kernel fuzzer两部分。

框架的输入为windows kernel相关的DLL以及已知的API以及其类型信息。静态分析器的前端会将输入的DLL转化为中间表示，并在此基础上生成控制流图。已知API的类型信息也会在这一阶段进行解析。

由于Windows Kernel巨大的代码量，对其进行全内核分析是一项巨大的挑战。作者实现了模块化的分析方法以应对此挑战。
具体来讲，框架会按模块对输入的DLL进行划分，并在分析过程中记录function summary（类型信息以及内存状态）以保证分析结果的复用。

利用modular analysis的结果，类型推断阶段对syscall的参数类型进行推断，主要是针对结构体类型和数组类型进行推断。
静态分析阶段生成的syscall相关类型信息会传递给kernel fuzzer的syscall mutator，以生成合法的包含各类syscall的测试用例。针对syscall的类型信息，框架的mutator分别对整数、字符串、Handler、结构体、数组、指针等不同数据类型采取了不同的突变策略，并利用hooking-based fuzzing技术进行fuzzing。

kernel crash会导致windows蓝屏，因此作者通过在windows vm crash创建内存dump来收集crash信息；此外fuzzer会存储最近使用的syscall payload，结合两者可以轻易的复现crash。

Fingerprinting the Fingerprinters: Learning to Detect Browser Fingerprinting Behaviors

主流浏览器通过禁止第三方cookies来防止有状态的追踪，对于不透明并且无状态的追踪，例如fingerprinting，也采取了一些缓解的措施。然而这些措施都不能保证在不损害用户体验的情况下达到很高的检测精度。所以本文提出了FP-INSPECTOR，一个基于机器学习方法的browser fingerprinting检测器，其结构如下：

之前的防御方法：随机化方法，标准化方法，启发式方法都有其局限性，而作者的FP-INSPECTOR解决了这些问题。

  • 自动学习fingerprinting脚本的新出现的属性，而不是手动构造的启发式方法。

  • 同时利用静态特征（脚本语义）和动态特征（脚本执行）。

具体实现：

  • 通过OpenWPM收集脚本内容和执行路径。

  • 从AST中提取静态特征。

  • 记录每个脚本访问每个APIs的次数，以及参数和返回值。

  • 使用top-1K特征作为输入，训练决策树分类器。

作者爬取了17,629个网站，用FP-INSPECTOR来进行训练。结果如下：

基于静态特征训练的模型可以达到99.8%的准确率，85.5%的召回率，基于动态特征的模型可以达到99.9%的准确率和96.7%的召回率。

对于检测到的网站，作者实现了以下对抗策略：

  • 限制所有脚本对fingerprinting APIs的访问。

  • 限制检测到的fingerprinting脚本对fingerprinting APIs访问。

  • 阻止对fingerprinting脚本所在域的下载请求。

  • 在第三点中排除掉第一方脚本和内联脚本。

并评估了不同策略对网站的损害：

利用FP-INSPECTOR，作者分析了top-100K网站的fingerprinting的使用情况，发现fingerprinting的使用一直在增长，在top-10K的网站中超过了1/4，并且fingerprinting在新网站中更加流行。

8B: Network Security

Cross Layer Attacks and How to Use Them (for DNS Cache Poisoning, Device Tracking and More)

Linux内核中广泛使用了伪随机数发生器（PRNG）并且这些使用通常是跨层次的——比如UDP端口生成算法、IPv6流标签生成算法和IPv4ID生成算法。本文作者研究和分析发现，在Linux内核中使用的PRNG存在薄弱环节，因此攻击者可以对内核进行“跨层攻击”。在这些攻击中，可以实现从一个OSI分层推断PRNG的内部状态，并且使用它来预测其他OSI层使用的PRNG的值，或者也可以将其与从其他协议推断的PRNG的内部状态相关联起来。

作者运用这种方法，就可以实施一个非常有效的针对Linux的DNS缓存中毒攻击。通过收集IPv6的流标签值，或者UDP源端口、或是IPv4的IP ID值，重建内部PRNG状态，然后预测DNS查询的UDP端口，就可以实现3000倍到6000倍加速的DNS投毒攻击。这种攻击可以远程工作，也可以跨Linux用户和容器在本地安装，也可以使用任意DNS记录来毒害DNS stub服务器的缓存。

针对DNS stub服务器攻击的主要步骤：

  1. 攻击者学习目标服务器中PRNG的核心状态。可以通过收集一定数量的UDP数据包或是IPv4，IPv6的相关标签获得。

  2. 攻击者预测下一次DNS查询将要使用到的UDP端口。

  3. 攻击者强制目标机器向攻击者的域发起DNS查询，然后攻击者为预测的查询发送一组欺骗的DNS答案。

  4. 当攻击者的欺骗DNS答案先于递归解析器所提供的正确值达到，那么错误的DNS记录将被stub服务器所接收并缓存下来。

8C: Smart Contracts

SGUARD: Towards Fixing Vulnerable Smart Contracts Automatically

由于区块链不可篡改的特性，使得其上的存在漏洞的智能合约不可修补，如何在其部署前修补漏洞就成为了解决问题的关键。本文作者提出了一种工具，在智能合约运行时对其进行自动化检查，可以确保针对智能合约中4种常见的漏洞进行修补，其安全性是可证明的。作者的实验表明，本文提出的工具在所增加的时间开销（14.79%）和费用开销（0.79%）也非常的少。

本文针对的4种常见漏洞

  • 算术溢出漏洞

  • 单一函数重入攻击漏洞

  • 跨函数重入攻击漏洞

  • tx.origin利用漏洞

工具工作流程

  • 枚举符号执行信息：为了能够找到所有的漏洞，首先需要系统地产生最大范围的符号执行信息（最后一个符号执行操作必须是REVERT, INVALID, SELFDESTRUCT, RETURN, 或者是 STOP）。在遇到循环的情况（包括递归函数），本文给出了一种方法，确定出循环的上界值，并证明了该上界值足够支撑找到本文所提出的4中常见漏洞。

  • 依赖分析：此步骤根据上述枚举过程得到的符号执行信息，分析出每个符号执行操作之间的依赖关系，用于后续对合约漏洞的检测。

  • 合约修复：根据文章对4种漏洞模式定义的符号执行依赖信息，以及上一步的执行结果，找到存在漏洞的合约，并对其进行修复。

本文选取了存在源码的5000个智能合约进行分析。实验平台为 Intel Core i9-9900，64GB内存，操作系统为Ubuntu 16.04.6 LTS。

Compositional Security for Reentrant Applications

智能合约中出现的问题带来了毁灭性的影响。这也警醒了我们，到目前为止我们还不知道怎么可以在存在危险代码的情况下，使得合约的组件依旧是安全的。重入攻击的出现也使得信息流控制方案失效。

本文提出了一种普遍的重入攻击定义形式，引入了一种安全类型系统，以此来确保可以存在安全的重入代码。由于本系统结合了执行过程动态分析机制，即使在存在未知代码的情况下，也能可证明地强制了重入安全性。与此同时，本文的方案还有助于定位和纠正一些常见的漏洞。

9A: Vulnerabilities

HackEd: A Pedagogical Analysis of Online Vulnerability Discovery Exercises

相信我们的读者对CTF并不陌生，甚至很多是非常厉害的CTFer，笔者相信在成长为一名厉害的CTFer的过程，肯定少不了在靶场上进行了大量的训练。

在IEEE S&P 2021的论文“HackEd: A Pedagogical Analysis of Online Vulnerability Discovery Exercises”中，作者对黑客练习平台（hacking exercise）进行了研究。

作者首先提出了以下两个问题：

目前可用的练习是否适用科学文献中建议的一般教学原则?如果有，这些原则是如何实现的?
练习的组织者是怎样考虑实施哪些原则?
为了回答上面的问题，作者进行了一项两阶段的研究:对流行的在线练习进行定性检查，并对这些平台的组织者进行采访。对于第一个问题，作者选择了5个核心的教学原则：与学生先验知识的来联系（connecting to learners’ prior knowledge），组织陈述性知识（organizing declarative knowledge），主动练习和反馈（active practice and feedback），鼓励元认知学习（encouraging metacognitive learning），以及建立支持性和协作性的学习环境（collaborative learning environment）。对于第二个问题，作者联系了31个练习平台的组织者。

  • 没有一个练习平台贯彻了所有的教学原则 ，大多数平台通过练习来达到原则，有些则通过创造性的方式来达到。

  • 许多练习不提供结构来帮助学生组织知识，或反馈来指导他们通过学习目标的进步。很少有组织者考虑过元认知，即帮助学生从更高的角度考虑他们学了什么和学了多少。

9B: Wireless and Electromagnetic Channels

Method Confusion Attack on Bluetooth Pairing

本文作者发现了蓝牙配对机制中的一个设计缺陷，能够让攻击者使用不同的方法干扰原来要进行配对的两台设备，而在交互时受害设备不会意识到这种方法混乱（Method Confusion）攻击。与其他攻击相比，该攻击即使在蓝牙最高安全模式中也可以实现，并且无法在协议实现中解决。通过该攻击，攻击者能够渗透到受害者的安全连接中，并拦截所有流量！！！作者将该攻击成功应用于多个场景中，实现了端到端的PoC，并使用了手机、智能手表、银行设备来进行测试，均能够在用户未察觉的情况下攻击成功。
