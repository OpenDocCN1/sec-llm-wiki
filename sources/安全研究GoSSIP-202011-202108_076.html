Session 1A: Software Security 1

When Function Signature Recovery Meets Compiler Optimization

这篇论文讨论了编译器代码优化对反汇编分析过程中函数签名（function signature）的识别产生的（正面与负面并存）的影响。

在二进制代码的控制流图（CFG）分析中，识别间接调用（indirect call）往往是分析的难点，如果无法准确找到所有的调用关系，对控制流完整性（CFI）的实现就难以做到尽善尽美。一些已有的工作（如TypeArmor）在二进制代码上对函数的调用约定（call convention）进行分析并生成函数签名，为caller和callee寻找配对关系。

为了研究编译器优化对基于函数签名的识别工作的影响，本文的作者详细分析了编译器存在的8类对函数签名的改变，其中包括对使用stack还是使用register来进行参数传递的识别的影响，对特定寄存器的使用的误判。

详细内容请阅读：G.O.S.S.I.P 学术论文推荐 2020-09-24 。

Session 1B: Mobile Security 1

Android Custom Permissions Demystified: From Privilege Escalation to Design Shortcomings

作者评估了Android的自定义权限模型，并开发了一个Fuzzing工具CUPERFUZZER发现特权提升漏洞。在Android9/10的Pixel 2的手机上，CUPERFUZZER在进行了40,195次模糊测试后找到了2,384个成功的exploit例子。

作者认为Android的自定义权限模型有4个缺陷，只要恶意应用能够成功攻破任意的缺陷，就可以在用户不能感知的情况下获得dangerous级别的权限。

CUPERFUZZER的设计如图2所示，包括5个主要步骤。

  1. Seed Generation

    作者首先生成一组种子应用，申请了所有dangerous和system级别的系统权限，同时定义或者请求自定义权限。自定义权限的定义包含不同属性：1）权限名；2）权限级别；3）权限组。

  2. Test Case Construction

    随机执行应用安装，应用卸载，应用升级，系统升级操作，这四种操作都可能触发系统更新赋权状态，过程如图3所示，其中因为目标是检测最新版本的系统问题，所以OS update只能执行一次。


  1. Test Case Execution

使用adb实现四种操作，使用PC控制多台测试设备实现并行测试。

  1. Effective Case Checking

使用adb查看测试应用被赋予的权限，检查是否出现以下两种情况：

  • 测试应用在用户不能感知的情况下被赋予了dangerous级别权限。

  • 测试应用被赋予了signature级别的权限，但与权限定义的应用使用不同的证书进行签名。

  1. Critical Path Extraction

对于有效的测试用例，CUPERFUZZER通过以下几步提取关键路径：

1）测试用例分类，每类用例导致同一个权限被赋予。

2）查找关键路径，修剪开始和结束的操作寻找最短路径。

3）删除重复路径。

得到关键路径后进行人工分析。

作者对总共30个关键路径进行了分析，发现了4种缺陷。

  • DS#1 Dangling custom permission（CVE-2021-0307）

    normal或者signature级别的自定义权限定义在被删除后，申请权限应用权限授予状态不会删除，如果有另一个应用重新定义了这个权限可能会造成特权提升。

  • DS#2 Inconsistent permission-group mapping (CVE-2020-0418)

    system和自定义权限以来不同的源来获取<permission, group>映射关系，攻击者可以利用不一致从而在用户没有感知的情况下获取dangerous权限。

  • DS#3 Custom permission elevating（CVE-2021-0306）

    系统在覆盖自定义权限时（更改所有者），权限授予状态没有撤销。对于Android 9中为normal权限的应用如果在Android 10中变成了dangerous应用仍然可以继续使用，不需要动态请求，例如ACTIVITY_RECOGNITION。

  • DS#4: Inconsistent permission definition（CVE-2021-0317）

    当一个normal或者signature级别的自定义权限被升级为dangerous级别后重启设备，在原始级别下申请权限的应用可以自动获取升级后的权限。

How Did That Get In My Phone? Unwanted App Distribution on Android Devices

恶意开发人员可能会将unwanted apps分发给大量用户。作者使用unwanted apps来联合指代恶意软件（例如，勒索软件，银行木马）和unwanted app（PUP）（例如，广告软件，流氓软件）。
但是，安全社区对如何分发unwanted apps缺乏全局了解。作者研究了unwanted apps如何分发到用户设备中，作者希望这项发现能推动未来的防御，激发人们对保护Play市场的进一步研究。

数据集
作者使用表I中汇总的两个主要数据集。来自安全供应商的信誉日志包含有关Android设备上的应用程序的信息，以及它们之间的父子安装关系。作者查询VirusTotal（VT）以获得AV标签，以进行unwanted app分类。这些日志是从安全供应商的客户正在使用的真实设备中收集的,涵盖了从2019年6月1日至2019年9月30日的四个月。


数据集包含243个国家/地区代码中的设备和来自3K多家设备供应商的设备。


作者在VirusTotal（VT）中查询APK的哈希值。作者将VT报告中的AV标签用作unwanted apps标识和分类的输入。

方法：

  1. 获取父信息：对于每个安装事件，作者扫描该设备4个月内的所有信誉查询，并提取那些查询包名称与安装事件中的父级相对应的APK。

  2. 识别平台密钥：作者首先从AOSP存储库中获取65个软件包名称的列表，然后，在信誉日志中搜索满足特定属性的密钥。对于每个候选密钥，确定由密钥签名的前10个数据包。

  3. 安装者分类：作者将安装程序手动分为与分发媒介相对应的12类：官方Play市场，替代市场，浏览器，商业PPI，备份和还原，IM，主题商店，文件管理器，文件共享应用，bloatware，移动设备管理（MDM）和软件包安装程序。

Session 2B: Cyber Risk and Abuse

SoK: Quantifying Cyber Risk

作者介绍了一种受结构方程模型（structural equation modeling）启发的因果模型(casual model)，该模型用自反性指示器(reflexive indicators)测量潜在因素来解释网络风险结果。本文目标在于系统化量化网络风险的认识。风险评估能够证实多余的资源应被用作缓解措施还是指导灾后响应。

图2表示受安全性和暴露影响的威胁级别和预期危害之间的关系。符号E(+)表示正相关，暴露越多，威胁和伤害之间的联系就越紧密，而S(-)表示负相关。许多研究设计未能考虑到所有这三个变量。将安全建模为潜在变量latent variables，连接噪音、可观测的指示器到高层概念。


虽然图2描述了理想的研究设计，但像S(-)这样的关系仍然可以代表由显性变量（manifest variables）组成的统计模型，其中安全或威胁等变量被认为是直接可测量的。很少有研究直接将安全干预与危害结果联系起来。引入调解因素：妥协（compromise），它可能会也可能不会导致损害。
图3展示了使用SEM符号的拓展模型。


表1给出了量化网络损害的实证方法概览。数据泄露和股市反应受到了最多的研究关注。随着时间的推移，市场反应变得不那么消极了。表2显示了许多关于数据泄露的矛盾结果，这取决于数据如何被分割和分析方法。对于数据泄露研究记录数量的分布并没有转移到财务成本的分布上。少数研究对财务成本进行了量化，发现典型的网络风险比非网络损失更小、更轻。对公司和个体的调查揭示的危害估计不那么惊人。


表3总结了系统化。第一列显示了相应研究中探索的关系，图表的第一块主要是“传统”安全研究，使用了相对较短的样本窗口。这可以与危害研究(第二组)形成对比，后者利用第三方汇总的数据库探索纵向趋势。


本文对网络危害评估和安全干预有效性的实证研究进行了系统化。受结构方程模型的启发，作者引入了一个模型，利用潜在的安全因素，暴露和威胁来解释安全结果。将该模型应用于风险缓解研究表明，威胁级别常常被省略。暴露指标对网络风险结果具有较好的解释力。没有控制这两个因素的统计测试会导致虚假的结果。
此外，企业不应低估不必要的风险。在降低风险方面，应忽略承诺简单解决方案(单一指标解释)的供应商，并为安全团队配备资源，以专注于避免网络危害的任务的多样性。政策制定者的注意力应该从一般的损失转移到我们完全不了解的系统性风险上。

Session 3A: Hardware Attacks

CacheOut: Leaking Data on Intel CPUs via Cache Evictions

这是一篇关于cache侧信道攻击的文章。文章中提出了一种新的针对Intel处理器的cache timing攻击方案：CacheOut。其实，相关作者早在2019年10月就向Intel通报了这项新发现，而Intel方面也对此攻击方案给予了认可，并为其分配了CVE编号：CVE-2020-0549，将其称为L1 Data Eviction Sampling (L1DES)漏洞。最终，Intel方面于2020年6月9日发布了用于缓解CacheOut攻击的微代码。从这些可以看出，该攻击具备相当的现实威胁性。

与此前备受关注的RIDL、Fallout、ZombieLoad等攻击相同，CacheOut也借助了CPU的Line Fill Buffer（LFB）来完成攻击。Line Fill Buffer用于处理L1-D cache、L2 cache和物理核之间的数据传输，如下图所示。


当物理核需要数据时，物理核会并行查询LFB和L1-D cache，处于两者中任意一者内的数据都是可以被物理核直接访问的。只有当两者均不包含所需数据时，物理核才会向L2 cache请求数据。

与之前提出的cache攻击方法相比，本文作者提出的CacheOut攻击，允许攻击者窃取到整个L1-D cache中的任意特定位置的数据，这也是CacheOut攻击最具威胁性的一点。

具体而言，针对受害者写入数据和读取数据的操作，本文作者设计了不同的攻击流程，如下图所示。


1.针对受害者写入的数据

在受害者向主存写入数据的过程中，受害者的写操作会使被写入数据的L1-D cache line被设置为脏cache line（即数据被修改过，但是相关修改还未同步到下一级存储单位的cache line）。这之后，攻击者可以通过构造驱逐集来将受害者的数据驱逐出L1-D cache。在这种情况下，受害者的数据就需要被写回到L2 cache。本文作者猜测并验证了，此时处理器首先会暂时性地将受害者数据放入LFB中，之后再慢慢地将受害者数据从LFB中写回到L2 cache中。这样，受害者数据就必然会出现在LFB中，攻击者就可以借助针对LFB中数据的攻击方法完成攻击。

值得一提的是，本文作者提到，在驱逐受害者数据之前，可以利用verw指令来清空LFB中的数据，以降低后续攻击过程中的噪声，提高攻击准确度。这使得，最初为了防御侧信道攻击而设计出的verw指令，反过来被用于了侧信道攻击的实施。

2.针对受害者读取的数据

与写操作不同，受害者的读操作不会使某个cache line被标记为脏cache line。因此相关攻击的条件也有所不同。本文作者假定攻击者和受害者分别运行在同一个物理核的两个逻辑核上。在受害者线程读取数据之前，攻击者线程会持续不断地将受害者所读取数据对应的cache line中的数据驱逐出cache。这就会使得，受害者线程在读取数据时出现cache miss，处理器需要从L2 cache或更底层存储单位中取数据。取到数据之后，处理器会首先将数据放入LFB中，之后再慢慢地将受害者数据从LFB写入到L1-D cache中。这样，受害者数据就必然会出现在LFB中，攻击者就可以借助针对LFB中数据的攻击方法完成攻击。

本文作者也进行了实验测试，发现CacheOut能够从受害者的地址空间中窃取到整个4KB页中的全部数据，从而恢复敏感数据以及敏感数据片段之间的相对位置。作者还表示，CacheOut对于OpenSSL、Kernel Address Space Layout Randomization （KASLR）、Hypervisor ASLR、Software Guard Extensions （SGX）也具备威胁性。


Session 4A: IoT Security and Privacy

DIANE: Identifying Fuzzing Triggers in Apps to Generate Under-constrained Inputs for IoT Devices

现有的IoT Fuzzing方法大多是针对应用UI上用户输入相关的函数参数来为IoT设备生成有效的模糊输入，但是这种方法是在从UI获取变量后立即对变量进行变异，一旦应用对输入进行筛选或格式匹配，Fuzzing的有效性就会大大降低。

本文作者针对这种应用端验证代码约束的问题提出并设计了一种新的IoT Fuzzing工具——DIANE，该工具能够分析得到IoT设备配套应用中的fuzzing triggers函数，并以此来生成有效的模糊输入（不受验证代码的约束），从而大大的提高fuzzing的效率。

详细内容请阅读：G.O.S.S.I.P 学术论文推荐 2021-02-02 。

Data Privacy in Trigger-Action Systems

Trigger-action平台（TAPs）允许用户通过连接独立的网络或物联网服务实现自动化的操作，这些平台提供一些简单的接口来帮助终端用户创建触发-计算-动作的规则，并在不同的网络服务中传输数据。


然而，目前TAPs包含一些安全风险，例如不同组件之间敏感数据的明文传输、对数据的不规范操作等。如果相关的组件被损坏，攻击者能够获得成千上万用户的敏感数据。


为了避免这种风险，作者提出了一个隐私增强的TAPs——eTAP。该平台不需要获得用户明文隐私数据或任何计算结果，即可执行相关触发-计算-动作规则，其主要原理是利用混淆电路（garbled circuit）的相关特性来保证相关敏感数据在不受信组件上的处理、传递的安全性。


作者实现了eTAP原型，该平台不仅支持流行平台的常用操作，还支持对敏感触发数据的布尔、算数以及字符串操作，能够成功执行IFTTT前500规则和Zapier平台上93.4%的公开规则。此外，测试结果也表明eTAP对性能的影响不大：平均规则执行延迟增加了70ms(55%)，吞吐量减少59%。
