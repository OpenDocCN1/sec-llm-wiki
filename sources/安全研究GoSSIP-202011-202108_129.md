今天给大家推荐的是一篇来自USENIX Security 2021的论文“An Investigation of the Android Kernel Patch Ecosystem”。

![](../Images/adbeb9f0673d23d2c4f3bbc8b8c71222.png)

Android 系统是一个开源内核生态系统，其包含了大量的漏洞，每周都有针对开源软件(如Linux) 的新安全补丁发布。由于开源软件的多个版本或分支共存（如下图），在这种广泛的重用现象下，安全更新的 patch 从上游 linux 项目通过多层传播到最终用户的终端设备可能会存在严重的时间延迟，此前并没有相关工作对这个问题开展针对性的研究。

![](../Images/ec71f7bc0a621ade7e3cdd97c7a272b2.png)

本文作者对patch在整个Android内核生态系统中的传播行为进行了深入的研究。作者根据Android安全公告确定上游补丁，然后对下游厂商（三星，华为，小米等）各时期的内核进行补丁存在性测试。由于对其内核的公开程度不同，作者将其分成了三类并分别给出了分析方法：  

*   直接提供了 git 存储库。通过 git 存储库提供的内核包含完整的提交历史，可以很容易地在提交日志中定位到其是否更新上游补丁。因为通常他们只是复制提交消息和（或）引用在Android安全公告链接中给出的提交。高通、Nexus和Pixel等内核都属于这一类。
    
*   源代码快照。大多数OEM厂商更喜欢以源代码快照的形式发布他们的内核，而不是提交历史记录。作者通过源代码的函数比较来检查特定的CVE补丁是否在。
    
*   binary 。最常用的OEM内核形式是二进制固件映像。因此，作者选择对patched函数生成签名来测试目标binary中是否存在patch。
    

![](../Images/dbff9372861ff896f0351f56b45622f0.png)

具体来说，作者构建了一个 binary的更新补丁存在性检测工具 ，其原始工作流程如上图所示。它有三个主要步骤:

*   首先分析一个补丁，并确定每个更改点的唯一性，选择几个合适的变化点。
    
*   编译更新补丁后的内核并提取合适的变化点相关指令序列来进行签名生成。
    
*   与目标二进制文件进行签名匹配。
    

最后作者选取了上游数百个CVE补丁，并对数十家厂商的设备内核进行了补丁存在性测试，发现从第一个公开可用的补丁到它在终端设备上的最终应用程序之间的差距通常是几个月甚至几年，这给有经验的黑客留下了一个很大的攻击窗口来利用这些未修补的漏洞。
