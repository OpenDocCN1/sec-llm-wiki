今天推荐的学术论文来自ICSE 2021，是UC Irvine研究人员和著名安全研究团队HexHive的老大Mathias Payer一起完成的关于Android应用中native代码安全更新的调查研究

  

![](../Images/6a2ad0abdc07be6585e47ea22aa3e806.png)

  

在Android生态中，安全更新是一件如家常便饭般的事情，可是大部分应用开发人员和安全研究人员都聚焦在Java代码部分，却忽视了native代码的安全问题的修复。作者从200款流行的Android app中选择了53款存在已知CVE的问题app，并检查了它们从2013年9月到2020年5月期间的安全状况，发现其中14款app一直未能修复存在于native代码中的问题。作者继而提出了一种名为LibRARIAN (LibRAry veRsion IdentificAtioN)的方法，这种方法利用了作者提出的bin^2sim相似性比较测度，可以准确分析出natvie code（library）的版本号，从而发现有问题的代码。

  

![](../Images/db8d069a5ae7e3d11495c59366e3bf67.png)

看上去很简单，让我们仔细看看这个分析方法的细节，其中关键就是这个bin^2sim测度，作者主要关注如下表中列举的一些特征

![](../Images/625b21ceb163fc226e08bd56398faf00.png)

看上去是不是很启发式，还有更启发式的：

![](../Images/0df15d016a2b2f26aab539e0d0507814.png)

基于这些特征，论文中的计算相似度的方法看上去也并不是那么特殊。作为一篇Empirical Study的论文，接下来作者开展了相关的调研：

1.  **RQ1**: Accuracy and effectiveness of LibRARIAN. Can LibRARIAN accurately and effectively identify versions of native libraries? How does LibRARIAN compare against stateof-the-art native-library version identification? How effective are LibRARIAN’s feature types at identifying versions of native libraries? 
    
2.  **RQ2**: Prevalence of outdated libraries. How prevalent are vulnerabilities in native libraries of Android apps? 
    
3.  **RQ3**: Patch response time. After a vulnerability is reported for a third-party library, how quickly do developers apply patches?
    

  

作者首先发现在流行的Android app中，大约每个app拥有11个.so文件也就是native代码库，而某些app拥有超多数量的代码库，例如Instgram在其2013年12月到2020年的所有版本中一共包含了6677个不同版本的.so文件，最多的时候特定版本的Instgram居然包含了141个.so文件！  

  

作者的分析系统对.so文件的分析速度还不错，针对最复杂的libTensorflow库也只用了4分38秒就分析完成。平均来说，LibRARIAN推断出一个库的版本只需要118.19秒，而分析的准确性也是相当不错的：LibRARIAN 对46个不同库的分析表明，针对904个样本的分析结果中有824 (91.15%) 个是正确的，即使是那些不正确的，推断出的版本号和正确版本的差别也很小。作者还说明了一下各项特征对正确推断的贡献：

我们注意到一个细节，作者的LibRARIAN运行在拥有两块AMD EPYC 7551 32-Core CPU和512GB RAM 的Ubuntu 18.04服务器上，看来现在研究人员的硬件军备竞赛也日趋激烈。而G.O.S.S.I.P作为拥有AMD 3990x+256G内存、3970x+256G内存+2080Ti、双Intel Xeon 5122金牌处理器+128G内存三台小当量核武服务器的研究团队，欢迎大家加入我们，充分利用这些硬件资源开展高水平安全研究！
