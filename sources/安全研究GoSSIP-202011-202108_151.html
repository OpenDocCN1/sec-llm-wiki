Session 5A: “Smart” Home

Hey Alexa, is this Skill Safe?: Taking a Closer Look at the Alexa Skill Ecosystem

Amazon Alexa语音助手可以使用户通过语言对话来直接与各种Web服务进行交互，开发人员可以创建可在Alexa上运行的第三方应用（被称为"skill"），然而这其中存在许多安全与隐私问题。本文作者对Alexa skill进行了首次大规模的分析，发现了其中存在一些潜在的漏洞和审计缺陷，这些缺陷使得攻击者能够发布恶意的Alexa技能并欺骗用户，会造成用户隐私信息泄露等后果。

首先，作者描述了Alexa skill的构建过程和审计过程。当用户向一台Alexa-enabled设备发出对话（激活技能）时，语音信息会被传输到Alexa web服务，通过语音识别和自然语言处理技术来识别匹配技能短语；然后，Web服务向注册技能的后端服务器发送包含JSON请求，服务器处理并响应。当开发者想要提交发布一个新的skill时，Amazon也会对该skill的内容进行安全审计。

为了对Alexa技能进行系统性的分析，作者从七个不同国家的Alexa技能库中收集数据，获得了总计90,194个技能，技能的信息包括标题、调用名称、所需权限以及隐私策略链接等。接下来，作者对这些技能进行了半自动化的分析，最终得到了十个方面的结论，其中部分结论如下：

  • Duplicate Skill Invocation Names：作者发现大量技能拥有相同的调用名称，而对于具有相同调用名称的技能，Amazon会自动的从其中选择一个；如果没有匹配到调用名称，Alexa会自动填充请求。因此，由于Amazon没有公开自动选择具有相同调用名称技能的策略，用户很容易激活错误的技能。

  • Registering using Well-known Developer Names：当技能被发布到技能商店中，会显示开发者的名称。但由于Amazon目前没有采用任何自动方法来检测使用第三方商标的侵权行为，攻击者可以使用任意著名的公司名称来发布技能以实现对用户的欺骗。

  • Code Change after Approval：Amazon要求在后端服务器上托管代码，但对于后端代码的更改没有任何限制。因此攻击者可以在审计后更改代码，诱使用户泄露敏感信息。

  • Bypassing the Permission Model：Alexa技能可以请求访问用户隐私信息的权限，用户在激活时对这些技能权限进行授权，但Amazon对隐私信息的检查依赖于权限API声明而不是所请求的数据类型。因此，作者发现存在一些skill能够绕过权限API而直接从终端用户请求这些隐私信息，即攻击者可以直接向用户请求由权限API保护的数据。

  • Common Approaches for Squatting Skills：作者研究了调用名称之间语音相似性对skill squatting的影响，发现了四种常见的squatting技术，包括同音字、标点符号、空格和不同的拼写（包括拼写错误）。

  • Availability of Privacy Policies：Amazon允许开发者提供一个隐私策略链接来显示终端用户的数据如何被收集和使用，但Amazon并不对所有技能都强制要求提供隐私策略，而仅对那些请求访问权限API的技能进行要求。作者经过检测发现在US技能商店中，仅有28.5%的技能提供了隐私策略链接，而其中有2.9%的链接无法访问。

IoTSafe: Enforcing Safety and Security Policy with Real IoT Physical Interaction Discovery

目前智能家居环境中设备之间的物理交互可能会造成两种威胁：1）攻击者可能会通过一些方式来间接触发相关危险操作；2）设备物理交互对环境会有后续影响，可能会导致危险的情形。

本文提出了一种动态安全策略执行系统——IoTSafe，该系统利用静态分析和动态测试技术捕获智能家居环境中设备之间的物理交互，并且能够通过构建的交互流图预测可能发生的危险情形。

作者基于Samsung SmartThings平台实现了IoTSafe原型，并选取了21个应用以及33台（23类）设备部署在测试环境中，对IoTSafe性能进行了评估。此外，作者还提供了两个案例来说明IoTSafe的安全策略执行对于抵御利用物理交互间接攻击的有效性。

Session 5B: Software Defenses

POP and PUSH: Demystifying and Defending against (Mach) Port-oriented Programming

针对XNU kernel的传统攻击通常需要信息泄露和控制流劫持这两类漏洞，即先借助信息泄漏漏洞来解决KASLR，然后借助控制流劫持漏洞去执行ROP gadget。然而，由于PAC的应用，控制流劫持变得很困难，而且要达到越狱的需求，需要在root权限上更进一步。

在漏洞利用的过程中，研究人员开始把目光投向XNU中的进程间通信方式。用户空间的进程可以通过IPC机制，向Mach port（在内核空间由指向ipc_port对象的指针表示）发送消息，来请求一些敏感的服务。由于Mach port对象在内核中是被无条件信任的，因此借助Mach Port的攻击能够进一步获取内核内存的控制权，也就是本文总结的(Mach) Port Object-Oriented Programming (POP)攻击，如图2所示。

这类攻击之前已经在iOS jailbreak中使用了，本文则是先对这类攻击进行了系统的归纳。首先，其条件是存在能用于破坏内核对象的内存破坏漏洞，然后借助图3中的这几个攻击原语一步步提升：

  1. Querying Primitive (QP)：用于打破基于随机化的保护策略，能够借助错误返回值等有限的信息来找到corrupted port对应的handler。

  2. Kernel Memory Read Primitive (RP)：用于获取内核内存读取能力。该原语基于对类型完整性的不充分检查来滥用破坏的端口对象。

  3. Kernel Memory Write Primitive (WP)：依赖RP获得的内核信息，WP原语能够利用伪造的ipc_port对象来修改内核内存。

  4. Privileged Purpose Primitives (PPP)：获取权限向一些特权端口发送消息来得到强力的系统调用。

  5. 其他攻击原语：作者主要讨论了着眼于破坏函数指针的任意代码执行原语ACEP。

借助这五种原语，就能构建POP攻击链。作者文中以用于iOS 10.2越狱的Yalu Exploit为例子进行了POP攻击的具体说明。并进一步地归了模型（可以理解为label、pattern、object、Entry with object的四元组）

对应地，作者提出了Port Ultra-SHield (PUSH) 作为防护，如图7所示。由三部分组成：

  1. POP primitive searcher：根据之前归纳的模型从XNU源码与kernel cache中查找潜在的POP原语；

  2. PUSH policy generator：为Mach port对象采用对应策略从而在特定的Mach系统调用前后保护其完整性；

  3. PUSH checker：用于部署PUSH policy generator，相当于kernel extension。

在评估中，作者对表2的一系列漏洞进行了测试，涵盖了macOS 10.12-10.15和iOS 10-13。其表现用插桩点IPs来表征，并通过case study进行了具体说明。除此之外，也对性能开销进行了测试，只有约2%的额外开销。测试的设备数量相当多，在阿里的40000多台macOS设备上部署了PUSH，结果显示确实能有效防御公开的18个exploit和一个0day exploit，也得到了苹果的致谢。

Detecting Kernel Memory Leaks in Specialized Modules with Ownership Reasoning

针对内核代码的内存泄露检测主要面临以下两个问题：（1）内核不同模块会有其定制的内存管理函数，准确的检测需要对这些函数进行识别；（2）内核中指针的传递涉及复杂且冗长的数据流，准确的检测需要准确推断变量的生命周期以及释放点。
现有的方法无法很好的解决上述问题，检测效果较低。对于上述挑战，本文作者分别针对内存管理函数识别和内存对象所有权推测提出了新的方法，该方法对内核内存泄露的检测取得了较好的效果。

对于内存分配函数的识别，作者观察到大多数分配函数会返回指针并进行null-check，以此为模式并利用额外的规则过滤，得到了内存分配函数的集合。

作者利用内核模块的error-handling特性，通过{alloc, check, release, return}的模式，在代码的出错处理分支将内存释放函数与分配函数进行对应。随后作者分别利用逃逸分析（escape analysis）和消费者检测（consumer detection）来推测内存对象的所有权（即最终负责释放内存的函数）。逃逸分析用来判断内存对象的向上传递（即当前函数不负责对内存释放）；消费者检测用来递归向下推测内存的释放点（即最终“消费”指针的函数）。最终作者通过模式匹配的方式，判断内存对象在其释放点是否被正确释放，以确认是否存在内存泄露。

详细内容请阅读：G.O.S.S.I.P 学术论文推荐 2020-01-12

Session 6A: Fuzzing

Favocado: Fuzzing the Binding Code of JavaScript Engines Using Semantically Correct Test Cases

JavaScript本身不具备如内存管理和文件读取这类必须的底层函数，因此JS运行时系统（Runtime system）在JS引擎中囊括了绑定代码（binding code）部分，如图1所示。该部分能够在具有底层函数功能的原生代码和JS之间创建必要的数据类型。绑定代码必须以严格的安全原则执行翻译过程，以避免原生代码存在的问题被引入到JS中。

作者认为，现有的JS Fuzzer面临的挑战有二：第一，测试用例必须是语义上正确的；第二，模糊测试的输入空间要精简。为了解决这些挑战，作者设计了Favocado方法。

首先，Favocado对接口定义语言（Interface Definition Language，IDL）和API引用进行了语义上的解析。

接下来，Favocado生成了一个带有绑定代码语义信息的JS文件（测试用例生成器），并使用这个JS文件对目标JS运行时系统进行模糊测试。

此外，作者注意到了JS绑定层的一个特性，即DOM对象之间相互隔离，于是作者将整个输入空间划分为多个等价类，而Favocado仅需要在等价类中进行的模糊测试，以此提升效率。

最后，作者验证了Favocado的有效性，实验结果表明，Favocado的性能优于最先进的DOM fuzzer。作者使用Favocado对四个JavaScript运行时系统（Adobe Acrobat Reader、Foxit PDF Reader、Chromium和WebKit）进行了模糊测试，并发现了61个以前未知的bug。其中33个漏洞是安全漏洞。

详细内容请阅读：G.O.S.S.I.P 学术论文推荐 2021-01-29。

WINNIE : Fuzzing Windows Applications with Harness Synthesis and Fast Cloning

现有的Fuzzing主要作用对象为Unix-like系统。针对Windows系统，作者提出三个Fuzzing面临的挑战：第一个是Windows是闭源的系统；第二个是图形化界面的大量使用，而图形化界面需要用户的交互才能继续执行，并且在fuzzing时会耗费大量的时间在初始化界面；第三个是缺乏一个快速的流程克隆机制，大大降低了Fuzzing的速度。

为了绕过GUI，现有的方法是针对程序人工进行extract parsing routine来生成一个可供fuzzing的更小程序即harness。harness的编写通常有四个部分：1.Target discovery；2.Call-sequence recovery；3.Argument recovery；4.Control-flow and data-flow dependence。然而，人工编写的过程也是极其容易出错的。此外，现有的克隆流程对循环执行的要求非常严格，例如不能有内存泄漏或者对全局变量的修改。

在本文中，作者提出了WINNIE系统来克服这些挑战，WINNIE系统包含两个部分：1）半自动的fuzzing harness生成器；2）包含一个fork-server的Windows Fuzzer。

(1) harness generator

这个部分是整篇文章最主要的部分。首先,通过动态分析的方法，追踪主程序和library之间的API call，以及一些关于文件的Windows API，记录他们的调用，参数以及返回值等信息。

然后通过追踪到的动态trace，重新构建CFG，并且从中提取出一些fuzzing target，例如一些可以到达文件操作API的function。

最后是构建一个harness，这个过程包含四个步骤：

  1. Differential analysis，通过输入相同的输入来获得一些信息比如说指针（如果开启了ASLR，每次的地址都会随机化，那么相同的输入但是中间值有变化的可能是指针）和core logic。

  2. Skeleton，确定harness中调用的API以及其中正确的参数顺序。

  3. Reconstruction，通过重建控制流和数据流信息，填入正确的调用参数等并对用户提出一些建议。

  4. Evaluate，进行一些测试，比如去掉一些正确的输入导致crash的harness，以此选择最好的一个harness。

(2) 包含fork-server的fuzzer

对于如何进行fork，作者在会议中并没有进行太多的描述，更多的细节可以在论文中查找。最后的结果就是实现了Windows上的CoW fork。

至于覆盖率的统计，作者通过添加断点在基本块中，统计中断次数来进行覆盖率的统计。

评估部分：

  1. WINNIE可以支持更多的Windows应用。

  2. 在相同时间里，WINNIE有更高的fuzzing覆盖率。

  3. 生成的harness平均只需要人工修改百分之4的代码说明harness generator的有效性，人工修改的主要是callback和struct部分。

  4. 在32个binaries中共发现了61个新的bugs。

Session 7C: Machine Learning Applications

CV-Inspector: Torwards Automating Detection of Adblock Circumvention

在web页面上的广告投放者和一些广告禁用插件之间往往是一种竞争的关系：广告投放者会对投放的广告加一些混淆措施来绕过插件，从而获得更多的广告曝光度来实现盈利；而AdBlockPlus之类的禁用插件通过Filter List Authors主动维护过滤列表，来屏蔽掉尽可能多的广告。

但是对过滤规则的维护需要大量的人力，为了帮助Filter List Authors来识别那些成功绕过插件的广告(CV)，作者设计了CV-Inspector来自动化识别CV。

首先，作者介绍了广告投放者在检测到广告被禁用后的两种混淆措施。当浏览器中的JavaScript代码检测到广告被禁用后，会向广告服务器发送请求，服务器返回对URL或者DOM变异过的广告再重新植入页面中。

而新植入的广告会在HTML源代码、URL请求、DOM结构等方面发生变化，为此作者通过对JavaScript代码进行插桩来收集大量的数据集，通过差分分析提取出所需要的特征，在收集的Ground Truth数据集基础上来训练机器学习模型进行分类。

最后，CV_Inspector在收集的Ground Truth上对CV和NO CV的识别F1-Score分别为89%和94%，在AdBlockPlus的监测数据集上分别能达到80%和99%的准确率。

FlowLens: Enabling Efficient Flow Classification for ML-based Network Security Applications

在现今的安全高速网路上，可编程交换机可以被用来做网络拓扑结构的混淆、过滤钓鱼IP路由、缓解DDOS攻击等。引入机器学习后，通过对统计流量的分析，还可以来检测僵尸网络、隐蔽信道，分析IOT的行为等。

但是因为可编程交换机的内存限制(~100Mb)和数据包实时发送的需求，导致我们并不能在交换机上存储许多的数据，能在交换机上执行的额外指令数量也受到限制。所以，在可编程交换机上收集数据包分布变得额外困难。

为此，作者设计了FlowLens，通过在交换机上获得数据包分布的压缩表示，在交换机硬件上收集流标记，并对不同的应用配置不同的流标记器，从而获得当前网络流量分布。

作者将FlowLens应用到了隐蔽信道检测、网站指纹绘制、僵尸网络检测三个任务上，实验结果表明FlowLens在仅略微牺牲准确性的前提下，能够大幅度的提升可编程交换机对流规模的分析，对于隐蔽信道检测流规模的提升更是达到了150倍以上。

PrivacyFlash Pro: Automating Privacy Policy Generation for Mobile Apps

由于GDPR、CCPA之类的数据保护的法律存在，移动app的开发者需要知道他们是否需要以及如何写一份关于自己app的privacy policy文件。先前的方法（例如lubenda、TermFeed、Termly）完全采用问卷的形式来帮助开发者生成privacy policy文件，但是如果这些生成器对问题的描述不完全，那么会导致最后生成的隐私保护政策也是不完全或者错误的。

为了更清晰的展示现有privacy policy生成器存在的一些问题，针对95个app中的7项隐私权限，作者对现有的方法生成的privacy policy的正确性进行了调研。以Location权限为例子，仅18%的app是使用了这项权限并在policy中进行公开的，6%的app因为第三方库的原因不知道是否使用但进行了公开，21%的app并没有使用此权限但进行了公开。

于是作者通过代码静态分析+问卷的形式来帮助app的开发者自动生成privacy policy。其工作流程图如下所示：PrivacyFlash Pro是一个基于浏览器的桌面端软件，在本地来分析swift源代码和第三方库，使用PLIST权限字符串来识别出权限相关API，最后让开发者完成一个调查问卷来生成privacy policy。

最后作者在40个app上对权限API进行了检测，结果中没有误报且只有少量的漏报，说明了此方法对权限API检测的精确性。此外，作者还调研了40位ios开发者对PrivacyFlash Pro的使用满意度，31个人认为易于使用，6个人认为和其他的软件差不多，3个人认为更难使用。
