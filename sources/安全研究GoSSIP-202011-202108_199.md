# G.O.S.S.I.P 学术论文推荐 2020-12-28

今天给大家推荐的是来自加州大学河滨分校论文，对Android kernel patch的生态问题进行了研究，文章被Usenix Security 2021录用。

![](../Images/2282f3248286d47a91fc051990c41821.png)

大家还记得11月份我们推荐的发表在CCS‘ 2020上的PDiff的工作吗？那篇工作通过借助代码相似度分析的方法来进行kernel patch的存在性测试，在评估阶段，PDiff与钱志云老师发表在Usenix Security 2018上的针对二进制代码的补丁存在性测试工作FIBER进行了比较。  

  

今天这篇文章同样是出自钱志云老师的实验室，对Android内核生态系统中的补丁传播行为进行了深入研究，其中也对曾经的FIBER工作进行了改进。

  

![](../Images/c3a8affac1cc499f29f5a40306caf2d8.png)

图1为我们描绘了安卓内核生态的层次结构：Linux mainline及其LTS branch、Google Android、高通等SoC厂商维护的Android和最底层的OEM厂商维护的内核。这种多级上下游之间的重用，会使得上游通过多层到终端设备的补丁传播存在严重延迟，导致攻击面的产生。  

![](../Images/41ad08d47623f44e2f5d0897c154868e.png)

本文针对三种公开的kernel类型（分别是git仓库、源码快照和二进制代码）进行了补丁存在性测试，流程如图2所示：  

1.  首先crawler从Google的安卓安全公告中抓取内核相关的CVE信息，包括CVE编号、补丁commit及对应的仓库。然后locator在git repo这类的kernel中尝试定位patch，也就是去遍历所有的commit来做匹配。
    
2.  tracker在上一步中收集patched function的所有可能版本，用于源码快照和二进制代码的分析。作者选取了高通的repo作为reference kernel，对其mainline分支进行追踪（因为mainline上的漏洞最先patch而且具有普遍性）。接着，matcher在源代码级别进行严格的字符串匹配
    
3.  最后，作者对二进制层面的kernel进行分析。本文构建了FIBER的改进版本，其原始工作流程如图3所示。主要包括三个步骤：首先分析补丁，检查每个change site的唯一性并选取其中合适的用于签名生成 ；然后FIBER编译内核，并提取代表这些change site语义的相关指令序列作为签名；最后FIBER将签名与目标二进制文件进行匹配。考虑到patched function会随着时间而发展，但FIBER仅选择其初始版本来生成签名，因此作者借助前面的tracker来识别patched function的多个版本。
    
      
    
    ![](../Images/5f55f5872ce69b2e73d7172d2f8f993d.png)
    

  

接着来看评估部分。作者收集了表1所示的3个级别的上游内核，包括8个最受欢迎的Android品牌、涵盖26种手机型号和701个内核实例，另外还收集了表2所示的402个CVE。这一套方法的准确率还是不错的（见表3），也得到了很多有意思的结果。

![](../Images/ba1cc8f737b86b68d9501f0afb5012a5.png)

![](../Images/3ffd109888aabb2d004c082eb5d335ef.png)

![](../Images/e1968b7b92cbac97f6b0d783f58b714e.png)

结果显示近一半的CVE在上游公开提交原始补丁后约200天后才在OEM设备上进行了修补，其中10％至30％的CVE甚至延迟了一年以上的时间。这种延长实际上还是由于整个生态中安全漏洞的知识缺失与信息传播的逐级延迟，另外下游kernel的定制化设计使得上游的补丁不能直接采用。这些原因在PDiff工作中也有说到，不过本文花了大量篇幅去展开论证。  

  

最后稍作总结，这篇文章并非“技术向”地去解决补丁存在性测试中的问题，而是系统地应用补丁存在性测试来对安卓内核生态进行调查。实际上本文中困难的技术部分基本就是沿用之前的FIBER工作来对二进制kernel进行分析，但是通过对整个安卓内核生态垂直结构、三类内核公开形式的系统性探索，令人眼前一亮，工作量也还是相当大的，能体现实验室长期的研究积累。
