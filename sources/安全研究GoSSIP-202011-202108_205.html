今天给大家推荐的论文，是来自SEEMOO实验室的针对蓝牙的wireless fuzzing研究论文，发表于Usenix Security 2020，相关代码已在GitHub上开源并收获了258个star。

蓝牙相关的安全研究我们之前也推荐过不少，比如针对BLE配对过程的Downgrade Attack等，大多偏向人工去发现实现过程中的缺陷。但是蓝牙的固件通常是闭源的，因此对蓝牙的over-the-air fuzzing是主流的自动化检测技术。这种over-the-air方式的缺陷是显而易见的：速度受限、可重复性有限、调试能力受限。


于是作者提出了Frankenstein（大概是“科学怪人”的意思吧）这个fuzzing框架，其亮点在于它是基于firmware emulation的。我觉得作者pre的slide里的这张图更方便我们理解固件仿真的fuzzing，如下图，实际上就是对物理设备取了快照，然后在QEMU中仿真来进行full stack的fuzz。仿真固件实现线程和任务切换，以fuzz多个处理程序，并附到Linux主机上。

这种仿真的好处是由虚拟的调制解调器来提供over-the-air data，也就是图中的fake IO，可以从stdin中直接读入wireless frame。而且仿真环境可以输出调试信息，比如上图中的terminal输出。


接着，我们再把攻击模型以及漏洞加上，就得到了图1，我们来简要介绍其中两种有趣的攻击：

  1. Link Key Extraction：在初始配对过程中两个设备会协商一个link key用于后续安全的连接，而芯片本身除ROM外没有永久存储，因此由主机存储所有连接的link key。攻击者可以在Broadcom芯片中hook reply函数来将link key复制到全局设备名称变量；

  2. 由蓝牙芯片影响Wi-Fi芯片造成kernel panic（CVE-2019-15063）：Wi-Fi和蓝牙被合并在同一芯片中，尽管每个协议在单独的ARM内核上运行，但是它们共享收发器的一部分，有一个通用的接口来传达他们的需求，作者提出的攻击则利用它来持续关闭Wi-Fi。

回到仿真的设计上，Frankenstein通过hook来获取所需的快照。由于快照是没有符号的原始二进制文件，作者将其重编译为一个ELF文件，如图3所示。然后将用户自定义的代码编译并链接到固件映像。编译后的代码存储在单独的页中，并为仿真提供初始入口点_start。它与固件共享相同的地址空间，因此它可以调用函数并解析映像中的数据结构。

在fuzzing的设计上，作者并不是把所有输入数据作为一个单独的Binary Large Object (BLOB)来处理，而是表示为一个package sequence。其中package和sequence是分别mutate的。于是Frankenstein可以对已知数据包重排列也可以添加新的数据包来增大覆盖率。图5体现了这种方式对覆盖率提升的帮助。

作者将固件附到host stack的设计也增加了覆盖率，如表3所示，这对于一些需要BCS kernel和link manager之间交互的漏洞的发现是必须的。

最后我们来看一下fuzz的结果。作者发现测试的所有设备都没有DEP、ASLR等保护策略。通过堆溢出，攻击者可以控制空闲列表指针指向任何位置。由于重复分配，该指针被视为有效的BLOC缓冲区，如图6所示。这会导致“write-what-where”的gadget，从而进行远程代码执行。

例如Classic Bluetooth的设备查询中的堆溢出漏洞利用(CVE-2019-11516)，攻击者可以利用主机在未知设备连接时发出HCI_Remote_Name_ Request命令，返回的事件具有在受影响的BLOC池中分配的正确大小。攻击者控制的远程名称通过LMP在多个数据包中读入该缓冲区的，通过省略最后一个数据包并静默删除连接，缓冲区将保留几秒直到发生超时。重复此过程，可以写入任意内存，从而产生RCE。

另外还有BLE协议数据单元（PDU）接收中的堆溢出（CVE-2019-13916）。表4和表5显示了这两个漏洞的影响范围。在测试漏洞时，作者还找到独立于芯片的Android RCE漏洞BlueFrag。

这篇文章内容还是很丰富的，当然读起来也要费劲些。总的来说，文章的重点并不在fuzz，而是在firmware emulation和漏洞的利用，而且漏洞是与硬件芯片相关的，需要很多相关知识的。这里不得不提一下SEMOO实验室，他们在Wi-Fi、蓝牙安全方面有着很深厚的研究积累，之前我们也推荐过来自他们实验室的Apple AWDL的研究，这些研究都需要大量的逆向来还原协议与实现，从他们的工作中能感受到层层递进、不断深入的感觉，向他们致敬。
