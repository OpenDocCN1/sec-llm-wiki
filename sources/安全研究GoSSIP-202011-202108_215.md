# G.O.S.S.I.P 学术论文推荐 2020-12-09

今天推荐的论文是来自ACSAC 2020的《CAPS: Smoothly Transitioning to a More Resilient Web PKI》，作者设计了Certificates with Automated Policies and Signaling（CAPS）系统，该系统能够帮助Web PKI在遇到重大缺陷时进行“平缓流畅”的改进。

![](../Images/d0459167c8148f1557e782d3d29e3775.png)  

首先，作者总结了当前Web PKI在面临改进时遇到的四个挑战。第一，要求对PKI的参与者进行大幅度的调整；第二，缺乏防御降级到旧版本的信号机制；第三，缺乏增量部署的策略；第四，缺乏针对错误部署或密钥泄露的灵活的应对机制。因此，作者提出了CAPS系统，该系统为Web PKI过渡到更加弹性的版本提供了路线图。

![](../Images/1c7201b7c5a02e1680f23fc923a7e245.png)

CAPS的框架如图一所示。可以发现，除了引入了Log Aggregators实体，框架并没有对传统的PKI进行大幅度调整，CA、Logs（CT/Censys）、服务器和客户端的工作机制基本没有改变。

  

当客户端与服务器建立连接时，客户端会首先向Log Aggregators发送域名进行查询。如果返回no\_cert，则客户端拒绝与服务器连接；如果得到的是one\_cert，则与服务器进行标准的TLS握手，并拒绝HTTP连接；如果得到的是multi\_cert，则与服务器进行CAPS扩展的握手（该扩展的握手主要是通过签名来确定域名确实拥有相应的私钥），并与域名建立连接。

  

Log Aggregators会从可用的公开数据集（CT，Censys，CRL，OCSP等）中收集可用的信息，并构建了域名到证书公钥的映射。通过查询，Log Aggregators会返回{no\_https, one\_cert, multi\_cert}。作者使用了无环确定有限状态自动机来保存域名的信息（在这里就不做赘述了，感兴趣的读者可以看论文）。

  

通过该机制，CAPS框架可以在一定程度上缓解了HTTPS降级为HTTP的风险，其多证书机制还可以帮助服务器更灵活的管控服务器私钥。

![](../Images/9ddca9b60967ffebbef8bc3fad50cdd0.png)

  

最后，作者评估了CAPS的性能，结果显示，它对原有的客户端和服务器的连接的延迟，仅增加了5%。

  

笔者认为，作者的工作亮点在于，将Web PKI改进的压力转移到了Log Aggregators上，以达到帮助传统Web PKI进行平滑过渡的目的。
