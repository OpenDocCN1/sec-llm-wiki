继续昨天的话题吧，今天我们推荐一篇来自USENIX Security 2019的关于PAC的论文。这篇论文借助PA对多种runtime attack进行了防御，并且开源了代码，文章也有着不错的引用量。

这里说的的runtime attack实际上就是指control-flow attack（其代表就是ROP攻击）和data-oriented attack。昨天推荐的PACStack仅着眼于控制流攻击，而这篇PAC it up对这两种类型的攻击都进行了防御的设计。

Pointer Authentication（PA）是从ARMv8.3-A开始引入的，在昨天的论文推荐中也说明了，今天就不赘述了，就用图1和2来回顾一下。其核心思想就是对指针值和一个modifier计算message authentication code (MAC)，从而在运行时保护指针。昨天那篇论文将这个MAC拓展为chained MAC，而今天讲的这篇，则是普通的MAC计算方式。

正如昨天提到过的，基于PA的防御是存在弱点的。作者总结了两类针对PA的攻击：Malicious PAC generation和Reuse attacks。前者通常需要借助CFI来防止认证指令被攻击者用作signing gadget，后者主要是由于作为MAC中上下文信息的modifier不一定具有唯一性（所以才有了昨天论文的chained mac思路）。

本文中作者考虑的攻击者是具有任意内存读/写能力的，仅受DEP限制。防御的设计目标则是Pointer Integrity、PA-attack resistance、Compatibility和Performance。

作者设计并实现了Pointer Authentication Run-Time Safety（PARTS），来保护返回地址，局部、全局以及静态的指针和C结构体中的指针，架构如图3所示。

为了抵御重用攻击，作者对指针进行了划分，如表1所示。通过将data和code指针分开处理，能够限制重用攻击。但这种指针划分粒度较粗，于是作者又设计了Run-time type safety，通过在PA修饰符中编码指针的类型进行记录，并且根据指针指向的数据、结构体、函数签名来分配unique id（基于LLVM ElementType）。对于返回地址的保护，PARTS则组合了当前栈指针的值和编译时生成的函数id，以确保验证后的返回地址不能在不同函数间重用。作者还在PARTS中设计了runtime bootstrap来保护静态分配的数据中的指针。

评估环节，作者在ARMv8-A Base Platform Fixed Virtual Platform (FVP)上进行仿真，这个FVP也是当时唯一支持PA的公开环境。图4显示了PARTS与EL0-3的关系，其中PA key在kernel存储与管理。

在安全性评估方面，作者主要有四点安全性衡量：

  1. return address signing：通过组合指针值和函数id来防御不同函数间的重用；

  2. Forward-edge code pointer signing：防止攻击者使用注入程序内存的伪造代码指针，从而抵御ROP/JOP攻击。另外，run-time type safety也能防御多种重用攻击；

  3. Data pointer signing：防止攻击者加载伪造的数据指针，从而抵御data oriented attack。同样也采用了run-time type safety，但是这对数据指针的完整性会产生阻碍（存在pointer conversion）。

  4. PAC entropy：来抵御暴力猜测攻击。

最后来看看开销，如图5所示。我们可以看到，data pointer signing的开销还是很大的，主要的开销就集中在这里。实际上，对于data oriented attack的防御，还是有做文章的空间的，毕竟这里的方案开销还是太大，而且完整性依然没有充分保障，期待未来能看到基于PA来解决这个问题的研究。
