让我们暂时忘记一下AI的喧嚣，回到经典的安全主题——isolation上，今天我们要进入到2023年的Oakland论文 *μSWITCH: Fast Kernel Context Isolation with Implicit Context Switches* 中，了解一下如何对内核资源进行轻量级的隔离（还记得我们在今年4月3日推荐的论文KIT【[G.O.S.S.I.P 阅读推荐 2023-04-03 KIT](http://mp.weixin.qq.com/s?__biz=Mzg5ODUxMzg0Ng==&mid=2247494772&idx=1&sn=07c362fac6793ff4d6d0ee570f0af06a&chksm=c063c2adf7144bbbaf61ea08d7e8f3638b084f2e8349c7172b60b2b54be4d21b0ee0bde6fcb0&scene=21#wechat_redirect)】吗？对，就是同一批作者，他们在那篇论文中提出了问题，这篇论文就来解决问题啦~）

![](../Images/a07641f05ffecbaae4fc0dd937596be5.png)

回顾一下，之前我们讨论过，在传统的隔离体系中，内核维护的socket、文件、计时器（timers）等资源特别容易因为被不同的隔离域（domain）共享使用，而产生一些信息泄露相关的安全问题。特别是最近几年火热的in-process isolation，其实只是做到了in-process的memory isolation，也就是只对内存访问进行了隔离，对共享资源的访问并没有进行隔离（还远远达不到Hypervisor对OS隔离那种程度——给每个隔离域虚拟出不同的资源）。实际上，在基于domain的隔离机制中，不仅需要隔离内存，还需要给不同的domain分配不同的kernel context，也就是说，一旦从domain A切换到domain B，不仅要重新设置内存访问权限，也要重新设置kernel上下文（出国以后不光要换手机卡，整个通讯录也给你换喽）

作者大概是最近一直在做和WebAssembly相关的研究，所以总是喜欢用WebAssembly举例。在WebAssembly中，为了实现不同的隔离域之间的kernel context，专门有一个高权限的domain去虚拟实现了kernel context，这种方法听起来就很不系统，作者表示我们需要更加科学的设计，于是就提出了一套叫做`μSWITCH`的机制：在kernel层面上引入并维护了一种比进程上下文更加轻量级的μContext数据结构，然后，为用户态设计了一种隐式系统调用（implicit system call），允许进程（假设这时候进程里面部署了in-process isolation）内部不同的domain之间切换时，不必切换到kernel权限就完成μContext的变更。

下图比较了进程隔离、WebAssembly内的资源隔离和作者设计的μContext隔离，如果你比较熟悉系统安全研究，对这种安全防护方式应该不会感到陌生——通过在可信空间（例如本文中的kernel）设定一套机制，让不可信的空间（本文中的用户态）中有一部分代码得到“特殊照顾”而作为“安全代理人”存在。

![](../Images/56ae4274e090d6ba3a494dfbc61475f1.png)

更具体一点，我们看看下面这幅图的对比，如果基于进程进行隔离，每次切换上下文就涉及到从用户态到内核再返回用户态的一系列非常消耗资源的操作，即使在这里只是使用了一次`open`操作；而如果在`μSWITCH`的机制开启以后，只有在真正的`open`操作时候需要到内核里面走一趟，其他所有的上下文切换都留在了用户态，这样性能的提升是非常明显的！在本文中，作者把他们设计的这种机制命名为 *implicit context switching*

![](../Images/47d8667c352f59d802272ac5c9806df8.png)

那么，到底`μSWITCH`的关键细节是什么，从下图的design overview中我们看到，首先`μSWITCH`在内核中为每个进程维护了一个μContext表，并且在PCB中也加入了相关的指针，指向该表格；同时，内核和用户态共享了当前μContext的信息（用两个descriptor——*shared-desc*和*current-desc*标记了当前的μContext以及最近一次的μContext）。然后，注意到 *implicit context switching* 机制的工作方法：不管平时发生了多少次上下文切换（下图中的`μswitch`操作），都不会切换到内核态，只在用户态更新这些μContext信息，仅当真正的系统调用发生的时候，在进入到内核之后，执行相关操作之前，才会把μContext真正更新，这样就节省了许多开销！

![](../Images/c79c050748524f93492270d15e027ccf.png)

当然，你会问，不在内核态进行的`μswitch`操作，怎么保证它的安全呢？答案是——使用Intel MPK（当然作者也说了，可以用其他一些等价的防护原语）~ 通过基于MPK的isolation，将上图中用户态那些和内核共享的内存页单独放在一个高权限的domain里面，只有特定的操作才拥有访问这个domain中内存页的权限。

![](../Images/f6698259cfd799c422f39b087bb3e10e.png)

进入到实验环节，作者首先比较了一系列的sandbox机制的性能开销，可以看到`μSWITCH`比起进程切换性能是要好太多了~ 这篇论文中还有很多性能评估的环节，但是我们的读者可能更关注安全，这里就不再一一介绍实验结果了。

![](../Images/2c6408e66f2356a40e518acd72ee55ca.png)

最后要提一下`μSWITCH`的应用，作者将其部署到了两个非常典型的应用场景上——FireFox的浏览器内部沙盒RLBox（实现各种浏览器使用的三方库的isolation），以及对各种HTTP server（包括Apache和Nginx）使用的三方库的隔离。
