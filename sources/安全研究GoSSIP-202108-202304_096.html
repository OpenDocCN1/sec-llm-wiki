喜气阳阳的圣诞节之后，我们今天推送的这篇名为Isolated and Exhausted: Attacking Operating Systems via Site Isolation in the Browser的论文非常有趣, 作者脑洞大开，利用了本来是保护浏览器安全的站点隔离（site isolation）技术，再结合WebRTC通信，构造出了能够对操作系统进行DoS攻击和DNS投毒的恶意攻击，论文目前已被USENIX Security '23接收，让我们赶紧去看一下吧！

在现代浏览器中，通过部署site isolation策略，限制每个网站的加载都由一个单独隔离的渲染进程负责，这也意味着一个网站无法访问另一个网站的内存或资源。这防止了攻击者可能利用的内存漏洞或其他漏洞，并使得攻击者更难以跨网站访问敏感信息。

然而，浏览器在部署site isolation策略的时候忽视了对系统可用资源的管理，这导致攻击者可以滥用使用site isolation策略来消耗本地系统资源。例如访问不同的域名或IP地址（浏览器认为不同IP就是不同的site）轻松创建大量站点，并不断创建 iframe 加载这些站点，在目标系统上创建足够多的进程抢占系统资源，最终实现拒绝服务攻击。这个攻击方式门槛极低，却非常有效果。

除了site isolation策略，另一个现代浏览器中常用的技术——WebRTC (Web Real-Time Communication) 允许浏览器在不使用插件的情况下进行实时通信。 WebRTC 使用 JavaScript APIs 在浏览器中提供了视频和音频通信功能，包括音视频会议、文件共享和 P2P 文件传输。同样地，通过不断创建 WebRTC 对象，浏览器会占用所有UDP端口（从而导致可用资源枯竭），这会引发后续的一系列非常严重的攻击！

特别地，在对端口的占用上，作者在对含有单个数据通道的WebRTC对象测试时发现，该对象会占用两个 UDP端口，所以如果在攻击时产生了大量的WebRTC对象，而此时刚好有奇数个可用 UDP 端口，则最后会有1个 UDP 端口无法占用。通过这种攻击方式，不仅可以耗尽所有 UDP 可用端口使得所有新的 UDP 通信无法进行，还刚好留下了一个端口，你能想到这会导致什么问题吗？

作者想到，利用 UDP 端口占用，可以破坏DNS的端口随机化（关于DNS端口随机化的引入，大家可以去了解一下DNS安全的一些基本研究工作），从而快速猜测出DNS请求的源端口，然后只需要爆破 TXID 即可实现 DNS 投毒！！！

作者实现了名为DEMONS的本地DNS缓存投毒攻击，首先，在构造的恶意网页中不断创建WebRTC对象来占用全部 UDP 端口，并保留一个WebRTC对象最后释放，使得系统只有一个UDP端口可用；然后，网页通过Websocket把这个端口信息传回恶意服务器；最后，当攻击者想要污染某个域名对应的DNS信息时，就通过 XMLHttpRequest 请求这个包含这个域名的URL，系统发送 DNS 请求查询 IP 后，由于恶意服务器已经掌握了这次DNS请求的源端口，就可以马上用UDP抢先向被攻击者的机器源端口发送包含不同 TXID 的 DNS 响应，从而实现投毒！

在 Windows 平台上，对于Chrome、Edge和Firefox，在开启site isolation的情况下，攻击效果显著，同时攻击效果和系统内存（及磁盘交换空间）大小也有关系，特别地，如果磁盘交换空间很小或者关闭的情况下，如果内存不足，大概率只会造成浏览器崩溃，而不是系统无响应。在 Linux 平台上，无论交换区是否开启，Chrome都会造成系统无响应；而Firefox则只会造成浏览器的崩溃。

在Windows平台上，使用 WebRTC 在 Chrome 和 Edge上都可以实现占用全部 UDP 端口（可能留下一个）的目标。可在Linux平台上，通过 WebRTC 的攻击效果就没有那么好了，只能占用接近一半的 UDP 端口，很难达到攻击效果（需要猜测的端口过多）。

作者分别在 Internet 和 局域网环境下评估了攻击效果，同时对比了通过病毒配合进行攻击的效果。结果如下图所示

作者发现，即使攻击者处在Internet端，发送的伪造响应到达被攻击者的机器的时间更长，其投毒成功率和在局域网环境下的攻击（伪造响应几乎总是先到达）相近，效果都很不错。

作者向浏览器厂商提交了漏洞报告。Google 认为通过不断创建进程实现 DoS 是安全问题，没有进行修复。对于使用 WebRTC 占用 UDP 端口进行攻击，Google 在全局限制了只能占用 6000 个 UDP 端口。要彻底解决 DNS 投毒问题，作者推荐使用大家都去使用DNS-over-HTTPS~
