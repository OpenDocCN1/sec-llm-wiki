今天给大家介绍的是来自ISSTA 2022收录的一篇论文——“A Large-Scale Study of Usability Criteria Addressed by Static Analysis Tools”，作者对静态分析工具的可用性进行了全面评估，结果表明大部分工具的可用性方面实现都存在不足之处，例如警报信息不足、不提供修复支持等。

静态分析工具 (SAT) 目前已被广泛用于程序代码分析。除了检测相关代码问题，静态分析工具还需要全方位的提供可用功能以帮助用户使用工具。因此，本文首次从用户的角度全面探究了静态分析工具的可用性现状，并对现有工具进行了较大规模评估。

  • 评估对象：作者收集了一些流行语言（如C、C++、Python等）的静态分析工具，共计243个；在此基础上，作者对这些工具在功能方面（有警报信息）、可用文件（可执行文件/源代码）、私有性以及维护情况进行筛选，结果如图1所示。

  • 评估标准：作者基于已有文献提出了六类可用性问题，包括警报消息、修复支持、误报、用户反馈、工作流集成以及用户交互。

  • 评估测试：作者首先检查工具文档并在虚拟机中对工具进行配置安装；之后，作者使用multiple-raters方法，让两位专家对工具进行相互独立评估；最后，对两个评估进行比较，如果结果存在分歧，则由专家协商达成一致。

主要的可用性评估结果如表2所示：

(1) Warning Messages: 静态分析工具需要以清晰的方式呈现错误信息，并且需要指出错误原因，即为什么将某些点识别为错误。评估结果表明，超过一半的SAT没有提供足够的警报信息（30/42），且几乎没有任何工具提供详细的错误原因。

(2) Fix Support: 静态分析工具在发现错误后，应当提供响应的修复思路，结果显示有37种工具没有提供修复信息。

(3) False Positives: 开发人员不使用SAT的一个主要原因是由于SAT的高误报率，因此作者从可用性的方面对开发人员如何处理误报进行评估（如SAT需要实现基于用户反馈的误报抑制、可信度评估等）。结果表明只有12种工具允许开发者将警报报告为误报，且只有15种工具部分提供了相关误报处理措施。

(4) User Feedback: 除了误报情况，静态分析工具也需要能够接收处理一般的用户反馈，如可定制的规则、基于用户反馈的结果验证、警报忽略等。评估结果显示，有8种工具支持用户反馈；大部分工具都允许关闭规则，19个工具能够对规则进行修改；少数工具支持警报忽略。

(5) Workflow Integration: 是否能够将SAT集成到开发人员的工作流程中也是SAT可用性的一个重要方面，如SAT需要对警报优先级进行确定、IDE集成、工具独立使用、浏览器访问、运行时间等。评估结果显示只有22个工具能够通过CLI继承使用，且有22个工具需要超过1分钟的分析时间。

(6) User Interface: SAT需要有清晰的用户界面来支持用户交互，如错误高亮显示、IDE/CLI一致性以及警报追踪等。评估结果表明只有三种工具具有良好的用户界面支持，所有的CLI工具都没有代码高亮显示，大部分工具都不支持警报的搜索与追踪。

总的来说，这篇文章对静态分析工具的可用性进行了大规模的评估，所使用的方法也比较简单，其中作者提出的一些可用性的标准与见解也可以帮助我们对安全分析工具进行评估与改进。
