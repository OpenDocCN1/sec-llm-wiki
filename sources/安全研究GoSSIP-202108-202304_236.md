# G.O.S.S.I.P 阅读推荐 2022-07-26

今天给大家推荐的是来自ICSE 2022的一篇论文——“The Extent of Orphan Vulnerabilities from Code Reuse in Open Source Software”，作者主要针对开源项目中的漏洞重用问题展开研究，设计并开发了一个工具——`VDiOS`来帮助识别和修复开源项目中的Orphan Vulnerabilities，结果表明开源项目的代码重用可能会导致易受攻击代码片段大范围传播，并且即使在提供修复方案后，很多重用的漏洞也没有被修复。

![](../Images/8931d5f6e7482c771d731e52fb01e41d.png)

Orphan Vulnerabilities是指已知漏洞在另一个项目中发现并修复后仍存在于某个项目中的情况，此类漏洞可能是由于对开源软件OSS代码复制重用导致的。此外，由于此类漏洞的攻击方式通常是公开的，并且相关的开源项目可能会被再次重用到其他项目中，从而会造成更加严重的后果，因此本文主要针对开源项目中的此类Orphan Vulnerabilities展开研究和分析。

![](../Images/7ded2ddba86700e6f61653778cd43105.png)

为了深入了解Orphan Vulnerabilities，作者设计并开发了一个工具——`VDiOS`来检测开源项目中所包含的漏洞。`VDiOS`主要架构如图1所示，其输出为HTML格式报告。

**(1) Data Layer & API Layer**  
`VDiOS`底层主要基于World of Code (WoC)来实现高效的开源项目数据查找，包括blobs、commits、项目、文件、作者以及时间；它还能够利用源代码托管平台（GitHub、Bitbucket、GitLab等）API接口来连接到其他流行平台进行数据检索。

**(2) Algorithm**  
`VDiOS`漏洞检测主要包含四个阶段：

*   Phase 1 - 识别包含漏洞/修复的所有blob。`VDiOS`首先查找在漏洞提交之后修复漏洞提交之前的所有blob，这些blob都可能会包含易受攻击的代码；之后，`VDiOS`会利用WoC映射获得descendent blob，这些blob可能会包含修复代码；最后，作者人工检查这些blob以确认两个列表，即漏洞blob列表和修复blob列表。
    
*   Phase 2 - `VDiOS`利用WoC查找包含或曾包含易受攻击blob副本的所有项目。
    
*   Phase 3 - 检查易受攻击的blob是否存在项目的最新版本中。利用托管平台API，`VDiOS`能够找到文件最新版本，并进一步查看该版本中是否匹配漏洞blob和修复blob。如果匹配到前者，则认为该项目中仍包含问题代码；如果匹配到后者，则认为该项目中的漏洞已修复；否则，则认为漏洞代码被修改过，但无法确认漏洞是否被修复。
    
*   Phase 4 - 以HTML格式生成检测报告。
    

作者描述了四个Orphan Vulnerabilities案例，包括CVE-2021-3449、CVE-2014-0160、CVE-2021-29482、CVE-2017-12652。这里以CVE-2021-3449 in OpenSSL为例进行说明。该漏洞存在于OpenSSL ssl/statem/extensions.c文件中，在commit c589c34e61中引入，在commit 02b1636fe3中被修复，所有OpenSSL 1.1.1版本都会受到影响。  
根据算法流程，`VDiOS`首先在Phase 1中找到了56个版本的文件包含此漏洞，发现3个版本文件包含修复。通过进一步的分析，`VDiOS`发现了1,614个项目中包含漏洞代码，11个项目中包含修复后的代码，1079个项目中对相关代码进行了修改但无法确认漏洞是否修复。  
为了进一步了解Orphan Vulnerability的影响，作者进一步分析了这些包含漏洞代码项目的活跃度和流行度。结果显示，1,614个项目被132个项目fork，其中23个项目在6个月内至少有一次commit，64个项目在18个月内至少有一次commit。此外，有4个项目超过10,000个star，10个项目超过1,000个star。这些结果也能够印证Orphan Vulnerability可能会造成广泛的影响和严重的后果。

作者在最后也提出了一些`VDiOS`存在的限制，比如说工具的检测能力与WoC的覆盖率紧密联系，后续还可以建立更广泛的网络来增强；如果开发者在commit之前对重用的文件进行了修改，那么`VDiOS`将无法进行匹配等。详细内容可以查阅原文~
