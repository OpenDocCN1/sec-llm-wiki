# G.O.S.S.I.P 阅读推荐 2022-07-25 KSplit

2022年（或者说过去三年）的中国热词，也许非“隔离”莫属。在大暑刚刚过去的这个周一，我们来关注热力四射的隔离技术在内核驱动安全防护方面的安全应用，继续为大家介绍OSDI 2022的研究论文——**KSplit: Automating Device Driver Isolation**

![](../Images/8912512efaf381761fd806373525d7c3.png)

随着MPK的广泛应用（感觉我们每次都在强行安利自己的工作……），对运行时代码进行细粒度隔离，其性能开销不再是生产环境的“拦路虎”。接下来要回答的问题是，所谓的“细粒度”隔离真的实现了“精确抗yi”吗，亦或是仍然存在很多高风险代码和低风险代码混合在一起的情况。在操作系统的内核中，这种情况就非常普遍——驱动代码和内核代码不仅运行在同一个权限级别下，还共用了许多内存数据，在这种情况下实施细粒度隔离，显然是给安全防护提出了巨大的挑战。本文作者希望能够实现一个更好的隔离框架，能够为当前的Linux内核中的设备驱动提供隔离防护（而且尽可能少需要开发者去介入）。

作者指出，无论采取什么样的隔离政策，都要充分考虑到相关的“风土人情”，例如对Linux内核的隔离，你一定需要对它里面的大量奇怪的代码风格有充分的认识，否则贸然采取naive的静态代码分析一定会产生大量错误。下图中列出了很多在Linux内核（尤其是驱动代码）中常见的代码写法：

![](../Images/08a79407b7405a5d970b5fc39c57f254.png)

除此之外，内核中的一些数据结构（可能是由于历史遗留问题）非常复杂，例如下图中的这个`sk_buff`结构体，你以为它只是像下图那样简单？你错了！实际上它有66个field（包括5个指针和2个offsets），最终可以指向3132个其他结构体的field（又涉及到1214个指针)……

![](../Images/6d142936300918de8e5e5647cee004b3.png)

认识到世界的复杂性，是正确解决问题的第一步，作者开发了`KSplit`框架，在标准的程序分析的基础上，增加了一个核心步骤——对内核代码和驱动代码之间共享的内存的静态分析（下图中的Shared Data Computation）。当然，这部分在实践中非常复杂，绝非下图几个框框就能解释清楚，大家可以仔细去看看论文的第四章。

![](../Images/cd912235fcea117b55c23f4c00221b72.png)

在完成了分析之后，`KSplit`能够自动将代码切分为不同的domain，然后引用了本文作者在VEE 2020年的研究论文**Lightweight Kernel Isolation with Virtualization and VM Functions**中引入的LVD框架。在LVD框架中，作者引入了interface definition language（IDL）来帮助不同的domain进行数据同步，`KSplit`也在完成静态分析后，利用了一个IDL编译器来自动化生成隔离所需的IDL代码。

`KSplit`对Linux内核的九个子系统进行测试，实验表明，`KSplit`可以很好应对这些（复杂的）代码并得到可用的分析结果：

![](../Images/cb873cab8293cff11359dfbb554dd4ee.png)

论文中有一个地方可能值得商榷，尽管`KSplit`对内核中的354个驱动进行了分析（并生成了对应的IDL），但是最后只对其中的10个驱动进行了实际的运行测试，尽管作者表示既然剩余的344个驱动都可以生成IDL，就说明`KSplit`还是蛮有效果的，但是我们也还是会谨慎怀疑一下相关的适用性吧。

最后是`KSplit`的性能评估，作者用`Memcached`进行了测试（部署了一个代码隔离版本的`ixgbe`网络驱动）。从实验数据可以看到，在线程数不多的情况下，隔离对性能的影响比较明显（论文中说的是5.4-18.7%），而到了10线程的情况下，隔离和非隔离版本的性能差异已经不大了（因为这时候瓶颈是网络处理能力）
