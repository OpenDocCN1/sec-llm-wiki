Trinity: High-Performance Mobile Emulation through Graphics Projection

Di Gao, Hao Lin, Zhenhua Li, Chengen Huang, and Yunhao Liu, Tsinghua University; Feng Qian, University of Minnesota; Liangyi Gong, CNIC, CAS; Tianyin Xu, UIUC
本文来自清华大学团队，对安卓模拟器的GPU模拟性能进行了大幅度提升，并在华为内部开发得到了大规模部署和使用。
移动端的模拟可用于PC模拟手机游戏、手机app调试、恶意移动软件检测等。模拟的方法是使用虚拟机对手机环境进行仿真，从而运行完整的手机操作系统，如谷歌的安卓模拟器（Google Android Emulator，简称GAE）。移动端模拟器的主要痛点在于手机app以交互型为主，需要图形化界面的渲染。
现有的应对方法如下：
（1）使用CPU模拟GPU完成图形渲染工作，然而CPU不擅长并行计算任务，因此性能很差。
（2）改进做法之一是API remoting，将虚拟机内的图像API调用截获，转化成宿主机的GPU调用，二者通过RPC协议进行通信，该做法的主要问题是引入了太多VM Exits，而且GAE的实现中虚拟机必须等待宿主的API执行完成后才能继续进行（同步调用），因此性能依旧不佳。
（3）进一步的改进做法为设备虚拟化，使用了驱动作为交互边界，允许虚拟机内的驱动将命令通过共享内存直接发给宿主机的GPU设备，驱动命令更少也更有利于异步执行，然而使用驱动命令丢失了上层抽象的语义，将窗口、线程等信息转化为的内存地址和寄存器值，对于多线程UI程序而言，驱动命令的串行执行降低了并发程序的渲染速度。
（4）另一种方法是打破虚拟化边界，允许客户机内的应用程序直接使用宿主的GPU（如DAOW），需要将安卓的Linux系统调用转化为Windows系统调用，主要难点在于系统调用转化的工程量，以及潜在的安全风险。
本文提出了Trinity系统，对现有移动端模拟器的GPU模拟进行卓有成效的改进，兼具高效性、兼容性和安全性（不破坏虚拟化的隔离特性）。核心观察为：
  • 94%的GPU调用不需要立即和GPU进行交互，因此可以高度异步。这类调用主要为Context、Resource的配置，通常使用句柄（handle）进行操作。
Trinity的主要技术点如下：
  • Projection Space：将宿主机GPU上的Context和Resource投影到虚拟机内部，暴露为Shadow Context和Resource Handles，Trinity负责客户机和宿主机的句柄映射。借助投影空间，可以尽可能地将大量GPU操作转化为异步，降低VM Exits次数。
  • Elastic Flow Control：为了协调好宿主机和客户机之间的配合，避免突发高频绘制导致的拥塞问题，Trinity参考了网络MIMD拥塞算法。
  • Adaptive Data Teleporting：将宿主机和客户机的数据交互过程分解为3部曲：1）data aggregation 2）data persistence 3）arrival notification，然后使用static timing analysis为动态挑选合适的流控策略，从而有效提升交互吞吐。
作者从谷歌应用中挑选了前100的3D应用，和前1万中随机挑选的手机app程序作为benchmarks。
  • 性能层面，Trinity平均能达到原生性能的93.3%；在和主流的6大移动端模拟器（GAE、QEMU-KVM、Windows Subsystem for Android、VMware Workstation、Bluestacks、DAOW）的对比实验中，Trinity的性能优化在1.4x到20x之间。
  • 兼容性层面，能支持 97.2% 的前1万apps。
Trinity目前已被集成到Huawei DevEco Studio中，代码链接：https://trinityemulator.github.io/。
Q&A
Q：是否考虑将Trinity用于GPGPU任务的加速？
A：确实可以做一部分有渲染需求的通用计算任务。

Orion and the Three Rights: Sizing, Bundling, and Prewarming for Serverless DAGs

Ashraf Mahgoub and Edgardo Barsallo Yi, Purdue University; Karthick Shankar, Carnegie Mellon University; Sameh Elnikety, Microsoft Research; Somali Chaterji and Saurabh Bagchi, Purdue University
这篇论文由来自 Purdue、CMU、Microsoft Research 的研究者合作完成。其中一作 Ashraf Mahgoub 是专门做通过 reconfiguration 来对云上系统的性能和成本进行优化的，他之前的工作 Sophia (ATC‘19) 是对 NoSQL 数据的成本和性能进行优化，同时还有一篇 OptimusCloud 发表在 ATC‘22 对分布式数据库的性能和成本进行优化。本篇 ORION 则是对 Serverlss chain 的时延和成本进行优化。
Serverless 计算是最近云上一种备受关注的编程范式，由于其具备按需分配资源、弹性扩容、无需开发者关注云基础设施 (容器、虚拟机) 和软件运行时的管理、“pay-as-you-go” 的付费模式等优势备受开发者和云厂商的青睐。Serverless 应用经常使用有向无环图 (directed acyclic graph, DAG) 来表示，图中的节点表示函数，边表示数据依赖。一个 serverless DAG 由两个或两个以上的阶段 (stage) 构成，每个 stage 包含调用同一个函数产生的一个或多个函数实例，同一个 stage 的函数实例之间并行运行，不同的 stage 之间串行运行。现在主流的 serverless 平台为每个函数实例准备一个 VM 作为运行环境，每个 VM 的大小 VM-size (包括 vCPU 个数、内存大小、网络带宽等资源) 由用户进行配置，而 VM-size 则会影响函数执行的收费。
作者对 Azure Durable Function 六个数据中心为期一周的 serverless 执行日志采样并进行分析。作者发现想要对 serverless DAG 的端到端时延和成本进行优化 (对成本进行优化指在满足时延要求的情况下选取尽量小的 VM-size) 面临三点挑战：
  1. DAG 端到端时延的可变性和偏度非常之大，在作者采集到的数据中调用最频繁的5个 DAG 的 P95 尾时延可以达到 P25 尾时延的80倍。
  2. 属于同一 stage 的多个并行函数实例的运行时间偏度非常大，即某个函数的运行时间可能是其他函数运行时间的数倍。
  3. serverless DAG 运行过程中可能会有冷启动的情况发生。
Right-sizing： 为了根据端到端时延目标为 DAG 中的函数选择合适的 VM-size，ORION 提出一种概率统计学的方法对 serverless DAG 进行性能建模，得到 DAG 端到端时延的概率分布（使用 CDF 图来描述）。如下图所示，对于属于不同 stage 串行运行的函数，ORION 使用 Convolution 对其概率分布进行组合；对于属于同一 stage 并行运行的函数，ORION 使用 Max 对其概率分布进行组合。最终就可以获得整个 DAG 的端到端时延概率分布。利用该建模方法， ORION 先为每个函数选取最小的 VM-size 配置，然后不断的增大 VM-size 并重新预估 DAG 端到端时延的概率分布，直到找到满足端到端时延目标的 VM-size 配置。对建模方法和算法细节感兴趣的同学可以看论文 3.2 章节。
Bundling： 同一 stage 并行运行的多个函数实例可能由于输入不同导致运行时间偏度大 (execution skew)。为了解决这个问题，ORION 提出了 bundling 的方法，即将并行运行的多个函数实例放在一个 VM-size 更大的 VM 里降低时延。比如下图中，运行时间较短的函数 worker2 和 worker4 执行完成后，其余还未完成的函数 worker1 和 worker3 就可以利用多出来的空闲资源加速自己的运行，从而减低该 stage 的整体时延。对如何决定一个 stage 是否应该 bundling 以及如何选取合适的 bundle size 等细节刚兴趣的同学可以去看论文 3.3 章节。
Right-prewarming： 为了减少 DAG 运行中遇到的 VM 冷启动对端到端时延造成影响，pre-warming (即在函数执行开始前预先初始化 VM) 是一种非常直观的解决方案。然而如何决定 pre-warming 的时机非常重要，过早的 pre-warming 会因为浪费 VM 时间而导致资源利用率下降，过晚的 pre-warming 则对冷启动问题并没有产生太大优化。ORION 可以在满足用户规定的资源利用率目标下，根据之前提到的性能模型来为每个 stage 的函数选择合适的 pre-warming 时机。
测试阶段，作者选取 VideoAnalytics, ML pipeline 和 Chatbot 三个真实的 serverless 应用来测试 ORION 和对比方案对 DAG 端到端时延的影响。根据测试结果，在不涉及冷启动的情况下，ORION 的时延仅次于 Best Memory (Best Memory 在分配 VM-size 的时候采取了激进的策略，也因此成本最高)，而且成本也达到了最低。在考虑冷启动的情况下，ORION 比起三个对比方案都表现出了最优的端到端时延，同时在 VideoAnalytics、ML pipeline 这两个应用中也花费了最低的成本。

Q：你们是否考虑过在性能和成本之间做 tradeoff，比如设置一个更差的 latency 目标，我就可以使用更低的成本？
A：很好的问题。latency 目标是由用户自己设置的，如果你设置了更高的 latnecy 目标，我们的系统可以在该基础上选择最优的配置使成本最低。这和我们最近被 SIGMETRICS 接受的另一篇论文 WISEFUSE 相关，那篇论文里面研究了我们如何达到不同的时延和成本 tradeoff。

Occualizer: Optimistic Concurrent Search Trees From Sequential Code

Tomer Shanny and Adam Morrison, Tel Aviv University
这篇论文来自特拉维夫大学Adam Morrison教授团队，它提出了一种将非线程安全的串行搜索树数据结构机械地（非手动）转化为高效可扩展的并行数据结构的方法，Occualizer。Occualizer使用乐观同步（optimistic synchronization）方法，只将同步注入到更新操作中，使操作执行的遍历步骤不涉及同步，从而最大化并行度。作者评估了Occualizer转化的并发B+树、前缀树（trie）和红黑树的并发版本，发现它们在读写工作负载上的性能明显优于其他转化方法构造的并发树，并在只读工作负载下相比串行版本仅损失4%的性能。通过将STOv2内存数据库使用的Masstree替换为Occualizer转化的并发B+树，系统吞吐量下降不到30%。
内存搜索树被广泛地使用在数据库、操作系统，以及存储系统中，这些多核系统的性能不仅取决于搜索树的串行（单线程）执行速度，更常常主要取决于树结构同步协议的可扩展性。目前，为构建高效的并发搜索树，开发人员需要根据系统的使用场景和工作负载定制数据结构及其同步协议，并保证在任何可能的并发执行下提供协议的正确性，即可线性化（linearizability）。每当数据结构的算法发生变化时，开发人员还需要重复验证算法修改的正确性。
Occualizer接口
Occualizer提供了一个自动化将串行搜索树实现转化为可扩展的并行搜索树的方法。用户仅需要使用其提供的接口编写串行搜索树，Occualizer运行时库负责保证树操作的遍历过程观测到的是一个一致的状态，同时缓存写操作并原子地应用树操作对一个或多个节点的修改。具体而言，用户需要声明操作的开始点和结束点，以及树遍历的结束点，并通过Occualizer提供的接口来分配或销毁的节点，以及读取和写入节点字段。

本地化写时复制示意图
并行一个搜索树实现可以通过简单的写时复制（copy-on-write，COW）实现，但这样会导致任何写操作都将锁住并复制从叶结点到根结点路径上所有节点，造成严重的可扩展性瓶颈。为此，Occualizer提出并使用了一种针对搜索树的写入时复制方法，本地化写时复制（localized copy-on-write，LCOW）。相比于传统写时复制，本地化写时复制通常不针对树的根节点，从而避免产生同步瓶颈。概括地说，本地化写时复制追踪并缓存每个操作写入的节点，并在操作完成时识别出一个包含这些节点的最小子树，从而可仅对这一子树实施写时复制，并通过原子地修改子树根节点来提交（commit）操作。
Occualizer和其他自动并行化方法产生的并发搜索树性能与手动设计与实现的并发搜索树性能比较（R-X表示负载中读操作比例为X%）
为评估Occualizer的效果，作者分别选取了B+树、前缀树和红黑树的串行实现来应用Occualizer。作为基准，作者使用了其他自动并行化方法来转化这些串行实现，包括使用全局锁、使用事务性内存（transactional memory）来保护树操作、使用CX通配构造方法（universal construction）、使用传统写时复制方法，作者还选取了三个手动设计与实现的并发B+树、前缀树和红黑树。实验结果显示Occualizer显著缩小了读写工作负载下自动转化的并发树和手动设计的并发树之间的性能差距：B+树、前缀树和红黑树的差距分别缩小了13.54倍、1.38倍和8.64倍。
Occualizer转化的B+树和Masstree在TPC-C下的性能对比
作者将内存数据库STOv2的Masstree索引替换为Occualizer转化的B+树，并通过TPC-C负载评估了其性能。结果显示，Occualizer转化的B+树性能低于Masstree，但它们之间的性能差距随着更多线程的增加而缩小。

Immortal Threads: Multithreaded Event-driven Intermittent Computing on Ultra-Low-Power Microcontrollers

Eren Yıldız, Ege University; Lijun Chen and Kasim Sinan Yıldırım, University of Trento
近年来，随着低功耗电子设备和能量收集技术的发展，出现了不使用电池的自维持系统（sustainable system）。这类系统使用电容储存从日光、电磁辐射等环境因素中收集的能量，能量足够时启动系统，执行传感、计算、通信等操作，能量用尽时关闭系统。因此，这类系统上的软件需要在充放电周期之间间歇性地工作。
间歇性的断电对软件设计的挑战在于：首先，断电会使易失性存储中的程序状态丢失；其次，断电可能导致非易失性存储被写入不一致的状态。先前的工作主要采用（1）检查点（2）基于任务的编程模型，来保证程序的可进展和正确性。第一种方法在断电后会将程序恢复到最近的检查点，然后再继续执行。这一方法有较大的保存和恢复开销。第二种方法要求开发者将程序实现为一系列任务，任务之间的转移遵循all-or-nothing的语义。这种方法的保存和恢复开销很低，但是使用该编程模型开发事件驱动程序十分困难。由于大部分传感应用都采用事件驱动，该模型不适合许多间歇计算的使用场景。
本文提出的Immortal Threads为间歇计算（intermittent computing）提供了一个与有栈多线程类似的编程模型。开发者可以在对间歇不感知的情况下，编写传统的事件驱动多线程代码，同时获得与事件驱动模型类似的低开销。
Immortal Threads由编程接口、编译器前端和运行时库组成。用户可以使用普通的有栈多线程可抢占模型编写应用程序，无需关心可能的断电。编译器前端负责插入库中与断电处理有关的代码，将有栈的用户代码翻译成无栈的中间代码。
作者在真实硬件上将Immortal Threads与现有的间歇计算运行时对比。测试表明，Immortal Threads可以提供更好的编程模型，同时开销与传统方法类似。

Debugging the OmniTable Way

Andrew Quinn, UC Santa Cruz; Jason Flinn, Meta; Michael Cafarella, MIT; Baris Kasikci, University of Michigan
开发人员将大部分时间花费在软件调试上。软件调试常常是通过观察程序执行的状态实现，对于复杂的软件故障（如原子性违例和性能降低），开发人员往往需要编写用于观察、收集、打印软件运行状态的调试程序。本文将这一过程称为”调试编程“。现有调试编程方法（编写gdb脚本、基于printf的代码插装、二进制插装等）在进行复杂的调试编程时往往引入很高的性能开销，降低软件运行性能。此外，复杂的调试编程本身是困难的，导致开发人员编写的调试程序可能自身存在故障。此前工作要么通过并发调试和底层优化等方式降低调试程序的性能开销，但没有降低调试的复杂性；要么使用高阶编程模型观察和总结程序状态，降低了调试的复杂性，但没有降低调试的性能开销，并且限制了程序员能够观察到的状态。
本文提出了OmniTable，一种新的调试编程范式。OmniTable在程序执行过程中将运行状态存储在一个关系型数据库中，其中包含了每条指令执行前的体系结构状态（如内存值和寄存器值）。OmniTable为开发人员提供了SQL查询接口，开发人员可以使用SQL语句进行调试编程，查询观察程序状态。使用现有数据库原语和新的查询操作符（如函数遍历操作），开发人员可以查看程序状态在函数执行等较高抽象层面的视图，降低了调试的难度。
下图举例说明了OmniTable为开发人员提供的信息和使用方法，表1是一次执行中，OmniTable提供的Vars(ot)视图，显示了OmniTable执行过程中每条指令所在的作用域中存在的变量的值，其中eip表示程序计数器的值、name表示变量的名称、value表示变量的值；表2是Functs(ot)视图，显示了OmniTable执行过程中函数进入或退出的信息，其中name表示函数的名称，args是函数调用的参数和值的映射，rVal表示函数的返回值。而time、enterTime、exitTime是单调递增的逻辑时间，代表OmniTable中时间的全序关系，具体的值与实现相关。Query 1中开发人员使用SQL语句查询一个时间窗口内函数lookupKey被调用时不同的参数key的数量，在实践中该项查询可能用于识别程序工作集大小等调试目的。
OmniTable提供了相当于在每条执行执行后进行核心转储的信息，因此简单地在运行时捕获并存储这些信息将带来巨大的性能和存储开销，是不现实的。作者设计了SteamDrill系统，使用确定性捕获重放机制、在运行时仅收集所有不确定状态（如用户输入），以惰性实例化（Lazy materialization）的方式，仅当开发人员发出查询请求时重放相关联的执行，产生查询所需的状态。SteamDrill的查询规划机制将查询操作分解为多个部分查询，使用在一部分更为高效的查询中得到的结果作为过滤器，减少更为昂贵的查询操作。

XRP: In-Kernel Storage Functions with eBPF

Yuhong Zhong, Haoyu Li, Yu Jian Wu, Ioannis Zarkadas, Jeffrey Tao, Evan Mesterhazy, Michael Makris, Junfeng Yang, Columbia University; Amy Tai, Google; Ryan Stutsman, University of Utah; Asaf Cidon, Columbia University
随着微秒级的NVMe存储设备的出现，Linux存储软件栈在总访问开销中的占比也随之明显上升。如下图所示，在最新的高速存储设备上，来自软件栈的开销几乎让访问开销翻倍了。
针对这个问题，本文认为现有的方案都太激进了。它们都需要对应用或是硬件有着侵入性的修改。例如有些kernel bypass的方案如SPDK允许应用去直接访问底下的设备，但是也会强迫应用实现自己的文件系统，同时放弃隔离性和安全性，并且还需要polling导致了CPU资源的浪费（尤其是IO利用率低的时候polling的坏处尤为明显）。本文的测试数据展示出使用SPDK的应用在可调度线程数量大于CPU数量时会导致更差的尾时延，甚至吞吐量都会严重下降。因此，本文希望能够探寻一种既易于部署，又无需对应用有过多侵入修改，能够充分利用现有kernel和文件系统功能的高速存储访问方案。
本文观察到当前部分应用的一些存储IO操作中，需要用户态去处理大量的中间结果。如果每个中间结果都需要往返于内核态和用户态才能处理的话，会引入大量的传递开销（如下图所示，开销主要来自于内核上下文切换和文件系统，此外bio层的开销相比于设备驱动也更为明显）。
一个典型的例子是当应用进行基于b-tree的索引，应用的最终目的其实是想找到最末端的叶子节点，但是通常的b-tree搜索过程中会将搜索路径上的每一个节点读取到用户态。该过程中就会反复多次触发上图中的各项开销。针对这个场景，本文提出XRP，其核心解决思路（如下图）是将多次应用逻辑在软件栈底层batch起来，消除冗余的上层开销。具体来说，本文利用eBPF技术，将部分原本在用户态执行的应用逻辑放入内核态的NVMe驱动层，从而使该过程中的中间结果不用再返回用户态，而是在内核态中就可以继续下一步处理。
之所以选择hook在NVMe驱动层则是因为在内核态的位置也应当尽量能避免经过上图中那些开销较大的步骤（如ext4和bio层）。如下图所示，作者之前的研究中有对深度为10的b-tree进行测试，如果不绕过内核中的syscall和文件系统层，那在延时和吞吐量上的提升并不明显。而在NVMe驱动层则能显著提升这两项性能。
尽管这个方法看起来很直观，但是依然存在两个主要挑战：
  1. NVMe驱动层目前无法访问文件系统的元数据。例如在索引穿越场景下，NVMe中的XRP在处理一个read操作时会在从当前block中通过offset去提取下一个block。但是它无法获知这个offset所关联的物理block，因为它不知道文件系统的相关元数据。
  2. XRP系统难以应对由文件系统处理的并发读写操作。如果文件发生改写，NVMe driver层无法观察到缓存在kernel page cache中的文件更改，这可能会导致XRP读取到错误的数据。而用锁来保护文件结构带来的开销则会比较大。
针对上述挑战，作者观察到大部分on-disk的数据结构都非常稳定。常用的数据库大部分采用了index文件创建后不再更改或更改频率较低的索引文件结构，且大部分数据库会选择自行管理page cache而不是使用fs提供的page cache。另一方面，大部分索引都集中在少数几个大文件中，且每个索引都不会跨多个文件。因此，本文的解决方式是限定XRP的使用场景为索引文件结构比较稳定和用户管理page cache的场景，同时缓存和维护单个文件所需的logical-to-physical-mapping信息（metadata digest）以供NVMe driver层访问。大致架构如下图所示，当NVMe存储设备发送中断后，中断handler最终会调用hook的BPF函数进行处理。该函数利用metadata digest所提供的接口安全地访问少量ext4文件系统元数据从而绕过NVMe驱动以上所有软件层的介入直到本次resubmission逻辑全部处理完成后返回用户态。
本文在Linux上通过eBPF实现了支持ext4文件系统的XRP原型。为了和Baseline（linux的同步与异步syscall以及kernel bypass方案SPDK）进行对比，作者构建了一个简单的KV存储程序——BPF-KV。在尾延时方面可以看到，99th下XRP显著好于linux的同步和异步syscall，而在99.9th下，尽管大部分时候依然是SPDK好于XRP，但是当线程数大于执行的物理核心数（6个）时，SPDK的尾时延会显著上升，而XRP则依然稳定。
吞吐量方面也类似，单线程下，随着索引深度变深，所有测试的吞吐量都下降，但是XRP依然优于Linux的同步和异步syscall，仅次于SPDK，而多线程时，当线程数量增多超过6个后SPDK吞吐量则会明显下降，而XRP则体现出了良好的可扩展性。
如下图，本文进一步在更多线程下进行测试，发现超多线程场景下SPDK的吞吐量甚至会下降3倍，而XRP在延迟和吞吐量上依然优秀。
为了测试在真实数据库上的性能，本文对mongoDB的默认存储引擎WiredTiger使用eBPF进行了改造并与改造前进行对比。从下图可知在各种测试条件下，使用XRP都能提升吞吐量并降低延迟。

TriCache: A User-Transparent Block Cache Enabling High-Performance Out-of-Core Processing with In-Memory Programs

Guanyu Feng and Huanqi Cao, Tsinghua University; Xiaowei Zhu, Ant Group; Bowen Yu, Yuanwei Wang, Zixuan Ma, Shengqi Chen, and Wenguang Chen, Tsinghua University
这篇文章由清华大学的研究者和蚂蚁集团合作完成，提出了一种高效且用户透明的SSD存储缓存方法。
目前，尽管NVMe SSD已经可以满足高性能和大容量，但其仍受制于块设备的接口，且访问时延通常超过DRAM的100倍。为了消除SSD和DRAM之间的性能鸿沟，实现高效的SSD数据访问，应用通常都会采用将DRAM作为SSD数据的缓存的方案。目前的DRAM缓存有两类方案，一类是利用操作系统提供的page cache，这类方案的优点在于用户不需要手动对缓存进行控制，然而其存在性能和可扩展性的问题，导致无法充分NVMe SSD的性能。因此，许多数据密集型应用选择自己维护缓存，这一做法虽然可以达到更高的性能，但会导致开发难度增加，代码的可读性和可维护性变差。针对上述问题，本文希望在用户态实现高效、用户透明的缓存。
本文提出的系统名为TriCache，架构如上图所示，主要包含一个LLVM的编译器插件和一个运行时模块。首先，TriCache需要使用LLVM编译器将目标应用程序编译为LLVM的字节码，然后通过编译器插件识别到字节码中所有的load和store指令，在访存前插入一条地址翻译的指令（get_raw_ptr），将原有的地址修改为经过TriCache翻译的地址。这一函数会从下层缓存和存储系统中获取数据，并返回其在内存中缓存的地址供应用正常使用，下图左侧是一个翻译的例子。上图虚线框内是TriCache的运行时，包含多级的缓存。get_raw_ptr请求首先会走到Direct SATC（Software Address Translation Cache）模块，这是一个直接映射的线程私有小缓存。当缓存不命中时，进入第二级的Private SATC模块，这是一个组相连（set associative）的线程私有缓存。最下层称为Shared Cache，是一个共享的缓存。为了避免现有操作系统page cache中由于大锁导致的可扩展性问题，TriCache中的共享缓存采用了分区的设计，通过哈希决定每个地址所在的缓存分区。
分层缓存的巧妙之处在于，第一，Private SATC和Direct SATC是线程私有的，可以确保当前线程频繁访问的数据不会被踢出，且对其的访问不用涉及全局状态甚至是跨NUMA状态的操作；第二，在组相连的Private SATC之上再添加一个Direct SATC缓存，避免了在Private SATC中进行哈希查找等操作对热数据访问带来的开销。
作者将TriCache应用于多种场景进行测试，包括图计算、KV数据库和大数据分析，结果显示TriCache相比Linux的page cache性能有数量级的提升，相比手工设计的缓存方案也有相似或更优的性能。下图是图计算场景的一个性能对比，在不同内存可用量的情况下对比不同系统的计算时间。Ligra是一个内存中的图计算框架，可以分别通过swap的方式和使用TriCache的方式访问SSD中的数据，FlashGraph是一个为SSD设计的图计算框架。在512G内存的情况下，所有数据都缓存在内存中，TriCache最多会带来64%的额外性能开销；在16G内存的情况下，FlashGraph在两个工作负载中由于OOM无法完成计算，而TriCache相比操作系统的swapping提升高达38.3倍。

Tiger: Disk-Adaptive Redundancy Without Placement Restrictions

Saurabh Kadekodi, Google; Francisco Maturana and Sanjith Athlur, Carnegie Mellon University; Arif Merchant, Google; K. V. Rashmi and Gregory R. Ganger, Carnegie Mellon University
这篇工作由谷歌和卡内基梅隆大学的研究者合作完成，关注的是在大规模存储系统中冗余方案的设计问题。
目前的大规模存储集群通常会部署成百上千块不同品牌或型号的硬盘，此时硬盘的故障十分容易产生。为了避免由于硬盘故障造成的数据丢失和可用性下降，大规模存储系统通常会采用冗余设计。例如，使用纠删码（erasure coding, EC）的方案后，数据被划分成k块（data chunk），向其中添加n-k块校验块（parity chunk）后形成了一个由n个块组成的条带(stripe)，这一条带允许容忍n-k块数据的故障，带来的存储空间额外开销是n/k。
本文关注数据条带的放置问题，下图展示了三种不同的放置算法，其中不同颜色代表不同可靠性（用年均故障率衡量，AFR）的硬盘，红色可靠性最低，蓝色可靠性最高，黑色矩形代表数据条带，越短的条带拥有越高的数据冗余。左侧传统算法中，条带的选择忽视了不同硬盘可靠性的区别，导致其必须保守地选择条带长度，空间的利用率较低。这是因为在相同可靠性要求（用平均数据丢失时间衡量，MTTDL）的情况下，使用越可靠的硬盘时冗余可以越少。中间的名为Pacemaker的放置算法考虑了不同硬盘的可靠性区别，但同一个条带只能放置在相同可靠性级别的硬盘上，对于数据放置位置有比较强的要求。本文提出的系统名为Tiger，消除了条带放置的限制，可以将不同可靠性级别的磁盘用于同一个条带。
Tiger的架构图如下图所示，它的核心抽象称为eclectic stripe，指的是一个包含不同可靠性级别硬盘的数据条带，而放置策略相同（使用相同硬盘）的eclectic stripe被组织成一个eclectic volume。Eclectic stripe allocator（ESAllocator）负责选择若干块硬盘组成一个eclectic stripe，并把选择的信息交给Eclectic stripe manager。其中的MTTDL engine会检查由这些磁盘组成的数据条带是否满足用户所需的MTTDL。如果不满足要求，会要求ESAllocator调整分配策略并再次检查。在数据条带建立好后，ESAllocator将其交给Eclectic volume manager（EVManager），其会将这一条带添加到现有的eclectic volume中，或创建一个新的eclectic volume。由于单块硬盘的可靠性是随时间变化的，EVManager中的Health inspector会持续监控每个volume，若其中的硬盘可靠性发生变化，会通知EVManager，EVManager获取条带的元信息后由Stripe reorganizer负责冗余级别切换。如果当前的条带已经无法满足MTTDL，会通知ESAllocator重新决定数据的放置。
值得注意的是，Tiger中将相同放置策略的条带组织成了一个volume，这极大地减轻了Health inspector所需的工作量。由于同一volume中的条带位于相同的硬盘，因此监控一个volume就可以起到监控其中所有条带的效果。
本文的测试使用BlackBlaze和Google四个集群真实场景的日志进行模拟。测试结果显示，Tiger的放置策略相比Pacemaker，硬盘的利用率更高，风险多样性更好，空间利用率更高。下图展示了在不同可靠性条件下两种策略可用硬盘的比例，在4个集群中，Tiger在所有情况下都有超过75%的硬盘可以被利用，而Pacemaker的利用率显著地更低一些。

zIO: Accelerating IO-Intensive Applications with Transparent Zero-Copy IO

Timothy Stamler, Deukyeon Hwang, and Amanda Raybuck, UT Austin; Wei Zhang, Microsoft; Simon Peter, University of Washington
该工作面向I/O密集型应用场景，提出了一套对应用程序透明的zero-copy机制，旨在通过消除应用程序内部以及I/O栈中不必要的I/O数据拷贝以提升整体性能。
作者观察到现代I/O密集型应用程序在每次处理I/O请求的过程中通常会涉及多次的I/O数据拷贝，包括应用程序内部处理I/O请求时的拷贝以及应用程序与I/O栈交互时的拷贝。这些I/O数据拷贝的目的主要是简化程序开发和数据处理，例如对齐、padding、序列化等操作，此外一份I/O数据的多份拷贝也允许不同独立子系统不用担心其所使用数据的生命周期问题。该工作在调查了多种I/O密集型应用后将它们的I/O数据拷贝次数总结如下表1所示，可以看出处理一个I/O请求可能需要高达8次的I/O数据拷贝。
然而多次I/O数据拷贝未必会导致明显的性能开销，拷贝涉及的数据量大小也是一个重要的性能影响因素。作者以Redis处理SET请求为例进行了一系列测试，实验结果如下图1所示，数据拷贝所消耗的CPU资源占比随着I/O请求的大小增长不断升高，最高可以占用超过50%的CPU资源。因此在I/O请求数据量较大的场景下，降低数据拷贝开销对于提升应用程序性能是必要的，而zero-copy方法则是一种非常有效的优化手段。
现有zero-copy方案都要求对于应用程序进行侵入式修改以消除与I/O栈交互时的拷贝，同时也无法消除应用程序内部的I/O数据拷贝，因此该工作想要提供一套透明且能够消除上述两种拷贝的zero-copy方案。作者提出了zIO方案，主要思想是跟踪应用程序从I/O栈中读取数据（例如recv操作）到其向I/O栈写入数据（例如send操作），对于处理流程中未经修改的数据消除有关的拷贝操作，对于被修改的数据则依旧进行拷贝。zIO整体设计如下图2所示，包括：1）通过拦截API调用的方式透明地捕获应用程序的I/O数据拷贝、与I/O栈的交互等操作，追踪多次操作之间的内存关系；2）将API原有的内存拷贝实现变更为映射为只读内存区域，并利用userfaultfd机制拦截对于这些区域的修改操作，若只读内存区域被修改，则将修改的内存页进行拷贝并做记录；3）在应用程序最终将I/O数据写入I/O栈时，若对应内存区域未被修改则直接使用源数据内存实现zero-copy，否则拷贝被修改后的数据内容。该工作也考虑了NVM场景下的zero-copy优化。
根据作者对于原型系统的评测，zIO对于Redis在特定场景下的性能提升可以高达2.5倍，而对Icecast的性能则最高可以优化1.25倍。
Q&A
Q: 是否有考虑某些应用场景下，zIO可能会比拷贝引入更大的性能开销？比如I/O数据量很小，或者应用程序一开始就修改了I/O数据导致追踪page fault开销大？
A: 考虑了，zIO经过对现有I/O密集型应用程序的统计后设定了一些阈值，当zIO本身开销超过一定阈值后就会fallback到原有使用内存拷贝的方法。
Q: 对于那些非I/O相关的数据拷贝，例如应用内的某些字符串处理，zIO如何区分它们避免对这些操作进行zero-copy？
A: zIO会全程对目标内存进行追踪，因此使用zero-copy的内存区域一定会从I/O栈开始就被zIO记录了，因此可以避免对非I/O操作的变更。

Verifying the DaisyNFS concurrent and crash-safe file system with sequential reasoning

Tej Chajed, MIT CSAIL; Joseph Tassarotti, Boston College; Mark Theng, M. Frans Kaashoek, and Nickolai Zeldovich, MIT CSAIL
这篇工作研究的是如何验证一个文件系统在并发及系统可能随时崩溃（crash）场景下的正确性。本文提出了一种将并发与crash-safety的证明隔离到一个事务系统（transaction system），然后对剩余文件系统部分采用串行证明的做法，这种做法有助于系统增量开发，并且证明负担小，开发的系统性能好。这篇工作是MIT团队继Perennial，GoJournal之后又一验证系统并发崩溃安全性的工作。
本工作的架构如图所示，从实现角度，DaisyNFS这一网络文件系统的实现基于Go语言，DaisyNFS调用了GoTxn事务系统。从验证角度，下层GoTxn拓展了其前序工作验证的GoJournal，GoTxn在规约中描述了以何种方式调用事务系统能够仅仅用串行的方式证明；使用这一规约，上层DaisyNFS的操作使用了Dafny这一串行验证语言进行证明，享受到了串行证明的自动化与相对较小的证明负担。
这篇工作要解决的核心挑战是如何隔离并发与崩溃一致性的证明，他们提出了simulation transfer theorem来形式化这一直觉，即GoTxn系统的事务主体只需要串行证明，并仍然能够得到在并发和崩溃下的正确性保障。他们在Coq中证明了GoTxn符合这一正确性条件。在获得了DaisyNFS的串行证明后，就能借助GoTxn的正确性得到DaisyNFS在并发和崩溃条件下的正确性。测试显示了DaisyNFS相比于基于ext4的Linux NFS服务器能够取得至少60%的吞吐性能。
本工作目前存在一些局限，包括目前只能支持同步的commit操作，没有验证系统没有死锁，以及连接DaisyNFS和GoTxn的定理目前仅在纸上证明。

Design and Verification of the Arm Confidential Compute Architecture

Xupeng Li and Xuheng Li, Columbia University; Christoffer Dall, Arm Ltd; Ronghui Gu and Jason Nieh, Columbia University; Yousuf Sait and Gareth Stockwell, Arm Ltd
本文针对ARM架构提出了一种新的硬件安全机制CCA（Confidential Compute Architecture），并且通过形式化验证保证了CCA固件的正确性。本工作由哥伦比亚大学的Ronghui Gu（顾荣辉）团队、Jason Nieh（聂哲生）团队以及Arm团队合作完成。
首先介绍本文考虑的威胁模型。攻击者可以通过被攻破的hypervisor、其他用户的虚拟机等软件来窃取用户虚拟机中的私有数据，用户本身不会恶意泄漏自己的数据，另外侧信道攻击等也不在本文考虑的范围内。
接下来介绍CCA的设计。如上图所示，为了增强安全性，CCA中引入了一个称为Realm的执行环境，与现有的secure world以及normal world相互隔离。安全VM运行在Realm中的非特权模式下，而一个称为RMM（Realm Management Monitor）的固件运行在Realm的特权模式下，负责管理Realm。在内存隔离方面，GPT（Granule Protection Table）作为一个第三阶段页表被引入以控制系统中所有模块对每个物理页的访问。运行在Realm和secure world中的软件无法访问对方的内存，但它们都可以访问normal world的内存。此外，CCA对Realm中运行的所有安全VM均使用相同的密钥进行加密，消除了密钥个数对安全VM数量造成的限制。CCA中还引入一个称为EL3M的固件，在Root world中运行，具有最高权限，负责管理GPT以及CPU执行在Realm、secure world、normal world之间的切换。TCB也只包括Realm中的RMM以及EL3M。
Realm提供的安全性保证都建立在RMM等CCA固件的基础上，因此对这些固件的功能正确性和安全性进行形式化验证是很有必要的。具体来说，本文证明了CCA能够保证Realm的confidentiality和integrity，confidentiality的意思是Realm对私有数据的修改只对Realm可见，integrity的意思是Realm不会观察到它没有对私有数据做过的修改。证明这些性质面临四个方面的挑战。第一，固件中使用hand-over-hand locking处理对数据结构的细粒度并发访问，这要求考虑所有可能的并发情况。第二，相比于TSO等其它内存模型，Arm使用的弱内存模型允许更多对内存的乱序访问，使得验证需要考虑的并发执行情况更加复杂。第三，固件的实现中同时包含C代码和汇编代码，需要对C语言和汇编语言之间的交互进行建模。最后，传统的安全性定义non-interference对于CCA来说太严格了，和上述本文想要验证的性质不一致，需要重新定义安全性。针对这些挑战，本文提出了一系列新的验证技术，是第一个同时解决以上四个挑战的工作。
本文使用交互式验证工具Coq进行验证。CCA中需要验证的固件主要包括RMM和EL3M，其中RMM包含3.2K行C代码和300行汇编，EL3M包含100行C代码和700行汇编。如上表所示，验证RMM和EL3M总共需要20.6K行的Coq代码。基于形式化验证技术，本文作者在CCA固件中找到了多个真实的bug。
为了测试CCA引入的性能开销，论文修改了Linux KVM，把CCA集成进去并使用真实的应用进行测试。测试结果表明，使用CCA和不使用CCA的情况下，应用的性能差距不大，证明了CCA带来的性能开销不大。

DuoAI: Fast, Automated Inference of Inductive Invariants for Verifying Distributed Protocols

Jianan Yao, Runzhou Tao, Ronghui Gu, and Jason Nieh, Columbia University
本文主要关注分布式协议的自动验证问题，由哥伦比亚大学的Ronghui Gu（顾荣辉）团队和Jason Nieh（聂哲生）团队合作完成，这也是他们继DistAI（OSDI'21）之后又一篇自动化验证分布式协议的工作。
验证分布式协议正确性的关键在于找到分布式系统满足的不变式（inductive invariant），从而基于inductive invariant推导出分布式协议的正确性（safety property）。具体来说，inductive invariant是描述系统性质的命题，在系统运行的任意时刻都成立。在作者之前的工作DistAI中，只能自动生成含有全称量词的inductive invariant，无法生成含有存在量词的inductive invariant，而证明某些分布式协议恰恰需要含有存在量词的inductive invariant，这使得DistAI无法证明某些分布式协议。本文提出的工具DuoAI克服了这个问题，能够生成含有存在量词的inductive invariant，从而能够证明更多的分布式协议。此外本文还提出了性能优化措施，加快验证的速度。
首先，DuoAI以析取范式（disjunctive normal form）的形式枚举潜在的inductive invariant。通过限制谓词个数等，DuoAI可以得到一个有限的搜索空间，之后根据这个搜索空间中公式之间的蕴含关系，DuoAI建立如上图所示的minimum implication graph。这是一个有向无环图，图中每个点是一个公式，公式A有边指向公式B表示公式A可以推导出公式B，公式A比公式B强，公式B比公式A弱。
之后DuoAI会通过类似随机测试的方式过滤掉一部分不是inductive invariant的公式。具体来说，DuoAI设置不同的机器节点数量，模拟协议的运行，得到一组系统状态。然后检查minimum implication graph中的公式是否在这些状态下都成立，如果某个公式不成立，那么这个公式就不是inductive invariant，会被去掉。
最后，DuoAI基于SMT solver查找剩余的公式中哪些是inductive invariant。为了加快搜索速度，DuoAI并行地运行两种搜索算法同时查找inductive invariant。第一种搜索算法先从minimum implication graph的根结点开始，尝试验证当前公式是否是inductive invariant并且能够推导出safety property。如果是，那么算法结束，否则说明当前公式太强，那么算法会把当前公式弱化为其子节点的公式，继续进行验证。第二种搜索算法首先搜索出不含存在量词的inductive invariant，然后再不断增加含有存在量词的公式到当前inductive invariant中直到可以推导出safety property。如果证明分布式协议时需要的含存在量词的公式比较多，那么第一种搜索算法会更快，否则第二种算法搜索速度更快。
作者将DuoAI运行在了27个不同的分布式协议上，并和其他已有的验证工具进行对比。从结果来看，DuoAI能够验证的协议个数最多，运行所需的时间在大多数情况下也快于其他工具，证明了DuoAI强大的验证能力。

Verifying Hardware Security Modules with Information-Preserving Refinement

Anish Athalye, M. Frans Kaashoek, and Nickolai Zeldovich, MIT CSAIL
本文提出了形式化验证硬件安全模块HSMs（hardware security modules）的框架Knox，作者来自MIT的PDOS实验室。为了保证安全性，一些核心的安全性功能往往被实现在专门的硬件设备上，例如HSMs被广泛用于在服务器端存储密钥等关键数据，所以这类硬件安全模块的安全性就变得至关重要。Knox提供了一个框架可以验证用verilog、c实现的硬件安全模块。
首先介绍本文考虑的威胁模型。攻击者可以直接访问硬件安全模块输入输出的数字信号，通过设置硬件的输入信号、读取硬件的输出信号来尝试窃取密钥等信息。如上图表示，攻击者可以设置输入信号rx和cts并读取每个cycle的输出信号tx和rts。因此，和以往验证软件正确性等工作不同，Knox需要在wire层面对硬件实现进行验证。
接下来我们介绍论文中的正确性定义。以上面这个模块为例，使用者通过编写functional specification，定义这个模块应该实现的业务逻辑。上面这个代码定义了一个存储密码和数据的模块，store用来设置密码pin和数据secret，retrieve判断用户给的密码guess是否正确，如果正确就输出secret，否则如果连续超过10次输错密码，那么就不允许继续尝试。
定义好正确性之后，Knox会验证硬件安全模块的实现physical implementation是否和正确性定义functional specification一致。Knox定义了information preserving refinement，表示physical implementation实现了functional specification相同的业务逻辑，它们之间存在refinement关系。具体来说，如上图所示，information preserving refinement涉及到两个world，real world中安全模块内部是verilog等具体代码实现的，而在ideal world中安全模块内部是用户定义的正确性标准functional specification。functional interface是functional specification的调用接口，physical interface是physical implementation的调用接口，Driver负责把functional specification的调用转化为对physical implementation的调用，emulator把对physical implementation的调用转化为对functional specification的调用。证明information preserving refinement，就是证明在给定相同输入信号的情况下，调用者无法通过输出信号区分real world和ideal world。
Knox框架基于Rosette语言实现。如上表所示，论文基于Knox实现并验证了3个硬件安全模块，成功找到了实现中的bug。其中的TOTP包含2950行verilog以及360行C和汇编，而编写的spec只有10行代码，proof代码只有830行，证明了Knox的证明负担是可接受的，具有一定实用性。
