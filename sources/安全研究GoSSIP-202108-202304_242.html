Session-10: Security and Private Messaging

BlackBox: A Container Security Monitor for Protecting Containers on Untrusted Operating Systems

Alexander Van't Hof and Jason Nieh, Columbia University
这篇论文使用了硬件虚拟化对容器进行隔离，从而实现了轻量化的容器隔离与安全加强。文章的核心想法并不新奇，有很多类似的工作采用了虚拟化以及VMFUNC做内存隔离。其核心的贡献点，在于能够支持未经修改Docker应用，以及对syscall的支持较为完整。由此可见，Solid的工作也是会受到PC们的青睐的。
背景
容器作为共享计算的基础设施，被广泛地运用在应用程序的部署，打包与应用隔离中。相较于虚拟机的方式，容器所需要的资源更加少，有更好的启动性能与IO的性能。但是，容器以来与特权OS作为安全的保障，然后以Linux为代表的商用OS代码量大，复杂存在很多攻击的漏洞。攻击者可以通过攻击OS从而实现对容器中数据和内容的攻击。
近几年也有不少的工作，通过不同的软硬件机制，对容器的安全进行加强。例如，基于硬件Enclave的方式对容器中的代码和数据进行强隔离，但是需要应用开发者重写代码，并且会引入较高的CPU计算的开销。而基于虚拟化的方式，也会增加虚拟化的开销同时引入guest OS的代码扩大的TCB。因此当前缺少一种轻量化的安全容器方案。
设计
为了实现轻量级安全容器，作者提出了BlackBox的设计，它能够提供细粒度的内存隔离，同时保护容器的完整性和机密性，并且不需要相信OS。如上图所示，在BlackBox中引入了一个新的安全监视器：container security monitor (CSM), 它负责提供一个受保护的内存空间protected physical address space（PPASes），保证所有外部的代码无法访问受保护的内存地址中的数据，同时内部的代码也无法访问其他的PPASes空间。
BlackBox重用了虚拟化技术，只用于对内存的隔离，而不需要做任何虚拟化相关的工作，从而极大减少了TCB的大小（不需要GuestOS的介入）。BlackBox不需要修改容器中运行的应用程序。应用程序和OS之间的交互会受到CSM的检查（例如系统调用，中断和异常），如果一个受保护的容器需要切换到OS中运行，CSM会将所有与容器相关的寄存器保存并清零；反之，CSM会恢复容器的上下文，并且给予其访问对应PPAse的权限。其中syscall的参数是唯一一个容器内的内容需要被OS访问。CSM会将syscal的参数拷贝到OS的内存中，同时对IO的数据进行端到端的加密。为了保证没有恶意的代码运行在容器中，所有加载到容器中的代码，都需要容器的提供者签名并且加密，由CSM负责解密并加载。
内存隔离
CSM保证OS无法直接访问容器中的内存，为了减少CSM的TCB，CSM允许OS进行内存分配。但是与此同时，需要防止OS发起基于内存的Iago攻击。例如用户希望通过mmap得到一块没有被使用过的内存，但是OS可能返回一个栈地址空间，导致栈上的数据被覆盖重写。
为了解决这个问题，BlackBox不允许OS直接修改容器的页表，而需要CSM介入。CSM会对页表修改的操作做两个检查：（1）所有映射的虚拟地址是一个合法的地址；（2）映射的物理地址不在容器所有的PPAS中。
除此之外，BlackBox还提供额外的接口允许OS以CoW的方式获得container中内存数据，但是需要经过CSM的额外的安全检查；同时BlackBox也支持动态的内存回收。
很多系统调用会需要传递内存数据，在BlackBox中采用了和OS共享的缓存，作为系统调用源内存地址。CSM会将需要传递的内存数据拷贝到该缓存区中。对于系统调用的返回值，CSM也会做检查，保证所有的返回值落在预定义的返回值区间内。
进程间通信
类似于pipe以及Unix socket这类system cal允许实现进程间通信。当container想要和外部通信前，会将需要传递的数据加密并拷贝到syscall的共享内存中。数据的加密传输同样应用在read/recvmsg这类调用时。在实现IPC的时候，需要使用futex进行同步保护，因为futex需要OS和container共享同一个futex的标记，所以CSM提供了一个新的CSM call允许OS通过该接口读取在container中存储的futex标记。同时，还需要实现通知的机制，BlackBox采用了signal的机制，但是由于OS需要创建一个signal的栈，所以在创建的时候，OS将signal的栈建立在PPAS之外，当处理signal的时候，CSM会将signal的栈移到PPAS之中。当signal执行结束之后，再将signal的栈移到PPAS之外。
容器的文件系统
为了减少TCB，BlackBox让应用加密保护敏感的数据，并且允许OS加载加密的二进制文件并且正常执行。
实验
作者在两个Arm的平台：Raspberry Pi 4 Model B with a 4-core Cortex-A72以及AMD Seattle Rev.B0 server with an 8-core Cortex-A57 64-bit ARMv8-A 2 GHz AMD Opteron A1100 SoC进行的测试。比较了BlackBox和docker之间的性能。
作者选择了四个比较的对象（以native没有采用容器隔离作为baseline）：
（1）Docker以及未经修改了Linux容器；
（2）BlackBox以及未经修改的Linux容器，但使能了NPT；
（3）BlackBox使用CSM对容器进行管理，但是没有使能加密IPC；
（4）BlackBox采用了CSM以及加密的IPC等。
测试结构显示了：
  1. null syscall上BlackBox虽然会导致一定的overhead，但是主要的开销在seccomp做的syscall过滤。而CSM call在Arm的架构上因为有独自的EL2的寄存器，所以开销只在于存储与恢复通用寄存器，因此不是主要的开销。
  2. 读和写会造成小于两倍的开销，因为需要将读写的内容先拷贝到共享的syscall缓存中。
  3. Fork会造成小于三倍的开销，因为在exec的时候会调用mmap需要进行额外的检查，同时加载的binary需要经过解密。
  4. 加密的IPC在大多数的场景中的开销都比较小，但是在pipe, UNIX socket等IPC机制中的开销非常的明显。当然，这部分开销也是显而易见的，因为需要对传输的数据进行加解密保护。
  5. 作者在memcached, MySQL, and Nginx这些应用上测试结果表明，在真实应用上BlackBox的开销小于15%
总结
该论文采用的方法：NPT对内存进行隔离，以及一个安全monitor对容器和OS之间的交互进行保护，都是非常成熟的技术。同时在测试部分，也只是和docker进行了比较，没有和其他安全容器的技术进行比较，在部分benchmark上的性能相较于其他方式，并没有明显的提高。
Q&A
Q1：因为BlackBox假设OS是不可信，如何保证运行在OS之下的CSM是可信的呢？
A1：我们认为系统的启动是可信的，我们通过安全启动的方式验证CSM代码的完整性
Q2：有提供运行时验证的机制吗？开发者如何知道，应用程序被安全并完整地加载到了BlackBox之中？
A2：应用程序会被开发者加密，在加载的时候有CSM解密，并且检验其完整性。

Blockaid: Data Access Policy Enforcement for Web Applications

Wen Zhang, UC Berkeley; Eric Sheng, Yugabyte; Michael Chang, UC Berkeley; Aurojit Panda, NYU; Mooly Sagiv, Tel Aviv University; Scott Shenker, UC Berkeley/ICSI
许多Web应用使用关系型数据库来保存一些敏感的用户数据。为了保证这些敏感数据不被任意访问，对数据的访问需要满足一定的安全规则（data-access policies)。Web应用的每个数据库query都需要通过一个access check来保证用户是否有访问权限。先前的工作主要通过以下几种方式来达到：通过静态检查来验证应用代码是否只会发出合规的请求，但是，这要求用户使用特殊的语言或框架，如Jif之类，限制了Web应用的可兼容性；Query modification，会透明地将返回结果中不符合规则的结果删除，这可能会导致unexpected application behavior。
Blockaid通过在用户query和数据库访问之间添加一层能够在运行时拦截用户query并且检查访问可行性的系统，来做到与现有应用兼容的同时，能够完整的返回query结果中是否包含不合规的数据（而不是部分删除结果中的不合规数据导致有误导性的结果）。Web应用发送的每一个query，都会被Blockaid拦截，并检查query是否合规。如果请求合规，Blockaid将请求不经修改地发送给数据库。否则，Blockaid会block这次请求并且返回error。
Blockaid使用基于SQL view的定义来指定一个用户能够访问哪些信息。然而，一次Web应用的请求可能会导致多次数据库的query，下一个query是否合规，可能会和同一个request中先前query的结果相关。因此，作者引入了trace的概念，将一次请求的多个query都考虑进去。为了验证query的合规性，Blockaid将规则转化为SMT公式，并使用SMT solver来进行求解。
虽然SMT solver能够检查很大范围的queries，但是一次检查通常会花费上百毫秒的时间来完成，一次请求可能会发送数十次query，这就导致一个请求的开销可能达到秒级。因此，为了缓解这部分开销，Blockaid将是否合规的判断缓存在Decision cache中，从而减少重复的求解操作。如果直接将一次query在trace下是否合规的结果cache起来的话，缓存命中的概率将很低，因为所有可能的情况会非常多（如不同的参数都会被认为是不同的query）。幸运的是，应用真正的行为是有限的，例如针对一个日历应用的不同event发送的多个query在结构上是一致的，仅仅是event ID不同。因此，Blockaid对这样的信息进行抽象，得到一个decision template，如果先前的一个query是合规的，那么Blockaid会针对query生成decision template并cache起来，之后当这条信息仍然存在于cache中时，满足该decision template的query也会被认为是合规的，这样能够显著提高缓存命中率。
作者将Blockaid应用在三个不同的应用上 (diaspora, Spree and Autolab)，发现当缓存命中时，加载页面的额外的开销大概为2% - 12%。并且在benchmark中，没有query被错误地拒绝了访问。

SHORTSTACK: Distributed, Fault-tolerant, Oblivious Data Access

Midhul Vuppalapati and Kushal Babel, Cornell University; Anurag Khandelwal, Yale University; Rachit Agarwal, Cornell University
本文为USENIX Security 2020最佳论文Pancake所在团队的后续工作。
云计算为应用程序提供诸多便利，但隐私安全问题却格外引人关注——攻击者可以通过访问模式猜测数据的真实内容。无论是防御主动攻击（主动干预运行时行为）的ORAM技术（核心是对访问位置的保护），还是防御被动攻击（只记录访问模式）的Pancake工作（核心为frequency smoothing，即对访问频次的保护），都需要借助一个中心化的、有状态的的代理来完成工作。这类工作的主要缺点是：
  1. 单点失效：代理失效会导致服务不可用。重启代理后如果不恢复原先的状态，则会导致违背安全语义。重构状态需花费较长时间，停机过长。
  2. 可扩展性瓶颈：单节点代理的计算和通信带宽都有限，容易成为性能瓶颈。
本文和SOSP 2021的Snoopy的解法相类似，都是引入分布式的代理节点来缓解性能瓶颈，但本文加入了容错维度的考量。贡献如下：
  1. 首先形式化地定义了针对ORAM访问的分布式容错安全模型：如果访问分布独立于输入分布，亦可以保证安全。
  2. 构建分布式容错ORAM系统——SHORTSTACK，容忍有界的服务失效。难点在于如何在多代理访问存储时，依旧保证均匀分布。本文的方法和Pancake十分类似，将明文分布补齐为均匀分布，使得每个子分布都是均匀随机，并且子分布彼此之间也是是同向的。
  3. 形式化论证本文的方案是安全的。

SHORTSTACK提出了3层代理的方案：L1负责生成假查询；L2根据明文key的情况负责UpdateCache状态的分区；L3负责执行真假查询，和后端的KV存储交互。UpdateCache是一层维护明文key的缓冲区。依靠3层代理实现高可扩展性且容错性强的分布式代理。SHORTSTACK使用了fail-stop的错误模型，L1/L2通过chain replication协议容错，而L3则简单地将请求转发给剩余在线的L3代理。最终，SHORTSTACK通过f+1个物理实例容忍至多f个错误。
作者将本文的方案同1）只加密但不做ORAM的baseline，2）Pancake进行对比：对YCSB，比baseline最差有6x的开销；和Pancake的吞吐相当（但增加了容错能力）。SHORTSTACK可以随着物理代理节点数量的增加而吞吐线性增长，在崩溃出现后3-4ms内完成恢复。整体只引入7ms左右的时延。

Groove: Flexible Metadata-Private Messaging

Ludovic Barman, EPFL; Moshe Kol, Hebrew University of Jerusalem; David Lazar, EPFL; Yossi Gilad, Hebrew University of Jerusalem; Nickolai Zeldovich, MIT CSAIL
本文是 Nickolai Zeldovich 在隐私通讯系统的又一篇工作，之前的工作系列包括：Vuvuzela (SOSP’15), Alpenhorn (OSDI’16), Stadium (SOSP’17), Karaoke (OSDI'18), Yodel (SOSP'19)。
在之前的工作中，系统的角色主要是 client(用户), mix network server, dead drop 三类角色。其中Mix network 用来混淆网络连接，每个 server 接收前一层 server 的 message，解密打乱之后传给下一层的 server。如此，只要通信时有一个 server 是诚实的，攻击者就无法判断用户的信息是发给谁的。Dead drop 用来交换信息的 server，通信双方最终信息会发送到同一个 dead drop，交换之后发送给双方以达到通信的目的。
如上图所示，隐私通信系统有很多个 round，每个round 用户发送和收取信息。为了防止攻击者通过查看 dead drop 有多少个 message 来观察谁和谁在通信，隐私通信系统会在通信中掺杂 noise。比如 Vuvuzela 会保证 dead drop 有一个或者两个access，无论是否有人在该dead drop上通信。Karaoke (OSDI'18)保证每个 dead drop 上都有两个 access，隐私性更高。
之前的工作虽然能够有效地隐藏通信双方的元数据，但是要求通信双方必须同时在线。并且网络开销和能耗高。因为client 需要定期发送、接受消息（按需发送/接收会暴露用户隐私），而这对手机用户几乎不现实（网络不稳定、在线时间短、电量少）。同时之前的工作不允许多设备登录。如果一个用户的两个设备在同一个 round 发送消息给同一个人，就会出现有一个 dead drop 有 3 个 access，可能会暴露隐私。
Groove 的角色比起之前的工作多一个 Service Provider，一共有四个角色：Client, Service Provider, Mixnet Server, Dead Drop。通过引入一个长期在线的不可信的 Service Provider 代表用户进行通信。这样可以解决网络开销和能耗高的问题，也能在用户不在线的时候代表用户进行通信。
Groove 的通信是按照 epoch 组织的，一个 epoch 内有多个 round。每个 round client 向 Service Provider 发送信息，接收信息，Goove 会保证 Service Provider 在这个过程中无法破坏用户的隐私（判断 Alice 和 Bob 是否在通信）。Groove 的通信通过 circuit 传递，circuit 是从 Service Provider 到 dead drop 的路径，是由 Client 随机选取一些 mix server 构成的。circuit 在一个 epoch 内不改变。Circuit setup message 是用每一层的 server 的 public key 层层加密的，每一层包含 server 的 ID，Diffie-Hellman 公钥 和 一个完整性验证码。server circuit 信息后利用自己的 private key 解密，然后通过 Diffie-Hellman 生成和 Service Provider 的共享密钥，并验证完整性。
Server 会将 curcuit 的 shared key 和 circuit 的 shuffle permutation 存下来，以后与后续的 communication message 的加解密。通信阶段的消息用之前生成的 DH 共享密钥加密，诚实的 mixnet server 会保证每个 circuit 都有一条消息。和 Karaoke (OSDI'18) 一样，Groove 会保证每个 dead drop 都有两个 access。
Client 通过线下扫码/其他方式添加好友，添加好友的同时生成一个共享密钥，用来端到端加解密。Client 选择 Service Provider 存储从 mixnet 收到的信息，代表 Client 发送信息。Client 仅和 Service Provider 交互，一个简单的交互逻辑如 Figure 2 的伪代码所示，Client 定期和 Service Provider 交互，获取信息，发送信息。Schedule 频率越高，能耗越高，信息收发延迟越低。当且仅当 Client 在线，可以发送信息，而当 Client 离线时，Service Provider 仍可以代替 Client 收信息（Client 委托 Service Provider 在未来的某些时刻建立 circuit，之后 Service Provider 就会收取发送到对应 dead drop 的信息）
Client 调用 RefreshCircuits 完成 Circuit setup。Client 可以提前为未来的多个 epochs 准备好 circuit message。Service Provider 会将这些 circuit message 加入队列，在正确的时刻创建 circuit。因此，即使 client 下线了，也可以由 Service Provider 建立 circuit 接收消息。
Evaluation
Latency
  • Groove的messaging round延迟在100M、200M、300M的circuits下分别为 32.4 s, 55.9 s 以及 79.83 s

在蜂窝网络下，30s、1m、5m的频率对应着47%、16%、6%的额外能耗。

UPGRADVISOR: Early Adopting Dependency Updates Using Hybrid Program Analysis and Hardware Tracing

Yaniv David, Columbia University; Xudong Sun, Nanjing University; Raphael J. Sofaer, Columbia University; Aditya Senthilnathan, IIT, Delhi; Junfeng Yang, Columbia University; Zhiqiang Zuo, Nanjing University; Guoqing Harry Xu, UCLA; Jason Nieh and Ronghui Gu, Columbia University
本工作出自哥伦比亚大学的Junfeng Yang组。作者观察到，虽然当前应用开发迭代频繁，但是开发者很少更新应用的依赖。对Python应用的调研显示，截至2021年8月，一项依赖从更新发布到更新得到应用平均会经历200天的延迟。开发者担心依赖更新会产生兼容性问题，因而不愿更新应用依赖，导致新版本依赖中的漏洞修复与性能优化无法及时地得到应用。本工作设计了UPGRADVISOR工具，帮助开发者判断是否可以安全地更新一项依赖。UPGRADVISOR工具的原型系统面向Python应用。
UPGRADVISOR的分析过程结合了静态分析与动态分析，总共分为三步：
  1. 对应用与新旧版本的依赖进行静态分析，找出可能与应用相关的被更新函数，这些函数被称为追踪目标；
  2. 在生产环境下对应用进行追踪，记录下追踪目标内部的执行流，通过分析执行流排除掉追踪目标中与应用无关的修改；
  3. 对于剩下的可能与应用相关的修改，由开发者判断这些修改是否有兼容性问题。
如果静态分析没有产生追踪目标，或动态分析排除了所有追踪目标，则无需开发者参与即可确认该依赖可以安全地被更新。静态分析帮助动态分析排除了大部分无关修改，使得动态分析可以只关注少部分函数，降低了程序追踪的开销。
在静态分析中，UPGRADVISOR对比依赖更新前后的抽象语法树找出依赖中被更新的函数，并构建应用与依赖的过近似（over-approximating）函数调用图判断一个函数更新是否与应用相关。
在动态分析中，UPGRADVISOR利用Intel PT硬件能力实现生产环境下的低开销程序追踪。UPGRADVISOR修改了Python解释器，每次执行字节码前，先跳转到一张跳转表中该字节码对应表项，然后再跳转回原处。Intel PT追踪跳转表区域内的跳转指令，通过该记录可以得出应用执行过程中的字节码序列。上述技术弥合了Python字节码与Intel PT之间的语义差。
UPGRADVISOR被应用于172个潜在的依赖更新，静态分析显示56%的依赖更新可以安全地进行，动态分析进一步发现了更多可以安全更新的依赖。作者提交了一些依赖更新的合并请求，大部分得到了开发者的接收。测试显示生产环境下UPGRADVISOR程序追踪的平均开销为3%。

Hubble: Performance Debugging with In-Production, Just-In-Time Method Tracing on Android

安卓设备已经广泛地融入日常生活，然而用户在使用这些设备时可能遇到故障问题（如间歇性性能降级）。这时，用户常常将问题归因于设备制造商，设备制造商不得不大量投入到故障的调试中。设备制造商进行故障的调试通常基于两种信息，一种是故障发生后采集的故障报告，一种是故障发生前采集的运行时跟踪日志。在故障发生后收集故障报告往往为时已晚，难以获得有关故障根因的关键信息。而由于无法准确预测故障发生的时间，想要收集故障发生前的跟踪日志，就需要跟踪程序在系统正常执行过程中持续记录运行状态，而这带来了运行时开销。
在移动端受限制的资源条件下，现有的运行时跟踪程序难以以开销收集足够多的运行时跟踪信息。因此，现有的故障诊断程序收集的信息往往只包含稀疏的运行时跟踪日志（如Systrace traces）和详细的故障发生后的报告，增大了故障调试的困难，甚至在大多数情况下不足以调试复杂的间歇性性能降级故障。
为了解决这一问题，本文提出了Hubble，一个能在用户真实使用的生产环境下以低开销运行，提供细粒度运行时跟踪日志的安卓应用跟踪系统。
Hubble的基本组件包括：
  • 代码插装：Hubble修改了Android Runtime interpreter和optimization compiler，从而在所有非内联函数的入口和出口处添加跟踪逻辑，记录函数调用方法名称和时间戳。该方法能够捕获所有通过解释执行或编译执行的Java函数调用，但不能追踪NI在原生库中的本地调用。
  • 内存缓冲区：Hubble在内存中默认维护2个32MB的缓冲区，分别记录前台UI线程和最近切入后台的UI线程的函数调用日志。单个跟踪点仅占用8字节，因此32MB的缓冲区能够捕获足够多的调试信息。
  • 控制线程：Hubble为每个应用程序添加了一个控制线程，该线程负责通知其他线程开启和关闭跟踪。当安卓系统内部的性能检测器发现异常（如UI卡顿）时将会通知控制线程，控制线程进而暂停跟踪，将环形缓冲区刷新到磁盘，然后重启跟踪。跟踪信息将会在之后发送给厂商用于调试故障。
Hubble尽可能保证在生产环境下的最坏情况的时延和内存开销低于3%，低于这一比例的开销通常不容易被稳定识别出来。Hubble通过高效的跟踪逻辑和手动插装优化实现这一目标，例如使用汇编编写插装指令在环形缓冲区中执行预取，从而在不支持乱序执行的处理器小核心上实现35%的性能加速。
作者采用充分的逐级测试（内部测试、Beta用户组内测、Beta用户组公测、公共部署）确保Hubble满足生产环境性能要求。在由大量热门应用组成的内部测试平台显示，Hubble的每个跟踪点跟踪开销小于1ns，远小于Android Studio的CPU分析器造成的微秒级的开销。在启动时延上Hubble没有造成与未开启使用Hubble的情况下的显著差异，而Android Studio的CPU分析器则延长了应用10倍的启动时间。自2019年Hubble已经进入华为的安卓系统主开发分支，由内部开发工程师测试。华为公司还运行了一个Beta测试公测项目，目前有数万用户加入这一项目。在2020年8月，Hubble已经进入华为的安卓系统生产分支，在用户同意情况下启动使用。

Jawa: Web Archival in the Era of JavaScript

Ayush Goel and Jingyuan Zhu, University of Michigan; Ravi Netravali, Princeton University; Harsha V. Madhyastha, University of Michigan
本工作出自密西根大学和普林斯顿大学的研究者。
Web Archive（互联网档案或网页历史快照）是一种现有的网络服务，其目标在于为现有的在线网页创建一份离线的快照副本，使得后续人们可以通过访问该副本的方式，获取某一网页在某一时期的具体状态。现有的Web Archive技术通常采用爬虫的方式，递归爬取并保存某一网页的全部资源文件（html、CSS、JavaScript等），并将网页中的所有外部链接替换为保存下来的本地版本，从而完成某一网页本地快照副本的创建。
然而，随着时代的发展，目前大多数网页依赖大量的JavaScript脚本提供必要功能，给现有的Web Archive服务带来了较大的问题。一方面，JavaScript的代码较多，占有空间较大，使得存储大量网页快照具有较大的存储容量占用，给通常出于公益性质的Web Archive服务带来了较高的成本；另一方面，JavaScript代码的增多导致网页动态性增强，使得Web Archive在爬取时难以爬取到所有可能访问到的外部服务，导致Web Archive存储内容不全，进而影响Archive后的网页存在大量内容与功能缺失。
为此，本工作利用一系列程序分析（如函数调用分析等）的方法，分析了现有网页的JavaScript脚本的行为模式，得出了如下的核心发现，用以实现低空间占用和高可访问性的Web Archive：
  • 许多JavaScript代码是用于和外部服务器通信，并基于服务器返回的动态结果执行特定逻辑的。在快照版本中，由于外部服务器的无法使用，因此此类代码没有意义，也无需被存储。经分析，删除此类代码对网页的显示不会产生较大问题，且此类代码通常属于第三方js文件（如使用外部验证码、广告服务等）或被封装在一些特定的用于通信的JS文件中。因此，可以通过应用简单的基于URL的过滤器做到不爬取此类代码，从而减少网页的存储空间占用且不影响网页存储效果。
  • 由于网页代码执行的不确定性（如基于目前设备信息、运行时信息、日期、随机数等），许多资源会选择性被加载，使得Web Archive难以爬取所有必要信息，影响最终快照页面显示效果。经分析，在Archive过的页面中，由于不存在本地cookie等客户端状态，所有服务端状态均采用Web Achieve的快照，而经测试随机数等信息通常并不影响Web页面渲染，因此，此类不确定性主要是由设备信息（如该网页是运行于桌面端还是手机端等）所导致的。通过修改设备信息相关JavaScript代码的返回值，即可一方面裁切掉不必要的多设备代码，另一方面确保网页快照在访问时JavaScript代码的执行路径同其被爬取时的执行路径相同。
  • JavaScript代码也常用于用户与网页的交互（如编写按钮被点击后的逻辑等，后文称为event handler）。由于网页快照中对JS代码进行了裁剪、对外部服务器返回值和客户端设备信息等进行了固定，因此，经分析，在快照中多次执行同一event handler的代码具有较高的确定性。可以基于这一确定性对存储的网页快照中的JS代码做进一步的剪枝，从而降低快照的存储空间占用。
基于上述三点发现，本文作者提出了Jawa，一个如下图所示的Web Archive系统，在该系统中，负责获取外部数据的爬虫模块在爬取的过程中，会通过基于URL的过滤器，减少爬取不必要的同Server端通信的JS代码。同时，爬取过程中，Jawa会记录爬取过程中event handler所能够访问到的所有JS代码。后续Jawa会将爬取到的网页进行剪枝，并通过代码注入的方式限定该网页部分函数调用的返回值以增强网页的确定性。最后，Jawa会将完成了剪枝与注入的网页存储到Web Archive中。
经测试，通过Jawa的剪枝，可以降低41%的存储空间占用（由减少了84%的JS代码数量实现）；在Archive过的页面中，经随机采样测试，event handler均可正常工作；相较于现有的Web Achieve系统，Jawa可以减少99%的访问achieve时遇到的资源缺失问题。
最后，本工作现已开源，项目地址：https://github.com/goelayu/Jawa。

FAERY: An FPGA-accelerated Embedding-based Retrieval System

Chaoliang Zeng (Hong Kong University of Science and Technology), Layong Luo (ByteDance), Qingsong Ning (ByteDance), Yaodong Han (ByteDance), Yuhang Jiang (ByteDance), Ding Tang (Hong Kong University of Science and Technology), Zilong Wang (Hong Kong University of Science and Technology), Kai Chen (Hong Kong University of Science and Technology), Chuanxiong Guo (ByteDance)
基于嵌入的检索（Embedding-based retrieval, EBR）被广泛应用于推荐系统中，用于从一个包含数百万或更多条目的大型语料库中检索候选条目。本文设计了一个FPGA加速的EBR系统FAERY，与基于GPU的EBR相比，FAERY拥有更低的延迟和更高的吞吐。
EBR利用语义嵌入向量（或称embedding）表示用户查询和候选条目，将条目检索问题转化为嵌入空间中的相似度搜索问题。下图是一个典型的EBR算法，首先将扫描语料库以获得所有条目，并计算每个条目的embedding与给定查询embedding之间的相似度得分（通过内积等方式），然后进行K-selection，根据相似度得分返回Top-K条目，EBR返回的Top-K条目通常是有序的，以便于后续算法的合并和过滤。
该算法中，第3行的语料库扫描是内存密集型操作，一个工业语料库的大小达若干GB，将产生数百万次内存访问，需要较大的外部存储器和较高的内存带宽。第4行的相似度计算是计算密集型操作，该操作计算用户查询和所有条目embedding之间的相似度得分，由于不同条目embedding的计算是相互独立的，该操作可以采用数据并行的方式。第6行的K-selection也是计算密集型操作，该操作在现有工作中已有多种实现方式，常见方式是将其划分为多个子步骤，并按照流水线的方式进行组织。
现有的EBR实现方式中，基于CPU的方案内存带宽太小，并行度有限；基于GPU的方案中，根据实验，如果将所有操作集成为一个kernel，则难以利用pipeline，且线程同步、结果合并操作开销较大，而如果将操作拆分为多个kernel，则需要externel memory进行通信，同样有性能问题。而FPGA拥有大带宽的HBM 以及大量片上RAM，并可以通过自定义逻辑实现流水线，很适合EBR。

FAERY将条目embedding存储在HBM中，语料库管理器（Corpus Manager）进行语料库扫描和更新，相似性计算（Similarity Calculation）操作采用数据并行，K-Selection操作采用流水线结构，过滤器位于K-Selection和Similarity Calculation两个操作之间，用于解决两者吞吐量不匹配的问题，并降低资源需求。
经过测试，对于HBM，为了达到90%以上的带宽利用率，一次内存访问大小应不小于64字节，因为embedding大小可能小于64字节，FAERY 将一个或多个embedding压缩到一次内存请求中。
相似度计算（Similarity Calculation）同时接收来自多个HBM通道的多个embedding，为了匹配HBM的带宽，FAERY的多个评分单元（Score Unit）并行工作，每个单元独立进行条目embedding的相似度计算。
FAERY 采用了一种基于现有工作的硬件开销较小的流水线 K-selection 方案，每个时钟周期处理一个score，但相似度计算操作采用数据并行，吞吐更高。为了解决吞吐不匹配的问题，FAERY引入了过滤器，如果K-selection的输入分数不大于现有的Top-K的最小分数，则输入不会改变内部正在运行的Top-K，因此过滤器可以直接删除该输入，从而大大减少发送到K-selection的score的数量，过滤器示意图如下：
根据分析，过滤器的输出仍然不能被K-Selection操作在一个周期内处理的概率极小，但过滤器中仍然设有一个缓冲区存储暂时无法被处理的输出，以应对该小概率事件。
多个FAERY加速器可以一起以复制或分片的模式工作，在复制模式下，不同加速器存储相同语料库的独立副本，并同时服务不同的查询，以提高查询吞吐量；在分片模式下，多个加速器存储同一个语料库的不同分片，同时服务一个查询，以增加支持的语料库大小。
在测试部分，本文基于Xilinx VU35P FPGA 进行了系统实现，并与可以支持CPU/GPU的系统 Faiss 在不同的语料库上进行延迟和吞吐的对比，结果表明FAERY降低1.21×-12.27×的延迟并提高4.29×的吞吐。

Efficient and Scalable Graph Pattern Mining on GPUs

Xuhao Chen and Arvind, MIT CSAIL
G2Miner是 MIT CSAIL 的 Xuhao Chen 和 Arvind 在图模式挖掘上的工作。
图模式挖掘(GPM)在给定的数据图中找到与给定模式相匹配的子图（如上图）。GPM在许多领域都是一个关键的构建模块，例如，蛋白质功能预测、网络对齐、垃圾邮件检测、化学信息学、社会计量学研究、图像分割。图机器学习任务也可以受益于GPM，包括异常检测、实体解析、社区检测、角色发现和关系分类。GPM的计算量非常大，因为它的搜索空间与模式大小呈指数级关系。例如，Peregrine，CPU上最先进的GPM系统，在一个56核CPU机器上，在Friendster图中挖掘4个圆形的模式（下图）需要9个小时。gpu提供了比cpu更高的计算吞吐量和内存带宽，因此对GPM加速非常友好。
然而，在GPU上高效地实现GPM是一个挑战。这是因为它需要通过利用GPU硬件架构中的信息、感兴趣的模式和输入数据图来进行复杂的优化。
本工作提出了 G2Miner，这是第一个在多gpu上高效运行的GPM框架。G2Miner采用架构感知、模式感知和输入感知的搜索策略，在gpu上实现高效的图模式搜索。
架构感知：GPU的内存容量通常比CPU小，需要更细粒度的数据并行才能充分利用GPU的算力。然而，更多的线程需要更多的内存来容纳中间数据。因此，GPU上的GPM需要仔细地编排并行度和内存使用，以最大限度地提高效率。GPU对 thread divergence和工作负载不平衡也比cpu敏感得多。这就使得GPU需要比CPU更复杂的 task-to-hardware映射。
模式感知：CPU上最先进的GPM系统使用模式感知的搜索计划，使用模式信息对搜索空间进行剪枝。这已经被证明比模式无关搜索快了几个数量级。这种模式感知方法在CPU上工作得很好，但在GPU上还没有得到很好的探索。例如，许多模式感知的剪枝方案只在DFS探索下有效，但现有的基于gpu的系统使用BFS，因此失去了这些剪枝的机会。
输入感知：动态内存分配在GPU中是非常昂贵的，如果我们可以估计最坏情况下的内存使用情况，那么我们可以避免动态内存分配。这可以通过使用一些元信息来实现，比如输入图的最大度等信息。对于有标记的图，我们可以利用输入图的顶点标签分布来获得可能的模式的最大数量，这有助于节省内存空间。通常，输入信息有助于更好地权衡工作效率、并行性和内存消耗。
上表将G2Miner与最先进的系统进行了比较，包括那些只解决子图匹配问题的系统（子图匹配问题是GPM问题的一个子集）。在上表中，子图匹配系统包括emptyheaded、Graphflow、GraphZero、GraphPi和PBE, Peregrine、Pangolin和G2Miner是通用的GPM系统。之前的大部分工作都集中在CPU上，并使用DFS来减少内存占用。另一方面，基于GPU的系统(Pangolin和PBE)使用BFS，因为直接在GPU上实现DFS会遇到thread divergence和负载不平衡的问题。无论如何，这限制了他们的效率和/或他们可以解决的问题的规模。此外，G2Miner通过自动生成CUDA代码简化了GPU编程，而Pangolin则需要用户手工编写CUDA代码，而PBE则完全不能编程。同时，G2Miner是唯一一个可以扩展到多个gpu的系统。
上图是G2Miner的overview。G2Miner由图形加载器、模式分析器、运行时系统、CUDA原语库和代码生成器组成。用户只负责使用G2Miner的API指定感兴趣的模式。模式分析器对模式进行分析，并生成一个特定于模式的搜索计划，基于此，代码生成器自动为GPU生成特定于模式的CUDA内核。内核包含对GPU原语库中定义的设备函数的调用，其中包括了高效实现的集合操作。NVCC编译器将生成的内核、GPU原语库和运行时一起编译，以生成在多GPU上运行的可执行文件。
在V100 GPU上的实验表明，G2Miner比目前最先进的两种单GPU系统Pangolin和PBE分别快5.4×和7.2×。在多gpu设置中，G2Miner实现了从1到8个gpu的线性加速，用于各种模式和数据图。作者还将G2Miner同最先进的基于CPU的系统Peregrine和GraphZero做了对比。G2Miner运行在V100 GPU上，而Peregrine和GraphZero运行在56核CPU机器上，G2Miner的速度比后两者分别快48.3和15.2倍。
