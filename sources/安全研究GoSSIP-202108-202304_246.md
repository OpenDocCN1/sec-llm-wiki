今天给大家推荐的是来自ICSE 2022的一篇文章"Demystifying Android Non-SDK APIs: Measurement and Understanding"。由于SDK的实现和使用特性，我们已经看到过很多工作针对各类Android SDK API的安全性展开研究，而在这篇文章中，作者从另一个角度——**Android Non-SDK API**来展开研究，这些API通常以非常规的方式调用且并不稳定。通过对大规模Android应用及源码的分析，本文系统性的探索了Android Non-SDK API的使用和设计，并发现了其中存在的一些安全隐患。

![](../Images/e7dd8d243f0eda66dc5553efc6cc7267.png)

![](../Images/ad013c24cfc2b050543510eac2236f82.png)

Android Non-SDK API是指存在于framework.jar但不存在于android.jar中的API，通常分为三类：

*   Internal APIs: 在com.android.internal包中，提供了Android系统核心功能，可用于访问敏感资源，且不对外开放，仅供系统内部使用。
    
*   Restricted APIs：由private或default标记的APIs。
    
*   Hidden APIs: 用@hide标记的APIs。
    

![](../Images/c21f140e9b6a202c1ff25504244ad58a.png)

Android Non-SDK API常用的访问方式包含三种：

*   SDK replacement: 开发者使用自定义的android.jar（包含non-SDK APIs）替换原来的android.jar。
    
*   Java reflection: 通过Java反射机制，开发人员能够在运行时调用任何对象方法、属性，包括由private标记的Non-SDK APIs。
    
*   Java Native Interface (JNI): 开发人员能够通过JNI调用native代码，并通过NDK在native代码中访问Non-SDK APIs。
    

Non-SDK APIs的不稳定性可能会导致兼容性问题，如程序崩溃或其他意外行为，因此Google鼓励开发者使用SDK提取的公共API来开发应用，并引入了一系列检查机制来限制Non-SDK API的使用，包括blacklist、greylist-max-x、greylist和whitelist（SDK APIs）。其中，前三个列表中的Non-SDK API不受官方支持，可能会随时更改或删除。

![](../Images/07e4f7a79999a45c04d2300115667b23.png)

为了探究Android Non-SDK APIs的使用和实现情况，作者进行了大规模的测量，主要方法如图2所示。

(1) App Dataset Construction: 数据集包含两类，即从18个应用市场下载的226,209个良性应用和从VirusTotal获得的10,029个恶意应用。

![](../Images/127dc877269c97be35425093389c0526.png)

(2) API List Generation: 作者利用Google提供的Veridex工具来检测应用中所使用的Non-SDK APIs。

(3) Multi-dimension Analysis: 作者从四个方面对Non-SDK APIs展开研究。

*   **RQ1: Can Google’s restriction on non-SDK APIs be bypassed?**  
    如前所述，Google实现了一系列机制限制Non-SDK API的使用，作者测试了应用这些限制机制前/后三种Non-SDK API访问方法的有效性，结果如表2所示，且即使在Android 9和更高版本中，开发人员仍然能够使用Double-reflection和Call Stack Breaking来绕过Google限制机制，访问Non-SDK APIs。
    

![](../Images/534465bf25d4302a0cf8ae7ae0c7519c.png)

*   **RQ2: What is the present status of using non-SDK APIs in apps?**  
    作者调查了Non-SDK API的使用现状，如表3所示，超过85%的应用仍然使用Non-SDK API，且在Google推出限制机制后，单个应用使用的Non-SDK API有所增加。此外，作者还发现开发人员通常只使用一小部分的Non-SDK API，用于实现SDK不支持的一些独特功能。

*   **RQ3: What are the differences in using non-SDK APIs between malicious and benign apps?**  
    作者分别对良性应用和恶意应用中Non-SDK API的使用情况展开分析，如图5所示，结果表明与良性应用相比，Non-SDK API在恶意应用中的使用十分普遍，有61%的恶意应用使用了至少一个Non-SDK API，这些API通常被滥用来达到一些恶意目的。
    

![](../Images/6e4e65a0d6957e255f175c19c521bbf2.png)

*   **RQ4: How did non-SDK APIs evolve in the Android framework?**  
    作者还对Android框架中的Non-SDK API的演变展开了研究，结果表明Android系统框架中的Non-SDK API经常会被调整，增加Non-SDK API限制的原因通常出于安全考虑和细粒度管控，放宽Non-SDK API限制的原因主要是由于开发者的要求和新功能的添加。
