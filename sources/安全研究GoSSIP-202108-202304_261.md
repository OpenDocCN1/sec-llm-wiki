# G.O.S.S.I.P 阅读推荐 2022-06-28 CVE考古

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=Mzg5ODUxMzg0Ng==&mid=2247490543&idx=1&sn=b3dd5f4e7899f3a3b0b13950b84da282&chksm=c0603536f717bc2027455dbf3ea8b7d5fabcfaec19671fd043cc96d7d24440ebd6ae6667339a&scene=126&sessionid=1681404150#rd](http://mp.weixin.qq.com/s?__biz=Mzg5ODUxMzg0Ng==&mid=2247490543&idx=1&sn=b3dd5f4e7899f3a3b0b13950b84da282&chksm=c0603536f717bc2027455dbf3ea8b7d5fabcfaec19671fd043cc96d7d24440ebd6ae6667339a&scene=126&sessionid=1681404150#rd)

此前我们也曾推荐过一些研究论文，讨论开源或闭源代码中漏洞的演化史，其中【G.O.S.S.I.P 学术论文推荐 2022-03-10 OpenBSD/Firefox 漏洞演化史】（[https://mp.weixin.qq.com/s/GvD1b9Lb6VLZQht7c0YMsw](https://mp.weixin.qq.com/s?__biz=Mzg5ODUxMzg0Ng==&mid=2247489042&idx=1&sn=83fd0fc442d849cbb0cd6b272c0174c4&scene=21#wechat_redirect)）讨论了OpenBSD（从1998年的2.3版本到2020年的6.7版本）和Firefox（2011年发布的4.0版本开始直至2020年发布的75.0版本）中的情况。今天我们将目光聚焦到USENIX Security 2022上的一篇相关论文——**How Long Do Vulnerabilities Live in the Code? A Large-Scale Empirical Measurement Study on FOSS Vulnerability Lifetimes**，这篇论文把研究对象换成了更多的（11个知名）开源项目，结论表明，在这样的具有代表性的开源项目中，**CVE漏洞的平均存在周期长达4年之久**！

![](../Images/583191ae91d456cd186a7a06473f633c.png)

  

大概此类论文都会首先画个图，把漏洞的生命周期给大家展示展示（这可能是安全研究领域为数不多的共识或者说科学结论了）：

![](../Images/a0d4fe2ad6d0699a9fc6928993352cb8.png)

除了这个共识，好像此前的论文都各有各的结论，本文作者不太服气，号称要提出一种更为科学精确的方法，要把以往那些只能估计出CVE生命周期下界的方法都比下去。为了证明自己的豪情壮志，作者不仅提出了方法，也对一个包含了5900多个CVE的数据集进行了实验（号称过去从来没有人在这么大规模的数据集上实验过）。首先让我们读者感觉到很好奇的就是这个数据集的建立过程：

作者首先关注了大型开源项目中那些既包含CVE同时又包含和修复漏洞相关的commit的信息，例如：

*   Ubuntu CVE Tracker: https://git.launchpad.net/ubuntu-cve-tracker
    
*   Debian Security Tracker: https://salsa.debian.org/security-tracker-team/security-tracker/-/tree/master/data/CVE
    
*   Vulnerability History Project: https://github.com/VulnerabilityHistoryProject
    

作者决定只保留比较高水平的开源项目（例如Apache和Chromium）的信息，且只关注C和C++代码的项目，最后选出来11个相关项目：

![](../Images/1a1192c333b41ebcfb649523b772bd2e.png)

在这些项目中，作者搞出来一套类似国内的这种“世界知名大学排行榜”的启发式估计算法（开玩笑），这个算法可能比较难理解（也许是小编比较懒），反正就是效果蛮好的（看下图），感兴趣的读者不要打我，可以去读读论文第四章的细节。

![](../Images/4ffa6061e56a975048e53a737032050a.png)

让我们来看看结论吧，估计大家对结论都很感兴趣，首先是对11个项目中CVE的生命周期的估计：

![](../Images/1fd298c9770c6f0d7e7c21b5aa8b5ffb.png)

小编突然想起来自己的大学本科的时候读《大学物理》要去做实验，经常需要对实验数据进行“分析”（你懂的），然后看到论文中对CVE生命周期曲线的拟合，突然热泪盈眶怀念起青葱岁月了（强行卖情怀，是不是要考虑取关我们公众号）

![](../Images/7158b0d5805bf77c971adbb8011596c1.png)

为了预测CVE的发展大势，作者对数据进行了一番分析后，发现CVE的平均生命周期在逐渐变长，基本上每年下来都会增长42.78天左右，当然这个结论也很容易理解——凡是已有没修复的CVE每过一年就又老了365天，而新的CVE也有条不紊地进入到新代码中来。。。

![](../Images/23b377068ac567c5fbfb41b803d9b905.png)

作者认为，根据对数据的调查，在现实中我们可能要面对一个比较悲观的结论，那就是对已有CVE的修复速度可能要低于新CVE引入的速度，这样，由于缺乏足够的物质，宇宙就会一直膨胀下去……

![](../Images/aeb980e4d61d3b2e0ec429a41ae80d71.png)

当然，作者也观察到在开源项目中，同有漏洞的代码相比，没有漏洞的代码要活得更久（这好像有点废话）
