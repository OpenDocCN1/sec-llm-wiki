# G.O.S.S.I.P 阅读推荐 2022-04-08 Sharing is Caring

今天给大家推荐一篇来自EuroSys 2022会议上的论文——Sharing is Caring: Secure and Efficient Shared Memory Support for MVEEs。论文作者指出虽然MVEE（变体程序执行环境）保护措施能够有效检测出程序是否受到了攻击，但是却不能有效区分诸如使用共享内存的程序变体版本之间的不一致性。因此论文作者设计了新的方案解决了这一短板，使得MVEE技术的应用更加广泛。

  

![](../Images/aab2f181a7fc16d6aa054fdae490e5f9.png)

  

论文作者首先调研了当前主流程序对共享内存的使用情况，得出了这类内存被广泛使用。而由于任意进程都可以修改共享内存，则攻击者可以通过相应的修改达到使变体程序的行为一致的目的，进而导致MVEE没法对大量的程序提供保护。

  

![](../Images/a5913ab4f1d41ebfc92e4ca10a433913.png)

  

为了支持对存在共享内存使用的程序的保护，论文作者提出了新的方案。

  

1\. 针对使用外部共享内存情况的保护方案（fall-back）流程如下图所示。当变体程序需要访问ESHM时，MVEE监视器会将其拦截，执行mmap后返回一个不可被解引用的内存指针。一旦程序想要对指针解引用就会触发页错误，并被监视器捕捉到。随后将直接进行程序的一致性检查，若通过检查则监视器会代为访问共享内存执行操作，并将结果复制到变体进程中的相应内存中。

  

![](../Images/7013d41b58cd52d4fe96158bbac837b4.png)

  

2\. 针对使用内部共享内存情况的保护方案（wrapped，包含fall-back方案在内 ）流程图如下。监视器会对指针进行判断是否涉及到共享内存，若没有则进行正常解引用，否则会调用SHM\_RVP\_type处理函数进行操作，将两个变体程序做相应的检查。

  

![](../Images/7b0edd3d0a0ef24806f637593883d519.png)

  

为了验证方案的有效性，论文作者对其方案（fall-back和wrapped）所带来的开销进行测试评估。实验结果如下所示，wrapped方案在内存分配较少的情况下比fall-back方案的开销要少。在内存大小超过2KB之后，两个方案的开销均较低并相差无几。

  

![](../Images/c166e7ddf8d208007c009e4e68eeeb86.png)

  

随后论文作者还是用MPlayer播放器对其方案做了压力测试，从结果中看出在使用改进的MVEE策略的情况下会对视频播放带来较大影响，但是在常用分辨率和帧率下不会造成太多的差距。

  

![](../Images/ce7717c4b7e0e3c4e52f46387f3b0ed1.png)

  

最后，论文作者在两台web服务器（nginx 1.18.0和apache 2.4.46）中进行了实际测试。其结果显示，论文中设计方案所带来的延时不高，并且使用wrapped方案比单独使用fall-back策略的方案有更高的吞吐率。

  

![](../Images/40f1bcbf14a2e193faa02231a16a9595.png)
