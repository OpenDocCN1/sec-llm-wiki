今天给大家带来的阅读推荐是由明尼苏达大学[卢康杰](http://mp.weixin.qq.com/s?__biz=MzA5MzQ1MDI2MA==&mid=2456040622&idx=1&sn=b5f009181d091b5241cda6ecd8419a8f&chksm=87cd2dd5b0baa4c375af10d0e58e854c121071074212af0131e426d2b7073f69a924bdfc22bd&scene=21#wechat_redirect)研究组和西安交通大学齐勇研究组联合投稿的，关于如何在没有硬件设备和模拟器的情况下测试驱动的工作***Semantic-Informed Driver Fuzzing Without Both the Hardware Devices and the Emulators***，该工作目前已被NDSS 2022录用。

  

![](../Images/d2872b7bcf7e098050cfb2af2254324c.png)

  

设备驱动是操作系统中至关重要的一个部分。以Linux这样的宏内核为例，操作系统代码中有70%左右的代码与设备驱动有关，有数十万个驱动程序与kernel相同的特权域运行。一旦驱动代码中的漏洞被恶意攻击者利用会危害整个系统的安全，比如之前Thunerspy利用Thunderbolt获得计算机信息的完全访问权限。而之前的研究表明设备驱动包含了大量漏洞，其主要原因有一下几点：1，设备驱动同时处理来自用户空间以及硬件设备的复杂数据。2，部分设备驱动是由一些经验不足的第三方开发者提供。3，设备驱动面对的种类繁多的设备，很难获取或者模拟所有的硬件设备，因此这些驱动代码并没有经过很充分的测试。这些原因导致设备驱动更为复杂和更易被攻击。现有研究表明，驱动程序往往具有更高的错误密度，并已成为主要的安全威胁。近些年来针对设备驱动fuzzing是系统安全领域研究的一大热点。

  

现有的fuzzing工作如Linux kernel使用的syzkaller只能对部分USB控制器代码进行fuzzing。PeriScope只能检测部分DMA代码。这些系统只能支持针对特定设备进行测试。同时，目前的fuzzing系统在进行设备驱动测试时，需要存在对应硬件设备或者有该设备的模拟实现。考虑目前设备的庞大数量以及模拟器中提供的有限的设备支持，当前的fuzzing都很难比较完整的对设备驱动进行测试。以PCI设备为例，Linux内核代码中包括了超过13000的相关驱动程序，而常用的模拟软件QEMU中只有对应的130个左右。现有的fuzzing系统只关注于有限数量的具有相应设备或仿真器的驱动程序上，因此无法扩展。考虑到目前系统中设备驱动的多样性以及庞大数量，如何在不依赖对应硬件的情况下对该驱动进行fuzzing是一个具有挑战的问题。

  

本文作者首先研究了目前Linux系统中设备驱动的基本特征，如驱动开发遵循LKDM,设备驱动的工作流程等。从这些基本特征中作者发现了成功初始化设备驱动程序的必要条件，通过Input-Validation Chains的验证。而用于验证的代码中存在着非常有用的信息，即temporal input, hard-code I/O address-value mappings 和普遍的error handling。这些信息可以极大的减少fuzzing时硬件设备端的输入空间，使得在不依赖硬件设备及模拟器的情况下，对相应的设备驱动代码进行fuzzing测试成为可能。因此作者设计并实现了DR.FUZZ, 该系统的主要目标是可以在不依赖硬件设备及模拟器的情况下，对相应的设备驱动代码进行fuzzing测试。图1展示了DR.FUZZ的框架，该系统由以下两个个核心部分组成，分别为semantic-informed mechanism以及The fuzzing framework for drivers。后者主要负责管理VM的运行，I/O交互时设备数据的注入，以及数据mutation等。而semantic-informed mechanism是这篇文章可以成功对设备进行fuzzing的核心部分。

  

![](../Images/57ccc7d07b1693e3c97f99719d939cd5.png)

图1 DR.FUZZ系统结构图

  

Semantic-informed mechanism 旨在通过Input-Validation Chains来获取可以成功进行驱动程序初始化所需的有效输入，以显著减少fuzzing时的输入空间。其基本思想是通过对代码的语义分析和插桩，使得fuzzer可以获知不同输入对驱动状态的影响，以指导fuzzer生成semi-malformed 的设备输入。它包含两个部分，即语义分析和状态反馈。图 2 描述了semantic-informed机制的示意图，该机制提出如下所示的三种新技术，分别为T1 (Byte-level, field-sensitive and I/O address-field mapping)、T2 (Byte-priority inference) 和 T3 (Path state as fuzzing feedback)。

  

![](../Images/092202cf446f8172bab484e1c59af61c.png)

图2    Semantic-informed mechanism  

  

下面简单介绍一个这三个技术解决的具体问题。Byte-level, field-sensitive value inference主要是通过对驱动代码进行静态分析，推断设备驱动运行所需的数据结构中的部分项的值。I/O address-field mapping 是将一部分I/O地址和数据结构里面的域做映射，这样可以获取在访问特定I/O地址时fuzzer应该提供的具体值。Byte-priority inference 通过代码分析获取每次设备输入中字节被使用的优先顺序，该信息可以指导fuzzer优先mutate本次输入中哪个字节。这样可以将原先输入空间大幅减少。比如对于一个4字节的输入，在不知道使用顺序的情况下，随机的bit flip的输入空间为232次，如果已知前2个字节会优先使用，则可以将输入空间减少位216+216。Path state as fuzzing feedback利用驱动代码中的error handling信息可以告知fuzzer导致其产生无效输入的代码位置，因此可以更好的指导fuzzing。图2描述了Semantic-informed mechanism的工作流程。将驱动代码以IR的形式提供给semantic analysis模块。该模块基于以上提到的三个技术对代码进行语义分析，在该语义分析的过程中，会将语义信息提取并生成相应的信息提供给fuzzer，同时通过代码插桩将运行时需要的信息以及驱动的状态反馈给fuzzer。在fuzzing实际运行中，fuzzer会结合运行时地收到的反馈信息和语义分析时生成的信息来指导mutation以产生更有效的设备输入。

  

在系统评估中，作者从驱动初始化的有效性，漏洞发现，以及性能方面对系统进行了评测。

作者进一步对该系统下设备驱动代码fuzzing的一些性能指标进行了评测，包括了代码的覆盖率，运行的速度。从表V中可以看出即使成功初始化了一部分设备驱动，整个系统的code coverage仍然很低。作者认为主要原因在于只针对syscall进行fuzzing以及只运行了24个小时。相较于HFL以及syzkaller，DR.FUZZ仍然具有更好的覆盖率。同时，在同一平台下，作者也比较了DR.FUZZ与syzkaller的运行速度，大约提高了18%，主要原因在于引入path-error state的反馈使得fuzzing系统可以更快的响应无效输入。

总体而言，该工作围绕如何在不依赖于硬件设备的情况下，仍然可以有效的对系统中包含的驱动代码进行测试。其核心思想是利用设备驱动程序中的包含的语义信息来减少fuzzing时产生输入的空间大小，尤其是驱动中特有的validation chains。作者通过挖掘可以利用的语义信息并实现DR.FUZZ系统使得该想法成为现实。对系统的评估也可以看出驱动代码中语义信息对于fuzzing过程的巨大帮助。
