本周我们的论文推荐大部分和软件安全漏洞的分析评估相关，前几天关注了很多具体的漏洞分析测试技术细节，今天来看一篇更为宏观的调研性质论文——Does OpenBSD and Firefox’s Security Improve with Time，由华中科大的研究人员为我们分析了从1998年到2020年期间OpenBSD和Firefox开发中的安全漏洞演化状态

作者的研究沿袭了2006年USENIX Security论文“Milk or wine: Does software security improve with age?”的研究方法论，针对OpenBSD（从1998年的2.3版本到2020年的6.7版本）收集了263个相关漏洞，针对Firefox则从其2011年发布的4.0版本开始直至2020年发布的75.0版本中收集了总共1630个漏洞。然后，针对这些漏洞在整个调查周期里面的属性进行了大规模分析和总结。

针对一个特定的漏洞，作者根据其引入、发现、（对外）披露、补丁生成和补丁部署，将其生命周期刻画出来（下图）。其中比较有意思的是如何确定一个漏洞何时被引入，作者提出了相关算法，根据代码的diff情况进行深入挖掘

在所有这些漏洞中，尽管大部分情况下开发者犯错的情况都比较类似，但是由于Firefox的软件性质，相比OpenBSD而言，它包含的漏洞更容易被攻击者远程利用（这好像是废话）

大家可能更为关心的是，这些漏洞到底会在软件中存在多久（从引入到最后被修复）？统计数据表明，大部分漏洞一般存在周期都比较长。对于OpenBSD，作者发现大约50%的漏洞存在时间超过477天，75%的漏洞会在1156天内被修复，如果考虑至少修复90%的漏洞，则时间会拖长到2655天。对于Firefox，修复时间会稍微快一些：50%的漏洞会超过308天得不到修复，75%的漏洞在737天内修复，而开发者需要1547天来修复其中90%的漏洞。

考虑到OpenBSD和Firefox作为操作系统和浏览器这两类完全不同的软件（但是代码都很多！），作者也统计了一下它们中的哪些组件更容易出问题。在OpenBSD中，内核和libssl成了最容易出问题的组件（但是这是否因为两者和安全关系最密切，大家也更集中去找漏洞？），而在Firefox中，js引擎简直就是犯罪现场！另一个臭名昭著的组件当然是和处理dom相关的代码部分。

最后作者进行了时间尺度的分析，发现软件开发者随着时间的飞逝，确实在产生漏洞这方面有所改进。然而我们要考虑到也许现在的代码中有更多的漏洞是还没被披露的，所以我们只能谨慎地猜测，开发者可能在犯错这件事上面吸取了过去的教训而会变得更好。
