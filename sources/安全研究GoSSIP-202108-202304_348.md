# G.O.S.S.I.P 学术论文特别推荐 2022-03-07 内存破坏猎手——Goshawk

1977年，科幻电影史上著名的《星球大战》首部曲问世，在这部经典之作的尾声，在共和国生死攸关的摧毁帝国死星战役中，男主角之一的天行者卢克驾驶战斗机朝着死星的核心位置发起攻击。

![](../Images/56dd220eb6c6a2b7849453a498d1167b.png)

由于战机速度极快，配合驾驶员发起攻击的计算机辅助系统都无法定位精确的发射时机，此前的其它战机都没能完成任务，而天行者卢克在这个时候听到了原力之声，让他用自己的直觉来进行攻击，于是卢克关掉了计算机系统！

![](../Images/4c5659ae010badeeb7256cf50be0c167.png)

![](../Images/cc75923aea8a8ae0afc8cbe4197d5591.png)

结局我们当然都知道，卢克借助原力精确命中目标，摧毁死星，共和国取得了胜利！

![](../Images/4806e77e788b0e2cd0f1a6ceeb7bba7d.png)

我们当然不是在给大家推荐科幻影视，而是借着卢克这个不迷信机器逻辑而相信自己感觉的故事，引出今天要介绍的论文——由 G.O.S.S.I.P 研究人员担纲的Goshawk: Hunting Memory Corruptions via Structure-Aware and Object-Centric Memory Operation Synopsis. 作为一篇刚刚被安全领域的旗舰级学术会议IEEE S&P 2022接收的论文，它充分体现了2021年G.O.S.S.I.P的研究工作的一大特色：在程序分析（逻辑）和领域知识（直觉）方面的结合，帮助我们在寻找和保护程序中的缺陷和漏洞方面取得了重要的进展！正如这篇论文的名字 Goshawk（下图来自animals.net）所体现，我们研发了一套极为锐利的分析系统，能够在海量代码中发现内存破坏问题（use-after-free和double-free）的分析系统，并利用它在现实中捕获了Linux和FreeBSD内核、OpenSSL、Redis以及微软和腾讯IoT SDK中的92个新bug，从准确性和可扩展性上大大超越了现有的分析系统（例如Clang官方的MallocChecker）！

![](../Images/c6321c23f65f91205db2a32dbd47504b.png)

看到这里，诸位肯定不免嘀咕一下，use-after-free和double-free这样的内存破坏问题又不是什么新型代码缺陷，学术界和工业界很早就开展了针对它们的检测，为什么Goshawk能够比别的系统做得更好呢？这就回到我们一开始所提到的“直觉”的引入：我们通过为Goshawk引入能够“看见”自定义内存管理函数的“天赋”，帮助它在开展海量代码规模的程序分析时，也不会陷入到路径爆炸和分析精度缺失等传统的分析迷局中，从而更好地捕猎内存破坏问题。

实际上，这种引入“直觉”，帮助代码分析特别是缺陷检测的思路，在G.O.S.S.I.P早期的研究中就已经提出，其核心思路是利用人工智能相关技术，对代码进行辅助标记，从而快速定位到分析的关键点。我们在2019年发表于RAID的论文 NLP-EYE: Detecting Memory Corruptions via Semantic-Aware Memory Operation Function Identification 里面已经利用自然语言处理（NLP）技术来标记相关内存操作，提升了传统的内存破坏问题检测的能力。然而，想要真正具备非凡的检测能力，就需要拥有不一样的直觉，而这正来自于对问题细致入微的认识，正如福尔摩斯对华生说的“你看见了，却没有观察。这两种活动是有明显区别的。”

在Goshawk的研发过程中，我们注意到现实世界中的软件代码里面包含的内存破坏问题，虽然本质上是由对原子级内存分配函数（如`malloc`, `kalloc`等）的错误使用，但是也可以从更为高层次去观察这类问题。如下图中的代码所示，我们注意到这里面的内存破坏（double-free）涉及到一些诸多和内存操作相关的函数（`framebuffer_alloc`, `framebuffer_release`, `alloc_apertures`, `kfree`等等），如果我们直接对这类函数进行建模，将其视为内存管理的接口，是不是可以极大简化程序分析，实现更为简洁的内存破坏问题检测呢？

![](../Images/5e9ad11562638ce4137a8bba3a0a9692.png)

这种朴素的想法非常有力量，也是Goshawk的直觉观察能力的基础。但面对现实代码，我们需要考虑更多的细节：注意到就在上图的例子中，里面涉及的函数（如`framebuffer_alloc`和`framebuffer_release`）不是对原子级内存分配函数的简单封装，而具备了在一次调用中就能分配/释放复杂结构的内存对象的能力。而这种对复杂内存对象的管理需求，一方面正是程序员去实现大量自定义内存管理函数（custom memory management function）的动机，另一方面也会导致更多隐蔽的代码缺陷的引入。以上图为例，我们看到，`framebuffer_release`函数执行了对两处指针（首先是`info`指针的成员变量`apertures`、其次是`info`指针）的释放，但在代码的46行中，另一个函数`hvfb_getmem`在特定条件分支上仅会释放`info`指针的成员变量`apertures`，这种*时而同时释放复杂内存对象全体，时而只释放部分对象的自定义内存管理操作*，特别容易产生隐蔽的内存破坏行为。

同时，在这种使用模式中，我们还注意到另一个问题——传统意义上认为的内存分配和释放的配对模式不再成立了。例如本例中的`framebuffer_alloc`和`framebuffer_release`函数，看似可以成对使用，但`framebuffer_alloc`函数并没有完全完成内存分配行为，需要配合`hvfb_getmem`一起才完整分配了一个`fb_info`对象（其中包含了一个同样需要动态分配的成员变量`apertures`）。试问，程序员在使用时难道不会被这些接口的名字迷惑而用错吗？

为了让Goshawk能够察觉所有这些复杂的内存分配行为，我们提出了一个（自我感觉）非常漂亮的函数抽象概念——*memory operation synopsis*（即论文中大量出现的MOS），用以帮助简化代码中的内存使用模型。如下图所示，MOS是对一个函数的（复杂）内存管理行为的总结，在图中，`pool_alloc_page`函数执行的复杂内存分配（既在第7行分配了`page`对象，同时又在第11行引入了`dma_alloc_coherent`函数去分配一个`vaddr`成员变量），可以抽象为图中底部的MOS表示。在这个MOS表示中，记录了自定义内存管理函数的名称（`pool_alloc_page`）和性质（分配器），同时记录了该函数分配的（多个）内存对象，以及这些对象是通过什么方式（返回值或参数）传递给其外部调用者的。Goshawk对MOS的使用，类似数学上对抽象符号的使用，一下子就把复杂的内存管理函数的内部细节全部封装起来，大大简化了对这些自定义内存管理行为的理解！

![](../Images/fcdfc1a774fafc39bf638ff559d3a013.png)

既然已经有了MOS这么好的一个理念，接下来我们要做的事情，就是为Goshawk提供三项基本功——准确发现自定义内存管理函数、将自定义内存管理函数的内存管理行为精确总结为MOS、运用MOS简化内存数据流从而寻找内存破坏问题。究竟Goshawk是怎么做到这三点的，让我们来简单介绍一下。

首先，Goshawk需要在茫茫代码中非常高效地定位哪些函数是自定义内存管理函数，否则在诸如Linux内核这种具有成千上万函数的项目中，光是定位此类函数就要花掉许多时间，更不要说后面还有复杂的代码分析和缺陷检测要做。而这个能力，正是来源于我们自2019年`NLP-EYE`系统中就使用的自然语言处理能力——运用NLP技术，只需要检查函数的声明原型，就可以较为准确（同时极为高效）地标记出可能的自定义内存管理函数。

我们必须指出，Goshawk绝不是一个简单依靠直觉行事的系统，实际上，运用NLP技术去标记成千上万函数，可能会产生大量的误报（从名称和参数上判定一个函数是否为自定义内存管理函数，不容易遗漏，却容易把一些名称相似、不具备内存管理能力的函数错误标记为自定义内存管理函数），因此，Goshawk在直觉引导之下，同时还会用严谨的逻辑去检验相关标记结果。在初步识别一个自定义内存管理函数后，Goshawk利用数据流分析技术来探索这个函数的内部实现，观察其是否包含原子级内存管理函数，如果包含，则利用数据流分析检查其生成内存对象的流向（从原子级内存管理函数到自定义内存管理函数边界）。这样，Goshawk不仅能够以极高的置信度确认一个函数确实为自定义内存管理函数，同时也顺便完成了对其MOS的生成。

拿到所有自定义内存管理函数的MOS之后，Goshawk就可以在内存破坏行为检测上大显神通啦！简单说来，Goshawk沿用了标准的基于数据流追踪的内存破坏行为检测模型，只不过是在代码分析时，一遇到自定义内存管理函数就直接根据其MOS来建模相应的内存对象（而不需要追踪深入到函数内部的原子级内存管理函数）。同时，由于MOS可以表征复杂的内存对象，Goshawk可以准确追踪多重内存分配和释放所涉及的问题，而这往往是传统的检测方法（即使它们也考虑了对自定义内存管理函数的接口抽象）所不擅长的。

![](../Images/d1acb43462d78713243352c42c4f9dc9.png)

作为一个硬核且实用的系统，Goshawk不仅只是一项学术研究，而是一项从2020年开始不断在实战中打磨的工作。在这个过程中，Goshawk得到了G.O.S.S.I.P的孵化初创企业蜚语安全的鼎力支持和广泛测试，相关实验覆盖了大量现实的软件代码，其中不仅包含Linux和FreeBSD这种特别复杂的代码项目，也同时包括了一些轻量级的项目（比如大家都很喜欢用来当成编程学习对象的Redis代码）以及IoT领域的应用（微软Azure和腾讯Qcloud的SDK），实验结果表明，由自定义内存管理函数引起的内存破坏问题非常普遍，在各类软件中均有可能出现！

![](../Images/1679777e14042b8e6158785f9e301a75.png)

除了能够更准确捕捉代码中的缺陷，Goshawk凭借其良好的“内存函数识别直觉”，实现了非常高的分析性能，对于Linux内核这种复杂的项目，在一台48核、192G内存的服务器上仅需要七小时左右就可以完成检测！相比之下，如果不是用MOS这样的简化模型，我们在一台64核、1T内存的服务器上运用标准的use-after-free和double-free检测模型执行相关分析（且为其配置了相比Goshawk大10倍的代码搜索范围），也仅仅只能识别Goshawk找到的92个bug中的25个。这其中还有另一个重要的区别在于，通过使用MOS来表征内存管理行为，Goshawk提供的bug检测结果更为易读（直接报告那些因为自定义内存管理函数引起的问题），而传统的bug检测结果即使同样准确，其报告结果往往涉及更为冗长的代码执行路径和更复杂的数据流，而难以被开发人员确认。

![](../Images/9d3d32815f0b4febe0fb38dcf9146067.png)

我们从去年12月论文投稿之后，在Goshawk的专用网站 https://goshawk.code-analysis.org 上公开了Goshawk的源代码、相关工具链和测试结果。同时，在2021年7月的Let’s GoSSIP软件安全暑期学校上，论文的两位主要作者吕云龙和方屹就已经为参加活动的听众带来了《追踪非标准内存破坏漏洞》的技术分享。经过长时间的锤炼，Goshawk已经具备了极佳的易用性和扩展性，在论文投稿之后，在上海交通大学研究生课程《软件与系统安全》课程上作为project推广，同学们利用该工具又找到了新的问题（例如NASM中的内存破坏漏洞），这让我们对Goshawk的品质充满了信心！事实上，Goshawk论文在2021年8月投稿Usenix Security却遭到了early reject，但这并没有影响我们对自己工作价值的判断，也是作为一个研究过程中的心得和大家分享：作为研究人员，一定要自信，把自己的工作做好，不要太在意有时候会收到的负面反馈。

同时，我们注意到类似自定义内存管理函数引发的问题绝非孤例，就在我们投稿之前，在2021年12月1日，Google Project Zero博客上发表的文章中，介绍了一个在Network Security Services (NSS) 库中存在的很明显（却没有被代码分析工具发现）的问题——由一个自定义函数`PORT_Memcpy`引发的内存越界写漏洞，这一下子给我们带来了更多的信心，我们相信，Goshawk和它背后所蕴含的技术想法，一定能够帮助研究人员更好地追踪代码缺陷，为代码安全带来更好的自动化分析和防护能力！
