# G.O.S.S.I.P 学术论文推荐 2022-02-24 DataGuard

今天为大家介绍一篇NDSS 2022上关于内存破坏的隔离保护相关研究论文The Taming of the Stack: Isolating Stack Data from Memory Errors

![](../Images/522baee9a77a58d3752c75749c38ab2c.png)

在这篇论文中，作者开展了对stack数据的精确分析，能够区分stack上哪些区域（变量或buffer）是不会受到内存破坏攻击影响的，对这类（定义为safe的）区域就毋需进行任何的隔离保护。对于那些可能会被内存破坏问题威胁到的区域，则是对其进行隔离（实际上就是将safe区域放在另一个stack上）。为了尽可能多的确定stack上哪些区域是safe的（这样需要隔离保护的unsafe区域就少了，性能开销也就减少了），作者设计了`DataGuard`系统，基于静态分析和符号执行，最大化发掘stack上的safe区域，进而实现精细化、轻量级的隔离防护。

![](../Images/5581c1d6e54dbbb718c670ca4dc935a1.png)

作者首先科普了一下stack上内存破坏的三种典型案例（Spatial、Type和Temporal错误，上图），然后对标了OSDI 2014年著名的Code Pointer Integrity这篇论文中提出的Safe Stack防护方案，指出该方案对很多涉及到stack的内存破坏并没有很好的保护，而更侧重于保护code pointer。与之相比，`DataGuard`对代码进行了较为细致的静态分析，能够更准确地标记出哪些区域需要保护。例如下图中的代码，其中caller函数将stack上的数组指针传给了callee函数，然后在callee函数里面执行了相关的操作。传统情况下，大家都认为callee函数可能会破坏stack上的数组的内存完整性，但是`DataGuard`可以执行代码静态分析，并确定这种情况下，callee函数对stack上的数组的内存访问并没有什么风险，这样就排除相关隔离防护的必要（听上去是不是很像上海对疫情的管控呀~）

![](../Images/6a05515bd1657d443cadcd4c86ff3e78.png)

整个`DataGuard`的工作流程并不复杂，如下图所示。其中，为了实现精确的管控，`DataGuard`中使用了一项核心技术——对Stack Object内存对象的约束（constraint）的分析（Step 2）。基于对stack上内存对象的约束（可分为Spatial Constraint、Type Constraint和Temporal Constraint三类，详细定义见论文的Section V.B）的收集和整理，`DataGuard`能够在接下来的步骤中确定到底哪些对象可以被标记为safe，进而把它们都放在一个safe stack上进行隔离。

![](../Images/595d0f7b96c9e208e513d44040dabc02.png)

看到Constraint大家往往会很自然联想到符号执行，对，`DataGuard`也是利用了符号执行来分析stack上内存对象相关的三类Constraint，并最终精确判定一个内存对象的safe属性。当然，符号执行在现实中依然会遇到路径爆炸和分析引擎不够健壮等问题，作者虽然做了相当的优化，同样还是没法避免对一些函数进行处理，在这种情况下，只能将这些函数整体视为unsafe函数。

为了验证`DataGuard`的有效性，作者对nginx-1.18.0,  
httpd-2.4.46, proftpd-1.3.7, openvpn-2.5.2, opensshd-8.6 以及 SPEC CPU2006 benchmark suite 进行了分析，和同类分析工具相比，`DataGuard`对所有的测试对象普遍能发现更多的safe对象

![](../Images/56a312607bd2fb8a7137093d49e6d06a.png)

`DataGuard`的另一个特长是它对可能的内存错误进行了分类，如下表所示，对所有发现的可能错误，`DataGuard`按照Spatial、Type和Temporal错误进行了分类统计

![](../Images/409d1063d75a251146f26a94a50a57e2.png)

最后是大家比较关心的防护带来的性能开销，如下图所示，`DataGuard`的平均开销是4.3%，与之相比，另两个系统的开销要高出不少——8.6% for CCured, 11.3% for Clang’s Safe Stack
