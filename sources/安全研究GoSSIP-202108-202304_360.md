# 渡鸦：RISC-V 上的内核调试工具

##  文章简介 

题目：Raven: A Novel Debugging Tool on RISC-V

作者：卢弘毅、张锋巍

会议：DAC' 22 (July 10-14, San Francisco)

关键词：Debugger, Kernel Debugging, RISC-V

##  起因 Motivation 

我们之所以会尝试打造 Raven 这个调试工具，实际上是因为我们实验室自己的需求。目前 RISC-V 板子多且杂，每个厂商都实现了自己的调试器标准。

例如全志的 Nezha 开发板由于采用了 T-Head 的 C-906 处理器，导致必须使用国产的 CKLink 调试器才能调试。

而我们实验室因为正在尝试为 RISC-V 开发 TEE，因此一个好的调试工具是必须的，所以我们也就有了 Raven 的想法，利用 RISC-V 的硬件特性来打造一款只需要串口的**内核**调试器。

我们基本的需求如下：

1.  不需要外接硬件
2.  不依赖 Linux 内核（能够调试只在 TEE 内运行的微内核）
3.  不修改内核程序的二进制文件（防止破坏完整性 integrity）

其主要难点在于后面两点，目前大部分调试器例如 GDB 等都是通过操作系统提供的 `ptrace` 等接口实现调试功能，而 `ptrace` 等接口是通过插入二进制指令 `ebreak` 来实现的。

我们采用的解决方案是，利用 RISC-V 提供的 `Machine Mode` 在固件内嵌入一个迷你调试器 Raven，然后 Raven 使用 RISC-V 拥有的内置的硬件特性 Physical Memory Protection (PMP) 来实现调试器所需要的断点等功能。

##  背景 Background 

### RISC-V 权限级别

如图所示，RISC-V 提供了 3 个不同的权限级别，分别是 U-Mode、S-Mode 和 M-Mode。

其中 U-Mode 是最低的权限级别，一般用户程序运行在这个级别，内核则运行在 S-Mode 为用户程序提供操作系统接口。而 Raven 则和固件一起运行在 M-Mode，因此可以修改各类 PMP 寄存器并且监控内核内存。

![](../Images/fbc904befdecaff438736aa927405f69.png)

### RISC-V 物理内存保护

RISC-V 提供了 PMP 功能来限制对特定内存区域的访问。它由一组 PMP 项组成，每一项包含两个寄存器，地址寄存器 `pmpaddr` 与 配置寄存器 `pmpcfg`。通过这些寄存器，我们可以配置不同物理内存区域所具有的权限 (R/W/X)。值得注意的是，PMP 的实现根据厂家的不同而略有不同，例如 Nezha D1 提供了 8 组精度最高为 4 KB 的 PMP 寄存器，而在 QEMU 虚拟机则提供了 16 组精度为 4 Byte 的 PMP 寄存器。如果某条指令违反了 PMP 的约束，它会立即触发一个异常，相关的异常信息会被存储在如下图所示的寄存器内。

![](../Images/752ae2cd17b4afc1497eb0f545280bfa.png)

### RISC-V 指令集格式

如上文所说， PMP 的精度根据厂商的不同可以在 4 byte~4 KB 之间取值。而断点的大小通常都是该指令集的**指令长度**。对 RISC-V 而言，这个值是 4 byte，恰好与 PMP 支持的最高精度相当。然而，RISC-V 提供了一个可选扩展被称为 “C” 标准扩展，提供了对压缩指令的支持，这类压缩指令长度仅有 2 byte。通常的 4 byte 指令以 `11` 结尾，而 2 byte 指令则以 `00`、`01` 和 `10` 结尾。

##  Raven 设计 

### 整体概览 Overview

下图就是 Raven 的整体设计。其中，Raven 作为固件的一部分运行在 M-Mode 下，通过串口或者网络从调试客户端接收命令并返回结果。根据调试客户端的命令的不同，Raven 会使用 PMP 将内核代码中的代码段设为特定的权限级别，以触发异常来满足调试需求，例如图中的 `csrw satp a0`。

![](../Images/a3ba303d57167d2289e7f3dd0b5dac01.png)

### 利用 PMP 实现调试原语

PMP 本身是用于实现 RISC-V 的安全特性的，因此它并不具备调试指令的功能特点。我们分析了调试器所需要用到的基本特性。可以分为下面两种，指令断点 `breakpoint` 与 数据断点 `watchpoint`，而其它的功能例如单步调试，内存监控等都可以通过这两种原语组合而成。

![](../Images/21159acda1f3b5e2e1bf8bb853bc28b3.png)

上图说明了 Raven 是如何通过 PMP 实现调试原语的，对于指令断点，他将对应的指令设置为不可执行，在处理器尝试执行该指令时，会触发 PMP 保护并陷入异常。通过相同的方式，我们可以设置只读断点与只写断点。

然而，正如背景介绍中所说，PMP 的精度并不存在标准，而是每个厂商根据自己的需求决定。对于数据断点而言，精度问题不大，不准确的陷入只会导致轻微的性能损失。但是对于指令断点，这会造成严重的问题，例如对一条 4 byte 的指令而言，如果我们将它周围的 4 KB 空间都使用 PMP 设为不可执行。那么根据 locality，在执行到我们希望执行的指令之前，我们会触发上百个不准确的陷入，导致这个方案无法使用。

对于这个问题，我们采用更为传统的 `ebreak` 指令来实现低精度 PMP 下的指令断点。如下图所示，但我们还是希望在下面的形式中保持内核的完整性，我们采用 PMP 保护针对 `ebreak` 所在区域的读写。这样一来，当远程验证发生的时候，Raven 可以拦截下来这类读写，进行模拟，返回原来的指令内容。

![](../Images/7c335ad7a2734501cc9964cf3652bd7a.png)

### 功能扩展

接下来，我们介绍我们如何将上面实现的两个调试原语扩展成单步调试功能。对于单步调试功能，一个直接的想法就是，我们随着单步调试的流程不断更新断点的位置，来做到单步调试。但这样的实现有一个问题，那就是控制流转移指令（control-transfer instruction）。

![](../Images/b588182649e932f75fa44b77b8824b22.png)

对于一般指令而言，我们采用直接的思路，每次更新断点位置，而对于控制流转移指令，我们采用指令分析的方法，例如上图中的 `beqz a0 0x1008`，我们将解析这条指令，预测其可能的终点为 `0x1008`。将断点下在那里以避免丢失当前的 `pc`。

### 精度与隐藏指令问题

即使在 4 byte 的 PMP 保护下，Raven 仍存在一个问题，RISC-V 是支持 2 byte 指令的，而最高精度的 PMP 也只支持 4 byte 的保护。我们将这个问题称为**隐藏指令问题**。

如下图所示，`c.jr a0` 就是这样一条只有 2 byte 长度的压缩指令，同时也是一条控制流转移指令。这条指令直接导致我们在单步执行中发生了*不可预测的控制流转移*，导致 Raven 丢失了当前 `pc`。

![](../Images/26a87fa8cf54309c78e4c21fa6c4de7f.png)

我们采用预测的方式来解决这个问题，当 Raven 发现在单步执行的过程中，当前 `pc` 可能存在隐藏指令，它会向前提前解码一条指令，并预测将会抵达的终点，以防止丢失控制流。如下图所示。

![](../Images/8e3a0f563015b312a5263d84b0d7bb2a.png)

### 虚拟地址与物理地址的同步

PMP 如其名字一样，它只能识别物理地址。由于大部分程序二进制编码中只包含虚拟地址，调试器也只使用虚拟地址来设置断点。因此我们还需要解决虚拟地址与物理地址的同步的问题。幸运的是，RISC-V 提供了一个被称为*虚拟地址陷入*（TVM）的功能。当它被开启之后，所有对页表根目录 `satp` 的更新以及 TLB 刷新 `sfence.vm` 命令都会触发异常。

当 Raven 发现这类异常被触发时，Raven 可以在当前新的 `satp` 中查找它已有的断点的虚拟地址所对应的物理地址。

##  案例分析 Buggy Device Tree 

为了测试 Raven 的可行性，我们使用了一个真实可能发生的 Bug，错误的设备树。在嵌入式 Linux 中，因为缺少设备枚举能力，通常 Linux 都是通过一个被称为设备树的文件来得知目前的硬件信息。一个错误的设备树可以导致整个内核崩溃，而这类问题通常非常难以解决，因为这类 Bug 可能发生在内核初始化串口之前，导致 Linux 完全不进行输入输出。

我们执行了下面这几步来模拟一个现实生活中的场景。

1.  修改中断管理器的地址来构造一个错误的设备树
2.  使用这个错误的设备树启动 Linux 来触发内核崩溃
3.  使用 Raven 来定位并修复这个问题

如下图所示，我们进行了下面这些步骤来定位这个问题。在内核崩溃之后，我们使用 GPIO 发送一个中断令 Raven 获得控制流，之后我们发现内核崩溃位置是内核的异常处理函数 `handle_exception`。接下来，我们在该异常处理函数设置断点，观察发现是由于 `load fault (scause=5)` 导致异常发生。通过查看异常触发位置和单步执行，我们发现错误发生在中断管理器的初始化流程中 `irq-sifive-plic.c`，一个错误的地址被使用了。

##  总结 

我们使用 PMP 实现一种不依赖外部硬件的调试器实现方案，同时利用 RISC-V 的一些非调试特性来实现调试器功能。当然我们也存在许多局限性，例如只能做到双指令精度的单步调试和隐藏指令等问题。如果后续 RISC-V 的相关硬件支持例如 PMU 完善之后，我们实际上可以将 Raven 扩展成更强的调试器模型，实现所谓的**透明调试**，以达到能够针对恶意软件调试的能力。

这篇文章也是 COMPASS 实验室关于调试器的第三篇文章（DAC 2022），之前有在 x86 上实现的 MaLT （Oakland 2015）和 Arm 上实现的 Ninja （USENIX Security 2017），至此，COMPASS 实验室也算凑齐了三个主流平台的调试器，笑。但是 Raven 较于前面两篇还有很多提升的空间，待 RISC-V 拥有更多的硬件扩展之后，我们也可以让 Raven 具备透明调试的能力。
