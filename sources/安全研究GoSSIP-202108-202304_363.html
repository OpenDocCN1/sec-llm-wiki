去年9月我们为大家推荐了大家推荐的论文是来自张殷乾老师研究组与百度安全实验室合作的通过密文侧信道高攻击窃取AMD SEV安全虚拟化保护的工作CIPHERLEAKS: Breaking Constant-time Cryptography on AMD SEV via the Ciphertext Side Channel。今天我们收到了来自张殷乾老师研究组的投稿，同样的团队，同样的配置，从另外一个角度来为我们介绍AMD安全加密虚拟化技术的最新工作TLB Poisoning Attacks on AMD Secure Encrypted Virtualization，该工作目前已经被ACSAC 2021录用。




随着对数据安全性重视的提升，云平台上的数据安全性获得了工业界广泛的关注。AMD 安全加密虚拟化技术（Secure Encrypted Virtualization 或SEV ）就是AMD在服务器级可信计算领域给出的答案。AMD安全加密虚拟化技术旨在保护云平台上的虚拟机中的数据安全并抵挡来自其他恶意用户甚至恶意虚拟机管理器（hypervisor）的攻击。不同于Intel Software Guard Extension （SGX） 针对单个应用程序并且需要对源代码进行重构，AMD安全加密虚拟化技术通过在处理器芯片集成系统（system-on-chip）上内嵌的安全处理器（AMD secure processor）和内存加密引擎（Memory Encryption Engine）对整个虚拟机的数据实现实时的加密，从而只需要部署者在内核层面适配AMD安全加密虚拟化技术而不需要重新撰写应用程序的源代码。


在这篇文章中，作者系统而深入的解密了AMD安全加密虚拟化技术中管理TLB的机制, 并且指出了在现有TLB管理机制下恶意的虚拟机管理器能够绕过TLB隔离，污染不同进程之间的TLB条目，以此进一步的破坏受到安全加密虚拟化保护的虚拟机中的机密性和完整性。在文中，作者提出了针对SEV-ES （SEV Encrypted States）的两种不同形式TLB Poisoning攻击并且分析了潜在的解决措施。本文的工作受到了AMD 安全加密虚拟化团队的重视，并针对TLB Poisoning攻击发布了相应的安全公告AMD-SB-1023（https://www.amd.com/en/corporate/product-security/bulletin/amd-sb-1023）。


AMD安全加密虚拟化技术中管理TLB的机制

作者首先介绍了在传统 AMD Virtualization （AMD-V）中使用的 以ASID （Address Space Identifier）作为TLB标签的机制。具体的来说，针对每一个逻辑处理器，虚拟机管理器负责确保虚拟机的每一个虚拟CPU（virtual CPU）拥有独特且新鲜的ASID。同时，虚拟机管理器以及其他非虚拟化进程的ASID都被预设为0。在这样的设计下，不同的虚拟CPU之间以及虚拟CPU和虚拟机管理器进程之间能确保拥有不同的ASID。当上下文切换的情况发生时，由于属于不同的虚拟CPU的TLB条目有着不同的ASID，硬件不需要清空TLB条目就能保证TLB的隔离，从而也能够大大减少清空TLB条目带来的性能开销。值得注意的是，在某些特定情况下，比如说ASID的分配超过了预设的范围，硬件仍然需要清空TLB条目。在此类情况下，虚拟机管理器负责将虚拟机控制单元（Virtual Machine Control Block）中对应的TLB 控制区域标记成非零的数值，以此来通知硬件在虚拟机执行（VMRUN）时清空现有的对应页表缓存。

AMD安全加密虚拟化在原有基于ASID的TLB管理机制上有了对应的改进来满足AMD安全加密虚拟化的设计。因为受安全加密虚拟化技术保护的虚拟机存储在内存中的数据是由其对应的虚拟机加密密钥（VM Encryption Key）加密过的密文。而虚拟机加密密钥是由ASID来标记并由安全处理器进行存储和调用。所以受到AMD安全加密虚拟化保护的虚拟机的所有虚拟CPU必须拥有相同且固定的ASID。在这样的背景下，AMD安全加密虚拟化在虚拟机管理器的软件层面加入了相应的需要清空TLB条目的情况和逻辑。当（1）受到安全加密虚拟化保护的虚拟机的虚拟CPU在新的逻辑处理器中运行时，以及（2）当属于同一个受到安全加密虚拟化保护的虚拟机的多个虚拟CPU同时运行在同一个逻辑处理器上时，在这两种情况下，虚拟机管理器需要标记对应的TLB 控制区域，以此来清空现有的对应页表缓存。

这样的TLB管理机制带来显而易见的潜在威胁，在虚拟机管理器本身是不可信的威胁模型下，恶意的虚拟机管理器可以在应该清空TLB的条件下选择性的不清空TLB条目，从而打破不同进程之间的TLB隔离。在文中，作者接下来探究了如何利用这样的TLB管理机制来实现行之有效的攻击。


打破进程之间的TLB隔离

作者首先用一系列实验来探究由于虚拟机管理器恶意破坏的TLB隔离可能会带来哪些潜在的威胁。在在受到安全加密虚拟化保护的虚拟机中，作者假定了一个受害者进程和一个被攻击者控制的攻击者进程。实验表明，恶意的虚拟机管理器可以破坏攻击者进程和受害者进程的TLB隔离，让攻击者进程能够（1）执行受害者进程的代码或者让受害者进程执行自己预定的恶意代码和（2）读取受害者进程的数据，从而实现破坏虚拟机机密性和完整性的目的。在文中，作者针对受害者进程和攻击者进程处于虚拟机的两个虚拟CPU或者处于一个相同的虚拟CPU这两种情况分别提出了绕过TLB隔离的攻击方式。在这两种攻击方式之下，作者进一步地提出了潜在的两种真实世界攻击案例。


有协助进程的TLB Poisoning攻击

在第一种攻击案例中，作者假设攻击者拥有在服务器端的管理者权限，并且在受安全加密虚拟化保护的虚拟机中存在着一个由攻击者控制的拥有普通用户权限的协助进程，同时假定协助进程能够以CROSSLINE攻击等方式获取到部分目标函数的虚拟地址。作者进一步并展示在这样的攻击假设下，攻击者如何通过污染虚拟机中有管理者权限进程的TLB的方式来绕过密码验证以及以管理者权限执行恶意指令。

攻击的具体步骤如下：

  1. 攻击者首先定位一些共享库的某些函数的物理地址，在本文的攻击中，攻击者的目标是OpenSSH守护进程中会调用的pam_authenticate() 函数。协助进程可以通过尝试访问对应函数的方式帮助攻击者定位目标函数的物理地址。OpenSSH守护进程也被称作受害者进程。

  2. 攻击者接着通过嵌套页表的缺页异常（Nested Page Fault）controlled channel的方式来跟踪OpenSSH守护进程的运行。当目标进程在建立新的SSH连接并尝试运行到pam_authenticate()函数的时候，攻击者需要短暂的暂停对应虚拟CPU的运行以提供让协助进程污染TLB条目的时间窗口。

  3. 协助进程在这个时间窗口将访问之前在自己地址空间预先分配的目标函数在受害者进程的地址空间的虚拟地址。协助进程在自己的地址空间内，在目标函数的虚拟地址中存储着恶意的代码，而在时间窗口中访问该虚拟地址的操作将在TLB条目中缓存该虚拟地址和恶意代码的映射。在本文的攻击中，恶意代码对应的指令是直接返回0。

  4. 攻击者之后让受害者进程继续执行，并且恶意跳过本来应该通知硬件的清空TLB条目的操作。此时，受害者进程将以访问目标函数逻辑地址的方式继续尝试调用pam_authenticate() 函数。而此时的TLB条目已经被错误的映射污染，OpenSSH守护进程将直接执行恶意的直接返回0的代码，而因此跳过密码的验证并允许任意的用户建立起之后的SSH连接。


没有协助进程的TLB Poisoning攻击

作者接着介绍了如何在没有协助进程的帮助下进行TLB Poisoning攻击。与有协助进程的情况不同的是，因为在受害者虚拟机内部没有协助进程，攻击者将不能访问任意的逻辑地址。作者同时发现，常见的一些网络程序（比如Nginx, Apache服务器，以及OpenSSH）会以fork()的方式来应对不同用户的网络连接。而fork出来的子进程即使在内核地址空间布局随机化被启用的情况下也往往拥有相似的地址空间，这将给攻击者提供在不同的进程之间污染TLB条目的机会。在本文中，作者以Dropbear SSH为例，展示了如何在不知道密码的情况下，通过污染TLB条目的方式，建立起SSH连接。攻击的具体步骤如下图所示：

TLB Poisoning攻击的反抗手段

作者在文中指出针对TLB Poisoning攻击最有效的防御措施是对fork函数的优化。以OpenSSH为例，在守护进程尝试fork子进程来应对不同的登录请求的时候，会有exec()的操作，以此来保证每一个子进程都有完全独立且随机的地址空间，这将能有效的应对TLB Poisoning攻击。同时在安全加密虚拟化的第三代版本SEV-SNP中，清空TLB的机制部分转交给了硬件并同时提供了额外的TLB隔离和管理机制，同样能够有效地抵御TLB Poisoning攻击。
