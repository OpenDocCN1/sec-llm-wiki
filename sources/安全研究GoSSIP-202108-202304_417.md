# G.O.S.S.I.P 学术论文推荐 2021-12-04 Debloating Address Sanitizer

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=Mzg5ODUxMzg0Ng==&mid=2247488086&idx=1&sn=0e8eb6b1f048d3342675e72b0995bfaa&chksm=c0603c8ff717b5996f5378b403445057c4a6b77ce7eb0099e0429bf559c795ee24bfb5ef5b2e&scene=126&sessionid=1681404232#rd](http://mp.weixin.qq.com/s?__biz=Mzg5ODUxMzg0Ng==&mid=2247488086&idx=1&sn=0e8eb6b1f048d3342675e72b0995bfaa&chksm=c0603c8ff717b5996f5378b403445057c4a6b77ce7eb0099e0429bf559c795ee24bfb5ef5b2e&scene=126&sessionid=1681404232#rd)

十二月的第一个周末，我们邀请到来自[斯蒂文斯理工学院S^3实验室](http://mp.weixin.qq.com/s?__biz=Mzg5ODUxMzg0Ng==&mid=2247484548&idx=1&sn=b1468932eef2cda96fba2aaf1fd7695b&chksm=c0602a5df717a34bc4dadfef0e9e1a15b2c44def34500e6994591aa5fd1cd1864aeb3ea3186f&scene=21#wechat_redirect)的Yuchen来为大家介绍他们在内存漏洞检测研究上的最新研究成果，目前该工作已经被USENIX Security 2022录用。  

  

![](../Images/08b0b9ea821567682340ef5818a301ad.png)

  

Address Sanitizer (ASan)是一款强大的面向C/C++语言的内存错误检测工具，它可以检测使用已释放内存(use-after-free) ，堆内存越界(heap-buffer-overflow)，栈内存越界(stack-buffer-overflow)，全局变量越界(global-buffer-overflow)和内存泄漏(memory-leak)等。但同时，ASan也有明显的运行速度问题，如果将ASan全部的功能打开，它会拖慢程序两倍左右。

  

本篇文章首先对ASan的运行时间进行拆解，并归类于六个部分：sanitizer check, library function interception, poisoning, logging, heap management and redzone。通过实验证明，sanitizer check是造成ASan拖慢程序运行速度的主要原因。约80%的虚耗来自于sanitizer check。下图是每个部分所产生的虚耗：

  

![](../Images/75afb429f33434dbd6c9cbfb66c76bca.png)

  

鉴于sanitizer check在ASan总运行虚耗中占有很大的比重，减少check的数量从而降低运行时间，对整个ASan的优化非常重要。现有工作大多采用随机减少check或根据虚耗比例减少check来尝试解决ASan虚耗过高的问题，例如ASAP或者SanRazor。然而，正如文章在第五小节提到，这些方法不能保证其可用性，甚至会降低ASan原本的检测能力。

  

为了确保优化不会损害ASan本身的检测能力，可延展性以及可用性，文章作者提出了ASan--，基于四个分别针对不同类型check的优化方案。

  

1.  移除不会触发error的check
    
      
    
    ![](../Images/395e015d0c16ac5451f19735fa558d73.png)
    
      
    
    在这个例子中，buf的size为20，i为buf的index，同时i(<=10)的值会永远小于buf的尺寸20，所以第5行的check可以被安全的移除，因为第6行访问永远都是inbound的。
    
      
    
2.  移除重复的check
    
      
    
    ![](../Images/393906a6bd9935ab30ded3d8efaac8d7.png)
    
      
    
    在这个例子中，第2行和第4行check相同的值p，同时第2行的check占据主导位置，所以第4行的check可以被安全的移除，因为第2行的check已经保证了访问p的安全性。  
    
      
    
3.  优化相邻的check
    
      
    
    ![](../Images/c2591730804661de681e4ad1cfa26afc.png)
    
      
    
    在这个例子中，第6行和第8行被check的值有相同的基址，所以在内存上它们是相邻的，这时我们可以将第8行的check合并到第6行check 1中，及同时check两个shadow byte的值。而第12行check 4位于第10行和第14行的check之间，任何触发第12行check的error都可以被check 3的后置redzone和check 5的前置redzone捕捉到，所以check 4也可以被优化。
    
      
    
4.   优化位于循环内的check
    
      
    

![](../Images/489f52042fcb12f83569613b7b197e8f.png)  
在这个例子中，第7行被check的值(ptr2)为恒定值(Invariant)，及值不受循环的影响，所以check 2可以被迁移到循环外执行，从而减少执行次数。而第4行被check值(ptr1+index) 为单调递增或递减值 (Monotonic Increase/Decrease) ，所以我们可以运用第3个优化方案，同时check多个shadow byte的值，来减少check的执行次数。

  

为了验证这四种算法的有效性，作者将ASan--用于目前业界使用最广泛的性能测试集SPEC CPU2006，同时分别统计了sanitizer减少的数量，以及对运行时间的优化。总体来看，ASan--可以减少38.7%的check，并同时带来41.7%的性能优化。下图是每个算法带来的优化：

  

![](../Images/67c509372206c0502b6f30b71641d5c4.png)

  

为了进一步证明ASan--并没有损害ASan本身的特性，作者分别使用了Juliet Test Suite和Linux Flaw Project进行Bug检测能力的对比。从下图可以看出，ASan--和ASan的结果是完全一致的，但是SanRazor会发生Bug漏报情况。

  

![](../Images/4c1ae8742b93370e803a311c4e745fcb.png)

  

SanRazor会检测不到CVE-2017-12858和CVE-2017-14406

  

![](../Images/e89bdb38fb7b01e9f78e24fbe3e737c5.png)

  

因为同时继承了ASan的可延展性，作者分别将ASan--用于编译由Google研发的Chromium，以及业界最受欢迎的Fuzzing。下图为用ASan--编译的Chromium，基于ASan在六个不同的Benchmarks上带来35.7%的性能提升：

  

![](../Images/c1e16fd217d404d05799783efed35c76.png)

  

对于AFL-Fuzz，ASan--编译的测试程序在24小时内可以提升约40%的运行速度，以及提高约5%的代码覆盖率。下图为测试所用的程序：
