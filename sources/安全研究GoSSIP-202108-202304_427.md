在这个美好的周末，我们非常荣幸邀请到[浙江大学网络空间安全研究中心](https://mp.weixin.qq.com/s?__biz=MzA5MzQ1MDI2MA==&mid=2456041684&idx=1&sn=0e5616b071b568c205363cef332469a5&scene=21#wechat_redirect)的老师和同学，为大家介绍他们在嵌入式固件安全研究方面的系列工作成果。固件（firmware），是一种为上层用户提供硬件支持的软件，通常存在于嵌入式设备中，从手机、路由器、摄像头、照相机到电脑中的键盘、硬盘，甚至工控设备、机器人中都可见到它的身影。传统的固件分析广泛地应用静态分析技术，利用特殊的常量、字符串或程序流图等方式来检测固件中的安全问题。这些方法简单有效，但是无法获取更多的运行时信息来更加深入地分析固件中的安全问题。浙江大学网络空间安全研究中心的老师和同学以及南洋理工、香港理工和佛罗里达州立大学的合作者在固件移植动态分析方面展开了研究探索，取得了一系列成果，包括 FirmGuide@ASE 2021，ECMO@CCS 2021，以及 EXAMINER@ASPLOS 2022。下面就是这几项工作的详细介绍：

### FirmGuide：Boosting the Capability of Rehosting Embedded Linux Kernels through Model-Guided Kernel Execution @ASE 2021

![](../Images/f02e7ae95908ac57f248fcd06ab54e7c.png)

当我们有固件的源代码时，是否能将固件移植到虚拟执行环境中呢？FirmGuide工作中，作者提出了一种模型引导执行的技术，并设计实现了FirmGuide工具。FirmGuide能半自动化地分析Linux内核源代码，生成虚拟设备模型，将基于Linux内核的嵌入式设备固件移植到虚拟执行环境（QEMU）中，以便固件安全分析人员对嵌入式Linux内核进行动态地调试和分析。要做到这一点面临三个挑战。

首先，片上系统（SoC）有许多外围设备。基于 Linux 内核核心功能是否需要外设支持的分类原则，作者将外设分为两种类型。Type-I 外设，包括处理器、内存、中断控制器、定时器和 UART，它们对于内存管理、调度和用户内核交互至关重要，则必须为他们设计高仿真度的虚拟设备模型。Type-II外围设备是不需要高仿真度的，作者仅仅需要适当初始化这些虚拟设备来通过一些检查，以免在Linux 内核在启动时卡住。为每种类型的外围设备设计高仿真度的模型是一个需要数年时间的复杂问题，这种分类以最小的努力，即专注于Type-I型外围设备，获取最大的效果，是移植嵌入式Linux内核并对其动态分析的第一步。接下来，作者将讨论在对 Type-I 外设建模时的另外两个挑战。

第二个挑战是即使是一种类型的外设，例如中断控制器，也有不同的模型。我们需要为每个中断控制器建模吗？答案是不。根据作者的观察，中断控制器的驱动程序必须遵守 Linux 内核在中断子系统中定义的协议。为了解决这一挑战，作者从 Linux 内核子系统中提取通用状态机，以进一步构建高仿真度的模型。  
第三个挑战是每个外设都有复杂的交互语义。例如，要屏蔽中断源，中断控制器将读取屏蔽寄存器，屏蔽特定位，然后将值写回寄存器。为了加载未决中断的编号，中断控制器将加载相应寄存器的值，解析它，并调用相关的中断服务程序。作者观察到中断控制器的驱动程序必须实现中断子系统中定义的回调。每个特定的驱动程序回调都通过 MMIO 读写序列嵌入了这种复杂的交互语义。同时，作者分析了 Type-I 外设的驱动程序，并从这些回调中提取出 MMIO 读写序列，以补充从中断子系统中提取的状态机。

![](../Images/033f34f6ffbf5d0bb3db7899a5047ebb.png)

作者在论文中提出了一种名为模型引导内核执行的新技术，这个想法是可以利用状态机模型来指导内核的执行。外围设备模型由两部分组成。第一部分是模型模板，即状态机。它是由专家手动构建的。请注意，转换条件为空。第二部分是MMIO读写序列作为转换条件。这部分可以通过分析驱动程序的源代码自动推断出来。模型引导的内核执行如何工作？外设模型监控Linux内核的执行，比较状态机中编码的MMIO读写序列，然后转移到相应的状态。最后，Linux 内核将成功启动并弹出一个交互式 shell。

![](../Images/6c8e829a1c7c915d9842d892b0185b82.png)

这是作者设计的系统设计和实现。FirmGuide 由两个组件组成。第一个组件“离线模型生成”，分析Linux内核源代码，最终生成虚拟设备。该组件使用 LLVM pass 进行预处理，使用 KLEE 进行 MMIO 读写序列分析，以及使用 Python 脚本进行粘合。第二个组件“在线内核引导”以二进制固件为输入，分析其设备树并列出外围设备，获取相应的设备模型，并生成整个虚拟机。该组件使用 Python 编写，利用模板渲染设计模式生成代码。  
作者评估的第一个问题是FirmGuide 可以生成哪些外围设备模型。如第一张表所示，FirmGuide 可以支持五个不同系列的 SoC，涵盖六个中断控制器和五个定时器。在参数推断中，符号执行引擎可以在 1 小时内解决第一个解决方案。作者还计算了 CFSV 和计时器语义感知值的数量。根据实验表明，这些外围模型可以移植嵌入式 Linux 内核，并保证Linux内核的基本功能。在第二个表中，作者列出了 Type-II 外设的数量以及我们应该处理的初始化值的数量。一般来说，由于初始值的数量有限，所以用符号执行很容易处理。

![](../Images/760b3d335d541b97ae5823b4986a958a.png)

![](../Images/bd3c2e7d9bcc90154f38fccc29e366a1.png)

第二个问题是可以移植多少嵌入式 Linux 内核。在图中，作者列出了解包固件的数量、提取的内核数量、进入用户空间的嵌入式内核数量以及弹出 shell 的嵌入式内核数量。对跨十家厂商、三种架构、22个Linux内核版本的六千多个固件，FirmGuide可以成功地移植其中的96%以上，显示了FirmGuide的可扩展性。

![](../Images/0b57530211de1687c92fae8a0fb4ad28.png)

第三个问题是通过 Linux 测试项目（LTP）中的系统调用测试工具测试移植的嵌入式 Linux 内核的功能。作者手动开发了一个 QEMU 虚拟机，并将结果与FirmGuide 生成的虚拟机的结果进行比较。表中的结果表明，在系统调用方面，FirmGuide 生成的虚拟机与手动开发的 QEMU 虚拟机具有相同的保真度。

![](../Images/b0d7ca5383a493da2289f05fb18d1d4e.png)

第四个问题是FirmGuide的应用。作者使用 FirmGuide 来复现和开发针对六个 Linux 内核 CVE 。作者还利用模糊测试来测试移植的嵌入式 Linux 内核。

![](../Images/776d1626aff48b9ab57928c343deb271.png)

总结一下，首先，作者提出了一种新技术。其次，作者设计并实现了第一个用于嵌入式 Linux 内核重新托管的半自动框架。最后，作者应用FirmGuide 来分析和挖掘嵌入式Linux 内核中的漏洞。

最后谈谈FirmGuide的局限性和未来的工作。首先，需要专家手动从 Linux 内核子系统中提取状态机。它取决于子系统是否有良好的抽象。对于复杂的外设，自动推断外设模型仍然很困难。其次，由于最小努力策略，FirmGuide 无法支持 Type-II 外设的高保真度。支持更多的Type-II外设，在嵌入式Linux内核中启用更多Type-II外设驱动的分析是一个重要的问题。

### ECMO：Peripheral Transplantation to Rehost Embedded Linux Kernels @CCS 2021

![](../Images/89a2b7726c8bdc3803f761493fcb907f.png)

当我们没有固件的源代码时，如何模拟执行嵌入式固件的内核呢?在ECMO这篇文章中，作者提出了一种外设移植的技术，并设计实现了ECMO工具。ECMO不需要嵌入式固件的内核提供源代码，给定一个固件的内核，即可将其自动地执行在虚拟环境中。值得一提的是，ECMO这篇文章开始做的时候正值20年初，疫情刚刚发生，很多重症患者因为感染病毒而心肺衰竭。那时候，通过各种新闻媒体，文章的作者们了解到了医学界的一个救命神器,叫做ECMO，中文叫做体外人工心肺。外设移植和ECMO的概念非常像。文章中主要移植的外设，如中断，Timer,之于内核就像是心肺之于人体一般。因此，给这个系统命名为ECMO。

模拟执行嵌入式固件的内核主要有三个挑战。1）外设具有依赖性，在内核启动过程中，会根据外设特定寄存器的值决定程序的执行路径。如果对这些外设的功能无法正常模拟，内核可能在启动过程中失败，宕机，或者陷入死循环。2）外设种类繁多，不同的嵌入式固件内核可能有不同的外设，这对开发一个普适的支持各种固件内核的模拟器带来了不小的挑战。3）厂商不一定会严格遵循GPL license的规定，源代码也许不会开源。这对于诊断模拟过程中可能出现的问题，以及理解特定外设的功能带来了挑战。

针对上述的挑战，ECMO 提出了一种叫做外设移植的技术。不同于构建精准的外设模型，外设移植会将特定的外设驱动以及外设的硬件模型通过动态二进制改写的方法，利用ECMO Pointers插入到待移植的固件内核中。这样做的好处是，无论原先内核中的外设是何种型号，都可以使用一个同样的外设将其替换。如不同的内核可能有不同类型的中断控制器，我们很难实现一个通用的中断控制器，支持所有类型的中断。因此我们可以统一使用VIC将其做替换。下图展示了ECMO外设移植的主要流程。

![](../Images/d7d87255703743966adfd056e2033314.png)

为了评估ECMO的有效性，可用性，作者将ECMO适用到了来自OpenWRT和Netgear的815个不同的嵌入式固件内核中，试图将中断（Interrupt Controller），时钟控制器（TImer）,以及通用非同步首发传输器（UART）三种不同类型的外设移植到目标内核中，实现内核的启动，并且可以进入到命令行，作者从四个维度评估了ECMO。相关实验数据见文末。

1.  对于外设移植高度依赖的ECMO Pointers, 作者发现，所有的ECMO Pointers都可以被准确确定
    
2.  815个内核中，710个可以被成功模拟执行，涵盖了37种不同的设备类型，20个不同的内核版本
    
3.  通过Linux 测试套件发现，模拟执行的内核支持94%的系统调用，表明其可用性和可靠性
    
4.  作者还基于模拟执行的内核开发了三个不同的应用，包括崩溃分析，rootkit分析，以及内核fuzzing

### EXAMINER: Automatically Locating Inconsistent Instructions between Real Devices and CPU Emulators for ARM @ASPLOS 2022

当我们进行模拟执行时，模拟器的准确性十分重要。模拟器可能对于指令的执行存在bug，或者跟硬件执行的结果存在不一样的情况。针对这种问题，固件分析系列的第三个工作 EXAMINER 给大家带来了解答。

Examiner其实也是西游记中“谛听”的英文翻译，谛听在于可以成功的分辨真假美猴王。而作者设计开发的Examiner的作用与谛听相似，旨在可以自动的寻找到那些在模拟器中和硬件设备中运行不一样的指令，为了可以有效地寻找这些指令，作者设计并且实现了第一个基于ASL的符号执行引擎，从而可以产生高效的种子，遍历所有的指令执行路径。进一步，作者通过差分分析，给CPU状态进行有效建模，从而寻找到那些在模拟器和硬件中执行结果不一样的指令。

ASL是一种用来描述ARM指令执行逻辑的语言，一条ARM指令，因为特定的符号位，值不同，可能会导致不同的执行逻辑。通过符号执行的技术，可以有效地探索到可以执行的路径。

![](../Images/dd76778cf7395ad28bed9fdf2ebfdbc6.png)

在产生了有效地测试用例后，作者对CPU建模，通过插入前缀指令初始化所有的寄存器状态，并且通过后缀指令，自动的将对应的状态获取，并记录下来做差分分析。

作者总共产生了包括A64,A32,T32,T16在内的两百多万条指令，并且将这些指令放在四种不同的硬件平台（涵盖ARMv5,v6,v7,v8）和三种不同的指令模拟引擎（QEMU, Unicorn, Angr）中进行差分分析，最终发现了几十万条不同的可以导致运行行为不同的指令。其主要原因在于ARM中的未定义的行为（UNPREDICTABLE）,其次，模拟器的执行也存在漏洞，比如共有12个模拟器的漏洞被揭露。下图是针对QEMU的执行结果

![](../Images/4786d197b8f67da18d04258686d494fc.png)

同时，作者还设计构建了3种不同类型的测试应用，包括虚拟器检测，反模拟执行，和fuzzing，来展示这些可以导致运行行为不一致指令的用途。
