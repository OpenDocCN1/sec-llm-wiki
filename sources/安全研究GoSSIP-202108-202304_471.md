今天给大家推荐的是来自USENIX Security 2021的一篇和fuzz相关的论文 —— "APICraft: Fuzz Driver Generation for Closed-source SDK Libraries"，作者提出了一种自动的fuzz driver生成技术 —— APICraft。  

![](../Images/59e41400a0c5545f3a0054f7fcf9ae60.png)

在通常情况下，如果要对一个库进行模糊测试，fuzzer需要一个调用该库的程序（fuzz driver）来提供一个入口点。该fuzz driver主要是由安全分析人员来实现，其效果也取决于安全分析人员的知识和能力。因此，本文的目标是设计一种高效的自动化生成fuzz driver方法。现有的自动化方法大多是利用SDK源代码来生成fuzz driver，尽管源代码能够提供准确的API信息，但是这也限制了这些方法无法应用到闭源的SDK中。

![](../Images/819a2e2bb81dce8c06d9991208bddca5.png)

本文提出了一个针对闭源SDK的fuzz driver自动化生成工具 —— APICraft，该工具以目标SDK及其consumer programs为输入，以生成的fuzz drivers为输出。APICraft主要分为三个阶段：  

1）Pre-Processing：利用多种分析手段（文件头分析、静态二进制分析、动态二进制分析）提取目标SDK的信息，输出结果包括一个library metadata的集合和consumer programs的执行过程追踪。  

2）API Function Dependency Collection：根据预处理的结果，收集数据依赖和控制依赖关系。

*   数据依赖：APICraft 认为当函数FA的输出与函数FB的输入存在交集，FB依赖于函数FA，表示为<FA, Out, FB, In>。
    

*   首先，APICraft 从SDK的头文件中收集函数的声明信息（包括参数和返回值的类型）。
    
*   然后，APICraft 通过hook每个函数来记录函数执行过程中的线程id、嵌套级别（如果直接由consumer program调用，则认为其为1；如果由SDK其他函数调用，则嵌套级别递增1）、输入输出值（参数、返回值、输出参数）。
    
*   最后，APICraft 可以获得一个按执行顺序排序的函数列表以及相关的输出参数；对于其中的任两个函数，APICraft 按照之前的定义尝试找到其中是否存在数据依赖关系。
    
*   此外，除了执行过程中提取的依赖，作者还指定了三条启发式规则来从已有的依赖中推理出新的数据依赖关系，以实现更高的覆盖率。
    

*   控制依赖：APICraft 记录执行追踪过程中记录的API函数的返回地址，通过静态分析和动态污点分析收集错误处理信息，包括每个函数的输出是否需要执行错误处理以及错误的条件。
    

3）Dependency Combination：在收集数据依赖和控制依赖之后，APICraft 通过多目标遗传算法（NSGA-II）来利用提取的依赖关系来生成fuzz driver。

*   APICraft 首先从输入相关的函数出发，通过随机、重复地链接提取到的数据依赖来构建数据流（fuzz driver）。APICraft 根据三个指标来评估数据流的质量。
    

*   Diversity：fuzz driver要包含尽可能多的函数和数据依赖
    
*   Effectiveness：fuzz driver要尽可能正确的调用函数API，减少误报
    
*   Compactness：fuzz driver要尽可能减少重复或不相关的函数调用/数据依赖，以降低人工成本和计算资源的使用  
    

*   之后，APICraft 利用控制依赖关系来提高fuzz driver的健壮性。  
    

  

作者利用macOS SDK中的五个常见的攻击面（Image, Font, PDF, Audio, RTF）来对 APICraft 进行评估，实验数据集中包含13个macOS的内置应用（即consumer programs）。作者对APICraft 的有效性和性能进行了评估，并将其与人工编写的fuzz driver进行了比较。结果表明，APICRAFT 在时间和效果上具有较为明显的优势，其生成的fuzz drivers在macOS SDK中一共发现了142个漏洞。
