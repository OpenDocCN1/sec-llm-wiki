8月的最后一天，送上一篇来自软件工程会议ESEM 2021的论文，调研了一个有意思的问题：许多移动应用APP与服务器通信过程中，专为APP提供的服务器可能存在与一般的 Web 应用相同或相似的安全问题。作者测试并分析了大量提取自 Android 应用的 URL，统计发现超 69% 的 Android 应用的服务器端存在三种及以上的安全问题。在这些安全问题中，未受保护的通信与配置错误最为普遍。具体地，作者详细分析了移动应用服务器端六类安全问题的普遍性并从安全角度调查了这些安全问题可能导致的后果及体现的问题，通过间隔 14 个月的两次数据收集，分析了安全问题与服务器维护之间的关联性。研究结果表明，使用 JSON 格式的服务器存在的问题是未使用 JSON 格式的服务器的 1.5 倍，而闭源应用存在的问题是开源应用的 1.6 倍。在这些安全问题中，源代码及版本信息泄露、缺乏更新对服务器都是很大的安全隐患。




随着 Web 服务的发展，基于 Web 的移动应用不断增长，移动应用与服务器端的通信安全越来越被重视，出现了许多针对移动应用和服务器端开发的安全支持工具。但这些工具往往是在开发过程中使用，从代码层级保护移动应用的安全，而一些现存的服务器端 API 的配置安全问题没有得到足够的重视。之前的一些工作已经总结出移动应用的服务器端 API 可能存在的八种安全问题，因此，作者主要解决以下两个问题：

  1. 这些服务器端的安全问题在移动应用中的普遍性如何

  2. 这些安全问题与服务器维护之间存在什么关联

在研究过程中，作者主要分析八种安全问题中的六种，并总结了这些安全问题的特征：

  1. Insecure transport channel (不安全的传输信道)

    使用不提供任何安全防护的 HTTP 协议而非更安全的 HTTPS 协议，HTTP 协议中一切以明文传输，传输的任何信息都不会被加密。

    特征：URL 以 http:// 开头

  2. Disclosure of source code (源代码泄露)

    没有对服务器端错误进行合理处理，直接将报错信息返回给移动应用，这些报错信息可能会含有错误发生处的调用栈，可能会泄露所调用的方法名、源代码文件名及错误发生的行号，甚至可能包含错误发生的代码片段。

    特征：HTTP 响应体包含错误发生处的调用栈或代码片段。

  3. Disclosure of version information (版本信息泄露)

    服务器端返回的一些 HTTP 头 (如 X-Powered-By) 可能会泄露程序的版本信息，对于一些版本较老的程序，攻击者可能会直接通过这些版本信息找到对应的漏洞进行攻击。

    特征：HTTP 响应头存在以下字段之一：engine, server, x-aspnet-version, x-powered-by。

  4. Lack of access control (缺乏访问控制)

    敏感数据和敏感操作的访问权限并未受到严格的控制，使用了攻击者容易伪造的认证方式或者根本没有采取任何权限认证，直接向访问者提供所有数据。

    特征：服务器没有返回 401 Unauthorized 或 403 Forbidden，而是在没有提供任何凭证的情况下成功访问到数据。

  5. Missing HTTPS redirects (缺乏 HTTPS 重定向)

    尽管服务器以及支持加密的 HTTPS 协议，但并没有将 HTTP 请求重定向到 HTTPS，对于老版本的应用发起的 HTTP 请求，直接使用没有安全防护的 HTTP 协议进行处理。

    特征：对于 HTTP 请求，不会通过 HTTP 3xx 重定向到 HTTPS，而是使用 HTTP 继续请求。

  6. Missing HSTS (缺乏 HSTS)

    HTTP Strict Transport Security (HSTS) 提供了针对 HTTPS 到 HTTP 降级攻击的防护，如果没有配置 HSTS，用户在访问时可能受到诸如 MITM (中间人攻击) 等攻击，将用户的请求重定向为 HTTP 请求，并对其进行攻击。

    特征：HTTP 响应头中没有提供 Strict-Transport-Security 字段。


EMPIRICAL STUDY

Dataset

作者在 2019 年六月和 2020 年八月两次收集数据构成实验数据集，并通过对数据集的分析开发工具用于自动化的提取 Android 应用中存在的 URL 和对应的 HTTP 请求。

数据集包含 303 个开源应用和 3073 个闭源应用，其中闭源应用来自 Google Play，开源应用来自 F-Droid。这些应用来自 Google Play 中 48 个不同的分类，绝大部分的应用都有 3.0 及以上的评分 (满分 5.0)，下载量位于 100-1000 之间的应用最多，大多数应用的上一次更新时间为 2018 年 (数据统计于 2019 年)。

最终，从这些移动应用中共提取出 9716 个 URL，其中开源应用提取出 1230 个 URL，闭源应用中提取出 8486 个 URL。在这些 URL 中，只有少部分请求使用了现在常用的 JSON 格式，大部分采用了传统的 XML 格式或纯文本格式。在开源应用的 URL 中，只有 59 个 URL 的请求中使用了 JSON 格式，而在闭源应用中，使用 JSON 格式请求的 URL 有 489 个。

接下来的部分从是否开源以及是否使用 JSON 格式两方面进行统计分析。

Prevalence

这一部分通过对数据集进行统计分析，回答了 Introduction 中的问题 1，这些服务器端的安全问题在移动应用中的普遍性如何。

作者首先分类统计不同应用中含有各安全问题的比例，结果显示，对于开源应用，约半数的非 JSON 格式的服务器端 API 使用了未受保护的传输信道，而只有约 10% 的 JSON 格式 API 存在该问题；而对于闭源应用，该问题更加严重，约 71%的非 JSON 格式 API 和约 50% 的 JSON 格式 API 存在该问题。

对于其它的安全问题，统计结果如下图所示：

之后作者又分析了对于存在源代码泄露问题的 API，统计了他们所使用的应用框架，结果显示，共识别出 5 种应用框架：ASP(.net), PHP, CherryPy, Java, NodeJS，对于闭源应用，绝大多数存在源代码泄露问题的 API 均使用了 ASP(.net) 框架，而开源应用只有 6 个 API 存在源码泄露问题，分别由 ASP(.net) 或 CherryPy 引起。

而对于存在版本信息泄露问题的 API，作者从操作系统信息、服务信息和引起版本信息泄露的响应头或响应体三方面进行了统计分析，其中泄露最多的操作系统为 Ubuntu，泄露最多的服务为 Apache。存在于响应头中的版本信息泄露问题由 Server, X-Powered-By, X-AspNet-Version, X-AspNetMvc-Version 等字段产生，存在于响应体中的版本泄露问题由 Apache, Nginx, Apache H3, OpenResty, CherryPy 等服务产生。

对于缺乏权限控制问题，只有 53 个闭源非 JSON 格式 API 和 28 个开源非 JSON 格式 API 存在该问题，JSON 格式 API 均不存在该问题。

绝大多数缺乏 HTTPS 重定向的问题出现在闭源非 JSON 格式 API 中，且存在 48 个闭源非 JSON 格式 API和 15 个开源非 JSON 格式 API 存在 HTTPS 到 HTTP 降级风险。

对于 HSTS 的问题，作者对多种不正确的配置分别进行了统计，绝大多数 URL 均存在 HSTS 配置不当的问题，其统计结果如下图所示：

根据以上统计结果，作者总结，大多数安全问题存在于超过 25% 的 Android 应用中，无论应用开源或闭源，使用了 JSON 格式或未使用 JSON 格式，这些普遍存在的安全问题都可能对应用造成很大的威胁。

Maintenance of Server Infrastructure

作者通过研究服务器维护操作并分析其与安全问题的相关性，回答了第二个问题，这些安全问题与服务器维护之间存在什么关联。作者调查了两次数据收集之间的 14 个月内服务器技术设施的升级情况，这些升级情况通过 Server 响应头对比两个数据集之间的版本号差异获取，所以这部分的统计数据只包含 309 个开源应用和 3006 个闭源应用。

在分析前一百个 API 时，作者总结出以下八种不同的情况：

  1. 应用没有任何更新

  2. 应用降级，即版本号降低

  3. 应用升级，即版本号升高

  4. 版本信息泄露问题被修复，无法获取具体版本号

  5. 环境发生改变，即所用应用被替换

  6. 使用了 Cloudflare 的保护，版本信息被 Cloudflare 替换

  7. 第一次测试没有收到版本信息，第二次测试收到版本信息

  8. 第一次测试收到版本信息，第二次测试没有收到版本信息

对于以上八种情况的统计结果如下图所示：

统计发现在 14 个月内，绝大多数应用没有进行升级，也有较多应用的环境发生改变，只有很少一部分 (103 个)  应用彻底解决了版本信息泄露的问题，另外还有很少一部分应用 (104 个) 使用了 Cloudflare 保护，也间接解决了版本信息泄露的问题。

由上述结果可以得知，服务器端包含五种安全问题时，进行服务器维护的比例最低，而含有一种安全问题的情况下，不存在没有进行维护的服务器，而随着包含安全问题的增多，进行服务器维护的比例呈下降趋势，因此作者推测大量安全问题表明服务器缺乏维护。
