动机

  

       最低可用安全产品（Minimum Viable Secure Product，MVSP）是B2B软件和业务流程外包供应商的一个最小安全检查清单。

        设计时就考虑简单性，为保证合理的安全态势，检查列表只包含那些必选的、必须实施的最少项目。

        我们推荐所有打造B2B软件或在最广泛定义下处理敏感信息的公司，实施所列控制，并强烈鼓励他们在安全程序中远远超出这些控制。

  

哪些地方使用？

需求建议

       厂商选择通用基线，简化了采购团队的工作。MVSP精炼简洁，可用包含到RFP文档中，不会使之臃肿。

自我评估

        尚未足够成熟、无法承担SOC 2和PCI DSS等大型合规工作的小型公司，使用MVSP作为基线，保证他们最小可用产品的安全态势。

第三方安全

       尝试对供应商安全态势分类的大型公司把MVSP作为他们通用的调查问卷。

现有技术

        MVSP的动机来自Dropbox 的供应商安全模型合同（Vendor Security Model Contract ，VSMC）和谷歌的供应商安全评估调查问卷（Vendor Security Assessment Questionnaire ，VSAQ）。

       我们已经分析了现存主要协议，生成了一个包括其中大部分要求的基线。

 

检查清单

  

| 1 业务控制 |
| --- |
| 控制 || 描述 |
| 1.1 漏洞报告 || 

*   在你的网站上，发表安全报告的联系人
    
*   在合理的时间范围内，响应安全报告
    

 |
| 1.2 客户测试 || 

*   根据要求，让你们的客户或他们的代表测试你应用的安全
    
*   在非生产环境测试，如果其在功能上和生产环境非常类似
    
*   保证非生产环境不包含生产数据
    

 |
| 1.3 自我评估 || 使用这个文档，最少每年执行自我安全评估 |
| 1.4 外部测试 || 联系安全厂商，在你的系统上，每年执行全面的渗透测试 |
| 1.5 培训 || 对和他们业务职能有关的个人，实行基于角色的安全培训 |
| 1.6 合规 || 

*   遵守和你业务有关的所有行业安全标准，如PCI DSS，HITRUST，ISO27001，SSAE18
    
*   遵守适用于你的公司和你的客户司法管辖区的本地法律法规，例如GDPR，约束性公司规则，标准合同条款
    

 |
| 1.7 事件处理 || 

*   入侵发现后不晚于72小时提醒你的客户，不得无故拖延，
    
*   通知中包括下列信息：
    
*   相关联系人
    
*   入侵的初步技术分析
    
*   修复计划的合理时间表
    

 |
| 1.8 数据清除 || 基于NIST 800-88或同等标准，确保媒介清除流程 |
| 2 应用设计控制 |
| 控制 || 描述 |
| 2.1 单点登录 || 使用现代和行业标准协议，实施单点登录 |
| 2.2 只用https || 

*   重定向http协议到https
    
*   使用广泛采用的TLS扫描工具，执行扫描
    
*   在所有使用includesubdomain指令的页面，包含Strict-Transport-Security头
    

 |
| 2.3 内容安全策略 || 设置最小许可的内容安全策略 |
| 2.4 密码策略 || 除了单点登录，是否使用其他密码认证：

*   不要限制可以使用的字符
    
*   不要限制密码长度，只要小于64字符
    
*   不要使用秘密问题作为密码重置唯一要求
    
*   密码变更时，要求电子邮件验证
    
*   密码变更时，要求输入现有密码
    
*   根据常用密码列表或泄露密码数据库验证新生成的密码
    
*   定期检查当前用户密码，防止密码泄露
    
*   使用内存耗费（memory-hard）或CPU耗费（CPU-hard）单向哈希函数，以哈希格式和加盐格式存储密码
    
*   账户访问时，实施适当的密码锁定和防暴力破解保护
    

 |
| 2.5 安全库 || 通过转义输出和清理输入，使用框架、模板语言或库，系统地解决实施弱点， |
| 2.6 依赖补丁 || 排名“中等”或更高的补丁，尽快升级，保证在补丁发布的一个月内，应用栈所有组件得到同样的缓解措施 |
| 2.7 日志 || 保存日志：

*   用户登录和退出
    
*   应用、系统用户和操作对象的读、写、删除操作
    
*   安全设置变更（包括关闭日志）
    
*   应用所有者访问客户数据（透明访问）
    

日志必须包括用户ID，IP地址，有效时间戳，操作类型和对象。日志必须存储30至少30天，不能包含敏感数据或payload |
| 2.8 备份和灾难恢复 || 

*   异地备份所有数据
    
*   维护和定期测试灾难恢复计划
    
*   定期测试备份恢复
    

 |
| 2.9 加密 || 使用现有的加密方式保护系统间传输的敏感数据和在线数据存储和备份的静止数据 |
| 3 应用实施控制 |
| 控制 || 描述 |
| 3.1 数据列表 || 维护应用程序将要处理的敏感数据类型列表 |
| 3.2 数据流图示 || 维护最新的图表，指明敏感数据如何到达你的系统，最后存储在哪里 |
| 3.3 漏洞阻止 || 培训你的开发人员并实施开发指南，至少阻止下列漏洞：

*   授权旁路绕过。例子：从普通账户访问其他客户数据或管理功能
    
*   不安全会话ID。例子：可猜测token；存储在不安全位置token（例如，没有设置安全、httponly标记的cookie）
    
*   注入。例子：SQL注入、NoSQL 注入、XXE、os命令注入
    
*   跨站脚本。例子：调用不安全JavaScript 函数、不安全DOM操作、将用户输入返回html而没有转义
    
*   跨站请求伪造。例子：接受来自不同域的初始报文头的请求
    
*   使用漏洞库。例子：使用有漏洞的服务器端框架或JavaScript库
    

 |
| 3.4 修复漏洞时间 || 漏洞发现后90天内，生成和部署补丁，解决影响安全的应用程序威胁 |
| 4 操作控制 |
| 控制 || 描述 |
| 4.1 物理访问 || 验证相关设施物理安全，保证已使用下列控制：

*   分层的边界控制和内部隔离措施
    
*   秘钥托管访问
    
*   进入和退出日志
    
*   入侵报警的合适响应计划
    

 |
| 4.2 逻辑访问 || 

*   只允许有合法需要的用户访问敏感信息，数据所有者必须授权这种访问
    
*   及时取消冗余账户和过期的访问批准
    
*   执行定期访问检查，验证需要知道的信息
    

 |
| 4.3子进程 || 

*   在你网站上发布可以访问客户数据的第三方公司列表
    
*   依照本基线，每年评估第三方公司
