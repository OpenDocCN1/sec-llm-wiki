# Gartner DevSecOps够酷厂商，2021年

在应用安全领域的创新，重点是满足DevOps开发类型对速度和自动化的要求。本报告总结了四家厂商，他们的创新技术把安全引入到这些新的开发类型中，实现高效率的DevSecOps。

概述

关键发现

*   满足DevSecOps要求的、传统的开发工具无法提供的自动化安全能力。
    
*   使用基于风险机制的方案，帮助安全团队识别最需要关注的特定应用的代码，减少在非生产性测试上花费的时间。
    
*   在CI/CD管道中集成应用安全控制，鼓励安全团队寻找新的工具，能更简单和无缝集成到DevOps工具链中，而且不会降低DevOps速度。
    

推荐

负责DevSecOps的安全和风险管理的领导者们，应该：

*   仅仅在真正值得注意的代码变更时执行测试，基于它可能引入的风险，评估每一次变更。
    
*   为了自动识别潜在应用风险变更，解决威胁建模时的任何漂移，评估和监控应用组件及配置。
    
*   尝试使用新的方法，在开发和部署之间，实现代码漏洞的自动化修复。
    

分析

        这个研究并没有在任何给定的技术领域，打造一个包含全部厂商的详尽名单，而只是重点关注有趣的、新的、创新的厂商、产品和服务。Gartner 否认和本研究有关的任何明示或者暗示的保证，包括对可销售性或特定意图的适用性的任何保证。

你需要知道什么？

        DevOps引入了一个安全挑战，想把开发和运营团队更紧密地团结在一起。DevOps的目标是快速和持续地交付新应用和功能。传统的安全流程和工具并不是为这个目的而设计的，既拖累了DevOps流程，减少了DevOps的敏捷优势，也没有明显地提高安全性。

        DevSecOps的理想是解决DevOps带来的安全挑战。DevSecOps把安全引入到DevOps中，不会降低DevOps本身具有的速度和灵活性。为了达到这个目标，DevSecOps需要从安全的角度，关注真正重要的事情，提供自动化的方法修复这些问题。

        本报告概述了四个厂商，他们创新性的解决方案展示了安全和应用开发的领导者们，如何能够去掉混乱，自动化执行DevSecOps，他们提供的产品帮助回答了如下图所示的常见问题—把安全集成到DevOps生命周期中。

  

  

![](../Images/04e01575438b6b254f30d16ff790f712.png)

这四个厂商是：

*   Apiiro。基于风险，识别代码中值得安全关注的一些资料变更，通过评估技术上的发现和例如开发人员技能等信息来实现这个目的。
    
*   Bionic。监控应用组件和配置，以便识别也许需要修订威胁建模结论的风险变化。
    
*   Jaroona。提供自动化代码漏洞修复—在应用安全测试领域很难实现的功能。
    
*   Sqreen。提供应用运行时监控和防护，曾经入选以前的“够酷厂商”，在本报告末尾的“他们的现状”部分有介绍。
    

Apiiro 

以色列，特里维拉  www.apiiro.com

        为什么够酷：Apiiro提供了一种自动识别需要安全关注的代码资料变更的方法。排除了大多数没有产生安全风险、因此也不需要安全测试的变更。基于代码和开发元数据，如代码提交信息，拉取需求讨论和用户故事，也包括开发者资历等背景信息，对这些信息历史上的变化做持续分析。Apiiro关联企业资源控制管理者和ticket系统，有选择地连接应用安全测试工具，如白盒扫描器，软件成分分析工具和API网关。

挑战：

*   因为Apiiro的方案透明操作，买家可能很难在内部传达其价值
    
*   Apiiro方案基于风险指标，忽略掉不引起安全注意的不重要资料变更，这个方法会有漏报的风险
    
*   Apiiro客户必须要做需求评估，以决定他们的需求，以及在工具中如何反映需求
    

谁应该关注：

*   寻找简化SDL流程的安全领导者们，应该监控Apiiro提供的方法。
    

Bionic    

美国加利福尼亚，帕罗奥图  www.bionic.ai

        为什么够酷：Bionic 开发了一种无代理方法，对应用组件和他们的配置建立了一个基线目录，使复杂和快速变化的应用具有更多的可视化—包括服务依赖、数据流和架构漂移。随着应用变得更复杂和短暂，以及开发速度的提高，这种可视化帮助应用安全团队保持他们对应用架构的了解，保证符合架构标准。也加快了威胁模型的变更、潜在安全或合规违反行为，漏洞等方面的识别。

        应用安全团队需要保持和开发团队一致，避免生成摩擦和拖累流程—这一直是一个长期的挑战，而且被更快的开发流程和更复杂的架构不断的强化。Bionic的方法帮助安全团队理解经过管道的新代码的安全含义，不会减慢代码引入流程。

挑战：

*   Bionic工具收集了架构、控制和数据流信息，组成了一个综合性的阵列，但用户仍然需要把这些信息转化成可操作的任务。Bionic可能必须要注意，客户在这一点上做的有多成功？给他们提供额外的帮助，实现对安全和开发架构、操作手册、工作流的集成。
    
*   所提供的信息对组织内的多个成员有价值，包括安全团队、开发人员和架构师。并有可能和其他搜集信息的工具存在潜在的竞争关系，这需要精确的定义出和其余宣称提供同样类型数据工具的区别。
    
*   虽然Bionic 对DevOps工具和云平台，特别提供了一系列有用的集成，但客户还需要做其他的集成来保证和他们环境的适配，跟上不断出现的新的信息源的步伐。
    

谁应该关注：

*   应用安全团队。他们可以使用Bionic工具来加强安全标准和作为一个数据源，帮助他们了解应用，因此简化识别和修复合规及漏洞问题。Bionic工具也被用于应用程序现代化中，帮助开发团队在云环境中重构应用。
    
*   安全领导们。他们寻找实用的机制去提高他们对复杂应用环境的理解，以改进威胁建模和风险评估，保证对安全及架构标准的合规，维持对其的了解。
    

Jaroona

维也纳，奥地利  https://jaroona.com

        为什么够酷：Jaroona有一个与众不同的技术，可以识别安全漏洞和建议代码修复。而不是给开发人员提供一个建议的最佳实践去修复漏洞。Jaroona训练了一种机器学习算法，在建议自动化修复之前，先扫描来自其他的SAST工具和开源软件中修复代码。然后再扫描自动化修复的代码，保证修复这个问题不会引起其他问题，交付更加干净和快速的方案。

挑战：

*   大多数SAST厂商声称已经有了这个能力，但他们只提供基于最佳实践的建议和高水平的指南，或在某些情况，利用远程人工对话方式解决。虽然Jaroona的修复功能是独一无二的，可厂商面临着一个挑战，把自己和其他宣称提供同样方案的厂商区分开。
    
*   Jaroona的技术，非常有趣，有很高的潜在价值，但没有在大规模的部署中得到验证
    
*   自动化代码修复和DevOps的一些原则相抵触，如“拥有你的代码”原则，即只有开发人员应该更改代码，因为只有开发人员对此有责任。虽然这个原则关注的是代码所属权，而不是修复，但这可能是一个明显的障碍。
    
*   自动代码引擎名声不一。在过去，使用这些类型的机器学习工具修复代码，但代价是降低了性能或可靠性。Jaroona的技术，能够设置成验证模式，因此一个开发人员必须在实施修复前来验证它，而且，对开发人员提供自动修复建议之前，Jaroona通过检测分析返回结果，保证任何以前报出的漏洞已经得到修复。
    

谁应该关注：

*   没有安全编码经验的开发人员，或者相对于工作量，积压了大量安全相关的技术债务的组织
    
*   小的或中等规模的团队，缺少时间和修复资源去保证正确的安全软件开发生命周期。
    
*   安全和风险管理领导人，开发部分的领导，有降低组织不安全代码风险的任务
    

他们的现状

Sqreen

加利福尼亚，旧金山   www.sqreen.com

        曾入选Gartner 2019年，安全和风险管理的够酷厂商

        为什么够酷：Sqreen 通过监控应用运行时他们的行为来保证应用安全，并从内部提供保护。具有一系列模块，根据每个应用的需要，可提供运行时安全防护（RASP）,应用内Web应用防火墙，内容安全策略和虚拟补丁。

        他们的现状：2021年，Sqreen被Datadog收购，一个应用性能监控厂商。Gartner已经说明过，应用性能监控和应用安全监控正在融合，这次收购扩展了这个进程。这两个厂商方案可能的集成，会和思科的AppDynamics，还有Dynatrace的产品进行竞争。

谁应该关注：

*   寻找一个创新的、模块化的、基于平台的方法来监控和保护重要应用的组织的安全和应用部门的领导们
