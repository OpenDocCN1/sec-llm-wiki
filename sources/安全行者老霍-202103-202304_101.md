为什么精确度重要  

开源软件使用广泛，Sonatype 2018年软件供应链状态报告表明，平均每个应用包括100个以上的开源组件，构成应用代码库80%-90%。2018年，单单被JavaScript开发者下载的npm包，每周的下载量就达到70亿，Java的下载量大约每年1460亿，比前一年增加68%。

软件团队对开源代码的兴趣增加有很多原因，开源组件给开发团队提供了重要的功能，加速推向市场的时间，大规模的降低了开发成本。如果一个应用50%由开源软件组成，都用自己编写代码代替的话，需要组织或者增加50%的开发人员，或者增加50%时间，在今天的世界，这两个都无法接受。

随着开源软件消耗量的增加，大家也明白，无法管理的使用也带来的组件中安全漏洞和限制许可证导致的风险。今天，每八个开源组件中，就含有一个已知漏洞，平均漏洞的爆发时间已经从45天减少到3天。现代软件的开发节奏已经超过了组织手工发现风险组件，并缓解风险的能力。需求增加导致投入增加，好几个厂商已经进入这个市场，提供不同的功能解决这个问题。本文考察这些公司使用的不同方法。

你不能保护你没看见的

任何安全程序的一个基本的信条就是理解你系统和应用中现存的风险，然后对风险缓解步骤做优先级排序。对开源风险，这要求组织对应用中的所有开源代码具有透彻的了解。没有这些，你无法保护不正确的许可证和安全漏洞等已知风险。

软件组成清单

每个生产过程要求一个物料清单，所需的每一个部件的列表。这帮助公司在整个供应链流程中，标准化部件和减少费用。也允许他们快速解决质量问题。当一个部件有问题（想想汽车的安全气囊），他们能很快的决定，哪个单元受到影响，对修复步骤排序。

对软件也是如此，在软件组成清单的帮助下，组织能跟踪所使用的每一个外部的组件，当一个组件发生问题时，更好的解决问题。在安全使用场景中，知道每个组件的确切版本很重要，既然漏洞常常影响组件的特定版本，精确性允许团队快速鉴别风险，减少不必要的重复工作，比攻击对手领先一步。

软件如何构建

如前所述，开源软件改变了软件的构建过程。15年前，从头构建应用是非常普遍的。开源软件的引入，很快就达到了占领大多数应用的代码库的现状。开发人员在工作中和代码库中维护开源组件，缺省首先采用开源代码，然后再编写定制专有代码。开源代码有三种方式进入代码库：

*   直接依赖库
    

开源组件常常被软件工程师直接添加到代码库中，这是在不使用“包管理器”的编程语言中，唯一被使用的添加开源组件的方法，如C，C++。

*   声明依赖库
    

使用包管理器的编程语言，软件工程师构建过程清单中，可以声明需要一个组件，构建工具将会从二进制代码库中引入这个组件，如Nexus Repository。

*   传递性依赖库
    

当一个声明依赖库要求额外的开源组件，才能正确运行时，会要求传递性依赖库。

    在组件添加到应用时，这三种方法都可以产生许可证和安全风险。因此弄清以任何方法增加的组件，都很重要。

不准确软件清单的后果

不完整的软件组成清单，可能漏掉导致安全风险的组件，每年几千个开源漏洞被暴露出来。对这些漏洞的攻击软件常常在暴露后几天之内就可公开获得。甚至一个经验不多的攻击者也能简化攻击载体。如Equifax，Canada Revenue Agency，Okinawa Power，Delaware大学等事件。从一个许可证的角度，如果一个漏掉的组件，正好是在受限开源软件许可条件下发布的，如GPL，“其衍生出来的工作”包括应用程序的其余部分，将使知识产权处于风险之中。想像一个大的制造公司，不得不对开源社区和竞争者们，发布他们占有优势地位的代码的情景。

当组件清单被误识别时，软件组成清单也是不精确的。或者由于选择了错误的开源项目，或者由于选择了错误的版本。前者带来了和漏掉软件成分完全一样的风险，后者增加了一个组织不正确假设一个漏洞没有影响组件的风险，导致不必要的工作。

生成一个完整和精确的软件组成清单并不是一个简单的过程，在早期，一个部分软件组成清单，需要向开发管理者询问软件列表，管理者会写下她知道的组件，但清单毫无疑问是不完整的，个人开发者也不可能有完整的清单，因为他们在按期交付预订功能的持续压力下，使用开源软件是他们工作很自然的一部分，手动记录每个库和版本，也是让人难以接受和不可靠的实践。即使一个开发人员注意到他加入代码库的每个组件，他们也不可能知道几十个自动加入构建过程的传递性依赖库。

打造一个软件组成清单

一个自动化生成软件清单的过程，监控风险，减少开发人员的负担，允许合规，安全和工程团队就策略达成一致，并加强这些策略。软件清单越精确和越完整，结果就越有用和越有可执行性。首先，我们看一个快速但不完整的方法，然后，一个缓慢，但仍然不精确的方法。

为声明依赖库打造过程监控

构建软件组成清单最简单的方法，是仅仅看开发人员在包清单中的声明，一个功能应用需要哪个组件。使用这种方法的工具，通过查看文件或清单中打包指令并以字母数字顺序查找文件名记录来识别组件。换句话说，仅仅重复开发人员列表和证实组织相信存于软件供应链中的信息。

这当然是生成软件组成清单最快的方法，但缺少很多方面的信息：

完整性

*   包管理器对开发人员添加到代码库中的任何直接依赖包都不清楚，这种方法只能确认包管理器列表内容，会错过很多组件。
    
*   对不使用包管理器的软件语言，这个方法就不起作用了，如C，C++。企业使用多语言开发，也许需要多种工具。
    

精确度

*   一个包管理器提供组件的坐标，这样构建系统知道从哪里加载这个组件（e.g..org.apache.struts:struts-core:1.0）。坐标复制是一个常见的问题，仅仅因为包管理器认为它有了正确名字空间的文件，不意味它不是一个从其他包仓库中的被修改过的。甚至一个字符的区别都能生成误报或者漏报。完全弄错组件。
    
*   包系统插入一些未知组件，无法按照字母数字顺序识别。
    
*   多个常用的打包系统，将上述问题复杂化，产生更多的噪音，这样生成的软件组成清单驱使开发人员去追逐可能不存在的漏洞。
    

直接依赖包的源代码签名

其他生产软件组成清单的简单方法，是检查源代码，计算每个文件的哈希值。这些哈希值和数据库中的已知源代码和代码片段哈希值对比，相比只监控构建过程，这是一个进步，常常可以发现由开发人员直接加入的组件。但它也有缺点

DevOps兼容性

*   及时性。DevOps环境要求精确和即时反馈。计算哈希值和同云里面的厂商数据库对比，耗费时间。这个方法也许会产生“部分匹配”（见下段），要求人工检查，进一步延迟结果。
    

完整性

*   修改库也许不会被检测到，开发人员常常增加、删除、修改开源组件，这会引起哈希值同厂商计算的不一样，导致或者漏掉组件，或要求人工检查，确认正确的组件和版本。
    

精确度

*   不正确的匹配能错误地混淆类似的组件，这是因为存在共同的编码特征，使不同的源代码片段表现类似。基于碎片分析的源代码匹配，导致许多误报。
    
*   因为被给的一段源代码，特别是在开源软件中，常常存在于多个项目中，在一个项目中，可能存在一个组件的许多版本，导致冗余的匹配结果。这就产生多个重复组件的软件清单。当和这个组件有关的一个漏洞被暴露出来，也常常会出现多次报警。
    

一个不同的方法，高级二进制指纹

    开发和安全团队，特别是DevOps团队，需要速度，准确度和精密度。上述方法的不足之处是列出一个应用中完全的和精确的组件清单，Sonatype投入了必要的时间和精力，在数据科学中，找到新的技术、流程和算法。高级二进制指纹允许Sonatype快速精准识别一个应用中所有的开源组件，避免其他方法中常见的误报和漏报，实现在DevOps环境中成熟的软件成分分析方案。

这是成果的两个例子：

*   Java
    

一个应用程序作为Java Enterprise Archive (EAR)制件提供，EAR包含三个Java web application（WAR），每个WAR包含许多JAR文件，包括通过修补（分叉）一个开源项目并重新编译它来创建一个新的自定义JAR文件。Sonatype高级二进制功能，能成功识别所有嵌套文件，而且，专利算法将触发相似性结果，对分叉开源代码，包括项目版本，指出相近的部分匹配。

*   JavaScript
    

一个应用程序作为自解压zip文件提供，文件包含许多JavaScript文件，包括一个jQuery依赖库文件，然而，文件被重命名，jQuery依赖库方面，在丢失了许多识别信息，使用Sonatype的专有匹配技术，能够识别组件，跟踪到最初的jQuery依赖库，包括特定的版本。

在数据情报上的精准匹配

    一旦你能够精准的识别组件，下一步是保证描述组件的元数据足够精确。这支持DevOps环境  通过自动化的流程调整，而不是人工检查，允许一个组件的可接受度(与策略相比)。

    组件识别之后，借助各种数据库搜索如组件名称相关的安全暴露，将不可避免的产生质量不高的信息，Sonatype投入一个数据专家团队，进行专有研究，开发组件的深度情报，团队使用公开和专有数据接入，挖掘常见的代码库（如Github），监控项目Web站点，提供比NVD或邮件清单更多的漏洞信息，进一步，团队能够给用户更快的提供信息，比其他信息源提前几周识别漏洞，更重要的是，数据研究人员从来都不仅仅依靠那些没有完整、独立、软件风险分析的信息源。

    对许可证，这意味着不仅仅依靠项目本身许可证声明，也考察源代码的代码头。对于安全缺陷，这意味着不仅仅依靠公开报告的问题，还要识别漏洞的根本原因，记录修复路径或可替代的解决方案。对其他属性，这意味着架构和项目完整性定量和定性评估。

有信心加强策略

    精确性是赋能团队，做出更好决定的唯一之路，这样他们能够扩展的更快，足够灵活的控制，根据正在开发的应用的前后关系，反映组织的策略。

    每个组织，每个团队，每个应用，都是独一无二的，因此，你需要问你自己下述问题，在软件周期的哪一点上，你想检查一个组件的属性？

*   开发人员每一次下载新的组件的时候
    
*   开发团队构建的时候
    
*   产品发布前测试
    
*   应用准备什么时候上线？
    

哪一个最好？

    答案，当然是所有这些都很重要，因为现代软件开发世界，不是一招鲜吃遍天。事实上，每个情况都是不同的，因此，拥有组件情报工具，足够灵活的对DevOps工具链的每个阶段，增加价值非常重要，包括开发人员IDE，构建系统，软件仓库管理，CI/CD工具，镜像生成者，交付编排者，产品运行时环境。

    当应用部署后，保证应用的安全也没有结束，软件安全没有一劳永逸。开源软件中新攻击方式的发现，新漏洞的爆发，能马上改变应用的安全概况，那也就意味保存一份软件组成清单，监控生态系统的新信息，新安全弱点的发现，是非常重要紧迫的。

总结

    当需要使用开源组件生产现代软件，底线是—完整的、精确的情报很关键。缺少可见性和精确的工具，无法随着现代软件开发的需要而扩展。不精确的/不完整的数据会给组织留下漏洞，许可证，其他质量问题，直接导致更高的费用，减少创新。

    Sonatype Nexus 情报和高级二进制指纹技术，提供了一个独一无二的方案，帮助组织：

*   加强创新通过使团队具备精确识别和最高质量识别开源组件的能力
    
*   快速扩展在组件情报足够精确的保证下，在软件开发周期每个阶段实现自动化
    
*   控制组件使用  灵活的策略，跨不同的团队，语言，应用概况，推动细粒度的决策支持，
    

    在您这一侧，有了精确识别，就有了发现软件供应链错误的力量，可以确信，这意味着会消除影响创新的风险和低效率。这也意味着释放天才程序员的全部潜力，你能在全球的赛场上，更快的创新，更有效的竞争。
