# 第六章、结论：建立安全的 DevOps 能力和文化

**“**本文为 《DevOpsSec》一书的第六章翻译，介绍如何建立安全的DevOps 能力和文化**”**

  

  

DevOps（文化、流程框架和工作流，对自动化和反馈的重视）都可以用来改善安全性。

 

可以向此领域的领导者如 Etsy、Netflix、Amazon 和 Google 等学习成功经验。还有伦敦多资产交易所、Capital One、Intuit、E\*Trade 或美国国土安全部。名单在不断增加中。

 

这些组织都找到了平衡安全性、合规性与交付速度，并在其平台和管道中建立保护措施的方法。

 

他们通过使用“持续交付”作为管控基础设施来保护软件交付和执行合规性策略来做到这一点，那么你也可以做到这一点；通过基础设施即代码来保护运行时；在DevOps 中将安全性作为反馈循环和改进周期的一部分；以 DevOps 文化和价值观为基础，并扩展这一点拥抱安全。

 

选择一个地方开始吧。从解决一个重要问题或一个重要风险开始。或者从简单的事情开始，你可以快速取得成功并建立动力。

 

实施软件组件分析以自动为系统创建构建清单很容易。这样，你就可以在 SDLC 的早期识别和解决第三方组件中的风险，而不会直接影响开发工作流程或减慢交付速度。

 

确保持续交付管道本身的安全是另一个重要而直接的动作，你可以在不减慢交付速度的情况下开展这个举措。你和你的企业可以通过自动化变更的完整性来确保以可靠、可重复和可审核的方式进行变更。这样做还将帮助你更好地了解工程流程和工具链，以便准备采取进一步的措施。

 

你可以从头开始，通过确保对每个新应用或服务进行风险评估，分析工程团队要使用的语言和框架的安全保护措施（和风险）。你可以加固 Chef recipes 或 Puppet manifests 来保护基础设施。或者，你可以从最后开始，通过添加运行时检查（例如 Netflix 的 Monkey）来发现生产中危险的配置或部署错误。

 

关键是要开始去做，做一些小的有意义的改变。评价结果并持续迭代。利用开发人员和操作人员所使用的相同工具和工作流程。将脚本和工具融入版本控制。使用Docker 打包安全测试和取证工具。使用持续交付管道来部署它们。与开发人员和运维部门合作，识别并解决风险。使用 DevOps 保护 DevOps。

 

寻找帮助团队以安全的方式将风险降至最低，并确保合规性，同时将摩擦和成本降至最低交付的方法。不要妨碍反馈循环，相反使用它们进行度量、学习和改进。

 

与开发人员和运维人员合作，了解他们的工作方式，使用相同的工具，共同解决问题，将开发人员和运维人员与安全结合在一起。

 

在我的组织中，迁移到 DevOps 和 DevOpsSec 的工作一直并将持续进行下去。我们从在框架中构建安全保护开始，与安全顾问一起审查体系结构并培训开发团队。我们实现了持续集成，建立了我们的自动化测试套件，并融入了静态分析测试。

 

我们已经建立了强大的代码评审文化，并将增量威胁建模作为变更控制的一部分。定期进行渗透测试可作为学习如何以及在何处需要改进安全流程以及设计和编码的机会。我们的系统工程团队使用与开发人员相同的工程实践通过代码管理基础设施：版本控制、代码评审、静态分析和持续集成中的自动化测试。随着我们缩短交付周期，转向持续交付，我们继续简化和自动化更多的步骤和检查，以便可以更频繁地执行它们并创建更多的反馈循环。现在，安全性和合规性只是我们构建、交付和运行系统的另一部分，也是每个人工作的一部分。

 

DevOps 从根本上改变了当今开发和运维的方式。这也将改变安全性的实现方式。它需要新技能、新工具和新的优先级。这将需要时间和新的视角。所以越早开始越好。
