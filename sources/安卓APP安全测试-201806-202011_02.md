# 第五章、合规即代码

**“**本文为 《DevOpsSec》一书的第五章翻译，介绍 DevOps 中合规性的嵌入与检测。**”**

  

可以遵循 DevOps 来实现 Justin Arbuckle 在 Chef 上所说的 “合规即代码”（Compliance as Code）：将合规性纳入开发和运维中，并将合规性策略、检查与审计纳入持续交付中，从而使合规性成为 DevOps 团队每天工作的一部分。  

***Chef Compliance***

 

Chef Compliance 是 Chef 的一个工具，可扫描基础设施并报告合规性问题、安全风险和老旧软件。它提供了一种集中管理的方式，可以连续自动地检查和执行安全性和合规性策略。

 

使用 InSpec（用于指定合规性、安全性和策略要求的开源测试框架），在代码中定义合规性配置文件以验证系统是否正确配置。

 

你可以使用 InSpec 编写高级的、文档化的测试/断言，以检查如密码复杂性规则、数据库配置、是否已安装软件包等内容。Chef Compliance 附带了一套针对Linux 和 Windows 环境以及如 Apache、MySQL 和 Postgres 之类的通用软件包的预定义配置文件。

 

当检测到差异时，会将它们报告到中央仪表板，并可以使用 Chef 自动修正。

  

“ DevOps Audit Defense Toolkit” 中描述了一种实现代码合规的方法，该工具包是由 James DeLuccia，IV，Jeff Gallimore，Gene Kim 和 Byron Miller 编写的免费的社区构建的流程框架。该工具包以真实案例为基础，这些案例基于我们刚刚提到的 “ Security as Code” 实践和严格的持续交付，说明了如何在受监管的环境中成功遵循 DevOps。它以案例研究的形式编写，描述了虚构组织的合规性，列出了常见的操作风险和控制策略，并展示了如何自动化所需的控制。

  

  

01

—

  

预先定义策略

  

合规性将管理、合规、内部审核、PMO 和信息安全以及开发、运维拉到了一起。合规策略、规则以及控制工作流程需要所有这些利益相关者共同努力预先定义。管理层需要了解如何通过管道（pipeline）控制运维操作风险和其他风险。对这些政策、规则或工作流程的任何更改都须正式批准和记录，例如在变更顾问委员会（CAB）会议上。

 

但是，策略和规则不应依靠 checklist、过程和会议，而是通过自动控制来强制执行（和跟踪），这些自动控制应被植入到配置管理工具和持续交付管道（pipeline）中。每次变更都与版本控制和 Jira 之类的票务系统（ticketing system）联系在一起，来实现可追溯性和可审核性：所有更改都必须在票证（ticket）下进行，并且票证（ticket）会自动从初始工作请求一直到部署沿着管道（pipeline）进行更新。

  

  

02

—

  

自动门禁和检查

  

第一次审查大部分是手动的。对代码和配置的每次更改提交前都必须进行评审。这有助于发现错误，并确保至少一个其他人检查正确性之后才进行变更。高风险代码（由团队、管理人员、合规和安全定义）也必须经过 SME（安全管理评估） 审查；例如，安全敏感代码必须由安全专家审查。管理层会进行定期检查，以确保审核工作的一致性和责任感，并避免出现“橡皮图章”现象。所有审查的结果都记录在票证中。任何未立即解决的后续行动都将作为另一张工单添加到团队的待办事项列表中。

 

除了手动审查之外，还执行自动静态分析检查，以捕获常见的安全错误和编码错误（在 IDE 中以及在持续集成/持续交付管道中）。发现的任何严重问题将使构建失败。

 

检入后，所有代码都通过自动化测试管道运行。Audit Defense Toolkit 假定团队遵循测试驱动开发（TDD），并列出了应执行的一组示例测试。

 

使用自动化的配置管理工具（如 Puppet 或 Chef）来完成基础设施变更，并遵循以下管控规则：

*   代码变更提交前进行评审
    
*   高风险的变更（由团队定义）必须由 SME 进行第二次审核
    
*   静态分析/lint 检查在管道中自动完成
    
*   使用如 rspec-puppet、Chef Test Kitchen 或 ServerSpec 的测试框架执行自动测试
    
*   通过自动冒烟测试和集成测试后分阶段将变更部署到测试和预发布环境
    

 

同样，每个变更都应通过一个记录单进行跟踪和记录。

  
  

03

—

  

持续交付中的变更管理

  

由于 DevOps 意味着更多是小的变更，因此 “Audit Defense Toolkit” 假定大多数更改都可以视为标准或常规更改，这些更改本质上是由管理层预先批准的，因此不需要 CAB 批准。

 

DevOps 还假设更大的变更将是“灰度的”。换句话说，将对它们进行小的、安全的增量更改，并在默认情况下通过将运行时功能开关关闭来进行保护。只有在开发、运维、合规和其他利益相关者之间进行协调同意时，才能发布该功能。

 

生产中发现的任何问题都会做复盘，然后将测试添加到管道中以发现问题（遵循TDD 原则）。

  
  

04

—

  

DevOps 审核工具包中的职责分离

  

在 DevOps 审核工具包中，许多管控规则强制或支持职责分离：

 

*   强制性的独立同行评审，确保任何工程师（开发人员或操作人员）都无法在其他人不知情或未批准的情况下进行变更。为防止串通，会在可能的情况下随机分配评审人员。
    
*   为开发人员授予对生产系统的只读访问权限，以协助进行故障排除。任何修复都需要通过持续交付管道（向前修复）或通过自动回滚变更（再次通过持续交付管道/自动部署过程）来进行，这些变更是完全可审计和可追溯的。
    
*   通过管道进行的所有变更都是透明的，并发布到仪表板，IRC 等。
    
*   生产访问日志由 IT 运维管理每周审核一次。
    
*   定期检查访问凭据。
    
*   使用自动检测变更控制工具（例如 Tripwire、OSSEC、UpGuard）检查未经授权的变更。
    

 

这些管控规则最大程度地降低了开发人员能够对产品进行未经授权、未被发现的变更的风险。

  
  

05

—

  

使用 Audit Defense Toolkit

  

DevOps Audit Defense Toolkit 提供了一个路线图，说明如何利用 DevOps 工作流和自动化工具，以及我们已经研究过的一些安全控制和检查，来支持你的合规和治理要求。

 

它需要较高的纪律性和成熟度，对于某些组织而言（至少一开始来说）要求太高了。你应该检查控制措施并决定从哪里开始。

 

尽管持续部署中假设将变更直接部署到生产环境中，但是在将变更推送到生产环境之前，你可以通过在持续部署中添加一个手动检查门禁来轻松地适配以上的想法和实践。

  

  

06

—

  

用代码代替文书工作

  

“合规即代码”（Compliance as Code）尝试尽量减少文书工作和开销。但你仍然需要明确记录变更如何批准和管理的策略，以及无法自动化的过程清单。虽然大多数过程和门禁都是通过持续集成/持续交付管道中的自动化规则来实施的，依靠自动化管道和工具并利用自动创建的详细审计跟踪记录，来确保所有步骤都得到一致遵循。

 

就像频繁执行构建和部署可以降低操作风险一样，遵循相同的标准化流程和自动化步骤，对每项更改执行合规性要求也可以降低违反合规性的风险。你和你的审计人员可以确信，所有更改都是以相同的方式进行的，所有代码都通过相同的测试和检查，并且所有内容的跟踪方式都相同：一致、完整、可重复和可审计。

 

标准化是审计人员乐于见到的。当然开展审计也是审计人员乐于见到的。“合规即代码”（Compliance as Code）为每个变更提供了一个精美的审计线索：从何时提出变更，为何提出变更，谁进行了变更，此人进行了哪些变更，谁审核了变更以及在审核中发现了什么，何时做了哪些测试，直到何时进行了部署。除了为每一个更改设置一个记录单并用一个票证号标记更改之外，合规对于执行该工作的人员来说是自动且无缝的。

 

就像情人眼里出西施一样，审计人员也是如此看待合规的。审计人员起初可能不理解或不同意这种方法。你需要逐步指导他们，并证明管控是有效的。但正如《持续交付》的原作者之一戴夫·法利（Dave Farley）所解释的那样，这应该不会太困难：

 

我曾有在多家金融公司迁移到持续交付的经验。监管者通常起初会比较谨慎，因为持续交付超出了他们的经验，但是一旦他们理解了，他们就会异常热情。因此，监管并不是真正的障碍，如果先让一个理解持续交付的理论和实践的人对他们进行解释会更有帮助。

 

如果你看看部署管道的实现（持续交付中的核心思想），那么很难想象如果没有很好的可追溯性，如何实现这样的东西。只需很少的工作，部署管道就可以提供完善的审计跟踪机制。部署管道是生产的途径。这是一个自动发布所有变更的渠道。这意味着我们可以自动执行合规性要求-“如果测试失败，则不能发布”，“如果未测试交易算法，则不能发布”，“未经授权人员批准，则不能发布”，等等 。此外，你可以建立审计每个步骤以及任何变化的机制。一旦监管者看到了这一点，他们很少希望回到纸质流程的糟糕过去。
