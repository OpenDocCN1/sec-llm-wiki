“安全即代码”旨在将安全性纳入 DevOps 工具和实践中，使其成为工具链和工作流程的重要组成部分。你可以通过映射代码和基础架构的更改，并在不引入不必要的成本或延迟的情况下找到添加安全检查、测试和门禁的位置来实现这一点。


“安全即代码”使用“持续交付”作为控制主干和自动化引擎，以实现安全性和合规性。首先，我们简要定义“持续交付”，然后逐步介绍如何在“持续交付”中建立安全性。

持续交付


敏捷开发的思想和原则（通过文档、频繁的交付、面对面的协作、专注于技术卓越和自动化来交付软件）构成了DevOps的基础。而且，持续交付（即 DevOps 的控制框架）也建立在基本的敏捷开发实践“持续集成”之上。

 

在持续集成中，每次开发人员更改代码时，系统都会自动构建和测试，从而对代码库的运行状况提供快速和频繁的反馈。持续交付会在此基础上进行下一步工作。

 

持续交付不仅仅是开发团队已经有的自动化构建和单元测试。持续交付是指自动提供和配置测试环境以尽可能模仿生产环境。这包括打包代码并将其部署到测试环境；自动进行运行验收、压力和性能测试，以及安全测试和其他检查，并反馈“通过/失败”结果；审核所有这些步骤并将状态传递给仪表盘。之后，你将使用同一管道（pipeline）将变更部署到生产中。

 

持续交付是 DevOps 的支柱和驱动它的引擎。它提供了一个自动化框架，用于进行软件和基础架构变更，以可重复、可预测、高效且经过全面审核的方式发布升级、补丁和对配置的更改。

 

将持续交付管道（pipeline）整合到一起需要开发人员和运维部门之间高度的合作，并且需要对系统的工作原理、生产的真实情况以及运行方式有更多的共识。它迫使团队间开始互相交谈，暴露和探索他们现在的工作方式以及想要的工作方式的细节。

 

有许多工作需要完成：理解依赖关系、标准化配置以及将配置引入代码中。清理构建（消除不一致、硬编码和关联操作）；将所有内容纳入版本控制中，包括应用程序代码和配置、二进制依赖、基础设施配置（recipes, manifests, playbooks, CloudFormation 模板, and Dockerfiles）、数据库结构以及持续集成/持续交付管道（pipeline）本身的配置；最后，自动化测试（将部署所需的所有步骤都放在一起并进行仔细的自动化编排）。你可能需要在异构环境中（使用不同的架构、技术平台和语言）来完成所有这些工作。

伦敦多资产交易所的持续交付


伦敦多资产交易所（LMAX）是英国受到严格监管的外汇零售市场，戴夫·法利（Dave Farley）（《持续交付》一书的合著者）在这里开拓了持续交付模式。

 

LMAX 的系统是按照敏捷最佳实践从头开始构建的：TDD（测试驱动开发）、结对编程和持续集成。但是他们更进一步，自动将代码部署到集成、验收和性能测试环境中，从而建立了持续交付管道（pipeline）。

 

LMAX 在自动化测试上进行了大量投入。每个构建运行 25000 个单元测试，其中包含代码覆盖率、简单代码分析（使用 Findbugs、PMD 和依赖性检查之类的工具）以及自动集成完整性检查。对于提交的每一段代码，都必须通过所有这些测试和检查。

 

最新一个成功的构建会被自动选取并进行集成和验收测试，在此过程中，在一个测试集群上运行了 10,000 多个端到端测试，包括 API 级别的验收测试，多个级别的性能测试以及故障注入测试。故障注入测试会选择性地使系统的某些部分发生故障，并验证系统是否可以不丢失数据并正确恢复。不到 1 小时的并行测试可以达到超过 24 小时的常规测试效果。

 

如果所有测试和审查均通过的话，则对构建进行标记。所有构建以及相关的二进制文件（例如Java Runtime）都保存在安全的存储仓库中。代码和测试都通过版本控制进行跟踪。

 

质量检查人员（QA）可以进行手工测试或其他类型的测试。然后，运维人员可以将标记的构建从开发存储仓库中提取到其单独的安全生产存储仓库中，并使用统一的自动化工具来部署到生产中。固定在每两周的周六，并且不在交易时间进行生产发布。

 

这是持续交付，而不是 Amazon 或 Etsy 遵循的持续部署。即使在 DevOps 工具可用之前，LMAX 只使用脚本和简单的工作流程约定自研了许多工具，但它仍然充分利用了与持续部署相同类型的自动化和控制的优势。

将安全性融入持续交付中


在开始添加安全检查和控制之前，你需要了解工程团队正在使用的工作流程和工具：

  • 变更前和变更时会发生什么？

  • 存储仓库在哪里？谁可以访问它们？

  • 变更如何从签入到构建到持续集成和单元测试、功能和集成测试，再到预发布最终到生产过渡？

  • 运行哪些测试？结果记录在哪里？

  • 使用了哪些工具？它们如何工作？

  • 什么时候进行什么人工检查或评审？

 

以及如何利用所有这些来实现安全性和合规性？

 

让我们规划一下从签入到生产的变更所涉及的步骤，并确定在哪里可以插入安全检查和控制。请参见图4-1的模型，该模型解释了如何以及在何处向持续交付工作流程中添加安全检查。


图4.1 工程工作流中的安全检查和控制

Commit前

 

以下是在将软件或配置更改提交到源代码仓库之前的步骤。要在这里添加额外的安全检查和控制，包括：

  • 轻量级、迭代的威胁建模和风险评估

  • 工程师的IDE中的静态分析（SAST）检查

  • 同行代码评审（针对防御性编码和安全漏洞）

 

提交阶段（持续集成）

 

这是由签入自动触发的。在此阶段，你将构建并执行系统的基本自动化测试。这些步骤将快速地反馈结果给开发人员：此更改是否“破坏了构建”？此阶段最多需要几分钟。以下是此阶段应包含的安全检查：

  • 编译和构建检查，确保这些步骤是干净的，并且没有错误或警告

  • 构建中的软件组件分析，确定第三方风险组件

  • 增量静态分析，扫描bug和安全漏洞

  • 告警通过静态分析或测试发现的高风险代码变更

  • 安全功能的自动单元测试，并做代码覆盖率分析

  • 对二进制制品进行数字签名并将其存储到安全仓库中

 

验收阶段

 

此阶段由成功提交触发。拉取最新的良好（通过之前检查的）构建并将其部署到验收测试环境。执行自动验收（功能、集成、性能和安全性）测试。为了最大程度地减少所需的时间，这些测试通常被分发到不同的测试服务器并行执行。遵循“快速失败”（fail fast）方法，将更昂贵、更耗时的测试保留到测试周期中尽可能晚的时间，以便仅在其他测试已经通过的情况下才执行它们。

 

此阶段的安全控制和测试包括以下内容：

 

  • 安全、自动化的配置管理，并将配置推送到生产环境（使用诸如Ansible，Chef，Puppet，Salt和/或Docker之类的工具）。确保测试环境是干净的，并配置为与生产尽可能接近。

  • 从二进制制品库中自动部署最新的合格构建。

  • 冒烟测试（包括安全测试），旨在捕获配置或部署中的错误。

  • 动态扫描（DAST）。

  • 安全特性的自动功能和集成测试。

  • 使用 Gauntlt 或其他安全工具进行自动安全攻击。

  • 深度静态分析扫描（可以异步完成）。

  • 模糊测试（API，文件）。这可以异步完成。

  • 渗透测试（异步）。

 

生产部署和部署之后

 

如果上述所有步骤和测试都通过，则可以将变更部署到生产中，流程为等待手动审查/批准、计划（在持续交付中）、自动部署（在持续部署中）。生产部署和部署后需要其他安全检查和控制措施：

  • 安全、自动化的配置管理和运行时环境的配置

  • 自动化的部署和发布编排（需要授权，可重复和可审核）

  • 部署后的冒烟测试

  • 自动化的运行时断言和合格性检查（Monkey）

  • 生产监控/反馈

  • 运行时防御

  • 红队

  • 漏洞赏金计划

  • 问题复盘（从失败中学习）


根据组织和系统的风险状况，你需要至少实施其中一些实践和控制措施。这个领域的领导者已经完成了大多数工作。

 

现在，让我们从设计开始更仔细地研究这些安全管控和实践以及可以使用的一些工具。

DevOps 中的安全设计


DevOps 中的安全设计首先要建立在安全库和框架之上，预先建立安全性，并对开发人员透明。安全风险评估还需要集成到设计阶段，尤其是设计和软件供应链有变更的时候。因为团队使用的开源、三方组件或者框架对系统来说很重要。

 

风险评估和轻量级威胁建模

 

我们已经讨论过在快节奏的 DevOps 环境中设计的基本问题。这些团队希望尽早并经常地交付给真正的用户，以便他们能够根据产品反馈改进特性集和设计。这意味着设计在一开始就必须是轻量级的，并且它会根据反馈不断变化。

 

在持续部署中，没有像瀑布式开发中的设计规范提交给编码人员，可能根本没有任何设计规范可以作为风险评估的一部分进行审查。当需要做的设计工作很少，并且“代码即设计”时，你在哪里以及如何在设计中发现安全问题？

 

首先你要明白，即使设计只是粗略的并且可能会发生变化的，团队仍然需要使用一系列工具和执行一系列动作。这就是威胁建模（从攻击者的角度审视设计，寻找安全控制和防御方面的漏洞或弱点）需要开始的时机。

 

例如，在 PayPal，每个团队都必须经过初步的风险评估，在开始开发新的应用程序或微服务时填写一份自动的风险问卷。关键决策点之一是团队是否使用已经过审查的现有语言和框架。或者，他们是否在引入一些安全团队从未见过的新技术？在经过批准的平台上构建“只是另一个 Web 或移动应用程序”与使用新语言和工具进行技术实验之间，风险存在很大差异。

  

以下是在前期风险评估中需要了解和评估的一些问题：

 

  • 你了解如何安全地使用语言和框架吗？框架中提供了哪些安全保护？需要添加什么使开发者在默认情况下可以轻松“做正确的事情”？

  • 针对语言和框架是否有良好的持续交付工具链支持，包括 SAST 检查或 IAST工具，以及依赖关系管理分析能力用来捕捉第三方和开源库中的漏洞？

  • 是否使用敏感和机密数据？需要哪些数据，如何处理，哪些需要审核？是否需要存储，如果需要，如何存储？是否需要考虑加密、标记化、打码、访问控制和审核？

  • 是否了解此应用程序/服务与其他应用程序/服务之间的信任边界：在哪里需要对身份验证、访问控制和数据质量进行控制？设计中做了什么假设？

 

在微服务环境中，这些问题尤其重要，在微服务环境中，团队需要灵活地使用正确的工具来完成工作：当不总是容易理解调用链依赖关系时，当无法控制调用你的人和调用者对你的服务的期望时，以及你无法控制下游服务做什么、何时或如何改变时。对于微服务，您需要了解以下内容：

 

  • 你对调用者有什么假设？身份验证和授权在哪里以及如何完成？你如何确定？

  • 是否可以信任从其他服务获得的数据？其他服务可以信任你提供给他们的数据吗？

  • 如果下游服务失败，超时或返回不完整或不一致的结果会怎样？

 

在进行前期评估之后，对于大多数更改而言，威胁建模应该变得更加简单，因为大多数更改将是小的、增量的，因此风险较低。你可以通过让团队在进行更改时向自己提出一些问题来经济、非正式和迭代式地评估风险：

  • 是否更改相关工具或流程？是否引入或切换到新语言，是否更改后端存储，是否升级或替换应用程序框架？由于设计是快速迭代的，因此团队可能会发现他们最初的架构方法不适用，并且他们可能需要切换全部或部分技术平台。这可能需要从头重新评估风险。

  • 你如何影响系统的攻击面？你是在添加新字段或者表单？你要开放新的端口或新的API，添加新的数据存储，还是调用新服务？

  • 你是否要更改身份验证逻辑或访问控制规则或其他安全性？

  • 你是否添加敏感或机密的数据元素？你是否更改与机密，敏感或机密数据有关的代码？

 

回答这些问题你就会知道何时需要更仔细地研究设计或技术，或者何时应检查和验证信任假设。DevOps 中威胁建模的关键在于认识到，由于设计、编码和部署是在紧密的迭代循环中连续进行的，因此你在评估技术风险时会陷入相同的循环中。这意味着可以并且需要使威胁建模高效、简单、实用和快速。


保护软件供应链


安全前置的另一个重要部分是保护软件供应链，从而最大程度地减少构建系统所用软件的安全风险。当今的敏捷和 DevOps 团队充分利用开源库来减少开发时间和成本。这意味着他们还从其他人的代码中继承了质量问题和安全漏洞。

 

据运行中央存储库（世界上最大的开源软件存储库）的 Sonatype 称，当今应用程序中 80% 的代码来自库和框架，其中许多代码存在严重问题。2014年，Sonatype 调查了来自 106000 个不同组织的 170 亿次下载请求。结果如下：

 

大型软件和金融服务公司平均使用 7600 个“供应商”。这些公司在 2014年 平均使用了 240,000 个软件“零件”，其中 15,000 个包含已知漏洞。

 

中央存储库中超过 50000 个软件组件存在已知的安全漏洞。每 16 个下载请求中就有一个是至少有一个已知安全漏洞的软件。平均每天都会报告 50 个开源软件中的新的严重漏洞。

 

害怕了吗？你应该害怕。你需要知道应用程序中包含哪些开源代码以及何时进行更改，并检查这些代码是否存在已知的安全漏洞。幸运的是，你可以使用 OWASP 的 Dependency Check 项目之类的软件组件分析（SCA）工具或 Sonatype 的Nexus Lifecycle 或 SourceClear 等商业工具来自动执行此操作。你可以将这些工具嵌入到构建或“持续集成/持续交付”工作流中，以自动清点开源依赖关系，识别过期的库以及具有已知安全漏洞的库，如果发现严重问题，则自动使构建失败。通过为每个系统建立物料清单，你可以为诸如 Heartbleed 或 DROWN 之类的漏洞做好准备-快速确认是否存在漏洞以及需要修复的内容。

 

这些工具还可以在检测到新的依赖项时提醒你，以便创建工作流程来对其进行审查。

 

OWASP 依赖项检查

 

OWASP 的 Dependency Check 是一种开源扫描程序，可对应用程序中使用的开源组件进行分类。它适用于Java、.NET、Ruby（gemspec）、PHP（composer）、Node.js 和 Python，以及某些 C / C ++项目。Dependency Check 可以与常见的构建工具（包括 Ant、Maven 和 Gradle）和 Jenkins 等 CI服务器集成在一起。

 

Dependency Check 会报告 NIST 的国家漏洞数据库中报告的任何已知漏洞的组件，并从 NVD 数据源获取更新。

 

其他流行的开源依赖项检查工具包括：

•Ruby 的 Bundler Audit

•Javascript 的 Retire.js

•NuGet 库的 SafeNuGet

 

如果在生产中（甚至在开发和测试中）使用像 Docker 这样的容器，则应对容器映像中的依赖项实施类似的控制。虽然 Docker 的 Project Nautilus 会扫描官方仓库中的镜像来查找具有已知漏洞的软件包，你仍应确保使用 OpenSCAP 或 Clair 之类的工具或 Twistlock、FlawCheck 或 Black Duck Hub 的商业服务来扫描所有 Docker 容器。

 

你的战略目标应该是随着时间的推移转向“更少、更好的供应商”，简化供应链，以降低维护成本和安全风险。Sonatype 开发了一个免费的计算器，帮助开发人员和管理人员了解使用过多的第三方组件会随着时间的推移而带来的成本和风险。

 

但你需要认识到，即使从长远来看很有意义，要让不同的工程团队标准化使用一组通用组件也不是一件容易的事，尤其是对于微服务环境而言，在这种环境中，开发人员可以自由使用合适的工具，根据他们的特定要求甚至他们的个人兴趣选择技术。

 

可以先在最低层（内核、操作系统和VM）以及通用实用程序功能（例如日志记录和指标收集）上进行标准化，这些功能需要在应用程序和服务之间一致使用。

在持续交付中编写安全代码


DevOps 实践强调了编写良好代码的重要性：有效且易于更改的代码。安全计划可以利用此特点，利用代码审查并添加自动静态分析工具以尽早发现常见的编码错误和安全漏洞。

 

使用代码评审来提高安全性

 

在许多敏捷和 DevOps 实践中，同行代码评审是一种常见的工程实践，在诸如Google、Amazon、Facebook 和 Etsy 这样的头部组织中，同行代码评审是必需的。

 

同行代码评审通常是为了在整个团队中共享信息，帮助确保代码是可维护的，加强约定和标准，并确保框架和模式得到正确和一致的遵循。这使得代码更容易理解和更安全地更改，而且在这个过程中，评审人员经常会发现需要修复的 bug。

 

你还可以使用代码评审以某些重要方式提高安全性。

 

首先，代码评审增加了开发人员的责任感，并保证了变更的透明性。强制性审核可确保在至少一个其他人知道所做的事情和原因的情况下才能发布变更。这大大降低了内部威胁的风险：例如，有人试图在代码中引入逻辑炸弹或后门。知道将要审查其代码也鼓励开发人员在工作中更加谨慎，从而提高了代码质量。

 

可以使用代码评审工具来确保代码评审的透明度，如：

  • Gerrit

  • Phabricator

  • Atlassian Crucible

 

框架和其他高风险代码，包括安全功能（身份验证、访问控制、输出编码、加密）和处理金钱或敏感数据的代码，需要对逻辑进行认真详细的审查。代码必须正确运行，包括在错误情况和边界情况下。

 

鼓励开发人员仔细研究错误和异常处理以及其他防御性编码实践，包括仔细的参数验证，这将大大改善大多数代码的安全性并提高系统的运行时可靠性。

 

只需一点培训，开发人员就可以学习如何发现诸如硬编码凭证或创建自定义加密算法之类的不良实践。通过更多的培训，他们将能够在早期发现更多的漏洞。

 

在某些情况下（例如，会话管理、机密处理或加密），可能需要请安全专家来检查代码。可以鼓励开发人员主动要求对代码进行安全审查。还可以通过简单的静态代码扫描来识别高风险代码，查找特定字符串（例如凭据）和危险函数（例如加密函数和加密原语）。

 

为了识别高风险代码，Netflix 绘制了微服务的调用序列。由许多其他服务调用的或散布到许多其他服务的任何服务都会自动标记为高风险。在 Etsy，一旦通过审查或扫描识别出高风险代码，他们就会对其进行哈希处理，并创建一个单元测试，在代码哈希值发生更改时自动向安全团队发出警报。

 

代码评审实践还需要扩展到基础设施代码，扩展到 Puppet manifests 、Chef cookbooks、 Ansible playbooks、 Dockerfiles和 CloudFormation templates。


结对编程

 

结对编程，即开发人员一起编写代码，一个开发人员“驾驶”键盘，另一个开发人员充当导航，帮助引导方向和寻找未来的麻烦，这是一种让新团队成员跟上速度的好方法，而且它被证明能产生更好、更紧凑、更可测试的代码。但是结对会错过重要的错误，包括安全漏洞，因为结对编程更多的是联合解决问题，找到解决方案，而不是主动寻找错误或 bug。

 

即使在规范的 XP（极限编程）环境中，也应该对高风险代码进行单独的安全性代码审查。

 

SAST：在IDE、持续集成/持续交付中

 

另一种提高代码安全性的方法是使用自动静态分析软件测试（SAST）工具扫描代码中的安全漏洞。这些工具可以发现评审者有时会遗漏的细微错误，并且通过其他类型的测试可能很难发现这些错误。

 

但是，像 Twitter 和 Netflix 这样的实施 DevOps 的组织不依赖于由安全团队运行的集中式安全扫描，而是为开发人员提供自助式安全扫描，将 SAST 扫描直接预置到工作流的不同位置。

 

开发人员在编码时可以使用 IDE 中的内置检查器，如 FindBugs 或 Find Security Bug 之类的插件，或 Coverity、Klocwork、HPE Fortify、Checkmarx 或 Cigital的 SecureAssist 的商业插件来捕获安全问题和常见的编码错误。

 

还可以将预提交和提交的增量静态检查集成到到 CI 中，以快速捕获增量代码中的常见错误和异常模式。但仍需要对代码进行全量扫描，以发现某些增量扫描无法找到的过程间问题。需要在带外进行全量扫描，而在大型代码仓库上全量扫描可能会运行几个小时甚至几天的时间。但是结果仍然可以自动通过备忘录、电子邮件或其他通知机制反馈给开发人员。

 

不同种类的静态代码扫描工具提供不同的价值：

  • 用于检查代码一致性，可维护性和清晰度的工具（用于 Java 的 PMD 和Checkstyle，用于 Ruby 的 Ruby-lint）可帮助开发人员编写易于理解，易于更改，易于查看和安全变更的代码。

  • 寻找常见编码错误和错误模式的工具（如 FindBugs 和 RuboCop 之类的工具）将捕捉可能导致运行时失败或安全漏洞的细微逻辑错误。

  • 通过污点分析、控制流和数据流分析、模式分析和其他技术（Find Security Bugs、Brakeman）来识别安全漏洞的工具可以发现许多常见的安全问题，例如使用加密功能时的错误、配置错误和潜在的注入漏洞。

 

你不应该仅依赖一种工具，即使最好的工具也只能捕获代码中的某些问题。好的做法是，至少运行每种类型中的一种，以查找代码中的不同问题，作为整体代码质量和安全性计划的一部分。

 

如今，已经有经过验证的 SAST 工具可用于流行语言（如Java、C/C ++ 和 C＃）以及常见框架（如 Struts 、 Spring 和 .NET），甚至适用于某些较新的语言和框架（如Ruby on Rails）。但是，很难找到对其他新语言（例如 Golang）的工具支持，而对于动态脚本语言则尤其困难。对于这些语言，大多数静态分析器（尤其是开源工具）仍然仅限于 lint 规则和基本的不良做法检查，这虽然有助于编写更好的代码，但不足以确保代码安全性。

 

用于配置管理语言的静态分析检查工具（如用于 Chef 的 Foodcritic 或用于puppet 的 puppet lint）也仅限于对良好编码实践和一些常见语义错误的基本检查。它们有助于确保代码正常工作，但不会在系统配置中发现严重的安全问题。

 

SonarQube

 

SonarQube 为多种语言封装了多个 SAST 扫描工具。它最初只包含开源工具，现在包含了由 SonarSource 编写的专有 checker。这些 checker 中的一些，如Objtovi-C 和 Swift、C/C++和其他旧版语言，只能在商业版本中使用。但是对于Java、JavaScript、PHP 和其他语言（比如 Erlang），SonarQube 的开源版本有很好的支持。

 

SonarQube 的主要目的之一是评估和跟踪应用中的技术债务。这意味着大多数代码检查程序都关注于可维护性（样式和编码约定），以及编码正确性和常见的 bug模式。但是，SonarSource 最近开始包含更多安全性 checker，尤其是针对Java。

 

SonarQube 可以运行在持续集成/持续交付中，并带有针对 Jenkins 和 GitHub 的插件。你可以设置质量门禁，并在质量门禁失败时自动通知团队。它收集指标，并提供报告和仪表板，以便随着时间的推移分析这些指标，确定 bug 聚集在哪里，并可以进行跨项目比较。

 

为了确保反馈循环是有效的，重要的是调整这些工具以最小化误报，并为开发人员提供关于需要修复的实际问题的清晰、可操作的反馈。产生大量误报、需要审查和分类的嘈杂 checker 仍然可以定期运行，结果选择性地反馈给开发部门。

持续交付中的安全测试


敏捷开发的思想和原则（通过文档、频繁的交付、面对面的协作和专注于技术卓越和自动化来交付软件）构成了 DevOps 的基础。而且，持续交付（即 DevOps 的控制框架）也建立在基本的敏捷开发实践“持续集成”之上。

安全测试需要集成到持续集成和持续交付中，以便在进行更改后立即验证安全性。这意味着将应用程序扫描和模糊测试集成到持续交付流程中。这也可能意味着利用开发团队已经完成的自动化测试套件，将安全检查添加到单元测试中，并在集成和功能测试中自动执行安全攻击。

 

你需要在持续交付之外进行渗透测试和漏洞赏金计划，它们会为自动测试程序提供有价值的反馈。你需要在漏洞管理中跟踪扫描和测试中发现的所有漏洞，无论是管道（pipeline）内部的还是外部的。

 

动态扫描（DAST）

 

黑盒动态安全性测试（DAST）工具和服务可用于测试 Web 和移动应用程序，但在持续集成或持续交付中并不总是能很好地发挥作用。大多数 DAST 工具都是为安全分析人员或渗透测试人员设计的，而不是为像 Jenkins 或 Bamboo 这样的持续集成引擎设计的。

 

你可以使用如 OWASP ZAP 之类的工具来自动扫描 Web 应用程序中的常见漏洞，作为持续集成/持续交付工作流的一部分。你可以通过命令行在无头模式下运行扫描器，也可以通过扫描器的 API 或使用某种封装程序，例如 ZAProxy Jenkins 插件或更高级别的测试框架（如 BDD-Security）来运行（我们将在下一节中介绍）。

 

关于如何最好地将扫描集成到持续交付中，还没有明确的指导（虽然 ZAP 项目团队正在研究中），你需要自己进行探索。你可以尝试爬取应用程序（如果它足够小），但是通常在“持续集成”和“持续交付”中明确扫描目标更有意义，以便减少执行测试所需的时间并最大程度地减少误报。为此，你可以通过代理由 Selenium 之类的工具执行的自动功能回归测试，以绘制和导航要扫描的关键表格和字段。然后，调用扫描程序的 API，执行其模糊测试攻击。

 

然后，你需要仔细检查结果，过滤误报，并定义通过或失败的规则，以及是否需要终止工作流。与静态分析工具一样，你需要优化动态扫描将误报降到最低。你需要将“错误门禁”设置得足够高，以确保不会浪费开发团队的时间。

 

每次扫描后，还需要删除重复的发现。诸如 Code Dx 或 ThreadFix 之类的工具（我们还将在后面的章节中介绍）可以帮助做到这一点。

 

与静态分析扫描一样，动态分析检查也需要时间，因此可能需要将其拆分以与其他测试并行运行，甚至带外进行。


模糊测试与持续交付

 

另一种在发现安全漏洞（尤其是注入漏洞）方面可能有价值的测试技术是模糊测试。模糊测试是一种蛮力可靠性测试技术，你可以在其中创建随机数据并将其注入文件或 API 中，以便有意触发错误，然后观察结果。模糊测试在嵌入式系统开发中非常重要，因为错误的成本很高，并且已成为 Microsoft、Facebook、Adobe和 Google 的应用程序安全测试程序的基本组成部分。安全研究人员也经常使用模糊测试工具来寻找漏洞。

 

然而，与扫描一样，模糊测试并不能很好地适应持续集成和持续交付自动化，原因有很多：

  • 模糊测试通常不可预测或不可重复。模糊测试的本质是尝试随机事物，看看会发生什么。

  • 模糊测试的结果也是不可预测的。系统可能会崩溃或可能发生某种异常，这些异常可能会使系统对于未来的测试来说处于不确定状态。

  • 模糊的结果可能难以评估和理解，并且当多个问题具有相同原因时，可能需要人工检查者来识别和界定问题。

  • 良好的模糊测试需要花费数小时或数天的时间才能完成，并且需要大量的CPU 资源，因此很难适应持续交付的时间要求。

 

一些较新的模糊测试工具被设计成在持续集成和持续交付中运行（或可以适应运行）。它们允许你设定测试值以创建可重复的测试、在测试运行时设置时间框、检测重复错误以及编写脚本以在系统崩溃时自动设置/恢复状态。但你可能仍然会发现模糊测试最好在带外进行。


单元测试和集成测试中的安全性

 

持续集成和持续交付，尤其是诸如行为驱动开发（BDD）和测试驱动开发（TDD）之类的实践（开发人员在编写代码之前先编写测试），鼓励开发人员创建一套强大的自动化测试来发现错误并保护自己添加新功能或对代码进行更改或修复时不至回滚。

 

这些测试大多数将是积极的、幸福的测试用来证明功能可以按预期工作。这是大多数开发人员的思考方式，也是他们得到报酬的原因。但是，这意味着他们经常错过对可能引发安全问题的边缘情况、异常情况和负面情况进行测试。

 

按照自动化的“测试金字塔”惯例，这些自动化测试大多数是低级单元测试，由开发人员编写，用于验证方法或功能中的详细逻辑。单元测试对于在重构代码或进行其他更改时捕获回归很重要，但是它们不会发现调用函数或服务时发生的错误或误用，例如根本不调用某些函数（这是安全漏洞的常见原因），只能在更高级别的功能或集成测试中发现。

 

对于安全代码和框架代码以及其他高风险功能，你应该说服开发人员围绕边界条件（尤其是外部条件）编写好的单元、功能和集成测试。他们需要测试错误处理和异常处理逻辑，并编写否定测试：除非出现问题，否则永不通过的健壮性测试。坚持对高风险代码进行高水平的自动测试覆盖。

 

花一些时间与团队合作，提出滥用或“恶意用户”的故事，以探讨不良用户如何尝试利用某项功能，或者如果他们误用了该功能，以及会发生什么。这不一定需要专门的安全知识；你只要问一下以下问题就能发现很多：

 

但是，如果用户没有...会发生什么呢？

 

然后，针对这些情况编写负面测试用例，来证明未经身份验证的用户无法访问管理功能，用户无法查看或更改其他帐户的信息，无法篡改返回值，等等。如果这些测试失败，则说明某些东西出错了，你需要尽早了解它。


自动攻击

 

即使进行了这些测试，你仍然需要进一步尝试攻击你的系统。坏人会攻击你的系统（即使尚未进行攻击的话）。你应该试着打败他们。

 

有一些测试框架旨在简化此过程，并且可以很好集成到持续集成和持续交付中：

  •  Gauntlt

  •  Mittn

  •  BDD-Security

使用这些工具中的一个，你就可以对你的系统进行一组基本的自动化渗透测试，并将其作为自动化测试周期的一部分。


Gauntlt：来吧，对你的代码刻薄点

 

Gauntlt 是使用 Ruby 编写的流行的开源测试框架（现在也有 Golang 版本），该框架使用 Cucumber 来描述简单的与安全相关的断言或可供开发人员或者审计人员使用的复杂的自动攻击场景。

 

Gauntlt 封装了渗透测试和安全测试工具，抽象化了它们工作方式的细节并使它们更易于使用，并控制这些工具，以便你可以创建可重复的确定性步骤，并获得清晰的通过/失败结果。

 

你可以使用 Gherkin 语法来编写攻击场景，Gherkin 语法是一种类似英语的高级语言，基本上是自文档化的，从而可以轻松地描述和编写测试：

Given    Set up conditionsWhen    Attack stepsThen    Parse output, filter out noise, and check return values to determine pass/fail

 

以下是来自 Gauntlt 站点的一个简单攻击示例：

# nmap-simple.attackFeature: simple nmap attack to check for open ports    Background:        Given "nmap" is installed        And the following profile:            | name | value |            | hostname | example.com |Scenario: Check standard web ports    When I launch an "nmap" attack with:        """        nmap -F <hostname>        """    Then the output should match /80.tcp\s+open/    Then the output should not match:        """        25\/tcp\s+open        """

  

Gauntlt 的目的是鼓励开发人员、测试人员和安全专家在安全测试上进行协作，将更多的精力放在他们要测试的内容上，而不是在如何进行测试上。

 

它预包装了针对不同工具（curl、sslyze、sqlmap、garmr、arachni、dirb、heartbleed）的攻击适配器，这些适配器实现了从 Gherkin 到可执行代码的步骤定义。它还包括你可以自定义和扩展的示例攻击文件。

 

使用 Gauntlt 之类的工具可以执行的一些常见测试包括运行 nmap 来检查打开的端口，检查 SSL 的配置是否正确，尝试 SQL 注入以及测试诸如 Heartbleed 的高危漏洞。

 

与自动化集成测试或验收测试一样，在持续交付中建立一组强大的安全测试也将需要一些时间。可以先建立一个部署后的安全冒烟测试，这是一个基本的回归测试，将在验收测试和生产中运行，以捕获常见和重要的安全问题，并确保安全配置正确。



渗透测试和漏洞赏金计划

 

在持续交付和持续部署中，手工渗透测试作为门禁并不有效。交付速度太快，而渗透测试花费的时间太长。但是，从持续交付流程进行带外渗透测试仍然具有重要的价值，不仅可以满足强制性的合规性要求，更重要的是，你可以通过渗透测试的结果来验证你的安全流程，标注出优势和劣势。

 

好的渗透测试具有探索性和创造性，这与“持续交付”中的大多数自动测试不同，后者旨在一遍又一遍地捕获设计、编码和配置中的相同类型的错误。优秀的渗透测试人员将帮助你发现原本不会去寻找的问题或不知道如何发现的问题。

 

这些测试的真正价值不在发现的 bug 中。而是在于 bug 提供给你的信息，如果你看得足够深入的话。bug 来自何处？你为什么自己没有找到它？它一开始是怎么出现的？为了防止类似的问题再次发生，我们需要改变或改进什么？

 

同样的原则也适用于漏洞赏金计划，它是 Google、Etsy、Netflix 和 Facebook 等领导厂商的安全计划的一部分。招募安全社区研究人员来查找软件中的安全性和可靠性错误，使你能够获得原本不具备的创造力和技能。他们会发现一些重要的错误。修复这些错误将使你的系统更安全。但是，更重要的是，它们将为你提供有关需要改进设计、编码、审查、测试和配置管理的信息。可以使用这些信息来优化组织，构建更好、更安全的系统。


在 LMAX 使用渗透测试改善自动化测试

 

在伦敦多资产交易所（LMAX），作为其持续交付承诺的一部分，该团队的目标之一是尽可能通过自动化测试覆盖系统的所有行为。这不仅包括功能和集成测试，还包括性能（可伸缩性和延迟）、操作弹性（通过故障注入）和安全性。

 

作为受监管的金融实体，LMAX 接受了外部专家的定期渗透测试。团队认为渗透测试不仅是复选项，必须通过的合规性门槛，而且还是宝贵的学习机会和挑战。他们试图理解并预测渗透测试人员在寻找什么以及如何发现安全问题。然后，LMAX将其内置到自己的自动化测试中，以尝试在将系统部署到生产环境之前自行发现尽可能多的问题。


漏洞管理

 

信息安全需要对管道（pipeline）、系统以及管道（pipeline）、系统和资产的组合有自己的视角，以便跟踪漏洞，评估风险和了解趋势。你需要有适用于合规性和风险管理目的的度量标准，以决定在评估应用程序安全计划时如何确定测试和培训工作的优先级。

 

收集有关漏洞的数据会让你能够提出一些重要问题：

  • 发现了多少个漏洞？

  • 漏洞是如何找到的？哪些工具或测试方法可以带来最佳回报？

  • 最严重的漏洞是什么？

  • 漏洞需要花多长时间才能修好？随着时间的流逝，这种情况会变得好还是坏？

 

可以通过将持续交付管道（pipeline）中的安全测试结果反馈到漏洞管理器（例如Code Dx 或 ThreadFix）中来获取此信息。

 

ThreadFix

 

ThreadFix 是一个漏洞管理工具（有开源和企业版），它整合了漏洞信息，提供了跨工具、管道（pipeline）和应用程序以及随时间推移的漏洞风险和修复的视图。ThreadFix 自动从 SAST 和 DAST 工具（以及手工渗透测试）中获取漏洞，对结果去重，供分析人员查看和分类漏洞，并轻松地将其转换为报告，然后将其反馈给开发人员的错误跟踪系统或 IDE。ThreadFix 旨在促进从测试到开发人员的反馈循环，同时向安全分析人员提供分析和报告工具，以便他们可以比较整个产品组合中的漏洞风险并跟踪进展（例如修复时间）。

 

开源版本包括与不同的测试工具、持续集成/持续交付服务器以及开发工具集的集成。商业企业版提供跨项目组合的分析和报告以及扫描器编排功能。

保护基础设施


在持续交付中，用于构建和交付安全代码的相同做法---自动化工作流和管控措施可以用于保护基础设施：

  • 将配置作为代码进行管理（对代码进行版本基本检查，确保对其进行了评审，并针对常见错误进行扫描）

  • 默认情况下将加固策略构建到配置代码中

  • 使用持续交付管道（pipeline）自动测试、部署和跟踪配置变更

  • 保护持续交付管道（pipeline）本身安全

让我们更详细地看看这些想法。

 

自动化配置管理

 

通过代码驱动的配置管理工具（如Puppet、Chef 和 Ansible），可以使用通用模板轻松地在数百台服务器上设置标准化配置，从而最大程度地降低了黑客可以利用一台未打补丁的服务器的风险，并最大程度地减少了生产、测试以及开发环境之间的差异。管控环境的所有配置信息都在中央存储库中可见，并且处于版本控制之下。这意味着，当在诸如 OpenSSL 之类的软件组件中出现漏洞时，很容易确定需要修补哪些系统。而且也很容易推出补丁。

 

这些工具还提供了一些基于主机的入侵检测功能，并可以控制配置漂移：它们持续不断地自动审核运行时配置，以确保每个系统都与主配置定义相匹配，在缺少某些内容或出现错误时发出警报，并能自动更正。

 

安全性应该被纳入Amazon Machine Images（AMI）和其他配置模板中。编写和评审 Puppet manifests、Chef cook‐books、Ansible playbooks、and Docker files 时都应该考虑安全性。配置代码的单元测试应包括安全检查，例如：

  • 确保禁用不必要的服务

  • 确保不需要打开的端口确实没有打开

  • 查找硬编码的凭据和秘钥

  • 查看敏感文件和目录的权限

  • 确保正确安装和设置 OSSEC 或 AIDE 等安全工具

  • 确保开发工具未安装在生产服务器中

  • 检查审计、日志记录的策略和配置

 

在流程中建立标准的加固步骤，而不是使用脚本或手动清单去检查。这包括通过删除所有不需要的和存在已知问题的软件包来最大程度地减少攻击面，更改默认配置以确保安全。

 

可以将安全标准（例如网络安全中心（CIS）基准和 NIST 配置清单）融入到Puppet、Chef 和 Ansible 规范中。那里有一些 Puppet modules 和Chef cookbooks 的示例，可帮助您根据 CIS 基准和《Defense Information Systems Agency Security Technical Implementation Guides》来加固 Linux 系统。

 

Hardening.io

 

Hardening.io 是 Deutsche Telekom 的开源的 Linux 服务器基础架构加固框架。它包括针对操作系统和 ssh、Apache、nginx、mysql 和 Postgres 等通用组件的实用加固步骤。

 

提供了用于 Chef 和 Puppet 以及 Ansible 的加固模板（Ansible 当前仅实现了OS 和 ssh）。加固规则基于德国电信的内部准则、BetterCrypto 和 NSA 加固指南。


保证持续交付管道（pipeline）安全

 

重要的是，不仅要保护应用程序及其运行时环境，而且要保护持续交付工具链以及构建和测试环境。需要对交付的完整性和监控链有信心，这不仅仅是出于法规遵从性和安全性的原因，还需要确保安全、可重复和可跟踪地进行变更。

 

持续交付工具链本身也是一个危险的攻击目标：它提供了进行变更并将其自动推送生产的清晰路径。如果遭到破坏，攻击者可以轻松进入你的开发、测试和生产环境。他们可能会窃取数据或知识产权，将恶意软件注入环境中的任何位置，对系统进行 DoS 攻击，或者通过关闭流程本身来削弱你的组织应对攻击的能力。

 

持续交付和持续部署可将生产系统的攻击面有效地扩展到构建以及自动测试和部署环境。

 

你还需要通过确保所有更改都是完全透明的并且可以从头到尾进行跟踪来保护发布管道（pipeline）免受内部人员攻击，确保恶意的和知情的内部人员无法进行更改而不被发现，并且它们不能绕过任何检查或验证。

 

对持续交付管道进行威胁建模。寻找设置和控制方面的弱点，以及审核或日志记录方面的差距。然后，采取措施保护你的配置管理环境和持续交付管道：

  • 加固存储源代码和构建仓库的系统，加固持续集成、持续交付服务器，以及承载配置管理、构建、部署和发布工具的系统。确保清楚地了解并管控本地执行的操作以及云中的操作。

  • 加固持续集成和/或持续交付服务器。像 Jenkins 之类旨在为开发人员提供便利的工具，默认情况下并不安全。确保这些工具（和所需的插件）保持最新并经常进行测试。锁定并加固配置管理工具。例如，可参阅“How to be a Secure Chef”。

  • 确保密钥、凭据和其他机密信息受到保护。将机密信息从脚本、源代码和纯文本文件中移除，并使用经过审核的安全秘钥管理器，例如 Chef Vault，Square 的 KeyWhiz 项目或 HashiCorp Vault。

  • 安全访问源代码和二进制存储库，并审核对它们的访问。

  • 在整个工具链中实施访问控制。不允许匿名或共享访问存储库、持续集成服务器或认证服务器或任何其他工具。

  • 更改构建步骤以对二进制文件和其他构建工件进行签名，以防止篡改。

  • 定期查看日志，以确保它们是完整的，并且可以从头到尾跟踪更改。确保日志是不可变的，不能擦除或伪造。

  • 确保将所有这些系统作为生产环境的一部分进行监视。

生产安全


系统投入生产后，安全工作并未停止。在 DevOps 中，自动安全检查、持续测试和监视反馈循环是生产操作的组成部分。

 

运行时检查和 Monkeys

 

如果你要允许开发人员进行自助服务，点击按钮就可以部署到生产中并且不能对每个更改进行详细审查，那么就需要添加一些运行时检查以捕获疏忽或错误。这就是Netflix 上的 Jason Chan 所说的“从大门到护栏”（from gates to guardrails）。

 

每次部署后，请检查工程师是否正确使用了模板，以及他们在配置或部署中没有犯过可能会使系统受到攻击或在出现故障时降低系统可靠性的根本性的错误。

 

这就是 Netflix 创建 Simian Army 的原因，Simian Army 是一组自动化的运行时检查和测试，包括著名的 Chaos Monkey。

 

作为 Netflix 混沌工程方法的一部分，Chaos Monkey、Chaos Gorilla 和 Chaos Kong 通过将故障随机注入生产以检查系统的设置和设计是否能够正确处理故障。

 

其他 Monkey 是规则驱动的合规性服务，可自动监视运行时环境以检测更改并确保配置与预定义的相匹配。他们查找违反安全策略和常见安全配置的弱点（对于Security Monkey 来说）或不符合预定义标准的配置（Conformity Monkey）。它们会定期在线运行，并在出现问题时通知服务和信息安全的所有者。负责服务的人员需要调查和纠正问题，或说明情况。

 

Security Monkey 捕获策略随时间变化的详细信息。它还可以用作分析和报告工具，并用于取证目的，使你可以跨时间段以及跨帐户、区域、服务和配置项目搜索变更。它突出显示了诸如更改访问控制策略或防火墙规则之类的风险。

 

类似的工具包括 Amazon 的 AWS Inspector，该服务提供对部署在 AWS 上的应用程序的自动化安全评估，扫描漏洞以及检查与最佳实践的偏差，包括 PCI DSS 规则和其他合规性标准。它提供了安全问题的优先列表以及有关如何解决这些问题的建议。

 

像这样的检查在 Netflix 运行的公共云环境中（开发人员经常在其中进行更改）特别重要，但同样的想法也可以扩展到任何系统。始终假定会犯错误，并且每次进行更改时都要进行检查以确保系统设置正确无误。你可以编写自己的运行时断言：

  • 检查防火墙规则是否正确设置

  • 验证文件和目录权限

  • 检查 sudo 规则

  • 确认 SSL 配置

  • 确保日志记录和监控服务正常运行


每次在系统部署测试和生产时，运行安全性冒烟测试。

 

Puppet 和 Chef 等工具将自动持续扫描基础设施，以检测与预期基准状态之间的差异，并发出警报或自动将其还原。


态势感知和攻击驱动防御

 

DevOps 重视生产反馈，并强调衡量和监控生产活动的重要性。你可以把相同的方法和相同的工具扩展到安全监控，使安全度量在运行的系统的上下文中可用，并对与安全性相关的数据进行图形化和可视化以识别趋势和异常，这会涉及整个团队而不是仅是 SOC。

 

认识到你的系统正在或将受到持续的攻击。利用上述信息可以识别和了解攻击以及系统的威胁概况。

 

攻击需要时间。移至杀伤链的左侧，并在早期阶段将其捕获。通过充分利用DevOps 团队对生产反馈的密切关注，并将安全数据添加到这些反馈循环中，从而减少攻击平均检测时间（MTTD）。通过与更熟悉系统的人员进行交流，你也会从中受益：编写代码并维持系统运行的人员更了解系统工作原理、正常状态以及异常情况。

 

将这些数据反馈到测试和评审中，根据在生产中看到的情况来确定操作的优先级，就像对待生产中持续集成或 A/B 测试的反馈一样。这是真实的反馈，而不是理论上的反馈，因此应立即认真地采取行动。

 

这就是 Signal Sciences 的 Zane Lackey 提出的“攻击驱动防御”（Attack-Driven

Defense）。有关安全事件的信息可帮助你根据生产中当前发生的情况了解威胁并确定优先级。监视运行时错误、异常和攻击特征可显示正在被探测和测试的位置、攻击类型、正在攻击的位置、攻击成功的位置以及需要保护代码的哪些部分。

 

这应该有助于确定安全优先级，告诉你应该在哪里进行测试和修复。从未受到攻击的漏洞（可能）不会伤害你。但是现在正在发生的攻击需要马上解决。


Signal Sciences

 

Signal Sciences 是一家技术创业公司，为 web 系统提供下一代基于 SaaS 的应用防火墙。它通过增加攻击的透明度来“使安全可见”，以便了解风险。它还提供了在运行时识别异常并阻止攻击的功能。

 

Signal Sciences 由 Etsy 安全团队的前领导人创立。防火墙利用了他们为 Etsy 开发的思想和技术。它不像大多数 Web 应用程序防火墙（WAF）一样基于攻击签名。它通过分析流量来检测攻击，并在其云后端聚合攻击信号来确定何时阻止流量。它还将攻击信号与运行时错误相关联，以识别系统何时可能受到破坏。

 

团队可以通过仪表板、电子邮件发出的警报通知或通过与 Slack、HipChat、PagerDuty 和 Datadog 之类的服务集成，看到攻击数据。仪表板是通过 API 构建的，因此可以将数据集成到 Splunk 或 ELK 等日志分析工具中，或 ThreadFix、Jira 等工具中。

 

通过持续交付，防火墙及其规则引擎会进行持续的改进和更新。


运行时防御

 

如果你不能成功地将安全性左移到早期的设计和编码、持续集成和持续交付，那么在系统投入生产之后，将需要在最后添加更多的保护。网络 IDS/IPS 解决方案工具，如 Tripwire 或基于攻击签名的 WAFs，并不是为了跟上 DevOps 系统和技术的快速变化而设计的。对于云 IaaS 和 PaaS 环境而言，尤其如此，因为它们没有清晰的网络边界，并且你可能通过自助式连续部署在不同环境（公共、私有和混合）中管理成百上千个临时实例。

 

也有许多云安全保护解决方案可用，它们提供攻击分析、集中式帐户管理和策略实施、文件完整性监视和入侵检测、漏洞扫描、微分段，并可与配置管理工具（例如Chef 和 Puppet）的集成。其中一些解决方案包括：

  • Alert Logic

  • CloudPassage Halo

  • Dome9 SecOps

  • Evident.io

  • Illumio

  • Palerra LORIC

  • Threat Stack

 

另一种运行时防御技术是运行时应用程序安全保护/自我保护（RASP），它使用运行时工具来捕获出现的安全问题。像应用程序防火墙一样，RASP 可以自动识别和阻止攻击，你也可以将 RASP 扩展到没有源代码的旧版应用程序中。

 

但是与防火墙不同，RASP 并不是基于边界的防御。RASP 检测应用程序运行时代码，并可以在执行时识别和阻止攻击。RASP 工具没有创建代码的抽象模型（例如静态分析工具），而是获取代码运行时上下文，并使用污点分析、数据流、控制流和词法分析技术，直接检查数据变量和语句来检测攻击。这意味着 RASP 工具的误报率比防火墙低得多。

 

你还可以使用 RASP 工具将日志记录和审核注入到旧版代码中，以深入了解正在运行的应用程序以及针对它的攻击。需要权衡运行时成本与进行代码修复的成本。

 

目前，只有少数的 RASP 解决方案可用，大部分仅限于运行在 JavaJVM和 .NETCLR 中的应用程序，但是正在逐渐出现对其他语言（如 Node.js、Python 和Ruby）的支持。这些工具包括：

  • Immunio

  • Waratek

  • Prevoty

  • Contrast Security (我们将更详细地介绍)


Contrast Security

 

Contrast 是一种交互式自动化软件测试（IAST）和 RASP 解决方案，可以直接检测正在运行的代码，并使用控制流和数据流分析以及词法分析在程序运行时跟踪和捕获安全问题。在 IAST 模式下，Contrast 可以在开发人员的工作站上或测试环境中运行，也可以在持续集成/连续交付中运行，以在功能测试期间警告是否发现了诸如 SQL 注入或 XSS 之类的安全问题，所有这些都会增加较小的开销。你只需执行代码即可自动发现安全问题；测试越全面，涵盖的代码路径越多，发现漏洞的机会就越大。而且由于这些问题是在代码执行时发现的，因此误报率比静态分析低得多。

 

Contrast 会删除重复数据，并通过电子邮件，Slack 或 HipChat 或通过在 Jira 中记录错误报告等不同方式来通知你安全问题。在 RASP 模式下，Contrast 在生产中运行来跟踪和捕获相同类型的安全问题，然后警告操作或自动阻止攻击。

 

它可以工作在 Java、.NET（C＃和Visual Basic）、Node.js 等一系列运行时环境中。


其他运行时防御解决方案采用与 RASP 或防火墙不同的方法。以下是该领域的一些创新型初创公司，值得关注：

 

tCell

tCell 是一家提供应用程序运行时免疫的初创公司。tCell 是基于云的 SaaS 解决方案，可在运行时对系统进行检测，并将检查和传感器注入到正在运行的应用程序的控制点中：数据库接口，身份验证控制器等。

 

它使用此信息来绘制系统的攻击面，并识别攻击面的变化。tCell 还可以根据以下内容识别并阻止运行时攻击：

  • 已知的不良行为模式（例如，SQL注入尝试），类似 WAF。

  • 威胁情报和关联-如黑名单的 IP 等等。

  • 行为学习-识别行为和流量异常。随着时间的推移，它能识别出什么是正常的，并可以通过阻塞或在异常时发出警报来强制执行正常的活动模式。

 

tCell 可用于Java、Node.js、Ruby on Rails和Python（正在开发.NET和PHP）。

 

Twistlock

Twistlock 为企业环境中的 Docker 容器提供了运行时防御功能。Twistlock 的保护包括企业身份验证和授权功能-Twistlock 团队正在与 Docker 社区合作，以帮助实现授权框架（其授权插件框架作为Docker 1.10的一部分发布）和身份验证，并且 Twistlock 为细粒度访问控制规则以及与 LDAP/AD 的集成提供了插件。

 

Twistlock 扫描容器中的依赖项和配置中的已知漏洞（包括根据 Docker CIS 基准进行扫描）。它还通过扫描来了解每个容器的用途。它标识了调用栈，容器的行为配置文件以及行为方式，从而创建了一个预期行为和允许行为的白名单。

 

在运行时环境的每个节点上安装一个 agent（也作为容器），并与该节点上的所有容器以及 OS 进行通信。该 agent 会监控所有容器的运行时活动，强制执行身份验证和授权规则，并对每个容器执行应用预期行为的白名单以及已知不良行为的黑名单（像恶意软件解决方案一样）。

 

而且由于容器是不可变的，因此 Twistlock 可以识别并阻止运行时更改容器配置的行为。


从失败中学习：Game Days，红队和复盘

 

Game Days-运行真实的、大规模的失败测试（比如关闭一个数据中心）在DevOps 公司，如 Amazon、Google 和 Etsy 中也已成为惯例。这些演习可能需要（例如在Google）数百名工程师日以继夜地工作几天，以测试灾难恢复，并评估压力和疲劳程度如何影响组织处理实际事故的能力。

 

在 Etsy，Game Days 在甚至包括支付等核心功能的生产中运行。当然，这引出了一个问题：“为什么不在 QA 或 staging 环境中模拟它？” Etsy 的回应是，首先，这些环境中存在任何差异都会给演习带来不确定性。其次，无法恢复的风险在测试期间不会产生任何后果，这可能会将隐含的假设带入容错设计和恢复中。目标是减少而不是增加不确定性。

 

这些演习都是事先经过仔细测试和计划的。团队集思广益并为故障场景做好准备，首先在测试中运行故障并修复出现的任何问题。然后，是时候在生产环境中执行方案了，开发人员和运维人员密切关注，随时准备投入恢复，尤其是在意外出现的情况下。

 

你可以从旨在测试系统的弹性以及 DevOps 团队处理系统故障的准备情况，并可以通过红队的方式将其应用于安全攻击场景的 Game Days 中获得许多思路。这是Microsoft、Facebook、Salesforce、Yahoo 等的核心实践，也是 Intuit 对于其基于云的服务的核心实践。

 

像运维的 Game Days 一样，红队演习在生产中最有效。

 

红队发现了他们认为可以利用的弱点，并以道德黑客的身份攻击线上系统。通常会赋予他们短时间瘫痪系统或者损坏、获取敏感数据的权利。红队的成功与否可以通过他们所发现问题的严重性以及攻击成功的平均时间来衡量。

 

蓝队由运行、支持和监视系统的人员组成。他们的职责是识别攻击何时进行，了解攻击并提出遏制攻击的方法。是否成功可以通过“检测攻击的平均时间”及其共同做出有意义的响应的能力来衡量。

 

这些演习的目的如下：

  • 通过入侵自己的系统来发现真实的可利用漏洞，从而找出测试、设计和实施方面的差距。

  • 锻炼事件响应和调查能力，找出监控和记录、行动手册、升级程序和培训方面的差距或弱点。

  • 通过关注使系统更安全的共同目标，在安全团队与开发和运维之间建立联系。

 

在 Game Day 或红队演习之后，就像真正的生产中断或安全事件之后一样，团队需要聚在一起以了解发生了什么并学习如何变得更好。他们会做事后复盘。在这里，每个人都在一个开放的环境中讨论事件的事实：发生了什么，何时发生，人们如何反应以及接下来发生了什么。通过冷静、客观地关注于事实和出现的问题，团队可以更多地了解系统、了解他们自己以及他们是如何工作的，他们可以开始了解什么地方出了问题，质疑为什么出了问题，并寻找改进的方法（系统设计、测试、部署、运行等方式）。

 

为了取得成功，你需要营造一个环境，让人们能够安全地分享信息，做到诚实、真实、透明，并且能够进行批判性思考，而不被批评或指责，这就是 Etsy 所说的“公正文化”。这就需要管理层的支持，理解并接受事故终将发生，但它会提供重要的学习机会。如果做得正确，事后复盘不仅可以帮助你从失败中学习并理解和解决重要问题，而且还可以使人们团结在一起，增强开放性和信任度，从而使组织更强大。


Netflix 的安全

 

Netflix 是另一个 DevOps 独角兽。像 Etsy、Amazon 和 Facebook 一样，它的成功是基于“自由与责任”的文化（员工，包括工程师，可以自由地做他们认为正确的事情，但他们也要对结果负责）以及对自动化的巨大承诺，包括安全性，尤其是安全性。

 

在运行自己的 IT 基础设施遇到严重问题后，Netflix 决定将其在线业务迁移到云中。它一直是亚马逊 AWS 平台的最大用户之一。

 

Netflix 的 IT 运维方法有时称为“ NoOps”，因为他们没有运维工程师或系统管理员。他们已将部分运维有效地外包给了 Amazon AWS，因为他们认为数据中心管理和基础架构运营是“无差别的繁重工作”。或者换一种说法，工作很难做，但不能为他们的业务增加直接价值。

 

以下是 Netflix 安全计划的四大支柱：

 

毫无区别的繁重工作和共同责任

Netflix 高度依赖 AWS 的功能，并根据需要构建或扩展这些功能以提供额外的安全性和可靠性功能。它依靠其云提供商进行自动配置、平台漏洞管理、数据存储和备份以及物理数据中心保护。Netflix 在此基础上构建了自己的 PaaS 层，其中包括大量的安全检查以及分析和监视服务。Netflix 还将安全默认植入到用于配置每个实例的基础镜像中。

 

开发中的可追溯性

源代码控制，通过 Git 拉取请求进行的代码评审以及持续集成和持续交付管道提供了从签入到部署的所有更改的完整跟踪。Netflix 使用相同的工具来跟踪信息，在满足自己的支持目的同时也满足审计人员为了合规性的诉求，就避免了浪费时间单独进行审计跟踪。工程师和审计人员都需要知道谁在何时进行了哪些更改，如何测试这些更改，何时进行了部署以及接下来发生了什么。这为支持和持续验证合规性提供了可视性和可追溯性。

 

持续的安全可见性

认识到环境正在不断变化，并使用自动化工具来识别和了解安全风险，监控和捕获问题。Netflix 编写了一套自己的工具来实现这一点，包括 Security Monkey，Conformity Monkey 和 Penguin Shortbread（它们会自动识别微服务并根据运行时依赖项持续评估每个服务的风险）。

 

分隔

利用云帐户隔离、数据令牌化和微服务来最大程度地减少系统的攻击面并遏制攻击，并实施最小权限访问策略。Netflix 认识到工程师通常会要求比他们需要的更多的特权，以防万一。因此，Netflix 创建了一个名为 Repoman 的自动化工具，该工具使用 AWS Cloudtrail 活动历史记录，并根据每个账户在一段时间内的实际操作将账户权限降低到实际需要的程度。分隔还会遏制失败的“爆炸半径”，从而减少出现问题时对操作的影响。

 

无论你是在云中工作还是在自己的数据中心中实践 DevOps，这些原则对于构建和运行安全可靠的系统都是至关重要的。
