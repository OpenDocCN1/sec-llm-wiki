将安全融入 DevOps 中：Etsy 的故事


Etsy 是一个成功的在线工艺品市场，以持续部署模式而闻名，其工程师每天都会发布 50 次以上变更。它也以其“公正文化”（Just Culture）而闻名，在这种文化中，工程师被教导拥抱失败，前提是他们从错误中吸取教训。


Etsy 的安全文化建立在其工程文化的基础之上，并与组织的更广泛的文化联系在一起。它的一些驱动原则是：


  • 相信人们会做正确的事情，但仍然要验证。依靠代码审计和测试、默认安全，并进行培训以防止错误或发现错误。如果生产中发生了错误，进行复盘，了解发生了什么，以及如何从源头上解决问题。


  • “如果变动，进行图形化展示”。使数据包括有关安全风险、威胁和攻击的信息对每个人都可见，以便每个人都能理解并采取行动。


  • “尽管发布”。每个工程师都可以随时推送到生产。其中也包括安全工程师。如果有东西坏了，你可以修理它，把它修好，然后马上发布上线。如果不需要的话，安全工程师不会把问题抛给开发人员或运维人员。他们与其他团队合作，了解问题并解决问题，如果可以的话，也可以自己解决问题。每个人都使用持续部署管道和相同的工具将变更推送到生产中，也包括安全团队。


  • 安全不能成为阻碍因素。“No”这个词是一种有限的资源——只有在你必须使用它的时候才使用它。安全部门的工作是与开发和运营部门合作，帮助他们交付，但要安全交付。这就要求安全性要切合实际，在涉及到安全性调查结果时作出合理的权衡。这个问题是否严重到需要阻止代码现在发布？是否可以稍后修复？或者它真的需要修复吗？了解系统和组织面临的真正风险，并妥善处理问题。安全团队知道，如果真的出现了严重的问题，每个人都会认真对待。


Etsy 的安全团队采取了许多步骤来建立安全团队和工程部门之间的关系。


“Designated Hackers”是一个系统，通过这个系统，每个安全工程师支持整个组织中的四到五个开发团队，并参与设计和发布。安全工程师试图了解这些团队在做什么，并在出现需要解决的安全风险或问题时发出信号。它们充当安全和开发团队之间的通道和倡导者。这有助于建立关系，并在产品的安全性非常重要的时候为设计和早期决策提供参考。


每一个新来的工程师都会参加为期一周的训练营，在那里他们会与安全团队合作，了解他们的工作并帮助解决问题。而且每年每个工程师都会进行一次高级轮换，轮换中他们会花一个月的时间与另一个团队合作，这就包括安全团队。这些计划建立了组织和种子安全工程师之间的理解和关系。

安全左移


为了跟上持续交付的步伐，安全必须“左移”，更早地进入设计和编码以及自动化测试周期，而不是等到系统设计和构建之后，再在发布之前尝试进行一些安全检查。在 DevOps 中，安全性必须符合工程师的思考和工作方式：以更多的迭代和增量，并以高效、可重复和易于使用的方式自动化。瀑布式交付和 DevOps 周期之间的比较见图3-1。

一些组织通过将信息安全专家嵌入开发和运维团队来实现此目的。但是很难以这种方式进行扩展。因为信息安全工程师很少，尤其是那些懂得安全设计和安全编码的安全工程师。这意味着需要赋予开发人员和运维人员更多的安全责任，加强安全原则、安全实践、安全工具方面的培训以及帮助他们构建和运行安全的系统。


开发人员需要学习如何通过威胁建模（从攻击者的角度查看设计中的漏洞或弱点）来识别和缓解设计中的安全风险，以及如何利用应用程序框架中的安全特性和安全库来防止如注入攻击之类的常见漏洞。OWASP 和 SAFECode 社区提供了许多有用的免费工具、框架和指南，以帮助开发人员理解和解决系统中的常见应用程序安全问题。



02

—


OWASP Proactive Controls


OWASP Proactive Controls （https://owasp.org/www-project-proactive-controls/）是构建安全应用程序时应该遵循的一系列安全的开发实践、指导原则和技术。这些实践将帮助你更早地将安全性转移到设计、编码和测试中：


尽早并经常验证安全性

不要将安全性测试和检查留在项目的最后，而要在持续集成和持续交付中的自动测试中包括安全性。


参数化查询

通过使用参数化数据库接口防止 SQL 注入。


编码数据

在将数据传递给 interpreter 之前，对其进行安全编码，以保护应用程序免受 XSS 和其他注入攻击。


验证所有输入

将所有数据视为不可信。使用白名单技术验证参数和数据元素。了解并多使用正则表达式。


实施身份验证控制

使用安全、标准的方法和模式进行身份验证和身份管理。如果需要自己构建这些功能，请充分利用 OWASP 的备忘单中关于身份验证、会话管理、密码存储和忘记密码的内容。


实施适当的访问控制

在实现访问控制过滤器时，请遵循一些简单的规则：默认情况下拒绝访问；在中央过滤器库中实现访问控制，不要在应用程序的任何地方硬编码访问控制检查；记住编码要针对活动而不是角色。


保护数据

了解如何正确使用加密算法来加密静态和传输中的数据。使用经过验证的加密库，比如 Google 的 keychar 和 Bouncy Castle。


实施日志记录和入侵检测

在设计日志策略时要考虑入侵检测和取证。在应用程序中插入埋点并保证日志的安全性和一致性。


利用安全框架和库

尽可能利用应用程序框架的安全特性，并在需要的地方使用特殊用途的安全库，例如 Apache Shiro 或 Spring Security。


错误和异常处理

在整个应用程序中注意错误处理和异常处理。错过错误处理可能会导致运行时问题，包括灾难性故障。在错误处理中泄漏信息可能会给攻击者提供线索，不要为攻击者提供便利。


03

—


默认安全


安全左转首先要使工程师更容易编写安全代码，更难犯危险错误，将安全默认值植入到其模板和框架中，并内置上面列出的主动控制。你可以在框架层面通过使用参数化查询来防止 SQL 注入，隐藏或简化保护应用程序免受 XSS攻击所需的输出编码工作，强制执行安全的 HTTP 头以及提供简单而安全的身份验证功能。你可以通过使用该框架让上述的功能对于开发人员透明。


确保软件和软件开发的默认安全是 Google、Facebook、Etsy 和 Netflix 等组织的安全计划的核心。虽然回报可能是巨大的，但它要求从根本上改变信息安全与开发协同工作的方式。这需要安全工程师和软件工程师之间的密切协作，强大的应用程序安全知识和软件设计以及编码技能，以安全且易于使用的方式将安全保护构建到框架和模板中。最重要的是，它要求开发人员及其管理人员做出承诺，尽可能使用这些框架。


我们大多数人都无法以此开启我们的应用程序安全计划；相反，我们需要从头开始，并在后续的阶段建立更多的安全性。



04

—


安全自助服务


DevOps 模式中的工程师在自助服务环境中工作。自动化持续集成服务器提供自助式构建和测试。云平台和虚拟化技术（如Vagrant）提供了自助服务、按需供应。像 Docker 这样的容器技术提供了简单的自助式打包和发布。


安全性需要以同样的方式提供给团队：方便、需要时即可用、无缝且高效。


“别拦路”。不要让开发人员等待答案或者为了得到帮助而停止工作。给他们提供他们可以理解和使用的并且可以自动配置和运行的安全工具。并确保这些工具适合其工作方式：持续集成和持续交付，开发代码的 IDE，代码拉取请求中。换句话说，请确保测试和检查提供快速，清晰的反馈。


在Twitter，每次开发人员进行更改时，都会自动运行安全检查。像Brakeman 这样的工具会检查代码中的安全漏洞，如果发现问题，就直接向开发人员提供反馈，说明错误之处，错误原因以及修复方案。开发人员有一个 “bullshit” 按钮来拒绝误报。安全检查只是他们编码周期的另一部分。



05

—


基础设施即代码


DevOps 的另一个关键是基础设施即代码：使用 Ansible、Chef、Puppet 和 Salt 等工具管理代码中的基础架构配置。这可以简化配置系统，加快了配置效率，尤其是在大规模的系统中。它还有助于确保系统之间以及测试与生产之间的一致性，使配置标准化并使配置偏差最小化，并减少攻击者发现和利用一次性错误的机会。


将基础设施的供应和配置视为软件问题，并遵循软件工程实践，如版本控制、同行代码评审、重构、静态分析、自动化单元测试和持续集成，而且，通过同一种持续交付管道（pipeline）进行验证和部署变更，可以使配置变更可重复、可审核且更安全。


安全团队还可以使用基础设施即代码，将安全策略直接集成到配置中，在运行时持续审核和执行策略，并快速安全地修补漏洞。



UpGuard：从基础设施到安全代码

UpGuard 是一项服务，可帮助你自动将配置信息捕获到测试和代码中，然后建立策略并根据这些策略监视合规性。UpGuard 从 Linux、Windows 服务器、网络设备和云服务中发现配置的详细信息，并跟踪该信息随时间的变化。你可以将它用作类似 Tripwire 的变更检测控制工具来告警对配置的未授权更改或审计配置管理活动。

你还可以可视化系统的配置并确定它们之间的差异。通过创建细粒度的自动化测试或断言，可以为不同的系统或系统类型建立策略，以确保安装了正确版本的包，正确设置了特定的文件、用户和目录，确保打开或关闭了特定端口，确保运行程序的正确性。

UpGuard会自动为配置管理工具（包括Ansible、Chef、Puppet、Microsoft Windows PowerShell DSC 和 Docker）创建指令，以便使用预构建的测试框架将基础设施配置纳入代码中。

它根据合规性（测试覆盖率、通过率以及与外部基准（如CIS）的符合性）、完整性（跟踪对配置的未授权更改）和安全性（基于对漏洞的扫描--UpGuard 默认集成了一个社区版的漏洞扫描工具，并且可以与其他扫描器集成）来持续评估配置的风险。

—


通过迭代、增量变更来控制风险


DevOps 和持续交付可以通过进行许多小的增量变更而不是一些“大爆炸”（大的）更改来降低变更的风险。


频繁变更可以锻炼并证明具备测试并成功发布变更的能力，从而增强对构建和发布过程的信心。此外，它还迫使你自动化并简化这些流程，包括配置管理、测试和部署，并使它们更具可重复性、可靠性和可审计性。


较小的增量变更本质上更安全。因为任何变化的范围都很小，而且通常是孤立的，所以每个变化都可控。错误也更容易被发现，因为小批量进行的增量更改更易于预先检查和理解，并且需要较少的测试。


当出现问题时，也更容易了解发生的情况并进行修复，即通过回滚更改或使用“持续交付”流程快速发布补丁。


认识到 DevOps 中的许多更改都是灰度的，这一点也很重要。也就是说，它们在默认情况下被禁用，使用时进行“功能标记”或“功能切换”。这些功能通常只在一次或短时间内为少数用户打开，在某些情况下，只有在“可操作性审查”或复盘审查之后才能打开，以确保团队了解需要注意的内容并为问题做好准备。


另一种降低持续交付或持续部署中变更风险的方法是金丝雀发布（canary releasing）。基于“煤矿中的金丝雀”比喻，可以先将变更部署到单个节点，然后自动检查以确保关键指标（例如转换率）中没有错误或负面趋势。如果发现金丝雀系统有问题，则回滚变更，取消部署，并关闭流程，直到准备好修复方案。在指定的一段时间后，如果金丝雀仍然正常，则会将变更部署到更多的服务器，然后最终扩展到整个环境。

发挥持续交付的速度优势


对于信息安全分析师和审计师而言，DevOps 的速度似乎令人恐惧。但是安全也可以利用交付速度来快速响应安全威胁并处理漏洞。几乎所有组织都面临的严重问题是，即使他们知道系统中存在严重的安全漏洞，也无法做到快速修复该漏洞，并阻止攻击者利用此漏洞。


漏洞暴露的时间越长，系统受到或已经受到攻击的可能性就越大。WhiteHat Security 提供扫描网站中的安全漏洞的服务，它定期分析和报告收集到的漏洞数据。WhiteHat 使用 2013 年和 2014 年的数据，发现 35％ 的金融和保险网站“总是易受攻击”，这意味着这些网站每天都至少存在一个严重漏洞。其他行业和政府组织的统计数据甚至更差。在一年中只有 25％ 的金融和保险站点，易受攻击时间少于 30 天。平均而言，严重漏洞会存在 739 天，而由于修复漏洞所涉及的成本，风险和开销，只修复了 27％ 的严重漏洞。


持续交付以及开发人员、运维以及安全人员之间紧密协作可以关闭漏洞窗口。大多数安全补丁都很小，并且不需要很长时间来编写代码。可重复的，自动化的持续交付流程意味着你可以找出并修复安全漏洞或从供应商处下载补丁，进行测试以确保它不会引发回滚，并以最小的成本和风险快速将其发布。这与过去在压力下进行的“热修复”形成了鲜明对比，后者曾导致失败。


速度还使你能够做出有意义的风险和成本权衡决策。难以利用的漏洞，你可以决定暂时接受风险，因为迭代速度快你不需要等待几个星期或几个月到下一个版本，并且团队可以在需要时快速响应修复。


现在，交付速度已成为安全优势，而不是风险来源。

—


蜜月效应


DevOps 的快速似乎还有另一个安全优势。最近的研究表明，更小、更频繁的更改可以通过 “蜜月效应” （Honeymoon Effect）使系统面对攻击者更安全：较脆弱的旧软件比最近变更的软件更容易受到攻击。


攻击需要时间。识别漏洞需要花费时间，了解漏洞、利用漏洞也需要时间。这就是为什么许多攻击是针对有已知漏洞的旧代码的原因。在代码和配置变更迅速且频繁的环境中，攻击者更难以实时跟踪，识别弱点并弄清楚如何利用它。系统成为了一个移动的目标。在攻击者准备采取行动之前，代码或配置可能已经更改，漏洞可能已经改变或关闭。


从某种程度上来说，依靠变更来迷惑攻击者，是很弱的防御手段。快速发展的组织可以利用不断变更的优势，并有机会隐藏防御行为，以防攻击者在你的系统中站稳脚跟，正如微软的 Sam Guckenheimer 所解释的：


如果你是坏人，你想要什么？你想要一个静态的网络，有很多地方可以隐藏，并且这些地方是不受管制的。而且，如果有人检测到你，你希望能够发现防御行动，以便采取对策...借助 DevOps，您将拥有非常快速的自动化发布渠道，并且可以不断进行重新部署。如果你要在网络上的某个地方进行部署，这看起来不像是针对攻击者采取的特殊措施。
