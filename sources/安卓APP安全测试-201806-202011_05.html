首先，我们来看一下 DevOps 中安全与合规性的主要挑战与约束。



01

—

速度：交付速度


IT 的变更速度不断提高。对于敏捷开发团队来说，需要在一到两周的时间内冲刺交付软件，如何保证安全性与合规性成为一个严峻的挑战。同时，某些 DevOps 系统发起和交付变更的速度更令人惊讶。比如 Etsy 每天向生产推送 50 次以上变更。亚马逊有数千个独立工作的小型（“two pizza”）工程团队，并在其基础设施中不断部署变更。2014年，亚马逊部署了 5000 万次变更，相当于不到一秒钟就要部署一次变更。


变更太快了...


安全如何才能跟上这种变更速度？当系统在上线之前没有时间进行渗透测试或审计，没有地方设置控制门禁，甚至无法添加安全特性或加固的情况下，如何了解风险，以及如何管理这些风险？


02

—

设计在哪里？


DevOps 建立在敏捷开发实践的基础上，并将敏捷的思想和实践从开发扩展到运维。


对于许多已经在敏捷环境中工作的安全团队来说，一个挑战是开发人员在设计上花费的时间较少。敏捷宣言强调“工作的软件高于详尽的文档”（ “working software over documentation”），这通常意味着“代码即设计”（“the code is the design”），因此，“前置的大版本设计”（“Big Design Up Front”）是大多数敏捷团队的反模式。敏捷团队希望以一种简单、干净的方式开始，并在获得有关问题领域的更多信息时以一系列的迭代方式来进行详细设计。YAGNI（“你不需要它”）的原则告诉他们，用户可能永远不会使用预先设计的大多数功能，因此，他们试图将设计和功能集减少到最低限度，并尽可能快地只发布重要的功能，在变更中不断进行重构。


许多 DevOps 团队都将所有这些想法都做得更进一步，特别是遵循精益启动方法的团队。他们从最小可行产品（MVP）开始：将具有基本功能集的想法以最简单和最便宜的方式实现，并将该功能尽快交付给生产中的实际用户。然后，他们利用这些用户的反馈、采集指标数据并进行 A/B 实验，迭代并完善其余功能，不断地以最快的速度交付变更和新功能，以便获得更多反馈，从而在连续的循环中推动进一步的改进，并根据需要进行调整和转变。


所有这些都使得安全团队很难搞清楚他们应该在何处以及如何介入，并确保在编码之前设计是安全的。如果设计没有完成，没有设计文档，并且设计随着代码和需求不断变化，你如何评审设计？何时以及如何进行威胁建模？



03

—

消除延误和浪费


DevOps 深受精益原则的影响：最大化效率，消除浪费、延迟和不必要的成本。成功的前提是先要将一个新的想法或特性推向市场，这意味着团队要对交付的周期进行度量和优化。对于团队来说，尤其是精益创企业团队，他们希望快速失败并尽早失败。为此，他们进行快速原型制作并与真实的用户一起在生产中进行实验，检验他们的想法是否会流行起来，或者了解他们需要改变什么才能成功。


这增加了交付和安全之间的紧张关系。工程师需要投入多少（他们能负担多少）来保护在未来几天内可能被丢弃或重写的代码？什么时候安全建设是负责任的事，什么时候是在浪费有限的时间和精力？

 

在一个由持续的价值流驱动并通过看板和其他精益技术进行管理以消除瓶颈并使用自动化来最大化效率的环境中，安全性不能成为障碍。这对安全性和合规性是一个严峻的挑战，安全与合规通常更关心的是把事情做对并将风险降到最低，而不是高效和快速周转。



04

—

云


尽管你不需要在云中运行系统来利用 DevOps 的优势，但是如果你在云中操作，则可能需要遵循 DevOps 实践。这意味着云在许多组织的 DevOps 实践中扮演着重要角色（反之亦然）。


在今天的云（基础设施即服务（IaaS）和平台即服务（PaaS））中，像 Amazon AWS、Microsoft Azure 和 Google Cloud Platform 这样的平台可以为你做很多事情。它们消除了对硬件供应的等待，消除了购买硬件和建立数据中心的前期成本；它们提供了弹性容量以跟上业务增长。这些服务隐藏了管理数据中心和网络，以及维护、配置、管理和监控服务器和存储的细节。

 

云现在已经包含了太多的功能，有些功能是大多数团队不打算自己建设的，如内置的安全和操作管理功能。像 AWS 这样的云平台为帐户管理、数据分区、审计、加密和密钥管理、故障转移、存储、监视等服务提供了大量的 api 服务。它们还提供了快速设置标准配置的模板。

 

但你需要知道如何正确地找到和使用这些功能。在云操作的共享责任模型中，你需要了解云提供商的责任在哪里结束，你的责任从哪里开始，以及如何确保你的云提供商确实在做你需要他们做的事情。

 

云安全联盟的“Treacherous Twelve”指出了云计算服务用户面临的一些主要安全风险：


1.数据泄露
2.身份、凭据和访问管理薄弱
3.不安全的接口和 API
4.系统和应用程序漏洞
5.帐户劫持
6.恶意的内部人员
7.高级持续威胁（APT）
8.数据丢失
9.尽职调查不足
10.滥用和恶意使用云服务
11.拒绝服务
12.共享技术问题



05

—

微服务


微服务是 DevOps 众多成功案例中的又一个。微服务--设计小型的、独立的功能，可以完全独立地进行更改、测试、部署和管理，使开发人员能够快速行动进行创新，而不会受到组织其他成员的束缚。这种体系结构还鼓励开发人员对他们的系统部分从设计到交付和运维全部负责。亚马逊和 Netflix 在围绕微服务构建自己的系统和组织方面取得了巨大的成功。

 

但是微服务所带来的自由和灵活性也有一些缺点：

 

  • 操作复杂性。理解一个单独的微服务很简单（这就是微服务的意义所在）。但理解和映射不同微服务之间的工作流、运行时依赖关系，调试运行时问题或预防级联故障要困难得多。正如 Michael Nygard 所说：“一个微服务很好理解，但众多微服务之间的关系复杂程度超出想象。”


  •  攻击面。单个微服务的攻击面可能很小，但系统的总攻击面可能很大，并很难分析。


  • 与分层式 web 应用程序不同，微服务没有明确的边界，没有明显的“卡点”可以用来强制执行身份验证或访问控制规则。但你需要确保建立信任边界并一贯执行。


  • 多语言编程问题。如果每个团队都可以自由地使用他们认为适合工作的工具（比如在Amazon），那么理解和管理跨多种不同语言和框架的安全风险会变得非常困难。


  •  除非所有团队都同意使用标准化的活动日志策略，否则对使用不同日志记录方法跨不同服务进行取证和审核会是一场噩梦。

容器


容器 LXC、rkt ，特别是 Docker 在 DevOps 广泛使用。

 

像 Docker 这样的容器技术使开发人员更容易打包和部署应用程序所需的所有运行时依赖。这消除了“在我的机器上正常工作”的配置管理问题，因为你可以将相同的运行时环境与应用程序一起从开发交付到生产环境。

 

使用容器，可以在单一设备上部署和运行多个不同的实例，与使用虚拟机相比，开销和成本要低得多。与微服务一起使用，可以支持微分段（microsegmentation）；也就是说，每个微服务在各自独立的、单独管理的运行时环境中运行。

 

容器尤其是 Docker 之所以如此成功，是因为它们使得打包和部署工作流对于开发和运维都很容易。但这也意味着开发人员和运维人员很容易在不知情的情况下引入安全漏洞。

 

使用容器打包和部署应用程序的易用性也会导致无法管理的容器扩展，在许多不同的环境中部署了许多不同的实例（以及这些实例的不同配置和版本）。找到它们（甚至首先弄清楚怎么去寻找它们），检查它们是否存在漏洞，并确保它们打上了最新的补丁，这些都是非常困难的。

 

尽管容器在默认情况下提供了一些隔离和安全保护，有助于减少应用程序的攻击面，但它们也引入了一系列新的安全问题。《Using Docker》一书的作者Adrian Mouat 列出了使用 Docker 时需要注意的五个安全问题，并找到了一种管控方法：

 

内核漏洞

内核是在主机和所有容器之间共享的，这意味着内核中的漏洞会使主机上运行的所有容器受到攻击。

 

拒绝服务攻击

除非使用 cgroups 限制资源，否则一个容器中的问题可以使同一台主机上运行的其他所有容器都受到 DoS 攻击。


容器逃逸

因为容器中的隔离不如在虚拟机中那么强，所以你应该假设，如果攻击者攻破了一个容器，那么他就可以入侵该主机上的任何其他容器。

 

中毒的镜像

Docker 通过从仓库中拉取依赖项，使组装运行时堆栈变得容易。然而，这也很容易通过拉取过期镜像来引入漏洞，并且坏人也有可能在整个链路中引入恶意软件。Docker 和 Docker 社区提供诸如可信仓库和镜像扫描之类的工具来管理这些风险，但是需要正确地使用它们。


敏感信息泄露

容器需要秘钥来访问数据库和服务，这些秘钥需要得到保护。

 

您可以使用 CIS 准则和其他安全最佳实践以及 Docker Bench 等扫描工具锁定容器，还可以通过剥离运行时依赖项并确保开发人员不会将开发工具打包到生产容器中来最小化容器的攻击面。但所有这些都需要额外的工作和知道该做什么。没有一个是开箱即用的。

DevOps 中的职责分离


DevOps 给合规带来了一些挑战。职责分离（SoD）是其中最难解决的问题之一。

 

Ops 和开发之间的 SoD 旨在通过确保个人在未经批准或透明的情况下无法进行更改，从而降低欺诈风险并防止代价高昂的错误和内部攻击。职责分离是安全和治理框架（如ISO 27001、NIST800-53、COBIT和ITIL、SSAE 16评估以及SOX、GLBA、MiFID II和PCI DSS）中的基本控制措施。

 

审核员密切关注 SoD，以确保满足数据机密性和完整性的要求；未经授权的个人无法更改数据和配置；未经授权的个人无法查看机密和敏感数据。他们审查变更控制流程和审批流程，以确保没有任何一个人拥有对系统的变更的完全控制权，并且管理层在做出重大变更之前了解所有的变更，并且变更已经过适当的测试和审查以确保不违反监管要求。他们希望看到审计记录来确保这一切。

 

即使在没有特别要求 SoD 的合规环境中，也经常强制执行严格的隔离，以避免利益冲突或控制失败的出现。

 

通过打破孤岛并在开发和运维之间分担责任，DevOps 似乎与 SoD 存在直接冲突。允许开发人员在持续部署中将代码和配置变更推送到生产环境中，这给审计人员带来了危险信号。然而，正如我们将在第5章中看到的，只要有严格的自动化和手动管控和审计，这是可以做到的。

 

另一个有争议的问题是按照亚马逊的“谁构建，谁运行”（You build it, you run it）模型，授予开发人员访问生产系统的权限，以帮助支持（有时甚至帮助操作）他们编写的代码。在2009年的 Velocity 大会上，John Allspaw和Paul Hammond 提出了让开发人员访问或至少有限访问生产的有力观点：

 

Allspaw：“我相信运维人员应该确保开发人员无需经过操作就可以看到系统上发生的事情。。。


给某人（例如开发人员）一个只读 shell 帐户的风险很低。没有这个shell 解决问题时候就会很难。”

 

Hammond：“我们并不是说每个开发人员都应该有生产环境的 root 权限。”

 

开发人员对受监管系统的任何访问，即使是只读访问，都会给监管机构、合规性、信息安全和客户带来问题。要解决这些问题，你需要实施强有力的补偿控制：

 

  • 限制对非公开数据和配置的访问。

  • 仔细检查日志代码，确保日志不包含机密数据。

  • 审核和审查开发人员在生产中所做的一切：他们执行的每一条命令，他们查看的每一条数据。

  • 你需要进行变更控制检测，以跟踪在持续交付流程之外对代码或配置所做的任何更改。

  • 你可能还需要关注数据外泄：确保开发人员无法将数据从系统中取出。

 

这些都是很棘手的问题，但是可以解决。

 

例如，在 Etsy，即使在系统中受 PCI 规范的部分，开发人员也可以对指标仪表盘（Etsy称之为“dataporn”）和异常日志进行读取访问，以便帮助他们发现所编写代码中的问题。但是，对代码或配置的任何更改或修复都将通过其经过审核的持续部署工作流进行审查和执行。

变更控制


如果开发人员每天向生产环境推送10到50次变更，你如何证明所有变更都被管控？变更咨询委员会（CAB）在 DevOps 中如何运作？在开发人员将更改直接推向生产的环境中，如何以及何时进行更改控制和授权？如何证明管理层在部署这些更改之前就知道这些更改？

 

ITIL 变更管理和相关的文书工作和会议旨在处理很少发生的重大变化。重大变更需要你确定操作依赖关系，并了解操作风险以及如何减轻这些风险，因为不经常进行的大型复杂变更是有风险的。在 ITIL 中，较小的变更是例外，并按标准进行。

 

DevOps 通过针对小的和频繁的变更进行优化，将大的变更分解为小的增量变更，简化和自动化小变更的管理方式，从而逆转了这种变更管理方法。合规和风险管理需要改变来适应这一新的现实。
