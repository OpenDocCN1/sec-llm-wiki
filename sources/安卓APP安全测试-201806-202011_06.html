图书作者简介


Jim Bird 在金融服务技术领域拥有 20 多年的经验，历任软件开发经理、项目经理和CTO。他曾在 30 多个国家/地区的证券交易所、中央银行、票据交换所、证券监管机构和贸易公司工作。他目前是美国一家大型机构另类投资交易系统的首席技术官。

Jim 在敏捷和 DevOps 环境中工作了多年。早在 1990 年代初他在一家西海岸的技术公司就开始实践渐进式和迭代式（“循序渐进”）开发了，每月开发、测试和交付软件给世界各地的客户，但他当时并没有意识到这有多独特。Jim 活跃于 DevOps 和 AppSec 社区，是 OWASP 的贡献者，有时还担任 SANS 研究所的分析师。

Jim 还是 O'Reilly 的报告《  DevOps for Finance: Reducing Risk through Continuous Delivery》的作者。

DevOpsSec：通过持续交付来交付安全软件


介绍


DevOps 被硅谷及相关的企业供应商大肆宣传，并被一些人视为另一种时尚。另外一些人认为，DevOps 是一种真正的破坏力，正在从根本上改变我们设计、交付和运维的方式。

 

就像敏捷、测试驱动开发（TDD）和持续集成改变了我们编写代码以及管理项目和产品开发的方式一样，DevOps 、基础设施即代码和持续交付正在改变 IT 服务的交付和运维方式。正如 Scrum（迭代式增量软件开发过程）和 XP（极限编程）取代 CMMi （CapabilityMaturity Model Integration，即能力成熟度模型集成）和 Waterfall （瀑布模型）一样，DevOps 也将取代 ITIL（Information Technology Infrastructure Library）成为管理 IT 的首选方式。

 

DevOps 正在打破设计、开发人员与运维人员之间的组织孤岛。这些孤岛是由于 ITIL 和 COBIT（Control Objectives for Information and related Technology）而建立的，目的是提高管控和稳定性，但却妨碍了组织价值交付。


DevOps 没有尝试预先计划和设计所有内容，而是在进行持续实践，并使用实践中的数据来推动设计和流程改进。

 

DevOps 正在寻找更有效的方式来利用自动化的力量，利用可编程配置管理器和应用程序自动化发布等新工具来简化和扩展从设计到构建、部署和运维的一切，并利用云服务、虚拟化和容器来更快、更便宜地启动和运行系统。


持续交付、持续部署、精益启动、MVP（最小可行产品），使用 Ansible、Chef、Puppet 等工具进行代码驱动的配置管理，云中的 NoOps，以及使用 Docker、Vagrant、Terraform的快速自助系统打包和供应都在改变着 IT 中每个人对如何交付和管理系统的想法。而且，随着 DevOps 头部厂商利用这些想法超越竞争对手并进行创新，他们还改变了在线业务的游戏规则。


DevOps 头部厂商所取得的成功是令人信服的。Puppet Labs 的 2015 年 DevOps 现状报告显示：

  • 部署变更的频率是其他组织的30倍，交付时间短200倍。

  • 变更成功率高60倍。

  • 当出现问题时，恢复故障的速度快168倍。


要达到这些结果需要做些什么呢？而且，如何以一种不会损害安全性或合规性的方式来做到这一点，或者更好地以一种实际上可以改善安全性并强制执行合规性的方式来做到这一点？

 

作为一个非常关心系统安全性和可靠性的人，当我第一次听说 DevOps 时，我非常怀疑，如“每天做 50 次不可能的事情”一文所述（http://timothyfitz.com/2009/02/10/continuous-deployment-at-imvu-doing-the-impossible-fifty-times-a-day/）。里面关于如何“快速移动并打破规则”的内容太多了，而关于如何构建有效且可信赖系统的还不够。第一批成功案例来自在线游戏和社交媒体平台，这些平台与大企业面临的挑战或小企业的担忧完全不同。

 

对于“代码分支（branchingin code）”和“灰度发布（dark launching）”，或者开发人员拥有自己的代码并在生产中负责代码，我没有发现任何新的或令人兴奋的东西。这其中的大部分看起来像是向 25或30 年前的方式倒退了一步，即在 CMMi 和 ITIL 被投入到控制牛仔编码（cowboycoding）和生产环境中的黑客攻击之前。

 

但是，随着我对 DevOps 的深入研究，我发现了一些重要的、实质性的新想法和模式，它们可以为当前构建和运行系统的方式增加真正的价值：


基础设施即代码（Infrastructure as Code ）

通过代码来定义和管理系统配置，并使用 Chef 或 Puppet 等工具进行版本控制和测试，可以显著提高系统构建速度和大规模交付的效率。这种配置管理方法还为安全性提供了强大的优势：对详细配置信息的完全可见性，对配置漂移的控制，消除一次性的雪花异常，以及定义运行时安全策略并自动实施。


持续交付

使用持续集成和测试自动化来构建从开发到测试再到生产的流水线，它不仅提供了驱动变更的引擎，而且还为合规性和安全性提供了关键的控制设施，并提供了一种用来响应威胁的快速打补丁的路径。

 

持续监控与度量

这包括创建从生产回溯到工程、收集指标的反馈循环，并使每个人都可以看到它们，以了解系统的实际使用方式以及使用反馈数据来学习和改进。你可以将此扩展到安全性，以洞悉安全威胁并启用“攻击驱动防御”的机制。


从失败中学习

认识到失败总会发生的，通过混沌工程注入失败，在演练中练习失败，进行客观的事后复盘分析，并将其作为学习的机会。所有这些都会促使形成更具韧性的系统和组织。通过红队，可以建立一个更安全的系统和行之有效的应急响应能力。


关于DevOps

本文适合安全分析师、安全工程师、渗透测试工程师以及想要了解如何开展DevOps 中的安全性工作的管理者。同时也可以供 DevOps 工程师、开发人员、测试工程师以及对应的管理者来了解同样的事情。


你应该对应用程序和基础设施安全性有基本的了解，并且对 DevOps 和敏捷开发实践和工具（包括持续集成和持续交付）有所了解。有一些资源可以帮助你快速上手：


  • Gene Kim、 Kevin Behr 和 George Spafford 写的《The PhoenixProject》很好的介绍了为什么开展以及怎么开展 DevOps，并且很有趣味性。

  • 早在2009年2月，John Allspaw 和 Paul Hammond 就做了题为 “10+ Deploys per Day”的演讲，介绍了很多关于 DevOps 的想法

  • 而且，如果您想了解如何构建自己的持续交付流水线可以阅读 Jez Humble 和 DaveFarley 写的《Reliable SoftwareReleases through Build, Test, and Deployment Automation》


随着我与 Etsy 和 Netflix 等在 DevOps 方面取得成功的公司的员工交谈得越多，我越深入了解 ING、Nordstrom、Capital One 和 Inuit 等企业如何成功地采用 DevOps，我就越开始接受 DevOps。

 

并且，在我自己的组织中，我们在 DevOps 思想、工具和实践方面取得的成功越多，我就越能理解 DevOps 如何在正确操作的情况下，可以用来安全可靠地方式交付和运行系统。


无论你将其称为 SecDevOps，DevSecOps，DevOpsSec 还是 RuggedDevOps，这都是本文将探讨的内容。


我们将首先研究 DevOps 面临的安全性和合规性挑战。然后，我们将介绍安全 DevOps 的主要思想，以及如何实施关键的 DevOps 实践和工作流（例如，持续交付和基础设施即代码）来设计、构建、部署和运行安全系统。在第 4 章中，我们将把安全检查和控制映射到这些工作流程中。由于 DevOps 非常依赖自动化，因此我们将研究在此过程中可以使用的不同工具，着重介绍满足需求的开源工具，以及我使用过的、熟悉的或值得了解的新工具。最后，我们将探讨如何将合规融入到 DevOps 中，或在 DevOps 中建立合规性。
