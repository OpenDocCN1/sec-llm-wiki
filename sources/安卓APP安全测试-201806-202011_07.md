**CommandExecCheck.java**

```
@Rule(key = CommandExecCheck.RULE_KEY)public class CommandExecCheck extends AbstractMethodDetection {
    public static final String RULE_KEY = "CommandExecCheck";    public static final String MESSAGE = "请确保用户无法控制所要执行的命令";
    @Override    protected MethodMatchers getMethodInvocationMatchers() {        return MethodMatchers.or(                MethodMatchers.create()                    .ofTypes("java.lang.Runtime")                    .names("exec")                    .withAnyParameters()                    .build(),                MethodMatchers.create()                .ofTypes("java.lang.ProcessBuilder")                .names("start")                .withAnyParameters()                .build()        );    }
    @Override    protected void onMethodInvocationFound(MethodInvocationTree mit) {        super.onMethodInvocationFound(mit);        reportIssue(mit, MESSAGE);    }}
```

大概猜一下就应该明白检测原理了， 就是通过检测命令执行的方法是否被调用来判断是否需要报告漏洞。

 

CommandExecCheck 继承自 org.sonar.java.checks.methods.AbstractMethodDetection，并重写了 getMethodInvocationMatchers 和 onMethodInvocationFound方法。

 

getMethodInvocationMatchers 方法会返回调用方法的匹配规则，一旦规则命中就会调用 onMethodInvocationFound 方法进行处理。

 

首先，我们来看一下 getMethodInvocationMatchers 方法，里面用到了 MethodMatchers 类。MethodMatchers是sonar api 6.3 新增的工具类，用于通过 类型、方法名、参数 来匹配一个方法，大大降低了插件开发成本。

  

MethodMatchers 基本用法示例如下：

**1、匹配任意名为a或b，并且没有参数的方法**

*   
*   
*   
*   
*   

```
MethodMatchers.create()              .ofAnyType()              .names("a","b")              .addWithoutParametersMatcher()              .build();
```

 

**2、匹配A/A的子类中任意参数且名为a/b的方法，或者B/B的子类中任意参数且名为b/c的方法**

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
MethodMatchers.or(    MethodMatchers.create()                  .ofSubTypes("A")                  .names("a","b")                  .withAnyParameters()                  .build(),    MethodMatchers.create()                  .ofSubTypes("B")                  .names("b","c")                  .withAnyParameters()                  .build());
```

 

**3、匹配名为f的方法，且只有一个参数，参数类型为int或者long**

*   
*   
*   
*   
*   
*   

```
MethodMatchers.create()              .ofAnyType()              .names("f")              .addParametersMatcher("int")              .addParametersMatcher("long")              .build();
```

**4、匹配名为f的方法，且有一个参数为int或者有一个及以上参数且第一个参数为long**

*   
*   
*   
*   
*   
*   

```
MethodMatchers.create()              .ofAnyType()              .names("f")              .addParametersMatcher("int")              .addParametersMatcher(params->params.size()>=1&&params.get(0).is("long")              .build();
```

 

**5、匹配任意类型参数为int 任意 int 的方法**

*   
*   
*   
*   
*   

```
MethodMatchers.create()              .ofAnyType()              .anyName()              .addParametersMatcher("int",ANY,"int")              .build();
```

 

**6、匹配任意类型，方法名为a/b，且参数为int/long**

*   
*   
*   
*   
*   
*   

```
MethodMatchers.create()              .ofAnyType()              .names("a","b")              .addParametersMatcher("int")              .addParametersMatcher("long")              .build();
```

  

拿 Runtime.exec 来说，它的签名信息是： java.lang.Runtime#exec(java.lang.String)

我们就可以创建一个对应的MethodMatcher:

*   
*   
*   
*   
*   

```
MethodMatchers.create()              .ofTypes("java.lang.Runtime")              .names("exec")              .withAnyParameters()              .build()
```

**2、DES 弱加密漏洞**  
通过这个案例我们可以了解到如何获取并判断函数的参数值。  

## 漏洞原理

  

对称加密算法DES/3DES加密强度弱，容易被破解。

漏洞示例代码：

## 检测规则解读

  

抽象出漏洞模型是 要检测出代码中使用了 DES 算法，即Cipher.getInstance("DES/ECB/PKCS5Padding")

相比上一个漏洞，这里除了要匹配出方法本身，还要能够判断方法的参数是否包含 “DES”。

 

检测规则还是有3个文件

DESCheck.java （检测规则）

DESCheck\_java.html（检测规则描述）

DESCheck\_java.json（检测规则的元数据）

  

**DESCheck.java**

```
@Rule(key = DESCheck.RULE_KEY)public class DESCheck extends AbstractMethodDetection {
    public static final String RULE_KEY = "DESCheck";    private static final String MESSAGE = "禁止使用DES算法或3DES加密算法进行对称加密";
    @Override    protected MethodMatchers getMethodInvocationMatchers() {        return MethodMatchers.create()                .ofTypes("javax.crypto.Cipher")                .names("getInstance")                .withAnyParameters()                .build();    }
    @Override    protected void onMethodInvocationFound(MethodInvocationTree mit) {        ExpressionTree firstArgument = mit.arguments().get(0);        ExpressionTree defaultPropertyValue = JavaPropertiesHelper.retrievedPropertyDefaultValue(firstArgument);        ExpressionTree algorithmTree = defaultPropertyValue == null ? firstArgument : defaultPropertyValue;        String algorithmName = ExpressionsHelper.getConstantValueAsString(algorithmTree).value();        if (algorithmName != null && isInsecureDES(algorithmName)) {            reportIssue(firstArgument, MESSAGE);        }    }
    private static boolean isInsecureDES(String algorithmName) {        //Cipher.getInstance("DES");Cipher.getInstance("DESede")        return algorithmName.startsWith("DES");                  }}
```

我们发现Cipher的getInstance有3个重载的方法：

![](../Images/f2b4df17d0a6ac51e00ed5a3b787192a.png)

  

因为第一个参数是加密算法的名称，于是 MethodMatchers 就只是匹配类和方法名就好了。

 

然后可以通过ExpressionsHelper类的getConstantValueAsString方法取出第一个参数的值，并且这个方法支持常量传递。如

Cipher.getInstance(DES\_CIPHER\_ALGORITHM) 而DES\_CIPHER\_ALGORITHM的值为"DES/ECB/PKCS5Padding"。

 

同时 ExpressionsHelper 类还提供了获取布尔类型参数值的方法getConstantValueAsBoolean。

这两个方法在判断方法参数值时候非常有用。

 

后续的代码逻辑就很简单了，不再赘述。

DESCheck\_java.html 和 DESCheck\_java.json文件同上一个漏洞，大家自行修改内容适配就好了，不再赘述。

## 漏洞原理

  

若 WebView 中如果不设置 setAllowContentAccess 为 false，则可以通过 url访问 ContentProvider 中的内容。

漏洞示例代码：

![](../Images/2df5a7ea48f660d346b680f35d12cb5e.png)

## 检测规则解读

  

这是一个存在应用克隆漏洞的 webview 配置，不过大家先忽略。这里主要是展示没有显式设置 setAllowContentAccess 为 false，从而存在通过 url 访问ContentProvider 漏洞。

 

检测规则还是有3个文件

WebviewContentAccessCheck.java （检测规则）

WebviewContentAccessCheck\_java.html（检测规则描述）

WebviewContentAccessCheck\_java.json（检测规则的元数据）

  

**WebviewContentAccessCheck.java**

![](../Images/fef8f944f20876ecc15ee93a06cdaaf0.png)

这次我们不再继承 AbstractMethodDetection 类，而是选择继承 org.sonar.plugins.java.api.tree.BaseTreeVisitor 类。

BaseTreeVisitor 类可以用来遍历整个语法树，包括类、方法、变量、注解、Import 信息等等所有语法的内容。

 

因为漏洞文件中的代码是通过 webSettings 变量来进行设置的，所以选择了遍历变量的语法树。

当变量的类型是 “android.webkit.WebSettings” 时，去扫描整个文件的内容，判断是否显式设置 setAllowContentAccess 为false 或者直接将 setAllowContentAccess 为 true。

这里获取文件内容是通过 context.getFileLines() 来实现的。context 是 org.sonar.plugins.java.api.JavaFileScannerContext 类型的变量，通过它可以获取扫描文件的上下文信息，包括文件内容、工程、工作目录、语法树、语义模型等等，在规则编写中可以适当使用。代码结构如下：

**4、上一个案例的优化**  

规则三可能会存在漏报，聪明的你可以已经发现。

当同一个java文件中存在多处 webview，且任意一个设置了setAllowContentAccess 为 false，其他的未显式设置的会被漏报。

这里我们换一个检测思路：首先判断变量类型，接下来获取变量父方法，遍历父方法中是否有显示设置 setAllowContentAccess 为false，报告问题。

```
@Rule(key = WebviewContentAccessCheck.RULE_KEY)public class WebviewContentAccessCheck extends BaseTreeVisitor implements JavaFileScanner {
    private JavaFileScannerContext context;    public static final String RULE_KEY = "WebviewContentAccessCheck";    private static final String MESSAGE = "Webview中应尽量显式设置setAllowContentAccess为false";
    @Override    public void scanFile(final JavaFileScannerContext context) {        this.context = context;        scan(context.getTree());    }
    @Override    public void visitVariable(VariableTree tree) {
        super.visitVariable(tree);        if (tree.symbol().type().isSubtypeOf("android.webkit.WebSettings")) {            MethodInvocationVisitor methodInvocationVisitor = new MethodInvocationVisitor();            MethodTree enclosingMethod = getEnclosingMethod(tree);            enclosingMethod.accept(methodInvocationVisitor);            if (!methodInvocationVisitor.setAllowContentAccessFalse){                context.reportIssue(this, tree, MESSAGE);            }        }    }
    static MethodTree getEnclosingMethod(Tree tree) {        Tree result = tree.parent();        while (result != null && !result.is(Tree.Kind.METHOD, Tree.Kind.CONSTRUCTOR)) {            result = result.parent();        }        return (MethodTree) result;    }
    private static class MethodInvocationVisitor extends BaseTreeVisitor {
        private boolean setAllowContentAccessFalse = false;
        private static final MethodMatchers SET_Allow_Content_Access = MethodMatchers.create()                .ofSubTypes("android.webkit.WebSettings")                .names("setAllowContentAccess")                .withAnyParameters()                .build();
        @Override        public void visitMethodInvocation(MethodInvocationTree methodInvocation) {
            if (!SET_Allow_Content_Access.matches(methodInvocation)) {                return;            }
            ExpressionTree firstArgument = methodInvocation.arguments().get(0);
            ExpressionTree defaultPropertyValue = JavaPropertiesHelper.retrievedPropertyDefaultValue(firstArgument);            ExpressionTree algorithmTree = defaultPropertyValue == null ? firstArgument : defaultPropertyValue;            Boolean value = ExpressionsHelper.getConstantValueAsBoolean(algorithmTree).value();            if (false == value) {                setAllowContentAccessFalse = true;            }            super.visitMethodInvocation(methodInvocation);        }    }}
```

  

这里通过 getEnclosingMethod 来获取父方法，通过methodInvocationVisitor 来遍历父方法。MethodInvocationVisitor  代码如上，依然是继承 BaseTreeVisitor，并通过 MethodMatcher 来匹配是否有调用方法，通过 ExpressionsHelper 类的 getConstantValueAsString 方法来判断参数值。

优化的代码其实是上述三个案例的一个综合使用。
