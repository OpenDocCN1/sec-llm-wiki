Sonar 简介

在甲方安全建设过程中，源代码扫描是不可或缺的部分。使用商业产品还是自研各有利弊。自研的好处高度定制化，比较容易满足公司定制化安全基线的要求，同时容易融入到研发流程中。本文将介绍基于 Sonar 引擎的代码检测插件编写的基础知识。


Sonar（官网https://www.sonarqube.org/）是一个用于代码质量管理的开源平台，用于管理源代码的质量，当然也可以用于安全检测。其通过插件形式，可以支持包括 java,C#,C/C++,PL/SQL,Cobol,JavaScrip,Groovy，XML 等二十几种编程语言的代码质量管理与检测。


安卓代码检测主要涉及 Java 或 Kotlin、XML 语言，所以是可以使用 Sonar 进行检测的。Sonar 对于 Java 语言的检测是基于语法树和语义分析来进行的，存在天然的缺陷就是无法对变量的传递做污点跟踪，安全问题误报率会高一点。不过，对于静态代码扫描来说误报率一直是难以解决的问题，即使做了污点跟踪的产品也很难有效解决。相对于可高度定制化和开发简单的优点来说，并应用于 DevOps 这种快速迭代，每次做增量扫描的场景中时，误报率是完全可以接受的（增量扫描单次误报可能只是个位数）。

入门


要开发的规则将通过专用的自定义插件来承载，并依赖于SonarSource Analyzer的Java API。为了有效地工作，我们提供了一个空的maven    模板工程，你将在本教程中按照规则来填写。
 
通过https://github.com/SonarSource/sonar-custom-rules-examples/tree/master/java-custom-rules下载模板工程并导入到IDE中。
 
该项目已经包含自定义规则。我们的目标是增加一条额外的规则！

POM 文件

自定义插件是 Maven 工程，在深入研究代码之前，有必要注意一下自定义插件的几行配置信息。
 
在下面的代码片段中，请注意通过 properties 设置的插件 API 版本（<sonar.version>）。它与插件将支持的 SonarQube 的最低版本有关，并且通常需要与你公司的 SonarQube 实例保持一致。在此模板中，我们依赖版本8.2.0.32929（长期支持/LTS版本为 7.9，但是在打包插件时可以保证与最新版本的兼容性）。值得注意的是，JavaAnalyzer 的最新发行版始终与 SonarQube 的当前 LTS 版本兼容。
 
属性 <java.plugin.version> 定义了 SonarQube 实例中运行自定义插件所需的Java Analyzer 的最低版本。由于我们将依赖 Java 插件的 6.2.0.21135 版本，因此对应的 SonarQube 实例也需要 Java 插件的 6.2.0.21135 版本。
 
当前，先不要动这两个属性。
其他的属性，如 <groupId>, <artifactId>, <version>, <name> 和 <description> 可以随意修改。
<groupId>org.sonar.samples</groupId><artifactId>java-custom-rules</artifactId><version>1.0-SNAPSHOT</version><packaging>sonar-plugin</packaging> <properties>  <sonar.version>8.2.0.32929</sonar.version>  <java.plugin.version>6.2.0.21135</java.plugin.version></properties><name>Java Custom Rules - Template</name>

在下面的代码片段中，通过 sonar-packaging-maven 插件中的 <pluginClass> 来设置插件的入口类，注意使用 MyJavaRulesPlugin 的全类名。如果重构代码，重命名或移动 org.sonar.api.SonarPlugin 的扩展类，则必须更改此配置。属性 <sonarQubeMinVersion> 保证了与 LTS 7.9 的兼容性。

<plugin>  <groupId>org.sonarsource.sonar-packaging-maven-plugin</groupId>  <artifactId>sonar-packaging-maven-plugin</artifactId>  <version>1.17</version>  <extensions>true</extensions>  <configuration>    <pluginKey>java-custom</pluginKey>    <pluginName>Java Custom Rules</pluginName>    <pluginClass>org.sonar.samples.java.MyJavaRulesPlugin</pluginClass>    <sonarLintSupported>true</sonarLintSupported>    <sonarQubeMinVersion>7.9</sonarQubeMinVersion> <!-- allows to depend on API 8.x but still run on LTS 7.9 -->  </configuration></plugin>

编写规则


在本节中，我们将从头开始编写自定义规则。为此，我们将使用测试驱动开发（TDD）方法，首先依赖编写一些测试用例，然后再实施解决方案。
 
三个文件打造规则

编写规则时，至少要创建3个不同的文件：
1、测试文件，包含用作规则测试的 Java 代码
2、测试类，包含规则的单元测试
3、规则类，包含规则的实现

要创建我们的第一个自定义规则（通常称为“检测”），首先在模板项目中创建这3 个文件，如下所述：

1、在文件夹 /src/test/files 中，创建一个名为 MyFirstCustomCheck.java 的空文件，然后复制粘贴以下代码段的内容。
class MyClass {}
 2、在 /src/test/java 下的 org.sonar.samples.java.checks 包中，创建一个名为MyFirstCustomCheckTest 的测试类，然后复制并粘贴以下代码段的内容。
package org.sonar.samples.java.checks; import org.junit.Test; public class MyFirstCustomCheckTest {   @Test  public void test() {  } }
3、在 /src/main/java 下的 org.sonar.samples.java.checks 包中，创建一个名为 MyFirstCustomCheck 的新类，并继承自 Java Plugin API 提供的 org.sonar.plugins.java.api.IssuableSubscriptionVisitor 类。然后，将 nodesToVisit() 方法的内容替换成以下代码段中的内容。该文件将在实现规则时进行描述！
package org.sonar.samples.java.checks; import org.sonar.check.Rule;import org.sonar.plugins.java.api.IssuableSubscriptionVisitor;import org.sonar.plugins.java.api.tree.Tree.Kind;import java.util.Collections;import java.util.List; @Rule(key = "MyFirstCustomRule")public class MyFirstCustomCheck extends IssuableSubscriptionVisitor {   @Override  public List<Kind> nodesToVisit() {    return Collections.emptyList();  } }

更多文件...
如果上述3个文件是规则编写的基础，而在某些情况下可能需要额外的文件。例如，当规则使用参数时，或者如果其行为依赖于检测到的Java版本，则可能需要多个测试文件。也可以使用外部文件来描述规则元数据，例如html格式的描述。这种情况将在本文档的其他主题中进行描述。
正确的规范
当然，在更进一步之前，我们需要规则编写中的关键要素：规范！为了便于练习，让我们使用以下来自著名大师的引用来作为我们自定义规则的规范，因为它是绝对正确且无可辩驳的。
Gandalf - Why Program    When Magic Rulez (WPWMR, 第42页)
“对于具有单个参数的方法，其返回值和其参数的类型永远不能相同。”
覆盖检测规则的测试文件
因为我们选择了 TDD 方法，所以第一件事就是编写规则对应的代码示例。在测试文件中，我们考虑了规则在分析期间可能遇到的多种情况，并标记了插件规则需要引发问题的行。使用一个简单的 // Noncompliant 尾随注释来标记需要引发问题的代码行。为什么不合规？因为标记的行不符合规则。
不一定涵盖所有可能的情况，该文件的目标是涵盖分析期间可能遇到的所有情况，同时抽象不相关的细节。例如，在第一个规则的上下文中，方法的名称，其主体的内容以及方法的所有者不同都没有什么区别，并且不区分是抽象类，实体类还是接口。请注意，此样本文件在结构上应该正确，并且所有代码都应能编译通过。
在先前创建的测试文件 MyFirstCustomCheck.java 中，复制并粘贴以下代码：
class MyClass {  MyClass(MyClass mc) { }    int     foo1() { return 0; }  void    foo2(int value) { }  int     foo3(int value) { return 0; } // Noncompliant  Object  foo4(int value) { return null; }  MyClass foo5(MyClass value) {return null; } // Noncompliant    int     foo6(int value, String name) { return 0; }  int     foo7(int ... values) { return 0;}}

现在，测试文件包含以下测试用例：
 
  • 第2行：构造函数，用于区分普通方法；
  • 第4行：无参数的方法（foo1）;
  • 第5行：返回void）的方法（foo2；
  • 第6行：返回与其参数相同类型的方法（foo3），这将是不满足规则的；
  • 第7行：具有单个参数，但返回类型（foo4）不同的方法；
  • 第8行：另一个具有单个参数和相同返回类型的方法（foo5），但是参数为非原始类型，因此也不满足规则；
  • 第10行：具有多个参数的方法（foo6）；
  • 第11行：带有可变长参数的方法（foo7）；


测试类

测试文件更新后，让我们更新测试类来使用它，并将测试链接到我们的（尚未实现）规则。为此，回到我们的测试类 MyFirstCustomCheckTest，并更新 test() 方法，如下代码片段所示（你可能需要导入类 org.sonar.java.checks.verifier.JavaCheckVerifier）：
  @Test  public void test() {    JavaCheckVerifier.verify("src/test/files/MyFirstCustomCheck.java", new MyFirstCustomCheck());  }
你可能已经注意到，该测试类包含一个测试用例，其目的是验证我们将要实现的规则的行为。它依赖于使用 Java Plugin 规则测试API提供的 JavaCheckVerifier 类。JavaCheckVerifier 类提供了验证规则实现的实用方法，使我们可以完全抽象与 analyzer 初始化有关的所有机制。请注意，在验证规则时，验证程序将收集标记为 Noncompliant 的行，并验证规则是否引发了预期的问题以及仅引发了这些问题。

第一版：使用语法树和基础API

在开始实现规则之前，你需要了解一些背景知识。 
在运行任何规则之前，SonarQube JavaAnalyzer 会解析给定的 Java 代码文件并生成等效的数据结构：语法树。Java 语言的每种构造都可以用一种特定的语法树来表示，详细说明其每种特性。每一个构造都与特定的 Kind 以及明确描述其所有特性的接口相关联。例如，与方法声明关联的类型为 org.sonar.plugins.java.api.tree.Tree.Kind.METHOD，其接口由 org.sonar.plugins.java.api.tree.MethodTree 定义。https://github.com/SonarSource/sonar-java/blob/5.12.1.17771/java-frontend/src/main/java/org/sonar/plugins/java/api/tree/Tree.java#L47 列举了所有的类型。
创建规则类时，我们选择实现API中的 IssuableSubscriptionVisitor 类。该类在提供了一些引发问题的实用方法的基础上，还定义了在分析文件时将使用的策略。从名字上就能看出，它基于订阅机制，可以指定规则应处理哪种树。要覆盖的节点类型列表是通过 nodesToVisit() 方法指定的。在前面的步骤中，我们修改了该方法的实现以返回一个空列表，因此不订阅语法树的任何节点。
 
现在终于到了实现我们的第一条规则的时候了！回到 MyFirstCustomCheck 类，并修改 nodesToVisit() 方法返回的种类列表。由于我们的规则以方法声明为目标，因此我们只需要访问方法。为此，只需返回仅包含 Kind.METHOD 作为参数的 singletonList 即可，如下面的代码片段所示。
@Overridepublic List<Kind> nodesToVisit() {  return Collections.singletonList(Kind.METHOD);}

指定要访问的节点后，我们必须实现规则在处理方法声明时候的代码。为此，需要重写 IssableableSubscriptionVisitor 中从 SubscriptionVisitor 继承的方法 visitNode(Tree tree)。
@Overridepublic void visitNode(Tree tree) {}

因为我们注册了访问方法节点的规则，所以每次调用该方法时，参数 tree 都是org.sonar.plugins.java.api.tree.MethodTree（与 MEHOD 类型关联的接口树）类型。因此，第一步，我们可以安全地将 tree 直接转换为 MethodTree，如下所示。请注意，如果我们注册了多个节点类型，则必须在类型转换前使用 Tree.is（Kind ... kind）方法测试节点类型。
@Overridepublic void visitNode(Tree tree) {  MethodTree method = (MethodTree) tree;}
现在，我们先缩小规则范围，只检查方法是否具有单个参数，并在这种情况下引发问题。
@Overridepublic void visitNode(Tree tree) {  MethodTree method = (MethodTree) tree;  if (method.parameters().size() == 1) {    reportIssue(method.simpleName(), "Never do that!");  }}

IssableableSubscriptionVisitor 中的 reportIssue(Tree tree，String message) 方法允许使用特定消息在给定的树上报告问题。在本案例中，我们选择在精确的位置报告问题，即方法的名称。

IssuableSubscriptionVisitor 和 BaseTreeVisitor
实现此规则，我们选择使用 IssableableSubscriptionVisitor 作为规则的基础类。该visitor 提供了一种简便的方法来编写快速简单的规则，因为它使我们可以通过订阅规则来将检测规则聚焦到要访问的特定类型的树。但是，这种方法并不总是最佳方法。在某些情况下，API中提供的另一个  visitor 可能会很有用：org.sonar.plugins.java.api.tree.BaseTreeVisitor。BaseTreeVisitor 包含每种语法树专用的 visit() 方法，当必须微调文件的访问时特别有用。
在Java插件中已实现的规则中（https://github.com/SonarSource/sonar-java/tree/5.12.1.17771/java-checks/src/main/java/org/sonar/java/checks），你可以找到同时使用了两种方法的多个规则：将 IssableableSubscriptionVisitor 作为入口点，并通过 BaseTreeVisitor 来识别代码其他部分。
第二版：使用语义API
到目前为止，我们的规则实现仅依赖于语法树直接提供的数据，这些数据是通过解析代码产生的。但是，Java 的 SonarAnalyzer 提供了有关正在分析的代码的更多信息，因为它还构建了代码的语义模型。该语义模型提供与每个被操纵符号有关的信息。例如，对于方法而言，语义API将提供有用的数据，如方法的所有者，其用法，其参数的类型及其返回类型，它可能引发的异常等。不要犹豫，浏览 API 中的语义包吧（https://github.com/SonarSource/sonar-java/tree/5.12.1.17771/java-frontend/src/main/java/org/sonar/plugins/java/api/semantic），以便了解在分析过程中可以获取哪些信息！
但是现在，让我们回到实现并利用语义。
当知道方法只有一个参数后，让我们开始使用 MethodTree 中的 symbol() 方法获取方法的符号。
@Overridepublic void visitNode(Tree tree) {  MethodTree method = (MethodTree) tree;  if (method.parameters().size() == 1) {    MethodSymbol symbol = method.symbol();    reportIssue(method.simpleName(), "Never do that!");  }}
然后从符号中很容易地检索其第一个参数的类型以及返回类型（你可能必须导入org.sonar.plugins.java.api.semantic.Symbol.MethodSymbol 和 org.sonar. plugins.java.api.semantic.Type）。
@Overridepublic void visitNode(Tree tree) {  MethodTree method = (MethodTree) tree;  if (method.parameters().size() == 1) {    MethodSymbol symbol = method.symbol();    Type firstParameterType = symbol.parameterTypes().get(0);    Type returnType = symbol.returnType().type();    reportIssue(method.simpleName(), "Never do that!");  }}
由于该规则仅在这两种类型相同时才会引发问题，因此我们在引发问题之前通过Type 类提供的 is(String fullyQualifiedName) 方法来判断第一个参数类型与返回类型是否相同。
@Overridepublic void visitNode(Tree tree) {  MethodTree method = (MethodTree) tree;  if (method.parameters().size() == 1) {    MethodSymbol symbol = method.symbol();    Type firstParameterType = symbol.parameterTypes().get(0);    Type returnType = symbol.returnType().type();    if (returnType.is(firstParameterType.fullyQualifiedName())) {      reportIssue(method.simpleName(), "Never do that!");    }  }}

可以使用什么，不能使用什么
编写自定义 Java 规则时，只能使用 org.sonar.plugins.java.api 包中的类。
当从 SonarSource Analyzer for Java 浏览现有的 500 多个规则时，你会注意到某些其他实用程序类的使用，而不是API的一部分。虽然这些类有时在你的上下文中非常有用，但这些类在运行时不适用于自定义规则插件。这意味着，尽管构建插件时单元测试可以通过，但是规则很可能在分析时使分析崩溃。

好的，到这里你可能会很高兴，因为我们的第一条规则正在按预期运行...但是，我们尚未真正完成。在对任何实际项目使用规则之前，我们必须在定制插件中进行注册。
 
规则元数据

首先要做的是向我们的规则提供所有元数据，从而能够在 SonarQube 平台中正确注册它。为此，请在 MyFirstCustomCheck 类规则中添加 org.sonar.check.Rule 注解，并提供 key、name、description 和可选的 tags，如以下代码片段所示。
@Rule(  key = "MyFirstCustomCheck",  name = "Return type and parameter of a method should not be the same",  description = "For a method having a single parameter, the types of its return value and its parameter should never be the same.",  priority = Priority.CRITICAL,  tags = {"bug"})public class MyFirstCustomCheck extends IssuableSubscriptionVisitor {  // ...} 
规则激活

第二件事是激活插件中的规则。为此，请打开类 RuleList(org.sonar.samples.java.RulesList)。在此类中，有方法 getJavaChecks() 和getJavaTestChecks()。这些方法用于将我们的规则与此 Java 插件的规则一起注册。请注意，在 getJavaChecks() 中注册的规则将仅针对源文件生效，而在getJavaTestChecks() 中注册的规则仅对测试文件生效。要注册规则，只需将规则类添加到列表构建器中，如以下代码片段所示：
public static List<Class<? extends JavaCheck>> getJavaChecks() {  return Collections.unmodifiableList(Arrays.asList(      // other rules...      MyFirstCustomCheck.class    ));}

规则注册

由于规则依赖于 SonarSourceAnalyzer for Java API，所以还需要告诉父 Java插件去检索一些新规则。如果你使用自定义插件模板作为本教程的基础，则应该已经完成了所有工作，可以随意看看作为连接桥梁的 MyJavaFileCheckRegistrar.java 类。最后，确保在插件定义类（MyJavaRulesPlugin.java）中正确将注册类添加为了自定义插件的扩展。
