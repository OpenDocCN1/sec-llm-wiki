**Sonar 简介**  

在甲方安全建设过程中，源代码扫描是不可或缺的部分。使用商业产品还是自研各有利弊。自研的好处高度定制化，比较容易满足公司定制化安全基线的要求，同时容易融入到研发流程中。本文将介绍基于 Sonar 引擎的代码检测插件编写的基础知识。

  

Sonar（官网https://www.sonarqube.org/）是一个用于代码质量管理的开源平台，用于管理源代码的质量，当然也可以用于安全检测。其通过插件形式，可以支持包括 java,C#,C/C++,PL/SQL,Cobol,JavaScrip,Groovy，XML 等二十几种编程语言的代码质量管理与检测。

  

安卓代码检测主要涉及 Java 或 Kotlin、XML 语言，所以是可以使用 Sonar 进行检测的。Sonar 对于 Java 语言的检测是基于语法树和语义分析来进行的，存在天然的缺陷就是无法对变量的传递做污点跟踪，安全问题误报率会高一点。不过，对于静态代码扫描来说误报率一直是难以解决的问题，即使做了污点跟踪的产品也很难有效解决。相对于可高度定制化和开发简单的优点来说，并应用于 DevOps 这种快速迭代，每次做增量扫描的场景中时，误报率是完全可以接受的（增量扫描单次误报可能只是个位数）。

## 编写规则

在本节中，我们将从头开始编写自定义规则。为此，我们将使用测试驱动开发（TDD）方法，首先依赖编写一些测试用例，然后再实施解决方案。 **三个文件打造规则**  
编写规则时，至少要创建3个不同的文件：1、测试文件，包含用作规则测试的 Java 代码2、测试类，包含规则的单元测试3、规则类，包含规则的实现  
要创建我们的第一个自定义规则（通常称为“检测”），首先在模板项目中创建这3 个文件，如下所述：  
1、在文件夹 /src/test/files 中，创建一个名为 MyFirstCustomCheck.java 的空文件，然后复制粘贴以下代码段的内容。

*   
*   

```
class MyClass {}
```

 2、在 /src/test/java 下的 org.sonar.samples.java.checks 包中，创建一个名为MyFirstCustomCheckTest 的测试类，然后复制并粘贴以下代码段的内容。

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
package org.sonar.samples.java.checks; import org.junit.Test; public class MyFirstCustomCheckTest {   @Test  public void test() {  } }
```

3、在 /src/main/java 下的 org.sonar.samples.java.checks 包中，创建一个名为 MyFirstCustomCheck 的新类，并继承自 Java Plugin API 提供的 org.sonar.plugins.java.api.IssuableSubscriptionVisitor 类。然后，将 nodesToVisit() 方法的内容替换成以下代码段中的内容。该文件将在实现规则时进行描述！


  
***更多文件...****如果上述3个文件是规则编写的基础，而在某些情况下可能需要额外的文件。例如，当规则使用参数时，或者如果其行为依赖于检测到的Java版本，则可能需要多个测试文件。也可以使用外部文件来描述规则元数据，例如html格式的描述。这种情况将在本文档的其他主题中进行描述。***正确的规范**  
当然，在更进一步之前，我们需要规则编写中的关键要素：规范！为了便于练习，让我们使用以下来自著名大师的引用来作为我们自定义规则的规范，因为它是绝对正确且无可辩驳的。*Gandalf - Why Program    When Magic Rulez (WPWMR, 第42页)*“对于具有单个参数的方法，其返回值和其参数的类型永远不能相同。”**覆盖检测规则的测试文件**因为我们选择了 TDD 方法，所以第一件事就是编写规则对应的代码示例。在测试文件中，我们考虑了规则在分析期间可能遇到的多种情况，并标记了插件规则需要引发问题的行。使用一个简单的 // Noncompliant 尾随注释来标记需要引发问题的代码行。为什么不合规？因为标记的行不符合规则。不一定涵盖所有可能的情况，该文件的目标是涵盖分析期间可能遇到的所有情况，同时抽象不相关的细节。例如，在第一个规则的上下文中，方法的名称，其主体的内容以及方法的所有者不同都没有什么区别，并且不区分是抽象类，实体类还是接口。请注意，此样本文件在结构上应该正确，并且所有代码都应能编译通过。在先前创建的测试文件 MyFirstCustomCheck.java 中，复制并粘贴以下代码：

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
class MyClass {  MyClass(MyClass mc) { }    int     foo1() { return 0; }  void    foo2(int value) { }  int     foo3(int value) { return 0; } // Noncompliant  Object  foo4(int value) { return null; }  MyClass foo5(MyClass value) {return null; } // Noncompliant    int     foo6(int value, String name) { return 0; }  int     foo7(int ... values) { return 0;}}
```

  
现在，测试文件包含以下测试用例： 

*   第2行：构造函数，用于区分普通方法；
*   第4行：无参数的方法（foo1）;
*   第5行：返回void）的方法（foo2；
*   第6行：返回与其参数相同类型的方法（foo3），这将是不满足规则的；
*   第7行：具有单个参数，但返回类型（foo4）不同的方法；
*   第8行：另一个具有单个参数和相同返回类型的方法（foo5），但是参数为非原始类型，因此也不满足规则；
*   第10行：具有多个参数的方法（foo6）；
*   第11行：带有可变长参数的方法（foo7）；

**第一版：使用语法树和基础API**  
在开始实现规则之前，你需要了解一些背景知识。 在运行任何规则之前，SonarQube JavaAnalyzer 会解析给定的 Java 代码文件并生成等效的数据结构：语法树。Java 语言的每种构造都可以用一种特定的语法树来表示，详细说明其每种特性。每一个构造都与特定的 Kind 以及明确描述其所有特性的接口相关联。例如，与方法声明关联的类型为 org.sonar.plugins.java.api.tree.Tree.Kind.METHOD，其接口由 org.sonar.plugins.java.api.tree.MethodTree 定义。https://github.com/SonarSource/sonar-java/blob/5.12.1.17771/java-frontend/src/main/java/org/sonar/plugins/java/api/tree/Tree.java#L47 列举了所有的类型。创建规则类时，我们选择实现API中的 IssuableSubscriptionVisitor 类。该类在提供了一些引发问题的实用方法的基础上，还定义了在分析文件时将使用的策略。从名字上就能看出，它基于订阅机制，可以指定规则应处理哪种树。要覆盖的节点类型列表是通过 nodesToVisit() 方法指定的。在前面的步骤中，我们修改了该方法的实现以返回一个空列表，因此不订阅语法树的任何节点。 现在终于到了实现我们的第一条规则的时候了！回到 MyFirstCustomCheck 类，并修改 nodesToVisit() 方法返回的种类列表。由于我们的规则以方法声明为目标，因此我们只需要访问方法。为此，只需返回仅包含 Kind.METHOD 作为参数的 singletonList 即可，如下面的代码片段所示。

*   
*   
*   
*   

```
@Overridepublic List<Kind> nodesToVisit() {  return Collections.singletonList(Kind.METHOD);}
```

  
指定要访问的节点后，我们必须实现规则在处理方法声明时候的代码。为此，需要重写 IssableableSubscriptionVisitor 中从 SubscriptionVisitor 继承的方法 visitNode(Tree tree)。

*   
*   
*   

```
@Overridepublic void visitNode(Tree tree) {}
```

  
因为我们注册了访问方法节点的规则，所以每次调用该方法时，参数 tree 都是org.sonar.plugins.java.api.tree.MethodTree（与 MEHOD 类型关联的接口树）类型。因此，第一步，我们可以安全地将 tree 直接转换为 MethodTree，如下所示。请注意，如果我们注册了多个节点类型，则必须在类型转换前使用 Tree.is（Kind ... kind）方法测试节点类型。

*   
*   
*   
*   

```
@Overridepublic void visitNode(Tree tree) {  MethodTree method = (MethodTree) tree;}
```

现在，我们先缩小规则范围，只检查方法是否具有单个参数，并在这种情况下引发问题。  

*   
*   
*   
*   
*   
*   
*   

```
@Overridepublic void visitNode(Tree tree) {  MethodTree method = (MethodTree) tree;  if (method.parameters().size() == 1) {    reportIssue(method.simpleName(), "Never do that!");  }}
```

  
IssableableSubscriptionVisitor 中的 reportIssue(Tree tree，String message) 方法允许使用特定消息在给定的树上报告问题。在本案例中，我们选择在精确的位置报告问题，即方法的名称。现在，再次执行 MyFirstCustomCheckTest.test() 来测试我们的实现。

当然，我们的测试再次失败了... JavaCheckVerifier报告说，第5、7和11行引发了意外的问题，如上面的堆栈跟踪所示。通过查看我们的测试文件，很容易发现引发问题的第5行是错误的，因为方法的返回类型为void，第7行是错误的，因为Object与int不同，第11行也是错误的由于方法有可变参数。但是，根据我们的实现，引发这些问题是正确的，因为我们没有检查参数的类型和返回类型。但是，要处理类型，我们仅使用语法树知识是无法实现的。这次，我们将需要使用语义API！  
*IssuableSubscriptionVisitor 和 BaseTreeVisitor**实现此规则，我们选择使用 **IssableableSubscriptionVisitor** 作为规则的基础类。该**visitor** 提供了一种简便的方法来编写快速简单的规则，因为它使我们可以通过订阅规则来将检测规则聚焦到要访问的特定类型的树。但是，这种方法并不总是最佳方法。在某些情况下，API中提供的另一个  **visitor** 可能会很有用：**org.sonar.plugins.java.api.tree.BaseTreeVisitor**。**BaseTreeVisitor** 包含每种语法树专用的 **visit()** 方法，当必须微调文件的访问时特别有用。**在Java插件中已实现的规则中（https://github.com/SonarSource/sonar-java/tree/5.12.1.17771/java-checks/src/main/java/org/sonar/java/checks），你可以找到同时使用了两种方法的多个规则：将 **IssableableSubscriptionVisitor** 作为入口点，并通过 **BaseTreeVisitor** 来识别代码其他部分。***第二版：使用语义API**到目前为止，我们的规则实现仅依赖于语法树直接提供的数据，这些数据是通过解析代码产生的。但是，Java 的 SonarAnalyzer 提供了有关正在分析的代码的更多信息，因为它还构建了代码的语义模型。该语义模型提供与每个被操纵符号有关的信息。例如，对于方法而言，语义API将提供有用的数据，如方法的所有者，其用法，其参数的类型及其返回类型，它可能引发的异常等。不要犹豫，浏览 API 中的语义包吧（https://github.com/SonarSource/sonar-java/tree/5.12.1.17771/java-frontend/src/main/java/org/sonar/plugins/java/api/semantic），以便了解在分析过程中可以获取哪些信息！但是现在，让我们回到实现并利用语义。当知道方法只有一个参数后，让我们开始使用 MethodTree 中的 symbol() 方法获取方法的符号。

*   
*   
*   
*   
*   
*   
*   
*   

```
@Overridepublic void visitNode(Tree tree) {  MethodTree method = (MethodTree) tree;  if (method.parameters().size() == 1) {    MethodSymbol symbol = method.symbol();    reportIssue(method.simpleName(), "Never do that!");  }}
```

然后从符号中很容易地检索其第一个参数的类型以及返回类型（你可能必须导入org.sonar.plugins.java.api.semantic.Symbol.MethodSymbol 和 org.sonar. plugins.java.api.semantic.Type）。

*   
*   
*   
*   
*   
*   
*   
*

```
@Overridepublic void visitNode(Tree tree) {  MethodTree method = (MethodTree) tree;  if (method.parameters().size() == 1) {    MethodSymbol symbol = method.symbol();    Type firstParameterType = symbol.parameterTypes().get(0);    Type returnType = symbol.returnType().type();    reportIssue(method.simpleName(), "Never do that!");  }}
```

由于该规则仅在这两种类型相同时才会引发问题，因此我们在引发问题之前通过Type 类提供的 is(String fullyQualifiedName) 方法来判断第一个参数类型与返回类型是否相同。

```
@Overridepublic void visitNode(Tree tree) {  MethodTree method = (MethodTree) tree;  if (method.parameters().size() == 1) {    MethodSymbol symbol = method.symbol();    Type firstParameterType = symbol.parameterTypes().get(0);    Type returnType = symbol.returnType().type();    if (returnType.is(firstParameterType.fullyQualifiedName())) {      reportIssue(method.simpleName(), "Never do that!");    }  }}
```
