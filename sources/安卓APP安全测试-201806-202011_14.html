在《移动 APP 的加密技术》一文中，我们介绍了通用的加密最佳实践，并描述了在移动应用程序中错误使用加密技术时可能出现的典型漏洞。在本章中，我们将详细介绍 Android 的加密 API。我们将展示如何在源代码中识别这些 API 的使用以及解释相关配置的含义。做代码审计时，可以将使用的加密参数与本文中当前最佳实践进行比较。


验证加密标准算法的配置


概述


Android 加密 API 是基于 Java 加密体系结构 (JCA) 的。JCA 将接口和实现分开，从而使得加密算法可以有多个不同的安全提供商来实现。大部分的 JCA 接口和类都在 java.security.* 和 javax.crypto.* 包中定义。此外，还有 Android 特有的包 android.security.* 和 android.security.keystore.*。


Android 中包含的加密算法提供商列表因 Android 版本和 OEM 版本而异。 现在已知旧版本中的某些提供程序实现是不太安全的或者说是易受攻击的。 因此，Android 应用程序不仅应该选择正确的算法并使用良好的配置，在某些情况下，它们还应该关注传统提供程序中加密算法的实现强度。


可以通过以下代码来枚举加密算法提供商：

StringBuilder builder = new StringBuilder();
for (Provider provider : Security.getProviders()) {
    builder.append("provider: ")
           .append(provider.getName())
           .append(" ")
           .append(provider.getVersion())
           .append("(")
           .append(provider.getInfo())
           .append(")\n");
}
String providers = builder.toString();
//以下是在 android 8 模拟器下获取的结果.
provider: AndroidNSSP 1.0(Android Network Security Policy Provider) 
provider: AndroidOpenSSL 1.0(Android's OpenSSL-backed security provider) 
provider: CertPathProvider 1.0(Provider of CertPathBuilder and CertPathVerifier) 
provider: AndroidKeyStoreBCWorkaround 1.0(Android KeyStore security provider to work around Bouncy Castle) 
provider: BC 1.56(BouncyCastle Security Provider v1.56) 
provider: HarmonyJSSE 1.0(Harmony JSSE Provider) 
provider: AndroidKeyStore 1.0(Android KeyStore security provider)


如下是使用 Google Play API 并运行 Android 4.4 的模拟器中的输出结果：

provider: GmsCore_OpenSSL1.0 (Android's OpenSSL-backed security provider)
provider: AndroidOpenSSL1.0 (Android's OpenSSL-backed security provider)
provider: DRLCertFactory1.0 (ASN.1, DER, PkiPath, PKCS7)
provider: BC1.49 (BouncyCastle Security Provider v1.49)
provider: Crypto1.0 (HARMONY (SHA1 digest; SecureRandom; SHA1withDSA signature))
provider: HarmonyJSSE1.0 (Harmony JSSE Provider)
provider: AndroidKeyStore1.0 (Android AndroidKeyStore security provider)

对于某些支持旧版 Android 的应用程序（例如：仅使用 Android Nougat 之前版本的），打包最新的库可能是唯一的选择。这种情况下通常会选择 Spongy Castle（Bouncy Castle的重打包版本）。之所以重新打包，是因为 Android SDK 中包含了 Bouncy Castle。Spongy Castle 的最新版本会修复包含在 Android 早期版本中的 Bouncy Castle 中遇到的问题。请注意，Android 的 Bouncy Castle 库往往不是 Bouncy Castle 的完整版。最后：请记住，打包 Spongy Castle 等大型库通常会导致 Android 应用程序出现多个 dex 文件。


Andorid SDK 经历了以下更改：

  • 对于Android Nougat（7.0）及更高版本，Android 开发者博客显示：

  • 建议停止指定安全提供者，并始终使用打过修补的安全提供者。

  • Crypto 提供者的支持力度已经下降，并且不推荐使用该提供者。

  • 安全随机不再支持使用 SHA1PRNG，而是运行时提供 OpenSSLRandom 的实例。


  • 对于 Android Oreo（8.1）及更高版本，开发者文档显示：

  • Conscrypt，即 AndroidOpenSSL，推荐优先级高于 Bouncy Castle。并且它实现了以下新的内容，AlgorithmParameters：GCM、KeyGenerator：AES、KeyGenerator：DESEDE、KeyGenerator：HMACMD5、KeyGenerator：HMACSHA1、KeyGenerator：HMACSHA224、KeyGenerator：HMACSHA256、KeyGenerator：HMACSHA384，、KeyGenerator：HMACSHA512、SecretKeyFactory：DESEDE和 Signature：NONEWITHECDSA。

  • GCM 模式时，不应再使用 IvParameterSpec.class，而是使用 GCMParameterSpec.class。

  • 套接字已从 OpenSSLSocketImpl 更改为 ConscryptFileDescriptorSocket 和 ConscryptEngineSocket。

  • 带有 null 参数的 SSLSession 会产生 NullPointerException 异常。

  • 需要有足够大的数组作为 inputbytes 来生成密钥，否则抛出 InvalidKeySpecException 异常。

  • 如果 Socket 读取被中断，则会出现 SocketException 异常。


  • 对于 Android Pie（9.0）及更高版本，Android 开发者博客显示了更激进的更改：

  • 如果仍然使用 getInstance() 方法指定提供者，当 Target API 为 P 以下时会出现警告，如果 Target API 为 P 或者更高，则直接出现错误。

  • 删除了 Crypto 提供者，调用它将导致 NoSuchProviderException 异常。

Android SDK 提供了指定安全密钥的生成和使用机制。 Android 6.0（Marshmallow，API 23）引入了 KeyGenParameterSpec 类，可用于确保应用程序中的密钥的正确使用。


以下是在 API 23+ 上使用 AES/CBC/PKCS7Padding 的示例：

String keyAlias = "MySecretKey";

KeyGenParameterSpec keyGenParameterSpec = new KeyGenParameterSpec.Builder(keyAlias,
        KeyProperties.PURPOSE_ENCRYPT | KeyProperties.PURPOSE_DECRYPT)
        .setBlockModes(KeyProperties.BLOCK_MODE_CBC)
        .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_PKCS7)
        .setRandomizedEncryptionRequired(true)
        .build();

KeyGenerator keyGenerator = KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore");
keyGenerator.init(keyGenParameterSpec);

SecretKey secretKey = keyGenerator.generateKey();

KeyGenParameterSpec 指明密钥可用于加密和解密，但不用于其他目的，例如签名或验证。 它进一步指定了块模式（CBC），填充（PKCS＃7），并明确指定需要随机加密（这是默认值。）“AndroidKeyStore” 是此示例中使用的加密服务提供者的名称。这将自动确保密钥存储在 AndroidKeyStore 中以保护密钥。


GCM 是另一种 AES 块模式，与其他较旧的模式相比，它提供了额外的安全特性。除了在加密方面更安全之外，它还提供身份验证。使用 CBC 和其他模式时，需要使用 HMAC 单独执行身份验证。 注意，GCM 是唯一不支持填充的 AES 模式。


尝试违反上述规范使用生成的密钥将导致安全异常。

以下是使用该密钥加密的示例：

String AES_MODE = KeyProperties.KEY_ALGORITHM_AES
        + "/" + KeyProperties.BLOCK_MODE_CBC
        + "/" + KeyProperties.ENCRYPTION_PADDING_PKCS7;
KeyStore AndroidKeyStore = AndroidKeyStore.getInstance("AndroidKeyStore");

// byte[] input
Key key = AndroidKeyStore.getKey(keyAlias, null);

Cipher cipher = Cipher.getInstance(AES_MODE);
cipher.init(Cipher.ENCRYPT_MODE, key);

byte[] encryptedBytes = cipher.doFinal(input);
byte[] iv = cipher.getIV();
// save both the IV and the encryptedBytes


需要保存 IV（初始化向量）和加密字节，否则无法解密。


以下是密文的解密方式。输入是加密的字节数组，iv 是加密步骤的初始化向量：

// byte[] input
// byte[] iv
Key key = AndroidKeyStore.getKey(AES_KEY_ALIAS, null);
Cipher cipher = Cipher.getInstance(AES_MODE);
IvParameterSpec params = new IvParameterSpec(iv);
cipher.init(Cipher.DECRYPT_MODE, key, params);
byte[] result = cipher.doFinal(input);

由于每次都会随机生成 IV，因此应将其与密文（encryptedBytes）一起保存，以便后续解密。


Android 系统在 6.0 之前是不支持 AES 密钥生成的。 因此，许多实现选择使用 RSA 并使用 KeyPairGeneratorSpec 生成公私钥对进行非对称加密，或使用 SecureRandom 生成 AES 密钥。


以下是使用 KeyPairGenerator 和 KeyPairGeneratorSpec 来创建 RSA 密钥对的示例：

Date startDate = Calendar.getInstance().getTime();
Calendar endCalendar = Calendar.getInstance();
endCalendar.add(Calendar.YEAR, 1);
Date endDate = endCalendar.getTime();
KeyPairGeneratorSpec keyPairGeneratorSpec = new KeyPairGeneratorSpec.Builder(context)
        .setAlias(RSA_KEY_ALIAS)
        .setKeySize(4096)
        .setSubject(new X500Principal("CN=" + RSA_KEY_ALIAS))
        .setSerialNumber(BigInteger.ONE)
        .setStartDate(startDate)
        .setEndDate(endDate)
        .build();
KeyPairGenerator keyPairGenerator = KeyPairGenerator.getInstance("RSA",
        "AndroidKeyStore");
keyPairGenerator.initialize(keyPairGeneratorSpec);
KeyPair keyPair = keyPairGenerator.generateKeyPair();

此示例创建密钥大小为 4096 位（即模数大小）的RSA密钥对。


注意：人们普遍错误地认为应该使用 NDK 来隐藏加密操作和硬编码密钥。但是，使用这种机制是无效的。攻击者仍然可以使用工具来查找使用的机制并找出在内存中密钥。接下来，可以用 IDA(pro) 来分析控制流程。如 Android 开发者博客中所述，从 Android Nougat 开始，不允许使用私有 API，而是需要调用公共 API，这进一步降低了隐藏密钥的有效性。

测试随机数生成


概述


密码学需要安全的伪随机数生成（PRNG）。标准 Java 类不能提供足够的随机性，实际上可能使攻击者猜测出下一个将生成的值，并使用此猜测来模拟其他用户或者访问敏感信息。


通常，应使用 SecureRandom 类。 如果要支持 KitKat 以下的 Android 版本，则需要额外注意要解决 Jelly Bean（Android 4.1-4.3）版本中无法正确初始化 PRNG 的 bug。


多数时候开发人员应该通过无参数的默认构造函数实例化 SecureRandom。其他构造函数用于更高级的用途，如果使用不当，可能会导致随机性和安全性降低。 支持 SecureRandom 的 PRNG 提供程序默认使用 /dev/urandom 设备文件作为随机源。


静态分析


识别随机数生成器的所有实例，并查找自定义或已知的不安全 java.util.Random 类。该类为每个给定的种子值生成相同的数字序列。因此，数字序列是可预测的。


以下是弱随机数生成的代码示例：

import java.util.Random;// ...


Random number = new Random(123L);
//...

for (int i = 0; i < 20; i++) {
  // Generate another random integer in the range [0, 20]
  int n = number.nextInt(21);
  System.out.println(n);
}

相反，应该使用经过严格审查的算法，这些算法应该是目前被该领域的专家认为是健壮的，并且选择具有足够长度种子的经过良好测试的算法实现。


标识未使用默认构造函数创建的 SecureRandom 的所有实例。指定种子值会减少随机性。首选 SecureRandom 的无参数构造函数，它使用系统指定的种子值生成一个 128 字节长的随机数。


通常，如果 PRNG 被认为非加密安全（例如java.util.Random），那么它可能是统计PRNG，不应在安全敏感的上下文中使用。如果生成器已知并且可以猜测种子，则伪随机数生成器可以产生可预测的数字。使用 128 位种子是产生“足够随机”数字的良好起点。


以下是安全随机数生成的代码示例：

import java.security.SecureRandom;
import java.security.NoSuchAlgorithmException;

// ...
public static void main (String args[]) {
  SecureRandom number = new SecureRandom();
  // Generate 20 integers 0..20
  for (int i = 0; i < 20; i++) {    
      System.out.println(number.nextInt(21));
  }
}


动态分析


一旦攻击者知道使用了什么类型的弱伪随机数生成器（PRNG），很容易就可以编写基于先前观察到的随机值生成下一个随机值的 POC（参考针对 Java Random 的）。对于非常弱的自定义随机生成器，可以通过统计来发现生成模式。以上推荐的方法需要反编译 APK 并检查算法（参见静态分析）。 


如果你想测试随机性，你可以尝试捕获一大堆数字，通过 Burpsuite 的 sequencer 来看看随机性的质量。


测试密钥管理


概述


在本节中，我们将讨论存储加密密钥的不同方法以及如何测试它们。讨论生成和存储密钥材料最安全的方式和安全性较低的方式。


处理密钥材料最安全的方法就是永远不要将其存储在设备上。这意味着每次应用程序需要执行加密操作时，都要提示用户输入密码。虽然从用户体验的角度来看这不是理想的实现，但它是处理密钥材料最安全的方式。原因是密钥材料只有在使用时才在内存中的数组中出现。一旦不再需要密钥，就可以将数组清零。这最大限度地减少了攻击窗口。密钥材料不会接触文件系统，也不存储密码短语。需要注意的是，某些密码无法正确清理其字节数组。例如，BouncyCastle 中的 AES 算法并不总是清理其最新的工作密钥。另外，无法从堆中删除基于大数的密钥（例如私钥），也不会将其清零。最后，在尝试将密钥清零时要小心。请参阅“测试Android数据存储”一节，了解如何确保密钥的内容确实已清零。


通过使用基于密码的密钥导出功能版本2（PBKDF2），可以从密码短语生成对称加密密钥。 此加密协议旨在生成安全和非可爆破的密钥。 下面的代码清单说明了如何根据密码生成强加密密钥。

public static SecretKey generateStrongAESKey(char[] password, int keyLength)
{
    //Initiliaze objects and variables for later use
    int iterationCount = 10000;
    int saltLength     = keyLength / 8;
    SecureRandom random = new SecureRandom();    
    
    //Generate the salt
    byte[] salt = new byte[saltLength];
    random.nextBytes(salt);    
    
    KeySpec keySpec = new PBEKeySpec(password.toCharArray(), salt, iterationCount, keyLength);    
    SecretKeyFactory keyFactory = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA1");    
    byte[] keyBytes = keyFactory.generateSecret(keySpec).getEncoded();    
    return new SecretKeySpec(keyBytes, "AES");
}


上述方法需要一个包含密码和所需密钥长度的字符数组，例如 128 或 256 位 AES 密钥。定义了迭代计数为 10000，稍后用于 PBKDF2 算法。这显著增加了暴力破解攻击的工作量。将 salt 长度设置为等于密钥长度，除以 8 来处理位到字节的转换。然后使用 SecureRandom 类随机生成 salt。salt 应保持不变，以确保每次相同的密码会生成相同的加密密钥。注意，可以将 salt 以私有形式保存在 SharedPreferences 中。建议从 Android 备份机制中排除 salt，以防止在风险较高的数据情况下进行同步。请注意，如果您将 root设备或未打补丁的设备或 patched（例如重新打包）的应用程序作为对数据的威胁考虑在内，那么最好使用 AndroidKeystore 中的密钥对 slat 进行加密。然后，在 API 26 之前推荐使用 PBKDF2WithHmacSHA1 算法生成基于密码的加密（PBE）密钥，在 API 26 及之后最好使用 PBKDF2withHmacSHA256，两者的密钥长度不同。


现在来看很明显，定期提示用户输入密码并不适合每个应用程序。在这种情况下，请确保使用 Android KeyStore API。 此 API 专门用于为密钥材料提供安全存储。只有你的应用程序可以访问它生成的密钥。从 Android 6.0 开始，还强制要求 AndroidKeyStore 在存在指纹传感器的情况下提供硬件支持。这意味着会使用专用加密芯片或可信平台模块（TPM）来保护密钥材料。


值得注意的是，AndroidKeyStore API 在各种 Android 版本中都发生了显著的变化。在早期版本中，AndroidKeyStore API 仅支持存储公钥/私钥对（例如，RSA）。自 API 23 及之后才添加了对称密钥的支持。因此，当开发人员想要在不同的 Android API 级别上安全地存储对称密钥时，需要加以注意。为了安全地存储对称密钥，在 Android API 22 或更低级别的设备上，我们需要生成公钥/私钥对。使用公钥加密对称密钥，并将私钥存储在 AndroidKeyStore 中。加密的对称密钥可以安全地存储在 SharedPreferences 中。每当我们需要对称密钥时，应用程序从 AndroidKeyStore 检索私钥并解密对称密钥。当在 AndroidKeyStore 中生成并使用密钥并且KeyInfo.isinsideSecureHardware() 返回 true 时，不能 dump 密钥，也不能监视其加密操作。以下两种哪个会更安全目前是有争议的：使用PBKDF2withHmacSHA256 生成仍在可访问的可 dump 的内存中的密钥，或使用密钥可能永远不会进入内存的 AndroidKeyStore。使用 Android Pie，我们看到已经实现了额外的安全增强功能，以便将 TEE 与 AndroidKeyStore 分开，这使得使用 AndroidKeyStore 优于使用 PBKDF2withHmacSHA256。当然，后续对该主题还会进行更多测试和调查。


Android 提供的另一个 API 是 KeyChain，它提供对凭证存储中私钥及其相应证书链的访问，由于需要交互和密钥链的共享特性，通常不会使用它。更多详细信息，请参阅开发者文档。


一种不太安全的存储加密密钥的方式是将密钥存在 Android 的 SharedPreferences 中。 使用 MODE_PRIVATE 初始化 SharedPreferences 时，该文件只能由创建它的应用程序读取。但是，在 root 设备上，任何其他具有 root 访问权限的应用程序都可以读取其他应用程序的 SharedPreference 文件，无论是否使用了 MODE_PRIVATE。在这点上，AndroidKeyStore 是不同的。 由于 AndroidKeyStore 访问是在内核级别进行管理的，因此在AndroidKeyStore 没有清除或销毁密钥的情况下需要更多的工作和技能才能绕过限制进行访问。


还有三种方式：在源代码中使用硬编码加密密钥；使用基于稳定属性的可预测密钥派生函数；将生成的密钥存储在公共存储，如 /sdcard/。显然，硬编码加密密钥不是可行的方法，因为它意味着应用程序的每个实例都使用相同的加密密钥。攻击者只需要做一次从源代码中提取密钥（无论是原生代码中还是在 Java/Kotlin 代码中），就可以解密应用程序加密的任何数据。接着，当你使用基于其他应用程序可访问的标识符的可预测密钥派生函数时，攻击者只需找到 KDF 并将其应用于设备就可以找到密钥。最后，非常不鼓励将加密密钥存储在公共存储区，因为其他应用程序可以申请读取公共存储的读权限并窃取密钥。

做为示例，介绍一下如何定位硬编码密钥。首先，使用 Baksmali 工具将 DEX 文件反编译成 smali 字节码文件。

$ baksmali d file.apk -o smali_output/

有了 Smali 字节码文件后，就可以在文件中搜索 SecretKeySpec 类了。可以简单在得到的文件中递归搜索。请注意，Smali 中的类描述符以 "L" 开头，以 ";" 结尾。

$ grep -r "Ljavax\crypto\spec\SecretKeySpec;"

会高亮显示使用 SecretKeySpec 类的所有类，接下来检查所有突出显示的文件并跟踪用于传递密钥材料的字节。下图显示了某生产应用程序的检测结果。为了便于阅读，我们将 DEX 字节码反编译为 Java 代码。可以清楚地找到在静态字节数组 Encrypt.keyBytes 中初始化的硬编码加密密钥的使用。

当有权访问源代码时，应至少检查以下内容： 

  • 检查用于存储密钥的机制：优先选择 AndroidKeyStore 解决方案。 

  • 检查是否使用深度防御机制来确保使用TEE。例如：是否实施了暂时有效性？是否评估了代码中的硬件的安全使用情况？ 有关更多详细信息，请参阅 KeyInfo 文档。 

  • 如果是白盒加密解决方案：研究它们的有效性或咨询该领域的专家。
