移动 APP 的加密技术

本文主要翻译自 《OWASP Mobile Security Testing Guide》中的 Cryptography for Mobile Apps 章节，介绍移动 APP 的加密技术相关知识。


密码学在保护用户数据方面发挥着特别重要的作用，在移动手机环境中更是如此，因为在此环境中攻击者可能会物理接触用户的设备。 本章会概述与移动应用程序相关的加密概念和最佳实践。 这些最佳实践独适用于不同的移动操作系统。


1. 核心概念


密码学的目标是在即使面对攻击的时候提供持续的机密性、数据完整性和真实性。 机密性指通过使用加密来确保数据隐私。数据完整性则处理数据一致性以及检测数据的篡改。真实性确保数据来自可信来源。 


加密指将明文数据转换为隐藏原始内容的密文。解密指从密文恢复明文数据。 加密可以是对称的（秘密密钥加密）或非对称的（公钥加密）。通常加密操作不保护完整性，但某些对称加密模式也能达到保护完整性的目的。


对称密钥加密算法使用相同的密钥进行加密和解密。这种类型的加密很快并且适用于批量数据处理。由于每个有权访问密钥的人都能够解密加密的内容，因此对称密钥加密算法需要妥善保管密钥。公钥加密算法使用两个单独的密钥，公钥和私钥。公钥可以自由分发，而私钥不应与任何人共享。使用公钥加密的消息只能使用私钥解密。由于非对称加密比对称操作慢几倍，因此通常仅用于加密少量数据，例如用于批量加密的对称密钥。


散列不是一种加密形式，但确实使用了加密技术。散列函数确定性地将任意数据片段映射为固定长度值。从输入计算哈希很容易，但很难（即不可行）反推出哈希的原始输入。散列函数可用于完整性验证，但不提供真实性保证。


消息认证码（MAC）将其他加密机制（例如对称加密或散列）与密钥结合在一起，以提供完整性和真实性保护。然而，为了验证 MAC，多个实体必须共享相同的密钥，并且这些实体中的任何一个都可以生成有效的 MAC。HMAC 是最常用的 MAC 类型，它依赖于散列作为底层加密。HMAC 算法的全名通常包括底层哈希函数的类型（例如，HMAC-SHA256 使用 SHA-256 哈希函数）。


签名将非对称加密（即使用公钥/私钥对）与散列相结合，通过私钥加密消息的散列来提供完整性和真实性。与 MAC 不同，签名还提供不可否认属性，因为私钥与数据签名者一一对应。


密钥派生函数（KDF）从秘密值（例如密码）派生密钥，用于将密钥转换为其他格式或增加其长度。KDF 类似于散列函数，但也有其他用途（例如，它们用作多方密钥协商协议的组件）。KDF 除了与散列函数一样必须难以还原明文，还要求它们生成的密钥必须具有随机性。


2. 识别不安全、过时的加密算法


在评估移动应用程序时，应确保它不使用具有明显已知缺陷的加密算法和协议，且应满足现代安全要求。过去被认为是安全的算法可能会随着时间的推移变得不安全。因此，定期检查当前的最佳实践并相应地调整配置就显得非常重要。


验证加密算法是否是最新的并符合行业标准。易受攻击的算法包括过时的分组密码（例如DES 和 3DES），流密码（例如 RC4），散列函数（例如 MD5 和 SHA1）以及被攻破的随机数生成器（例如 Dual_EC_DRBG 和 SHA1PRNG）。需要注意，即使经过认证的算法（例如，NIST）也会随着时间的推移变得不安全，还是要定期验证算法的健壮性。 应该使用更安全的替代方案替换具有已知弱点的算法。


检查应用程序的源代码，识别已知较弱的加密算法实例，例如：

  • DES, 3DES

  • RC2

  • RC4

  • BLOWFISH

  • MD4

  • MD5

  • SHA1


在不同的移动平台上，加密算法 API 不尽相同:

  • 加密算法是最新的且符合行业标准，就要求但不限于：不能使用过时的分组密码（例如 DES），流密码（例如 RC4），以及散列函数（例如 MD5）和被攻破的随机数发生器如 Dual_EC_DRBG（即使它们是 NIST 认证的）；所有这些都应标记为不安全，且不应在应用程序和服务器中使用。

  • 密钥长度符合行业标准，并提供足够长时间的保护。可以在线去获得根据摩尔定律计算出来的不同密钥长度所需的破解时长。

  • 密码参数在合理范围内明确定义。 这包括但不限于：加密盐的长度应至少与散列函数输出相同，合理选择密码导出函数和迭代次数（例如PBKDF2，scrypt或bcrypt），使用块加密时初始化向量（IV）是随机且唯一的（例如，除特定情况外不应使用 ECB），正确进行密钥管理（例如 3DES 应具有三个独立密钥），依此类推。


建议使用以下算法： 

  • 机密性算法：AES-GCM-256 或 ChaCha20-Poly1305 

  • 完整性算法：SHA-256、SHA-384、SHA-512、Blake2 

  • 数字签名算法：RSA（3072位和更高）、ECDSA 和 NIST P-384 

  • 密钥生成算法：RSA（3072位和更高）、DH（3072位或更高）、ECDH 和 NIST P-384


此外，应始终依靠安全硬件（如果有的话）来存储加密密钥、执行加密操作等。


有关算法选择和最佳实践的更多信息，请参阅以下资源：

  • "Commercial National Security Algorithm Suite and Quantum Computing FAQ"

  • NIST recommendations (2016)

  • BSI recommendations (2017)


3. 常见的配置问题


密钥长度不足


即使是最安全的加密算法，当密钥长度不足的时候也会受到暴力破解攻击。确保密钥长度满足 https://www.enisa.europa.eu/publications/algorithms-key-size-and-parameters-report-2014 中的要求。


使用硬编码加密密钥进行对称加密


对称加密和密钥哈希（MAC）的安全性取决于密钥的保密性。 如果密钥被泄露，则加密获得的安全性将丢失。为防止这种情况，请勿将密钥与加密数据存储在相同的位置。开发人员经常犯一个错误，即使用静态的硬编码加密密钥加密本地存储的数据，并将该密钥编译到应用程序中。这使得任何人都可以通过反汇编程序来获取密钥。


首先，确保源代码中没有存储密钥或密码。 这意味着你应该检查 Android 上原生代码、Javascript / Dart代码、Java / Kotlin代码， iOS 中的 Objective-C / Swift 代码。 请注意，即使源代码被混淆，硬编码密钥也存在问题，因为动态检测很容易绕过混淆。


如果应用程序使用双向 SSL 校验（同时校验服务器和客户端证书），请确保：1.客户端证书的密码不存储在本地或锁定在设备证书链中；2.所有安装都不共享客户端证书。


如果应用程序依赖于存储在应用程序数据中的其他加密容器，请检查加密密钥的使用方式。 如果使用密钥封装方案，请确保为每个用户初始化主密钥，或者使用新密钥重新加密容器。 如果可以使用主密钥或以前的密码来解密容器，请检查密码更改的处理方式。


弱密钥生成函数


某些加密算法（例如对称加密或某些 MAC）会使用固定长度的密钥。例如，AES 使用 16 个字节的密钥。原生实现可以直接使用用户提供的密码作为输入密钥。使用用户提供的密码作为输入密钥有以下问题：

  • 如果密码比密钥长度短，则不能使用完整的密钥空间，剩余的空间就会被填充（空格有时用于填充）。

  • 用户提供的密码实际上主要由可打印和可读的字符组成。因此，256 个 ASCII 字符中只有一部分会被使用，并且熵减少大约四倍。


确保密码不应直接传递给加密函数。相反，应将用户提供的密码传递到 KDF 来创建加密密钥。使用密码派生函数时，应选择适当的迭代计数。例如，NIST 建议 PBKDF2 的迭代次数至少为 10,000。


弱随机数发生器


从根本上说，不可能在任何确定性设备上产生真正的随机数。 伪随机数发生器（RNG）通过产生伪随机数流来弥补这一点，伪随机数流可以认为是真正的随机数。 生成的随机数的质量因所使用的算法类型而异。 密码安全的 RNG 生成的随机数能够通过统计随机性测试，并且能够抵抗预测攻击。移动 SDK 提供了 RNG 算法的标准实现，可生成具有足够随机性的数字。


密码学的自定义实现


发明专有加密函数既耗时又困难，并且可能失败。相反，我们可以使用被广泛认为是安全的众所周知的算法。移动操作系统提供实现这些算法的标准加密API。


仔细检查源代码中使用的所有加密方法，尤其是那些直接应用于敏感数据的方法。 所有加密操作都应使用 Android 和 iOS 中的标准加密API。应仔细检查不使用已知加密算法提供者的任何加密操作。重点关注修改的标准算法。必须要记住，编码与加密不同！当发现使用 XOR（异或）等位操作运算符时，需要进一步调查。


在加密的所有实现中，应确保始终执行以下操作： 

  • 工作密钥（如AES / DES / Rijndael中的中间/派生密钥）在使用后可以从内存中正确删除。

  • 应尽快从内存中删除密码的内部状态。


AES 配置不当


高级加密标准（AES）是移动应用程序中广泛接受的对称加密标准。 它是一个基于一系列链式数学运算的迭代分组密码。AES 在输入上执行可变数量的轮次，每个轮次涉及输入块中字节的替换和置换。每轮使用 128 位轮密钥，该密钥源自原始 AES 密钥。在撰写本文时，尚未发现针对AES的有效密码分析攻击。但是，实现细节和可配置参数（例如分组密码模式）使用不当肯能会造成一些错误。


弱分组密码模式 


块加密是在离散输入块上执行的（例如 AES 具有 128 位块）。 如果明文大于块大小，则明文在内部被分成给定输入大小的块，并对每个块执行加密。 分组密码操作模式（或块模式）决定来加密前一个块的结果是否影响后续块。


ECB（电子密码本）模式将输入划分为固定大小的块，并使用相同密钥加密每一个块。 如果多个分割的块包含相同的明文，则它们将被加密成相同的密文块，这使得数据中的模式更容易识别。在某些情况下，攻击者可能能够重放加密数据。

建议使用使用密码块链接（CBC）模式代替 ECB 模式。 在 CBC 模式下，明文块与先前的密文块进行异或。这确保即使块包含相同的信息，每个加密块也是唯一的并且是随机的。 请注意，最好将 CBC 与 HMAC 结合使用确保没有出现以下错误，例如“填充错误”，“MAC错误”，“解密失败”，以便更好地抵抗 padding oracle 攻击。


为了增强数据加密，我们建议使用可以保护存储数据的完整性的块模式，例如伽罗瓦/计数器模式（GCM）。 其具有额外的好处，即该算法对于每个 TLSv1.2 是要强制实现的，因此可在所有现代平台上使用。有关有效块模式的更多信息，请参阅《NIST guidelines on block mode selection》（https://csrc.nist.gov/groups/ST/toolkit/BCM/modes_development.html）。


可预测的初始化向量


CBC、OFB、CFB、PCBC 模式需要初始化矢量（IV）作为密码的初始输入。 IV 不必保密，但不应该是可预测的。 确保使用加密安全的随机数生成器生成 IV。 有关 IV 的更多信息，请参阅 http://www.cryptofails.com/post/70059609995/crypto-noobs-1-initialization-vectors。


有状态操作模式下的初始化向量


请注意，使用 CTR 和 GCM 模式时，IV 的使用会有所不同，GCM 模式中初始化向量通常是计数器，而在 CTR 中的 IV 是计数器与 nonce（随机数）一起使用。 因此，在 CTR 模式中使用具有自己的状态模型的可预测 IV 正是所需要的。 在 CTR 中，在每个新块操作使用一个新的 nonce 和计数器作为 IV。 例如：对于 5120 位长的明文：有 20 个块，所以需要 20 个由 nonce 和计数器组成的 IV。 而在 GCM 中，每个加密操作只有一个 IV，并且不应重复。 有关 IV 的更多详细信息和建议，请参阅 https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf 文档的第 8 部分。


由于填充或块操作实现较弱导致的 Padding Oracle 攻击


在过去，PKCS＃7（公钥加密标准7）被用作非对称加密的填充机制。 在当前 Java 环境中，它被称为 PKCS＃5。这种机制很容易受到 Padding Oracle 攻击。 因此，最好使用 OEAP（Optimal Asymmetric Encryption Padding）（ 或PKCS＃1 v2.0）。 请注意，即使使用 OAEP，仍然可能会遇到 Kudelskisecurity 博客中（https://research.kudelskisecurity.com/2018/04/05/breaking-rsa-oaep-with-mangers-attack/）描述的 Mangers 攻击。 


注意：当实现不当提示不同警告信息的时候，使用 PKCS＃5 填充模式的 AES-CBC 也易受 Padding Oracle 攻击，例如“填充错误”、“MAC错误”或“解密失败”。 有关示例，请参阅https://robertheaton.com/2013/07/29/padding-oracle-attack/。 接下来，最好确保在加密明文后添加 HMAC：因为当密文的 MAC 错误时候，就不会进行解密操作。


保护内存中的密钥


当考虑到内存 dump 威胁的时候，是可以在密钥使用时在内存中获取到它的。内存 dump 需要 root 访问权限（例如root设备或越狱设备），或者需要使用 Frida patch过的应用程序（此时你可以使用像 Fridump 这样的工具）。因此，如果设备仍需要密钥，最好考虑以下内容： 

  • 确保所有加密操作和密钥本身都保留在可信执行环境（例如，使用Android密钥库）或Secure Enclave中（例如，使用密钥链并在签名时使用ECDHE）。 

  • 如果需要在TEE / SE之外使用密钥，请确保对它们进行模糊/加密，并仅在使用期间对其进行去模糊处理。无论是否使用原生代码，在释放内存之前始终将密钥置零。这意味着：覆盖内存结构（例如，使数组无效）并知道 Android 中的大多数不可变类型（例如 BigInteger 和 String）都保留在堆中。 

注意：鉴于内存 dump 的简易性，除了用于签名验证或加密的公钥之外，永远不要在不同帐户或设备之间共享相同的密钥。
