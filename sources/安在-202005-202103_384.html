1) 今天你的漏洞修了吗？；

目前，大多数客户都有Web应用发布在互联网上。在发现了安全漏洞后，大家的第一反应就是修复漏洞，但是，漏洞修复之后是不是就安全了？近段时间，在攻防演练的过程中，我们常听到的一种攻击方式就是Webshell，哪怕已经将漏洞进行修复，但是依旧存在一些其他的安全问题。


事实上，企业用户对于不断发现问题、再响应问题的这套流程感到非常被动，他们也希望更好的解决方案，以便能够主动地对未知威胁进行防护，在这一块，Imperva可为用户带来默认的安全防护，本次分享中我也会介绍一些新的想法和思路。


众所周知，Imperva 在网页应用防火墙领域基本上是NO.1的产品，我们公司也有专门的WAF解决方案，但是默认安全防护和WAF并不是同一个概念，在后面的分享中我将会介绍新方案的不同之处和优势。

一、今天你的漏洞修了吗？




上图显示的数据大家应该都不陌生，这些数据来自安全代码检查的第三方公司的报告。目前现在的应用大多都是web应用，一直面临着非常高的安全风险。


原因在于写代码的是人，而人总会犯错，况且大多数写代码的人并不是安全人员，没有足够的安全意识，写代码时考虑更多的是应用的可用性，而不是安全。这就是为什么在第三方的报告里，平均每1000行代码中就会出现25处错误或者漏洞。


另外，互联网上的Web应用大多都有上万行代码，有的甚至是几十万、几百万行代码。大多数企业不具备独自开发该数量级的代码量的应用，为了加快速度肯定也会使用一定的第三方的组件。报告中的数据也说明了这一情况，网页应用中使用第三方组件的比率高达83%。这里就产生了一个问题，第三方组件是开源的，其中蕴含的安全问题企业无法控制。


而发现漏洞之后，厂商通常会推出相应的补丁，企业一般只需升级即可解决该漏洞。但是，如果这个漏洞出现在代码层或者业务逻辑层，那么修复的速度将会非常缓慢，通常要等到维护窗口期或者下一次版本发布时才能进行修复。这意味着漏洞修复期间存在一大段空窗期，即便是有了WAF、虚拟补丁等措施，这段时间依旧存在很大的隐患。


这也正是企业用户面临的挑战，也是他们感到痛苦的地方。这个挑战有多么严重呢？Imperva的Cloud WAF每天帮客户阻拦 4.2M 次的攻击，由此可知Web应用被攻击的次数之多，量级之大。哪怕我们做再多的安全防护也无法保证百分百的安全，过滤之后也必定会有一些问题遗留。


那么这些问题集中在哪些地方呢？



第一，未知风险，因为使用了第三方的组件无法预知是否存在风险。例如，就在几天前，腾讯安全实验室曝光了Apache组件存在被绕过的风险，出于安全的考量文中并未曝光具体的细节，但这也表示，我们现在不可能有应对该漏洞的签名或者安全规则。换句话说，这段时间内，企业只要使用了Apache组件就存在被绕过的风险。


第二，迫于时间的压力很难完全修复漏洞并进行充分验证。比如某一个漏洞出现后，企业必须要统计哪些平台用了第三方组件，哪些平台需要打补丁，特别是一些大体量企业用户，一个系统可能就有几百台服务器，如果都使用了第三方组件，那么每台服务器都要打补丁。此时你会发现企业根本没有足够的时间进行验证：打完补丁是不是一定有效，安全问题是不是已经完全解决，每一台服务器的补丁是不是都已经安装好了等。


第三，传统的安全控制手段无法适应新架构、新攻击，包括容器化、微服务、东西向流量、API安全、私有加密协议（冰蝎）等。近期不少企业正在进行攻防演练，冰蝎攻击特别常见，攻击队会利用各种安全漏洞，把攻击木马上传至web应用，这样就可以使用访问网页的方式进行访问，甚至是随意修改文件和数据库的内容，以及做任何想要做的事情。


随着新型攻击越来越隐蔽，传统的网络设备监测的效果也越来越低，比如通过加密的方式进行攻击，或者绕过系统安全检查的伪装式攻击等。


另外，运行环境也在发生变化。早期企业的服务和应用相对单一，且基本都在物理服务器上，我们只需要保护应用即可，如今，我们将单一的功能架构逐步改为微服务架构，组件之间可能也会互相访问，黑客的攻击更偏向于接口，而传统的安全防护架构也难以适应随时横向拓展、东西向访问的请求。


因此，Imperva Cloud WAF虽然能够每天为用户阻拦 4.2M 次的攻击，过滤掉绝大部分安全问题，但仍然建议客户针对剩下的部分采用更精细化的手段进行防护。



这张图显示的是，企业用户的网络环境、应用环境的变化。从开发者的角度来看，开发模式已经从传统的先调研需求再进行开发的瀑布式开发，到现在的敏捷开发，再到当下留下的DevOps；使用的架构也从单一架构到微服务架构；服务器也从物理服务器向虚拟化转变；不少互联网公司基本上所有的应用都上了容器，以便随时进行部署、拓展；传统的数据中心也在慢慢迁移至云端。


所有变化的背后或多或少都带来了新的安全问题，传统的安全防护手段越来越无法适应当下的环境。比如现在很多应用已经往云上迁移，传统解决方案的WAF难以全部覆盖，更不用说还要考虑公有云、容器化以及东西向流量等等。


二、要是应用默认就有

安全防护就好了


当下，越来越多的公司正在往运维开发的方向发展，安全如果还是以盒子的形式存在，自然无法适应这种新的开发架构，因此，他们开始寻找能够适应这种新型结构和变化的安全产品。


Imperva在帮客户进行安全配置时发现，客户通常会有几百个域名或者应用，其中一些应用安全防护都配不全。主要是因为我们打交道的都是安全部门的人，他们可能也不知道应用是不是全的。所以，有时进行攻防演练时就会发现没有防护措施生效，最后检查才知道还有一些应用，比如只用于内部访问，或者不太访问的应用，没有加入进来，导致防护效果不好。


因此，很多客户都希望应用在上线发布时就将安全的组件放进去。实际上应用安全做的好的公司，应用的发布流程里面确实含有安全团队，目的就是把相应的需要保护的应用添加到安全设备中，确保流量经过安全设备。


但是，这样的发布流程很难适应像DevOps等节奏特别快的方式，所以客户才会希望有一种默认的安全防护配置，就像小孩子出生后默认要打疫苗，而上学时学校看的是疫苗本，只要该打的疫苗都打了，那么就可以认为这个孩子没有传染病。



这也正是我们现在正在做的事情，在新架构下为企业用户提供默认的安全防护。这样做有三个好处：1、降低打补丁的风险和成本，企业不再担心第三方组件的安全问题，还可以保证漏洞修复空窗期的安全问题；2、提高企业应用安全防护基准，为应用提供默认的安全防护，可以有效地帮助应用快速投产；3、可以应对现代化架构和现代化攻击，而且可以适应各种架构和环境，无论木马在传输上如何加密和变形都无处遁形。也就是说，有了默认安全防护之后，之前提到的三个挑战都将不复存在。


这里给大家介绍一下我们的默认的安全防护层或者说新的技术方向——Imperva Runtime Application Self-Protection (RASP)，运行环境的应用的自我保护。



从上图我们可以看到它的实现逻辑和运行逻辑。以前企业的网络检查一般发生在互联网边界或者内网边界，比如将防火墙部署在入口处，通过网络设备检查网络流量。而Imperva RASP插件是装在应用运行的环境里，并不是运行在操作系统中，而是和应用包的发布在一起，这样在运行应用的同时将RASP也运行起来，而不是跟着网络环境和应用。


当RASP运行之后，我们可以看到请求的方框。因为它是运行在环境中，而信息到了JAVA环境中已经是解密后的内容，包括编码还原后或者是已经拼接完成后的内容，这点非常重要。因为它有自我保护，意味着出现问题时可以进行拦截，区别于我们刚说的检测系统，一般的主机检测系统只能检测本地文件或者端口的变化。


对于RASP，为了让大家好记，我们把它总结为“三无产品”。


第一，无连接，不需要网络连接，不依赖更新，这也是和大多数安全解决方案不一样的地方。RASP并不依赖于签名进行匹配，而是通过上下文进行语义分析，以及对应用运行环境的判断，因为不依赖签名，自然也就不需要网络连接，也不用进行更新。


第二，无签名，Secure by Default，不依赖签名或学习做判断，速度快(≤5 ms)。我们有个口号叫默认的安全规则，上文已经提到，这个规则不依赖签名，主要是语法和运行环境的分析，如果外部的命令是一个有风险的命令，那么它不需要任何签名就可以进行告警或屏蔽。


第三，无感知，简单插件，不改变已有的部署，随WebAPP/服务/API一起运行。因为没有签名，所以它的运行速度也特别快，即便是把插件装在应用系统上，也不对系统性能产生任何影响，在后面的案例中，RASP在规模非常大的企业中部署过，它的影响非常小。


再者，RASP是作为一个插件随着业务发布而发布，因此在网络上没有任何感知，不需要串联设备，也不需要引流，只要跟随应用一起运行，然后改一下JAVA的运行脚本的参数即可，不需要改任何的程序代码，而且它的部署方式也非常简单。


很多小伙伴都对没有签名表示好奇，这里顺便再解释一下。Imperva 有一个LangSec 专利技术，简单来说是一个语义分析的技术，当然现在很多产品都有语义分析，我们一起来看下两者的区别。



在上图的右边，我圈出来一部分内容，大家应该都非常容易读懂。简单来说就是要查一下数据里有没有一个叫Chris的人，然后从customer里取他的名字和邮箱。这个可能是前端应用需要查询客户信息时提交的数据库语句。


但是如果这里有一个SQL注入，那么黑客就会想办法在前端可输入的字段里拼接一点内容，比如1=1，这大概是最简单的SQL注入语句。因为1=1一定是成立的，所以前置条件就相当于没有，系统就会将整个表里的名字和邮箱全部列出来。


如果我们做签名类的检测时，在提交内容的时候并没有把完整的一句话提交上来，而是只提交了后半部分。比如我们在输入栏里输入了Chris这个名字，想要查询这个人的邮箱地址，那么在网络层检测的话看到的信息就是参数等于Chris。如果是SQL注入加上了1=1，它能匹配的字符串其实只是后面这一部分。这个时候如果要做签名匹配就很容易出现误判，因为它拿到的信息比较少。


现在其他设备在网络层也有语义分析，但它拿到的信息还是很少，只有Chris和1=1，虽然我不清楚它们是怎么做语义分析的，肯定没有RASP这个点做得好，因为RASP能够看到完整的语句。我们在前端输入，但在应用层它会把完整的语句拼接好，然后再提交到后台数据库，这意味着RASP可以拿到完整的信息，而不是部分信息。


有了足够多的信息，自然就可以判断的更准确。我们的专利技术LangSec会将完整的语句进行语法解析，然后我们就会发现两部分Where条件有重叠的部分，这里有个技术术语，中文翻译过来叫套套逻辑，指的是句子中出现了冗余的语法，比如1=1就是如此，因为这是恒等式，通常这类语法是有问题的，所以我们判断语句有问题。


只要是有语法意思的情况下，比如说跨站、SQL注入等攻击都有语法，我们的做法是将表达式列出来，去做正规化、做词的解析，再做语义的解析，分析是否存在冗余的结构。还有一种则是结合上下文进行语义分析，这也解释了为什么我们不需要签名，为什么不需要频繁进行更新，毕竟几十年来英语语法没有出现大的变化。


Imperva的RASP解决方案也是一样，通过语法进行分析的检测手段相对固定，更新频率非常低，可能1年也就推出1~2个引擎上的更新，其他时间并不需要进行大的调整。我们把这种默认的语法知识放在了检测引擎上就可以自动进行检测，特别适合刚刚提到的漏洞利用（0day）的场景。


三、我们有WAF了还要其他吗？


目前，RASP解决方案全球已经有不少企业用户，包括美国最大的电商平台也在使用。看到这里，也许有人会有疑问：有了WAF之后还需要RASP吗?两者看上去似乎有不少的重叠部分，比如都是防SQL注入和防漏洞利用。



实际上两者之间存在区别，从WAF的角度来看更适用于已知的攻击，是通过网路边界阻拦恶意流量让企业获益。比如一些老的业务系统可能存在几年前的漏洞，而且需要签名；或者是应对机器人的恶意扫描、恶意注册等适合在云端解决的问题。从这里可以看出，WAF防护的对象基本来自公网和外部，保护的是南北向流量，通常由企业运维人员或者服务供应商来运维管理。


RASP就不太一样，是通过降低代码修复的成本，包括零日漏洞的防护，来让企业受益，就像前面提到的美国电商用户，面临着未知的攻击和威胁，依靠传统手段难以奏效，更加适合0day漏洞以及有背景信息、语法分析的攻击。另外，传统的WAF是检查南北向流量，而RASP可以随着应用一起运行，可以用于检查内部访问等东西向流量。运维管理团队也有一定的变化，由安全团队、开发团队或者是DevOps团队运维管理的可能性更大，因为DevOps团队在开发的同时就可以把安全功能放在应用中一起发布。


总的来说，两种解决方案作用的时间和层次不一样，部署的位置也不一样，而防御纵深也需要在不同的层次选择正确的方案。


知识锦囊


接下来，我将继续分享一些实际的应用和案例，这些内容全都来自于我的工作经验，或者是和客户沟通过程中所遇见的问题，并总结出4个RASP锦囊。


RASP锦囊1：运行环境里进行检测，打破传统网络架构束缚：SSL卸载、各种编码绕过问题、东西向流量。


近期攻防演练非常多，很多客户比较关心SSL加密之后，安全设备就有可能被绕过，而且现在很多安全产品都不支持国密，如果有一天需要检查国密的流量，产品不支持自然无法解密，也就无法查看内容。另外，现在的安全产品大多都在网络层进行检查，不论是嗅探还是串接，如果流量被加密、编码或使用私有协议进行传输，那么就没有办法检查流量是不是有问题。


而RASP作为一个插件可以在任何的物理、虚拟化、公有云、容器的环境下运行，可以在最终的运行环境中检测，所以流量、国密和私有的加密方式都不是问题。同时，它检查的是最后的执行代码，意味着可以看到完整的语句，有效性和准确性都比网络层检测要高。



从上图我们可以看到，流量从南北向进入到公司，但是，越来越多的应用因为微服务，其流量变成了东西向。随着微服务趋势日益明显，南北向的安全设备想要检测流量的困难度会越来越高。而RASP可以和应用一起发布，把组件和微服务连接起来，这样的话它们互相之间的访问或者后台访问就都不是问题。


这里分享一个冰蝎的案例，是我们真实的客户。在搭建好的一个环境中，我们使用冰蝎进行访问，它在第一次访问页面的时候就传出一个16位的密钥，后续的所有访问和提交全都进行了加密，如果没有密钥或者不知道传输过程，那么很难在网络层进行检测。而RASP则可以轻松检测到这一攻击，在测试过程中可以看到解密后的具体执行命令。


RASP锦囊2：RASP集成在应用发布中，成为应用健康体系的一部分，不再担心是否被安全设备覆盖。


安全团队经常发现，企业存在大量未知的应用被悄悄发布，甚至没有经过正常的上线流程，自然也就没有网络安全设备的防护，又或是WAF上定义了错误的信息导致没有正确检测，这些都将给企业安全带来了严重的威胁。当然，我们可以从流程上进行规范，但实施的难度非常大，特别是微服务的方式出现的情况下。


RASP的解决方案则是默认的安全防护，和应用系统一起发布，运行之后不需要更新签名，直接提供默认的安全服务。虽然无法解决百分百的问题，但就像孩子打疫苗一样，可以有效将大的风险全部覆盖，还可以自己写黑白名单进行细调。


RASP锦囊3：无需实时的管理和更新安全设备策略，无需签名、无需网络连接，不再为最新的CVE漏洞出现而手忙脚乱。


目前企业面临的问题是应用层的安全设备管理成本很高，安全人员需要懂安全，还需要懂应用，配置安全规则对能力要求很高，而且每出现一个新的漏洞都要第一时间确认：是否需要升级对应的应用组件；安全设备是否有防护的手段（签名策略）；漏洞是否有后续新的变种和新的POC（需要新的签名）等，可能漏洞每一次出现变种我们都要做一波签名，以及升级漏洞补丁，不仅非常烦而且容易遗漏。


RASP的解决方案最大的好处就是企业只需要开启默认的安全防护就可以。不依赖于签名、不需要网络连接更新，基于语义分析、运行上下文、白名单等机制，只需要关注最新的漏洞最终的攻击动作是哪种方式就可以知道RASP是否可以防护。


以RCE（Remote Command Execution）类型的漏洞举例，无论漏洞是利用不同的入口、不同的POC，最终目标还是在运行环境中执行有破坏性的指令，对于RASP来说就是检测是否有Command Injection。


RASP锦囊4：代码层的攻击可视化，告警日志信息指出到具体执行错误的代码行。


传统安全设备的告警是基于网络流量分析的，哪怕仅仅是黑客的探测行为也同样会被告警，但是其实业务可能并没有这样的漏洞，而且无法确定攻击行为是否真的对应用有威胁，安全告警无法对应用漏洞的改进和修复有实际的参考意义。


RASP的解决方案可以在运行环境中对攻击代码进行检查，探测不存在的页面和无法被执行的攻击尝试不会进入到运行环境；且在运行环境中检测到的攻击，都是实际有效的威胁；还可以检测到具体的执行错误代码位置，甚至还可以针对每个应用遭受攻击情况生成热力图，把修复资源投入到最需要的地方。
