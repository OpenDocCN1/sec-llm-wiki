# 从阿里云事件看安全觉悟与管理艺术

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzU5ODgzNTExOQ==&mid=2247534036&idx=1&sn=d57288483884cc5fbcf4352fce44f4fe&chksm=febc2f14c9cba6025907d128a832dd1c9c5f940debc84808f13da5a948b2168b62922872d143&scene=126&sessionid=1681310607#rd](http://mp.weixin.qq.com/s?__biz=MzU5ODgzNTExOQ==&mid=2247534036&idx=1&sn=d57288483884cc5fbcf4352fce44f4fe&chksm=febc2f14c9cba6025907d128a832dd1c9c5f940debc84808f13da5a948b2168b62922872d143&scene=126&sessionid=1681310607#rd)

近日，工信部网络安全管理局通报称，阿里云计算有限公司（下称：阿里云）发现阿帕奇（Apache）Log4j2组件严重安全漏洞隐患后，未及时向主管部门报告，未有效支撑工信部开展网络安全威胁和漏洞管理。

  

通报指出，阿里云是工信部网络安全威胁信息共享平台合作单位。经研究，工信部网络安全管理局决定暂停阿里云作为上述合作单位6个月。暂停期满后，根据阿里云整改情况，研究恢复其上述合作单位。

  

![](../Images/0260063ad6bd54fb0ce17c01ca3bffa8.png)

  

对此，阿里云回应称，因在早期未意识到该漏洞的严重性，未及时共享漏洞信息，将强化漏洞管理、提升合规意识，积极协同各方做好网络安全风险防范工作。

  

阿里云在情况说明中表示，阿里云一名研发工程师发现Log4j2 组件的一个安全bug，遂按业界惯例以邮件方式向软件开发方Apache开源社区报告这一问题请求帮助。Apache开源社区确认这是一个安全漏洞，并向全球发布修复补丁。随后，该漏洞被外界证实为一个全球性的重大漏洞。

  

![](../Images/9358fcf7f955e32c70d0bb055be8d777.png)

  

阿里云官网显示，12月9日，阿里云安全团队发布 Apache Log4j2 远程代码执行漏洞（CVE-2021-44228） 安全通告。据多家外媒报道称，该漏洞最早由阿里云的网络安全专家发现，并在11月24日报告给阿帕奇软件基金会，远早于12月9日工业和信息化部网络安全威胁和漏洞信息共享平台收到有关网络安全专业机构报告的时间节点。

  

  

**阿里云问题出在哪里**

  

阿里云事件一出，很快就在行业内引起轩然大波，舆论的导向也很匪夷所思。冷静下来看一看，首先，在工信部官网上并没有公布阿里云的处罚通知，该消息是媒体、业内人士以及阿里云自己公布的，并没有广而告之；其次，阿里云所受到的处罚是暂停合作六个月，没有罚款、没有整改，也没有提及危害国家安全。这样看来，阿里云所受到的惩罚不轻，也不重。

  

![](../Images/d6b6ebd33daa58129ce1f443e4bbaf5e.png)

  

在阿里云的回应中提到了业界惯例，互联网生态的内核精神是“开源共享”，在今年推出的《网络产品安全漏洞管理规定》中也明确规定了，发现或者获知所提供网络产品存在安全漏洞后，应当立即采取措施并组织对安全漏洞进行验证，评估安全漏洞的危害程度和影响范围；对属于其上游产品或者组件存在的安全漏洞，应当立即通知相关产品提供者。这样规定的目的就是减少各方的沟通成本和博弈造成的损失，防止造成互相猜忌、互相伤害的局面，因此，阿里云将漏洞披露给Apache理所当然，并不存在卖国。

  

阿里云此次的问题，是因其在发现漏洞后未意识到该漏洞的严重性，这对于目前我国建设网络安全威胁信息共享平台造成不良影响。另一方面也反映出信息安全在组织架构中的下传上达不流畅以及全面风险管理的决策层级不完善等问题，这不仅是阿里云内部的问题，而是整个行业目前所反映出的一种现状。

  

![](../Images/af106919b36efe8d353d3b416d57d652.png)

  

“安全负责就是背锅”，这不仅仅是一句玩笑话，而是真真正正反映出一个问题，那就是在组织架构中，CSO或者CISO是否具有话语权。以此次阿里云事件为例，在上级管理部门的处罚内容中，并没有对安全研发人员做任何点名和批评，问题出现在哪里显而易见。当网络安全与国家安全紧密相连时，技术问题便不再单纯，可当沟通汇报流程不通畅或是技术人员话语权过低，无法参与决策时，类似阿里云的事件将层出不穷。

  

  

**从业者三省吾身**

  

实际上，越来越多的安全人员反映，自身地位与责任并不平等。在一个组织的内部，安全往往是成本中心而非利润中心，可现在，安全与业务的关联性越来越高，安全人员的话语权却没有达到与业务人员同级别的水平上。明明是安全的问题，却造成了组织业务的损失，安全人员该如何自处？安全负责人不参与公司决策，没有对各种风险进行横向比较，如何能够具备意识？安全负责人自身不主动去理解业务，只顾着埋头写代码，想方案，决策层又怎么会把权利下放到他的手中呢？

  

![](../Images/608fcafbc83b09ee7fd400a0da4a661a.png)

  

因此，安全从业者要想改善当下的处境，首先要从自身下手，改变自己固有的意识形态，以核心业务作为切入点进行安全赋能，要充分了解组织的业务模式、业务架构、核心业务能力、支撑业务开展的核心流程、支持性的业务流程与职能、业务职责分工、关键业务人员及团队、支撑核心业务的系统以及技术团队关键人员等等。

  

其次要规划好安全治理与战略。做好战略一致性，使信息安全的战略与重点应该与业务的战略、布局、拓展等能力需求保持一致；实现信息安全价值，信息安全的成本投入要转化成生产力、产品技术壁垒、商业竞争优势以及业务保障能力；风险优化，信息安全工作不是成为能力喜好、偏好的试金石，而是要考虑影响现在或未来业务生存与发展、优化风险管理能力、优化信息安全战场态势、变被动为主动；资源投放效率，使资源合理使用，最大化发挥价值；度量评价，根据组织实际业务情况结合安全体系所构建的针对性测评指标。

  

![](../Images/dafda18c9495b41c6c6a1eed37fed70f.png)

  

接着要完善安全风险管理与架构，以企业核心业务价值链进入到业务流程，再上升到业务风险和安全风险，从而给出安全管控及方案，最终落实到企业安全落地实践，业务风险与安全风险之间通过安全威胁、技术架构、安全场景进行衔接，确保安全与业务的契合，同时基于目前安全技术实现能力，持续自适应风险与信任评估。要加强对本地政府、监管以及法律法规合规的理解和关注，对一些基本要求需要得到有效关注与落实，主动与监管部门沟通，不要试图游离于法规边界，主动参与影响规则制定过程而不是被动等待甚至隐瞒欺诈，以更加开放的心态来看待安全合规，更加主动的行为来拥抱变化，使安全合规变成企业安全能力的倍增器与推动力。

  

最后做好安全审计，结合传统“IT审计“的理念，分为”审计准备“与”审计执行“两个阶段。审计准备包括对审计目的、目标的充分理解以及涉及的环境、技术、系统、流程、业务等内容的调研分析过程，并根据审计目的与风险理解，确定重点内容；编制审计计划等。审计内容则包含对信息安全有自身的特点与规律，技术、管理、人员、文化等都可能存在风险与威胁点，换句话说，就是目前能见到的安全技术、产品、理念都可以作为审计的内容。

  

  

**安全与发展并重**

  

组织对信息安全首先要足够重视，不应只把安全当做成本，而是要作为竞争力，只有确保安全合规，组织才能往更高质量、更大规模发展。要清楚，建立安全体系是一个长期过程，所以要不断进行修正和完善，根据自身发展阶段进行划分和合规管理，通常可根据周期的不同指定安全计划。同时要注意加强整体安全意识，不能仅依靠技术人员的反馈，要建立全面的上下双向沟通渠道，加强员工的主动申报及安全意识，定期对相关法律法规进行宣发并解读。在战略及人员规划好后，还要根据具体方向，建全企业安全体系，如禁止root登陆、禁止弱口令、脚本执行、用户名查看、二次验证以及禁止免密跳转登陆等。要牢记，安全是发展的前提，发展是安全的保障，安全生产不容半点偷懒、取巧，唯有脚踏实地，确保安全发展理念落到实处，才能实现可持续发展。

  

![](../Images/def7c4af191512822317fe95db73a200.png)

  

某企业安全专家唐龙表示：针对此次Apache Log4j2漏洞，要从来两方面吸取教训，一个是安全情报的生态问题，一个是供应链的管理问题。

  

安全情报一定要和国家、行业进行挂钩，我们必须要识别清楚国家重要还是企业重要，对于公司来说，国家安全是第一的，所以所有的情报输入，可以来自与任何地方，但是情报输出，必须要满足与国家和生态要求。我认为，必须加强与国家专业网络安全机构的交流与协作，促进地方、行业、国家企业网络安全成果共享，并积极参与有关行业网络安全标准、规范的编制工作。意思就是要和国家、行业建立起夯实的沟通关系，任何的安全发现都必须先要和国家进行共享和沟通，当员工发现问题以后，一定要先提交给情报中心，再由情报中心和CERT中心进行提交，不允许扩散，这个也是网络安全法第57条的要求。否则就是法律和政治问题。

  

另外，对于供应链的安全管理，一定要对代码进行安全管理，首先要了解软件的来源，其次要了解软件的安全性。针对该情况，我有两点建议，一是审核产品入网资格，严格执行网络安全审查要求。对软件所使用的开源组件进行识别，检测开源组件漏洞，分析组件安全风险，避免开源组件带来的安全风险。对硬件的固件进行统一源代码缺陷分析、源代码后门审计和源代码缺陷修复跟踪，避免固件缺陷导致的安全风险。二是当识别已入网软硬件产品发生高威胁漏洞或者已知重大隐患情况时，及时进行产品替换或者版本更替，实现业务连续及可靠。这样才能确保相关软件产品能够及时发现问题，就算出问题也有相关的预防措施进行替换，确保公司业务不受到影响。

  

![](../Images/7537520ff28f61eda320a933da73db6a.png)

  

  

**国家政策还需完善**

  

回归到事件本身，《网络产品安全漏洞管理规定》第七条规定：网络产品提供者，应当在2日内向工业和信息化部网络安全威胁和漏洞信息共享平台报送相关漏洞信息。因此，阿里云并不属于网络产品提供者，对漏洞威胁没有上报的责任，而第十条规定：鼓励发现网络产品安全漏洞的组织或者个人向工业和信息化部网络安全威胁和漏洞信息共享平台、国家网络与信息安全信息通报中心漏洞平台、国家计算机网络应急技术处理协调中心漏洞平台、中国信息安全测评中心漏洞库报送网络产品安全漏洞信息，也仅仅是鼓励而已。

  

![](../Images/cd6e7934ada5e4626f4fbf70c66fa2fb.png)

  

由此可以看出，阿里云并非因此规定受到惩罚，可能是没有履行好作为网络安全威胁信息共享平台的成员职责。所以，网上铺天盖地的帽子可以先放一放，这并不是为阿里云辩解，而是要清楚事件发生的最核心本质是什么。这件事反映出当前的管理规定对于阿里云这样的第三方机构是不够的。当然，国家安全是动态的，运动监管也是没有办法，但是还要从中吸取经验，逐渐完善相关法律法规，让国家安全处在持续稳定的状态。

  

总而言之，无论是组织还是个人，面对当前越来越复杂的信息安全环境需要足够的尊重和重视，开源技术没有国界，但信息安全有。要吸取此次阿里云事件带来的教训，也要明白国家此次处罚的良苦用心，敲一钟而醒世人，信息安全人人有责。
