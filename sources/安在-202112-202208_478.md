**\# 核弹级高危漏洞被曝光 #**

  
  
2021年12月9日晚，业内多名信息技术人员被临时叫回公司加班，原因无他，只因360安全大脑监测到，有黑客疑似利用开源项目Apache Log4j 2的一个远程代码执行漏洞对Minecraft（游戏名称“我的世界”） Java版发起了大规模的安全攻击。而其攻击方法竟极其简单，只要在游戏的在线聊天中发送一条带漏洞触发指令的消息，就可以对收到这条消息的用户发起攻击。  
有人会问，这不就只是游戏的事吗？和各大平台之间有啥关系？  
需知Log4j 是一款开源 Java 日志记录工具，而日志记录主要用来监视代码中变量的情况，周期性的记录，可以为文件中其他的应用程序进行统计分析工作，并跟踪代码运行时的轨迹作为日后审计的依据，同时还可以担当集成开发环境中调试器的作用，如向文件或控制台打印代码的调试信息。而在强调可重用组件开发的今天，Apache 提供的强有力的日志操作包 Log4j则可以轻松控制 log 信息的显示、log 信息的输出端类型、输出方式、输出格式等，还能更加细致地控制日志的生成过程。因此，很多企业的信息技术配置都选择使用 Log4j ，比如互联网、高校、工业制造、金融、政府、医疗卫生、运营商等几乎所有的行业都受到了该漏洞的波及，连全球知名科技公司、电商网站啥的也未能幸免。也就是说，虽然普通用户不会直接接触漏洞，但是我们日常使用的网络服务、软件系统，都在一定程度上受到该漏洞的影响并面临着巨大的安全风险。  
目前百度搜索、苹果 iCloud 搜索、360 搜索等都出现了该问题。看到没，log4j2漏洞可以在所有产生log的地方发挥作用，像线上的 web 业务，其任何数据都可能写入 Log4j，甚至一些 pre-auth 的地方，比如注册、登录等也一样，而在游戏中呢，直接发在聊天栏里就行，完全没有权限要求。

**\# 原理和具体情况 #**

  
  
经过分析，本次 Apache Log4j 远程代码执行漏洞正是由于组件存在 Java JNDI 注入漏洞，即当程序将用户输入的数据记入日志时，攻击者可以通过构造特殊请求来触发 Apache Log4j2 中的远程代码执行漏洞，从而利用此漏洞在目标服务器上执行任意代码，看仔细了，是任意代码！  
通俗点讲就是在打印日志的时候，如果你的日志内容中包含关键词 ，攻击者就能将关键字所包含的内容当作变量来替换成任何攻击命令，并且执行。就好比小偷（黑客）偶然间知道了你家备用钥匙藏在了门口的地毯（后门-这次的漏洞）上，趁你白天不在家（非值守时间，比如半夜），就可以随意进入你家（你的服务器）并任意妄为！  
果然！从云防御平台监测得知，自2021年12月10日0点开始，漏洞攻击次数直线上升，12月10日0点-16点，国内利用该漏洞进行的攻击次数高达48820，随后来自境外的攻击也开始不断增加；从国内被攻击的区域分布来看，被攻击的业务系统中，北京、云南是被攻击最多的地区；从国内被攻击的行业分布来看，政府部门、高校、金融行业都是被攻击的重点对象。  
  

**\# 曾经的“心脏滴血” #**

  
  
串联起“开源”、“漏洞”、“互联网灾难”这几字，可联想到什么？  
众所周知，SSL（安全套接层）协议是使用最为普遍的网站加密技术，而OpenSSL则是开源的 SSL 套件，为全球成千上万的web服务器所使用，Web服务器正是通过它来将密钥发送给访客然后在双方的连接之间对信息进行加密，使用 https协议的连接就采用了SSL加密技术。在线购物、网银等活动均采用SSL技术来防止窃密及避免中间人攻击。  
而“红极一时”的Heartbleed（心脏滴血）漏洞正从中而生！  
其之所以得名，就是因为用于安全传输层协议（TLS）及数据包传输层安全协议（DTLS）的 Heartbeat扩展存在漏洞，和如今的Apache Log4j2漏洞在概念上异曲同工。  
Heartbleed漏洞，这项严重缺陷(CVE-2014-0160)的产生是由于未能在memcpy调用受害用户输入内容作为长度参数之前正确进行边界检查，使攻击者可以追踪OpenSSL所分配的64KB缓存，并将超出必要范围的字节信息复制到缓存当中再返回缓存内容，这样一来，受害者的内存内容就会以每次64KB的速度进行泄露。  
此漏洞让当时版本的openSSL成为无需钥匙即可开启的“废锁”，入侵者每次可以翻检户主的64K信息，只要有足够的耐心和时间，就可以翻检足够多的数据，如拼凑出户主的银行密码、私信等敏感数据。  
当初自这个漏洞被爆出后，全球的黑客与安全专家们展开了前所未有的竞赛。黑客们的目的是试图从漏洞中抓取到尽量多的用户敏感数据，而安全专家们则在争分夺秒地升级系统、弥补漏洞，甚至关闭了某些服务。要知道，黑客一旦入侵了某些服务器，受损的便远不止这公司一个个体，还包括存放在公司数据库里的大量用户敏感资料。在当初那个“亦步亦趋”的年代，谁也不知道是否已有黑客利用漏洞获取了用户资料，又由于该漏洞即使被入侵也不会在服务器日志中留下痕迹，所以许多损失根本无法补救。

**\# 为何如此“灾难”屡禁不止 #**

  
  
2014年，心脏滴血漏洞让世界上 2/3的 网站失去保护个人信息的作用；2017年，永恒之蓝漏洞让数百万台主机面临被勒索病毒攻击的风险；2021年，Log4j2 的漏洞再一次影响了互联网上70%以上的企业系统。  
不禁要问，为何类似于这样的“漏洞风险”屡禁不止？  
针对这次Log4j2 的漏洞有人说：“这个漏洞要求攻击者使用LDAP服务器，逻辑上可能很难想到，测试也没覆盖全面，只能吃一堑长一智。”；也有人说：“在开发的时候，使用一些第三方开源的框架和服务，是没有绝对可信、完全不出问题的开源的，我们能做的就只有常常小心、警惕，尽量针对一些服务的不稳定性去设计些熔断，或者是做些其他的降级保护措施，给自己留一个后路。”  
而有专家认为，目前市场讲究敏捷开发，所以会大量复用外部成熟的开源应用及组件，但是开源应用和组件本质上还是程序，是程序就有可能出现漏洞。所以，为何“屡禁不止”的问题从本质来说更像是一个经济问题，因为在开发过程中特别重视安全对于开发者、团队、企业等并没什么收益，而基础设施上，比如开发语言、重要功能的组件什么的还是要依赖于大量开源的成果，这导致了其本身的不可控性；而在应用迭代后期，为追求面面俱到被大批量引入的特性式或后门式的系统功能，都有衍生性的危害。很多系统的复杂性是我们应该各种问题时难以预测的。  
因此，我们可以从中得出这样的概念，传统的基础型和技术型问题已经得到充分的认识、解决，甚至在发展过程中逐渐消失了，但复杂性从来没有从现实和系统中消失，相反越来越复杂。解耦与耦合同时发生，彼此加深后。我们需要理解系统复杂性背后的一系列问题。  
如此看来，流行的组件功能（尤其是开源的），用的多自然面临的攻击威胁就会多，复杂性、业务和技术变化太快，绝大多数企业安全管控能跟上就很不错了，想做到绝对安全几乎是不可能的。像这次对 Maven 官方仓库的分析，发现如 Java ORM（Java 应用中，对数据库的操作基本上都是通过 ORM 进行的） 一样的基础组件中，存在被攻击风险的高达十几万个，影响几百万个组件的版本。而在 Github 上，共有60644个开源项目发布的321094软件包存在风险，甚至影响了众多主流开源基金会的著名项目。  
因此，这又引申出一个新的命题：供应链。  
  

**\# 开源在供应链上的安全问题 #**

  
  
当前，开源已成为云计算、大数据、人工智能、工业互联网等新兴领域的主要开发模式，操作系统、数据库、中间件、应用软件、设备固件等开发、编译、测试都越来越多的采用开源代码，软件供应链的开源化趋势越来越明显，但同时软件供应链也越来越趋于复杂化和多样化，软件供应链的安全风险不断加剧，针对软件供应链薄弱环节的网络攻击就会随之增加，因此，软件供应链将成为影响软件安全的关键因素之一。  
软件供应链，简单来说其开发的产品就只是供应链中的一环，因为产品可能涉及到了硬件、公共库、第三方依赖库、还有其他软件工具等，这些东西一起组成了供应链。而"软件供应链攻击" 指的就是攻击软件所依赖的代码库或服务。  
最常见的攻击方式有两种，一是起一个和依赖库或域名很容易混淆的名字；二是向依赖库注入恶意代码。软件供应链攻击可以直接针对产品，也可以针对其上游元素（如外部依赖项或提供的服务），因此，从受害者的角度而言，产品要么是直接遭受攻击的，要么就是成了受损资源的供应商。比如在开发环节，攻击者通过污染开发工具、复用开源代码等方式控制上游软件供应链，借助软件开发碎片化显著等特点促使污染代码快速传播影响中下游用户。像2015年9月爆发的苹果开发工具XcodeGhost 事件（Xcode 是苹果的开发工具），攻击者将病毒注入进非官方渠道发布的 Xcode 上，导致 2500 多款使用该开发工具开发的苹果 App 被植入恶意代码，受影响的苹果 iOS 用户多达 1.28 亿。  
而这次log4j2 的漏洞就属于这第二种攻击方式：向依赖库注入恶意代码。故此，log4j2 作为一个第三方的依赖包，大量的项目在使用它，它一旦出现了漏洞，使用这个包的项目就会受到攻击，其影响比之“苹果事件”只会更加巨大。  
所以说，本次事件虽然表现为一个模块出现了漏洞，但其本质却是供应链中的公共模块出现了漏洞！而在不久的将来，因为公共库的增加、依赖库的使用更为广泛，供应链攻击将会成为常态。  
就这次Log4j2漏洞在软件供应链上的安全问题做如此总结：开源软件的引入在减少开发时间的同时，增加了软件供应链安全的复杂度，类似Log4j2这样应用广泛的基础组件在供应链的各阶段均存在深入的影响；大型项目中依赖关系数量与依赖层级数量的复杂度，增加了厂商对漏洞的排查难度；上游软件供应链产品中漏洞累积的影响，最终会在下游应用场景中浮现。

**\# 软件供应链上的法律法规 #**

  
为应对国内外软件供应链安全威胁，近年来我国先后颁布的《中华人民共和国网络安全法》《网络安全审查办法》《中华人民共和国国民经济和社会发展第十四个五年规划和 2035 年远景目标纲要》《关键信息基础设施安全保护条例》等政策法规强调加强软件供应链的安全保障。  
2018年，我国出台了供应链安全管理国家标准《信息安全技术 ICT 供应链安全风险管理指南》(GB/T 36637-2018)。  
2021年，我国率先开展针对软件供应链安全的国家标准立项工作，拟通过研究制定《信息安全技术软件供应链安全要求》提升国内软件供应链各个环节的规范性和安全保障能力。  
如此看来，国家层面正高度重视软件供应链的安全问题，并通过不断建立健全法律法规、标准制度等，以保障供应链的完整性、保密性、可用性和可控性，这也是我们所有人都最该重视的安全问题之一。  
  

**\# Log4j2最新版本 #**

  
  
  
最新正式版本 Log4j 2.16.0 发布了，可用于生产环境。它默认禁用 JNDI 功能并移除了消息的 Lookups 功能，显而易见，这次更新的目的为了斩草除根，将未知风险扼杀在摇篮里，同时也是为了防止用户不小心开启。
