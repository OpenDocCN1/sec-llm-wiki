什么是JWT




JWT全称是JSON Web Token，是一种使用 JSON 作为数据载体，通过对称或非对称加密方式对数据进行加密并加签，可以安全传输数据保证不被数据篡改，一般用于认证 Authentication与授权 Authorization。

Header

Header是JWT的第一个部分，是一个 JSON 对象，主要声明了JWT的签名算法，如“HS256”、“RS256”等，以及其他可选参数，如“kid”、“jku”、“ x5u”等，其中比较关键的一些参数将在文中具体介绍。


Payload

Payload是JWT的第二个部分，这也是一个 JSON 对象，主要承载了各种声明并传递明文数据，一般用于存储用户的信息，如 id、用户名、角色、令牌生成时间和其他自定义声明。


Signature

Signature 是对 Header 和 Payload 进行签名，具体是用什么加密方式写在 Header的alg 中。同时拥有该部分的JWT被称为JWS，也就是签了名的JWT。


攻击方式



常规利用方式一般为针对 Header 中的参数进行篡改，进而操控密钥完成服务端对 Signature 部分校验步骤，实现签名校验步骤绕过，然后可以通过修改 Payload 中 id 、用户名等参数，实现伪造任意用户 token 的目的。


下面以靶场为例，学习JWT中的几种典型攻击方式。

1、敏感信息泄露



由于 Header 和 Payload 两部分是使用 Base64URL 方法编码的，所以这两个部分的内容是任何人都可以查看的。


如果这两个部分中传递敏感信息(例如密码、密钥等)，将会导致敏感信息泄露。

2、空算法验证



Header中“alg”参数用于声明加密算法，如果应用程序没有有效验证“alg” 的值，那么我们可以将其值更改为“none”，这样就不需要使用有效的签名进行验证。


这种配置一般是用于开发环境中测试使用，但是生产环境中也有可能因为开发人员误操作而导致此类问题的发生。


以靶场中 None Algorithm 为例，注册账号登录后可以看到 cookie 中 challenge 字段的值是JWT。

3、不验证签名内容



服务端如果没有对 JWT 签名部分进行校验，则可以直接删除最后的签名部分，最终格式为{Header.Payload.}，此时可以修改 Payload 内容为其他用户信息，并且令牌将始终有效。



4、密钥泄露&暴力破解密钥



JWT签名最常用的两种算法是 HMAC 和 RSA 。


HMAC是对称加密算法，使用同一个密钥对JWT进行签名和认证，这意味着对JWT进行签名的密钥也用于对其进行验证。


因此我们可以通过文件读取、SSRF等漏洞获得对密钥文件的访问权限，然后对其进行重新签名。


同时，由于使用的是对称加密算法，即使无法直接发现密钥泄露，我们仍然可以通过暴力破解的方式检查token是否使用弱密钥进行加密。


获取靶场 Weak Signature 中 JWT 进行解码后可以看到使用 HS256（ HMAC 算法的一种，也是JWT默认使用的加密算法)，因此可以对其密钥进行暴力破解。


python jwt_tool.py <JWT> -C -d wordlist.txt

成功获取密钥后，便可对经过篡改后的 Payload 重新进行签名。


5、密钥混淆攻击



除了 HMAC ，另一种常用加密算法是 RSA 。RSA 是非对称加密算法，需要两个密钥，先用私钥加密生成 JWT ，然后使用其对应的公钥来解密验证。


假设我们能够将签名算法从 RS256 更改为 HS256，我们就可以强制应用程序仅使用一个密钥来完成加密和解密这两项任务，此时服务端代码将使用公钥作为密钥，然后使用HS256算法验证签名。


此类攻击方式需要攻击者能够在程序中获取到泄露的公钥。


以靶场Exposed Key为例，靶场直接提供了公钥信息，将其复制保存为本地文件 public_key 。


接着我们使用本地的公钥文件对解码后的原始 token 使用 HS256 算法重新签名，然后替换到原始请求中查看返回内容是否正常，如果返回内容一致，则存在此漏洞，可以进一步篡改 Payload 字段中其他参数进行 token 伪造。

python jwt_tool.py -X k -pk public_key <JWT>

6、kid可操控



密钥 ID (kid) 是Header中一个可选标头，用于指示文件系统或数据库中存在的特定密钥，然后使用其内容来验证签名。


如果应用程序有多个用于签署令牌的密钥，那么这个参数就尤为重要。但是如果它的值是可以被操控的，攻击者便可以将其指向内容更改为可以预测的特定文件。


常见攻击方式为使用 Web 服务器中存在的文件，例如CSS或JS文件，并使用其内容来验证签名。


同时还有一种针对Linux系统更高效的方式，那就是我们可以直接将kid指定内容更改为“/dev/null”这个空设备文件。


获取靶场 Vulnerable Kid 中 JWT ，可以看到Header中有 "kid": "rsa_private"。


我们将kid内容修改为 /dev/null ，并将 Payload 中 name 修改为 admin ，然后生成新的 token 。

7、JKU & X5U可操控



在 Header 中除了 kid 外，JWT 还允许开发人员通过 URL 来指定密钥。同样，如果它的值是可以操控的，攻击者也可以将其 URL 更改为自己提前部署好的站点，进而操控密钥进行JWT伪造。


靶场只能验证五种基本攻击方式，后面几种类型攻击方法暂时没找到可以进行验证的靶场。


JKU

jku（JWK Set URL）表示把公钥信息放到指定的 URL 中，服务端通过访问URL来获取相应密钥进行校验，这样可以更灵活地切换密钥。

JKU的攻击原理就是通过篡改Header中jku的值，让服务端以我们指定的公钥进行JWT验证。

# 生成私钥openssl pkcs8 -topk8 -inform PEM -outform PEM -nocrypt -in keypair.pem -out privatekey.key

8、公钥注入



公钥注入方式与 jku 也有许多相似之处，相比于在 Header 中指定相应的 jku 值，有些应用程序则会选择将公钥直接嵌入到令牌中，相应的我们则可以尝试将它们直接替换为自己的公钥，并使用相应的私钥对令牌进行重新签名。

思路延伸



SQL注入

由于 Payload 中可能存在多个参数与数据库进行交互，因此在绕过签名后，可以尝试对Payload 中参数插入 sql 语句后重新加密请求，由此可能会导致注入产生。

python jwt_tool.py <JWT> -I -pc name -pv "admin' ORDER BY 1--" -S hs256 -k public.pem

除了 Payload 部分之外，如果 Header 中 kid 指定是从数据库中检索某些值的对应内容作为密钥，也可能会导致注入发生。

"kid":"admin' UNION SELECT 'secretkey';--"

上面这个注入因为数据库中不存在名为“admin”的密钥，所以会使用字符串“secretkey”作为密钥来认证token。


jku & x5u绕过

真实环境中为了确保jku指向的JWK服务器是可信的，应用程序通常会对指向的地址增加各种防护措施。常见方式是对指向的URL地址进行白名单限制。


我们在利用过程中常见的绕过思路是结合其他漏洞进行组合利用，比如利用JWK服务器本身的文件上传漏洞，对其JWK内容进行篡改，或是利用重定向漏洞，绕过白名单限制等。


使用JWT的安全建议



● 避免在令牌中直接传输用户的敏感数据以及系统内部的关键参数。

● 若使用对称加密算法，应使用强密钥提高秘钥破解的难度。

● 若使用非对称加密算法，应在服务端增加已授权算法的白名单，限制签名算法类型，防止密钥混淆攻击。

● 严格验证并过滤从用户端接收的数据，例如kid、jku等关键参数，防止因没有对参数进行正确校验而产生的安全风险。

● 在Payload字段中增加一些业务上的字段，用于校验当前JWT是否被滥用，例如增加设备号、权限的信息等，可以与上下文的信息进行对照。
