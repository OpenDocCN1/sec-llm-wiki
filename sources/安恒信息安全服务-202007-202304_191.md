**Header**

**Header**是JWT的第一个部分，是一个** JSON 对象**，主要声明了JWT的签名算法，如“HS256”、“RS256”等，以及其他可选参数，如“kid”、“jku”、“ x5u”等，其中比较关键的一些参数将在文中具体介绍。

  

**Payload**

**Payload**是JWT的第二个部分，这也是一个** JSON 对象**，主要承载了各种声明并传递明文数据，一般用于存储用户的信息，如 id、用户名、角色、令牌生成时间和其他自定义声明。

  

**Signature**

**Signature **是**对 Header 和 Payload 进行签名**，具体是用什么加密方式写在 Header的alg 中。同时拥有该部分的JWT被称为JWS，也就是签了名的JWT。

  

**攻击方式**

  
  

**常规利用方式**一般为针对 **Header 中的参数进行篡改**，进而操控密钥完成服务端对 Signature 部分校验步骤，实现签名校验步骤绕过，然后可以通过修改 Payload 中 id 、用户名等参数，实现伪造任意用户 token 的目的。

**4、密钥泄露&暴力破解密钥**

  

  

JWT签名最常用的两种算法是 **HMAC **和** RSA** 。

  

**HMAC是对称加密算法**，使用同一个密钥对JWT进行签名和认证，这意味着对JWT进行签名的密钥也用于对其进行验证。

  

因此我们可以通过文件读取、SSRF等漏洞获得对密钥文件的访问权限，然后对其进行重新签名。

  

同时，由于使用的是对称加密算法，即使无法直接发现密钥泄露，我们仍然可以通过暴力破解的方式检查token是否使用弱密钥进行加密。

**5、密钥混淆攻击**

  

  

除了 HMAC ，另一种常用加密算法是 RSA 。**RSA 是非对称加密算法**，需要两个密钥，先用私钥加密生成 JWT ，然后使用其对应的公钥来解密验证。

  

假设我们能够将签名算法从** RS256 **更改为** HS256**，我们就可以强制应用程序仅使用一个密钥来完成加密和解密这两项任务，此时服务端代码将使用公钥作为密钥，然后使用HS256算法验证签名。

  

此类攻击方式需要**攻击者能够在程序中获取到泄露的公钥**。

**6、kid可操控**

如果应用程序有多个用于签署令牌的密钥，那么这个参数就尤为重要。但是如果它的值是可以被操控的，攻击者便可以将其指向内容更改为可以预测的特定文件。

  

**常见攻击方式为使用 Web 服务器中存在的文件**，例如CSS或JS文件，**并使用其内容来验证签名。**

**使用JWT的安全建议**

  
  

● **避免**在令牌中**直接传输用户的敏感数据以及系统内部的关键参数**。

● 若使用**对称加密算法**，应使用强密钥提高秘钥破解的难度。

● 若使用**非对称加密算法**，应在服务端增加已授权算法的白名单，限制签名算法类型，防止密钥混淆攻击。

● **严格验证并过滤从用户端接收的数据**，例如kid、jku等关键参数，防止因没有对参数进行正确校验而产生的安全风险。

● **在Payload字段中增加一些业务上的字段**，用于校验当前JWT是否被滥用，例如增加设备号、权限的信息等，可以与上下文的信息进行对照。
