# 九维团队-青队（处置）| 页面篡改分析-http流量劫持页面篡改应急分析处置

写在前边

  

在近期的某次应急中，笔者注意到某客户web应用每隔一段时间移动端UA访问就会发生跳转现象，但并非传统的篡改，情况比较特殊，特在此记录分享，希望能对大家有所帮助。

  
  

  

首先我们对页面篡改安全事件的现象进行复现，观察页面篡改的实际情况：  
访问某页面，http://xxx/xx 偶尔会跳转到 https://xxxx.xxx/xxxx；https://xxxxxx.vip/ ，经确认访问后的特点除了以下几个返回内容之外，同时header存在max-age=0，触发方式不固定，而将UA修改为移动端或切换移动端UA访问会有一定几率触发跳转。

   

**跳转情况1:**

![](../Images/0d70fcd47f0f3025be36c159fb0980c4.png)

  

 使用top.location.href="xxx"，在样式顶层进行跳转，可以在iframe外进行跳转。  
  

**跳转情况2:**

![](../Images/e8c2447cac47a0c79c761aa47f877bc2.png)

  

 通过分析可以看到跳转的连接为 https://xxxxxx.vip/。  

![](../Images/fa4d041a897f31aa334e761ecf0e262a.png)

   

**跳转情况3:**

 

![](../Images/1f5b42a015ffc01b9e587a26a3e22632.png)

  
  

 也是使用了top.location.href="xxx"，使用的不同的地址跳转。  

  

![](../Images/2e8645ab49e068826449bf3fd795a75b.png)

  
由于每次跳转触发不固定，因此复现的时候也花了一点时间。

  

这里看到返回包的js，可以知道确实是通常相关黑灰产使用的js跳转方式。可以注意到此处使用了top.location.href的方式，这种方式可以在iframe之外进行跳转。

   
通常的页面篡改，到这里我们看到的现象是访问不论是页面还是js都会发生跳转，首要目的会思考是否页面中被插入的js导致返回的内容受控跳转。  

  

这里针对三种情况的关键词都在系统中进行全文查找内容， 结果并没有发现相关内容。  

  

![](../Images/cc45fab82a69013ec537dd19d462aba9.png)

  

接着查看相关的页面和js内容, 结果都没有发现可疑的脚本。

![](../Images/802cfff50b68c7cd9f268006937984b4.png)

   

![](../Images/0cbc8b7b88df764ba02edea60b45d037.png)

   
这里只在文件内容中发现了一些max-age=0的页面。  

![](../Images/7b5793743ca41b7fbca0cb4a157ee34e.png)

  
查看下中间件的配置, 发现中间件配置也没有发现问题。  

![](../Images/b109c89e0e930313fe005db3ec33c882.png)

  
到此为止，我们发现与传统的跳转方式都不同，与中间件控制的跳转方式也不同，因此考虑到是否存在劫持。

  

首先DNS劫持，经过排查发现不论是多地多运营商解析域名、还是通过dnslookup都没有看到域名解析异常情况，由于客户的域名是XX域名，使用修改本地的DNS为223.5.5.5以及223.6.6.6再访问还是有问题。但IP在以上情形下都无变化，因此判断不是DNS劫持情况。  

![](../Images/c11f0b2665dc9e077edb8b8155118c72.png)

   
随后，我们排除了系统异常登录、ssh密钥登录等情况，判断可能是流量劫持问题。

![](../Images/794102401c640cd4b3512966ffb3b9aa.png)

  

![](../Images/2e8645ab49e068826449bf3fd795a75b.png)

  

最终，笔者及同事给出了最终的排查解决方案。在服务端和客户端排查无异常的情况下，建议进一步排查措施：  
1、向相关运营商反馈请帮忙解决；  
2、建议加上证书，配置https防止网络层恶意接触；  
3、建立常态化安全监测机制，及时发现异常问题。

  
第二天客户反馈, 采用https+反馈运营商，问题解决，至此整个跳转情况结束。
