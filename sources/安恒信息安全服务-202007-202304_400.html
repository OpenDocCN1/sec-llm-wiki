3. 检测测试

进行了两次测试，以测试工具检测 IOC 和其他异常的能力的有效性。首先，使用 Metasploit 和图3中的步骤对三个 Windows 10工作站执行模拟攻击。第二个测试将活性恶意软件引入到环境中，并试图识别它所创建的修改。在每次测试之后，索伦之眼用于识别发生的更改，并使用 VMware 快照将工作站返回到其原始配置。


该测试遵循第2.1节中指示的步骤。首先，使用msfvenom，使用以下命令创建可执行文件。运行时，此可执行文件将建立与攻击者计算机上的Metasploit侦听器的连接。


使用 Meterpreter shell，通过 net user 创建本地帐户，然后使用 net group 命令将其添加到本地管理员组。此外，还使用类似的命令创建域账户并将其添加到域管理员组。创建 post/windows/manage/Persistence.exe 在注册表中以用户启动模式配置Metasploit模块。


使用创建的域管理员帐户，攻击通过 Metasploit 的 PSEXEC 模块转向第二个工作站。接着，使用与前面相同的模块建立持久性，但是需要将其作为一个新服务而不是启动键。最后，创建含恶意软件的网络共享用于攻击。


3.1.1结果分析

下列类别有助于深入了解这次攻击:

过程。如图6所示，在查找新进程时，有一个名为 fun.exe 的唯一进程，这是用于启动恶意软件的可执行文件的名称。虽然知道恶意软件的名称会使识别更容易，但是不知道 fun.exe 是恶意软件仍然会引起告警。对于一个进程来说，这是一个不寻常的名称，它运行在用户的下载目录中，其父进程 browser _ broker 是 Edge 浏览器的一部分。

图6新过程


新的进程还显示 PowerShell 在 WIN102上运行。运行 PowerShell 并不是什么异常现象，但是查看在 WIN102上运行的进程侦测到更多内容，包括进程使用的命令行。如图7所示，这些结果表明 PowerShell 的处理过程比最初想象的有趣得多，有效负载由一个编码命令组成，在大多数环境中这是极不寻常的，值得进一步研究。


图7在 WIN102上运行的带有一段加密 PowerShell 命令的进程


本地帐户和管理员组。检测新的本地帐户始终是需要关注的一个原因，如果它是本地管理员组的成员，则更是如此。这次攻击创建了两个账户，一个是本地账户，另一个是域名账户。此工具不会发现域帐户，因为它只查询本地系统。


图8新的本地帐户和本地管理员组的新成员


另一个选择是寻找新帐户，使用数据叠加来计算每个唯一帐户的出现次数，查找其中的异常情况(Fuchs，2020年)。图9中的这个总结显示了三个工作站上存在的五个帐户，而 evil 用户只存在于一个系统上。运行一个单独的查询系统可以显示哪个工作站有“evil”用户。


图9环境中发现的本地账户汇总表


服务。在过去24小时内创建的新服务显示了一个结果，如图10所示，它有一个不寻常的名称。进一步查看服务可以发现它正在运行一个来自 \Windows\TEMP directory的可执行文件。非法服务会从这个目录运行，也没有类似的名称，而且这是恶意软件安装的常见位置，因为登录用户将对该文件夹具有读写访问权限，不管他们是不是管理员。


图10在 WIN102上为持久性创建的服务


启动项目。当与部署新应用程序无关时，新的启动条目在企业环境中很少见。将创建限制在一个人或少数系统上，这样会变得更加可疑。查看图11中 WIN101上的新启动条目，可以看到它有一个异常名称，并从用户的 temp 目录运行。此外，可执行文件与先前发现的服务具有相同的名称。


图11 WIN101上的启动条目

图13“ qduTUYCZhya”启动项的查询


可执行文件。在发现具有异常特征的启动项和服务以及可疑文件之后，将运行查询以查看在过去30天内发现的可执行文件。这些结果表明 fun.exe 位于两个系统中，而用户 evil 和 用户default 分别位于不同系统中。它还显示了 evil 和 default 是基于 md5散列的同一个文件。需要对这些文件进行进一步分析，以验证它们是否是恶意的。

3.1.2. 结果摘要

在这个实验中，该工具能够找到本地系统的所有更改，并提供了被篡改的记录。它无法检测的是域帐户的创建，当然，这是原本设定的。然而，一些情况可能会影响这些结果。这个工具捕获了一个时刻，因此删除文件、停止进程和断开网络连接都会阻止这个工具检测它们。在注册表和服务中创建用于持久化的启动项将更难隐藏，但是为了避免被发现，可以不那么明显地命名。然而，仔细分析新的内容仍然会产生发现它们的高概率。


另一个可能严重影响工具识别异常能力的因素是配置管理。简单的组态管理使得识别未经授权的改变和异常变得相当困难，并导致更多的错误肯定。相比之下，严格的配置管理使这些异常更加明显。除了威胁狩猎，这个工具还可以帮助审计和执行组态管理。


这个工具并没有提供关于整个过程的清晰图片或路线图，只能看到确实有事件发生。这就需要对这些机器进行进一步调查并深入分析文件。这些发现的确提供了一些关键项目，如文件名、散列和外部 ip，以缩小对日志和其他安全工具的搜索范围。

3.2.1结果分析

利用索伦之眼对试验结果进行了分析。和以前的实验不同，恶意软件的行为是未知的，提供了一个更可能的现实世界的情景。对这些结果的分析揭示了以下问题:


新本地帐户。系统上有一个新的本地帐户，用户名是 TekDefense。该帐户不是本地管理员组的成员，需要对日志进行进一步研究，以确定关于该帐户的其他信息。


图18安装恶意软件后的新本地帐户


新进程。系统中有几个新的进程，如图19所示，值得进一步研究。特别是其中的两个，由于试图模仿名称略有更改的合法进程(lssas.exe 和 svchsot.exe，而不是 lsass.exe 和 svchost.exe) ，它们立即显示为恶意进程。其他三个有不异常的名称和路径，表明他们最有可能是恶意文件。


图19 WIN101安装恶意软件后的新进程


新的可执行文件。对负责新服务的可执行文件的进一步调查，提供了包括文件的 md5哈希的其他详细信息。结果还包含最后一次写入时间(从图20中删除) ，它可以提供事件发生时间的一些指示。识别这些文件是否是恶意的，可以通过搜索他们的网站，如病毒总计。


图20安装恶意软件后新的可执行文件，突出显示的项目是可疑的。


VirusTotal 中 lssas.exe 的散列验证文件是否是恶意的。它还提供了可以搜索并与事件相关联的其他行为，例如 IPs、域名和其他文件名。第二个例子是 lkpfye.exe 文件，VirusTotal 说这个文件通过 IP 148.81.111.121与 ilo.brenz.pl 通信，如图21所示。在工具的 netstat 和 DNS 部分中搜索这些条目会识别出类似的行为，稍后将介绍这些行为。


图21 lkpfye.exe 来自 VirusTotal，显示了一个域名和它与之建立连接的 IP


启动项目。搜索新的启动项将返回图22中的两个结果，由于随机名称，这两个结果看起来都很可疑。第一个条目启动 lssas.exe 进程，该进程已被识别为恶意进程，而第二个条目用于 rqxm.exe。之前的查询没有定义这个文件，对工作站的进一步调查显示这个文件是在2015年5月21日创建的。创建日期解释了因为集合脚本查询的是创建日期而不是修改日期，这表明该文件没有被创建，而是从不同的位置移动了，所以它没有被发现为一个新文件。在 VirusTotal 中研究这个文件的散列验证它是恶意的，并解析相同的 ilo.brenz.pl DNS 条目，这意味着它很可能与 lkpfye 可执行文件有关。


图22安装恶意软件后的新启动项


服务。如图23所示，有三项新服务是可疑的。其中两个服务正在使用以前被认定为可疑的可执行文件，而第三个服务 rgvrixx 运行“ svchost.exe-k netsvcs” ，似乎不属于该服务。需要对主机进行进一步研究，以确定关于此服务的其他信息。

图23安装恶意软件后的可疑服务

图24安装恶意软件后的网络连接


DNS 查询。图25所示的 DNS 查询也返回了两个可疑条目。对于 lkpfye 文件，这两个条目都解析为同一个 IP，并在 VirusTotal 中再次列出。

3.2.2结果汇总

在这个测试中，该工具发现了多个指标，需要从多个类别进行进一步调查。关联来自多个查询的数据可以提供更清晰的图像，并增加对恶意活动的怀疑。分析人员可能忽略单个指标，或可能全部忽略，例如没有作为新文件检测到的 rqxm.exe 文件。总的来说，它们为恶意软件操作提供了强有力的证据。


这些结果清楚地显示了可疑活动的发生，但一次是不足以把所有的碎片信息放在一起。需要进一步分析日志和网络数据。该工具提供了进程、文件名和散列、 ip 和 DNS 条目，以供进一步研究。


4.分析

在每个场景中，该工具都识别出表明潜在恶意活动的异常。这个工具并不是为了对这些发现进行深入的分析。相反，它试图显示新的或可疑的项目，并提供一种进一步搜索特定 IOC 的环境的方法，如文件散列。在这项研究中，这个工具被多次修改，以提供精确的结果，宣传其灵活性，以及防御者根据自己的需要改变它的能力。


在只有三个系统的小环境中，可能很难识别异常。当在拥有数百个工作站的组织中使用时，只要配置控制到位，结果就会变得更加清晰可读。在没有配置控制的环境中，该工具的有用性会急剧下降，因为它识别不属于的东西的能力需要有一个共同的基线。


4.1进一步改进

还需要进一步增强该工具，例如从数据库中提取 IOCs 并进行搜索。在这个实验中，发现异常和新项目比寻找单个指标更有成效。有必要继续对工具进行改进，并进行更高级的测试以更好地确定其功能。查询的性能也是一个问题。即使在很小的环境中，有些查询也需要一些时间; 例如，需要30多分钟才能溯源过去24小时内创建的新文件的查询。在更为庞杂的环境中，运行这样的查询是不可行的，因为它需要时间来获得结果。使用数据库而不是 CSV 文件存储是提高性能和功能的一个潜在可能性。


5.总结

监听客户端工作站是至关重要，因为它们是进入组织的门户。对于庞杂的环境，收集日志并通过 SIEM 处理它们可能是一项负担很重的任务，需要大量的存储和处理能力。“一家全球500强企业每月可以生成10TB的纯文本日志数据”(Constantine，2018)。由于需要收集大量数据，因此通常不包括客户端日志。相反，防御者依赖于网络和服务器提供的信息，这可能造成一个盲点，一个谨慎的对手可以在很长一段时间内定位和收集数据而不会被检测到，因此识别漏洞需要消耗平均时间较长。


对于有这种盲点的组织，索伦之眼通过自动化收集和数据分析提供了一些帮助。如果没有这样的工具，安全团队必须找到一种方法进入每个端点，手动收集数据，或者购买第三方工具来完成。虽然不如 OSQuery 强大，但是它可以快速、容易地实现，并提供对环境的即时洞察。它已被证明在发现异常、IOC和在这个实验中的一般变化方面是有用的。这是网络防御者的又一个必要工具，可以用来更好地保护他们的网络环境。
