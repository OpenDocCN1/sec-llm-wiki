0x00 前言

最近看到一篇取证分析文章讲的是ios的日志分析，正好身边有相关的设备，就决定跟着研究分析一下看看ios的日志中到底包含了什么。

0x01 抓取ios日志

设备版本号：

macos => 10.15.6ios   => 15.4.1
1.1 图形化抓包
图形化相对来说比较简单，分为两种情况：
1、若手机和电脑登录了同一个AppleID账号，处在同一网络下，可实现网络获取日志。2、若手机和电脑未登录同一个AppleID账号，则需要数据线进行连接，手机和电脑互相信任后，获取日志。
连接后，打开电脑上的控制台app。
可在左边边栏的设备处见到手机和电脑的相关标志。
右边则是日志，若需要查询相关的信息，在右上角搜索处直接进行关键词搜索就行了。
但是有个问题就是，控制台app显示的都是流化的日志，关闭后就丢失了，无法对抓到的日志进行单独的保存，若需要保存的话，就要使用命令行进行抓包。
1.2 命令行抓包
命令行抓包的相对来说麻烦一点，mac自带了一个命令叫做log命令，需要使用log命令进行日志的抓取、保存、查询、展示等功能。
若要抓取mac的日志，直接使用命令log collect即可。
若要抓取其他设备的日志，则需要再添加另外的参数。
在知道iphone的name情况下可以使用--device-name进行指定设备，若不知道name或者udid，则可以使用第三方工具libimobiledevice进行获取。macos系统使用brew install libimobiledevice命令进行安装，安装完后多了很多idevice开头的命令行工具。
其中，idevicename和idevice_id这两条命令是分别获取name和udid数据的。
获取到这两部分数据之后，就可以对设备进行指定，然后获取并保存日志了。
0x02 日志分析
2.1 加载日志
前面我们使用命令行获取了日志，接下来我们进行分析，使用log show命令，此时我们会发现是无法显示日志的，用控制台还是命令行都无法进行加载，报错原因是版本问题。
我们【右键=>显示包内容】，查看配置文件info.plist，在其中可以发现OSArchiveVersion的版本号为5
根据系统对应关系，10.15系统的OSArchiveVersion是4，无法读取OSArchiveVersion为5的日志包。
所以既然无法读取5版本的包，就直接走捷径，强行修改info.plist文件里的版本号，修改为4，当前系统就可以读取了。
修改完后就可以使用命令行和控制台app进行读取了。
 注意 ： 这里是我想当然了，本以为直接修改版本号即可在本系统上打开存储的日志数据包，但是通过这种方式读取的日志，存在部分数据无法解析的情况，只能以<compose failure [shared UUID]的形式展示，无法显示详细的数据。后来找了一台mac系统版本在12.1的电脑，才成功读取了OSArchiveVersion为5的数据包。
2.2 日志分析
2.2.1 AirDrop基础分析
首先，我们需要先确认用户的AirDrop ID是多少，AirDrop ID在设备的生命周期内是不一致的，会一直发生变化。
log show system_logs.logarchive --color always --predicate 'eventMessage contains "AirDrop ID"'
同时，在日志中还保存着一些当前设备的基础信息，其中包括了AirDrop当时使用的是哪种发现模式。
log show system_logs.logarchive --info --debug --color always --predicate 'eventMessage contains "SharingDaemon"'

里面包含了很多设备相关的信息，如下：

2.2.2 用户操作过程日志分析
AirDrop启动的过程被称为“ShareSheet”。启动启动分享窗口，用户可以选择如何分享项目。例如我想在照片应用程序中共享一张照片，我们可以选择隔空投送（Airdrop）、信息、邮件、微信等。

此时，日志中记录了整个屏幕的显示内容的用户操作过程，我们可以通过下面的命令来进行查询。
log show system_logs.logarchive --info --debug --color always --predicate 'category = "ShareSheet" or category = "SharingUI"'
查询到的结果中，分为几个部分：
第一部分：Activating com.apple.sharing.sharesheet这条信息，表明了有文件要进行分享，即将与com.apple.mobileslideshow(321)进行连接。
第二部分：Calling into PeopleSuggester和Received response from PeopleSuggester代表了项目正在寻找可以分享的人，显示有1个人被推荐。

第三部分：上面两张图，显示了用户在手机界面中看到的分享以及其他操作。

第四部分：Performing activity表明了用户选择了Airdrop功能。

第五部分：Item开头的后面接的GUID的内容代表了图片在分享前将要做的一系列操作，用GUID来进行跟踪，下面的路径则表示了文件分享前用于准备的临时路径，文件名则与分享的文件名一致。
2.2.3 AirDrop传输过程日志分析
当用户操作结束以后，AirDrop开始工作，我们可以通过如下命令查看：
log show system_logs.logarchive --info --debug --color always --predicate 'category = "AirDrop"'
将AirDrop进程筛选出来，我们就可以看到整个传输的过程了，分为以下几部分

第一部分：iPhone试图通过Bonjour和awdl发现可分享的联系人，找到了我的另一台待分享的设备（AirDrop ID:8de1d95833b4），然后与之成功建立连接。
第二部分：与对方成功建立连接后，准备开始进行发送，详细记录了发送过程所需的信息（文件名、文件类型、接收方姓名、接收方ID等），然后开始与nothing建立传输通道，对文件进行压缩，完成后进行发送，然后两次接收到对方发送的ask response和upload response，证明发送成功，最终结束传输通道，本次传输到此结束。
0x03 总结
以前从未接触过ios手机日志取证，本次学习过后发现手机日志中包含的信息很多，我们的每一步操作、每一次点击都会留下痕迹。通过分析发现，ios日志中只能记录传输的图片名称，无法记录传输的图片的具体内容，传输的具体内容是通过awdl的，应该可以通过网络抓包获取，暂时还不知道如何从手机端抓取流量，等后面学会了再抓抓看吧。
