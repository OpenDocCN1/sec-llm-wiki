0x00 前言

最近在复现网鼎杯朱雀组pwn题的时候，发现通过攻击exit_hook劫持程序流getshell,这种攻击方式在某些情况下可能会实现非预期解题，本文将通过两道利用exit_hook的题目来介绍二进制安全中的程序流劫持，相信看完这篇文章之后，你会对程序流劫持有更清晰的认识。

1.3 exit_hook详解

先来看一下exit()函数的源码：

voidexit (int status){__run_exit_handlers (status, &__exit_funcs, true, true);}libc_hidden_def (exit)

可以看套函数中调用了__run_exit_handlers函数，用gdb简单调试一下：

     0x7ffff7e09bc5 <exit+5>       pop    rax     0x7ffff7e09bc6 <exit+6>       mov    ecx, 1     0x7ffff7e09bcb <exit+11>      mov    edx, 1     0x7ffff7e09bd0 <exit+16>      lea    rsi, [rip + 0x1a1b41]         <0x7ffff7fab718>     0x7ffff7e09bd7 <exit+23>      sub    rsp, 8   ► 0x7ffff7e09bdb <exit+27>      call   __run_exit_handlers                <__run_exit_handlers>          rdi: 0x0          rsi: 0x7ffff7fab718 (__exit_funcs) —▸ 0x7ffff7fad980 (initial) ◂— 0x0          rdx: 0x1          rcx: 0x1
     0x7ffff7e09be0 <on_exit>      endbr64      0x7ffff7e09be4 <on_exit+4>    push   r12     0x7ffff7e09be6 <on_exit+6>    push   rbp     0x7ffff7e09be7 <on_exit+7>    push   rbx     0x7ffff7e09be8 <on_exit+8>    test   rdi, rdi

单步进入，发现调用了_df_fini函数，事实上这也是glibc十分常见的一种套娃式的函数调用现象。

1    0x7ffff7e1ea0a <__run_exit_handlers+218>    mov    rdi, qword ptr [rax + 0x20]2    0x7ffff7e1ea0e <__run_exit_handlers+222>    mov    qword ptr [rax + 0x10], 03    0x7ffff7e1ea16 <__run_exit_handlers+230>    mov    esi, ebp4    0x7ffff7e1ea18 <__run_exit_handlers+232>    ror    rdx, 0x115    0x7ffff7e1ea1c <__run_exit_handlers+236>    xor    rdx, qword ptr fs:[0x30]6  ► 0x7ffff7e1ea25 <__run_exit_handlers+245>    call   rdx                           <_dl_fini>7  8    0x7ffff7e1ea27 <__run_exit_handlers+247>    jmp    __run_exit_handlers+106                <__run_exit_handlers+106>
那就再看一下_df_fini函数的源码：
void_dl_fini (void){#ifdef SHARED  int do_audit = 0; again:#endif  for (Lmid_t ns = GL(dl_nns) - 1; ns >= 0; --ns)    {      /* Protect against concurrent loads and unloads.  */      __rtld_lock_lock_recursive (GL(dl_load_lock));
      unsigned int nloaded = GL(dl_ns)[ns]._ns_nloaded;      if (nloaded == 0#ifdef SHARED      || GL(dl_ns)[ns]._ns_loaded->l_auditing != do_audit#endif      )    __rtld_lock_unlock_recursive (GL(dl_load_lock));
这里省去了一部分注释，来方便阅读，可以看到又出现了调用 rtld_lock_default_lock_recursive 和 rtld_lock_default_unlock_recursive函数,下一步自然是观察一下这两个函数，在调试过程中会发现，在这两个函数调用之前都会给rdi赋值，所赋的值为某个地址：
 0x7ffff7fe0dba <_dl_fini+106>    lea    rdi, [rip + 0x1cba7]          <0x7ffff7ffd968>   0x7ffff7fe0dc1 <_dl_fini+113>    call   qword ptr [rip + 0x1d1a1]     <rtld_lock_default_lock_recursive>
 0x7ffff7fe0eca <_dl_fini+378>    lea    rdi, [rip + 0x1ca97]          <0x7ffff7ffd968>   0x7ffff7fe0ed1 <_dl_fini+385>    call   qword ptr [rip + 0x1d099]     <rtld_lock_default_unlock_recursive>
而这个地址实际上是_rtld_global._dl_load_lock.mutex.__size的地址。这样分析完，攻击的思路就很清晰了，可以通过改rtld_lock_default_lock_recursive 和 rtld_lock_default_unlock_recursive函数为one_gadget，或者改rtld_lock_default_lock_recursive 和 rtld_lock_default_unlock_recursive函数为system，并且改把 _rtld_global._dl_load_lock.mutex的值改为 /bin/sh\x00。两种方式都可以实现getshell，利用过程中可以通过libc基地址获取ld基地址，再通过ld获取_rtld_global地址。
0x03 总结
与常用的malloc_hook、free_hook、relloc_hook相比较，exit_hook不算是真正意义上的hook，严格来讲它是一种指针的劫持，与使用钩子劫持程序流还是有一定区别的，随着glibc版本的更新，很多攻击方式被修复，在libc2.34版本之后，hook基本退场，不过还是有师傅研究出了新的攻击手段，感慨技术发展之快的同时，也鼓励一下自己，长路漫漫，与君共勉。
