漏洞背景

GRUB2引导加载程序中的“ BootHole”漏洞使用安全启动来打开Windows和Linux设备的攻击。使用GRUB2和安全启动的所有操作系统都必须使用新的安装程序和引导加载程序。


前情提要

研究人员Mickey Shkatov和Jesse Michael在大多数Linux系统使用的GRUB2引导加载程序中发现了一个称为“ BootHole”的漏洞，即使启用了安全引导，该漏洞也可用于在引导过程中获得任意代码执行。
黑客利用此漏洞可以安装永久性的隐秘引导程序或恶意引导程序，从而使他们可以对受害设备进行几乎完全的控制。 
另外，GRUB2支持其他操作系统，内核和管理程序，例如Xen。该问题还扩展到将安全启动与标准的Microsoft第三方UEFI证书颁发机构一起使用的所有Windows设备。因此，大多数笔记本电脑，台式机，服务器和工作站，以及工业，医疗保健，金融和其他行业中使用的网络设备和其他专用设备均受到影响。此漏洞使这些设备容易受到攻击者的攻击，例如最近使用恶意UEFI引导加载程序的攻击者。

Eclypsium已与包括OS供应商，计算机制造商和CERT在内的各种行业实体协调了该漏洞的披露。缓解措施包括对新的引导加载程序进行签名和部署，同时撤消易受攻击的引导加载程序，以防止攻击者在攻击中使用较早的，易受攻击的版本。这将耗费很长的时间才能完成修补。

1.背景


安全启动可以是一个相当深入的技术性主题。我们在不深入所有技术细节的情况下，对与本研究相关的关键概念进行概括性介绍。我们提供了各种外部链接，为感兴趣的人提供一些了解。


1.1引导过程的威胁


引导过程是任何设备安全性中最根本的重要方面之一。它依赖于各种固件，这些固件控制如何初始化设备的各种组件和外围设备，并最终协调操作系统本身的加载。通常，加载的代码越早，特权就越高。

如果此过程受到威胁，则攻击者可以控制操作系统的加载方式，并破坏所有高层安全控制。最近的研究已经确定了使用恶意EFI引导加载程序在野使用勒索软件作为引导时控制计算机的一种方法。以前，攻击者使用恶意软件篡改了旧版操作系统的引导加载程序，包括   APT41 Rockboot，LockBit，FIN1 Nemesis，MBR-ONI，Petya / NotPetya和Rovnix。

有关对现代PC引导过程的威胁的其他信息，请参阅系统固件“ Bootkit和UEFI安全引导 ”部分。


1.2 UEFI安全启动


UEFI安全启动最初是由UEFI论坛开发的，目的是保护启动过程免受这些类型的攻击。安全启动还有其他针对不同环境设计的实现，但是UEFI安全启动是PC和服务器的标准。目的是通过在运行每个固件和软件之前对其进行加密检查，以防止将恶意代码引入引导过程。在启动过程中不会执行任何未被识别为有效的代码。 

安全启动使用密码签名来验证启动过程中所需的每段代码的完整性。此过程涉及两个关键数据库：已批准组件的Allow DB（db）和易受攻击或恶意组件（包括固件，驱动程序和引导程序）的Disallow DB（dbx）。修改这些数据库的访问受到密钥交换密钥（KEK）的保护，而密钥交换密钥又由平台密钥（PK）进行验证。尽管PK用作更新平台的信任根，但它显然不是引导过程的一部分（但在下面显示以供参考）。dbx，db和KEK用于在引导时验证已加载的可执行文件的签名。


1.3 信任链和GRUB2


接下来，OEM必须管理一个允许谁签署由安全启动数据库信任的代码的列表。通过安全启动，无需让每个OEM都管理每个可能的固件，驱动程序或OS提供商提供的证书，而是可以使用集中式证书颁发机构（CA）。微软的第三方UEFI CA为安全启动提供了行业标准的签名服务。简而言之，第三方可以将其代码提交给Microsoft，并且Microsoft将通过Microsoft CA验证并签署代码。这建立了一条信任链，仅要求OEM在启用安全启动时默认将Microsoft第三方UEFI CA注册到其平台上，以使它们能够默认启动第三方安装媒体和操作系统。


这包括从非Microsoft操作系统（例如Linux）对引导加载程序进行签名的功能。在几乎每个现代Linux发行版中，GRUB（大统一引导加载程序）都是用于将控制加载并转移到操作系统的引导加载程序。在本文档中，所有对GRUB的引用都旨在引用GRUB2，它是对以前称为“ GRUB传统”的以前版本的完整重写。从2009年开始，所有广泛使用的Linux发行版都已转变为使用GRUB2。GRUB Legacy已被弃用，通常仅在较旧的版本中找到。


由于许可证不兼容引起的法律问题，开源项目和其他第三方构建了一个名为“ shim”的小型应用程序，其中包含供应商的证书和验证并运行引导加载程序（GRUB2）的代码。使用Microsoft第三方UEFI CA对供应商的填充程序进行验证，然后，该填充程序将使用嵌入在自身中的供应商证书加载并验证GRUB2引导加载程序。


1.4 安全启动的挑战

与任何技术过程一样，安全启动也有潜在的问题。该过程涉及许多代码，其中任何一个代码中的漏洞都会导致单点故障，攻击者可能会绕过安全启动。此外，尽管UEFI安全启动尝试为启动过程提供某些完整性保证，但其他硬件配置错误或缺少保护功能也会破坏启动安全性。一个这样的例子是使用诸如PCIe Microblaze之类的工具的DMA攻击。此外，正如我们在这篇文章中所讲的，即使可以验证安全的启动签名，启动过程中的漏洞也可以使攻击者控制启动过程和操作系统，从而使任意代码得以执行。

攻击者还可以对系统使用易受攻击的引导程序。例如，如果发现有效的引导加载程序存在漏洞，则恶意软件可以用易受攻击的版本替换设备现有的引导加载程序。引导加载程序将被安全启动所允许，并赋予恶意软件对系统和操作系统的完全控制权。要缓解此问题，需要非常主动地管理用于标识恶意或易受攻击代码的dbx数据库。

此外，对安全启动过程的更新和修复可能特别复杂，并存在无意间破坏计算机的风险。引导过程会涉及各种组件和人员，包括设备OEM，操作系统供应商和管理员等等。考虑到引导过程的基本性质，任何类型的问题都极有可能导致设备无法使用。因此，对安全启动的更新通常很慢，需要进行广泛的行业测试。


2 通过GRUB2破坏安全启动

在Eclypsium的分析过程中，我们以GRUB2解析GRUB2配置文件（grub.cfg）中的内容的方式确定了一个缓冲区溢出漏洞。注意：GRUB2配置文件是一个文本文件，通常不像其他文件和可执行文件那样进行签名。此漏洞允许在GRUB2中执行任意代码，从而控制操作系统的启动。攻击者可以修改GRUB2配置文件的内容，以确保在加载操作系统之前运行攻击代码。这样，攻击者就可以在设备上获得持久性。 

该攻击要求攻击者具有更高的特权。但是，即使启用了安全启动并在所有已加载的可执行文件上正确执行签名验证，它也将为攻击者提供强大的设备特权和持久性升级。安全启动的显式设计目标之一是通过禁用安全启动或修改启动链来防止未经授权的代码（甚至具有管理员权限的运行）获得其他特权和OS之前的持久性。

除了一个可启动工具供应商的唯一例外，该供应商除了在GRUB2可执行文件上执行签名验证外，还添加了自定义代码来执行grub.cfg配置文件的签名验证，所有版本的GRUB2都从外部grub.cfg加载命令。配置文件容易受到攻击。因此，这将要求针对所有版本的Linux发布新的安装程序和引导程序。供应商将需要发布其引导加载程序的新版本，以由Microsoft第三方UEFI CA进行签名。重要的是要注意，在将所有受影响的版本添加到dbx吊销列表中之前，攻击者将能够使用易受攻击的shim和GRUB2版本来攻击系统。这意味着信任Microsoft第三方UEFI CA的每个设备在这段时间内都将受到攻击。

除了供应商使用由Microsoft第三方UEFI CA签名之外，一些同时控制其设备中的硬件和软件堆栈的OEM均使用出厂时提供给硬件的自已密钥直接对GRUB2进行签名。他们还将需要为这些系统提供GRUB2以前的易受攻击版本的更新和吊销。

漏洞分配了CVE-2020-10713“ GRUB2：精心构造的grub.cfg文件可能导致引导过程中执行任意代码”

2.1 漏洞分析

该漏洞是解析grub.cfg文件时在GRUB2中发生的缓冲区溢出。此配置文件是通常位于EFI系统分区中的外部文件，因此可以由具有管理员特权的攻击者修改，而无需更改已签名供应商shim和GRUB2 bootloader可执行文件的完整性。缓冲区溢出使攻击者可以在UEFI执行环境中获得任意代码执行权限，该代码可以用于运行恶意软件，更改启动过程，直接修补OS内核或执行许多其他恶意操作。
为了更深入地了解漏洞本身，我们将仔细研究代码在内部的工作方式。为了处理来自外部配置文件的命令，GRUB2使用flex和bison从语言描述文件和帮助程序函数生成针对特定域语言（DSL）的解析引擎。
与为每个DSL手动编写自定义解析器相比，通常认为这是一种更好的方法。但是，GRUB2，flex和bison都是复杂的软件包，具有自己的设计假设，很容易忽略。这些不匹配的设计假设可能会导致易受攻击的代码。

flex生成的解析器引擎将此定义包含为令牌处理代码的一部分：
#define YY_DO_BEFORE_ACTION \    yyg->yytext_ptr = yy_bp; \    yyleng = (int) (yy_cp - yy_bp); \    yyg->yy_hold_char = *yy_cp; \    *yy_cp = '\0'; \    if ( yyleng >= YYLMAX ) \        YY_FATAL_ERROR( "token too large, exceeds YYLMAX" ); \    yy_flex_strncpy( yytext, yyg->yytext_ptr, yyleng + 1 , yyscanner); \    yyg->yy_c_buf_p = yy_cp;


在此宏中，生成的代码检测到它遇到的令牌太大而无法放入flex的内部解析缓冲区并调用YY_FATAL_ERROR()，这是使用flex生成的解析器的软件提供的帮助函数。

但是，YY_FATAL_ERROR()GRUB2软件包中提供的实现是：
#define YY_FATAL_ERROR(msg)                     \  do {                                          \    grub_printf (_("fatal error: %s\n"), _(msg));     \  } while (0)
它不会停止执行或退出，而只是将错误输出到控制台并返回到调用函数。但是，在编写flex代码时就期望YY_FATAL_ERROR()不会再返回任何调用。这导致yy_flex_strncpy()被调用，并将源字符串从配置文件复制到一个太小而无法容纳它的缓冲区中。


API开发者和使用之间错误的假设是漏洞的非常普遍的来源。 

最终，通过为配置文件提供输入令牌，这些令牌太长而无法由解析器处理，此缓冲区溢出将覆盖堆中的关键结构。这些被覆盖的字段包括内部解析器结构元素，这些元素可以用作任意在哪里写的原语，以获取任意代码执行并劫持引导过程。


还要注意的是，UEFI执行环境没有地址空间布局随机化（ASLR）或数据执行保护（DEP / NX）或其他现代操作系统中常见的缓解漏洞的技术，因此，针对此类漏洞创建漏洞很容易。堆是完全可执行的，无需构建ROP链。

最后，此漏洞不是特定于体系结构的，而是在通用的代码路径中，并对已使用签名的ARM64版本的GRUB2进行了确认。


2.2 其他漏洞


在GRUB2中发现了几个先前的漏洞示例，这些漏洞导致任意代码执行，但范围要小得多。

2.3 影响


由于GRUB2解析其配置文件的方式存在缺陷，攻击者可以执行绕过签名验证的任意代码。Eclypsium发现的Boot Hole漏洞可用于安装持久的和隐秘的Bootkit或恶意Bootloader，即使启用了安全启动并正常运行，它们仍可运行。这样可以确保攻击者代码在操作系统之前运行，并且可以使攻击者控制操作系统的加载方式，直接修补操作系统，甚至将引导加载程序定向到备用OS映像。攻击者实际上可以不受限制地控制受害设备。最近在野外发现了恶意的引导程序，该漏洞会使设备容易受到这些类型的威胁的影响。 

从外部grub.cfg文件读取命令的所有GRUB2签名版本都容易受到攻击，从而影响每个Linux发行版。迄今为止，已知有超过80个shim受到了影响。除Linux系统外，将安全启动与标准Microsoft UEFI CA结合使用的任何系统都容易受到此问题的影响。因此，我们认为，当今使用的大多数现代系统，包括服务器和工作站，笔记本电脑和台式机，以及大量基于Linux的OT和IoT系统，都可能受到这些漏洞的影响。

此外，也可以绕过任何基于依赖UEFI安全启动的信任机制的硬件。



3 漏洞缓解


想要完全缓解此问题，需要多方协同努力：受影响的开源项目，Microsoft和受影响的系统的所有者，等等。措施包括：


（1）更新到GRUB2以解决该漏洞。


（2）Linux发行版和其他使用GRUB2的供应商将需要更新其安装程序，引导程序和垫片。


（3）新shim片将需要由Microsoft第三方UEFI CA签名。


（4）受影响的设备的管理员将需要在现场更新操作系统的已安装版本以及安装程序映像，包括灾难恢复介质。


（5）最终，需要在每个受影响的系统的固件中更新UEFI吊销列表（dbx），以防止在引导过程中运行此易受攻击的代码


但是，此撤消过程的完全部署可能很慢。与UEFI相关的更新具有使设备无法使用的情况，因此供应商必须非常谨慎。如果在更新给定的Linux引导加载程序和填充程序之前更新了吊销列表（dbx），则将不会加载操作系统。因此，随着时间的推移对吊销列表进行更新，以防止破坏尚未更新的系统。在某些情况下，很难更新dbx，例如使用双引导计算机或已取消配置的计算机。当安装或启动任何操作系统时，需要先对引导加载程序和操作系统进行更新，然后再将撤销应用于系统。

更为复杂的是，如果应用了dbx更新，则企业灾难恢复过程可能会遇到这样的问题，即已批准的恢复介质不再在系统上启动。此外，当由于硬件故障而需要进行设备交换时，相同型号的新系统可能已经应用了dbx更新，并且在尝试引导先前安装的操作系统时将失败。在将dbx更新发布到企业机群系统之前，还必须更新和验证恢复和安装介质。

Microsoft将发布一组已签名的dbx更新，该更新可应用于系统以阻止可用于加载GRUB2易受攻击版本的填充程序。由于存在建立系统或破坏操作或恢复工作流的风险，因此最初会将这些dbx更新提供给感兴趣的各方以手动将其应用于他们的系统，而不是推送撤销条目并自动应用它们。这将使IT专业人员，发烧友和其他人员有机会在强制执行吊销之前对其各自系统上的吊销更新进行测试，并确定所有问题。

组织还应确保它们具有监视系统中UEFI引导程序和固件以及验证UEFI配置（包括吊销列表）的适当功能。组织还应在可用更新时测试恢复功能，包括UEFI设置中的“重置为出厂默认值”功能。如果设备受到更新的负面影响，这将确保他们可以恢复设备。最后，组织应监视其系统中是否存在使用易受攻击的引导加载程序感染或破坏系统的威胁和勒索软件。


推荐建议


（1）立即开始监视引导加载程序分区（EFI系统分区）的内容。这将为其余过程节省时间，并有助于确定环境中受影响的系统。对于部署了Eclypsium解决方案的用户，您可以在设备的“ MBR / Bootloader”组件下看到此监视。

（2）继续照常在台式机，笔记本电脑，服务器和设备之间安装OS更新。攻击者可以利用OS和应用程序中的特权升级漏洞来利用此漏洞，因此防止他们获得对您系统的管理级别访问至关重要。此后，系统仍然容易受到攻击，但这是必要的第一步。稍后安装吊销更新后，旧的引导加载程序应停止工作。这包括应急磁盘，安装程序，企业黄金映像，虚拟机或其他可启动媒体。

（3）测试吊销列表更新。确保专门测试与现场使用的固件版本和型号相同的固件。它可能有助于先更新到最新固件，以减少测试用例的数量。

（4）要关闭此漏洞，您需要部署吊销更新。确保所有可启动媒体都已首先收到操作系统更新，一次仅将其缓慢推广至少量设备，并将从测试中学到的经验教训纳入此过程。

（5）与您的第三方供应商联系，以确认他们知道并正在解决此问题。他们应为您提供响应，以了解其对您提供的服务/解决方案的适用性，以及针对此严重漏洞的补救计划。


4 总结 


尽管大多数用户很容易将安全启动视为理所当然，但它是大多数设备中安全性的基础。一旦受到威胁，攻击者几乎可以完全控制设备，操作系统，应用程序和数据。而且，正如该漏洞表明的那样，当在启动过程中发现问题时，这些问题将对许多类型的设备产生深远的影响。
