漏洞背景

SMBv3.1.1压缩机制中的SMBGhost（CVE-2020-0796）漏洞已在大约三个月前修复，利用该漏洞可以进行本地特权提升。

漏洞研究团队发现，它不是SMB decompression功能中唯一的bug，在查看SMBGhost的漏洞功能时，又挖掘了另一个漏洞：SMBleed（CVE-2020-1206）。SMBleed与SMBGhost具有相同的功能。该错误使攻击者可以读取未初始化的内核内存，正如我们在本文中详细说明的那样。

同时利用SMBGhost和SMBleed，可以实现远程代码执行。

漏洞分析

该错误与SMBGhost（srv2.sys SMB服务器驱动程序中的Srv2DecompressData函数）具有相同的功能。下面是该函数的简化版本


typedef struct _COMPRESSION_TRANSFORM_HEADER{    ULONG ProtocolId;    ULONG OriginalCompressedSegmentSize;    USHORT CompressionAlgorithm;    USHORT Flags;    ULONG Offset;} COMPRESSION_TRANSFORM_HEADER, *PCOMPRESSION_TRANSFORM_HEADER;  typedef struct _ALLOCATION_HEADER{    // ...    PVOID UserBuffer;    // ...} ALLOCATION_HEADER, *PALLOCATION_HEADER;  NTSTATUS Srv2DecompressData(PCOMPRESSION_TRANSFORM_HEADER Header, SIZE_T TotalSize){    PALLOCATION_HEADER Alloc = SrvNetAllocateBuffer(        (ULONG)(Header->OriginalCompressedSegmentSize + Header->Offset),        NULL);    If (!Alloc) {        return STATUS_INSUFFICIENT_RESOURCES;    }      ULONG FinalCompressedSize = 0;      NTSTATUS Status = SmbCompressionDecompress(        Header->CompressionAlgorithm,        (PUCHAR)Header + sizeof(COMPRESSION_TRANSFORM_HEADER) + Header->Offset,        (ULONG)(TotalSize - sizeof(COMPRESSION_TRANSFORM_HEADER) - Header->Offset),        (PUCHAR)Alloc->UserBuffer + Header->Offset,        Header->OriginalCompressedSegmentSize,        &FinalCompressedSize);    if (Status < 0 || FinalCompressedSize != Header->OriginalCompressedSegmentSize) {        SrvNetFreeBuffer(Alloc);        return STATUS_BAD_DATA;    }      if (Header->Offset > 0) {        memcpy(            Alloc->UserBuffer,            (PUCHAR)Header + sizeof(COMPRESSION_TRANSFORM_HEADER),            Header->Offset);    }      Srv2ReplaceReceiveBuffer(some_session_handle, Alloc);    return STATUS_SUCCESS;}


Srv2DecompressData函数接收客户端发送的压缩消息，分配所需的内存，然后解压缩数据。如果“偏移”字段不为零，它将原样放置在压缩数据之前的数据复制到分配缓冲区的开头。


SMBGhost得以发生是因为缺少整数溢出的检查，即使进行整数溢出的检查，该函数仍然存在严重的漏洞。

通过将OriginalCompressedSegmentSize字段设置为一个巨大的数字来利用SMBGhost，从而导致整数溢出，然后越界写入。如果我们将其设置为一个比发送的实际解压缩数据大一点的数字怎么办？例如，如果解压缩后压缩数据的大小为x，并且将OriginalCompressedSegmentSize设置为x + 0x1000，则将得到以下内容：

未初始化的内核数据将被视为我们消息的一部分。您可能会认为Srv2DecompressData函数调用应该由于SmbCompressionDecompress调用之后的检查而失败：

if (Status < 0 || FinalCompressedSize != Header->OriginalCompressedSegmentSize) {    SrvNetFreeBuffer(Alloc);    return STATUS_BAD_DATA;}

具体来说，在我们的示例中，您可能假设OriginalCompressedSegmentSize字段的值为x + 0x1000，但在这种情况下，FinalCompressedSize将设置为x。实际上，由于SmbCompressionDecompress函数的实现，FinalCompressedSize也将设置为x + 0x1000：

NTSTATUS SmbCompressionDecompress(    USHORT CompressionAlgorithm,    PUCHAR UncompressedBuffer,    ULONG  UncompressedBufferSize,    PUCHAR CompressedBuffer,    ULONG  CompressedBufferSize,    PULONG FinalCompressedSize){    // ...     NTSTATUS Status = RtlDecompressBufferEx2(        ...,        FinalUncompressedSize,        ...);    if (status >= 0) {        *FinalCompressedSize = CompressedBufferSize;    }     // ...     return Status;}


如果成功解压缩，则将FinalCompressedSize更新为保留CompressedBufferSize的值，该值是缓冲区的大小。对FinalCompressedSize值的故意更新使对SMBGhost的利用更加容易，并且还允许存在SMBleed错误。


利用漏洞的SMB消息是SMB2 WRITE消息。消息结构包含字段，例如要写入的字节数和标志，后跟可变长度缓冲区。SMB2 WRITE是利用该漏洞的完美之选，因为我们可以编写一条消息以指定标头，但可变长度缓冲区包含未初始化的数据。我们将POC基于Microsoft的WindowsProtocolTestSuites存储库（我们也将其用于第一个SMBGhost复制），为压缩功能引入了这一小的补充：

// HACK: fake sizeif (((Smb2SinglePacket)packet).Header.Command == Smb2Command.WRITE){    ((Smb2WriteRequestPacket)packet).PayLoad.Length += 0x1000;    compressedPacket.Header.OriginalCompressedSegmentSize += 0x1000;}

该漏洞利用需要凭据和可写共享，在许多情况下都可以使用这些凭据和可写共享，但是该错误适用于每条消息，因此无需身份验证就可以被利用。还要注意，泄漏的内存来自NonPagedPoolNx池中的先前分配，并且由于我们控制分配大小，因此我们也许能够在某种程度上控制泄漏的数据。

解决方案

1. Windows更新将完全解决问题（推荐）

2. 阻塞端口445将阻止使用漏洞内网漫游

3. 加强主机隔离

4. 禁用SMB 3.1.1压缩（不推荐）
