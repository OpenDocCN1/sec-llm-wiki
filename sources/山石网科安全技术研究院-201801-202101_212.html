事件来源

近日，山石网科安全应急响应中心（HSCERT）监测到大量Sodinokibi勒索病毒的攻击事件，我们对Sodinokibi勒索病毒样本进行了跟踪分析，Sodin最早出现在2019年上半年，它通过Oracle Weblogic漏洞进行分发攻击，并对MSP提供商进行攻击。在详细分析中，我们发现它还利用CVE-2018-8453漏洞来提升Windows中的权限（这在勒索软件中很少见），并使用合法的处理器功能来规避安全解决方案。

计算私钥和公钥，如图所示


私钥和公钥的计算方法如下:


私钥是由256位随机数生成的，从图中可以看到随机数生成子程序PRNG(伪随机数生成器):


该函数生成的PRNG使用的是硬件the hardware Intel Ivy Bridge，基于NIST的SP 800-90准则，通过调用汇编rdrand指令


生成的随机数，在成为私钥之前，私钥和公钥使用ECC(椭圆曲线密码术)生成。密钥(私有和公共)都是256位的两个数字，它们定义椭圆曲线上的两个点。密钥交换采用“椭圆曲线Diffie-Hellman”(ECDH)方法，其中:

dAPB = dBPA

给定曲线的不动点G，其中:

dA = private key of A (secret random number)

PA = G*dA = public key of A (G multiplied by dA)

dB = private key of B (secret random number)

PB = G*dB = public key of B


Sodinokibi使用eliptic curve“Curve25519”，其中G={9}，由Dan Bernestein开发。


Sodinokibi在内存中生成ECC密钥对后，公钥存储在pk_key值内部的recfg regisry密钥中我们将其称为dk_key(私钥)和pk_key(公钥)，:

HKEY_LOCAL_MACHINE\SOFTWARE\recfg

[pk_key] = Public Key

 

此时，调用Sub_13597B函数生成sk_key数据结构:

pBuff_sk_key = Sub_13597B (key_pubblica_json, key_privata, size IN, size out)

Sub_13597B的目的是加密sk_key数据结构中生成的私钥。


Sub_13597B函数有4个输入参数:

key_pubblica_json: public key “pk” inside the json configuration section

key_privata: private key generated “dk”

size IN: size of “dk”

size out: sk_key structure dimension


Sub_13597B函数执行以下步骤:

分配一个0x58字节的缓冲区，并将私钥(dk_key)“key_privata”从偏移量0x4复制到缓冲区中

计算一对新的ECC密钥，一个私有密钥(dk_new)和一个公共密钥(pk_new)

计算dk_new*pk -> shared_key_new(其中pk是json配置部分中的公钥)，结果是SHA-3的“hashato”

计算一个16字节的随机数——> random_16，它将被用作IV(初始化向量forAES)

通过IV初始化向量和SHA-3 (shared_key_new)通过AES-256 CTR将从0分配到0x24的缓冲区加密

将公钥pk_new复制到偏移0x24处分配的缓冲区中

将随机数random_16复制到偏移0x44处分配的缓冲区中

计算从0分配到0x24的缓冲区的CRC32，并将结果保存在偏移量0x54处

Sub_13597B函数返回指向缓冲区的指针，该缓冲区在sk_key数据结构中分配给0x58字节。

每一个要加密的文件都会生成一个Salsa20密钥，如下:


Sodinokibi使用的加密算法是Salsa20。

Salsa20的加密密钥是这样获得的:

计算一对新的ECC私钥/公钥(dk_new_file, pk_new_file)

计算SHA-3 (dk_new_file*pk_key) -> shared_key_salsa(其中pk_key是存储在注册中心pk_key voice下的公钥)。在shared_key_salsa中，我们将获得插入到Salsa20主表中的密钥。

为Salsa20主表的初始化向量计算一个8字节的随机数。

组成Salsa20主表


它在内存中创建一个数据结构，其中包含:

Handle of the file to be encrypted

sk_key

0_key

pk_new_file

Initialization vector of Salsa20

The CRC32 of pk_new_file

Master table of Salsa20


这个数据结构通过API函数传递给之前创建的线程:

CreateIoCompletationPort

PostQueuedCompletionStatus


线程挂起在GetQueuedCompletionStatus API函数上，当它接收到一个新的调用时，它通过Salsa20算法启动文件加密阶段，然后添加包含以下字段的部分数据结构:

sk_key

0_key

pk_new_file

Initialization vector of Salsa20

The CRC32 of pk_new_file


附加部分的大小取决于Sodinokibi恶意软件的版本。在版本1.0和1.1中，长度是0xE0字节，而在版本1.2中是0xE4字节。

恢复Sodinokibi加密文件的唯一方法是使用dk_key私钥,解密密钥在sk_key和0_key中加密。

攻击者通过以下方式恢复dk_key:

Decrypting  sk_key

Decrypting  0_key

 

为了解密sk_key，攻击者使用一个秘密密钥，即只有他们知道的私钥dk。私钥dk是存储在json配置中的公钥pk的对称密钥。

公钥pk_new以未加密的方式放在sk_key结构中。

计算值为:dk * pk_new = shared_key_new


shared_key_new与:dk_new*pk相同。

私钥(dk_key)是通过SHA-3 (shared_key_new)和偏移0x44上的随机数(IV)用AES-256 CTR加密的。

通过SHA-3 (shared_key_new)和得到的随机数dk_key，用AES-256将缓冲区从0x4解密到0x24。

现在可以执行相同的过程解密0_key，在本例中使用主私钥(只有Sodinokibi的作者知道)来获得dk_key。



现在知道了dk_key，为了确定Salsa20中使用的加密密钥，执行以下操作:

SHA-3 (dk_key *pk_new_file) = shared_key_salsa

 

其中公钥pk_new_file以未加密的方式放在加密文件的末尾。

shared_key_salsa=SHA-3 (dk_new_file*pk_key)


在shared_key_salsa中将拥有插入到Salsa20主表中的键。现在可以通过shared_key_salsa解密文件。
