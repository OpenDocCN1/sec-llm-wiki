分 析 复 现

![](../Images/20fc93ba0de255e5c242c5658672fcbc.png)![](../Images/20fc93ba0de255e5c242c5658672fcbc.png)首先是斗象发出的通报关于漏洞描述：

> 该漏洞源于Grafana 在获取公共插件资产的相关函数中对于路径参数的字符清理不当，导致攻击者可以通过将包含特殊目录遍历字符序列(../)的特制HTTP请求发送到受影响的设备来利用此漏洞。成功利用该漏洞的攻击者可以在目标设备上查看文件系统上的的任意文件。

一个go写的项目，在简单搜索了一个各种关键字，如`/admin`,router后能够将路由点定位到：pkg/api/api.go能够看到这块有很多路由：![](../Images/226d087f2d823e3dd814f8278d4b9af8.png)描述中如此写到：在获取公共插件资产的相关函数中对于路径参数的字符清理不当因此搜索一下plugins，其实很容易能够定位到：

```
r.Get("/public/plugins/:pluginId/\*", hs.getPluginAssets)
```

跟入getPluginAssets函数内：![](../Images/1ffc65331ec5f60b68d3358352944385.png)很明显了，os.Open做了一次容易文件读，不过造成漏洞的关键还是在于：filepath.Clean![](../Images/aededba0a39894e35d636569605954ef.png)尽管它会处理..，但处理方式如下：

*   它消除了每个内部..路径名元素(父目录)以及在其前面的non ..元素
*   它消除了..元素开始于根路径：即，在分隔符为“ /”的情况下，在路径的开头用“/”替换“/..”

因此此处的逻辑为从\*的路径获取requestedFile，随后将plugin.PluginDir和requestedFile做了一次拼接，原意其实就是一个动态调用插件的功能，不过因为使用的filepath.Join拼接插件的目录，所以可以简单使用../来做路径回溯达成任意文件读的效果。最后只需要寻找一个存在的插件：

```
/public/plugins/welcome/../../../../../../../../etc/passwd
```

绕 过 反 向 代 理

![](../Images/20fc93ba0de255e5c242c5658672fcbc.png)![](../Images/20fc93ba0de255e5c242c5658672fcbc.png)

  

在实际利用时我们与grafana之间通常还会经过一层反向代理，而我们的../会被路径规范化，具体可看：https://www.acunetix.com/blog/articles/a-fresh-look-on-reverse-proxy-related-attacks/例如绕nginx可以采用：

```
/public/plugins/welcome/#/../..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f/etc/passwd
```

> /#/../console/
> 
> When Nginx starts processing the request, it throws off everything after `#`, so it skips the `/console/` rule. It then forwards the same unprocessed path (`/#/../console/`) to the Weblogic, the Weblogic processes the path and after path normalization, we are left with`/console/`.
