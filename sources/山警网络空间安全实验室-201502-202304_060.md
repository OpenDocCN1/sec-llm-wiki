> 反序列化漏洞在各个语言里本不是一个新鲜的名词，但在 2015 年 @gebl 和 @frohoff 在 AppSecCali 上提出了利用 Apache Commons Collections 来构造命令执行的利用链，并在年底因为对 Weblogic、JBoss、Jenkins 等著名应用的利用，一时激起千层浪，彻底打开了一片 Java 安全的蓝海。

两位原作者在此议题中释出的一个里程碑式的工具——ysoserial，它可以让用户根据自己选择的利用链，生成反序列化利用数据，通过将这些数据发送给目标，从而执行用户预先定义的命令。

## 什么是利用链

利用链也叫 “Gadget Chains”，我们通常称为 Gadget。在 PHP 反序列化漏洞中，可以将 Gadget 理解为一种方法，它连接的是从触发位置开始到执行命令的位置结束，在 PHP 中可能是 `__desctruct` 到 `eval`。如果你没学过其他语言的反序列化漏洞，那么 Gadget 就是⼀种生成 POC 的方法罢了。

## URLDNS

URLDNS 就是 ysoserial 中的一个 Gadget 的名字，但准确来说，这个其实不能称作 “利用链”。因为其参数不是⼀个可以 “利用” 的命令，而仅仅是⼀个 URL，其能触发的结果也不是命令执行，而是一次 DNS 请求。

虽然这个 URLDNS 实际上是不能 “利用” 的，但因为其如下的优点，非常适合我们在检测反序列化漏洞时使用：

*   使用 Java 内置的类构造，对第三方库没有依赖。
*   在目标没有回显的时候，能够通过 DNS 请求得知是否存在反序列化漏洞。

### 构造利用链

回顾前面的反序列化过程，`key` 是使用 `s.readObject()` 方法取出来的：

![](../Images/2c9fc57dd92deff0a1e2d7e6c766e7cf.png)

也就是说在 `HashMap.writeObject()` 方法中一定有类似 `s.writeObject(key)` 的操作。我们找到 `HashMap.writeObject()`，并在这里下断点：

![](../Images/d35c4057aabc23ca286521c0c46c6330.png)

步步跟进最终进入 `internalWriteEntries(s)` 方法：

![](../Images/83813447335b88824d3946b96476d87d.png)

不难发现，这里的 `key` 和 `value` 是从 `tab` 中取的，而 `tab` 的值即 HashMap 中 `table` 的值，要想改变 `table` 的值，就需要调用 `HashMap.put()` 方法。

知道了反序列化的调用流程后，我们可以自己手动构造出这个链子。要构造这个 Gadget，只需要初始化一个 java.net.URL 对象，作为 `key` 放在 java.util.HashMap 对象中。然后，设置这个 URL 对象的 hashCode 为初始值 -1，这样反序列化时将会重新计算其 hashCode，才能触发到后面的 DNS 请求，否则不会调用 `URL.hashCode()`。相关代码如下：

但是，上述 POC 在运行时就会触发 DNS 查询，我们通过调试寻找原因。在 `ht.put(u, url)` 处下断点进行动态调式：

![](../Images/13842ce4b5ef3c44b1a360366ddeb64f.png)

步入 `ht.put(u, url)` ，来到 `HashMap.put()`：

![](../Images/21f91ca9870ec6d90c557a4a6f236450.png)

可以看到，在 `HashMap.put()` 也一次调用了 `hash()` 方法，我们知道，在反序列化过程中，正是通过 `hash()` 最终调用了 `URLStreamHandler.getHostAddress()` 执行了 DNS 查询，那么是不是由于这里，导致在生成序列化 Payload 的时候触发 DNS 查询呢？

我们继续步入，最终又来到了 `URL.hashCode()` 方法：

![](../Images/b43d9032f23217c27cdc58be96ef2c3f.png)

可以看到，由于这里默认情况下 `hashCode` 变量为 -1，也就会直接绕过 `if{}` 语法直接进入 `hander.hashCode()`，根据前文的分析结果，最终会调用 `URLStreamHandler.getHostAddress()` 发起 DNS 请求。

### Yoserial 利用链构造分析

下面让我们分析一下 ysoserial 是如何构造这个 Gadget 的。

首先找到 ysoserial 的入口类 GeneratePayload.java，设置 IEDA 的 “Run/Debug Configurations”，在 “Program arguments” 处添加以下运行参数：

```
URLDNS "http://jroj1a.dnslog.cn"

```

![](../Images/5c48f50e54f6e45df7a4a348a56edd95.png)

然后在 GeneratePayload 类的 `final Class<? extends ObjectPayload> payloadClass = Utils.getPayloadClass(payloadType);` 处下断点，开始动态调试：

![](../Images/33d045927450e53f289cfbe226f06957.png)

`Utils.getPayloadClass()` 为 ysoserial 中用来获取目标类的方法，跟进 `Utils.getPayloadClass()`：

![](../Images/d178e8a71a8401c7ec99e68eed47206b.png)

可以看到，在该方法中通过用户提供的 `className` 执行反射，以获取的指定的类。但此时 `className` 为 URLDNS，`Class.forName(className)` 将获取到 `null`。因为此时 `className` 只是个类名，URLDNS.java 位于 `ysoserial.payloads`，要想获取到 URLDNS 类需要使用它的完全限定名称。

继续步入，来到如下图所示位置：

![](../Images/a5db6d8d839e3be656516852b4859aff.png)

这里 `if{}` 检测到 `clazz` 为 `null`，会继续将 URLDNS 类名转换为完全限定名称，也就是 `ysoserial.payloads.URLDNS`，然后再次调用 `Class.forName()` 成功获取到 URLDNS 类。

继续步入，来到下图所示位置：

![](../Images/12f0224e6b36fada52f6e198c19a6930.png)

这里通过 `newInstance()` 将获取到的 URLDNS 类初始化，然后直接调用 `ysoserial.payloads.URLDNS` 中的 `getObject()` 方法，获取 Payload 对象。

继续步入，终于来到了 URLDNS 类：

![](../Images/1e1b9ec9362af5c55d6e4f3b6de9c1ff.png)

首先通过获取一个 SilentURLStreamHandler 类的对象，并将其赋给 `handler`，这个 SilentURLStreamHandler 类有什么作用？

如下图所示，我们可以看到，在 URLDNS 类中定义了 SilentURLStreamHandler 内部类，并继承自 URLStreamHandler 类，同时重写了父类 ` URLStreamHandler` 中的 `getHostAddress()` 方法，然后直接 `return null`。

![](../Images/cf8bf1e0eaf9079286fa30986421f84a.png)

目前还不知道这个 SilentURLStreamHandler 内部类的作用，因此我们继续往下分析。继续跟进，直到调用 URLDNS 类中的以下代码：

![](../Images/aaf018ce7a5ce6bb6de4a021f60a396d.png)

这里初始化一个 java.net.URL 对象，这里会调用 URL 对象的构造方法又多个重载，这里调用的是以下重载：

```
public URL(URL context, String spec, URLStreamHandler handler) throws
 MalformedURLException
```

执行后，会在 URL 对象中将 `this.handler` 设为 URLDNS 的内部类 SilentURLStreamHandler 的对象：

![](../Images/c97fe2172ae6a5e7e9186d8550fe0dea.png)

到这一步也就明朗了，在 URLDNS 通过实例化 URLStreamHandler 的子类 SilentURLStreamHandler，调用子类的 `getHostAddress()` 方法，避免了调用父类的 `getHostAddress()`，完美地规避了在序列化的时候执行 DNS 查询。

当后续过程中从 `URLStreamHandler.hashCode()` 方法调用到 `getHostAddress()` 方法时，并不是调用的 `URLStreamHandler.getHostAddress()`，而是 `SilentURLStreamHandler.getHostAddress()`，由于 SilentURLStreamHandler 在继承 URLStreamHandler 后重写了 `getHostAddress()` 方法，使其直接 `return null`，自然不会继续往后调用 `InetAddress.getByName()` 来执行 DNS 查询了。这与我们在前面手动编写 POC 时通过反射修改 `hashCode` 属性值的方法有异曲同工之妙。

那么此时你可能有一个疑问，重写 `getHostAddress()` 后进行序列化，为什么在反序列化的时候又可以重新触发 DNS 查询了呢？是因为这里的 URL 对象中的 `handler` 属性被修饰符 transient 所修饰，如下图所示。

![](../Images/376e4c4184b8dd57edf239f3d9875a66.png)

当序列化的对象包含被 transient 修饰的实例变量时，JVM 将跳过该特定的变量。也就是说这个 `handler` 属性无法被序列化，所以最终反序列化的时候，URL 对象中的 `handler` 属性依然是其初始类型，也就是 URLStreamHandler，不会变为 SilentURLStreamHandler。这也就解释了为什么前文反序列化后获取的 `handler` 的类型并不是前面设置的 SilentURLStreamHandler 了。
