heap exploitation巩固——IO_file

前言

本来想把这个放在后面的，但是发现glibc2.34下，取消了free_hook和malloc_hook（难过），大佬发现了可以替代的io调用链，用于没有听summerN的话及时总结，所以现在来狼狈不堪的亡羊补牢一下QAQ

IO_FILE结构

ILE 在Linux系统的标准 IO 库中是用于描述文件的结构，称为文件流。FILE 结构在程序执行 fopen 等函数时会进行创建，并分配在堆中，然后以链表的形式串联起来，但系统一开始会自动创建的三个文件即stdin、stdout、stderr，它们是在libc上。

struct _IO_FILE_plus
{
    _IO_FILE    file;
    _IO_jump_t   *vtable;
}

IO_file_plus的结构大致包括这两个部分，一个是_IO_FILE file结构，还有一个是_IO_jump_t *vtable指针，简单来说就是IO_FILE_PLUS的结构是由io_file结构还有一个指针构成的。整体的结构看起来是这样的：

我们看到io_file的结构里面有个_chain这个指针指向stdin，我们继续跟踪下去我们发现结构是这样的_chain->stderr->stdout->stdin。

需要注意的是，io_file是_IO_FILE_plus的一部分，_IO_FILE_plus除了io_file还有一个vtable指针。

IO的利用

利用IO泄露libc（leak）

此方法常用于没有show功能的堆题中。

主要的思路就是修改_IO_2_1_stdout_的flags，还有_IO_write_base、_IO_write_ptr

常见的结构是这样的

int _flags;
    char *_IO_read_ptr;
    char *_IO_read_end;
    char *_IO_read_base;
    char *_IO_write_base;
    char *_IO_write_ptr;
    char *_IO_write_end;
    char *_IO_buf_base;
    char *_IO_buf_end;
    char *_IO_save_base;
    char *_IO_backup_base;
    char *_IO_save_end;

我们需要做的就是将flags修改成0xfbad18**，为了设置_IO_CURRENTLY_PUTTING=0x800，_IO_IS_APPENDING=0x1000，IO_MAGIC=0xFBAD0000

_IO_write_base是要泄露地址的起始地址，_IO_write_end是指要泄露的结束地址。之后在遇到printf或者puts的时候就将指向的内容打印出来，

我们惯用的方法就是将flags设置为0xfbad1800，然后将_IO_read_ptr，_IO_read_end，_IO_read_base;设置为0，最后将_IO_write_base的低位设置为'\x00'。

FSOP

这一部分原理性的东西，有些不太理解，我尽力去写一些我所理解到的东西。

（当然图是piao的）

_IO_list_all，利用每个file的_chain将stderr、stdout、stdin连在一起。有了这个链表我们就很好理解fsop的原理了。就是通过修改file链表中的节点来劫持程序的执行流。利用程序中的漏洞来覆盖_IO_list_all(全局变量)来使链表指向一个我们能够控制的区域，从而改写虚表*vtable。通过调用 _IO_flush_all_lockp()函数来触发,，该函数会在下面三种情况下被调用：

1：当 libc 执行 abort 流程时。

2：当执行 exit 函数时。当执行流从 main 函数返回时

3：当执行流从 main 函数返回时

当glibc检测到内存出现错误的时候函数的调用链为：

malloc_printerr ->libc_message->__GI_abort -> _IO_flush_all_lockp -> _IO_OVERFLOW

既然有了调用链，我们就可以通过劫持_IO_OVERFLOW来控制程序的执行流。

同时我们还需要绕过检测：

if (((fp->_mode <= 0 && fp->_IO_write_ptr > fp->_IO_write_base)   
#if defined _LIBC || defined _GLIBCPP_USE_WCHAR_T
       || (_IO_vtable_offset (fp) == 0
           && fp->_mode > 0 && (fp->_wide_data->_IO_write_ptr
                    > fp->_wide_data->_IO_write_base))
#endif
       )
      && _IO_OVERFLOW (fp, EOF) == EOF)

只需要伪造fp->_mode = 0， fp->_IO_write_ptr > fp->_IO_write_base即可。

在glibc2.24以及之后，程序会对vtable的合法性进行校验，不能想之前一样将其改为堆地址。

但是我们可以寻找到合法的指针—— _IO_str_jumps。可以利用它来绕过检查。

看下 _IO_str_jumps指向的结构

IO_str_overflow在虚表中的偏移为0xe0，所以我们在利用的时候，将_IO_str_jumps结构偏移为0xe0的地方修改为gadget，然后将vtable的指针指向_IO_str_jumps即可实现劫持。
