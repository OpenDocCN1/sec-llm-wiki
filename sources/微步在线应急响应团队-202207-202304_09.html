3、Zegost 僵尸网络
目前网络上有大量的僵尸网络家族，SQLServer蠕虫模块基本就是其标配了，以 Zegost家族为例，根据我的观测分析，他们主要通过ftp来分发恶意软件，在获取到一台SQL Server的执行权限后，会将SQLServer 能去执行命令的手法都挨个尝试一遍，以此来下载传播恶意软件。
在执行SQL语句时，他们会通过“DECLARE”来声明一个长度为8000字节的变量“@a”，然后将要执行的SQL 语句进行16进制编码后赋值给变量“@a”，最后调用 Exec执行变量“@a”达到执行SQL语句的效果，从而躲避流量检测。
我们提取其中一段代码进行分析，解码后可以得到实际要执行的SQL语句，可以看出攻击手法就是利用上面提到的“作业”来执行恶意代码。
当然，这只是僵尸网络传播的一点，真实情况它是对我们上篇提到的所有攻击手法都会去打一遍，以保证自身能够百分百被执行。
该类型僵尸网络的核心传播方式基本一致，提取其中真正实现传播的命令，对其分解，可以看出其执行流程：
（1）通过xp_cmdshell等方式执行cmd命令将 ftp 登录方式与恶意文件下载语句写入一个".exe"（也有可能“.dll”、“.dat”、“.tmp”等）后缀的文本文件
（2）通过 ftp 启动该文本文件，ftp 会根据文本内容登录恶意ftp站点并将恶意文件下载到本地指定文件夹
（3）判断恶意文件是否存在，存在则直接运行
（4）删除恶意文件并退出

02 SQL Server 应急分析
1、流量分析
SQL Server客户端和服务器之间通信使用 TDS（表格数据流）协议来进行通信，这是一个基于TCP的应用层协议，通信端口即我们熟知的1433，被微软SQL Server数据库和Sybase公司数据库产品所使用。
TDS协议默认是明文传输的，即客户端与数据库的认证过程及命令交互我们是肉眼可见的。所以，我们在处理 SQL Server的应急事件中，首先可以对相关的流量进行分析（前提是部署了全流量相关的产品），查看攻击者IP对应的会话流量，可以分析出最原始的攻击过程：
Tips：
对于TDS协议的流量分析，需要注意的是数据库传输时使用的是UTF-16 编码，一个字符会占用两个字节，每一个字符前面都会有一个0x00，Wireshark 默认使用的ASCII解码，所以我们看到的载荷内容总有一堆点，让人很是难受，你不妨设置编码方式为UTF-16试试！
作为重要的数据库系统，可以采用加密方案来保证流量安全，一般有两种方式进行加密：
  • SQL Server服务端配置加密：该方案跟https 一样在TCP协议上套接TLS 加密传输，这种方式会强制所有的客户端都使用TLS加密，一般安全建设足够到胃的企业都应该启用TLS加密，需要在服务端配置证书，加密后的流量我们只能看到TLS 流量，不会再看到TDS协议交互内容；
  • 客户端加密：这种方式就是客户端来决定是否对数据加密传输，只有设置了加密策略的那条流传输的数据才会进行加密，其他没有设置加密的连接都是明文传输，像我们常用的“Navicat工具”，就会通过这种方式来对认证信息进行加密传输，但其他交互都是明文传输。

2、数据库排查
在讨论如何排查 SQLServer 之前，有必要了解下微软提供的 SQLServer 的管理工具 SQL Server Management Studio (SSMS)，这应该是 SQL Server 部署后必备的服务端管理工具，部署了MSSQL的服务器，大部分都会安装该工具，通过它我们可以对数据库进行管理配置，类似于我们常用的 Navicat，但功能要比 Navicat 丰富的多。
下载地址：https://docs.microsoft.com/zh-cn/sql/ssms/download-sql-server-management-studio-ssms?view=sql-server-ver15

（1）进程分析


针对SQL Server的利用，不论是 xp_cmdshell 还是作业，在执行 cmd 或 powershell 等命令时，其调用者均为 SQLServer的服务进程，因此，在分析进程时，如果发现可疑的Powershell等进程其父进程为 SQL Server 相关，那么问题一定是出在 SQL Server 服务本身，基本可以排除其他的入侵点了～



（2）代理作业（job）检查


代理作业即SQL Server的计划任务，是利用频率最高的功能点之一，排查时我们只需通过 SSMS 查看“SQL Server代理”的作业部分，是否存在创建时间异常、执行操作异常的计划任务。如图，攻击者通过写入计划任务“abc82”来执行恶意的powershell代码：

此外，我们还可以通过查看“作业活动监视器”，来查看计划任务的创建及执行记录：

（3）存储过程检查


上篇中提到，攻击者可以通过 CLR 注册恶意的程序集来实现自定义存储过程，所以，存储过程的检查也不能遗漏，在SSMS中查看每个库的“可编程性—>存储过程”，是否存在可疑的存储过程。



（4）程序集检查


如果在存储过程中发现了恶意的自定义存储过程，那么一般都会有对应的程序集存在，检查对应库的“可编程性—>程序集”，是否存在与恶意存储过程对应的程序集。

3、日志分析


关于MSSQL的日志分析，bypass师傅的应急文章里面其实也有提到，SSMS工具的使用就不做过多解释，基本有手就行～


  • SQL Server日志：SQLServer本身的日志有事物日志和信息日志两种，事物日志是数据库操作相关的记录，我们重点分析信息日志；

  • Windows系统事件日志：作为一个Windows开启和管理的服务程序，Windwos系统自带的Application和system日志会对 MSSQL 的启动、关闭、异常、登录等信息进行记录。

（1）SQLServer 日志分析
SQLServer日志（认证、错误日志）存储路径：
C:\Program Files\Microsoft SQL Server\MSSQL13.MSSQLSERVER\MSSQL\Log
在应急时我们一般只需关注“ERRORLOG”和“log.trc”就够了，前者记录了 SQLServer认证及一些敏感操作触发的相关信息，直接以文本形式或着SSMS 的日志查看器浏览即可，后者记录了详细的认证及报错等关键信息，需要用SQLServer的对象查看工具来打开。
Tips：“ERRORLOG*”在 SQLServer 启动时就会生成，默认只保留7份errorlog文件，按照时间顺序，依次用文件扩名 1,2,3,...,6表示，每重启一次服务，文件扩展名都会加一，最早的那份会被删除，建议上机后第一时间备份这里的日志文件。
SQL Server默认只记录报错和登录失败记录，强烈建议开启登录成功审计，需要在安全性设置中勾选。
在应急过程中，我们通过客户服务器上安装的SSMS工具自带的日志查看器可以更高效的分析errorlog日志，该工具支持查看SQLServer日志、作业历史记录、维护计划、SQL Server 代理等多种日志类型，还支持筛选和导出，功能与系统的事件查看器基本一致。
在分析SQLServer日志时，我们一般只需要关注以下几个日志ID就能解决我们的大部分问题了，同时，这些ID也与系统事件日志中的ID保持一致。

（2）系统事件日志分析


Windows系统本身也对SQLServer服务的相关事件进行了记录，通过 Application事件日志即可查看，但是事件日志与SQLServer本身记录的日志基本没什么区别，所以我们只需要分析其中一个就可以。


在 Application 事件中筛选日志源“MSSQLSERVER”，就可以查看SQLServer相关日志，可以看到，记录的内容与 SQLServer 日志基本保持一致。



分析Application日志时，我们也可以使用LogParse工具进行快速检索：


# 使用 LogParse 查看 SQL Server 登录失败、成功日志

LogParser.exe -i:EVT –o:DATAGRID  "SELECT *  FROM C:\Windows\System32\winevt\Logs\Application.evtx where EventID=18454 or EventID=18456"

（3）日志检索关键词：存储过程名


存储过程的启用、调用及权限配置等操作，均会在日志中留下痕迹，通过在日志中检索常见的存储过程名或其他关键词，我们可以发现是否存在敏感的存储过程调用行为：


# 常用关键字

xp_cmdshell
show adcanced options
TRUSTWORTHY
Unsafe assembly
RECONFIGURE
sp_OACreate
...
搜索“xp_cmdshell”、“show adcanced options”、“RECONFIGURE”关键字，如下日志，不难判断攻击者登录成功后尝试启用xp_cmdshell存储过程来执行恶意命令。
搜索“TRUSTWORTHY”、“Unsafe assembly”关键字，如下日志，结合上篇中提到的恶意程序集注册利用，可以判断攻击者试图修改master库的TRUSTWORTHY属性为ON，并尝试写入不安全的程序集。

（4）日志检索关键词：".dll"

大多数恶意软件的传播代码都会涉及恢复存储过程操作，在调用 dll 文件去恢复对应存储过程的同时，日志中也会记录该行为。

因此，我们只需要在日中检索关键词“.dll”，如果匹配到包含以下 dll 的相关日志，我们基本就可以判定攻击者执行了存储过程恢复命令：

xpstar.dll // 可用于恢复xp_sqlagent_notify

xpsqlbot.dll // 可用于恢复xp_qv
