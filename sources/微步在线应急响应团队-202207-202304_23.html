大家好，我是花十一。

作为微步在线资深的安全工程师，我常常奔波于帮助客户处理各种应急事件的路上，从未想过在生活场景中还能遇到“挖矿事件”！没错，这次应急帮助的对象不是客户，而是我那个初入安全圈的小白“表弟”（手动滑稽）... ...

01 前言

事情源于表弟写的一个企微机器人。

他说他为了方便日常工作中的数据监测，利用这个机器人每天早上十点通知前一天数据库中增量（不得不说年轻人挺有想法）。

国庆节后上班的第一周，我美滋滋地休假在家。

“哐哐哐”！

睡眼惺忪的我，拖着国庆游玩后疲惫的身躯，开门就看到了这个面露急色的孩子。

原来是他发现机器人没有返回内容。所以当下他就慌了，直接扛着电脑飞奔来我家。

开始我想肯定是磁盘满了导致数据库崩了。为啥这么笃定呢？因为这台机器跑的业务生成的日志很大，我之前写的机器人就遇到过硬盘写满导致业务宕机的情况。

结果竟然意外发现了这起挖矿事件。（文末有彩蛋喔）

02 事件分析

登上服务器，查看硬盘大小发现还有12G。
查看网络连接mongo数据库端口关闭。
尝试重启服务却重启失败，直到这里才发现事情并不简单。
然后又细看了一下网络连接，服务器怎么会存在45.9.148.x网段的网络连接，不会被黑了吧。
看了下进程kswapd0详情，其位于/home/elastic/.rsync目录下，而且与45.9.148.58和45.9.148.117存在网络通信。
查询X情报社区两个IP都是矿池，果然鸡了，主机被挖矿了。
进入/home/elastic/目录，发现恶意程序位于dota3.tar.gz和.rsync目录中。
回看进程启动用户是elastic，大概是弱口令进来的。查看/var/log/secure，果然在9月28日的时候用户elastic存在登录成功记录，攻击者执行成功后还尝试执行sudo命令，但是该用户并没有sudo权限。
至此整个挖矿事件理清楚了，28号中的马，10月份才发现，着实不应该呀。接着启动mongodb，查看mongo日志，提示/tmp目录权限不足。
查看/tmp目录权限，缺少了“写”权限，添加权限后至此数据库启动成功。

03 样本分析

从服务器上把木马文件拉回本地，dota3.tar.gz里的文件内容和.rsync内的文件一样。
这里做个简单分析。initall是一个bash脚本，主要作用是删除主机上可能存在的恶意文件、结束相关恶意进程，然后执行init 和init2脚本。
init和init2脚本内容大致一样，执行挖矿初始化操作，主要功能有清除主机可能已经存在的木马，然后启动木马并创建持久化，首先后台运行a、b目录下的a脚本和c目录下的start脚本，然后设置持久化操作，该脚本将a目录下upd脚本和b目录下的sync脚本设置为每次系统重启后执行，c目录下的aptiude脚本每三天执行一次。
a目录下的upd脚本主要作用是启动挖矿程序kswapd0
将kswapd0上传沙箱，存在恶意标签。
通过ida的分析，挖矿的配置文件被编译到挖矿程序中，存在多个矿池地址，钱包地址都指向
483fmPjXwX75xmkaJ3dm4vVGWZLHn3GDuKycHypVLr9SgiT6oaZgVh26iZRpwKEkTZCAmUS8tykuwUorM3zGtWxPBFqwuxS
b目录下的sync脚本主要是启动run脚本，执行后会在authorized_keys中写入ssh公钥。
c目录下aptitude脚本功能启动tsm程序
该工具是一个扫描弱口令工具，操作说明如下。
执行命令后会在本地生成a、b、p、ip四个文件夹，a和ip文件内容一样，存储的是需要扫描的ip和端口， b和p文件内容是用户名和密码。

04 矿池拓线

从样本kswapd0中提取到攻击者使用的矿池地址有45.9.148.117、45.9.148.129、45.9.148.125、45.9.148.58、45.9.148.59
查询情报社区以上IP都存在"矿池"标签。
针对以上IP做端口扫描，都开放了80和443端口，且这两个端口都存在证书，相关信息如下。
通过证书hash在测绘平台上检索发现未发现有新的攻击者资产，继而观察资产的其他特征进行拓线，攻击者使用的矿池端口都为80/443，且都绑定了证书，证书有效期是十年，证书的颁发者和使用者都是localhost，根据这个特征利用测绘筛选出一批IP。
cert.subject="localhost" && cert.issuer="localhost" && cert.validity.not_before="2022-07-23" && cert.is_expired=false && protocol="ssl"
一起获取到了17个IP，筛出样本中已知的IP，尝试对余下ip发送stratum协议数据包，包的内容为
{"agent":"XMRig/6.6.2 (Linux x86_64) libuv/1.40.0 gcc/9.3.0","id":1,"jsonrpc":"2.0","method":"login","params":{"login":"xxx","pass":"x"}}
如果ip是存活的xmr节点就会给予返回包。如下195.138.91.246:3333端口返回了xmr响应。
利用这种思路对IP进行探测，又发现矿池地址如下
195.138.91.246:3333
45.77.152.200:5555
45.77.152.200:3333
05 事后复盘

上班后，拿回样本在公司的服务器上跑了一下，OneEDR轻松检出。不得不说如果当初装了agent，可能这样的事件就避免发生了。

这次事件反映出在运维个人服务器的时候存在一些盲点，服务器被入侵检测时间迟缓，业务宕机响应时间迟缓。我给他写了一个服务监控脚本，传入需要监控的服务名称。一旦服务停止，就会自动给企业微信机器人发送告警信息，实现及时响应。

#!/bin/bash
function GetPID()
{
   PsName=$1
   pid=`ps -aux | grep $PsName|grep -v "proc-monitor.sh" |grep -v grep|grep -v vi|grep -v dbx|grep -v tail|grep -v start|grep -v stop |sed -n 1p | awk '{print $2}'`
   echo $pid
   if [ ! -n "$pid" ]; then
     content="$1服务宕机,请及时排查"

   else
     echo "$1 存活"
   fi
}
function Weixin
{

               >详情：$content
       "

}
