**HW期间样本整理  
**

研究人员在最近整理 HW 期间的样本时发现了一个比较有意思的自写木马**osshunter**。该木马使用 go 语言编写，伪装成邮件文档进行钓鱼。木马功能较为完善，基本实现了常规木马的所有功能，如执行 shell 命令、下载文件、上传文件、浏览文件目录等。比较新奇的是，该木马使用对象存储服务作为信道，通过对象存储的文件上传和下载实现受控端和控制端的通信，完成整个远程控制的流程。对象存储服务，简单来说就是一种云端存储文件的服务，用户只需提供访问区域（Endpoint）和访问密钥（Accesskey），就可以通过各种接口方便的上传和下载文件。![](../Images/e38be4cba186db901621063b9d38fc1a.png)

阿里云对象存储（OSS）Go SDK官方示例  

相较于云主机可以自己搭建不同的服务，对象存储服务仅提供存储文件的功能，更具有针对性，更加方便，价格也更低。并且木马使用存储服务时，主机仅会与域名 <Bucketname>.<Endpoint> 通信，且流量特征为对象存储服务通信协议本身的特征，从网络行为上更加不容易引起怀疑。

![](../Images/4942e853a9693d8059ea87b16a919685.png)

木马在微步云沙箱中的网络行为  

**木马详细分析**

该木马利用对象存储服务实现了较为完整的木马功能，总体通信示意图如下：  

![](../Images/bfb2b2f632887b3a55eb22e103c47b1c.png)

总体通信示意图  

木马使用阿里云对象存储（OSS）作为代理，访问密钥和存储空间（Bucket）名称均硬编码在文件中。木马将连接控制端和受控端的中间文件均存储在名为 ”ccb-images” 的存储空间中，通过上传和下载文件实现二者通信（虽然请求时有目录层级形式的路径，但对象存储是没有目录结构的，这是厂商支持的特性）。

![](../Images/6d8039ace27e5de80130dd114ff6188e.png)

OSS访问密钥硬编码在文件中  

木马在启动执行后会生成一个 UUID，用来在通信中标识自身，方便控制端区分不同的木马实例。同时会创建互斥体，避免同一主机运行多个实例。木马启动后会判断自身路径是否在 %localappdata%\\Microsoft\\Windows 目录下，从而确定自身是否为用户执行或者自启执行。如果为用户执行，则弹出消息框，提示用户文档异常，否则直接执行木马逻辑。

![](../Images/8d1b9edb7d6095d3ee4ea1bf74b659db.png)

木马整体的执行流程  

木马会请求是否存在 UUID/alive 文件，用于判断是否为首次上线。首次上线的木马会执行 init 流程：创建 UUID/alive 文件用于通知控制端有新主机上线；创建任务文件夹 UUID/job 为后续下发任务做准备，上传用于加密主机信息和命令执行结果的 AES 密钥 UUID/aeskey 文件，收集并加密上传主机信息 UUID/info 文件。

![](../Images/73f57a3d809af329f6feb3700f8d09d9.png)

init流程  

木马首次上线时，收集的信息包括用户名、主机名、IP地址、系统版本、进程列表、是否为管理员等。

![](../Images/e4cc921ca34a3e7799b387e2768abd67.png)

木马收集的受控主机信息  

木马上传的主机信息以及执行命令的结果信息均使用 AES-CBC 算法进行加密传输。

![](../Images/61e0435335cda4b0c93de90e7d575b19.png)

使用AES-CBC加密  

完成首次上线的准备流程后，木马会休眠一段时间，然后进入 check\_in 流程，请求 UUID/job/ 下的文件，解析并执行其中的任务。

![](../Images/c39ed57c3c453d98d656197dc53b9b2a.png)  

读取文件接收任务  

![](../Images/a49498407137aa02f723bfa93a9d0638.png)

解析执行命令  

木马接收执行的命令和功能如下（其中 upload 与 download 名称和功能相反，应该是为了与控制端名称统一）：

| 命令 || 功能 |
| --- | --- |
| kill || 结束并删除自身 |
| shell || 执行shell命令 |
| reinit || 重新初始化 |
| upload || 下载文件 |
| options || 设置请求任务的时间间隔 |
| fileBrowser || 遍历磁盘及目录 |
| download || 上传文件 |

将任务执行的输出结果上传至 UUID/result/ 目录下。![](../Images/4a7e3ae40b597b3d183d42d2ed6d97a5.png)上传命令执行结果  

这里虽然没有控制端的样本，但从被控端与 OSS 通信的情况来看，控制端的操作文件的方式应该与被控端相反。控制端通过监听 uuid/alive 文件上传事件得知新主机上线，使用 uuid/aeskey 中的密钥解密 uuid/info 文件获得主机信息，上传 uuid/job/\* 文件向主机下发任务，从 uuid/result/\* 文件中读取任务执行输出的结果。  

  

**后记**

在网上进行关键字搜索 “OSS远控”，发现一个使用 Java 开发的开源远控工具OSSTunnel (https://github.com/Ramos-dev/OSSTunnel），其整体实现与 osshunter 木马非常类似，比如都使用 UUID 标识每个木马通信、受控端间隔时间接收命令执行等。由于 osshunter 木马比 OSSTunel 远控工具出现的更晚，并且功能更加完善，因此可以推测 osshunter 木马借鉴了 OSSTunel 的实现并加以改进。虽然距离样本首次上传到 VT 的时间已经过去了好几个月，但这个木马现在就只有2家厂商报毒，就算不对原始样本进行加壳混淆也可以免杀绝大多数的杀软。另外木马作者选择自写，而没有使用已有的比如像CS这样的木马。因此该木马再次出现的可能性很大。当下次遇到包含这种网络请求的可疑样本时就很有可能是 osshunter 木马或类似的木马。  

![](../Images/99267bc0e63245d37e3c38b38abd8efa.png)

安全厂商的检测结果  

根据这个木马的特征，笔者在 VT 近3个月内的样本中查找使用阿里云对象存储的 go 语言样本，但可能是由于加壳或其他原因，结果只发现了一个红队样本。因为缺少其他的相关组件，在该样本中仅发现使用对象存储存放失陷主机信息的用法。

![](../Images/8477e31f94d95bd83ecd2de6b6c5ebac.png)

存储用户的基本信息代码  

总体来看，**使用对象存储的木马还比较少，以后可能会有更多的红队使用**。但使用对象存储时, 需要提供访问密钥，**木马投放出去就会造成密钥泄露，****存在被蓝队利用的风险。**

![](../Images/ec11b653118a9105bbcf84d0321f2b4d.png)

红队样本中的访问密钥  

最后，国内外云厂商都提供对象存储的服务，价格相较于云主机更低廉，并且接口都大同小异。红队的小伙伴可以尝试一下，也许就想到了不同的使用方法，开发出新姿势。蓝队的小伙伴可以写些规则，检测和狩猎使用相似手法的样本。
