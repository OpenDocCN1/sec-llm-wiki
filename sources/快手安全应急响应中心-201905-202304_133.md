01

CSP简介

        XSS漏洞是前端会出现的较为严重的漏洞之一，有可能能够直接获得用户的身份（Cookie），达到冒充他人登陆私密系统的效果，由于前端的灵活性相对后端来讲更强，因此XSS相对于其他漏洞在一定情况下可能较难发现和完全修复（即使是对安全很重视的厂商，如gitlab，在某些最近的版本也存在XSS漏洞）。此外，由于利益的驱使，流量劫持也是一个能够对用户造成影响的问题，中间人能够替换服务器发给用户的流量，在其中插入广告等等，严重的影响了用户的体验。为了缓解这两个问题造成的影响，CSP策略应运而生。

        CSP指的是内容安全策略，以白名单的机制来限制浏览器在当前页面中加载的资源与执行的脚本的来源。主要用于缓解跨站脚本攻击（XSS）与页面劫持（劫持的来源包括但不限于运营商、浏览器本身等）问题。在一个生效的CSP策略（虽然“CSP”中的“P”已经代表策略的意思了，不过为了中文行文方便，下文仍会出现“CSP策略”的说法）中，指定了浏览器在当前页面中允许加载的资源，这样一来能够一定程度上的防止对恶意脚本，或由中间人插入的页面资源的引入。CSP策略最终在浏览器上生效，因此需要配置在响应头中，也可以配置在页面的meta标签中。

02

CSP的常用字段含义

  

       一个比较简单的CSP策略类似于如下形式

       "defualt-src 'self' example.com;script-src 'self' 'unsafe-inline' http://example2.com 123.124.125.126 data:"

       CSP策略由多个“指令：来源”组成，“指令”可以非常粗略但易于理解的认为是使白名单生效的标签（如script-src对应的<script>标签），“来源”是规定浏览器可以执行的脚本（即js文件等）、页面资源（如图片、字体等）的来源白名单。比如一个简单的CSP中：img-src 'self'; 中，img-src即为指令，意味后面的配置对<img>标签中src属性生效，‘self'为来源，规定<img>中的src属性只允许包含与当前页面地址同源（同协议、同域名、同端口）的链接。值得注意的是，由于CSP策略相当于白名单，因此没有被加入白名单的来源会被浏览器拒绝访问。

**1、CSP策略相关响应头**

       CSP策略可以被配置在http响应的响应头中，与CSP策略相关的响应头有两种：

| 响应头 || 含义 |
| --- | --- |
| Content-Security-Policy || 浏览器将会拒绝引用所有未在CSP策略中添加白名单的脚本与页面资源来源，在设置了report-uri指令时，会向指定的地址发起报警（实际就是一个Post请求，向服务端报告浏览器阻拦了哪些资源加载）。 |
| Content-Security-Policy-Report-Only || 浏览器将不会拒绝引用所有不在CSP策略中的脚本与页面资源，只会将未在CSP中配置的脚本与页面资源向外部报告（report-uri指令指向的地址中），其他与Content-Security-Policy基本相同（特例在 三. 6 中介绍）。必须设置report-uri指令，一般于测试时使用。 |

## **2、CSP策略中的“指令”**

        CSP策略有很多指令，分别对应着不同的html标签，这样一来可以有很灵活的配置，可以想象下，允许从任意的来源引入图片可能是一个正常的业务需求，而允许从任意的来源引入脚本的必要性和安全性显然比较令人怀疑。

        下面列出比较常用的CSP指令的含义

| 指令 || 含义 |
| --- | --- |
| default-src || 用于其他大部分指令的后备指令，即在未检测到最相关的"指令"时，按照default-src的规则生效 |
| font-src || 字体资源来源 |
| connect-src || 限制可以使用脚本接口加载的URL，如使用xhr等 |
| img-src || 图片资源来源 |
| style-src || 样式表资源来源 |
| media-src || 媒体资源来源 |
| frame-src || 页面嵌套来源 |
| form-action || 表单的提交地址，该指令不会回退到default-src |
| script-src || 脚本来源 |
| report-uri || 浏览器根据CSP策略阻拦了资源的加载时会生成一个报告，会向report-uri指定的地址发送一个post请求。值得注意的是，<meta>标签中配置的CSP无法使用report-uri指令 |

       实际上还有超多的其他CSP指令，这些指令都可以在https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy中找到，需要特别注意的是，由于CSP策略由浏览器自行实现，因此会出现某种浏览器对某些指令不支持的情况，各浏览器对不同指令的支持情况也可以在如上的链接中找到。因此我个人的建议是，如无必要，只使用最基本、最常用的指令就好。比如，类似于prefetch-src 这种指令似乎目前根本得不到浏览器的支持，为什么还要对其进行配置呢。

**3、CSP策略中的“来源”**

        前文中说过，一个能够生效的CSP策略由多个“指令：来源”组成，下面是比较常用的CSP来源

| 配置 || 含义 |
| --- | --- |
| 'self' || 允许同源的资源引入 |
| 'none' || 不允许引入任何资源，不允许调用任何脚本 |
| \*.example.com || 允许根域名为example.com的域名 |
| http://www.example.com || 允许协议为http，域名为www.example.com |
| www.example.com:8080 || 允许www.example.com，8080端口 |
| 121.122.123.124 || 允许从121.122.123.124引入资源，ip似乎无法使用通配符 |
| 'unsafe-inline' || 允许网页内联资源（见下文详细配置说明） |
| 'unsafe-eval' || 允许使用eval()函数执行脚本 |
| data: || 允许使用data:伪协议，一般指数据的引入方式，类似的配置（伪协议）还有如blob: 等 |
| ftp: || 允许ftp协议，其他协议类似，如http,https等 |
| \* || 允许任意的来源（但不包含其他协议、’unsafe-inline'、'unsafe-eval'等） |

         因此CSP策略中，来源的形式并不只是一个url，还可能是其他奇奇怪怪的东西。比如'unsafe-eval'就对应着javascript中的eval()函数（当然实际也有一些其他乱七八糟的东西算在'unsafe-eval'中了，这个后文也会介绍），CSP策略中来源的形式比较多，具体需要在实际情况中不断摸索。

03

CSP策略配置中值得注意的地方

         CSP策略的配置实际上还是比较复杂的（个人觉得这是由于前端就很复杂），因此我在这里总结了一些可能会遇到的坑

**1、同源策略对CSP的影响**

        在"来源"基于url形式时，CSP策略会基于当前页面的链接判断"来源”是否合法。举个具体的例子，假设当前页面的链接为https://a1.example.com:80 ，某一个CSP配置为：

       "img-src a1.example.com"

       某一个页面中的img标签有

       (1)<img src=ftp://a1.example.com/a.jpg>

       (2)<img src=https://a1.example.com:8080/a.jpg>

       (3)<img src=https://a2.example.com:80/a.jpg>

        则（1）、（2）、（3）都不会成功被页面加载（（1）协议与当前不同，（2）端口与当前不同，（3）域名与当前不同），因此很容易能够看出CSP和同源策略存在一定的关系。可以粗糙的认为，在未明确规定“来源”的端口号或协议的情况下，会以当前页面的端口号或协议为准。

       如果需要（1）、（2）、（3）都被页面成功加载，对应的CSP策略可以为：

       A. "img-src ftp://a1.example.com"

       B. "img-src a1.example.com:8080"

       C. "img-src a2.example.com"

       如果三者需要在同一页面中加载，使他们能够同时被加载的CSP策略可以为：

       D. "img-src ftp://a1.example.com a1.example:8080 a2.example.com"

**2、对于script-src的特别说明**

        script-src规定了允许引入或执行的js脚本，因此在CSP策略中相当重要。最安全的配置方式是只允许特定来源的js文件，如"script-src 'self' \*.example.com"。

       但在实际的配置中，很可能页面中存在内联脚本（内联脚本指的是通过<script>XXXX</script>这种直接写在页面中的js代码），对于这两种情况，可以使用sha256（引入脚本哈希）或nonce（script标签属性，相当于一个标记），如在以下前端代码中：

  

| <meta http-equiv="Content-Security-Policy" content="script-src 'self' https://\*.example.com">  
<script>  
 alert(1)  
</script> |
| --- |

      在上面的配置中，由于未允许内联的script脚本执行，浏览器将会报错

![](../Images/d61a7242ce97000965b6d293b1329cd8.png)

       可以根据提示将CSP策略引入内联脚本的sha256：

  

| <meta http-equiv="Content-Security-Policy" content="script-src 'self' https://\*.example.com 'sha256-zJ9j8ZNh4YjHkqESkHprxY8KEWhVJbI6hzl1yBId/4E='"> |
| --- |

     或同时修改前端meta标签和CSP策略，增加nonce值：

  

| <meta http-equiv="Content-Security-Policy" content="script-src 'self' https://\*.example.com 'nonce-abcd'"><script nonce=abcd>    alert(1)</script> |
| --- |

       但在实际的CSP策略配置中，从业务方工作量的角度，对所有的script标签都添加sha或nonce的方式可能并不现实，且无法对标签内“on"事件中的javascript伪协议（如最经典的xss测试向量之一<img src=# onerror=alert(1)>）使用这两种方法允许内联脚本（是的，这种情况也归script-src配置管）。次优的配置允许内联脚本与eval函数的执行，如"script-src 'self' 'unsafe-inline' 'unsafe-eval' \*.example.com"，不过这样会提高XSS漏洞被利用的风险。

**3、form-action**

       该配置针对表单提交信息的地址，传统的前端发送数据一般使用表单实现，如

  

| <form class="new-wiki-page" action="http://eval.com/login">  <input type="text" name="username" id="username" class="form-control">  <input type="password" name="password" id="password" class="form-control"></form>  
  
 |
| --- |

       该表单会向http://eval.com/login发送请求，其参数为用户填写的username和password，特别需要注意的是，在未找到form-action指令时，对<form>标签的配置并不会回退到default-src，因此需要单独配置。在存在XSS的情况时，黑客可以在页面中插入表单，进行钓鱼攻击并诱导用户输入密码，最终可能将数据发送到由黑客控制的服务器，因此建议限制form的请求地址，如"form-action \*.example.com"。

**4、通配符“\*”的使用**

       可以使用通配符"\*"来匹配所有域名，子域名或端口等。如"img-src \*"，允许所有图片来源（但不包含'unsafe-inline'、'unsafe-eval'，其他协议等）。"script-src http://\*.example.com \*.example1.com a.example2.cn:\*"，即允许http协议的example.com的子域名、与当前页面协议相同的example1.com子域名，及a.example2.cn的所有端口。需要注意的是，"\*"在ip中的配置是无效的，即133.55.44.\* 或 133.55.44.0/24 这种配置无法在CSP中生效。

**5、中/英文文档问题**

       目前CSP策略有部分中文文档（https://cloud.tencent.com/developer/section/1189879），推荐使用英文文档（https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Headers/Content-Security-Policy ），因为中文文档有部分错误，如worker-src的回退指令，中文文档中描述“如果此指令不存在，用户代理将查找child-src指令（该指令回退到default-src指令）。”，英文文档中描述"If this directive is absent, the user agent will first look for the child-src directive, then the script-src directive, then finally for the default-src directive, when governing worker execution." 。当然，这种情况很可能是由于CSP指令的修改，而不一定是由于翻译错误。

**6、对于wasm技术，谷歌浏览器的CSP策略实现比较特殊**

        一般来讲，在使用Content-Security-Policy响应头（以下简称CSP响应头）Content-Security-Policy-Report-Only响应头（以下简称CSPRO响应头）时，在console.log报警和向远程报警的规则是一样的（即 a.假如引起了console.log报警，在设置了report-uri指令时，浏览器也会同时向远程发送报警；b. 如果CSP策略的配置和页面加载的资源不变，设置CSPRO响应头引起了报警，则设置CSP响应头中也会出现相同报警。），但在谷歌浏览器加载的页面中使用wasm技术时，却出现了例外。

        wasm简单来说是浏览器提供的一种能够直接执行二进制代码的功能，主要用于提升浏览器性能，允许wasm执行的CSP策略为"script-src 'unsafe-eval'"。在谷歌浏览器(chrome)中CSP响应头和CSPRO响应头对wasm的处理比较特殊，在已经设置了"script-src 'unsafe-eval'"时，如设置为CSPRO响应头，使用wasm会在console中有如下报错（本地测试时也会有该报错）：

| \[Report Only\] Refused to compile or instantiate WebAssembly module because 'wasm-eval' is not an allowed source of script in the following Content Security Policy directive: "script-src 'self' 'unsafe-inline' 'unsafe-eval' hm.baidu.com \*.abc.com". |
| --- |

        如能够确认该报错只是由于前端使用了wasm导致的，则在使用CSPRO响应头测试过程中可以忽略该报错，在策略上线时将响应头更改为CSP响应头即可。出现该问题的原因是由于谷歌浏览器对wasm的处理比较特殊（题外话：显然谷歌也没有想清楚该如何对wasm设置一个合理的CSP策略，目前有一些对这个问题的讨论），而firefox不存在该问题。

        Chrome对wasm的报警机制和正常的报警机制并不相同，当使用CSP响应头时，如果设置了"script-src 'unsafe-eval'"，虽然不会阻拦wasm的执行，且console.log中也不会有报警，却仍然会向远程报警对wasm进行了拦截。正常情况下如果浏览器不会阻拦脚本执行或资源加载（因为对应的来源已经添加到了对应指令的来源中），则不会进行报警。
