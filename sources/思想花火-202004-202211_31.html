1、“什么是”的问题

1.什么是https协议？

HTTPS是身披SSL外壳的HTTP。HTTPS是一种通过计算机网络进行安全通信的传输协议，经由HTTP进行通信，利用SSL/TLS建立全信道，加密数据包。HTTPS使用的主要目的是提供对网站服务器的身份认证，同时保护交换数据的隐私与完整性。

  1. 第一个阶段，完成 Client Hello、Server Hello等握手。包含使用SSL版本、服务器和客户端的随机数、密码套件、数据压缩等参数响应。

  2. 第二个阶段，服务端把域名证书的公钥下发给浏览器（客户端），浏览器（客户端）校验证书合法性

  3. 第三个阶段，客户端把自己的证书发送给服务端（证书登陆的情况下），服务端检测客户端证书等。

  4. 第四个阶段，完成密钥协商、对称加密密钥交换。

SSL/TLS协议的四次握手中引入了一个新的概念，那就是“证书”。

2.什么是证书？

SSL证书和我们日常用的身份证类似，是一个支持HTTPS网站的身份证明，SSL证书里面包含了网站的域名，证书有效期，证书的颁发机构以及用于加密传输密码的公钥等信息，由于公钥加密的密码只能被在申请证书时生成的私钥解密，因此浏览器在生成密码之前需要先核对当前访问的域名与证书上绑定的域名是否一致，同时还要对证书的颁发机构进行验证，如果验证失败浏览器会给出证书错误的提示。

从上图可以看到，证书需要从“签发者”处购买并部署于自身的Web服务当中。

那么，换到我司而言，就是要把证书部署在Nginx当中，因为我司的Web服务使用的是Nginx。

3.什么是Nginx？

简单来说，Nginx (engine x) 就是一个高性能的HTTP和反向代理web服务器，其特点是占有内存少，并发能力强，事实上nginx的并发能力确实在同类型的网页服务器中表现较好，国内大部分互联网公司都在使用他，例如阿里、百度、京东以及我司等。


2、 “是什么”的问题

普通用户在访问网站时候会在浏览器地址栏输入域名，但通常不会刻意输入"http"或者"https"这样的前缀。那么，web服务是如何知道该使用https协议呢？

1.http 301和http 307的区别是什么？

其实，用户在浏览器直接输入域名默认发起的是http请求，web服务会对用户请求进行响应，返回一个三位数字的状态码以表示服务对请求的处理结果。我们通过查阅http状态码列表可知3XX代表重定向，也就意味着当一个http请求到了服务端，服务端可返回3XX代码并附上一个新的地址让浏览器再次发起请求。

在我们的https升级场景中，用到的是http 301代码和 http 307代码。

  • http 301Moved Permanently
    永久性定向。该状态码表示请求的资源已被分配了新的URI，以后应使用资源现在所指的URI。

举例：

用户发起一个请求：


GET /index.html HTTP/1.1

HOST: www.example.com


Web服务返回301


HTTP/1.1 301 Moved Permanently

Location: https://www.example.com/index.html

在Web服务返回的响应中我们可以看到服务指定新地址的时候是连同协议和地址一并附上的，那么，浏览器接下来自然就会愉快的发起https请求了。

不过，http 301有一个很显著的问题，就是当用户发起的请求是POST, PUT, DELETE的时候，Web服务会直接将请求中的表单或者载荷丢弃并使浏览器在接下来的请求中使用GET方法。

在实践中我们发现，通常像内容上传的站点第一个请求会使用POST或PUT方法，这时候我们就可以配置Web服务返回HTTP 307来规避上述问题。

  • http 307 Temporary Redirect
    临时重定向。当重新发出原始请求时，不允许更改请求方法。例如，应该使用另一个POST请求来重复POST请求

举例：

用户发起一个请求：

POST /index.html HTTP/1.1

HOST: www.example.com

{name=zhangsan;age=34;gender=male}


Web服务返回307

HTTP/1.1 307 Temporary Redirect

Location: https://www.example.com/index.html


尽管http 307返回的内容和http 301返回的内容很相似，但当浏览器看到307这个代码后会重新在https协议下发起POST请求。

2. Nginx中实现301和307的配置是什么样的？

了解完了http 301和http 307的原理与区别之后，那一定再要深入了解一下这两个状态码在Nginx上是如何实现的。

可以在nginx.conf中对server_name进行配置。

http 301

server {    listen 443 ssl;    server_name www.example.com;    add_header Strict-Transport-Security "max-age=63072000; includeSubdomains; preload";    add_header X-Frame-Options "DENY";    ssl on;    ssl_certificate 1_www.example.com_bundle.crt;    ssl_certificate_key 2_www.example.com;    ssl_session_timeout 5m;    ssl_protocols TLSv1 TLSv1.1 TLSv1.2;    ssl_ciphers ECDHE-RSA-AES128-GCM-SHA256:HIGH:!aNULL:!MD5:!RC4:!DHE;    ssl_prefer_server_ciphers on;    root /usr/local/angular/oa/dist/ng-oa/;
    location / {        try_files $uri $uri/ /index.html;        proxy_http_version 1.1;        proxy_set_header Upgrade $http_upgrade;        proxy_set_header Connection keep-alive;        proxy_set_header Host $host;        proxy_cache_bypass $http_upgrade;    }}
server {    listen 80;    server_name www.example.com;    add_header X-Frame-Options "DENY";    return 301 https://www.example.com;}

http 307

将return 301 改成 return 307

另外，Nginx超级灵活，还可以根据location返回不同的http code，编写判断条件根据请求schema返回不同的http code，配置LUA模块以后还能编写更复杂的程序进行更加灵活的配置，这些知识我已经无力掌握了。

3、“为什么”的问题

在项目推进过程中，还会碰到很多七七八八的技术问题，这个时候需要自己多问自己几个“为什么会这样？”我挑选了我碰到的典型的三个问题。

1.为什么要用src="//"?

这个问题的是因为有很多同学告诉我他在代买里写死了引用URL的schema而不能升级或者升级非常麻烦。这时候，可以自己问自己一下，为什么要写死呢？有什么不写死的方法吗？在技术大佬的帮助下，我了解到了src="//URL"的写法。

这种写法的意思就是浏览器会使用当前页面的schema去访问被引用资源，灵活方便，可进可退。

引用一个前端大佬在知乎的回答来说说为什么要这样写前端代码。

  • 如果你用 http:// ，那你就是默认当前页面是 http 协议了，你一个前端凭什么决定当前页面的协议？难道你不知道 http 链接在 https 页面里会报错啊？你应该沿用当前页面的协议，所以你要写 //

  • 如果你用 https://，也是一样的问题，你怎么知道三年后会不会出现一个 httpshe://，难道到时候你再全部改成 httpshe:// ？

  • 不要做任何明显是错误的假设！你根本就不知道当前页面会用什么协议打开！所以你要用 // 啊！

2.为什么浏览器会报告证书错误？

在升级过程中，有不少同学反馈说在Nginx上配置了证书浏览器却报错了，不知道为什么。

答案其实很简单，因为证书配错了。

浏览器在加载证书的时候会对证书有效性进行检查，主要包括以下内容：

  • 是不是由受信任的机构颁发的证书

  • 证书是否被吊销

  • 证书是否在有效期内

  • 证书中的授予域名和当前域名是否一致

  • 其他各浏览器厂商特有的检查项，例如是不是在某个黑名单列表中
