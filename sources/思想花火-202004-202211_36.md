# 如何做在线业务的安全性评估

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MjM5Mjc0MDU1MQ==&mid=2452313597&idx=1&sn=aaa15062e6d7b7ddff06aea66dde52a1&chksm=b17e50558609d943fef91f4fea0e3d26ed5478ba81a61568d76676a181b72ddfebed4d888d7e&scene=126&sessionid=1681657723#rd](http://mp.weixin.qq.com/s?__biz=MjM5Mjc0MDU1MQ==&mid=2452313597&idx=1&sn=aaa15062e6d7b7ddff06aea66dde52a1&chksm=b17e50558609d943fef91f4fea0e3d26ed5478ba81a61568d76676a181b72ddfebed4d888d7e&scene=126&sessionid=1681657723#rd)

日常工作中，时不时会有业务同学找过来，希望我们能帮忙评估一下在线业务的安全性。

常见做法是找白帽子来撸一遍漏洞，看看有没有可以被利用的问题。业务同学拿到了一份安全测试报告之后开心的走了，我们也为找出了不少问题而喜悦。但我们还是不禁要自问，这样就足够了吗？

  

在我看来，单纯的安全测试是不够的，我们需要做的更全面。  

  

当我们下次再接到这样的需求时，我们可以先对在线业务进行一个分层思考，再制定评估方案。  

  

  

| **逻辑分层**  
 || **描述**  
 |
| :-: | :-: |
| 业务层  
 || 业务需求的系统功能映射 |
| 数据层  
 || 业务相关数据的生命周期  
 |
| 应用层  
 || 实现在线业务所编写的程序 |
| 基础设施层  
 || 在线业务运行所处的系统、网络、数据库等环境 |

  

今天就不讨论基础设施层了，因为这不归业务管。我们只讨论最上面三层。

  

**1、业务层安全的评估方法**  

  

简单而言，我们的方法是通过分析业务流程中安全控制措施是否能够有效满足安全控制目标来判断当前环节安全性的。

实施方法如下：

![](../Images/61b180d2049dba938335570d83809400.png)

了解流程活动就是了解业务，即了解当前业务系统是如何实现业务需求的。

例如当你在评估外卖B端业务系统时，你需要知道一个商家是如何在平台上注册开店的。

接下来，就是对该业务流程环节中的威胁进行分析，即以攻击者视角审阅在该环节能如何实现STRIDE威胁。

  

例如：  

商家登录环节，需要输入手机号和短信验证码。那么，这个功能可能存在SID的问题，即Spoofing仿冒（被盗号）、Information Disclosure信息泄露（窃听）、Denial of Service 拒绝服务（短信炸弹）等问题。  

  

整个过程就像一个简化的DFD。

  

![](../Images/c4483c0913bd4cddea0bcd9a18bf15e1.png)

（复杂的DFD）

  

  

当分析出了威胁，接下来该识别业务流程上都部署了哪些控制措施。

  

知道了威胁和控制措施，那就好办了，只用回答“当前的控制措施能否应对威胁”这个问题就好了。

**2、数据层安全评估方法**  

  

绘制一个数据流，标识出数据流中重要的数据类型，比如个人信息、资金信息、订单信息等。  

下图就是一个个人信息流转的样例。  

![](../Images/0aa148764fe26689ba54a03b667f00e7.png)

  

接下来，可以使用等保要求里的控制点对数据生命周期的各个阶段进行审阅，包含：

*   账户管理
    
*   身份认证
    
*   权限分配
    
*   数据加密
    
*   完整性校验
    
*   可用性设计
    
*   应急演练
    
*   日志记录
    

  

**3、应用层安全评估方法**

**4、总结  
**

其实，还漏了一个“合规性”评估，特别是涉及到个人信息收集和处理时非常重要。不过，一般这事儿都有专门的团队在管，无需将这个领域特别的放在在线业务的安全评估范围。

总之，完成了三个层面的分析，才能够给在线业务的安全性一个全面的评价。
