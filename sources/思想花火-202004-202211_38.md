**1\. 对SDL理解**

  

说到产品安全，必须离不开SDL。

安全开发周期，即Security Development Lifecycle (SDL)是微软提出的从安全角度指导软件开发过程的管理模式。

SDL不是一个空想的理论模型。它是微软为了面对现实世界中安全挑战，在实践中的一步步发展起来的软件开发模式。

  

![](../Images/ec1e438fa690d5cd9f29e472780cb351.png)

可以看到，微软将安全能力集成到了软件开发生命周期的各个环节当中，使安全与业务更加紧密的结合了起来。Google采用的也是这种套路。  

在《building secure & reliable systems》里，Google是这样说的：  

Because of Google and Alphabet’s large size, in addition to a central security team and distributed security champions, we also have special decentralized security teams for more complex products. For example, the Android security team sits within the Android engineering organization. Chrome has a similar model (see Chapter 19).This means the Android and Chrome security teams are responsible for the end-toend security of their respective products, which includes deciding on product-specific

standards, frameworks, infrastructure, and methods. These specialized security teams run the product security review process and have special programs to harden the products. For example, the Android security team has worked to harden the media stack and has benefited from an integrated security and engineering approach.

  
即安全专家要深入业务，与业务线紧密合作，一起工作。这意味着，一个公司，需要雇佣一批有经验有能力的工程师只负责一条业务线，也意味着这条业务线足够重要且能赚钱养活这些工程师。

  

微软和Google这种国际一线大厂确实能做到这样吧，毕竟他们捣鼓的是操作系统、浏览器、编译器这些又大又基础的玩意，需要大量的人力物力和时间成本，而且特别会赚钱，多加一些安全猛人也是应该的。

  

反观我们。我们的业务策略是小步快跑，高速迭代，在试错中成长。如果，还这样让安全团队在产品开发的各个环节设置流程卡点，搞不好就容易成为业务前进路上的“绊脚石”。  

  

所以，我们需要打造自己的产品安全的逻辑。

  

  

**2. 我们的SDL实践**  

  

我们拿着微软SDL的各阶段比照着梳理。  

  

![](../Images/f3fd8e8a4855aa34bcffc8a9e81e94fb.png)

  

**2.1 培训**  

培训的目标是提升研发人员的安全意识和安全编码能力，但国内互联网公司的人员流动率高已经是行业共识了，研发人员来来往往的，非常频繁，如果你试图想要靠传统的面对面培训的方式就提升研发人员的安全编码能力，老板肯定会质疑做这事的ROI。  

  

那该怎么办呢？可以这样做：  

  

1.录制在线课件。

一个公司用的编程语言是有限且相对固定的，组织一波同事录制一波课程放在在线学习系统里方便研发同学查阅，也可以发动研发同学自学。  

2.设定产品安全红线。

一份易懂明了的红线要求可以让研发同学知道安全的底线在哪里，入职后必须学习，是提升他们安全意识的好帮手。  

3.大力发展公共服务。

公司一定要避免重复造轮子。重复造轮子意味着研发成本浪费，也会导致安全风险分散，难以管理。使用公司公共服务必须写入《产品安全红线》。  

  

**2.2 需求&设计**

在传统的SDL里，产品需求设计阶段会梳理安全需求，做威胁面分析与威胁建模，绘制复杂的DFD（Data Flow Diagram）。  

![](../Images/e6c5d4a39914f2e970a4ebac6999faaf.png)

但其实，在我们的工作场景中，一般都是产品经理在设计阶段咨询法务意见时，如果法务发现涉及数据保护或隐私保护的领域，才会把我们卷进去。  

  

这时候，我们需要绘制DFD吗？

  

根据我的经验来说，做DFD是没有意义的。不是说DFD和STRIDE分析这个玩意不好，而是产品和研发同学都有上线倒排计划的，他们没有空跟你一起绘制这个DFD。一般做法就是在理解业务流程的基础上，搬出来合规要求。

1.监管合规要求  

例如，公司某业务要去海外落地了，你需要研究当地的法律法规要求，行政处罚案例，然后形成安全建议，落实到技术方案中去。

2.公司合规要求  

就是甩出来上一个小节所说的《产品安全红线》呀。

  

监管合规要求和公司合规要求放进产品的需求设计当中，这就足够了。

  

**2.3 发布**  

完整的SDL还需要安全人员参与产品的开发测试环节，做代码走查、单元测试、Fuzzing等工作，这在现在的互联网企业基本是不可能实现的，但安全测试又必须做，怎么办？

  

我们可以在产品正式发布前做一轮全面的安全测试。只有通过了测试的产品，才能从预发布环境部署到线上环境。

  

那我们都测哪些呢？其实，就是之前提到的监管合规要求与《产品安全红线》呀。凡是不符合红线要求的issue，都必须让业务方整改。在这个时候，安全部门必须要强势起来。

  

**2.4 响应**  

产品发布之后，就进入了运维阶段，一般而言，工作就是监测和事件处置。但我觉得，这个阶段有两个事情，值得深入思考。

  

1.蓝军与威胁情报。

业务越做越大，业务价值越来越高，事故的成本也随之增加，盯着我们的眼睛也越来越多。一个不小心，公司很可能万劫不复。

Google将所有对公司业务不利的人都称为：adversary（不知道用什么中文对应比较好。。。。对手？）。他们会利用业务流程、系统环境的各种漏洞，来达到他们的目的。

漏洞可以简单的分为四类：  

1.  我们知道，adversary也知道的漏洞
    
2.  我们知道，adversary不知道的漏洞
    
3.  我们不知道，adversary知道的漏洞
    
4.  我们不知道，adversary不知道的漏洞  
    

对于类型1&2，我们要及时修。

对于类型3，我们需要有一个高效专业的情报网络和情报处理系统，全网收集各类信息，并与公司资产和业务相关联，能够自动化的给出有效情报。  

对于类似4，我们需要有一个足够野的、具备adversary思路的蓝军队伍，向我们的业务系统发起“毁灭性”攻击尝试，将类型4漏洞转化为类型2漏洞，减少类型3漏洞。

  

纸上谈兵很容易，蓝军与威胁情报网络建设路漫漫。

2.网络安全保险  

很多人可能没想过将保险作为运维环节里一个兜底的手段。

在我国，网络安全保险是一个新鲜事物，而在科技和保险都非常发达的美国，这已经是一个常见的险种了。这个保险主要帮助企业解决网络安全事故中的第一方损失和第三方责任问题。

  

例如万豪酒店数据泄露之后，网络安全保险的赔付帮他们支付了大部分的诉讼费、技术检测费和客户赔偿费。

  

根据万豪酒店2018年的财报描述，他们花了2800万美元处理data breach事件，保险公司承担了2500万美元。而300万美元对于万豪而言，那就是洒洒水了。

![](../Images/2128f7785981f124d0f350936a32f49d.png)

  

目前，国内的一些大保险公司也有类似的网络安全责任险产品，可以赔付各种网络攻击导致的业务中断或是赔偿诉讼等。

![](../Images/6ff32f0de205e45724e6448813029e79.png)

不过，我仔细研究了一下目前国内的这种保险，感觉对于业务种类不多的中小型企业是比较合适的，而对于像BAT这种业务种类繁杂的超大型互联网公司，目前国内的保险公司还缺乏更具针对性的保险方案。  

  

**3.总结**

兵无常势，水无常形。SDL不过是一个名字而已，在实践中不必拘泥于瀑布模型，而是应该根据自己的业务特点在流程的关键节点设置ROI最高的卡位，并随着业务的发展和组织的发展，及时的重新评估ROI，并调整卡位设置。

  

时刻谨记，业务的想象空间是无限的，而安全的发挥空间是有限的，把有限的安全资源投入ROI最高的事项里，是永远正确的。
