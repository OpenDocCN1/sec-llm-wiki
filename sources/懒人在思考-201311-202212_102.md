大家好，我是菜鸟 k0shl，今天给大家带来的是关于 ZoomEye 和 Seebug 二进制恶魔果实的神奇力量初探与思考。

  

近期，ZoomEye 开放了 API，也加大了我们与这款强大的搜索引擎的融合度，在使用过程中，我慢慢探索了一些关于 ZoomEye + Seebug 这个强大的恶魔果实的力量，但个人水平有限，而网络空间的暗物质十分丰富，ZoomEye 探测到的 banner 也相当庞大，更多精彩更酷的内容，有待海盗们继续深入探索。  
  
**0x02 打开新世界的大门——ZoomEye API**

  

要想早日踏上伟大航路，需要打造属于我们的“梅莉号”！对于 ZoomEye 的架构，每个人都有不同的设计思路，在这里分享一下我的设计思路，架构分为四个模块。

  

> 1、登录模块：

> 用于根据用户名密码获取 access\_token；
> 
> 2、基础信息获取模块：
> 
> 用于获取基本探测信息，比如返回的主机数量，Web 服务器数量等等；
> 
> 3、主机探测模块：
> 
> 用于利用 banner 探测目标主机；
> 
> 4、Web 服务器探测模块：
> 
> 用于利用组件等信息探测 Web 服务器。

  

下面对模块信息进行简要讲解。

  

首先是登陆部分，需要用账号密码登录获取服务器返回的 token，之前碰到了服务器的 bug，刚开始我以为是密码编码的问题，后来改成了简单的弱口令仍然不行，最后和 yoyo 反映后，联调发现是服务器的一个 bug，这样就能顺利返回 access\_token 了：

  

> def ZoomEye\_Login(g\_strUsername,g\_strPasswd):  
>     m\_strZoomEyeLoginUrl = 'http://api.zoomeye.org/user/login'  
>     m\_strfPostData = {"username":g\_strUsername,"password":g\_strPasswd}  
>     m\_strjData = json.dumps(m\_strfPostData) # Post JSON 格式  
>     req = urllib2.Request(url = m\_strZoomEyeLoginUrl,data = m\_strjData)  
>     #req.add\_header('User-agent','Mozilla 5.10')  
>     m\_strResultData = urllib2.urlopen(req).read()  
>     return m\_strResultData

  

另外 API 交互是用 JSON 格式，这样在获取返回信息的时候也很方便，就用 json.dump 和 json.loads 来读取 JSON 格式。

  

![](../Images/e6123159cdaede43e8a4c876dff48e31.png)  

  

这个 token 是和 ZoomEye API 交互的关键部分，接下来请求中需要用到这个 token，在 Authorization 字段中需要加入这个 token，根据官方文档，需要在 access\_token 前加上 JWT：

  

> g\_strLoginToken = "JWT “+m\_strLogintoken

  

然后进一步利用 ZoomEye 的时候主要有3种方法，其实 ZoomEye 的利用非常简单，主要就是通过 get 包和 post 包实现，但真正对暗物质的探索，还是在搜索部分。ZoomEye 对 banner 的识别非常强大，这里我只是抛砖引玉。

  

对主机和 Web 服务器基本信息情况进行一个简单的探测：

  

> m\_strZoomEyeSearchUrl = 'http://api.zoomeye.org/resources-info'  
> req = urllib2.Request(url = m\_strZoomEyeSearchUrl)  
> req.add\_header("Authorization",g\_strLoginToken)  
> m\_strResultData = urllib2.urlopen(req).read()

  

可以返回一部分主机和 Web 信息，ZoomEye 对普通用户开放的扫描权限相对有限，但每天都会更新一部分主机和 Web 服务器信息，因此对于我们此次的初探来说已经够用了。  

  

![](../Images/1c5c3106de7de71318bc61fe0d707199.png)  

  

可以看到可以搜索到的信息相对有限，但是这并不妨碍我们的探测。接下来，针对 url：/host/search 和 /web/search，提供了两种搜索方法，根据官方文档，其主要区别还是在于 JSON 元素的不同，针对主机和 Web 服务搜索的元素不同。打个简单的比方，对于主机可以通过搜索 app、version、device 等搜索主机信息；而对于 Web，可以通过搜索 header、title、keywords 等搜索 Web 服务器信息。  
  
今天我要做的是二进制方面的探索，那么就从 Host Search 开始，其实 Web Search 大同小异，有待各位表哥进一步发掘：

  

> m\_strZoomEyeSearchUrl = 'http://api.zoomeye.org/host/search?query='+g\_strReqData+'&page='+str(i)+'&facet=app,os'  
>     req = urllib2.Request(url = m\_strZoomEyeSearchUrl)  
>     req.add\_header("Authorization",g\_strLoginToken)  
>     m\_strResultData = urllib2.urlopen(req).read()

  

这里关键在于 url 构造，其他的信息和之前基本信息的探测一致，仍然要通过 add\_header 的方式将 token 加入头部，关键在于 query 中的查询构造，在 page 中填写页数。如果全扫描的话，就在外层调用中用 ，然后通过 for 循环调用即可，然后可以获取到返回信息：

  

![](../Images/155eaef41e1b78b84128e1ff27ec7e0c.png)  

  

返回信息量很大，但它也是 JSON，可以去掉无用部分，比如我们可以直接总结出 IP 地址的部分：

  

> for j in range(0,m\_intHostCount):  
>     print m\_strHostData\[“matches"\]\[j\]\["ip"\]

  

![](../Images/966567748a14e25c7627eb8a78869073.png)  

  

其实以上我们对于 ZoomEye 基础的架构就完成了。其实到这里还只是 ZoomEye 的冰山一角，更强大的探测功能需要表哥们继续发掘，接下来才是我们的正题。

  

**0x03 恶魔果实的力量——ZoomEye + Pocsuite**

  

初次接触 ZoomEye API，我觉得对于 banner 的探测是 ZoomEye 的一大亮点。之前我也提到过对于 app 和 version 的探测，在 ZoomEye 里对于各个端口的 banner 探测非常犀利。  

  

![](../Images/936579ef8781fefce1a4ab86fb5ffd75.png)  

  

这也是值得我们好好利用的地方，其实仔细观察之前的查询返回，里面已经包含了 banner 信息，但是相对复杂，不易查询，但是我们可以用 app + version 的方式识别软件及版本，这里我们就利用21端口和 Seebug 的 Pocsuite 结合来完成一次批量攻击探测。

  

首先我们选取的是 FreeFloat FTP 的一个缓冲区溢出漏洞，这个漏洞是我之前提交的，相关的漏洞分析和 PoC 如下：

  

![](../Images/0e7eb79b8ad489d9d89dc83647f7b112.png)  

![](../Images/e8cd156d23b088e764cd73b5912de9d1.png)  

  

Pocsuite 虽然目前只能用于 Web，但实际上我仍然可以利用 Pocsuite 构造一个二进制攻击的代码，但是利用部分相对麻烦，因为 -u 是必加的参数。

  

> m\_strTestIp = m\_strHostData\["matches"\]\[j\]\["ip"\]  
> m\_sock = socket.socket(socket.AF\_INET,socket.SOCK\_STREAM)  
> try:  
>     m\_sock.connect((str(m\_strTestIp),21))  
>     print m\_strTestIp  
>     m\_sock.close()  
> except Exception,e:  
>     continue

  

通过这段代码对扫描到的21端口进行连接探测，确认端口可以正常进行 socket 通信，这样才能顺利发出我们的 payload，可以得到可连接21端口的主机。这里我们设置 page=1，只针对第一页探测到的信息进行获取，能够探测到一台可连接的主机。

  

![](../Images/7311109060f892a76977bcef5ef56cd3.png)  

  

目标 IP：188.59.102.104！  
之后使用 ftp 连接，验证主机存在，同时可以看到 banner 的信息。

  

![](../Images/1e4ecfc2a73f0d78b1c0803bf08f6702.png)  

  

接下来我们将我们的 PoC 导入 Pocsuite 中，PoC 获取可以通过 Seebug，也可以自己编写。导入后，Pocsuite 会将 payload 添加进自身的模块中。

  

![](../Images/dbdbdcd8055cf0fbe5df81492e31ec74.png)  

  

在测试前，我们可以先通过本地安装 freefloat 做一次测试，以确认 Pocsuite 中包含的二进制 payload 可以正常触发攻击行为。在靶机中测试后发现成功触发异常，导致服务崩溃。这个 PUT Command 的缓冲区溢出漏洞的详细漏洞形成原因已经在 Seebug 上作出了说明，这里不做进一步讲解。

**0x04 作为一名海盗船扫地工的思考**

  

一次利用 ZoomEye + Seebug 的探测 + 攻击到这里暂告一段落。实际上 ZoomEye 的玩法多种多样，针对 Web 组件，针对端口服务，甚至于针对于 IoT 设备等等，都有不错的发掘能力。但同时也需要我们拥有一个合适的查询信息用来探测，在初探的过程中，同样发现了一些值得思考的地方，我进行了一些比较粗浅的总结：

  

第一  
  
是如何让 ZoomEye 和 Pocsuite 有更好的结合。在海盗群里大家讨论的时候，提到了 pip install，其实将 ZoomEye API 封装成 SDK，然后在 Pocsuite 或者自己的工具集中引用是一个不错的想法。

  

第二  
  
是 ZoomEye 对 banner 的识别是否完善。是否可以将 Seebug 中所有存在漏洞的组件包含，一些组件所在的端口比较特殊，比如我之前做过的 FHFS 漏洞分析，提到了漏洞端口在5631，那么是否可以通过 Seebug 获取这些特殊组件的端口，并将针对这种端口的探测加入 ZoomEye 的整体之中。

  

第三  
  
是 Pocsuite 的进化。现在对 Web 的支持已经相对饱满，但是仍然不支持二进制方面的 PoC。上述例子虽然也引用了我写的二进制 PoC，但是整个框架还是基于 Web，包括命令执行时还需要调用 -u 这种在二进制攻击中无用的参数。相信今后 Pocsuite 能支持二进制 payload，以便对 IoT 设备、端口服务等进行探测攻击。
