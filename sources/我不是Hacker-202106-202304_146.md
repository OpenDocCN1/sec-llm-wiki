# Http请求走私浅谈

一、前言

最近HAProxy出了一个Http请求走私的漏洞（CVE-2021-40346），很久没关注这个漏洞类型了（RCE和文件上传的洞才会掀起波浪qwq），翻开多年的笔记温习一遍。  

![](../Images/1f34a4bc0b2d1f5a22a96862bdef63e5.png)![](../Images/6427e4ec747a6e625ee2afe9592ec9cb.png)  
二、危害

Http请求走私漏洞可以使攻击者能够绕过安全控制，未经授权访问敏感数据并直接危害其他应用程序用户。  

![](../Images/1f34a4bc0b2d1f5a22a96862bdef63e5.png)![](../Images/6427e4ec747a6e625ee2afe9592ec9cb.png)  
三、成因

反向代理服务器和后端服务器，处理Http请求的实现方式不同，反代服务器认为一个请求为合法请求，发送到后端服务器后，后端服务器只认为其中的一部分请求是正常请求，另一部分请求就是走私请求。

  

主要是因为反代服务器和后端服务器对 **Content-Length（CL）** 和 **Transfer-Encoding: chunked（TE）** 同时存在时的处理差异导致的

![](../Images/1f34a4bc0b2d1f5a22a96862bdef63e5.png)![](../Images/6427e4ec747a6e625ee2afe9592ec9cb.png)  
四、分类

根据反代服务器和后端服务器根据哪个头（CL，TE）解析，可分为5类

  

**1\. 解析一致(TE--TE)**

这种情况一般不会产生Http请求走私

  

**2\. 解析一致(CL--CL)**

2个CL，反代和后端解析不一样的CL

  

**3\. CL不为 0 的GET请求**

假设前端代理服务器允许GET请求携带请求体，而后端服务器不允许GET请求携带请求体，它会直接忽略掉GET请求中的Content-Length头，不进行处理

  

**4\. CL--TE**

所谓CL-TE，就是当收到存在两个请求头的请求包时，前端代理服务器只处理Content-Length这一请求头，而后端服务器会遵守RFC2616的规定，忽略掉Content-Length，处理Transfer-Encoding这一请求头

  

**5\. TE--CL**

所谓TE-CL，就是当收到存在两个请求头的请求包时，前端代理服务器处理Transfer-Encoding这一请求头，而后端服务器处理Content-Length请求头
