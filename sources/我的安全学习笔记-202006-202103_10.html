    疑问解答：

    上篇中提到经过分析 /dubbo/qos/legacy/InvokeTelnetHandler.java 文件，发现Dubbo在InvokeTelnetHandler.java时候就使用了Fastjson进行数据解析。

该文件在这里（上一篇地址没有给对）：

https://github.com/apache/dubbo/blob/3257ef48f524c748c0651e97f6a8d06ff2963c94/dubbo-plugin/dubbo-qos/src/main/java/org/apache/dubbo/qos/legacy/InvokeTelnetHandler.java


这里是处理telnet连接上来的invoke命令的函数定义，可以看到invoke命令的参数的处理过程。这里拿到命令的参数args后，直接进入了JSON.parseArray处理。就是这里打开了Fastjson反序列化漏洞利用入口。

这里有点意外的是，这个JSON.parseArray和平时看到的Fastjson漏洞poc触发方式不一样。平时复现时多数为JSON.parse(xxx) 或者 JSON.parseObject ，这里看来也是触发了Fastjson漏洞了。

出于好奇，我还像下面这样试了一下:

String bbb = "[{\"@type\":\"java.net.Inet4Address\",\"val\":\"c5n7qw.dnslog.cn\"}]";List list = JSON.parseArray(bbb, Object.class);

结果果不其然，构造 [poc] 这样的数组形式字符串，是可以触发的。【内心一片吃惊，fastjson的fuzz插件遗漏了这种形式的参数，赶紧补上。】


我们以https://github.com/apache/dubbo-spring-boot-project 2.7.x为例，下断点调试看一看，确实telnet连接上，invoke正常进入了fastjson的解析。

这里证明了未授权的dubbo服务端口等于开放了Fastjson的漏洞利用入口。


     

    疑问解答2：我怎么知道我的dubbo使用了什么版本的fastjson？

      解决这个疑问可以从Maven的仓库去查，所谓的Dubbo其实有多个版本，阿里自身维护的版从dubbo2.0.* 到  2.6.*，开源给apache后，维护的是dubbo 2.7.*版本，以及原阿里dubbo团队解散后，当当维护了一个dubbox的版本。地址分别是：

  1. https://mvnrepository.com/artifact/com.alibaba/dubbo【阿里在维护】

  2. https://mvnrepository.com/artifact/org.apache.dubbo/dubbo【开源社区在维护】

  3. https://github.com/dangdangdotcom/dubbox【当当的几个核心开发者，3年前已停更】

这里需要注意的是，当当维护的Dubbo，从版本号是很容易迷惑人的，比如下面。

我怎么知道哪些容易被攻击？


     通过maven的依赖关系可以看出使用fastjson的版本情况, 这里以公开的fastjson 1.2.47以下版本通杀poc影响的版本来举例：

  • 阿里dubbo 2.6.8 以下使用的是fastjson<=1.2.60, 其中dubbo <= 2.6.7使用的fastjson<=1.2.46.

  • Apache dubbo <=2.7.3以下使用的fastjson<=1.2.46.

  • 当当 dubbo 3年前已经挺更了，停更前fastjson最后升级版本为1.2.28.

甚至还有大佬开始担心这些老的dubbo也受到最近的漏洞的影响

探索修复方案：

    对于Dubbo在安全方面，Dubbo提供通过配置Token令牌防止用户绕过注册中心直连，然后在注册中心上管理接口的访问权限。Dubbo还提供服务黑白名单，来控制服务所允许的调用方。

   

   1、配置Token方案，解决暴露的dubbo服务被恶意的消费者直接连接和调用

   参考文档

http://dubbo.apache.org/zh-cn/docs/user/demos/token-authorization.html

<dubbo:provider interface="com.foo.BarService" token="true" /> # 随机token<dubbo:provider interface="com.foo.BarService" token=“12340@!@#" /> # 自定义token

 

 在telnet下进行直连自定义的服务，提示token不可用。

 

2、配置dubbo协议，telnet支持的命令，我们只允许status, ps 这样的简单的命令

http://dubbo.apache.org/zh-cn/docs/user/references/xml/dubbo-protocol.html

3、配置prompt提示信息，伪装dubbo的指纹

<dubbo:protocol name="dubbo" port="20882" prompt="zookeer" telnet="pwd"/>

伪装之后，telnet连接上去看到的如下：

Nmap进行服务识别，已无法扫描出Dubbo的服务。【伪装成功】

4、自定义validation，对服务进行IP白名单限制

    a. 在/resources目录下，新建META-INF/dubbo目录，并新建一个名为com.alibaba.dubbo.rpc.Filter的文本文件，内容如下：

ipWhiteListFilter=com.tommy.service.provider.filter.IPWhiteListFilter

    b. dubbo的配置文件中增加filter的配置：

<dubbo:service interface="com.exploitcat.api.DemoService" ref="demoService" protocol="dubbo" filter="validation"/>

    c. 新建ValidationFilter类

package com.filter;import java.io.IOException;import java.io.InputStream;import java.util.Properties;import com.alibaba.dubbo.rpc.*;

public class ValidationFilter implements Filter {    @Override    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {        Properties prop = new Properties();        InputStream in = ValidationFilter.class.getResourceAsStream("/ipwhitelist.properties");        String clientIp = RpcContext.getContext().getRemoteHost();//客户端ip        try {            prop.load(in);            String ipwhitelist = prop.getProperty("ipwhitelist");//ip白名单            if (ipwhitelist.contains(clientIp)) {                return invoker.invoke(invocation);            } else {                return new RpcResult(new Exception("ip地址："                        + clientIp + "没有访问权限"));            }        } catch (IOException e) {            e.printStackTrace();        } catch (RpcException e) {            throw e;        } catch (Throwable t) {            throw new RpcException(t.getMessage(), t);        }        return invoker.invoke(invocation);    }}

5、其他建议

  • Dubbo 和 Zookeeper 基本都是部署在内网，不对外网开放

  • Zookeeper 的注册可以添加用户权限认证

  • 升级保持官方发布的最新版本
