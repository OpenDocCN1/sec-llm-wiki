二、审计

1、目录结构分析

一般代码审计先看目录结构情况，不管是否是框架都可根据文件夹名称了解该网站的大致情况。

可以看到安装完的semcms目录结构如下：



  • Edit

根据名称是一个什么编辑目录；点开目录看到文件kindeditor.js之后基本确定是kindeditor编辑器。发现这个可以直接看一下js内容，直接查找版本漏洞，没必要专门去审计他。



  • Images

一看名称就可以得知是图片目录可以看到images目录里面再分了目录，为网站不同模块的的图片。



  • Include

包含的一些文件内容，可能存在某些重要文件什么的，需要审计看看。



  • Install

网站的安装目录，这个cms安装完成之后有对安装文件进行删除，遇到么有删除安装文件的cms可直接对安装文件进行利用；当前cms已将安装文件进行删除。



Templete

文件名称来说就是模板，点进去看可以发现基本为前台文件。



  • TydhOi_Admin

看到admin基本可以判断该目录为后台文件。



其他文件

然后就是接口或者解析什么的文件，这里都可以分别看一下，一个是index.php看看有没有文件包含或什么的，然后就是robots.txt有没有泄露些什么，sitemap.xml看看有没有泄露什么，最后就是使用说明的文本文件，这个也是一个隐患文件，包含了网站建站信息。



目录结构看完，可以不用急着去代码分析，再看一下网站功能点，以及数据表结构，有助于之后的代码分析。

  • 后台

4、include目录

  • Class文件

class.phpmailer.php、class.smtp这两个文件是php处理邮件用的特定类，不用看。


  • Contorl文件

contorl.php一打开就看到注释说是防注入的，之后我们仔细分析一下代码。


 


以下代码片段表示对get进行传递的参数使用verify_str函数，后门还比较贴心害怕你看不懂，备注了get。



然后进行追踪verify_str函数，该函数收取参数作为$str,然后调用inject_check_sql函数进行判断，如果返回值为真，则显示错误信息，否则返回该字符串。



这里调用了inject_check_sql函数，我们对该函数进行跟踪，发现用到了preg_match函数，该函数根据正则表达式对字符串进行搜索匹配，当我们传入的字符串中出现列出的字符串，那么返回true，否则返回false。根据正则表达式可以发现，过滤如下：

Select、insert、update、union、load_file、outfile、’

 

可以发现闭合只过滤了单引号，相关sql语句过滤也不全，还有一些报错函数没有过滤。根据作者编写的防sql文件，可以分析得出以下几种情况的注入：

当闭合为数字；当闭合双引号；当闭合是单引号，但没有使用到verify_str函数进行检测；由于所有get都会检测，那么只有post传参的情况；报错注入。



到这里可以有两个走下去的方法，一个是直接根据情况进行全局搜索，匹配相关注入；一个是继续通读全部代码，把当前发现的先保留。

当然，一般情况是直接进行匹配搜索，毕竟留在哪里心里面痒。

这里我们还是先把contorl.php文件读完先

 

之后的代码是一个邮件发送的代码，基本没有什么

 



  • 反射型xss

再之后有个获取IP的，作为一个开发应该对这段获取ip的代码比较熟悉，这里是直接获取head信息里面的Client-IP信息或者X-Forwarded-For信息，其中Client-IP是直接拿来用的，然后X-Forwarded-For经过分割。



然后前面看数据表结构和网站结构的作用来了，因为在网站后台处存在一个显示ip的地方，更改网站head的Client-IP或X-Forwarded-For为xss语句，实现弹窗。



  • 用户登录判断

再往后读取，发现一个验证用户登录情况的判断，简单一看逻辑上好像可以绕过。获取cookie对应的参数，在到数据库查询匹配。



但是仔细一看，获取的两个cookie值，经过两次处理，第一次是test_input，看了一眼test_input，首先替换了%，然后去字符串首尾空格，解转义，实体编码。再加上verify_str的处理，这个点也可以直接丢掉了。




5、Sql注入

由于前面通过contorl.php已经了解防sql注入的规则，可能还有其他的防护，但可以以此来进行过滤查找。

一个是通过相关sql语句、单词进行全局筛选，适合细致审计

一个是结合代码审计工具来审计

这里我们查看seay的审计结果，根据目录的分析，我们主要看Templete目录和TydhOi_Admin目录下的漏洞

审计工具给到的是Fuction.php这个文件内存在大量注入，我们依次来查看。



  • 第一个点：

根据sql语句已经数据包情况，这里是纯数字，但是追踪了一下web_nav。



没有发现参数$language的获取，然后追踪的文件又是include目录下的，此时需要找一下language从哪里获取的，直接全局找一下。



全局找到一个language的获取。



通过打印对应的参数，发现传递的参数不可进行更改。审计到后面，发现这里审错了，功力不够啊。。。。。



后面发现一个注入点，进行追踪审计时，发现参数languageID传递的值到了这边。



根据这个点的sql语句，我们查找了一下监听结果，发现sleep函数被成功带入。

  • 用户登录判断

根据源代码看到是直接去判断cookie中的两个参数，获取再拿到数据库去匹配。但是这里的注入没有办法绕过，参数采用了单引号闭合，而单引号被过滤了无法对语句闭合。



我们可以看一下参数传递后的sql语句，这个点也可以放弃了。



Sql注入就审这些吧，要细致的话就把所有sql语句进行归类、拆分，然后进行审计。

由于网站写防sql注入是采用的黑名单，然后又只对get请求判断，反正根据这些特点，对sql语句进行筛选，就可以查到剩下的注入漏洞了。


6、任意密码重置

根据功能点进行的审计，发现密码重置处存在任意重置的逻辑漏洞

首先查看验证码生成以及发送的处理，验证码的生成是根据函数rand从10到10000中选取的随机数，生成后调用配置文件进行发送。我们这里可以看到一句update的sql语句，他将获取到的验证码存到了数据库。



由于没有配置邮件服务器，点击发送后出现错误。但是不影响，数据库已经获取到新的验证码。



再之后，我看看下面的验证代码，一句为查询验证码匹配，一句为密码更新。



测试也很简单，直接对接口进行爆破。



这里遇到一个坑，最开始没有去数据库查看验证码，直接按照逻辑走进行爆破。结果返回状态码和长度都一样，我还以为我搞错了，忽略了什么。结果就是一样。。。。。。黑盒测试下不注意估计就错过。
