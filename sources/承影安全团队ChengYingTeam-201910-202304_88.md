## 0x00  Spring Boot Actuator 简介

Spring 是一个轻量级的 java 开发框架，而 Spring Boot 可以让开发者更加快速的开发 Spring 应用程序。其最大的特点就是自动化配置，能根据类路径下面的 jar 包和配置，动态加载配置和注入 bean。Actuator 是 Spring Boot 提供的服务监控和管理中间件。当 Spring Boot 应用程序运行时，它会自动将多个端点注册到路由进程中。而由于对这些端点的错误配置，就有可能导致一些系统信息泄露、XXE、甚至是 RCE 等安全问题。

## 0x02  JNDI 注入

当然，JNDI 注入有各种各样的方法，并且各种 JDK 版本限制也不同。参考链接 https://kingx.me/Restrictions-and-Bypass-of-JNDI-Manipulations-RCE.html ，这里利用的是文章中 `kingx` 大佬提供的方法：利用本地 `Class` 作为 `Reference Factory class` ，来绕过高版本 JDK 的限制。

![](../Images/00d7fed3f987313be6089d41845f9092.png)

现在，我们来梳理一下整个利用流程：  

1\. 构造 Get 请求访问目标，使其去外部服务器加载恶意 `logback.xml` 文件；

2\. 解析 `logback.xml` 时，最终会触发 `InitialContext.lookup(URI)` 操作，而URI 为恶意 RMI 服务地址；

3\. 恶意 RMI 服务器向目标返回一个 Reference 对象，Reference 对象中指定了目标本地存在的 BeanFactory 类，以及Bean Class 的类名、属性、属性值（这里为 `ELProcessor` 、`x`、`eval(...)`）；

### 0x02  RMI 远程对象调用流程

*   如果 Client 端向 RMI 请求一个远程对象，那么 RMI 会给 Client 端传递一个远程对象的 Stub。Stub 可以相当于是对远程对象的引用或者代理，其中包含了远程对象的 Socket 端口、Server 端主机地址等信息。而 Stub 的一种获取方式，就是通过调用远程方法。但是调用远程方法又必须得先有远程对象的 Stub 。那么这里就会出现一个死循环的问题。于是，JDK 提供了一个 RMIRegistry 来解决问题。
    
*   那么当有了 RMIRegistry 之后，RMI 的远程对象的调用流程如下图：
    
    ![](../Images/33c6131ccaa9d7532660e98c243da18f.png)
    
*   由图可知，当 Client 端向 RMIRegistry 查询某个远程对象的名称（2）时，如果这个远程对象存在于注册表中（即 Server 端已经注册（1）的远程对象），那么 RMIRegistry 将会给 Client 端（3）返回这个远程对象的 Stub。Client 端根据 Stub 中的信息，去对应的 Server 端（4）调用远程方法。
    
*   所以从 Client 端的角度来看， Server 端其实是有两个端口：RMIRegistry 端口和远程对象通信端口。对应上述我们的 RMI 恶意服务代码。可以发现，我们其实只设置了 RMIRegistry 端口为 1099。虽然远程对象的通信端口是随机分配的，但是我们并没有设置远程通信对象的 Host ，而其默认值是 Server 端本地主机名对应的 IP 地址。
