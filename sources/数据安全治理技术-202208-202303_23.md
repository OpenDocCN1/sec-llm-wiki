# 一致性哈希算法应用及说明

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzAwNzk2OTQ4MQ==&mid=2247483721&idx=1&sn=5501aa6d276b08d6659cffb307bdb8c2&chksm=9b774eefac00c7f970d5dd25f522370fcb672bed060c0e25b5cc4d8aa3eac159789dfd20b212&scene=126&sessionid=1681269349#rd](http://mp.weixin.qq.com/s?__biz=MzAwNzk2OTQ4MQ==&mid=2247483721&idx=1&sn=5501aa6d276b08d6659cffb307bdb8c2&chksm=9b774eefac00c7f970d5dd25f522370fcb672bed060c0e25b5cc4d8aa3eac159789dfd20b212&scene=126&sessionid=1681269349#rd)

     一致性哈希算法在1997年由麻省理工学院提出，是一种特殊的哈希算法，目的是解决分布式缓存的问题。 在移除或者添加一个服务器时,能够尽可能小地改变已存在的服务请求与处理请求服务器之间的映射关系。一致性哈希解决了简单哈希算法在分布式哈希表( Distributed Hash Table，DHT) 中存在的动态伸缩等问题。  

  

  

01

—

场景描述

  

我们有三台缓存服务器，用于缓存图片，我们为这三台缓存服务器编号为0号、1号、2号，现在，有3万张图片需要缓存，我们希望这些图片被均匀的缓存到这3台服务器上，以便它们能够分摊缓存的压力。

  

  

02

—  

 普通hash方式

** hash(图片名称) % 3**  3为服务器数量。对文件或图片名称进行hash，得出的结果应该是不变的，如果我们有3台服务器，使用哈希后的结果对3求余，那么余数一定是0、1或者2,正好对应服务器编号

![](../Images/d85996270588755a20d529eb7ecc0007.png)

  

缺陷：当一台服务器出现问题，或者增加一台服务器时，所有数据都要重新缓存。会引起缓存的雪崩，可能会引起整体系统压力过大而崩溃。

03

—  

一致性hash说明

  

我们把2的32次方想象成一个圆，就像钟表一样，钟表的圆可以理解成由60个点组成的圆，而此处我们把这个圆想象成由2^32个点组成的圆

![](../Images/31f495627e4985d3c3d5df39cc17a3c1.png)

正上方的点代表0，0点右侧的第一个点代表1，以此类推，2、3、4、5、6……直到2^32-1,也就是说0点左侧的第一个点代表2^32-1，构成一个hash环。

  

上面的三台服务器，我们可以通过公式：hash（服务器A的IP地址） %  2^32

通过公式可以把三台服务器分布到环上。

![](../Images/90736eee1b3df75454dedb33668f9a03.png)

  

图片数据公式：**hash（图片名称） %  2^32**

通过上面公式，我们可以把所有图片分布hash环上，顺时针找到最近服务器

![](../Images/c056197def940a845a9669acca9d4670.png)

一致性哈希算法就是通过这种方法，判断一个对象应该被缓存到哪台服务器上的，将缓存服务器与被缓存对象都映射到hash环上以后，从被缓存对象的位置出发，沿顺时针方向遇到的第一个服务器，就是当前对象将要缓存于的服务器，由于被缓存对象与服务器hash后的值是固定的，所以，在服务器不变的情况下，一张图片必定会被缓存到固定的服务器上，那么，当下次想要访问这张图片时，只要再次使用相同的算法进行计算，即可算出这个图片被缓存在哪个服务器上，直接去对应的服务器查找对应的图片即可

  

  

04

—  

一致性hash优点

  

某台服务器出现故障，我们现在需要将服务器B移除，那么，我们将上图中的服务器B从hash环上移除即可，移除服务器B以后示意图如下：

![](../Images/cbf105da2b75d0df29b19e8d3d9ef260.png)

当服务器B移除以后，按照之前描述的一致性哈希算法的规则，图片3应该被缓存到服务器C中。其它节点缓存服务器不变。不会出现全部重新缓存的情况。

  

05

—  

hash倾斜

  

  

一致性哈希的概念时，我们理想化的将3台服务器均匀的映射到了hash环上，如下图所示：

![](../Images/90736eee1b3df75454dedb33668f9a03.png)

理想很丰满，现实很骨感，我们想象的与实际情况往往不一样

![](../Images/c6ea9a1cf59bae552f79e326e00309fd.png)

如果服务器分布不均，很可能出现下图这样：

![](../Images/207f34dbdebdedd22284c47aa7421d02.png)

1号、2号、3号、4号、6号图片均被缓存在了服务器A上，只有5号图片被缓存在了服务器B上，服务器C上甚至没有缓存任何图片。极端情况下，仍然有可能引起系统的崩溃。

**上面的问题可以通过虚拟节点方式解决：**

凭空的让服务器节点多起来，既然没有多余的真正的物理服务器节点，我们就只能将现有的物理节点通过虚拟的方法复制出来，这些由实际节点虚拟复制而来的节点被称为”虚拟节点”

![](../Images/2c694daafa62df117fee9ade3732d111.png)

“虚拟节点”是”实际节点”（实际的物理服务器）在hash环上的复制品,一个实际节点可以对应多个虚拟节点。

A、B、C三台服务器分别虚拟出了一个虚拟节点，当然，如果你需要，也可以虚拟出更多的虚拟节点。引入虚拟节点的概念后，缓存的分布就均衡多了。
