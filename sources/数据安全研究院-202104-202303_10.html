在阅读笔记|挖掘0day的新“姿势”一文中我们跟大家推荐了 "SaTC" 这个自动化挖漏洞的工具，想必大家已经开始挖洞了吧！是不是发现自动化挖洞时间有点长呢？趁着SaTC在自动挖漏洞的空档，本文再来讲讲SaTC的技术原理，了解下安全大牛们的技术思想，学习下自动化挖漏洞工具的关键技术。



简介
嵌入式设备固件漏洞挖掘技术简介

SaTC挖掘漏洞的对象是嵌入式设备固件，具体就是无线路由器、网络摄像头等设备。针对这类漏洞挖掘，现在一般有两种方法：

1）动态分析法，将设备固件运行起来后进行测试。典型的动态分析方法如Fuzzing，它的挑战在于需要有真实设备（一般人可能做不到买那么多设备）或仿真环境，而仿真环境的搭建就是个比较大的挑战，例如2016年在NDSS上发表的FIRMADYNE就是个比较好的仿真工具，但能支持的设备也有限；

2）静态分析法，对设备固件文件（一般为二进制程序文件）进行分析。典型的静态分析方法如符号执行，它的挑战在于难以准确全面的模拟程序上下文，解决如跨进程通信、路径爆炸、开销大等问题。经过多年的技术发展，现在比较有效的是一种混合符号执行（Concolic Execution）技术，也称之为动态符号执行，而传统的静态符号执行基本上是不可用的。例如2020年在S&P上发表的KARONTE就是个比较好的动态符号执行工具。SaTC也属于该类工具，它在KARONTE的基础上做了一些创新和改进。



技术思想

为了让大家更直观的了解SaTC自动化漏洞检测的思想，我们通过一个漏洞实例来展开说明。图1展示的是一个典型的路由器命令注入漏洞实例，这个漏洞触发的步骤如下：先往路由器上插入U盘，然后进入路由器管理界面，在USB App管理界面中点击 "Unmount"按钮触发卸载USB功能，在这个功能接口中进行命令注入。

图1 典型路由器命令注入漏洞

接下来，我们来深入分析下图1这个漏洞产生的技术原理。如图2所示，Front-End是路由器固件的前端界面及相应代码，Back-end是路由器固件的后端服务代码。可以看到在前端界面对应的js代码中有一个函数 unLinkUsb，这个函数的主要作用就是向后端服务发送卸载usb设备的请求。该函数第4行代码表示向后端请求地址为goform/setUsbUnload的服务，请求参数为deviceName。我们再看右侧的后端服务代码，其第4行代码表示从请求体中取出deviceName参数的值并赋值给cmd变量，第5行代码表示执行系统命令（doSystemCmd是该路由器中用于调用系统命令的函数名），而参数是由一段固定字符串与cmd变量进行字符串拼接后的字符串。只要在发送该请求时，对deviceName参数值做些特殊构造，如构造值为 abc;ls，那么后端服务代码经过拼接后的字符串为 "netctrl ?op=,string_info=abc;ls"，该字符串作为系统命令执行时，会在执行完分号前的命令后再执行ls命令。这样我们就可以在分号后构造任意命令让系统执行，这就是典型命令注入漏洞的技术原理。

图2 典型路由器命令注入漏洞

通过上述分析，有一个直观的感觉就是前端JS文件中出现的关键字 deviceName 同时出现在了后端的二进制程序中，并被用于提取其从前端中传入的值。如图3所示，在前端JS文件中，用户输入被一个字 符串"deviceName="标记，在后端的二进制程序中，采用完全相同的字符串 "deviceName"可提取http请求数据包中对应的deviceName的值。

图3 前后端存在 deviceName 共享关键字

根据http接口设计常识可以推断，前后端文件中是存在很多共享关键字的（前端发送请求中的参数名称，在后端都会有对应提取参数值操作）。如果可以把这些关键字从前端文件中提取出来的话，那么就可以在污点分析的过程中起到作用。传统的污点分析都是从入口函数开始的，而对于嵌入式设备来说，在http服务接口函数前的这些函数并没有太多分析意义，因为这些函数与通过发送http请求实现命令注入并没有太大关系。如果有这些前端关键字的话，污点分析就可以重点关注http服务接口函数，其涉及的符号执行路径会极大缩减，在可用性上就得到了进一步的提升。通过前后端共享的关键字，找到这些关键字在后端二进制程序中的引入点，再将这些引入点作为污点分析的起点进行漏洞检测，这就是SaTC的技术思想。有了这个想法后，作者通过实验统计分析，最终确认这种现象并不是只有这个路由器才存在。如图4所示，作者提取了10款不同设备的前端输入，验证平均有 92.4% 的关键字参数对同时出现在前后端。同时，作者对近期的35个可以获取固件的CVE进行分析，发现其中的29个可以通过共享关键字来定位漏洞点，说明这个方法具有一定的普适性。

图4 主流路由器设备前后端关键字统计分析



挑战

验证想法基本可行后，接下来就是实现问题。通过对上述想法的梳理，如图5所示，接下来的实现工作大概会面临以下三个挑战：

1.识别前端文件中的关键字。前端文件数据量多，关键字数量多，如何全面、准确地识别前端文件中的关键字是一个挑战；

2.定位后端二进制程序中的用户输入处理函数。后端二进制程序中有大量函数，但只有少部分函数会处理用户输入，同时，二进制程序中包含大量字符串和交叉引用的指针，如何正确标识用户输入的引入点是一个挑战；

3.跟踪大量用户输入的相关路径，检测是否存在安全漏洞。从用户输入的引入点到可能存在问题的函数间可能包含大量路径，对大量路径的跟踪分析，现有工具存在高开销问题，且无法处理复杂的CFG或绕过用户输入的sanitization方法，需要一个有效的方法来做数据流分析和路径探索。

图5 三大挑战说明



技术原理
一、SaTC技术架构

为了解决上述问题，作者提出了SaTC，将嵌入式设备固件作为输入，经过SaTC分析后，输出可能存在的漏洞，其技术架构如图6所示，主要包括五个模块：

1.Pre-Processing 模块，负责对固件做些预处理操作，将前端文件和后端文件识别出来；

2.Input Keyword Extraction 模块，主要用于从 Front-End 文件中提取出关键字；

3.Input Entry Recongnition 模块，它的输入包括 Back-End 文件和从 Input Keyword Extraction 模块中识别的关键字，主要作用是识别出关键字在 Back-End 文件中的位置，即 input entry；

4.Taint Engine 模块，向 Input Sensitive Data Flow Analysis 模块提供污点分析能力，用于检测是否存在漏洞；

5.Input Sensitive Data Flow Analysis 模块，该模块的输入为 Input Entry Recognition 模块中识别出的 input entry，主要作用是从 input entry（Start Point） 开始，对数据流进行分析并输出可能存在的漏洞。

图6 SaTC技术架构


二、关键技术

1. Input Keyword Extraction

输入关键字提取模块，该模块的主要作用是从一堆前端文件中提取出关键字。关键字基于其在后端的使用方式分为两类：1）parameter 类关键字，用于标识用户输入，类似 deviceName 参数；2）action 类关键字，用于标识处理函数，类似 setUsbUnload 函数。

第一步从前端文件中提取关键字，常见的前端资源文件HTML、JS、XML三种类型分别进行处理：

1.HTML：使用正则表达式提取关键字，例如 id、name、action 等属性对应的值，id、name等属性对应的值作为 parameter 类关键字，action属性的值作为 action 类关键字；

2.XML（SOAP、UPnP）：使用固定格式，第一级标签的 name 作为 action 类关键字；

3.JavaScript：将js代码解析为 AST，提取所有 Literal 节点的 value attributes 的值作为 parameter 类关键字，提取包含 / 符号的 Literal 节点的字符串为 action 类关键字，扫描所有 CallExpression 节点，提取被特定API（如sendSOAPAction）调用的 CallExpression 节点的名称和参数作为 action 类关键字等。

第二步是对提取的关键字进行过滤。在第一步中会提取出大量的关键字，但里面包含了很多无用、无效的字符串，这里需要根据一些前端开发经验进行过滤，如采用以下规则：

1.过滤掉一些包含特殊符号的字符串，例如!、@、$等符号；

2.字符串以“=”结尾的，仅保留等号前的内容；

3.去除长度少于指定阈值的字符串，默认为5；

4.采用两种heuristics（启发式）方法识别并排除关键字：1）去除共享库中字符串，JavaScript文件被一堆HTML文件引用，我们认为是通用文件，公共库，例如charting library等；2）过滤多个前端文件中同时出现的高频关键字，例如Button、Cancel等。

现在我们有了前端文件中包含的所有关键字，但是你会发现后端还有大量的二进制程序文件，那么就需要确认哪个二进制程序文件才是前端文件对应的后端服务文件。这里作者也提供了一个简单的方法进行识别：使用GNU strings提取所有后端二进制文件中的字符串，将前端文件中提取的关键字与后端二进制程序中的字符串进行匹配，对所有二进制文件按照匹配到的关键字数量进行排序，可以认为关键字数量靠前的就是对应的后端服务的二进制程序，这样就把边界服务识别出来了。


2. Input Entry Recognition

当后端服务接收到一个前端请求时，web server会调用相应的处理函数解析前端输入的数据，这里的前端数据解析提取点就是分析的目标，这个提取点就是input entry。Input Entry Recognition模块的主要作用就是在后端二进制文件中找出前端关键字对应的引入点。

2.1关键字引用定位

最直接的定位就是关键字的引用定位，如图7所示，L和P都是属于关键引用的函数，都可以认定为input entry。具体如图8中的deviceName，红色框语句就是input entry。

2.2隐式引用定位

但有时候会出现后端二进制程序中的input entry在前端文件中找不到相应的关键字的情况，这时就需要通过上下文启发式方法解决，也就是文章中提到的对隐式引用的定位。例如图9中的formSetSambaConf函数负责从网络数据包中接收参数，每个参数字符串都会被认定为是有效的input entry，例如password。然而在关键字提取模块中并未在前端文件中找到action和usbName关键字，即正常使用前端界面发送网络请求时，数据包中会缺少action和usbName参数，此时第4行将会返回null，第9行判断值为false，导致第10行中的命令注入漏洞不会被触发，因此正常情况下这个漏洞是不会被发现的。解决方案就是把与已知input entry类似代码模式的代码也认为是input entry，即通过password关键字可以找到Extract(data,"password","admin")这个input entry，那么可以同时认定Extract(data,"action",&unk_F213C)也是input entry（即使关键字提取模块并未提取出action关键字），这样在后续分析的时候就会存在从action这个input entry到doSystemCmd函数的路径，可以发现该漏洞。

2.3 跨进程引用的定位

在后端程序中，有些数据通信是跨进程的，关键字出现在多个后端二进制程序中，这种情况下就需要特殊处理，否则会丢失input entry。如图10所示，1）SetWebFilterSettings函数是二进制程序prog.cgi的代码，第2行代码将网络请求数据包中的 /SetWebFilterSettings/WebFilterMethod 关键字对应内容取出放到pcVar1变量中，第7行代码将pcVar1变量值存储到nvram的url_filter_mode键中；2）upload_url_filter_rules函数是二进制程序rc的代码，第14行代码从nvram中取出url_filter_mode键的值，因此，用户的输入可以从prog.cgi程序传播rc程序的__s1变量上，这行代码也应该认定为input entry，也需要进行污点分析。UCSB的KARONTE能支持多个二进制程序间的识别，但是它无法从用户输入的源头开始分析。

图10 跨进程数据通信


3. Input Sensitive Data Flow Analysis

在通过关键字识别到一些input entry后，接下来就要开始做输入敏感的数据流分析。这里面将会涉及到三个核心技术：1）Coarse-Grained Taint Engine；2）Efficient Path Exploitation；3）Path Prioritization Strategy。

3.1Coarse-Grained Taint Engine

粗粒度的污点分析引擎，基于用户输入进行轻量化的数据流分析，目标是兼顾效率和准确性。

第一步是污点源的设置。根据input entry标记污点源，这个污点源可以是目标函数的参数或者返回值，如图11所示，根据deviceName关键字找到第9行代码作为input entry，这时可以设置cmd字符串指针变量为污点源。

图11 污点源示例

第二步是设计污点传播策略。污点引擎在指令级别传播污点属性，基于angr来实现多架构二进制程序支持。影响污点分析效率和准确性的关键在于函数调用的污点定义，这里的解决方案是把函数分成下列三种类别，并通过算法1对三类函数进行分析处理：

1.summarizable function：标准库函数，与操作内存区域相关，如strcpy、memcpy；

2.general function：不包含任何函数调用指令的函数，或只有调用summarizable function，如图12中的funcA，仅包含strlen、strcpy标准库函数调用；

3.nested function：嵌套函数，包含调用general function的函数，如图12中的funcB，第17行代码调用funC函数。

图12 不同函数类型的污点定义

算法1逻辑说明：

1.如果Ins指令不是函数调用时，污点引擎使用相应的污点规则（第19行代码）处理，并更新Taint_Map；


2.对于数据赋值指令，污点引擎将污点属性从源传递到目标操作符；


3.如果Ins指令是函数调用func，它的一个实参包含污点属性（第5行代码），污点引擎将跟踪func对Taint_Map的影响：

● 如果func为summarizable函数，根据函数语义进行污点分析（第8行代码）

● 如果func是general函数，将进入函数并跟踪从入口点到函数结束的数据流（第16行代码）

● 如果func是nested函数，如果一直进入函数跟踪所有数据流将会耗费大量时间，这里采用直接传播参数属性到计算结果（第9-14行代码）。如果函数有返回值，则所有参数的污点属性将传播到函数返回值retv，否则参数的污点属性传播到所有指针参数上。


3.2Efficient Path Exploitation

为了在路径探索时高效的处理函数，可以将所有函数分类处理，如图13所示，左侧是一个函数调用树，右侧表示将这个调用树中的函数分成两类：一类为Guiding Function；另一类为Sink Function，包含可能存在漏洞的函数，为了加快路径探索，SaTC仅关注可能导致两类漏洞的函数：
1.memory-corruptionbugs，如 buffer overflows，关注memcpy-like函数，例如strcpy。在二进制中找memcpy-like函数，将这些函数标记为sink函数。如果攻击者可控输入可不安全的到达memcpy-like函数，这时就会报告存在漏洞；
2.command injection，关注system-likefunction，并将这些函数标记为sink函数，检测攻击者是否可以构造poc绕过约束，如果可以就报告存在漏洞。

图13 input entry调用树

虽然仅关注这两类函数，仍然有一大堆的input entry需要跟踪分析，为了提高分析效率，在探索路径之前先搜索函数里面是否存在sink call trace（sink call trace表示一个从input entry到sink function的函数调用序列），如果不存在则删除这个函数中的所有input entry，不用再对这个函数进行分析。

同时，每个input entry可能都会有大量的调用跟踪，而许多调用跟踪会共享一些通用路径。为了减少分析量，可以尽可能的合并一些相同input entry的调用跟踪，避免重复分析。


3.3Path Prioritization Strategy

有一些特殊函数在路径探索中对准确性和效率有重要的影响。例如，sanitizer类函数可能导致无限循环，parser类函数可能引入under-taint问题。为了减小这些函数引入的问题，可以对这些函数进行识别并做特殊处理，当某个函数符合三个条件：1）包含至少一个循环；2）函数中包含超过阈值的比较类指令；3）部分比较指令可以影响函数参数所指向的内存区域的内容，可以将这个函数按照memcmp-like类函数进行处理。符合这些条件的函数可以分成两类：

1.parsers：包含一个loop，switch条件，在循环中跳转到其他指令，污染其他指令，采用与 KARONTE 相同的方式处理，需要验证函数中的所有路径，看是否会跳转到其他位置，如图14所示：

function SANITIZER_CONS_COLLECTION(totalNodes, Max, N, rootNode)  Tree ← 0/  visitedNodes ← 0/  basicNodes ← totalNodes  times ← 0  if !HASSUCCESSOR(rootNode) then return 0/;  end if  while visitedNodes != basicNodes and times < Max do    Tree, visitedNodes ← RANDOM_WALK_SEARCH(rootNode, Tree, visitedNodes, basicNodes)    times++;   end while   for leafNode in Tree.leafNodes do     if num ← GET_FORWARD_NUM(leafNode) > N then       Tree ← REMOVE(basicNodes, leafNode)     end if   end for   Cons ← GET_PATH_CONSTRAINTS(Tree)   return Consend functio
算法2逻辑说明（算法的主要目的是探索最长路径并获取约束）：

1.rootNode是待分析函数调用树的起始基本块，使用RANDOM_WALK_SEARCH函数探索从rootNode开始的后续基本块（第8行代码）。RANDOM_WALK_SEARCH随机选择一个rootNode后续基本块，循环调用直到找到叶子节点，并记录叶子节点（第9行代码）；


2.扫描出所有叶子节点，删除入度比阈值N大的叶子节点（第13行代码），如图15代码段中else分支代码块是入度最大的叶子节点，根据阈值判断后应该会被删除。阈值N可以设置为块总数的一半，意味着有超过一半的基本块都会走到该叶子节点，但凡出现这种特征可以判断当前函数是sanitizer类函数；


3.最后，在Tree中重新探索函数路径，输出最长路径约束（第17行代码），只要用户输入符合这个约束并在后续代码中检测出漏洞，那就意味着发现了可利用的漏洞。



实战示例

目标：使用SaTC分析路由器固件US_AC15V1.0BR_V15.03.05.19_multi_TD01.bin，在后端httpd二进制程序中找出漏洞。

一、启动SaTC docker
docker run -it johnawm/satc:1.0
二、复制固件文件系统到docker中

默认已经将该固件的文件系统放在docker的 /home/satc/squashfs-root 目录下，可直接对该固件进行分析。如需要分析其他固件，可下载新固件，通过binwalk解压固件文件系统，压缩文件系统如 squashfs-root.tar.gz，通过docker cp命令将压缩文件复制到docker中使用。

三、使用satc分析

在docker中进入SaTC目录，使用satc命令分析命令注入与buffer overflow问题。若已知需要分析的后端二进制程序，可以将二进制程序拷贝到 /home/satc/SaTC 目录下，通过 -b 参数指定分析该二进制程序，否则可以不加-b参数，让程序自动识别后端二进制程序。这里我们演示使用SaTC分析后端httpd二进制程序中的cmdi类漏洞，使用命令如下：

python satc.py -d /home/satc/squashfs-root/ -o /home/satc/res --ghidra_script=ref2sink_cmdi -b httpd --taint_check
