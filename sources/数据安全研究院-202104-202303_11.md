**二进制溯源****什么是二进制溯源？**

能挖到有影响力的“0day”漏洞是晋升安全圈“大佬”的标志之一，也是众多安全研究者梦寐以求的目标。说到漏洞挖掘技术，了解过的同学可能最先想到的是**Fuzzing，符号执行**，污点分析等传统技术，但本文要给大家介绍的是一种近年来比较火，并越来越被一些顶级安全研究团队重视的漏洞挖掘技术，即**二进制溯源技术**。

这里的**“二进制”**是指**文本文件以外的二进制文件**，常见二进制文件包括：**ELF**格式文件，应用软件，移动app，固件等。通常一个二进制文件是下面这样的：

![](../Images/11bce79282f7b48abe44d2003e83377b.png)

要对二进制文件做漏洞挖掘是一件非常困难的事，通常需要具备**逆向分析、PWN、虚拟化仿真**等技术能力，其难度之高在漏洞挖掘领域也近乎于**“天花板”**般的存在。但试想一下，如果我们能够找到二进制文件对应的源代码或是其包含了哪些已知的开源代码库，问题是不是就变得简单多了？

**二进制溯源就是这样一种，从二进制程序追溯其所包含开源代码库的技术（from binary to source ）。**其基本模型是：**输入为一个二进制程序**，如：httpd，firmware.bin；**输出为所包含的开源库**，如：openssl，sqlite。

![](../Images/5b424f18dc8328161678c726d4ae47d5.png)

该技术大大简化了二进制程序的漏洞挖掘，具体体现在以下三方面：1、这些找到的开源库，在特定版本下通常都有不少已知的安全漏洞，而此二进制程序很可能也存在这些漏洞。2、可以借助源码审计工具（如：Sonar，Fortify，“代码卫士”等）来扫描其源代码，以提升挖洞效率。3、大大降低了人工静态分析代码的难度，读源码总比读汇编代码容易得多吧（当然像IDA这类工具也具有反编译的功能，能将汇编代码转成C代码，但此种反编译出来的代码在可读性和准确性上，较真实源码还有很大差距）。

  

  
**发展史****二进制溯源技术的发展史：**

了解了什么是二进制溯源后，大家可能关心截至目前都有哪些这方面的研究成果和可用技术？于是我帮大家整理了国内外关于二进制溯源技术的12篇文章，如下所示：

  
1**BAT^(\[1\])** ，发布于2011年，被引用128次。

最早提出了要从二进制程序溯源到源代码的问题，并给出了三种检测方法：字符串匹配，文件压缩和增量计算。此技术用在未知二进制程序上的精度和效率上还有待提升。

  
2**RESource**^(\[2\])****，发布于2012年，被引用16次。

通过提取汇编代码特征（常数、字符串、函数名、引用）实现了从二进制程序检索其源代码，以降低软件逆向工程的难度。

  
3**OSSDFSSB**^(\[3\])****，发布于2014年，被引用13次。

使用函数级静态软件胎记来检测二进制文件中的源码重用。此技术在C语言上表现良好，但在C++上则差强人意。

  
4**discovRE**^(\[4\])****，发布于2016年，被引用192次。

利用基于函数控制流图（CFG）的结构相似性计算来检测二进制程序代码重用，该方法需要函数本身具有一定复杂度，否则误报率将显著提升。

  
5**BinPro**^(\[5\])****，发布于2017年，被引用5次。

利用内联预测分类器来提出二进制程序特征，并使用了静态分析管道计算二进制程序与源码之间的相似性。

  
6**OSSPolice^(\[6\])**，发布于2017年，被引用41次。

利用OSS源的结构化和模块化布局，引入分层索引方案，以实现二进制文件与数十万个OSS源（十亿行代码）的高效、准确匹配。OSSPolice 目前仅支持 Java 和 C/C++的源码库，未来将扩展到更多语言上。

  
7**BCFinder^(\[7\])**，发布于2018年，被引用5次。

基于自动化特征匹配的轻量级二进制溯源工具。开源组件之间的交叉引用，会导致大量误报和漏报，这个问题有待进一步研究。

  
8**B2SFinder^(\[8\])**，发布于2019年，被引用2次。

通过7种代码特征提取，并计算加权特征的相似性，以实现二进制溯源。

  
9**OrderMatters^(\[9\])**，发布于2020年，被引用31次。

利用语义感知神经网络的方法提取二进制代码特征，并使用CNN的方法来计算图的相似性，取得了不错的效果。

  
10**C****odeCMR^(\[10\])**，发布于2020年，被引用2次。

对函数级二进制源代码匹配进行了深入探索，在提取字符级源代码上采用DPCNN，在提取二进制代码上使用GNN模型，获得了不错的效果。未来，此方案在模型的选择和微调上还有提高的空间。

  
11**B2SMatcher^(\[11\])**，发布于2021年，被引用3次。

对函数级二进制源代码匹配进行了深入探索，在提取字符级源代码上采用DPCNN，在提取二进制代码上使用GNN模型，获得了不错的效果。未来，此方案在模型的选择和微调上还有提高的空间。

  
12**BugGraph^(\[12\])**，发布于2021年，被引用9次。

对函数级二进制源代码匹配进行了深入探索，在提取字符级源代码上采用DPCNN，在提取二进制代码上使用GNN模型，获得了不错的效果。未来，此方案在模型的选择和微调上还有提高的空间。

  

二进制溯源技术最早是源于2011年GPL协议维护组织和代尔夫特理工大学联合发布的一项研究成果^(\[1\])，提出了一个检测工具**“BAT”**（**the Binary Analysis Tool**，不是百度、阿里、腾讯哈）。当时提出该项技术仅是为了通过二进制程序重用的检测，帮助GPL协议维护组织查处开源许可违规情况（通俗来讲就是对二进制程序“查重”），并未想到此技术能够用于安全漏洞的挖掘。而近几年，腾讯科恩实验室，中科院信工所，清华大学等都开始致力于这一方向的研究，足以说明此技术方向的研究价值。腾讯科恩实验室还发布了一个免费的二进制源码分析工具--BinaryAI，可作为IDA的插件来使用，感兴趣的同学可以去了解下：

https://binaryai.readthedocs.io/

  

**本文作为此系列文章的第一篇**，会用尽可能通俗易懂的语言，带大家一起深入剖析作为**二进制溯源的“鼻祖”--BAT。**

  

  
**“BAT”的技术实现**BAT共提出了三种检测方法，分别是：**字符串匹配检测**，**文件压缩检测**和**增量计算检测**。**一、****字符串匹配****：**

![](../Images/8e611ec30429017f859019fa1bbf438e.png)

做过二进制分析的同学应该都知道，虽然二进制程序中指令代码与高级语言中源码相差很大，但是其中定义的**字符串几乎不会有变化**，例如：“REMOTE\_ADDR”，“Welcome to”, "Segment fault"。所以通过扫描二进制程序中的字符串，并与开源代码库中的字符串进行匹配，就是最直接的一种二进制程序重用检测方法。该方法又可以分成三个关键步骤：

**第一步：从源码库中提取字符串，并构建一个字符串数据库。BAT从Fedora版本5、9、11、14**中获得所有**23,896个RPM**包，然后从1,728,718 个 C 和 C++ 源文件中提取了 42,238,120 个字符串文字。生成的SQLite 数据库大小为 13 GiB。每条数据库记录为一个**元组（string, packageName, version, sourceFile）**，即**（****字符串，包名，版本，源文件）**。

**第二步：检测二进制文件中的字符串。**通过调用GNU的**strings**工具提取出二进制文件中的可打印字符串，并在第一步构建的数据库中检索出所有能够匹配的元组。

![](../Images/0798f3e9cff919901f981c25f3575b97.png)

**第三步：计分和排名方法。**根据第二步中字符串匹配到的元组，对其中所有的包进行打分，根据得分进行排名并判断将其中哪些包视为存在源码克隆的包，是字符串匹配方法的关键。

![](../Images/f77e918b27d094dab8db371a585b843a.png)

在给出分数计算公式前，大家可以先思考一下这个分数应该跟哪些要素有关，为了便于思考，**这里做个类比：**一名老师要判断班里学生的作文是否有相互抄袭的嫌疑，假设目前已统计出了任意两篇作文共同出现的字词，那判断抄袭的关键因素是什么？**首先大家最容易想到的是重复的总字数**，对于约1000字的作文，重复字数为300显然比重复50字的两篇作文存在更大的抄袭嫌疑。**其次应该是重复字词的稀有程度**，若两篇文章重复的字词全都是如：“的”，“个”，“我”这类常用字，而另两篇重复的是一些的地名、人名等稀有字词，那么重复内容更稀有的后两篇文章显然就更有可能存在抄袭。

再回到BAT的计分方法，若二进制程序中的字符串 s 匹配到了源码包 p ，则字符串 s 对包 p 的得分的贡献为：

![](../Images/ab96cc38056c2717a5e991721f597519.png)

其分子 **length(s) **即为字符串s的长度，分母中 **|pkgs(s)| **是存储库中包含字符串 s 的所有包数量，比如：s 为字符串 “Welcome to”，而所有源码库中共有13个不同的源码包含有“Welcome to”，那么 |pkgs(s)| = 13。常数 **α > 1 **导致经常发生的字符串对分数的贡献迅速减少**（BAT 使用 α=5）。这里需要注意，计分的粒度是以包为单位，而不是以包版本，即出现在包 p 的多个版本中的字符串计为 p 的单次命中。**可以看到BAT的计分方法中，将代表字符串稀有程度的因子 |pkgs(s)| 以指数方式放到了公式中，说明其对匹配程度的影响要远大于字符串长度这个因子，这其实也符合我们的直观感觉。

**![](../Images/63977ee3be81c6e8a41d19d235995197.png)**  

这就是BAT的字符串匹配方法了，也是最基础的基础方法之一，比较容易理解。当然BAT中还考虑到了另外一个重要问题，比如：源码库本身也存在互相克隆的情况，因此用 |pkgs(s)| 直接表示字符串稀有属性就有所偏差，比如：字符串 **“internal error: inflate stream corrupt”**，出现在了5个不同的源码包中，但实际上这个字符串是源于zlib包的gzread.c文件，只不过其它四个包都引用了zlib，所以该字符串的稀有程度就不应该简单按照 |pkgs(s)|=5来计算。关于这个问题要如何解决，篇幅原因这里就不多介绍了，有兴趣的同学可去看看原文。

**三、****增量计算检测：**

**总结与预告**

BAT提出了三种二进制溯源的检测方法，并通过对已知二进制程序（svn）的实验获得了不错的效果，也表明这些方法确是可行的。在BAT文章的实验部分还使用了字符串匹配的方法，**对于未知二进制程序进行检测，但效果上则差强人意**，如下表所示；并且因为没有关于此二进制程序生成的可靠信息，故最多也只能通过人工审核确定准确率，但无法确定召回率。

![](../Images/f968aa333360272d1cc3be494d5fe4eb.png)

值得一提的是，**在真实场景中，字符串匹配方法相比与其它两种对二进制文件计算的方法有一个巨大优势，那就是字符串匹配方法能够提供判定重用的证据**，如：与字符串匹配的元组（字符串、报名、版本、文件）信息统计，这可帮助有经验的工程师快速确定检测结果的正确性。

另外BAT也具有一定的局限性，例如：加密或混淆过的二进制难于检测，检测力度粗**（以包为单位）**，仅涉及C和C++类型源码库等。

当然BAT提出的三种检测方法，用到的都是基础的检索、压缩、计算、统计等方法，并未用到任何**AI技术**，故在检测精度和效率上还有待提升。**在此系列的后续文章中，会为大家介绍如何将AI算法运用到二进制溯源技术中，并获得更加出色的表现，敬请期待！**
