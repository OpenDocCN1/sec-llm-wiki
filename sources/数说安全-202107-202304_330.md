昨天我们发布了国内网络安全行业首个关于Log4j2漏洞的专家圆桌讨论——“谭校有鸿儒”系列圆桌视频第四期**《Log4j2》**，为方便读者更加清晰灵活地接收专家们的专业解读，我们将圆桌谈话内容整理为文字版再次发出。  
**本期圆桌嘉宾**：

*   赛博英杰董事长、正奇安全创业营创始人 谭晓生；  
    
*   盛邦安全创始人/CEO 权小文；
    
*   华云安创始人/CEO、国家信息安全漏洞库特聘专家 沈传宝；  
    
*   微软msrc安全精英榜全球第一、pwn2own世界黑客大赛冠军、赛博昆仑CTO  古河（陈雪斌）；
    
*   悬镜安全创始人/CEO 、DevSecOps 敏捷安全专家 子芽（张涛）。
    

  
**圆桌内容文字整理：**  

  

谭晓生 ：大家好，12月9号 Log4J2爆出来了一个大漏洞，今天我们邀请了行业内的4位专家一起来聊聊这个漏洞到底是怎么回事，以及对这种漏洞的处置大家有什么经验？  
我们今天请到的有权小文——盛邦安全的创始人，他们做WAF、扫描器起家， 10多年来一直和漏洞打交道；第二位是华云安的创始人沈传宝，他是国家漏洞库的专家；第三位是陈雪斌（古河），在360工作了多年，也业界挖洞大神，现在是专门做漏洞管理的赛博昆仑的首席技术官；最后一位是子芽（张涛），他是悬镜安全的创始人，子芽在上大学的时候也是做安全的，现在在DevSecOps这个领域做创业。  
可以说4位都是安全漏洞相关领域的专家，那么今天咱们就一起聊一聊。首先log4J2漏洞在各位的视角来看它到底是怎么一回事儿？  

子芽：Log4J2这个漏洞其实是 Java语言里面的一个生态组件，记录的模块出了问题，核心就是它里面有个叫JNDI的 Lookup的函数安全引用校验不足，之所以现在影响比较大，我觉得首先因为开源生态里面这种基础库和基础框架相互引用，导致它的影响力是指数级的。第二，它的利用条件几乎等于是没有条件，所以业内说是核弹级或者是更大的影响力。

  

权小文：我来补充一下 ，Log4J这个漏洞整个影响了6910个组件，其中前500个组件被9.2万个框架调用。这个值其实挺恐怖的，在整个互联网的开放生态里面，9万多个框架基本上覆盖了我们日常所有的生活，所以这是为什么漏洞严重级别高。

  
沈传宝 ：我这里补充权总刚才说的一个数字，前段时间Google安全团队也公开了一个数，是一个比较主要的 Java的组件库，叫Maven Central，大家可能做开发的都知道。库里面大概有35,000多个组件受影响，占整个组件库里面的比例是8%左右。也就是说所有采用Java的这种组件里面的平均有8%受漏洞的影响，所以从这个角度来讲，它确实影响范围是很广的。  
谭晓生：这次这个漏洞的利用能够造成什么样的结果？可以执行任意代码是吗？  
大家：对。  
沈传宝：这个漏洞利用基本上没有条件，而且是个RCE。  
谭晓生：好，这个漏洞危害比较大是能达成共识的，但是到底有多大？这个话题在各种微信群里面讨论的是比较多的，有媒体在报道上说这是“史诗级漏洞”，“核弹级漏洞”，“有史以来最严重的漏洞”等等这些东西，圈里面的TK、袁哥、韦韬，他们其实有一些不同的观点。  
问一下诸位，在你们的心中你觉得Log4J2的漏洞到底它是一个多严重的漏洞？  
沈传宝：多年前的心脏滴血漏洞影响面也比较广，但是不是RCE，它的影响面没有清场的结果，但是Log4j2是RCE（远程命令/代码执行漏洞）。所以我觉得两者相比的话，心脏滴血和Log4j2漏洞其实是差不多的，但是要跟 MS17-010这一类比，我觉得还是差距很大。  
谭晓生 ：你的观点和TK的比较像，他认为Log4j2是和心脏滴血是是近乎相同水平的洞。  
古河 ：沈总提到17-010，就是WannaCry，还有我这些年的漏洞生涯让我印象比较深刻的最早是03年的冲击波。  
从影响面来讲的话，这些漏洞可能各有优劣，我觉得TK说Log4j2最终的影响不如冲击波和永恒之蓝，角度可能是他从实际造成破坏和造成攻击的数据来看，似乎没有当年的永恒之蓝和冲击波明显。这个可能会跟漏洞的特性有一些关系，这个漏洞太好用了，它的特征又太强烈了，导致大家响应的速度非常快，通过部署了方案以后，导致它最终造成的实际破坏程度没有那么大，但是**Log4J可能现在处于刚爆出来的阶段，之后的影响面会不断的被深挖出来，所以接下来造成的破坏性可能我们现在也没有办法完全断定。**  
谭晓生 ：觉得我们还需要拭目以待，看后续的发展会怎么样。  
古河：对  
谭晓生：在02年的时候，还有一个MS02-039 Slammer,它是在头一分钟之内，感染主机数量每8.5秒增长一倍，3分钟后该病毒的传播速度达到峰值，每秒能够进行5500万次扫描。在2002、2003年它能做到5500万次扫描，接下来的传播速度由于自身挤占了绝大部分网络带宽开始下降，10分钟后易受攻击的主机基本上已经被感染殆尽。  
权小文 ：这个肯定与当时的环境有关系。这次这个漏洞 CVSS评分是10分，确实 CVSS评分10分的漏洞不多，再加上它很好利用，所以我的角度来看，**这次大家响应相对比较快，是因为大家意识强，2002，2003年的时候，安全意识不如现在，当时2002年我跟别人说我是做防火墙的，有人会说你是做耐火材料的吗？**  

社会发展水平不一样，这其实也是个现状，这是两个漏洞造成社会影响面不一样的一部分原因。

  

谭晓生 ：前面也有人发了一篇文章，说是“Log4j2漏洞是人为植入的后门”这种情况。你们怎么看这个事儿？

  
权小文：我不认为这个是阴谋，首先我自己从做技术角度来讲，如果埋这种漏洞的话，得花多大的精力？我是不太认可这个观点的。  
子芽 :从漏洞的本身涉及到的模块和函数看，JNDI的这种lookup这种函数和它配套的模块其实很早就已经公布了，应该不是一个后门。  
谭晓生 :2020年底的SolarWinds和Log4j2有共同点，都是软件供应链安全。在前不久CNCC 2021上面王怀民院士讲，说是今天的软件开发的范式其实改变了，就是软件开发方式，他认为以前是工程范式，现在是开源范式，工程范式就比如像微软它开发操作系统，开发office，它就会有相当严格的流程，虽然它出来的软件也有漏洞，但是相对控制还是比较严的；  
开源范式特点是我想做一个什么东西我就做，做得好就会有更多的人用，这种情况它是叫做“从强调生产控制到鼓励创作自由，从聚焦软件产品到聚焦软件作品，从有组织的群体到无组织的群体，从承诺确定性到不承诺确定性”，而且他说未来可能还会演进到群智范式。  
那么在这种情况下，软件生产里面用到组件等这些东西，可能会没有人给你承诺他未来的安全状况。这种情况之下，未来客户该怎么办？  
子芽 :早些年国内有安全厂商提出来一个概念“内生安全”，也有叫“内建安全”或者“原生安全”，刚好我们就做这一块。

  

我们理解，首先内生安全有两层基本的含义很重要，第一层从组织的发展角度，数字化应用普及度越来越高，任何一款数字化应用在上线前，应该有一套相对适应自己的这种安全开发体系，不管是大一点的还是小一点的，能保证他出厂的时候是有一套安全流程。  
第二个角度就是以前开发叫原生应用，未来我觉得这种安全可信的应用至少应该具备对内部的应用缺陷或漏洞的自我检测。  
谭晓生：你这个思想其实是工程范式的思想。  
子芽：对。  
谭晓生：但是我现在所看到的状况，王怀民院士的观点是，未来可能软件是不是就不是那么严谨，就变成了就是谁想造什么就造，好用就有更多的人用，不好了会慢慢淘汰。在这样的时代，你再用要求厂家负责安全这种情况之下，会不会走不下去呢？  
子芽： 我们悬镜12月30号有一个 OpenSCA的开源发布会，用开源的方式做开源治理，动机也是说看到现在开源的趋势在企业ToB端决策成本是非常高的，或者说决策链非常长。  
而且在我们的商业模式里面，PLG模式（产品驱动模式）更盛行，之前行业里更多的是一些开源的软件或应用，未来我们可以看到在国内和国际上出现更多开源安全能力或者安全工具，它也会以一种属性的形式被大家集成到自己的研发体系里面去。对，这是一个趋势。  
谭晓生 :正好我挑战你一下，比如说你要开源SCA，你们的系统里面有没有用log4J这个模块？  
子芽：有。  
谭晓生：那这次是不是也受漏洞的影响？  
子芽：但是还好，因为我们提倡RASP，我们开发的东西具备自我免疫能力，就怕在上线发布的时候出问题。  
谭晓生:比如这次也是一个专家在说的：我的安全软件自己都受这次的漏洞的影响。  
子芽：整个软件供应链开源治理这一块，包括上线前的开发安全我觉得比较重要，DAST这种传统扫描对它检测识别率是不高的，或者是有效性是不高的，但是新一代的IAST，特别是像SCA这种软件成分分析，上线前的检测效果是比较好的。另外在治理层面，SBOM这种软件物料清单对于软件供应链安全，特别是对这次漏洞，具备很有效的作用；此外RASP技术也是能够对它起到热防护的作用。  
总的来说，未来开发的应用应该是具备自我漏洞缺陷的检测和外部威胁的防御能力。Gartner 2014年提出来RASP，12年提出来IAST，现在已经做到完全可以商业化了。  
权小文 : 正常企业比如像我们现在用开源的时候，有一个技术委员会对所有开源的东西有把关。**我觉得Log4J这个事情是不可避免的，但是你只要知道你用哪些组件，很快就能做应急。就是说开源软件有一堆，但是你用了什么、怎么用的必须有一套管理。特别我们是做商业化的软件。**  
谭晓生 :这就是刚才子芽说的要有SBOM。  
谭晓生 :茄子（宋申雷）最近也提出了，什么原因导致这个漏洞存在了8年，他一直在反思考这个问题，如果漏洞存在发现的概率，业界如何解决黑天鹅问题？ 子芽 :我们的观点还是说应用它本身自身就应该有免疫能力，出厂之前这种通用漏洞可以被免疫能力的自查对象覆盖。第二个就是Fuzz，只是不是每一个企业都有Fuzz的能力。  
谭晓生：每隔一段时间总会爆出来这样那样的严重漏洞。那么我们到底该怎么应对？您刚才讲了一些像RASP之类的这种动态防护的机制，还有没有更好的方法能够做漏洞的管理？  
沈传宝 :其实从漏洞的防御的角度来讲啊，第一个角度是现在大家说的比较多的安全前置，在上线前就把安全要保证到一定的程度。  
第二方面漏洞是层出不穷的，即使我们前期检查再多后面仍然会出现，这个时候就要求我们要有快速的检测和响应的这种机制。漏洞出现了以后，不管是我们说所说的0 day也好，还是1 day，我们就要最快的时间把相关的情报信息、防御的方法推送给我们的用户。  
谭晓生 :你要给他快速的Detect，快速的Response。  
沈传宝 :对，快速检测快速响应。  
第三个就是我们讲从已知到未知，过去我们可能关注的很多是已知漏洞，不管是n day也好还是1 day也好，其实都是已知漏洞，未来我们可能面临的更多的是未知漏洞。 谭晓生:那么从已知到未知，现在都有些什么样的技术，有些什么样的东西可以帮助用户？  
沈传宝:这块跟漏洞研究有很大的关系，在漏洞研究的时候，我们经常会认为一类的漏洞会引发一系列的周边问题，可能在外面暴露出来的0 day漏洞，其实它相关联的还有很多潜在的漏洞，这种是有技术可循的。一个方面是通过漏洞研究的技术能够把它特征化，然后在我们的产品里面能够具有这种响应的能力。  
还有一种我们通过类似于刚才说软件基因的能力，把海量数据的分析能力系统化的去实现，通过软件化来实现未知威胁检测的能力。  
谭晓生 :嗯，看来传宝强调的还是检测和响应速度问题。这边问一下古河，赛博昆仑团队主要是挖洞出身的，那么在XP挑战赛的咱们也曾经成功的做了动态防御。现在赛博昆仑你们对这次漏洞这种有什么样的方案？  
古河:主要是两方面，一方面是工具，就是你用什么工具去防这些漏洞，第二个是说你防哪些漏洞，工具其实刚才子芽这边也提到不少RASP这一类的，其实它都有很好的效果，  
刚才谭总您提到 Xp挑战赛，其实当时XP挑战赛，做了一个比较强的这样一个加固把Win7的防护手段挪到了XP上，起到非常好的效果，因为像这种叫Mitigation缓解措施移过来以后其实杀的是一片漏洞，而不是说单个的，并且不仅是已知的，未知的也包括在内。  
其实DEP这边也有一个比较好的例子，前阶段我们对某款国产办公软件做一个加固，当时我们发现它在最新的Win10系统上连DEP都没开，我们很轻易的做一个 Fuzz，找一些崩溃的可以控制指令的洞，然后就能很好的去完成这样一个利用。我们就用类似 XP挑战赛那种方法给他去加上保护，这样的话其实我们就防住了，或者说几乎防住了所有的这些内存类型的漏洞，  
**所以我觉得接下来漏洞对抗变得越来越激烈的情况下，前置性的研究，这些攻击面的研究和环节可能是会比较派用场的。**  
谭晓生:我觉得挺有意思的，传宝这块就是华云安似乎在D和R更加的重视，那么赛博昆仑这边似乎是在P这上面下更大的功夫？  
沈传宝 :我们确实是以检测响应为核心，而且我们推崇持续的检测响应，漏洞不可避免，没有什么灵丹妙药，也有什么一招鲜，只有发现一个漏洞，去快速检测，快速地修复。响应本身就是防御。  
谭晓生:还是等事先发生了，一个漏洞先发生了，然后我能及时的知道，然后去止损。  
权小文:我也是个观点，网上有一个观点是说这次漏洞发现以后打了好多主动防御的脸，是吧？其实说我们主动防御是有一些方法，但这个方法是在特定场合下有用的，在这种大面积漏洞影响的情况下，检测和响应还是第一优先级的。  
谭晓生:传宝和小文都是这个观点，古河你怎么看？  
古河: 作为一个真正的比较完善的漏洞的防御方案，必然是要有检测、快速的响应这样的能力，因为我们不可能把所有的洞都先挖到，都预先给他防御掉。**但是我觉得检响应和漏洞预防这两部分其实都有它的作用，需要结合在一起，会是一个比较完善的方案。** 谭晓生:这次咱们来说说阿里被罚的这件事儿，大家首先判断阿里的安全研究人员在报给阿帕奇漏洞的时候，他知道这个漏洞是这么严重的一个洞么？  
沈传宝 :我觉得大家可能基本上比较一致的观点认为是至少从技术人员角度来讲，可能没有想到这个漏洞的危害性会有这么大，或者是说最终产生的这种政治影响会有这么大。  
谭晓生 :咱们知道工信部的安全威胁与漏洞信息共享平台，今年7月份的时候发了一个文，9月1号开始实施的。类似的漏洞报送平台我们国家有几个，咱们安全研究人员今后报洞到底该怎么报，先后顺序该怎么样才能够不出现阿里这次的悲剧？  
沈传宝 :我简单说一下。网络安全法出台了以后，当时漏洞缺一个网络安全法下面的一个下位法，我是比较早参与漏洞相关的立法工作的，后来几大部委之间的协同，最后的产出就是今年7月1号正式发布的网络产品安全漏洞管理规定。  
正式规定发布了以后，其实我们可以看到报送的途径基本上分两类，第一类就是像网络产品提供商，比如说这次阿里报送给阿帕奇集团组织，其实理论上从漏洞管理规定角度来讲，其实是没有问题的。  
那么第二个附件就是国家相关部门，从目前来看主要是三大国家部委，包括公安部漏洞通报中心应该是4个渠道。至于报哪个其实每家漏洞门户的定位不太一样，主要是看定位。但从目前的牵头职能来讲，主要是工信部来牵头漏洞管理规定，所以理论上报工信部的漏洞威胁漏洞共享平台是最主要的一种手段。

**附：名词解释**

**一、SCA**SCA，Software Composition Analysis，软件成份分析,软件成分分析产品通常在开发过程中对应用程序进行分析，以检测开源软件组件是否带有已知的漏洞，例如具有可用安全补丁程序的过期库，以及需要相应授权许可（法律风险）的商业软件或第三方产品。SCA致力于解决的问题：

*   应用第三方组件中的已知漏洞。
    
*   第三方组件的软件许可问题。 
    
*   第三方组件中的恶意代码问题。
    
*   引用版本过旧的第三方组件。
    

  
**二、SAST**SAST（Static Application Security Testing，静态应用程序安全测试）对应用程序源代码执行直接的白盒分析。分析是在代码的静态视图上运行的，这意味着代码在审查时没有运行。如今，SAST已经完全成为主流，并且在整个软件行业中被广泛采用。SAST的优点：

*   广泛的编程语言支持；
    
*   检出率较高；
    
*   可以定位到代码行。
    

SAST的缺点：

*   准确性差：优秀SAST产品的误报率也在53%（据OWASP数据）；
    
*   无法看到执行流；
    
*   通常需要一些定制或调参；
    
*   不适用于生产阶段的系统；
    
*   通常运行很慢。
    

  
**三、DAST**DAST（Dynamic Application Security Testing，动态应用程序安全测试）对应用程序进行黑盒分析，这意味着它们不能访问代码或实现细节。DAST只检查系统对潜在漏洞测试的请求和响应。换言之，DAST是外部的漏洞扫描程序。DAST的优点：

*   独立于应用程序的技术和平台，无需代码细节；
    
*   执行相对较快；
    
*   误报率较低。
    

DAST的缺点：

*   检出率低：优秀的DAST产品检出率也只有18%（据OWASP数据）；
    
*   无法定位到代码行；
    
*   使用门槛高，报告通常需要安全专家解读。
    

  
**四、IAST**IAST（Interactive Application Security Testing，交互式应用程序安全测试）结合了SAST和DAST的优点。IAST可以像SAST一样看到源代码，也可以像DAST一样看到应用程序运行时的执行流。

*   IAST的优点：
    
*   检出率较高；
    
*   误报率较低；
    
*   可以在研发测试和生产环境中使用；
    
*   实时产生结果；
    
*   可以持续检测，对DevOps支持度更高；
    
*   即插即用，无需配置或调参；
    
*   可以与CI平台集成，创建相互连接的工作流。
    

IAST的缺点：

*   需要特定的语言支持
    
*   发展还不成熟
    

  
**五、SBOM**SBOM（Software bills of materials，软件物料清单 )，包含构建软件使用的各种组件的详细信息和供应链关系的正式记录，是软件的嵌套清单，是组成软件组件的成分列表，列出和记录软件组件，有效地显示了整个供应链。  
**六、RCE**RCE (Remote Code Execution，远程命令/代码执行漏洞，简称RCE漏洞)，可以让攻击者直接向后台服务器远程注入操作系统命令或者代码，从而控制后台系统。  
**七、CV**SSCVSS （Common Vulnerability Scoring System，即“通用漏洞评分系统”），是一个“行业公开标准，其被设计用来评测漏洞的严重程度，并帮助确定所需反应的紧急度和重要度”。它的主要目的是帮助人们建立衡量漏洞严重程度的标准，使得人们可以比较漏洞的严重程度，从而确定处理它们的优先级。最低0分，最高10分。  
**八、RASP**RASP（Runtime Application Self-Protection，运行时应用程序自我保护），可使应用程序通过实时识别和阻止任何恶意攻击来保护自己。该保护位于应用程序的运行时环境中，并拦截所有调用以确定它们是否安全。  
**九、Fuzz**Fuzz（模糊测试，fuzz testing, fuzzing）是一种软件测试技术。其核心思想是将自动或半自动生成的随机数据输入到一个程序中，并监视程序异常，如崩溃，断言（assertion）失败，以发现可能的程序错误，比如内存泄漏。模糊测试常常用于检测软件或计算机系统的安全漏洞。  
**十、DevSecOps**DevSecOps 是“开发、安全和运营”的缩写，它是一种文化取向、自动化方法和平台设计方法，将安全性作为整个IT 生命周期的共同责任。在软件开发生命周期的每个阶段自动集成安全性 - 从最初的设计到集成、测试、部署直至软件交付。  
**十一、CI/CD**CI/CD（Continuous Integration/Continuous Deployment，持续集成/持续部署），在软件工程中，CI/CD或CICD通常指的是持续集成和持续交付或持续部署的组合实践。CI/CD通过在应用程序的构建、测试和部署中实施自动化，在开发和运营团队之间架起了桥梁。  
**十二、DEP**DEP（Data Execution Prevention，数据执行保护） 是一组在存储器上运行额外检查的硬件和软件技术，有助于防止恶意程序码在系统上运行。DEP可透过监视程序来协助保护电脑，确保程序能够安全地使用电脑存储器。如果DEP发现有某程序正尝试运行数据用存储器区块中的指令，DEP便会关闭该程序并通知用户。  
**十三、ASLR**ASLR（Address Space Layout Randomization，地址空间配置随机加载，又称地址空间配置随机化、地址空间布局随机化）是一种防范内存损坏漏洞被利用的计算机安全技术。  
**十四、CNVD**CNVD（China National Vulnerability Database，国家信息安全漏洞共享平台，简称CNVD）是由国家计算机网络应急技术处理协调中心（中文简称国家互联应急中心，英文简称CNCERT）联合国内重要信息系统单位、基础电信运营商、网络安全厂商、软件厂商和互联网企业建立的信息安全漏洞信息共享知识库。  
**十五、CNNVD**CNNVD（China National Vulnerability Database of Information Security ，国家信息安全漏洞库，"简称"CNNVD"），是中国信息安全测评中心为切实履行漏洞分析和风险评估的职能，负责建设运维的国家信息安全漏洞库，于2009年10月18日正式成立。
