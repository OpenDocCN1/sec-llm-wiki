Go在供应链安全上的策略

    很多软件都是在供应链环节上出问题，这是个头痛且不好解决的问题。正好看到一篇Go基于自身供应链上面的安全做法的思考文章，推荐给大家，值得参考。          

    现代软件工程是协作的，并且基于重用开源软件。尽管有流程或措施，每个依赖项也是基于一种信任关系。但现实是：通过破坏其依赖关系(供应链)而使目标受到攻击。

    Go 工具和设计有助于降低各个阶段的风险。

一、构建即“锁定”

    外部世界中的更改（例如发布依赖项的新版本）无法自动影响 Go 构建。与大多数其他包管理器文件不同，Go 模块没有单独的约束列表和锁定特定版本的锁定文件。参与任何 Go 构建的每个依赖项的版本完全由主模块的go.mod文件决定。

    从 Go 1.16 开始，默认情况下会强制执行这种确定性，如果 go.mod 不完整，构建命令 ( go build, go test, go install, go run, ...)将失败。唯一会改变go.mod（以及因此构建）的命令是 go get and go mod tidy。这些命令预计不会自动运行或在 CI 中运行，因此必须有意识地对依赖关系树进行更改，并有机会通过代码审查。

这对于安全性非常重要，因为当CI系统或新机器运行go build时，签入的源代码是构建内容的最终和完整的真实来源。第三方无法影响这一点。

此外，当使用go get添加依赖项时，其传递依赖项将添加到依赖项的go.mod文件中指定的版本，而不是最新版本，这要归功于最小版本选择。go install example.com/cmd/devtoolx@latest 的调用也会发生同样的情况，在某些生态系统中，其等效项会绕过pinning。在Go中，将获取example.com/cmd/devtoolx的最新版本，但所有依赖项都将由其go.mod文件设置。

如果一个模块遭到破坏并发布了一个新的恶意版本，那么在他们明确更新该依赖项之前，任何人都不会受到影响，这为生态系统提供了审查更改和检测事件的时间的机会。


二、版本内容不改变

确保第三方无法影响构建所需的另一个关键属性是模块版本的内容是不可变的。如果破坏依赖项的攻击者可以重新上传现有版本，他们可以自动破坏依赖它的所有项目。


这就是 go.sum 文件的用途。它包含有助于构建的每个依赖项的加密哈希列表。同样，不完整的 go.sum 会导致错误，只有 go get 和 go mod tidy 会修改它，因此对它的任何更改都会伴随着故意的依赖更改。其他版本保证有一套完整的校验和。


这是大多数锁定文件的共同特征。使用校验和数据库（简称 sumdb）超越了它，这是一个全局只能追加的加密验证 go.sum 条目列表。当 go get 需要向 go.sum 文件添加一个条目时，它会从 sumdb 中获取它以及 sumdb 完整性的加密证明。这确保不仅每个模块的每个构建以及每个模块都使用相同的来源内容！

sumdb 保证您使用的代码与其他所有人使用的代码完全相同，例如example.com/modulex的v1.9.2正在使用并已审核。

最后，最喜欢sumdb的特性：它不需要模块作者进行任何密钥管理，并且可以与Go模块的去中心化特性无缝协作。


三、VCS 真实来源

大多数项目都是通过一些版本控制系统（VCS）开发的，然后在其他生态系统中，上传到包存储库。这意味着有两个帐户可能会遭到破坏，即 VCS 主机和软件包存储库，后者使用得更少，也更容易被忽视。这也意味着更容易在上传到存储库的版本中隐藏恶意代码，特别是如果源作为上传的一部分被例行修改。

在 Go 中，没有包存储库帐户之类的东西。包的导入路径嵌入了直接从 VCS go mod download 获取其模块所需的标签定义版本的信息。

我们确实有Go Module Mirror，但这只是一个代理。模块作者不注册帐户，也不将版本上传到代理。代理使用工具使用的相同逻辑go（实际上，代理运行 go mod download）来获取和缓存版本。由于校验和数据库保证给定模块版本只能有一个源代码树，因此使用代理的每个人都会看到与绕过它并直接从 VCS 获取的每个人相同的结果。（如果版本在 VCS 中不再可用或者其内容发生更改，直接获取将导致错误，而从代理获取可能仍然有效，从而提高可用性并保护生态系统免受“left-pad?(这个什么意思？)”问题。）

在客户端上运行 VCS 工具会暴露出相当大的攻击面。这是 Go Module Mirror 另一个地方：go代理上的工具在强大的沙箱中运行，并配置为支持每个 VCS 工具，而 默认情况下仅支持两个主要的 VCS 系统（git 和 Mercurial）。使用代理仍然可以获取使用默认 VCS 系统发布的代码，但攻击者在大多数安装中无法访问该代码。


四、构建代码不执行

Go 工具链的一个明确的安全设计目标是，无论是获取还是构建代码都不会让该代码执行，即使它是不受信任和恶意的。这与大多数其他生态系统不同，其中许多生态系统都对在包获取时运行代码提供一流的支持。这些“安装后”钩子过去曾被用作将受感染的依赖项转变为受感染的开发人员机器并 通过模块作者蠕虫的最方便的方法。

公平地说，如果您要获取一些代码，通常会在不久之后执行它，无论是作为开发人员机器上测试的一部分还是作为生产中二进制文件的一部分，因此缺少安装后挂钩只会减慢攻击者的速度. （构建中没有安全边界：任何有助于构建的包都可以定义一个init函数。）但是，这可能是一种有意义的风险缓解措施，因为您可能正在执行一个二进制文件或测试一个只使用一个子集的包模块的依赖。例如，如果您example.com/cmd/devtoolx在 macOS 上构建和执行，则仅 Windows 的依赖项或 的依赖项 example.com/cmd/othertool无法危及您的机器。

在 Go 中，不为特定构建贡献代码的模块对其没有安全影响。


五、Go的零依赖

Go 生态系统中最后一个可能也是最重要的软件供应链风险缓解措施是技术性最低的：Go 有一种拒绝大型依赖树的文化，并且更喜欢复制而不是添加新的依赖。高质量的可重用 Go 模块自豪地贴上了“零依赖”的标签。如果您发现自己需要一个库，您可能会发现它不会导致您依赖其他作者和所有者的数十个其他模块。

丰富的标准库和附加模块也支持这 golang.org/x/...一点，这些模块提供常用的高级构建块，例如 HTTP 堆栈、TLS 库、JSON 编码等。

总之，这意味着只需少量依赖项就可以构建丰富、复杂的应用程序。无论工具多么好，它都无法消除重用代码所涉及的风险，因此最强的缓解措施始终是一个小的依赖树。
