内核驱动的文章，讲得不多，总共才有两篇，一篇是Ghidra静态分析驱动木马《Windows内核驱动程序静态逆向之套路方法》，一篇是《利用内核驱动Dump被保护进程内存镜像》。因为没有开发过内核驱动程序(无作品)，对这块始终不得深入，所以文章也较少，但对驱动非常关注，尤其是对驱动级的木马，也一直在找寻内核驱动分析方面的工具，近日寻得了一个IDA插件：Driver Buddy Reloaded。它是一个 IDA Pro Python 插件，可以帮助 Windows 内核驱动程序自动完成一些乏味的逆向工程任务。


一、安装

将DriverBuddyReloaded文件夹和DriverBuddyReloaded.py文件复制到 IDA 插件文件夹（如C:\Program Files (x86)\IDA 7\plugins\）或安装 IDA 的任何位置。





二、用法

.自动分析功能：

  1. 启动 IDA 并加载 Windows 内核驱动程序。

  2. 转到Edit -> Plugins -> Driver Buddy Reloaded或按CTRL+ALT+A开始自动分析。

  3. 检查分析结果的“输出”窗口。



.解码 IOCTL：

  1. 将鼠标光标放在包含可疑 IOCTL 代码的行上。

  2. 右键单击并选择Driver Buddy Reloaded -> Decode IOCTL; 或者按CTRL+ALT+D。




1、查找调度设备控制：该工具可以自动定位和识别 DispatchDeviceControl，函数用于将所有传入的 DeviceIoControl 代码路由到与该代码相关联的特定驱动程序函数。自动识别这个函数可以更快地找到每个驱动程序的有效 DeviceIoControl 代码。此外，在调查由于崩溃导致的驱动程序中可能存在的漏洞时，了解这个函数的位置有助于将重点缩小到与崩溃 DeviceIoControl 代码相关的特定函数调用。


当分析成功的时候，一些代码将被重命名如下:

  • DriverEntry: 加载驱动程序后调用的原始的第一个驱动程序提供的例程。它负责初始化驱动程序。

  • Real_driver_entry: 通常是将 DriverEntry 的执行转移到的函数。它通常是初始化 DeviceName 的位置。

  • DispatchDeviceControl/DispatchInternalDeviceControl: 如果工具能够以某些特定的偏移量恢复函数，那么将使用适当的名称重命名函数。

  • Possible_DispatchDeviceControl # : 如果该工具不能恢复 DispatchDeviceControl 或 DispatchInternalDeviceControl，它会根据执行流进行实验性搜索，并检查函数是否正在加载已知的 IO stack location & IRP 地址; 这表明该函数可能是 DispatchDeviceControl。由于它基于启发式算法，因此可能返回多个结果，并且容易出现误报。



所有 WDM/WDM 驱动程序共享多个驱动程序结构。这个工具能够自动识别这些结构，比如 i/o stack location，IRP和 DeviceObject 结构，并且能够帮助节省逆向工程过程中的时间，并且为驱动程序中这些功能正在使用的区域提供上下文。


2、寻找和解码IOCTL：当逆向驱动，它是常见的遇到 IOCTL 代码作为分析的一部分。当这些代码被解码时，会显示出有用的信息，并且可能会把注意力集中到驱动程序中更有可能存在漏洞的特定部分。


通过右键单击一个可能的 IOCTL 代码，提供了一个上下文菜单选项(当光标位于包含可疑 IOCTL 代码的行时，可以使用 Ctrl + Alt + d 快捷方式) ，并可用于解码该值。这将打印出一个表与所有解码 IOCTL 代码。通过右键单击已解码的 IOCTL 代码，在反汇编视图中，可以将其标记为无效; 这将保留任何非 IOCTL 注释的完整性。


如果在 Driver Buddy Reloaded 菜单下右键单击您认为是 IOCTL 调度程序(dispatcher，dispatcher control/DispatchInternalDeviceControl/Possible _ DispatchDeviceControl _ #)的第一条指令，将出现一个“ Decode All”选项，它试图解码函数中可以找到的所有 IOCTL 代码。大多数时候它可以加快速度。




3、标记功能：Driver Buddy Reloaded 有一个 c/c + + 函数和操作码以及 Windows API 的列表，这些函数和操作码通常容易受到攻击，或者可以帮助缓冲区溢出条件。在自动分析过程中，所有找到的实例都会被报告回来，并且在查找可能到达敏感函数的用户控制的代码路径时有所帮助。


4、寻找DeviceName：该工具会自动尝试查找已注册的设备路径(DeviceName)的驱动程序，如果查看二进制文件中的 Unicode 字符串无法找到路径，那么分析人员可以尝试手动使用 Madiant 的 FLOSS 来查找模糊路径。




5、导出标签：在自动分析过程中，该工具还将二进制文件使用的 Pooltags 转储为与 Pooltags.txt 一起使用的格式。然后，可以在文件末尾复制粘贴输出，之后由 WinDbg 接收。




警告：


  • 目前 DispatchDeviceControl 搜索只适用于 x64驱动程序


  • 快捷键与 F-Secure 的 win_driver_plugin 不兼容。
