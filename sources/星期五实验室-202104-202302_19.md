**01**

**漏洞简介**

![](../Images/88f26e00724fcd0df56ab72932bd1c8b.png)

  

Atlassian Confluence Server是澳大利亚Atlassian公司的一套具有企业知识管理功能，并支持用于构建企业WiKi的协同软件的服务器版本。Atlassian Confluence Server 和 Data Center 存在注入漏洞。攻击者利用该漏洞执行任意代码。以下产品及版本受到影响：

*   1.3.0 版本至 7.4.17 之前版本
*   7.13.0 版本至 7.13.7 之前版本
*   7.14.0 版本至 7.14.3 之前版本
*   7.15.0 版本至  7.15.2 之前版本
*   7.16.0 版本至 7.16.4 之前版本
*   7.17.0 版本至 7.17.4 之前版本
*   7.18.0 版本至 7.18.1 之前版本

**03**

**漏洞分析**

![](../Images/88f26e00724fcd0df56ab72932bd1c8b.png)

根据官方公告

*   

```

```

  

本次漏洞修复主要修改了xwork-1.0.3-atlassian-10.jar中的com.opensymphony.xwork.ActionChainResult#execute方法

  

在/confluence/confluence/WEB-INF/lib/webwork-2.1.5-atlassian-3.jar/com/opensymphony/webwork/dispatcher/ServletDispatcher.class第64行处下断点

  

客户端发起请求后，服务端先将其交给Tomcat的Filter处理，然后进入ServletDispatcher，这是一个Servlet分发器。

![](../Images/1f867538ecca9b5370c50b1783029c2c.png)

  

然后经过一系列字符串处理后获取servletPath步骤

![](../Images/17ab5b01da14a3a5449feacb1251ad94.png)

  

获取到servletPath之后又来到断点处，该方法将servletPath通过如下五个函数分别获取对应值

*   getNameSpace
*   getActionName
*   getRequestMap
*   getSessionMap
*   getApplicationMap
    
      
    

本次漏洞发生在getNameSpace方法中，所以我们在/confluence/confluence/WEB-INF/lib/webwork-2.1.5-atlassian-3.jar/com/opensymphony/webwork/dispatcher/ServletDispatcher.class第133行处下断点，继续运行并触发断点：

![](../Images/fd9b18795dd0fa70654b6db02f5c297b.png)

  

该方法会截取字符串最后一个/之前的部分作为servletPath传入![](../Images/5ef0b59d6e929d0a430ad0526789dc64.png)

  

根据serviceAction方法，代理者会实例化execute()抽象类![](../Images/09a0bd7b66386d66fcb4296dfcb8c190.png)

  

ctrl+右键跟一下execute，跟一下这个接口的调用![](../Images/384dc42452cff2af6ea083464d591f72.png)

  

发现其在com.opensymphony.xwork.DefaultActionProxy中实例化，并调用了execute方法![](../Images/cdaf482e394486c741f09111c7bb5f0c.png)

  

看到xwork，分析过Struts2系列漏洞的同学们应该很熟悉了，这是一个框架，在本漏洞的作用就是用于执行OGNL表达式。  
下一步会进入invoke方法![](../Images/320f10ac564d19d04f13038da625f476.png)

  

invoke函数通过Next获取拦截器对象，并调用了实例化了intercept接口![](../Images/221e0e0dc478f45bc8e9d0c059b18ca7.png)

  

ctrl+右键跟一下intercept方法，查看他的第三个实现![](../Images/e7ce44d8900fd6023b87488d2b81f821.png)  
发现 com.opensymphony.xwork.interceptor.Aroundlnterceptor中intercept方法调用了invoke方法来进行轮询![](../Images/862414c28150c2af48a0cf5f3af438bc.png)

  

再看intercept在com.atlassian.confluence.security.interceptors.ConfluenceAccessInterceptor中的实现：![](../Images/51804b5e1015743a9502ea55898f6218.png)  
发现intercept做了两件事：

1.  判断状态：判断容器是否正常启动
2.  鉴权：循环判断当前的请求用户是否拥有访问这个action的权限，如果鉴权失败了就会返回一个notpermitted，并在将结果赋值给resultCode之后跳出循环。

![](../Images/06db682ffabf57845cd01760e847dacd.png)

  

然后来到了com.opensymphony.xwork.ActionChainResult的excute函数中：可以看到这里已经获取到了namespace的值，并在finalNamespace的赋值中调用了translateVariables![](../Images/fab04b46fe7914f27c537a819d525e22.png)

  

接下来进入com.opensymphony.xwork.util.TextParseUtil的VtranslateVariables方法，其中调用了findValue方法![](../Images/db42216de6b81b8f25c53ea43a17439a.png)

  

跟进com.opensymphony.xwork.util.OgnlValueStack，findValue函数中会对OGNL表达式进行解析![](../Images/316b5345e9671a216262540973599495.png)

  

经过一系列OGNL表达式处理后，最终触发了OGNL表达式注入：![](../Images/341a097627829e6d49b6fada249f898d.png)
