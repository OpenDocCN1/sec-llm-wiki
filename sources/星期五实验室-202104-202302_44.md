**三、约束委派攻击**

在学习完了非约束委派之后，知道了委派就是拿着一个域内用户的服务账号TGT，去访问这个账号所能访问的服务。**什么是约束委派：**在 Windows Server 2003 中引入了约束委派，对 Kerberos 协议进行拓展，引入了 S4U (S4U2Self / S4U2proxy), 运行服务代表用户向 KDC 请求票据。S4U2self (Service for User to S4U2Self) 可以代表自身请求针对其自身的 Kerberos 服务票据(ST)；如果一个服务账户的 userAccountControl 标志为 TRUSTED\_TO\_AUTH\_FOR\_DELEGATION, 则其可以代表任何其他用户获取自身服务的 TGS/ST。S4U2proxy(Service for User to Proxy) 可以以用户的名义请求其它服务的 ST，限制了 S4U2proxy 扩展的范围。服务帐户可以代表任何用户获取在 msDS-AllowedToDelegateTo 中设置的服务的 TGS/ST，首先需要从该用户到其本身的 TGS/ST，但它可以在请求另一个 TGS 之前使用 S4U2self 获得此 TGS/ST。  

**S4U2self**

这是实现约束委派的第一个扩展，它的作用就是允许服务代表特定用户向自己请求一个特殊的可转发服务票证。怎么来理解上面句话？就是除去前面用户A向service1发起的流程之后，然后以S4Uself的名义代表某个特定的用户，去找KDC请求一张可以访问service1的可以转发的票据，而这个票据就代表了service1可以以用户A的方式操作，但是还是操控的是其自己本身service1，只是借助了A。![](../Images/4d7ec26ad4e4aaaa590f7b35de1ef91e.png)

*   
*   
*   
*   
*   

```
(1) 用户向 service1 发送请求。用户已通过身份验证，但 service1 没有用户的授权数据。通常，这是由于身份验证是通过 Kerberos 以外的其他方式验证的。(2) 通过 S4U2self 扩展以用户的名义向 KDC 请求用于访问 service1 的 ST1。（这里就是请求自身的）(3) KDC 返回给 service1 一个用于用户验证 service1 的 ST1，该 ST1 可能包含用户的授权数据。(4) service1 可以使用 ST 中的授权数据来满足用户的请求，然后响应用户。尽管 S4U2self 向 service1 提供有关用户的信息，但 S4U2self 不允许 service1 代表用户发出其他服务的请求，这时候就轮到 S4U2proxy 发挥作用了。
```

**S4U2proxy**

对于S4U2proxy来说：它是以用户的名义去请求其他服务ST，不像上一个协议是请求自身的。

比如：用户A拿用户X的TGS去请求KDC访问主机B的权限，但是身份还是用户X，通过之后用户A就可以拿着用户X的权限去访问主机B（更通俗来讲就是另一个人捡到了丢失者的身份证，并拿这个身份证去上网，当时另一个拿的是丢失者的身份上的网），这就是这个协议的作用。而约束委派就是限制了S4U2proxy扩展的范围

还是上面的图。

*   
*   
*   
*   
*   
*   

```
(5)用户向 service1 发送请求，service1 需要以用户身份访问 service2 上的资源。(6)service1 以用户的名义向 KDC 请求用户访问 service 2的 ST2。(7)如果请求中包含 PAC，则 KDC 通过检查 PAC 的签名数据来验证 PAC ，如果 PAC 有效或不存在，则 KDC 返回 ST2 给 service1，但存储在 ST2 的 cname 和 crealm 字段中的客户端身份是用户的身份，而不是 service1 的身份。(8)service1 使用 ST2 以用户的名义向 service2 发送请求，并判定用户已由 KDC 进行身份验证。(9)service2 响应步骤 8 的请求。(10)service1 响应用户对步骤 5 中的请求。
```

总的来说整个过程就是：  
1.当用户A想要访问service1的时候2.service1就会通过s4u2self协议向KDC请求一个用户A可以访问service1自身的一个票据，这个票据是域控授予用户A访问service1的3.service1想要以用户A访问service2，这时候就去访问KDC执行s4u2proxy获取访问service2的TGS，其实就是约束委派攻击里面的ST24.最后获得票据访问service2  
约束委派的目的是在模拟用户的同时，限制委派机器/帐户对特定服务的访问,相当于约束委派设置白名单，非约束设置的是黑名单。

**关于约束委派的黄金票据攻击**

环境不变

*   
*   
*   

```
当前域：god.org域控主机名：OWA（IP：192.168.52.138）、用户 god\administrator  （win2008）域内主机名：stu1（IP：192.168.52.143）、用户 god\ash   （win7）
```

因为在普通的权限下面我们是读取不到krbtgt的hash的，而且TGT是用krbtgt的NTLM hash去加密的，如果委派的用户去访问TGS，那么就可以伪造任意的用户TGT，因为TGS默认的spn是krbtgt/domain name。  
对于这里委派的用户访问TGS，我的理解就是在kerberos中省去了前面验证身份的环节了，之后到了最后TGS给ST的环节，只要有了ST，前面身份也无所谓是谁，可以自己伪造，然后访问特定的权限。  
krbtgt默认是禁用的而且无法启用，所以我们无法使用界面来添加这个SPN。![](../Images/bb79ceb99891e64ff20f65aae10c27a1.png)

通过powershell的方式添加

*   
*   
*   

```
Import-Module ActiveDirectory$user = Get-ADUser ashSet-ADObject $user -Add @{ "msDS-AllowedToDelegateTo" = @("krbtgt/god.org") }
```

![](../Images/26e45853db36633b6b006db2732e5a53.png)好像只有域管理员才能执行这些命令成功。![](../Images/2b603d4b6f872baea2592264537749e2.png)已经成功添加。
