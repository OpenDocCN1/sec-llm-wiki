**漏洞分析**

**针对思科视频通信服务中关键问题的补丁**

  

近期，思科披露了影响其 Expressway 系列和 TelePresence 视频通信服务的两个严重缺陷。这些问题被跟踪为CVE-2022-20754和CVE-2022-20755，它们在 CVSS上的得分都很高，为9.0。

![](../Images/51c8c2ca70b8c0f88adc4725c72e58e4.png)

  

第一个漏洞允许经过身份验证的具有读/写访问权限的用户使用集群数据库 API 执行路径遍历攻击。攻击者可以利用此漏洞覆盖操作系统上的任意文件，从而可能导致设备接管。该漏洞是由于未能完全验证用户提供给 API 的输入（一种注入攻击形式）引起的。  

第二个漏洞是基于 Web 的管理界面上的命令注入漏洞，它允许经过身份验证的用户执行任意命令执行。同样，根本原因是输入验证不足。

  

思科证实，他们没有证据表明任何一个漏洞都在实时系统上被利用，但仍然建议客户将他们的系统升级到最新版本，以尽量减少任何漏洞被利用的可能性。

  

**漏洞分析**

**自我管理的 GitLab 实例中的安全漏洞**

  

根据近期发表在 TheHackerNews 上的研究，流行的 CI/CD 平台 GitLab 的自我管理版本很容易受到 GraphQL API 的攻击。该漏洞被跟踪为 CVE-2021-4191，CVSS 评分为 5.3。

![](../Images/11e4c0d019ed27a4e6eb082d53625564.png)

  

该漏洞由 Rapid7 的安全研究人员发现并报告，最初于 2021 年 2 月 18 日披露。该漏洞已在 GitLab 最近的更新中得到修补，建议所有自我管理实例上的用户尽快更新其安装。

该漏洞允许未经身份验证的用户（API2:2019 - Broken authentication）访问 GraphQL 端点并收集其他注册用户的私人信息，例如姓名和电子邮件地址。这些详细信息对于执行初始安装侦察的攻击者来说可能是无价的，从而导致暴力破解或猜测密码。

估计表明，大量 GitLab 安装可能会受到此漏洞的影响。

  

**漏洞分析**

**安全漏洞影响校园门禁系统**

  

第三个也是最后一个漏洞影响了一个校园的访问控制系统：一位好奇的用户发现移动应用程序的后端 API 没有对用户进行身份验证（ API2:2019的另一个案例——身份验证失败）。实际上，此漏洞为攻击者提供了系统控制的所有门的“万能钥匙”。

![](../Images/3625dbe7382ed5dd92057e3c10dbd320.png)

大学生 Erik Johnson 对控制校园建筑访问的 GET Mobile 应用程序性能不佳感到沮丧，并使用基本网络监控来了解应用程序的行为。他发现他必须提交位置坐标来验证与目标门的接近程度，但这很容易通过 API 进行欺骗。

约翰逊随后做了一个惊人的观察：API 端点实际上并没有验证学生的凭据。这意味着任何知道容易获得的标识符（如学生证、用户名或电子邮件地址）的人都可以访问目标的帐户，再加上在已知位置解锁门的能力，就产生了数字“万能钥匙”。

约翰逊试图向解决方案开发商 CBORD 报告该漏洞，但在那里碰壁，因此不得不通过 TechCrunch 进行披露。报告显示，同一家公司在 2009 年也受到了类似漏洞的影响。

该漏洞已被 CBORD 承认并修复，CBORD 还撤销了受影响系统的所有会话密钥。目前尚不清楚该漏洞是否被用于任何恶意访问，或者用户是否已被告知该问题。

  

**文章分享**

**隐私成为 API 日益关注的问题**

  

最后，本周我们分享一篇文章，强调了与 API 相关的数据隐私日益受到关注。API 的主要功能是作为数据的管道。随着连接性的提高和 API 的增长，API 正在成为信息泄露的第一大攻击媒介。

**API 中信息泄露的根本原因包括，例如：**

• 损坏或丢失的用户身份验证（本周我们介绍了API2:2019 的两个实例 — 身份验证损坏）

• 在功能或对象级别实施访问控制不佳

• 不完整的库存或资产管理

• 数据分类和访问控制失败

• 治理不善

  

![](../Images/feb2ccdf2ca4c0c28cb749286e34500f.png)

根据Salt Security的最新API 安全状态报告，识别哪些 API 暴露 PII 或敏感数据通常被称为 API 安全平台所需的重要属性，而不是阻止攻击。虽然阻止攻击始终是重中之重，但人们意识到主动解决漏洞和漏洞利用说起来容易做起来难。

根据 Salt Labs 的数据，对 API 的攻击量增长速度是已经炙手可热的整体 API 使用量增长速度的两倍。然而，面对这些攻击，我们最大的收获是，在 250 多名受访者中，有 30% 表示他们在“敏感数据暴露/隐私事件”方面存在与 API 相关的问题，高于 Salt Security 2021 年第三季度的 19%学习。与之形成鲜明对比的是，由“漏洞”和“身份验证”引起的 API 安全问题分别从 55% 下降到 39% 和 48% 下降到 32%。

由于采用了技术，身份验证问题的减少可能有所下降，但 Salt Labs 研究的 94% 的被利用 API 都是针对经过身份验证的 API。此外，根据其客户数据，91% 的 API 会暴露 PII 或个人数据。

![](../Images/398ce00f14fc78b48c9ff320c54b1466.png)

记录拥有的 API 以及它们公开的数据对于解决隐私问题大有帮助。许多人认为他们在过去两年中取得了长足的进步，但他们可能过于自信。当第一个 API 安全状态发布时，55% 的人对 API 清单已完成有一定或非常有信心；在最新研究中，这一比例跃升至 72%。当被问及这些 API 清单 API 清单是否提供了足够的详细信息时，例如关于敏感数据的暴露，现在 75% 的人至少有一定的信心，高于一年前的 61%。

当 Salt Security 实际与潜在客户和客户互动时，该公司至少识别出比以前已知的多 40% 的 API。43% 的受访者表示他们最大的 API 安全问题是“僵尸”。或过时的 API。

敏感信息的泄露并不是一个新问题，但 API 优先公司的突出地位使得这个问题比以往任何时候都更加重要。在这个重新想象的世界中，API 可能会按照设计的方式工作，但是当 5000 万条 LinkedIn 记录被暴露时，这听起来只是一个借口。Salt Security 的营销副总裁Michelle McLean告诉 The New Stack，虽然数据泄露显然不是一个新问题，但操纵 API 的机制却是全新的。
