观点：API安全问题看

API 安全问题如此普遍的原因如下：

  • 由于开发越来越敏捷，迭代周期越来越短，这给仍然依赖手动测试程序的安全团队带来了挑战。

  • 应用程序开发技术正在发生变化：整体正在被分解，现代应用程序由多个API组成 - 通常是客户端 - 无需足够的控制即可直接调用。

  • 往往在应用生开发的后期，作为强制合规的一部分，才会检测程序的安全性，导致后期的安全测试存在很高的误报率。

  • 现代 API（特别是在微服务中）侵蚀了典型的网络边界，降低了传统边界防护，例如 Web 应用程序防火墙 （WAF）。国际专家建议，随着边界重要性的降低，保护数据比边界本身更重要。

  • 另一个关键因素是确保API安全工具具有完整的上下文，保证工具做出正确的决策，无论是静态决策（如根据 OpenAPI 标准审核API合同时），还是在API端点上检测流量行为动态决策。而WAF无法区分不良行为与良好（预期）行为。

专家强调了API 合约对于建立一个良好安全模型的价值，其中预期行为被明确定义，与推断不良行为的消极安全模型相反。通过使用 API 定义（如 API 合约的 OpenAPI 定义），可以验证开发和部署周期每个阶段的 API 开发过程。这种方法使安全负责人能够尽早了解API的安全态势，并保证API可以根据其合约进行测试。

报告：三分之二的云安全漏洞是由于配置不当的 API 造成的

IBM 最近的一份报告显示，三分之二的云安全漏洞是由于对API的配置不当导致的。该报告包含来自 IBM 多个研究团队的12个月的调查结果，并得出结论：云环境需要更好地保护。

报告的主要结论包括：

  • 有一个庞大并且活跃的黑市，在转售如远程桌面访问等其他公有云访问信息和凭证

  • 由于弱口令和策略不完善，许多系统可能会遭到入侵。

  • API安全问题是导致入侵的最常见原因，约占三分之二。

  • 对于传统边界的侵蚀导致这些老旧系统很难保护目前的复杂场景。

报告的主要建议包括：

  • 系统环境需要加固的更完善。

  • 必须对"影子 IT"实施更严格的治理，因为它代表着一种未量化的业务风险，并且经常成为威胁入侵的来源。

  • 组织必须了解向外界快速公开内部API的风险，因为这会产生新的攻击面。

  • 用于 Web 或移动应用程序的 API 端点受到越来越多的恶意攻击。能够识别系统中的此类威胁攻击，提前进行防御。

为 API 开发人员提供了几个关键建议：

  • 为Web和移动应用程序使用单独的域名。通过这种方式，能够识别，例如，当能检测到用户在通过浏览器去访问移动应用程序终端时，可以做为有攻击者想要试图逆向工程的判定指标。

  • 注意 API 端点中的“爬虫”——例如 Facebook 和谷歌，常用于枚举网站——尤其是那些用于移动应用程序的端点。日志中爬虫程序的存在通常表明正在进行主动侦察和即将发生的攻击。

  • 定期查看 API 日志，特别注意用户代理字符串 - 异常或意外行为的迹象通常是攻击的前兆。


最佳实践：GraphQL攻击向量

GraphQL 是一种允许客户端针对底层数据存储构造任意数据查询的数据查询语言，与更完善的允许通过已知端点进行结构化访问的REST API 形成鲜明对比

虽然 GraphQL 端点为客户端消费者提供了更多的灵活性，但由于底层实现的复杂性，它确实需要去考虑更多的安全性。一些常见的攻击方式：
自省：GraphQL 的好处之一是能够动态枚举底层数据，然而不幸的是，这也可以促进攻击者的发现过程。
缺少访问控制：默认并不提供访问控制，开发人员必须在定制逻辑中实现它们。
SQL 和 NoSQL 注入：GraphQL 很容易受到对支持数据存储的传统注入攻击。
信息泄露：默认的 GraphQL 实现往往非常冗长，可能对攻击者有利。
绕过速率限制：批处理查询可能导致对 GraphQL 端点的拒绝服务 (DoS) 攻击。

DoS攻击：除了上述之外，嵌套查询也可以很容易地用于发起 DoS 攻击。

结论：默认的 GraphQL 实现在默认情况下通常是不安全的，明智的 API 开发人员最好加强实现以消除一些更常见的攻击向量。星阑科技可以提供全景化API识别、API高级威胁检测、复杂行为分析等，帮助用户构建API Runtime Protection体系，守护数字世界的每一次网络调用。
