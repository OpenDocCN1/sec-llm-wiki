前言

最近在做Rpc的相关漏洞研究，分析一下以前的漏洞来熟悉Rpc的通讯过程和硬链接的攻击方式。

背景


Windows下有一个名为Schedule的有关任务计划程序的服务，在Win10中，程序通过ALPC (Advanced Local Remote Call，ALPC就是Client和Server都在同一台Windows机器上进行Rpc通信的一种类型)调用SchRpcSetSecurity函数的时候，会自动检测C:\Windows\Tasks（Windows计划任务存放的相关目录）下是否存在.job的文件(计划任务的存储文件)，如果存在，则会通过安全描述符来设置文件的属性。


但是SchRpcSetSecurity并未对调用此函数的用户权限进行检查，任何用户都可以调用此函数来对Tasks目录下的job文件进行权限修改，从而导致一个越权的操作，如果可以修改某些系统文件，则可以在触发系统文件之后，以system的身份来运行恶意的代码。


_SchRpcSetSecurity函数原型如下：

long _SchRpcSetSecurity(    /* [in] */ handle_t IDL_handle,    /* [string][in] */ wchar_t *arg_1,    /* [string][in] */ wchar_t *arg_2,    /* [in] */ long arg_3););


传入参数arg_1为C:\Windows\Tasks\目录下job的名字，传入参数arg_2为SDDL。


SDDL即安全描述符字符串，是安全描述符（SecurityDescriptor）转化成的字符串形式。SecurableObject(安全对象)是拥有安全描述符的Windows的对象，安全描述符存储在ACL(access control lists)列表中，一个安全描述符有两部分ACLs:

  • ‍一个system ACL(SACL) ，来决定对一个对象的哪种操作会被记录下来。

  • 一个Discretionary  ACL(DACL)，用来决定哪些用户可以执行特定的操作。‍


当一个进程尝试访问一个安全对象的时候，系统会检查对象的DACL中的ACE(即Access Control Entry，指Windows中被访问对象的安全描述符中的DACL中的相关字段)来决定是否赋予访问权限。如果对象没有DACL，则系统赋予完全的访问权限，如果对象的DACL没有ACE()，那么系统拒绝所有访问对象的尝试。


ACE字符串的格式化如下：

ace_type;ace_flags;rights;object_guid;inherit_object_guid;account_sid;(resource_attribute)


如果想让普通用户对某个文件进行读写操作，可以任意找一个普通用户可读写的文件提取出SDDL字符串，或者如下就是普通用户可进行读写文件的SDDL字符串例子：

D:(A;;FA;;;BA)(A;OICIIO;GA;;;BA)(A;;FA;;;SY)(A;OICIIO;GA;;;SY)(A;;0x1301bf;;;AU)(A;OICIIO;SDGXGWGR;;;AU)(A;;0x1200a9;;;BU)(A;OICIIO;GXGR;;;BU)


每个()里面对应的都是ACE字符串，用前两个来进行举例：

https://docs.microsoft.com/en-us/windows/win32/secauthz/security-descriptor-string-format

ConvertStringSecurityDescriptorToSecurityDescriptorW 函数原型如下：

BOOL ConvertStringSecurityDescriptorToSecurityDescriptorA(  LPCSTR               StringSecurityDescriptor,  DWORD                StringSDRevision,  PSECURITY_DESCRIPTOR *SecurityDescriptor,  PULONG               SecurityDescriptorSize);

那么我们可控的这两个参数a2,a3有什么用呢？


a2就是job的名字，_ScheSetSecurity会通过job的名字(例如TaskName)来解析成一个完整路径:C:\windows\tasks\TaskName.job。


a3是SDDL，_ScheSetSecurity会将安全描述符字符串转换为安全描述符，然后给a2所解析成的完整路径进行安全描述符a3的设置。

在中间的步骤中，没有对用户的权限和进行修改的文件权限进行比较，导致了普通用户可以通过JobSecurity::AddRemovePrincipalAce()进行设置DACL。


现在可以对C:\windows\tasks\TaskName.job文件的内容和属性进行任意更改的操作，这时漏洞已经可以自由控制了。那么如何进一步利用，达到获取System的权限呢？这就不得不提到windows下的一个概念--“硬链接”。

通常，每个文件都只有一个硬链接，通过文件名（例如xxx.dll）对内容进行修改时，磁盘上存储的数据也会发生相应的变化，但如果我们创建一个硬链接（C:\windows\tasks\TaskName.job）并指向这个文件，通过硬链接进行修改，xxx.dll的内容和属性也会发生相应的变化。


这样，我们就可以首先创建一个硬链接（C:\windows\tasks\TaskName.job）指向想要修改的文件，再通过 _ScheSetSecurity 对该文件进行DACL设置，就可以达到任意读写系统文件的目的了。

然后再准备一下远程调用rpc的一个步骤：

然后就可以对硬链接指向的dll进行内容上的修改，就可以达到以系统权限启动某些程序的时候，会以system的身份加载我们所修改的dll，完成提权操作。


总结

在Windows上，存在很多这样的Client和Server进行通讯，一旦没做好权限检查，就会使得Server以System的权限去操作一些意料之外的事情，那么，之后就可以对Windows上的RPC接口进行枚举，去批量寻找类似的利用方式简单的漏洞。
