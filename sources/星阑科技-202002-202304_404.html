一、前言

今年有幸继续作为r3kapig的一员参加了此次 WCTF ，可惜由于疫情，WCTF 改在了线上举办，没有了线下的乐趣，加上举办时间在周中，以及在准备题目的时间上我们内部协调出了一点点问题，导致整个比赛过程并不是特别顺利，最终的成绩也不是很理想。但是总的来说，WCTF的题目质量依然得到了保证，这里需要感谢主办方和各大战队的优秀题目！


在比赛期间，我主要做了 minesweeper 这个题目，因为是周中，所以也有了一些时间上的耽误，另外在我逆向完之后，出题人把源码放了出来，导致这个题目的难度骤降，所以也没能拿到一血，比较可惜（虽然考虑非预期解的话，应该很早就没了……）。赛后出题人也表示抱歉，当时出题人其实并没打算在逆向问题上设槛，因为题目难度并不大，想看看如果直接逆向，在第一天是否有队伍能做出来，结果发现没有的时候，就把源码放出来了，结果造成了已经逆完的队伍有一点劣势……


不过总的来说这个题目还是有趣的，除开逆向部分的难度也不大，所以我就放飞自我了，希望这篇文章给大家带来一点乐趣~

三、找找思路

到现在为止，我们对题目基本上了解了，这是一个由 Rust 语言编写的扫雷修改而来，提供了 7 个难度，如果仔细看看原来的文件，可以发现是没有这个难度区分的，人家原来可是一个正经游戏，但是现在肯定是不正经了……


这个时候，我们就需要说一句：“停停。”然后思考一下，我们的目标是什么：

1. 题目玩通了就能有 flag ，rdp 文件如果点开会在远程 windows 上运行这个游戏让我们玩

2. 但是直接玩通是不可能了，所以应该找到程序修改了什么地方，看看这些地方是不是有什么密籍之类的玩意儿。


两分钟……两分多钟以后，啊，就想明白了，看来需要逆向，可是，这可是个 Rust 的程序啊，还没有符号，出了名的难逆，那么怎么办呢？

效果确实还不错：

其中红色的函数都是由 binary AI 给认出来的，但是其实有许多的函数被跳过了，我看了一下，发现是因为 binary AI 运行的过程中会进行反编译，由于 Rust 程序很不巧的，IDA 默认分析不太正确，所以反编译无法成功，这些函数就都被跳过了。 


到这一步，其实我们的逆向工作量就已经小了很多了，接下来就是 Rust 逆向了，现在我们可以找到 main 函数，时不时的还能看到一个有名字的函数，搭配 xref ，我们可以很容易的找到更多的函数，接下来就是需要恢复一部分函数，然后去找到不一样的地方了。

五、Rust 逆向

Rust 逆向的难点在于 IDA 的支持并不是很好，大概存在这几种问题：


1. IDA 分析出错，导致两个函数变成了一个函数（如果用 graph view 看 CFG 可以看出来，其实是两个不连通的图，但是却奇迹般地成为了一个函数）：这个时候其中一个函数会直接消失。这个时候的解决方法一般是，把这个函数 undefine 掉，然后找到那个被 IDA 吃掉的函数，先 define 出来，然后再 define 那个原来就有的函数，这样就不会因为 IDA 的胃口大而被吃掉了。

六、不一样的地方

经过不懈的努力，我们发现有几个地方不一样：

1. 日志输出：原来的代码里是没有的，而且似乎还有个检查，只有在开启检查的时候才有

2. 键盘处理：原来没有难度调整嘛，所以是没有键盘事件处理的，现在有了，而且必须在开启了一个变量的时候才会打印

经过我的深思熟虑，我决定将其命名为一个言简意赅的名字：custom_needs_logging


3. 初始化的奇怪现象：在原来的代码里，第一个雷是永远不会失败的！但是现在我一点就失败了，这肯定不是因为我运气不好！肯定是的。不过这个时候，我被一个队友打破了幻想：因为他发现，他的第一个总是能成功，在哪死的，在哪爬起来，就不会失败。（点那个输掉之后，再点那个，肯定不是雷）

看来我是真的运气不好，我怎么就没发现。


在经过一段时间的怀疑人生之后，我决定解决一下这个疑惑：最后发现，在移动指针的事件处理的地方，多了一个 sweep 函数。这个函数呢，本来是在扫的过程中用的，从你名字上，我们也能看出来，也就是你点的时候才会用到，他可以用来判断一个位置是不是雷。但是现在移动指针的地方也会用到，就很奇怪了。


至于为什么他总是运气这么好，我也得到了答案，原来是 sweep 会进行初始化，初始化的时候他所在位置的第一个一定不是雷，本来是在点的时候才会进行的，但是现在只需要移动鼠标，不用点，就会初始化，所以，在刚刚死掉的时候，再点一下鼠标重新开始，这时鼠标悬浮在哪一个块上方，哪个块就一定不是雷。


一个疑惑解决了，确实不是我的运气问题，我感到很高兴。

九、最后的扫雷

现在其实我已经不怎么需要源码了……


日志有了之后，下一步其实还是很明显的，因为日志只有 INFO 级别，这个在扫到雷的时候，会有一个 animation_cache（可以通过字符串日志的输出猜到） 的过程，然后会输出 cache 完成，而没有扫到雷的时候，就不会进行 cache ，但还是会输出 cache 完成。那么这中间就存在一个时间差了。


下面就是老套路了，时间测信道，鼠标只要在一个块上浮动就会打印一次，所以如果可以控制鼠标的速度，然后观察打印的速度，就可以知道是不是有雷了。


然后我试了一下，发现不是很靠谱。仔细观察了一下，发现 animation_cache 里有找四周雷的操作（这个看源码和逆向都容易看出来），那么雷少了，效果就不明显了，要不然要那么高的难度干嘛。所以，我毅然决然地打开了最高难度，然后，拿起了我的鼠标，开始了手动扫雷。


然而由于我已经年迈，右手止不住的颤抖，导致鼠标并不稳定，已经不复当年 CS 战神的荣光（好吧，我其实忘记带鼠标，用的触摸板），判断频频失误，最后决定，一定要搞一个稳定的移动鼠标的方法。


经过一段时间的搜索，我发现了 pynput ，完美解决的我需求，反正就是移动鼠标嘛，于是我写了这么个脚本（切记，开着这个脚本的时候，不要打字……不信，自己试试）：

import time from pynput import keyboard, mouse  mouse = mouse.Controller()  def keyboard_press(event):     if event == keyboard.KeyCode.from_char('a'):         for i in range(3):             for j in range(5):                 mouse.move(1, 0)                 time.sleep(0.002)              for j in range(5):                 mouse.move(0, 1)                 time.sleep(0.002)              for j in range(5):                 mouse.move(-1, 0)                 time.sleep(0.002)              for j in range(5):                 mouse.move(0, -1)                 time.sleep(0.002)  with keyboard.Listener(         on_press=keyboard_press) as listener:     listener.join()

这个的功能就是，只要我按键盘的 a ，鼠标就会进行魔力转圈圈，并且时间比较稳定，于是我开始了我的扫雷工作……
