**基本概念与介绍**

在开始分享之前，考虑到各位伙伴们对于红队了解的深度不一，在此，我先简要介绍一下 Redteam 中常见的一些基本概念：

**Redteam**

可能大部分人对于 Redteam 都有一定的了解，但是往往都会存在一定的偏差。Wikipedia上是这么定义 Redteam 的：测试一个组织的网络安全的白帽子组织。此外，再引用一下 Redteam wing 的一段话：红队使用真实的攻击技术来模拟攻击过程，以评估蓝队的安全防御是否做的到位。

对于以上的表述，我是这么理解的：红队是由一群白帽子组成的；红队的攻击是模拟的攻击，而非真实攻击；与红队对应的还有蓝队，负责进行防御；红队行为的最终目标是测试一个组织的网络安全和防御。

**TTP**

第一个 T 是 tactics（战术），第二个 T 是 techniques（技术），第三个是 P 是 process（过程）。在 APT 组织的分类中，我们往往从上述三个特征入手，将与 TTP 具有高度相似行为的攻击归类为一个 APT组织，并为其提供一个编号。

**渗透测试/RedTeam/APT组织的区别**

很多刚刚接触 Redteam 或者刚从渗透测试转到 Redteam 的小伙伴往往混淆`渗透测试`以及`Redteam`这两个概念，除此之外，还有一个 APT 组织的概念。在此，我通过参考一些主流的资料，分别从广度、深度、载荷、跨度四个方面，将三者进行了对比，对比的具体内容如下表所示：

![](../Images/74c9b377d144c16ce4690d1de1a3e818.png)

从上表可以看出渗透测试相较于 Redteam，它的广度和深度受到了制约。渗透测试中，我们一般只能针对甲方给定的几个目标进行渗透，并且在拿到权限后，还不允许进行后渗透，在时间跨度上一般不会超过一周，其时间特征上更加的短平快。相对而言，Redteam 允许较大范围的目标扩展，以及可控范围下的后渗透，而且时间一般在数周到数月不同。APT 攻击更加自由，不限目标、不限深度、不限载荷、不限时间，以拿下目标主机甚至是持久控制为目标，往往还会带有一个经济和政治的因素在里面。

**Redteaming的生命周期**

一般而言，完整的 Redteaming 包含以下几部分：信息收集、攻击尝试获得权限、持久性控制、权限提升、网络信息收集、横向移动、数据分析（在这个基础上再做持久化控制）、痕迹清理。

**CC**

cc 的全称是 command & control，一般简写 c2 。c2 使得目标机器可以接收来自服务器的 command，并以此来 control 目标机器，并可以进一步对内部网络发送后续攻击。

  

**RedTeam 团队建设与人才培养**

**道：**

形而上者谓之道，形而下者谓之器。

本次分享中介绍的道，不会以玄之又玄的形式进行展示，相反我们整理了一系列大家关心的核心问题，来探索主题中内在的道。

对于 Redteam 团队建设与人才培养，我们的思考是：

（1）我们为什么要做 Redteam ？

        首先，人是网络安全问题的起源，也是网络安全问题的答案。为什么这么说呢？因为漏洞是人写，漏洞也是人挖的，网络攻击是人打的，漏洞修复也是人做的。因此，网络安全的核心问题也是人，对于攻击方而言，核心就是 Redteam 。

（2）Redteam 的最终产物是什么？

        “我们要打造的是世界一流的网军，而不是水军”。这是某次比赛时传出的口号，我们做红队的最终产物，便是打造世界一流的网军。

（3）如何培养高水平的Redteam人才？

         技术为核心，物质为激励的野蛮生长。形成红队闭环。

**器：**

那么如何具体地进行 Redteam 的团队建设与人才培养呢？我们将从以下的要点入手进行介绍：

（1）多元化的团队组成

（2）任务分发与团队合作

（3）知识库构建、内部分享、仿真环境训练

  

**多元化的团队组成**

  

**团队的规模**

红队核心成员的准入门槛相对于其他业务部门较高。可以说是百里挑一。而且受业务规模的制约，红队的总人数也不会太多。根据相关调研，一般在10-20人左右。

**团队的组成**

作为公司红队部门负责人，在我面过的大部分红队的简历中，大部分的人都偏爱渗透岗。但实际上，理想中的红队真正的渗透人员仅占团队总人数的30%-40%。剩余60%-70%均为渗透人员的支撑单位。他们负责搞定除渗透任务之外的所有任务，他们被统称为安全工程师（包括但不限于环境支撑，数据分析，数据取证，对接，二进制支持等）。虽然做的不是纯粹的渗透，他们的重要性却一点也不小，甚至可以说是每一个优秀红队必须具备的坚实后盾。

![](../Images/166d18173726bf5ed6a3bdec8fb78813.png)

**理想中的红队架构**

理想中的红队架构应该由以下几个小组组成：

1.  渗透实战小组该小组专注于红队攻击，内部可以按照个人特长，进行任务细分为打点以及横向移动。
    
2.  信息系统支持与工具研发小组该小组负责红队的服务器运维，并为红队成员的日常工作提供匿名化工具，还负责进行红队工具的研发。
    
3.  情报与信息收集小组该小组负责对于目标的关键情报和信息进行收集。
    
4.  二进制支持小组该小组负责分析恶意程序、研究后门技术、rootkit 技术以及免杀对抗技术，并在红队行动中提供关键技术的支持。
    
5.  安全研究与代码审计小组该小组负责安全研究和代码审计。
    

如果有条件的话，我希望能在我的愿望清单中加入：

6.  移动安全小组该小组负责 android cc 和 ios cc， 以及移动端程序逆向、加解密，移动端后门分析。
    
7.  报告、文档工作与对接小组该小组负责报告撰写，文档整理以及对外的项目对接，将红队主力从繁重的报告与对接任务中解放出来。
    

**任务分发与团队合作模式**

我们用一个典型的例子，来看一下各个红队小组在一项具体的红队任务中，是如何运作。该例子的具体技术细节，可以参考我们的公众号文章：

> [从一个App开始的渗透测试之旅](http://mp.weixin.qq.com/s?__biz=Mzg5NjEyMjA5OQ==&mid=2247483945&idx=1&sn=feae1b1cc6642113e9ecf1259a30f79c&chksm=c004afb5f77326a31301033e6f6b8daba754743efa86b141c7f996e85690f682f1a02b18198f&scene=21#wechat_redirect)
> 
> 该任务的背景是我们拿到了一个App，需要对App后面的系统进行 Redteaming 。在拿到任务后，我们对该任务的流水线进行了任务分解：App分析 => 信息收集 => 红队渗透 => 后门驻留 => 终端钓鱼 => 移动终端攻击 => 取证与监控 => 报告与总结输出

1.  App分析：`移动安全部门`主要分析 App 中出现的 api 地址，以及其他的信息泄露。如果 App 代码存在加密和混淆，还需要进一步的分析。
    
2.  信息收集：`情报与信息收集小组`对 App 中包含的域名、IP 进行扫描，通过子域名、同站、c 段等信息扩展我们的目标站群，并收集目标站群暴露的信息，以及可能存在的问题。此处，我们使用到了`信息系统支持与工具研发小组`负责研发的工具，以及他们运维的匿名服务器。
    
3.  红队渗透：`渗透实战小组`的红队工程师接入，以扫描得到的信息为切入点，尝试攻击目标站群。倘若获取到目标源码，则交由`安全研究与代码审计小组`进行审计。
    
4.  后门驻留：在`渗透实战小组`渗透获取到相关的权限之后，渗透实战小组的红队工程师开始使用信息系统支持与工具研发小组与二进制支持小组合作开发的 rootkit 植入目标机，并启动相应的持久化后门。
    
5.  终端钓鱼：`渗透实战小组`的红队工程师将`信息系统支持与工具研发小组`提供的 cc 载荷以钓鱼的方式植入到特定位置，等待触发。该cc载荷的免杀由`二进制支持小组`维护。
    
6.  移动终端攻击: `渗透实战小组`的工程师尝试利用 WIFI 和 USB 连接，将`移动安全小组`提供的移动端 RAT 植入到目标移动终端中。
    
7.  取证和监控：`渗透实战小组`的红队工程师利用在（移动）终端中植入的后门对（移动）终端进行取证和长时间的监控。监控中的使用的工具有`移动安全小组`、`信息系统支持与工具研发小组`研发，工具的基础原理由`二进制支持小组`、`安全研究与代码审计小组`研究得到。（如 whatsapp 监控涉及到大量的逆向与加解密工作）。
    
8.  报告与总结输出：输出报告与总结由`渗透实战小组`提供粗略版本，`报告、文档工作与对接小组`负责整理。

**知识库构建**

知识库的主要内容包括项目记录和知识分享，旨在 Redteam 新人和老手之前快速地传递经验和知识，也方便个人的总结。

**内部分享**

每周一次的技术分享，带来最前沿的技术。

**仿真环境**

漏洞复现与实际渗透能力、综合安全素养的提升。培养新人的实战能力。在此推荐一下我的 awd-platform(https://github.com/zhl2008/awd-platform).

RedTeam的人员存在一定的流动性。我们必须花一定的精力在新人的培养上。红队团队建设与人才培养的可持续性发展，是红队流水线能够正常运转的根基所在。

**信息系统建设**

  

**云服务器的匿名性需求**

考虑到红队行动的风险性，为了保护我们的红队成员，我们在挑选云服务器时，首先便要求的是云服务器的匿名性，在这种需求下，我们不能通过常规渠道购买阿里云、腾讯云上的服务器。感谢区块链和数字货币的创造，让我们有了其他的选择。我们可以使用匿名的数字货币，在一些国外的云服务器厂商那购买服务器。

![](../Images/4f8d64bd3e2a9e047364240e292e3364.png)

为了购买到心仪的服务器，我们对市场上主流的支持数字货币的云服务器厂商做了一个调研，对比了他们的一些特性，得到了如下的统计表格：

![](../Images/aac70067df2cba32ad378e67c9287431.png)

但是，使用数字货币购买云主机也会存在如下的一些问题：

1.  价格相较于国内的云主机价格会高上不少；
    
2.  比较难找到到国内速度快，带宽高的服务器；
    
3.  线路连接可能因为某些特殊问题出现波动，甚至断线；
    
4.  部分主机商如 bitvps ，和客服交涉只能通过邮件，一旦到期服务器立刻销毁，不能恢复。这坑点曾今导致我们的 cc 服务器上的重要数据被意外销毁。
    

**主机安全策略**

既然是红队的信息系统，我们必须要保证我们的服务器的安全性，安全决不能是我们的短板。我们使用如下的主机安全策略。

1.  通讯流量加密：接入可以使用一些 VPN 协议，例如  wireguard + 混淆协议这样的解决方案；
    
2.  ssh 严格的登录限制：常见的 IP 限制+仅公钥登录限制；
    
3.  日志清理：使用 crontab 定时清理服务器上的敏感日志，尽量减少服务器失陷后被溯源的可能性；
    
4.  防火墙策略：敏感管理服务的端口，只能由统一的跳板服务器接入；
    
5.  定期的安全检查和渗透测试：保证服务器不失陷。
    

**红队高压线**

在红队行动中，有一些明确不能出现的行为和现象，我们称之为高压线，一旦越过此线，就将受到相应的处罚。大致内容如下：

1.  不允许泄露敏感信息：个人信息、公司信息、密码信息。此前有一个红队成员，在渗透时添加 authorized\_keys 时，在公钥后添加了自己的真实邮箱；
    
2.  不得违反红队操作限制：登录以及代理的使用；
    
3.  其他高危操作：某次渗透中，某红队成员在某 gitlab 上使用自己的真名注册了gitlab ；
    

**服务器架构**：

我们红队服务器主要架构一般由三个部分组成：

1.  跳板：跳板主要负责接入我们的红队服务器，并且不会开放任何无关服务以及无关端口，尽可能将攻击面降至最低，通常会安装wireguard、frps、nps 这样的代理攻击和 VPN 攻击；
    
2.  红队服务器：CC server，web 服务器，测试服务器；
    
3.  bots(僵尸网络）：盈余的服务器和攻陷的终端作为 bots，形成代理池。

**cc服务器的架构优化**  

对 cc 服务器的架构优化有什么好处呢？首先我们可以提升 cc 流量的隐蔽性，其次一旦我们的 cc 域名被标记为恶意域名后，可以方便我们对 cc 服务器的迁移，最后也可以提升 Redteam 在使用 cc server 时的用户体验。一般我们可以使用如下的优化方案：

方案一：针对 cc profile 的优化。类似于 CS 这样的工具，对于其中使用了HTTP（s)的交互流量，我们可以将流量伪装成 js 以及 CSS 的加载流量，还可以将我们的域名伪造成一些常见的 CDN 域名，以混淆视听。

方案二：针对 cc redirector 的优化。我们可以将 cc 服务器分为前置服务器和后端服务器两部分，前置服务器根据 HOST 指定的具体域名，将不同的连接转发到不同的后端服务器上。需要迁移时，只要重新搭建前端服务器即可，后端服务器无需做任何改动。cc redirector 可以使用frp，apache，nginx 等提供反向代理的软件和中间件来实现。

![](../Images/37aaba5c708123f5852ba7a2aa1a76c7.png)

方案三：针对 cc redirector 方案的网络优化。使用商网直连的线路，或者在使用优化二的时候，将服务器置于内网。（在没有托管机房的情况下，也要考虑到服务器的噪音）。

**红队域名**

红队的域名一般也是需要较高的匿名性，可以使用数字货币在一些国外的域名商那里购买，比如 namecheap 。红队的域名一般用于：cc载荷分发、cc 连接以及 DNS tunnel 。

  

**匿名性**

  

匿名性是红队攻击必须要考虑的因素，在复杂的网络对抗中，我们常常要求极高的匿名性（向APT组织看齐）。匿名性主要体现在一下几个方面：

*   基础设施的匿名性：redteam 服务器和域名等信息资产
    
*   红队工具的匿名性：减少红队TTP 被追踪的可能性
    
*   网络通讯的匿名性：代理，VPN，物联卡等
    
*   网络身份的匿名性（邮箱，社交账号，虚拟身份等）
    

  

**红队项目管理**

  

高效的红队项目管理能够提升整个红队的工作效率，红队的项目管理涉及到以下几个问题：

*   项目进度管理：此处我们使用的是明道云
    
*   项目文档管理：google docs 和其他国内的在线协作文档
    
*   项目数据管理：敏感和脱敏分开存储
    
*   项目代码管理：项目使用 gitlab 进行管理，敏感项目一律私有，按需开放权限，定时回收权限
    

  

**RedTeam 三大库的建立**

此处介绍三大库，分别指的是：Redteam 知识库，Redteam 工具库以及红队漏洞库。

**道：**

1.  三大库在红队行动中扮演什么样的角色？
    

       三大库是对红队的加强和补充，也是红队武器库的主要组成部分。

   2. 如何为三大库添砖加瓦？

      三大库由 Redteam 日常工作中的点滴积累而来。

与之前的团队建设和基础设施相比，Redteam 的三大库更加依赖于团队在实战中的积累，是需要用时间去积淀的。

  

**RedTeam知识库**

  

红队知识库主要由项目记录、公众号文章、内部分享、最新漏洞跟进以及研究类文章组成。

*   项目记录：其中项目记录在前文已经提到，其主要是Redteaming 的产物，有时候也可能是安全研究的产物。对于Redteaming ，它是项目结束后的渗透路径复盘，以及项目中的得失的总结；
    
*   公众号文章：在公众号文章方面，我司对于每一个部门都有一些硬性的指标要求，需要在一定的时间内提供一定量的公众号文章。公众号文章一般会来源于脱敏后的项目记录；
    
*   内部分享：一般是每周一次，可能会介绍一些技术向的内容；
    
*   漏洞分析文章：紧追时代潮流，对于最新漏洞的关注；
    
*   研究类文章：漏洞挖掘方案、自动化方案以及安全方法论的探讨和研究。
    

  

**RedTeam工具库**

  

Redteam 工具库是 Redteam 在网络攻坚中的武器，一般主要包含以下的类型的武器：

*   CC 类工具：cc 类型的工具还可以进行进一步的划分，包括有针对多种平台的 cc，以及下发 cc 载荷的钓鱼平台
    
*   终端对抗类工具：用于终端的免杀、杀软对抗以及一些非传统型的后门（参考 xshell phpstudy 的后门）
    
*   rookit 类工具：各类平台下的 rootkit，可以隐藏进程、网络连接和文件，用于长时间的后门驻留
    
*   自动化类工具：自动化信息收集、自动化漏洞扫描、自动化代理与转发工具等
    
*   取证与监控类工具：用于在控制目标终端后的取证以及长期的监控。主要包括浏览器监控，IM 监控，邮件客户端监控以及常见终端管理工具和数据库管理工具的监控
    

  

**RedTeam漏洞库**

  

漏洞库是在红队行动出奇制胜的法宝，有 1day 和 0day 之分。

*   1day：对于 1day 型漏洞，我们会收集并适当改良原先的攻击脚本，使其更加适应于我们的自动化漏洞利用框架，并搭建配套的漏洞利用环境；
    
*   0day：对于一些小型的框架、cms、OA，可以按需挖掘，即挖即用；对于常见网络设备漏洞（VPN，邮箱），常用库（fastjson），常用中间件（weblogic）中的漏洞，由专业的安全研究部门进行审计。
    

总结展望

  

在红队建设的道路上，我们仍然任重而道远。或许对于不同的业务，不同的人员组成，我们建设红队的历程会有所不同，但是作为基本原理和基本方向的道，我相信一定会有很多的共同之处。团队、基础设施以及三大库的积淀，是我们红队建设者避不开的问题，最后，也希望能够在未来，和国内外其他的红队自由交流，共同成长，守护网络空间的安全。
