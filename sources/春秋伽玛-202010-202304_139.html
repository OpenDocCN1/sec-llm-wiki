0x01 题目设计



新的协议机制

首先，现在绝大多数PWN题的设计逻辑都是选手构造一个恶意输入，程序在接收到恶意输入后，在主逻辑中由于进行了不当操作导致了漏洞的发生，这种题目可以认为是漏洞存在于程序端。
那么，本题的设计预期是在常规的数据传输上额外加了一层，选手和题目文件的交互不再是不同的明文传输，而是需要遵循我自定义的协议进行。可能也有选手注意到了，这个题目的名字中带有1.0的字样，这其实也代表了本题中所应用的协议仍是一个较为初级的明文协议，我定义的协议结构如下：
在本题中，对于消息首部(Header)有以下要求：
  • 魔数(Magic Number)：需要恒为0x1234567812345678，魔数不正确将被认为是无效消息。
  • 消息长度(Message Length)：长度应为密钥长度和内容长度的总和加上0x20，否则认定为经过了中间人攻击的消息或无效消息。(事实上此字段在首部长度不可变时为无效字段)
  • 密钥长度(Key Length)：密钥长度，将依据此从消息主体中读取Key，同时，此字段应该与服务器端的密钥长度一致。
  • 内容长度(Content Length)：内容长度，将依据此从消息主体中读取内容。
此外，由于本题中的Content实际依然使用了明文传输，并未使用Key加密，并且没有引入临时会话密钥机制(即，每次向选手发送消息会导致上一次会话的Key失效并重新分配Key的机制)所以事实上Key字段在此时与魔数字段效果相同，需要恒为AAAAAAAA，同时密钥长度需要为8。
最后，为了方便选手接收消息进行分析，同时也为了避免格式化字符串漏洞的发生，最后将封装后的消息进行了标准Base64编码。
可以看出，整个题目的消息传输中，没有出现任何的加密算法，唯一的编码算法还是使用了标准Base64编码，完全可以使用findcrypt插件识别。但是为了更贴近实战，在未来的题目版本中，将会引入安全传输机制，让Key字段真正发挥作用，例如引入AES或DES对Content进行一次加密。

协议漏洞埋设

真正分析了此题目的选手其实可以看出，本题的主逻辑很简单，同时也没有任何的预设堆漏洞。因为此题我将漏洞埋设在了协议中，当服务器接收到选手发来的消息时，会顺次进行以下解包操作：

  1. 取首部进行操作。

  2. 验证魔数是否为0x1234567812345678。

  3. 取三个长度字段的值，并依据密钥长度和内容长度分配两个Chunk用于存放密钥和内容。

  4. 验证消息长度是否经过了中间人攻击或无效。

  5. 利用密钥长度从主体中取Key并存入密钥Chunk。

  6. 验证密钥是否和服务器密钥一致。

  7. 利用内容长度和密钥长度从主体中取Content并存入内容Chunk。

  8. 将内容Chunk返回到接收消息处，消息使用结束即释放内容Chunk。

  9. 以上任何一步判定为非法消息时，调用以下逻辑清理：

    msg_pack("Illegal Head!");
    free(recv_msg.content);
    free(recv_msg.key);
    return "ERROR";
如果能理清这个逻辑，漏洞点就很明显了，Chunk指针的新建在第三步，而当第二步出错也会调用free,并且此时不验证指针有效性，这将会导致Double Free漏洞的发生。
但是由于频繁的消息接发，这个漏洞往往只能演变为拒绝服务攻击，并且，可以在主逻辑发现这样的代码段：
if(!strcmp(recv_choice,"ERROR")){
    free(recv_msg.content);
    exit(0);
} 
这意味着当非法消息被接收时导致程序退出。
但是，真的是这样吗，或者说，这个机制真的有全覆盖吗？答案显然不是，当我们选择表单中的一项进入子逻辑时，可以发现，所有的逻辑块并未调用上面所述的防护代码，此处我预期是想模拟Bypass机制，为保证子逻辑业务稳定而抛弃了可能导致整个程序退出的防护代码，而这里，就将导致RCE漏洞的发生。
case '1':

0x02 预期解


通过给定一个过大的密钥长度来获取一个unsorted bin中的chunk，并在之后申请chunk时，不给定任何内容。此时libc基址将会直接被传入新申请的chunk中，随后打印即可计算出libc基址，在那之后就是常规的fastbin attack了。

0x04 春秋留言


这个题可能还有些选手觉得IDA的反编译结果觉得很差，觉得是我某些逻辑故意实现的很恶心。但事实上，我是开启了一个名为Fortify的GCC防护，它能帮助程序在编译期就检查可能的内存溢出，同时当等级开到2级，将会加入运行时内存监管代码(类似于Canary)，这同样是GCC官方提供的防护，并非是我为了恶心选手所为。
gcc -fstack-protector-all -D_FORTIFY_SOURCE=2 -O2 -z noexecstack -fPIC -fpie -pie -z now -o <ELF Name> <Source Code Name> base64.c -lm
