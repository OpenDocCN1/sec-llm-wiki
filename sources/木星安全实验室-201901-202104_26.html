01

介绍



这是《恶意软件的开发与检测》系列文章的第四篇。


在本系列的前几篇文章中，我们讨论了检测沙箱，虚拟机，自动分析以及使分析人员更难进行手动调试的方法。


在本文中，我们将讨论更多有关使用Visual Studio编译和链接代码，重点主要放在静态分析和混淆上。


注意：本文用的时64位执行环境——某些代码示例可能不适用于x86应用程序（例如，由于硬编码的8字节指针长度或PE和PEB中的数据布局不同）。





02

在Visual Studio上创建可执行文件



在Visual Studio中创建一个新项目，浏览编译和链接选项，查看其中的内容。我们会用到这个Metasploit shellcode注入器：


void main(){  unsigned char shellcode[] = "\\xfc\\x48\\x83 (...) ";  PVOID shellcode_exec = VirtualAlloc(0, sizeof shellcode, MEM_COMMIT | MEM_RESERVE, PAGE_EXECUTE_READWRITE);  RtlCopyMemory(shellcode_exec, shellcode, sizeof shellcode);  DWORD threadID;  HANDLE hThread = CreateThread(NULL, 0, (PTHREAD_START_ROUTINE)shellcode_exec, NULL, 0, &threadID);  WaitForSingleObject(hThread, INFINITE);}


某些编译和链接设置可能会对二进制文件进行更改，缩小文件的大小（让其更容易传输），或加大调试和反向工程的难度。





03

编译器选项



3.1 C语言运行库（/ MT）


我们应该做的第一件事是强制应用程序使用运行库（CRT）的静态版本——否则它无法在未安装MSVCRT的计算机上运行。这可能会大大增加可执行文件的大小，因为必须将库嵌入其中。


开发常规应用程序时，通常最好使用系统上的共享运行库（可以将其捆绑在安装程序中）。但是，恶意软件不能这么做，因为它要尽可能地轻便。


有一种方法可以减小可执行文件的大小，使用某些CRT特征。可以用每个Windows版本上都有的msvcrt.dll库。我们需要在msvcrt.dll库里创建一个静态库msvcrt.lib。使用自定义CRT静态库，不要用Visual Studio自动添加的静态库（由于/NODEFAULTLIB链接器参数），可以把可执行文件的大小减少到4 KB左右。另外，_NO_CRT_STDIO_INLINE需要被定义。


有关使用内置msvcrt.dll的更多详细信息，请查看Solomon Sklash的文章：

https：//www.solomonsklash.io/smaller-c-payloads-on-windows.html。


3.2 代码优化（/ O1，/ O2等）


有两种代码优化策略——支持速度或大小。每种方法都会导致编译器应用一些更改代码的技术，这可能会让程序集难以读取和理解。例如，调试器可能无法评估某些（优化）变量的值。某些指令可以用不那么明显的指令代替，但是会产生相同的结果。内联函数可能会使代码更难理解，因为它在逻辑上分离的功能块数量较少。


在不考虑编译器的优化情况下，__forceinline 指令可用于标记编译期间要内联的特定函数。





04

链接器选项



4.1 调试信息（/ DEBUG）


特定的调试信息.PDB文件路径放置在最终的可执行文件中，该文件可能包含敏感信息。要删除最终可执行文件中的敏感信息。我们还可以伪造一个.PDB文件路径来欺骗研究人员，例如把恶意软件分到不同的组。


可以从这篇文章（https://www.fireeye.com/blog/threat-research/2019/08/definitive-dossier-of-devilish-debug-details-part-one-pdb-paths-malware.html）中提取恶意软件的样本。


4.2 清单（/ MANIFESTUAC）中的UAC设置


这个特定选项不会更改代码，但是值得一提。我们可以将应用程序配置为提示用户同意或提供凭据（取决于系统设置），来获得管理特权运行。有时，这可以作为UAC派上用场来实现“绕过”。如果需要更高的特权，问用户要就行。但这可能会引起某些用户的怀疑，因此只能在特定情况下使用。无论如何，我们可以将UAC级别设置为highestAvailable-仅当用户是本地Administrators组的成员时，应用程序才需要获得管理员同意或凭据。





05

静态分析和混淆



我们要怎么做才能混淆代码？对二进制文件进行静态检查时，要尽可能降低信息可见度。


Windows可执行文件（Portable Executable）包含一些从逆向工程师的角度来看特别有趣的信息：标头，节标头和内容（代码，资源等），导入和导出的功能，时间戳。分析人员仅通过检查可执行文件（无需运行它）就可以提取大量有用的信息。这包括代码，导入的函数，硬编码的字符串和其他数据。静态PE文件分析还可以指示使用了打包程序或其他混淆技术。当然，最简单的方法是计算文件哈希，在数据库中查找它（VirusTotal等）。


那么，我们如何应对静态分析技术？





06

更改文件哈希



稍微更改文件的一点点内容都会让其哈希完全不同，因此可以将多态性引入代码中，也就是复制可执行文件，同时在末尾添加一个空字节。更复杂的方法可能包括对嵌入在可执行文件中的资源（例如图标）进行更改。


我们无法删除与正在运行的进程关联的可执行文件。尽管可以重命名正在执行的文件。但是，我们需要启动另一个进程，等主进程终止，然后修改磁盘上的二进制文件并重新启动恶意应用程序。我们还可以复制可执行文件（更改其名称的最后一个字符）并修改副本：


wchar_t oldExecutablePath[MAX_PATH];wchar_t newExecutablePath[MAX_PATH];size_t executablePathLength;GetModuleFileName(NULL, oldExecutablePath, MAX_PATH);StringCchCopy(newExecutablePath, MAX_PATH, oldExecutablePath);
StringCchLengthW(oldExecutablePath, MAX_PATH, &executablePathLength);wchar_t mutatingChar = newExecutablePath[executablePathLength - 5];newExecutablePath[executablePathLength - 5] = mutatingChar / 2 * 2 + !(mutatingChar % 2);CopyFile(oldExecutablePath, newExecutablePath, FALSE);
HANDLE hFile = CreateFile(newExecutablePath, FILE_APPEND_DATA, FILE_SHARE_READ, NULL, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);DWORD bytesWritten;SetFilePointer(hFile, 0, NULL, FILE_END);char toWrite[] = "\\0";WriteFile(hFile, toWrite, 1, &bytesWritten, NULL);CloseHandle(hFile);  // Make sure that newExecutablePath is run next time - e.g. modify persistence entry

导入地址表（IAT）存储有关应用程序使用的库和函数的信息。在可执行程序启动时，OS动态加载它们。但是表内容可以提供许多有关程序功能的信息，例如内存操作和线程操作功能（VirtualAlloc，VirtualProcect，CreateRemoteThread）可以指示应用执行某种代码注入。WSASocket通常shell捆绑和逆向， SetWindowsHookEx用于键盘记录。

7.1 API哈希


我们可以对特定库导出的所有函数名称的哈希进行计算，而不必对功能名称进行编码/加密（应用程序将动态解析该函数名称），在可执行文件中硬编码此类哈希，然后基于这些哈希列表来选择适当的函数。


使用一些简单的哈希函数（如djb2），但要把5381常量替换为其他常量。我们可以用任何加盐哈希来击溃恶意软件分析人员进行的简单哈希计算。我们已经为某些kernel32.dll导入预先计算的哈希——我们需要做的就是浏览库导出，计算函数名称哈希。

7.2 引导程序：shellcode样式


现在我们的导入表包含GetModuleHandle和GetProcAddress函数，能指出恶意软件的存在（尤其是打包的可执行文件）。现在，我们的应用程序可能比以前更加可疑。需要隐藏这些导入。


我们可以利用以下事实（以下情况适用于x64体系结构；偏移量和x86的不同）：


  • PEB位于相对于GS寄存器的地址：GS:[0x60]。

  • _PEB_LDR_DATA 结构（包含所有已加载模块的信息）位于 $PEB:[0x18]。

  • 加载程序数据包含位于偏移量0x20的指针InMemoryOrderModuleList。

  • InMemoryOrderModuleList是LDR_DATA_TABLE_ENTRY结构的一个双向链表，每个包含了单个模块的BaseDllName与DllBase。 

  • 我们可以浏览所有加载的模块，找到kernel32.dll它的基地址。

  • 知道kernel32.dll在内存中的位置，我们可以找到其导出目录，并浏览获取GetProcAddress函数。

  • 使用GetProcAddress可以找到其他必要的函数，加载所有所需的模块。


现在来执行以下进程：

08

PE分析与指标



8.1 段


要确保段名称反映合法、已编译的PE结构。例如，打包文件可能会把段名称改为任意字符串或带有明显标记的加壳软件（UPX0，UPX1等等）。


添加新的段也可能引起怀疑，最好就把数据存储在现有资源段中。


同样，段的原始大小（在磁盘上的大小）一般等于虚拟的大小（加载映像时在内存中的大小）—— 由于不同的内存对齐方式（磁盘与RAM）通常会有小的差异。例如，.text原始大小为0，虚拟大小为数百KB的部分可能意味着实际的可执行文件已打包。


8.2 资源


我们可以将任何数据作为资源嵌入可执行文件中，例如图标，诱饵文档或shellcode。但Resource Hacker或任何类似工具都可以看见这些东西。嵌入加密的恶意资源或使用隐写术可以加大检查它们的难度。


8.3 时间戳记


PE标头包含TimeDateStamp 4字节字段，这是Unix的编译时间。很容易就能把它更改掉（例如使用十六进制编辑器），隐藏实际的编译日期。

熵分析



熵分析可用于寻找嵌入了可执行文件中的潜在加密内容。加密的数据通常有较高的熵（几乎8位）。压缩数据也是如此。


我们可以使用这个简单的Python脚本（一定要安装pefile模块）来计算PE文件段的熵：


import sysimport mathimport pefileimport peutils
def Entropy(data):  entropy = 0    if not data:    return 0  ent = 0  for x in range(256):    p_x = float(data.count(x))/len(data)    if p_x > 0:      entropy += - p_x*math.log(p_x, 2)  return entropy
pe=pefile.PE(sys.argv[1])for s in pe.sections:  print (s.Name.decode('utf-8').strip('\\x00') + "\\t" + str(Entropy(s.get_data())))


从之前开发的shellcode加载器开始。这是各段的熵：


.text   4.616090501867742.rdata  5.4577520758849944.pdata  0.10191042566270775.rsrc   4.7015032582517895


位于.text.段的应用程序代码的熵与人类语言文本相当。shellcode位于.rdata段，含有较高的熵。


现在，嵌入一些较大的加密数据，例如给可执行文件添加资源。如下所示，该.rsrc段可能包含一些加密或压缩的数据。实际上，它可能是某些映像或压缩了的任何其他文件格式。


.text   4.616090501867742.rdata  5.458570681613711.pdata  0.10191042566270775.rsrc   7.95737230129355


为了能控制数据块的熵，我们可以使用Base64编码。熵值可参阅plain shellcode，AES-encrypted，GZIP-compressed和Base64-encoded。因此，要击溃基本的熵分析，我们可以加密，然后用诸如Base64（或Base62或其他任何自定义变量——BaseN编码数据的熵约等于log 2（N））的自定义变量对数据/有效载荷进行编码。
