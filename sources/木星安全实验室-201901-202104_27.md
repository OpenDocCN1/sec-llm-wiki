**介绍**

  

  

这是《恶意软件的开发与检测》系列的第三篇文章。详细介绍请看《恶意软件的开发与检测Part 1》。

**02**

**检测并阻碍手动分析**

  

  

有一些特定特征表明恶意软件分析人员正在手动检查该应用程序。为了保护我们的恶意软件，我们可以检查这些特征，不让分析人员改变我们的代码。

  

  

  

**03**

**检测调试器**

  

  

首先，检查应用程序是否在运行了调试器的情况下执行。有很多技术可用于调试检测——其中有一部分我们会讨论到。尽管分析人员可以缓解每种技术，但某些技术比其他技术更为复杂。

  

**3.1 查询信息**

  

如果运行了任何调试器，可以 “通知”操作系统。IsDebuggerPresent函数基本上会检查BeingDebuggedPEB中的标志：

*   
*   
*   
*   

```
if (IsDebuggerPresent()) return;  // same checkPPEB pPEB = (PPEB)__readgsqword(0x60);if (pPEB->BeingDebugged) return;
```

  

另一个类似的函数是CheckRemoteDebuggerPresent，它调用NtQueryInformationProcess：

*   
*   
*

在调试时，进程地址空间里会有一些特定的标记。NtGlobalFlag是位于PEB中的标记集合，这些标记能指示调试器的存在。

  

注意：这没有检测到Visual Studio调试器（msvsmon）。

*   
*

注意：这没有检测到Visual Studio调试器（msvsmon）。

**3.3 通过检查代码的更改来检测断点**

  

通过函数调试器放置软件断点，把中断指令注入到函数代码（INT 3\-0xCC操作码）。在运行时扫描函数代码，把每个字节与该值进行比较，或者通过计算函数字节的校验，并把它与适当的值（针对“有效”函数进行计算）进行比较，以检查操作码0xCC是否存在。但是，我们需要知道函数的开始位置和结束位置。我们可以用CrucialFunction后的存根函数。另外，我们需要确保链接器不会链接对象文件和库。#pragma auto\_inline(off)用于防止函数被编译为内联。

  

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
#pragma comment(linker, "/INCREMENTAL:YES")
DWORD CalculateFunctionChecksum(PUCHAR functionStart, PUCHAR functionEnd){  DWORD checksum = 0;  while(functionStart < functionEnd)  {    checksum += *functionStart;    functionStart++;  }  return checksum;}#pragma auto_inline(off)VOID CrucialFunction(){  int x = 0;  x += 2;}VOID AfterCrucialFunction(){};#pragma auto_inline(on)
void main(){  DWORD originalChecksum = 3429;  DWORD checksum = CalculateFunctionChecksum((PUCHAR)CrucialFunction, (PUCHAR)AfterCrucialFunction);  if (checksum != originalChecksum) return;    wprintf_s(L"Now hacking...\n");}
```

  

通过从DR0到DR3来检查调试寄存器来检测硬件断点：

**3.5 异常处理程序**

  

通常调试器会先处理异常。如果可以添加新的或修改异常处理进程（以执行任意代码），那么我们就能发现调试器的存在，因为只有调试器不捕获异常，代码才会执行。

  

结构化异常处理（SEH）是一种Windows机制，用于处理异常。当引发异常且没有其他设施能处理该异常时，该异常将传递给SEH。在运行时期间操纵SEH函数可以检测调试器。

  

在x86环境中，异常处理程序以链接列表的形式存在，并且第一个元素地址存储在TEB的开头。我们可以添加一个自定义处理程序，把它链接到列表的开头。自定义异常处理程序可以表明没有在调试应用程序。

  

但是，在x64环境中，SEH操作是在内核模式下完成的（这可以防止SEH数据通过缓冲区溢出攻击被堆栈覆盖），因此上述技术通常不适用。但是，如果没有任何处理程序能够处理该异常，则将其传递给kernel32.UnhandledExceptionFilter函数（这是异常处理的最后手段）。

  

可以设置自定义过滤器函数，用SetUnhandledExceptionFilter函数从过滤器函数中调用UnhandledExceptionFilter。只有在不调试应用程序的情况下，才能调用自定义未处理异常过滤器。这是因为UnhandledExceptionFilter使用带有ProcessDebugPort标记的pNtQueryInformationProcess函数检查调试器的存在。

  

因此，我们可以注册任意未处理的异常过滤器函数来表明哪个地方缺乏调试器。

  

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
BOOL isDebugged = TRUE;
LONG WINAPI CustomUnhandledExceptionFilter(PEXCEPTION_POINTERS pExceptionPointers){  isDebugged = FALSE;  return EXCEPTION_CONTINUE_EXECUTION;}
void main(){  PTOP_LEVEL_EXCEPTION_FILTER previousUnhandledExceptionFilter = SetUnhandledExceptionFilter(CustomUnhandledExceptionFilter);  RaiseException(EXCEPTION_FLT_DIVIDE_BY_ZERO, 0, 0, NULL);  SetUnhandledExceptionFilter(previousUnhandledExceptionFilter);  if (isDebugged) return;
  wprintf_s(L"Now hacking...\n");}
```

  

**3.6 创建断点**

  

我们可以在代码中创建断点中断，调试器会将其解释为软件断点（就像由用户设置的那样）。下面创建一个简单的SEH处理程序：

  

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
BOOL isDebugged = TRUE;__try{  DebugBreak();}__except (GetExceptionCode() == EXCEPTION_BREAKPOINT ? EXCEPTION_EXECUTE_HANDLER : EXCEPTION_CONTINUE_SEARCH){  isDebugged = FALSE;}if (isDebugged) return;
```

  

这可以检测VS调试器（msvsmon）和WinDbg，但不能检测x64dbg。后者把“断点”异常传送给SEH。

  

用RaiseException函数而不是DebugBreak会引起一些未定义的行为-调试器跳转到错误的地址弄乱了代码流，并产生了EXCEPTION\_ILLEGAL\_INSTRUCTION异常循环。这有助于增加应用程序分析的难度。

  

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
BOOL isDebugged = TRUE;__try{  RaiseException(EXCEPTION_BREAKPOINT, 0, 0, NULL);}__except (GetExceptionCode() == EXCEPTION_BREAKPOINT ? EXCEPTION_EXECUTE_HANDLER : EXCEPTION_CONTINUE_SEARCH){  isDebugged = FALSE;}if (isDebugged) return;
```

  

调试器处理此类断点中断的另一种方法是注册向量异常处理程序。

  

向量异常处理是SEH的扩展。向量异常处理程序不会代替SHE——它们可以同时工作，但是VEH优先于SHE——VEH处理程序在SEH处理程序之前被调用。无论如何，在调试器处理（或不处理）断点异常之后，可能会调用（或不调用）VEH。

  

用DebugBreak函数可以重现与SEH相似的情况（只有当不存在特定调试器时才执行VEH）。这可以检测VS 调试器（msvsmon）和WinDbg，但不能检测x64dbg。

  

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
BOOL isDebugged = TRUE;
LONG WINAPI CustomVectoredExceptionHandler(PEXCEPTION_POINTERS pExceptionPointers){  if (pExceptionPointers->ExceptionRecord->ExceptionCode == EXCEPTION_BREAKPOINT)  {    pExceptionPointers->ContextRecord->Rip++;    return EXCEPTION_CONTINUE_EXECUTION;  }  return EXCEPTION_CONTINUE_SEARCH; // pass on other exceptions}
void main(){  AddVectoredExceptionHandler(1, CustomVectoredExceptionHandler);  DebugBreak();  RemoveVectoredExceptionHandler(CustomVectoredExceptionHandler);  if (isDebugged) return;
  wprintf_s(L"Now hacking...\n");}  
```

‍

  

同样，RaiseException函数引起一些未定义的行为-EXCEPTION\_ILLEGAL\_INSTRUCTION异常循环。我们试着用它来阻止分析：

  

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*

```

**一般检测分析**

  

  

通过枚举运行进程，加载的库等资源，我们可能会发现分析人员试图对我们的应用程序进行逆向工程。有关更多详细信息，请参见上一篇文章（“文件，目录，进程和窗口名称”部分）。

  

**4.1 执行时间处理时间**

  

上一篇文章中描述的时间检查（作为规避沙盒的一部分）还可以用于检测应用程序是否正在分析或调试。检查某个指令块之前和之后的系统时间，假设测得的经过时间应小于某个值。如果应用程序正在被分析，则该指令块中可能设置了断点。如果这样，执行时间将超过假定的时间段。

  

*   
*   
*   
*   
*   
*   

```
int t1 = GetTickCount64();Hack(); // should take less than 5 secondsint t2 = GetTickCount64();if (((t2 - t1) / 1000) > 5) return; 
wprintf_s(L"Now hacking more...\n");
```

  

GetTickCount64函数可能会受到函数挂钩的影响。为了解决这个问题，我们可以用上一篇文章说到的技术（请参阅“延迟执行和函数挂钩”部分）。

**为难分析人员的办法**

  

  

**5.1 规避调试器**

  

用Windows的本地功能隐藏线程，不让调试器发现——线程会停止发送事件。用于隐藏线程的函数（NtSetInformationThread）可能会被钩住——可以用一些虚假参数来调用它并检查返回状态（若参数不正确，则不返回STATUS\_SUCCESS），从而进行验证。

  

*   
*   
*   
*   

```
typedef NTSTATUS(WINAPI *NtSetInformationThread)(IN HANDLE, IN THREADINFOCLASS, IN PVOID, IN ULONG);NtSetInformationThread pNtSetInformationThread = (NtSetInformationThread)GetProcAddress(GetModuleHandleW(L"ntdll.dll"), "NtSetInformationThread");THREADINFOCLASS ThreadHideFromDebugger = (THREADINFOCLASS)0x11;pNtSetInformationThread(GetCurrentThread(), ThreadHideFromDebugger, NULL, 0);
```

  

当然，这不会影响隐藏线程之前发送的事件。

  

同样，我们可以创建一个新线程，用NtCreateThreadEx函数来规避调试器。新线程不会将事件发送到调试器。

  

*   
*   
*   
*   
*   
*   

```
typedef NTSTATUS(WINAPI *NtCreateThreadEx)(OUT PHANDLE, IN ACCESS_MASK, IN PVOID, IN HANDLE, IN PTHREAD_START_ROUTINE, IN PVOID, IN ULONG, IN SIZE_T, IN SIZE_T, IN SIZE_T, OUT PVOID);NtCreateThreadEx pNtCreateThreadEx = (NtCreateThreadEx)GetProcAddress(GetModuleHandleW(L"ntdll.dll"), "NtCreateThreadEx");#define THREAD_CREATE_FLAGS_HIDE_FROM_DEBUGGER 0x4HANDLE hThread;pNtCreateThreadEx(&hThread, 0x1FFFFF, NULL, GetCurrentProcess(), (PTHREAD_START_ROUTINE)shellcode_exec, NULL, THREAD_CREATE_FLAGS_HIDE_FROM_DEBUGGER, NULL, NULL, NULL, NULL);WaitForSingleObject(hThread, INFINITE);
```

  

创建新线程可以使应用程序的分析变得复杂。除非在适当的位置设置了断点，否则新线程中的代码可以自由执行。

**5.3 TLS回调**

  

TLS（线程本地存储）回调是一种Windows机制，它允许在进程和线程的启动和终止上执行任意代码。它可以在main函数（或其他入口点）之前运行一些反调试代码。但是，大多数调试器会自动在main（“系统断点”- ntdll.LdrpDoDebuggerBreak）之前甚至在回调的开头放置断点。无论如何，回调执行需要某些链接器指令：

  

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
void NTAPI TlsCallback(PVOID DllHandle, DWORD dwReason, PVOID){  if (dwReason == DLL_PROCESS_ATTACH)  {    if (CheckIfDebugged()) exit(0);  }}
#pragma comment (linker, "/INCLUDE:_tls_used")#pragma comment (linker, "/INCLUDE:tls_callback_function")
#pragma const_seg(".CRT$XLA")EXTERN_C const PIMAGE_TLS_CALLBACK tls_callback_function = TlsCallback;#pragma const_seg()

在较旧的Windows版本上，TLS回调可用于检测调试器在进程中创建的新线程。从Windows 7开始，DebugActiveProcess调用带有标记的NtCreateThreadEx，导致在新线程的环境块中设置SkipThreadAttach标记，阻止了TLS回调的执行。
