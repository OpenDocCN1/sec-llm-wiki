.NET在后渗透利用中仍然存在。它和大多数C2框架捆绑在一起，已经有了通用工具，并且可以绕过AMSI机制,但是同时也出现了一些巧妙的新方法来启动非托管代码。不过加载.NET程序集的过程是一样的。


我们知道，像Cobalt Strike的execute-assembly这样的工具极大地提高了从内存中加载.NET程序集的可能性，大多数攻击者会在Github发布用.NET编写的工具。在这种趋势下，Blue Team自然就变得十分擅长在内存中寻找合适的攻击位置。但是作为攻击者，我们仍然处于这样一种情况，即无论目标是托管还是非托管进程，在进程内启动.NET代码的方法是类似的。如果我们希望将托管代码注入到进程中，采用的路径也是相同的：(即使目标是已经加载CLR的.NET进程.)



这个问题困扰了我很多年，所以我花了几个晚上研究可以更改签名的方法。我的目标很简单：找到一种在.NET进程中直接调用.NET方法的方法，无需把Shellcode或rDLL专门注入非托管空间，只需抓住CLR的接口然后加载.NET程序集。


这篇文章将探讨如何实现此目标，通过利用Windows公开的调试框架，我们可以看到使用调试API在目标进程中调用任意.NET代码所需要的内容。




01

ICorDebug



如我们在Visual Studio中所见的那样，.NET拥有强大的调试功能，提供了在附加进程中执行代码的功能：



我想起了一种在.NET进程中执行特定方法的简单方式，当然，有一种方式可以模拟此功能，在.NET进程中获得代码执行，而不必加载shellcode和full。至于.NET程序集，我想用的是某种DebuggerEvaluateCSharpInThisProcess方法，显然这并不存在。但有一个文档齐全（尽管非常复杂）的API，能让我们能通过编程来利用.NET调试的功能。


ICorDebug是.NET调试神奇的切入点，并提供了无数功能，使我们可以控制.NET进程。首先要设计一个简单的调试器，将其附加到我们选择的进程中。

03

注入什么？



我们先从简单的事情开始，调用.NET方法，该方法会从磁盘把程序集加载到目标进程中。为此，我们尝试远程调用具有以下签名的.NET方法Assembly.LoadFile：


public static System.Reflection.Assembly LoadFile (string path);


在.NET进程中调用任意代码需要一个ICorDebugEval接口实例，顾名思义，该实例公开了在目标.NET运行时评估代码所需的几种方法。


其中一个方法是ICorDebugEval::CallFunction能让我们直接调用.NET方法，在本例中为.NET方法Assembly.LoadFile。当然，我们还需要创建一个新的System.String作为参数传递。这是用已完成的ICorDebugEval::NewString。


但什么时候调用这些方法？事实证明，这是用ICorDebugEval接口其中一个比较复杂的地方，因为目标需要处于一种我们可以实际评估代码的状态。


如果我们在错误的位置评估代码，则会收到如下错误：



那么错误0x80131c23或“ GC unsafe point”是什么意思？并没有文章围绕HRESULT展开讲述，但是经过一番挖掘，我找到了一篇文章，其中解释了：


当JIT编译器编译方法时，它可以插入对检查GC是否挂起的特殊函数的调用。如果是这样，线程将被挂起，GC将运行到完成，然后继续执行该线程。编译器插入这些方法调用的位置称为GC安全点。


因此，从本质上讲，我们需要以一种类似于垃圾回收的方式来评估代码。


事实证明，要找到满足这一要求的时机可能很棘手（目标没有可用的源代码或PDB），但我发现，要实现这个目标，一种较简单的方法是通过附加的进程使用ICorDebugStepper的实例。该接口能使你在使用标准调试器时，以相同的方式单步调试托管代码。如果重复执行此操作，最终就能找到一个可以评估所需的.NET代码的安全点。


该技术在实践中很实用，当我们试图到达目标CLR即时编译为IL代码时，就意味着挂起的应用程序（或处于停滞状态的应用程序做得不多）无法让我们注入自己的代码。幸亏有许多候选程序（以及一些我们稍后将讨论的COMPlus变量）使这一过程变得容易，我们将在以后进行介绍。


现在，在继续创建步进器之前，我要要重点介绍.NET应用程序的组件如何映射到调试器API，这将有助于我们以后理解一些POC代码。在视觉上，它看起来是这样子的：



要创建步进器，我们需要找到一个与其关联的活动线程。这可以通过ICorDebugProcess::EnumerateThreads或ICorDebugAppDomain::EnumerateThreads来枚举现有线程来枚举现有线程ICorDebugAppDomain::EnumerateThreads，从而检索ICorDebugThread实例数组。


注意：虽然这里讨论的是线程，但它们是“托管线程”的表示形式，和我们平常处理的传统OS线程不同。然而，这些术语在文档中通常没有区别，但对于API调试器而言，弄清楚它们的区别很重要。


通过收集活动线程列表，我们可以使用该ICorDebugThread::CreateStepper方法创建并关联步进器。


我们需要确保在连接后，还要向目标进程可能产生的任何新线程添加步进器。当有趣的事件通过托管回调程序发生时，我们已经有了合适的调用的方法，因此可以根据需要用CreateThread事件添加其他步进器：

  // Continue execution of our assembly  pAppDomain->Continue(false);  return S_OK;}


创建步进器后，在继续执行目标前，我们会用ICorDebugStepper::Step触发执行代码的步骤。一旦发生单个步骤，就会通过事件再次提醒我们的ManagedCallback::StepComplete处理程序。


确定我们是否处于GC安全点的一个办法是在目标进程中创建一个新的字符串对象，稍后将其用作Assembly.LoadFile调用的参数：


HRESULT ManagedCallback::StepComplete(ICorDebugAppDomain *pAppDomain, ICorDebugThread *pThread, ICorDebugStepper *pStepper, CorDebugStepReason reason){  ICorDebugEval *eval;  bool stepAgain = false;
  // Create our eval instance  if (pThread->CreateEval(&eval) != S_OK)  {    stepAgain = true;  }
  // Request a new string is created within the .NET process  if (eval->NewString(L"C:\\test.dll") != S_OK)  {    // If we land here, chances are we aren't in a GC safe point, so we need     // to step again until we are    stepAgain = true;  }
  // If we were unable to create our string, we continue stepping until we can  if (stepAgain) {    pStepper->Step(0);  } else {  // If we were successful, we stop our stepper as we no longer require it    pStepper->Deactivate();  }
  // Continue our targets execution  pAppDomain->Continue(false);  return S_OK;}


在这里，我们只是尝试System.String使用ICorDebugEval::NewString在目标进程中创建.NET对象。如果成功完成，就可以确保我们处于GC安全点，然后停止单步执行代码，而只要知道评估代码可以工作就能继续安全地执行应用程序。如果无法创建字符串，可以继续单步执行并重试。


一旦能够成功执行ICorDebugEval::NewString，接下来便是等待调试器触发一个事件，该事件表明我们的评估已完成。这可以过API调用ManagedCallback::EvalComplete回调程序来完成。在此，我们检索对创建字符串的引用：

04

分离


现在我们已经注入了代码，可以选择在执行恶意命令时将其捆绑在目标进程上，或者分离调试器，让目标继续自己执行（希望我们的有效载荷在内部运行）。


分离只是一个调用问题：


debug->Detach();


但是，如果要分离目标，并让在其在继续执行的情况下不被杀，则需要满足许多条件。我们需要做到：


  1. 停止当前连接到线程的所有步进器。

  2. 我们所有的代码评估都需要完成。

  3. 我们必须处于同步状态，可以通过调用ICorDebug::Stop，或处于回调事件处理程序中。


第1、3点非常容易实现，但是我想说下第2点。以一个非常简单的.NET方法为例，该方法要在目标中执行：


namespace Injected {  class Injected {    public static void Entry() {      while(true) {        Console.WriteLine("I'm in...");        Thread.Sleep(2000);      }    }  }}


然后我们通过以下方式请求执行此代码：


pEval->CallFunction(function, 0, NULL);


这时会发现我们无法完全脱离进程。因为没有满足第2点要求，代码评估永远不会返回，所有EvalComplete永远不会发生回调。这意味着任何分离尝试都会遇到CORDBG_E_DETACH_FAILED_OUTSTANDING_EVALS错误。


因此，我们要始终确保初始代码执行返回，并且在尝试分离之前处理回调。下面，我们来看一些典型目标的示例，以及如何使用它们执行一些常见的后渗透工具。

标准注入



为了在运行的进程中执行我们的代码，我们需要找到一个不会停滞的目标。我们需要一些非常活跃的东西，来即时编译代码。


一个可用的进程是eventvwr.exe，它实际上是mmc.exe在加载.NET运行时产生的，该进程在后台处理事件，所以它成为这类技术的理想目标。


那么我们如何才能在这个进程中执行.NET方法呢？首先让我们生成事件查看器，以便我们可以用一些东西：

生成和注入



所以，我们已经了解如何注入现有进程，设计有效载荷来触发特定应用程序状态允许注入。但是，如果我们只是想立即生成并注入新进程以迁移我们的恶意代码，完全可以通过使用ICorDebug公开的CreateProcessW来实现：


debug->CreateProcessW(    L"C:\\\\Windows\\\\Microsoft.NET\\\\Framework64\\\\v4.0.30319\\\\AddInUtil.exe",    NULL,    NULL,    NULL,    false,    CREATE_NEW_CONSOLE,    NULL,    NULL,    &si,    &pi,    (CorDebugCreateProcessFlags)0,&this->process);


通过新的父进程或缓解策略，你可以用自己知道和喜欢的相同参数来做调整。这也使我们的安全点搜寻变得轻松多了，因为我们知道，在进程生成时，即时编译器会拼命运行，从而使我们有足够的时间来达到GC安全点。


现在，在新的.NET进程中，想要调用任意.NET方法时，需要考虑一些因素，这些因素主要是应用程序在有效载荷运行时执行的时间长度。毕竟，如果目标只是打印一些help并退出，则注入有效载荷并没有多大用处。


避免此限制的一种方法是制作.NET有效负载来生成其他托管线程。由于.NET支持后台和前台托管线程的代码，即使Main()函数返回，生成的前台线程也会阻碍目标的退出，然后可以继续运行注入的代码。


例如，下面时一个非常简单的有效负载：


namespace Injected {  class Injected {    public static void ThreadEntry() {      while(True) {        Console.WriteLine("Injected... we're in!");        Thread.Sleep(1000);      }    }
    public static void Entry() {      var thread = new System.Threading.Thread(new ThreadStart(ThreadEntry));      thread.Start();     }  }}

提高成功的几率



在前面的示例中，我演示了该技术在正确的情况下的实用性，以及在不进行任何CLR massaging的情况下可以应用在哪些地方。但是，值得注意的是，有一些事情可能会破坏我们的生活，其中最主要的是ngen（或本地映像），它们是pre-JIT'ed预编译的二进制文件，已加载到.NET进程中，目的是加快执行速度。当我们遇到这个问题时，显然要达到可以评估所需的JIT编译代码的程度，尝试注入会变得非常困难。然后还有.NET优化过程，这将再次减少我们在某些过程中找到GC安全点的机会。


那么有什么办法可以避免这种情况？事实证明，使用COMPlus环境变量的功能就可以了。具体来说，有两种设置会增加我们在进程中实现执行的几率...COMPlus_JITMinOpts和COMPlus_ZapDisable。事实上，与x64相比，x86进程似乎更需要这些设置。

因此，现在我们有了一个思路，即如何使用API调试器在.NET进程中执行任意方法，我们需要考虑所有后台发生的事件，以及防御者如何着手检测其使用情况。我不会深入了解Windows的调试子系统，因为已经有一系列文档记录调试用户模式的内部。下面，让我们看一些对检测有用的特定区域。


首先是流程之间的交互，例如，调试框架在附加到目标时会调用哪些值得注意的API？当然，与大多数注入方法一样，WriteProcessMemory在整个调试会话中都会大量使用它来修改目标过程。

ntdll!NtCreateThreadEx的调用负责在远程进程中创建线程。用于此远程线程的入口点ntdll!DbgUiRemoteBreakin仅用于触发一个断点，来挂起目标并向我们的调试器发出事件。当然，这意味着基于传统分配的内存入口点来寻找注入的线程是行不通的，因为线程的初始地址是ntdll函数的地址，但是对特定的DbgUiRemoteBreakin调用，是以某种形式操纵目标的好兆头。
