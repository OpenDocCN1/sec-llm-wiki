# 1        研究背景

西门子PLC有多个系列，其中S7-200/300/400全部采用了S7Comm私有协议进行通信，而S7-1200/1500则是使用了私有协议S7Comm-plus进行通信.本文主要基于S7-400系列对S7Comm协议的数据包进行研究和攻击。通过对S7Comm协议的数据包进行抓取，学习和分析S7Comm协议的结构，通过对协议结构的了解，构造指令数据包对PLC设备进行远程攻击。在进行数据包分析和攻击之前，对PLC硬件进行组态是必不可少的，下面先进行硬件组态连接到PLC，完成PLC的联机环境配置。

# 3        S7Comm协议分析

## 3.1       S7协议结构

S7Comm以太网协议基于OSI模型：

| OSI layer || Protocol |
| --- | --- |
| 7 Application Layer || S7 communication |
| 6 Presentation Layer || S7 communication (COTP) |
| 5 Session Layer || S7 communication (TPKT) |
| 4 Transport Layer || ISO-on-TCP (RFC 1006) |
| 3 Network Layer || IP |
| 2 Data Link Layer || Ethernet |
| 1 Physical Layer || Ethernet |

其中，第1-4层会由计算机自己完成（底层驱动程序）第5层TPKT，应用层数据传输协议，介于TCP和COTP协议之间。这是一个传输服务协议，主要用来在COTP和TCP之间建立桥梁；第6层COTP，按照维基百科的解释，COTP 是 OSI 7层协议定义的位于TCP之上的协议。COTP 以“Packet”为基本单位来传输数据，这样接收方会得到与发送方具有相同边界的数据；第7层，S7 communication，这一层和用户数据相关，对PLC数据的读取报文在这里完成。可能会对TPKT和COPT迷惑，其实在具体的报文中，TPKT的作用是包含用户协议（5~7层）的数据长度（字节数）；COTP的作用是定义了数据传输的基本单位（在S7Comm中 PDU TYPE：DT data）。  
![](../Images/ab2485a7e273738106f7cfca7d8fc14d.png)  

## 3.2       TPKT协议

![](../Images/53ba914a095472e5dd8bbb5833a1a11d.png)

TPKT协议占用4个字节，只要的作用是记录S7协议payload的总长度

Version(1个字节)：版本号

Reserved(1个字节)：保留

Length(2个字节)：TPKT、COTP、S7三层协议的总长度  

  

## 3.3       COTP协议

COTP协议分为两种形态，分别是COTP连接包（COTP Connection Packet）和COTP功能包（COTP Fuction Packet）。  
  

### 3.3.1        COTP连接包

COTP连接包（COTPConnection Packet）也就是S7Comm的握手包  
  

### 3.3.2        COTP功能包

![](../Images/6125bcb34c31965fc14417dcbc52d4e5.png)  

结构如下：

Length(占1个字节):COTP数据包的长度（不包含Length本身的长度）,一般为2 bytesPDU Type(占1个字节):0×1: ED Expedited Data，加急数据  
0×2:EA Expedited Data Acknowledgement，加急数据确认  
0×4:UD，用户数据  
0×5:RJ Reject，拒绝  
0×6:AK Data Acknowledgement，数据确认  
0×7:ER TPDU Error，TPDU错误  
0×8:DR Disconnect Request，断开请求  
0xC:DC Disconnect Confirm，断开确认  
0xD:CC Connect Confirm，连接确认  
0xE:CR Connect Request，连接请求  
0xF:DT Data，数据传输opt(占1个字节):最高位1表示YES，否则是NO，是Bool类型  

  

## 3.4       S7Communication协议

S7Comm协议包含三部分，根据实现的功能不同，S7 comm协议的结构会有所不同：•            Header•            Parameter•            Data

  ![](../Images/5a68b28aa39d4fdcd827c18230af3505.png)

  

首先来看Header部分![](../Images/1eab2e17c5236340584e85c7c3919c80.png)ProtocolId(占1个字节):协议ID，通常为0×32；ROSCTR(占1个字节):PDU的类型，它决定了后续参数的结构，一般有以下值：         0×01 – JOB：作业请求。由主设备发送的请求（例如，读/写存储器，读/写块，启动/停止设备，设置通信）；  
           0×02 – ACK：确认响应，没有数据的简单确认；  
           0×03 – ACK\_DATA：确认数据响应，一般是响应JOB的请求；  
         0×07 – USERDATA：原始协议的扩展，参数字段包含请求/响应ID（用于编程/调试，读取SZL，安全功能，时间设置，循环读取等等）。Reserved(占2个字节):冗余数据，通常为0×0000Protocol Data Unit Reference(占2个字节):协议数据单元参考，通过请求事件增加Parameter length(占2个字节):参数的总长度Data length(占2个字节):数据长度 S7Comm的Parameter和Data部分会因PDU类型不同而不同，所以接下来的内容将根据PDU类型的不同进行分别讲解。  

  

### 3.4.1        PDU类型为JOB的协议结构

S7Communication协议的Header中的ROSCTR，也就是PDU类型为JOB时，并且Parameter的Function为0x1a为下载功能，比如下载块等，我们就以下载块时抓取到的数据包作为学习样本

![](../Images/2bc93e4ef73ef296f276eeef392563f7.png) 

在西门子设备中有8种不同类型的功能块，这些块在上传/下载请求中用特殊的ASCII文件名寻址。这个文件名的结构如下：![](../Images/20871954ef7382fe62eb6f7e64e0c2ed.png)文件标识符(占1个字节)：有\_ 、$ 两种文件标识符；块类型(占2个字节)块编号(占5个字节)目标的文件系统(占1个字节)：文件系统有三种：•            P：被动文件系统•            A：主动文件系统•            B：既主既被文件系统 下载有3中不同的功能类型：•            请求下载（Request download\[0x1A\]）•            下载块（Download block\[0x1B\]）•            下载结束（Download ended\[0x1C\]）在下载过程中，先是Step7向PLC发送一个请求下载的Job，PLC收到后则回复一个Ack\_Data，然后PLC会发请求下载数据，此时请求里是没有数据的，Step7收到后开始下载数据到PLC，此时数据在数据包中开始下发，在发送完所有字节后，PLC发送一个下载完毕的请求，Step7回应，下载结束。 ![](../Images/2f71bcdbc131c063a2d389540d984c5c.png)

上图中的Download block Ack\_Data响应包包含了下载数据

![](../Images/1a77df52709858b435f16344c760c1fb.png)

### 3.4.3        PDU类型为UserData的协议结构

![](../Images/62c4406ab2eb6d407c5dd27b4282e6de.png) 

Parameter Header(占3个字节)：参数头Parameter length(占1个字节)：参数长度Method(Request/Response)(占1个字节)：请求方式Type(占半个字节，高位)：参数类型Function group(占半个字节，低位)：功能组Subfunction(占1个字节)：子功能码Sequence number(占1个字节)：序号Data unit reference number(占1个字节)：数据单元引用序号Last data unit(占1个字节)：最后的数据单元，bool值Error code(占2个字节)：错误类型
