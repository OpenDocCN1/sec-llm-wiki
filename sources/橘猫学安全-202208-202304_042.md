# **姿势1:CSRF Token Tracker**

CSRF Token Tracker是个插件,可以在BApp Store下载安装

![](../Images/b32a0fc46f47068b9c0447d2332647ad.png)

  

这种方式可以说是**最简单的**,但是不适用姿势2和姿势3中的案例

现有一个请求参数是user\_token  

![](../Images/90ae2fe7701dbda1771c6afab19b3b47.png)

只需要在插件中添加  

![](../Images/3f3f5ba767056f23294fc330cc54e0e1.png)

**注意这里有个坑(搞了好久)**

比如你想在repeater模块测试一下重新发送请求会不会修改密码  

![](../Images/a821e63958140403b18a39c03011a6c9.png)

发现返回的结果仍然是302

这里是需要有一个有效的,没有使用过的user\_token去请求的!

然后再去重放请求包就都会自动更新token了

总结一句就是你第一次用有效的token重放请求包就永远有效(自动更新token了)

你第一次用无效的token重放请求包就永远无效

# 姿势3:宏+Extractor

  

**在****这个案例中****前两种姿势均无效**

下载安装插件

![](../Images/3f775fe4cb4beb86bd4c2c9a0ccfc916.png)

先看下两个请求包  
第一个请求包就是获取token的

![](../Images/d01fbc81850e02176b465a8af781d8a5.png)

第二个就是带着token去访问

![](../Images/7595d0c4c0582b2745996b4e2fd04f67.png)  

看过这两个请求包应该就明白了  

这次token是在请求头中

而定义宏的时候会让你选择更新token的地方

这个地方却没有更新请求头的功能

所以姿势2在这里就失效了  

![](../Images/a05d9e078aecc5516ee98e323e7de7b0.png)

首先定义宏获取token

这个宏只需要要确保在请求2之前会执行请求1

相比于姿势2的步骤简单一点

![](../Images/f6be2f6b361a9605cea5628bc1e24be0.png)

![](../Images/9f11a48b02b74cb882ca5e57d16db2e9.png)

![](../Images/c3ac9a89ab97f5ecfa6c29cf829a8a96.png)

到这里宏就配置好了  

在repeater重放请求2然后再logger+=里面查看

确保每次都会在请求2前自动执行请求1就是正常的

![](../Images/23ee15e0763e209c7362b26464656228.png)

然后配置插件Extractor

把两个请求包都发送到Extractor

![](../Images/0ed0ebe41c64da8a8aff9a32b4613258.png)

  

![](../Images/874d60cc26861f5e304e8f7f7e0e74f9.png)

![](../Images/d7daf202fd73765355106484d6886b92.png)

  

此时回到repeater模块重放发现token就有效了

![](../Images/610f329cc7711234b16f964b4345156b.png)

再次回到logger++看发生了什么

看到第87个请求获取的token值为

407667d008b147199d174681a655aea0

![](../Images/a8fd9e8dc95aa93c68637a343130965b.png)

第88个请求包的accessToken值也是407667d008b147199d174681a655aea0

![](../Images/11108f5e1fe539025a6e9532af6eeaec.png)

总结一下姿势3的思路

**宏负责在请求2前发送请求1**

**Extractor插件负责匹配和替换token**
