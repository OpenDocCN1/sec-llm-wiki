0x03

形成漏洞的点也在这两个函数的操作上,
      write函数中
$data = str_replace(chr(0) . '*' . chr(0), '\0\0\0', $data);

read函数中

$result = str_replace('\0\0\0', chr(0) . '*' . chr(0), $result);
在数据进入write函数入库前,会将chr(0).'*'.chr(0)替换为\0\0\0,这是因为mysql数据库是无法处理NULL字节的,而类中的protected修饰的字段经过序列化处理后是*即chr(0).'*'.chr(0),替换完之后存入数据库,等从数据库取出即执行read操作的时候,再将还原成chr(0).'*'.chr(0),防止无法正常反序列化。即
chr(0).'*'.chr(0)-->\0\0\0-->chr(0).'*'.chr(0),
而在php的序列化机制中,PHP在序列化数据的过程中，如果序列化的字段是一个字符串，那么将会保留该字符串的长度，然后将长度写入到序列化之后的数据，反序列化的时候按照长度进行读取。举个例子: username=admin在序列化后
{s:8:"username";s:5:"admin";s:8:"password"}
反序列化的时候会按照长度进行读取,例如 按照5的长度去读admin这五个字符,但是如果经过一波操作把admin变成ad两个字符,在反序列化的时候会自动按照长度去读, ";s 这三个字符也会被读进去。再看上面的write和read操作,在序列化入库的时候是 长度为6个字符,经过替换后为chr(0) . '*' . chr(0)这是三个字符,这样在反序列化的时候,因为长度还是6,会继续往后读三个字符。


测试代码

POP链简析

根据payload和CVE-2015-8562的分析文章了解到是利用了JDatabaseDriverMysqli和SimplePie类,在

libraries/joomla/database/driver/mysqli.php
public function __destruct(){        $this->disconnect();    }

不管中间如何执行，最后都将会调用__destruct，__destruct将会调用disconnect函数继续跟进disconnect函数。

public function disconnect(){    // Close the connection.    if ($this->connection)    {        foreach ($this->disconnectHandlers as $h)        {            call_user_func_array($h, array( &$this));        }        mysqli_close($this->connection);    }    $this->connection = null;}
call_user_func_array回调函数是可以构造一句话后门的。但这里第二个参数无法控制,跟前段时间thinkphp中反序列化pop链是一样的。
call_user_func_array([$obj,"任意方法"],array( &$this))
在libraries/simplepie/simplepie.php可以找到满足构造pop链的点。

       关键代码如下:

$cache = call_user_func(array($this->cache_class, 'create'), $this->cache_location, call_user_func($this->cache_name_function, $this->feed_url), 'spc');
