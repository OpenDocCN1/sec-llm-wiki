# **4  计划：安全信息和事件管理**

# **4.2 警报关联**

警报关联，旨在理解SIEM平台收到的警报流。这种相关性有几个目标;

1.     通过将警报分组在一起来减少分析师必须处理的警报数，

2.     添加上下文元素，以便更准确、更快速地分析警报组，

3.     将警报添加到正在进行的更高级别的规划和缓解元素中，以便正确处理它们，以及

4.     以丢弃被视为误报且不需要进一步处理的警报。为了实现这些目标，警报关联可以采取多种形式：

警报之间的关联第一种警报关联旨在将来自一个或多个传感器的警报s组合在一起，这些警报对应于同一威胁。IDPS传感器往往具有数据流的狭窄视图。如果事件在跟踪中反复发生（例如，当恶意软件传播时），则会向SIEM报告多个警报。对对应于相同现象的警报进行分组有助于分析人员识别它并判断其重要性。

警报与环境之间的相关性另一个重要的知识来源与检测的上下文有关，即传感器所在的环境。有关环境的信息来自许多来源，其中两个最有趣的来源是网络清单和漏洞扫描。这两个来源确定了活跃资产及其可能遭受的风险。这种类型的关联特别有趣，因为它为分析师提供了有关警报所产生的影响的信息。

警报与外部来源之间的相关性最近，态势感知已开始提供有关攻击者及其动机的信息。这再次提供了有关攻击者可能遵循的路径的其他信息，并帮助分析人员主动决定阻止攻击者的进度，而不是在事件发生后做出反应。

事件和信息交换另一个相关趋势是信息交换。通过监管压力，关键基础设施运营商被要求在成为网络安全漏洞的受害者时通知当局。长期以来，银行和信用合作社的情况一直如此。共享有关违规行为的信息有助于同一域中的其他人或使用类似技术主动保护自己。

警报关联的最初方法是基于规则。基于规则的关联显式描述警报之间的逻辑关系，或推断此类关系的规则。多年来，研究界已经使用了各种语言和技术，从而产生了详尽而正式的模型。这导致了第一代SIEM平台的开发，该平台将结构强大的高性能SQL数据库与解释规则的逻辑引擎相结合。第一代遇到了两个问题，一是随着警报量的增加而提高性能，另一个是创建和维护规则库的难度。SQL数据库会对索引进行严重性能损失。这有利于查询，而SIEM平台是插入密集型工具。

尽管性能提高和数据库调整，但已经开发了第二代SIEM平台，利用NoSQL等结构较少的数据库技术。这种大数据或数据密集型方法很早就开始使用计数器，统计模型或其他技术。从技术上讲，这种方法是通过日志聚合和汇总查询来实现的，就像众所周知的ElasticSearch-Kibana-Logstash（ELK）堆栈一样。这种面向数据的方法在今天已经变得非常普遍，因为它能够处理大量传入的非结构化信息。缺乏关系结构是否不会导致不一致和命名混乱，影响分析师诊断和缓解威胁的能力，以及关注数量是否不能阻止处理罕见的攻击现象，如APT。.安全操作和基准测试

出于多种原因，需要测量SOC的活性。首先，SOC是技术平台，信息，流程和技术人员的组合。因此，很难确定特定SOC在哪些方面表现良好，以及哪些方面应该得到改进。由于SOC有时外包给MSSP，因此安全服务级别协议必须在客户和服务提供商之间协商，并由客户进行验证。客户还可能受到法规的约束，作为其合同的一部分，服务提供商必须满足这些法规。因此，有必要以一种能够进行测量，行业间比较和现有技术的方式来衡量SOC的活动，并决定应该改进哪些活动领域。

ETSI的信息安全指标（ISI）行业规范小组为此开发了籼稻。这些指标是共识方法的产物，其中几个行业领导者（泰雷兹，空中客车），用户（银行，电信公司）和技术提供商（ESI集团，Bertin）共同定义和测试了这些指标。该方法是欧洲范围的，因为ETSIISI小组得到了来自法国，德国和意大利的成员以及欧洲R2GS分会网络的支持（除了国家之外）在ETSIISI，英国，卢森堡-布尔格，比利时，荷兰）。最后，这些指标应该能够比较衡量SOC绩效，并对任何给定组织对网络，物理或组织威胁的抵抗力进行一般衡量。

ISI规范可从ETSI免费获得，参考信息图表可从多个来源获得。这种方法的主要困难是能够自动生成指标，或者至少是指标的子集，因为有些指标的水平非常高。
