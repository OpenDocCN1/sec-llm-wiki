# 介绍

本文的目的是说明安全供应链消费框架 (S2C2F) 的核心概念，以概述和定义如何将 OSS 依赖项（例如 NuGet 和 NPM）安全地消费到开发人员的工作流程中。开源软件，采用自由软件定义，是确保最终用户可以自由使用、学习、共享和修改该软件的软件。有关开源软件 (OSS) 定义的更多详细信息，请参阅开源定义. 此框架适用于开发人员工作流程中消耗的 OSS 依赖项，例如任何源代码、语言包、模块、组件、容器、库或二进制文件。本指南提供了一个专门的框架来增强任何组织的 OSS 治理计划，以解决特定于 OSS 消费的供应链威胁。

OSS 已成为任何软件供应链的一个关键方面。在整个软件行业，开发人员正在使用并依赖 OSS 组件来加快开发人员的工作效率和创新。然而，攻击者正试图滥用这些包管理器生态系统来分发他们自己的恶意组件，或破坏现有的 OSS 组件。

本文分为两部分：一组解决方案竞争性实践和基于成熟度模型的实施指南。实践部分应由首席信息安全官 (CISO) 和安全、工程、合规/风险经理等个人使用，而实施指南应由软件开发人员和其他安全从业人员使用。

关于安全供应链消费框架

安全供应链消费框架 (S2C2F) 是一种安全保障和风险降低流程，专注于保护开发人员使用开源软件的方式。自 2019 年以来，作为 Microsoft 范围内的一项计划，S2C2F 在整个开发人员内环和外环流程中提供安全指南和工具，这些流程在通过 Microsoft 开源软件消费来防御和防止供应链攻击方面发挥了关键作用。使用基于威胁的风险降低方法，S2C2F 的目标是：

1.  提供强大的OSS治理方案
    
2.  改进解决 OSS 中已知漏洞的平均修复时间 (MTTR)
    
3.  防止使用受损和恶意的 OSS 包
    

S2C2F（在本文档后面描述）以三个核心概念为模型——*控制所有工件输入、持续过程改进和规模。*

![](../Images/712e5d5a30d22abda416fc94a76acdec.png)

*   *控制所有工件输入*：如今，开发人员使用 OSS 的方式有无数种：git clone、wget、复制和粘贴源代码、将二进制文件签入存储库、直接从公共包管理器获取、将 OSS 重新打包为 .zip、 curl、apt-get、git 子模块等。如果开发团队不遵循使用 OSS 的统一流程，那么在任何组织中保护 OSS 供应链几乎是不可能的。实施有效的安全 OSS 供应链战略需要在整个组织的各个开发团队中标准化 OSS 使用流程，以便所有开发人员使用受监管的工作流程使用 OSS。
    
*   *持续流程改进*：为了帮助指导组织持续改进流程，我们将 S2C2F 组织成一个成熟度模型。这有助于组织确定他们应该首先实施的要求的优先级。由于安全风险是动态的，新威胁随时可能出现，因此 S2C2F 非常重视了解 OSS 供应链面临的新威胁，并*要求*定期评估 S2C2F 控制并引入变化以应对新技术进步或新威胁。
    
*   *规模*：S2C2F 工具在设计时就考虑到了规模。一些组织可能会尝试通过组织内所有开发人员都应该从中提取的中央内部注册表来保护其 OSS 摄取过程。但是，如果一位开发人员选择直接从 pypi.org 或 npmjs.com 拉取内容怎么办？有什么能阻止他们这样做吗？中央内部注册表还存在需要团队管理流程和工作流的问题，这是额外的开销。因此，开发 S2C2F 工具是为了保护他们如今大规模使用 OSS 的方式，而不需要中央内部注册表或中央治理机构。
    

# 什么是安全供应链消费框架？

S2C2F 框架是任何组织都可以采用的要求和工具的组合。该框架包括一个能力成熟度路线图，以帮助建立一个安全的 OSS 摄取过程，以保护开发人员免受 OSS 供应链威胁，并建立一个强大的治理计划来管理您的组织对 OSS 的使用。

# 安全供应链消费框架实践

## 目标听众

本节是一个解决方案竞争性描述，说明应该实施什么来保护您组织的 OSS 供应链。该指南对合规/风险经理、安全经理、工程经理和首席信息安全官 (CISO) 很有用。

## 安全供应链消费框架实践

### *练习 1：摄取它*

*如果外部 OSS 源受到损害或不可用，我可以运送任何现有资产。*

此作业解决的示例威胁场景：

*   Docker Hub 存储库遭到破坏
    
*   一个团队可能成为依赖混淆攻击的目标
    
*   Azure 本身不可用，我们需要访问 OSS 资产来恢复它
    
*   包变得永久不可用（即 left-pad 被删除）
    

确保软件供应链安全的第一步是确保您控制所有工件输入。为了满足这种做法，有两种摄取机制：一种用于打包工件，一种用于源代码工件。

对于打包的工件，我们需要摄取到工件存储库——Linux 包存储库、工件存储库、OCI 注册表——以完全支持*上游源*，它透明地从工件存储代理到外部源，并保存从该源使用的所有内容的副本。当混合使用内部和外部打包工件时，保护您的包源文件配置以保护您自己免受依赖混淆攻击 ( CVE-2021-24105 ) 非常重要。

对于源代码工件，我们需要将外部源代码存储库镜像到内部位置。除了在本地缓存包之外，镜像源也很有用，原因有很多：

*   业务连续性和灾难恢复 (BCDR) 目的，以便您的组织可以在从上游删除关键依赖项时获得代码的所有权
    
*   启用主动安全扫描以查找后门和零日漏洞
    

*   使您的组织能够向上游贡献修复
    

*   使您的组织能够在需要时执行修复（在极端情况下）
    

### *练习 2：扫描它*

*我知道我的管道中是否有任何 OSS 工件存在漏洞或恶意软件。*

此作业解决的示例威胁场景：

*   某团队尝试使用存在已知漏洞的OSS包
    
*   一个团队已经在使用一个被认为是安全的 OSS 包，但该包中的一个新漏洞后来被公开披露
    
*   一个团队试图使用已知的 OSS 包来窃取比特币（即*事件流*场景）
    
*   一个团队试图使用带有后门的 OSS 包
    

一旦我们控制了所有工件输入，我们必须扫描所有输入以信任它们。这种信任是使用查找漏洞、恶意软件、恶意或异常行为、无关代码和其他已知或以前未发现的问题（即零日漏洞）的扫描器建立的。

### *实践 3：盘点它*

*我知道 OSS 工件在生产中的部署位置。*

此作业解决的示例威胁场景：

*   在 log4j 中发现了一个严重漏洞，事件响应团队想知道所有使用 log4j 的生产服务，以便他们可以适当地配备人员并协调响应工作
    

一旦我们摄取并扫描了进入软件供应链的工件，我们必须确保我们有一个清单，其中每个工件被使用，通过了解它部署在哪些服务中以及它在哪些产品中发布。这是事件响应场景所必需的，以便可以联系受受损包影响的团队，以便采取适当的措施来删除受影响的包。

### *实践 4：更新它*

*我可以在更新公开可用后立即部署更新的外部工件。*

此作业解决的示例威胁场景：

*   一个团队目前正在使用三个不同的易受攻击的 NuGet 包，升级每个包对团队来说将是一项大量的工作。该团队选择从升级部署最广泛的包开始。
    

一旦我们摄取、扫描和清点了每个工件的使用位置，我们就可以让开发人员通过了解发布需要修复的产品/服务的供应链流程来*解决*已经使用的工件的问题。

考虑到SaltStack 事件，其中一个漏洞在公告后 3 天内被利用，每个组织都应该渴望在 72 小时内修补易受攻击的 OSS 包，以便您修补的速度比对手运行的速度快。使用 Dependabot 等工具自动生成合并请求 (PR) 来更新易受攻击的 OSS 成为保护供应链的关键功能。

### *实践 5：审计*

*我可以证明，生产中的每个 OSS 工件都有来自原始工件来源的完整监管链，并通过官方供应链进行消费。*

此作业解决的示例威胁场景：

*   一个善意但被误导的开发人员绕过官方工程管道直接在版本中更新 OSS 包；然而，这个新版本包含一个已知的漏洞
    
*   具有网络访问权限的攻击者故意绕过官方工程管道将恶意软件部署到服务中
    

既然我们已经摄取、扫描、清点并提供了正确更新通过软件供应链产生的任何工件的能力，您必须在您的组织内具有审计 OSS 消耗的能力，以查看它是否来自标准化的消耗工具（例如包存储库解决方案）由您的组织建立。

### *实践 6：强制执行*

*我可以依靠我的组织内安全和可信的 OSS 使用。*

此作业解决的示例威胁场景：

*   开发者绕过官方工程流水线使用存在已知漏洞的OSS包
    

所有 OSS 工件都必须从可信来源和官方 OSS 消费渠道消费。下一步是启用供应链的实施，以便以任何方式影响生产服务/发布的所有工件都必须通过完整的供应链。强制执行的一个示例是重新路由 DNS 流量或将构建配置为在尝试使用来自不受信任来源的 OSS 时中断。

### *实践 7：重建它*

*我可以从源代码重建我正在部署的每个 OSS 工件。*

此作业解决的示例威胁场景：

*   团队使用带有隐藏后门的恶意 OSS 包（这可能通过传统剥削、政治影响、勒索甚至暴力威胁发生）；结果，包的二进制文件与其源代码不匹配。
    
*   攻击者获得构建基础设施的权限并在构建过程中修改生成的二进制文件；因此，非法更改可以以其原始作者和用户基本上看不到的方式注入。
    

到目前为止，我们一直假设我们在供应链的开头按原样获取输入*：*作为作者提供的包裹、容器或其他运载工具。对于业务关键的关键工件和输入到高价值资产的所有工件，此假设可能不够充分。因此，确保供应链安全的下一步是*从原始源代码*为用于创建生产服务/发布的每个工件创建监管链。

基线 REBUILD IT 要求是使严重依赖某些 OSS 组件的开发人员能够摄取源代码（包括发现源代码，它并不总是链接到构建的工件），重建它（可能在此过程中开发构建脚本，如果它们不是源代码的一部分），进行任何构建后修改（例如签名），缓存重建的工件，并向组织中的其他团队公布内部重建版本的存在。另一种可能的方法是使用多个第三方来构建并就“正确的”工件（例如可复制构建）达成共识。

### *实践 8：修复 + 上游*

*我可以在收到危害通知后 3 天内私下修补、构建和部署任何外部工件，并秘密地将修复程序贡献给上游维护者。*

此作业解决的示例威胁场景：

*   一个团队依赖了一个包；后来发现该软件包存在严重漏洞，维护者需要帮助/更多时间来修复该问题
    

何时使用： *这仅用于极端情况和临时风险缓解。仅当上游维护者无法在您组织的风险承受能力可接受的时间内提供公共修复时，才应使用它。任何组织应该采取的第一个行动是秘密地向上游维护者报告漏洞并帮助提出修复建议*。

一旦我们可以重建软件供应链中使用的任何工件，最后一步就是能够私下修复它，同时秘密地向上游维护者披露漏洞。假设摄取源代码并重建工件的团队允许 PR 到他们的源代码的分支副本并适当地设置 CI 构建，那么任何需要私有修复组件的人都可以使用正常的 PR 工作流程。唯一需要做的额外工作是能够根据需要在组织内尽可能广泛地分发私有修复程序。

与下面的说明相关，已实施的修复程序应保密地贡献给上游维护者以回馈社区。

# 安全供应链消费框架实施指南

## 目标听众

本节详细介绍了一个成熟度模型，它将上一节中的实践拆分为 4 个级别来实现。还有一个工具列表，您的组织可以实施这些工具来满足框架中的每个安全级别。该指南对软件开发人员、持续集成和持续开发 (CI/CD) 管理员以及安全从业人员很有用。

## 安全供应链消费框架成熟度等级

首次开发 S2C2F 时，确保我们的 OSS 供应链安全的策略包括 8 个实践。

![](../Images/f28755852ba35f30d58dc692fd7777ba.png)

由于无法同时合理地实施所有 8 种实践，因此以下成熟度模型将 8 种实践中的每一种实践的要求组织为 4 个不同的级别。它允许组织从其现有的安全功能集向更安全的防御态势迈进。此外，成熟度模型在每个成熟度级别考虑不同的威胁和主题。

根据项目及其标准，您可能会跨项目实施混合框架级别。此外，与风险/回报相比，成熟度模型第 4 级的实施成本估计较高，因此应将其视为贵组织的理想北极星愿景。虽然很难在整个组织中大规模实施第 4 级，但在最关键项目的最关键依赖项上实施第 4 级是可行的。

  

![](../Images/02bd32f7351c3a7291b307deda53c6dc.png)

级别 1 – 使用包缓存解决方案、执行 OSS 清单以及扫描和更新 OSS 代表了当今软件行业最常见的 OSS 安全功能集。

级别 2 – 此成熟度级别侧重于通过提高摄取配置安全性、降低 MTTR 以修补 OSS 漏洞以及响应事件来进一步降低安全性。2020 年的 SaltStack 漏洞向我们表明，攻击者能够在 CVE-2020-11651 公布后的 3 天内开始利用它。即使有补丁可用，组织也无法足够快地修补他们的系统。因此，此级别的一个关键组件利用自动化来帮助开发人员保持其 OSS 健康和更新。理想的目标是组织能够比攻击者操作更快地打补丁。

级别 3 – 主动对组织最常用的 OSS 组件执行安全分析并降低使用恶意包的风险是此成熟度级别的主题。在下载包之前扫描 OSS 中的恶意软件是防止危害的关键。然后，要对 OSS 进行主动安全审查，需要组织可以将源代码克隆到内部位置。主动安全审查可帮助您寻找尚未发现的漏洞，以及识别其他威胁类别，例如检测后门。

第 4级——在大多数情况下，这个级别被认为是理想的。在受信任的构建基础设施上重建 OSS 是一个防御步骤，以确保 OSS 在构建时不被破坏。构建时攻击是由最老练的对手执行的，并且不会经常发生。因此，这种成熟度水平是抵御最复杂的对手所需要的。另外，重构OSS还有很多微妙的技术挑战，比如包起什么名字来防止和上游冲突？如何确保所有开发人员都使用内部包而不是外部包？重建还使您能够实施修复（如果需要）并在整个组织中大规模部署它们。

## 如何评估您的组织在成熟度模型中的位置？

任何成熟度评估都应在组织级别进行，以便评估来自不同开发团队的多个不同 OSS 消费流程。一些团队可能比其他团队拥有更成熟的流程，即使在一个组织内也是如此，因此最好执行全公司范围的评估以确定跨不同软件开发团队的 OSS 消费实践。执行成熟度评估的步骤如下：

1.  准备评估。第一步是了解 S2C2F 背后的概念，这样您就可以轻松地与开发人员和工程师打交道，询问他们现有的工具、功能和工作流程。接下来，确定来自整个公司的不同开发团队的良好样本量以进行面试。
    
2.  执行评估。您可以在此处评估组织在软件开发人员 OSS 管理、安全性和消费流程方面的成熟度。以下是您可以提出的一组示例问题：
    

1.  您在项目中使用什么类型的 OSS？（例如原生 C/C++、NuGet、PyPI、npm 等）
    
2.  您如何将 OSS 用于您的项目？（例如，使用 Azure Artifacts 等包缓存解决方案、curl 或 git clone 等命令、将 OSS 签入存储库等）
    
3.  您从哪里使用 OSS？（例如 NuGet.org、npmjs.com、pypi.org 等）
    
4.  您是否混合使用内部包和外部包？（*这会使您容易受到依赖性混淆攻击*）
    
5.  您的包源文件（例如 nuget.config、pom.xml、pip.conf 等）的配置中是否包含多个提要？（*这会使您容易受到依赖性混淆攻击*）
    
6.  您是否对您使用 OSS 的方式做了任何定制？（例如，使用项目的私有分支，将 Golang 组件放入 NuGet 等）
    
7.  您的项目是否使用包锁定文件？（例如，用于 NuGet 的 packages.lock.json、用于NPM的 package-lock.json等）
    
8.  您的团队如何清点项目中 OSS 的使用情况？使用什么工具？
    
9.  当 OSS 组件中存在漏洞时，您的团队如何知道？使用什么工具？
    
10.  OSS 漏洞在软件开发生命周期 (SDLC) 的什么时候出现？（例如发布后？构建期间？作为 PR 中的评论？）
     
11.  OSS更新以解决已知漏洞的速度有多快？（例如，平均修复时间是多少）
     
12.  更新 OSS 是手动还是自动过程？（例如使用 Dependabot）
     
13.  您是否对您的软件如何与您必须验证没有破坏性更改的依赖项进行接口进行集成测试？
     
14.  您是否在使用 OSS 之前扫描恶意软件？
     
15.  您的团队是否能够阻止摄入已知的不良/恶意软件包？
     
16.  您的团队是否在内部克隆开源代码？
     
17.  您的团队在使用之前是否对 OSS 进行过任何类型的安全审查或扫描？
     
18.  您的团队是否将错误修复回馈给上游 OSS 维护者？
     
19.  您是否在内部重建任何开源软件？
     
20.  您是否有事件响应计划或行动手册来应对使用恶意 OSS 组件的事件？
     

4.  改进计划。根据您从整个组织收到的采访和回答，您应该能够确定您在 S2C2F 成熟度级别中的位置。有些团队可能领先于其他团队，因此您的重点应该是将所有开发团队提升到特定的成熟度级别。建议您通过推动软件开发团队使用 OSS 的流程和工具标准化来实现这一目标。
    

S2C2F 将其需求分类为成熟度级别，以更好地帮助您确定改进投资的优先顺序。此外，S2C2F 建议使用具有特定功能的工具来缓解已知的供应链威胁，但您可能应该就哪一组工具适合您的业务和安全目标做出业务决策。
