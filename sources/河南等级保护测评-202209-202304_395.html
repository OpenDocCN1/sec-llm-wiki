云服务使世界成为一个高度互联的生态系统。企业利用其他企业提供的服务（虚拟和物理）而不是从头开始构建它们，从而创建连接设备、应用程序和用户的网络。API就是这样一种服务。

应用程序编程接口 (API) 允许连接不同的程序。例如，电子商务商店可以使用 PayPal API 来收款，而不是建立自己的支付网关。API 有用的原因显而易见——它们提供了必要的功能，同时节省了企业的时间和精力。

API 安全解决方案涉及保护这些 API 以及所有连接的应用程序和用户免受安全威胁和破坏。

本文涵盖了企业应立即实施的 20 个 API 安全提示。

为什么 API 安全很重要？ 

企业使用 API 连接应用程序和平台，连接到存储敏感用户信息的数据库。受损的 API 会迅速导致对连接的应用程序的攻击，更糟糕的是，用户数据的丢失或被盗。

API 安全是开发它的公司和使用它的公司的责任。

每个企业都应该实施的 20 个 API 安全提示 

1. 实施安全认证和授权协议

验证和授权正确的用户是 API 安全策略的第一步。访问点是第一个攻击点，攻击者试图利用 API 身份验证过程中的缺陷来获得对帐户的临时或永久访问权限。

有两种方法可以加强身份验证和授权安全性：

  1. 通过用户名和密码进行基本身份验证，需要复杂的密码

  2. 为每个连接的应用程序配置唯一标识符的 API 密钥的使用

  3. 使用 OAuth 登录

OAuth 可能是实现最大身份验证安全性的最佳方式之一。它为用户提供方便的 SSO，无需将用户名和密码发送到 API 服务器，防止凭据被钓鱼。

2. 使用“最小特权”原则 

在信息安全中，“最小权限”涉及让用户或应用程序仅访问他们正确执行其功能所需的数据和操作。

以下是在 API 中实现最小权限原则的几种方法：

  1. 开发 API 时牢记最小权限原则

  2. 执行定期访问审计并评估 API 调用以识别特权过高的应用程序（有权访问他们不需要访问的数据或操作的应用程序）

  3. 撤销特权应用程序对不必要数据和操作的权限

通过限制对必要操作的访问，减少了攻击面，这有助于限制安全漏洞的暴露。

3.限制数据共享  

最小化 API 漏洞的一种方法是最小化暴露。为了使产品工作，数据在 API、API 和应用程序以及 API 和用户之间共享。这可能是访问数据，如令牌、用户数据、JSON 代码等。

随着节点之间共享的数据量增加，风险敞口也增加。像 OAuth 这样的机制可以很好地抵御安全威胁——它将平台之间共享的数据减少为授权密钥而不是用户的凭据，因此在发生攻击的情况下，攻击者不会获得任何有用的信息。

跟踪应用程序、API 和用户之间共享的数据，以识别漏洞点，然后通过限制共享数据来保护它们。

4. 始终使用 HTTPS  

HTTP 连接不保护数据，并且可以被劫持以窃取信息。

另一方面，HTTPS 连接会加密大部分数据并有助于保护连接。HTTPS 连接保证了三件事：

  1. 真实性- 已与真实的 API 或应用程序建立连接，而不是冒名顶替者

  2. 机密 性——所有数据（元数据、cookie 等）都经过加密和安全

  3. 完整性 ——传输的数据是可信的，没有被修改或篡改

API 使用 HTTP 连接开始并需要安全套接字层 (SSL) 或传输层安全 (TLS) 加密来保护正在传输的数据。

5. 使用单向密码散列安全存储密码

确保 API 具有强大的密码存储策略对于最大限度地减少安全漏洞至关重要。

使用基本身份验证（用户名和密码）的 API 必须将此数据存储在数据库中。如果数据库被外部威胁入侵或被不良行为者内部访问，则用户凭据可能会被盗并用于访问个人帐户。

保护凭证的一种方法是在将密码提交到数据库之前对其进行哈希处理。

散列使用散列函数（如 SHA-1）将任意大小的输入字符串转换为固定大小的散列字符串。例如：

不同字符和长度的输入数据被转换为固定大小的散列键。

与具有可以从加密输出中提取原始数据的解密密钥的加密不同，散列函数的输出不能反转以获得原始数据。

当用户尝试登录时，API 将对输入的密码进行哈希处理，并将其与存储的哈希值进行匹配。仅当输入的密码相同时，哈希才会相同，这就是验证用户的方式。

如果数据库遭到破坏，攻击者获得的所有内容都是哈希字符串，无法通过逆向获取原始数据。

6. 执行零信任政策  

当涉及到 API 安全提示时，我们可以排除零信任策略。它假定每个用户、设备和服务器在被证明可信之前都是不受信任的。

传统的验证模型是信任一些基于预定义协议的连接，例如，由公司网络内的设备或之前访问过 API 的用户建立的连接。来自此预定义边界之外的任何连接都需要在访问数据之前进行身份验证和自我验证。

在零信任模型中，所有连接（绝对没有例外）在访问资源之前都被要求进行身份验证。这大大降低了安全风险。

7. 采用整体方法进行 API 安全测试

当谈到 API 安全提示时，采用整体方法进行测试是我们不能跳过的。假设任何可能出错的地方并测试 API 的各个方面是否存在安全漏洞。可以执行的一些测试是：

  1. 参数篡改——测试 API 之间发送的哪些 参数可以被篡改
  2. 命令注入 ——测试 API 是否容易受到代码注入的影响
  3. 输入模糊 测试——测试以检查 API 之间传递的数据是否可以修改
  4. HTTP 方法 ——测试是否有任何 URL 通过未加密的连接发送数据

8. 使用应用程序优先级桶

可以根据应用程序的优先级将应用程序分类到存储桶中——使用最多的应用程序、使用时间最长的应用程序、很少使用的应用程序等等。理想情况下，这些存储桶应该是动态的，应用程序应该根据最适合的存储桶自动从一个存储桶移动到另一个存储桶。

然后可以将不同的策略应用于每个存储桶，以改进 API 安全策略，而不会影响应用程序的性能。

9. 使用 TLS 加密数据

对 API 处理的所有数据进行加密是谨慎的做法，无论是个人身份信息 (PII) 还是正在传输的连接数据。加密数据不能被滥用，即使攻击者以某种方式窃取它。对传输中的数据进行加密的一种方法是将 TLS 与 REST/API 结合使用。

10. 持续审核 API 构建

有了技术，总有改进的余地。维护一个审核周期，定期审核 API 构建。测试攻击者可以利用的漏洞、错误和其他构建问题。始终维护审核日志以跟踪版本更新和错误修复。

11. 让供应商参与进来

每当推出更新或补丁时（通常是在审核之后），确保所有 API 用户都知道 并强调更新到最新版本的重要性。

使用 API，安全性不仅限于开发它的企业，还包括使用它的供应商。如果供应商的应用程序或服务器因 API 中的漏洞而受到攻击，供应商和 API 开发人员都有责任。

使用电子邮件、推送警报、应用内消息和其他形式的通信将补丁消息传递给所有供应商，并主动监控哪些供应商尚未更新其 API 版本。

12. 实施数据记录

我们的 API 安全提示列表中的下一个是数据记录。日志在解决问题和寻找解决方案、启用服务器和应用程序级别的日志记录方面非常有用。

为这些日志定义一个保留期，以便有足够的历史数据来识别违规事件发生很久之后，同时确保不超过存储空间。

日志有助于手动检查和监控，并为管理员提供大量可用于提高 API 安全性的信息。

13.设置API速率限制

API 限制或 API 速率限制是对客户端请求（或消耗）数据的数量或大小进行限制。

建立的连接数和请求的大小会影响 API 的性能。允许不受限制的访问可能会导致连接过多，这将导致 API 服务器滞后并最终崩溃，这发生在拒绝服务 (DoS) 攻击的情况下。在 DoS 攻击中，攻击者不断发送大量请求以使服务器过载和崩溃，从而拒绝为实际用户提供服务。

应用 API 速率限制有助于降低 API 崩溃的风险。管理员可以限制每个请求的请求数和事务数，以保持平衡和最佳性能。

14. 实施监控和警报软件

主动缓解安全威胁的另一种好方法是实施监控和警报软件（例如 SCOM）。这些平台监控 API 调用、日志和 API 的其他方面，以检测异常并提醒管理员，然后管理员可以采取预防性或反应性措施来应对安全威胁。

它还提供了更轻松地实施其他 API 安全提示的机会。

15. 遵循 OWASP API 安全指南

非营利基金会开放 Web 应用程序安全项目 (OWASP)在 2017 年列出了一套 10 条 API 安全指南。安全漏洞原因的优先级在 2021 年更新，它们如下：

  1. 访问控制损坏
  2. 密码失败
  3. 注射
  4. 不安全的设计
  5. 安全配置错误
  6. 易受攻击和过时的组件
  7. 识别和认证失败
  8. 软件和数据完整性故障
  9. 安全日志记录和监控故障
  10. 服务器端请求伪造

解决OWASP API Top 10中的每个潜在漏洞是处理 API 安全性的好方法，并且在开始时，此列表可以作为蓝图。

16. 执行内容协商

内容协商是一种通过同一 URL 动态提供数据和资源的方法。同一资源的不同版本（在语言、扩展名、格式等方面）根据某些预定义的标准交付给用户。

在 API 服务器中实施内容协商允许用户构建将内容协商留给 API 服务器的应用程序，从而减少安全漏洞的可能性。

17. 扫描每个 API 请求

API 请求容易受到网络钓鱼和篡改等攻击。例如，请求 URL 中的参数可以被篡改，以诱使 API 提供敏感的用户数据。

扫描每个 API 请求的异常情况将有助于减轻这种威胁。有一些可用的解决方案（例如 Fiddler）可以监控 API 请求并通过 UI 提供可操作的信息。

18. 定义数据处理安全措施

保护所有数据处理服务和操作对于 API 保护至关重要。这包括识别和验证用户、根据级别授权访问、记录和报告访问事件等。

创建定义数据处理操作的 API 指南将有助于实施每个操作的安全措施。

19. 清理输入

功能使用用户输入来访问数据库和检索信息，因此是一个安全漏洞。例如，代码注入是一种安全威胁，攻击者通过在 API 服务器上执行的输入字段传递代码。

减轻这种风险的一种方法是通过输入清理。输入清理是一种网络安全策略，用于检查、清理和过滤发送到 API 的不需要的字符和字符串的输入数据。这可以防止不良行为者注入恶意代码并破坏 API 服务器。

20. 实施 Web 应用程序和 API 保护 (WAAP)

如果没有 WAAP，API 安全提示列表将是不完整的。随着云服务的广泛使用，大多数企业使用至少一个托管在 Web 上的应用程序（而不是完整的本地基础设施）。Web 应用程序和连接的 API 可通过 Internet 访问，并且更容易受到攻击。

传统的物理 Web 应用程序防火墙 (WAF) 设备已不足以保护 Web 应用程序和 API。Web 应用程序和 API 保护(WAAP) 是一种专门用于保护 Web 应用程序和 API 的安全工具。

WAAP 解决了传统安全设备和协议中的缺陷，并提高了 Web 应用程序和 API 的安全性。

结论

随着技术和互联网的发展，安全是一项持续的努力。不幸的是，安全威胁不会不复存在，随着物联网等技术变得越来越普遍，漏洞和风险只会增加。

虽然安全漏洞令人恐惧，但可以采取措施防止它们并保护用户、设备和应用程序。关键在于积极主动——监控现有技术、修复漏洞并整合现代网络安全解决方案。
