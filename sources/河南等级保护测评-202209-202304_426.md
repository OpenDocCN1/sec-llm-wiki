# **渗透测试：前期交互阶段**

# **概述**

PTES这一部分的目的是介绍和解释可用的工具和技术，这些工具和技术有助于渗透测试的成功预参与步骤。本节中的信息是世界上一些最成功的渗透测试人员多年综合经验的结果。如果寻找渗透测试的客户，我们强烈建议您转到本文档的“一般问题”部分。它涵盖了测试开始前应回答的主要问题。请记住，渗透测试不应该是对抗性的。它不应该是一个查看测试人员是否可以“破解”你的活动。它应该是关于识别与攻击相关的业务风险。要获得最大价值，请确保涵盖本文档中的问题。此外，随着范围界定活动的进行，一家好的测试公司将开始为您的组织量身定制其他问题。

# **范围简介**

定义范围可以说是渗透测试中最重要的组成部分之一，但它也是最容易被忽视的组成部分之一。虽然已经写了很多关于可用于访问网络的不同工具和技术的书，但关于渗透之前的主题：准备的文章很少。忽视正确完成参与前的活动可能会使渗透测试人员（或他的公司）面临许多头痛，包括范围蔓延、客户不满意，甚至法律问题。项目的范围具体定义了要测试的内容。如何进行测试的每个方面将在参与规则部分中介绍。确定参与范围的一个关键组成部分是概述测试人员应该如何度过他们的时间。例如，客户要求以 100，000 美元的价格测试 100 个 IP 地址。这意味着客户为每个测试的 IP 地址提供 1，000 美元。但是，这种成本结构仅在该数量上仍然有效。一些测试人员陷入的一个常见陷阱是在整个测试过程中保持线性成本。如果客户只要求以相同的定价结构（1，000 美元）测试一个业务关键型应用程序，而测试人员仍然只攻击单个 IP，则工作量会急剧增加。根据完成的工作改变成本非常重要。否则，公司很容易发现自己的服务收费不足，这促使他们做一份不完整的工作。尽管有坚实的定价结构，但这个过程并不全是非黑即白的。客户完全不知道他们需要测试的确切内容的情况并不少见。客户也可能不知道如何有效地传达他们对测试的期望。在预接洽阶段，测试人员能够作为指导，了解客户可能未知的领域，这一点很重要。测试人员必须了解专注于具有严重强度的单个应用程序的测试与客户端提供各种 IP 地址进行测试并且目标只是找到一种方法的测试之间的区别。

# **时间估计指标**

时间估计与测试人员在某个领域的经验直接相关。如果测试人员在某个测试中具有丰富的经验，他可能天生就能够确定测试需要多长时间。如果测试人员在该领域的经验较少，重新阅读电子邮件并扫描公司以前进行的类似测试的日志是估计当前参与时间要求的好方法。一旦确定了测试时间，谨慎的做法是增加 20% 的时间。时间值后端的额外 20% 称为填充。在顾问圈子之外，这也称为顾问开销。填充对于任何测试都是绝对必要的。如果测试中发生任何中断，它提供了一个缓冲。有许多事件经常发生并阻碍测试过程。例如，网段可能会出现故障，或者可能会发现一个重大漏洞，这需要与许多级别的管理层进行多次会议才能解决。这两个事件都很耗时，如果填充不到位，则会显著影响原始时间估计。如果 20% 的填充最终变得没有必要，会发生什么情况？向客户收取未工作的时间费用将是非常不道德的，因此由测试人员提供额外的价值，如果达到参与时间限制，通常可能无法提供这些价值。示例包括引导公司安全团队完成利用漏洞的步骤，提供执行摘要（如果它不是原始可交付结果列表的一部分），或者花一些额外的时间尝试破解在初始测试期间难以捉摸的漏洞。时间和测试指标的另一个组成部分是每个项目都需要有一个明确的死亡日期。所有好的项目都有一个明确的开始和结束。如果您已到达测试结束的特定日期，或者如果在该日期之后要求您进行任何其他测试或工作，则需要签署一份签名的工作说明书，说明所需的工作和小时数。一些测试人员很难做到这一点，因为他们觉得在成本和时间方面他们太痛苦了。但是，作者的经验是，如果您为主要测试提供特殊价值，客户不会拒绝为您支付额外的工作费用。

# 范围界定会议

在许多情况下，范围界定会议将在合同签署后举行。确实存在许多与范围相关的主题可以在合同签署之前讨论的情况，但它们很少而且相距甚远。对于这些情况，建议在进行任何深入的范围界定讨论之前签署保密协议。范围界定会议的目标是讨论将要测试的内容。本次会议将不涉及接洽规则和费用。这些主题中的每一个都应该在会议中处理，其中每个部分都是该会议的重点。这样做是因为如果没有明确说明重点，讨论很容易变得混乱和混乱。重要的是充当主持人并保持讨论的主题，防止切线并在必要时宣布某些更适合离线讨论的主题。现在，已经为项目建立了粗略数量级（ROM）值，是时候与客户会面以验证假设了。首先，需要明确确定参与范围内的 IP 范围。客户端抵制并认为识别他们的网络并攻击它是测试人员的特权，以使测试尽可能逼真的情况并不少见。这确实是一个理想的情况，但是，必须首先考虑可能的法律后果。因此，测试人员有责任向客户传达这些问题，并向他们传授隐式范围的重要性。例如，在会议中，应验证客户是否拥有所有目标环境，包括：DNS 服务器、电子邮件服务器、运行其 Web 服务器的实际硬件及其防火墙/IDS/IPS 解决方案。有许多公司将这些设备的管理外包给第三方。此外，必须确定目标环境所在的国家、省和州。法律因地区而异，测试很可能会受到这些法律的影响。例如，众所周知，属于欧盟的国家对个人隐私有非常严格的法律，这可能会显着改变社会工程项目的执行方式。

# 基于小时费率的额外支持

任何未明确涵盖在参与范围内的事情都应非常谨慎地处理。造成这种情况的第一个原因是范围蔓延。随着范围的扩大，资源被消耗，削减了测试人员的利润，甚至可能给客户带来混乱和愤怒。还有另一个问题，许多测试人员在临时承担额外工作时没有想到：法律后果。许多临时请求没有正确记录，因此很难确定在发生争议或法律诉讼时谁说了什么。此外，合同是一份法律文件，规定了要完成的工作。它应该与测试备忘录的权限紧密相关。超出原始范围的任何请求都应以工作说明的形式记录下来，明确指出要完成的工作。我们还建议在合同中明确说明将以每小时固定费用完成额外工作，并明确说明在签署和会签的 SOW 到位之前无法完成额外的工作。

# 调查问卷

在与客户的初步沟通中，客户必须回答几个问题，以便正确估计参与范围。这些问题旨在更好地了解客户希望从渗透测试中获得什么，为什么客户希望针对其环境执行渗透测试，以及他们是否希望在渗透测试期间执行某些类型的测试。以下是在此阶段可能会提出的示例问题。

# 一般问题

## 网络渗透测试

1.为什么客户要针对其环境执行渗透测试？2.特定合规性要求是否需要渗透测试？3.客户希望何时进行渗透测试的活动部分（扫描、枚举、利用等）？如果是的话：

1.在工作时间？

2.下班后？

3.周末？

4.总共有多少个 IP 地址正在测试中？如果是的话：

1.有多少个内部 IP 地址（如果适用）？

2.有多少个外部 IP 地址（如果适用）？

5.是否有任何设备可能会影响渗透测试结果，例如防火墙、入侵检测/防御系统、Web 应用程序防火墙或负载均衡器？6.在系统被渗透的情况下，测试团队应该如何进行？如果是的话：

1.在受感染的计算机上执行本地漏洞评估？

2.尝试在受感染的计算机上获得最高权限（Unix 计算机上的 root，Windows 计算机上的 SYSTEM 或管理员）？

3.对获得的本地密码哈希执行无密码、最小密码、字典攻击或详尽密码攻击（例如，Unix 机器上的 /etc/shadow）？

## Web 应用程序渗透测试

1.正在评估多少 Web 应用程序？2.正在评估多少个登录系统？3.正在评估多少个静态页面？（近似值）4.正在评估多少个动态页面？（近似值）5.源代码会随时可用吗？6.会不会有任何类型的文档？如果是的话：

1.如果是，什么样的文档？

7.是否会在此应用程序上执行静态分析？8.客户端是否希望对此应用程序执行模糊测试？9.客户端是否希望对此应用程序执行基于角色的测试？10.客户端是否希望对 Web 应用程序执行凭据扫描？

## 无线网络渗透测试

1.有多少个无线网络？2.是否使用访客无线网络？如果是的话：

1.访客网络是否需要身份验证？

2.无线网络上使用什么类型的加密？

3.覆盖范围的平方英尺是多少？

4.是否需要枚举恶意设备？

5.团队是否会评估针对客户端的无线攻击？

6.大约有多少客户端将使用无线网络？

## 物理渗透测试

1.正在评估多少个地点？2.此物理位置是共享设施吗？如果是的话：

1.范围内有多少层？

2.哪些楼层在范围内？

3.是否有任何保安人员需要绕过？如果是的话：

1.保安人员是否通过第三方雇用？

2.他们有武装吗？

3.他们被允许使用武力吗？

4.大楼有多少个入口？5.是否允许使用撬锁或缓冲键？（另请参阅当地法律）6.此测试的目的是验证是否符合现有政策和程序还是执行审核？7.范围内区域的平方英尺是多少？8.是否记录了所有物理安全措施？9.是否正在使用摄像机？

1.相机是客户拥有的吗？如果是的话：

2.团队是否应该尝试访问摄像机数据的存储位置？

10.是否正在使用武装警报系统？如果是的话：

1.闹钟是无声闹钟吗？

2.警报是由运动触发的吗？

3.打开门窗会触发警报吗？

## 社会工程学

1.客户端是否有他们希望对其执行社会工程攻击的电子邮件地址列表？2.客户端是否有他们希望对其执行社会工程攻击的电话号码列表？3.是否批准以未经授权的物理访问为目的的社会工程？如果是的话：

1.有多少人将成为目标？

应该注意的是，作为不同级别测试的一部分，可能不需要向业务部门经理、系统管理员和技术支持人员提问。但是，如果这些问题是必需的，可以在下面找到一些示例问题。

## 业务部门经理的问题

1.经理是否知道将要执行测试？2.如果暴露、损坏或删除，对组织造成最大风险的主要数据是什么？3.测试和验证过程是否用于验证业务应用程序是否正常运行？4.测试人员是否可以访问应用程序首次开发时的质量保证测试程序？5.是否为应用程序数据制定了灾难恢复过程？

## 系统管理员的问题

1.是否有任何系统可以被定性为脆弱？（有崩溃倾向的系统、较旧的操作系统或未修补的系统）2.网络上是否存在客户端不拥有的系统，可能需要额外的批准才能进行测试？3.变更管理程序是否到位？4.修复系统中断的平均时间是多少？5.是否有任何系统监控软件？6.什么是最关键的服务器和应用程序？7.是否定期测试备份？8.上次还原备份是什么时候？

# 范围变更

范围蔓延是使渗透测试公司倒闭的最有效方法之一。问题在于，许多公司和经理几乎不知道如何识别它，或者在它发生时如何应对它。在与范围蔓延作斗争时，有几件事需要记住。首先，如果客户对在特定业务中所做的工作感到满意，他们通常会要求额外的工作。将此视为一种赞美，并毫不犹豫地要求额外的资金来补偿所花费的额外时间。如果客户拒绝为额外的工作付费，那么几乎不值得留下来做这项工作。第二点更为关键。在与现有客户打交道时，请注意保持较低的价格。通过价格欺诈来利用良好局面是赶走回头客的可靠方法。考虑到价格可以降低，因为公司避免了获得客户的成本，例如正式的RFP流程和寻找客户本身。此外，未来工作的最佳来源是通过现有客户。善待他们，他们就会回来。

# 指定开始和结束日期

击败范围蔓延的另一个关键组成部分是明确说明开始和结束日期。这允许项目有明确的结束。发生范围蔓延的最常见区域之一是在重新测试期间。在执行合同时，重新测试听起来总是一个好主意。这表明公司是关怀和勤奋的，试图确保客户尽可能安全。当忘记工作在完成之前没有报酬时，问题就开始了。这包括重新测试。为了减轻这种风险，请在合同中添加一个简单的声明，其中提到所有重新测试必须在最终报告交付后的一定时间内完成。然后，测试人员有责任带头进行重新测试工作。如果客户请求延期，请始终允许延期，条件是在最初指定的日期完成付款。最后，也是最重要的，进行质量重新测试。请记住，未来工作的最佳来源是您现有的客户群。

# 指定IP范围和域

在开始渗透测试之前，必须确定所有目标。这些目标应在初始调查阶段从客户那里获得。客户可以以特定 IP 地址、网络范围或域名的形式提供目标。在某些情况下，客户提供的唯一目标是组织的名称，并希望测试人员能够自行识别其余部分。重要的是要定义防火墙和IDS/IPS等系统或测试仪和最终目标之间的网络设备是否也是范围的一部分。应识别和定义其他元素，例如上游提供程序和其他第三方提供程序，无论它们是否在范围内。

## **验证范围**

在开始攻击目标之前，必须验证它们是否确实归您正在执行测试的客户所有。想想如果你开始攻击一台机器并成功渗透它，但后来发现这台机器实际上属于另一个组织（如医院或政府机构），你可能会遇到法律后果。

# 与第三方打交道

在许多情况下，参与将包括测试由第三方托管的服务或应用程序。近年来，随着“云”服务变得越来越流行，这种情况变得越来越普遍。要记住的最重要的事情是，虽然客户可能已经授予了许可，但他们并不代表他们的第三方提供商。因此，还必须从他们那里获得许可才能测试托管系统。与往常一样，未能获得适当的许可会带来违反法律的可能性，这可能会引起无休止的头痛。

## 云服务

测试云服务的最大问题是，来自多个不同组织的数据存储在一个物理介质上。通常，这些不同数据域之间的安全性非常宽松。云服务提供商需要收到测试警报，并需要确认测试正在进行，并授予测试组织测试权限。此外，云服务提供商内部需要有一个直接的安全联系人，如果发现可能影响其他云客户的安全漏洞，可以联系该联系人。一些云提供商对渗透测试人员有特定的程序，并且在测试开始之前可能需要他们的请求表格、日程安排或明确许可。

## 互联网服务提供商

与客户核实 ISP 服务条款。在许多商业情况下，ISP将有具体的测试规定。在发起攻击之前，请仔细阅读这些条款。在某些情况下，ISP会回避并阻止某些被认为是恶意的流量。客户可能会批准此风险，但在开始之前必须始终明确传达。虚拟主机 与所有其他第三方一样，测试的范围和时间需要与网络托管服务提供商明确沟通。此外，在与客户沟通时，请务必清楚地阐明测试将仅用于寻找 Web 漏洞。该测试不会发现底层基础架构中的漏洞，这些漏洞可能仍会提供破坏应用程序的途径。

## MSSPs

托管安全服务提供商也可能需要收到测试通知。具体来说，在测试他们拥有的系统和服务时，需要通知他们。但是，在某些情况下不会通知MSSP。如果确定MSSP的实际响应时间是测试的一部分，那么通知MSSP肯定不符合测试完整性的最佳利益。作为一般经验法则，每当测试 MSSP 明确拥有的设备或服务时，都需要通知它们。

## 托管服务器的国家/地区

验证服务器所在的国家/地区也符合测试人员的最佳利益。验证国家/地区后，请在开始测试之前查看特定国家/地区的法律。不应假设公司的法律团队将为测试人员提供当地法律的完整概要。也不应假设公司将对其测试人员违反的任何法律承担法律责任。每个测试人员都有责任在开始测试之前验证他们正在测试的每个地区的法律，因为测试人员最终必须对任何违规行为负责。

# 定义可接受的社会工程借口

许多组织希望以与当前攻击一致的方式测试其安全状况。如今，社会工程和鱼叉式网络钓鱼攻击已被许多攻击者广泛使用。虽然大多数成功的攻击都使用性、毒品和摇滚乐（分别为色情、伟哥和免费 iPod）等借口，但其中一些借口在企业环境中可能是不可接受的。在测试开始之前，请确保为测试选择的任何借口都得到书面批准。

# DoS 测试

在开始服务之前，应讨论压力测试或拒绝服务测试。由于测试的潜在破坏性，这可能是许多组织感到不舒服的主题。如果组织只担心其数据的机密性或完整性，则可能不需要压力测试;但是，如果组织也担心其服务的可用性，则应在与生产环境相同的非生产环境中进行压力测试。

# 付款条件

准备许多测试人员完全忘记的测试的另一个方面是他们应该如何获得报酬。就像合同日期一样，应该有具体的付款日期和条款。大型组织尽可能长时间地延迟付款的情况并不少见。以下是几种常见的付款方式。这些只是例子。绝对建议每个组织创建和调整自己的定价结构，以更恰当地满足客户和他们自己的需求。重要的是在测试开始之前要有某种结构。

## Net 30

总金额应在最终报告交付后30天内支付。这通常与每月不付款的百分比罚款有关。这可以是您希望授予客户的任何天数（即45或60）。

## 半预付

在测试开始之前，要求预付总账单的一半的情况并不少见。这在长期参与中很常见。

## 经常性

定期付款计划更常用于长期参与。例如，某些活动可能长达一两年。让客户全年定期分期付款的情况并不少见。

# 目标

每个渗透测试都应该以目标为导向。也就是说，测试的目的是识别导致客户业务或任务目标受损的特定漏洞。这不是关于寻找未打补丁的系统。它是关于识别将对组织产生不利影响的风险。

## 主要

测试的主要目标不应由合规性驱动。这种推理有许多不同的理由。首先，合规不等于安全。虽然应该理解，许多组织因为合规性而接受测试，但这不应该是测试的主要目标。例如，作为PCI-DSS要求的一部分，可以聘请一家公司来完成渗透测试。处理信用卡信息的公司并不缺乏。然而，使目标组织在竞争激烈的市场中独一无二和可行的特征如果受到损害，将产生最大的影响。信用卡系统遭到入侵肯定是一个严重的问题，但信用卡号码以及所有相关的客户数据泄露将是灾难性的。

其次

次要目标与合规性直接相关。主要目标和次要目标密切相关的情况并不少见。例如，在PCI-DSS驱动测试的示例中，获取信用卡是次要目标。将数据泄露与组织的业务或任务驱动因素联系起来是主要目标。次要目标意味着合规性和/或 IT。主要目标引起高层管理人员的注意。

## 业务分析

在执行渗透测试之前，最好确定客户端安全状况的成熟度级别。有许多组织选择直接进入渗透测试，首先评估此成熟度级别。对于安全计划非常不成熟的客户，首先执行漏洞分析通常是一个好主意。一些测试人员认为，漏洞分析（VA）工作存在污名。这些测试人员忘记了目标是识别目标组织中的风险，而不是追求所谓的“摇滚明星”生活方式。如果一家公司还没有准备好进行全面的渗透测试，他们将从良好的VA中获得比渗透测试更多的价值。提前与客户确定他们将提供的有关系统的信息。询问有关已记录的漏洞的信息也可能有所帮助。这将节省测试人员的时间，并通过不将测试发现与已知问题重叠来节省客户资金。同样，如果合规性不是绝对要求的，则完全或部分白盒测试可能会比黑盒测试为客户带来更多价值。

# 建立沟通渠道

任何渗透测试最重要的方面之一是与客户的沟通。您与客户互动的频率以及您接近他们的方式会对他们的满意度产生巨大影响。下面是一个沟通框架，有助于让客户对测试活动感到满意。

# 紧急联系信息

显然，能够在紧急情况下与客户或目标组织取得联系至关重要。可能会出现紧急情况，必须建立联络点才能处理。创建紧急联系人列表。此列表应包括测试范围内所有各方的联系信息。创建后，紧急联系人列表应与列表中的所有人共享。请记住，目标组织可能不是客户。收集有关每个紧急联系人的以下信息：

1.全名

2.职称和运营责任

3.讨论测试活动细节（如果尚未指定）的授权

4.两种形式的 24/7 即时联系，例如手机、寻呼机或家庭电话（如果可能）

5.一种形式的安全批量数据传输，例如 SFTP 或加密电子邮件

注意：帮助台或运营中心等组的号码可以替换一个紧急联系人，但前提是它有 24/7 全天候工作人员。每个渗透测试的性质都会影响谁应该在紧急联系人列表中。不仅需要提供客户和目标的联系信息，而且在紧急情况下，他们可能还需要联系测试人员。该名单最好包括以下人员：

1.参与测试组中的所有渗透测试人员

2.测试组的经理

3.每个目标组织两名技术联系人

4.客户两个技术联系人

5.客户的一名高层管理人员或业务联系人

上面的列表中可能会有一些重叠。例如，目标组织可能是客户，测试组的经理也可能在执行渗透测试，或者客户的技术联系人可能是高层管理人员。还建议为每个相关方定义一个联系人，由其领导并代表其承担责任。

## 事件报告流程

出于多种原因，在参与之前讨论组织当前的事件响应功能非常重要。渗透测试的一部分不仅是测试组织拥有的安全性，还包括测试其事件响应能力。

如果整个参与可以在目标的内部安全团队没有注意到的情况下完成，则安全状况存在重大差距。同样重要的是要确保在测试开始之前，目标组织中的某个人知道何时进行测试，以便事件响应团队不会因为认为自己受到攻击或受到威胁而开始在半夜打电话给每个高层管理人员。

## 事件定义

美国国家标准与技术研究院 （NIST） 将事件定义如下：“违反或即将威胁违反计算机安全策略、可接受使用策略或标准安全实践。（计算机安全事件处理指南 - 特别出版物 800-61 修订版 1）。事件也可能发生在物理层面上，其中一个人以任何方式获得未经授权的物理访问区域。目标组织应针对不同类型的事件具有不同的类别和级别。

## 状态报告频率

状态报告的频率可能差异很大。影响报告计划的一些因素包括测试的总长度、测试范围和目标的安全成熟度。有效的时间表可以让客户感到参与。被忽略的客户是以前的客户。

一旦确定了状态报告的频率和时间表，就必须完成。推迟或推迟状态报告可能是必要的，但不应成为长期报告。如有必要，可能会要求客户同意新的时间表。完全跳过状态报告是不专业的，应尽可能避免。

## PGP 和其他替代品

加密不是可选的。与客户的沟通是任何渗透测试参与的绝对必要部分，由于参与的敏感性，敏感信息的通信必须加密，尤其是最终报告。在测试开始之前，必须与客户端建立安全通信方式。几种常见的加密方法如下：

1.PGP/GPG既可以通过电子邮件进行通信，也可以用于加密最终报告（请记住，主题行以明文形式传递）

2.托管在客户网络上的安全邮箱

3.电话

4.面对面会议

5.要传递最终报告，您还可以将报告存储在 AES 加密存档文件中，但请确保您的存档实用程序支持使用 CBC 的 AES 加密。

还要询问哪些信息可以以书面形式提出，哪些信息只能口头传达。一些组织有很好的理由限制以书面形式传输给他们的安全信息。

# 接战规则

虽然范围定义了将要测试的内容，但参与规则定义了测试的发生方式。这是两个不同的方面，需要彼此独立处理。

## 时间轴

应为参与制定明确的时间表。虽然范围定义了参与的开始和结束，但参与规则定义了介于两者之间的一切。应该理解的是，时间表会随着测试的进行而变化。但是，拥有一个严格的时间表并不是创建一个时间表的目标。相反，在测试开始时制定时间表将使所有相关人员能够更清楚地确定要完成的工作以及负责所述工作的人员。甘特图和工作分解结构通常用于定义工作以及每个特定工作将花费的时间。以这种方式查看计划有助于相关人员确定需要应用资源的位置，并帮助客户识别在测试过程中遇到的许多障碍。

互联网上有许多免费的甘特图工具。许多经理都非常认同这些工具。正因为如此，它们是与目标组织的高层管理人员沟通的绝佳媒介。

## 地点

任何给定参与的另一个参数对于提前与客户建立很重要，是测试人员在测试期间需要前往的任何目的地。这可以像识别当地酒店一样简单，也可以像确定特定目标国家的适用法律一样复杂。

组织在多个位置和区域运营的情况并不少见，需要选择一些选定的站点进行测试。在这些情况下，应避免前往每个客户位置，而是应确定与站点的 VPN 连接是否可用于远程测试。敏感信息的披露

虽然给定服务的目标之一可能是访问敏感信息，但实际上不应查看或下载某些信息。对于较新的测试人员来说，这似乎很奇怪，但是，在许多情况下，测试人员不应该拥有目标数据。例如，根据《健康保险流通与责任法案》（HIPAA），个人数据必须受到保护。在某些情况下，目标系统可能没有防火墙或防病毒 （AV） 保护它。在这种情况下，应绝对避免测试人员拥有任何和所有个人身份信息（PII）。

但是，如果无法物理或虚拟地获得数据，如何证明测试人员确实获得了对信息的访问权限？这个问题已经通过多种方式解决了。有很多方法可以证明金库门是在没有拿走任何钱的情况下打开的。例如，可以截取数据库架构和文件权限的屏幕截图，或者可以显示文件本身，而无需打开它们来显示内容，只要文件名本身中没有 PII。

测试人员在给定的参与中应该有多谨慎是一个需要与客户讨论的参数，但进行测试的公司应始终确保在法律意义上保护自己，无论客户意见如何。无论是否假定暴露于敏感数据，都应在每次参与后充分清理所有报告模板和测试器计算机。作为特别的旁注，如果测试人员发现非法数据（即儿童色情），应立即通知适当的执法人员，然后通知客户。不要听从客户的指示。

## 证据处理

在处理测试证据和报告的不同阶段时，对数据格外小心非常重要。始终使用加密并在测试之间清理测试计算机。切勿在安全会议上分发带有测试报告的 U 盘。无论您做什么，都不要重复使用来自其他客户参与的报告作为模板！在文档中留下对另一个组织的引用是非常不专业的。

## 定期情况会议\*

在整个测试过程中，与客户定期会面，告知他们测试的整体进度至关重要。这些会议应每天举行，并应尽可能短。会议应遵循三个概念：计划、进展和问题。

通常会讨论计划，以便在重大计划外更改或中断期间不进行测试。进度只是向客户更新到目前为止已完成的工作。问题也应该在本次会议上讨论，但为了简洁起见，有关解决方案的对话几乎总是应该离线进行。

## 一天中的测试时间

某些客户要求在工作时间之外完成所有测试。对于大多数测试人员来说，这可能意味着熬夜。在测试开始之前，应与客户充分确定一天中的时间要求。

## 处理回避

有时回避是完全可以接受的，有时它可能不符合测试的精神。例如，如果您的测试是一个完整的黑盒测试，您不仅要测试技术，还要测试目标组织安全团队的能力，那么回避是完全可以的。但是，当您与目标组织的安全团队协调测试大量系统时，避免攻击可能不符合测试的最佳利益。

## 测试许可

渗透测试需要获得的最重要的文件之一是测试许可文件。本文档说明了范围，并包含一个签名，用于确认对测试人员活动的认识。此外，它应该明确指出测试可能导致系统不稳定，测试人员将给予所有应有的注意，以免在此过程中使系统崩溃。但是，由于测试可能导致不稳定，客户不应要求测试人员对任何系统不稳定或崩溃负责。至关重要的是，在客户签署此文档之前，不要开始测试。

此外，一些服务提供商在测试其系统之前需要提前通知和/或单独许可。例如，亚马逊有一个必须填写的在线申请表，并且该请求必须在扫描其云上的任何主机之前获得批准。如果需要，它应该是文档的一部分。

## 法律考虑

渗透测试中常见的某些活动可能违反当地法律。因此，建议在要执行工作的地点检查常见渗透测试任务的合法性。例如，在某些区域，在渗透测试过程中捕获的任何VOIP呼叫都可能被视为窃听。

# 能力和技术到位

良好的渗透测试不会简单地检查未打补丁的系统。他们还测试目标组织的能力。为此，下面列出了您可以在测试时进行基准测试的内容。

1.能够检测和响应信息收集2.能够检测和响应脚印3.能够检测和响应扫描和漏洞分析4.检测和响应渗透（攻击）的能力5.能够检测和响应数据聚合6.能够检测和响应数据防爆过滤

跟踪此信息时，请务必收集时间信息。例如，如果检测到扫描，则应通知您，并记下当时正在执行的扫描级别。
