前言

suid提权原理

SUID 是一种对二进制程序进行设置的特殊权限，可以让二进制程序的执行者临时拥有 root 的权限，设置了该权限的程序在运行时，程序的 Effective UID 会被设为该程序的所有者，当 Effective UID 为高权限用户（如0）的情况下，我们就可以以低权限用户的身份去用高权限执行该程序，如果该程序存在命令注入之类的漏洞，就能得到一个高权限的 shell 了，比如

我们有 ftp 程序的 suid 权限

则可以直接

[user@centos6 ~]$ ftp
ftp> !/bin/sh -p

这样来得到一个高权限的 shell

注：

每个 unix 进程都拥有 3 个 UID

  • Real UID  真实用户 ID：创建这个进程的用户的 ID

  • Effective UID 有效用户 ID：用来扩充权限，是程序实际操作时生效的用户的 ID

  • Saved UID 保存用户ID：高权限用户操作完后降权，保留的进程原本用户的ID

不同linux发行版中suid的区别

在很多提权方法介绍中，可以看到类似这样的注释：

If it is used to run sh -p, omit the -p argument on systems like Debian (<= Stretch) that allow the default sh shell to run with SUID privileges.

有的 linux 发行版（Debian）中可以忽略 -p，而其他的则不能忽略

首先 要弄清楚 这个 -p 参数是什么

在 centos 的文档中，可以看到对 shell 中 -p 参数的描述

If the shell is started with the effective user (group) id not equal to the real user (group) id, and the -p option is not supplied, no startup files are read, shell functions are not inherited from the environment, the SHELLOPTS, BASHOPTS, CDPATH, and GLOBIGNORE variables, if they appear in the environment, are ignored, and the effective user id is set to the real user id. If the -p option is supplied at invocation, the startup behavior is the same, but the effective user id is not reset.

大意为，bash 启动时如果 Effective UID 和 Real UID 不相同，并且没有加 -p 参数的时候，bash的 Effective UID 会被设置为 Real UID 的值

这就解释了为什么在 centos 中，利用 suid 提权调用 bash 时，需要 -p 参数，如果不加 -p 参数，低权限用户执行 suid 程序时，id 依然为这个低权限用户

centos和ubuntu  bash和dash

刚刚提到的是在 centos 的 bash 执行中，需要 -p 参数，但如果是在 dash 中执行的，因为 dash 中没有限制 Effective UID 所以不需要额外的参数，也能以 root 权限执行（旧版中，如 centos6）

但在 ubuntu 中，/bin/sh 默认指向 dash，我们却依然无法通过相同的方法获得 root 权限

这是因为 ubuntu 在 dash 中增加了一些代码

我们比较 dash 的原始代码和 ubuntu中 dash 的代码，发现多出了一个 setprivileged 函数

void setprivileged(int on)
{
    static int is_privileged = 1;
    if (is_privileged == on)
        return;

    is_privileged = on;

    /*
     * To limit bogus system(3) or popen(3) calls in setuid binaries, require
     * -p flag to work in this situation.
     */
    if (!on && (uid != geteuid() || gid != getegid())) {
        setuid(uid);
        setgid(gid);
        /* PS1 might need to be changed accordingly. */
        choose_ps1();
    }
}

这里根据用户有没有添加 -p 参数做了一个判断，如果没有 -p（on 取值为 false），且 real UID 不等于 Effective UID 的情况下，会重新恢复成当前用户的权限，这就是为什么在 ubuntu 中，不能直接用 SUID 权限的 system() 来提权了

在 debian10 中，也对 dash 做了类似的限制

突破限制

那么怎样突破这类限制呢，有两种思路，一种是阻止重新设置 UID，一种则是增加 -p 选项，让其不对 shell 降权

例如

int main(int argc, char* argv[]) {
    setuid(0);
    system(argv[1]);
}

这里仅假设需要留一个 suid 特权的 shell 当后门的情况，我们可以人为将当前进程的 Real UID 设为 0，这样 Real UID 和 Effective UID 相等，就绕过了 dash 的检测判断，从而不会被重新设置 UID 了

或者增加 -p 选项，但我们不能直接使用 system() 函数，然后执行 sh -p，因为 system 函数相当于执行 /bin/sh -c 我们无法给 /bin/sh 中再增加 -p 的参数，可以使用 execl 等函数，如下例

int main(int argc, char* argv[]) {
    return execl("/bin/sh", "sh", "-p", "-c", argv[1], (char *)0);
}
