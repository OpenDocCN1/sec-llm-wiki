漏洞综述

在Linux kernel v4.19之后引入的HCI时间解析器包含漏洞。控制HCI事件数据包能够造成安全影响。

  1. CVE-2020-24490 BadVibes 基于堆的缓冲区溢出
  2. CVE-2020-12352 BadChoice 基于堆的信息泄露
  3. cve-2020-12351 BadKarma 基于堆得类型混淆

poc执行

仔细分析漏洞作者的writeup发现此poc的运行环境为

1.victim使用蓝牙5.0的蓝牙适配器(目前未满足，蓝牙适配器采购中)
2.victim开启蓝牙扫描，接受advertise数据包
3.poc通过linux内核版本 linux-image-5.4.0-48-generic 开发krop利用链

漏洞的触发前提条件是利用了蓝牙4.0与蓝牙5.0关于蓝牙的advertise的长度分别为31和255字节，为了满足多蓝牙版本的兼容从而导致的数据溢出，导致内核溢出执行krop，最后触发内核任意命令执行。

victim开启蓝牙扫描的方式有两种

sudo hcitool -i hci1 scan //蓝牙扫描
sudo hcitool -i hci1 lescan//低功耗蓝牙扫描

使用树莓派作为attacker，vmware中的ubuntu20.04 with kernel linux-image-5.4.0-48-generic 作为victim。ubuntu外接usb适配器hci1.

在实际测试中发现，触发的条件为开启低功耗蓝牙扫描

由于当前的victim使用蓝牙4.0适配器进行扫描，未能成功触发漏洞

蓝牙数据发送函数 hci_send_acl_data()函数实现方式

static void hci_send_acl_data(int hci_sock, uint16_t hci_handle, void *data,
                              uint16_t data_length, uint16_t flags) {
 uint8_t type = HCI_ACLDATA_PKT;
 
 hci_acl_hdr hdr = {0};
 hdr.handle = htobs(acl_handle_pack(hci_handle, flags));
 hdr.dlen = data_length;
 
 struct iovec iv[3] = {0};
 iv[0].iov_base = &type;
 iv[0].iov_len = sizeof(type);
 iv[1].iov_base = &hdr;
 iv[1].iov_len = HCI_ACL_HDR_SIZE;
 iv[2].iov_base = data;
 iv[2].iov_len = data_length;

 //hci_send_acl_data 的实现核心是向蓝牙socket进行数据写入
 if (writev(hci_sock, iv, sizeof(iv) / sizeof(struct iovec)) < 0) {
  perror("[-] writev");
  exit(1);
 }

 usleep(HCI_SEND_ACL_DATA_WAIT_USEC);
 wait_event_complete_packet();
}

蓝牙数据接收函数 wait_event_complete_packet()函数实现方式

static void wait_event_complete_packet(void) {
 while (1) {
 uint8_t buf[256] = {0};
 if (read(hci_sock, buf, sizeof(buf)) < 0) {
   perror("[-] read");
   exit(1);
  }
  if (buf[0] == HCI_EVENT_PKT) {
   hci_event_hdr *hdr = (hci_event_hdr *)&buf[1];
   if (btohs(hdr->evt) == EVT_NUM_COMP_PKTS)
    break;
  }
 }
}

漏洞原理与内核动态调试

漏洞原理

此漏洞完成远程内核rce为 内核地址泄露 + 内核krop的组合攻击

内核地址泄露原理

cve-2020-12352 badchoice，堆栈信息泄露

在内核源码 net\bluetooth\a2mp.c 对于蓝牙的a2mp协议访问控制中，存在返回未初始化变量的问题

hci_dev_get() 类似于 hciconfig命令，列出当前设备所有的蓝牙适配器

poc使用了lib_bluetooth库的头文件

调试 l2cap_config_rsp()函数 在内核中的执行过程

在阅读内核源码的过程中思考了作者选取此条逻辑的思路

作者选取

conf_rsp.cmd_hdr.code = L2CAP_CONF_RSP;
conf_rsp.conf_rsp.result = htobs(L2CAP_CONF_UNACCEPT);

的原因是，作者在构造利用的时候，挨个尝试了内核中的逻辑分支

同级别case所有函数中都会有一个指向l2cap_chan的指针，不同函数在执行过程中，申请的栈空间大小不同，正好作者选取的函数能够将保存结构体l2cap_chan结构体的指针，函数结束执行结束后，rsp rbp指针变化，但之前的栈数据依旧保存在栈内。

作者通过选取特定的逻辑分支将l2cap_chan的指针放到执行a2mp_getinfo_req()函数时结构体 a2mp_info_rsp 未初始化变量的空间内 从而造成 l2cap_chain 结构体地址的泄露，作者在编写exp时有可能按照顺序将l2cap_bredr_sig_cmd()中的switch case挨个进行了调试，从而构造一条巧妙地利用构造。

泄露利用函数中都是标准的c蓝牙调用，利用蓝牙标准通信，未进行任何填充，但是泄露出了一个目标结构体的指针。感叹作者的脑洞之余，调试就跳过吧，比较吓人[doge]

内核未初始化变量防御手段

CONFIG_INIT_STACK_ALL_PATTERN=y
