一、事件时间线


2019年5月15日，美国时间5月14日

微软官方发布5月份安全补丁，Microsoft MSRC在最新的安全更新公告中披露了RDP（Remote Desktop Protocol，远程桌面服务）远程代码执行漏洞，且被标记为严重，编号CVE-2019-0708，一个潜在的可能成为具有MS17-070类似影响力的重要漏洞“Windows RDP服务蠕虫级漏洞”。通过此漏洞，攻击者无需经过身份验证，只需发送特制的RDP数据包到目标系统，就可以实现在目标系统上远程执行代码，从而获取目标系统的完全控制。

2019年5月15日当天

深信服在获取到漏洞相关信息后，第一时间发布漏洞预警，提醒广大用户及时更新微软安全补丁。对于无法及时安装微软更新补丁的情况，给出了暂时的缓解措施。

2019年5月15日

Qualys发布消息:”Windows RDP Remote Code Execution Vulnerability (BlueKeep) – How to Detect and Patch”, 新发布的QID为91534的插件据称能监测这个漏洞，需要登录扫描或者本地Agent插件安装后扫描。

2019年5月15日至20日

在漏洞信息发布后，该漏洞热度极速上升，网络上关于该漏洞的讨论持续不断，并流传出多个虚假PoC，其中大多数为娱乐性质，但有部分PoC附带了恶意代码（病毒、后门、木马等），深信服提醒用户慎重对待网上流传的PoC。

2019年5月21日

NCCGroup社区发出suricata规则，经验证该规则可以在原生snort环境下正常运行。

2019年5月22日

深信服通过对该漏洞的分析，成功开发出漏洞防御的检测规则，并集成到深信服下一代防火墙中。考虑到该漏洞的严重性，深信服给出该漏洞二次预警，披露了部分漏洞细节，并再次提醒用户及时更新微软官方的安全补丁。

2019年5月22日

McAfee的研究员在发布了针对CVE-2019-0708的详细分析文章，其中包含部分漏洞细节，并称McAfee已经分析完毕该漏洞，且已经开发出对应的Exploit。

2019年5月27日

深信服开发出针对该漏洞的扫描插件，并集成到云眼、云镜等产品，可实现对受影响系统的漏洞扫描。

 

二、漏洞描述及发展趋势


2.1 Remote Desktop Protocol组件介绍

Remote Desktop Protocol(远程桌面协议，RDP)是微软公司创建的专有协议。它允许系统用户通过图形用户界面连接到远程系统。在默认情况下，该协议的客户端代理内置在微软的操作系统中，也可以安装在非微软操作系统中。RDP的服务器端安装在微软操作系统中，从客户端代理接收请求，显示发布应用程序的图形界面或者远程访问系统本身。默认情况下，系统在3389端口来监听来自客户端的通过RDP的连接请求。


通常情况下，在企业中，RDP或者终端服务会话被配置在需要分布式客户端机器来连接的服务器上。它可以用于管理、远程访问或者发布用于中央使用的应用程序。该协议还常被桌面管理员来远程访问用户系统，以协助排除故障。如果RDP没有正确配置或存在漏洞，这种特定功能将会给企业带来威胁，因为未授权访问者将可以访问关键企业系统。


到目前为止，在全球范围内对互联网开放RDP的资产数量已经多达1250万，其中美国地区对外开放的RDP数量排名第一，为341万台。排名第二与第三的分别是中国和德国，其中中国数量远远超过德国的数量。

(统计数据仅为对互联网开放的资产，本数据来源于FOFA，20190515。)

2.2漏洞描述

CVE-2019-0708，属于远程代码执行漏洞，当未经身份验证的攻击者使用RDP连接到目标系统并发送特制请求时，即可以触发该漏洞。此漏洞属于预身份验证，无需用户交互，成功利用此漏洞的攻击者可以安装应用程序，查看、更改或删除数据或创建具有完全用户权限的新账户。


恶意攻击者还很有可能利用该漏洞专门编写恶意代码到定制的恶意软件， 利用此漏洞的任何未来恶意软件都可能以与 2017年WannaCry恶意软件遍布全球的类似方式从易受攻击的计算机传播到易受攻击的计算机。


2.3漏洞攻击发展趋势


2.3.1 CVE-2019-0708综述


自CVE-2019-0708公布以来，全球的安全工作者和有恶意企图的黑客都在时刻关注该漏洞的发展情况，同时也在使出浑身解数尝试去分析漏洞原理、技术细节、触发过程，以编写出PoC甚至是exp。


在漏洞公开初期没有出现PoC和攻击事件的部分原因是RDP协议自身较为复杂，需要一定的技术基础和时间去理解、分析协议的实现过程以及可能出现问题的环节。在15日到22日一周的时间内，网上陆续流传出关于RDP协议和CVE-2019-0708的部分分析信息和结论，这对于有一定技术实力的安全研究员和黑客来说，综合网上的各方信息已经完全足够复现该漏洞并编写出PoC和exp，所以我们认为此时出现的攻击有很大的可能性为真实的利用该漏洞的攻击。


根据深信服云脑监测数据，自22日开始，监测到的攻击日志逐渐增多，结合网上逐步有人爆出自己已经开发出exp的信息，我们有理由相信该漏洞的相关利用已经开始传播。但其传播速度较2017年的WannCry慢很多，我们分析这主要是由于微软在发布安全补丁之前没有透露该漏洞的任何信息，且给出的安全补丁涵盖了受影响的各个版本的操作系统。这无疑给了用户足够长的时间来更新安全补丁，提前做好防御措施，很大程度上减小了受影响的面积。但考虑到该漏洞的利用难易程度和影响程度，我们仍然需要对该漏洞保持足够高的警惕性。

三．漏洞细节分析


3.1 RDP协议部分解析

RDP协议主要作用是指定了多个会话参与者如何在共享程序上进行查看和共享。该协议是微软对ITU-T T.128应用共享协议的扩展，利用了T.120标准中较低层协议提供的其他服务，比如T.124 Generic Conference Control(GCC)、T.122 Multipoint Conmmuication Services(MCS)等。


RDP连接以序列消息的连接为开始，Basic Connectivity and Graphics Remoting(MS-RDPCGR)协议对序列消息的连接以及各个消息的详细信息进行了详细描述，如下图所示：

图5  序列消息连接建立过程

连接初始化阶段，主要是客户端通过发送一个X.224 Connection Request PDU到服务器，然后服务器会返回一个X.224 Connection Confirm PDU作为响应。


客户端在从服务器端接收到X.224 Connection Confirm的响应消息后，客户端将会使用MCS Connect Initial PDU 发送到服务器，然后服务器将会返回一个MCS Connect Response PDU。其结构如下图所示：

图6 MCS Connect Initial PDU

图7 MCS Connect Response PDU

Connect Initial PDU包含一个Generic Conference Control (GCC) Conference Create Request，Connect Response PDU 包含一个服务器发送的GCC Conference Create Response。这两个GCC数据包包含一些连接的设置信息数据块，比如安全信息、虚拟信道建立信息以及其他受支持的客户端功能的相关信息。而此次漏洞主要与“MCS Connect Initial and GCC Create”请求过程相关。


其结构如下所示：

3.2  漏洞触发过程分析

clientNetworkData的CS_NETHeader字段为0xC003，以小端显示为\x03\xc0。 channelCount字段指明请求的静态虚拟信道(Static Virtual Channel,SVC)。 channelNamen（其中n=1,2，...，N）字段定义了信道的8字节的null-terminating名称，channelOption_n字段指定了信道的属性。


RDP协议支持SVC，旨在用作各种RDP组件和用户扩展的通信链路，这些信道包括标准的Microsoft-supposed通道，如“rdpdr”（重定向），“rdpsnd”（声音），“cliprdr”（剪贴板共享）等。除上述信道外，Microsoft还会默认创建两个信道：MS_T120（用于RDP本身）和CTXTW（用于Citrix ICA）。客户端不应该通过网络创建这两个信道，当建立连接时，这两个信道由Windows RDP系统在内部初始化。


使用termdd!IcaCreateChannel()函数创建信道，它首先检查指定的命名信道是否存在，如果不存在，则分配信道结构来创建信道。指向ChannelControlStructure结构的指针存储在ChannelPointerTable中，所有RDP连接都以ChannelPointerTable开头，如下所示：

图12  ChannelPointerTable Structure

在上面的表中，每个Slot都可以存储一个ChannelControlStructure指针，其中标记为Empty的存储的为空指针。当客户端通过在clientNetworkData中指定它们来进行信道连接和打开时，将创建相应的ChannelControlStructures，并将其指针存储在从Slot 0开始的ChannelPointerTable中。需要注意，CTXTW始终存在于Slot 7中，MS_T120存在于Slot 0x1F中。


 Windows RDP内核驱动程序termdd.sys中存在UAF漏洞。在接收到包含clientNetworkData的MCS Connect Initial和GCC Create数据包后，将创建其中指定的信道的ChannelControlStructures。如果指定了名为“MS_T120\x00”的信道（例如，在Slot 10中），则termdd!IcaCreateChannel()调用termdd!IcaFindChannelByName()并返回由Slot 0x1F中的MS_T120结构指向的ChannelControlStructure。该指针（与Slot 0x1F中的指针相同）存储在函数termdd!IcaBindVirtualChannels()中的用户指定的Slot（在此示例中为Slot10）中。然后，当使用MCS Channel Join Request打开信道后，MS_T120信道也会被成功打开。如果攻击者将精心制作的数据发送到MS_T120信道，termdd.sys会尝试通过发送错误消息并使用termdd!IcaCloseChannel()函数关闭信道来响应该消息，termdd!IcaCloseChannel()函数将会调用termdd!_IcaFreeChannel()函数，进行MS_T120信道ChannelControlStructure的释放并清除ChannelPointerTable中用户控制的Slot（本例中的Slot 10）中的指针。


但是，Slot 0x1F中的相同指针不会被清除。当连接终止时，调用RDPWD!SignalBrokenConnection()，再调用termdd!IcaChannelInputInternal()并尝试使用Slot 0x1F处的指针写入释放的ChannelControlStructure。这就导致UAF。 远程未经身份验证的攻击者可以通过在打开MS_T120通道时与目标服务器建立RDP连接并向其发送精心设计的数据来利用此漏洞。成功利用将导致攻击者能够使用管理（内核级）权限执行任意代码。


四、未来发展预测


虽然距CVE-2019-0708公开至今已经十多天，但目前尚未发现公开表示受到利用该漏洞的攻击的具体案例，但无法保证后续不会出现。且随着时间的推移，将会有越来越多的技术人员研究清楚漏洞的原理，这将有助于开发出稳定可行的利用代码。一旦怀有恶意的黑客拥有了稳定可行的可利用代码，将会发动实际的攻击。
