漏洞扫描是基于漏洞数据库，通过执行漏洞检测插件等手段对指定的远程或者本地计算机系统的安全脆弱性进行检测，发现可利用漏洞的一种安全检测行为。漏扫十年当业务修改上线时，你是否希望能够进行安全体检，防止被爆？当新的漏洞出现时，你是否希望能够进行批量扫描，刷爆乌云？当推销安全产品时，你是否希望能够获取漏洞情报，以此切入？当监管单位检查时，你是否希望能够做到预先防范，做好知己？... ...信息安全行业从业者，离不开漏扫，过去的十几年漏扫进行着自己的达尔文演化，从各自为营到相依为命，从漏洞的发现到漏洞的闭环管理，从单一的漏扫应用软件到分布式的云漏扫平台，抛开其他维度的演化，我们抽离从应用软件到云漏扫的进化，浅谈一下如何快速的构建自己的云漏扫。借助开源第一种方案：借助开源漏扫软件构建。其基本的实现类似下图：![](../Images/9b29e4a6e2b1f5e8f0d4e49b52d19bd5.png)  
用户通过 WebUI 把不同的漏扫任务提交入库后，由 Scheduler 把任务分发到 Scanner，Scanner 就是具体的开源扫描软件，其自身带有插件库，不需要由 Scheduler 下发，Scanner 自身完成信息收集、插件选择等工作，最后把结果反馈给 Scheduler，由 Scheduler 入库。可以看到这种方案是 SCHEDULABLE （可调度）、SCABLE （可扩展）的、OPEN （开放的）的。知名的开源漏扫软件有 W3AF、OPENVAS、NMAP 等，这种方案就是把这些开源漏扫软件搬到云上，以云的方式提供安全漏扫能力，当然也不一定非得采用开源漏扫软件，整合商用漏扫软件也是 OK 的，再就是方案实现过程中，Scanner 很难做到只通过 Scheduler 与数据库交互，可适当有所改变。依赖安全社区第二种方案：依赖安全社区与白帽子合作共赢。其基本实现类似下图：![](../Images/fcd7d60ca6d9483f6476480ebcc6199e.png)  
这是一种“分布式无状态”的扫描架构，“一个问题确认”就是运行一个插件，所以“插件运行”就是任务，“分布式”就是创建多个任务执行的节点，“无状态”就是任务和任务之间是独立的，没有必然的联系。这种架构的好处是，任务执行节点可以同时处理多个网站的任务，而不用关心不同网站不同任务之间的联系，通过 Scheduler 控制任务的下发，可以控制对目标网站的并发连接数等网络参数。这种方案一个端口的识别可以是一个任务、一个网页的爬取可以是一个任务，一个漏洞的确认也可以是一个任务，总之任务可以是任何事情，通过社区白帽子贡献并给予一定回报的方式来获取插件。目前 TangScan、BugScan 采用类似的方式构建，云框架由自己构建，开放插件撰写的API，由安全白帽子撰写插件提交审核，并提供给白帽一定的奖励。理想框架第三种方案：是一种理想的构建方案。其基本的实现类似下图：![](../Images/9b8ff4e0099b6f45ecc118f2234deca2.png)  
这是一种硬件盒子与云联动的方案，硬件盒子一般是指安全网关，内置 SCANNER 扫描器，目标可选择安装 AGENT 客户端代理。硬件盒子可以根据网路流量分析出网络相关参数指标，如各个时间点的平均会话数等，进而确定业务繁忙程度，为不同时间点选择合适的扫描带宽，防止业务系统因为扫描中断，硬件盒子还可以被动的分析流量，进行信息收集，加上内置 SCANNER 主动信息收集的结果一起加密反馈给云端 SCHEDULER，SCHEDULER 对信息收集的结果进行智能分析，加密下发插件由 SCANNER 调度。不是所有的问题通过远程扫描的方式都可以发现的，这就需要 AGENT 配合 SCANNER 完成扫描， AGENT 如果得到客户允许，也可以进行一些信息收集，上传云端做为智能分析的依据。漏扫总结漏洞如雨后的蘑菇，永远都摘不完，一场大雨之后，新的蘑菇又冒出来了。安全企业要想更快更多帮助客户摘蘑菇，建立自己的云漏扫是无法阻挡的趋势，虽然惟漏洞论影响了安全市场十余年，将企业安全建设带进了攻防的怪圈，但是即使在不远的将来，有更好的安全解决方案，漏扫也一定是打包解决方案中的一部分。例如在行业威胁情报平台建设如火如荼的今天，云漏扫平台作为威胁情报平台的一部分，为其提供漏洞情报，而漏扫也与威胁情报平台的资产发现、漏洞管理等打包提供了更好的安全解决方案。
