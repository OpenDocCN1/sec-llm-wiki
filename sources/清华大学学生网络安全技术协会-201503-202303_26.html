（1）Root是什么

大家对于Root应该不会陌生，直观理解就是拥有操作设备的所有内容的权限。在安卓上获取root可以删除设备上自己不需要的软件，提高设备的流畅度，而且可以使用很多炫酷的功能。（此处不再赘述）举个栗子，人类对于自己的身体是没有root权限的，你并不能控制自己的心跳以及外貌（如果每个人都能把自己改造成帅哥美女该是一个多么美妙的世界哈哈）

（2）安卓Root相关背景知识

2.1 bootloader

安卓设备上不只安装着安卓系统，还有底层的其他系统，比如bootloader和baseband。bootloader，可以被翻译为引导加载程序。

在大多数设备上，bootloader是厂商的私有代码，负责对一些底层的硬件做初始化（设置时钟、内置RAM、引导介质等）并支持recovery和下载模式等。（引用自Android Hacker's Handbook）大家只要把它理解成一个安装系统的系统即可，如果其处于解锁状态，设备无法刷入不可信的系统（只能通过recovery刷入有合法签名的系统），那么通过刷新系统或者安装OTA更新获取root（后文提到）便不再可能。

事实上，很多设备都可以解锁bootloader，这样岂不就使得设备提供商的系统可被替换了么？为什么不完全锁定呢。大家可以思考下原因？

2.2 recovery

recovery系统，又叫做recovery控制台，或者就简称为recovery，是一个小型的操作系统，用来执行那些不能直接通过安卓系统执行的那些命令：比如恢复出厂设置（抹掉userdata分区）或者应用OTA更新。与bootloader的快速启动模式（用于刷入系统）类似，recovery系统既可以在系统启动的时候按特定的组合键，或者通过adb连接上宿主机，然后使用adb reboot recovery命令即可使设备重启之后进入recovery模式。大家可以理解为维护安卓系统的一个备用小系统，与Android系统在一个层面上，也就是比bootloader高一层。

recovery菜单一般有四个选项：重启，使用adb连接进行更新，恢复出厂设置和清除缓存分区。

recovery作为一个系统，也是可以被更新的，而且是在安卓主系统中进行更新。（大家可以思考这是为了什么？）在安卓启动的时候，会检查是否需要更新recovery，如是即执行/system/etc/install-recovery.sh脚本以更新recovery。这一点在之后的root过程中非常重要（是不是觉得不太合理，recovery的更新跟root有什么关系？请看下文）。

（3）安卓Root的三种方法

对于工程机来讲，获取root非常简单，对于不同的系统有不同的方法，此处不再赘述。本文将主要关注正式版系统的root方法。在“Android Security Internal”一书中，将root方法分为三种：修改/boot和/system镜像、OTA更新法以及Exploit方法。

第一种方法，修改boot分区是为了修改ro.secure和ro.debuggabe的系统属性值，将其修改成工程机。这种方法比较古老，而且现在的大部分正式版系统都会忽略该属性值，所以一般情况下不会使用。修改system镜像是为了在/system分区中增加一个SUID的su文件，这样不仅仅能够从shell中获取root访问，第三方应用也能够通过这种方法获取root权限。然而安卓4.3和之后版本的一些安全保护措施，直接禁止了应用执行SUID的程序：通过扔掉Zygote生成的能力集合的所有值，然后将system分区以nosetuid的标志位进行挂载。所以在安卓4.3版本之后，这种方法也不太行得通。

第二种方法——OTA更新法：通过recovery安装一个OTA更新包，获取系统root访问。但是这种方法需要bootloader的解锁。这种方法是常用root软件SuperSU使用的方法。也将是我们本次介绍的主要内容。

第三种方法——Exploit：通过安卓内核或者其他提权漏洞获取root。本文篇幅有限，其内容将会在之后讨论。

（4）OTA更新法获取root

通过OTA包的安装，可以在不替换掉系统的前提下修改系统文件；因此这种方法也是在设备上增加root权限的很好的途径。大部分流行的超级用户的应用都是以OTA包的组合进行发布的。OTA包只需要安装一次，而对应的管理程序仅仅是一个普通应用，可以通过网络进行更新。

本文用SuperSU为例，讲解这种方法的细节。（参考Android Security Internal）

步骤1：在recovery下执行该OTA更新脚本：以可读可写模式挂载rootfs文件系统和system、userdata分区。

步骤2：将su和daemonsu文件拷贝到/system/xbin目录下。（/system/xbin和/system/bin两个目录的不同在于：xbin下一般用来存放安卓系统本身的运行并不必须的二进制文件，而bin中一般存放系统必须的二进制文件）。将root权限管理应用拷贝到/system/app下。并将install-recovery.sh拷贝到/system/etc/目录下。（又看到这个recovery更新脚本了）

步骤3：设置步骤1中的文件的权限和SELinux安全标签。以--install参数调用su命令完成安装之后的初始化。随后卸载/system和/data分区。之后recovery会重启设备进入主安卓系统。

步骤4：在步骤3中完成了SuperSU的安装，启动安卓之后init进程（系统的第一个进程，在所有现有安卓版本中都拥有无限制的root权限）会执行install-recovery.sh脚本：a. 执行daemonsu文件，以root权限启动一个守护程序。b. 执行install-recovery-2.sh，让其他root应用完成额外的初始化操作。

步骤5：应用使用su文件执行命令，但su会将该命令通过UNIX的域套接字转发给daemonsu，而daemonsu是以root权限运行的，所以充当了一个类似跳板的功能执行了用户请求的命令。

通过上面5个步骤，用户可以获取到系统的root权限，而这种以daemonsu作为“跳板”的方式是必须的：因为在安卓4.3版本及其之后，所有的应用的进程都是从zygote进程分支出来的，而这些进程的能力集合已经被完全剔除掉了，就是为了防止应用执行一些高权限的操作。即使这些应用成功启动了root的进程，也无法执行高权限的操作，所以必须使用守护程序，才有可能让应用执行root权限的操作。此外，在安卓4.4版本中，SELinux处于enforcing模式，所以从应用启动的任何进程都包含有其本来的安全标签（一般是untrusted_app），因此还遵循着与其应用一样的强制访问控制（MAC）的限制。
