K8s API Server鉴权问题简介

鉴权，顾名思义就是：对资源访问者进行验证，鉴别其能否访问或具备访问系统什么资源的什么权限，如果访问者具备访问特定资源的权限，则系统可以为其提供相应的可访问资源供其进行访问。

在K8s中的API服务器在实际运行过程中会开启8080和6443端口，其中8080端口作为本地测试端口；6443端口通过引入TLS证书加密保障传输数据的保密性。

在系统中，kube-apiserver进程负责提供 Kubernetes API 服务。

8080端口服务特性

1.使用HTTP协议访问；2.默认端口为8080，可通过 --insecure-port 参数修改其默认值；3.无认证和授权操作，可直接通过本地访问相关服务。

6443端口服务特性

1.使用HTTPS协议提供服务；2.默认端口号为6443，可通过 --secure-port 参数修改其默认值；3.可以通过远程地址进行访问；4.会对用户合法性进行认证。

K8s的RBAC访问控制简介

据cdxy大佬描述，在实际环境中由于对cluster集群的鉴权配置不当：将 system:anonymous 用户绑定至 cluster-admin 用户组，导致6443端口允许匿名用户以管理员权限向集群下发指令。本菜鸡根据大佬的描述初步理解认为：k8s应当有类似于Linux的RBAC权限机制，通过阅读相关文档佐证了我的看法，您且听我简单跟您掰扯掰扯：

RBAC基于角色的访问控制：根据在组织内的个人用户角色，调整相应资源的访问权限的方法。

RBAC角色或ClusterRole包含代表一组权限的规则。权限是累加的（没有“拒绝”规则）。其中K8s API所支持的角色列表如下：

•Role：是一组权限的集合，用于给特定的某个Namespace进行鉴权；•ClusterRole：同样是一组权限的集合，但可以用于给所有Namspace及集群级别资源进行鉴权；

官网上有句话说的好啊（我就不给翻译了！溜！）：If you want to define a role within a namespace, use a Role; if you want to define a role cluster-wide, use a ClusterRole.

K8s还支持RoleBinding和ClusterRoleBinding，其中K8s所支持的角色绑定主体有三种：

•users：用户，对应于User account。•groups：用户组，可能是一组用户构成了一个组。•Service accounts：服务账户，为方便Pod中的进程调用K8s API或其他外部服务所设计的。

通过绑定方案，能够将定义在角色role中权限下放给用户或用户组，说白了呢：就是让某个user具有某个Role在某个Namespace的权限。ClusterRole我就不多说了，类似。

攻击流程描述

据cdxy大佬的描述，这类攻击发起者首先检查存在问题Server的可用API，进而列举系统所有的Node（k8s的计算资源）信息，通过在指定的Node中创建Pod（K8s可管理的最小集合，通常为一个或多个容器），通过该Pod拉取并启动一个Docker镜像形成容器1，并在容器1中以privilege模式启动一个新的Docker容器，记为容器2（容器2是容器1中的容器）。由于k8s能够管理相关Pod，因此可以通过API提供的attach方法进入到容器2内，并在其中拉取Xmrig-centos7这一镜像并运行。结合大佬的讲述、图例和理解，我又画了一遍图，不好看别打我！毕竟我还是个弟弟！

经大佬点拨我理解的针对该问题的检查流程

1.观察k8s日志，是否有6443匿名登陆成功的情况，如果有则继续进行步骤2；2.检查是否有pod创建，以及在pod创建后，是否有特权Docker容器被启动（关键：能够共享主机各种信息），如果有，则继续进行步骤3；3.观察主机内部日志，是否有存在恶意的外连矿池的链接/恶意脚本下载/敏感的image下载等，如果有则基本判断存在问题存在。
