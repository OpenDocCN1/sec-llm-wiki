0x00 Rules Format


规则签名在Suricata中发挥非常重要的作用。在大多数情况下，人们在使用现有的规则签名集。最常用的是Emerging Threat， Emerging Threats Pro和SourceFire的VRT。使用Oinkmaster的规则管理中介绍了一种安装规则的方法。这Suricata规则签名文件解释所有关于规则签名；包括如果阅读，调整和创建它们。

规则签名包含以下内容：

-这个动作决定了规则签名匹配时会发生什么；

-该规则签名的头部，定义的协议，IP地址，IP端口和IP方向；

-该规则签名的设置，定义的细节内容。

规则签名的一个例子如下：

drop tcp $HOME_NET any -> $EXTERNAL_NET any (msg:”ET TROJAN Likely Bot Nick in IRC (USA +..)”; flow:established,to_server; flowbits:isset,is_proto_irc; content:”NICK “; pcre:”/NICK .*USA.*[0-9]{3,}/i”; reference:url,doc.emergingthreats.net/2008124; classtype:trojan-activity; sid:2008124; rev:2;)

在这个例子中，红色是动作，绿色是规则头，蓝色是细则。

在本节内容中，我们将使用上述的规则签名作为示例，突出签名的不同部分。这是一个来自Emergin Threats数据库的规则签名。这是一个开放的数据库，其中包含许多在Suricata实例中自由下载和使用的规则。

-SSH
-SMTP
-IMAP
-MSN
-modbus（默认禁用）
-dnp3（默认禁用）
-enip（默认禁用）
-nfs（依赖规则的可用性）
-ntp（依赖规则的可用性）
这些协议的可用性取决于是否在配置文件suricata.yaml中启用
如果您有一个例如http协议的签名，Suricata会确保只有在涉及http-traffic的情况下，规则签名才能匹配。

04

Ports（source and destination）

源端口和目的端口



drop tcp $HOME_NET any -> $EXTERNAL_NET any (msg:”ET TROJAN Likely Bot Nick in IRC (USA +..)”; flow:established,to_server; flowbits:isset,is_proto_irc; content:”NICK “; pcre:”/NICK .*USA.*[0-9]{3,}/i”; reference:url,doc.emergingthreats.net/2008124; classtype:trojan-activity; sid:2008124; rev:2;)

第一个强调的部分是源，第二个是目的（注意方向箭头的方向）。
流量进出是通过端口的。不同的端口有不同的端口号。例如，HTTP的默认端口是80，而443通常是HTTPS的端口。但请注意，该端口不会规定通信中使用哪种协议。而是确定哪个应用程序正在接收数据。
上面提到的端口通常是目标端口。源端口，即发送数据包的应用程序，通常由操作系统分配一个随机的端口。当为自己的HTTP服务编写规则时，通常会编写规则，因为这意味着从任何端口到HTTP应用程序的任何数据包都会匹配。（any -> 80）

05

Direction

方向


drop tcp $HOME_NET any -> $EXTERNAL_NET any (msg:”ET TROJAN Likely Bot Nick in IRC (USA +..)”; flow:established,to_server; flowbits:isset,is_proto_irc; content:”NICK “; pcre:”/NICK .*USA.*[0-9]{3,}/i”; reference:url,doc.emergingthreats.net/2008124; classtype:trojan-activity; sid:2008124; rev:2;)

方向表明规则签名必须以哪种方式匹配。几乎每个规则签名都有一个向右的箭头（->）。这意味着只有具有相同方向的数据包才能匹配。但是，也可以有一条规则匹配两种方式（<>）：
源 - >  目的地
源 <>  目的地  （两个方向）

警告

没有“反向”风格的方向，即没有<-。
以下示例说明了这一点。假设有一个IP地址为1.2.3.4和端口为1024的客户端和一个IP地址为5.6.7.8的服务器在端口80（通常时HTTP）上侦听。客户端服务器发送消息，服务器回复其答案。


现在，假设我们有一个包含以下标题的规则：
alert tcp 1.2.3.4 1024 -> 5.6.7.8 80
只有第一个数据包将与此规则匹配，因为方向指定我们在响应数据包上不匹配。


06

Rule options

规则设置


规则的其余部分由选项组成。这些由括号括起来并用分号分隔。某些选项具有设置（如msg），由选项的关键字指定，后跟一个冒号，后跟设置。其他人没有设置，只是关键字（如nocase）：
< keyword > ：< settings > ;
< keyword > ;
规则选项具有特定的顺序，更改顺序会改变规则的含义。

注意

字符;和"具有在Suricata规则语言特殊含义，在规则选项值使用时必须转义。例如：

msg:"Message with semicolon\;";

因此，您还必须避开反斜杠，因为它充当转义字符。

本为的其余部分在文档中记录了各种关键字的使用。

关键字的一些通用细节如下。


1

01

修饰符关键字

某些关键字功能充当修饰符。有两种类型的修饰符。
-旧式'内容修饰符'回顾规则，例如：
alert http any any -> any any (content:"index.php"; http_uri; sid:1;)
在上面的例子中，模式'index.php'被修改以检查HTTP URI缓冲区。
-最近的类型称为“粘性缓冲区”。它首先放置缓冲区名称，并将其后的所有关键字应用于该缓冲区，例如：
alert http any any -> any any (http_response_line; content:"403 Forbidden"; sid:1;)
在上面的例子中，模式'403 Forbidden'针对HTTP响应行进行检查，因为它遵循http_response_line关键字。

因为数据正在被标准化，所以它不是以前的样子; 这是一种解释。标准化缓冲区包括：所有HTTP关键字，重组流，TLS，SSL，SSH-，FTP和dcerpc缓冲区。
