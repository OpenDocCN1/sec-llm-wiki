**0x00 前言**

记之前对某cms v1.2版本的代码审计，到现在已经更新了几个版本，本文提到的漏洞在最新版中均已修复。基于安全披露原则，对cms进行打码处理。  

  

**0x01 前台SQL注入**

发现前台功能点有一处在线留言  

![](../Images/87fa860a1f59c56c2554d819c7a59d84.png)  

对应源码处，看到会记录ip

![](../Images/c7cdd9ac1a6d8ac71e7532cd882fe51e.png)  

跟进`getIP()`方法，发现会从 xff 请求头获取 ip，存在一个ip伪造的问题，同时这里没有过滤

![](../Images/684a6d7101533c2e6b18aee3686df2df.png)

  

接着通过`mysql::insert($data, 'feedback')`最终会被插入数据库中，我们打个断点跟一下

![](../Images/374ac9da140e1cefd2ec7756a9b7dcc1.png)  

发送数据包，指定xff为：`127.0.0.1'`

![](../Images/95ef719b7857251102438034bac1a494.png)  

可以看到`127.0.0.1'`最终拼接到了 insert语句中插入数据库，造成SQL注入漏洞

![](../Images/d9fc2418123e302e94ebfcf2b4d5088f.png)

  

不过因为这里只会返回`提交失败`或者`提交成功`，没有回显，我们使用时间盲注来获取数据库中数据

  
构造payload：`127.0.0.1',sleep(5),'1')#`

![](../Images/1dba440d25862122dfe0b6810b12a7e7.png)  

延时五秒成功，获取数据库名长度

![](../Images/b986c794ea62e2dedf930079c17e8b62.png)

**0x03 文件包含漏洞**

看到这个主题配置功能点的数据（模板标题，模板描述等）之前没有在数据库中见到  

![](../Images/d355d8c14fe4cf133dfb16666410896b.png)

  

全局搜索了一下发现数据存放在主题模板目录下的`config.json`文件中![](../Images/1986cfc94851202579a7b8eea873f97d.png)

  

想到是应该包含了这个 json 文件，在源码中找了一下![](../Images/c83c2657c016ab0f65d4de4388f795c3.png)

  

跟进`load_json()`![](../Images/a6d616746f608342ca861e7c52c155f2.png)

  

看到调用了`json::get($file)`，继续跟![](../Images/2cde23dc184003ef3b3ed9dcf9289d56.png)

  

确定是调用了`require`函数进行包含。接下来的思路就是找可以修改`config.json`文件的功能点。  
找了一圈才发现该 cms 提供了一个在线插件进行修改(插件只能从官方提供的插件市场进行下载)，我在写本文的时候，官方已经将该插件升级到了 V1.1，已经不适配 cmsV1.2 版本(下面会说明)![](../Images/c9a22498dd227039d149f44343d4b96f.png)

  

安装完成后，就可以点击修改对`config.json`文件进行修改![](../Images/338418bc4aef06a1a71ba8be5dea306d.png)![](../Images/f98b133f0d7d2d2e6c4849dbe919c364.png)

  

当然直接修改会报错，因为在插件V1.1版本中的方法命名做了修改![](../Images/f13ecdb7964a30d47837585eff6ff94f.png)![](../Images/9e9665534b1e15d07158e55182b88c33.png)

  

v1.1插件版本对应的是最新版的cms源码，在最新cms版本中该处代码命名为`delSlashes()`![](../Images/461bd9fd431302d82bc87c364ec0b27a.png)

  

而cmsV1.2版本源码没有`delSlashes()`方法导致报错，而是命名为`delFilter()`![](../Images/e0ebe2e2db9edee3465a197a1322b5c7.png)

  

我们做一下修改，回滚插件代码为对应的v1.2时的情况复现当时情景

  
可以正常对 config.json 文件进行修改之后  
![](../Images/4bd4628aaf2b5a537a9487ee789b8b1b.png)![](../Images/1cd6ba746cc73ee9554950b3bf2237a6.png)

  

成功包含并且执行 php 代码

![](../Images/5135f1301542956bdd1a7b7ea3044442.png)  
写入webshell![](../Images/797c996254769cef77d956eb2be29fb0.png)![](../Images/39662cef6a37f104ce570f0551987004.png)

  

在最新版本中的修复方法是使用了`htmlspecialchars()`函数将`<、>`实体化编码成`&lt;&gt;`![](../Images/44a7301b76ca69169f26747006d9f860.png)

  

**0x04 文件上传漏洞**

前面的文件包含因为插件更新的缘故，所以现在无法利用。继续寻找别的漏洞点

  

看到一个 ueditor 编辑器，尝试附件上传 php一句话木马失败

![](../Images/e729c12ff0fbcde5dc5bffe5ebe05998.png)

  

找到对应源码![](../Images/ca31e7a7d4e7a61aab08e47cf78b51db.png)

  

关键判断为

*   

```

```

  

跟进`upload`类的`files`方法，一共有两个关键判断![](../Images/75f2699573024a2fbaa15ed2dc4bed79.png)

  

首先看判断一，判断文件后缀在不在`$type`列表里对应的后缀，而前面我们传进来的`$type=code|zip|word|excel|powerpoint|audio|text|pdf`中，code对应的后缀列表是含有`.php`的

![](../Images/b34273b127a3cd76a90fc2f73211481e.png)

  

接着看判断二，判断文件后缀在不在`$extension`数组中![](../Images/c67093e8db36053064c6450424bbfb07.png)  
`$extension`数组是从数据库表中取出，没有`.php`导致文件上传失败![](../Images/9a1c40419cc0df1f59207577efc31401.png)

  

知道了原因之后我们开始找可以修改数据库中表的功能点，最后发现有个文件上传类型可以直接更改![](../Images/47b90955ad003382b723995132624e8f.png)

  

添加上`.php`后缀保存，再上传![](../Images/6856bbc67e0955440d0c56dad8f58818.png)

  

成功上传webshell![](../Images/82c2ddf2a6d46b988aa9ba5d2853d35f.png)

  

最新版修复办法是将`$type`参数的内容改成了`null`![](../Images/5ef4ad49c493ebf9be7a8f7b9f6d6645.png)
