> 特别因为是eBPF只能通过"helper functions"调用内核能力，而不能直接调用内核函数、修改内核数据结构，所以我好奇eBPF后门怎么实现"进程隐藏"。

  

**lkm rootkit是怎么隐藏进程的**

  

通过修改 `__sys_call_table`，hook了kill、getdents64系统调用。

用户在调用kill系统调用时，rootkit在收到信号"SIGMODINVIS"(头文件中可以看到是31)后，就会执行两步：

*   for*each*process找到进程task\_struct
    
*   修改task\_struct的flags
    

1.  // diamorphine.c
    
2.  hacked\_kill(pid\_t pid, int sig)
    
3.  {
    
4.  ...
    
5.  struct task\_struct \*task;
    
6.  switch (sig) {
    

case SIGINVIS:

if ((task = find\_task(pid)) == NULL) // 根据pid找到task\_struct实例

    return -ESRCH;

8.         task->flags ^= PF\_INVISIBLE;
    
9.         break;
    

用户在getdents64系统调用查看目录信息时，rootkit会修改返回给用户的目录信息。  

1.  hacked\_getdents64(unsigned int fd, struct linux\_dirent64 \_\_user \*dirent,
    
2.  unsigned int count)
    
3.  {
    
4.    int ret = orig\_getdents64(fd, dirent, count), err;  // 调用原先的getdents64函数
    
5.  ...
    
6.    
    
7.    kdirent = kzalloc(ret, GFP\_KERNEL);   // 申请ret大小的内核内存
    
8.  ...
    
9.    
    
10.  err = copy\_from\_user(kdirent, dirent, ret);   // 将"目录信息"复制一份
     
11.  ...
     
12.    
     
13.  while (off < ret) {
     
14.  dir = (void \*)kdirent + off;
     
15.  if ((!proc &&
     
16.  (memcmp(MAGIC\_PREFIX, dir->d\_name, strlen(MAGIC\_PREFIX)) == 0))   // 文件以MAGIC\_PREFIX开头
     
17.  || (proc &&
     
18.  is\_invisible(simple\_strtoul(dir->d\_name, NULL, 10)))) { // /proc/${pid} 被标记成需要隐藏
     
19.        ...
     
20.      }
     
21.    
     
22.    ...
     
23.    err = copy\_to\_user(dirent, kdirent, ret);   // 将修改后的"目录信息"复制给用户
     

测试后，就会发现rootkit会影响 `/proc`目录中是否可以看到进程目录。

![](../Images/868350833af5518e9e3a4f76e5f0bf85.png)

实际上是rootkit影响了getdents64系统调用的结果![](../Images/203ff71445e0793106059ed5f7310511.png)

ps命令也是读 `/proc`目录来获取进程信息的，所以rootkit影响ps命令结果![](../Images/203ff71445e0793106059ed5f7310511.png)

所以这个lkm rootkit是通过修改task\_struct的flags字段来给进程打个标记，等getdents64时会根据标记判断是不是要修改目录信息。

eBPF程序不能直接修改内核数据，那eBPF后门是怎么做"进程隐藏"的呢？

**ebpf rootkit是怎么隐藏进程的?**

getdents64系统调用可以用来获取目录信息， `man2getdents`可以知道第二个指针参数指向"目录条目"buffer

```
1.  int getdents64(unsigned int fd, struct linux\_dirent64 \*dirp,
    
2.               unsigned int count);
    
```

"目录条目"数据结构如下，因为有"柔性数组"，所以用d\_reclen记录了大小，这样就可以在"目录条目"buffer中定位到下一个"目录条目"。

```
1.  struct linux\_dirent64 {
    
2.      ino64\_t        d\_ino;    /\* 64-bit inode number \*/
    
3.      off64\_t        d\_off;    /\* 64-bit offset to next structure \*/
    
4.      unsigned short d\_reclen; /\* Size of this dirent \*/  当前"目录条目"的大小
    
5.      unsigned char  d\_type;   /\* File type \*/
    
6.      char           d\_name\[\]; /\* Filename (null-terminated) \*/ 柔性数组
    
7.  };
    
```

pr0be.safe.c 注释写得很清楚，通过增大"目标进程所属的目录条目的前一个目录条目"的d\_reclen值，使得用户程序在遍历 `*dirp`结果时，就会跳过"目标进程所属的目录条目"。

```
1.  SEC("tp/syscalls/sys\_exit\_getdents64")
    
2.  int handle\_getdents\_patch(struct trace\_event\_raw\_sys\_exit \*ctx) {
    
3.    ...
    
4.    // Unlink target, by reading in previous linux\_dirent64 struct,
    
5.    // and setting it's d\_reclen to cover itself and our target.
    
6.    // This will make the program skip over our folder.
    
7.    ...
    
8.    // Attempt to overwrite
    
9.    short unsigned int d\_reclen\_new = d\_reclen\_previous + d\_reclen;
    
10.    long ret = bpf\_probe\_write\_user(&dirp\_previous->d\_reclen, &d\_reclen\_new,
     
11.                                    sizeof(d\_reclen\_new));
     
```

因为 `&dirp_previous->d_reclen`是用户空间地址，而不是内核空间地址，所以ebpf可以用 `bpf_probe_write_user` helper functions 修改 `dirp`地址中的数据。

  

![](../Images/64569558a6ac9723fdb25db57ab75b32.png)

  总结 

案例中的lkm rootkit和ebpf rootkit都是通过修改getdents64系统调用中 `dirp`地址指向的内容，使得查看 `/proc`目录信息时，看不到进程信息。

根据帖子知道，ebpf几乎不能修改系统调用的参数值或返回值。但因为 `dirp`是一个用户空间地址，所以ebpf程序可以用 `bpf_probe_write_user`修改此地址的内容。
