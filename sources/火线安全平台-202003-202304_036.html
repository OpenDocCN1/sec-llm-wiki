浙江禾连网络科技有限公司（简称“禾连健康”），2014年成立于中国杭州，是一家从体检场景切入的健康管理服务公司。目前，已完成7500万美金B轮融资，市场估值接近10亿美金，是体检领域市值领先的独角兽企业。


禾连健康CTO亲自引入洞态IAST，经过半年多的推广使用，目前公司主要业务线的测试环境已全量部署洞态IAST，并取得一些成果。本文为禾连健康CTO亲笔，主要记录了技术管理者视角下的IAST实践过程及思考。

为什么要使用洞态IAST


洞态是一个IAST产品(Interactive application security testing)，顾名思义，和其他安全产品最大不同是它是交互式的，用户对业务系统进行交互操作后，根据实际执行的代码，IAST产品就可以发现执行过程中的漏洞。一般来讲，这类充分的交互操作会发生在测试环境和正式环境，如果在正式环境使用，一般采用原理类似的RASP产品，可以对异常执行进行阻断，这时候有点像WAF，但实现原理不同；而测试环境，是IAST主要定位的使用场景，能够在上线前发现漏洞，并及时解决。

IAST落地与团队分工


安全测试可以独立进行，也可以左移放在日常迭代中，即DevSecOps。我们采用了后者，即在测试环节使用洞态，可以认为是执行了DevSecOps中的‘Sec’。


对于线上的即时防御、响应，我们交给运维团队来处理，而日常业务迭代主要由测试团队来承担，避免引入明显的安全漏洞。当然，部署和运维洞态，还是交给运维团队，测试团队作为安全工具的甲方，使用洞态并向运维团队提出需求。


洞态的部署还是很方便的，在全面k8s化的基础上，在测试镜像中统一添加洞态的agent，加上洞态对agent可以做到在线升级，基本一劳永逸地在各个业务中部署了洞态。实际跑下来，没有碰到洞态对业务接口造成干扰的情况，这点得给洞态的代码质量点个赞。


部署之后，更重要的是在各个业务小组中进行落地。研发团队目前是横纵交错的组织架构，日常迭代以纵向的、包含前后测业务小组为主，由PMO推动来执行，同时也保留了前后测的横向团队，由横向经理来推动技术、流程改进。因此，我们一方面通过PMO确定了新的项目管理流程，明确了在提测后由测试团队提供基于洞态的安全报告，确保没有引入新的漏洞，一方面对测试团队进行了使用的统一培训、答疑解惑。这样测试流程中的Sec部分就得以落地。实际执行过程中由于对测试新增的负担较低，也没有遇到什么阻力。

洞态IAST漏洞检出


应用漏洞

洞态的界面上会直接展现出应用漏洞列表，可以分项目或者按照漏洞级别进行筛选。


业务中报出最常见的就是“不安全的JSON反序列化”，由于FastJson的反序列化漏洞引起。由于FastJson使用简便，在程序员中使用度非常高，很难在各个团队都清除掉FastJson的存在，目前只能选择共存，通过升级版本或者关闭AutoType开关来规避漏洞。而在共存状态，洞态的“误报”就会很常见，因为代码确实执行到了有风险的函数。

将用户提供的数据写入 JSON 时，应该遵守以下准则：

1、不要创建名称来自用户输入的 JSON 属性。

2、确保使用安全的序列化函数（能够以单引号或双引号分隔不可信赖的数据，并且避免任何特殊字符）执行对 JSON 的所有序列化操作。

组件漏洞

洞态也提供了组件漏洞的扫描。这个功能还是很贴心的，虽然很多工具也能做，但洞态集成后，我们很自然的在测试流程就可以简单地发现是否有新的组件漏洞。


组件漏洞的识别或许相对容易，升级就没那么简单了。升级一个核心组件，需要做完善的回归测试，常常出现业务依赖了某个组件的一个bug，然后这个bug在新版本被修复了，导致业务失败。因此，升级组件是一个需要做好规划的逐步升级的过程，在此之前，收到洞态的告警，只能先看下对应的问题是否被WAF等防御工具覆盖，确保线上安全的情况下，排入升级规划。


组件漏洞另外一个难点在于，依赖的依赖怎么发现。在有洞态这类工具的情况下，我们可以很清楚地看见最终包里是否还有某一个特定依赖。例如Log4j的漏洞，开发可能在1级依赖中已经完成了清除或升级，经过检查发现仍然有该依赖，此时就是多级依赖导致的，需要进一步分析，看下能否覆盖升级掉。（注：笔者使用的洞态开源版，不支持组件多层依赖分析。洞态IAST商业版支持组件多层依赖调用分析）

遇到的一些问题


同个问题被多次报告

由于洞态这类IAST产品的实现原理，往往会出现同个问题多次报告的情况。第一种，就是URL Path参数不同，洞态会作为两个URL来处理，导致同一个漏洞被重复上报了很多遍。第二种，是切面类实现引起的，例如我们在请求拦截器中使用FastJson做了特定解析，此时所有请求都会上报该问题，形成了大量的重复数据。

（洞态IAST团队回应：目前洞态团队也正在调研如何解决同个风险被多次报告的问题。欢迎大家提供相关issue和pr。）


问题代码的定位

目前洞态提供的污点流图，和基于hook点的代码调用链图，但是研发工程师的代码如果没能hook，无法直接体现在代码调用链上。当遇到一些开发不熟悉的漏洞时，开发往往不知道从哪里查起，当落地DevSecOps流程时，测试发现问题后，开发往往无法第一时间找出fix的方法，需要上报经过其他同事一起定位，确认问题，一定程度上影响了问题解决的效率。

（洞态IAST团队回应：目前洞态团队也在调研如何定位到更多的用户代码，进一步提升研发解决问题的效率。欢迎大家提供相关issue和pr。）
