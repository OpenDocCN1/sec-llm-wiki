为什么网站突然就404了！


本文为网名：主治医生 的用户投稿


夜深人静的告警



事情发生在几天前


半夜三点左右，被一阵钉钉铃声吵醒，看到告警群传来N条信息，公司某个网站404了！！瞬间睡意全无，抓紧时间打开电脑，亲手尝试，硕大的404 NOT FOUND出现在眼前。整个人瞬间蒙了，甚至拥有了第二天带个书包去公司收拾东西的冲动。


经过几分钟的冷静，网站丢了又不是代码丢了，跑啥。迅速链接公司服务器，开始排查丢失的原因。


...此间省略一系列的排查过程，最终看到了一个奇怪的文件夹。


(下文的xxxx均为屏蔽原始文件名字而采用的替代)

/rm_file/xxxx

进入/rm_file/xxxx一看，果然！整个项目都被丢到这里面来了！能操作它的代码只有一个，那就是前些日子做的回收站功能！



业务代码查看



进入之前功能查看代码


@RestControllerpublic class ConfigController {    @RequestMapping(value="/configRemove",method= RequestMethod.GET)    public String configRemove(@RequestParam String path){        String[] buff = path.split(";");        String finalpath = buff[buff.length-1];        String npath = String.format(System.getProperty("user.dir"),"/rm_file",path);        File file = new File(path);        file.renameTo(new File(npath));    }}


finalpath 是根据入参来进行分割取的最后一条 然后定位文件进行文件的软删除


但是这条入参信息不可能存在呀，如果用户不能成功创建那么就没有办法进行软软删除操作呀，在业务理论上是安全的。


然后打开操作日志，发现了这么一条请求，入参为"/xxxx;../"


整个人瞬间恍然大明白，原来用户没有正常使用程序，也没有任何的数据创建，而是直接模拟了登陆状态，对服务器发起了一次不同寻常的请求。


这时候后端代码拿到../以后，会把整个项目当作需要删除的路径，然后将项目移动到了rm_file下。从而代理给用户的前端路径也消失了，这时候打开网站得到的就是一个404 NOT FOUND页面。


把文件mv回来，危机暂时解除。(顺带给这个接口参数加了校验，不用收拾书包了)



亡羊补牢



第二天到公司后，还是提心吊胆，担心会不会后面还有这种危险情况发生，还好这次是半夜，用户不多。如果是白天，后果不堪设想。于是在网上搜寻方案时候发现了dongtaiIAST，于是按照教程部署，在有危险的项目上测试了一下，结果发现还有其他危险漏洞，并且那个害我3点起床修代码的危险方法也被检测出来了！

事故反思



公司没有安全人员，所以对于这种安全性的细节考虑不全，但是我们研发人员更多的心思在于功能实现，并不会刻意得去注意这类风险，因此导致了这次404事件。现在在我的强力安利下，公司已经上了Dongtai IAST，分享这次经历，感谢洞态为我们这类小公司带来的便利。
