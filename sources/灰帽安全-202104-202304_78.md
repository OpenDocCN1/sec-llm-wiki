# Cisco RV路由器设备模拟仿真

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=Mzg2MjYxODQ4Mw==&mid=2247483787&idx=1&sn=44b3b12478220a252a78be378937b9b5&chksm=ce045797f973de818ca990c63e4e469b943ac16530ba22f91d13ae9f01f43581f5ae4ed849ff&scene=126&sessionid=1681667171#rd](http://mp.weixin.qq.com/s?__biz=Mzg2MjYxODQ4Mw==&mid=2247483787&idx=1&sn=44b3b12478220a252a78be378937b9b5&chksm=ce045797f973de818ca990c63e4e469b943ac16530ba22f91d13ae9f01f43581f5ae4ed849ff&scene=126&sessionid=1681667171#rd)

  

Cisco RV系列路由器是Cisco公司开发的小型家用路由器，但是其相关模拟资料非常有限，因为其具有较多的依赖，于是利用时间，对Cisco RV系列路由器模拟进行了研究。模拟平台为qemu平台，用户级别和系统级别均进行了模拟实现。

## 一、固件解包： 

固件型号：RV34X-v1.0.03.18-2020-06-11-11-55-25-AM.img  
解包方式：和传统的.bin固件不相同，通过binwalk解压img文件，会得到7z压缩格式的压缩包，继续对压缩包进行连续的解压，即可得到最后包含openwrt-rootfs.img的文件，利用binwalk解压该文件，即可获得文件系统。根据观察，也可知道该路由器固件基于openwrt开发。  
解包命令：

```

binwalk -e openwrt-comcerto2000-hgw-rootfs-ubi_nand.img  
```

得到文件系统如下：  

![](../Images/1b2c9be86c35c0dd854e7911d5a258a7.png)

##  二.固件用户级模拟： 

我们首先模拟启动路由器终端，在启动终端之前，先赋权以及挂载dev和proc目录。

```


chmod a+x bin/shbind
 /dev devbind

 /proc proc
```

  

![](../Images/16dfac9a5a3ef614fd7e94ff487f3df4.png)

为了分析路由器的启动流程，我们进入etc/init.d文件夹下分析相关启动脚本， init.d目录包含许多系统各种服务的启动和停止脚本，里面的shell脚本能够响应start，stop，restart，reload命令来管理某个具体的应用。我们查看init.d文件夹下的各个脚本文件：

![](../Images/a688857603818b6ac7db97fcdc420121.png)

我们发现init.d文件夹下有nginx服务，因此可以推测路由器的web服务框架为nginx框架，因此为了模拟路由器的web服务，我们利用脚本启动nginx服务。  

```
cd

 etc/init.d/
```

发现nginx服务没有正常启动，其中报错信息如下，有多个依赖错误，需要我们依次解决。首先是缺少confd相关服务。  

![](../Images/f5fd9d7427e29522feee4f6cc251fde9.png)

我们利用全局搜索“confd”字符串：  

```
grep -r "confd"

```

  

![](../Images/ba7163798fc65209d40a7da9f1a6cc5c.png)

发现在init.d的confd执行文件中进行了confd服务的启动，因此我们尝试启动confd服务：  

```

./confd start
```

但是启动confd时发现错误：  

![](../Images/9c207b5c7dcad9f16c5b7598924dfe7e.png)

根据错误提示我们知道是ssl相关配置证书出现问题，因此我们继续查询ssl相关配置证书的文件，发现生成默认证书：generate\_default\_cert脚本。  

![](../Images/1bd89dd3df92c4067567e812881f1acc.png)

执行该脚本：  

```

generate_default_cert
```

执行后发现提示缺少相关的uci文件：  

![](../Images/3b8f8bca8d0fa6251a0a3fb85879433b.png)

查找uci相关文件，定位到boot文件：  

![](../Images/24f9e8be3860cb2c81285533179ebcd6.png)

因此我们知道，需要先进行boot启动：  

```

./etc/init.d/boot
```

因此我们可以知道整体的模拟流程：

```

chmod -R 777 rootfscd
 rootfsbind
 /proc procbind

 /dev dev
```

当再次启动nginx服务时，发现端口被占用：  

![](../Images/5d111c6cad2ec5721f499ddf333dc1ce.png)

怀疑是之前nginx服务关闭时出现问题，相关端口没有完全关闭。因此我们重启nginx服务。  

```


./nginx stop
```

现在访问127.0.0.1，即可进入cisco登录界面。  

![](../Images/34ecead6aeff77cfd47adc73c4acdaf2.png)

  

## 三.固件系统级模拟： 

查看架构，得知路由器为ARM小端架构，因此进行系统模拟，系统模拟启用脚本如下：

```


wget https://people.debian.org/~aurel32/qemu/armhf/debian_wheezy_armhf_standard.qcow2#qemu启动
if=sd,file=debian_wheezy_armhf_standard.qcow2 -append "root=/dev/mmcblk0p2"
 -net nic -net tap,ifname=tap0,script=no,downscript=no -nographic -s#qemu网卡配置

#上传根目录文件

bind
 /proc procbind

 /dev dev
```

之后的配置脚本同用户级模拟，配置完毕后，在虚拟机中访问qemu对应IP即可进入相关的web服务。

##  四、cve-2021-1414漏洞分析 

根据网上的相关资料可知，RV340路由器存在命令注入漏洞。该漏洞位于json-rpc中，当其对snmp相关协议进行处理时，存在命令注入漏洞。我们利用qemu模拟的路由器，进入其web界面，对snmp服务进行相关操作：  

![](../Images/a3882211d06ab8936256882a5b9a6836.png)

发现在qemu模拟起来的nginx服务终端上，可以追踪到其后端的服务文件：jsonrpc.cgi：  

![](../Images/992dfb53f66791962188f56507545b2a.png)

利用ida逆向jsonrpc.cgi，定位rpc处理的相关函数：sub\_149FC，定位snmp设置，即set\_相关函数：  

![](../Images/9a47f083dfe52853d03a7e5209d1c404.png)

sub\_12D84判断请求是否非法，合法即调用sub\_13BA0进行处理，跟进sub\_13BA0函数，发现其调用jsonrpc\_set\_config函数进行配置：  

![](../Images/7b817c53c2c84b0e6bffb7decc74e241.png)

jsonrpc\_set\_config为动态链接库中的函数，我们利用全局搜索定位一下其所在的so文件，位于libjsess.so中。  

![](../Images/0cd1fda8c60f66c06bf38a5f060ed976.png)

libjsess.so中提供snmp相关服务函数，我们根据漏洞描述，定位usmUserPrivKey相关函数：  
![](../Images/b8dfc3dd80b64ffd149e3188a5b46068.png)

![](../Images/cde0366421e5b75fd9603e9712947703.png)

  
根据逆向可知，v44接收SNMP配置中的usmUserPrivKey字段内容，赋值给v19，v19通过sprintf赋值给v60，系统不做检查，直接利用popen对v60进行执行，造成命令注入。  
利用qemu模拟的web服务，更改SNMP相关配置：  

![](../Images/405e0e6ef56cf1395d798e15a5d0f428.png)

利用Burpsuite抓取数据包，将usmUserPrivKey字段修改为要执行的命令，重放攻击即可。
