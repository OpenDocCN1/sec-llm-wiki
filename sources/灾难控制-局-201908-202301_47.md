### 1.Linux LKM编写

内核模块是Linux内核向外部提供的一个插口，其全称为动态可加载内核模块：Loadable Kernel Module，简称LKM。Linux内核之所以提供模块机制，是因为它本身是一个单内核（monolithic kernel）。单内核的最大优点是效率高，因为所有的内容都集成在一起，但其缺点是可扩展性和可维护性相对较差，模块机制就是为了弥补这一缺陷。

本文并不着重讲解LKM的编写，在网络上可查的教程非常繁多，有兴趣的可以自行查找阅读。

  

### 2.Linux System Call

Linux内核提供用户空间程序与内核空间进行交互的一套标准接口，这些接口让用户态程序能受限访问硬件设备，比如**申请系统资源**，**操作设备读写**，**创建新进程**，**创建网络连接**等。用户空间发生请求，内核空间负责执行，这些接口便是用户空间和内核空间共同识别的桥梁。

在用户空间和内核空间之间，有一个叫做Syscall(系统调用, system call)的中间层，是连接用户态和内核态的桥梁。这样即提高了内核的安全性，也便于移植，只需实现同一套接口即可。Linux系统，用户空间通过向内核空间发出Syscall，产生软中断，从而让程序陷入内核态，执行相应的操作。

可以理解为我们在用户态执行的大多数对资源的申请和对资源的使用都需要借助Linux Kernel来实现，而system call就是这个桥梁。

关于Linux System Call的更详细的介绍也可以从网络上得到，本文就不多赘述了。

  

### 3.关于task\_struct

很多同学都会找到我问一个问题，就是AgentSmith-HIDS是如果获取到诸如：UID/PID/node\_name这些信息的呢？这里就不得不说task\_struct这个关键的数据结构了。

Linux内核通过一个被称为进程描述符的task\_struct结构体来管理进程，这个结构体包含了一个进程所需的所有信息，你可以理解为一个拥有当前进程的基础信息的上下文“全局变量”，在软中断陷入Kernel层的某个syscall时，我们可以通过**current**来获取该进程的task\_struct，来得到关于这个进程的相关信息，其中就包括了比如UID/PID/node name等信息。关于task\_struct具体有哪些信息，有兴趣的可以直接查看源码(这里是3.10的)：https://elixir.bootlin.com/linux/v3.10/source/include/linux/sched.h#L1034

比如当我们想要得到PID的时候，通过：**current->pid **就可以获取，namespace相关等信息也在里面，这也是AgentSmith-HIDS支持Docker的基础。

  

### 4.关于Hook syscall

关于Hook syscall网上也有不少资料，这里只简单讲一下流程。

我们首先通过编写的LKM加载到Kernel内核态，这时我们可以通过操作syscall table来实现hook syscall，比如：

```
 orig\_init\_module = (void \*)(sys\_call\_table\_ptr\[\_\_NR\_init\_module\]);
sys\_call\_table\_ptr\[\_\_NR\_init\_module\] = (void \*)monitor\_init\_module\_hook;
```

在monitor\_init\_module\_hook函数中return：

 return orig\_init\_module(umod, len, uargs);

就可以在不影响原来syscall的基础上进行Hook。

这里`orig_init_module是`原来的syscall，我们将其替换成了我们的`monitor_init_module_hook`,然后我们在`monitor_init_module_hook`中：

### 5.关于Hook connect/accept/accept4

connec是一个重要的syscall，在全部的TCP和部分的UDP网络主动连接中，都会出现，Hook connect的好处是，不用担心传输数据量的大小，我们只关注了连接(如果对connect不是很了解，可以查阅关于socket编程的基础知识)。

但是Hook中比较容易出现的问题有2个：

1.  Hook前存在**SYN\_SEND**或**SYN\_RECV**的连接，**SYN\_SEND**是表示发送连接请求后等待匹配的连接请求，而**SYN\_RECV**是指服务端被动打开后,接收到了客户端的SYN并且发送了ACK时的状态。如果在这个时候Hook替换了原来的connect和accept/accept4，那么会导致这些状态的连接返回时会返回到原地址，导致出现Kernel Crash的恶劣情况，为了避免这种情况，AgentSmith-HIDS在安装前会检查**tcp\_hashinfo**来确保没有这种情况，具体检测逻辑可以看：https://github.com/EBWi11/AgentSmith-HIDS/blob/master/syshook/LKM/syscall\_hook.c#L2211
    
2.  用过Linux Auditd的同学应该知道，Auditd Hook connect是没有源端口的，那是因为Auditd借助的Hook位置要早于connect分配端口的时间(为了有阻断能力)。但是作为以监控为主的工具，源端口还是比较重要的。因此我们可以先执行connect，再去获取信息，这时就可以得到连接的源端口了。
    
3.  同情况一，我们在退出的时候也需要注意，有没有未完成的connect/accept/accept4情况应该避免退出，这里AgentSmith-HIDS是通过增加LKM引用来实现的(**update\_use\_count&&del\_use\_count**)，具体可以看：https://github.com/EBWi11/AgentSmith-HIDS/blob/master/syshook/LKM/syscall\_hook.c#L556

### 7.关于DNS Hook

对于DNS Query 我们目前仅Hook了**recvfrom**，目前可以应付诸如：curl/ping/wget这些使用了**getaddrinfo/getnameinfo**来查询DNS的情况，但是比如nslookup这类并不是使用**getaddrinfo/getnameinfo**的，因此无法得到相关数据。

这里我们需要注意的是需要对recvfrom的数据进行解析，做一些关键偏移量的计算，并取得我们想要的DNS Query，这个按DNS协议来解析即可，具体可以看：https://github.com/EBWi11/AgentSmith-HIDS/blob/master/syshook/LKM/syscall\_hook.c#L1653
