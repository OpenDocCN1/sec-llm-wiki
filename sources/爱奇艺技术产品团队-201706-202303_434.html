插件化框架可以在主程序不重新安装的情况下，针对单个业务模块进行动态加载达到模块更新的目的，整个加载更新过程，对用户来说也是无感知的。


为什么需要插件化




在爱奇艺APP快速发展的历程中，需要插件化的原因，归结起来有以下几点：


  • 业务快速发展，代码膨胀，APP不可避免地遇到了65536的大坑


  • 代码量增大带来了APK包体积的增加，而爱奇艺APK包体积一直在竞品中保持领先地位


  • 模块耦合度高，协作开发困难，编译时间长


  • 应用频繁更新，用户粘性降低，新版本覆盖率和覆盖速度不满足业务需求


  • 新功能开发，需要支持动态升级，插件动态下发形式可以完成模块的热部署和实时更新


爱奇艺APP从2013年就开始了插件化技术的研究和改造，截止目前一共有20多个独立业务模块以插件化的方式运行和并行迭代，其中包括APP首页的奇秀、文学、电影票、漫画等业务。开发插件化框架的Demo并不是很难，但是要开发一款完善的插件化框架，兼容适配国产各种碎片化的ROM，同时满足业务需求，却不是那么容易。插件框架的稳定性和兼容性，从原有代码模块解耦到插件化的迁移成本、后期维护成本等方面都需要考虑到。本文将介绍插件化实现的技术原理，分享爱奇艺APP在插件化实践过程的解决方案。


爱奇艺轻量级插件化方案Neptune已经在Github开源，喜欢阅读代码的同学可以出门左转

项目地址：https://github.com/iqiyi/Neptune


插件化背后的技术原理




插件化技术听起来高深莫测，炫酷无比。由于需要动态加载系统未安装的APK，或多或少会用到一些黑科技。揭开其神秘的面纱，实际上需要解决的问题无非就是以下三点。

  • 代码的加载（dex，so）


  • 资源的加载 (res, assets)


  • 组件的生命周期（Activity, Service)


代码的加载


我们知道Java中类的加载都是通过ClassLoader实现的，而Android中类的加载也离不开ClassLoader机制。Android中ClassLoader主要涉及以下几个


  • BootClassLoader：用来加载系统类，Java和Android的类库


  • PathClassLoader：用来加载系统中已安装的应用程序中的类


  • DexClassLoader：可以加载指定路径的dex，apk或jar，支持从SD卡加载



在插件化类的动态加载具体实现方式上有两种机制可以选择，分别为单ClassLoader机制和多ClassLoader机制



  • 单ClassLoader机制：与Google MultiDex和Qzone的热修复原理类似，都是通过Dex前插或后插，运行时把所有插件的类注入到宿主中，插件和宿主的类全部通过宿主的ClassLoader加载。该方案代码实现简单，但是兼容性很差，容易出现类重复冲突，要求各个插件及宿主不能使用重复的类。典型代表是滴滴的VirtualApk方案。


  • 多ClassLoader机制：每个插件都有自己独立的ClassLoader，插件之间类是完全隔离的，不能直接互相访问。该方案还有一个优点，为插件的热部署提供了可能。插件需要升级时，可以直接创建新的ClassLoader加载新插件即可。典型代表是阿里的Atlas和360的RePlugin方案。


爱奇艺的Neptune框架在类加载时采用的是多ClassLoader机制，框架会为每个插件创建一个PluginClassLoader（继承自DexClassLoader）对象，负责该插件中的类的加载；同时在此基础上扩展了插件之间依赖的实现。


在爱奇艺的业务中，主程序没有使用到的一些类库，但是又需要被多个业务插件依赖，比如retrofit，rxJava，butterKnife。如果每个插件都打入这些类库，无疑增加了每个插件的包体积。我们会把这些类库做成基础插件，提供给其他业务插件依赖。在创建这些业务插件的PluginClassLoader时，其内部会持有其依赖插件的ClassLoader列表，在findClass阶段我们优先尝试从其依赖插件中去搜索类。


Neptune框架与Atlas、RePlugin方案还有一点不同的是，我们没有Hook宿主的PathClassLoader。应用类是通过PathClassLoader加载，而PathClassLoader是存在于LoadedApk中，但是LoadedApk对象是@hide的，需要反射获取LoadedApk，再反射替换PathClassLoader，我们认为风险很高。同时，还存在Android N混合编译和Android P内联优化等潜在风险，我们至始至终都没有替换宿主的PathClassLoader。


资源的加载


Android APP运行除了类还有资源，运行时需要解决插件中资源的加载问题。资源加载核心点都是使用AssetManager的@hide方法addAssetPath(),直接构造插件的AssetManager和Resource对象。当然如果插件完全不需要访问宿主的资源的话，可以使用PackageManager的公开API getResourcesForApplication()来创建插件的Resources和AssetManager对象。


try{
    AssetManager am = AssetManager.class.newInstance();
    Method addAssetPath = AssetManager.class.getDeclaredMethod("addAssetPath", String.class);
    addAssetPath.setAccessible(true);
    addAssetPath.invoke(am, pluginApkPath);
    Resources pluginResources = new Resources(am, hostResource.getDisplayMetrics(), hostResources.getConfiguration());
} catch (Exception e) {
    e.printStackTrace();
}


各大插件框架在资源处理上的差异，无非在于各个插件和宿主的资源共享和隔离上，有两种不同的策略。


  • 资源隔离：每个插件只能访问自己的资源，不能访问依赖插件和宿主的资源。


  • 资源合并：把插件的资源和宿主的资源合并到同一个AssetManager。根据合并策略的不同，可以向宿主的AssetManager添加插件的资源，也可以向插件的AssetManager中反向添加宿主的资源。该方案还需要解决宿主和插件中资源ID冲突问题。


爱奇艺的Neptune框架在处理资源上选择了一种折中的方案，归并了两种策略的优缺点。考虑到兼容性，Hook宿主的Resources合并所有插件的资源风险很高，不仅需要处理5.0以下AssetManager无法扩展资源表的问题，还需要Hook替换掉系统中所有Resources引用，在不同版本上Resources对象的位置一直在变化，而且还会遇到不同厂商自定义的Resources，特别是小米，Vivo和Nubia的手机，兼容性很差。在Neptune框架中，插件之间的资源不能互相访问，但是插件可以共享宿主的资源。


资源ID的固定


宿主依赖的android support库，fresco库，lottie库等都是aar形式，里面包含有资源，需要共享给插件业务使用。插件和宿主都是独立打包编译，并行迭代，aar在插件工程里无法直接通过provided形式依赖而保证代码和资源不打入插件apk的。我们的做法是分离aar中的Java代码和资源，分别以maven方式提供jar包和res包给插件依赖，jar包以provided，res包以compile的形式参与编译。由于两者独立打包，相同的support库资源在宿主生成的R文件中的id值会与插件中R文件不一致，导致插件在运行时找不到正确的资源。为了解决这个问题，需要保证同一个资源在宿主和插件中id值保持一样，我们的解决方案是通过生成public.xml和ids.xml文件放到/res/values目录下，使用gradle脚本固定住需要共享的资源，确保宿主和插件访问相同资源时id值一致。


资源ID的分区


完成了资源Id的固定，即使不做资源Id分区，已经能够解决大部分场景的问题了。根据目前插件资源的访问策略，优先查找插件的资源，找不到的情况下才去宿主查找。但是还是会存在一些小问题，需要优化解决。


  • compile res的方式，导致宿主的重复资源打进了插件apk里，存在冗余


  • 宿主提供的Java类里会存在一些资源的访问，而这些资源又不需要暴露给插件依赖，在插件Context环境下访问时会出现资源查找失败，需要切换上下文。


这些问题是因为宿主资源ID与插件资源ID会存在重复，导致运行时ID值指向了错误的资源。我们知道资源ID是在编译期生成的，生成规则是0xPPTTNNNN。要解决冲突需要对资源进行分区，固定PP段或TT段，由于TT段数量有限，很容易达到上限，因此采用固定PP段方式。从技术实现上，有两种方式可以做到


1.修改aapt源码实现分区，参考携程方案。该方案的缺点是代价太大，对编译流程侵入性大，严重依赖Android Gradle插件，gradle一旦升级维护很麻烦，升级适配aapt2也需要修改源码


2.Hook Gradle构建流程，直接修改resources.arsc中的PackageId。刚方案可以gradle plugin形式实现，缺点就是Android Gradle升级时接口变化，需要做一定的适配


通过资源Id分区可以解决上面提到的切换Context上下文和资源冲突问题，使用插件的Context就可以共享宿主的资源。这里要感谢Small和VirtualApk团队，我们的资源分区Gradle Plugin是参考VirtualApk实现的，目前已经兼容适配aapt2和Android Gradle Plugin 3.2版本。


与资源混淆和热修复的兼容性


插件打包Gradle工具在编译插件工程时，会自动修改R.java中引用的宿主资源Id跟宿主的保持一致，同时删除插件APK中与宿主相同的资源，并修改arsc文件中的Package Id为指定的非0x7f值。该工具修改的是资源Id，而微信混淆修改的是资源名称和路径改短，两者并不冲突。该工具处理的是资源和R.java问题，而热修复主要修复的是Java类，两者也没有冲突。


特殊资源访问


插件中通知栏使用到的自定义Layout相关资源，overridePendingTransition中实现Activity转场的动画资源，需要放置在宿主工程里，通过Resources.getIdentifier()方式访问。宿主在做资源混淆时，需要keep住这部分插件使用到的资源。


组件的生命周期


对于Android来说，很多组件都是有生命力的，类加载成功之后，还需要给它们注入活力，管理组件的生命周期。


爱奇艺Neptune框架实现了Activity/Service/Receiver的插件化，限于篇幅，这里仅介绍Activity的插件化思路。


Activity插件化


正常启动一个Activity/Service，在AMS进程会对Activity/Service的合法性进行一些校验，确保Activity/Service已经声明注册过。而插件的Activity/Service一般都没有在宿主AndroidManifest中注册，直接启动必然会出现ActivityNotFound等错误，因此需要一些黑科技骗过系统，绕开校验流程。


主流实现方案的过程都是靠欺上瞒下，坑蒙拐骗来实现，主要流派有以下几种：


  • 动态代理+Binder Hook（AMS/PMS）方式


  • 静态代理+占坑方式实现偷梁换柱

  1. Hook Instrumentation

  2. Hook ClassLoader

  3. ProxyActivity转发，手动调用Activity#attach


爱奇艺Neptune方案在Android P之前采用的是ProxyActivity转发机制。我们在坑位InstrActivityProxy的onCreate方法中，模拟系统创建Activity的流程，通过插件的ClassLoader加载插件的Activity实例，反射调用其attach方法给插件Activity注入基础信息，然后重写InstrActivityProxy所有生命周期方法，调用插件真实Activity对应的生命周期方法，从而给插件Activity注入生命力。


该方案一直运行了4年多，直到遇到了Android P的非公开SDK接口限制。我们在测试过程中发现Activity#attach()被列入了dark list，现有的插件方案完全不行了，紧急评估了其他替代方案。Binder Hook风险太高，Hook宿主的ClassLoader对现有框架改造成本太高，且在Android P还有各种不确定的风险，最终选择了Hook Instrumentation方案。因为ActivityThread#mInstrumentation的位置从Android 2.3以来从来没有变过，尽管ActivityThread类是@hide的，但是我们可以通过编译原生android.jar依赖方式直接访问，只需要反射一次就可以做到，相对风险较小且API稳定，不需要考虑各种ROM的兼容性。目前，Neptune框架已经适配Android P，可以在Android P设备上无缝运行。


插件的Context

插件化框架Neptune




经过前面对插件化技术原理的剖析，相信大家对插件化技术不那么陌生了。原理讲完了，剩下的就是真枪实战了。Neptune是爱奇艺移动端研发的一套灵活，稳定，轻量级的插件化解决方案。经过不断的研发，迭代和线上验证，目前已经完全适配了Android P，能够在数亿的设备上动态加载和运行插件APK，为爱奇艺众多的垂直业务团队提供了稳定的服务。


Neptune的特性


功能完善，支持Activity/Service/Recevier，几乎支持所有Android原生特性。由于ContentProvider使用场景较少，暂时没有支持。


  • 四大组件无需在宿主Manifest中预先注册，组件具备完整的生命周期


  • Activity：支持显式和隐式调用，支持theme，luanchMode，taskAffinity，支持透明主题


  • Service：支持显式和隐式调用，支持start，stop，bind，unbind等操作


  • BroadcastReceiver：支持静态广播和动态广播


  • 支持共享宿主的代码和资源，实现资源分区


  • 支持插件之间存在相互依赖，代码共享


  • 插件ClassLoader和资源互相隔离，避免类冲突和资源重名


  • 宿主Activity容器支持加载插件中的Fragment和View


兼容性和稳定性


  • 几乎兼容市面上所有的Android设备


  • 极少的Hook，核心Hook点只有Instrumentation和AssetManager，没有binder hook


  • 插件可以运行在独立进程，与宿主完全隔离，互不干扰


  • 插件之间类是隔离的，不会出现重复类的问题


  • 插件使用自身的AssetManager，没有Hook宿主的Resources，无需适配小米，vivo等ROM


侵入性低


  • 插件开发和开发原生APP类似


  • 插件可以依赖宿主的代码和资源，也可以完全不依赖


  • 插件和宿主可以独立打包和编译，并行迭代


  • 插件依赖宿主的资源，通过Gradle插件自动完成资源适

配和处理，对开发者透明


Neptune的架构图



Neptune整个框架实现是非常轻量级的，没有包含插件下载/安装/版本管理的逻辑，提供了PluginClassLoader，PluginContextWrapper，ActivityProxy，ResourcesProxy等基础组件实现了全面插件化。更多细节欢迎访问Github，Read the fucking source code。


插件管理中心




在Neptune框架之上，爱奇艺APP针对插件业务，实现了一套完备的插件管理方案，负责插件的下载，安装，升级，版本管理，插件启动控制，插件与宿主之间的通信。由于这部分涉及具体APP业务的交互形态，且与后端数据结构关联，因此没有开源。


这里简单介绍下设计思路。对于每一个插件版本数据，在APP层是一个OnLineInstance实例，里面字段与后端数据结构保持一致，包含基本的插件包名，插件版本，插件依赖，还包含一些下载控制策略，patch升级策略等。APP层的OnLineInstance，对应于Neptune框架的PluginLiteInfo。由于一些插件可能会来自不同的地方或者配置不同的版本，如内置插件，本地缓存的旧版本插件，线上最新插件。因此在APP层一个插件业务会关联多个OnLineInstance，我们会选择最高版本的兼容插件进行升级，安装。


插件实例状态机

一个插件OnLineInstance从初始状态（OriginalState)到可用状态（InstalledState)有一套严格的状态机演变。版本不兼容的插件实例会被下线，优先使用本地已安装版本，空闲时机下载升级最新的插件，尽量做到让用户使用无感知。



插件增量更新


插件包体积越大，下载成功率和转化率越低，为了提高插件升级的覆盖率和成功率，我们采用了增量更新的机制。插件后台更新插件时，后台会基于历史版本插件生成增量的diff包。APP端在请求插件数据时，后端接口额外返回增量patch的url及生成patch所有的base插件版本。前端根据本地已安装插件的版本，选择使用patch增量合成新版本插件apk还是走全量下载新插件，优化网络下载流量。


总结



截止2018年，Android插件化在国内已经发展了好几年，各种方案百花齐放。但是在业务快速迭代的过程中，只有适合自身业务需求和特点的插件化方案，没有最完美的解决方案。限于篇幅，本文只是分享了爱奇艺APP在插件化实践上积累的经验，无法呈现所有的设计细节，感兴趣的同学可以关注Neptune项目。

随着Android P的到来以及Google对Android系统政策的逐渐收紧，插件化方案还能运行多久，我们只能继续带着镣铐跳舞，拭目以待。
