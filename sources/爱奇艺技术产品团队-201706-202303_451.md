背景

  

  

    与数据存储系统交互是后端web服务中不可或缺的一个环节。在Java生态中，基于SSM(Spring+SpringMVC+MyBatis)或SSH(Spring+Struts+Herbinate)搭建后端web服务系统已成为主流。以SSM框架为例 ，MyBatis是一款优秀的持久层框架，支持定制化的SQL、存储过程和高级映射；避免几乎所有的JDBC代码和手动设置参数及获取结果集。Spring整合MyBatis后，由Spring统一管理数据源的连接、关闭、动态切换，SQL session的创建和关闭，事务管理等，使得开发者可以专注于业务逻辑开发。

  

      随着NoSQL系统的兴起与不断完善，很多业务场景下，使用NoSQL系统存储数据与查询数据，较使用传统关系型数据库，在存储数据量和查询、更新效率等方面有极大的提升。随之而来的问题是，后端服务代码中需要整合、接入各种NoSQL系统（比如Redis，Couchbase，ES，MongoDB，HBase等等）。开发者需要调用不同NoSQL系统的客户端进行数据操作，不同客户端之间的配置方式，连接方式以及方法调用方式都不尽相同。这时，我们希望使用一种数据接入层，既可以屏蔽底层存储系统的差异，对开发者提供一套统一的API处理基本的CRUD操作，又可以保留不同存储系统的差异性，使开发者可以灵活地使用不同存储系统的特有功能操作数据。这样可以减少开发工作量，大大提高开发效率，并且保持代码结构的一致性，提高代码可读性。对于Java开发者而言，我们还希望这种数据接入层可以很方便地与Spring框架进行整合，符合以往的开发习惯，降低开发成本。

  

    本文介绍一种数据接入层框架—Spring Data，并且以接入ES为例讨论了如下四方面内容：

*   Spring Data的特性
    
*   Spring Data的应用场景
    
*   整合Spring Data的实践经验
    
*   Spring Data Repository的加载原理
    
  

什么是Spring Data

  

  

     

    Spring Data是Spring项目下一个用于简化存储层（包括关系性数据库和非关系型数据库）访问，并支持云服务的开源框架。该框架的主要目标就是对于不同数据存储系统，提供基于Spring的一致的数据访问模型，同时保留各存储系统的特殊性。Spring Data下包括众多子项目，对接不同数据存储系统，比如Spring Data Redis，Spring Data Elasticsearc，Spring DataCouchbase等等

Spring Data的特性

  

  

  

    大部分Spring Data子项目都提供了以下三方面的功能：

  

*   存储数据结构到Java类的映射（类似MyBatis中的Model）
    
      
    
*   Repository接口（类似MyBatis中的Mapper接口）
    
      
    
*   Templating
    

  

    其中，Repository提供了一套统一的接口实现方式，包括基本的CRUD操作，条件查询，排序、分页查询等，同时又保留了底层数据存储系统的特性。使用Spring Data Repository进行条件查询时，开发者仅需要按照一定的规范声明接口即可，不需要实现具体的查询方法。Spring Data会根据底层数据存储系统，在运行时自动实现真正的查询方法（该过程对开发者透明），执行查询操作，返回结果数据集。

    其中，Repository接口仅作接口声明；CrudRepository接口中声明了最基本的CRUD操作；PagingAndSortingRepository接口提供翻页功能；ElasticsearchCrudRepository是空接口，仅作接口声明；ElasticsearchRepository继承上述接口，增加了Elasticsearch独有的index，search等操作接口声明。开发者需要做的只是继承ElasticsearchRepository并声明相应的CRUD方法即可。

  

    通过基于Repository接口声明方法的方式，可以很方便的自定义各种条件查询方法，但是对于插入/更新操作的支持却比较单一，只能插入一条新纪录或者批量插入新数据。如果我们想实现ES中的upsert操作，或者基于脚本的局部更新操作，通过Repository接口声明是无法实现的。  

  

    这时，我们就可以使用Spring Data提供的Templating功能完成复杂的数据操作。回忆下之前的Spring Data项目结构示意图1，每个Spring Data子项目在启动时都会初始化对应的Template，Repository接口内部实现其实是对Template功能的封装，所以Repository中的功能是Template功能的子集。而Template本身又是对存储系统client的封装，所以Repository无法实现的功能，可以通过直接操作Template实现。

  

Spring Data的应用场景

  

  

  

    基于Spring框架的项目在处理业务逻辑和数据存储系统交互的场景中，无论是关系型数据库，还是NoSQL数据系统，都可以考虑使用Spring Data做为数据接入层。尤其当项目中需要接入多种数据存储系统时，Spring Data的特性使得开发者利用一套Repository接口就可以对接各类底层数据存储系统，完成基本的CRUD操作；与此同时，每个子项目初始化的Template又使开发者可以执行复杂的或某个数据存储系统独有的数据操作方法。

  

  

整合Spring Data的实践经验

  

  

  

    现在我们以Spring Data Elasticsearch为例，说明在Spring应用中如何整合Spring Data。

    首先，在applicationContext中配置ES连接：

  

1.  <!-- 声明Repository接口包名 -->  

2.  **<elasticsearch:repositories** basepackage\="com.qiyi.project.Repositories.es"**/**

**   >**  

3.  <!-- 配置ES连接参数 -->  

4.  **<elasticsearch:transport-client** id\="client" clusternodes\="${es.cluster.node

   s}" cluster-name\="${es.cluster.name}"**/>**  

5.  <!-- 初始化ES template -->  

6.  **<bean** name\="elasticsearchTemplate" class\="org.springframework.data.elasticsearch.core.ElasticsearchTemplate"**\>**  

7.      **<constructor-arg** name\="client" ref\="client"**/>**  

8.  **</bean>**  

  

其中Repositories标签用来指明Repository接口所在的包名，项目启动时会自动扫描该包名下的接口，作为Repository接口进行初始化。  

  

然后，定义实体对象类，每个实体对象类的实例对应ES中的一条记录。实体对象类需要加上@Document注解，用于指定index和type。如下所示定义了一个Article实体类，它在ES中的index和type分别为blog和article，每条记录有两个field，分别为title和authors，@Id用于指明记录的唯一id。

  

1.  @Document(indexName = "blog",type = "article")  

2.  **public** **class** Article {  

3.      @Id  

4.      **private** String id;  

5.    

6.      **private** String title;  

7.    

8.      @Field(type = FieldType.Nested)  

9.      **private** List<Author> authors;  

10.}  

  

    第三步，声明需要用到CRUD接口方法。如下是ArticleRepository接口的声明，除了声明了插入（save）和删除（deleteAll）方法之外，还声明了一个自定义的条件查询方法findByTitle()。该方法从ES中查询title等于入参的全部记录并返回。

  

  

1. **public** **interface** ArticleRepository **extends** ElasticsearchRepository<Article,S

   tring> {  

2.    

3.         List<Article> findByTitle(String title);  

4.    

5.     <s **extends** Article> S save(S entity);  

6.    

7.      **void** deleteAll();  

8.  }  

  

    最后，我们在Service中注入Repository，直接调用Repository中声明好的方法，即可完成ES数据的CRUD操作，得到结果数据集。

  

1.  @Autowired  

2.  **public** ArticleRepository articleRepository;  

3.    

4.  List<Article> articleList = articleRepository.findByTitle("XXX");  

  

    至此，我们完成了在Spring应用中整合Spring Data Elasticsearch。从上述过程中可以看到，无论是基本的CRUD方法还是自定义条件查询方法，作为开发者只需要声明方法名即可，不需要实现方法。需要注意的是，对于自定义方法的声明需要按照一定规范，比如查询方法需要以findBy开头，字段名也需要和type中的字段名保持一致，整个方法命名需要符合驼峰式命名规范等。如果熟悉MyBatis中的Criteria条件式，会发现自定义条件查询方法命名方式与Criteria条件式编写是非常类似的。

  

    对于比较复杂的条件查询，Spring Data还支持基于注解的接口方法声明方式。只需要在接口方法声明上加上@Query注解即可，查询语句写在@Query注解中，上述条件查询也可用如下方式声明：

  

1.  **public** **interface** ArticleRepository **extends** ElasticsearchRepository<Article,S

   tring> {  

2.        

3.      @Query("{"constant\_score":{"filter":{"bool":{"must":\[{"term":{"title":"?0"}}\]}}}}")  

4.      List<Article> findByTitle(String title);         

5.    

6.  }    

  

当然，我们还可以使用ES Template来实现同样的条件查询：  
  

1.  CriteriaQuery criteriaQuery = **new** CriteriaQuery("title").is("XXX");  

2. List<Article> articleList = elasticsearchTemplate.queryForList(criteriaQuery

  ,Article.**class**);  

  

Spring Data Repository加载原理

  

  

  

我们可以看到，在使用Spring Data进行简单的CRUD操作时，开发者仅需要按照一定规范声明接口方法即可，不需要具体实现方法；Spring Data框架会根据底层存储系统，自动为我们实现对应的接口方法。接下来以Spring Data Elasticsearch为例，简单介绍下Spring Data Repository的自动加载原理。

  

由于我们在配置ES连接的xml文件中指定了Repository接口所在的包名，在项目启动的时候，Spring会扫描指定包名下的接口，并使用动态代理类的方式对Repository接口进行实例化，放到Spring容器中备用。

  

在实例化Repository接口的过程中，类RepositoryFactoryBeanSupport和类RepositoryFactorySupport起到了重要作用。

    其中，RepositoryFactoryBeanSupport作为一个适配器，可以使我们方便地通过Spring配置设置Repository工厂。RepositoryFactoryBeanSupport类中持有一个RepositoryFactorySupport类型的私有变量factory 。在执行RepositoryFactoryBeanSupport.afterPropertiesSet()方法时，通过createRepositoryFactory()方法，实例化一个ElasticsearchRepositoryFactory，赋值给factory。在afterPropertiesSet()方法最后，调用了initAndReturn()方法，这个方法的作用是返回之前已初始化的Repository代理；若之前没有初始化的话，初始化并返回，核心代码如下所示：

1.  /\*\* 

2. \* Returns the previously initialized repository proxy or creates and returns 

   the proxy if previously uninitialized. 

3.  \*  

4.  \* @return 

5.  \*/  

6.  **private** T initAndReturn() {  

7.    

8.           Assert.notNull(repositoryInterface, "Repository interface must not be nu

   ll on initialization!");  

9.    

10.    **if** (**this**.repository == **null**) {  

11.        **this**.repository = **this**.factory.getRepository(repositoryInterface, customImplementation);  

12.    }  

13.  

14.    **return** **this**.repository;  

15.}  

     

  再看RepositoryFactorySupport.getRepository()方法，该方法中主要为Repository接口生成动态代理。  

  

其中比较重要的一个Advice交由QueryExecutorMethodInterceptor的实例来处理。在这个拦截器中，首先获取QueryLookupStrategy的实例和queryMethods，然后遍历每个queryMethod，调用QueryLookupStrategy.resolveQuery()解析查询方法，最后把解析完成的queryMethods放在一个ConcurrentHashMap中。

  

ElasticsearchRepositoryFactory实现了自己的resolveQuery方法，会返回两类RepositoryQuery，ElasticsearchStringQuery和ElasticsearchPartQuery。被@Query注解的查询方法属于ElasticsearchStringQuery类，而开发者自定义的条件查询方法属于ElasticsearchPartQuery类。时序图如图5：

  

![](../Images/553b13b0e8daa605693ca91c8ffbb892.png)

图5

  

ElasticsearchStringQuery和ElasticsearchPartQuery都实现了RepositoryQuery中的execute方法。当业务逻辑中调用Repository中声明的方法时，实际调用的是已初始化好的Repository的动态代理类，触发QueryExecutorMethodInterceptor.invoke()方法，该方法会从之前设置好的记录query方法的ConcurrentHashMap取出对应查询方法的RepositoryQuery，执行execute方法，进行实际的数据查询操作。  

  

例如，当业务逻辑中调用自定义的条件查询方法时，实际调用的是一个ElasticsearchPartQuery实例，而该实例中已初始化了文本解析器PartTree。执行execute()方法时，会首先利用PartTree解析自定义方法声明，生成对应的ES条件查询语句，执行查询操作，返回结果数据集。时序图如图6：

总结

  

  

  

随着NoSQL系统的兴起与发展，为了满足业务需求，后端web服务需要接入不同的NoSQL数据存储系统。本文介绍了数据接入层框架Spring Data的特性和应用场景，并且以Spring Data Elasticsearch为例，分享了项目中整合Spring Data进行基本CRUD操作的实践经验。最后，本文还通过分析Spring Data源码，简单阐述了Spring Data Repository的加载原理。
