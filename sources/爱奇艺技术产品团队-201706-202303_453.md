# 爱奇艺的工作流调度系统——Gear

关键词

  

**作业调度 工作流**

导语

  

Gear 是由爱奇艺云平台开发的工作流调度系统，负责定时任务、工作流的调度和管理。Gear 的设计初衷是为了解决 Hadoop 上的任务调度，目前已经管理了大部分 Hadoop / Spark 任务，也应用到一些与 Hadoop 无关的定时任务管理上，目标打造成爱奇艺内部通用的定时任务、工作流管理平台。本文将把 Gear 的产品设计和技术架构分享给读者，欢迎各位一起探讨。

  

为什么要建立 Gear？

  

在爱奇艺内部，使用 Hadoop 的业务线众多，无论是 HDFS 还是 YARN 都承载了大量的访问请求。2015 年底的时候，Hadoop 集群上每天大约要运行 15 万个作业。这么多作业跑在集群上，本身就给业务线同学带来了一些监控和运维负担，更何况其中大量的作业是有依赖关系的，下游业务线只能通过脚本不断地检测上游数据是否到位，然后才能运行自己的作业。业务线同学还必须在脚本中考虑作业运行失败的情况，编写重试以及报警逻辑。

对于 Hadoop 运维同学，这种情况也是非常令人头疼的。当时大量出现的情况是，Hadoop 作业因为集群、业务、以及上游原因导致没有运行或运行失败，都会引起业务线同学的报障，运维压力很大。而且一旦出现问题，业务线同学只能手动重跑任务，这不仅麻烦，容易出错，也可能导致任务堆积，进而影响 Hadoop 集群的稳定性。Hadoop 集群作为一个类生态系统，也有它自我净化的能力的限度，因此一个合理的任务编排显得尤为重要。

  

Gear 的主要功能

  

Gear 的主要功能包括以下几点：

*   作业管理：Gear 提供了 Web 界面和 Java SDK 来管理用户的作业，包括启动、暂停、恢复、停止、重跑、补跑等，也支持查看（或获取）运行状态、进度和日志等
    
*   定时启动：与 Linux 的 crontab 类似，用户通过定义 cron 表达式来描述定时启动的逻辑
    
*   依赖管理：包含两方面含义，一是定时任务启动前的依赖检测（如 HDFS 文件或目录、HTTP URI 等），二是任务之间的依赖关系管理，以 DAG（Directed Acyclic Graph，有向无环图）的形式展现
    
*   报警机制：包括工作流的失败报警，以及 SLA 报警（规定时间内未启动、规定时间内未结束、运行时间过长）
    
*   重试机制：包括单个任务失败后的自动重试，可配置最大重试次数和重试间隔
    
*   高可用性：Gear 的每一个环节，包括工作流引擎、后台服务、任务执行机，都提供了高可用方案，确保用户的任务执行不受单点故障影响
    
      
    

产品交互设计和技术选型

  

同时，我们从以下几个方面对几款主流的开源工作流调度系统进行了深入的研究与对比：

*   功能性
    
*   用户交互便利程度
    
*   可扩展性
    
*   社区活跃度
    
*   文档完善度
    

综合考虑之后，我们认为 Apache Oozie \[1\] 最适合我们使用。Oozie 是 Apache 社区开源的一款工作流调度系统，主要用于管理 Hadoop 作业，它的功能性、可扩展性、社区活跃度和文档完善度都非常好。但 Oozie 的缺点也很明显，就是使用起来比较困难，用户需要理解各种繁杂的概念，不容易上手。因此，我们决定选择 Oozie 作为 Gear 的工作流引擎，并且对其进行封装和二次开发，一方面提供新的用户交互方式，另一方面也扩展 Oozie 的功能。

下面分几个方面介绍一下 Gear 的产品交互设计。

（1）工作流定义语言 —— 基于 YAML 的配置文件

Oozie 的工作流定义是用 XML 语言书写的。XML 格式尽管严谨，但编写起来效率太低，有大量冗余。另外，用户需要对 Oozie 足够了解，才能写出符合需要的工作流定义，因此学习成本较高，不适合我们这样有大量用户的情况。于是，我们基于时下流行的 YAML 序列化语言创建了一套工作流定义语言，大幅简化了 Oozie XML 配置，消除了冗余。YAML 是目前比较流行的序列化语言，因为其可读性强，多用于书写各种配置文件。另外 YAML 和 Java 对象的相互转换方便，且可扩展性强。Gear 的工作流定义语言除了能够表示各种参数配置外，还能够表示工作流的 DAG 图，即顺序执行（sequence）和分支执行（fork / join）逻辑，具体的语法在这里就不展开介绍了。

（2）代码托管和提交方式 —— GitLab + CI 自动提交，Workflow-as-Code

Gear 作为工作流调度系统，需要提供一种提交工作流的方式，最好还有版本管理功能。GitLab 是一个可以借助的平台，我们给用户提供了 GitLab 上的 CI（Continuous Integration）脚本，当用户把工作流定义文件（YAML）push 到 GitLab 后，就会自动运行 CI 脚本，将变更提交进 Gear 后台。这样做的好处是，版本管理和 Code review 都可以不费力地实现了。将工作流配置提交进代码库即能自动同步到 Gear，我们将这种方式称为 Workflow-as-Code。

（3）工作流管理方式 —— Web 页面

将工作流提交进 Gear 之后，相当于将任务注册到了 Gear 中，实际并没有运行。此时，用户可以通过 Web UI 来查看自己提交的工作流，点击运行。之后的管理操作（查看、暂停、恢复、停止、重跑等）都可以通过页面来进行。

  

技术选型方面，Gear 通过对 Oozie 进行封装和二次开发，来实现上述交互设计，也增加一些开源版本的 Oozie 所不具备的功能。

Gear在爱奇艺的实践

  

**Gear 1.x（2016 年 5 月 ~ 2017 年 8 月）**

  

在 Gear 出现之前，公司内部大量的 Hadoop 任务（MapReduce / Hive / HBase）都是直接通过 shell 脚本提交的，使用 crontab 定时执行。为了让用户能够以最低的代价快速迁移，Gear 1.x 主要支持了 SSH Action，即工作流的节点均为 SSH 任务。用户只需要编写一个工作流定义文件，即可构建工作流 DAG，并复用之前的脚本，在原有的机器上执行。

![](../Images/923eaeeb50bd759d931a5fc137b9adc5.png)

这种方式的最大好处是用户迁移代价低，可以保留之前的脚本，不需要完全重做。但是，这也带来了一些问题。首先，用户的脚本中包含一些检测和重试逻辑，这部分和 Gear 的功能有重合。其次，一般来说，工作流系统无法获知用户的 Shell 脚本具体在执行什么程序，是 MapReduce、Hive 还是 Spark。针对这个问题，我们做的一个改进是，将 Gear 和用户 shell 脚本中提交的 YARN App 打通，这样既可以从 Gear 工作流查询到具体的 App，也可以从 App 追溯到提交来源。为了实现工作流脚本和 YARN App 的打通，我们采用的技术方案有两个要点：一是通过环境变量传递，将工作流 ID 等信息传给用户脚本；二是修改 App 提交代码，在提交前先向 Gear 注册，并设置 App 的 configuration，这样 Gear 就能把 App 和工作流双向关联起来了。  

在实际使用中，我们也发现了 Oozie 在工作流组织方面的不足。用户需要提交和管理大量的工作流，这些工作流分别属于不同的项目，有不同的负责人。Gear 在 Oozie 的基础上增加了工作流负责人、项目、描述、标签等字段，方便用户进行工作流的管理。另外，Gear 还接入了爱奇艺内部的报警平台，将在工作流定义中指定报警接收人的模式，修改为发送和接收解耦的订阅模式，并支持用户订阅一整个项目下的所有工作流，增加了使用的便利性。

**对 Oozie 引擎的改进**

  

Gear 对所依赖的工作流引擎 Oozie 进行了多项改进，这里介绍三个，分别是 SSH 任务负载均衡、工作流节点失败后继续运行非依赖的节点、支持基于 HTTP 等协议的前置依赖检测。

SSH 任务负载均衡

SSH 任务依赖于用户指定的机器，一旦这台机器不可用，部署的任务都将无法执行。另一方面，将越来越多的任务部署到有限的机器上，会使得机器的压力越来越大。因此，我们做的一个改进是，实现了 SSH 任务的负载均衡。Gear 支持用户指定多个 host，任务运行时会根据机器的负载情况以一定概率随机选择一台。随机选择的大致思路是，负载相近的机器被选中的概率也相近，负载相对越高的机器被选中的概率就越低。

工作流节点失败后继续运行非依赖的节点

我们知道，一个顺序执行的工作流 DAG 表示任务节点之间有相互依赖关系，当前一个任务失败时，后一个任务从逻辑上无法被执行。很多时候，一个工作流有多条并行执行的通路，他们之间相互没有依赖关系，但属于同一个业务，因此放在了一个工作流中。在默认的逻辑下，一旦工作流的某个节点失败，Oozie 会 kill 整个工作流，不考虑其他节点对这个失败的节点是否有依赖关系。

  

我们通过修改 Oozie 源码，对这一行为做了改进。我们将默认的方式改为，在某节点运行失败后，继续运行其他无依赖关系的节点，直至该工作流没有其他节点可以运行，才 kill 整个工作流。

支持基于 HTTP 的前置依赖检测

首先介绍一下前置依赖检测的含义。在定时工作流的每个运行实例开始之前，用户可以通过配置一个或多个 URI 作为该工作流的前置依赖，当所有依赖都准备好的时候才开始运行，否则将继续等待。Oozie 原生支持的 URI 类型有 HDFS 和 HCatalog，前者可以支持 HDFS 文件和目录的依赖检测，后者可以支持 Hive 元数据的依赖检测。

  

在实践中我们发现，这两种依赖类型有时不能满足业务需求。一些时候依赖数据存放在 MySQL 中，另一些时候依赖的是 HDFS 上特定文件的个数，而不是某个文件或目录。想要将如此多样的逻辑仅用一个 URI 来表达是非常困难的。

  

针对这个问题，Gear 支持了基于 HTTP 的前置依赖检测，具体的逻辑由业务方的 HTTP 服务来实现。用户只需要配置一个 HTTP URI 和返回内容中标识检测成功的关键词，即可实现这一依赖。这样一来，Gear 前置依赖检测的能力就大大扩展了。

**Gear 2.x（2017 年 9 月以后）**

  

随着 Gear 在爱奇艺内部的广泛使用，以及为大数据开发平台的批处理模块提供基础服务支持，我们开发了 Gear 2.x 版本。下面具体介绍几个 2.x 版本的新特性。

多种任务类型支持

从 2.0 版本开始，Gear 逐步支持了多种任务类型，包括 MapReduce、Hive、Spark、Shell、CheckFile、DistCp、Impala、Kylin 等。这些任务类型一部分是 Oozie 原生支持的，另一部分是我们在 Oozie 的基础上二次开发支持的。针对这些任务类型，Gear 也提供了更友好的 YAML 定义格式。有了多种任务类型的支持，用户可以直接在工作流中配置各种类型的任务节点，而不必额外准备执行机器、写执行脚本了。  

支持定时工作流之间的依赖

社区版的 Oozie 管理依赖的方式有两种，一种是工作流内部的依赖，以 DAG 的形式表示；另一种是定时工作流可以依赖某一个外部 URI，如 HDFS 文件或目录。实际使用中我们发现，用户有时候不希望把一个工作流 DAG 做得太大，而是希望拆分成各个相互依赖的模块工作流，并且能够上下游联动重跑。针对这个需求，Gear 的开发团队研究了 Oozie 本身支持的依赖检测逻辑，最终用扩展依赖检测的 URIHandler 的方式实现了这一功能。使用这一功能，不仅无需 HDFS done 文件标识，还能够很容易地找到一个工作流的上下游工作流。

工作流内部并行度控制

一个工作流内部可能会有很多相互平行的作业，如果用一个 fork 节点就会同时启动，如果用顺序执行，则可能一个作业失败影响其他作业的运行。为解决这个问题，Gear 的开发团队通过修改 Oozie 启动任务的机制，引入了工作流内部节点级别的并行度控制。用户可以通过指定并行度，来控制最多允许多少个节点同时运行。

Hadoop 作业集成

即便 Gear 是一个通用的工作流调度系统，也不影响它与 Hadoop 做更好的集成。用户经常会关心这几个问题：

*   我的工作流节点背后运行了哪几个 Hadoop 作业？
    
*   反过来，这个 Hadoop 作业是哪个工作流的哪个节点提交的？
    
*   这些 Hadoop 作业运行时间多长？每天的变化趋势如何？
    
*   这些 Hadoop 作业消耗了多少资源？
    

针对这些问题，我们在 SSH、MapReduce、Hive、Spark 等任务类型上提供了 Hadoop 作业集成的支持，即记录下这些作业提交了哪些 Hadoop 作业，并在 Hadoop 作业的配置中记录下 Gear 工作流和节点的 ID。有了这些数据作为支撑，既方便了用户查看任务运行情况，也为以工作流为单位的资源审计提供了支持。

  

Gear 未来的规划

  

未来的 Gear 将在拓展 Oozie 的调度功能和增强使用便利性两个角度继续深化，如更丰富的工作流执行逻辑和前置依赖逻辑、工作流集群间切换、工作流优先级调度等等。
