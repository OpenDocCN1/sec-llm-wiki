前言


维基百科中关于APK的定义：Android应用程序包（Android application package，APK）是Android操作系统使用的一种应用程序包文件格式，用于分发和安装移动应用及中间件。


爱奇艺拥有庞大的用户群，版本的更新迭代速度非常快。源源不断的新需求的提出，使得客户端功能日益完善与强大的同时，不可避免的遇到了APK体积膨胀的问题，会一定程度上影响到了用户体验。


为了能够有效地量化分析APK构成细节，摸清各个业务部分对于APK的贡献比例，进而针对性的制定精简计划，同时也为了定期量化各个部分的精简程度，我们对APK各部分构成进行了详细的研究。基于这些研究结论，我们开发了一套详细的分拆方案dexSplitter，用来持续监控各个版本的增长细节。


本文将介绍在爱奇艺我们是如何具体分析解决这个问题，并具体给出了设计思路与实现步骤。 核心部分简化后，开源在了github上，喜欢看代码的同学出门左转。项目地址: https://github.com/iqiyi/dexSplitter

核心问题点



APK的文件结构，基本可以划分如下:

  • AndroidManifest.xml 程序清单文件

  • assets 静态资源文件

  • META-INF 签名信息，证书信息等

  • res 资源文件

  • classes.dex 虚拟机可执行文件

  • resources.arsc 资源索引表


分拆APK的主要思路在于资源（res，assets）与源码部分（classes.dex）部分。 Android已经提供了AAPT套件，最新版本是AAPT2(有个惊喜是可通过package-id进行资源分区，再不用hack了...)，可以通过它来分析资源部分。这一点，不作为本文讨论重点。 最大的难点在于classes.dex的分拆。


设计与实现



现有分析方案


有些APP架构设计天然就具备衡量各业务占比的功能，比如阿里开源的Atlas，携程开源的DynamicAPK等，其基本思路是将各个业务模块拆分成类似so文件（内容包含资源与源文件，本质为zip文件），然后框架层面支持解析，并可动态加载这些so文件。这种架构类型app分析各业务占比，比较得天独厚，可以直接查看so文件。


但绝大部分APP采取的仍是Google提供的源生multidex方案，实现多Dex的加载。源代码部分会被自动的编译成多个Dex文件。


从Android编译原理分析，Dex文件生成过程，可简单抽象为以下二个关键步骤:

  • java 文件转换成混淆的 .class 文件

  • class 文件转换成dex文件


常见的dex分析工具：

dex2jar等工具逆向化dex文件为jar文件
jd-gui等工具查看源码


既然Dex文件是可以逆向化的，通过逆向化工具可以得到jar文件。 理论上可以分析出jar文件所包含的class文件与工程源文件之间的对应关系。从这个角度去分析实施，可不可行呢？答案是否定的。


由于Dex生成过程的特殊性，Dex生成经过了混淆，压缩，优化过程，相同特征值会被合并，即便分离出各class，并实现与源文件的一一对应，也无法确定各部分经过dx工具处理后实际占比情况。与这个思路相仿的，还有以源文件代码量占比作为分析手段，这个思路，也同样面临上述问题。

技术思路



具体实现方法：


我们从系统生成maindex的设计思路里，想到了灵感。Android为了保证App可以正常的启动，设计了一个multidexkeep的文件，里面配置的是一些必须在Application生命周期加载的类文件，通过这些配置文件，将一些必要的类加载到maindex中。


我们可不可以也设计一个类似的配置文件，将各业务模块的class类，也加入到一个类似的subDexKeep配置文件中,生成与之对应的subDex。有一点需要注意的是，通常放入multidexkeep清单里的都是不混淆的文件（这通常是为了避免ClassNotFoundException）,但subDexKeep中配置的大部分class类应该都是混淆过的，因此需要一份mapping文件去匹配生成这个混淆后的配置文件。


设计实现



首先，通过Andorid正常的打包流程，生成mapping文件，按照不同的业务模块对类名进行分类，并与mapping文件匹配后，放到一个配置文件里。 其中class文件种类:

各工程自身源代码（src目录）

  • Libs/*.aar（内含*.jar）

  • build.gradle 直接引入的*.aar（内含*.jar）

  • Libs/*.jar 

  • 需要指出的是，mapping文件通常比较大，而我们仅需比对class字典即可，所以我们第一步是对mapping文件进行了初步的精简，仅保留所需的class部分。另外mapping中包含了大量的内部类，好在我们可以根据$标识，筛选出他们。


然后我们修改了dex生成工具，使其像支持识别Google原生的maindex标识一样，具备识别配置文件里分类标识的能力，并按照分类标识，生成对应的dex文件。

基本的干预思路如下： 

图1


两种实现的思路，一种相对方便，直接去修改dx工具，对应的文件是dx.jar（业界有不少技术大咖们提供了编译各种Android工具的教程），具体来说，先去下载Android Framework dx部分源码（dexSplliter提供了修改后的源文件，并给出了修改说明），然后定制开发。优势在于轻量，源码比较少，按需生成dex文件后，结合dex2jar等工具也可以分析出各dex具体属于哪个业务模块。


第二种是直接去修改gradle编译工具（android.tools.build.gradle）源码 ，好处在于除了以上修改外，还可以修改打包阶段的命名逻辑。


基于第二种思路，因Android在打包阶段对dex文件进行了重命名，我们简单修改下这部分逻辑，使其保持我们原定的业务分类命名，最后生成的dex文件的大小就是各业务源代码在最终app包里的大小。


最后根据Google提供的开发套件，分拆出各部分资源的分布情况，两者结合起来，就能分析出app包中各部分总体的贡献率。

结果来看，按照dexSplliter拆分后，dex总体大小稍稍变大了些，这是因为之前提到的dex的生成过程，经过了合并、优化、重组，dex拆分数量变多，最终dex总体大小也会略有增加。我们计算过，dex总体变大了约5%-9%（取决于拆分业务粒度与业务代码重复度），平摊到各个模块上，这个误差可以接受。

收益


通过dexSplitter,持续监控IQIYI客户端多个版本apk体积变化，详细分解了如泡泡，基础库，播放器，支付模块等业务模块，按照代码与资源相对apk整体贡献比每个版本出具量化报告。 为科学量化与严格监控客户端包体积变化提供了有效数据支撑。

限于篇幅，本文无法将所有设计都呈现出来，比如dex文件生成过程控制，这部分绕过了根据android系统的最大Method数，最大Filed数限制生成dex文件的限制，具体的代码我们已经放进了 github 仓库，也欢迎大家一起为dexSplitter项目添砖加瓦，一起为Android App包体积高效分析贡献力量。
