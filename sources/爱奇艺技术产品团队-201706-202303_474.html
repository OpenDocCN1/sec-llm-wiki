苹果官方文档对提交AppStore的APP的二进制 __TEXT 段大小做了明确的限制，如下图。

因为我们的最低支持系统版本是 iOS 8.0系统，所以按照要求，我们发布的程序中每个架构的__TEXT 段必须小于 60M。这对于一个庞大的 APP 来说是一个非常严苛的要求。每个版本都在不断增加业务需求，所以我们始终要为控制 APP 的 __TEXT 段大小做努力。


下面分享一些最近我们为控制 __TEXT 段大小做的一些工作。



经验分享


1

删除代码

在需求开发前期，工程师应该要考虑可复用性的代码，禁止拷贝代码，共用代码下沉为底层组件，尽量用资源文件代替代码。但是不可避免的是随着项目的越来越大，开发人员越来越多，以及各种版本需求的变更，最后会导致工程中包含了很多无用代码。


1. 删除无用class

我们知道，Objective-C 是一门动态语言，拥有很强大的Runtime。我们调用一个类，无需引用这个类的头文件，也可以通过类和方法名反射获得这个类和方法进行调用。


所以在编译OC工程时，编译器并不会像C编译器那样，自动做优化，把没有引用的文件过滤掉。只要在 Compile Sources 中的代码都会被编译进最后的二进制 __TEXT代码段中。


如何查找这些无用的类文件，这里推荐一个非常好用的开源工具: fui


Github地址：https://github.com/dblock/fui


具体使用可以参考它的说明。经过实践，它能找出工程中大量未被使用的文件。但是正如前面说的，正因为 OC 强大的 Runtime，这里的结果会存在误伤，所以在删除之前必须进行核对，确定之后再删除。

2. 删除无用selector

因为 OC 强大的动态特性，其实没有比较好的查找未使用的 selector 的方法。但是我们也尝试过一些方式，大概原理是：


先分析 Link Map 文件，提取所有 objc 类方法和实例方法，再用 otool 方法逆向 ipa 中的可执行文件的__DATA.__objc_selrefs 段，提取可执行文件里引用到的方法名。 


Link Map 中提取的所有的方法名 和 可执行文件中提取的使用的方法名 ，它们的差值就可以大致认为都是未被调用的方法。


但是这样操作的误伤非常大，其中还包括了非常多属性的 set 和 get 方法，排除误伤的工作量非常大，而且得到的收益很小，这里不建议做无用 selecror 的查找。

2

监控代码段大小

在删除无用代码之后，我们花了很多的努力去监控代码段。 这也是控制代码段大小的主要工作。

1. 使用 link map 文件

我们对代码段的分析，全部是依据 Link Map 文件。生成该文件需要在主工程中开启编译选项Write Link Map File

Xcode -> Project -> Build Settings -> 搜 link map -> 把 Write Link Map File选项设为yes

编译完成之后，Link Map 文件就在 Path to Link Map File 选项中指定的目录中。


这个Link Map文件里展示了整个可执行文件的全貌，列出了编译后的每一个.o目标文件的信息（包括静态链接库.a里的），以及每一个目标文件的代码段，数据段存储详情。

        

具体对Link Map 文件的分析可以参考如下博客：

https://blog.cnbang.net/tech/2296/


我们基于 Jenkins 的可持续化集成系统，其中部署了一个名为“Daily Build”的定时 Job，该 Job 每小时都会拉取最新代码进行编译并且跑出一个 ipa 。 每次编译之后 脚本都会自动分析 Link Map 文件 ，整理出工程下每个 .m 文件对应的 .o 目标文件的大小，并进行多个维度的分析。


首先对项目各个子模块的分析

如图分析泡泡业务下各个子模块的 __TEXT 段的大小，并且给每个模块 Owner 限定总大小，由每个模块的开发人员去控制对应模块的大小。


每个模块下，所有 .o 目标文件的大小分析

如图分析每个模块中 .o 目标文件的大小并排序，每个 .o 目标文件对应一个 .m 实现文件。这个数据可以给团队分析提供数据支持，评估一些页面是否需要考虑 RN 化，或者考虑使用XIB来绘制UI。


按Xcode 索引中的 Group 进行分类统计

同时我们也支持对 Xcode 索引中的Group 进行大小统计分析

这个数据主要分析各个业务模块的体积大小，帮助权衡需求和代码段之前的关系，当然这个需要工程目录结构比较完善，统计结果才会有意义。


各文件体积监控

Daily Build 的 Job 还可以和指定的某次编译结果进行对比，罗列出各个 .o 目标文件的前后差别，以及整个工程是否有目标文件增减。

团队成员可以依据这个数据来确定自己的在控制__TEXT 段大小的工作成果。决策层也可以据此来了解该版本 __TEXT 段大小的变化。


SizeLine值( Size of Line )

SizeLine 值是我们自己定义的一个指标，可以简称为 SL 值，是一个文件的“目标文件的大小”和“该文件对应的 .m 实现文件的行数”的比值，文件大小单位为B，粗略表示该文件每行代码的大小。

分析工程中每个.m实现文件的SL值，可以发现，数据model 的 SL 值是最大的。这是因为数据model 的 .m 文件代码量很少，但是头文件中带有很多的 property 属性，在编译前，实现文件中会自动生成对应的 set 和 get 方法，而所生成的 set 和 get 方法 是在__TEXT 段中占体积的。这就是导致了 SL 值偏大，但是这个不可避免，并且并无太多优化空间，所以可以在数据中剔除所有的数据model文件。而其他文件，平均的 SL 值是在60以下较为合适，如果超过60，就需要关注是否可以写的更小，这个在后面会做进一步分析。


总体上来说 SL 值比较粗略，如果代码中存在很多的注释也会影响结果。 但是排除误伤，它能帮助我们查找可以进一步通过改写来缩小体积的文件，对整体分析也是有很大的帮助。后面会结合例子说明。

如何写出更小代码段的代码

关于如何写出更小的代码，除了上面提到的，写出更简洁、更可复用的代码，禁止拷贝代码，共用代码下沉为底层组件 之外，再也分享一些我们遇到的一些坑。

1. 尽量减少Block 的使用

通过上面 SL 值的分析，我们筛选出了一些问题文件。比如 QPChatCellViewCrowdFunding.m文件。它作为一个 View，其 SL 值 是偏大的


88.92 size=21698.56 linenum=244 file=QPChatCellViewCrowdFunding.m


打开后我们发现，这个文件使用了大量的 Mansory 代码来做自动布局

Mansory 采用 Block 来实现链式结构写自动布局的参数，而我们知道 Block 本质是一个对象，它有自己的内存结构。而一个对象在代码段中所占的体积，肯定是比普通的赋值语句大的多的。


我们打开Link Map文件，搜索QPChatCellViewCrowdFunding.o , 我们可以发现，setupView 方法下面存在大量的block 占用代码段。如下图所示，第一列是地址偏移，第二列是十六进制的大小值。我们通过转换可发现每个block 基本占用0.5k - 1k 之间，这个值还是很大的。

从这一点也可以看出，代码段的控制和代码的便利性是矛盾的。是否使用 Mansory 这种优秀和便利的工具，需要根据项目情况和需求进行一个权衡。


2. 谨慎使用宏定义

虽然宏定义在开发带来了很大的便利，但是一定要谨慎的写宏定义，尽量不要写多行宏定义，也不要在宏定义中写太多的操作语句。我们多次遇到了书写不当的宏定义，导致代码段增加的问题。

总结

控制 __TEXT 代码段大小需要贯彻整个项目开发过程，在优秀的代码架构的基础上，工程师们需要总结经验，写出更优秀的代码，并且还需要监控每个需求对 __TEXT 代码段带来的变化，以平衡业务需求和代码段之前的矛盾。
