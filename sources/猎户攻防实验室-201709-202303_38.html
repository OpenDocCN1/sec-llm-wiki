什么是分块传输

分块传输即分块传输编码(Chunked Transfer Coding)是一种传输编码，把报文分割成若干个大小已知的块进行传输。（这里是官方链接RFC7230-4.1）

The chunked transfer coding wraps the payload body in order totransfer it as a series of chunks, each with its own size indicator,followed by an OPTIONAL trailer containing header fields.  Chunkedenables content streams of unknown size to be transferred as asequence of length-delimited buffers, which enables the sender toretain connection persistence and the recipient to know when it hasreceived the entire message.

要想知道为什么会有分块传输编码，那么就要了解为什么会有传输编码。

传输编码(Transfer coding)是为了保证报文能进行可靠传输，而可靠传输是在HTTP协议中考虑的是以下两点

  • 未知的尺寸

    众所周知，报文在传递的时候是带有一个Content-Length的头的，告知接收方报文的大小，这样就可以知道报文边界了。但是有一部分报文是没办法确定最终大小的，所以希望在知道大小之前就开始传递。于是使用传输编码来解决此类问题。

  • 安全性

    可以使用传输编码来把报文内容扰乱，来提升一部分安全性。不过由于现在都采用SSL来提高安全性，所以尽管可以提升一部分安全性，但是不需要使用传输编码。

以下是Wiki上关于分块传输编码的好处描述

  1. HTTP分块传输编码允许服务器为动态生成的内容维持HTTP持久链接。通常，持久链接需要服务器在开始发送消息体前发送Content-Length消息头字段，但是对于动态生成的内容来说，在内容创建完之前是不可知的。[1]

  2. 分块传输编码允许服务器在最后发送消息头字段。对于那些头字段值在内容被生成之前无法知道的情形非常重要，例如消息的内容要使用散列进行签名，散列的结果通过HTTP消息头字段进行传输。没有分块传输编码时，服务器必须缓冲内容直到完成后计算头字段的值并在发送内容前发送这些头字段的值。

  3. HTTP服务器有时使用压缩 （gzip或deflate）以缩短传输花费的时间。分块传输编码可以用来分隔压缩对象的多个部分。在这种情况下，块不是分别压缩的，而是整个负载进行压缩，压缩的输出使用本文描述的方案进行分块传输。在压缩的情形中，分块编码有利于一边进行压缩一边发送数据，而不是先完成压缩过程以得知压缩后数据的大小。

如何使用分块传输

 分块传输是在客户端和服务端都可以使用的。

 使用方法：

  1. 首先要使用Transfer-Encoding: chunked头部声明使用分块传输

  2. 注意不能有Content-Length头部，否则会报错

  3. 在body体里写入分块的数据，每块由两行组成，第一行是一个数字，表示这一块的数据的大小（数据在第二行，大小不包括第一行），第二行是这一块的传送的数据，在数据传输完成时，用0来表示结尾，并且在0后面有两行空行

  4. 有一个小tips，在数字行后面可以跟着;xxx来表示扩展

以下是RFC的定义

chunked-body   = *chunk                   last-chunk                   trailer-part                   CRLF
  chunk          = chunk-size [ chunk-ext ] CRLF                   chunk-data CRLF  chunk-size     = 1*HEXDIG  last-chunk     = 1*("0") [ chunk-ext ] CRLF


重点是


chunk          = chunk-size [ chunk-ext ] CRLF                 chunk-data CRLF


这就是每一块的官方格式描述，由 块大小+可选的的块扩展+换行+块数据+换行


其中块扩展的描述如下


chunk-ext      = *( ";" chunk-ext-name [ "=" chunk-ext-val ] )
  chunk-ext-name = token  chunk-ext-val  = token / quoted-string


形如 ;xxx 或者 ;xxx=xxx


其中 trailer-part 是可选的，想详细了解请看RFC


那么我们举个栗子：

  1. 正常的注入包被WAF拦截（PS：这是一个线上的CTF靶场环境，为GO语言写的应用，WAF是GO的小WAF，基于关键词拦截）


  1. 加入分块之后轻松绕过（PS：注意每一块里不要有关键词，不然还是会被拦截，关键操作在于不要被WAF识别到完整的关键词，比如select、and等）

  1. 来个尾部特写

  1. 加入trailer-part的包的样子（PS：这里还是被拦了，怀疑是trailer-part里有关键词，不过这都不重要，重要的是看一下带trailer-part的包，某些WAF就靠这招能过）



分块为什么能绕WAF

首先，WAF分为非嵌入型与嵌入型，非嵌入型指的是硬WAF、云WAF、虚拟机WAF之类的；嵌入型指的是web容器模块类型WAF、代码层WAF。非嵌入型对WEB流量的解析完全是靠自身的，而嵌入型的WAF拿到的WEB数据是已经被解析加工好的。所以非嵌入型的受攻击面还涉及到其他层面，而嵌入型从web容器模块类型WAF、代码层WAF往下走，其对抗畸形报文、扫操作绕过的能力越来越强，当然，在部署维护成本方面，也是越高的。（引用自对过WAF的一些认知)

所以这里对于非嵌入式的WAF，由于中间件会解析分块传输，但是WAF没有解析，所以在关键字被块分割的情况下，就绕过了WAF

其次对于部分嵌入式的WAF，如果检测规则不是很强，也会绕过，详情看利用分块传输吊打所有WAF(https://www.anquanke.com/post/id/169738)

WAF对应的防御机制

WAF在看到分块传输的头的时候，依照RFC提供的解析方式，将分块包按照标准方法解析，拼接回来，即可将此绕过方式拦截。

据文章里写，一些如Imperva、360等比较好的WAF已经对Transfer-Encoding的分块传输做了处理，可以把分块组合成完整的HTTP数据包，这样可以防止绕过。（PS：但是文章里说可以使用添加;xxx来绕过）

以下为RFC上的解析伪代码

 length := 0  read chunk-size, chunk-ext (if any), and CRLF  while (chunk-size > 0) {     read chunk-data and CRLF     append chunk-data to decoded-body     length := length + chunk-size     read chunk-size, chunk-ext (if any), and CRLF  }  read trailer field  while (trailer field is not empty) {     if (trailer field is allowed to be sent in a trailer) {         append trailer field to existing header fields     }     read trailer-field  }  Content-Length := length  Remove "chunked" from Transfer-Encoding  Remove Trailer from existing header fields




由此引发的一些思考

在安全问题中，有相当一部分的安全问题或者绕过，是由于不一致带来的，分块传输绕过WAF就是一个标准的不一致问题，即中间件的解析与WAF的解析不一致导致的

WAF绕过的攻防就是从一些细节上入手，外加一些脑洞，由于WAF开发和维护是需要考虑人力成本的，所以绕过方式会一直存在
