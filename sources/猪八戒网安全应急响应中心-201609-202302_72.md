**一、为什么要做静态代码扫描系统**

随着公司的高速发展，业务迭代量日渐剧增，传统繁琐的安全检测流程，往往无法跟上项目的迭代速度，所以需要一款自动化的产品，来帮助我们完成基础性的安全检测。这样可以大大的减少开发人员和安全人员的工作量，使整个上线流程更加简单快捷。  

  

**二、静态代码扫描系统在企业中的运用**

静态代码扫描系统，在企业中一般用做上线前的安全检测，开发人员在将项目开发完毕后，可以使用静态代码扫描系统进行漏洞扫描，通过扫描结果，可以快速发现项目中潜在的安全问题，第一时间进行修复，减化由基础安全漏洞导致的项目滞留问题，同时也可以减少安全测试人员的部分工作。静态代码扫描系统还也可以对线上项目进行自动扫描，发现潜在的安全问题，减少线上项目安全事故的发生。  

![](../Images/accaf9e31331f23c23762af21f6bff87.png "1484203621536611.png")

**三、静态代码扫描系统支持扫描漏洞**

**

静态代码扫描系统，一般支持扫描SQL注入、XSS、CSRF、命令执行、文件上传等基础漏洞的扫描。安全开发者想让系统支持新的漏洞类型，只需根据检测系统规定的标准进行开发。并将漏洞脚本上传至静态代码扫描系统，完成基础配置即可支持新的漏洞类型。![](../Images/3c36c81321b2436769c6f76b9844494d.png "1484204672748924.png")

**五、重构思路**

 如上图在使用Cobra原有扫描引擎时，我们遇到了许多未知的问题，虽然我们不断的去优化扫描引擎，加入新的算法，但最终还是因为代码耦合度等诸多问题而选择放弃这套扫描引擎。至于其它功能点根据企业实际情况，适当调整即可。

![](../Images/3fc6713deeed103f24c2218dfe29e751.png "1484210553196098.png")

1扫描引擎重构思路   

    扫描引擎在建立之初，必须考虑其扩展性，通用性，耦合性等问题。漏洞的产生复杂多变，如果模块功能，不利于扩展。当新需求产生，模块功能算法不足以完成新需求时，修改算法将可能导致其它功能运行错误。所以我们需要将整个扫描引擎中不变的部分划分出来，对可能发生变动的部分，进行扩展支持，这样不但易于开发，还可以对算法进行自由装配组合。如下图

![](../Images/38bed1e5271ff184057879c9265d20e1.png "1484210737537192.png")

2扫描引擎如何实现功能扩展

扫描引擎的执行思路还是引用Cobra原有的模式，但在具体实现上，保留Cobra中好的思想，将算法重写实现的同时，也需要加入更多较为强悍的算法。

在进行静态或动态分析时，一个漏洞对应一种分析过程，这个分析过程是随着漏洞的变化而变化的，它可能只需要简单的向上匹配，也可能需要复杂的污点分析。所以我们只需要对不同的漏洞，编写不同的分析器即可完成功能扩展。如下图：![](../Images/3105e915cbb2737db610633a2bbee02e.png "1484210831192998.png")

3分析器模板建设

    在进行分析器模版搭建时，我们需要指定一系列规范，开发人员在扩展新漏洞时，只需遵守开发规范即可。同时提供基础的算法包，安全开发人员可以根据漏洞的执行流程自由变换组合算法。

4常见问题处理

    在生产环境中每一种漏洞，都有属于自己独特的特征，它们的产生与利用各不相同。比如SQL注入（SQL Injection），人工审计的时候主要分为2种方式，**通过入口定位****漏洞**或**通过漏洞特征 ****跟踪入口**。不管理使用哪种方式，都需要看执行过程中有没有正确的对数据进行效验。这时就会产生一个贯穿全文的算法“**变量跟踪**”，在Cobra作者的博客，提到了**向上和向下跟踪**，其实在实际开发过程中，还需要**全局变量跟踪**和**全文函数跟踪**。以下是变量跟踪的具体实现思路，希望能通过介绍，能快速上手。

    不论是向上跟踪还是向下跟踪，它们的原理都一样，我们可以通过一个点（入口或终点），定位到一个面（代码块），再从一个面到一个体（所有调用关系链）。如下图：

![](../Images/7927da0b1efc667c4b94d24ba4f6d4f5.png "1484210961631765.png")

根据上图代码，我们需要找到$id或者$did,通过它们确定代码执行的流程，让这个流程中所有的点形成链路结构：

$id（入口）**\=>**intval($aid) => $bid => $cid => $did =>SQL(终点) 或 $id（入口）**<=**intval($aid) <= $bid <= $cid <= $did =>SQL (终点)。这样做的好处是，验证模块可以快速的判断其漏洞是否存在。如下图：

![](../Images/bdbd652c93aaa5050fb3d2a9b69c6a89.png "1484211006995911.png")

在完成了基本代码追踪以后，需要对变量追踪进行扩展功能开发。首先来看一种最为常见的场景，在if语句中，根据不同的情况，$aid会得到不同的参数，这种情况，基础的变量跟踪模块，可能产生漏报。如下图：

![](../Images/312057926e9027638795db84b3a2f787.png "1484211055415964.png")

这时我们需要将代码进行扩展，让代码支持更灵活，当变量存一对多的关系时，让链路结构形成树状结构，如下图：

![](../Images/9fac8c9b7514ab028fc03e7cab697c6c.png "1484211091736047.png")

这时验证模块将发生改变，在遇到树状链路时，也能正常验证数据，如下图：

![](../Images/8323c807f86c6fc2be451c7960faecd4.png "1484211115223029.png")  

再来看另外一种情况，下图中$array的下标通过了foreach进行处理，在进行变量跟踪时，无法自动跟踪到foreach语句内，这将导致大量的误报

![](../Images/ff26a2d111f941439f767ab21b744b02.png "1484211151592031.png")

这段代码在实际业务场景中运用广泛。针对这种场景，我们需要另一个模块的介入，它需要根据变量的特性将断掉的链路进行修复，我们称这个模块为变量续跟，如下图：![](../Images/ca6178d95e5574e041a72709c3e9b338.png "1484211181497685.png")

同时开发者还可能遇到更多的情况，比如由if语句、foreach语句、三元运算等带来的问题，这些问题都会直接或者间接的影响到变量的定位，下图中if语句的判断不能被变量追踪识别，这时需要进行污点处理。当追踪到三元运算时，也可能产生误报，其实将三元运算想成是分支语句，就能很好解决。

![](../Images/cb371024e109411713119600f85ce26b.png "1484211237271818.png")

最后还有个非常实用的算法，叫做全文函数追踪，当进行正反向跟踪时都会用到它，但建议使用在反向，这样程序的效率会有明显提升，且能快速定位到漏洞函数的上层代码中是否存在可控点。如下图：

![](../Images/eb263bccff788537d263489ac871ca77.png "1484211271813057.png")

5准确率评估

一款静态代码扫描系统，想要真正运用到企业中，其检测结果的准确性至关重要，而基于规则的静态代码扫描系统，只能做为过度产品。因为它的准确性和误报率，都需要庞大的规则支持，同时由于各种环节细节的处理不当，也会间接或直接的影响扫描结果的准确率。![](../Images/71d9a7000392a9780ed62a8787a99e5b.png "1484211335585580.png")

根据重构后的系统，我们对多个大型项目进行扫描，通过扫描结果逐步分析，尽可能的找出通用的误报点，针对性进行修复。最终让各种漏洞的准确率停留在70%\-100%之间。而剩余部分的误报主要由编码不规范和规则不完善导致。

  

**六、总结**

任何一款静态代码扫描系统，都有它的好处和坏处，可能基于规则的分析方式在静态代码扫描系统中属于初级方案。但不可否认的是，它能帮新组建的安全团队，快速发现项目中的安全问题，且投入时间少、见效快，是作为过渡产品的不二选择。在拥有了过渡产品以后，企业就需要实现一套基于编译器的静态代码扫描系统将其替代，据了解这种方案在准确率上有大幅提升，同时我们还会将静态检查产品和持续集成产品打通，真正实现全自动静态检查以保障业务安全。目前我们已经启动了这个项目，如果你对此有经验或者有感兴趣，我们欢迎您的加入。
