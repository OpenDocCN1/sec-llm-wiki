##1.1. 前言


10月1日，tendermint的Head of Security jessy在cosmos论坛通知在hackerone赏金计划中收到一个影响全版本tendermint的漏洞。本文根据代码仓库的修改，研究复现该漏洞。


此漏洞初步修复后可被绕过，已经进行二次修复，tendermint给出了5000+2000美元的赏金。本文就初步修复版本进行分析，绕过分析将在后续文章进行。


##1.2. 漏洞定位


根据描述，tendermint的0.31.9和0.32.5是漏洞修复版本。所以第一个思路是比较0.31.9和0.31.8版本，或者0.32.5和0.32.4版本的代码。0.32.6和0.31.10为二次修复版本。


###1.2.1. 版本代码对比


0.31和0.32版本应该是两个并行的版本，这里选择0.32版本来测试。可以通过`github`的在线比较或者将源码下载下来再离线比较。由于漏洞在0.32.4被发现，于是对0.32.5和0.32.4进行比较。


github的tendermint仓库地址`https://github.com/tendermint/tendermint`


github的在线比较版本
`https://github.com/tendermint/tendermint/compare/v0.32.5..v0.32.4`



可以使用源码比较工具
[diffmerge](http://sourcegear.com/diffmerge/downloads.php)，离线比较



比较可以发现，主要代码修改在`\p2p\conn\secret_connection.go`文件里面，说明这是一个P2P层面的漏洞。


### 1.2.2. 查看changelog


从changelog可以看到漏洞原因是，当向peer节点发送空的公钥时，peer节点由于对nil处理不当而造成panic。


这种漏洞一度在RPC层面上非常多，详情可以参考`海豚链`关于[空值处理不当](https://dolphinchain.org/2019/04/23/dc-03-%E7%A9%BA%E6%8C%87%E9%92%88/)的漏洞。


## 1.3. 代码分析


### 1.3.1. 漏洞触发分析


根据漏洞描述，如果`remPubKey`为`nil`，则会在`remPubKey.VerifyBytes()`引发`panic`

// tendermint\p2p\conn\secret_connection.go
func MakeSecretConnection(conn io.ReadWriteCloser, locPrivKey crypto.PrivKey) (*SecretConnection, error) {
    locPubKey := locPrivKey.PubKey() //公钥是由私钥变换而来

    // skip...

    authSigMsg, err := shareAuthSignature(sc, locPubKey, locSignature)
    if err != nil {
        return nil, err
    }
    // 如果remPubKey为nil，则会在remPubKey.VerifyBytes()引发panic
    remPubKey, remSignature := authSigMsg.Key, authSigMsg.Sig
    if !remPubKey.VerifyBytes(challenge[:], remSignature) {
        return nil, errors.New("Challenge verification failed")
    }

我们在IDE`Goland`里面寻找函数`MakeSecretConnection`被引用的位置，如下图所示


在`socket_listeners.go`里面是接收连接的函数，`socket_dialers.go`是发起连接的函数。可以猜想，攻击者通过`socket`方式发起精心构造的连接(使公钥为nil)，触发接收节点的`MakeSecretConnection`函数中的`panic`，造成节点崩溃。



### 1.3.2. 构造nil值


`remPubKey`为`nil`时，会使节点崩溃，那么`remPubKey`是如何变为`nil`的呢？


让我们来看看`shareAuthSignature`函数,返回值是


- `authSigMessage`类型的`recvMsg`

- 错误`err`


随后`recvMsg`结构体中的`Key`将会被赋值给`remPubKey`。最后`remPubKey`为`nil`，也就是说，`recvMsg.Key`也是`nil`


`shareAuthSignature`函数接收3个参数。分别是


- 类型为`SecretConnection`的私密连接`sc`

- 公钥`pubKey`，类型为`PubKey`

- 签名`signature`,类型为`[]byte`切片


其中公钥`pubKey`是外部可以控制的。

猜测输入的`pubKey`为`nil`时，会引发panic


func shareAuthSignature(sc *SecretConnection, pubKey crypto.PubKey, signature []byte) (recvMsg authSigMessage, err error) {

    // Send our info and receive theirs in tandem.
    var trs, _ = cmn.Parallel(
        func(_ int) (val interface{}, err error, abort bool) {
            var _, err1 = cdc.MarshalBinaryLengthPrefixedWriter(sc, authSigMessage{pubKey, signature})
            if err1 != nil {
                return nil, err1, true // abort
            }
            return nil, nil, false
        },
        func(_ int) (val interface{}, err error, abort bool) {
            var _recvMsg authSigMessage
            var _, err2 = cdc.UnmarshalBinaryLengthPrefixedReader(sc, &_recvMsg, 1024*1024) // TODO
            if err2 != nil {
                return nil, err2, true // abort
            }
            return _recvMsg, nil, false
        },
    )

    // If error:
    if trs.FirstError() != nil {
        err = trs.FirstError()
        return
    }

    var _recvMsg = trs.FirstValue().(authSigMessage)
    return _recvMsg, nil
}

让我们看看`trs.FirstValue`函数。可以看到如果`trs.results`中的`result.Value`一直为空，最后会返回我们想要的空值。


// Returns the firstmost (by task index) error as
// discovered by all previous Reap() calls.
func (trs *TaskResultSet) FirstValue() interface{} {
    for _, result := range trs.results {
        if result.Value != nil {
            return result.Value
        }
    }
    return nil
}

继续看看`TaskResultSet`。`TaskResultSet`的`results`是一个类型为`taskResultOK`的集合。


type TaskResultSet struct {
    chz     []TaskResultCh
    results []taskResultOK
}

type taskResultOK struct {
    TaskResult
    OK bool
}

type TaskResult struct {
    Value interface{}
    Error error
}

同时注意到在`trs.FirstValue`之前还有一个检查错误的判断


    if trs.FirstError() != nil {
        err = trs.FirstError()
        return
    }

所以要保证这里不报错，我们才能进入下一步去使得_recvMsg为nil


func (trs *TaskResultSet) FirstError() error {
    for _, result := range trs.results {
        if result.Error != nil {
            return result.Error
        }
    }
    return nil
}

这里只要不报错就ok


### 1.3.3. 分析Parallel函数


最后来看看`Parallel`函数。


我们如何控制输入，使我们可控制的参数进入`Parallel`函数，并且使其输出一个符合上述条件的`trs`



首先看参数`sc *SecretConnection`，它是作为函数`cdc.MarshalBinaryLengthPrefixedWriter`的第一个参数。


`pubKey`和`signature`是作为函数`authSigMessage`的两个参数。


`authSigMessage`包含这两个参数的返回值,且同时和参数`sc *SecretConnection`并列作为`cdc.MarshalBinaryLengthPrefixedWriter`的第二个参数。


函数`cdc.MarshalBinaryLengthPrefixedWriter`会影响这个匿名函数返回的两个task的`abort`参数。进而影响到函数`Parallel`的输入参数，最终影响到输出结果`trs`。


// tendermint\libs\common\async.go
func Parallel(tasks ...Task) (trs *TaskResultSet, ok bool) 

`Parallel`函数的作用是使任务并行执行。如果有任务abort，则返回值ok为false


那么我们进一步分析，从`Parallel`这一层面上来分析，怎么样的`tasks`可以使得输出`trs`满足我们的条件。


我们对`trs`的条件是：


- trs.results这个集合里面是`nil`

- trs.results会被range遍历


1.首先分析参数`tasks`出现的位置。


首先是len(tasks)，出现在开头和末尾。这个是数组`tasks`的大小。已经是固定值2，所以可以不用看。


    var taskResultChz = make([]TaskResultCh, len(tasks)) // To return.
    var taskDoneCh = make(chan bool, len(tasks)) 

    for i := 0; i < len(tasks); i++ {
        abort := <-taskDoneCh
        if abort {
            ok = false
            break
        }
    }
可以看到如果出现`abort`，这个任务会被跳过循环


2.接下来是一个循环，由于对`tasks`进行了遍历，所以关注`task`


for i, task := range tasks {


`trs`相当于

`newTaskResultSet(taskResultChz).Reap()`


这两个任务就是`MarshalBinaryLengthPrefixedWriter`，即序列化二进制长度前缀。而公钥`pubKey`作为参数只是简单打包到结构体中，如果输入为空，在结构体里面的`recvMsg.Key`也是`nil`。以上为理论分析，可以借助测试文件来进行调试验证。


## 1.4. 代码复现测试


根据上面的思路，通过测试文件来进行相关验证。构造一个构造一个不存在公钥的私钥(即私钥对应的公钥为`nil`)，类型为`privKeyWithNilPubKey`，作为参数输入到`MakeSecretConnection()`函数中去，看看会不会产生`panic`


在文件`secret_connection_test.go`中增加代码


    // 增加两个依赖
    "github.com/tendermint/tendermint/crypto"
    "github.com/tendermint/tendermint/crypto/secp256k1"

// 写在测试文件后面，如果报错将依赖更新到最新版本
type privKeyWithNilPubKey struct {
    orig crypto.PrivKey
}

func (pk privKeyWithNilPubKey) Bytes() []byte                   { return pk.orig.Bytes() }
func (pk privKeyWithNilPubKey) Sign(msg []byte) ([]byte, error) { return pk.orig.Sign(msg) }
func (pk privKeyWithNilPubKey) PubKey() crypto.PubKey           { return nil } // 这里模拟空的公钥pubKey
func (pk privKeyWithNilPubKey) Equals(pk2 crypto.PrivKey) bool  { return pk.orig.Equals(pk2) }

func TestNilPubkey(t *testing.T) {
    var fooConn, barConn = makeKVStoreConnPair()
    var fooPrvKey = ed25519.GenPrivKey()
    var barPrvKey = privKeyWithNilPubKey{ed25519.GenPrivKey()} // 没有公钥的私钥

    go func() {
        _,err := MakeSecretConnection(fooConn, fooPrvKey)
        t.Log(err)
    }()

    go func() {
        _, err := MakeSecretConnection(barConn, barPrvKey)
        t.Log(err)
    }()

}

可以看到在会产生`panic: runtime error: invalid memory address or nil pointer dereferenc`，看具体信息，可以知道是在`MakeSecretConnection`处的`remPubKey.VerifyBytes`处空指针引用造成的panic。


说明此处漏洞存在




## 1.5. 漏洞修复


`tendermint`团队第一时间通过判断`remPubKey`是否为`nil`进行了修复。随后又进一步完善逻辑，不仅不接受空的公钥，还要求公钥满足相关格式才能通过。


代码修复链接见参考
