# 【359期-1】关于伪基站及网络安全的一点总结

本文尽量不装B，摊开来欢迎各路大神一起来讨论，如能为移动通信网络安全切切实实做一点贡献，我想也是一个快事。下面分RRC空闲态和连接态，重点讨论三个内容：如何将终端诱骗到伪基站，如何获得终端的IMSI号，伪基站的不同反馈如何影响终端正常通信。

**一、RRC空闲态下**

1、如何将终端诱骗到伪基站

在RRC空闲态下，伪基站只要做少量的配置（采用相同的PLMN号，设置一个现网在用的EARFCN和PCI），通过发射一个较高的功率或者通过设置极端的重选参数就可以很容易将UE诱骗过来。

2、如何获取终端的IMSI号

一般的伪基站设置了一个现网不同的TAC，这样当终端重选到伪基站后，就会率先发起TAU过程。由于TAU会被伪基站拒绝，随后UE会发起ATTACH过程，下面分三个部分来展开。

（1）TAU过程

图1是一段真实捕捉的伪基站下的TAU过程。

![](../Images/3bbb7ce85481890261f7774167f20c2c.png)  
图1(a) 伪基站下的TAU信令流程

![](../Images/86001510d3fb161309cb913b5ef6b53a.png)  
图1(b) 真实基站下的TAU信令流程

         从上图可以看出，

*   伪基站是通过IdentityRequest/Response过程获得UE的IMSI号。
    
*   伪基站会下发TAUreject，原因值15为No Suitable Cells In tracking area（不是原因值10隐式分离，可能不同的伪基站有不同的实现），UE会存储该基站的TAI到禁止TAI列表内，在其他的跟踪区内进行小区搜索，重新发起TAU。
    

好了，这里有两个问题值得讨论：

*   UE有无可能认定TAU过程中的Identity查询是非法的操作？
    

首先要说明的是上述截图中的网络设置本身不够安全，在TAU流程中本来是需要有鉴权、NAS和AS安全模式协商过程的，很显然这个网络为了提高TAU成功率和路测的上下载速率（长时间的跨TAU操作会导致较长的业务断流），这一切都是万恶KPI考核惹的祸——牺牲安全，赢得考核。

也正是协议建议要在TAU过程中做鉴权和安全协商，Identity查询才变得不可或缺，即，这个过程在终端看来是很正常的一个操作，终端不但需要响应而且必须响应。否则，后续的鉴权和安全模式协商所需要的UE Security capability和IMSI从哪里取得？具体可进一步看ATTACH过程的讨论。

也有人说UE之前已经完成了鉴权和安全模式协商，UE中必然缓存有Non-Current full native EPS安全上下文，因此TAU request可以同时做NAS和AS的完整性保护和加密。不过很遗憾告诉你，在RRC空闲态下，重选动作是UE发起并执行的，网络无法知道UE的下一个移动目标eNB和MME，因此网络侧无法实现Kasme和Kenb的传递，具体可参考连接态的讨论。因此一开始的几条消息都不得不以无完整性保护和明文的形式来发送，直到完成鉴权，才逐步开始完整性保护和加密。

*   伪基站的TAI被禁止后，是否意味着伪基站就失去作用了？
    

一旦伪基站的TAI被UE列入禁用列表后，该UE可以做到对该TAI免疫，若伪基站不改变TAI，UE在重选到该伪基站之后会立即识别出来不会发起TAU Request过程，也就不会再被获取IMSI号了。

但不幸的是，伪基站的TAC是可以修改的，有些变态的伪基站甚至可以做到周期性的动态修改，因此TAI禁用列表几乎是起不到作用的。更严重的是，若是伪基站设置了现网实际使用的TAI，将会导致UE在真实TAI所在区域无法提供服务，这恐怕才是运营商最应该担心的问题，而不是UE瞬时断网的烦恼。

 （2）ATTACH过程

如上讨论，TAU reject原因值决定了UE下一步如何操作，而原因怎么设置，那就看伪基站的心情了，常见的原因值有以下这些。

![](../Images/03469e1be849c361ef8999f981b59dda.png)  
可以看到，原因值为15算是比较温和的了。UE只是瞬断，很快就可以重新获取服务。若是设置成10呢。我们来讨论一下情况有多糟糕。根据规范，此时UE会删除本地参数（包括PLMN、EPS安全上下文等），搜索一个合适小区，并继续发起Attach。但很可能UE还是继续在伪基站下发起Attach，这样会延缓UE获得正常服务的时间。

![](../Images/d388745abca96ad92ea7dab48043fab5.png)  
图2(a) 伪基站下的ATTACH信令流程

![](../Images/3cba86b41cd66741ec0a001be45ab740.png)  
图2(b) 真实基站下的ATTACH信令流程

*   IMSI获取
    

通常由于TAU Reject原因值为10引发的Attach还是携带GUTI，但伪基站可以发送原因值为9的Attach Reject让UE重新在本小区发起带IMSI的Attach；另外伪基站还是可以通过Identity查询过程来获得IMSI。结合正常的Attach流程来看，没有Identity过程，后续的鉴权、NAS和AS安全模式协商是无法进行下去的。

*   Attach reject后的操作
    

本例中的attach reject原因值还是15（No SuitableCells In tracking area），UE会存储该基站的TAI到禁止TAI列表内，在其他的跟踪区内进行小区搜索，重新发起 ATTACH。其余的原因，UE的响应情况与TAU Reject类似。

（3）本节总结

*   ATTACH和TAU流程中，通过Identity request/response流程来获取IMSI是难以避免的；
    
*   根据规范，终端会优先尝试用GUTI做ATTACH，若失败，则会直接用IMSI做ATTACH，因此即使防住了Identity流程，也防不住以IMSI做ATTACH时被窃取的必然；
    

**二、RRC连接态下**

在RRC连接态下，LTE的安全机制确实还是比较健壮的。通过前向和后向保护，保证了Kenb不会在网络内传播，较好地执行安全机制里的一个重要法则——密钥的空间局部性，即源基站的Kenb不会被目标基站获得，同时目标基站的Kenb也不会被源基站获得（实际上要下一跳基站才能断开密钥推导链）。下面是一个X2切换的例子。

![](../Images/9cf78f601c01a6ed4db26a39d56fa020.png)  
图3 X2切换中的Kenb密钥生成与传递

后向保护：原基站是将另外生产的Kenb\*发给目标基站的，且仅用于完整性保护和加密UE和目标基站完成Kenb\*\*协商前的消息（如RRC Connection Reconfiguration）；

前向保护：目标基站只是将NCC告知了源基站，并没有将自己生产的Kenb\*\*告知源基站。但事实上，源基站是可以根据NCC推导出Kenb\*\*的。在Pah Switch Request ACK时MME为目标基站分配了新的{NH, NCC}对，并用于目标基站的下一次切换。因此下一次切换之后，源基站就无法再导出Kenb了。注：若要求目标基站做一次站内或小区内切换，就可以实现更好的前向保护。

部分文献里，提出了通过修改HandoverRequest和Pah Switch Request ACK消息里的NCC，让目标基站和UE仅执行水平密钥推导（horizontal key derivation），这样就可以破坏密钥的空间局部性，使得只要获得一个Kenb就可以获得后续所有基站的Kenb，这样就可以监听和窃取用户敏感数据。

必须说明的是，对于常规的通信基站而言，这是不大可能的，除非有人破坏地面通信电缆以物理的方式连接到传输网络中，否则是无法实现攻击的。但是，越来越多的HeNB（如Femto，NanoCell）等设备，通过Internet连接到通信网络，采用常见的IP网络攻击手段（如拒绝服务型DoS攻击、扫描窥探攻击和畸形报文攻击）有可能获得对Handover Request和Pah Switch Request ACK消息里的NCC值的修改，这将有可能导致网络安全性能极度降低。

以上稍微跑题了一下，还是回到伪基站是否可以通过空口实施作案上来。伪基站仿冒正常目标基站的EARFCN和PCI，并发射较大的功率。终端根据源基站的MC进行测量，并上报伪基站的MR（RSRP和PCI），源基站向真正的目标基站发送Handover Request消息，得到相应的反馈Handover Request ACK，向UE发起切换命令（RRC Connection Reconfigration，该消息用Kenb完保和加密），UE将向伪基站做上行同步（RA/RAR），并向伪基站回复RRCConnection Reconfiguration Complete消息（用Kenb\*完保和加密）。尽管伪基站没办法解开该消息，但实际上该消息也没有携带有价值的内容。

至此，UE已经被诱骗到伪基站，由于下行链路不存在，终端很快就会因为下行链路失步而发起RRC重建，并且重建目标小区还是伪基站，由于伪基站缺乏EPS安全上下文，重建必然失败，UE返回RRC空闲态，并清除EPS上下文，然后UE重搜合适小区（一般是RSRP最强的小区）再发起RRC Connection Request。由于伪基站的TAI已发生改变，后续的过程与RRC空闲态下的TAU过程一样，稳稳可获得UE的IMSI。 

**三、进一步讨论**

1、伪基站不发任何TAU响应对UE行为的影响

如果伪基站不响应任何TAU消息，UE会等待T3430（固定15s）超时确认本次TAU失败；等待T3411（固定10s）超时后，再次发起TAURequest；该过程最多可以重复5次，然后UE启动T3402（默认12m），在此期间UE认为EPS网络不可用。T3402超时后，UE会再次尝试发起TAU Request。

上述只是UE对于LTE域的选择情况。实际上，UE的域选动作还受到两个参数的影响：(1)语音优先，还是数据优先："Voice centric" or "Data centric"；(2)IMS/PS 语音优先，还是CS语音优先："CSVoice only", "IMS PS Voice only", "prefer CS Voice with IMSPS Voice as secondary",  "prefer IMS PS Voice with CS Voice assecondary"。对于一般的VoLTE终端，设置为"Voice centric"和"prefer IMS PSVoice with CS Voice as secondary"，因此当UE认为EPS网络不可用，会去搜索23G网络，并接入。

2、伪基站不同TAU Reject原因值对UE行为的影响

*   原因值为3：UE会启动T3245（取值范围24-48h），直到人工开关机干预才能重新工作；
    
*   原因值为7：UE会认为EPS网络不可用，从而去搜索23G网络并驻留；
    
*   原因值为10：UE会删除了本地数据（包括PLMN、EPS安全上下文等），搜索一个合适小区，并继续发起Attach，可能携带GUTI或者IMSI；
    

相对而言，原因值为15对现网业务的影响程度是最低的。

3、伪基站释放RRC Connection时若携带了GSM频点

此时终端将回落GSM网络，由于GSM网络的安全性远低于LTE，在GSM网络不但可以轻易获得UE的IMSI，而且也可以做语音监听和数据窃取等更为恶劣的事情。

**四、总结**

1、利用伪基站获取在RRC空闲态或者连接态下驻留LTE网络的UE的IMSI号几乎是不可避免的，但好在LTE网络提供了较为强大的鉴权、NAS完整性保护和加密、AS完整性保护和加密、用户面加密、甚至传输层的IPSec加密的能力，使得语音监听与数据窃取几乎无法开展。

但需要提及的是，利用Internet提供传输的HeNB系列基站（如Femto、NanoCell等）仍然存在较大的安全隐患。从网络安全角度考虑，不建议这些HeNB设备与一般的宏基站之间有切换关系，以保证安全密钥推导链不至于在整个网络内传播，致整个网络处于极大的安全隐患之中。

2、如上所述，LTE伪基站可以很方便地将UE强行回落到GSM伪基站，GSM网络的安全性能远不如LTE，这就给伪基站开展语音监听和数据窃取提供了机会。

3、不得不说的，基于GSM技术的NB-IoT或基于LTE技术的eMTC物联网，同样存在极大的安全隐患，简单的攻击就可以很方便获取到设备的标识号，定位用户、窃取数据，甚至直接让设备停止工作（攻击机制非常类似IP网络的DoS）。

4、对电信运营商来说，当前最最可行的一个行动就是好好去跟暴力机构协商，统一使用一个未在现网使用的TAI，并且要求明确回复TAU Reject，原因值为15，而且RRC Connection Release不要携带GSM频点，只有这样才能将伪基站对现网的适应感知影响降低到最小，让你们辛辛苦苦，花大力气建立的LTE网络不至于变得这么脆弱。
