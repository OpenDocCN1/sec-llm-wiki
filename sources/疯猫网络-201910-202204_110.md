关于chunk的大小，包括ctf-wiki以及我能找到的所有视频对chunk的大小的大概，无非就是根据x86或x64不同，其大小必须是2 \*SIZE\_SZ的倍数。如果申请的内存大小不是2 \* SIZE\_SZ 的转换倍数，会被转换满足大小的最小的 2 \* SIZE\_SZ 的数倍。32 位系统中，SIZE\_SZ 是 4；64 位系统中，SIZE\_SZ 是 8。malloc/malloc.c 中解释如下。  

```
/*   malloc/malloc.c
```

## **三、刨根问底**

### **1.手动编译**

  

对于这个与理论计算不同的现象，我确定了问题的来源，首先是人工编译

```
# 从官网下载glibc并编译，以2.31为例
```

通过手动编译glibc 2.23 2.25 2.26 2.27 2.31 更真实了表面的结果，在glibc2.26之后，32位软件块的卫星(MALLOC\_ALIGNMENT)为0x10，之后不是0x8

  

### **2.查看版本更新信息**

通过重点查看glibc2.26版本更新信息发现有如下内容

```
2017-06-30  H.J. Lu  <hongjiu.lu@intel.com>
```

malloc-alignment.h 增加了两份，是在 sysdeps/generic/ 中，是在 sysdeps/i386/ 中，而我们经常查看（编辑器自动跳转）却在 sysdeps/generic /中，因为 malloc-alignment.h 是通过 malloc/malloc.c -> malloc/malloc-internal.h -> sysdeps/generic/malloc-machine.h -> malloc-alignment.h 包含进来的，编辑器自然我进入sysdeps/i386/malloc-alignment.h 看到如下内容。

```
/* Define MALLOC_ALIGNMENT for malloc.  i386 version.
```

当我看到这个的时候，我街头的我应该找到问题的关键了，并且我通过搜索 malloc-alignment.h 发现glibc文件夹中只有这两个 malloc-alignment.h 文件，所以应该是通过包含 sysdeps /i386/malloc-alignment.h 加上 MALLOC\_ALIGNMENT = 16。那么现在只剩下一个问题，为什么会包含 sysdeps/i386/malloc-alignment.h 不是包含 sysdeps/generic/malloc-alignment.h，等问题出在编译过程中。通过自己在人工编译中生成的config.make文件查到代码。

  

![](../Images/bf833a78e00517399f32718c21cf7b41.png)

  

在glibc的Makeconfig中

```
# Complete path to sysdep dirs.
```

sysdeps/i386/ 优先级高过 sysdeps/generic/

  

## **四、最后总结**

glibc 在编译过程中，如果选择编译成 32 位系统，config-sysdirs 中 sysdeps/i386/ 优先级高过 sysdeps/generic/ ，那么在编译使用 sysdeps/i386/malloc-alignment.h 就是 #define MALLOC\_ALIGNMENT 16 。最终导致32位软件chunk的暗号(MALLOC\_ALIGNMENT)为0x10，不是0x8。因为sysdeps/i386/malloc-alignment.h是在2.26以后才的，并且到本人写文章加入时的glibc2.32中一直存在，所以在 glibc2.26 之后，32 位软件块的邮箱 (MALLOC\_ALIGNMENT) 为 0x10，不是 0x8。

  

### **测试**

本着事实胜于雄辩的原则，我手动将 sysdeps/i386/malloc-alignment.h 中的#define MALLOC\_ALIGNMENT 16 修改为 #define MALLOC\_ALIGNMENT 8 提交手动编译，并使用 patchelf 修改 libc.so，进行调试结果如下。

  

![](../Images/8fe3e56013bf0541daf71a17a5b53e82.png)

  

从之前发生在 malloc(0x10) 时的chunk 为 0x18 ，直到这个实验成功。

注：随机的问题不是 chunk 的宏使用，因为 bins 的各种均使用 MALLOC\_ALIGNMENT 和 MALLOC\_ALIGN\_MASK 计算。各个讲解员中 smallbins largebins 的大小范围不是以软件计算，以影响 MALLOC\_ALIGNMENT 计算，所以在 glibc2.26之后，32位软件bins的取值范围和64位软件一样。（有待测试）

  

## **五、新的问题**

我没有定义垃圾了块的各种宏定义后发现的，垃圾的问题影响块的使用，因为垃圾箱的各种宏均使用 MALLOC\_ALIGNMENT 和 MALLOC\_ALIGN\_MASK 计算。各种说明 smallbins largebins 的大小范围不以软件计算，比例以 MALLOC\_ALIGNMENT 计算，细节上的变化见度。

  

![](../Images/1a60a1c9c401ae2b9bc79df5dbd9345d.png)

  

通过上表可以出现 x86 系统下 glibc2.2 之前，与 x64 系统下和网上教程的内容超标，只有在 glibc2.26 之后 x86 模式下块的大小会存在一些问题。

  

### **1.smallbin与smallbin的重叠largebin**

实际上在 bins 的数据结构中并没有 smallbin 与 largebin 的变量，只是通过运算将其单独，顺序在 2~63 的为 smallbin ，顺序在 64~126 的为 largebin ，但在 glibc2.26 以后 x86 模式下， index = 64 的bin 是否在largebin 的判断内，但实际上只有smallbin 的作用，存储了固定大小的chunk (0x3f0)。

```
#define NBINS             128
```

所以在 glibc2.26，32 位软件 bins 的取值范围 64 位软件之后差不多，只有少数有微小的差别。

  

### **2.fastbin链表空置。**

fastbin 是极速最大的 bins，因为fastbin 的宏定义并没有 MALLOC\_ALIGNMENT 和 MALLOC\_ALIGN\_MASK 计算，而直接使用 SIZE\_SZ，代码如下。

```
//  malloc_test_2.c
```
