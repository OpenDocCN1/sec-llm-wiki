*   连接之后反馈为“remember the anwser length of 'send how long ...' is 4,to improve your efficiency”，意思是设定长度为4，例如decrypt时输入0008，回车可能也算字符，所以手动nc会出现问题，没有规律。
    

根据反馈得到的直观信息![](../Images/8b6d0b3fd57df611b8254e1a392934fd.png)

*   encrypt用n和e。交流用的是base64，明文的数字记做m，密文的数字记做c。发送的时候发的是long\_to\_bytes(m)的base64，它回复的是str(c)的base64。
    
*   decrypt发送的密文记为c，发送的格式是long\_to\_bytes(c)的base64，它只会回复0或者1。但如果你是手动nc的话，就可能会觉得它的反应毫无道理，因为经常会因为输入不符合它的要求而直接中断连接了。确定了它的回复只有0和1之后，就思考一下这个bit会是什么信息，测试确定这个bit就是该密文所对应明文的最低位bit（第0位）。
    

题目设定题目的设定是：可以得到密文对应明文的第0位。那么如果可以算出flag右移一位之后的密文，那么flag的第1位也就知道了；如果可以算出flag右移两位之后的密文，那么flag的第2位也就知道了；依此类推。

解题过程

*   右移一位就是除以2，也就是乘以2的模逆（2^(-1) mod n）；对应到密文c就是乘以(2^(-1))^e mod n，把这个数记为rbit。如果明文m的最低位是0，那么c*rbit mod n 就是m右移一位对应的密文，即m//2；如果明文m的最低位是1，那么c*rbit mod n 就是(m+n)右移一位对应的密文，即(m+n)//2。
    
*   这里的n是2048bit，如果把上述过程重复2048次，每次都得到当前密文now\_c对应明文的最低位，然后now\_c = now\_c \* rbit mod n，就得到得到了一个2048bit的序列，这当然不是明文，但它已经携带了明文所有比特的信息。
    
*   首先把now\_m置为2048比特全1（防止减的时候出现负数），倒序遍历前面得到的2048bit的序列：如果当前bit是1，那么now\_m = now\_m \* 2 - n（不取模）；如果当前bit是0，那么now\_m = now\_m \* 2（不取模）；（完全是前面的逆运算）。遍历完之后，now\_m的低2048bit就是明文。

### GETFLAG

用jadx打开文件查看java源码，发现这是啥玩意儿，好像跟题目不搭边，这是个假的![](../Images/d8901b37eacdb45d82187fbbd8cf92c4.png)打开apk文件，发现assets文件下有一个secret.txt文件，查看内容，猜测是base64，解密，得到一个服务器地址。

推测这个apk是模拟了客户端和服务器之间的对话逻辑，看到apk里，设置的端口为8080，于是我们也nc ip 8080看看，发现通了，并且还返回一串数字，那么，应该能肯定apk里的代码就是模拟了逻辑。

当我们验证通过后，就能执行wget url，下载文件了。为了测试这个猜测，自己搭建了一个http服务器，然后把地址传进去，查看一下服务器的日志，发现了一个gun-androidabi的客户端，多次测试，可以肯定对方确实执行了wget xxx的代码。![](../Images/5ca36908df2e2497ac0008ccf117bbe8.png)于是想到了命令注入，发现注入的命令根本不会执行，查阅资料发现java的runtime.exec(String)，会切割string为数组，然后把arr\[0\]作为命令，后面的全部作为参数，并且exec不带shell解释器，我们用不了管道等特殊符号。

并且，我们看到程序里第一个字符串wget已经是固定住的了，这意味着我们只能有执行wget命令。

猜测wget不只有下载文件的功能，应该还可以上传文件吧。于是查阅资料，发现**wget有一个--post-file功能可以把文件post到url指向的服务**器处。

于是，我们事先在我们的服务器上建立好服务，然后利用--post-file上传flag即可。中途测试，上传其他文件到我们服务器，发现这个题竟然真的搭建在安卓环境里。

```
struct Node {
   char \*content;

如果我们输入的size大于1024，Node结构体内容就不会初始化。然后，本题glibc版本为2.23，所以存在fastbin机制，如果未初始化的Node节点的content正好指向了下一个空闲堆，并且下一次创建新节点时，那个大小0x10的空闲堆被作为另一个Node节点的空间，那么，我们就能通过edit，来控**制下一个Node的content指针，达到任意地址读写的功能**为了泄露地址，我们利用任意地址读写，修改free的got表为puts的plt表地址，然后free堆时，就会泄露堆里面的内容，得到glibc地址，计算出需要的函数的地址。接下来，同样利用任意地址读写，改写atoi的got表为system地址，然后输入/bin/sh即可getshell。完整的exp.py

### musl

这是一道musl libc的堆题，抛开了传统的glibc，考验我们的适应能力。musl libc是一种小型的libc，主要应用于嵌入式设备。

首先，我们检查一下程序的保护机制，发现没开PIE![](../Images/c4735bbef9f2eaed0009bb16219fd0d0.png)然后，我们用IDA分析一下，发现经典增删改查菜单![](../Images/6339f167f03be1899a869f31d8a03c60.png)直接看漏洞点在add函数里堆的范围在0~0x80，并且，我们有一次堆溢出的机会![](../Images/3fc8feff8c69f717f16cf9be2fa9d8de.png)然后，我们来看看用于输入的函数，发现要么遇到\\n结束，并把\\n处置0，要么size个字符输完，这意味在，即使堆内容前8字节有堆指针，我们也不能直接泄露出来。![](../Images/ccbe0d1a1487607641c6013b25c17820.png)调试发现，不管堆的size多大，它们释放后fd和bk的位置都有musl libc里的指针。![](../Images/811b8e4c96f563de23fcceec84e1f43d.png)借鉴着glibc下的堆利用思想，我们猜想应该可以修改fd和bk来达到某些利用，于是，就先试一下吧。为了能够修改到fd和bk，我们得制造出overlap chunk，并且，直觉告诉我，musl libc也存在类似于glibc下unsorted bin的切割机制，因此，我们利用一次堆溢出，伪造下一个堆的size，将下一个堆和下下个堆合并。如果我们接下来能够成功删除掉被我们改掉size的chunk1，那么就会形成unsorted bin。但是，当伪造好了之后，尝试delete掉chunk1，发现程序崩溃了。再调试调试，发现原来与glibc不同的是,musl libc的prev\_size的低1字节表示前一个chunk的空闲状态。并且，musl libc的堆头是0x30字节，使用中时，后0x10字节作为数据域使用。而glibc的堆头0x20字节，使用中时，后0x10字节作为数据域使用。

```
create(0x10,'a'\*0x10) #0
create(0x60,'b'\*0x60) #1
create(0x80,'c'\*0x50 + '\\x00'\*0x10 + p64(0xF1) + p64(0x21) + 'c'\*0x10) #2
delete(0)
#溢出，修改chunk
create(0x10,'a'\*0x10 + p64(0x21) + p64(0xF1) + '\\n','Y')
delete(1)
```

经过一番伪造，终于成功删除了，这意味着，我们已经得到了overlap chunk，接下来，与glibc下的思想一样，我们申请合适大小的堆，将libc指针移到chunk2里取，然后由于chunk2本身是没有delete的，我们就可以edit它，也可以show，显示出指针。当我们泄露出信息后，就可以计算出想要的函数、gadgets的地址，接下来，尝试edit chunk2，修改fd和bk指针，随便指向一个能够读写的区域，测试一下，调试跟踪，发现没有崩溃，并且申请堆后，**fd和bk指向的位置被写上了自身的地址。**后来推测，musl libc没有太多检测机制，以后再慢慢研究。**既然能够向任意地址处写上该处的地址**那么，我们我们**在堆数组里存入堆数组本身的地址，不就是能够实现任意地址读写了吗。**![](../Images/484241a1cbdd736f4df40377f2e0727a.png)实现了任意地址读写，发现不知道劫持哪里，musl libc里找不到malloc\_hook、free\_hook这些，got表也不能修改。此时想到了劫持栈，发现musl libc和glibc一样都有**\_environ变量，它存储着栈地址。**但是，我们show功能只能用一次，之前已经泄露过了libc地址，我们可以用任意地址读写，将dword\_602034处的标记复原，这样又可以show了。最后就是计算函数的返回处在栈中的地址，利用任意地址读写写入ROP即可。完整的exp.py

### webtmp

分析

考点是pickle反序列化，过滤掉了  R 指令码，并且重写了 `find_class`：

```
class RestrictedUnpickler(pickle.Unpickler):
    def find\_class(self, module, name):
        if module == '\_\_main\_\_':
            return getattr(sys.modules\['\_\_main\_\_'\], name)
        raise pickle.UnpicklingError("global '%s.%s' is forbidden" % (module, name))
```

这就禁止引用除了 `__main__` 之外的其他module，但是如果通过GLOBAL指令引入的变量，可以看作是原变量的引用。我们在栈上修改它的值，会导致原变量也被修改

于是可以先引入 `__main__.secret` 这个module，然后把一个 dict 压入栈，内容是 `{'name': 'xx', 'category': 'yyy'}`,之后执行 build指令，改写 `__main__.secret.name` 和 `__main__.secret.category`,此时 `secret.name`和 `secret.category` 已经变成我们想要的内容

```
