# 自2020年12月13日以来，FireEye已发现更多有关SUNBURST后门的信息。SUNBURST是SolarWinds Orion插件的木马版本经过数字签名后形成的，该插件名为SolarWinds.Orion.Core.BusinessLayer.dll。该插件包含一个后门，可通过HTTP与第三方服务器进行通信。在长达两个星期的初始休眠期之后，SUNBURST开始检索并执行命令，以指示后门传输文件，执行文件，对系统文件进行配置，重新引导系统并禁用某些系统服务。恶意软件的网络流量试图通过模仿Orion Improvement Program（OIP）协议与合法的SolarWinds活动融合，并将持久状态的数据存储在合法的插件配置文件中。后门使用多个混淆的列表来识别取证工具和防病毒工具，并控制他们的运行。

##   

反分析环境检查  
  

  

在与C2服务器通讯之前，SUNBURST进行了许多检查，以确保不存在任何分析工具。它会检查进程名称，文件写入时间戳和Active Directory（AD）域。这些检查帮助SUNBURST逃避防病毒软件和调查人员的检测。

首先，后门验证当前进程的小写名称为solarwinds.businesslayerhost。UNC2452计算字符串的哈希值并将结果与64位数字17291806236368054941进行比较，避免了将此字符串直接包含在源代码中。将哈希值计算为标准FNV-1A 64位哈希，并通过64位数字6605813339339102567进行额外的XOR 运算。额外的XOR操作会迫使恶意软件分析人员开发自定义工具，以强行破解哈希原像。

SUNBURST在触发前需要有至少两周的休眠时期。达到阈值后，该示例将创建命名管道583da945-62af-10e8-4902-a8f205c72b2e，以确保仅运行后门。如果命名管道已经存在，则恶意软件退出。

SUNBURST将其配置存储在合法的SolarWinds.Orion.Core.BusinessLayer.dll.config文件中。它在appSettings部分中重新利用了两个现有设置：  ReportWatcherRetry和ReportWatcherPostpone。在初始化期间，后门将确定ReportWatcherRetry设置是否为3。此值表示恶意软件已被停用，将不再执行任何网络活动。UNC2452可以命令后门禁用自身。在调查受到SUNBURST攻击的系统时，请检查此设置以确定是否禁用了后门。请注意，此值的存在并不能判断，SUNBURST是否对目标造成损害。

后门还需确定系统是否已加入Active Directory（AD）域，如果已加入，则检索域名。如果系统未加入AD域，则停止。SUNBURST根据阻止列表检查AD域名，如果包含以下值之一，则暂停执行：

![](../Images/576928d8ca83c741c41c42465473e4cb.png)

研究员怀疑这些硬编码的AD域可能是UNC2452想要避免的SolarWinds内部域。最后，SUNBURST通过可解析DNS名称api.solarwinds.com来验证系统是否具有Internet连接。如果没有连接，执行将停止并在稍后的随机时间重试。

##   

反分析黑名单  
  
  

  

SUNBURST的行为受到恶意软件分析和安全软件的影响。为了隐蔽这些用于检测安全工具的字符串，UNC2452计算并嵌入了每个字符串的哈希值。SUNBURST使用前面提到的FNV-1A加XOR算法来计算系统上每个进程名称、服务名称和驱动程序文件名的哈希。

如果找到了列入黑名单的进程或驱动程序名称，则SUNBURST会暂停并稍后再试。仅当不存在防御列表中的进程或驱动程序时，后门才继续此检查。

如果找到了被列入黑名单的服务，则SUNBURST会通过操作Windows注册表中的服务配置来尝试禁用被列入黑名单的服务。它将注册表值HKLM \\ SYSTEM \\ CurrentControlSet \\ services \\ <service\_name> \\ Start设置为值4，该值对应于SERVICE\_DISABLED。结果，被列入黑名单的服务将在下一个电源周期关闭。这意味着，如果受感染的主机上存在列入黑名单的服务，系统将会受到SUNBURST的影响。

修改注册表后，SUNBURST更新ReportWatcherPostpone配置值以表示其禁用的服务。然后，后门暂停，稍后会重试进程和服务拦截列表检查。

##   

域生成算法  
  

  

SUNBURST如何使用中间命令和控制（C2）协调器来检索其最终的C2服务器呢？C2协调器通过DNS CNAME记录将SUNBURST重定向到其最终C2服务器。这使UNC2452能够分隔其操作，从而限制了受害者之间共享的网络基础结构。

DGA生成具有以下DNS后缀的子域以创建FQDN：

*   .appsync-api.eu-west-1 \[.\] avsvmcloud \[.\] com
    
*   .appsync-api.us-west-2 \[.\] avsvmcloud \[.\] com
    
*   .appsync-api.us-east-1 \[.\] avsvmcloud \[.\] com
    
*   .appsync-api.us-east-2 \[.\] avsvmcloud \[.\] com
    

名为Update的方法负责初始化加密助手，以生成这些C2子域。子域是通过将编码的用户ID与系统域名的编码并置而生成的。C2协调器可以从编码数据中恢复受害域名，并可能使用该域名将SUNBURST路由到其最终C2服务器。

根据以下三个值生成用户标识：

1.第一个可用的非环回网络接口的MAC地址

2.域名

3.HKEY\_LOCAL\_MACHINE \\ SOFTWARE \\ Microsoft \\ Cryptography \\ MachineGuid值

SUNBURST使用这些组合值的MD5哈希值，并使用自定义XOR方案对其进行编码。UNC2452能使用此值来跟踪唯一的受害者。

SUNBURST使用四种不同形式的子域来表示后门的操作模式。每个表格包含的信息略有不同。但是，调查人员可以通过两种形式来恢复受害组织的域名。建议检查DNS日志，以确认SUNBURST C2协调器流量中存在受害者的域。

当SUNBURST处于初始模式时，它将受害组织的域嵌入到其DGA生成的域前缀中。一旦恶意软件转换为“活动”模式，该恶意软件就会使用其他两种形式的子域。这些不包括AD域，而是正在运行的服务列表或时间戳的编码。

开源社区在逆向工程许多子域表单方面做得非常出色。大多数解码器都专注于恢复最有用的信息：子域中嵌入的用户ID和域名。建议有权访问DNS日志的受害组织溯源人员使用这些工具来确认其AD域未嵌入SUNBURST生成的DNS子域中。可以参考以下来源来解码此类域：

https://github.com/RedDrip7/SunBurst\_DGA\_Decode

https://blog.cloudflare.com/a-quirk-in-the-sunburst-dga-algorithm/

##   

命令与控制  
  

  

SUNBURST使用包含DNS和HTTP的两部分C2协议。在“被动”模式下，后门通过DNS与C2协调器进行通信，并接收更新。例如，C2控制者可以控制后门休眠和唤醒。当后门处于“活动”模式时，它通过HTTP与最终的C2服务器通信，并接收详细的命令，例如“生成进程”或“传输文件”。

## DNS C2和C2协调器协议

与C2协调器通信时，后门会通过其DGA连续生成域。后门将生成域之间的随机间隔延迟执行。在某些情况下，此延迟最多需要9个小时。

如果C2协调器以DNS A记录响应，则SUNBURST会根据IP地址块的硬编码列表检查解析的地址。如果地址位于一个块内，则后门将转换为关联模式。后门以“被动”模式启动，在该模式中，它仅通过DNS检查阻止列表、睡眠和信标，直到看到过渡为止，什么都不做。其他模式是“活动”模式和“禁用”模式，在这种模式下恶意软件通过HTTP进行通信，在“禁用”模式下，永久禁用恶意软件。这些模式和转换在“操作模式”部分中定义。

C2协调器还可以使用DNS CNAME进行响应。在这种情况下，恶意软件会将CNAME中的指向域用于HTTPS C2通信。SUNBURST启动一个线程来处理命令执行和其他C2 HTTP（S）标注。如果发现avsvmcloud .com的子域的CNAME解析，则UNC2452很有可能在环境中启动了后续C2。

请注意，恶意软件必须在接收DNS CNAME响应之前立即收到指向以下子网之一的DNS A记录响应。否则，CNAME解析将被忽略并视为错误。此外，对于这些子网，将记录IP地址中最低有效字节，以获得配置数据。

##   

HTTP(S) C2  
  

  

在收到要与之通信的新主机的CNAME DNS响应之后，SUNBURST启动一个新线程来执行HttpHelper.Initialize方法。此方法负责C2通信和调度。HTTP线程通过延迟由SetTime命令控制的可配置时间开始。两次调用之间，HTTP线程至少延迟一分钟。该恶意软件使用HTTP GET或POST请求。该示例禁用证书验证，因此如果执行SSL中间人攻击，则可以解密HTTPS通信。

该恶意软件根据子字符串的随机选择构造HTTP GET或POST请求URI。使用的方案取决于CNAME DNS响应之前收到的A记录。发送GET请求时，恶意软件会添加“ If-None-Match” HTTP标头，其中包含编码的用户ID。这可能确定C2服务器哪个SUNBURST安装生成了该请求，从而进一步在单个服务器上启用C2流的多路复用。

在观察到的流量中，C2服务器使用隐写术将数据隐藏在HTTP响应正文中，并尝试显示为与.NET程序集相关的良性XML。命令数据分布在许多GUID和十六进制字符串中。通过使用以下正则表达式搜索十六进制字符串，从HTTP响应主体中提取命令：“ \\ {\[0-9a-f-\] {36} \\}” |“ \[\[0-9a-f\] {32}” |“ \[0-9a-f\] {16}”。响应中匹配的子字符串将针对非十六进制字符进行过滤，将他们合并在一起并进行十六进制解码。

![](../Images/a0554c1f9374c5d1446d2f355c21d9b5.png)

SUNBURST使用包含UTF-8字符串、附加的4字节DWORD和8字节userID协议将消息发送回C2服务器。这些是经过DEFLATE压缩的压缩文件，并使用XOR密钥对单字节XOR进行了编码。长度为10,000，更短的消息的有效载荷被转换为JSON文档，该文档类似于SolarWinds。大于10,000字节的消息按原样在HTTP请求正文中发送。

伪造的OIP文档包含以下字段：

1.userId –受害机器的唯一标识符

2.sessionID –为每个HTTP线程存储一个新的随机GUID

3.Timestamp、Index、EventType、EventName、DurationMs、Succeeded和Message。

JSON密钥EventType硬编码为Orion，而EventName硬编码为EventManager。经过Base64编码的消息发送到C2服务器，并存储在steps数组中的Message字段中。时间戳字段中的整数必须设置为0x2，以指示在恶意软件响应中使用了消息字段的内容。0x2位被清除的对象时间戳字段包含的随机数据在组合恶意软件响应时会被丢弃。

操作方式  
  

  

如DGA部分中所述，恶意软件具有多种操作模式，这些模式由A记录解析的IP块配置，并且取决于是否存在CNAME记录。这些操作模式存储在内部枚举中。接下来将描述这些映射和值。

以下模式控制恶意软件的内部操作：

| Mode Name || Value || Description |
| --- | --- | --- |
| Truncate || 3 || Disabled; the malware killswitch has been activated and the sample may never run again without external modification to the XML configuration on-disk. |
| New || 4 || Passive mode; DGA subdomains encode the system’s domain name |
| Append || 5 || Active mode; C2 beaconing will occur on next CNAME resolve or is already actively occurring. DGA domains encode either the userID or the list of services |

模式值将写入后门配置键ReportWatcherRetry中。研究人员可以考虑恢复恶意软件配置并检查此配置值以确定恶意软件的最后运行模式。

Q&A  
  

  

1.运行阻止程序，服务或驱动程序的系统是否不受威胁？

有时，但并非总是如此。如果找到了被黑名单列出的进程或驱动程序，则SUNBURST将无条件退出，直到不再被检测到，它们才会运行。另一方面，通过设置控制启动初始化的注册表值来禁用服务，并且服务不会显式停止。因此，当恶意软件稍后执行服务检查时，被列入黑名单的服务可能仍在运行。因此，在运行受黑名单限制的服务时，有可能感染受害系统。此外，SUNBURST仅尝试禁用服务一次，就更新其配置以将服务标记为已禁用。一旦配置更新，该服务在后续执行期间将不被视为列入黑名单的条目。 

2.在事件响应期间，观察一种DGA编码对另一种编码是否提供任何信息？

简短的答案：网络日志中DGA编码的更改表明该恶意软件可能已从“新建”移动到“附加”或“附加移到新建”。这会将恶意软件置于一种模式，在这种模式下，可以看到CNAME记录，那么HTTP C2就可以开始。事件响应应集中于尝试识别成功解析的CNAME记录，而不是完全集中于DGA编码。日志与更强的信号跟踪恶意软件模式相比，识别CNAME记录要容易得多。

3.什么是“ killswitch”？

FireEye发现某些DNS响应会导致恶意软件禁用自身并停止进一步的网络活动。

4.发生C2通信时，是否需要CNAME记录？

C2活动必须在通过CNAME记录提供的域名上进行。它不能直接通过原始IP发生。为了初始化C2信标，后门首先从其特殊的NetBios子网中查找A记录响应，然后期望收到CNAME记录。

5.如果将DGA域解码为公司域名，该公司是否受到威胁？

当后门处于“被动”模式时，它将使用DGA编码，该编码嵌入受害AD域名。这意味着存在后门的任何系统已经开始尝试联系DNS服务器，攻击者随后可以激活该后门以启动C2通信。如果从任何DNS日志中解码其域，则不能假定组织经历了后续活动。具体来说，它仅表示存在后门代码并且能够被激活。
