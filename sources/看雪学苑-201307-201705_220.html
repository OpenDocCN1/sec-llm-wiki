无需文件的 UAC 绕过方式：使用eventvmr.exe和注册表劫持

在深入挖掘 Windows 10 并且发现了一种相当有趣的绕过用户账户控制的方法后，我决定花点更多的时间来寻找能其他能用来绕过 UAC 的潜在技术。当前已经有一些公开的 UAC 绕过技术，这些技术大多需要一个使用 IFileOperation COM对象的带特权的文件复制，或 WUSA 提取（在Windows 7上），来帮助对受保护系统位置下的DLL 的劫持。所有这些技术都需要释放一个文件到磁盘（举个例子，放置一个 DLL 到磁盘来实施DLL劫持）。你可以在这里（由 @hfiref0x 提供）看一下其中的一些已被公开的技术。本文介绍的技术不依赖于一个带特权的文件复制、代码注入或将一个传统文件（比如DLL）放置到磁盘。这项技术目前已在 Windows 7 和 Windows 10 上经过测试，但理论上它应该可以工作在所有执行 UAC 的 Windows 版本上。


正如我在我的上一篇博文《使用磁盘清理绕过UAC 》内提到的：在 Windows 上，一种用来调查加载行为的典型方式是使用 SysInternals Process Monitor 来分析当一个进程执行时的行为。在用 ProcMon 深入挖掘 Windows 日志管理的过程中，我注意到 eventvwr.exe 会在HKEY_CURRENT_USER 储巢下执行一些注册表查询，以启动一个高权限进程。


在太深入之前，有必要理解一下什么是 HKEY_CLASSES_ROOT（HKCR）储巢和 HKEY_CLASSES_USER（HKCU）储巢，以及它们是怎么交互的。HKCR 储巢只是 HKLM:\Software\Classes和HKCU:\Software\Classes 的一个简单结合。你可以在这里阅读更多关于 HKCR 和为什么 HKLM 与 HKCU 需要合并的内容。既然这些储巢是合并的，你可以经常通过在 HKCU:\Software\Classes下创建键的方式，劫持 HKCR:\ 下相同名称的键。既然这层关系存在在这两个储巢内，任何与 HKCU 及 HKCR 进行交互并且成功的提权进程都是特别有趣的，因为你能够篡改 HKCU 里面的值。作为一个普通用户，你有对 HKCU 注册表键的写权限；如果一个提权的进程与这些你将要操纵的键进行交互，你就有可能干扰一个高权限进程将要尝试去执行的动作。


你们中的一些人可能知道，有一些微软签名的二进制文件是自动提权的，因为它们的 manifest 文件里面写有相应信息。你可以在这里阅读到更多关于这些二进制文件和 manifests 的知识。通过使用 SysInternals 系列的“sigcheck”工具，我验证了“eventvwr.exe”的自动提权过程是通过它的 manifest 完成的：



当更深地挖掘 ProcMon 的输出结果，我注意到“eventvmr.exe”在和HKCU\Software\Classes\mscfile\shell\open\command 交互，这导致一个“NAME NOT FOUND”的返回结果。随后，eventvmr.exe 被看到与 HKCR\mscfile\shell\open\command 进行交互，我注意到这个键对应的默认值被设定为对mmc.exe 的调用（微软管理控制台），这个程序代表加载 “Snap-Ins”组件对象模型：



正如上面提到的，从一个高权限进程对HKEY_CURRENT_USER (或者HKCU)的调用是相当有趣的。这经常意味着一个提权的进程不知怎么回事在与一个中等权限进程能篡改的注册表位置进行交互。在这个例子里面，我观察到“eventvwr.exe”在HKCR\mscfile\shell\open\command 之前查询了HKCU\Software\Classes\mscfile\shell\open\command。既然HKCU值返回了“NAME NOT FOUND”，这个提权的进程查询了 HUCR 的相应位置：



从结果来看，“eventvmr.exe”作为一个高权限进程，查询了 HKCU 和 HKCR 注册表储巢来启动mmc.exe。在 mmc.exe 启动后，它打开了eventvmr.msc，这是一个微软已保存的控制台文件，使得事件视图能被展示出来。因为微软管理控制台（MMC）加载了微软已保存的控制台文件（.msc）。你可以在这里读到更多关于微软管理控制台和相关的微软已保存的日志文件的知识。

有了这个信息，我决定去创建“eventvmr.exe”需要的注册表结构，以使它成功查询 HKCU 位置而不是后面的 HKCR 位置。既然位于HKCR\mscfile\shell\open\command 的（默认）值包含一个可执行文件，我决定将其简单地替换成 powershell.exe 可执行文件（的全路径）：



当打开“eventvmr.exe”的时候，我注意到它成功地查询和打开了HKCR\mscfile\shell\open\command键：



这个行为有效地用我们的值“powershell.exe”替换了本来应该是“mmc.exe”的值。随着这个进程继续执行，我观察到它结束后启动了“powershell.exe”而不是“mmc.exe”：



借助 Process Explorer 工具，我能够确认powershell.exe 确实在以高权限运行：



基于这个我能够劫持进程启动的事实，轻易启动我向要的任何恶意 PowerShell 脚本/命令都是可能的。这意味这代码执行可以在不需要释放一个DLL或其他文件到文件系统的情况下，被一个高权限的进程完成（绕过UAC）。这显著地降低了攻击者的风险，因为他们没有将一个传统文件放置到文件系统这种易被杀软\主防抓到，或者在随后被取证识别出来的行为。

为了证明这种攻击，Matt Graeber（@mattifestation）和我构造了一个powershell脚本，当这个脚本在系统上执行的时候，会在当前用户的注册表储巢下（HKCU\Software\Classes\mscfile\shell\open\command）创建一个所需的注册表入口，并将默认值设定为任何你想通过-Command参数传递过去的值，随后运行“eventvmr.exe”，最后清理创建的注册表入口。


你可以在这里找到上面的脚本：https://github.com/enigma0x3/Misc-PowerShell-Stuff/blob/master/Invoke-EventVwrBypass.ps1


在脚本内部，我们提供了一个示例命令。这个特殊的命令使用powershell向C:\UACBypassTest文件写入“Is Elevated: True”。这能够证明被执行的命令背后是一个高权限进程，基于“Is Elevated”等于True，并且输出的文本文件被写入了一个中等权限进程不被允许写入的位置（译者注：普通用户对C盘根目录没有写权限）这两个事实。


由于拥有一些便利性的优势，这项技术与其他已被公开的技术有些不同：


1．这项技术不需要释放一个传统文件到文件系统。当前大多数（如果不是全部）公开的UAC绕过方式需要释放一个文件（通常是一个DLL）到文件系统。这样做会增大攻击者被抓到的风险。既然这项技术不需要释放一个传统文件，攻击者面临的额外风险就被缓解了。


2．这项技术不需要任何进程注入，这意味着攻击者不会被监视这类行为的安全解决方案打上标签。


3．不需要带特权的文件复制。大多数 UAC 绕过技术需要某些带特权的文件复制，用来将一个恶意 DLL 放置到一个安全位置，方便进行 DLL 劫持。既然这项技术可以替换“eventvmr.exe”这个可执行文件启动去加载所需的 Snap-In 托管程序这一过程，它也可以被简单换成去使用一个已存在的，被信赖的微软二进制文件，在内存中去执行代码。

 

这项特别的技术可以通过将 UAC 级别设定为“Always Notify”或将当前用户从本地管理员组中移除来被补救或修补。进一步的，如果你想要监视这种攻击，你可以使用方法/规则去查找并警告HKCU\Software\Classes\下的新注册表入口。
