攻击方

防守方


看雪版主&评委 netwind 点评


此题设计新颖，加密保护技巧比较独到。作者设计了一个调试虚拟机来调试执行被保护的代码。被保护代码每次出现异常都会调用执行 case 表所指向的函数，而这些函数都是在调试虚拟机里实现的，追踪到了这些函数才能破解此题。


作者简介


QuiZow，贵州人，科锐 22 期学员，2015 年 8 月开始接触编程。之前学习经历主攻数学，10 月进入科锐学逆向，越学越感兴趣。


目前主要学习重心为安卓和 Python。


设计思路


这个 CM 设计思路来源于我在 CR 做的一个调试器项目；


我直接实现了一个小型调试器，语言是用 C++ 写的，当中没有用第三方库，就是 C 函数加winAPI，我叫他调试虚拟机文件名为CrackMe.exe；


而被调试的程序框架是用汇编写的，当中部分函数是混合编译了纯 C 代码生成的 obj，

名为 CrackMe_QuiZow_20161227，也是实际的窗口程序,由调试器启动；


需要把握住一点是，窗口程序人为制作的所有异常都实际上是在调用”内核”函数,而这个打引号的内核函数实现是放在调试虚拟机中实现的。


逻辑流程


一. 调试虚拟机调试启动窗口程序；


二. 窗口程序先 LoadLibrary 一下确定 kernel32的基地址，在空闲寄存器中指明 kernel32 的基地址，导入表填写位置，内存传参首地址以及其他要初始化的内容,制作单步异常；


三. 调试虚拟机接收单步异常后填入初始化内容并且保存内存传参首地址,完成初始化工作；


四. 这时候窗口程序根据宏定义的下标 call 导入表中的 API 地址,这样窗口程序的窗口功能就具备了；


五. 用户输入 SN 后窗口会调用总验证函数,总验证函数有8-9个分验证函数；


六. 这 8-9 个分验证函数内部原本都是简单的算法验证工作，我人为在每个其中制作了1-2个异常，并在制作异常之前指定内核函数 case 表的哪一项(这个很重要，对作者透明，对攻击者就是个数，有点像 windows 内核中的中断表)；


七. 指定内核函数 case 表后还要传递参数，这样这 8-9 个分验证函数就是分两段实现的，一段在窗口程序中一段在调试虚拟机中；


八. 验证都通过后通过导入表中 MessageBox 的宏下标，调用 MessageBox 弹框提示成功。


总结


这个模式等于是全程都在反调试，应该是完全避免了被动态调试，如果攻击者要动态调试，其实是在动态调试虚拟机即我自己实现的调试器，当然窗口程序中间验证过程还需要和调试器之间通过单步，内存异常等进行交互，这就使得我实现的这个调试器是唯一的虚拟机，因为别的调试器加载 CrackMe_QuiZow_20161227 不知道拿到异常应该怎么处理。


破解思路


在我写此文时候已经有了两位攻破者：风大侠和孤狼大侠；

 

破解这个 CM 需要攻击者基本了解调试器的实现，然后人工在小型调试器中找到原本属于实际的窗口程序的代码，恢复实际的窗口程序的模拟导入表以及各种异常，这样就几乎完全攻破这个程序了，程序中的算法验证都比较简单，实在不会逆推，直接穷举即可，因为大多数都是单个字节验证的；

PS：汇编写的窗口程序中间只是加了极为少量的范式混淆, 我写的混淆工具不成熟，也不敢多加；


破解的关键点是要找到我在设计思路中强调的内核函数 case 表，因为这个表窗口程序和调试虚拟机必须完全一一对应，这样调试虚拟机才能知道每个异常应该怎么处理，而我在窗口程序中每产生一个异常肯定会往一个全局变量中赋值，赋的这个值就是对应在调试虚拟机中的异常处理的 case 项；


这个 case 项的代码块也就是窗口程序异常这里缺失的代码，至于怎么翻译回来就是苦力活了(当然翻译过程还要特别细心，我传递参数是很随意的,因为对我来说调用约定想怎么定就怎么定)，所以风大侠和孤狼大侠应该是很快就定位到了缺失代码，但在搬运过程中耗费了大量时间。
