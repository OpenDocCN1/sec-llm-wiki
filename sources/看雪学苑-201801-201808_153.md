# 通过逆向PCHunter驱动学习64位 windows内核之 精准定位

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MjM5NTc2MDYxMw==&mid=2458290021&idx=2&sn=4bd0afe204bc512c518e2326542f2829&chksm=b181b7ef86f63ef92983d6f67a2b6efd0d179621f2dcd412fef707d3c833becfd218afd26232&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=MjM5NTc2MDYxMw==&mid=2458290021&idx=2&sn=4bd0afe204bc512c518e2326542f2829&chksm=b181b7ef86f63ef92983d6f67a2b6efd0d179621f2dcd412fef707d3c833becfd218afd26232&scene=27#wechat_redirect)

首先感谢下PCHunter的作者提供了这么优秀且还是免费的内核工具。  

  

这次逆向是我在科锐学习32位内核课程后，练手的小项目，感觉自己写得比较用心的，所以作为自己的首贴逆向贴，发布到看雪上来，与大家分享一下。

  

这篇作为第一篇，主要内容是通过分析 PCHunte 3环请求到0环的通信协议内容，来精准定位PCHunter驱动功能相关函数，之后的篇幅会在此基础上，逐篇分析PCHunter的各项内核功能的实现。

> 
> 版本号：1.0.0.5
> 
> 样本来源：PCHunter64.exe 释放的驱动文件  
> 
> 调试环境：host:  win7\_64 + IDA + VirtualKd  
> 
>                  dest:  WMware(win7\_64)
>

当前样本模块加载基址：

> PCHunter64ao.sys  FFFFF88003400000 00000000000C0000
> 
> nt                              fffff800\`03e00000 fffff800\`043ea000

  

因为双机调试环境搭建相关的帖子很多，所以略去。

  

在调试目标机开启PCHunter前, IDA载入样本PCHunter64ao.sys。

  

![](../Images/66703d4482b17076b2f162e5698abb6f.png)  

  

概述：

  

经过IDA分析之后,得知样本函数数量规模,大于等于1004个。

  

我的首要任务是解决在这众多的函数中，如何找到我们要分析的功能？

  

根据自己开发驱动的经验,功能较多的驱动服务中，3环应用程序一般使用DeviceIoControl函数，通过其提供的控制码功能,来实现与0环的功能请求通信，0环则通过派遣回调函数表对应的 IRP\_MJ\_DEVICE\_CONTROL 项中，3环传入的控制码来实现用户请求功能的区分和功能向下派发。

  

但是在实际分析过程中我发现，PCHunter 3环所有的用户请求控件码都是同一个，样品并没有使用常归的通信手法,难道另辟蹊径或是加密了？

  

之后经过一系列努力，最后发现作者确实是在设备控制的基础上，又实现了一套 自己的 3 环与 0 环通信协议，并对协议作了加密，解密后的内容中又发现了动态与静态的2处校验码。

  

至此心中对作者又升起一股由衷的敬意。一款免费的驱动工具，作者却一点也不马虎。

  

下面开始具体介绍菜鸟分析挑战之旅(大神老鸟可以略过)。

  

\------------------------------------------------------------------------------  

  

通过IDA很快找到样本入口处，也就是DirverEntry，F2设置断点，在目标机中打开PCHunter工具，于是IDA中断下来了。

  

如下图所示：

  

![](../Images/b1a090102f0b10720a863fcd2f8526e1.png)  

  

此时我已经有了pDriverObject对象指针

  

> WINDBG>dt nt!\_DRIVER\_OBJECT
> 
>     +0x000 Type             : Int2B
> 
>     +0x002 Size             : Int2B
> 
>     +0x008 DeviceObject     : Ptr64 \_DEVICE\_OBJECT
> 
>     //略
> 
>     +0x068 DriverUnload     : Ptr64     void
> 
>     +0x070 MajorFunction    : \[28\] Ptr64     long

  

下一目标是要找到 pDriverObject +0x070 位置的写入，也是注册其成员 派遣函数表的代码。

  

根据结构体信息参照，从入口向下，不远处就看到了关键位置，如下图所示：

  

![](../Images/3ad13ea4a0c55b16a7ec08e5cc6f3fd9.png)  

  

设备控制回调下标宏是 IRP\_MJ\_DEVICE\_CONTROL，是第14项

计算偏移等于 0x70+8\*14= 0xE0，由此可以断定图上 第二个红框就是设备控制回调函数注册的地方，对其进行命名。

  

鉴于0环和3环的通信常规是用控制码，下一步目标就是进入设备控制派遣函数中分析3环传来的控制码。

  

经过对该函数中第二个参数，IRP结构体的反复校验后，得到了通信控制码，并且找到SystemBuffer及它的长度校验位置。在此一并进行了标记，

如下图所示：

  

> signed \_\_int64 \_\_fastcall DispatchDeviceControl(\_\_int64 pDevObj, \_IRP \*pIRP)

  

![](../Images/30f01653e8b415d791ef9ff062d83980.png)

  

但是当我回到目标机器,多次刷新不同的PCHunter功能后，发现中断下来的控制码全部相同，此时断定了其采用的是统一通信控制码，并且在之后对这个固定通信控制码作合法校验，如果不等于此校验码就提前结束函数。

  

于是之前的思路就走不通了，剩下还有一种可能，就是它的功能是通过3环传的IOBuffer内的数据来区分用户功能请求的。

  

接着向下分析发现，发现了对3环传入的 IOBuffer 的操作相关代码：

  

![](../Images/602e260bdedaa27f0455756f951fede7.png)  

![](../Images/6ace460a422180604c2abca42c9ae11a.png)  

  

这段汇编代码是个循环，循环内逐字节的先作异或再求反的动作，疑似在做解密。

  

于是乎，我在此位置下断，并通过 在3环反复操作PCHunter相同和不同功能，得到多份解密后的内容，经过分析比较后得出结论：

PCHunter确实是通过3环传入0x30字节的IntputBuffer实现通信协议的,

  

下面是总结后的通信协议相关字段的功能：

  

解密后的请求协议内容：

  

![](../Images/ac9185b2bd5e607e1449ca65a6365f15.png)  

  

接着向下分析，

  

![](../Images/ba2da48e10d13f173e02831285ce15e7.png)  

  

样本在完成通信协议内容解密后，先用前4字节作为固定签名，用以验证3环请求调用者的身份。

  

之后是校验协议中的动态校验码：

  

![](../Images/a9c0c144118cbd76edab0703fe135404.png)  

  

在用户请求 动态校验成功后，再对 (请求功能号作 -0Fh + 90Dh)\*8 的运算，运算结果就是服务功能函数的相对分发基址(g\_srvfn) 的偏移， 通过全局服务请求函数信息指针加上该偏移，就能找到实现服务请求的相关功能函数，再调用此函数 就实现了3环用户请求的向下派发，如下图所示：

  

![](../Images/bafb216510f85d56db7521233070065d.png)  

  

对应的得出用户请求功能处理伪函数声明信息：

  

函数指针声明：

> \_\_int64 (\_\_fastcall \*)pfnSrvFunc(pIndata,IndataSize,pRetBuf,RetBufSize);

  

函数指针偏移：偏移 =  (用户请求号 - 0Fh +90Dh) \* 8   ;

  

相关功能函数地址：在rax中

  

在用户请求功能处理函数执行完后，用户请求的操作结果和数据返回在协义的相关字段，

  

如Retbuffer中。

  

到此，如何定位PCHunter用户层 相关功能请求的处理函数就分析完了，之后再分析PCHunter其它功能，就只要在上图红框处下断点 ( 请求功能向下派发处 )，观察用户层操作之后，通信协议中的功能号 和 传入传出的buff数据，就能精准定位PCHunter驱动功能的实现代码。
