此处可以理解为一个分发函数，由它调用到其他函数，尤其是中间那个调用，期间会调用多个反调试点，非常频繁(我单步了特别久，因此这里请自行调试分析。

  

仔细分析发现反调试主要有：

1、 自注册信号处理函数，然后自己主动抛出异常 

2、检测 android\_server 默认的 23946 端口 

3、时间检测 

4、多进程反调试 

5、 使 JDWP 相关的内存结构发生变化，让任何连接的 Java 调试器(例如 jdb)断开

  
其中第 5 种我是第一次遇到，但是因为样本中的是在 ART 模式下做的反调试对抗，而我是在 Dalvik 模式下调试的，所以没有起  
效

(这种反调试请移步阅读大神的文章 http://jxnu.hetianlab.com/html/news/news-2017040301.html)。

  

而第 4 种的反调试它主要是在 fork 的子进程中进行， 因为这里调试的是父进程，因此这里也不用管。时间检测它检测间隔比较近，因此不在中间单步就行。默认端口可以使用 android\_server -p 来自定义端口绕过。 而它的自注册信号处理自抛出异常可以说是非常频繁，所以更改IDA 的异常处理选项，使它默认让程序自己处理异常。

其中 XOSIMD.XOWAIT 来进行参数加密，这个最终也会调用到上面说明的 native 函数，而且之后可能还会进行 SecurityLibScd.cE 的二次加密也是最终会调用到上面的 native 函数，这些函数都为 ollvm+vmp 级别。 ChargeRequest 类间接继承自 com.openx.greq.c.a， 因此之后的发包和第一次一样，层层往父类上调用到 com.openx.greq.c.a， 然后层层返回。

## 总结

  

  
MG 把最重要的加解密算法全部放在了 c 层，并且加了 ollvm+vmp，发包的参数在上面都已经截图，各位可以自行总结出来。  
但是要想完整的模拟收发包，需要各位去逆向上面说的强加密函数，或者通过调试 java 层加密前后数据能自己猜出来(真能做  
到就太强了)，或者直接写个 loader 来把 so 来加载起来直接调用(我这里并没有试验 MG 是否做了对抗，各位自行验证可行性)。
