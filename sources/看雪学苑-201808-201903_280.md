# CVE-2010-0249 IE极光漏洞深入分析

## 

 前言

  

*   漏洞详情：
    

  

Use-after-free vulnerability in Microsoft Internet Explorer 6, 6 SP1, 7, and 8 on Windows 2000 SP4; Windows XP SP2 and SP3; Windows Server 2003 SP2; Windows Vista Gold, SP1, and SP2; Windows Server 2008 Gold, SP2, and R2; and Windows 7 allows remote attackers to execute arbitrary code by accessing a pointer associated with a deleted object, related to incorrectly initialized memory and improper handling of objects in memory, as exploited in the wild in December 2009 and January 2010 during Operation Aurora, aka "HTML Object Memory Corruption Vulnerability.

  

  

*   漏洞影响的操作系统版本 ：  
    

  

*   win 2000
    
*   win xp
    
*   win server2003
    
*   win vista
    
*   win server2008
    
*   win7  
    

  

  

*   漏洞影响的IE浏览器版本：
    
      
    

*   Microsoft Internet Explorer 6
    
*   Microsoft Internet Explorer 7
    
*   Microsoft Internet Explorer 8
    

  

  

*   漏洞原因：
    
      
    

通过访问已删除对象相关联的指针来执行任意代码。

## 

漏洞分析

  

*   HTTP服务器代码解读：
    

```

```

  

首先在main函数中启动了一个HTTP服务器，再用RequestHandler这个类来处理网页对服务器的访问请求,当网页访问服务器时会进行GET请求。  

  

由do\_GET函数响应，在do\_GET函数中，path等于'/'则调用get\_exploit返回html文件到浏览器， path等于'/aurora.gif'时发送gif图片数据到浏览器。

  

  

*   HTML与JavaScript代码解读：  
    

```

```

  

加载HTML文件时，首先被执行的是<script>.......</script>之中的Javascript代码，之后会进入HTML的<BODY>.......</BODY>部分执行HTML代码。

  

Javascript代码会先执行initialize函数创建200个HTML Elment对象，然后调用spray\_heap函数进行堆喷射。

  

HTML代码首先会创建一个id等于 “sp1”的 span对象，然后加载aurora.gif并在处理onload事件时调用Javascript 代码中的 ev1 函数去触发漏洞。

  

在 ev1 函数中第一个参数in\_event就是当前onload的Event对象,  函数先调用createEventObject为当前的Event事件创建一个副本，再调用getElementById访问。

  

HTML中的Span对象，并清空名为"sp1"的span对象内容, 这样将导致span对象被释放，之后调用setInterval对ev2函数进行延时重复调用，延时时间为1ms。

  

在ev2函数中会对 initialize 时创建的200个HTML Element对象的数据进行赋值, 之后使用srcElement访问对象本身触发漏洞。  

  

  

*   分析异常时基本信息 :
    

用OD启动IE浏览器，shellcode第一个字节下断，断下后观察栈区窗口，找到返回函数地址。

![](../Images/0472b6b9d1c5fc6b5dbd639703381b31.png)  

  

在IDA中输入地址找到异常函数，观察汇编代码，可以看出来这是访问虚函数表中的函数出现了错误，shellcode被当成虚函数执行了 !   

  

现在ECX对象指针的值是0x0A0A0A0A，可以看的出来对象指针已经错误, 再取出0x0A0A0A0A +0x34处的值仍然还会是0x0A0A0A0A。  

  

因为在堆喷射中已经将除shellcode外的内存数值进行了初始化，既然对象指针是错误的，那么说明调用这个GetDocPtr函数之前已经出错。

![](../Images/5403d8e387b85de0165c99c11c65ee82.png)

  

那么接下来再通过栈回溯找到GetDocPtr 的调用。

  

在 CEventObj::GenericGetElement函数的第54行：

![](../Images/f66064319725aefcdd700182a7f22e59.png)

  

CElement对象指针的是从pCtreeNode中取出的，用OD启动IE对0x7CEB5250下断，发现出错时Element对象指针的数值是0x0A0A0A0A：

![](../Images/8c800709f272999bb7bd6c7dff4d2d33.png)  

  

此时pCTreeNode对象中的内容已经被恶意数值覆盖，导致执行了恶意代码，因此可以推测pCtreeNode已经被释放。

  

  

*   CTreeNode对象分析：
    

  

CTreeNode的构造函数需要传入一个CElement参数，之后进行关联，这个传入的CElement经过分析其实是一个 CImgElement对象：  

![](../Images/43923b91c20236b10f0aa0b756ce2c46.png)  

  

CImgElement对象的构造代码比较简单，先申请了一块大小为0x40的内存，然后执行构造代码：  

![](../Images/7db06fc308fe180fabb89164d0c7c887.png)  

  

  

*   内存覆盖原因分析：
    

  

用OD启动IE浏览器，在CImgElement::CreateElement函数中的0x7CD4C76A地址处下断，输入指定的web服务器地址并进入。

  

当断点触发时，已经拿到了创建的CImgElement对象地址0x011FDF20：  

![](../Images/60398768e1e7c13aa5239fb059ae1b26.png)  

  

接下来今到CTreeNode::SetElement函数中的地址0x7CCD5296地址处按Shift+F2下条件断点，条件为0x011FDF20：  

![](../Images/c3e490dd47d72f923706a1657941eb77.png)  

  

等到断点触发后拿到CTreeNode对象的地址为0x011FD290，观察CTreeNode的内存布局可以看出来，CImgElement就存储在偏移为0的位置：

![](../Images/5f13d1d730cb084ef894812b93ea1daf.png)

  

在上面的异常分析中已经知道CTreeNode的内存出现被覆盖为0x0A0A0A0A的情况，那么为了找出产生内存覆盖的函数，需要对CTreeNode偏移为0的内存下内存写入断点：

![](../Images/e86acc092cb0007c4a7b42a27fbaa05f.png)  

  

F9运行，由于调试器附加的原因不是每一次都能被覆盖为0x0A0A0A0A，重启了IE好几次，才最终找到覆盖的函数，但此时CTreeNode的内存地址已经变成了0x011FDE90，这个函数只是一个循环copy，现在需要返回到上层函数：

![](../Images/aaec7f1656b3a5a0e12c31825573e1cb.png)  
  
一直按F8退出这个函数后发现断下来的其实是一个wcsncpy，那么这个CStr::Set函数主要是重新申请了一块内存，然后把字符串复制进新开的内存，到这里覆盖的原因其实就非常明显了，是因为此时CTreeNode对象内存已经被释放，而这边一直在申请内存。

  

一旦申请到CTreeNode使用的那片内存，就会把0x0A0A0A0A写入，而CTreeNode虽然被释放，却在CEventObj对象中还在一直使用着，也就是说CEventObj 并没有清空自身关联的CTreeNode ：  

![](../Images/25fa0c7f4c0d96624dfb907bda2b380b.png)  

  

  

*   指针重用过程调试验证：
    
      
    

用OD启动IE浏览器，重复上面的方法拿到CTreeNode地址0x011FDC70，到CStr::Set函数中的地址0x7CCD2C18地址处按Shift+F2下条件断点。

  

条件为eax >=0x011FDC00 &&  eax <=  011FDD00 , 断下来后一路F8到wcsncpy直接执行，观察内存窗口中的CTreeNode是否被覆盖成0x0A0A0A0A。

  

在经过几轮调试后成功的亲眼目睹了内存的覆盖，那么接下来再亲眼看看覆盖后如何执行的shellcode：

![](../Images/b525d572b8af16f992d8cfd08c701863.png)  

  

取消CStr::Set函数中的地址0x7CCD2C18地址处条件断点避免断点干扰， 到CEventObj::GenericGetElement函数中的地址0x7CEB5250地址处按Shift+F2下条件断点，断点条件为ecx == 0x0A0A0A0A，断点触发后可以看到ecx对象指针已经被恶意数值覆盖了，那么取消断点按F7进入函数：  

![](../Images/bc3a8d9609f2540b7ebdac6e7c1b956d.png)  

  

看看函数内部，很明显是要进行虚函数调用，不过调用的地址会变成0x0A0A0A0A，F7跟下这个CALL指令：  

![](../Images/abcdb8dda7bd50044fd72ff80d98c232.png)

  

shellcode在这片内存中的尾部，F9直接运行后计算器直接弹出！  

![](../Images/52c736fcc1c7c47c9c1175cd0de95b96.png)

  

## 

总结

  

在initiallize函数中先创建200个HTML对象方便后面进行内存覆盖，之后调用spray\_heap进行堆喷射，堆喷射就是申请了200块大内存。

  

并在每一块内存中都填入payload，在处理HTML Img 对象的onload事件时调用ev1函数创建当前事件对象的副本，创建副本对象时会关联CTreeNode，当产生对象关联后又立刻清空名为"sp1"的span对象，span对象被释放将导致 与 CEventObj副本对象关联的CTreeNode被释放。

  

接着重复调用ev2，ev2函数中对200个HTML对象 的数据进行赋值，值的内容为0x0A0A0A0A，而关键是每次赋值都会申请空间，一旦申请到了被释放的CTreeNode，就会把0x0A0A0A0A覆盖进去，产生覆盖后又调用副本对象的srcElement，执行get\_srcElement函数时会访问与CTreeNode，此时CTreeNode已经错误了，也就导致了payload的执行。
