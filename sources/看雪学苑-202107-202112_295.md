本文章仅作学习交流用途，最近看个样本，是4代注册协议了，来兴致分析了下。 ![](../Images/0fdd426982e6f1717779ef9c6e0b5448.png) 跟3代比，没有了finger和pri。我猜测data和ep也是八九不离十，也是这两个东西。  
![](../Images/1ea538e4f17ade033f9b6fda577c33ad.png)  
  
jni注册是这3个函数，比之前少了很多，后面hook了下w11是主函数加密。之前tn，pri都是在java层加密的。现在全部放在了ndk中。 进去w11这个之后，就是ollvm混淆的，hook一遍入参之后：  
![](../Images/97e2d83fcdeceadbdd1839099006fdf8.png) 这里先从rsakey出发，为了验证之前的猜想。查看引用，  
![](../Images/2e30746c3a08ead83208f066e9e199f2.png)  
  
跟到这一块有字符串加密了：  
![](../Images/132c2fbfab7dfd54fb2740fd4afc4cb0.png)  
  
那直接frida看内存就行。 这里推荐用unidbg去跑这个脚本，刚好之前龙哥也跑过sm，拿来就用。 先unidbg下个断点。

*   
*   

```
Debugger debugger = emulator.attach();debugger.addBreakPoint(module.base + 0x17E00+ 1);
```

  
断下来之后在控制台直接看这一片的内存。 ![](../Images/8013bf6cb0453ddf95b8ef3e51eb890c.png)  
  
一清二楚了。

*   
*   
*   
*   
*   
*   
*   
*   

```
sub_8C1E8(v48, &byte_DB176, *orgation);sub_8C1E8(v48, &byte_DB183, &byte_DB186);sub_8C1E8(v48, &byte_DB18E, *appiddetaily);sub_8C258(v48, &byte_DB194, COERCE_UNSIGNED_INT64(2.0), HIDWORD(COERCE_UNSIGNED_INT64(2.0)));sub_8C258(v48, &byte_DB19B, COERCE_UNSIGNED_INT64(3.0), HIDWORD(COERCE_UNSIGNED_INT64(3.0)));sub_8C1E8(v48, &byte_DB1A4, v52);// data  这个时候的data已经加密好了 随机数的md5keysub_8C1E8(v48, &byte_DB1A9, v50);// tn a100str(有b1，就是data加密前的str)+ep+orgation+appid+sm_tn 的md5 加密，在一次rsasub_8C1E8(v48, &byte_DB1AC, v51);// ep 随机数的rsa
```

  
拿到这些，8c1e8一看就是hash.put这样的操作。 先从ep开始分析。在5280c这块查看了引用（这是另一个so，本文中调试的so不是这个地址）。  
![](../Images/c4ac1c437dd10ee195da88b9d18105da.png)  
![](../Images/5516b035e6598ebb0340480e3eaeca85.png)  
  
unidbg断下来之后。看看这个函数的参数。一般都是r0-r4.r0就是第一个参数。  
![](../Images/aa9bc3220b6cfb426f3306b44c7f3127.png)  
  
更加确定了ep会用rsa加密。 第二个参数。  
![](../Images/4180d71dfc983620ff70e8337204a7f2.png)  
  
分析过3代的都知道，是根据一个随机数加密的rsa。这个随机数就是指纹最终加密的aes的key。 这里我把它固定住了。  
![](../Images/223d66a1edaa9bb2a77da148d3d843b4.png)  
  
从这个函数黎赋值的跟进去：  
![](../Images/75b3adacb035139a858e6e42783fd145.png) ![](../Images/44236d91bbd24f29a4330dfa6a7fb992.png)  
  
用了这些c库，那就是随机值了，当前时间为随机种子。把它固定住好分析。 然后再跟进去51200这个地址，大致看一下，也就是调用java层的rsa加密。 这里可以通过unidbg的jni打印来验证猜想。  
![](../Images/256c261ea3770053d4ca278ac649c4e2.png)  
确实是，那直接从unidbg中hook住这些结果看看。  
![](../Images/cff53840d86db7267d55ceb69c6cea1c.png)  
  
这是我写3代的时候写的代码，结合unidbg输出看看。  
  
![](../Images/d5eb1fd491cc522626b942ba27a42eda.png)  
果然一看：  
  
![](../Images/e4e2c58612dc94a523703df97bc1bf50.png)  
那没事了。跟3代一样。 继续分析tn，回到开始hash.put这里。也是同样的套路。废话我就不多说了。  
![](../Images/f41ad29cc177f0165e18dfd99b1cea35.png)  
  
到这里要注意，aa994是一个append操作。byte\_d51fa就是sm\_tn。这个也很熟悉。51200就是rsa加密的函数。然后hook住这个v40。 是一串md5、从4d06c那里打下断点来看，  
![](../Images/031fd168d69654f9d2e9c5dc5806a838.png)  

  

![](../Images/e1c62ab4340b24d5006a6eeb7bf67613.png)  
v43是字符串拼接之后的东西，应该是md5了一下。拿去验证一下，结果是的。  
  
![](../Images/efe5aeafe6104c673bb713afcea44beb.png)  
最后在验证一下这个值，是对的， tn的加密值也就出来了。  
![](../Images/0e93d0b56e11bedd735b79124887b2a3.png)  
最后重头戏，看data。  
data这里有很多处引用。慢慢分析吧，也可以根据unidbg先去打印一遍函数的执行流程，根据流程来trace。  
![](../Images/f833a5a07b4bc602c6de72821e9921b5.png)  
  
这里我也是习惯断在函数的前一个地址。  
![](../Images/848846d955d550c980fbd6cf8d5c7e50.png)  
  
v68就是之前那个随机数了。v66是res，那么v67是啥。 v54 = sub\_6D46C(a3, &v67); 这个函数引用了。a3就是我们需要加密的str。这个把a3做了一些操作。 deflateInit2\_(&strm, 9, 8, -15, 8, 0, &byte\_D5C55, 56); deflateEnd(&strm); 里面用到了压缩算法，那就是把整体的a3压缩了一遍，在aes一下。4c140里面是：  
![](../Images/71cb64690eefe1eab6c1efae7a69c58b.png)  
![](../Images/c326ddeb6bd49ba599ff978400a31e5e.png)  
  
的确从内存中看，也是byte流。  
为了进一步的验证，我把hex提取出来。解压一下试试：  
![](../Images/6f88ead4d6196a9758b939730b67f424.png)  
  
没啥问题。最后为了验证那个aes的算法。我们生成出来的data是根据随机值加密的。 固定住了，key也就固定住了。 拿到结果，进行解密一下，在解压缩。  
  
![](../Images/756c0bf53ee74ffd710b658a3e944db3.png)  
正常解。最终的算法我就不放了，自己研究一下就能搞定，都是标准算法。没有任何魔改的点。 最终试试。
