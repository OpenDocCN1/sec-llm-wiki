咳咳人生的三大错觉之一就是**她喜欢我**

  

![](../Images/c6646b7ca3e4027158c5c9238ac571f5.png)

  

为了解开粉丝的疑惑

让他面对现实

今天我就来给大家揭秘

乱码背后那些不为人知的事

![](../Images/2d30bcd2c9da2690e95c78b04c66394c.png)

首先

我们要意识到

『乱码』

本质上是**编码与解码的方式不一致**  

  

![](../Images/d8bed6a94fd88f54b2a7cc8deeeee313.png)

  

举个例子  

当用拼音的方式来解读英文  

![](../Images/2bf4fabfeac0cf13e14f152dbeae8b14.png)

事实上

Excel 对中文的解析编码  

默认是 **GBK**

  

![](../Images/165db47526635973a9c5fe8161008959.png)

  

所以

当有人把 **UTF-8** 编码的 Excel 文件发给你

Excel 默认会用 **GBK** 去解析

双击打开

出现一大坨乱码

其实是很正常滴

才不是有什么隐含信息呢

  

![](../Images/9baa244f8317ba4fe2b43a5051cd955a.png)

  

那么遇到这种问题该怎么解决呢？

  

![](../Images/08bcf3d37192b6514c71d0c2dda979a9.png)

知道了乱码产生的原理是  

**读取的编码方式与写入时不一致**

那么解决办法就很简单了

(把读取的编码方式改为 UTF-8)

![](../Images/3bc8da71bc99813d426aad7d9de0bcce.png)

![](../Images/775ae02eac68b9e316a027af32cfaf58.png)

因为 Numbers 默认是 **UTF-8**

所以不会显示乱码

![](../Images/cdfcb627b2105cdc73af878fe6ad111e.png)

什么？你说就这？

作为程序员  
当然还有更装逼的办法当然还有更加极客的办法(把文件转为 GBK)

```
iconv -f UTF-8 -t GB18030 test.csv > test2.csv
```

  

![](../Images/43e43732e11ead65b45827df00b339bb.png)

轻松搞定

  

![](../Images/1198c568ceaaf2a7c7d88c0923d87859.png)

  

既然讲到这了

那就再讲讲 **UTF-8** 到底是个什么东东

(非战斗人员可以撤离了)  

![](../Images/38e9e74887cea5c26c55200310ce2838.png)

首先，我们都知道

计算机起源于美国

他们用二进制来存储数据

![](../Images/f5fc81453243cd89fd63936f070e9804.png)

  

每一个 0 或 1 称为**一位**

  

![](../Images/d3e1e7beefa28e2ff76cc94076b10170.png)

  

而八位就组成了一个**字节**

![](../Images/3860c08867dba4b66f91a85f38131a12.png)

  

每一位能标识两种状态

每个字节则能标识 2^8 = 256 种状态

那么这些状态有啥用呢？

  

![](../Images/87a3849a8ea218ac89fc2050bfe3d05a.png)

  

美国人把 **0 - 127** 这 128 个状态

都映射到各种字符上

包括**大小写英文字母、标点符号、数字**等

这就是常说的 **ASCII** 字符集

![](../Images/7d3f0d12e5f11128f0d564e5fa6aeac2.png)

  

后来

随着其他国家开始使用计算机  

ASCII 里没有他们的字母

他们便利用起剩下的 128 - 255 位

这被称为 **ASCII 拓展字符集**

  

然而

事情并没有这么简单

等到中国人开始使用计算机时  

已经没有多余的位置了  

咋办呢？

  

![](../Images/9fbe8ec4ba8028cc1484ae5276ee18ea.png)

  

智慧的中国人民

毫不客气地去掉了127 位之后的编码

**用 2 个字节来编码一个汉字**

这样一来

7000 多常用汉字的编码问题就解决了

这就是 **GB2312 编码**

它是对 ASCII 的中文拓展

  

![](../Images/bd0c7aaeb8ba804fbc6e7b4373fea041.png)

  

但汉字实在太多了  

GB2312 不够用了咋办呢  

这个问题充钱(拓展)就能解决

  

![](../Images/829efdf42fceec5e95b66a456cf9e2d1.png)

  

这回拓展出了**GBK**

不仅包含 GB2312 所有内容  

还包含了 20000 多个

新的汉字(含繁体字)

  

![](../Images/08431e18efdd000af9659022ea7dd904.png)

  

再后来少数民族也要用电脑了

GBK 又拓展成了 **GB18030**

这一系列汉字编码标准被通称为  

**DBCS**

![](../Images/cfd8029dbd6b6cd7d8e00206df84eab6.png)

  

中国人的编码问题解决了  

但日本、韩国各自的编码问题咋办呢？

  

他们也各自搞了一套自己的编码标准  

结果就是

**谁也不支持谁**

  

![](../Images/fbbb2a982565f34bbd3025c8b282c722.png)

  

兼容性问题眼看着愈来愈严重

这可咋办呢？  

  

这时

**Unicode**

闪亮登场

  

![](../Images/df81857a82146c743341a09fd8659743.png)

  

Unicode 的制定就是为了

将世界上所有的符号都纳入其中

每一个符号都给予一个独一无二的编码

如此一来就可以**解决乱码问题**  

(虽然到现在并没有解决)

这就是字符集的发展过程

  

![](../Images/aa4b74fe34a24ad554ec024abce2e78a.png)

  

回到 UTF-8  

它其实是 Unicode 字符集的一种编码方式

  

![](../Images/84c8918e5fb0e7ef13487df1f9a62ee4.png)

  

UTF-8 由  

**肯·汤普逊**

和

**罗勃 · 派克**

发明

  

![](../Images/a0e66ef6bb02831b352f2d6c022dbe8e.png)

其中

**肯·汤普逊** 是名副其实的大佬  

  

![](../Images/73a758e6f89741a88c52f404bb821b1b.png)

![](../Images/cf58f989c2d665e94de459bdfaaf341c.png)

听听  

这是人话吗  

  

![](../Images/484b2566e27f5ad02759ddcb426da1c0.png)

  

知道了 UTF-8 的来历  

那么 UTF-8 具体是怎么编码的呢？

![](../Images/a06a75aba8b292d01ae836a13c015fc5.png)

UTF-8 作为一种可变长的编码方式  

也就是说

**不同的字符占用的字节数不同**

  

2003年11月

UTF-8 被 **RFC 3629** 重新规范后

使用 1- 4个字节来进行编码

规则其实很简单  

![](../Images/058ab8463457ff466e9bef56ad749245.png)

看不懂没关系

来看几个例子

  

![](../Images/47516433b2ea691eb9b3553b32d611f6.png)

![](../Images/0afd47a0be5a2d394f755bd2a356bb39.png)

同一句话被编码后的 01 字符串不同  

(正如我们前面所说的 UTF-8 和 GBK)  

  

![](../Images/497480bf288439fb6d2983d4643168aa.png)
