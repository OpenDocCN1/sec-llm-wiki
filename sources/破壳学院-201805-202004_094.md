# 提问の正确姿势

自破壳学院开课以来，学员们在学习的过程中不可避免会遇到各种问题。在回收问题的时候，我们发现大多数都表达不够清晰，或者缺少过程，隔着两个电脑屏幕的老师傅，纵有十八般武艺，但看不懂各位学员的提问也无处施展。

  

而很多学员的问题因此很容易就被忽略掉，没有得到应有的解答。这和我们宣传的「性感老师傅在线答疑」的定位相悖。  

  

为了方便各位学员提问和老师傅爆发小宇宙，我们参考了《提问的智慧》并总结了以下几点提问技巧，希望对大家的学习有所帮助。

  

![](../Images/c235c4fb01e1591732100362f0b2b1a7.png)

  

  

**提问前，先试着自己解决？**

  

黑客精神在于「热衷于动手解决问题」。在提问之前，你有没有先试着去解答自己的疑问呢？

  

你遇到的问题，或许也是大多数人遇到的问题，事实上，现代最好的老师叫搜索引擎，很多简单的问题，Google 和百度都能找到答案。你可以尝试：

  

> *   **在你技术论坛的旧文章中搜索答案。**
>     
> *   **在上网搜索以找到答案。**
>     
> *   **在阅读手册以找到答案。**
>     
> *   **在阅读常见问题文件（FAQ）以找到答案。**
>     
> *   **在自己检查或试验以找到答案。**
>     
> *   **向你身边的强者朋友打听以找到答案。**
>     
> *   **如果你是程序开发者，请尝试阅读源代码以找到答案。**
>     

  

使用搜索引擎也应当遵循某些策略。比如先搜索你所遇到的各种错误信息，样很可能直接就找到了能解决问题的文件或线索。

  

当然，也不要指望几秒钟的搜索就能解决一个复杂的问题，但也许你能在上述过程中收获更多，所学到的东西会更好。

  

当你无法从搜索引擎中寻找到自己想要的答案，这时候就轮到老师傅出场了。

  

![](../Images/e08de5fb7c83cf0b8d5300172f0f86ca.png)

  

  

**提问是一门技术活**

  

学会如何表达清楚你的问题，不但能让你清晰地明白自己的疑问在哪，还能极大地提高老师傅答疑的效率。

  

**1）使用有意义且描述明确的标题**

  

一个好标题范例是「目标—差异」式的描述，许多技术支持组织就是这样做的。在目标部分指出是哪一个或哪一组东西有问题，在差异部分则描述与期望的行为不一致的地方。

  

例如：

  

> **蠢问题：救命啊！我的笔记本电脑不能正常显示了！**
> 
> **聪明问题：X.org 6.8.1 的鼠标光标会变形，某牌显卡 MV1005 芯片组。**
> 
> **更聪明问题：X.org 6.8.1 的鼠标光标，在某牌显卡 MV1005 芯片组环境下 - 会变形。**

  

编写目标 —— 差异 式描述的过程有助于你组织对问题的细致思考。是什么被影响了？ 仅仅是鼠标光标或者还有其它图形？只在 X.org 的 X 版中出现？或只是出现在 6.8.1 版中？ 是针对某牌显卡芯片组？或者只是其中的 MV1005 型号？ 一个黑客只需瞄一眼就能够立即明白你的环境和你遇到的问题。

  

**2）用清晰、正确、精准并语法正确的语句表达**

  

我们从经验中发现，粗心的提问者通常也会粗心的写程序与思考。

  

正确的拼写、标点符号和大小写是很重要的。花点额外的精力斟酌一下字句，用不着太僵硬与正式 —— 事实上，黑客文化很看重能准确地使用非正式、俚语和幽默的语句。但它必须很准确，而且有迹象表明你是在思考和关注问题。

  

正确地拼写、使用标点和大小写。不要全部用大写或全部小写，因为不易阅读。

  

**3）精确地描述问题并言之有物**

  

> *   **仔细、清楚地描述你的问题或 Bug 的症状。**
>     
> *   **描述问题发生的环境（机器配置、操作系统、应用程序、以及相关的信息），提供经销商的发行版和版本号（如：Fedora Core 4、Slackware 9.1 等）。**
>     
> *   **描述在提问前你是怎样去研究和理解这个问题的。**
>     
> *   **描述在提问前为确定问题而采取的诊断步骤。**
>     
> *   **描述最近做过什么可能相关的硬件或软件变更。**
>     
> *   **尽可能的提供一个可以重现这个问题的可控环境的方法。**
>     

  

以上几点中，当你报告的是你认为可能在代码中的问题时，给老师傅一个可以重现你的问题的环境尤其重要。当你这么做时，你得到有效的回答的机会和速度都会大大的提升。

  

**4）按发生时间先后列出问题症状**

  

问题发生前的一系列操作，往往就是对找出问题最有帮助的线索。因此，你的说明里应该包含你的操作步骤，以及机器和软件的反应，直到问题发生。在命令行处理的情况下，提供一段操作记录（例如运行脚本工具所生成的），并引用相关的若干行（如 20 行）记录会非常有帮助。

  

如果挂掉的程序有诊断选项（如 -v 的详述开关），试着选择这些能在记录中增加调试信息的选项。记住，多不等于好。试着选取适当的调试级别以便提供有用的信息而不是让读者淹没在垃圾中。

  

如果你的说明很长（如超过四个段落），在开头简述问题，接下来再按时间顺序详述会有所帮助。这样老师傅在读你的记录时就知道该注意哪些内容了。

  

**5）描述目标而不是过程**

  

如果你想弄清楚如何做某事（而不是报告一个 Bug），在开头就描述你的目标，然后才陈述重现你所卡住的特定步骤。

  

经常寻求技术帮助的人在心中有个更高层次的目标，而他们在自以为能达到目标的特定道路上被卡住了，然后跑来问该怎么走，但没有意识到这条路本身就有问题。结果要费很大的劲才能搞定。

  

例如：

  

> **蠢问题：**
> 
> **我怎样才能从某绘图程序的颜色选择器中取得十六进制的的 RGB 值？**
> 
>   
> 
> **聪明问题：**
> 
> **我正试着用替换一幅图片的色码（color table）成自己选定的色码，我现在知道的唯一方法是编辑每个色码区块（table slot）， 但却无法从某绘图程序的颜色选择器取得十六进制的的 RGB 值。**

  

第二种提问法比较聪明，你可能得到像是建议采用另一个更合适的工具的回复。

  

![](../Images/75b46c8abe1ec69abbc6a87330f7d2aa.png)

  

**问题解决后，记得总结**

  

黑客本质上是一群懒虫。他们善于解决问题，但不屑于去重复解决问题，当你将问题解决之后，理应总结出自己的错误在哪，或是哪里操作不当，这样在以后遇到类似问题时，也会有一个大概的解决思路，对于有深度的问题，张贴调试记录的摘要是有帮助的。描述问题的最终状态，说明是什么解决了问题，在此之后才指明可以避免的盲点。

  

更重要的是，当别人问到你同样的问题时，你也可以像老师傅一样，指点江山。思考一下怎样才能避免他人将来也遇到类似的问题，试着写一份文件或加个常见问题（FAQ）看会不会有帮助，并分享出去。

  

在黑客中，这种良好的后继行动实际上比传统的礼节更为重要，也是你如何透过善待他人而赢得声誉的方式，这将是非常有价值的资产。
