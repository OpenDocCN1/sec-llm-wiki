前提

值得先提的是，涉及的所有静态分析的知识都可以通过南京大学李樾、谭添老师以及北京大学熊英飞老师的软件分析课程学习到，我学历低微，理解的不一定对，如有冲突或错误，还请以各位老师为权威，非常感谢各位老师以及各高校提供这么好的公开课程让像我这种没有机会在校学习的同学们能一窥程序分析的堂奥。

Analysis Engine

Analysis Engine 是由 JEB 驱动的 Android/Java 字节码分析引擎，负责对目标进行静态的代码分析，具备代码结构（Hierarchy）、调用图（Call Graph）、数据流图（Data Flow Graph）、类型推断（Type Inference）等分析能力。

Data Flows

我最初的目的就是为了做数据流分析，而引擎里提到的这些分析，大部分都是为了构建准确的数据流图而准备的。

那么，数据流分析是什么？我的理解是：一种分析数据在代码里的“流”向的方法，这里的数据在代码里可以指一个常量、变量或者字段；而“流”，可以是数据 A 指向另一个数据 B（指针分析，B = A），或者由数据 A 产生了另外一个数据 B （污点跟踪，B = f(A)，比如 f(x) = x^2），都可以称之为 A 流向了 B。而数据流图就是以数据为节点（node）、以流为边（egde）的图形数据结构。

过程内数据流分析

JEB 已经实现了过程内的数据流分析，并且其是基于 Dalvik 指令实现的，这代表我们连 JEB Pro 都不用买， 用免费的 JEB CE 就能白嫖到这个功能。

JEB 提供了 Use-Def Chain 和 Def-Use Chain，这一部分可以直接提取出来并且用于生成变量数据节点，然后根据自己的需求做指针分析，生成比如数组访问、move 赋值等的指向边。

如果只是做过程内的数据流分析，一般来说没什么争议，虽然各自的算法可能都会有一点差异，不过大体的结构和目的都是类似的。但是仅此的话完全无法满足我的分析需求，为了不浪费 JEB 提供的便利，我的实现方法是在完成过程内分析的基础上，补全过程间的边。

补全过程间数据流

补全过程间数据流主要需要解决两个问题：

  1. 方法调用时的入参与形参的数据连接问题
  2. 字段访问（load/store）时数据连接问题

这两个问题引出了另外两个分析需求：

  1. 连接参数需要依赖于调用图（Call Graph）分析， 后面将用 CallFlow 来表示函数调用关系。
  2. 实例字段的数据流实现 object-sensitive 需要知道访问的字段属于哪个 Object，所以需要分析 Object 的流向，后面将用 ObjFlow 来表示 Object 的流向。

这两个分析的精度将直接影响过程间数据流的结果。值得一提的是其中 CallFlow 的分析需要依赖于类型推断才能做出准确的分析，而类型推断可以通过 ObjFlow 实现，ObjFlow 却是通过 DataFlow 传播得到的，这是一个 on-the-fly 的分析过程，具体的稍后会进行描述，在这之前，需要先实现数据流传播才能开展后续的工作。

上下文与传播

想要进行准确的过程间数据流传播，就离不开上下文信息。我这里的上下文信息指的是调用点（Call-Site），我将其存储于边上，具体表现为：

  • 在每个调用点的入参节点连接被调用者（Callee）声明的参数节点的数据流边上，存储调用点信息。
  • 在被调用者返回的数据节点连接调用者存储返回数据的节点的边上，存储调用点信息。

然后在传播的时根据上下文信息，建立调用栈，就可以准确的得知应该返回到哪个调用点上去。

private static boolean checkContext(SimpleEdge edge, LinkedList<Object> stack, boolean forward) {
    if (!(edge instanceof ContextDataPointToEdge)) return true;

    Object edgeCtx = resolveEdgeContext(edge);
    if (edgeCtx == null) return true;

    boolean in = ((ContextDataPointToEdge) edge).isIn();
    if (forward == in) {
        stack.add(edgeCtx);
        return true;
    }

    if (stack.isEmpty()) return true;

    if (stack.getLast() == edgeCtx) {
        stack.removeLast();
        return true;
    }
    return false;
}

Object Flows

ObjFlow 的目标就是求解每个 Object 都会被传播到哪些变量上面，当实现了数据流传播了之后，可以很轻易的实现 ObjFlow 的分析。

Allocation-Site

Allocation-Site 指的就是代码里创建对象的地方，对应 Dalvik 里面的 new-instance 或者 new-array 指令。

首先收集所有 Allocation-Site，然后通过数据流分析里的 Defs 信息获取到此指令所产生的数据节点，将他们存放到集合中， 这些就是需要进行传播的 Object。

External Allocation

这里还有个 Case 是对外部的方法进行调用也会产生对象（比如 Message.obtain），如果不把这一部分的对象也进行分析的话就会丢失大量信息。

传播约束

因为数据流传播实际上缺少语义上的条件路径约束，所以会有错误传播的可能性，再加上 Field 分析做得并非那么精确，更是容易由此而引发路径爆炸。

这里我通过收集类型转换（Type Cast）、方法类型声明（参数、返回类型）的信息来确定一个节点的类型原型（Proto），然后根据类型结构（Class Hierarchy）推导类型范围。在传播时，将检查 Object 是否符合节点的类型约束，若不符合将会终止当前路径的传播。

Call Flows

Call Flows 就是调用图，用来表示函数之间的调用关系。调用图的连接方法很简单，但是想要准确的分析连接（调用）的目标（Callee）却是一大难题，在一些论文里经常会以调用边的数量作为指标来衡量不同分析方法之间的差距。

Callee

对于 invoke-static，invoke-direct 这样的直接调用，callee 则直接为指令声明的方法。对于 invoke-super 指令则是根据指令声明的类型向上进行推导，直到找到符合方法签名的方法。

而对于 invoke-virtual，invoke-interface 就需要依赖 ObjFlow 的结果了，从其中获取可以传播到 Call-Site 所使用的实例主体的 Object，并且根据其类型信息，就可以推断出一个相对准确的 Callee 列表。

连接方法

对于 CallFlow 的连接，我一共使用了四条边，对应指令和方法两个层级的两对边，分别是：

  1. Call-Site-Instruction - [Call] -> Callee-Method
  2. Call-Site-Instruction - [InvokeResult] -> Result-Site-Instruction
  3. Caller-Method - [Call] -> Callee-Method
  4. Callee-Method - [InvokeResult] -> Caller-Method

Call 边对应 invoke 指令， 而 InvokeResult 则对应 move-result 指令。指令层面上的边用于数据流的连接与传播，而方法层面上的边构造了一个纯粹的调用图。

On-The-Fly

是不是完成这三个分析就结束了呢？答案是否定的， 因为连接完调用边之后会发现又会有新的数据流产生，而数据流又可能导致新的 ObjFlow 产生，而 ObjFlow 可能导致出现新的调用边，鸡生蛋蛋生鸡生生不息，形成个类似于这样的一个循环：



这是一个良性循环，新的信息不断被产生然后消化，但是新的信息会不断减少，直到为无法产生，也就是到达“不动点”。

所以我编写了一个控制器，让上述三个分析的基本分析完成之后，控制它从 DataFlow 起飞， 到 CallFlow 结束。大致代码如下：

@Override
public void onReady(AnalysisHub hub) {
    timer.start();
    executor.execute(() -> ((DataFlowAnalysis) hub.resolve(DataFlowAnalysis.class)).onFly());
}

@Override
public void onEnd(Analysis from) {
    ...
}

@Override
public void onPass(Analysis from, int result) {
    if (from instanceof DataFlowAnalysis) {
        ObjectAnalysis objFlow = ((ObjectAnalysis) from.getHub().resolve(ObjectAnalysis.class));
        executor.execute(objFlow::onFly);
    } else if (from instanceof ObjectAnalysis) {
        CallAnalysis callFlow = ((CallAnalysis) from.getHub().resolve(CallAnalysis.class));
        executor.execute(callFlow::onFly);
    } else if (from instanceof CallAnalysis) {
        flyIter++;
        if (result > 0 || !isReallyEnd(from.getHub())) {
            DataFlowAnalysis dataFlowAnalysis = ((DataFlowAnalysis) from.getHub().resolve(DataFlowAnalysis.class));
            executor.execute(dataFlowAnalysis::onFly);
        } else {
            timer.stop();
            log.info("[*] on-the-fly end, iter count: " + flyIter + ", " +
                    "time elapsed: " + (float) timer.getTime() / 1000 + "s");
            executor.execute(() -> from.getHub().notifyFlyEnd(from));
        }
    }
}

当 CallFlow 不再产生新边的时候，就是到达了不动点。到达不动点就可以认为分析已经全部完成了，此时已经得到了所有所需要的数据， 即使继续循环也不会有新的信息产生；

Fly Scope

如果每一次迭代都进行全量的传播或分析， 那将大大消耗性能与时间， 所以我给每个分析里都设置了一个 flyScope，比如将每次新增的调用边都添加到 flyScope 里， 那么 DataFlow 就能知道这次需要连接的节点有哪些。

总结

最终数据流分析实现的策略是：上下文敏感（context-sensitive）+ 流敏感（flow-sensitive），不过对于部分 field 的分析是对象敏感（object-sensitive）并且流不敏感（flow-insensitive），目的是为了减少回调信息缺失导致的漏报，这带来了不精确性以及更多的误报以及路径爆炸的可能但却也降低了对控制流分析（调用图）的要求，也算是一种取舍吧。

因为只写了一个大体的工作流程，看起来感觉内容不多，但是只有真正自己开发的时候才能体验到这里面有哪些坑， 如何尽量的避免路径爆炸、内存爆炸，如何有效的利用多线程，如何调度各个分析之间的协作，如何选择高效的策略等等等等，很多都需要经过大量的实验、调教。在开始开发的一个半月后我才逐渐得到一个相对稳定的分析引擎，但实际上它依然很初级，并不具备什么高级的功能，甚至并不完善，光我能直接想到可以改进的地方就有很多，不过整体的框架有了总是可以慢慢优化的。

业界很多人想到 Java 字节码静态分析第一反应是开源的 Soot，但是 Soot 的代码贡献者实在是太多并且太乱了，它存在着大量的 Bug，而大量的祖传代码、复杂的逻辑也让人实在不敢乱动。即使是 ShiftLeft 的商业产品，里面用的也是他们自己维护的另外一个 Soot 分支，脱离了主线将近十年，然后产生了各不相同的 BUG。之前用 Soot 写项目就经常遇到这些莫名其妙的 BUG，给我带来的体验不是很好，对一个开源工程的掌控感还不如逆向使用一个黑盒引擎。而 JEB 的代码更加健壮，只有很少量的分析错误，但只要给够内存从来没有崩溃过，而其他的代码都在自己可控的范围内，可以根据自己的需求来调整以及开发，“自主可控” 确实很爽。
