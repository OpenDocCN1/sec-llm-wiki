先行篇

几个月前我在公众号里介绍了一个基于函数调用图的剪枝工具：“AtomShrink”。在其中我提到了对其效果的不满足以及后续的构想：在 JEB 的基础上配合图数据库（Graph Database）来实现数据流的分析。

经过几个月的努力，我觉得可以跟大家分享一些相关的进度以及成果了。首先，目前这个项目全新的定位是一个静态分析漏洞挖掘框架，我将用大约两篇文章来描述其中的一些实现。

架构

首先简单介绍一下这套框架的架构，主要由三部分组成，后续我将对以下每一个模块的实现分别进行具体描述：

  1. 【AnalysisEngine】 是由 JEB 驱动的 Android/Java 字节码分析引擎，负责对目标进行静态的代码分析，具备代码结构（Hierarchy）、调用图（Call Graph）、数据流图（Data Flow Graph）、类型推断（Type Inference）等分析能力。
  2. 【Database】是基于 Neo4J 的数据与图模型存储抽象层，负责对图结构的数据进行持久化存储以及对象映射，并将分析引擎的结果组合成多层级的代码属性图（Code Property Graph）。通过嵌入式以及多线程优化的形式大量提升了数据存储性能。
  3. 【RuleEngine】是可扩展的规则引擎，在利用 Neo4J 进行数据查询的基础上，重写了与分析引擎配套的路径搜索算法，提供进行污点跟踪的能力以及规则模版。

目前 Java 的总代码量约为一万行（准确来说还差 257 行），这比起一个完备的静态分析工具要完成的代码量（动辄十几万行）要少得多，但是对于自己而言基本能用、够用。

漏洞模型

相比于“漏洞规则”， 我觉得“漏洞模型”这个描述可能更适合那些通过描述约束然后输入到规则引擎来发现风险的模版。

漏洞模型可以由 Java 代码配合 CypherQL 编写，好处是保留了灵活性，利用规则引擎提供的功能，可以完全放开手脚对数据进行分析，只需要最后输出符合定义的结果即可。可以将规则引擎看作为一个 SDK，而模型模块则是规则引擎的一个插件，这个思想借鉴于 SonarQube，可以节省大量去驱动配置文件或者一个 QL 的开发工作，还能满足我的需求并且最大程度的保留灵活性。

漏洞模型这部分我不打算将其纳入到这个框架里面，正如前面所说，它更像是一个插件，我希望以后也许还能开发 rule-web 之类的模块（毕竟完全适用于分析 Log4Shell 这样的漏洞）。当然，在必要时不会吝啬于拿某些模型出来举例以便读者更好的理解。

成果

通过此框架，我提交了将近 20 个有关 Android 系统以及应用程序的漏洞报告， 其中包括谷歌、微软、亚马逊、小米、美团等大厂。这几个月都没有更新内容，因为每天的主要工作基本都是一样的：写/修 Bug -> 扫漏洞 -> 审代码 -> 写利用/报告 -> 等审（撞）洞。
