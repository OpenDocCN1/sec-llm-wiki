### frida-elfdump

迫于各种各样加固过的 ELF 文件难以静态脱壳、分析，并且继续贯彻 frida-dexdump 啥都能在内存里捞的思想，写了这个小工具希望可以用来通用的对付各种 ELF 壳。

本来是想做成脱壳机的（内存转储+文件修复），但通过以往对 SoFixer 的了解以及亲测，认为做文件修复的局限性还是比较大，并且发现一个比较神奇的问题一直没有破案：在 ELF 文件的 Dynamic Segment 中存储了例如 .init 或 .init\_array 列表中的函数偏移，当被 Linker 链接之后其位置会重定向至指向真实函数地址的 VirtualAddress，这看起来像是会在解析 dynamic 或者链接 GOT 表的流程中处理，但翻了半天源码也没有找到从 mmap 到 call\_array 之间有哪段代码在处理这个逻辑。

其实我觉得下个内存断点就能解决，但是迫于懒得写 demo 以及弄调试器环境并且也不看好这个路子，我决定等个热心观众直接把代码路径甩我脸上，谢谢姥爷们。

最后选择了跟以往脱壳机不一样的形式，做成了"内存转储 + 运行时信息收集 + Ghidra 脚本导入"，用到了三个框架分为三个步骤：

1.  使用 Frida 从内存里把目标模块的 range 都 dump 下来，并且收集运行时的模块列表(名称，基址)、符号列表(名称，地址)以及堆。
    
2.  使用 LIEF 来修复内存 ELF，不同于 SoFixer ，这里的修复并非是补充 Section 或其他文件信息，而是把 Section 信息全部抹掉，理由是真正的 Linker 可以完全不需要 Section 信息，而大部分现代的逆向分析工具的 Loader 也都遵循此规矩，错误的信息反而会误导它们的分析过程。
    
3.  通过 Ghidra Script 进行 Rebase 并且导入 Frida 收集的运行时信息，此时所有地址正确，所有符号正常，可以愉快的进行逆向了。对了，墙裂推荐 Ghidra ，你们看我现在连配套的 IDA 脚本都不写了，你懂的。
    

测试了几个样本没啥问题，最后的最后发条 Twitter 装逼，靠着 quarkslab 大哥的转发骗了几十个粉丝，愉快的把代码收进本地 gitlab，关机下班，底薪飞走。

### JEB Headless Analysis Client

这个项目没有想名字，主要的作用是使用 JEB 的功能做一些分析并且把数据都导出来，方便数据持久化使用。

主要是代码太菜了 + 内存不够用，所以重构了很多代码，包括整体架构以及下面的具体分析，自己整了个 Java Hierarchy Analysis 并且优化了好久，因为后面 CHACallGraph 的效率特别依赖于这个分析。

虽然内存还是不够用(主要是 JEB 吃太多了)，不过现在至少不会 out of memory，就是跑的慢。给 16g 让 JEB Decompiler 跑 100m 的 dex 得跑半个小时，然后带着这释放不掉的 16g 跑 CHACallGraph 又得跑半个小时...但是单独跑 CHACallGraph 只需要三分钟，就离谱。要实在释放不了 JEB 的内存就还是拆出来跑吧，反正数据持久化之后也不需要 JEB 的 Context 了。

吐肚：把数据应用起来，CheckMarx 还等着我自己减枝呢。

### frida-dexdump-pro

配合自己以前写的群控 + TaskBus 框架，给 frida-dexdump-pro 做了一个 SaaS 版本，不过目前看起来好像没有什么卵用，因为拿 Frida 来全量抽 CodeItem 效率确实不高，即使加了一个自动识别抽取方法的过滤器，但是基本上抽取壳都是全抽了，过滤的意义也不大。得亏最后掏了一个 OnePlus 6T 上架，性能才勉强能用，但是脱个一两百兆的估计还是得两三个小时。

### 程序分析

之前一直想自己写程序分析引擎，经过不懈的努力推翻代码之后，我决定还是先玩好工业界现成的吧。

首先排除掉众多使用成本比较高的日常混论文的开源框架们，然后再看看手里有哪些能嫖商业工具，最终选择了 CxSAST。毕竟 Fortify 的规则引擎搓得一批，还扫不出来，而相比于免费的 CodeQL，我还是选择相信三大之一。

Cx 的规则引擎叫 CxQL，看起来本质上应该是 C#，然后提供了查询 Cx 分析结果的 API 和数据类型。Cx 基于源码分析，提供了包括词法 Token，符号，表达式，语句，控制流，数据流等丰富的数据以及接口，还是很好用的，就是资料比较少。官方提供的 Guide 基本上就是一本 API References，不过看明白几个基本概念之后还是比较好懂的，可以参考 https://habr.com/ru/company/dins/blog/477742/。

试了很多静态分析工具，基本上对于几百兆的 Java 都没有一战之力，不是内存爆炸就是扫描无果，所以还是得先靠自己减一遍枝，给代码瘦瘦身，然后再丢进去扫描，所以才有了上面 JEB 的用武之地。

吐肚：用 CxQL 把几个常用的 Android 风险规则写好。
