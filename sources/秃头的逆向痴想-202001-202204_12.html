漏洞

最近半年时间关注了不少 Android 应用层的漏洞报告，自己也动手挖了几个有些危害的漏洞。看了许多漏洞报告，虽然随着移动互联网的发展出现了许多新的攻击方法以及利用方式 ，但攻击面在本质上并没有发生太大的变化，被利用最广泛的无非还是 "组件" 以及 "浏览器"。

漏洞都是人产生的，但开发者通宵达旦写下一行行代码的时候可能并不会意识到在某个地方已经埋下了漏洞，并且有时并非是开发者缺乏安全意识， 而是有些利用方式在公开之前根本想不到一个小小的误用会产生不可预料的后果。

风险发现

虽然发现攻击面或者发明利用方式很难，但站在巨人的肩膀上捡漏洞却轻而易举。绝大部分的风险都可以通过一定的特征规律被发现， 比如 WebView 各种不安全的配置， 比如使用外部输入调用敏感函数， 发现的这些问题都可以称之为风险。

通过特征规律发现风险之后，再进一步研究如何进行利用、构造利用链，有了危害它就成了漏洞。

程序分析

我一直相信，静态程序分析是自动化发现风险的绝佳帮手，绝大部分的漏洞特征规律，都可以通过静态程序分析被发现，在这些绝大部分被发现得差不多了之后，才轮到 Fuzzing 这种更具有探索性的技术来发现更多隐蔽的风险。

应用

除了发现风险之外，程序分析对于漏洞挖掘中的另一个至关重要的环节 —— “信息收集”，也具有重大的意义，光是提取字符串信息这一项，通常都能得到极高性价比的结果。

对于 S-SDLC 来说，制定安全的编码规范起到人治的预防作用， 而程序分析则可以成为安全质量的控制阀，在业务上线前及时发现风险代码，弥补人治的不足， 这也是许多安全方案中会将 SAST 接入到 CI/CD 中的原因。

程序分析的技术早已深入应用在各个信息安全的场景当中，最广为流传即污点分析技术。但我想也许可以从另外一个角度—— 剪枝，聊聊如何将程序分析应用在风险发现或逆向分析的工作当中。

剪枝

最近在学习养花，也不知道为什么我才二十来岁就开始慢慢着迷于各种适合养老的事情。在园艺工作中，给植物剪枝是为了控制枝叶生长的方向，同时也能减少无关的养分消耗，给主枝干提供更好的生存环境，得到更好的生长，而剪枝对于程序分析风险的意义亦是如此， 明确通向目标的路径，一步步的排除无关因素，一步步的逼近结果，最终，得到结果。

Phase-1 Code

上面说过，程序分析发现风险是通过一定的特征规律，而一个项目中大部分的代码都是与风险向量是无关的，为了避免在这些无关代码上浪费过多的“养分”， 我们应该将他们都“剪掉”，也就是平时所说的“按需分析”，那么，如何剪？

Phase-1.1 Call Graph

Call Graph 是过程间分析最为重要的一个基础分析，通过构建 Call Graph， 我们可以得到一个所有 Method 之间依赖关系的有向图。构建原始 Call Graph 的方法很简单， 只需要遍历所有 Call-Site（ 除了 Invoke 之外还需要包含 New-Instance 指令）， 将 Caller 和 Callee 作为节点连接起来， 我们可以将这个边定义为 Original-Call-Edge。

@Override
public void onCallSite(IJavaMethod caller, IJavaCall callsite) {
  IJavaMethod callee = callsite.getMethod();
  MethodDescriptor callerDescriptor = getMethodDescriptorFromJavaMethod(caller);
  MethodDescriptor calleeDescriptor = getMethodDescriptorFromJavaMethod(callee);
  onCall(resolveCallType(callsite), callerDescriptor, calleeDescriptor);
}

@Override
public void onStatement(IJavaMethod caller, IStatement statement) {
  if (!(statement instanceof IJavaNew)) {
    return;
  }
  MethodDescriptor callerDescriptor = getMethodDescriptorFromJavaMethod(caller);
  MethodDescriptor calleeDescriptor = getMethodDescriptorFromJavaMethod(((IJavaNew) statement).getConstructor());
  onCall(JavaCall.CALL_VIRTUAL, callerDescriptor, calleeDescriptor);
}

public void onCall(int callType, MethodDescriptor caller, MethodDescriptor callee) {
  calls.add(new JavaCall(
    callType,
    caller,
    callee
  ));
}

当然， 这个 Call Graph 是相当不靠谱的，因为 Invoke 指令除了 invoke-static、invoke-direct 之外都需要经过 Dispatch 才能到达真正的 Target Method。而想要得到一个完备的 Call Graph， 通常都需要经过完整的过程间指针分析来 on-the-fly 获得， 但我不想把这个事情放在这里做。

获得 Target Method 还有另一个方法： CHA(Class Hierarchy Analysis)。

Phase-1.3 Dependency Graph

首先我们要构造代码依赖图，还需要分析另外一个重要的信息——字段的访问情况，这个可以在 Phase 1.1 全程序遍历指令的时候顺带完成：

public void onStatement(IJavaMethod method, IStatement statement) {
  if (statement instanceof IJavaAssignment) {
    IJavaExpression left = ((IJavaAssignment) statement).getLeft();
    IJavaExpression right = ((IJavaAssignment) statement).getRight();
    onWriting(method, left);
    onReading(method, right);
  } else if (statement instanceof IJavaCall) {
    ((IJavaCall) statement).getArguments().forEach(argument -> onReading(method, argument));
  } else if (statement instanceof IJavaNew) {
    ((IJavaNew) statement).getArguments().forEach(argument -> onReading(method, argument));
  }
}

private void onReading(IJavaMethod method, IJavaElement element) {
  onAccess(method, element, JavaFieldRef.REF_READ);
}

private void onWriting(IJavaMethod method, IJavaElement element) {
  onAccess(method, element, JavaFieldRef.REF_WRITE);
}

private void onAccess(IJavaMethod method, IJavaElement element, int type) {
  if (!isFieldAccess(element)) {
    return;
  }

  FieldDescriptor fieldDesc = expr2Desc(element);
  if (fieldDesc == null) {
    return;
  }

  refs.add(new JavaFieldRef(type,
                            Utils.getMethodDescriptorFromJavaMethod(method),
                            expr2Desc(element)));
}

private boolean isFieldAccess(IJavaElement element) {
  return element instanceof IJavaInstanceField || element instanceof IJavaStaticField;
}

Phase-1.4 Cutting

经过一轮的 Whole Program Analysis， 我们最终得到了两个依赖图可以用来找到一个 Method 依赖的所有代码以及路径。虽然可能有些脱裤子放屁的嫌疑，但可以更好的一步步渐进剪枝。

按照其他按需分析的做法， 此时的剪枝应该是从定义 Entry 开始， 但这种做法对于风险发现来说其实并不友好，因为有时构造利用链并不是从常规的入口开始，或者分析不准确会导致信息缺失。我认为应该像寻找 Gadget 一样，找到可以利用的地方，然后再去想办法调用它。所以我要从所有可以到达攻击向量的地方开始，暂时使用污点分析中的 source 来具象化这个向量。

假设 source 是 getIntent，那么获取 Entry 的方法大概如下：

wl = set(getIntent, )
entries = set()
record = set()
while wl:
  node = wl.pop()
  
  if node in record: continue
  else: record.add(node)
    
  preds = MMDG.PredOf(node)
  if not preds: entries.add(node)
  else:
    for pred in preds:
      wl.add(pred)

然后根据 Entry 再向后传播， 将以 Entry 为首的整棵树都视为我们所需要的代码：

dependencies = set()

def func(node):
  if node in dependencies:
    return
  
  dependencies.add(node)
  for succ in MMDG.SuccsOf(node):
    func(node)

for entry in entries:
  func(entry)

最后查询 MCDG， 得到第一次剪枝完成的所有类：

PhaseFirstClasses = MCDG(dependencies)

最后的最后可以将查询到的这些 class 重新打包为 jar 或 dex， 然后继续分析，也方便用于其他分析工具。

Phase-2 Path

上面我们使用代码依赖图以及由 source 决定的 Entry 对程序代码进行了第一阶段的剪枝， 然后就需要用到 sink 了，我们根据 Entry 以及 sink 可以为代码路径进行剪枝， 为后面的数据流分析减少压力。

Phase-2.1 CHA Call Graph

上一阶段里我们虽然做了 CHA，但没有与 Call Graph 做合并， 在这一阶段里，我们需要将 CHA 的信息在 Call Graph 中连接起来， 可以将通过 CHA.Resolve 连接的边定义为 CHA-Resolve-Call-Edge， 然后在这个图里面做可达性分析。

Phase-2.2 Reachability

从 Entry 开始向前遍历， 遇到 source、 sink 都不可到达的节点则把边剪掉，直到遍历结束，伪代码如下：

wl = set(entry, )
record = set()
while wl:
  node = wl.pop()
  
  if node in record: continue
  else: record.add(node)
    
  if not cg.reachable(node, sink) and not cg.reachable(node, source):
    cg.cleanNode(node)
  else:
    wl |= cg.succsOf(node)

现在是早上六点， 不是很想写了，简单概括一下。

Phase-3.1 Inter-procedural Control Flow Graph

首先构建一下 ICFG， 就是给每个 Method 都画好 CFG 然后加上 Call Graph 的 Call-Edge 以及 Call-To-Return-Edge。

Phase-3.2 PointTo Analysis

因为剪枝工作基本已经接近尾声， 所以这里打算尝试一下 Flow-Sensitive + Context-Sensitive 的指针分析，应该是最精确的， 做完指针分析会产生精确的 Call Graph， 然后与 Phase-2 Call Graph 取交集，得到 PointTo-Based Call Graph，并且重新生成或裁剪 ICFG。

Phase-3.3 Data Flow Tracking

根据 PointTo Analysis 我们就可以对 source 进行跟踪， 从数据流图上看他是否会流向 sink， 保留数据流可达的路径， 就检出了风险。

人
