## 前言  

某日运营小哥找到产品吐槽导入excel后没反应，经过询问数据量大概在900条左右的数据，数据量不多，于是打算优化一下，于是开始了一场惊心动魄之旅......  

## 排查过程

使用阿里开源工具 Arthas(https://arthas.aliyun.com/doc/)  trace 命令查看接口耗时，trace命令格式如下：

![](../Images/207965c8b0dd116c9c1d0e081baed6bc.png)

  

监控单个方法耗时

*   

```
`trace com.**.**.controller.xxxController importXXX`
```

  

监控多个方法耗时

*   

```
`trace -E com.**.xxxController|com.**.xxxController XXX1|XXX2`
```

![](../Images/0bad23c8e8944a7e7e212af86f3c49cb.png)

  

上图为trace耗时结果，从图中可以清楚的看到controller中哪一行耗时多少，其中耗时最多的为XXXService 的第249行，saveImportExcelList()方法，继续追踪这个方法

*   

```
`trace -E com.**.xxxController|com.**.xxxService importExcel|saveImportExcelList`
```

  

![](../Images/dc918393dac8a06db81b9a90b52ce95f.png)

  

1.  由于项目使用apache的poi导入获取Excel获取数据，所以首先查看了一下导入获取数据的时间，平均在1-2秒内能读取3000+数据，而平时导入数据一般在1000+以内，所以忽略优化此处。
2.  查看代码时发现目前导入数据以后，使用循环逐条去判断数据格式、查询商品是否存在、商品配送时间是否匹配以及调用三方接口查询，最终查到Service中520行的checkData()方法耗时最严重，导入1232条数据，最小耗时2ms，最大耗时96ms，总耗时 60091ms。

  

既然找到了耗时严重的代码，那就好办了，接下来就优化吧，使用多线程去批量校验数据，能用批量的用批量，批量查询，然后放在内存中去做对比校验。

可以使用frok...join框架去分割成多份小任务去执行，线程池，CountDownLatch等，这里优化时选择了CountDownLatch，等计数器为0时，代表所有线程执行完毕，由于在创建CountDownLatch时疏忽大意，埋下了隐患。

  

优化完代码之后，放测试测了几遍，从原来的90S，到优化后的12S，其实还有很多可以优化的地方，时间紧迫，优化力度还可以，就发生产了，在坐等收获好评的时候，悲催的事情就来了......

```
// 业务代码 CountDownLatch cdLatch = new CountDownLatch(MAX_THRESHOLD);// 业务代码// 业务代码if(xxx == xxx){ // 代码1   // 执行计数器递减代码}try{   // 代码2   cdLatch.await(40,TimeUnit.SECONDS);}catch(){   throw new Exception();}
```

        在代码1之前new了CountDownLatch，如果代码1处的判断为false，那么就不会去执行计数器递减代码，那么就会导致线程一直处于等待状态，一直等到代码2处设置的超时时间为止，也幸亏这里设置了超时时间，要不然可能会导致线程池中大批量线程全部夯在这里。

        上线后，特意让运营小哥试了试，耗时均在\`15S\`以内，监控后台也没有任何问题，在上线后第三天，另外一个运营小姐姐说导入没反应，于是登录服务器查看该接口调用日志，发现接口返回正常，但耗时有大于\`45S\`以上，且\`45S\`以上的均为同一个活动导入商品，查看代码发现线程设置超时时间为\`40S\`，怀疑是此处问题，然后把数据放到测试环境进行测试，同时用Arthas查看耗时和堆栈信息，最终定位到没有执行\`代码1\`处的计数器递减代码，于是修改代码逻辑与 CountDownLatch 的创建位置，最终问题完美解决！

  

## 最后总结

*   系统中有比较耗时的接口，而又不知道具体哪块代码耗时，可以使用Arthas工具去trace接口，追踪真正耗时的代码块，进行优化。
    
*   大批量数据进行相同业务逻辑处理时，尽可能用批量进行处理，而不是使用循环进行单个处理，减少对数据库或者Redis的过多依赖。
    
*   使用多线程时，尽量复用项目中线程池，减少不必要的线程创建，也避免线程数过多时，CPU上下文的切换时间。
    
*   使用CountDownLatch的时候，加多少把锁，最终就要释放多少把锁，释放锁的操作最好放在finally代码块中。
    
*   如果子线程涉及到HTTP或者RPC调用时候，强烈建议设置超时时间，防止线程夯死。
