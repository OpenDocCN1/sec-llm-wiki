## 以前的工作和历史背景

  
HiSilicon在其设备上实施后门访问方面拥有很长的记录。  
  
它的最早已知版本启用了具有静态root密码的telnet访问，可以使用（相对）较少的计算工作从固件映像中恢复该密码。2013年，以前的作者文章（俄语）涵盖了此漏洞。2017年，Istvan Toth 对HiSilicon固件进行了最全面的分析。他还发现了内置Web服务器中的远程执行代码漏洞以及许多其他漏洞。值得注意的是，供应商忽略了披露。  
  
默认情况下，较新的固件版本禁用了telnet访问和调试端口（9527 / tcp）。相反，他们有开放的端口9530 / tcp，该端口用于接受特殊命令来启动telnet守护程序，并使用静态密码启用对所有设备相同的shell访问。这些条款涵盖了以下情况：  
  

*   https://www.cnblogs.com/mmseh/p/6537924.html，2017（中文）
    
*   https://habr.com/ru/post/332526/，2017（俄语，Habr用户CentALT）
    

  
最新的固件版本具有开放的端口9530 / tcp，用于侦听特殊命令，但是需要进行密码质询-响应身份验证才能提交。这是实际公开的主题。  
  
显然，多年来，HiSilicon不愿或无法为同一个后门提供足够的安全修复程序，而这是有意实施的。  
  

## 技术细节

  
讨论中的易受攻击的DVR / NVR / IP摄像机设备正在Linux上运行，其中busybox，主要视频应用程序`Sofia`和少量负责支持设备操作的自定义辅助实用程序提供的实用程序最少。硬件具有基于ARM的CPU，数十到数百兆字节的RAM。  
  
设备与脆弱的固件有`macGuarder`或`dvrHelper`运行过程和TCP端口9530上接受连接代码和日志字符串显示，`macGuarder`以前是一个独立的进程，但后来它的功能合并到`dvrHelper`过程作为一个单独的线程。  
  
值得注意的是，较早版本的固件已将dvrHelper进程作为附加的applet编译到busybox中。考虑到busybox具有GNU GPL许可证，可能会发生许可证冲突，因为dvrHelper软件是在没有源代码的情况下分发的。  
  
成功的后门激活过程如下：  
  

1.  客户端打开与设备的端口TCP端口9530的连接，并发送`OpenTelnet:OpenOnce`带前缀字节的字符串，该字符串指示总消息长度。此步骤是后门以前版本的最后一步。如果此步骤之后没有响应，则可能是telnetd已启动。
    
2.  服务器（设备）用字符串表示`randNum:XXXXXXXX`，其中`XXXXXXXX`为8位随机十进制数。
    
3.  客户端使用它的预共享密钥，并构造加密密钥作为接收到的随机数和PSK的串联。
    
4.  客户端使用加密密钥对随机数进行加密，并在string之后发送`randNum:`。整个消息前面都带有指示消息总长度的字节。
    
5.  服务器从文件加载相同的预共享密钥，`/mnt/custom/TelnetOEMPasswd`或者`2wj9fsa2`如果缺少文件，则使用默认密钥。
    
6.  服务器对随机数进行加密，并验证结果是否与客户端的字符串相同。在成功服务器上发送字符串`verify:OK`或`verify:ERROR`其他。
    
7.  客户端对字符串进行加密`Telnet:OpenOnce`，并以总长度的字节，`CMD:`字符串作为前缀，然后发送给服务器。
    
8.  服务器提取并解密收到的命令。如果解密结果等于字符串，`Telnet:OpenOnce`它将以响应`Open:OK`，启用调试端口9527并启动telnet守护程序。
    

  
整个身份验证过程可能类似于某种HMAC质询-响应身份验证，只是它使用对称密码而不是哈希。对于长于8个字节的密钥，此特定的对称密码类似于3DES-EDE2的某些变体，对于较短的密钥，它类似于简单的DES。  
  
很容易看出，成功进行身份验证所需的所有客户端都是PSK的知识（这是常见的，可以从明文从固件中检索到）以及该对称块密码的实现。恢复对称密码实现是最困难的，但这是在本研究中实现的。使用以下工具进行了探索和测试：  
  

*   来自NSA的Ghidra 9.1.1（https://ghidra-sre.org/）—用于二进制可执行代码检查的套件。
    
*   QEMU（更确切地说是Debian chroot中的qemu-user- https://www.qemu.org/）-一种允许在主机上透明地执行外部体系结构二进制文件（ARM）的软件。
    
*   通用的GNU实用程序和工具链。
    

  
telnet守护程序激活后，很可能会接受以下登录名/密码对之一：  

| 登录 || 密码 |
| --- | --- |
| `root` || `xmhdipc` |
| `root` || `klv123` |
| `root` || `xc3511` |
| `root` || `123456` |
| `root` || `jvbzd` |
| `root` || `hi3518` |

  
这些密码也可以通过`/etc/passwd`文件中哈希的暴力破解从固件中恢复。带有hashcat的现代消费级GPGPU 能够在几小时内找到用于哈希的原映像。  
  
调试端口9527接受与Web UI相同的登录名/密码，并且还提供了一些Shell访问和功能来控制设备。说到Web UI帐户，攻击者可能会重置密码或从`/mnt/mtd/Config/Account*`文件中获取密码哈希。哈希函数在 Istvan Toth的先前研究中已有描述。  
  

## 受影响的设备

  
先前的研究收集了许多受影响的品牌：https : //github.com/tothi/pwn-hisilicon-dvr#summary。有数十个品牌和数百种型号。  
  
该报告的作者以对随机IP地址进行的调查为基础，估计通过Internet暴露的易受攻击设备的总数在数十万到数百万之间。  
  
可能，检查设备是否易受攻击的最简单方法是下面提供的PoC代码。  
  

## 测试漏洞

  
PoC代码：https : //github.com/Snawoot/hisilicon-dvr-telnet。  
  
从源代码构建PoC程序：`make`在源代码目录中运行。  
  
用法：`./hs-dvr-telnet HOST PSK`  
  
最常见的PSK是默认值之一：`2wj9fsa2`。  
  
会话示例：  
  

```
$ telnet 198.51.100.23

```

  
  
上面示例中的IP地址是地址块中的IP地址，保留给RFC5737进行文档记录。  
  
在以下情况下，应将设备视为易受攻击的设备：  
  

*   Telnet端口在`hs-dvr-telnet`运行后打开。
    
*   设备在`hs-dvr-telnet`询问时回应挑战。即使由于错误的PSK验证失败，也可以从固件中提取正确的PSK。
    
*   hs-dvr-telnet卡在等待响应，但是telnet端口打开（这对于仅需要`OpenTelnet:OpenOnce`命令的较旧固件版本会发生）。
    

  

## 减轻

  
考虑到该漏洞（实际上是后门）的较早的虚假修补程序，期望供应商提供的固件安全修补程序不切实际。这种设备的所有者应考虑改用其他设备。  
  
但是，如果无法更换，则设备所有者应将访问这些设备的网络访问权限完全限制为受信任的用户。此漏洞涉及的端口是23 / tcp，9530 / tcp，9527 / tcp，但是早期的研究表明，没有其他服务实现的可靠性，也不包含RCE漏洞。  
  

## 本研究未涵盖的主题

  
代码分析表明，端口9530上的身份验证过程将任意大小（最大为一次从套接字读取的缓冲区大小）的“ CMD”有效载荷解密为固定大小为32字节的堆栈缓冲区。有针对性地利用此溢出需要PSK方面的知识，因此按常规方法进行访问更为实用。另一方面，使用CMD命令发送的垃圾可能导致堆栈损坏和dvrHelper守护程序失败。由于存在MacGuarder / dvrHelper后门功能严格来说是优越且直接的方法，因此未探讨这种（潜在）故障的可能影响。  
  
更新（2020-02-05 02：10 + 00：00）：先前对此主题研究的作者Istvan Toth 介绍了自己的PoC程序实现：https://github.com/tothi/hs-dvr-telnet给定的实现是用纯Python代码编写的，并且以更清晰的方式实现了对称密码。它还概述了HiSilicon用于后门身份验证的3DES密码变体与原始3DES密码之间的区别。这些差异可以通过以下git commit来表达：https : //github.com/tothi/pyDes/commit/7a26fe09dc5b57b175c6439fbbf496414598a7a2。
