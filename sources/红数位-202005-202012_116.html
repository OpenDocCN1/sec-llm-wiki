在参与过程中，我们发现其基础结构核心部分存在各种漏洞，这些漏洞可能使攻击者完全破坏客户和员工的应用程序，启动能够自动接管受害者的iCloud帐户的蠕虫，并检索内部的源代码。Apple计划充分利用Apple使用的工业控制仓库软件，并接管具有访问管理工具和敏感资源能力的Apple员工会议。

总共发现了55个漏洞，其中11个严重严重性，29个高严重性，13个中严重性和2个低严重性漏洞。我们出于汇总目的评估了这些严重性，并且取决于CVSS和我们对与业务相关的影响的理解。

截至2020年10月6日，这些发现中的绝大多数已得到修复并得到认可。通常会在1-2个工作日内对它们进行补救（有些问题会在4-6个小时之内修复）。

介绍

当我在7月左右某个时间滚动浏览Twitter时，我注意到有一篇博客文章被分享，一位研究人员因发现身份验证绕行而获得苹果公司10万美元的奖励，该绕行使得他们可以随意访问任何Apple客户帐户。这让我感到惊讶，因为我以前了解到，Apple的漏洞赏金计划仅授予影响其物理产品的安全漏洞，而没有为影响其Web资产的问题付款。

读完这篇文章后，我进行了一次Google快速搜索，找到了他们的程序页面，其中详细说明了Apple愿意为“对用户有重大影响”的漏洞支付费用，而不管资产是否明确列出。

这引起了我的注意，因为这是一个有趣的机会，可以研究一个似乎范围广泛且有趣的新程序。当时我从未从事过Apple Bug赏金计划，因此我真的不知道该期待什么，但决定为什么不试试运气，看看能找到什么。

为了使该项目更有趣，我向过去与之合作过的黑客发送了一些消息，并询问他们是否愿意在该程序上共同努力。即使不能保证支出，也不能保证程序的工作原理，但每个人都说是的，我们开始在Apple上进行黑客攻击。

侦察

入侵Apple的第一步是弄清楚实际目标是什么。Ben和Tanner都是这里的专家，所以他们开始弄清楚我们可以访问的所有Apple拥有的东西。他们扫描的所有结果都在一个仪表板中建立了索引，该仪表板包括HTTP状态代码，标头，响应正文以及Apple拥有的各个域下可访问的Web服务器的屏幕快照，我们将在参与过程中参考这些屏幕。


简而言之：苹果的基础设施规模巨大。

他们拥有整个17.0.0.0/8 IP范围，其中包括25,000个Web服务器，其中apple.com下拥有10,000个Web服务器，另外7,000个唯一域，最重要的是拥有自己的TLD（点苹果）。我们的时间主要花费在17.0.0.0/8 IP范围，.apple.com和.icloud.com上，因为那是有趣的功能所在。

在列出所有Web服务器的清单之后，我们开始在更有趣的服务器上运行目录暴力破解。

自动扫描的一些直接发现是...

  • 受Cisco CVE-2020-3452本地文件读取1天（x22）影响的VPN服务器

  • 破碎页面上的错误消息中泄漏的Spotify访问令牌

这些过程获得的信息有助于理解授权/身份验证在整个Apple中的工作方式，存在的客户/员工应用程序，使用的集成/开发工具以及各种可观察到的行为，例如使用某些Cookie或重定向到某些应用程序的Web服务器。

在完成所有扫描之后，我们认为我们对Apple基础架构有了一个总体了解，我们开始针对单个Web服务器，这些Web服务器本能地比其他服务器更容易受到攻击。

这开始了一系列发现，这些发现在我们的整个参与过程中一直持续，并逐渐增加了我们对Apple计划的了解。

通过身份验证和授权绕过Apple杰出教育者计划的全面妥协

我们花费大量时间进行黑客入侵的第一批服务之一是“苹果杰出教育者”网站。这是一个仅限邀请的Jive论坛，用户可以在其中使用其Apple帐户进行身份验证。这个论坛的有趣之处在于，一些注册到该应用程序的Jive核心功能是通过Apple构建的自定义中间件页面移植的，目的是将其身份验证系统（IDMSA）连接到通常使用用户名/密码身份验证的底层Jive论坛。。


这样做的目的是使用户可以轻松地使用其现有的Apple帐户向论坛进行身份验证，而不必处理创建其他用户帐户的问题。您只需使用“使用Apple登录”并登录到论坛即可。

不允许访问论坛的用户的登录页面是一个应用程序门户，您在其中提供了有关您自己的信息，该信息由论坛版主评估为批准。


当您提交使用该论坛的应用程序时，您几乎提供了帐户的所有值，就好像您是正常注册到Jive论坛一样。这将使Jive论坛根据IDMSA cookie知道您是谁，因为它将您属于Apple帐户的电子邮件地址绑定到了该论坛。

在应用程序内要注册使用该论坛的页面上隐藏的值之一是“ password”字段，其值为“ ### INvALID＃％！3 ”。当您提交包含用户名，名字和姓氏，电子邮件地址和雇主的应用程序时，您还提交了一个“密码”值，该值然后秘密地绑定到来自页面上隐藏输入字段的帐户。

观察到隐藏的默认密码字段后，我们立即想到了一种方法，可以手动验证应用程序的身份并访问论坛的批准帐户，而不必尝试使用“使用Apple登录”系统登录。我们对此进行了调查，因为我们每个人在单独注册时的密码都相同。

如果有人使用此系统提出申请，并且存在可以手动进行身份验证的功能，则只需使用默认密码登录到他们的帐户，然后完全绕过“使用Apple登录”登录即可。

乍一看，您似乎似乎无法手动进行身份验证，但是经过几次Google搜索后，我们发现了一个“ cs_login”端点，该端点用于使用用户名和密码登录Jive应用程序。当我们手动形成测试HTTP请求以对Apple Distinguished Developers应用程序进行身份验证时，我们发现它尝试通过显示错误的密码错误来对我们进行身份验证。当我们使用以前使用的自己的帐户时，该应用程序出现错误，并且由于我们尚未获得批准，因此不允许我们进行身份验证。如果要进行身份验证，我们将必须找到已批准成员的用户名。

在这一点上，我们将HTTP请求加载到Burp Suite的入侵者中，并尝试通过登录名和默认密码强行使用1到3个字符的用户名。

大约两分钟后，我们收到302响应，指示使用默认密码成功登录了用户名“ erb”。我们进去了！从这一点出发，我们的下一个目标是对具有提升权限的人员进行身份验证。我们截取了一些访问权限的屏幕快照，然后单击“用户”列表以查看哪些用户是管理员。我们登录到列表中看到的第一个帐户，以试图证明我们可以通过管理功能实现远程代码执行，但是，仍然存在一些障碍。

尝试以admin帐户浏览到“ / admin /”（Jive管理员控制台）时，该应用程序将重定向为登录，就好像我们尚未通过身份验证一样。这很奇怪，因为它是Jive应用程序的自定义行为，而且我们之前都没有人观察到这一点。我们的猜测是，Apple限制了基于IP地址的管理控制台，以确保永远不会完全破坏该应用程序。

我们尝试的第一件事之一是使用X-Forwarded-For标头绕过假设的限制，但不幸的是，此操作失败了。我们接下来尝试做的是加载另一种形式的“ / admin /”，以防应用程序具有访问管理员控制台的特定于路径的黑名单。

在再执行几个HTTP请求后，我们发现“ GET / admin; /”将使攻击者可以访问管理控制台。我们通过设置Burp Suite规则自动执行此绕过操作，该规则在HTTP请求中将“ GET / POST / admin /”自动更改为“ GET / POST / admin; /”。

当我们最终导航并加载了管理控制台时，立即很清楚，有些事情是不对的。我们无法使用演示远程代码执行的常规功能（没有模板，插件上传或标准的管理调试功能）。

在这一点上，我们停止考虑我们在哪里，并意识到我们通过身份验证的帐户可能不是应用程序的“核心”管理员。我们继续进行并通过了2-3个帐户的身份验证，然后最终以核心管理员身份进行身份验证，并看到了可以远程执行代码的功能。

攻击者可能（1）使用隐藏的默认登录功能通过手动身份验证来绕过身份验证，然后（2）通过在请求中发送修改后的HTTP路径来访问管理控制台，最后（3）使用一个完全破坏应用程序许多“嵌入RCE”功能中，例如插件上传，模板化或文件管理。

总体而言，这将使攻击者能够...

  • 在ade.apple.com网站服务器上执行任意命令

  • 访问内部LDAP服务以管理用户帐户

  • 访问苹果大部分内部网络

至此，我们完成了报告并提交了所有内容。

通过身份验证旁路完全破坏了DELMIA Apriso应用程序

在黑客入侵苹果公司时，我们曾想过很多事情，即他们是否拥有与产品制造和分销有关的任何可访问服务。事实证明，有一个名为“ DELMIA Apriso”的应用程序，它是第三方“ Global Manufacturing Suite”，提供了各种仓库解决方案。

遗憾的是，该技术似乎没有太多可用的交互方式，因为您只能从可用界面中“登录”和“重置密码”。

尝试在有限数量的页面上发现漏洞后，发生了一件奇怪的事情：我们通过一个名为“ Apple No Password User”的用户身份验证，该用户基于网站右上方的栏。

发生的事情是，通过单击“重置密码”，我们被临时认证为具有“权限”才能使用该页面的用户。

该应用程序的身份验证模型有效，而用户具有使用特定页面的特定权限。“重置密码”页面本身就是页面，因此，为了让我们使用它，应用程序自动将我们登录到能够使用该页面的帐户中。

为了提高权限，我们尝试了各种方法，但很长时间以来似乎都没有取得成功。一段时间后，我们向OAuth端点发送了HTTP请求，以尝试生成可用于探索API的授权载体。成功了！

即使我们的用户帐户的权限仅限于授权和重置密码，也可能会生成一个承载，该承载有权访问应用程序的API版本。

现在，我们能够探索API，并希望找到一些权限问题，这将使我们能够损害应用程序的某些部分。幸运的是，在我们的侦查过程中，我们找到了该应用程序的API请求列表。

遗憾的是，我们没有访问大多数API调用的权限，但是“操作”之类的某些部分披露了大量可用功能。

如果您点击“ / Apriso / HttpServices / api / platform / 1 / Operations”端点，它将返回将近5,000个不同的API调用的列表。除了我们最初发送的初始授权载体以外，这些认证都不需要认证。这里公开的操作包括...

  • 创建和修改货件

  • 创建和修改库存信息

支持案例IDOR

弄清楚该如何破解的更具挑战性的部分之一是拦截iOS HTTP流量。实际设备上有很多非常有趣的应用程序和API，但是属于Apple的许多域都是SSL固定的，我们都没有足够的移动背景，也没有足够的时间来分离实际的iOS设备。

人们过去已经做到了这一点，并且能够拦截所有HTTP流量，但是幸运的是，如果以某种方式设置代理，很大一部分流量仍然可以在各种应用程序中被拦截。

我们执行此操作的方法是设置Burp代理，安装证书，然后连接到启用了Burp代理的WiFi，只要我们进入要尝试拦截的页面即可。例如，在代理所有HTTP请求时无法加载核心App Store，而在不代理时无法加载应用商店，导航至您要拦截的正确子页面，然后在此时启用代理。

这使我们可以捕获iPhone默认情况下安装的Apple拥有的应用程序的许多API调用。其中之一是用于安排支持或与实时聊天代理对话的支持应用程序。

从拦截这些事件来看，来自多个端点的一些非常明显的IDOR会揭示有关支持案例详细信息的元数据。您可以检索有关受害者的支持案例详细信息的信息（他们要求的支持，他们的设备序列号，他们的用户ID）以及一个令牌，该令牌似乎在请求与支持代理进行实时聊天时使用。

总体而言，攻击者可能会滥用此信息来...

  • 泄漏的支持案例元数据，例如所有苹果支持案例的设备序列号和支持信息

结论

当我们刚开始这个项目时，我们不知道我们会花三个多月的时间来完成它。最初，这原本是一个附属项目，我们会不时进行，但是由于流行病带来了所有额外的空闲时间，我们每个人最终都花了数百个小时。

总体而言，苹果对我们的报告反应非常快。我们提交的更重要的报告仅在提交和修复之间有四个小时的时间。

由于没有人真正了解他们的错误赏金计划，因此，我们投入了大量时间投入了很多未知的领域。苹果与安全研究人员合作已有一段有趣的历史，但似乎他们的漏洞披露计划是朝着与黑客合作以保护资产并允许有兴趣的人查找和报告漏洞的正确方向迈出的重要一步。

写这篇博客文章是一个有趣的过程，因为我们不确定如何实际去做。坦白说，我们发现的每个错误都可能变成了包含大量随机信息的完整文章。苹果公司使用的身份验证系统相当复杂，用1-2个句子引用它，就好像我们在欺骗某人的信息一样。关于苹果基础设施中的许多元素，例如iCloud，苹果商店和开发者平台，也可以说同样的话。
