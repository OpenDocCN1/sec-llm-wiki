.NET Core漏洞可让攻击者逃避恶意软件检测

.NET Core库中的漏洞允许启动恶意程序，同时逃避安全软件的检测。



此漏洞是由Microsoft .NET Core库中的路径遍历漏洞引起的，该漏洞允许具有低特权的用户加载恶意垃圾回收DLL。


此错误会影响.NET Core 的最新稳定版本（3.1.x版本）。该修补程序当前不可用，它可使攻击者在系统上执行恶意代码，而不会被防病毒和EDR产品轻易检测到。1个


由Context Information Security的PaulLaîné发现，此漏洞可能是由于两个主要原因：


.NET Core允许您使用自定义DLL作为其垃圾回收器


未清除用于指定自定义.NET垃圾收集器的环境变量“ COMPlus_GCName”。因此，垃圾收集器路径中提供的所有遍历字符（../）都不会被过滤。   


.NET Core使用“垃圾收集器”来分配和释放.NET Core应用程序使用的系统内存。


但是，用户可以创建将由.NET核心应用程序加载的DLL形式的自定义垃圾收集器。


但是，.NET Core允许任何用户（包括特权低的用户）加载自定义垃圾收集器DLL，甚至是包含恶意代码的用户。


利用此错误

在利用此漏洞之前，攻击者已经需要至少对系统具有某种级别的访问权限才能设置环境变量。这意味着该漏洞将与现有漏洞利用结合使用，例如在  漏洞链接方案中。


黑客将这种攻击纳入其工具包的主要诱因是防止被感染计算机上运行的安全软件检测到他们的恶意负载。


要利用此错误，攻击者首先会创建一个自定义垃圾收集器，其中包含要在受感染计算机上执行的恶意代码。


然后，他们设置一个环境变量，使.NET Core使用此自定义的DLL。


设置自定义垃圾收集器  来源：Reddit


加载后，恶意代码将由合法的.NET Core进程dotnet.exe执行，以为DLL只是一个自定义的垃圾收集器。


恶意垃圾收集器DLL的示例


一旦垃圾收集器DLL由.NET框架核心加载，有效载荷开始执行时，它在此原因是反向TCP壳。


推出反向抄表器外壳


在现实情况下，有权访问受感染计算机的攻击者可以使用简单的批处理脚本来使.NET Core运行其恶意DLL，而不会被检测到。


为什么EDR产品无法检测到此情况？

Pentest实验室的研究人员进一步分析了此漏洞，并提供了更多的见解。


研究人员解释说，该漏洞利用了所谓的过程挖空技术。 


Pentest解释说：“ PaulLaîné在概念验证中使用了技术过程中空技术，以将代码注入到合法过程中，因为该过程是在挂起状态下创建的，内存区域未映射到文件，而是由实际的shellcode代替。”实验室  博客文章。 


由于恶意代码执行是在合法程序下进行的，因此该技术对于规避安全软件产品采用的严格检测和防御控制很有用。


如何检测和补救规避代码的执行？

Pentest实验室的研究人员提供了两种策略来检测此漏洞是否被滥用。


尽管几乎不可能预测恶意垃圾检测器DLL在系统上的位置，但是环境变量“ COMPlus_GCName”仍然是固定的字符串，可以对其进行监视。

微软说不是漏洞 

因为利用此机制要求攻击者已经具有在受感染系统上设置环境变量的能力，所以Microsoft认为这不是一个安全漏洞： 


“根据MSRC，我们认为这不是安全漏洞。利用这一点将要求对手修改环境块，此时他们已经可以控制应用程序执行的其他方面。”微软在Laîné报道的GitHub问题中表示。


Laîné  在他的原始披露中承认：“具有使用自定义GC的功能是一项合法功能，可能不应该删除。但是，应该解决路径遍历问题，以将自定义GC的使用限制为仅具有本地管理员特权的用户，这在服务器端应用程序或开发环境中应如此。”


鉴于此“合法”功能没有微不足道的修补程序，因此在.NET繁重的企业环境中仍然存在滥用的可能性。
