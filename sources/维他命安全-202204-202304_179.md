**0x00 风险概述**  

众所周知，网络安全已成为大多数组织的头等大事，尤其是那些处理敏感客户信息的行业。随着这些企业致力于构建稳健的安全策略，因此防范各种威胁和漏洞至关重要。

API安全是需要严格审查的领域之一。API 是应用程序编程接口的缩写，已成为数字化组织的常用构建块。它们促进了沟通和关键业务运营，还支持重要的数字化转型。

但从某些安全方面讲，API 会暴露应用程序逻辑和敏感数据，例如个人身份信息 (PII)，因此越来越频繁地成为攻击者的目标。

OWASP API 安全项目旨在通过强调不安全 API 的潜在风险并说明如何减轻这些风险来为软件开发人员和安全评估人员提供价值。为了促进实现这一目标，OWASP API 安全项目创建和维护API 安全风险Top 10文档，以及创建或评估 API 时最佳实践的文档门户。

OWASP API 安全项目2019 年首次发布了API 安全Top 10，旨在让软件开发人员和安全评估人员了解和减轻应用程序编程接口 (API) 的独特漏洞和安全风险。

###   

### **0x01 风险详情**

2019年API安全Top 10包括：

l**API1:2019 ****破坏对象级别授权**

API往往会暴露出处理对象标识符的端点，从而产生一个广泛的攻击面级别的访问控制问题。在使用用户的输入访问数据源的每个函数中都应考虑对象级授权检查。

攻击者可以通过操纵请求中发送的对象的ID，来利用容易受到破坏的对象级授权的API端点。这可能导致对敏感数据的未授权访问。这个问题在基于API的应用程序中极为常见，因为服务器组件通常不会完全跟踪客户端的状态，而是更多地依赖客户端发送的对象ID等参数来决定访问哪些对象。

**防御：**

ü实施依赖于用户策略和层次结构的适当授权机制。

ü使用授权机制来检查登录用户是否有权在使用客户端输入访问数据库中记录的每个函数中对记录执行请求的操作。

ü倾向于使用随机和不可预测的值作为记录ID的GUID。

ü编写测试来评估授权机制。不要部署破坏测试的易受攻击的更改。

  

l**API2:2019 ****损坏的用户认证**

认证机制的实施往往是不正确的，允许攻击者破坏认证令牌或利用实施缺陷暂时或永久地使用其他用户的身份。破坏了系统识别客户/用户的能力，从整体上损害了API的安全性。

API 中的身份验证是一种复杂且令人困惑的机制。该问题大概可分为两个子缺陷：

1\. 缺乏保护机制：负责身份验证的 API 端点必须与常规端点区别对待，并实施额外的保护层

2\. 机制实施不当：使用/实施机制时未考虑攻击向量，或者它是错误的用例（例如，为 IoT 客户端设计的身份验证机制可能不是 Web 应用程序的正确选择）。

如果 API 存在以下情况，则该 API 很容易受到攻击：

ü允许凭据填充，攻击者借此获得有效用户名和密码的列表。

ü允许攻击者对同一用户帐户执行暴力攻击，而无需提供验证码/帐户锁定机制。

ü允许弱密码。

ü发送敏感的身份验证详细信息，例如 URL 中的身份验证令牌和密码。

ü不验证令牌的真实性。

ü接受未签名/弱签名的 JWT 令牌 ( "alg":"none")/不验证它们的到期日期。

ü使用纯文本、未加密或弱哈希密码。

ü使用弱加密密钥。

**防御：**

ü确保您知道所有可能的流程以向 API 进行身份验证（移动/网络/实现一键式身份验证的深层链接等）。

ü阅读您的身份验证机制。确保您了解它们的用途和使用方式。OAuth 不是身份验证，API 密钥也不是。

ü不要在身份验证、令牌生成、密码存储方面重新发明轮子，使用标准。

ü在暴力破解、速率限制和锁定保护方面，凭证恢复/忘记密码端点应被视为登录端点。

ü使用OWASP 身份验证备忘单。

ü在可能的情况下，实施多因素身份验证。

ü实施反暴力破解机制，以减轻对身份验证端点的凭据填充、字典攻击和暴力破解攻击。这种机制应该比 API 上的常规速率限制机制更严格。

ü实施帐户锁定/验证码机制以防止针对特定用户的暴力破解。实施弱密码检查。

üAPI 密钥不应用于用户身份验证，而应用于客户端应用程序/项目身份验证。

  

l**API3:2019 ****过度的数据暴露**

期待通用的实现，开发人员倾向于暴露所有对象的属性，而不考虑它们各自的敏感性，依靠客户端在显示给用户之前进行数据过滤。

API 按照设计将敏感数据返回给客户端。这些数据通常在呈现给用户之前在客户端进行过滤。攻击者可以轻松嗅探流量并查看敏感数据。

**防御：**

ü永远不要依赖客户端来过滤敏感数据。

ü查看来自 API 的响应以确保它们仅包含合法数据。

ü后端工程师在暴露一个新的API端点之前，应该总是问自己 "谁是数据的消费者？

ü避免使用通用方法，例如to\_json()和to\_string()。相反，挑选你真正想要返回的特定属性。

ü对您的应用程序存储和使用的敏感信息和个人身份信息 (PII) 进行分类，审查所有返回此类信息的 API 调用，以查看这些响应是否会带来安全问题。

ü实施基于模式的响应验证机制作为额外的安全层。作为此机制的一部分，定义并强制执行所有 API 方法返回的数据，包括错误。

  

l**API4:2019 ****缺乏资源和速率限制**

很多时候，API并没有对客户/用户可以请求的资源的大小或数量进行任何限制。这不仅会影响API服务器的性能，导致拒绝服务（DoS），而且还为暴力攻击等认证缺陷打开了大门。

**防御：**

üDocker 可以很容易地限制内存、CPU、重启次数、 文件描述符和进程。

ü对客户端在定义的时间范围内调用 API 的频率实施限制。

ü当超过限制时，通过提供限制编号和重置限制的时间通知客户。

ü为查询字符串和请求正文参数添加适当的服务器端验证，特别是控制要在响应中返回的记录数的参数。

ü定义并强制执行所有传入参数和有效负载的最大数据大小，例如字符串的最大长度和数组中元素的最大数量。

  

l**API5:2019 ****损坏的功能级别授权**

具有不同层次、组和角色的复杂访问控制策略，以及管理和常规功能之间不明确的分离，往往会导致授权缺陷的出现。通过利用这些问题，攻击者获得了对其他用户的资源和/或管理功能的访问。

**防御：**

ü执行机制应该默认拒绝所有的访问，要求明确授予特定角色对每个功能的访问。

ü针对功能级别的授权缺陷审查您的API端点，同时牢记应用程序和组的层次结构的业务逻辑。

ü确保您所有的管理控制器都继承自管理抽象控制器，该控制器根据用户的组/角色来实现授权检查。

ü确保常规控制器内的管理功能根据用户的组和角色实现授权检查。

  

l**API6:2019****批量分配**

将客户端提供的数据（如JSON）与数据模型绑定，而没有根据允许列表进行适当的属性过滤，通常会导致大规模分配。无论是猜测对象属性、探索其他API端点、阅读文档，还是在请求有效载荷中提供额外的对象属性，都允许攻击者修改他们不应该修改的对象属性。

**防御：**

ü如果可能，请避免使用自动将客户端输入绑定到代码变量或内部对象的函数。

ü仅将客户端应更新的属性列入白名单。

ü使用内置功能将不应由客户端访问的属性列入黑名单。

ü如果适用，明确定义和实施输入数据有效负载的架构。

  

l**API7:2019****安全配置错误**

安全配置错误通常是不安全的默认配置、不完整或临时配置、开放的云存储、错误配置的HTTP头、不必要的HTTP方法、允许的跨源资源共享（CORS）以及包含敏感信息的冗长错误信息。

攻击者通常会尝试寻找未修补的缺陷、常见端点或未受保护的文件和目录，以获得未经授权的访问或对系统的了解。在以下情况下，API 可能容易受到攻击：

ü应用程序堆栈的任何部分都缺少适当的安全加固，或者它对云服务的权限配置不当。

ü缺少最新的安全补丁，或者系统已过时。

ü启用了不必要的功能（例如，HTTP verbs）。

ü传输层安全性(TLS) 缺失。

ü安全指令不会发送给客户端（例如，安全标头）。

ü跨域资源共享 (CORS) 策略缺失或设置不当。

ü错误消息包括堆栈跟踪，或暴露其他敏感信息。

**防御：**

API 生命周期应包括：

ü可重复的强化过程可以快速轻松地部署正确锁定的环境。

ü审查和更新整个 API 堆栈的配置的任务。审核应包括：编排文件、API 组件和云服务（例如，S3 存储桶权限）。

ü所有 API 交互访问静态资产（例如，图像）的安全通信通道。

ü一个自动化过程，用于持续评估所有环境中配置和设置的有效性。

此外：

ü为了防止异常跟踪和其他有价值的信息被送回给攻击者，如果适用的话，定义并执行所有API响应的有效载荷模式，包括错误响应。

ü确保 API 只能由指定的 HTTP verbs访问。应禁用所有其他 HTTP verbs（例如HEAD）。

ü希望从基于浏览器的客户端（如WebApp前端）访问的API应实施适当的跨源资源共享（CORS）策略。

  

l**API8:2019 ****注入**

注入缺陷，如SQL、NoSQL、命令注入等，当不受信任的数据作为命令或查询的一部分被发送到解释器时就会发生。攻击者的恶意数据可以欺骗解释器执行非预期的命令或未经适当授权访问数据。

在以下情况下，API 容易受到注入漏洞的影响：

üAPI 未验证、过滤或清理客户端提供的数据。

ü客户端提供的数据直接用于或连接到 SQL/NoSQL/LDAP 查询、操作系统命令、XML 解析器和对象关系映射 (ORM)/对象文档映射器 (ODM)。

ü来自外部系统（例如，集成系统）的数据未被 API 验证、过滤或清理。

**防御：**

ü防止注入需要将数据与命令和查询分开：

ü使用单一、值得信赖且积极维护的库执行数据验证。

ü验证、过滤和清理所有客户提供的数据或来自集成系统的其他数据。

ü应使用目标解释器的特定语法对特殊字符进行转义。

ü首选提供参数化接口的安全 API。

ü始终限制返回记录的数量，以防止在注入时大量泄露。

ü使用足够的过滤器验证传入数据，以仅允许每个输入参数的有效值。

ü为所有字符串参数定义数据类型和严格模式。

  

l**API9:2019****资产管理不当**

API 往往比传统的 Web 应用程序公开更多的端点，因此正确和更新的文档非常重要。适当的主机和已部署的 API 版本清单在缓解诸如已弃用的 API 版本和暴露的调试端点等问题方面也发挥着重要作用。

因为旧的 API 版本通常未打补丁，是一种破坏系统的简单方法，而过时的文档使查找和/或修复漏洞变得更加困难。攻击者可能获得敏感数据，甚至通过连接到同一数据库的旧的、未打补丁的API版本接管服务器。

**防御：**

ü点所有 API 主机并记录每个主机的重要方面，重点关注 API 环境（例如，生产、暂存、测试、开发）、谁应该对主机（例如，公共、内部、合作伙伴）进行网络访问以及API 版本。

ü清点集成服务并记录重要方面，例如它们在系统中的作用、交换的数据（数据流）及其敏感性。

ü记录 API 的所有方面，例如身份验证、错误、重定向、速率限制、跨源资源共享 (CORS) 策略和端点，包括它们的参数、请求和响应。

ü采用开放标准自动生成文档。在您的 CI/CD 管道中包含文档构建。

ü向授权使用 API 的人员提供 API 文档。

ü对所有暴露的 API 版本使用 API 安全防火墙等外部保护措施，而不仅仅是当前的生产版本。

ü避免将生产数据用于非生产 API 部署。如果这是不可避免的，这些端点应该得到与生产端点相同的安全处理。

ü当较新版本的 API 包括安全改进时，执行风险分析以决定旧版本所需的缓解措施：例如，是否可以在不破坏API 兼容性的情况下向后移植改进，或者您是否需要移除旧版本快速并强制所有客户端迁移到最新版本。

  

l**API10:2019****日志记录和监控不足**

日志记录和监控不足，再加上与事件响应的集成缺失或无效，使得攻击者能够进一步攻击系统，保持持久性，转向更多的系统，以篡改、提取或破坏数据。大多数违规研究表明，发现违规的时间超过200天，通常是由外部各方而不是内部流程或监测发现的。

攻击者可以利用缺乏日志记录和监控来滥用系统而不被发现。在以下情况下，API 容易受到攻击：

ü它不生成任何日志，日志记录级别设置不正确，或者日志消息没有包含足够的详细信息。

ü不保证日志完整性（例如，日志注入）。

ü日志不会被持续监控。

üAPI 基础设施没有得到持续监控。

**防御：**

ü记录所有失败的身份验证尝试、拒绝访问和输入验证错误。

ü日志应该使用适合日志管理解决方案使用的格式来编写，并且应该包含足够的细节来识别恶意行为者。

ü日志应作为敏感数据处理，在静止和传输时应保证其完整性。

ü配置监控系统以持续监控基础设施、网络和 API 功能。

ü使用安全信息和事件管理 (SIEM) 系统来汇总和管理来自 API 堆栈和主机的所有组件的日志。

ü配置自定义仪表板和警报，以便更早地检测和响应可疑活动。
