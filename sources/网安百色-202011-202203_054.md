# 微软紧急修复FIP-FS中的 “Year 2022” 漏洞

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzI0NzE4ODk1Mw==&mid=2652090042&idx=2&sn=f1865e03b62041d247ab3d09612678d4&chksm=f254d20cc5235b1a250c69c583dfb45e6bc396d0da1ec4729aacf6b776dcdab8fe4f44b5bd42&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=MzI0NzE4ODk1Mw==&mid=2652090042&idx=2&sn=f1865e03b62041d247ab3d09612678d4&chksm=f254d20cc5235b1a250c69c583dfb45e6bc396d0da1ec4729aacf6b776dcdab8fe4f44b5bd42&scene=27#wechat_redirect)

由于FIP-FS 反恶意软件扫描引擎中出现了 “Year 2022” 漏洞，从2022年1月1日开始，微软 Exchange 本地服务器无法传输邮件。

从Exchange Server 2013开始，微软默认启用 FIP-FS 反垃圾邮件和反恶意软件扫描引擎，保护用户免受恶意邮件风险。

  

![](../Images/a87859b6d5882fa5bfc0472597035dcf.png)**微软 Exchange Y2K22 漏洞**  
  

  

从全球微软 Exchange 管理员的无数报告来看，从2022年1月1日开始，FIP-FS 引擎中的漏洞拦截本地服务器传输邮件。

安全研究员和 Exchange 管理员 Joseph Roosen 表示，该漏洞是由微软使用已签名的 int32 变量存储日期的值引发的，该日期的最大值是2,147,483,647。然而，2022年的日期的最大值是2,201,010,001，大于存储在已签名 int32 变量中的最大值，导致该扫描引擎未能且没有发出邮件。

当触发该漏洞是，Exchange Server 的事件日志中会出现1106错误，“FIP-FS Scan Process 未能初始化。错误: 0x8004005。错误详情：未指定错误” 或 “错误代码：0x8004005。错误描述：无法转换 “2201010001” 为长字符”。

微软需要发布Exchange Server 更新，使用更大的变量来容纳该值，修复漏洞。

  

![](../Images/a87859b6d5882fa5bfc0472597035dcf.png)**非官方修复方案**  
  

  

然而，对于目前受影响的本地 Exchange Servers 而言，管理员发现可以禁用 FIP-FS 扫描引擎，允许邮件再次开始传输。要禁用该引擎，可以在 Exchange Server 上执行如下 PowerShell 命令：

*     
    
*     
    
*     
    

`Set-MalwareFilteringServer -Identity -BypassFiltering $true``   ``Restart-Service MSExchangeTransport`

  

重启 MSExchangeTransport 服务后，邮件会再次进行传输。

遗憾的是，这是非官方修复方案。微软将不再扫描所传输邮件，导致用户可能收到更多的恶意邮件和垃圾邮件。

  

![](../Images/a87859b6d5882fa5bfc0472597035dcf.png)**官方修复方案**  
  

  

微软指出，“我们已经修复了在本地 Exchange Server 2016 和 Exchange Server 2019 传输序列中导致报文无法传输的问题。该问题和新年的变化引发的日期检查错误有关，并非反病毒引擎本身的漏洞。它并非恶意软件扫描或恶意软件引擎的问题，也并非安全相关的问题。对签名文件的检查导致恶意软件引擎崩溃，从而使报文被拦截在传输队列中。”

微软指出，客户需要进行手动操作才能完成修复方案。对于自动解决方案而言，需要首先下载脚本（https://aka.ms/ResetScanEngineVersion）；运行Set-ExecutionPolicy -ExecutionPolicy RemoteSigned 更改 PowerShell 脚本的执行策略；在每个 Exchange 邮箱服务器上运行该脚本。另外，微软还提供了手动修复方案。

具体修复方案可见：https://techcommunity.microsoft.com/t5/exchange-team-blog/email-stuck-in-exchange-on-premises-transport-queues/ba-p/3049447
