还有下一个吧吗？Log4j第5个漏洞CVE-2021-44832来袭，Apache再发2.17.1版修复

Apache 发布了最新的 Log4j 版本 2.17.1，修复了 2.17.0 中新发现的远程代码执行 (RCE)漏洞，编号为 CVE-2021-44832。
在此之前，2.17.0 是 Log4j的最新版本，被认为是最安全的升级版本，但现在情况已经发生了变化。Apache官网已发布最新的更新，呼吁用户升级到2.17.1.
MITRE的官网上仅对该漏洞分配了CVE编号及简要描述，也并未给出漏洞报告时间和分配CVE的具体日期。

Log4j的第五个CVE

攻击者对原始Log4Shell 漏洞(CVE-2021-44228) 的大规模利用始于 12月9日左右，当时GitHub上出现了针对该漏洞的漏洞利用PoC 。
鉴于 Log4j 在大多数Java应用程序中的广泛使用，Log4Shell很快变成了全球企业和政府的噩梦。
虽然原始Log4Shell漏洞即CVE-2021-44228利用带来的严重风险至关重要，但该漏洞的温和变体出现在Log4j版本中，包括 2.15和 2.16—以前认为已完全修补。
BleepingComputer早些时候报道了影响 Log4j的四种不同的 CVE，一种是在“logback”框架中发现的漏洞。在 2.16 版中发现 DoS 漏洞后，建议迅速转向升级到被认为是最安全的2.17.0 版。
但现在第五个漏洞——一个RCE漏洞，被追踪为CVE-2021-44832已在 2.17.0中发现，并在最新版本 2.17.1 中应用了一个补丁。
该漏洞的严重性评级为“中等”，CVSS 评分为 6.6，该漏洞源于缺乏对 log4j中JDNI访问的额外控制。
“JDBC Appender在访问JNDI时应该使用JndiManager。JNDI访问应该通过系统属性来控制，”BleepingComputer 看到的问题描述说。
“与 CVE-2021-44832 相关，其中有权修改日志配置文件的攻击者可以使用 JDBC Appender构建恶意配置，其中数据源引用可以执行远程代码的 JNDI URI。”

“我们已经很久没有这样做了，唯一负责任的事情就是竖起一个巨大的闪烁的霓虹灯，上面写着‘LOG4J 无法修复，请勿将其用于任何事情。’”另一位嘲讽道。

披露的太快了？

在 Nizry发布推文时，BleepingComputer当时还没有看到表明log4j 2.17中存在 RCE 错误的官方建议或备忘录。
该推文本身没有包含有关该漏洞或如何利用漏洞的详细信息，但在几分钟之内就引发了一群安全专家和网民开始调查该声明。
过早披露安全漏洞可能会引诱威胁行为者进行恶意扫描和利用活动，这一点从12月9日的 Log4Shell 漏洞利用漏洞中可以明显看出。

到目前为止，从国家支持的黑客到勒索软件团伙等 各种威胁行为者都利用log4j漏洞将门罗币矿工注入易受攻击的系统。
已经看到Conti勒索软件团伙盯上了易受攻击的 VMWare vCenter 服务器。而攻击者通过 log4shell 破坏越南加密平台 ONUS要求 500 万美元的赎金。 
Log4j 用户应立即升级到最新版本 2.17.1(适用于 Java 8)。包含修复程序的反向移植版本 2.12.4 (Java 7) 和 2.3.2 (Java 6) 预计也将很快发布。
BleepingComputer已在撰写本文前联系 Checkmarx征求意见，正在等待他们的回复。
到目前为止，围绕Log4j的相关漏洞已达到6个。
