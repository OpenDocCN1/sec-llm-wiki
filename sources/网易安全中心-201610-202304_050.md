在入侵检测的过程中，主机监控是一切的前提，因为攻击者的绝大多数攻击行为都会在进程/文件/网络等处呈现。eBPF技术作为云原生时代Trace技术的宠儿，非常适用于安全监测这一场景。

本文将介绍eBPF技术在网易自研HIDS中的应用实践。

0x01 eBPF是什么

eBPF原理本文不再赘述，官网链接：https://ebpf.io/zh-cn/

  

  

eBPF近年来被视为linux的革命性技术，它允许开发者在linux的内核里动态实时地加载运行自己编写的沙盒程序，无需更改内核源码或者加载内核模块。同时，用户态的程序可以通过bpf(2)系统调用和bpf map结构与内核中的eBPF程序实时交换数据。  

  

![](../Images/87ddba92b5947a09ca2b0fe7ae6d3b82.png)

我们可以理解eBPF就是一个内核虚拟机，用户可以将自定义程序放入这个虚拟机，达到内核数据分析而不需要用户态介入的目的。

自定义程序只需要声明HOOK的内核事件，就可以在事件触发的时候第一时间接收到事件数据，这里的内核事件主要有这几类：

*   kprobes：实现内核中动态跟踪。
*   uprobes：用户级别的动态跟踪。
*   tracepoints：内核中静态跟踪。
*   perf\_events：定时采样和 PMC。

0x03 eBPF程序编写之前  

在编写eBPF程序之前，要先选择自己的eBPF程序的部署方式，不同的部署方式对应的程序编写方式也稍有不同。

目前主流的部署方式有3种，优缺点也很明显：

1.  ELF方式：预编译出.o文件，在运行时直接使用这个文件。

*   优点：稳定，对内核版本要求低。
*   缺点：基本无法移植，在不同内核机器上需要编译出各种版本的.o文件

    2. BCC方式：只管编写代码，不需要预编译，在运行时实时编译运行。

  

  
BCC (BPF Compiler Collection) 在 eBPF 编程接口之上封装了 eBPF 程序的构建过程，提供了 Python、C++ 和 Lua 等高级语言接口，并基于 Python 接口实现了大量的工具，是新手入门体验 eBPF 的最好项目。  

*   优点：无需编译，到处运行，对不同内核的机器不需要做差异化处理。
*   缺点：对运行环境要求较高（需要llvm，kernel header等编译所需）， 每次运行都需要编译，消耗机器资源。

   3. CO-RE+BTF方式：最新最流行的方式。

  

  
BPF CO-RE在软件堆栈的各个级别汇集了必要的功能和数据：内核，用户空间的BPF加载器库(libbpf)，和编译器(Clang)。通过这些组件来支持编写可移植的BPF程序，使用相同的预编译的BPF程序来处理不同内核之间的差异。BTF (BPF Type Format) 是一种节省空间，紧凑但依然具有足够表达能力的格式，可以描述C程序的所有类型信息。现在，已经可以在内核运行时显示地嵌入BPF类型信息：只需要启用CONFIG\_DEBUG\_INFO\_BTF=y内核选项即可。内核本身可以使用BTF功能，用于增强BPF验证程序自身的功能。         

*   优点：一次编译，到处运行！
*   缺点：机器需要支持BTF，即对内核版本要求较高。

`SEC("tracepoint/syscalls/sys_enter_execve")``int enter_execve(struct execve_entry_args_t *ctx)``{``  bpf_printk("execve syscall traced!");``  struct exec_data_t exec_data = {};``    // 参数地址``  const char* argp = NULL;``  exec_data.pid = bpf_get_current_pid_tgid();``  #pragma unroll``  for (__s32 i = 0; i < DEFAULT_MAXARGS; i++)``  {``    bpf_probe_read(&argp, sizeof(argp), &ctx->argv[i]);``    if (!argp) {``      goto finish;``  }``    exec_data.arg_size = bpf_probe_read_str(exec_data.args, ARGSIZE, argp);``    bpf_perf_event_output(ctx, &execve_perf_map, BPF_F_CURRENT_CPU, &exec_data, sizeof(exec_data));``  }``  finish:``  exec_data.type = 1;``  exec_data.tgid = bpf_get_current_pid_tgid() >> 32;``  exec_data.uid = bpf_get_current_uid_gid();``  exec_data.gid = bpf_get_current_uid_gid() >> 32;``  bpf_probe_read_str(exec_data.fname, sizeof(exec_data.fname), ctx->filename);`` ``  bpf_get_current_comm(exec_data.comm, sizeof(exec_data.comm));``  bpf_perf_event_output(ctx, &execve_perf_map, BPF_F_CURRENT_CPU, &exec_data, sizeof(exec_data));``  return 0;``}`
```

这个程序所实现的功能即：

1.  hook内核事件:SEC("tracepoint/syscalls/sys\_enter\_execve")
2.  获取内核事件参数 struct execve\_entry\_args\_t \*ctx
3.  组装自己需要的数据，通过perf方式发给用态 bpf\_perf\_event\_output

func main() {  args := make(map[uint32][]string)  objs := sysExecveObjects{}  loadSysExecveObjects(&objs, nil)  link.Tracepoint("syscalls", "sys_enter_execve", objs.EnterExecve)  rd, err := perf.NewReader(objs.ExecvePerfMap, os.Getpagesize())  if err != nil {    log.Fatalf("reader err")  }  for {    ev, err := rd.Read()    if err != nil {      log.Fatalf("Read fail")    }    if ev.LostSamples != 0 {      log.Printf("perf event ring buffer full, dropped %d samples", ev.LostSamples)      continue    }    b_arr := bytes.NewBuffer(ev.RawSample)
    var data exec_data_t    if err := binary.Read(b_arr, binary.LittleEndian, &data); err != nil {      log.Printf("parsing perf event: %s", err)      continue    }
    if data.Type == 0 {      // args      e, ok := args[data.Pid]      if !ok {        e = make([]string, 0)      }      e = append(e, string(data.Args[:]))      args[data.Pid] = e    } else {      argv, ok := args[data.Pid]      if !ok {        continue      }      fmt.Printf("[INFO] Pid: %d <Cmdline> %s\n", data.Pid, strings.TrimSpace(strings.Replace(strings.Join(argv, " "), "\n", "\\n", -1)))      delete(args, data.Pid)    }  }}
```

这个程序所实现的功能即：

1.  将我们编写的eBPF代码生效并与之绑定link.Tracepoint
    
2.  等待perf消息并处理 perf.NewReader

1.  内核限制：eBPF技术依旧还在蓬勃发展，具体特性在什么内核版本支持，可以查看https://github.com/iovisor/bcc/blob/master/docs/kernel-versions.md
2.  安全性限制：eBPF虽然处于内核态，但比DPDK等技术安全的多，其原因就是他有诸多安全性限制

  

eBPF 程序不能调用任意的内核参数，只限于内核模块中列出的 BPF Helper 函数。

  eBPF 程序不允许包含无法到达的指令，防止加载无效代码，延迟程序的终止。

  eBPF 程序中循环次数限制且必须在有限时间内结束。Linux 5.3 在 BPF 中包含了对有界循环的支持，它有一个可验证的运行时间上限。 

  eBPF 堆栈大小被限制在 MAX\_BPF\_STACK，截止到内核 Linux 5.8 版本，被设置为 512。 

  eBPF 字节码大小最初被限制为 4096 条指令，截止到内核 Linux 5.8 版本， 当前已将放宽至 100 万指令
