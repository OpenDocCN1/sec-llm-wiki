    从我开始学习编程以来，我一直对使用这样一个简单的命令而好奇：

    pip install package\_name

    一些编程语言（例如Python）带有一种简单的、看起来正式的方法来为项目安装依赖包。这些安装程序通常与公共代码存储库绑定，任何人都可以自由上传代码包供他人使用。您可能已经听说过这些工具：如Node具有npm和npm注册表，Python的pip使用PyPI（Python包索引），以及RubyGems可以在RubyGems上找到。从这些来源中的任何一个下载和使用软件依赖包时，您是否真实信任软件依赖包的发布者在您的计算机上运行的代码，您的这种盲目信任是否会被黑客利用？

![](../Images/0688e017797b2b42f8e99349da89c044.png)

图1、三种语言的依赖包下载网站

    当然会被利用！

    任何程序包托管服务都无法保证其用户上传的所有代码均不含恶意软件。过去的研究表明，依赖包包名抢注（利用流行的依赖包名称的错字版本进行的攻击）在增加全球随机个人计算机对包的访问率方面非常有效。其他众所周知的供应链链攻击的路径包括使用各种方法来破坏现有依赖包，或以不再存在的依赖包名称上传恶意代码。

![](../Images/29fb1a5cded7a204c787df34c22910db.png)

图2、依赖包包名抢注的路径  

  

    **一、思路**

    在2020年夏季我尝试入侵PayPal时，Justin Gardner（@Rhynorater）分享了在GitHub上发现的一些有趣的Node.js源代码。该代码旨在供PayPal内部员工使用，并且在其package.json文件中似乎包含公共和私有依赖项的混合，即来自npm的公共程序包以及非公共程序包名称，很可能由PayPal内部托管。这些名称当时在公共npm注册表中是不存在的。

![](../Images/6940a28cfab2625fff89de207bc0d5d8.png)

图3、npm的公共程序包以及非公共程序包名称  

    由于该公司依赖包的来源不是很清晰，根据这个逻辑会引起一系列问题：

        •如果以这些名称将恶意代码上传到npm，会发生什么？PayPal的一些内部项目是否有可能开始默认为新的公共软件包而不是私有软件包？

        •开发人员，甚至自动化系统是否会开始在库中运行代码？

        •如果这行得通，我们可以从中获得赏金吗？

        •这种攻击还会对其他公司起作用吗？

    事不宜迟，我开始制定计划来回答这些问题。

    这个想法是将我自己“恶意”的 Node程序依赖包以所有无人认识的包名上传到npm注册表中，如果安装成果，安装了它们的每台计算机会通知我。如果最终这些依赖包有安装在（PayPal）拥有的服务器上（或其他任何原因），则其中的代码会立即通知我。

    在这一点上，我认为必须明确指出的很重要的一点是，在研究过程中所针对的每个组织都已允许我通过公共漏洞赏金计划或通过私人协议来对其安全性进行测试。未经授权，请勿尝试这种测试。

  

    **二、“永远是DNS协议”**    

    幸运的是，npm允许在安装软件依赖包时自动执行任意代码，这使我可以轻松创建一个Node软件依赖包，该软件依赖包通过其预安装脚本收集有关所安装的每台计算机的一些基本信息。

    为了在通过数据识别组织名称与避免收集太多敏感信息之间取得平衡，我决定只记录用户名、主机名、每个唯一安装的当前路径与外部IP这些数据就足够了，可以帮助安全团队根据我的报告确定可能受到攻击的系统，同时避免将我的测试误认为是实际的攻击。现在剩下的一件事：如何将这些数据传回给我？

    知道大多数可能的目标都将位于受良好保护的公司网络内部，我认为DNS协议回传数据是解决之道。

![](../Images/e412cdcf8addac2b3f9bd3c76948b983.png)

图4、DNS协议回传  

    通过DNS协议将信息发送到我的服务器，这对于测试本身能否正常工作不是必须的，但它确实保证了在出站时不太可能被阻止或检测到该流量。

    数据经过十六进制编码，并用作DNS查询的一部分，该DNS查询直接或通过中间解析器到达了我的自定义的权威DNS服务器。服务器配置为记录每个接收到的查询，实质上记录了下载软件包的每台计算机的记录。

  

    **三、多多益善**

    有了基本的攻击计划，现在是时候发现更多可能的目标了。

    第一个策略是寻找可替代的软件生态系统进行攻击。因此，我将代码移植到了Python和Ruby上，以便能够分别将相似的软件包上传到PyPI（Python软件包索引）和RubyGems。

    但是可以说，该测试最重要的部分是找到尽可能多的相关依赖包名称。

    在整整地搜索了一些目标公司的私有软件依赖包名称几天后，通过各种互联网论坛上的帖子，发现了可以在GitHub以及主要的软件包托管服务上（在意外发布的内部软件包内部）甚至在内部找到许多其他名称。但是，到目前为止，找到私有程序依赖包名称的最佳位置竟然是…在javascript文件中。

    显然，内部package.json文件（包含javascript项目的依赖项的名称）在构建过程中会嵌入到公共脚本文件中，从而暴露内部程序包的名称，这是很常见的。同样，这些文件中泄漏的内部路径或require()调用也可能包含依赖项名称。苹果，Yelp和特斯拉只是以这种方式公开内部名称的公司的一些例子。

![](../Images/092be5f057563cbc548fe88f9ad44494.png)

图5、从javascript获取的依赖包包名

    在2020年下半年，由于@streaak的帮助和出色的侦察技能，我们能够自动扫描属于目标公司的数百万个包名，并提取数百个尚未在npm注册表中声明的javascript软件依赖包名称。然后，我将代码上传到所有找到的名称下的包托管服务中，并等待回调。

  

    **四、回报**

    成功率简直是惊人的。

    从开发人员在自己的计算机上犯下了一次性的错误，到内部或基于云的构建服务器配置错误，再到系统易受攻击的开发渠道，有一件事明显很重要，那就是：抢占有效的内部软件依赖包名称几乎是一种重要有效的方法。一些很大的科技公司的内部网络，可以远程执行代码，并且可能允许攻击者在构建过程中添加后门。

    迄今为止，我已经在超过35个组织中的所有三种经过测试的编程语言中检测到了这种类型的漏洞，我已经开始将其称为依赖关系混乱。绝大多数受影响的公司属于有超过1000名员工的大公司类别，这很可能反映了大型组织内部使用依赖库的普遍性。

    由于可以通过javascript更容易地找到依赖包名称，在所有已记录的回调中几乎有75％来自npm软件包，但这并不一定意味着Python和Ruby不太容易受到攻击。实际上，尽管在我的搜索过程中只能识别出属于八个组织的内部Ruby依赖包名称，但事实上，其中的四家公司很容易通过RubyGems造成依赖混淆。加拿大电子商务巨头Shopify就是这样的公司之一，其构建系统仅在我上载几个小时后自动安装了一个名为“shopify-cloud”的Ruby gem依赖包，然后尝试在其中运行代码。Shopify团队在一天之内准备好修复程序，并为发现问题提供了30,000美元的漏洞赏金。在我2020年8月上传到npm的Node包中的代码在其网络内的多台计算机上执行之后，我又从苹果获得了30,000美元的奖励。受影响的项目似乎与Apple的身份验证系统（外部称为Apple ID）有关。当我提出这个漏洞可能会允许黑客向Apple ID注入后门的想法时，当时Apple并不认为这种攻击可以确实达到这种效果，而是说：在运营服务中实现后门需要更复杂的事件序列，并且这是一个带有附加含义的非常特定的术语。但是，Apple最后确认使用此npm软件包技术可以在Apple服务器上执行远程代码。根据软件依赖包安装的流程，该问题在我报告的两周内得到解决，但仅在发布此帖子之前不到一天apple就授予了赏金漏洞。

![](../Images/3c95778f6e862c6160b3d5a904c82591.png)

图5、被后门植入的主机回传的参数信息  

    在针对其他公司的其他几次成功攻击中，可以看到在内部服务器和个人开发人员的PC上都安装了相同主题的npm软件包，其中一些安装通常是在软件包上载后数小时甚至数分钟进行的。这证实了依赖混淆bug的严重性通常很高。

    其他受影响的公司包括Netflix，Yelp和Uber。

  

    **五、这不是漏洞，这是特性**

    尽管有大量的依赖混淆的发现，但一个细节在某种程度上仍然是（现在仍然是）尚不清楚：为什么会这样？此类漏洞的主要根源是什么？

    可以理解，大多数受影响的组织都不愿透露有关其根本原因和缓解与修补策略的更多技术细节，但是在我的研究过程中以及与安全团队的沟通中确实出现了一些有趣的细节。

    例如，Python依赖关系混乱的主要原因似乎是错误地使用了“设计不安全”命令行参数--extra-index-url。当将此参数与pip install库一起使用以指定您自己的软件包索引时，您可能会发现它可以按预期运行，但是pip在幕后实际执行的操作如下：

        •检查指定（内部）包索引上是否存在库

        •检查库是否在公共软件包索引（PyPI）上存在

        •安装找到的任何版本。如果两个软件包均存在，则默认从具有更高版本号的源进行安装。

    因此，在上面的示例中，将名为库9000.0.0的包上传到PyPI将导致劫持依赖包。

    尽管这种行为已经众所周知，但是仅在GitHub上搜索--extra-index-url就足以找到一些属于大型组织的易受攻击的脚本-包括一个影响Microsoft .NET Core组件的错误。不幸的是，该漏洞可能已允许向.NET Core添加后门程序，但该漏洞在.NET Bug赏金计划中未发现。

    Ruby的gem install --source也可以以类似的方式工作，但是我无法确认其使用是否是我发现的根本原因。

    当然，将--extra-index-url更改为--index-url是一种快速而直接的解决方法，但是事实证明，依赖混淆的其他一些变体、衍生体却很难被缓解。

    JFrog Artifactory是一款广泛用于托管各种类型内部软件包的软件，它提供了将内部和公共库混合到同一“虚拟”存储库中的可能性，从而大大简化了依赖性管理。但是，许多客户表示Artifactory使用上述完全相同的、易受攻击的算法来决定在使用相同名称的内部软件包还是外部软件包。在撰写本文时，还仍然无法更改此默认行为。

                           

**    六、未来的研究**

    尽管许多大型科技公司已经意识到这种漏洞，并已在其基础架构中对其进行了修复，或者正在努力实施缓解措施，但我仍然感到还有很多新的发现。

    具体来说，我相信找到泄漏的内部程序依赖包名称的新方法将揭示更多易受攻击的系统，而寻找替代的编程语言和目标存储库将揭示依赖包管理混乱的其他攻击面。

    话虽这么说，无论您的经验水平如何，我都鼓励您花一些时间在脑海中尝试一下您的新想法，无论新想法是否与依赖包管理的安全性有关。
