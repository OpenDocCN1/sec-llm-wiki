## 漏洞分析

###    前  言   

5.26日，Nginx发布安全公告，修复了Nginx解析器中一个DNS解析漏洞(CVE-2021-23017)，该漏洞存在于ngx\_resolver\_copy()函数，当Nginx配置文件中使用了resolver指令时，未经身份验证的攻击者可以截获DNS请求(UDP)并伪造特殊的DNS响应包来触发该漏洞，导致Off-By-One，从而造成DDos或远程代码执行。

###    前 置 知 识   

**1.DNS动态解析 **Nginx在配置上游服务器时，支持域名配置。根据不同的配置，Nginx提供了静态解析和动态解析两种方式。开源版的Nginx提供了resolver这种动态的DNS解决方案，核心思想是以Nginx自身充当DNS的客户端进行动态解析。其中，指令resolver可以在http范围内全局设定，也可以在某一个server甚至某一个location里面单独设定。`http{       server{           listen 80;           resolver 114.114.114.114;           set $foo www.xxx.com;           location / {           proxy_pass http://$foo;           }       }   }`在上述的配置中，当访问服务器根目录时，会把请求转化到$foo变量定义的服务器中，而该变量定义的服务器www.xxx.com会通过resolver指定的DNS服务器进行动态解析。同时，还可以通过valid参数设置DNS解析结果的有效期。`resolver 114.114.114.114 valid=30s; //有效期30S,有效期过后访问根目录会重新对上游服务器域名进行解析`需要注意的是，如果proxy\_pass后面是一个域名而不是一个变量，那么对域名的解析也是发生在启动解析期间，无法完成动态域名解析的功能。  
**2.DNS标准名称表示** DNS使用一种标准格式对域名进行编码，它由一系列label构成，每个label首字节的高两位用于表示label的类型，RFC1035中定义了两种类型，分别为`00 普通label   11 压缩label`

*   普通label 
    

当label首字节的高两位为0时，表示这是一个普通label。此时使用该字节剩下的6bit表示该label后续的长度。因此它的取值范围为0x00-0x3f，换句话说，域名的一个label最长为63个字节。 ![](../Images/ae1fe362dddfd678736267075c2e4000.png)上述为一个标准的DNS响应包，可以看到域名www.google.com的完整编码为`[3]www[6]google[3]com[0]  //03 77 77 77 06 67 6f 6f 67 6c 65 03 63 6f 6d 00`

*   压缩label 
    

由于一个DNS报文内往往拥有多个域名，大多数情况下这些域名有一部分是完全相同的。比如13个根域名服务器地址的唯一的区别是三级域名由a编号至m，后面的15个字节的label完全相同(.root-servers.net)。如果所有域名都按照上述方法原样表示，那么会因为冗余数据浪费许多空间。为此，规定了一种针对域名的压缩表示法，即使用一个压缩指针来对域名数据进行复用。生成报文时压缩并不是强制要求的。label首字节的高两位为11时表示这个label是压缩表示的，即为一个压缩指针。换句话说，当你发现某个label首字节的值大于等于0xc0(十进制的192)时，说明这是一个指针。压缩指针长度为两个字节，指针的值是第一个字节的低六位和第二个字节，一共14位。![](../Images/0f439927f2d90c3ff5c4622fc761bac1.png)可以看到，在上述DNS响应包中使用到了压缩指针(C0 0C)。该指针指向了DNS Response段的0x0c位置，即域名www.google.com编码数据的存放位置。此外，还需注意的一点是压缩是可以嵌套的，且一个名称内最多使用一个压缩指针。示例如下

```
0x0010 \[7\]example\[3\]com\[0\] //example.com 0x0020 \[3\]www\[C0\]\[10\]//www.example.com 0x0030\[C0\]\[20\] //www.example.com 
```

###    Root  Cause  Analyze   

此次漏洞主要发生在core/ngx\_resolver.c的ngx\_resolver\_copy()函数中，该函数主要由以下两部分组成1.计算未压缩域名的大小并验证输入包的合法性，丢弃大于128个指针或超出输入缓冲区边界的域名。

```
`p = src; len = -1;	//len初始长度``for (i = 0; i < 128; i++) { n = *p++; //指针p指向DNS响应包中的label``    if (n == 0) {   //解析完成``          goto done;``    }``}`
```

2.分配输出缓冲区，对域名进行解压缩并复制到其中

```
`done:``    ······``      dst = ngx_resolver_alloc(r, len);   //分配输出缓冲区``  }``     }`
```

细心的师傅应该可以发现，在上述第二部分代码中，默认压缩label都必须指向一个非空的值，即指向下一个label。若此时该压缩label指向NULL，会发生什么？

```
0x0010	\[7\]example\[3\]com\[0\] //example.com `0x0020	[3]www[C0][10]//www.example.com`
```

以上述为例，当我们对第二个域名进行解压缩时，假设\\\[C0\\\]\\\[10\\\]指向NULL。则经由第一部分计算后len为0x03。此时分配的输出缓冲区长度为0x03。当执行到下面代码时

```
`  n = *src++;        //n=0xC0`
```

由于(n=0xC0)!=0，会在输出缓冲区末尾追加'.'，从而导致一个字节的缓冲区溢出，即Off-By-One。如果计算出的大小恰好与堆块大小对齐，则越界写入的'.'(0x2E)将覆盖下一个堆块大小元数据的最低有效字节。并导致PREV\_INUSE被清除和IS\_MMAPPED被设置。

### 写在后面

由于该漏洞仅能导致一个特定字节的缓冲区溢出，在实际应用场景中一般需结合其他漏洞进行利用。利用难度较高。我们可以通过在以下位置注入中毒的域名来对该漏洞进行多次触发。

```
`DNS Questions QNAME,``DNS Answers NAME,`DNS Answers RDATA for CNAME and SRV responses
```

此外，当我们注入中毒的CNAME时，程序会对其进行递归解析，最终在ngx\_resolve\_name\_locked()调用ngx\_strlow()函数(ngx\_resolver.c:594)期间触发额外的OOB write，并在调用ngx\_resolver\_dup()(ngx\_resolver.c:790)和ngx\_crc32\_short()(ngx\_resolver.c:596 )时触发额外的 OOB read。更多利用思路可参考\[X41 D-SEC\](https://x41-dsec.de/lab/advisories/x41-2021-002-nginx-resolver-copy/) 的文章。

### 修复建议

Patch: 对代码的位置进行一些细微的调换，导致在追加"."之前必须先判断所存放的压缩Label必须指向非空，且输出缓冲区指针不指向起始位置。
