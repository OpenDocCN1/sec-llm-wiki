定位补丁

由于公布漏洞的作者一开始标记为0day, 所以我猜测补丁应该是在4.12这天打的.

所以在进行定位之后, 注意到有如下的两个相关的安全patch:

  • [compiler] Fix bug in RepresentationChanger::GetWord32RepresentationFor (If1eed719) · Gerrit Code Review (googlesource.com)

    https://chromium-review.googlesource.com/c/v8/v8/+/2817791 @a

  • [compiler\][x64] Fix bug in InstructionSelector::ChangeInt32ToInt64 (Ib4ea738b) · Gerrit Code Review (googlesource.com)

    https://chromium-review.googlesource.com/c/v8/v8/+/2820971 @b

因为之前这位前辈写过16040的漏洞exploit,  所以我一开始觉得觉得patch为@a的可能性要大一点. 结果发现该exploit在不添加@a 的patch情况下, 依然无法触发, 这是因为在该版本@b的patch已经添加了. 所以可以推断@b才是该漏洞的究极patch.

在移除了该patch之后, 发现漏洞可以触发. 验证完毕.

补丁分析

重新审视该补丁:


注意到如下的细节:

  • 该漏洞发生在instruction selector环节

  • 该注释里面有一个很重要的关键词, 叫做 signed-extened

在查阅了Sign extension - Wikipedia（https://en.wikipedia.org/wiki/Sign_extension）之后, 可以定位到如下的信息:

    • movsx: move with sign extension

    • movzx: move with zero extension

‍为了理解这两个类比的区别, 重新回归 poc:

const arr = new Uint32Array([2**31]);function jit(){return (arr[0] ^ 0) + 1;    //  [+] arr[0] = arr.0 []}
%PrepareFunctionForOptimization(jit);let res1 = jit();%OptimizeFunctionOnNextCall(jit);let res2 = jit();
print("[+] res1: " + res1);print("[+] res2: " + res2);

关于arr[0]这个数, 采用二进制表示应该会变得更为有趣:

可以看到, arr[0]这个数在第32位为1. 这里的1可以有两种解释:

  • 如果该数为 unsigned, 该1作为值记入.

  • 如果该数为signed, 该1作为符号为记入.

结合信息该优化发生在 instruction selector, 查看IR:

这个地方, 显然Int64Add对应的是 (arr[0] ^ 0) + 1操作. 而(arr[0] ^ 0)的结果应该由81计算出来.  在这里, 就留下了一个问题：

81 这个地方的1到底是被当作符号使用, 还是被当作值使用?

对该 jit函数进行分析:

function jit(){return (arr[0] ^ 0) + 1;    //  [+] arr[0] = arr.0 []}

不难得出左边的这个节点的值应该被当作符号使用.

然而, 查看patch:

由于在上面的case的时候, 使用的为kX64Movl指令, 可以发现1被当作值使用了. 

这个漏洞其实还有另外一个关键在于 EarlyOptimization环节的优化, 会将 x ^ 0 优化为 x的形式.

自此, 可以对漏洞的root cause进行一个归纳:

当 ChangeInt32ToInt64对值进行convert操作的时候, 无论representation为signed还是unsigned, 都应该将最高位的1当作符号进行处理, 而不应该当作值进行处理, 在这个地方的 patch之前, 就犯了这个错.

    • Issue 2183923003: stubs,interpreter] Optimise SMI loading for 64-bit targets. - Code Review (chromium.org)

      （https://codereview.chromium.org/2183923003）

    所以我自己定位该漏洞应该存在了很久, 但是测试17和18年的两个chrome版本均不可以, 这可能和一些需要触发漏洞的优化有关. 但我依然认为2183923003为最初的漏洞case.
