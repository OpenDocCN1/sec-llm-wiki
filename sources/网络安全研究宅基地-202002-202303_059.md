## 定位补丁

由于公布漏洞的作者一开始标记为`0day`, 所以我猜测补丁应该是在`4.12`这天打的.

![](../Images/4c1e6a4ed915ee9a279a37c46cde22ea.png)

所以在进行定位之后, 注意到有如下的两个相关的安全`patch:`

*   \[compiler\] Fix bug in RepresentationChanger::GetWord32RepresentationFor (If1eed719) · Gerrit Code Review (googlesource.com)
    
    https://chromium-review.googlesource.com/c/v8/v8/+/2817791 @a
    
*   \[compiler\\\]\[x64\] Fix bug in InstructionSelector::ChangeInt32ToInt64 (Ib4ea738b) · Gerrit Code Review (googlesource.com)
    
    https://chromium-review.googlesource.com/c/v8/v8/+/2820971 @b
    

因为之前这位前辈写过`16040`的漏洞`exploit`,  所以我一开始觉得觉得`patch`为`@a`的可能性要大一点. 结果发现该`exploit`在不添加`@a` 的`patch`情况下, 依然无法触发, 这是因为在该版本`@b`的`patch`已经添加了. 所以可以推断`@b`才是该漏洞的究极`patch`.

![](../Images/b855818bdd5fafaf24f3ddebd9612617.png)

在移除了该`patch`之后, 发现漏洞可以触发. 验证完毕.

## 补丁分析

重新审视该补丁:

  

![](../Images/d00c78a42a8bfabd2463d83a5603c1b0.png)

注意到如下的细节:

*   该漏洞发生在`instruction selector`环节
    
*   该注释里面有一个很重要的关键词, 叫做 `signed-extened`
    

在查阅了Sign extension - Wikipedia（https://en.wikipedia.org/wiki/Sign\_extension）之后, 可以定位到如下的信息:

*   `movsx`: `move with sign extension`
    
*   `movzx:` `move with zero extension`
    

‍为了理解这两个类比的区别, 重新回归 `poc:`

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
const arr = new Uint32Array([2**31]);function jit(){return (arr[0] ^ 0) + 1;    //  [+] arr[0] = arr.0 []}
%PrepareFunctionForOptimization(jit);let res1 = jit();%OptimizeFunctionOnNextCall(jit);let res2 = jit();
print("[+] res1: " + res1);print("[+] res2: " + res2);
```

关于`arr[0]`这个数, 采用二进制表示应该会变得更为有趣:

![](../Images/8c94e3aab91cf406296816287eed99d0.png)

可以看到, `arr[0]`这个数在第`32`位为`1`. 这里的`1`可以有两种解释:

*   如果该数为 `unsigned`, 该`1`作为值记入.
    
*   如果该数为`signed`, 该`1`作为符号为记入.
    

结合信息该优化发生在 `instruction selector`, 查看`IR:`

![](../Images/b0f27af7d269c554fb5cf0cba693e4a4.png)

这个地方, 显然`Int64Add`对应的是 `(arr[0] ^ 0) + 1`操作. 而`(arr[0] ^ 0)`的结果应该由`81`计算出来.  在这里, 就留下了一个问题：

> `81` 这个地方的`1`到底是被当作符号使用, 还是被当作值使用?

对该 `jit`函数进行分析:

*   
*   
*   

```
function jit(){return (arr[0] ^ 0) + 1;    //  [+] arr[0] = arr.0 []}
```

不难得出左边的这个节点的值应该被当作符号使用.

然而, 查看`patch:`

![](../Images/7c42e7eb1a3b0fd76221a67abe68c5c5.png)

由于在上面的`case`的时候, 使用的为`kX64Movl`指令, 可以发现`1`被当作值使用了. 

这个漏洞其实还有另外一个关键在于 `EarlyOptimization`环节的优化, 会将 `x ^ 0` 优化为 `x`的形式.

自此, 可以对漏洞的`root cause`进行一个归纳:

> 当 `ChangeInt32ToInt64`对值进行`convert`操作的时候, 无论`representation`为`signed`还是`unsigned`, 都应该将最高位的`1`当作符号进行处理, 而不应该当作值进行处理, 在这个地方的 `patch`之前, 就犯了这个错.
> 
>   

## exploit

关于这个漏洞的`exploit`的编写学习其实应该存在起码三种可能性:

*   熟悉`cve-2020-16040`的利用在进行分析, 造成`oob`
    
*   见下文, 造成`oob`
    
*   利用`range`, 造成`type confusion`, 可能存在这样的可能性.
    

第二种方法在这里细说一下, 原作者的`exp`里面存在如下的关键代码:

![](../Images/9536e8a067c3867e8a3f44f72273035e.png)

这里显而易见:

*   红色部分的代码负责触发漏洞
    

*   蓝色部分的代码负责信息的传导, 调试清楚蓝色部分即可明白如何利用.
    

## blame

在进行`blame`操作之后, 发现该漏洞代码最初的引入在如下的`case`被引入:

*   Issue 2183923003: stubs,interpreter\] Optimise SMI loading for 64-bit targets. - Code Review (chromium.org)
    
    （https://codereview.chromium.org/2183923003）
    

所以我自己定位该漏洞应该存在了很久, 但是测试`17`和`18`年的两个`chrome`版本均不可以, 这可能和一些需要触发漏洞的优化有关. 但我依然认为`2183923003`为最初的漏洞`case`.
