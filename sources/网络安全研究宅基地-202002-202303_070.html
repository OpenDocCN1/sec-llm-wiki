于是, 让我们 更加聪明一些, 我们假设我们有如下的js代码:

function add(a, b){return a + b;}
for(let i = 0; i < 0x1000; i++){    add(1 + i, 2);}

我们对 add 函数调用了 0x1000次, 都是 {a:int, b:int}这种形式, 所以我们有充分的理由相信, 下一次的时候, add的参数接受的还是 {a:int, b:int}. 这样的话,   没准我们就可以把 add函数翻译为如下的形式(我们把它叫做优化版本):


add  a, b;  //  [+] we call it opt version

但是这个代码的准确性是依赖于 add接受的参数确确实实为 {int, int}. 我们是通过什么来判断呢? 我们通过的是它已经调用了 0x1000次都是这样. 蚂蚁竞走了十年, 它老是这样. 所以我们很难不赞成 a, b下一次依然为 {int, int}. 党相信我们, 组织也信任我们.

但是老是有邪恶分子想闹事, 比如下一次的时候, 依然可能是:

add("[+] evil", "demo");

这时, 我们优化版本的代码哑然失效. 基于此, 我们没法再去对它进行使用... 所以我们需要进行一个叫做 bailout的东西, 将优化版本的代码丢弃, 重新走上面复杂的逻辑.

note: 这里, 我没法确定我的描述一定是准确的... sorry.

  • profiling data

    • 咱觉得咱的 a总是 int, b也总是 int. 

    • 包含上述的信息的东西我们叫做 profilling data. 一般会和一个叫做 inline cache的概念相关联. profiling data用于告诉optimizing compiler, 变量的相关信息. 

  • bytecode

    • 我们把a + b这个操作翻译为Add a0, [0](这个可以用--print-bytecode进行观察得到, 以及, 这里翻译这个词其实是错误的...).

    • Add a0, [0] 就叫做 bytecode. 它用来告诉v8, 我们想要做一个加法操作. 需要注意的是, 它并不是底层的汇编代码...

  • interpreter

    • 我们将 add a0, [0]交由 interpreter处理, 在最开始的时候会生成对应上述我们所说的复杂的逻辑的汇编代码. 即判断 a 和 b 相应的类型. 并根据相应的类型进行代码处理. 

    • interpreter 执行了 n次add之后, 到达某个节点, v8会发现, add 函数怎么老是被调用哦, 是有必要给它生成一个快速的版本的了. 所以我们传递相应的 profilling data给 optimizer compiler. 进而让compiler勇敢的承担起 生成一个快速的版本的责任. 

      • 这个概念叫做 hot code. 当函数的调用到达某个条件之后, 我们标记它是一个 hot code. 并根据假设(即 profilling data), 为其生成一个优化版本的代码.  hot的意义在于我们猜测它在接下来的日子里也会被频繁调用. 

        • 频繁: 这是因为去生成一个优化版本的代码这个过程是十分耗费时间的. 但是生成之后的代码又会跑的飞快. 所以我们需要在这中间做一个取舍. 频繁保证了它值得.

        • 我们猜测: 这意味着即使 0x1000次的调用让我们有了充分的信心, 下一次的调用传入的 a, b有极大的概率满足我们的 profilling data所存储的相关信息. 但是 0x1001次的时候依然有可能打破假设... 所以我们是一个猜的过程, 而不是十分笃定的在下结论. 

      • n应该(注意, 我这里说的是应该... 即我没有确切性的把握)叫做 hot count. hot count的值应该设置为多少, 在什么值比较合适. 这主要依赖于在生成优化代码的时间和频繁的概率之间进行一个评估, 从而使得性能能够导致达到一个微妙的平衡. 不同的引擎是不一样的... 在这里, 推荐阅读我上面说的 jsc speculation一文.

  • turbofan(optimizing compiler)

    • 应该叫做 jit. 这一层将会依赖于我们的 profilling data进行假设, 即我们的 a , b老是 {int, int}. 从而生成优化版本的代码. 即 add eax, ebx

  • deoptimize

    • 一般而言, 我把 bailout, deoptimize, osr都归类为一类事务... 即使它是错误的...

    • 当我们生成优化版本的代码之后, 即 opt code. 如果我们在接下来的调用中发现 a, b不满足我们的假设(比如 add("hi", "hello")). 而我们的 opt code的运算结果的准确性又是依赖于 假设 存在的. 所以我们没法使用opt code.在这个时候,  我们需要进行 bailout. 在这个操作当中, 我们会丢弃 opt code. 转而重新运行复杂的逻辑代码.

    • 需要注意的是, bailout这个动作是十分消耗时间的... 所以我们不希望它发生... 这也是设计hot count的时候需要去考虑的因素之一. 

到了这里, 我们对 feedback, 和 deoptimize有了一个大概的判断. 接下来, 让我们做更多的事情去了解更多有关它们的细节.

接着, 我们思考一个问题, 为什么我们依赖于 0x4141和0x424242能够辨认出我们的属性 #x, #k. 其它的属性我们却认不出来了?

这是因为 0x4141和 0x424242都是整数(此处可以联想 c 里面的 int 类型来理解, 虽然它并不准确).  在 js当中, int类型的数据唾手可得, 在代码当中会频繁的出现. 比如:

关于 IR, 你可以找到很多官方的定义, 但是在这里, 我给出我的理解.

  • 我们都知道, 对于一个函数而言, 主要由两部分组成

    • 算法: 进行相应的处理, 返回处理完之后的信息.

  • add eax, ebx

    • 参数: 1, 2

    • 算法: 将 1+2的结果返回.

    • 所以我们可以认为 add指令也是一个函数.

  • 这样的话函数和指令的概念是就可以相通了.

  • 我们需要去检查 o的 map是否为 Map_X@a

    • 参数: o_map 和 Map_X

    • 算法: o_map == map_X ?

  • 这样, 我们就可以把 @a记作一个指令的形式. CheckMaps.

我们在 v8系统当中, 生成一套独有的指令系统, 只要看见 CheckMaps, 我们就认定在这个地方我们需要去做 Check map是否为我们期待的 map的操作.

这种指令我们就叫做 IR.

IR 显然具有如下的好处:

  • 统一了功能的表达

    • 所以我们可以依赖于平台的不同生成不同平台的assemble code

lazy deopt

让我们来重新看看 CheckMaps. 它的逻辑如下:

  • 如果 map 是吻合的, 那么我们就继续执行优化的代码.

  • 如果不吻合, 我们就触发 deopt, 转去使用其它更复杂的逻辑判断, 来执行 o.a这个操作.

可以看到, 我们 CheckMaps 是嵌入到opt code里面的. 这说明每次运行的时候我们都会运行CheckMaps这个 IR.

而有关 mA是否为 deprecated map, 我们显然也可以做一个类似的操作:

  • 我们将判定map是否为 deprecated map的方法抽象成 CheckDeprecatedMap这个 IR.

  • 插入到 opt code合适的位置. 每次需要的时候就检查一次.

这是一个可行的思路, 但是, 显然, 每一次检查都需要检测一次的话会相当的浪费时间. 我们最后能够移除这个 IR.

note:CheckDeprecatedMap这个 IR在 v8当中并不存在, 我只是随手举了个例子. 方便解释而已...

v8采用了另外一种机制, depedent code, 这个实现的思路和 jsc里面的 watchpoint是十分类似的. 如果有使用过 lldb的小伙伴也可以借用watchpoint命令来帮助理解.

思路的实现是这样的:

  • 首先, 在我们的 opt code里面, 我们并不插入有关 decrepted map的检测.

  • 但是我们把 mA, 即 保证准确性的map放入到一个 dependencies的类似列表的数据结构当中. 

  • 在编译完 opt code的末尾阶段, 我们取出 dependencies当中的内容, 并为其添加相应的 depedent code. 这里类似于一个callback function的概念.

  • 在后续的过程当中, 任意时候我们的mA变为 deprecated map, 我们会对 deopt对应的 jit函数.

    • 这个地方的表达是相当的不准确的, 想获取准确性的逻辑可以参考源码. 但是我说的这种情况其实是一种特例子, 一种方便解释的特例.

也就是说, 我们注册了一个回调函数, 只要mA变为 deprecated map, 我们就会触发该 callback function. 进而对 jit code进行deopt.

这里, 我们做一个小小的总结:

  • 前面那种类似由 CheckMaps进行 runtime check, 来判定是否需要 deopt的方式叫做 eager deopt.

  • 后面那种通过注册callback的形式来判断是否需要 deopt的方式叫做 lazy deopt.

而从 CanBeDeprecated, 我们知道, 如果我们tanstion chain的target map不会去添加 dependent code.

  • taggeed

  • double

double的情况我们已经讨论过了, 剩下的问题就会很明朗:

  • 存不存在某种可能性, 我们map representation的为 kTagged. 但是我们实际存储的值却是一个 double.

我们先不去考虑可能性, 我们来考虑就算这种情况发生了又能怎么样?

  • 我们先前能够把一个 JSObject当作是一个 HeapNumber的原因. 是因为我们 migrate里面有一个 cast的操作. 也即是p4nda师傅说所说的 trick.

  • 我们能进行cast的原因是因为我们的 representation里面存在一个 kDouble. 看到它们我们就能够笃定这一定是个 HeapNumber

  • 我们看到 tagged, 它是可以为任意值的. 我们就不能做出笃定的假设,  所以我并不认为这里存在类似于 JSObject::Cast的操作.

当然, 这只是一个猜测, 至少从逻辑上是讲的通的.

那么, 我们来看看可能性:

  • 我们之所以JSObject能够被误认为 double是因为smi->double(放在 chain 上的)必然会进行 in place.

  • 假设我们chain上存放的是 tagged, 那么任意的值到tagged都会采用 in place的形式. 所以我们没法通过 {any}->tagged去完成 deprecated map的构建.

  • 由于lattice的单调性, 所以我们也没法从 tagged->{any}构造 deprecated(因为没有这个关系).

所以我认为从数学上没有这种可能性的(这个地方的结论可能是错误的, 因为我的数学也不好...).

js是没有类似c里面的malloc和free的概念的, 它会自动的完成内存块的分配和回收.

这句话的意思也就是说, 我们把 malloc 和 free这种本来应该程序员去完成的工作交给语言的处理器(v8)自己去完成了. 我们把这个过程称之为垃圾的自动回收. 而处理器当中完成这个功能的组件, 我们叫做 garbage collector(gc).

我们先来想象一下我们作为一个程序员为什么要去 free一个内存.

free(p): 我们觉得p指向的这块内存再也不会被使用了, 所以我们 free该内存.

接下来, 让我们来看如下的代码:

let o1 = {x:1};  //  [+] m_1o1.x = 1.1;  //  [+] here will deprecated m_1, generate m_2

由前面的知识我们知道, 我们的 m_1会被标记为 deprecated. 对 o, 我们会用一个新的 map(m_2)来对其进行表达. 而后续假设还有类似 let o2 = {x:3}的操作, 我们都不会再去使用 m_1. 所以作为一个 c的程序员, 我们意识到这一点, 我们肯定会想调用 free(m_1)这样的操作.

而 v8怎么去完成这个操作呢?

首先, v8需要去意识到我们的 m_1再也不会被使用了.  所以 gc当中引入了两个概念:

  • dead

  • live

如果我们的对象被标记为 live, 则说明该对象还有继续存在的价值, 反之, 我们就可以回收这一块内存.

如何进行标记呢? v8对所有的对象构建了一个图. 

我们举一个浅显的例子:

let o = {x:1};let o2 = {obj:o};

如果我们能够让我们的 deprecated map不被任何的其它对象所指, 那么gc将把它标记为白色. 这样deprecated map就会被其它的对象所回收.

我们观察我们原有的 poc 代码, 发现 deprectaed map只会被如下的两个对象指向:
