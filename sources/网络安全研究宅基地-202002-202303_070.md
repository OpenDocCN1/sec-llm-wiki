*   turbofan进行相应的处理之后, 在这里, 最终会生成相应的assemble code.

这时, 我们`优化版本`的代码哑然失`效`. 基于此, 我们没法再去对它进行使用... 所以我们需要进行一个叫做 `bailout`的东西, 将优化版本的代码丢弃, 重新走上面复杂的逻辑.

> `note:` 这里, 我没法确定我的描述一定是准确的... `sorry`.

*   profiling data
    

*   咱觉得咱的 a总是 int, b也总是 int. 
    
*   包含上述的信息的东西我们叫做 profilling data. 一般会和一个叫做 inline cache的概念相关联. profiling data用于告诉optimizing compiler, 变量的相关信息. 
    

*   bytecode
    

*   我们把a + b这个操作翻译为Add a0, \[0\](这个可以用--print-bytecode进行观察得到, 以及, 这里翻译这个词其实是错误的...).
    
*   ![](../Images/48679cff4e739bdc57bd2e59bf9f6dee.png)
    
*   `Add a0, [0]` 就叫做 `bytecode`. 它用来告诉`v8`, 我们想要做一个加法操作. 需要注意的是, 它并不是底层的汇编代码...
    

*   `interpreter`
    

*   我们将 `add a0, [0]`交由 `interpreter`处理, 在最开始的时候会生成对应上述我们所说的复杂的逻辑的汇编代码. 即判断 `a` 和 `b` 相应的类型. 并根据相应的类型进行代码处理. 
    
*   `interpreter` 执行了 `n`次`add`之后, 到达某个`节点`, `v8`会发现, `add 函数怎么老是被调用哦, 是有必要给它生成一个快速的版本的了`. 所以我们传递相应的 `profilling data`给 `optimizer compiler`. 进而让`compiler`勇敢的承担起 `生成一个快速的版本`的责任. 
    

*   这个概念叫做 `hot code`. 当函数的调用到达某个条件之后, 我们标记它是一个 `hot code`. 并根据`假设(即 profilling data)`, 为其`生成`一个优化版本的代码.  `hot`的意义在于`我们猜测`它在接下来的日子里也会被`频繁`调用. 
    

*   `频繁:` 这是因为去`生成`一个优化版本的代码这个过程是十分耗费时间的. 但是生成之后的代码又会跑的飞快. 所以我们需要在这中间做一个取舍. `频繁`保证了它值得.
    
*   `我们猜测:` 这意味着即使 `0x1000`次的调用让我们有了充分的信心, 下一次的调用传入的 `a, b`有极大的概率满足我们的 `profilling data`所存储的相关信息. 但是 `0x1001`次的时候依然有可能打破假设... 所以我们是一个猜的过程, 而不是十分笃定的在下结论. 
    

*   `n`应该(注意, 我这里说的是应该... 即我没有确切性的把握)叫做 `hot count`. `hot count`的值应该设置为多少, 在什么值比较合适. 这主要依赖于在生成优化代码的时间和`频繁`的概率之间进行一个评估, 从而使得性能能够导致达到一个微妙的平衡. 不同的引擎是不一样的... 在这里, 推荐阅读我上面说的 `jsc speculation`一文.  
    

*   turbofan(optimizing compiler)
    

*   应该叫做 `jit`. 这一层将会依赖于我们的 `profilling data`进行假设, 即我们的 `a , b`老是 `{int, int}`. 从而生成优化版本的代码. 即 `add eax, ebx`  
    

*   `deoptimize`
    

*   一般而言, 我把 `bailout`, `deoptimize`, `osr`都归类为一类事务... 即使它是错误的...
    
*   当我们生成优化版本的代码之后, 即 `opt code`. 如果我们在接下来的调用中发现 `a, b`不满足我们的假设(比如 `add("hi", "hello")`). 而我们的 `opt code`的运算结果的准确性又是依赖于 `假设` 存在的. 所以我们没法使用`opt code`.在这个时候,  我们需要进行 `bailout`. 在这个操作当中, 我们会丢弃 `opt code`. 转而重新运行复杂的逻辑代码.
    
*   需要注意的是, `bailout`这个动作是十分消耗时间的... 所以我们不希望它发生... 这也是设计`hot count`的时候需要去考虑的因素之一.   
    

到了这里, 我们对 `feedback`, 和 `deoptimize`有了一个大概的判断. 接下来, 让我们做更多的事情去了解更多有关它们的细节.

*   这里, 我们对 smi有了一个清楚的概览. 这里有一个小小的问题. 用来存储 int其实 32位就够了,  剩余的4 byte其实是无用(这里是一个含糊的说法)的信息. 那么, 为什么不用低的 4 byte来存储其他值, 这样不是会节约空间吗? 我有三个猜测.

*   可能和内存对齐的好处相关.

*   

```

```

如果我们的`a`存放在 `properties`内, 我们怎么编写代码去获取值呢?

*   查询 map, 得到 a的 offset
    
*   查询对象, 获取 properties.

我们关于此函数会存在两种可能性:  

  

  

*   由于我们的 x = 1.1/y=2.2, 都是对变量的赋值,  且类型为 double， 我们假设分配的是 HeapNumber.

*   我们进行 arr\[idx\]之类的操作的时候, 会有一个 CheckBounds的 node, 用以判断我们的 idx是否在 length这个范围内.

*   但是我们前面已经证明了 0 < arr.length. 即 访问一定会在arr内. 所以我们可以移除 CheckBounds这个 node.
    
*   少了这部分代码, 这样我们的代码就能跑的更安全了.
    

*   由于我们的 x = 1.1/y=2.2, 都是对变量的赋值,  且类型为 double, 我们假设分配的是 MutableHeapNumber.
    

*   由于我们的 x, y的值都是可以 mutable的. 所以我们并不确定x, y的具体值.
    
*   所以 x != y的取值范围为 {0, 1}. 
    
*   所以 idx的取值范围为 {0, 3}.
    
*   而 arr.length为 (1, ...).
    
*   所以 idx可能比 arr.length小, 也有可能比他大.
    
*   所以我们没有理由移除该 CheckBounds

## in palce

需要注意, 这种关系是单调的. 即没有 `tagged->smi`的转换.  

> `note:` 一定要注意单调这个特性.

  

接着, 为了理清楚这层关系, 我们需要对每个元素进行讲解. 我们之前不是说嘛, 我们的 `representation`会对对应的属性的类型进行描述. 这就是 `field representation`   

![](../Images/d7326dbbb0b07f3a37aecf629d355fef.png)

*   `None:` 叫做`top`, 先不管.
    
*   `double:` `o.x`是一个 `double`.
    
*   `smi:` `o.x`是一个 `small interger`
    
*   `HeapObject:` `o.x`是一个 `!double && !smi`的 `HeapObject`, 比如 `string`之类的.
    
*   `tagged:` 叫做 `bottom`, 代表我们并不清楚 `o.x`存放的到底是什么类型, 我们假设它可以存放任意(`any`)的类型.
    

接着, 让我们来举一个具体的例子:

```

我们可以看到, 我们的关于 `a` 的 `field representation`会存在如下的更新.  

> `smi->double->tagged`.

  

`double->tagged`也就是 `@b->@c`这一步需要我们多提一下, 这里, 我们的 `o,a = {}`, `{}` 代表的 `field->representation`为 `HeapObject`, 由于我们并不存在 `double->HeapObject`的转换关系, 所以我们会采用 `double->tagged`的转换关系.

我们现在假设我们执行到了 `@c`这一步, 假设我们将关系表达为`source_fr->target_fr(fr aka file representation)`

*   此时我们的 other 为 tagged, 前面有所解释... 即 target\_fr
    
*   Is\*即为我们关系的 source\_fr 部分. 此时为 double.
    

`CanBeInPlaceChangedTo`即用来判定当我们从 `source_fr`到 `target_fr`的时候, 是否可以进行 `in place`操作.

*   如果可以进行 in place操作, 那么我们不会申请新的 map.
    
*   如果可以不可以进行in place操作, 那么我们会为属性申请一个新的 map, 而属性原本指向的 map会标记为 deprecated map.
    
*   这个地方 ISDouble()(source\_fr)为 true, other.isTagged() 为 true. 所以我们的结果也会返回 true. 我们就不会申请新的 map.
    

即 `in place`发生在如下的地方:  

*   `smi->tagged`
    
*   `double->tagged`
    
*   `heapObject->tagged`
    
*   `None->to any except double`
    

我们挑选重要的一个来理解, 为什么 `double`到 `tagged`会是一个 `in place`的过程.

*   
*   
*   

```
let o = {};o.a = 1.1;  //  [+] @a{double}o.a = {};  //  [+] @bwe |double->HeapObject| ? not exist, so we use {tagged}
```

当我们使用 `tagged`的时候, 这表明我们并不知道 `o.a`的确切类型, 所以对 `o.a`进行值的存储的时候, 我们就执行如下的逻辑判断:  

*

//  [+] o.aif(o_a.representation == tagged){  //  [+] oops! I don't know o's representation  let value = get_value_of(o_a);  //  [+] get the value of oif(value_smi_bit_set){  //  [+] the lower bit is zero//  [+] i am a smireturn value.    }else{//  [+] i am a address point to objectreturn address;    }}
```

需要注意的是, 这个地方的逻辑是错的. 即 `v8`并不采用这样的代码... 只是, 我个人觉得用这种方式来解释接下来的事情要轻松一些. 关于正确的方式会略微复杂. 所以我们稍后再谈.  

也就是说, 针对 `@b`那一步, 我们在 `v8`当中, 都是通过`address`进行存储, 而该值因为 `pointer compression`, 都是 `32bit`大小, 所以我们可以直接篡改 `representation`为`tagged`. 统一返回 `address`就可以了, 我们没有必要去更改 `map`.

这种方式我们就把它叫做 `in place`.

## turbofan

我们之前, 有讲述过一个`optimize compiler`的概念. 在 `v8`当中, 叫做 `turbofan`.

![](../Images/2bc27207870f7ac94a3ce8caf7d53bcc.png)

简单来说, 它的作用就是让我们的代码变得快起来. 在了解我们的 `v8`怎么个快起来法之前, 我们需要知道我们的 `js`为什么会变慢.

> `note:` 慢的原因总是千变万化, 所以在这里我没法去对每一种原因都做出详尽的解释, 我也没有那个能力... 所以我只能挑选特殊的点来解释. `sorry`.

首先, 我们假设我们有如下的代码:  

*   
*   
*   
*   
*   

```
function jit(o){return o.ho;}let o = {ho: 1.1};jit(o);
```

我们想想我们要获取 `ho`的值 需要去做哪些逻辑判断?

*   是一个对象吗
    

*   不是, 抛出 `type error`的异常.
    
*   是, 根据对象的相关函数来获取值.
    

我们先前不是说过嘛, 一个叫做 `hot code`的概念. 即到达那个点的时候我们就可以编译相应的代码. `v8`当中提供了两个函数来促使我们的 `code`强行的变为 `hot code`. 

*   
*   
*   
*   
*   
*   
*   
*   

```
function jit(o){return o.ho;}let o = {ho: 1.1};%PrepareFunctionForOptimization(jit);jit(o);   %OptimizeFunctionOnNextCall(jit);jit(o);
```

这样, 我们的 `trubofan`就可以将 `jit`函数编译成如下的样子:  

*   `check_o_is_object`
    
*   `get_value(o, ho)`
    

`check`那一步我们知道我们可以通过前面讲解`smi`的时候, 通过 `bit`来做. 

`however`, `get_value(o, ho)`这一部分还是做的取值操作, 听起来也没有变快...

`wait,` 还记得我们之前说的 `in object`的概念吗? 也就是说, 我们的取值可能至少会存在如下的两种方式:

*   `littel slow`
    

*   `o_addr= get_address_of_o`
    
*   `map = get_map(o)`
    
*   `properties = get_properties(o, properties_offset)`
    
*   `offset = get_offset_from_map(map)`
    
*   `value = properties[offset]`
    

*   `fast`
    

*   `o_addr= get_address_of_o`
    
*   `map = get_map(o)`
    
*   `offset = get_offset_from_map(map)`
    
*   `value = o_addr_inobject[offset]`
    

可以看到, 如果我们的 `ho` 是 `in object`的话, 那么我们其实可以通过 `偏移`来直接进行值的获取.   
`however`, 我们先前说到, 我们的`ho`也有可能不为 `in object properties`. 如果是那样的话, 这份代码就不对了. 所以我们需要去做一些事情保证运行这分`opt code`的时候, `ho`一定是一个 `in object property`. 那么, 如何保证?

我们先前说到, `map`用来存储一些信息, 自然我们可以通过 `map` 来辨别是否为`in object`.

*   我们先做一个假设, map\_X 里面的 ho为 in object properties.
    
*   于是我们可以生成这样的比较快的代码:
    

*   CheckMaps o\_map, Map\_X
    
*   if false, jmp deopt
    
*   load\_ho\_by\_offset
    
*   deopt:
    

*   do something
    

我们使用一个叫做 `CheckMap`的 `IR`来帮助我们来判定是否为 `x`的这个 `map_X`. 如果是, 那么我们就可以认为 `ho`一定是一个 `in object properties`.  

我们把 `CheckMaps`叫做叫做一个 `IR`. 

关于 `IR`, 你可以找到很多官方的定义, 但是在这里, 我给出我的理解.

*   我们都知道, 对于一个函数而言, 主要由两部分组成
    

*   参数: 用来传递原始信息.
    
*   算法: 进行相应的处理, 返回处理完之后的信息.
    

*   `add eax, ebx`
    

*   参数: `1, 2`
    
*   算法: 将 `1+2`的结果返回.
    
*   所以我们可以认为 `add`指令也是一个函数.
    

*   这样的话函数和指令的概念是就可以相通了.
    
*   我们需要去检查 `o`的 `map`是否为 `Map_X``@a`
    

*   参数: `o_map` 和 `Map_X`
    
*   算法: `o_map == map_X ?`
    

*   这样, 我们就可以把 `@a`记作一个指令的形式. `CheckMaps`.
    

我们在 `v8`系统当中, 生成一套独有的指令系统, 只要看见 `CheckMaps`, 我们就认定在这个地方我们需要去做 `Check map`是否为我们期待的 `map`的操作.

而我们的计算机内部其实是没有这个指令的. 所以我们在`v8`快结束(`generate`)的时候我们把它翻译成计算机对应的能够理解的指令就可以了.

这种指令我们就叫做 `IR`.

`IR` 显然具有如下的好处:

*   统一了功能的表达
    
*   跨平台
    

*   我们需要去构建`IR->assemble`的函数, 这一部分. 我们是可以自己实现代码的.
    
*   所以我们可以依赖于平台的不同生成不同平台的`assemble code`
    

我们对应的 `IR`会生成对应的 `assemble code`, 这意味着, 如果我们能够移除掉冗余的 `IR`. 那么, 我们的代码就能变快.  

所以我们可以给出一个粗糙的定义:

> `v8`的优化其实就是尽可能的生成更少的`IR`.

需要注意的是, 这个定义一定是不准确的. 但是确确实实是我们阅读到这里的直观感受.

好问题, 一问就问到了我们之前的知识. `deprecated map`.

我们知道, 如果我们的 `map update`, 假设它最后得到的结果不是 `mA`, 那么说明生成了新的`map`. 这就说明我们的 `mA`变成了 `decrepted map`.

所以我们只要去检测当我们对 `o`的 `map`值进行篡改的时候, 判断 `mA`是否为一个 `deprecated map`即可.

`However,`如何去进行判断.

## lazy deopt

让我们来重新看看 `CheckMaps`. 它的逻辑如下:

*   如果 `map` 是吻合的, 那么我们就继续执行优化的代码.
    
*   如果不吻合, 我们就触发 `deopt`, 转去使用其它更复杂的逻辑判断, 来执行 `o.a`这个操作.
    

可以看到, 我们 `CheckMaps` 是嵌入到`opt code`里面的. 这说明每次运行的时候我们都会运行`CheckMaps`这个 `IR`.

而有关 `mA`是否为 `deprecated map`, 我们显然也可以做一个类似的操作:

*   我们将判定`map`是否为 `deprecated map`的方法抽象成 `CheckDeprecatedMap`这个 `IR`.
    
*   插入到 `opt code`合适的位置. 每次需要的时候就检查一次.
    

这是一个可行的思路, 但是, 显然, 每一次检查都需要检测一次的话会相当的浪费时间. 我们最后能够移除这个 `IR`.

> `note:``CheckDeprecatedMap`这个 `IR`在 `v8`当中并不存在, 我只是随手举了个例子. 方便解释而已...

`v8`采用了另外一种机制, `depedent code`, 这个实现的思路和 `jsc`里面的 `watchpoint`是十分类似的. 如果有使用过 `lldb`的小伙伴也可以借用`watchpoint`命令来帮助理解.

思路的实现是这样的:

*   首先, 在我们的 opt code里面, 我们并不插入有关 decrepted map的检测.
    
*   但是我们把 mA, 即 保证准确性的map放入到一个 dependencies的类似列表的数据结构当中. 
    
*   在编译完 opt code的末尾阶段, 我们取出 dependencies当中的内容, 并为其添加相应的 depedent code. 这里类似于一个callback function的概念.
    
*   在后续的过程当中, 任意时候我们的mA变为 deprecated map, 我们会对 deopt对应的 jit函数.
    

*   这个地方的表达是相当的不准确的, 想获取准确性的逻辑可以参考源码. 但是我说的这种情况其实是一种特例子, 一种方便解释的特例.
    

也就是说, 我们注册了一个回调函数, 只要`mA`变为 `deprecated map`, 我们就会触发该 `callback function`. 进而对 `jit code`进行`deopt`.  

这里, 我们做一个小小的总结:

*   前面那种类似由 CheckMaps进行 runtime check, 来判定是否需要 deopt的方式叫做 eager deopt.
    
*   后面那种通过注册callback的形式来判断是否需要 deopt的方式叫做 lazy deopt.
    

到这里, 我们就可以看下面的代码逻辑(`src/compiler/compilation-dependencies.cc`):

![](../Images/305b984d306b314b1007bf162e83580a.png)

可以看到如果说我们认定此次 `transtion`操作的 `target_map`, 是永远不会被 `deprecated`的. 那么我们就返回一个 `nullptr`.   

相反, 如果是可能会 `deprecated`的, 我们就必须给他添加一个 `TranstionDependency`, 在后续会放入到 `dependencies`当中, 并通过 `dependent code`来保证其安全性.

这里的逻辑非常的简单, 想像一下, 如果它的 `target map`不可能`decrepted map`, 我们还给他注册相应的回调, 那且不是脱裤子放屁?

所以结合一下先前的结论, 再结合我们到现在这里的结论,我们可以做出如下的推断.

> `v8`会通过 `dependent code`来保证生成优化代码的安全性. 而是否 需要添加 `dependent code`有由 `CanBeDeprecated`来决定.

我们前面说过, 如果一个 `transtion tree`上, 我们全是 `kDouble`, 我们在这里会返回 `false`, 也就是说, 不会有`dependent code`来保证它的安全性.

而我们之前也推断过, 这个假设是错误的, 事实上, 我们在后续可以让他`deprecated`.

## fake object primitive 01?

周末晚上的时候我突然想起周五的时候和前辈说的另外一个点子, 我觉得是具有可能性的, 于是就此开始了我的悲哀的人生:

![](../Images/b41d68fe70ad2dadbc39aed0766d3792.png)

是这样的, 在我的利用观里面, `type confusion`和 `use after free`是十分的类似的. 我们可以来重新理一下这两个概念:  

*   如果一个内存块是 `free`的. 我们假设极端的情况下, 我们可以通过任意对象来对其占位, 这两个对象的 `class(type)`不相同的话, 那么我们就得到了一个 `type confusion`.
    

所以我们可不可以将这个漏洞转化为`use after free` 再来转换为其它的`type confusion`呢? 

我们前面提到过一个叫做 `deprecated map`的概念, 在中文的名字里面是丢弃的意思. 但是我们的 `jit`做的假设里面是并没有意识到这一点的, 所以, 这就引发了我如下的猜想:

*   可不可以通过某种方式, 让这个 deprecated map变成类似于 free的内存.
    
*   然后通过类似于堆喷的方式让其它的 map(记作 map\_confusion)来占位这个 deprecated map的内容.
    
*   我们的 jit做的假设没有意识到这一点, 所以我们存储的内容是{double, double }, 但是map存的却是 map\_confusion.
    
*   从而导致更加自由的混淆.
    

上面提到的所有内容都涉及到了 `内存`的分配. 而 `v8`的内存分配又和 `garbage collector`息息相关. 由于之前我并没有仔细的去看过 `garbage collector`的概念. 所以我决定先去学习有关 `gc`的概念.  

关于 `gc`, `大宝师傅`在他的 `blog`Edge Inline Segment Use After Free | Project Moon (https://blogs.projectmoon.pw/2018/09/15/Edge-Inline-Segment-Use-After-Free/)里面推荐了如下的书籍:

*   <<垃圾回收的算法与实现>>(https://item.jd.com/12010270.html)
    

本来是在我的待读书单里面的, 但是我的百事又好像刻不容缓, 所以我主要参考的是如下的文章, 进行快速的阅读(有时间的话我还是强烈推荐可以阅读上面的书籍).

*   High-performance garbage collection for C++ · V8
    
*   Trash talk: the Orinoco garbage collector · V8
    
*   Concurrent marking in V8 · V8
    
*   内存术语  | Chrome DevTools  | Google Developers
    

由于这个方法本身是失败的, 以及 `gc`我自己了解的也不是很清楚...很容易误人子弟,  所以这里我不会对 `gc`进行详细的讲解. 相反, 我只会去讲和我的利用思路相关的部分. 类似于一种信息的提炼, 而对 `v8 gc`本身感兴趣的小朋友可以自行查阅上述的文章.

首先, 我们来想想之前的我们任课老是告诉我们的一个信息:

> `js`是没有类似`c`里面的`malloc`和`free`的概念的, 它会自动的完成内存块的分配和回收.`   `

这句话的意思也就是说, 我们把 `malloc` 和 `free`这种本来应该程序员去完成的工作交给语言的处理器(`v8`)自己去完成了. 我们把这个过程称之为垃圾的自动回收. 而处理器当中完成这个功能的组件, 我们叫做 `garbage collector(gc)`.

我们先来想象一下我们作为一个程序员为什么要去 `free`一个内存.

> `free(p):` 我们觉得`p`指向的这块内存再也不会被使用了, 所以我们 `free`该内存.

接下来, 让我们来看如下的代码:

*   
*   

```
let o1 = {x:1};  //  [+] m_1o1.x = 1.1;  //  [+] here will deprecated m_1, generate m_2
```

由前面的知识我们知道, 我们的 `m_1`会被标记为 `deprecated`. 对 `o`, 我们会用一个新的 `map(m_2)`来对其进行表达. 而后续假设还有类似 `let o2 = {x:3}`的操作, 我们都不会再去使用 `m_1`. 所以作为一个 `c`的程序员, 我们意识到这一点, 我们肯定会想调用 `free(m_1)`这样的操作.

而 `v8`怎么去完成这个操作呢?

首先, `v8`需要去意识到我们的 `m_1`再也不会被使用了.  所以 `gc`当中引入了两个概念:

*   `dead`
    
*   `live`
    

如果我们的对象被标记为 `live`, 则说明该对象还有继续存在的价值, 反之, 我们就可以回收这一块内存.  

如何进行标记呢? `v8`对所有的对象构建了一个图. 

我们举一个浅显的例子:

*   
*   

```
let o = {x:1};let o2 = {obj:o};
```

我们可以简单的如下的形式表达他们的关系:  

`o2->o`: 代表`o`在 `o2`当中被引用.

有了这个概念之后, 假设我们的源码更加复杂一些, 我们就能够得到类似于如下的图:  

![](../Images/6a9a3e91222501e0fc5b36422fa65f32.png)

`v8`采用了三种颜色来表示对象的`live or dead`的相关信息.

![](../Images/f2c246c242484ae41ace985e0e13b3e3.png)

我们可以看到我们的 `white`, 对应的其实就是 `dead`的概念. 只要我们的一个对象被标记为 `dead`, 我们就会回收该内存.  而通过上述的描述, 我们很容易得到如下的结论:

如果我们能够让我们的 `deprecated map`不被任何的其它对象所指, 那么`gc`将把它标记为白色. 这样`deprecated map`就会被其它的对象所回收.

我们观察我们原有的 `poc` 代码, 发现 `deprectaed map`只会被如下的两个对象指向:

*   
*   
*   
*   

```
    %PrepareFunctionForOptimization(jit);    jit(mapX_o);    //  [+] feedback    %OptimizeFunctionOnNextCall(jit);    jit(mapX_o_1);  //  [+] compile
```

这意味着, 只要我们只要能够通过 `migrate`, 取消两个指向. 那么我们就能够通过 `gc`会收该内存块:  

*   
*   
*   
*   
*   

```
//  run with --expose-gcmapX_o.smi;  //  [+] migratemapX_o_1.smi;  //  [+] migrategc();jit(mapx_o_2);  //  [+] @a: would u use a free memory
```

`However`, 在完成了 `deprecated map`的释放之后, 我发现`v8` 将再也不会触发相应的漏洞.  

通过调试分析, 一番操作之后, 我意识到, 我的 `jit`函数 被 `bailout`了. 即使我传入的 `map`与之前的传入的 `map`保持了高度的一致.

而进行 `bailout` 的具体指令在此处:

![](../Images/45d63624f7a3b2d929e53d6502473bc8.png)

听起来, 这会和一个叫做 `CompileLazyDeoptimizedCode`的概念相关. 在对相关的概念进行搜索之后, 我找到了我想要的答案:

*   CompileLazyDeoptimizedCode - Google 搜索
    
*   An internship on laziness: lazy unlinking of deoptimized functions · V8
    

在 `v8`当中, 针对 `jit` 的函数, 我们通过给其设置一个 `marked_for_deoptimization`标志位来判定下一次运行该 `jit` 的时候是否需要 `bailout`. 这个问题的关键就变为了:

*   如果我们的 `deprecated map` 被`gc`回收, 该标志位会被置位.
    
*   如果不被回收, 就不会被置位.
    

上述的行为是可以通过 `windbg`动态调试观察得到的. 

大多数时候, 对于浏览器的学习者而言, `bailout`都不是一件好事情. 所以我显然需要知道为什么这个 `bit`位在`gc`中会被`free`.

也有不是的情况. 比如 `saelo`前辈写一个 `spidermonkey`的利用的时候, 还有大宝师傅所说的`深入浅出jsc(这个我没有听过, 但是看公告应该是和 bailout相联系的.)`

在对 `jit` 函数对象设置条件断点后, 最终我定位到了如下的函数:

![](../Images/1a2002b0ac5dca9130a49c38a489e4e8.png)

当我们的 `object`位 `white(!BlackOrGrey)`的时候, 我们会调用 `SetMarkedForDeoptimization`对 `bit`位进行设置. 

所以, 我们就得到了如下的矛盾:

*   如果想利用这个漏洞, 我必须调用 `jit` 函数, 所以我的标志位不能为 `1`.
    
*   而如果我想要利用 `uaf`, 我的 `object`必须为 `white`, 这样标志位肯定又必定为`1`.
