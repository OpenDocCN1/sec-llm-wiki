“第五篇：F5/NGINX与云原生之PaaS平台暴露”


在当前，越来越多的金融机构开始建设容器化平台，部分大型银行甚至已经试水将部分业务部署至容器化平台。在容器平台体系中，以Kubernetes这样的容器为例，容器平台的网络以及服务的最终对外暴露一直以来都是一块较大的挑战，如何选择符合企业的网络模型，采取何种方式将服务对外暴露都是容器化平台建设的考虑重点。在此我们想以Kubernetes为例探讨一下容器化编排平台下的网络与服务暴露方法，主要从以下几个方面进行：

  • K8s原生服务发布方案以及其优缺点

  • K8s如何与F5集成


K8S原生服务发布方案


Nodeport（非ipvs）

Nodeport是指通过在node节点上的对外物理（虚拟）网卡上的IP暴露一个高端随机端口（默认30000-32767）作为服务对外接入的端口，支持TCP,UDP协议，容器外部访问者访问NodeIP:port，连接经由node底层操作系统的iptable实现转发至pod网络。这种服务暴露的方式主要特点是：

  • 在多个node节点上同时暴露相同端口，服务具有多个入口点；

  • 在同一个node节点上不能同时暴露两个相同的如80这样的服务端口；

  • 使用iptables，在暴露大量服务的场景下，会创建很多iptables 规则；

  • 连接经由node 1节点进入，如后端pod在另一个node节点上，则需要利用iptables规则再次转发，经由目标节点的iptables规则转入最终pod网络；

  • 属于纯L4层连接控制，无任何L7策略；

  • 使用iptables实现非常简单的接近于RR算法；

  • 不支持网络隔离；

  • 如果node本身是基于openstack等的VM，其网络是租户的隔离vpc网络的话，采用nodeport直接暴露将更加困难，需通过外部Proxy来协助实现；

  • 除非节点本身是公网地址，否则这些nodeport发布的服务如果需要从互联网访问，那么需要外部设备来进行NAT地址映射，需要与外部NAT设备进行动态对接，这带来了额外的工作，对防火墙规则的设定也将产生极大的挑战；

  • 除非pods本身已经支持了SSL能力（但显然容器化的本质决定了这不该是容器内进程该实现的），否则HTTPS访问依旧需要外部来实现。

同时，在实际生产环境下，该方案还将导致大量的交叉转发流量，进一步增大iptables负担。

Nodeport的最大优势在于属于K8S原生方案，用户只需在服务发布时指明为nodeoport方式即可，尽管对网络、系统管理人员来说nodeport方式并不友好，但对应用服务发布者来说却是非常的简洁，因此在小规模k8s集群及服务数量不是很大的场景下，nodeport依然是一个不错的选择。从实际的用户部署使用看，结合上述nodeport的缺点，一般来说在nodeport的使用往往需要一定的外部搭配：

  • 在内网环境下，可使用内网DNS配合，将服务的nodeport IP以及端口注册到DNS中，外部应用系统通过查询DNS获取服务IP以及port实现GSLB。

  • 在对互联网发布场景下，通过在集群外部外置额外的负载均衡器，将node的IP:port作为外部LB设备的backend资源实现负载均衡，由外部负载均衡器最终对外提供统一的服务接入点，同时外部负载均衡器还可以实现诸如SSL卸载、L7层负载均衡策略等。对于AWS，Openstack等环境，可以通过在k8s中设置服务时候指定相关的Loadbalancer type定义实现与ELB/LBaaS的联动。其它环境，将在后面详细讲解Nodeport如何与F5进行联动集成。

  • 有部分用户通过将service IP地址段在外部网络中设定路由，使得外部网络知晓Service IP网络在哪里，这种方式在小型网络环境下可行，但是对于大型企业来说，策略上不太可行，会加剧外部网络管理员工作负担以及防火墙策略复杂性。


Ipvs


为解决上述iptables方式带来的性能问题，k8s社区于1.8版本后开始引入ipvs特性。Ipvs源自于lvs，是一款基于TCP/UDP协议的纯四层软负载均衡，其特点基本完全等同于lvs，具备较高的四层转发性能，已合并进入linux内核作为模块提供。K8s使用IPVS，完全兼容了之前的nodeport发布方式，对应用发布者来说是透明的，对系统管理员来说只需在配置kuebe-proxy时指明启用ipvs即可。K8S中的ipvs主要特点行为如下：

  • 在每个node几点上创建一个虚拟网卡如kube-ipvs0，网卡状态为down，其上绑定的IP地址都不响应arp；

  • 将K8S Service IP及端口绑定在上述虚拟网卡上；

  • 不支持网络隔离；

  • 对以nodeport 类型发布的服务，将node IP及相应端口绑定在上述虚拟网卡上；

  • 类似lvs的FullNAT模式，即执行目的地址和源地址转换，其中源地址转换依旧由iptables处理；

  • 不再创建数量巨大的iptables 规则；

  • 数据包进入node节点后，数据包直接被ipvs发送到endpoints上，从而绕过iptables；

  • 跨node节点通信，ipvs借助flannel等帮助实现k8s endpoints间互通的方式实现。

（Servic IP）


（Nodeport方式发布，节点IP与端口被配置到ipvs中）


相比于非ipvs模式，该方式最大的优势在于提高了性能，使得大规模节点、服务变得可能。集群外访问，只需要外部网络能够将相关服务IP（连接中的目的IP）路由到node节点的宿主IP即可，剩下的均交由ipvs进行转发和处理，相当于在每个node节点内置了一个四层负载均衡器。整体来说ipvs与非ipvs模型来说没有其它本质区别，外部配合上与非IPVS方式也完全一致。要注意的是ipvs模式可能会与calico网络方案冲突。


Host network


Host network网络模型是让pods直接共享宿主机（node节点）网络，就像vm桥接到物理网卡一样。这样的好处是无需再考虑复杂的pods网络内外互通问题，网络变得非常的简单。这种网络的特点是：

  • 同一个端口服务在同一个node上只能存在一个pod；

  • 同一个deployment中，replica副本数量不能多于node总数量，否则将无法调度；

  • 不同deployment中，相同端口pod的总数量不能多于node总数量，否则将无法调度；

  • K8s可以感知到不同pod在机器上的端口冲突，但不能感知到与node宿主机本身端口的冲突。

Host network是一个非常简单的网络模型，从网络管理角度运维成本低，但是对应用部署人员来说不够友好，会导致经常发生pods数量达不到设定值问题发生。同时pod在不同宿主机上漂移后，要求集群内的节点必须满足有不存在pod端口冲突的可调度机器，否则调度将失败，同样pod一旦发生漂移，对外暴露的IP地址就会发生变化，这要求外部网络必须能够感应到这样的变化。


Host port


Host port与host network类似，都是将容器、pod端口直接暴露给node宿主机，不同点在于，host port是从容器级别直接映射到宿主机网络，而host network是从pod级别映射到容器网络其它方面与host network并无不同。


Loadbalancer


Loadbalancer类型被主要用于云环境下的LB，不是特指企业自身购置的LB设备。可以直接配合nodeport来使用，通过将相关nodeport信息注入到外部Loadbalancer中，直接实现外部LB，支持AWS,Azure,GCE,Openstack。该方案可以解决nodeport中多个服务入口的对外统一，从而可以接入来自外部互联网的访问。缺点是每个service都需要一个公网IP。


Ingress


通过上述各种方案的分析，会发现上述方案中有几个关键的痛点：

  • 不支持更加复杂的7层访问策略；

  • 需要一定的外部解决方案辅助。

Ingress恰恰是用来解决上述问题的，Ingress是k8s中的一种资源对象，其主要负责定义更加复杂的7层应用路由策略，例如基于Hostname，URI策略分配，SSL终结、会话保持等配置。Ingress本身并不用来具体的proxy流量，因此需要有一个具体的proxy来执行这样的工作，例如 nginx，haproxy，traefik，AWS ALB，linkerd以及F5 BIG-IP等，但是这些proxy本身如何去获取相关服务配置及动态更新配置呢? K8s通过ingress controller实现对平台API的ingress、service、endpoint、secret、node、configmap对象不断监控，用来发现相关对象并动态配置到上述proxy中。然而上述这些proxy依旧是运行在pod中的，这就像一个鸡和蛋的问题一样，我们又回到了如何把pod服务暴露出来的问题。在Ingress的一般解决方案中，通过以下几种方式实现这样的边界服务接入：

  • 通过Dameonset 将所有proxy pod的服务在每个node节点上部署唯一一个实例；

  • 通过lable 控制将相关proxy pod部署在专用的node节点（称之为Edge nodes）上作为边界服务接入节点。

通过hostnetwork或hostport的方式将服务端口直接映射到node节点的网卡上，从而实现外部访问的接入。为了解决鸡和蛋的问题，要么依旧在通过加一层外部LB来负载，要么直接将专用的Edge node配置相关公网IP并使用keepalive等技术将多个Edge node构建为高可用集群。

同时也可以看出来，这样的方式，依旧决定了同一个node机器上极易出现服务端口冲突的问题，或者说，我们不得不在很多时候复用一套proxy来接入所有服务，这对需要更多隔离需求的场景来说会是比较大的挑战。另外，无论ingress支持哪些高级L7策略，最终需要具体的proxy来实现，也就是说proxy的实现决定了最终L7策略功能实现，比如会话保持必须要用Nginx的商业产品Nginx Plus来实现。

对于此类software方式的Ingress解决方案来说，如何避免频繁的reload配置都是一个极其重要的考量，除了使用K8S中默认的开源Nginx的Ingress Controller外，还可以使用Nginx Plus，Nginx Plus支持通过API接口动态管理配置且提供了开源版本没有的主动应用健康检查、集中管理与运行状态可视化等能力。

F5 BIG-IP 同样可以作为Controller来使用，作为kubernetes官方文档推荐方法，通过使用Container Connector监控k8s中的Ingress资源对象，自动化将Ingress规则转化为F5配置，容许企业将BIG-IP产品与容器化平台集成起来。详细可参考：

https://kubernetes.io/docs/concepts/services-networking/ingress/



F5与PaaS平台的集成


通过上述各种方案的分析，可以看出在大部分场景下依旧需要使用外部LB设备来解决k8s本身服务暴露方面的诸多问题。如果企业已经在使用F5产品，则可以通过使用F5 Container Connector这一解决方案来实现容器平台对外服务的暴露，这样企业可以充分利用现有F5实现更加丰富的应用交付功能，更多高级LB算法、高级健康检查、更好的SSL性能处理、更灵活的7层LB策略和更好的WAF安全特性，网络、角色、配置隔离等特性。使容器平台内的业务一样可以充分拥有和非容器平台一样的应用交付特性，同时也保持了运维体系的一致性，以前的运维方式不会因容器平台而发生过多改变。

(F5 BIG-IP扩展了容器平台环境下的业务服务治理能力)


本篇将通过介绍F5与主流容器平台的集成方案，包括k8s，openshift，Cloud Foundry，Mesos/Marathon。

F5提供Container Ingress Services产品，其作为一个容器运行在平台内部，该产品亦叫做big-ctlr或CIS，通过监听平台API实现将服务自动化配置到外部F5产品上。


K8s


在与k8S的集成上，支持Configmap或Ingress方式的服务部署。以下将主要描述在网络上方案上，F5如何与容器平台集成。

F5 CIS拥有两种网络对接模式，可通过pool-member-type来设定，这两种形式是：nodeport模式和Cluster模式。

Nodeport 模式

这是CIS的缺省模式，在这种模式下，F5对node IP:port进行负载均衡，连接/请求在进入到node后，交由node本身的kube-proxy来处理，比如通过iptables或ipvs。此时产生的F5配置将会类似这样：

此时，F5只会看到Node的信息，并不会感知到kube-proxy背后pods的变化情况，在健康检查上则采取的是针对L7服务的检查以保证服务本身可用而不是Node本身可用。正如上述nodeport等模式的分析，iptables本身是网络性能瓶颈点，且此时L7方面的策略会受到限制。但是，这种模式是最简的模式，F5只要与Node节点的IP能够通信即可。

Cluster模式

此模式下，F5的pool资源将直接是具体的endpoints信息，这解决L7等策略限制的问题，因而可以完全使用Ingress这样的定义，或使用AS3来实现更加复杂的配置，此时的Pool配置类似如下：
