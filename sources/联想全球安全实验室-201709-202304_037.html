什么是OAuth2.0？

OAuth2.0是一套常用的行业授权标准，在移动端App、Web平台提供一种安全、便利的授权方式，打破了传统的账号密码登录方式。OAuth2.0的使用是很常见的，比如使用微信、微博账号登录一些第三方应用。由于微信、微博这些应用拥有巨大的用户量，第三方应用使用OAuth2.0可以简化自身用户注册登录逻辑，也便于双方应用引流用户、扩大影响力，同时也提升了用户体验。

OAuth2.0工作方式

OAuth2.0协议由三部分组成：客户端、用户、OAuth服务提供方。

第三方应用：想要访问用户数据的第三方移动客户端或Web服务（以下简称：客户端）。

用户：数据的所有者，比如微信账号的所有者。

OAuth服务提供方：控制和管理用户数据的平台、应用等，提供API实现用户身份认证和授权、用户数据的访问。


OAuth2.0共有4种授权方式（grant type）：

Authorization Code grant type：

这种授权模式需要第三方应用先申请authorization code（授权码），在获得授权后申请access token（访问令牌）。access token的传递通过后端实现，前后端分离，安全性最高。

实线部分表示前端传输；虚线部分表示后端传输


第一步：客户端触发授权访问用户数据的请求，请求中涉及参数：



client_id：客户端身份标识，是OAuth 服务提供者为注册的第三方应用生成的唯一标识。

redirect_uri：成功授权后的回调地址，在OAuth服务向客户端授予Authorization code时，code会被发送到这一参数定义的url中。

response_type：声明使用的授权方式（grant type），对于Authorization code来说此值固定是code。

scope：声明客户端想要访问的用户数据集合。

state：客户端状态值。是一个唯一且无法猜测的数值，和客户端的当前session绑定。成功授权回调时会带上这个参数，用于防范CSRF攻击。




第二步：OAuth 授权服务器收到初始授权请求后，会把用户重定向到登录页，用户登录并根据请求访问的数据范围确认授权。


第三步：用户同意授权后，OAuth授权服务器会生成authorization code，通过Get请求重定向到redirect_uri实现将authorization code传给客户端。


第四步：客户端收到authorization code后，客户端会向OAuth授权服务器请求access token，由于是后端传输，攻击者很难窃取access token。在这一步中，除了需要传递client_id，还要需要提供client_secret和grant type。



client_secret：在注册OAuth服务时分配，保存在客户端服务器，用于OAuth服务对客户端身份的认证。

grant_type：告知客户端使用的授权方式。




第五步：OAuth授权服务器验证客户端获取access token的请求，验证通过返回access token和相关其他信息。


第六步：客户端使用获得的access token向资源服务器请求用户数据。


第七步：资源服务器验证token有效，根据scope定义的数据范围返回相关数据。


Implicit grant type：

这种授权模式相比Authorization code的授权方式简化了过程，整个过程都在前端实现，导致access token存在泄露的风险，安全性略差，一般应用在安全性要求不高的情景比如问卷调查。


第一步：客户端触发授权访问用户数据的请求，和authorization code的区别在于response_type参数必须是token。


第二步：OAuth 授权服务器收到初始授权请求后，会把用户重定向到登录页，用户登录并根据请求访问的数据范围确认授权数据的访问。


第三步：用户同意授权后，OAuth授权服务器会生成access token，通过Get请求重定向到redirect_uri实现将access token和其他相关数据传递给客户端。access token作为url的一部分，不会直接发给客户端，客户端需要通过脚本获取这一字段并储存。


第四步：客户端使用获得的access token向资源服务器请求用户数据，和authorization code 方式不同，这一步通过前端实现。


第五步：资源服务器验证token有效，根据scope定义的数据范围返回相关数据。


Resource Owner Password Credentials grant type：

这种授权模式中，用户需要向第三方服务提供自己的账号和密码，减少额外的转发，应用场景需要客户端和OAuth服务提供者高度的信赖关系。


第一步：用户向客户端提供账号和密码。


第二步：客户端利用用户提供的账号和密码信息向OAuth授权服务器申请换取访问资源的access token。


第三步：OAuth授权服务器确认用户信息后，返回access token.


Client Credential type：

这种授权模式中，客户端以自己的名义向OAuth服务申请授权，用户向客户端进行注册。严格来讲，并不存在用户授权行为，可能存在多个用户共用同一个token的情况。需要客户端和OAuth服务提供者更高度的信任，应用场景需要客户端在OAuth服务端存在可控资源。


第一步：客户端向OAuth授权服务器传递client_id和client_secret发起授权请求，申请获取access token。


第二步：OAuth授权服务器确认客户端合法性后，返回访问access token。


OAuth2.0常见安全问题

OAuth授权方式的漏洞成因一方面是OAuth的配置非常模糊且灵活，每种授权方式的配置方式大多数都是灵活可选的，其中包括一些确保用户数据安全的配置。这里的配置既包括客户端的安全配置，也包括OAuth服务自身的使用配置。另一方面OAuth自身并不具有安全特性，导致他的安全性完全依赖于使用者的配置方式以及使用一些额外的安全技术。


1. 错误使用Implicit grant type

Implicit grant type中所有请求会通过浏览器暴漏给攻击者，安全性差，因此不建议兼具前后端的Web应用使用。在使用Implicit grant type时，恶意用户可以抓包篡改发送到后端的认证参数，如果没有正确检查access token是否和请求中其他参数相匹配，可能导致权限泄露。


2. 客户端配置缺陷导致CSRF

在OAuth授权过程中，state不是必选参数，因此很多时候会被忽略或不验证，导致第三方应用容易受到CSRF攻击。正确使用和校验state参数，客户端在发起请求时带上state参数，OAuth授权时会将state参数和access token一起返回给客户端，证明回调请求是来自客户端发起的授权请求。如果没有这个参数，客户端无法得知回调请求是否是自己发起的。

尤其很多客户端都有账号密码和其他账号登录多种登录方式，使用其他账号登录时会涉及OAuth授权进行账号绑定。在此过程中，恶意用户可以自己发起授权请求，再通过CSRF攻击诱导其他用户浏览器完成授权，实现绑定他人账号登录客户端。


3. redirect_uri校验不足导致authorization code或access token泄露

用户同意授权后，authorization code或access token会通过Get请求传递给redirect_uri定义的回调地址。如果OAuth服务自身没有校验redirect_uri，恶意用户可以控制这一参数将回调请求传送到自己可控的地址，从而获得他人的authorization code或access token。

4. scope认证缺陷

scope参数用于定义客户端想要访问的数据范围。在authorization code授权方式中，如果OAuth服务端没有根据初始授权请求的scope参数验证后续code/token申请，可能导致客户端在申请code/token时，增加scope范围，获取用户未授权的数据。

 

5. 注册用户未认证

在使用OAuth完成认证时，第三方应用都默认OAuth服务提供的用户数据是正确的。然而，一些OAuth服务的提供者在用户创建时不会对全部的用户数据进行校验，导致第三方应用使用的授权信息可能并非是经过OAuth服务验证过的合法信息。因此，在一些第三方应用没有对获取信息进行二次验证的情况下，恶意用户可以使用OAuth服务提供的虚假信息完成非法认证。


6. 客户端凭据泄露

client_secret是客户端的凭证。在authorization code的授权方式中，client_secret存在客户端服务器通过后端传输难以窃取，降低了access token被劫持的风险。但在一些原生客户端，client_secret只能前端获取，很容易被劫持，用于后续窃取access token。


如何安全使用OAuth2.0

安全使用OAuth2.0需要OAuth服务提供者和第三方应用共同使用安全配置和一些安全验证手段。


对于OAuth服务提供者：

1. 强制第三方应用使用state参数。

2. 要求客户端针对redirect_uri参数注册白名单，并对请求中的uri进行精准匹配，避免使用模式匹配的方式引入校验缺陷。

3. 检查请求数据的范围是否和最初授权时范围相匹配。


对于第三方应用：

1. 严格按照规范流程开发使用OAuth2.0授权方式，尽量使用Authorization code的方式，前后端分离。

2. 规范使用state参数防范CSRF类攻击。

3. 在申请authorization code或申请access token阶段都要传递redirect_uri参数，防止redirect_uri被中途篡改。

4. 正确使用client_secret。在无法保证client_secret机密性的情况下，可以使用PKCE机制防止access token泄露。
