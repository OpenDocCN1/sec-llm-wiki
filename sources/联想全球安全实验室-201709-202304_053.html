How to use CAPTCHA and SMS verification code correctly

The reason of why I am writing this article, is because in the last 6 months I tested different web pages and applications, and I found a common mistake in most of them, the wrong use of SMS verification code and CAPTCHA. In this article, you are not going to find the technical details of how to implement it, instead I will explain the principles behind them, in which situation you should use which of them, the logic of how to use it right, and some recommendations.
CAPTCHA (Completely Automated Public Turing test to tell Computers and Humans Apart)
As his name indicates, is a test that help a computer to distinguish if a user is a human or is a machine, in this case machine means, any sort of automatic procedure or program.
This test is based in the next premise: if one client can’t solve a puzzle (read a distorted set of letters in one image), means the client is a machine, but if the client solves the puzzle that means is a human. The purpose is to adopt a different behavior if the client is a machine or a human, for example, if the client is detected as machine, don’t allow him to create a user, or send an email, but if is detected as human, he can perform the intended action.
Figure 1: CAPTCHA
Since the CAPTCHA code was invented in the 2000, and because of the new techniques in image processing, AI and security, new implementation and models appear, always trying to increasing the levels of difficulty, all in order to preserve the CAPTCHA functionality status quo. 
Figure 2 different CAPTCHA versions
From the information security point of view, when a web or application should use CAPTCHA?
The general answer is, every time you don’t want a machine perform an automatic job.
A more specific answer is:
1. To prevent brute force attacks.
2. To prevent/reduce spam delivery (SMS, e-mails, chat or forum messages).
3. To prevent crawling.
4. To prevent the indiscriminate use of computing resources.

SMS verification code
As his name indicates, is a way of verification using a code sent via SMS, can be numerical or alpha numerical, also have different lengths, but usually is from 4 to 6 characters. Nowadays we all already faced this way of verification in different places, usually appear in services registration, or in the moment of use a specific functionality that can lead in to potential legal problem, some examples are: when send emails from disposable emails, when buy or exchange bitcoins, etc.
The main functionality of this technology is as his name indicates verify a person, because theoretically speaking one phone number only belongs to one person, like the social security number or id number, then if the system sends a message to that phone number only that person will receive it.
 
Figure 4 SMS verification code 
From the security stand point of view, a web or application can use SMS verification code in the next cases:

1. As second factor authentication (a good idea, always two are better than one).

2. As trail, in case of LEA (Law Enforcement Agency) or a forensic procedure need it.

Out there exist other two cases where this technology is used, the first one is for password recovery, the second as a quick login; I do not, I repeat, I DO NOT recommend these two uses! because the relationship one to one between user and phone number is only temporary, just think what happens when one user change his phone number? The answer is, the company assign this phone number to another person, in this situation the new owner will be able to access to the user account. Also, the use of these two methods makes the user vulnerable to the sim swapping attack.

Logical Implementation
After talking about the functionality of each of the technologies and what they are intended for, now I will talk about the logic to implement those, in other words, the secure logic way of implement these technologies. By the way I found this mistake a lot!!!!
The next flowchart, is the representation of login process that use SMS authentication code as second factor authentication. The reader can exchange the SMS authentication code for other technologies like software token, CAPTCHA code, also can change the login process for other process that use those technologies.
Figure 6 Correct Logic implementation of code[1] diagram
As you can see in the diagram, after input the login credentials plus the second factor authentication, the first step you have to do is verify the secondFactor_code, then if the result of the verification is true, the process will continue to the next step (verify username and password). If the result of the verification is false, discard the request, send back the “wrong SMS code” error to the client, and finish the procedure.
Other recommendations
As I said before, I found the logic implementation mistake many times, but is not the only one, in this part I will touch how to correct some of the other mistakes I saw while testing those technologies.
1. These codes (CAPTCHA/SMS authentication code) are only for one use. What i mean is, you can only use it once, then if you used but your password or username is wrong or any other problem, this code should not be valid, then the user should use one new.
2. Those code [1] should have expiration time. What I mean is, if you don’t use the code in the predefined time after his generation, the code should be invalid even if you didn’t used.
3. The code [1] should be unrepeatable, what I mean is, the codes should repeat themselves as far as is possible, to prevent the re-usability problem.
4. Limit the number of codes requested by day and time for one user, this is specially for SMS authentication codes.
5. Never send the code [1] answer to the client, the verification of the code correctness, should be done in the server side, never in the client side. 
The recommendation 1,2,3 and 5 must be fulfilled, that means if one of the recommendations fail, the security of the CAPTCHA or SMS verification code is compromised.  
Summarizing
1. CAPTCHA’s are to prevent automatic jobs, for example brute force attacks.
2. SMS authentication codes are for LEA and user authentication, but use it carefully, a phone number can belong to a different person in different time.
3. Before process a request, prove the correctness of the code [1] , only if is correct, process the request; If is false, discard the request and send back one error.
4. The code [1] validation process should be performed only in the server side.  

[1] CAPTCHA code / SMS authentication code.
