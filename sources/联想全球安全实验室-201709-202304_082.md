# SESSION、TOKEN与JWT安全解析

**0x00 前言**最近JWT很火，于是研究了一下其原理和安全性问题。这里把SESSION和TOKEN相关安全理解也一起分享下，会更清晰一些。

> **水能载舟，亦能覆舟。我们要正确的使用它，绝不能对安全掉以轻心！**

  
**0x01 HEADER和COOKIE**严格地说，标题中提到的SESSION、TOKEN、JWT这三个并不是一类事物，他们之间没有什么可比性，放在一起也没有什么意义。只是在日常工作中总是会一块提及这三个词汇。所以要分别说清这三样东西呢，我还是要从“头”讲起。这个“头”指的就是HTTP协议中的头字段。HTTP消息头允许客户端和服务器通过request和response传递附加信息。这些信息可能包括：语言、来源、浏览器信息、数据类型。当然也包括下面要提到的Cookie。

![](../Images/8e66fac084684f2c0b7fc43a104bccd8.png)

我们知道HTTP协议本身是无状态的，也就是说服务器无法记住每一个客户端是谁、登没登陆、喜欢什么、要买什么。Cookie的出现就解决了这个问题。由服务器发送一小块带有状态信息的Cookie到用户浏览器，并保存在本地，它会在浏览器下次向同一服务器再发起请求时被携带并发送到服务器上，服务器也就知道你的信息了。嗯，，像在发饼干，也许Cookie的名字就是这么来的吧。

![](../Images/1488e885ff065d726428de878736d100.png)

**0x02 SESSION机制**Session是会话的意思。既然Cookie可以存储用户状态了，那么为了解决登陆会话问题，就产生了SESSION机制。这里的SESSION和Cookie也不是一类事物。准确的说，SESSION是一种机制，它利用了Cookie，来实现登陆认证。通常在工作交流中单独说到SESSION的时候，要么是指SESSION机制，要么就是指（存放在Cookie中或服务器上的）SESSION\_ID。这应是需要注意和明确的，避免我们在工作中因为概念混乱导致无效的沟通。简单地说，SESSION机制就是通过服务器给每个用户生成一段与用户对应的、很长的、无意义的、难以预测字符（SESSION\_ID）来作为登陆认证的凭据，通过Cookie发给客户端浏览器保存。这样以后浏览器再访问相同网站时就会带上这段Cookie，服务器则存储了这些SESSION\_ID与用户的对应关系，一查就知道你是谁了。

![](../Images/0803b2e4b7e5debe1af559f228f949aa.png)

如此看来，SESSION\_ID的值就显得极其重要。除了其本身的算法强度问题，他的存储与传输安全也十分重要。稍有不慎，就会出现安全风险。比如：XSS跨站脚本漏洞，就是攻击者在用户访问的页面中注入恶意js。由于js可以通过document.cookie等方式获取用户cookie，那么攻击者就可以通过XSS漏洞获取受害者的全部Cookie内容，这其中当然就包括登陆凭据SESSION\_ID。

![](../Images/670de54188ada74aa69c760a7011ab18.png)

开发者可以通过给Cookie设置HttpOnly属性来防止js读取cookie，起到缓解XSS安全风险的作用。但最好的解决办法还是从代码中修复XSS漏洞。**0x03 CSRF与TOKEN**除了XSS，还有一个安全问题是Cookie避不开的，那就是CSRF跨站请求伪造。简单说，就是攻击者在他可控的一个网站页面中插入一个访问到有CSRF漏洞网站的请求表单，受害者访问攻击者页面的时候，会在不知情的情况下向漏洞网站提交攻击者构造的表单请求。注意，这些请求将是带着受害者浏览器Cookie的，也就是说与受害者本人亲自登陆操作没有区别。这攻击请求可能是后台管理操作，也可以是买卖、交易请求，就看攻击者想怎样了。

![](../Images/49e0dde69a2a7fc5d586d7500f99282d.png)

解决方法除了验证请求来源Referrer，还可以增加CSRF\_TOKEN。终于说到了TOKEN，TOKEN就是令牌的意思，其实他和SESSION\_ID相像，一般它也是一串唯一的、随机的、不可预测的字符。拿到这个TOKEN就像拿到一块免死金牌，出示令牌就可以畅通无阻了。在CSRF的防御中，可以在每一个表单请求中添加一个隐藏的csrf\_token参数，并且这个token一次有效，每次刷新都会变化。这样，除非用户自己在页面中亲自操作，否则无法获得csrf\_token也就无法被攻击者实施伪造请求的操作了。

![](../Images/e46f86ec3884effa4d56b7800feb0c2f.png)

  

![](../Images/d228c7eec6bafcbe6b4b950c358ba2ff.png)

**0x04 JWT**最后我们来说说JWT，JWT是JSON Web Token的缩写。它的目的是为了解决SESSION机制中服务端开销和扩展问题。在传统SESSION机制中，SESSION\_ID与用户的对应关系是需要在服务端存储的。当用户量达到一定程度时，服务端开销将明显增大。在分布式环境中，由于服务器间不共享session，通常会将session单独放到一台Redis之类的服务器中，但这就不能完全发挥负载的作用了。而JWT就通过算法保证，将用户信息加密放在客户端作为token安全的保存，当用户下次带着这段token访问的时候，服务端再通过算法验证这段token的合法性，未被篡改，进而确定用户身份，完成登陆认证。这样服务端就无需存储用户身份与token对应关系，是一种用计算换取存储的思路。

![](../Images/d7f804d17c0f717315805a0e2d7bc9b0.png)

**JWT可以防XSS吗？**

答：不可以。JS可以通过JSON.stringify(localStorage)获取到存储在浏览器中的JWT。攻击者可以利用XSS漏洞页面获得受害者的JWT令牌。  
  

**JWT可以防CSRF吗？**

答：这个要分情况。CSRF利用的原理是浏览器针对跨站请求会携带目标站的Cookie。所以如果JWT放到了Cookie里面，那是无法御防CSRF攻击的。如果JWT单独放到HTTP的Header头里面，由于跨站请求无法携带这些附加的Header，就可以起到防御CSRF攻击的目的。  

**JWT使用中有什么安全风险和注意事项？**

**1\. 信息泄露**不应该在JWT的payload部分存放敏感信息，比如用户的密码、隐私信息等，因为该部分是客户端可解密的部分。一旦JWT被攻击者拿到，这些信息也将随之泄露。**2\. 密钥保护**保护好secret私钥，该私钥非常重要。因为如果攻击者知道了secret，就可以随意伪造payload并自行生成合法的signature签名。JWT就无法防篡改防伪造，整个验证机制也就土崩瓦解。另外密钥强度也要满足要求，应使用大于或等于哈希输出大小的密钥，例如：HS256为256位。简单的字符串密钥容易被暴力破解，比如使用Hashcat破解JWT。

![](../Images/e9cf11e600ce9d915fa1bbfe7eb72658.png)

对于可能的密钥泄露的情况，也要提前做好密钥更新的应急方案。  

**3\. 异常处理**对于客户端私自修改JWT签名算法类型、删除签名、错误签名的异常情况，服务端要有相应的识别和处理，并严格把控错误提示信息。防止攻击者通过异常情况绕过JWT认证，或通过错误提示信息获得正确的签名。  
**4\. 注销弱点**由于JWT是无状态的，服务端完全没有相关信息存储，所以如果一个用户想主动注销本次登陆，这在服务端是难以验证的。我们假设有攻击者通过XSS等漏洞已经获得了受害者的JWT，受害者也知道自己的JWT被泄露了，想将此JWT注销掉。但受害者能做的只是删除自己浏览器上的JWT，攻击者拿着得到的JWT一样可以登陆服务器，而服务器却无从验证。也就是说攻击者一旦获得了受害者的JWT，受害者无法通过注销操作阻止攻击者的进一步攻击。虽然开发者可以通过设置JWT超时时间、增加风控监测等方式使这种状况得到缓解。但都无法从根本上解决这个问题，这是JWT设计架构决定的。**0x06 结语**以上可以看出，JWT并不是为了安全设计的。它主要解决的还是资源问题。水能载舟，亦能覆舟。在开发工作中，我们要确保安全、正确的使用它。绝不能对安全掉以轻心呐！
