# 前言  

现在对智能硬件的安全研究越来越火，很多新人上手的时候往往需要在搭建环境上踩一些坑，在这种无关紧要的事情上浪费很多时间。本文旨在指导如何用docker搭建一个开箱即用的分析环境，或许文中的很多做法不是docker的最佳实践，但是对于那些想快速开始又对docker所知不多的人会有些用处，可以省去摸索的过程直奔固件的核心问题。

## IoTAnalysis简介

IoTAnalysis的docker镜像可以直接从docker hub拉取，运行 `docker pull pk8995/iotanalysis`即可。 这个项目是打算把IoT固件分析中用到的工具打包到一个镜像里方便使用，以后还会有更多的工具集成进来。

### 工具

*   Ubuntu 18.04
    
*   Binwalk 2.1.2
    
*   Qemu 4.15
    
*   ARM toolchain
    
*   MIPS toolchain
    
*   gdb and gdb-multiarch
    

曾经在使用AttifyOS的时候因为很多版本问题踩了许多坑，例如AttifyOS自带的qemu版本是2.0，不论使用大端格式的qemu-mips还是小端格式的qemu-mipsel都会报错。MIPS指令架构属于RISC（精简指令集）体系，mips是big-endian（大端）的mips架构，mipsel是little-endian（小端）的mips架构。他们之间的区别就是内存中存放的数据的字节顺序相反，也就是把低位放在低地址还是高地址。虽然18.04的qemu也不是最新版本，但还是总体的提高系统的版本尽可能回避这种问题。

## 使用

### 启动docker实例

```
docker run -it --name iot --privileged --rm -v $(pwd)
```

这里将一个host上的目录绑定到实例中，我们的分析结果可以在实例退出后保存下来。  
实例启动后会得到一个shell，在这里可以继续我们的分析了。

### binfmt

这里需要带 `--privileged` 参数启动，主要是因为需要`mount binfmt_misc -t binfmt_misc /proc/sys/fs/binfmt_misc` 使binfmt功能可用。binfmt是linux内核提供的一个机制，能让内核可识别任意类型的可执行文件格式并传递至特定的用户空间应用程序。  
简单的说它能让很多异构的程序直接通过模拟器或者虚拟机直接运行，看起来就像是原生程序一样。  
它的原理也很简单，就是把被执行的文件的一段特征注册到系统里，启动的时候根据这个特征去找对应的解释器、虚拟机或者模拟器。

可以用 `docker run --rm --privileged multiarch/qemu-user-static --reset -p yes` 注册，非常方便。

然后看一下是否注册成功

```
root@4b9414e26f08
```

### binwalk

首先不带参数运行 `binwalk` 看一下版本，这里使用了较新的2.1.2版本。binwalk是用来分析固件结构的基本工具，之前也因为binwalk的版本问题导致很多固件抽取出现各种各样的问题，所以这个镜像是从github上拉取了最新的版本编译的。

#### 固件扫描

`binwalk firmware`

可以看到基本的分析情况

#### 提取文件

选项“-e”和“–extract”按照预定义的配置文件中的提取方法从固件中提取探测的文件及系统。选项“-M”和“—matryoshka”根据magic签名扫描结果进行递归提取，仅对“-e“和”-dd“选项有效

`binwalk -e firmware.bin`

#### 例子

随便找一个固件试一下，比如openwrt的固件，就以18.06.4 mt7621 d-team\_newifi-d2-squashfs-sysupgrade.bin 为例吧。

```
root@c06d22498a92
```

这样就得到rootfs可以进行下一步分析了。  
从binwalk的扫描我们也能得到一些有用的信息，比如处理器架构以及内核的相关信息`MIPS OpenWrt Linux-4.14.131` ,当然这些信息还是需要进一步的从rootfs里确认。

### QEMU

qemu 是纯软件实现的虚拟化模拟器，几乎可以模拟任何硬件设备。 QEMU模拟器主要有两种比较常见的运作模式：

*   User Mode（使用者模式） User Mode模式下，用户只需要将各种不同平台的处理编译得到的Linux程序放在QEMU虚拟中运行即可，其他的事情全部由QEMU虚拟机来完成，不需要用户自定义内核和虚拟磁盘等文件；
    
*   System Mode（系统模式）。 System Mode模式下，最明显的特点是用户可以为QEMU虚拟机指定运行的内核或者虚拟硬盘等文件，简单来说系统模式下QEMU虚拟机是可根据用户的要求配置的
    

在编译qemu的时候有一点非常重要，最好编译成static使用，否在在后续模拟的时候经常会出现找不到库等情况。
