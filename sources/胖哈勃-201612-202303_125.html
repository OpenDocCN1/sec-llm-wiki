a drop of blood

商城应用，从注册、登录到下订单购买整个流程下来，发现访问的页面有 asp、php、jsp 扩展名的，Cookie 是 JESSIONID，404 页面看起来像 python web 的，响应报头里的字段也五花八门的，没法判断出 Web 程序环境的相关信息。

注册的用户初始有 600 分，商品列表里 flag 要 998 分，下订单到支付页面，把确认支付按 钮的 disabled 属性给删掉，显示余额不足支付失败，查看支付的请求包。

Signature 的值很像 md5，经过测试，改动订单数据的任何一个值都会提示签名错误，所以签名的作用应该是校验 post 的订单数据是否被篡改。
直接把订单数据 md5，果然和签名值不一样。猜测签名是 secret 值与订单数据拼接后 md5得到的。

针对这种情况，通过哈希扩展攻击来篡改数据通过校验的可能性很高。 编写脚本尝试哈希扩展攻击，利用已知的订单信息和签名值，使用 hashpump 来验证想法是否正确。在基本订单信息不改变的情况下，如果扩展的长度和 Web 程序里的 secrect 长度相同，就可以通过验证。

当扩展长度为 1024 的时候，哈希扩展攻击成功。接下来只需要篡改掉订单中的某一个数据 就有可能使订单支付成功。

通过分析登录流程，可以发现 Web 程序对于重复的参数取最后一个的值。所以直接在原来 的订单信息后面加上要修改的参数和值就能够修改订单信息的数据。

修改 buyer_point 和 good_price 的值，不成功。

因此只能改变 buyer_id 的值，当前用户的 id 为 733，推测从 1 开始的用户总会有人可以购买。

在用户 id31 的时候支付成功。

查看订单列表，得到 flag。
