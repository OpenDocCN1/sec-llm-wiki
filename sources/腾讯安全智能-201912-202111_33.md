# Flink 的 Event Time 与 Watermark 机制

处理数据时，时间常常是一个重要的维度。Flink 处理的数据往往经过 kafka 等消息系统的转发，在这种情况下，flink 处理数据的时间，和事件实际发生的时间是不一样的；我们一般希望从数据内容中提取时间，这就是 event time.

flink 收到数据的顺序，和从中提取的 event time 的顺序，有可能是不一致的。为了能按照 event time 有序地处理数据，我们可能需要缓冲收到的数据，按 event time 排序，再进行处理。要如何缓冲，则由 watermark 机制来控制。

本文将会详细地探讨以下内容：

*   如何提取 event time? Watermark 是如何产生的？
    
*   Event time 和 watermark 如何传播？
    
*   Watermark 机制如何起作用？什么时候会不起作用？
    
*   Watermark 对性能有什么影响？如何避免潜在的性能问题？
    

## 一、Event time 和 watermark 的产生

在 flink, event time 和 watermark 的产生有两种途径：

1.在数据源 SourceFunction 中，通过 collectWithTimestamp(T element, long timestamp) 在产生数据的时候携带 event time, 通过 emitWatermark(Watermark mark) 产生 watermark.

  

2.在处理数据的过程中，通过 TimestampsAndPeriodicWatermarksOperator 或者 TimestampsAndPunctuatedWatermarksOperator 产生 event time 和 watermark. 通过这种方式，可以覆盖掉之前的 timestamp 和 watermark.

  

实际使用中，我们很少会直接实现 SourceFunction 或 Operator, 大多数时候，会使用数据源实现（如 FlinkKafkaConsumerBase）或 DataStream 上的 assignTimestampAndWatermarks 方法来指定 event time 和 watermark.

assignTimestampAndWatermarks 一般有两个重载：

*   assignTimestampAndWatermarks(assigner: AssignerWithPeriodicWatermarks\[T\])
    
*   assignTimestampAndWatermarks(assigner: AssignerWithPunctuatedWatermarks\[T\])
    

AssignerWithPeriodicWatermark 和 AssignerWithPunctuatedWatermarks 都是接口 TimstampExtractor 的子接口。TimestampExtractor 声明了方法 extractTimestamp(T element, long previousElementTimestamp), 这个方法需要根据传入的当前元素 element, 返回该元素的 event time.

previousElementTimestamp 是该元素之前被分配的 event time, 一般不会用到这个参数。

而 AssignerWithPeriodicWatermark 和 AssignerWithPunctuatedWatermarks 的区别在于产生 watermark 的方式。

*   AssignerWithPeriodicWatermark: 定期产生 watermark. 这个接口需要实现一个 getCurrentWatermark() 方法，SourceFunction 或者 TimestampsAndPeriodicWatermarksOperator 会定期调用（默认是每 200 ms 一次）这个方法，获得当前 watermark. 这个是比较常用的 assigner.
    
*   AssignerWithPunctuatedWatermarks: 适用于数据流中本身带有 watermark 标记的场景。需要实现一个 checkAndGetNextWatermark(T lastElement, long extractedTimestamp) 方法，SourceFunction 或者 TimestampsAndPunctuatedWatermarksOperator 会在每次调用完 extractTimestamp 后，都调用一次这个方法。实现这个接口时，如果需要产生 watermark, 则返回 watermark; 否则返回 null.
    

#### 实际使用

实际使用中，我们常用两个 Flink 自带的 AssignerWithPeriodicWatermark 实现：

*   AscendingTimestampExtractor: 用于 timestamp 单调递增的场景，如 kafka 的每个分区都已经保证是按时间递增的。框架查询 watermark 时，会返回已经提取的最大 timestamp.
    
*   BoundedOutOfOrdernessTimestampExtractor: 用于 timestamp 可能乱序的场景，可以指定一个最大允许乱序的时间 maxOutOfOrderness. 框架查询 watermark 时，会返回已经提取的最大 timestamp - maxOutOfOrderness.
    
      
    

这两个实现已经可以满足大部分使用场景了。但在一种场景下，可能会遇到问题：

*   数据的流量很少，可能过个半小时、甚至几小时才有一条数据进来。在这种场景下，无论是使用 AscendingTimestampExtractor 还是 BoundedOutOfOrdernessTimestampExtractor, 在没有数据进来的时候，watermark 都不会更新，这会导致时间窗口等基于 watermark 工作的机制不会触发。
    
      
    

如何解决这个问题呢？我们可以认为，如果很长时间都没有数据进来，那就是真的没有数据了；而不是 kafka 什么的卡住了，不需要等待延迟的数据。这个时候，我们可以在没有数据进来的情况下主动推进 watermark. 我们可以通过继承 AssignerWithPeriodicWatermark, 实现自己的 getCurrentWatermark() 方法来实现这个特性。

## 二、Watermark 的传播

在实际使用中，我们一般只在在数据源处提取一次 timestamp, 后序的处理步骤都依赖这个 timestamp. 如果后序的处理流程是线性的，那么我们很清楚，每个步骤的 timestamp 和 watermark 都是上一步传递过来的；但如果数据流的拓扑比较复杂，我们就需要考虑 watermark 是怎么传播的了。例如：

*   一个 filter 操作把数据元素都丢弃了，那么 watermark 会不会往下传递？
    
*   一个 split 操作把数据流分成了两支，这时 watermark 如何往下传递？
    
*   一个 keyBy 操作根据数据内容来调度分区，没有数据进入的分区，watermark 如何传递？
    
*   如果一个操作从多个上游操作接收数据，那么这个操作的 watermark 如何计算？
    
      
    

实际上，Flink 内部的处理方式如下：

*   每个 subtask 把 watermark 广播给所有下游 subtask.
    
*   每个 subtask 会分别记录所有输入的 watermark, 取它们的最小值作为自己的 watermark.
    
      
    

如图：

![](../Images/91081264b8e65a60728bfe2e1db8a4de.png)

当一个 FlinkKafkaConsumer 作为数据源，向下游的一个 map 任务发送数据时，FlinkKafkaConsumer 的每个 subtask 会分别从分配自己的 kafka 分区中读取数据，并通过配置好的 AssignerWithPeriodicWatermark 来产生 watermark. 由于分区调度方式是 rebalancing, 对于其中的一个 subtask 来说，它产生的数据会以 round-robin 的方式发送给下游的 3 个 subtask. 但 watermark 的发送和数据是不一样的，每个 watermark 会以广播的形式，同时发送给下游的 3 个 subtask.

而对于下游的 map 来说，每个 subtask 会从两个上游的 subtask 接受数据和 watermark, 此时的 watermark 则是两个上游的 watermark 中比较小的那一个。

上面的例子是一个 task 中的不同分区间广播 watermark 的情况。在多个 task 的情况下，效果也一样，watermark 根据数据的流向，从上游往下游广播。这样，我们可以得到如下结论：

1.  一个数据源的 subtask, 只要有数据和 watermark 产生，watermark 就会沿着数据路径一直往后广播，filter, split, keyBy 这些操作可能会导致某些下游 subtask 接收不到数据，但 watermark 仍然可以接收到。
    
      
    
2.  如果一个 subtask 从多个来源（包括多个上游 task 或者一个上游 task 的多个 subtask）接收数据，那么这些上游 subtask 必须都有 watermark 产生，本 subtask 的 watermark 才会更新。
    

#### 实际应用

在实际使用中，我们一般只要关注数据源。只要数据源的每个 subtask 都有数据和 watermark 产生，这些 watermark 就会一直广播下去，下游的所有 task 都能更新 watermark.

但是如果某个 subtask 没有数据产生，watermark 不更新。那么由于上述第 2 点的限制，下游的 task 就可能不会更新 watermark, flink 任务看起来就会卡住不工作。一个典型的情况就是，FlinkKafkaConsuemr 的两个 subtask 各自读取一个 kafka 分区；由于外部的原因，写入 kafka 的数据全部落入了其中一个分区，另一个分区没有数据。这时，其中一个 subtask 读不到就不会产生 watermark, 下游的 task 由于从上游的两个 kafka subtask 接收数据，会取两个 watermark 中最小的那个，也就是一直没有产生 watemark 那个。这时 flink 任务看起来就卡住不工作了。

## 三、Watermark 的使用

Watermark 并不会神奇地把乱序的数据排序好；要使用 watermark 来处理乱序数据，需要借助实现了 watermark 语义的 flink 内置操作（如 window, CEP），或自己实现 watermark 语义。用一个例子来说明，下面这段代码的 watermark 完全没有效果：

*   
*   
*   

```
dataStream  .assignTimestampAndWatermarks(...)  .map(...)
```

这里虽然通过 assignTImestampAndWatermarks 设置了 watermark, 但 map 的时候，flink 框架并不会帮你把数据按照时间顺序排好。下面这段代码是有效果的：

*   
*   
*   
*   
*   

```
dataStream  .assignTimestampAndWatermarks(...)  .keyBy(...)  .window(...)  .reduce(...)
```

这里如果使用了时间窗口，并使用 even time, 那么 flink 的 WindowOperator 实现了 watermark 语义，会等待 watermark, 在 watermark >= 某个窗口的结束时间时，才会输出这个窗口的 reduce 结果。但是，这里只是按照 watermark 来等待乱序的延迟数据，仍然不会对数据做排序。如果要得到确定的结果，reduce 函数必须满足交换律和结合律。

那么有没有对数据做排序的情况呢？有，Flink CEP 严格依赖元素间顺序，因此用了一个 priority queue 来缓存并排序数据。如果我们自己的函数，需要严格按照时间顺序来处理数据，也需要用到这个方法。我们可以通过 KeyedProcessFunction 来显式处理 watermark, 并自己实现排序。

#### KeyedProcessFunction

通过一个 KeyProcessFunction\[Key, In, Out\] 来使用 watermark 时，我们需要用到以下两个方法：

*   processElement(value: In, ctx: KeyedProcessFunction\[Key, In, Out\]#Context, out: Collector\[Out\]): 在处理元素时，通过 ctx.timestamp() 可以获得当前元素的 timestamp; 通过 ctx.timerService().currentWatermark() 可以获得当前 watermark. 对比 watermark 和当前元素的 timestamp, 就可以知道我们是否需要丢弃收到的元素。
    
*   onTimer(timestamp: Long, ctx: KeyedProcessFunction\[Key, In, Out\]#OnTimerContext, out: Collector\[Out\]): 我们知道，就算没有元素进来，watermark 也可能更新。上述 processElement 方法只会在有元素进来时被调用，在没有元素进来时，我们需要通过 timer 来获取 watermark 的更新。
    
      
    

一个典型的使用模式如下：  

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*   
*

*   
*   
*   
*   
*   
*   
*

*

*   

```
class MyFunction[Key, In, Out] extends KeydProcessFunction[Key, In, Out] {    // 变量声明    var lastWatermark: Long = Long.MinValue    val sortQueue: mutable.PriorityQueue[In] = //...        override def open(parameters: Configuration) = {        // 初始化    }        override def processElement(value: In, ctx: KeyedProcessFunction[Key, In, Out]#Context, out: Collector[Out]): Unit = {        val currentTimestamp: Long = ctx.timestamp()        if (currentTimestamp < lastWatermark) {            // 过期元素，丢弃            return        } else {            // 否则保存到缓冲中            sortQueue.enqueue(value)        }        if (currentTimestamp > lastWatermark) {            // 只要队列中还有元素，我们就在当前 watermark + 1 的时间上注册一个 timer, 保证 watermark 一向前推进，就会回调我们的 onTimer 方法            val currentWatermark = ctx.timerService().currentWatermark()            ctx.timerService().registerEventTimeTimer(currentWatermark + 1)        }    }        def onTimer(timestamp: Long, ctx: KeyedProcessFunction[Key, In, Out]#OnTimerContext, out: Collector[Out]): Unit = {        val watermark = ctx.timerService().currentWatermark()        lastWatermark = watermark    // 更新 lastWatermark        // 从 priority queue 把 timestamp <= watermark 的元素都取出，并处理        // 由于是 prority queue, 取出的元素是按时间顺序排列的        // ...        if (sortQueue.nonEmpty) {            // 只要队列中还有元素，我们就在当前 watermark + 1 的时间上注册一个 timer, 保证 watermark 一向前推进，就会回调我们的 onTimer 方法            ctx.timerService().registerEventTimeTimer(watermark + 1)        }    }}
```

#### WindowOperator

Flink 内置的 window 操作，也同样使用类似的方式来实现 watermark 语义。可以参考 WindowOperator.java 的代码。

WindowOperator 是通过继承 AbstractStreamOperator 和 OneInputStreamOperator 来实现 window 操作的。与上面说的 KeyedProcessFunction, 这两个接口可以控制更多的细节，但实现起来也更加复杂.

## 四、Watermark 对性能的影响

了解了 watermark 的传播和生效机制后，就可以考虑其对性能的影响了。

首先，我们已经知道，watermark 必须主动通过 KeyedProcessFunction 或 AbstrackStreamOperator 等提供的接口来使用，才会起作用。如果只用了 map, flatMap, filter, split 之类的操作，watermark 是不会起什么作用的，也不会有什么性能开销。

如果我们没有手工实现 KeyedProcessFunction 或 AbstrackStreamOperator, 那会用到 watermark 的主要就是 time window 和 CEP 了。其中，time window 使用 reduce/fold/aggregate 函数的时候，是不需要缓存全部数据的，只要为每个窗口缓存当前的迭代结果，消耗的资源也不多。

但 CEP 就不一样了，CEP 对元素顺序有严格依赖，实现的方法就是上文演示的 priority queue, timestamp > watermark 的元素都会缓存在内存中。如果使用 BoundedOutOfOrdernessTimestampExtractor, 那么就会在内存中缓存允许乱序时间内的数据。在大吞吐量时，这个数据量相当大，一般只能把 outOfOrderness 设置成几秒或几十秒。

最后在考虑一些异常情况的影响。例如：上文提到的数据源分区偏斜，由于下游的 watermark 等于所有上游中最小的 watermark, 如果数据源分区偏斜，那么数据多的分区产生的数据需要等待数据少的分区的 watermark, 这也会造成额外的性能开销。

## 五、总结

本文涉及的主要是 flink 内部的实现细节。使用 flink 可以不了解这些，但如果遇到一些奇怪的问题，例如，

*   我的 window reduce 结果为什么延迟了几个小时才出来？flink 不是实时的吗？
    
*   我的 job 为什么消耗了这么多内存？
    
      
    

了解 watermark 的实现机制，会对定位问题很有帮助。当 flink 提供的高层 API 无法满足需求，需要自己扩展 flink 时，了解内部的实现机制也是必须的。
