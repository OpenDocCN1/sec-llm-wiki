还记得2017年初刷屏朋友圈的“召唤福神传福运”H5页面吗？…腾讯公益新年小福神项目，通过召唤不同小福神，传递福运的方式，给贫困山区的小孩，或者抗战老兵，或者先心儿童捐赠红包，邀请大家献爱心的活动。每个捐赠项目会对应一个小福神，分别为：康神、学神、食神、山神以及灶王爷，比如康神：  

![](../Images/46edd227bf68174ad16a6faa18760cb8.png)

下面以项目需求对接过程中产生问题并加以解决为主线，摘取项目过程中三个阶段加以描述，分别为：设计对接，测试优化，迭代调整：

  

**设计对接阶段**

   

图片模块抽取

在接到最初设计稿时，发现每个神仙出场动作不一，而且不能用transform组合技实现，动画时间长度短，约4s，不适合做成视频，初定方案是 序列帧动画，最初的设计版本是4个神仙在1个列表页里，用户可以主动选择哪个神仙icon的，从而召唤对于小神仙，所以需要在loading页 load 4个神仙的图片以保证用户点击神仙的时候，动画可以立即流畅播放。

  

葫芦 在最初的设计版本是loading页的载体，刚开始设想是葫芦下有加载的数字，100%了就切换成 摸摸我/召唤小福神 之类的文案，通过引导用户触发葫芦就进入神仙页面；每个神仙的出场都是统一的：喷烟-蹦出-循环，需要抽取共性的部分，减少画面的冗余，而共同的地方 喷烟 是可以剥离开神仙的，所以最初的序列帧，尝试把烟剥离开来，减少总体动画图片的体积，如下：

  

![](../Images/2386fc0b07746f9fc6cbdaddbc9e21cc.png)

按每秒15帧输出，18张图，大概1秒多点，将烟序列帧剥离，总体图片就减少了3份烟体积，而神仙的动画则分离为出场动画跟循环动画，出场动画只需要播放一次，与烟动画衔接匹配；

循环动画紧跟出场动画，然后一直循环播放。

  

   

序列帧合并压缩

然而单用CSS3去切换序列帧图片，图片请求太多，图片渲染不能精确的衔接，有卡顿现象出现，按惯例将图片合成gif，起到减少请求的作用，制作流程是：

 

PS -> 文件 -> 打开 -> 打开对应目录 -> 勾选 图像序列 的checkbox -> 储存为 Web所用格式 -> gif 

 

通过上述流程可以得到最早版本的gif，然后用GIFmicro压缩下体积，比率可调整，康神为例 这样 烟18张图片（如上），神仙出场25张图片，神仙循环30张图片（如下）：

![](../Images/a361378d6ead40b7fed992b25b8764a9.png)

  

![](../Images/013a4a85e092a3078ddccd57ffbdde40.png)

处理成3张gif，嵌套进页面播放2张gif，体验发现性能差点的机子有点卡顿，还没来得及调整，设计版本要修改为：点击葫芦，召唤1个小神仙，也就是现有的版本，不需要4个神仙同时出现供用户选择；虽然交互需要重新处理，不过修改后加载可以更快，因为随机1个神仙，说明不用同时出现4个神仙，那只要在页头加载一个神仙的动画便可，烟的剥离就没必要了，因为它也是播放一次，可以与出场动画合并，这样就可以避免上面的性能差的机子同时播放2张gif会卡的问题，修改交互后动画序列帧如下：

**测试优化阶段**

  

动态图片格式压缩

png输出后，建议用工具压缩后再制作gif，gif体积会更小些，工具随自己喜好，我用的是 Pngyu 对png序列帧进行压缩；

  

通过GIFmicro压缩gif后，图片体积依然有点大，比如山神循环gif 971k，接近1M的体积，需要进行三次压缩；

  

目前市面流行的动画图片格式为apng跟webp两种格式，还有bgp（1.91M的gif 可以压缩到 139k ，但需要耗费很长解码渲染时间），apng在IOS下可以默认打开，而webp的话，在安卓下可以默认打开，两者交换平台的话，需要添加JS（android播放apng动画需添加 apng-canvas.js、ios渲染webp图片需要添加 webpjs.js）做支撑，转成序列帧在canvas播放；

 

这里就只挑apng述说处理方式（webp处理方法类似）：通过工具 gif2apng 将gif转换为apng图片，山神循环gif压缩后体积为 749k，得到apng后通过JS获取浏览器版本信息，对Android跟IOS进行判断，选择加载对应的图片格式显示。

  

   

动态图片缓存播放问题

gif在移动端加载播放后，刷新页面，由于缓存原因，不会从头开始播放，对于出场动画只播一次的gif，刷新后会直接停在最后一帧，到设定时间后便直接切循环动画，解决方法是在加载图片时，给予一个时间戳，如下：

![](../Images/a722e5c5293ce8d941818bcd40c38e42.png)

保证图片对于加载媒体来说都是每次加载都是新的，从头开始播放，而缺点是同一张图片重复加载需要消耗用户多次流量。

   

动态图片解码渲染延迟问题

在算准时间情况下，比如，一帧15张图片，比如 山神的开场动画是 36张图片，换算成时间理论上是2.40s的播放时间，然后就要隐藏切换成循环动画播放，但用settimeout 定时2400ms时，会出现闪帧现象，图片切换时会出现了短暂空白，在关键的时候断了影响体验，需要锁定问题产生的原因，尝试检测图片帧不否有空白或者错帧，尝试用不同的机型体验，发现IOS空白时间相对于安卓空白时间短一些，那会不会跟渲染有问题，在解析gif/apng的时候，需要一定的解析时间，图片从解析到渲染播放，这段时间差造成的，于是尝试将出场动画延后消失，将循环动画出场的时间提前，在出场动画延后调整到70ms，循环动画提前40ms，并在出场动画的末尾做了一个99.9%-100%渐隐的处理，循环动画置于出场动画之上，此时在IOS10/小米4 下闪帧消失，出场跟循环动画衔接正常；于是才有这样的代码：

![](../Images/8e329438e211c391cd564c235d7e48b1.png)

  

![](../Images/49f61e2a4b88835ee8fb69a826b40b6b.png)

然后在IOS9下，发现图片闪帧依旧出现，但是闪的时间比之前短了些，说明IOS10系统对图片的渲染比IOS9要快一些，所以在针对IOS9系统，循环动画又做了100ms的提前显示，此时IOS9显示正常。

  

**迭代调整阶段**

   

添加数据页后动画处理

处理完神仙的动画后，产品提出添加数据页，拉取用户的捐助信息，葫芦则在动画末尾显示，而这样的修改，出现了动画位置的错位，刚做好神仙动画的版本葫芦是在这个位置：

  

![](../Images/e6b05c1710faffeabc79bb7bd9439910.png)

  

而数据页的葫芦是在这个位置：

  

![](../Images/26b3713a19f74d495286aef7bc242230.png)

  

从设计角度，数据页的版面数据为重，葫芦为轻，毕竟只是一个切换的触发点，放大挪到原有版面的位置不合适；而如果修改原有版面，所有神仙喷烟的出口都要调整，设计修改太多，出现需要解决处理的矛盾点：怎么让页面过渡自然，而且工作量要小…

 

葫芦从小要变大，位置变化，假想用户戳了葫芦，那么注意力就集中在葫芦上，背后背景图的修改，轻量化，不要引起用户特别的注意，选择了渐隐处理，渐隐时间0.6s，然后重点葫芦在用户触摸后 下压向上弹跳 的动作，也就是动画十四原则里面的 挤压变形原则，用这个动作吸引用户视觉焦点，在这个过程中，葫芦同时改变体积，因为有变形因素的存在，葫芦的体积大小变化便变得和谐，原本小葫芦跳跃后还需要用户再点击一下触发喷烟操作，鉴于这步操作有点多余，最后便成了用户在进入页面点击数据页的葫芦，葫芦往上跳跃喷烟召唤小神仙一气呵成；而在试试召唤其他小福神 的模式下，就会在该页面停留，让用户触发葫芦才喷烟召唤小神仙，这个停留是预留一定时间，用于随机其它小神仙时，加载新的动画图片所需，所以没有直接出来小神仙。
