我相信，大家应该都听过 Zookeeper 这个词，那大家对它又有多少了解呢？


我第一次听到这个词是在了解 Kafka 时，它使用 Zookeeper 管理自己的元数据配置，但那时候，并不了解 Zookeeper 。


而且，不光 Kafka 使用了 Zookeeper， Hadoop 、HBase 也用到了它 。


那 Zookeeper 到底是什么呢？为什么它在分布式系统里有着无可替代的地位呢？


01
Zookeeper 的概念


Zookeeper 最早诞生于雅虎公司（ yahoo! ），当时雅虎内的很多业务都需要一个组件来帮忙进行分布式协调，但是，这个系统存在单点故障的问题。


而雅虎为了解决这个问题，开发了一个分布式协调的框架，也就是—— Zookeeper 。


看到这，你可能会问，什么是分布式协调？什么又是单点故障？别慌，我接下来就会解释这两个概念。要想了解分布式协调的概念，我们首先得知道啥是分布式。

上图的服务器是大家很熟悉的单机部署，其实很多刚刚起步的业务都是这样单机部署的。


但是万一你的 APP 或者网站突然爆火，大量的用户开始涌入，随之而来的就是大量的请求。而此时，万一这个服务器宕机了，那么你的整个 APP 或者网站都将不可用，这就是单点故障。


那如何解决这个问题呢？当然是部署多台机器，大家一起来扛。

这样一来，多台机器部署在不同的地方，服务器之间组成了一个集群，你的系统此时就变成了分布式的系统。


02
Zookeeper 的作用


了解完其基础概念，我们继续了解 Zookeeper 具体可以用来做什么。


（1）元数据管理

元数据管理其实很好理解，系统虽然是分布式进行部署的，但是我们需要一个地方来集中管理集群中的元数据。


Kafka 会将自身集群的数据存储在 Zookeeper 集群中，例如 Topic、Broker、Consumer 等相关的数据。除此之外还会使用 Zookeeper 来进行 Leader 选举、分布式协调以及通知。


不过，在 Kafka 2.8 的版本中，Zookeeper 已经不是一个必需的组件了。


（2）分布式锁

同一个服务器在集群中是多实例部署的，客户端 1 在「服务器 1」上对资源进行了锁定，那么即使客户端请求的是服务器 3，也应该被阻塞。


使用 Zookeeper 来实现分布式锁，其实是很多分布式业务系统中最常见的一种用途。当然，也有的业务会采用 Redis 来实现分布式锁。


（3）分布式协调

实现分布式事务的协调，本质上是通过 2PC 来实现的。


（4）发布订阅

在一些业务场景下，可能需要给某个资源指定一个唯一标识，之后再通过这个唯一标识来获取， Zookeeper 就能完全满足这个需求。

除此之外，在微服务架构中，不同的服务可能会存在名称碰撞的情况，这也可以通过 Zookeeper 来解决。

03
Zookeeper 的节点


Zookeeper 管理节点的方式和 Linux 的文件系统类似。我们知道，在 Linux 中有一句特别经验的话——一切皆文件。


像我们熟知的各种文件，目录是文件，甚至连管道、socket 都是被文件系统管理着。不同的是在 Linux 系统中是文件，而在 Zookeeper 中是节点。


不过为了能够方便你理解，你可以暂时把 Zookeeper 中的节点理解为一个文件，即一切皆节点。



结合上图来看，files 是一个节点，file0000000001 是一个节点，subfile 也同样是一个节点。并且，我们能在节点下再创建子节点。


我们知道在 Linux 中，文件其实都有类别：

  • 文件

  • 目录


在 Zookeeper 的存储系统中也是同理，那都有些啥呢？如下：

  • 持久节点（Persistent）

  • 持久顺序节点（Persistent Sequential）

  • 临时节点（Ephemeral）

  • 临时顺序节点（Ephemeral Sequential）
