**秒杀问题总结**

![](../Images/8e2a76ebdf8c2838337014746228f26d.png)

  

#### **高并发**

高并发是系统运行过程中遇到的一种 “短时间内遇到大量操作请求” 情况，主要发生在 Web 系统集中收到大量请求时，该情况的发生会导致系统在这段时间内执行大量操作，例如对资源的请求、数据库的操作等。秒杀商品通常价格会十分的诱人，比正常商品价格少了很多，如果一个商城用户量有几万或者更多的话，高并发必须是考虑的问题之一。

#### **超卖**

秒杀商品的价格很低，商家的利润也就很少，基本上不怎么赚钱，卖个 100 件造造势可以，不允许多卖。然而在高并发场景下，如果有 100 个线程同时查询到秒杀商品库存为 1，他们都认为库存充足，于是开始下单减库存，当 100 个线程执行完之后，数据库中的库存数量就变为 -99，那么商品就多卖了 99 个，商家就血亏了，也不一定能发出来货，这就是超卖。

#### **数据库压力**

每秒上万甚至十几万的 QPS（每秒请求数）直接打到数据库，基本上都要把库打挂掉，而且你的服务不单单是做秒杀的还涉及其他的业务，所以商品秒杀数据库的压力也是需要考虑的问题。  
  
![](../Images/7354cd9c68a9a006bb315d5edf5081aa.png)

****解决方法****

![](../Images/8e2a76ebdf8c2838337014746228f26d.png)

  

**限流 & 降级**面对高并发的请求量，如果处理不好，不仅仅降低了用户的体验度（请求响应时间过长），同时可能导致服务宕机，严重的甚至发生连锁反应导致整个系统崩溃。如果想要系统能够适应高并发状态，则需要从各个方面进行系统优化，包括：硬件、网络、系统架构、开发语言的选取、数据结构的运用、算法优化、数据库优化……我们这里只考虑对系统的优化，这就需要对秒杀服务进行限流和降级，当请求达到一定的并发数或速率，就进行等待、排队、降级、拒绝服务等。限流与降级的方法很多，然后分布式系统中我们采用 zuul 网关技术对秒杀系统进行限流和降级处理，使用 zuul 技术是因为 zuul 的 jar 包中包含了 hystrix 的 jar 包，Netflix Hystrix 是 SOA / 微服务架构中提供服务隔离、熔断、降级机制的工具 / 框架。Netflix Hystrix 是断路器的一种实现，用于实现高微服务架构的可用性，是防止服务出现雪崩的利器。

#### **Redis 库存消减**

秒杀的本质，就是对库存的抢夺，每个秒杀的用户请求都去数据库查询库存、校验库存，然后扣减库存，请求量少的时候可以，但是针对高并发的用户数据库就顶不住了。此时我们可以用非关系型数据库 Redis 来顶。项目启动时就把秒杀商品的库存加载到 Redis 中去，让整个判断库存和消减库存的工作都在 Redis 里面进行。等秒杀结束了，再异步去修改数据库的库存就好了。注意：当我们对秒杀系统做了集群处理时，比如秒杀服务器有两个，两个服务一起查询了库存中还剩 1 个，然后都去扣除库存，结果库存就变成了 -1 个。这样也还是产生超卖了。此时就应该使用 Lua 脚本，Lua 脚本是类似 Redis 事务，有一定的原子性，不会被其他命令插队，可以完成一些 Redis 事务性的操作。我们把判断库存、扣减库存的操作都写在一个脚本丢给 Redis 去做，那到 0 了后面的都 Return False，一个失败了就修改一个开关，直接挡住所有的请求，然后再做后面的事情。

#### **削峰填谷**

假如说限流只限 1000 个请求允许进入服务，这 1000 个请求同 1 秒查询库存、减少库存，对于服务器的压力也是不小，那么我们就可以使用 MQ 来将这些请求放到消息队列中，把这些请求分摊到一段时间内，然后一点点消费去改库存就好了，从而起到 “削峰填谷” 效果。如下图所示：![](../Images/50a6d4f9e8c34c3483d883b0807c40fe.png)

#### **使用 Tidb 替换 MySQL**

前面我们使用了 Redis 进行库存消减，但是 Redis 只是缓存，库存最终还是要保存到数据库中。对于一个高并发的系统而言，用户量是相当多的，达到一定的量之后，数据库就会到达瓶颈，即便是对数据库进行分库分表，但对一张大表执行 DDL 的代价是非常大的。此时可以使用 NewSQL 的数据库 Tidb，Tidb 可以按需扩展吞吐或存储，轻松应对高并发、海量数据的场景。并且高度兼容 MySQL，无需修改代码即可从 Mysql 迁移至 Tidb。
