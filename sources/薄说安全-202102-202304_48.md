**六、安全架构**

ALC系统功能安全概念的核心要求是由电子系统或司机保持对车身横向位置的连续控制，提供了两种安全架构"fail-safe"和"fail-operational"，"fail-safe"架构列举了常见的一种实现方案2oo2，当系统发生单一故障时导向安全侧。  

![](../Images/f6c5cc990ef02912de543892cd50ed69.png)

"fail-operational"在故障安全基础上提高了系统的可用性，即单一故障时可检测出故障并隔离故障模块，对于ALC系统，这意味着（1）确保ALC系统能够继续接收和处理传感器数据，并且（2）指挥必要的适当的横向调整，以保持车辆沿着参考路径行驶而不违反任何安全目标。这种架构至少应有三个计算单元，常见的有2oo3架构。

![](../Images/f1018515deb34d2c05ec409eca4eed89.png)

实际的ALC产品的安全架构在功能安全概念是上述两种架构中的一种，但不一定与它们完全相同。  

由"fail-safe"和"fail-operational"结合异构实现方式，派生出四种实现方案：  

方案1：Fail-Operational With Similar Redundancy

相同的传感器、控制器、执行器的冗余配置  

方案2：Fail-Operational With Dissimilar Redundancy

异构的系统组件实现，可能是不同传感器如Lidar，camara的异构，这种架构的复杂度高，但异构性使得共因失效的概率大大降低  

方案3：Fail-Safe With Redundant Actuation

故障安全的ALC系统与驱动基础系统体系结构相结合，提供有限的fail-operational操作能力。

方案4：Fail-Safe or Fail-Passive

故障安全，但可用性最低，一旦故障需要人工立即接管。

4种方案与5种自动驾驶级别的适用性如下，这里有个疑问，方案2异构性的适用性一般来说是强于方案1的，而报告中正好相反。  

![](../Images/1190cda1ad210b22e44ef49b64f60fcb.png)

安全状态（safe state）

*   对于驾驶员接管的自动驾驶级别1和2级，ALC系统可以立即切换到手动控制模式。因此，潜在的安全状态可以包括完全运行、降级运行或关闭模式。
    
*   对于自动化2级（驾驶员不立即接管）和自动化3级，ALC系统可以在适当的通知期后恢复到手动控制模式。因此，潜在的安全状态可能包括完全运行、降级运行（有或不影响其他系统），或在适当的通知驾驶员后到关闭模式。  
    
*   对于自动化4级和5级，ALC功能可能是高级路径规划算法中的几个功能之一。此外，在某些4级或5级自动驾驶车辆中可能无法恢复到手动控制。因此，潜在的安全状态可能包括完全运行、降级操作（有或不影响其他功能）或停车或停止模式。
    

也就是说，对应不同的驾驶级别，根据不同的危害事件，ALC将导向的安全状态是不同的。

除ALC系统导向安全状态外，驾驶员通知也是确保驾驶员采取正确行动的关键因素。驾驶员警告策略是作为功能安全概念的一部分，并根据安全分析在功能安全要求中加以规定。

  

**七、安全目标和安全需求**

这篇报告的分析成果是通过上述的危害识别，安全分析得出的5个整车级安全目标和73个安全需求，

5个安全目标分别是：  

SG1：**防止横向调整不足，导致车道/道路偏离。**

Level 1和level 2-engaged automated systems——**ASIL-B**级

level 2-not engaged和level3-level5——**ASIL-D**级；

  

SG2：**防止过度的横向调整，导致车道/道路偏离。**

各Level——**ASIL-D**级；

  

SG3：**防止ALC功能的意外丧失。**

Level 1和level 2-engaged automated systems——**ASIL-B**级

level 2-not engaged和level3-level5——ASIL-D级；

  

SG4：**确保驾驶员和ALC系统之间的正确转换控制权。**

Level 1和level 2-engaged automated systems——**ASIL-B**级

level 2-not engaged和level3-level5——**ASIL-D**级；

  

SG5：**确保横向控制动作与其他车辆系统或功能协调。**

Level 1和level 2-engaged automated systems——**ASIL-B**级

level 2-not engaged和level3-level5——**ASIL-D**级。

**1.ALC系统级（9条）**  

1-1 Detect all electronic faults which are capable of significant adverse effect on ALC functionality. Annunciate and mitigate the detected faults without violating any safety goals. ——对所有产生功能危害影响的电子失效应有检测措施，故障检测和隔离不能违反任何安全目标

1-3 Subsequent to detecting and mitigating a first electronic fault in a fully fail-operational ALC system, provide continued functionality for a to-be-determined period of time until the operator (i.e., driver) is alerted and safely resumes control of the vehicle.——检测到电子失效后，应在规定的时间内继续提供运行功能，直到提醒司机安全的接管

  

1-4 If a fail-operational system degrades to a fail-safe system capability for a short duration, notify the operator (i.e., driver).——fail-operational 降级到fail-safe的短暂时间间隔内，通知司机

1-6 Demonstrate that the hardware architectural single-point fault and latent fault metrics targets per ISO 26262 are met for each safety goal.——根据ISO26262硬件架构满足单点故障和潜在故障安全目标。

1-9 Log and save the following data every time a transition to a safe state is executed due to a violation of a safety goal: 为了复盘故障发生的场景和事故原因判定，故障发生的各个时间点需要记录入系统的日志中。因此，因违反安全目标而转换到安全状态，应存储日志数据，内容包括：

• The diagnostics information of the faults including the time at which the fault was detected and the nature of the fault. 故障检测出的时间点和故障属性

• The time interval from the detection of the fault to reaching a safe state. 检测出故障到达到安全侧的时间间隔

• The time the system degradation strategy started, including the start and end of each phase if applicable and the values of the system metrics for each phase (i.e., torque output level).

系统降级策略启动以后的时间  

• The time the driver warning strategy started, including the start and end of each phase if applicable and the values of the system metrics for each phase.

司机警告策略启动以后的时间

**八、故障诊断**

故障诊断属于功能安全系统的主要功能，可以分为**诊断对象、诊断覆盖率和诊断方法**。

**诊断对象**应包括用于实现安全目标的传感器、控制器、执行器所有部分，例如

处理器的中央处理单元、内存、ALU、寄存器、I/O、电源等；  

**诊断覆盖率**分为低、中、高三级，例如，传感器的低诊断覆盖级别可能只检测到超范围和范围内卡滞的情况。除此之外，传感器的中诊断覆盖级别还要检测到偏移量。高诊断覆盖级别，除了偏移、超范围和卡滞的条件外，还需要检测到振荡。

**诊断方法**的特征是检测系统的关键参数何时偏离其正常工作范围。在任何电子系统中，在电子元件和通信网络中都可能出现短期异常。对于ALC系统，提出了三个不同级别的诊断策略：

Level 1：主控制器运行其计算，它使用不同的计算方法或算法再次重新运行。如果这两个结果不匹配，则会设置一个故障，并制定一个故障缓解策略。实现软件算法上的异构比较。

Level 2：辅控制器独立收集输入，并独立计算，但它使用不同的方法和算法。然后，辅助控制器将其结果与主控制器的结果进行比较。如果结果不匹配，则会设置故障，并制定故障缓解策略。实现系统上的异构比较。

Level 3：辅助控制器随机地向主控制器提出已有确定结果的输入问题或场景。如果主控制器未正确响应，则会设置故障，并制定故障缓解策略。实现系统功能的回环诊断。

故障诊断码也是系统诊断功能的必要组成部分，故障检测码用于响应检测到的故障，以便维修工程人员在维修过程中快速检索到信息。

**九、测试方案**

对于安全功能的测试方案，根据安全分析的结果用于测试场景用例的开发是一种可行的方案。每个测试场景应包括：

1.    测试目标

2.    驾驶场景

3.    故障注入的方法

4.    期望的安全行为：系统在注入故障后达到的安全状态；注入故障到进入安全状态之间的时间指标FTTI。

例如，SG1（防止横向调整不足，导致车道/道路偏离）的测试场景一，STPA和功能FMEA分析出的CF因素作为测试场景的测试条件。

**十、总结**

1.这篇报告按照ISO26262概念阶段危害识别及安全分析要求，分析了车道保持控制系统ALC的功能安全分析过程，分为：

*   系统定义（功能、接口、架构和假设）；  
    
*   系统级危害识别（运用HAZOP和STPA方法）；  
    
*   风险评估（确定ASIL等级）；  
    
*   安全分析（运用功能FMEA和STPA方法确定危害致因）；
    
*   得出安全需求，共73条；
    
*   得出安全需求的验证要求，测试方案的开发。
    

整个分析过程清晰地描述了每个过程的目的和主要过程，尤其对HAZOP、STPA的实际应用进行了解析，为遵循ISO26262开展概念阶段的危害识别、安全分析提供了一个很好的示例；

  

2.不同安全完整性等级的产品由于其防护风险的严重度不同，对它们的技术要求也不同。很重要的一个方面是故障诊断能力的差异，高、中、低不同诊断覆盖率的技术要求是逐级递增。在ISO26262-5硬件附录D中的要求外，这个报告中的Level1，2，3级监控机制也是经常用到的，值得借鉴；

  

3.对于系统安全的分析方法，不同行业的分析方法是相通的，如HAZOP、FMEA在汽车功能安全、轨道交通功能安全都是应用非常广泛的方法，其是否能起到良好的作用取决于系统定义的详细程度以及分析者对于相关行业规范要求、场景识别的理解深度。本报告还借鉴了美军标MIL-STD-882E系统安全规范，其中的分析方法也是可以跨行业使用和借鉴的。这些跨行业的标准、指南、最佳实践都为功能安全工作者提供了很好的指导；

  

4.安全分析是一个通过不断深入细化的分析达到"know-how"的过程，其过程非常耗时、需要投入大量的资源，如报告中的功能FMEA识别了53个失效模式和211个潜在失效原因，STPA识别了1005条致因点。单从系统复杂度来看，ALC系统只能算是一个中等偏下复杂度的系统，可想而知，对于复杂系统，整个过程输出的文档会多么庞大，维护和保持它们之间的一致性、正确性会多么困难。要解决这些问题，提高工作的效率，必然要利用工具，采用自动化的手段会代替人工解决过程中比较繁杂的事务，腾出精力放在主要的分析活动上。如何解决这些问题，将在以后的文章中进行分享。
