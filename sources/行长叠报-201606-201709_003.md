# MacOS High Sierra 漏洞解析

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzAxODg1MDMwOQ==&mid=2247486405&idx=1&sn=3d208661bc74811da31564f3968d8787&chksm=9bcebcafacb935b9c4bfa3ad54af33ad8b6d8bda4e83ddbfb8ffa8f3249620225ef534429662&scene=27#wechat\_redirect](http://mp.weixin.qq.com/s?__biz=MzAxODg1MDMwOQ==&mid=2247486405&idx=1&sn=3d208661bc74811da31564f3968d8787&chksm=9bcebcafacb935b9c4bfa3ad54af33ad8b6d8bda4e83ddbfb8ffa8f3249620225ef534429662&scene=27#wechat_redirect)

本文将简要介绍一下Sierra的有争议的“安全内核扩展加载”(SKEL)特性。  

  

我们将利用SKEL执行中的0day漏洞来绕过它：

![](../Images/5467b65634d98820eecb3c895be7b4bf.png)

  

  

在苹果的技术文档TN2459中，提到了安全内核扩展加载：

  

> 一个新特性，在加载新的第三方内核扩展之前需要用户的批准。

  

虽然我们最初认为主要攻击向量SKEL试图阻止恶意内核扩展(即rootkit)的加载，但我认为情况并非如此。

  

由于OS X Yosemite，任何kext都必须使用内核代码签名证书来签名。

  

与用户模式的开发者id不同，苹果非常“保护”内核代码签名证书——只有少数合法的第三方公司才有理由创建内核代码。

  

相反，SKEL的主要目标是阻止合法但脆弱的kexts的加载。直到苹果通过OSKextExcludeList字典（在AppleKextExcludeList.kext / Contents / Info.plist中）清除这些kexts。

  

攻击者可以轻易地加载这些kexts，然后利用它们在内核的上下文中获得任意代码执行。

  

注意，这样的黑名单经常被延迟，因为它会严重破坏合法的功能，直到用户升级到一个非黑名单版本的kext。

  

大约一年前，我在DefCon的演讲中讨论了一个名为Littlesnitch的攻击媒介。（注意:这是一个众所周知的攻击向量，可以绕过Windows和macOS上的内核代码签名要求）：

![](../Images/970844ebb98123a69c62fa3f49a71853.png)

  

在我的演讲中，我讨论了LittleSnitch的内核驱动程序LittleSnitch.kext中可利用的内核堆溢出问题。

  

虽然这个漏洞可能会被滥用，以在安装了LittleSnitch的Mac上提权，这个漏洞无法被完全修补。因为本地特权攻击者仍然可以利用脆弱的驱动程序绕过macOS的内核代码签名要求。这次攻击的步骤如下:

  

1.使用root权限，加载含有漏洞的LittleSnitch.kext（版本<3.61）副本。因为含有漏洞的驱动程序的签名依然有效。

  

2.利用堆溢出在内核中获得任意代码执行。在内核中，可以绕过SIP，加载未签名的kexts，以及更多!

  

虽然“安全内核扩展加载”也可以阻止恶意签名的kexts的直接加载，但它的主要目的是为了阻止恶意加载已知的含有漏洞的驱动程序。

  

  

**安全内核扩展加载**

  

那么当用户（或安装程序或恶意软件）第一次尝试在High Sierra上加载签名的第三方内核扩展时，它将被SKEL阻止，用户会被警告，除非：

  

*   该内核扩展在升级到macOS High Sierra时已经安装。
    
      
    
*   与先前批准的扩展名签了相同团队ID。
    
      
    
*   是“替换先前批准的扩展”。(我猜是基于密码学可验证的信息，如团队ID)。
    
      
    
*   在有MDM解决方案的Mac上加载。
    

  

例如，在这里，我们尝试手动将最新版本的LittleSnitch.kext加载到High Sierra的原始虚拟机实例上。即使kext使用合法（非撤销）内核模式签名证书进行签名，并且未列入黑名单，SKEL也将阻止它：

![](../Images/442f73ef8234d9d5730a9c707a10cac8.png)

  

一旦系统阻止kext加载，它还将向用户生成警报：

![](../Images/95070c4e138dbe7c94831c47941b38c9.png)

  

如果我们在此过程中监视文件系统I / O，我们可以看到kext（LittleSnitch.kext）和似乎是“内核策略”数据库的内容都可以被系统策略守护进程syspolicyd访问：

![](../Images/8a0af39aa87008cdcd37c55105242ffb.png)

  

如果我们转储'kext policy'数据库（/ private / var / db / SystemPolicyConfiguration / KextPolicy），我们可以看到LittleSnitch kext已被添加到'kext\_policy'表中，但目前不允许（'allowed'设置为0）：

![](../Images/6c775e6cd1c514f409fac5cdd9311621.png)

  

就像在向用户显示的警报中所述，假设他们想要（签名）的内核扩展加载，他们现在必须手动批准它。这可以通过启动“系统设置”应用程序（/ Applications / System Preferences.app），导航到“安全和隐私”窗格，在“常规”选项卡中单击“允许”：

![](../Images/f61f42e12ed111b938a47b9d628067a2.png)

  

一旦用户允许kext加载，系统会更新'kext policy'数据库中的条目（'allowed'设置为1），并允许kext加载：

![](../Images/310f45c359bba35eb734029c86c2c20d.png)

  

  

**开发**

  

现在，让我们限制安全内核扩展加载。不是因为我们不喜欢苹果，而是说明在目前的实施中，黑客或恶意软件很容易绕开它。

  

我们的目标是以编程方式加载从未在High Sierra系统上安装或加载的签名kext。

  

这个kext可能是一个恶意的，或者更有可能是一个脆弱的，一个攻击者不受约束的内核访问。

  

当然，这两种攻击都应该被SKEL阻止。但是没有。

  

如果攻击者可以直接修改'kext策略'数据库，显然他们可以简单地“预先批准”kexts。为了防止这种情况，Apple通过系统完整性保护（SIP）来保护数据库：

![](../Images/0a24829b76f4a8a7e298e9fd762e1099.png)

  

由于这个数据库属于SIP，所以这意味着即使攻击者拥有root权限，也不能破坏它：

![](../Images/4862675e7dbd01edfd3b1e9af8bd8bad.png)

  

另一个明显的攻击向量是与UI交互，可能是通过编程方式将鼠标单击事件发送到系统首选项“安全与隐私”窗格中的“允许”按钮。

  

但是，此窗格（和其他敏感的UI组件，如安全警报）旨在阻止最新版本的macOS中的（模拟/编程）交互。

  

例如，下面我们可以看到操作系统阻止一个苹果脚本尝试与“安全和隐私”窗格进行交互：

![](../Images/d74dc51f42cd63a6021617db637a1476.png)

  

让我惊讶的是，即使一个人试图截取“安全与隐私”窗格窗口的屏幕。应用程序，捕获这个失败- >窗口):

![](../Images/036241e50bfaeb3c628a8df10f0f722a.png)

  

当然，作为攻击者，我们有更简单的工作——在SKEL中一个单一的实现缺陷可能允许我们完全绕过它。另一方面，苹果必须保护一切。所以,我们总是会赢。

  

目前我不能公布该漏洞的技术细节，这是一个完整的绕过SCALE的演示。

  

在下面的iTerm窗口中可以看到，在转储系统版本(High Sierra,beta 9)之后，显示SIP已启用。而我们正在加载的内核扩展（LittleSnitch.kext）未加载。在“kext策略”数据库中也没有发生什么神奇的事情。

  

简而言之，我们利用SKEL中的执行过程中漏洞，允许我们以编程方式加载新的未经批准的kext，而无需任何用户交互：

  

![](../Images/45da1493fe577b2c2164ffd8f3510c4a.png)

  

  

**结论**

  

在这篇博文中，我们简要讨论了High Sierra的“安全内核扩展加载”（SKEL），并展示了一个新的0day漏洞，可以充分利用这个漏洞来完全绕过这个新的“安全”功能。

  

不幸的是，当这种“安全”功能的引入并不利于第三方开发人员和用户，而对黑客却不会造成影响。
