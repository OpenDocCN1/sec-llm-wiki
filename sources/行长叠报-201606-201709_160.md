**嘉宾分享以“解密”为主打，面对APP测试中“签名”和“加密”数据包，如何通过多种方式还原明文？特邀嘉宾分享独家渗透秘诀，解析渗透测试中鲜为人知渗透技巧！**  

  

**前言**

之前在漏洞银行做的一次分享，本着有始有终的想法，整理成文档。希望能给大家的思路带来一点启发。

  

今天我们要说的，是**在加密场景下的一种测试方法**。在我们平常做测试的时候，特别是APP测试，非常实用的一种方法。

 

**0x00**

正常的APP访问，是APP直接和Web服务器进行通讯，这整个过程中的流量我们是不知道的。  

![](../Images/8e055d4b7362c3e8433fda50d2a593ce.png)

而当我们做测试的时候，为了能够捕获到中间的流量，我们会架设一层代理，这里以Burp为例。

  

这样的话就构成了如图所示的场景——APP的流量会经过Burp，Burp对数据包进行记录，再将数据包发送给Web服务器。Web服务器的请求返回之后，同样会先经过Burp。Burp把这个返回结果记录下来，同时发一份给APP。

![](../Images/d11e4c930eb235f5c715dffd932ebbd8.png)

**这样的场景下，我们通过Burp成功拦截了流量，我们可以对数据包进行实时的修改，进行各种漏洞的测试。**

  

上文所述的场景非常理想化，在实际的测试中，我们发现实际上我们经常会遇到两种窘境。

 

**0x01**

**第一种情况是，我们发现我们无法修改拦截下的数据包。**

  

我们对数据包进行修改之后，服务器返回的信息，要么是服务器异常，要么是数据包无法通过校验。

  

这是为什么呢？

  

通过查看代码发现，APP对数据包进行了签名。APP对参数列表进行了哈希操作，将哈希值写进了数据包里。当我们更改了数据包的参数值之后，哈希值与参数值不匹配，自然无法通过Web服务器的校验。

  

**第二种情况是，代理拦截的信息我们完全看不懂，或者是乱码，或者是看起来像base64的编码，但是用base64解出来的依旧是乱码。这种场景就是非常典型的加密场景，也是目前运用越来越广泛的场景。**

  

在此场景下，APP的请求在发出之前，都会有一个加密的操作。而这些加密的请求到达Web服务器的时候，会有相应的函数进行解密。

  

**而Web服务器返回请求的时候，要分为两种方式进行探讨：**

一种方式是，服务器返回的请求不再进行加密，直接明文返回。另一种是，服务器在返回请求之前也进行一次加密，这样返回的也会是密文。

  

实际测试中，面对这两种情况，我们即便在中间架设了代理，也无法进行任何的实际操作。

![](../Images/f27608c9c732959964f19df3a38f2191.png)

![](../Images/4d894b142fa6a09bf203e38176e0c3ab.png)

所以，接下来要探讨的，就是解决这个窘境的一种方法。

 

**0x02**

在测试过程中，我们需要达到的效果就是可以实时对数据包进行修改，从而进行各种测试。**阻碍我们的就是APP的签名和加密。**

  

那么我们的第一条思路就是，是不是能够hook掉加解密的函数，这样所有往来的流量就都是明文。我们就可以在中间拦截到明文的请求，再明文发送给服务器。

![](../Images/a1e70fe0259f57d265d9b682ffebb7c0.png)

思路进行到这里，我们就遇到了第一个疑问。

  

那就是——在hook掉加解密函数之后，明文传递给服务器的请求，是否能够被服务器接受并处理？

  

经过实际的测试发现，有部分对低版本做了兼容的APP会有两套逻辑。当接受的请求是明文的时候，会直接处理。当接受的请求是密文的时候，又会执行另一套密文的逻辑。

  

**注意，是“有部分”。**

这样这个方式就不太通用，存在不成功的风险。

  

当然hook的方式也有它的可取之处，也可以与我们下面要讲的办法做出结合，这里暂且不提，先来讲解我所总结出的方法。

 

**0x03**

那现在就到了我们今天要讲的一个框架，就是使用三层代理来做中间人的劫持。

  

上文提到，APP到Burp再到web服务器，中间会存在签名或者加密操作，使我们对数据包进行修改。

  

那么我们希望达到的效果是，通过Burp可任意的进行编辑，并且这个结果能够正确地被服务器处理。

  

那么我们就可以搭建这样一个框架：

![](../Images/303456dea3ce28a010ec4c15282ab6f0.png)

**首先，APP发出请求，经过第一层代理做一个解密的操作，就把加密请求，还原成了明文。然后，第二层代理就可以捕获一个完全明文的request，那我们可以对这个请求进行任意的编辑。接着，编辑好的请求发送给第三层代理，第三层代理收到request之后，先进行加密，再发送到Web服务器。**

  

这里采用与APP完全一致的加密方法，所以能够被Web服务器正常地执行。Web服务器处理完成之后，再把这个数据包进行加密，密文再经由第三层代理先做解密，解密出一个明文response，这一明文的响应继续发给第二层代理（Burp），而我们可以通过第二层代理查看这一相应或进行更进一步的操作。

  

最终明文响应会回到第一层代理。第一层代理对这个响应做加密操作之后再发给APP。APP会对这个数据进行解密，解密完以正常逻辑进行处理。

  

整个流程就是这样架构的。

  

**接下来剖析这一流程里的细节点：**

首先就是第一层代理和第三层代理加解密需要使用的两个脚本。

  

第一层代理的脚本，是先对进来的数据包进行解密，再对返回来的响应数据包进行加密。

  

第三层代理的脚本，是先对进来的数据包进行加密，再对响应的数据包进行解密。

  

**那么这两个脚本从何而来？**

 

对这个APP 进行反编译，去了解到APP相应的加解密算法。

  

现在比较流行的算法是RSA的算法和3DES算法，需要去反编译得知究竟是什么样的算法。同时要得到相对应的秘钥，这样才可以在这个过程中进行实时的加解密。

  

当我们拿到这个秘钥之后，一方面我们可以自己去实现相对应的加解密的算法，另一方面也可以去调用一些公开的库做一些相应的配置。拿到相应加解密请求的处理方法。

 

而第一层和第三层代理，各位可以选择自己比较熟悉的中间人的框架。这里个人推荐大家使用MITMproxy，基于python方便各位自己去写一些脚本做相应的处理。

 

这里插入一下前文提到的hook的方法，对应的我们可以把第一层代理给去掉，用hook的方式把加解密的代码处理掉，APP出来的请求是明文，回来的也是明文，加解密便透明化了。

 

但是如果我们采取这种方式的话，首先需要能够hook 这个APP，同时还要有相应的root操作。

  

**这样，这个方法就没有三层代理的框架更通用，所以我个人更加偏向于用三层的代理。**

  

只需要在APP端设置相应地址的代理，把相应的请求路由到第一层代理，中间就可以得到明文做相应的操作，我们实际去测的时候就发现，完全可以达到实时解密的效果。

 

下面简单讲一讲就是关键的几个参数怎么去设置。

![](../Images/3ff47d179b4adbcd233221990a51d6c1.png)

当我们写好脚本之后，第一层代理需要使用-U这个参数。通过这个参数，我们可以把相应的包转发给Burp开启的代理，同时在burp里面有相应的一个选项设置可以设置下一层代理。

  

我们把这一层的代理设置到第三层代理监听的端口，这样我们整个流程就通了，这样我们就达到了实时去修改数据包的这样一个效果。

  

**最终可以看效果图，一是没有使用三层代理之前，我们通过burp的看到的就是完全就是加密的数据包。二是我们使用了三层代理之后，在Burp看到的是已经解密好了的请求跟响应。**

**行长问答**

  

***以下内容为嘉宾分享后群内“提问环节”：***

1、apk 反编译怎么弄？

**答：使用dex2jar+jd-gui或者apktool**

  

2、第一次代理加解密有两种方法是吗？

**答：是的，可以加解密，也可以hook掉app的加解密，直接看明文**

  

3、反编译的方法

**答：（见1）**

  

4、能不能用apktool反编译？

**答：可以**

  

5、一个是反编译，一个是用MITMproxy？

**答：反编译主要是去找到app使用的加密或者签名的算法，mitmproxy是我们可以去做透明加解密的地方**

  

6、有没有逆向方面的教程推荐？

**答：可以看一些android的基础，然后再找一些书或者教程，我记得有一本android反编译方面的书**

  

7、能写成BP插件的形式吗？

**答：可以的**

  

8、MITMproxy怎么弄呢？

**答：pip install mitmproxy 安装的时候注意版本**

  

9、想问下如何寻找加解密算法进行反编译？

**答：先反编译，看看能否找到一些加解密的函数，如果不好找的话，就找发送http请求的代码，在那边比较容易找到相关的，或者搜索一些关键词**

  

10、能否反汇编解密看明文？

**答：反汇编之后你可以看到加解密的地方，一种是你可以直接hook掉函数，明文输出来看**

  

11、hook掉原api之后，发送到服务器的也是明文，而其原本接受密文，怎么样保证服务器能返回消息？

**答：这个就是我说的一种情况，这样就需要再加一层代理，就是我们这里的第3层代理来做透明的加解密，或者还有一种情况，是服务器低版本兼容，可以处理这种明文的情况**

  

12、能不能通过更改dalivk字节码的防止hook？

**答：可以写到so文件里面，这种hook难度更大**

  

13、（接12）写进so之后，只要在Python调用so库就可以了吗

**答：和python没关系的**
