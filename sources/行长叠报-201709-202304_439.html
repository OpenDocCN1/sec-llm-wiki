技术分析


当用户试图登录未启用的帐户(即root)时，系统将使用用户指定的任何密码创建该帐户，即使这个密码是空的。这就是为什么要在UI中执行这个攻击，必须多次点击“解锁”。


接下来让我们深♂入研究


当用户试图对这样的帐户进行身份验证时，这将由opendirectory守护进程(opendirectoryd)处理。由于时间的限制，我们将向前跳转一点来显示一个有用的callstack:


在收到mach XPC消息后，opendirectoryd调用odm_RecordVerifyPassword方法，该方法反过来调用od_verify_crypt_password。odm_RecordVerifyPassword方法在PlistFile二进制文件中实现。这是一个从/ System / Library / OpenDirectory / Modules / PlistFile.bundle加载到opendirectoryd的包。


从odm_RecordVerifyPassword函数开始，它调用一个未命名的方法“sub_826b”。这个子程序首先调用另一个辅助函数“sub_826b”，从用户试图登录的账户读取shadowhash数据。对于已启用的帐户，此读取将成功，因为此数据存在。


注意：这些数据可以通过dscl . -read /Users/<user>命令从终端查看，或直接从/private/var/db/dslocal/nodes/Default/users/<user>读取。


对于已禁用的帐户（例如正在作为目标的root帐户），此信息不存在，所以此功能将失败！ 


当未找到hash/shadow hash信息时，将会执行一个“else”子句。


在读取密码后，它会调用od_verify_crypt_password函数来验证用户输入的密码是否与该帐户的密码相匹配。 因此，如果我们尝试使用“hunter2”登录到（禁用的）root帐户，则会使用“*”和“hunter2”调用od_verify_crypt_password。


如果我们跨过这个调用，那么它就会在al中返回0x1 。


由于返回了非零值，执行继续调用各种方法，如sub_13d00。 正如在反编译中显示的调试日志语句，它们将执行从crypt密码到shadowhash或securetoken的升级：


found crypt password in user-record - upgrading to shadowhash or securetoken


但是，如果我们看看这些“upgrade”子程序是用什么来调用的，那就是我们提供的密码（即'hunter2'）！


这个密码(实际上是shadowhash / securetoken)被保存为帐户(即为root)。因此，用户现在可以登录了!


总结


  • 对于那些被禁用的帐户(例如，没有“shadowhash”数据)macOS将尝试进行升级


  • 升级过程中，od_verify_crypt_password返回非零值，并且未检查错误代码


  • 用户输入的密码将被“升级”并保存到该帐户


苹果公司现在已经修补了漏洞，并声明该错误是“证书验证中存在逻辑错误”。通过对PlistFile二进制文件的分析，我们可以看到它们扩展了错误检查来检测无效凭证。
