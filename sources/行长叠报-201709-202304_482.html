本次漏洞是iOS的远程代码执行漏洞（CVE-2017-7115），可影响iOS设备上的Wi-Fi功能，经修复后，可使WiFi芯片的恶意代码执行受限。


苹果公司的WiFi芯片由博通公司（Broadcom）生产，该公司的芯片主要用于处理PHY和MAC层处理的Wi-Fi  Hard MAC SoC。

 
这些芯片主要安装在移动设备和Wi-Fi路由器中，并且能够在不委托主机操作系统的情况下处理许多Wi-Fi上的问题。


在iOS上，Apple BCMWLAN Bus Interface PCIe驱动程序被用来处理与Wi-Fi SoC（也称为加密狗）的PCIe接口和低级通信协议。


类似地，Apple BCMWLAN Core驱动程序被用来处理高级协议和Wi-Fi配置。
 

主机和加密狗的彼此通信

主机和加密狗使用一组“消息环”彼此通信。两个消息环用于将数据从主机传输到加密狗（H2D）：


  -H2D_MSGRING_CONTROL_SUBMIT （Ring #0）


  -H2D_MSGRING_RXPOST_SUBMIT  （Ring #1）


当主机希望通知加密狗某个事件（例如提交IO控制请求或发布可写入RX帧的地址）时，它会将小结构写入适当的消息环缓冲区，以此来实现当前写入的索引。


类似地，当从任何完成环（D2H）读取事件时，主机会去使用当前环的读取索引，以便通过环内的加密狗访问发布的消息缓冲区。


每个环都有他们固定的“项目大小”，这个项目大小会在环初的始化期间设置 ——单个项目的环内地址可以这样计算“ring_base + ring_index * item_size”。
 
当Wi-Fi加密狗通过PCIe连接到主机时，就可以向Root Complex发出IO请求。


如何防止恶意加密狗

为了防止恶意加密狗覆盖任意物理内存，甚至颠覆主机操作系统的情况，需要在设备可见的IO空间和主机的物理地址空间之间进行隔离。


这一般通过在iOS上安装被称为“设备地址解析表”（DART）的IOMMU来实现。
 
在iOS系统上，每个环（H2D和D2H）的读取和写入索引通过映射到IO空间，来实现对等体之间进行的同步 。


这样，通信的每一边都可以自由访问R / W指数并且知道下一个缓冲区将在哪里发布（由其本身或由其对等体）。


Apple BCMWLAN Bus Interface PCIe驱动程序把这些IO空间地址提交到Wi-Fi芯片中的RAM中，也就是RAM的PCIe共享结构中，然后直接写入芯片的TCM。

如何利用漏洞

利用这个漏洞的方法之一，是触发将OOB写入DART的转换表，从而有效地将映射添加到芯片的IO空间。


如果攻击者可以将DART的转换表本身添加到DART映射中，就可以自由添加内存映射，从而允许任意R / W进入内核的物理地址空间。

 
实际上，通过找到DART的转换表并进行逆向工程，我们可以找到DART描述符与环基地址相关的位置。

  Ring #1 - Base: 0xFFFFFFE0B0DE8000
  Ring #2 - Base: 0xFFFFFFE0B0DEC000
  Ring #3 - Base: 0xFFFFFFE0B0CC4000
  Ring #4 - Base: 0xFFFFFFE0B0CD0000
  DART:
    First Level Descriptor: 0xFFFFFFE02BB4000
      Second Level Descriptor: 0xFFFFFFE0B0CD4000
      ...
 
如上所述，DART的第二级描述符被放置在环＃0（H2D_MSGRING_CONTROL_SUBMIT）的范围内，这就允许攻击者向DART映射添加条目。


此外，即使Wi-Fi芯片或驱动程序遇到错误导致芯片重置，DART中添加的映射也不会被清除。


因此，之后利用芯片的尝试仍会包含恶意的IO-Space映射。


对策

1

由于索引永远不能大于16位。因此，处理大于此值的值时，就不需要过分担心了。


可以通过将索引类型更改为16位宽类型而不是32位来减少风险。


2

完全不需要将H2D指数映射为可写：

  • 如果DART支持只读映射，我建议将索引映射为本身。 
     

  • 否则，索引应该在每次迭代时只能从共享区域*once*读取，而不是在几个“helper”函数中重新读取索引。


3

提交和完成环中的索引应根据环的最大索引（this+ 88）进行验证，而不是针对最大可能值（0xFFFF）进行验证。


4

清除芯片复位时的所有DART映射。
