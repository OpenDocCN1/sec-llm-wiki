# 姿势1:CSRF Token Tracker

CSRF Token Tracker是个插件,可以在BApp Store下载安装

![](../Images/79cf39db0aaaae67aea3c888db3faaaf.png)  

这种方式可以说是最简单的,但是不适用姿势2和姿势3中的案例  
现有一个请求参数是user\_token

  
![](../Images/dad1429dc87f631c24c07b756202d246.png)  
  

只需要在插件中添加  
![](../Images/579a901880c8daed6d52fdc4e3c40881.png)

  

注意这里有个坑(搞了好久)  
比如你想在repeater模块测试一下重新发送请求会不会修改密码  
![](../Images/a47f7398ce8b45abb0a1ec08a46db1b2.png)  
  

发现返回的结果仍然是302  
这里是需要有一个有效的,没有使用过的user\_token去请求的!  
然后再去重放请求包就都会自动更新token了  
总结一句就是你第一次用有效的token重放请求包就永远有效(自动更新token了)  
你第一次用无效的token重放请求包就永远无效

# 姿势3:宏+Extractor

在这个案例中前两种姿势均无效  
下载安装插件

![](../Images/bf82793e0fe64bc3b1b48d2ae0e0c14c.png)

先看下两个请求包  
第一个请求包就是获取token的

![](../Images/d3bd8412e5abf01faa3d2f57003f823c.png)

第二个就是带着token去访问

![](../Images/b9943d53e93442d5e73e67c4db67f41b.png)

看过这两个请求包应该就明白了  
这次token是在请求头中  
而定义宏的时候会让你选择更新token的地方  
这个地方却没有更新请求头的功能  
所以姿势2在这里就失效了  
![](../Images/5570d9b94682a302de7f1032718d4f51.png)

首先定义宏获取token  
这个宏只需要要确保在请求2之前会执行请求1  
相比于姿势2的步骤简单一点

![](../Images/d9567db076ed2a611ab7d15060597a39.png)

![](../Images/8edd9c92a048af46e4432e0a96799dba.png)

![](../Images/2b382cd38ab0c9cc3f1c4def6c0c8115.png)

到这里宏就配置好了  
在repeater重放请求2然后再logger+=里面查看  
确保每次都会在请求2前自动执行请求1就是正常的

![](../Images/e67a4b8b190cab276bd5d61bdb312979.png)

然后配置插件Extractor  
把两个请求包都发送到Extractor

  

![](../Images/3b8be2570a2a5a9e4228301ad6f8fe3f.png)

![](../Images/a9b7f47b4df39842a8869a9a7236cafd.png)

![](../Images/f5fd1b467d5543e5ac18dce9c82a0c16.png)

此时回到repeater模块重放发现token就有效了

  

![](../Images/a03343811dd944a9110f1065bddb3990.png)

再次回到logger++看发生了什么  
看到第87个请求获取的token值为407667d008b147199d174681a655aea0

  

![](../Images/8c5fa2f0433d267af8347504c60a7bc2.png)

第88个请求包的accessToken值也是407667d008b147199d174681a655aea0

  

![](../Images/9f6736eaac8fb6a84b165f1265bdfe74.png)

总结一下姿势3的思路  
宏负责在请求2前发送请求1  
Extractor插件负责匹配和替换token
