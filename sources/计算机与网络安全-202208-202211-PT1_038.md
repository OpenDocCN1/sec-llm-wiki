**2022云原生安全报告**

▼

为保证工作负载（workloads）在可控的范围内，我们需要对漏洞、配置、权限和运行时威胁进行检测。检测期间，我们在生产环境中看到大量易受攻击的容器，许多暴露的云存储实例，以及许多与威胁事件有关的实例。

  

由于 Kubernetes 部署环境的短暂性，获得关于 Kubernetes 部署环境的准确容量信息是一项艰巨的挑战。本报告中显示了超过 50% 的容器没有定义 CPU 或内存限制，这可能会导致性能问题和成本超支。今年，随着容器密度再次增长，企业正在转向 Prometheus，并将其作为监控基础设施和应用程序的标准解决方案。与此同时，客户对 Prometheus 指标的使用率达到了 83%。对于 Falco 和 Prometheus 的快速发展，表明了企业用户对开源和开 放标准的偏爱。

  

在报告中，您将看到关于安全性、合规性、服务、告警和 Kubernetes 使用方法的详细信息。这些信息来自全世界各行各业的公司，对掌握容器环境的真实安全状态和使用情况非常有用。

  

随着团队将容器工作负载（workloads）转移到生产环境中，他们意识到需要将安全性和合规性集成到 DevOps 工作流程中。“安全左移”已成为云原生打工人的口头语，它指的是尽早发现软件缺陷，以避免部署不安全的工作负载。扫描漏洞是该工作流的关键组成部分，尤其是从公共镜像仓库中拉取镜像的时候。我们的数据还强调了严格的运行时策略，和需要重新评估持续运行的工作负载，以考虑配置漂移、之前未披露的漏洞或次优的配置等情况，以降低风险。

  

无论容器镜像来自私有镜像仓库还是公共镜像仓库，在将其部署到生产环境之前，扫描它们并识别已知的漏洞是至关重要的。我们评估了客户针对操作系统和非操作系统部署的所有镜像，发现操作系统镜像的缺陷比非操作系统镜像的缺陷少，这大概是因为它们通常由行业供应商支持和维护。

  

我们注意到 4 % 的操作系统漏洞是“高危”或“严重”的。尽管这个值看起来很低，但如果 OS 漏洞被利用，它可能会损害整个镜像并导致应用程序崩溃。此外，操作系统漏洞可能有一个非常大的影响半径，因为许多不同的工作负载可能会同时受到影响。

  

一般团队不会检查第三方库中的漏洞。我们发现 56 % 的非操作系统包有“高危”或“严重”的漏洞。开发人员可能会在不知不觉中从非操作系统的开源包(如 Python、PIP 或 Ruby Gem)中引入漏洞，并引入安全风险。获取第三方包的依赖关系，并确定它们是否真正无漏洞是一个巨大的挑战。若优先考虑运行时的上下文关系，可以帮助团队解决一些最紧急的漏洞。

  

随着容器应用数量的激增，企业努力在生产前和生产后的实施中总结最佳实践。漏洞只是云安全的一部分。即使在漏洞完全修复的工作负载上，不安全的配置也会产生严重的安全问题。此外，一旦将工作负载部署到生产环境中，团队仍然需要能够检测到某些异常行为，并实时触发安全警报，以应对潜在的威胁。

  

容器技术在应用交付中的作用日益显著。随着 DevOps 团队对 Kubernetes 关注度的提高，我们非常高兴地看到团队在构建过程中贯彻和落实安全规范。然而，还需要做更多的工作来保护容器和云服务，以防止可能的漏洞进入生产环境。运行时威胁检测将继续是保护云环境的关键，因为即使是最健壮的程序也无法解决所有的软件漏洞和错误配置。报告中主要强调了容器环境的持续增长，以及对一些容器开源解决方案的依赖逐渐增加：

  

1）云环境和容器的广泛应用也导致了许多不安全的行为，比如容器以 root 权限运行、云账号运行的容器拥有过多的特权。然而，Falco 的持续增长表明，各企业正在利用云安全工具试图降低风险。

  

2）在 Kubernetes 环境中容量的规划实践起来并不简单。只有通过适当的容器资源限制和持续监控，企业才能确保他们的应用程序不会超出预算或减少性能问题。

  

3）随着企业将工作负载转移到云计算资源上，Kubernetes 和容器的环境带来了持续的增长。使用像 Prometheus 这样 的开放标准并坚持安全最佳实践，是降低应用程序的风险的关键所在。
