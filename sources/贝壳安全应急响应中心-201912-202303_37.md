# 技术分享｜贝壳零信任安全的背景和选型

**01**

**贝壳面临的网络安全挑战**

  

从整体来看，贝壳企业信息安全除了需要面对监管合规要求、传统的安全威胁之外，还有自身产业特点所带来的挑战。

**①贝壳网络接入点多：**贝壳拥有数千链家门店、数百职场、数十万经纪人员工，导致网络接入点多、业务访问情况复杂，给网络的访问控制增加了很大的难度。  

  

**②贝壳的对外合作多：**贝壳在整个居住领域要扩展新的赛道、要链接更多的服务，对内部服务的对外开放灵活性也有了更多效率上的期待。

  

**③作业过程高度依赖核心敏感数据：**经纪人作业过程中、对外交互时涉及很多核心敏感数据，数据可能散落在各个网络接入点中，数据的边界是相对模糊的。

![](../Images/479952717f24c67eaec208af878e47a2.png)

  

**02**

**传统网络安全架构**

  

传统的解决方案，一般会形成如下的架构。

![](../Images/95c98804e407bd490a2b985771dd10d6.png)

防火墙会被放置在网络边界，比如IDC网络和互联网、办公网到IDC之间，用于对跨边界的IP-端口级别（俗称4层）流量进行访问控制。  

  

WAF(Web Application Firewall)通常会作为7层防火墙串联在web服务的接入层中，对常见的web漏洞攻击特征进行检测并作出阻断封禁的动作。

  

在各个主要的网络边界还会放置入侵检测设备，基于网络流量识别攻击行为。

  

这些安全产品能够比较好地解决外网威胁，因为通常一个企业需要对外暴露的服务端口会比较有限，并且大部分都是web服务。

  

**但传统的安全架构不适用于贝壳的网络环境。**

  

内网通常由IDC网络和办公网组成，两者通过专线打通。内网通常会被认为是安全且干净的网络而疏于防护，防火墙等安全策略也会制定的较为松散。内网就像企业安全的阿喀琉斯之踵，你只要进入到了内网中，就很容易长驱直入，直捣敏感数据。

  

那么是否可以通过在这样的架构基础上实施严格的安全策略来提高安全性呢？理论上是可行的，但是会面临许多问题。

**1、控制粒度粗**

首先是防火墙的控制粒度就是IP-端口，这样网络层级上的限制导致了控制粒度天然是比较粗的，所以最多只能做到从原来的门户大开变成只开了一个个小城门，而所有人依然可以通过这些城门进入到城堡。

  

而如果要让业务的维度匹配防火墙的控制粒度，让一个IP-端口对应一个域名，则业务的效率、网络的弹性又会大大降低，在贝壳这样的业务体量下是不会被接受的。

  

**2、无法识别数据流转**

由于只有网络层的信息，难以识别业务系统维度的数据流转，更无法针对系统进行控制。

  

**3、低效**  

传统的方案对于业务的开放，比如内部服务要开放到公网，只能依赖业务case by case的改造，在效率上安全帮不了什么忙。

  

**4、高成本**

这样的方案往往还意味着成本，在接入点多且分散的情况下，往往需要大量的防火墙来建立边界控制。

  

因此，只采用这样的方案在贝壳将很难达到理想的控制效果和效率之间的平衡。

  

**03**

**贝壳安全的方案选型**

  

安全的本质是信任问题，而在内网中核心的解决理念是4A(账号、认证、鉴权、审计)，即通过账号标识一个访问主体的身份、通过认证识别主体身份、通过鉴权判断主体有相应的访问权限、同时在整个过程中具备审计能力。

  

我们希望有一个方案既能够实现4A，又能够适应贝壳内部的场景，而这其实就是谷歌从2011年开始实践的零信任模型。

  

简单来讲，零信任模型期望没有任何人、设备或者网络是默认可信的，在没有隐式信任的前提下就需要通过身份认证、持续的风险评估以及显式的授权才能访问到内部业务系统，同时在整个过程中是可审计的。

![](../Images/64abd1e358ebb96ff03af03ae228fa50.png)

零信任也并不是一种全新的产品，并不否定传统的防火墙、WAF这类安全产品，而是在传统的基础之上，通过多种安全能力组合形成的综合解决方案。

  

贝壳在员工体量大的情况下很难像谷歌一样做到浏览器的统一，以及存在非web服务的访问需求，因此我们主要通过网关+agent的方式支撑访问需求，形成如下图的零信任架构，并支撑更高级的安全建设目标（权限得到有效治理、高效的无边界网络、动态的风控策略）。

![](../Images/08d7427964ac63a7d28a539727d17540.png)

相比传统方案，其效果就像在城门加设了人脸识别的门禁，每一个人都需要认证后才能进入城内。并且在城内的每一户人家都有统一的二道门禁，门禁都联到了统一的控制中心，在保证安全强度的同时还能实时对策略进行调整。同时城内人员的行为都能够被记录，从而事中能够发现不法行为、事后能够留痕取证。

  

通过这样的零信任架构，能够满足合规要求、降低安全风险，同时安全的控制更加内生化、更具扩展性，能够适应未来的服务开放趋势，并以此为基础实现权限的统一管控、灵活的控制策略。

  

**其主要包括以下基础模块：**

**灵活可扩展的安全网关**

通常企业内部都会有自己的负载均衡网关，我们可以将零信任的能力与负载均衡结合，形成具备安全特性的web网关。  

  

网关通过和SSO系统联动，强制基于SSO认证的结果进行鉴权，权限则会在零信任平台中实现统一的配置。这样的好处是能够保证权限控制的统一性和强制性，业务系统可以不需要改造就实现URL级的权限控制。而防火墙则使访问流量尽可能的收敛到网关和堡垒机，网关和堡垒机分别实现了员工到服务和服务器访问的4A。网关中心化的控制方式，能够避免网络接入点多导致的近源部署分散问题。相比硬件安全设备，软件的部署成本低，扩展起来会比较灵活。

  

对于需要开放到公网的内部业务系统，也可以将其域名解析到公网的零信任web网关上，通过平台配置限制允许访问的账号、IP、安全基线、认证方式等策略，而不需要业务线做代码层面的改造，也避免了业务实现安全机制的缺陷。这样很大程度上能够提高业务开放的效率，同时保障了安全机制的有效性。

  

**终端风险识别**

在办公终端上，我们还需要有相应的agent来解决终端风险识别和访问代理通道的问题，来达到终端可信的状态。通过agent可以识别PC中毒、不满足安全配置基线这些安全风险，对于高风险的设备禁止访问内部业务系统，从而防止PC被远控之后窃取数据的情况发生。由于web网关只能支撑HTTP流量的访问，因此还需要agent承担4层访问代理的能力，和VPN的区别在于VPN通常支持的策略控制有限并且不灵活，而零信任的agent可以将控制策略细化到账号-设备-业务系统的维度。

  

**基于主机的细粒度控制**

类似的思路我们可以应用到IDC中，只不过访问主体变成了服务器。IDC内服务之间的访问，通常有两种访问模式，一种是访问经过网关，网关反向代理后端服务，这种模式我们同样在网关上进行集中的控制；第二种是点对点的访问，服务之间的直接访问，比如RPC服务。

  

针对点对点的访问场景，我们需要通过服务器上的agent来实现4A，认证鉴权的主体可以是IP或者服务标识。在物理机的场景agent是部署在物理机中，在云原生的场景下agent是以sidecar的形式部署，从而使得网络的边界可以从大的网络区域缩小到主机、服务，实现粒度更细的微隔离。

  

**04**

**贝壳零信任的实施路线**

  

具体的实现细节我们将在后续的文章中分别展开，在此简要介绍主要的实施路线（如图中标号所示）。

![](../Images/2dcb21cea3f953122be3044301979633.png)

从零信任要支撑的几个上层安全建设目标来看，权限的治理和动态风险控制都依赖统一的安全控制抓手，而统一的接入层网关则是强有力的抓手，因此网关的能力需要前置建设。而网络无边界的目标，则需要终端agent的支持，才有可能实现全流量的代理。安全的建设通常是由外到内的，主机agent的建设、部署周期也较长，所以我们放到后期实现。

**web安全网关**

由于内部系统大部分都是web服务，因此我们首先构建针对web服务的零信任网关，通过网关实现对web服务访问的收口，这样能够优先解决大头的安全风险。而零信任安全平台则是统一的控制台，提供策略配置和管理的入口。

  

**权限治理**

在有了基本的权限控制之后，权限的合理配置成为了新的问题。将业务系统的权限收敛到最小可用的范围，是一个权限治理的过程。权限治理主要通过对权限管理制度的明确、权限配置owner意识的宣贯以及对权限使用情况的审计来让权限无限趋近于最小可用的理想状态。

  

**终端可信**

为了获得更丰富的终端安全风险信息，以及支持非web服务的访问，我们就需要建设终端agent了。当然配套的也还有4层的网关，终端agent会和网关结合，构成4层+7层的4A能力，使得我们可以实现账号-设备-业务系统维度的策略控制。  

  

**动态风险控制**

在有了静态的认证、风险识别和控制能力之后，我们可以通过各个模块之间的有效联动，根据用户的终端状况、行为审计得出其风险状况，根据其风险状况要求作出安全响应（比如更换安全的设备、进一步认证身份），否则不允许访问相应的业务系统。通过这样的动态控制，能够避免静态策略的局限，更全面地判断当前访问者的风险状况，进一步提高安全水位。  

  

**网络无边界**

对于常用的内部业务系统，我们可以逐步借助零信任的安全能力开放到公网，提升员工的访问效率和体验。最终希望能够达到不区分内外网，在任何环境下都能够访问内部系统的无边界网络状态。  

  

**IDC微隔离**

最后是将同样的思路应用到IDC中，通过agent实现主机和主机之间访问的4A。  

  

当然这只是我们大概的实施路线，其顺序也并不都是严格依赖的，在实际的建设过程中，部分能力也会并行开展。

  

**05**

**写在最后**

  

零信任是业界在持续探索的安全理念，在过去一年的落地探索中，我们通过零信任的建设有效降低了贝壳系统性安全风险，在后续的建设中也期待给大家带来更多效率的提升。
