VaultHSM：OpenPGP智能卡中确定性 ECDSA的测试方法

  

背景

DSA 型签名算法（包括 ECDSA）的原始实现中需要一个和私钥属于同种数学对象（GF(p) 的元素，p 为素数）的随机数，该随机数必须同时满足以下三个性质：

  

         1.随机性：无法仅通过被签名数据（以下称“载荷”）和生成的签名推算出来。

         2.机密性：不可泄露到签名过程之外。

         3.唯一性：该随机数对不同的载荷必须不同。

        

否则，攻击者将有可能通过载荷与签名推算出私钥。

  

如果该随机数来自一个有缺陷的随机数发生器，则随机性和唯一性会变得难以保证——攻击者可能通过收集足够多的载荷——签名对找到随机数发生器的规律，进而推算出私钥，虽然行业用户认为这是“可忍受”的缺陷直到LadderLeak漏洞的公开披露彻底让真相浮出水面，在最坏的情况下，攻击者只需要付出30万美金就可以破解P-224的密钥。  

  

![](../Images/ce9b5e55ffcb4b4b1ede6b72876dece3.png)

![](../Images/3937504a38cab3410d0851f58fc745e6.png)

在后LadderLeak时代选择忽视这个问题是不明智的，解决该问题的方法之一是由私钥和载荷的散列值以不可逆的算法（如散列算法或消息认证码算法）确定性地派生该“随机数”：私钥参与导出过程保证了性质 1 和 3，只要私钥本身不泄露。该方法已被标准化为RFC 6979，并被 libgcrypt 默认用于自身实现的 (EC)DSA 算法上。另外 EdDSA 则完全不使用随机数发生器，中间用到的“随机数”完全由私钥和载荷的散列值确定性地派生而出。

  

GnuPG 2 使用 libgcrypt，故其 (EC)DSA 算法的实现理应符合 RFC 6979，但只有使用存储在磁盘上的私钥时，GnuPG 才会完整地使用 libgcrypt 中的实现；如果私钥在储存于 OpenPGP Card 中，则与私钥有关的运算是在智能卡中完成的，与 libgcrypt 无关。

  

如果不能保证随机数发生器没有缺陷，则任何不符合 RFC 6979 的 (EC)DSA 实现都有通过上述问题泄露私钥的可能。因此，只有当智能卡提供的 (EC)DSA 实现确实符合 RFC 6979 时，我们才应该考虑使用它。

  

检验过程及结果

gpg 有个 \--faked-system-time 选项可用于固定签名中的时间戳（其中 ${TIMESTAMP} 不能超出子钥的有效期）：

  

         $ gpg -u ${SUBKEY\_ID}! -bo payload.sig --faked-system-time ${TIMESTAMP} payload

  

如果一个算法本身是完全确定的（所有输入都是用户可控的，且输出由输入唯一决定），则在时间戳、载荷、私钥三者不变的情况下，生成的签名应该完全相同。所以，如果一个 (EC)DSA 实现会在时间戳、载荷、私钥三者不变的情况仍然输出不同的签名，则该实现一定不符合 RFC 6979。

“payload” 为随机生成的载荷；带有字母 c 的为用卡中的私钥生成的签名；带有字母 d 的为用磁盘上的私钥生成的签名。

  

可见，固定时间戳后，无论使用磁盘上还是卡中的 rsa 私钥，在时间戳、载荷、私钥三者不变的情况下，的确会生成完全相同的签名，从侧面印证了这种判断方法的有效性。

  

磁盘上的 ecdsa 私钥也能生成不变的签名，但当使用卡中的 ecdsa 私钥时，砸在时间戳、载荷、私钥三者不变的情况下生成的签名不同，说明 gpg 在使用磁盘上的 ecdsa 私钥时使用的 ECDSA 实现是有确定性的；但该卡中的实现无确定性。

  

展望

如果确认了卡上的 (EC)DSA 算法实现有确定性还应进一步检测其实现是否符合 RFC 6979，方法是在时间戳固定的情况下，用同一把私钥分别在磁盘上和卡上对同一载荷生成签名，如果卡上的实现符合 RFC 6979，两种过程生成的签名应该相同。

  

总结

在 EdDSA 尚未在智能卡上普及的今天，我们应只在确认了其实现符合 RFC 6979 的智能卡上使用 (EC)DSA 算法来签名，否则，还是应该使用没有类似非确定性 (EC)DSA 算法的问题的 RSA 算法来做签名。

  

上述结论仅适用于签名。如果智能卡支持 ECC，则使用椭圆曲线型的密钥对来加解密是没有问题的。这种情况下，算法的非对称阶段会以 ECIES的方式进行，与 RSA 相比还多了来自 DH 的随机性，使得选择明文攻击更难奏效。

  

在应用 DH 的系统中，随机性对签名算法来说是个问题，处理不好可能泄露私钥；但对加密来说却会带来额外的优势。

  

防御手段

长期解决方案是等待 EdDSA 的标准化进入FIPS-186-5。在开源项目实现（如 OpenSSL）中，确定性 ECDSA 的实现推进并不如预期的顺利：

\* 确保所有你使用的证书是>= P-256或者RSA（有其他风险需要考量）

\* 不要漏掉没有接入互联网的服务

附录

为了避免测试过程对本地的 \`~/.gnupg/\` 目录造成干扰，建议在该处挂载一个 tmpfs 专用于测试：

  

$ killall gpg-agent

$ su root

\# mount tmpfs ${YOUR\_HOME}/.gnupg/ -t tmpfs -o nodev,nosuid,noexec,mode=0700

\# chown ${YOUR\_USERNAME}:${YOUR\_GROUP} ${YOUR\_HOME}/.gnupg/  

  

此后按照标准的 GnuPG 用法生成私钥并测试即可。完成测试后，可删除全部内容并卸载该 tmpfs：

$ killall gpg-agent

$ find ~/.gnupg -type f -exec shred -v {} \\;

$ su root

\# umount ${YOUR\_HOME}/.gnupg/
