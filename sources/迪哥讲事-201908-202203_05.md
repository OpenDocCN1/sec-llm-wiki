## 背景 

这个漏洞是joaxcar这个小哥发现的,2021年10月底提交的,也是一个权限方面的漏洞: 任何合并请求的author或assignee都可以批准该合并请求的外部状态检查。这包括具有Guest访问权限的用户，这些用户通过电子邮件或项目的一个分支创建MR。它还包括将具有Guest或Reporter访问权限的用户分配给MR，这在公共项目中并不少见。外部状态检查文档没有提供关于该特性如何工作的太多信息。但是开发人员的讨论和单元测试表明，批准外部状态检查应该限制在至少有开发人员访问项目的用户。下面是相对应的单元测试:

```
describe 'permissions' do
  do
  external_status_checks: true
)  end

```

为了验证发出请求的用户是否为developer+; 他们设置了一个身份验证块检查，如果用户有权限使用名为find\_merge\_request\_with\_access的函数,那么就可以以这种方式响应外部状态检查;

```
merge_request = find_merge_request_with_access(params[:merge_request_iid], :approve_merge_request
)
```

检查`:approve_merge_request`是否只为开发人员及其以上权限的人所启用。但事实证明，具有update_merge_request权限的用户也启用了该权限。在`https://gitlab.com/gitlab-org/gitlab/-/blob/master/app/policies/merge_request_policy.rb`中有这样一条规则:

```


 rule { can?(:update_merge_request) }.policy do  
```

这为任何被允许更新mr的人提供了权限。在`https://gitlab.com/gitlab-org/gitlab/-/blob/master/app/policies/issuable_policy.rb`中存在这条规则:

```


rule { can?(:guest_access) & assignee_or_author }.policy do  
```

分析到这里,可以知道拥有`guest_access`权限的`assignee`或者`author`都可以使用`update_merge_request`这个函数;这是这个漏洞产生的根源;

## 复现步骤 

1.创建两个用户owner01和guest01

2.以owner01的身份登录，并通过访问`https://gitlab.com/projects/new#blank_project`创建一个公共项目project01，并记录下项目ID

3.转到项目设置页面`https://gitlab.com/owner01/project01/edit`，展开标签合并请求，向下滚动到外部状态检查;

4.使用任意名称和端点创建状态检查，并保留;

5.登出并以“guest01”身份登录

6.转到项目页面`https://gitlab.com/owner01/project01`，用fork按钮创建一个fork，命名为fork01。

7.当fork被创建时，在fork `https://gitlab.com/guest01/fork01/-/branches/new`中创建一个名为new_branch的新分支

8.当fork被直接创建时，点击选项“create a merge request”，在“New merge request”页面中，点击Change branches并选择目标分支作为原始project01上的任何分支;

9.单击“创建”，应该在project01中创建一个新的MR(这是一个客户贡献和一个正常的开源流程，但请注意，guest01用户不是project01的成员)。

10.访问`https://gitlab.com/-/profile/personal_access_tokens`并为guest01的API创建一个访问令牌

11.打开终端并发出此请求以获取状态检查的ID(用户project01 ID和MR IID，可能是1和guest01令牌)，记录状态检查返回的ID

```

curl "https://gitlab.joaxcar.com/api/v4/projects/<PROJECT_ID>/merge_requests/<MR_IID>/status_checks" -H "Authorization: Bearer <TOKEN>"
```

12.发送此请求来检查SHA，该请求将失败，并将消息告诉你使用哪个SHA，在此请求中，我们使用一个假的SHA=a(确保将CHECK\_ID替换为步骤11中找到的ID)

```


curl --request POST \  
```

13.现在，在这个请求中使用返回的SHA来最终“批准”MR的状态检查

```


curl --request POST \  
```

14.转到MR页面:`https://gitlab.com/owner01/project01/-/merge_requests/1`,验证状态检查现在是绿色的并已检查过;

## 影响 

Guest(或Reporter)用户可以发送确认消息来“批准”MR的外部状态检查，其中用户要么是author，要么是assignee。这使得恶意用户有可能在项目中“欺骗”接受MR，而用户本不应该这样做;
