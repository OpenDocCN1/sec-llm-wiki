## 背景 

小哥jimeno在前年12月份向gitlab提交了此漏洞,这个漏洞主要阐述的是:攻击者通过改变GraphQL请求让MR(Merge Request)创建者(其实就是前面的攻击者)绕过锁定的状态;

## 前言 

在看这个漏洞之前首先看一看这里的官方文档以及关于什么是锁定讨论以及如何锁定/解锁讨论的官方文档

注意点: 下面是在仓库所有者(即受害者，naaytesting)锁定MR之前，攻击者(jimen0)配置文件查看MR状态的截图。正如你所看到的，可以解决讨论线程。在所有者锁定MR之后，就不可能这样做了。

![](../Images/274a93e69dd5449191ccaf9587d0fad3.png)

## 场景建立 

1.受害者创建一个公共存储库，并添加一个虚拟文件;

2.攻击者fork项目并添加更改

3.攻击者提交合并请求

4.任何一个人都可以随机添加评论，以便生成讨论线程

5.受害者:锁定合并请求(注意攻击者无法(取消)解决现有的讨论)

![](../Images/8dafbb0c16ee4d5fed75493c1981b679.png)

## 复现步骤 

1.攻击者是不能通过用户界面发布新的评论或解决讨论线程的

![](../Images/3a169c8fc8363169726c2044860608b8.png)

2.攻击者:运行以下GraphQL查询来查找讨论线程的ID。(你在复现的时候请在需要的地方替换相对应的参数)

```


{  
```

3.攻击者:注意讨论ID(这里应该指的是讨论线程的ID)。在当前这个例子中，它是`gid://gitlab/DiffDiscussion/da18f8200f0934b43fd1d1f62d5ea1a8dec2e1a8`。注意，当UI显示MR被完全锁定且不允许(取消)解析时，它的可解析属性被设置为true。

4.运行以下GraphQL查询，注意:你自己测试的时候用你自己的id。

```


mutation test {  
```

5.受害者:刷新MR并注意到攻击者能够对其执行活动，现在讨论就会结束。
