# 某黑客组织对越南政府的APT攻击样本

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzUyMzczNzUyNQ==&mid=2247484370&idx=3&sn=474082fbe7b0c79f919d797115f55020&chksm=fa394308cd4eca1eda34eaf6dc5472ef0bcaf393075c9575d06b56ce7279f1668c998a3dce12&scene=126&sessionid=1681376514#rd](http://mp.weixin.qq.com/s?__biz=MzUyMzczNzUyNQ==&mid=2247484370&idx=3&sn=474082fbe7b0c79f919d797115f55020&chksm=fa394308cd4eca1eda34eaf6dc5472ef0bcaf393075c9575d06b56ce7279f1668c998a3dce12&scene=126&sessionid=1681376514#rd)

近日，法国安全研究者兼BotConf和FastIR公司创始人Sebastien Larinier，针对RTF文档相关的CVE-2017–11882漏洞利用专门制作了一条YARA规则，来捕获攻击线索。经过海量数据比对，他发现了一个用来执行APT攻击的恶意RTF文档样本，其中的内容和越南岘港市海洲郡的建设项目相关，文档标题为《Chương trình hoạt động cnit 2018》。据Sebastien Larinier声称，按照该恶意文档表现出来的各项行为指标和特征值，他怀疑该APT攻击文档的幕后使用者为中国的黑客组织1937CN。

本文中，Sebastien Larinier着重描述了该恶意文档的感染攻击机制、网络攻击架构以及攻击者采用的相关TTPs技术。

## ![](../Images/3527b2068afecc82f2af65bd07908c65.png)感染攻击链

Joe sandbox 在线沙盒分析网站对该文档的详细感染行为给出了很好的描述：

![](../Images/8cde1c6649c473b8c87d1d7dc1aa9331.png)该恶意RTF文档利用漏洞会向目标操作系统中写入以下两个文件：

> 一个名为 RasTls.dll 的dll文件
> 
> 一个名为dascgosrky.exe的可执行文件

## RTF文档分析

在Python的RTF分析工具rtfobj帮助下，可以发现恶意RTF文档中的三个ole对象：一个类名为package的ole对象，以及另两个不良结构的ole对象。

![](../Images/da9cd78fb15f054e85432c0fbdc1056b.png)在名为package的ole对象中，存在一个8.t文件的加载路径：

![](../Images/8301e453b380a0f55fa1ed594cf372dc.png)这种技术看似是用来执行 .sct 格式文件，以向网络下载一个可执行程序，植入到目标操作系统中。McAfee安全实验室曾用 .sct文件为样本对这种技术进行过分析。这种技术由于简单有效，并且支持Office相关文档，屡次被很多攻击者进行了在野利用。这以上路径中，可以看到，RTF文档会从系统%TMP% 目录中加载一个 8.t 文件。经分析，8.t 文件为一个加密文件：

![](../Images/fb46b2e4681e0c83ce42bf61843bda5b.png)经检查，另两个不良结构的ole对象为涉及“Equation Native”流的ole公式对象，其中可以看到CVE-2017–11882漏洞利用的影子：

![](../Images/6b837e289ab2032534cb6740258d2f0d.png)ole对象末尾，能看到很多API接口的runPE技术调用，这样恶意程序会挂起一个系统进程，并在其中注入恶意执行代码。另外，还发现了对象开始处的有意思的字符串： 7e079a2524fa63a55fbcfe：

![](../Images/4eb7c4ee3df3f0048b99c18d1a3d4a9f.png)该字符串曾在“响尾蛇”APT攻击的ole公式对象中出现过，可能攻击者都使用了同一套恶意程序组装工具。现在有了加载文件8.t ，以及runPE技术的确定。接下来，需要来做更深入的shellcode分析。

## 逆向ShellCode

在分析伊始，Sebastien认为 Winword.exe 会调用 CreateProcess 函数来创建EQNEDT32.exe进程，所以他决定在CreateProcess 函数的调用处设置一个断点。

但是，后来发现，EQNEDT32.exe 进程是由Winword.exe利用COM Object对象调用的，并不是由 CreateProcess 函数来创建的，而且Winword.exe也不是EQNEDT32.exe的父进程。所以，只好在EQNEDT32.exe启动时附加上调试器。为此，可以采用映像劫持（Image File Execution Options,IFEO）方法来进行分析。

> 所谓的映像劫持（IFEO）就是Image File Execution Options，位于注册表的 HKEY\_LOCAL\_MACHINE\\SOFTWARE\\Microsoft\\Windows NT\\CurrentVersion\\Image File Execution Options 由于这个项主要是用来调试程序用的，对一般用户意义不大。默认是只有管理员和local system有权读写修改。通俗来说，就是比如我想运行a.exe，结果运行的却是b.exe，也就是说在这种情况下，a程序被b给劫持了，即你想运行的程序被另外一个程序代替了。

先在Image File Execution Options的注册表荐中创建了一个名为EQNEDT32.exe的键值：

![](../Images/cca7b0fdc6948dabc4f75438381bd4f2.png)然后，为它设置一个EQNEDT32.exe执行是启动调试器的变量串值，以此把调试器附加到EQNEDT32.exe进程中去。

![](../Images/38fa27bd88cd98d9f457fddf5b64b652.png)当打开恶意RTF文档后，Winword.exe和EQNEDT32.exe两个进程同时启动。

![](../Images/f99912d4191659e45291520077002a78.png)![](../Images/e67fb47d98466cac5fae987fa6dcd42c.png)在EQNEDT32.exe进程的入口点处，调试器被附加进入：

![](../Images/5e66393cd5e932c95b5fd1a6aa8b0970.png)现在，检查文件8.t是否在 %TMP% 目录中创建生成，果然8.t被drop到了 %TMP% 目录中：

![](../Images/fc7e71578188ad92d9f57ac8ab62173c.png)然后，在函数CreateFile处设置断点，查看漏洞利用的shellcode是否会读取文件8.t。在call eqnedt32.41E5EE处，函数CreateFile被调用。文件路径的参数在堆栈执行push dword ptr ss:\[ebp-4\]操作被压入堆栈，也即把内存ss:\[ebp-4\]处存放的双字压入堆栈。

![](../Images/216d46b316ceb41c53a4c01dcec12354.png)![](../Images/30ceb7acd1d4e25db7c0f58b382f52b3.png)Shellcode使用函数CreateFile把文件8.t创建生成到%TMP% 目录下，现在，可以在调用函数处返回用户代码。

![](../Images/6010d7ead6aae2d6a502285363d6b935.png)深入分析之后，进入shellcode区域，其地址空间已经发生改变。以下即为漏洞利用代码的shellcode段：

![](../Images/328faf150ce0a6917684dab7b932f7ec.png)在函数CreateFile调用之后, 函数GetFileSize被调用以获取文件大小：

![](../Images/b2d197b37eb7b5374d34e1ba1e3d4265.png)之后就是一个VirtualAlloc函数。VirtualAlloc是一个Windows API函数，该函数的功能是在调用进程的虚地址空间,预定或者提交一部分页，也可理解为申请内存空间。这里的VirtualAlloc函数在1FD0000 (eax value)处申请创建了一个内存页面，用它来加载文件8.t：

![](../Images/8e89be065389f79d23fc1d33c33a0bbf.png)VirtualAlloc函数之后，创建的内存页面由EAX操作指向：

![](../Images/bb18276ece13a3ac476eae5fd5a61fb1.png)分配的内存页面：

![](../Images/be78effe48e0a582d5785145093b8324.png)然后，用函数ReadFile去读取文件8.t：

![](../Images/0b284f0ae9ea2567a2160e5a45e3aef2.png)接着，文件8.t被读取加载到了分配的内存页面 1FD0000 处，以下为文件8.t在内存页面中的样式：

![](../Images/06d749cc7016175ef808654f17b68a70.png)在0066C82A内存处，shellcode会对文件8.t进行编码解密，解密循环是围绕解密密钥进行的一系列异或（XOR）操作，解密开始，解密密钥被设置到了7BF48E63中。以下为解密循环：

![](../Images/91095626d330212be92922b35d85024c.png)之后，执行异或（XOR）操作，解密密钥被设置到了EAX寄存器中：

![](../Images/66ac7aed4b9f0c6181fc52bf245ae362.png)如果检查异或（XOR）操作的目的地ds:\[edx+ebx\]，可以发现，在01FD0000处发生了文件8.t加载行为，两步执行解密之后，终于可以在内存区开头看到神奇的字符串“MZ”了，MZ为window的PE文件标志。

![](../Images/de4531afd4730a1c231c442eced26338.png)解密循环结束之后，我们会在内存01FD0000处得到一个PE程序，到此，文件8.t被解密了：

![](../Images/85f7ce7e3df3e58aa5909aec5574f6cc.png)接下来，shellcode使用VirtualAlloc函数在02070000处创建了一个内存页面：

![](../Images/6e8461edc27b7dce507eac24564489d3.png)之前，在内存01FD0000处解密得到的PE程序被拷贝到了这个地址处：

![](../Images/141a7aaed4be9420c73be4333bb45fbf.png)在EQNEDT32.exe运行过程中，shellcode调用GetModuleFileNameA函数来获取自身文件的完整路径。之后，shellcode将正常的EQNEDT32.exe进程进行分支，创建出另一个独立的EQNEDT32.exe进程，并把它执行挂起状态：

![](../Images/751fe3b4610d0a9c4ece5c3fbb916950.png)然后在地址02070000处把该进程进行覆盖：

![](../Images/a623e2aee9bad7d41c9bfab3254410c5.png)以下为NTWriteVirtualMemory写入内存时涉及的堆栈：

![](../Images/ad20b285d3358c5541b626f92372c5e4.png)之后，shellcode会把挂起状态的进程重启，以此执行新注入的PE程序。所以，可以发现在OLE对象开头处存在所有的API调用，并且存在runPE方法来启动新注入的 EQNEDT32.exe 程序。

## EQNEDT32.exe独立进程的分支创建分析

前面提过，被注入覆盖的新进程EQNEDT32.exe会在目标操作系统中写入以下两个文件：

> 一个名为 RasTls.dll 的dll文件
> 
> 一个名为dascgosrky.exe的可执行文件

如果把EQNEDT32.exe进程剥离出来，把它放到IDA中分析，可以发现该进程在sub\_00401150处释放文件的方法函数，把它命名为dropFiles。

![](../Images/9039d72b0ac7eec1115a7900827a538f.png)在该方法开始，存在一个xor循环：

![](../Images/0a9a93a76a88df290030305b65742495.png)之后，会调用压缩方法函数zlib:

![](../Images/790fabba40669fd9d5414f1275f96602.png)在sub\_4012D0处，文件释放函数dropFiles会被两次调用。

![](../Images/c7e72d157ae9593228c97e91b51752b9.png)检查整个流程，可以发现，函数dropFiles只会被sub\_4012D0进行调用，如下：

![](../Images/daa30e185cb9a2c4a8c5c73744673939.png)由于EQNEDT32.exe每次的执行，都会由函数CreateFile的onstaticcache.dat文件启动，所以，在函数CreateFile处设置了一个断点：

![](../Images/31a7e2b3a7c9642c490e5f6ed1a0fdc1.png)然后，回到用户代码中，在函数dropFiles初次被调用的0040159A处再设置一个断点，以便进行静态分析：

![](../Images/9562712cb93bbb16cf268aadd1865629.png)这样，就能分析第二遍解密循环了，先要来初始化解密函数：

![](../Images/9228f7c2c7c1a82a08888f8e6771808e.png)解密循环第一步中，结果被写入EQNEDT32.exe进程地址空间的411BC0：

![](../Images/559a19dd5f11c817adbb44210ec26519.png)循环完成之后，可以得到zlib压缩对象的头信息：

![](../Images/1c25c4af3e5df7584492065f6ab9ed9c.png)在内存页面021E0000中，会被分配存储dll文件：

![](../Images/5034d4b5d2bb03f8dd6fe89f028ebe73.png)在该IP地址中，存在多个越南语相关的对应域名，这些域名还和IP地址176.223.165.122有关联：

把这两次攻击的各项TTP指标进行对比，发现基本相似，攻击者都使用了RTF文档作为前期入侵，而用DLL劫持作为后期payload加载。

> 此次攻击中的另外一个域名cat.toonganuh.com，是toonganuh.com的子域名，也曾被发现和中国黑客组织-1937CN注册过的邮箱florence1972@scryptmail.com有关联。

## 总结

基于以上发现，Sebastien Larinier推断，中国黑客组织 1937CN 以同样的TTPs手法和更新过的工具组件，针对越南政府部门开展着持续的网络攻击。Sebastien认为，1937CN创建RTF恶意文档的特性和“响尾蛇”APT组织相似。Sebastien Larinier声称将会在后续的分析中给出更多证据。
