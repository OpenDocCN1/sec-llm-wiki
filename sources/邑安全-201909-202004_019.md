##   

## 介绍

2020年3月，Google修补了一个严重漏洞，该漏洞影响了许多基于MediaTek的设备\[1\]。此漏洞自2019年4月以来（联发科技已解决10个月之久）被联发科技所知道，并且允许没有权限的本地攻击者读写系统内存，从而导致特权升级。甚至还有一个名为`mtk-su` \[2\]的漏洞利用二进制文件，该文件可让许多易受攻击的设备扎根，该漏洞是在2019年开发的。在撰写本文时，有关此漏洞的信息很少。因此，我们决定自己看看。

##   

## 关于CVE-2020-0069

根据联发科技\[3\]，此漏洞使本地攻击者可以对物理内存地址进行任意读取/写入，从而导致特权升级。受影响的模块是*MediaTek Command Queue*驱动程序（或CMDQ驱动程序）。攻击者可以使用驱动程序上的IOCTL分配DMA（*直接内存访问*）缓冲区，并向DMA硬件发送命令，以使其能够读写物理地址。

提醒一下，*直接内存访问*是一项功能，允许专用硬件直接从主内存（RAM）发送数据或从主内存（RAM）接收数据。目的是通过允许大内存访问而不用过多的CPU来完成此任务，从而加快系统速度。该驱动程序似乎允许从用户域与DMA控制器进行通信，以实现与媒体或显示相关的任务。

此漏洞影响了10多个SoC（片上系统），甚至更多的设备。我们已经能够在小米Redmi 6a设备上（使用联发科技MT6762M SoC）对其进行利用。

##   

## CMDQ驱动程序

Web上有此驱动程序的源代码的多个版本。在本研究中，我们主要研究了小米Redmi 6a开源内核\[4\]。可以在*drivers / misc / mediatek / cmdq中*找到该驱动程序的实现。取决于SoC，关联的设备驱动程序可以是*/ dev / mtk-cmdq*或*/ proc / mtk-cmdq*，并且未经任何许可（至少在易受攻击的设备上）可用于任何应用程序。

从可用的操作中，我们将研究以下内容：

###   

### 分配DMA缓冲区

当调用`CMDQ\_IOCTL\_ALLOC\_WRITE\_ADDRESS时`，我们提供一个`cmdqWriteAddressStruct结构`，该`结构`在字段`count中`包含请求的缓冲区的大小。我们在`startPA`字段中收到一个物理地址。我们无法直接从用户名访问该地址。要访问此内存区域，我们可以使用`CMDQ\_IOCTL\_EXEC\_COMMAND`。

通过从先前的分配中调用带有`结构cmdqWriteAddressStruct`结构的`CMDQ\_IOCTL\_FREE\_WRITE\_ADDRESS`，可以释放DMA缓冲区。

如前所述，此IOCTL允许发送要由DMA控制器执行的命令。这些命令放在用户区缓冲区中，其地址必须放在字段`pVABase中`，其大小放在字段`blockSize中`。

执行`完`命令后，命令结构中的`readAddress`字段可用于从DMA缓冲区读取值。字段`readAddress.dmaAddresses`指向一个用户区缓冲区，其中包含来自我们DMA缓冲区的地址。其大小由字段`readAddress.count`引用。内核将读取所有地址，并将这些值放置在由`readAddress.values`字段指向的userland缓冲区中。

也可以通过使用IOCTL命令`CMDQ\_IOCTL\_READ\_ADDRESS\_VALUE`来读取DMA缓冲区。

####   

#### CMDQ\_CODE\_WRITE和CMDQ\_CODE\_READ

![](../Images/c7887b699c162ba05ba4daa1cb226e32.png)

写命令用于将数据寄存器中的值写入地址寄存器中的地址。读取命令读取地址寄存器所指向的地址处的值，并将结果放入数据寄存器中。

根据选项位（图中的`TYPE A`和`TYPE B`），可以从位于`REG NUMBER`字段中的名为`subsysID`的值和位于`VALUE`字段中的偏移量来计算地址。该`subsysID`随后将由内核DTS所引用的实际物理地址替换。

####   

#### CMDQ\_CODE\_MOVE

![](../Images/42f99c2c26f25eb88cc1c621852561fa.png)

  

该命令允许将一个值（最多48位）放入寄存器中。该值可以放置在数据寄存器或地址寄存器中，并且可以是任何数据或地址。这可能是最大的问题，因为未检查地址。

  

#### CMDQ\_CODE\_WFE

![](../Images/c3878f3df38bd1b5a154acf0427020d7.png)

  

WFE代表*等待事件和清除*。据我们了解，我们可以使用它来阻止某些寄存器的使用（就像我们使用互斥锁一样）。与该命令一起使用的事件标志与我们将在命令缓冲区中使用的一组寄存器相关联。例如，对于寄存器`CMDQ\_DATA\_REG\_DEBUG`（R7）和 `CMDQ\_DATA\_REG\_DEBUG\_DST`（P11），必须使用事件（或在源中调用的令牌）`CMDQ\_SYNC\_TOKEN\_GPR\_SET\_4`。我们需要在每个命令缓冲区的开头和结尾使用WFE命令。

####   

#### CMDQ\_CODE\_EOC

EOC代表*命令结束*。必须将其放置在**CMDQ\_CODE\_WFE**命令之后的每个命令缓冲区的**末尾**，以指示命令列表的末尾。它似乎包含许多标志，但是对于我们的用法，我们只需要始终设置似乎是IRQ标志的内容即可。

####   

#### CMDQ\_CODE\_JUMP

根据消息来源的评论，它允许使用偏移量跳入命令缓冲区。我们在每个命令缓冲区的最后，在命令**CMDQ\_CODE\_EOC**之后使用此命令，始终跳转到偏移量0x8，即上一个命令。我们的理论是，预取机制是在DMA控制器中实现的，并且此命令确保将**CMDQ\_CODE\_EOC**命令考虑在内。

### 小PoC

要确定内核使用的物理地址，可以使用设备`/ proc / iomem`（需要root权限）。


这些地址是静态配置的，在每次引导时都将保持不变。

PoC由两个程序组成：

> *   一个允许对基本内存进行读写的C程序；
>     
> *   一个shell脚本，该脚本调用前一个程序以在内核数据存储器中搜索“ Linux”字符串的第一个匹配项，然后将其替换为“ minix”。
>     

```


$ uname -a
```

很有用...

我们已经能够读写内核数据存储器。而且，我们可以对任何其他系统内存区域执行相同的操作，从而绕过系统中已有的权限和保护。因此，除了玩些小把戏之外，还可以使用此漏洞来修改系统内存的任何部分，例如内核代码和数据，以实现特权升级。

二进制`mtk-su`使用此漏洞在内核内存中执行了很多有趣的工作，从而实现了root身份。在本文中，我们将不提供有关`mtk-su`使用的这些内核利用方法的更多详细信息。但是，那些想了解更多的人可以看看我们制作的小型跟踪库。启动`mtk-su`时必须预先加载它，并且它将跟踪CMDQ驱动程序的某些IOCTL，例如发送给驱动程序的命令。

```


$ mkdir mtk-su
```

您可以在Quarkslab的存储库CVE-2020-0069\_poc中找到PoC和跟踪器库。

##   

## 结论

此漏洞非常关键。它基本上允许任何应用程序读写所有系统内存，包括内核内存。我们可能想知道为什么每个应用程序都需要访问该设备驱动程序，而不仅仅是HAL（*硬件抽象层*）和与媒体相关的进程需要访问该设备驱动程序。至少要增加一个额外的步骤才能从具有零特权的应用程序获得root用户权限。

根据Fire HD 8 Linux内核的资料\[5\]，已通过解析命令缓冲区中的所有命令并验证每个命令以及所使用的地址和寄存器来解决此问题。例如，仅允许将DMA缓冲区中的地址移至地址寄存器。

由于我们不是发现此漏洞的人，因此我们没有与MediaTek讨论此问题。但是从技术角度来看，没有什么可以使此漏洞修复这么长时间的。根据XDA Developers文章\[6\]，联发科技自2019年5月以来已进行修复，但花了10个月时间才在最终用户设备中对其进行广泛修补。借助Android许可协议，Google能够迫使OEM对其设备进行更新。这是Android生态系统中补丁程序管理复杂性的一个很好的例子，许多参与者（SoC制造商，OEM，ODM）必须共同行动，以在最终用户设备上修复漏洞。最后，似乎只有法律方面才能迫使所有这些参与者整合修补程序。

现在，我们可能想知道，所有嵌入Mediatek SoC并集成没有Android许可协议的AOSP OS版本的设备是否将从此修补程序中受益，而他们的供应商没有法律义务集成它。
