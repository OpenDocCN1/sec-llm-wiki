更多全球网络安全资讯尽在邑安全

随着组织希望整合无密码解决方案来帮助减轻密码使用固有的众多安全风险，生物识别身份验证开始在整个企业中迅速采用。

最广泛采用的无密码身份验证系统之一是 Windows Hello，它可以通过密码、指纹或面部识别实现无密码登录。据微软称，85% 的 Windows 10 用户使用Windows Hello 。

鉴于 Windows Hello 的流行，在过去的几个月里，CyberArk 实验室研究团队一直在探索该系统的潜在弱点，希望能全面加强生物识别安全。结果是发现了一个设计缺陷，该缺陷允许攻击者绕过 Windows Hello 的面部识别。该漏洞允许具有设备物理访问权限的攻击者通过捕获或重新创建目标面部照片并随后插入定制的 USB 设备将欺骗图像注入身份验证主机来操纵身份验证过程。我们没有证据表明这种攻击已被广泛使用，但有动机的攻击者可能会使用它来攻击研究人员、科学家、记者、活动家或在其设备上拥有敏感 IP 的特权用户。

这是概念验证视频，展示了我们如何绕过 Windows Hello 身份验证和登录屏幕。您将看到我们连接了自定义 USB 摄像头设备以传输先前捕获的目标红外帧。

虽然我们的研究专门针对Windows Hello以及企业产品Windows Hello 企业版，但重要的是要注意，任何允许可插拔第三方 USB 摄像头充当生物识别传感器的身份验证系统都可能容易受到这种攻击，而无需适当的缓解。然而，我们还没有进行实际测试来验证这一点。

我们很高兴在 2021年 8 月 4 日至 5 日的Black Hat 2021 大会上展示我们的发现，并分享我们研究的以下总结和技术解释，包括对微软于 2021 年 7 月 13 日发布的缓解措施(CVE-2021) 的分析-34466)作为我们协调漏洞披露的一部分。

探索 Windows Hello

微软开发了两个版本的 Windows Hello；一个适用于消费者，以及一个名为Windows Hello企业版的企业版（我们将在本文中将其称为WHfB）。Windows Hello 于 2015 年推出，使身份验证就像查看计算机屏幕一样简单。此外，它还在具有本机支持的 Windows 环境中启用无密码身份验证。

正如预期的那样，面向消费者和企业版本之间的主要区别在于它们的使用、实现和运行环境。例如，面向消费者的 Windows Hello 面向个人/消费者设备，即家庭用户。相比之下，WHfB面向运行任何 Active Directory 并希望实施无密码解决方案的企业和企业。

无密码身份验证被定义为任何身份验证方法，其中用户无需输入密码或类似的机密即可登录系统。

通常，Windows Hello 会根据 PIN 或生物特征验证强制执行验证，并降低键盘记录器和网络钓鱼攻击的风险，因为它提供了不需要密码的身份验证替代方案。但是，它不会完全替换您的密码。

在后台，系统仍然使用您的密码哈希进行身份验证。

WHfB 是 Windows Hello 的增强版本，并将提供的身份验证功能用于适合企业级的解决方案。Windows Hello 企业版使用由非对称公钥和私钥对或基于证书的身份验证支持的 PIN 码。

虽然我们的测试侧重于 WHfB，但绕过也适用于面向消费者的 Windows Hello，因为它们都基于相同的机制。

剖析 Windows Hello 生物识别身份验证

正如我们提到的，Windows Hello 的主要功能是生物识别身份验证。在决定将系统的哪个部分作为目标时，我们推测生物识别传感器是链中的薄弱环节，因为它可能使系统暴露于对目标设备的数据操纵攻击。

传感器是一种传输信息的设备，操作系统（尤其是 Windows Hello）根据这些信息做出身份验证决定。因此，操纵此信息可能会导致绕过整个身份验证系统。

图1：生物特征认证系统流程图

从上图中，我们可以看到收集到的数据来自一个来源：生物识别传感器。然后将该传感器的输入发送到生物特征分析（将传入数据与先前存储的数据进行比较）。之后，分析结果被发送到首先发布流程的认证系统（或任何其他组件）。

在面部识别场景中，生物识别传感器要么是嵌入在设备中的摄像头，如笔记本电脑中，要么是连接到计算机（在大多数情况下通过 USB 连接）。

全系统身份验证流程基于来自摄像头的输入，这可能会产生漏洞，我们将很快演示。

当然，并非所有 USB 设备都相同，因此并非所有 USB 设备输入都会导致安全风险。我们来谈谈两个 USB 设备，一个键盘和一个摄像头，因为它们都可以用于身份验证。USB 键盘不会像 USB 摄像头那样使人面临安全风险。你一定想知道为什么。

答案在于输入本身。只有在信息输入系统之前打字的人才能知道键盘输入，而相机输入则不然。

相机本质上将从其传感器接收到的帧发送到相应的操作系统，其中包含一个面向相机的人。然后，这些特定帧通过生物特征分析传递到计算机中，并与位于计算机硬盘驱动器中的预定义数据集进行比较。如果传感器接收到的数据与注册数据匹配，则操作系统要么让您登录，要么声明系统无法识别您。

面部识别不是使用只有您知道的东西来进行身份验证，而是使用“公共”信息（您的脸）将您登录到系统中。这类似于窃取密码，但由于数据（人脸）在那里，因此更容易访问。

我们的研究产生了一个有趣的攻击向量：捕获受害者的图像，保存捕获的帧，模拟 USB 摄像头设备，并最终将这些帧发送到系统进行验证。此漏洞的核心在于 Windows Hello 允许可操纵的外部数据源作为信任根。

人脸识别欺骗

Windows Hello 面部识别身份验证需要支持 RGB 和红外线 (IR) 的标准摄像头。这种类型的相机有两个独立的传感器，它们作为一个 USB 设备一起工作。

经过调查，我们发现在身份验证过程中只处理了 IR 摄像头帧。

为了验证这一点，我们进行了一项实验，其中我们创建了一个自定义 USB 设备，该设备充当带有 IR 和 RGB 传感器的 USB 摄像头。为此，我们使用了 NXP 制造的评估板。使用这款新的定制 USB 摄像头，我们传输了“目标人物”的有效 IR 帧，而我们发送的 RGB 帧是海绵宝宝的图像，令我们惊讶的是，它起作用了！

有了这种理解，从攻击者的角度来看，就需要实现一个支持 RGB 和 IR 摄像头的 USB 摄像头。然后这个 USB 设备只需要发送受害者的真实 IR 帧来绕过登录阶段，而 RGB 帧可以包含任何内容。

此外，在研究中，我们发现我们甚至不需要很多“目标”帧。

显然，我们只需要一个IR 框架和一个全黑框架。当我们试图在缓冲区中只发送一个有效的 IR 帧时，Windows Hello 不接受我们的输入为有效，但是当我们同时发送黑帧和正确的IR 帧时，我们进入了。我们认为有一个“ Liveness”/反欺骗机制，它寻找连续出现的每两帧之间的变化，但我们没有进一步追求这个假设来证实。

总结到目前为止我们学到的知识：我们已经看到攻击者可以创建 Windows Hello 可以使用的定制 USB 设备。攻击者控制来自该设备的数据。只需目标的一个有效 IR 帧，攻击者就可以绕过 Windows Hello 的面部识别机制，从而完全绕过身份验证并可能访问受害者的所有敏感资产。

很整洁，对吧？

嗯，我们也这么认为！但是这里有一点问题。攻击者如何获得受害者的有效 IR 帧？答案在于下面提到的两个选项：

  1. 捕获受害者的红外 (IR) 帧

  2. 将受害者的常规 RGB 帧之一转换为 IR 帧

让我们讨论第一个选项，即获取受害者的 IR 帧。

拍摄一个人的良好 IR 帧的方法是将 IR 摄像头设置得尽可能靠近目标的正面。这可以通过带摄像头的人经过或将此红外摄像头设置在人将经过的地方（如电梯）来实现。此外，借助先进的红外摄像头技术，您甚至可以从远处（例如街对面或汽车）拍摄这张照片。虽然这听起来有点牵强，但有动机的攻击者绝对可以做到这一点。欺骗目标面部的另一种方法是将 RGB 帧转换为 IR，但是，这可能非常困难。

微软在 2016 年的 Winhec 上提到，人们在近红外图像与 RGB 图像（彩色图像）中的外观往往非常不同。我们可以由此推断，微软的系统也是基于无法将 RGB 图像转换为 IR 图像的想法，但我们没有进行足够的测试来得出结论性的结果。

USB 设备 101

通用串行总线或 USB 是一种行业标准，它为计算机与外围设备、计算机与外围设备或外围设备与其他外围设备之间的通信和电源提供电缆、连接器和协议的规范。该标准于 1996 年制定，此后由USB-IF维护。自 1996 年以来，许多不同的 USB 版本被标准化并引入了许多连接器，从 USB-A 和 USB1.X 到 USB-C 和 USB4。USB 版本之间的显着差异在于它支持的数据速率和功率传输。

USB 设备通过定义设备接口、备用设置和端点的描述符来定义其功能和特性。（如果你想看一个，抱紧，我们稍后会在博客中讨论）。USB 配置描述符定义了设备的功能和特性。设备可以有多种配置，但一次只有一种是活动的。每一种配置都可以有一个或多个定义设备功能的接口。某些公开与一项功能相关的多个接口的设备（如网络摄像头）具有接口关联描述符 ( IAD )。

一个IAD组属于一个特定的功能界面在一起。

图 3：USB 设备布局

在上图中，我们可以看到 USB 设备布局及其层次结构。

USB 具有严格的树形网络拓扑结构和用于寻址外围设备的主/从协议。
一旦 USB 设备通过 USB 端口连接到计算机总线，主机就会开始与外围设备的会话。主机与USB设备建立会话后，主机会发送多个请求来识别USB设备，称为描述符请求。

主机无法识别哪个设备连接到 USB 端口，因此需要从连接的外围设备获取信息。尽管听起来令人难以置信，但这意味着每个设备都可以随心所欲地展示自己，而主机无法验证这一点。至少规范中没有定义这样的过程。


图 4：USB 描述符

根据USB 规范的第 5 章，共有五个常用描述符：

设备描述符——代表整个设备配置描述符 – 指定设备的功能和特性接口描述符 – 将 USB 端点分组为执行单个功能的功能组端点描述符 – 描述端点字符串描述符——提供人类可读的信息

设备描述符指定了有关整个设备的基本但重要的信息，例如支持的 USB 版本 ( bcdVersion )、供应商 ID、产品 ID，甚至 USB 设备支持的配置数量。另一个重要的描述符是配置描述符，它描述了设备的能力和特性。大多数设备具有一种配置选项，但它们通常可以支持多种配置。

USB 规范中指定了每个描述符的特定长度，但配置描述符长度可能因设备而异，因为它们描述了设备的功能和特性。长度未知的描述符，如配置描述符，分两部分发送。该部分包含描述符的基本格式，其中包含描述符的长度。这让主机知道它需要为完整配置描述符分配的内存空间量。

配置描述符包含有关 USB 设备的大量信息，例如主机与 USB 设备通信的方式、设备功能和最大功耗。

最后，USB 设备将字符串描述符传递给主机请求的主机。字符串描述符提供有关 USB 设备的人类可读信息，以 Unicode 格式编码。这些字符串充当指示器，使我们能够在设备管理器程序中轻松识别 USB 设备。

USB 设备 102 – USB 视频类

到目前为止，我们已经介绍了 USB 设备的基础知识，每个 USB 设备都必须实现这些基础知识。现在让我们谈谈 USB 基本规范的扩展——USB 视频类（或简称 UVC）。UVC 是一个 USB 设备类，它描述了网络摄像机、静态图像摄像机等设备的视频流功能。

UVC 规范的最新版本是 1.5。USB-IF 在一组文档中定义了 USB 规范，这些文档描述了基本协议（我们之前介绍过）和 UVC 支持的不同负载格式。UVC 1.5 支持传输许多压缩和未压缩的视频流，包括 YUV 格式、MPEG 格式等。

定制相机 – 胜利之路

现在我们已经掌握了基础知识，我们需要选择一个方便的开发平台来调试和开发我们的自定义 USB 摄像头设备。我们选择使用 NXP 评估 (i.MX RT1050)，它创建了一个简单直接的自定义 Eclipse IDE，称为MCUXpresso。NXP 提供了一个很棒的示例项目，它实现了一个“假”相机设备，包括大部分 UVC 堆栈，从而节省了我们的研究时间。

图 8：恩智浦 USB 摄像头项目示例

我们需要首先捕获并观察目标设备发送和接收的 URB（USB 请求块）数据包。我们捕获 USB 流量的一个选择是使用USBPcap，这是一个开源工具，也有一个 Wireshark 插件。另一种选择是USBview，这是一种由 Microsoft 开发的工具，可详细说明连接到您计算机的所有 USB 设备，包括它们的配置描述符。此外，您还可以看到他们解析的配置描述符，这对于尝试自己复制或创建 USB 设备的人来说非常有用。

可以想象，大量 USB 流量在一台 PC 中进出，因此查看 Wireshark 中的实时 USB 流量可能会让人不知所措。USBview 帮助我们找到了 USB 设备 id，过滤掉了 Wireshark 中不相关的 USB 流量，避免了很多压倒性的时刻。

在上图中，我们可以看到USB摄像头的设计结构。我们可以看到，在USB设备中，有两个摄像头——高清摄像头和红外（IR）摄像头，这意味着我们需要克隆这个USB设备中有两个IAD。

在恩智浦开发的示例项目中，只有一个“相机”支持。因此，我们需要实现另一种相机支持，这应该主要通过查看现有相机并复制其中的一些来实现，同时更改现有代码以支持两个相机。

我们的目标是创建一个充当真实相机的克隆，因此我们复制了配置和设备描述符。这可以通过多种方式完成，例如通过原始 URB 直接查询设备或从操作系统中提取此信息。我们从 WireShark PCAP 中提取了这些数据，这非常简单。然后，在提取之后，我们将其替换为示例项目中现有的配置描述符。

图 10：相机的设备描述符

此时，我们遇到了一个非常有趣的问题。

每当我们将定义我们的 USB 设备工作的 USB 版本的 bcdUSB 值更改为 0x201（与白标相机相同）时，我们都会遇到 USB 错误消息。当 USB 设备无法正常工作并且 Windows 拒绝使用它时，会显示此错误消息。回溯以确定原因，我们发现我们缺少一个关键的描述符，BOS 描述符！（Windows 中的MS OS 2.0 描述符）。

事实证明，在USB规范中，如果您的USB设备版本高于2.0，则需要询问BOS描述符。此描述符包含有关所连接 USB 设备功能的信息，并启用操作系统和 USB 制造商支持不在 USB 规范中的功能。

主机在 USB 会话“握手”中很早就发送了这个描述符请求，紧跟在设备描述符之后。如果外围设备不响应任何这些请求，Windows（可能还有大多数现代操作系统）将拒绝继续与 USB 设备的会话并断言 USB 设备工作不正常，随后显示上面的错误消息我们的任务栏。但是为什么我们错过了这个呢？我们嗅探了计算机上的所有 USB 流量。

显然，Windows 上的 USBPcap 不会显示或捕获此请求，因此，我们没有注意到我们错过了此请求。但是，在 Linux 中，WireShark 确实显示了它。在未来的任何 USB 研究中，我们将考虑使用 Linux 而不是 Windows，至少用于流量嗅探。

在下图中，您可以看到两者之间的差异。

图 11：比较不同捕获的 USB 数据包

如图所示，我们需要在我们的项目中添加对 BOS 请求的支持，并从捕获的数据中复制 BOS 描述符。这个想法与我们之前所做的类似。我们需要识别代表 BOS 请求的魔术字节，然后在我们的代码中解析它并发送回有效的 BOS 描述符（有两个需要发送）。

结论

这项研究揭示了隐式信任来自外围设备的输入的系统（例如 Windows Hello）如何将自身暴露于固有的安全漏洞。在某些情况下，此输入可能包含“公共”数据，例如人脸，这可能会引发安全问题。

我们的研究结果表明，任何 USB 设备都可以被克隆，并且任何 USB 设备都可以模仿任何其他 USB 设备。通过设备提供的描述符识别 USB 设备是造成这种情况的主要原因。操作系统无法验证此类设备的真实性，至少无法根据 USB 规范进行验证。

我们使用人的 IR 帧来“绕过”人脸识别机制。我们相信这些 IR 帧可以由常规彩色图像创建。

我们建议任何可能想要继续这个研究想法的人将他们的工作建立在将彩色图像转换为 IR 的自动化过程上。这可以通过多种方式实现，从自动过滤器到成熟的花式机器学习算法。

CyberArk 对 Microsoft 缓解建议的回应

根据我们对缓解措施的初步测试，使用具有兼容硬件的增强型登录安全限制了攻击面，但取决于拥有特定摄像头的用户。对于系统设计而言，对来自外围设备的输入的隐式信任仍然存在。为了更全面地缓解这种固有的信任问题，主机应该在信任生物特征认证设备之前验证它的完整性。
