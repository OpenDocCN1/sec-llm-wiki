# Log4j 2.17.1 现已发布，修复了新的远程代码执行错误

Apache 发布了另一个 Log4j 版本 2.17.1，修复了 2.17.0 中新发现的远程代码执行 (RCE) 漏洞，跟踪为 CVE-2021-44832。

在今天之前，2.17.0 是 Log4j 的最新版本，被认为是最安全的升级版本，但现在这个建议已经演变。

## 一个月内第五次 Log4j CVE

威胁行为者对原始Log4Shell 漏洞(CVE-2021-44228) 的大规模利用始于 12 月 9 日左右，当时 GitHub 上出现了针对该漏洞的PoC 漏洞利用。

鉴于 Log4j 在大多数 Java 应用程序中的广泛使用，Log4Shell 很快变成了 全球企业和政府的 噩梦。

虽然原始 Log4Shell 漏洞利用带来的严重风险至关重要，但该漏洞的温和变体出现在 Log4j 版本中，包括 2.15 和 2.16 — 以前认为已完全修补。

BleepingComputer 早些时候报道了 影响 Log4j 的四种不同的 CVE，一种是在“logback”框架中发现的。在 2.16 版中发现 DoS 漏洞后，建议迅速转向 升级到被认为是最安全的2.17.0 版。

但现在第五个漏洞——一个 RCE 漏洞，被追踪为 CVE-2021-44832 已在 2.17.0 中发现，并在最新发布的 2.17.1 版本中应用了一个补丁。

该漏洞的严重性评级为“中等”，CVSS 评分为 6.6，该漏洞源于缺乏对 log4j 中 JDNI 访问的额外控制。

“JDBC Appender 在访问 JNDI 时应该使用 JndiManager。JNDI 访问应该通过系统属性来控制，”BleepingComputer 看到的问题描述说。

“与 CVE-2021-44832 相关，其中有权修改日志配置文件的攻击者可以使用 JDBC Appender 构建恶意配置，数据源引用可以执行远程代码的 JNDI URI。”

Checkmarx 安全研究员 Yaniv Nizry 声称向 Apache 报告了该漏洞：

![](../Images/47501949507765fb1e17c106aea3cf00.png)

Nizry 的推文在流量中迅速爆发，吸引了来自安全专家和持续 log4j 补丁疲劳的“受害者”的评论和模因。

“我希望这是一个笑话，我希望如此……#log4j，”一位用户在推特上回应道。

“我们已经很久没有这样做了，唯一负责任的事情就是竖起一个巨大的闪烁的霓虹灯，上面写着‘LOG4J 无法修复，请勿将其用于任何事情。’”另一个人嘲讽道。

安全专家 Kevin Beaumont 在假期期间将该实例标记为另一个“失败的 Log4j 动态披露”。

## 披露的太快了？

在 Nizry 发布推文时，BleepingComputer 没有看到表明 log4j 2.17 中存在 RCE 错误的官方建议或备忘录。

该推文本身没有包含有关该漏洞或如何利用漏洞的详细信息，但在几分钟之内就引发了一群安全专家和网民开始调查该声明。

过早披露安全漏洞可能会引诱威胁行为者进行恶意扫描和利用活动，这一点从 12 月 9 日的 Log4Shell 漏洞利用漏洞中可以明显看出。

Okta 网络安全副总裁 Marc Rogers 首先披露了漏洞标识符 (CVE-2021-44832)，漏洞的利用取决于非默认的 log4j 设置，其中配置是从远程服务器加载的：

![](../Images/8e71b14c9359893194b183857d49362a.png)

到目前为止，从国家支持的黑客 到 勒索软件团伙 等 各种威胁行为者都利用 log4j 漏洞 将门罗币矿工注入 易受攻击的系统。

已经看到 Conti 勒索软件团伙盯上了 易受攻击的 VMWare vCenter 服务器。而攻击者通过 log4shell 破坏越南加密平台 ONUS要求 500 万美元的赎金。 

Log4j 用户应立即升级到最新 版本 2.17.1  （适用于 Java 8）。包含修复程序的反向移植版本 2.12.4 (Java 7) 和 2.3.2 (Java 6) 预计也将很快发布。
