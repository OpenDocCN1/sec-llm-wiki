http请求走私漏洞最近很火热，其实早就2005年就已经提出了该漏洞，由于近些年基于代理的技术越来越普遍，导致该漏洞出现的频率越来越多。**http请求走私漏洞利用条件之一首先是目标使用cdn技术也就是代理技术。**  

  

HTTP请求走私是一种干扰网站处理从一个或多个用户接收的HTTP请求序列的方式的技术。请求走私漏洞本质上通常很关键，它使攻击者可以绕过安全控制，未经授权访问敏感数据并直接危害其他应用程序用户。  

人话就是

**HTTP请求理论上是独立的实体，但利用http请求走私技术可以突破理论限制，使远程攻击者在未经身份验证的情况下，轻松攻击目标网络基础设施。**

要想搞清楚什么是http走私需要先简单了解一下http协议的知识，及web架构。

下面简单说一下

  

**http协议**

HTTP(超文本传输协议)：一种无状态的、应用层的、以请求/应答方式运行的协议，它使用可扩展的语义和自描述消息格式，与基于网络的超文本信息系统灵活的互动。  

![](../Images/6799ef6c6849a4cc0d3b1badcf3564c3.png)

HTTP协议工作于客户端-服务端架构之上。浏览器作为HTTP客户端通过URL向HTTP服务端即WEB服务器发送所有请求。Web服务器根据接收到的请求后，向客户端发送响应信息。

  

**http请求走私原因**

  

**web架构**

如今的Web应用程序经常在用户和web应用之间使用HTTP服务器进行连接。用户将请求发送到前端服务器（有时称为负载均衡或反向代理例如Nginx），并且该服务器将请求转发到一个或多个后端服务器。这种类型的体系结构在现代基于云的应用程序中越来越普遍。如下图

  

![](../Images/192fe787c220c6aed8e648921a31b81f.png)

  
  

在这种架构模式下，至关重要的是前端服务器和后端系统就请求之间的边界达成一致。**否则，攻击者可能会发送一个模棱两可的请求（恶意畸形的http请求），该请求被前端和后端系统以不同的方式解释：**

![](../Images/2af3d9d63a66675588c9a9888ef179f9.png)

在这里，攻击者使前端请求的一部分被后端服务器解释为下一个请求的开始。它实际上是在下一个请求之前（也就是还没进行下个请求之前），因此会干扰应用程序处理该请求的方式。换成人话就是，在一个http请求中构造了类似如下的请求

  

```
POST / HTTP/1.1
Host: ac491fe91ef65e09807a0dad006b002f.web\-security\-academy.net
User\-Agent: Mozilla/5.0 (Windows NT 10.0; WOW64; rv:48.0) Gecko/20100101 Firefox/48.0
Accept: text/html,application/xhtml+xml,application/xml;q\=0.9,\*/\*;q\=0.8
Accept\-Language: zh\-CN,zh;q\=0.8,en\-US;q\=0.5,en;q\=0.3
Accept\-Encoding: gzip, deflate
DNT: 1
Cookie: session\=eqdBic2TizWiC3INHEQsWxwcMrrW6DAq
Content\-Length: 96
Transfer\-Encoding: chunked

aa
GET /admin//delete?username\=carlos HTTP//1.1
Host: localhost

0
```

  

如果用户提交以上模糊的请求可能代理服务器认为这是一次HTTP请求，然后将其转发给了后端的源站服务器，但源站服务器经过解析处理后，只认为其中的一部分为正常请求，剩下的那一部分就是走私的请求了，这就是HTTP走私请求的由来。  

  

**HTTP请求走私漏洞如何产生？**

大多数HTTP请求走私漏洞的出现是因为HTTP规范提供了以下两种不同的方法来指定请求的结束位置：

  

*   
*   

```
Content-Length  标头 以字节为单位指定消息内容体的长度Transfer-Encoding  标头
```

Content-Length 例子如下 很简单以字节为单位指定消息内容体的长度

  

*   
*   
*   
*   
*   
*   

```
POST /search HTTP/1.1 Host: normal-website.com Content-Type: application/x-www-form-urlencoded Content-Length: 11 
q=smuggling
```

Transfer-Encoding 用于指定消息体使用分块编码（Chunked Encode）。消息报文由一个或多个数据块组成，每个数据块大小以字节为单位（十六进制表示） 衡量，后跟换行符，然后是块内容，**最重要的是：****整个消息体以大小为0的块结束，也就是说解析遇到0数据块就结束。**如：

  

*   
*   
*   
*   
*   
*   
*   
*   
*   

```
POST /search HTTP/1.1 Host: normal-website.com Content-Type: application/x-www-form-urlencoded Transfer-Encoding: chunked b
q=smuggling
0
```

很简单，相当于我发送请求，包含Content-Length，前端服务器解析后没有问题是个正经http请求，发送给后端服务器进行解析，但是我在请求时后面还包含了Transfer-Encoding（分块编码），这样后端服务器进行解析便可执行我写在下面的一些恶意请求，这样便可以绕过前端的waf。

  

**总结一下本质是利用了前端服务器和后端服务器的处理数据流时的不对称。**
