# 反CSRF爆破的三种姿势

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=MzkwNzI0MTQzOA==&mid=2247490473&idx=1&sn=afc4500ff601ef4f146a9b97b09417db&chksm=c0dd6918f7aae00ed75c7321aa4144996a6e758ff26d59dc80dcfd8481dc113f17220689ae68&scene=126&sessionid=1681664605#rd](http://mp.weixin.qq.com/s?__biz=MzkwNzI0MTQzOA==&mid=2247490473&idx=1&sn=afc4500ff601ef4f146a9b97b09417db&chksm=c0dd6918f7aae00ed75c7321aa4144996a6e758ff26d59dc80dcfd8481dc113f17220689ae68&scene=126&sessionid=1681664605#rd)

**1**

**姿势1:CSRF Token Tracker**

CSRF Token Tracker是个插件,可以在BApp Store下载安装

![](../Images/beec0bdbbc35607e8f9f7429ac86baea.png)  
这种方式可以说是最简单的,但是不适用姿势2和姿势3中的案例  
现有一个请求参数是user\_token  
![](../Images/56cf3d05ee456331dd8cf23f70ee425e.png)  
只需要在插件中添加  
![](../Images/505513bfc5739687f9eff13bddafa221.png)

注意这里有个坑(搞了好久)  
比如你想在repeater模块测试一下重新发送请求会不会修改密码  
![](../Images/fa17685cad99bbbfe39005d97dd995f1.png)  
发现返回的结果仍然是302  
这里是需要有一个有效的,没有使用过的user\_token去请求的!  
然后再去重放请求包就都会自动更新token了  
总结一句就是你第一次用有效的token重放请求包就永远有效(自动更新token了)  
你第一次用无效的token重放请求包就永远无效

  

**2**

**姿势2:定义宏**

在这个案例中使用CSRF Token Tracker无法成功自动更新token  

![](../Images/eb9b7de5e581efad0e848bbfc91e9c57.png)

![](../Images/127ac11413c6dfa9978e33834c8ce660.png)

开始定义宏

![](../Images/35a56558630fe0f73f51a0f85088cdf9.png)

![](../Images/490a3912690ee0cb8406b8d92fea856c.png)

![](../Images/7a174e4492eb67470a6fb54a71f2c902.png)

![](../Images/53308c664afd15fe41c2bfb54d56c6b4.png)

![](../Images/29e8524e17b57c66961902287cda91ba.png)

一路OK回到这里

![](../Images/72dc9a6bd2b123f5b52d1a414816ec5a.png)

![](../Images/9c99c310be1abe8f069d2e12dc98bad4.png)

![](../Images/ea96a025c35478445bf81e4f95290d55.png)

不懂就选择1,在所有请求前都运行宏  
![](../Images/661d864ed446e23b2d45e92d05b71312.png)

来到repeater模块重新发送请求就不会说非法的csrftoken  
![](../Images/08f525015781137cb49675f1d8360e10.png)  
来看日志发生了什么  
![](../Images/4d2e23ae6ca88ee8b08ddb3090169a2c.png)  
我们使用repeater重放了登录的请求,也就是图中第71个请求  
宏帮我们自动进行了了第70个请求获取了新的token让第71个带着新的token去登录

  

**3**

**姿势3:宏+Extractor**

在这个案例中前两种姿势均无效  

下载安装插件

![](../Images/9d8115e0dddfb03227b7f9872db311a4.png)

先看下两个请求包  
第一个请求包就是获取token的

![](../Images/aa6b802c5798f7174793e654cff8baf2.png)

第二个就是带着token去访问

![](../Images/c396ea8597c6621a2fab98a2830f508f.png)

看过这两个请求包应该就明白了  
这次token是在请求头中  
而定义宏的时候会让你选择更新token的地方  
这个地方却没有更新请求头的功能  
所以姿势2在这里就失效了  
![](../Images/7728d51bb8720eeca8479f4058931a23.png)

首先定义宏获取token  
这个宏只需要要确保在请求2之前会执行请求1  
相比于姿势2的步骤简单一点

![](../Images/2c194ec39f0bf06331d30e5acb59a94a.png)

![](../Images/4377b93dd07b3de3840c5392ad80b074.png)

![](../Images/cbebc532b2b05479b5f071ee64ad2336.png)

到这里宏就配置好了  
在repeater重放请求2然后再logger+=里面查看  
确保每次都会在请求2前自动执行请求1就是正常的

![](../Images/a088fa2cf064447eccff3a10eb9b993f.png)

然后配置插件Extractor  
把两个请求包都发送到Extractor

![](../Images/78ae43b4a29966fd43472e84a5d542dc.png)

![](../Images/ccc685d4a87fac46be4e97e9004c72f3.png)

![](../Images/f081213d6bcd8d17848eb60e1878b08e.png)

此时回到repeater模块重放发现token就有效了

![](../Images/ddbde62f5945603f8b7c22971ddab2ad.png)

再次回到logger++看发生了什么  
看到第87个请求获取的token值为407667d008b147199d174681a655aea0

![](../Images/56fcc55edaef54118067a23fed9418a4.png)

第88个请求包的accessToken值也是407667d008b147199d174681a655aea0

![](../Images/cc64d2ca7ce3109161152ef51174a10b.png)

总结一下姿势3的思路  
宏负责在请求2前发送请求1  
Extractor插件负责匹配和替换token
