从上帝视角来看待Kerberos，以及对Kerberos认证协议的攻击（白银票据，黄金票据）。


之前解决了问题一，现在来尝试看待一下问题二，不去详细观察交互的数据包细节，把重点关注在Kerberos在设计上如何来抵抗中间人攻击以及用户伪造上。

1、Client向AS发送请求（明文）

用户名不可伪造，Kerberos DB会直接查询。

2、AS通过Kerberos DB完成用户名校验之后返回TGT（通过krbtgt的hash加密，里面包含了TGS会话密钥）和一个Session Key（通过Client用户名的hash加密，里面包含TGS会话密钥）。

假设用户输入的密码hash正确，则解密成功，获取到TGS会话密钥。-现在客户端目前有客户端无法解密的TGT以及解密Session Key得到的TGS会话密钥。
如果用户输入的密码hash不正确，这里是无法获取到TGS会话密钥的，即无法进行下一步操作。-现在客户端有无法解密的TGT以及无法解密的Session Key
那么是不是可以进行伪造呢？接下来再看。-如果需要伪造TGT则需要krbtgt的hash-伪造时间戳需要的TGS会话密钥必须和TGT里面的一样

3、用户发送TGT（krbtgt的hash加密）和时间戳（使用TGS会话密钥加密）以及需要请求的http服务的信息（明文）给TGS。

TGS先检测http服务是否存在1.使用krbtgt的hash解密TGT，得到了TGS会话密钥2.使用TGS会话密钥解密时间戳，得到了时间
如果解密出来的TGS会话密钥不能解密时间戳，那么可以确定用户hash被伪造
TGS属于KDC拥有krbtgt的hash
为什么TGS不直接与AS共享TGS会话密钥反而要去解密TGT获取TGS会话密钥？双向认证。

4、TGS发送给用户HTTP Service Ticket（使用Server的hash加密，里面包含HTTP 服务会话密钥），和HTTP 服务会话密钥（使用TGS会话密钥加密）。

用户现在拥有HTTP Service Ticket和HTTP服务会话密钥
HTTP Service Ticket 通过 Server hash加密HTTP服务会话密钥通过TGS会话密钥加密
那么用户能不能伪造HTTP Service Ticket和HTTP服务会话密钥呢？-伪造HTTP Service Ticket需要Server hash加密-伪造时间戳使用HTTP服务会话密钥加密（伪造的HTTP服务会话密钥需要和HTTP Service Ticket里面的一样）

5、用户发送HTTP Service Ticket和时间戳（HTTP服务会话密钥加密）给Server。

Server 使用 server hash解密HTTP Service Ticket获得HTTP服务会话密钥加密再使用HTTP服务会话密钥加密解密时间戳

6、Sever发送时间戳（HTTP服务会话密钥加密）给用户

用户使用缓存的HTTP服务会话密钥解密时间戳

Kerberos认证流程


Client一共发起了3次请求（2次KDC（AS和TGS），1次Server）其中可以伪造TGT和Ticket。伪造TGT需要krbtgt的hash，伪造Ticket需要Server的hash。在AS不与TGS直接交互TGS会话密钥的情况下就构成了黄金票据，在Server不与KDC交互HTTP服务会话密钥的情况下就构成了白银票据的伪造。防范方法即AS与TGS交互TGS会话密钥，多重验证，避免篡改。白银票据同理。发现了一个有趣的地方，除了KDC之外，Client和Server都没有直接 交互hash。所以在理想情况下Kerberos完美的完成了身份认证。即白银票据和黄金票据主要用于维权，而不能直接横向或者纵向移动，因为不可能直接获取到hash。
