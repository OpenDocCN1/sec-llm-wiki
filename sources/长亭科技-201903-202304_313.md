**前言**  
  
  
  

  

本文主要介绍了笔者在某互联网企业（以下称Y公司）担任安全工程师期间，根据ISO27001信息安全管理体系中访问控制相关的安全控制目标，对公司原有的权限管理体制进行改进，解决了各种问题，特别是与人力部门的协调问题，自下而上推动体制的跨部门落地实施，形成相对标准化、规范化的且符合ISO27001合规要求的权限管理体制的过程与经验。

# 

  

  
  
  
**背景介绍**  
  
  
  

  

本文讲的权限管理，是信息安全领域的身份认证与访问控制的管理，在ISO27001信息安全管理体系中具体条目为A.9访问控制。许多企业内部都会有一套或者多套管理系统，这些系统支撑公司业务运行，涉及敏感信息、资金来往等，但在权限管理工作做得并不够到位，存在如离职员工账号未及时关闭、未贯彻最小权限原则导致个别角色被赋予了不必要的权限、缺乏权限审计和权限收回机制等安全管理缺陷。据笔者了解，一些中小型企业里权限管理员一般由IT运维或运营人员兼任。很多时候，公司管理层虽对权限管理工作很重视，但企业权限管理机制不完善，落地措施执行不到位，加上权限管理员的自身意识不足，会存在权限的开通、关闭和变更工作中缺乏相关的制度依据和流程审核，**权限管理员可能就只凭一封邮件、一条聊天消息甚至是口头传达就进行相关操作的情况，这些都是引起安全事故的潜在风险点。**

  

笔者刚入职Y公司时，权限管理工作也存在上述缺陷。当时公司内部有两个管理系统，而权限管理员分别是开发人员和财务人员，当笔者上任安全工程师之后，两个系统的权限管理员的职责也就顺理成章地交接过来了。

  

这两个系统里面的权限分配的情况大体相似，可以算是基于RBAC模型的管理模式。**RBAC即基于角色的访问控制模型，模型的三个基本属性分别为用户、角色和权限，将权限分配给角色，再将角色分配给相关的用户，是企业常用的一种访问控制模型。**这里说“算是”的原因是当时系统内的角色组不是根据部门或岗位来建立，而是一些相似功能或是业务上有关联的模块的集合。举例说明，将XXXX开通、XXXX登记、XXXX审核等前缀相同的功能相似的模块建立一个名称为XXXX管理的权限组。因此系统中存在很多个权限组，长久堆积下来，一个用户将会被授予很多个权限组，给权限管理员的日常管理工作带来很多不便，例如领导想知道某用户或是某部门的所有用户在系统中持有哪些权限时，管理员首先要列出用户被分配了哪些权限组，然后再逐一查看这些权限组被授予了哪些权限。系统中权限分配的情况相当杂乱，如下图所示。

  

![](../Images/0eeba02987c3c17fd36ba9b6e8b83c02.png)

  

当时权限开通的流程和执行情况大体如下：

  

| **新员工** || **旧员工** |
| --- | --- |
| 在纸质审批表上写着“开通与XXX(同部门人员)”相同的权限 || 员工在纸质审批表上勾选自己所需的权限，审批表将系统内所有的模块名称一一列举出来，足足有三四页A4纸 |
| 用户拿着表格找相关负责人签名审批后交给权限管理员执行 |
| 权限管理员为新员工新建账号，并记录XXX账号被授予的权限组，再将这些权限组授予用户。 || 查看员工勾选的权限模块在系统中是否存在已有的权限组，如果没有则单独再建立一个新的权限组，再将相关的权限组授予用户。 |
| 管理员将审批表格存档。 |

  

然而在实际操作中，以上每个环节都可能一些明显的不足：

  

|                 **新员工** || **旧员工** |
| --- | --- |
| 因为新员工对系统功能和业务不熟悉，在开通权限时无法准确选择所需的权限，所以一般是申请开通与其同岗位的员工账号的相同权限。但由于上述提到的“算是”的RBAC访问控制模型，每个账号中都堆积了很多个权限组。管理员需要先记录旧员工的权限组，再授予新员工的账号。 || 纸质审批表上列举了系统所有的权限模块，数量多且部分模块的名称相似，就算是旧员工也无法熟悉所有权限模块，在勾选模块时，容易错选或漏选，管理员在执行时也容易看漏。 |
| 如员工急需开通权限而相关负责人不在公司时，员工一般会请求管理员先执行后补审批，或者电话、微信等途径知会负责人后自行签字，甚至有可能出现未经同意假冒签字的情况。以上做法不仅不规范而且存在安全隐患，例如员工可能利用先执行后审批之间的空档期，利用所开通的权限进行恶意操作。 |
| 管理员需要先记录XXX账号所持有的权限组，再分配给新员工账号，这个方式容易出现权限漏给的情况。 || 基本上每次开通权限都需要新建权限组，再把新建的权限组授予用户账号，正是这种方式导致每个账号上都堆积了大量权限组。 |
| 因为每一份审批表都有数页A4纸，长期以往堆积下来的审批表格需要占用较多空间存放，且不方便溯源查找特定的审批记录。 |

  

  
  
  
**体制设计**  
  
  
  

  

笔者担任权限管理员后，恰逢公司准备申请ISO27001信息安全管理体系合规认证，因此笔者也借着这个机会开始着手对原有权限管理工作进行逐步改进，目标是建立一个真正基于RBAC模型的规范化、标准化的且符合ISO27001体系合规要求的权限管理体制。

  

ISO27001信息安全管理体系是基于ISO27001:2013和GB/T22080-1026标准文件。后者的附录A中列举体系的具体控制目标，其中A.9访问控制便是权限管理方面的相关要求，如下表。

  

| A.9 访问控制 |
| --- |
| A.9.1 访问控制的业务要求 |
| 目标：限制对信息和信息处理设施的访问 |
| A.9.1.1 || 访问控制策略 || 应基于业务和信息安全要求，建立访问控制策略，形成文件并进行评审。 |
| A.9.1.2 || 网络和网络服务的访问 || 应仅向用户提供他们已获专门授权使用的网络和网络服务的访问。 |
| A.9.2 用户访问管理 |
| 目标：确保授权用户对系统和服务的访问，并防止未授权的访问。 |
| A.9.2.1 || 用户注册和注销 || 应实现正式的用户注册及注销过程，以便可分配访问权。 |
| A.9.2.2 || 用户访问供给 || 应对所有系统和服务的所有类型用户，实现一个正式的用户访问供给过程以分配或撤销访问权。 |
| A.9.2.3 || 特许访问权管理 || 应限制并控制特许访问权的分配和使用。 |
| A.9.2.4 || 用户的秘密鉴别信息管理 || 应通过正式的管理过程控制秘密鉴别信息的分配。 |
| A.9.2.5 || 用户访问权的评审 || 资产拥有者应定期对用户的访问权进行评审。 |
| A.9.2.6 || 访问权的移除或调整 || 所有员工和外部用户对信息和信息处理设施的访问权在任用、合同或协议终止时，应予以移除，或在变更时予以调整。 |
| A.9.3 用户责任 |
| 目标：让用户承担保护其鉴别信息的责任 |
| A.9.3.1 || 秘密鉴别信息的使用 || 应要求用户遵循组织在使用密码鉴别信息时的惯例 |
| A.9.4 系统和应用访问控制 |
| 目标：防止对系统和应用的未授权访问。 |
| A.9.4.1 || 信息访问限制 || 应按照访问控制策略限制对信息和应用系统功能的访问 |
| A.9.4.2 || 安全登录规程 || 当访问控制策略要求时，应通过安全登录规程控制对系统和应用的访问。 |
| A.9.4.3 || 口令管理系统 || 口令管理系统应是交互式的，并应确保优质的口令。 |
| A.9.4.4 || 特权实用程序的实用 || 对于可能超越系统和应用控制的实用程序的实用应予以限制并严格控制。 |
| A.9.4.5 || 程序源代码的访问控制 || 应限制对程序源代码的访问。 |

**建设过程**  
  
  
  

  

01建立制度   

  

**笔者认为一项工作想要体制化发展，必须要有相关的制度作为支撑和依据，因此笔者第一步先编写了权限管理制度，**对权限管理相关工作包括权限开通、变更、关闭的流程、流程中相关负责人的职责、用户对于所持权限的相关责任等等作出了明确规定。

  

制度主要包括以下结构和内容：

  

1.  总则：指出制定该制度的背景、意义和作用，提出权限管理工作中遵循的相关原则其中最关键和核心的就是最小权限原则，指定权限管理员的担任者等等。
    
2.  审批流程：规定权限开通、变更、关闭的审批流程和相关审批人员。
    
3.  管理职责：规定相关人员的管理职责，如部门负责人、相关审批人员、账号持有者、权限管理员等，以及履责不力的问责条例。
    
4.  管理细则：规定各系统通过岗位角色建立权限组，对权限的开通、变更和关闭需要提交的审批流程进行说明。
    
5.  权限审计：规定各系统中的岗位权限组中的权限需要定期审计，核查是否存在多余权限、不当权限等情况。
    
6.  安全管理：对权限管理中的信息安全问题进行说明和规定，如初始密码的更改、密码的保管及异常情况的处理等。
    

  

制度编写完毕后，下一步是发布实施。因为笔者所在的运维部门不具备发布制度的职能，因此需要获得高层领导批准，由领导下达发布制度文件的任务予相关部门（如行政、法务等），笔者当时主要是以ISO27001体系的合规要求来取得领导批准，再由行政部门发布。

  

02规范流程   

  

**有了制度作为实施依据，下一步开始规范权限开通、变更和关闭的流程。**纸质化的审批表效率低下、浪费资源，当时Y公司使用钉钉作为内部沟通和协作工具，因此笔者将权限开通、变更的流程放到钉钉的审批功能上，流程主要审批节点设计如下：

  

1.  部门负责人：审核用户申请权限的需求是否符合实际情况，是否满足最小权限原则等。
2.  业务/运营/产品相关负责人：由于企业架构的不同，这里可能是不同部门的负责人，但是该负责人必须熟悉系统内功能模块以及对应的业务操作，需要审核用户申请的权限是否与其职能相匹配。
3.  特殊权限：当用户申请开通比较特殊的权限，如可以查看/修改大量敏感资料、可以操作客户资金或公司资金、可以对业务造成较大影响等，此时就需要相关部门如财务、风控，或者更高层的领导甚至是总经理进行审批。
4.  权限管理员所在部门负责人或上级：该审批人可能不会对流程内容进行过多的审批，更多作用是对下属工作的知情。
5.  权限管理员：流程最终走到权限管理员处执行，管理员只需要照单办事即可，一般情况下审批单申请了什么就操作什么，权限不多给也不少给。

权限关闭的流程则附带到员工离职流程里，因为在一些人数比较多的企业，作为一名基层技术人员很难及时掌握公司人员的变动情况，所以这个是最能保证离职员工账号得到及时关闭的做法。

  

03 梳理权限   

  

前面提到，各系统内的权限组不是按照部门或岗位建立，而是一些相似功能的权限模块的集合，一个账号上普遍堆积了十几二十个甚至更多的权限组，**梳理权限等于是将两个系统的所有权限组和权限模块的分配情况重新洗牌。**

  

笔者首先将系统内所有在用的账号整理出来，并连同账号使用者、部门、岗位等信息记录到表格里。再将各部门人员的账号所持有的权限组整理出来，再统计出这些权限组内包含的权限模块并进行去重。最后将整理好的权限按照部门和岗位重新建立权限组，整理后的权限分配情况表格如下：

  

![](../Images/a02ecd7a1c66e2ad3693da0516429211.png)

  

虽然这里看起来不难，但实际操作起来相当繁琐。因为每个账号上都分配了很多个权限组，需要逐个查看这些权限组里面的权限模块。理论上同岗位的人员所分配的权限组应该是一致的，而在这里却是各不相同，但是仔细查看又发现这些名称不同的权限组里面其实包含的权限模块是有雷同的，梳理权限时如果要逐个用户实施的话比较费时，因此笔者从每个部门每个岗位选取一个用户作为代表，整理出该用户所持有的所有权限模块后，再将这些模块分配到一个权限组，这个权限组就是后续分配给该用户所在岗位的权限组。

  

**经过梳理后，系统权限的分配情况由原先的一个用户多个权限组变为一个用户只有一个岗位权限组。**对比示意图如下，左侧是原本的权限组分配情况，右侧是梳理后的情况。

  

![](../Images/91cf0f4d45cbf9909799ab80b1775bc1.png)

  

权限梳理完毕后，笔者逐一跟各部门负责人核对表格上的岗位权限分配情况，部门负责人除了确认本部门岗位组所持有的权限是否符合最小权限原则外，也需要核查其他部门岗位的权限情况。比如，某业务岗位持有财务、风控这类比较敏感的权限，就需要对应部门负责人审查是否合理。

  

权限表格经过各部门负责人审查完毕并提交给高层领导审批后，就可以按照表格中权限分配的情况对各系统的权限组重新洗牌。洗牌后，必定存在某些用户会失去原先持有的权限，此时如果这些用户确实需要重新开通权限，统一走新的权限开通流程。

  

04 定期审计   

  

**权限审计是指定期对系统内的账号和账号所持权限定期进行核查以保证权限的分配情况始终符合最小权限原则。**在实施方面笔者主要借助两个表格。一个表格用于对各系统的账号、账号使用人、部门、岗位、持有权限、账号开通和关闭时间等进行记录，另一个表格则是前面提到的梳理权限后形成的权限分配情况表。

  

笔者首先核查第一个表格，主要目的审查是否存在未关闭的离职员工账号或是由于员工岗位调整不再需要的系统账号。在这个表格中记录了所有账号的开通和关闭时间，但是在实际操作中有可能会出现记录已关闭而实际未关闭。或者是记录未关闭而实际已关闭这两种情况。因此在核查时需要对照表格和系统中账号的实际情况，通过核对钉钉中的通讯录确认某位员工的在职情况和岗位情况，根据情况及时关闭或调整相关的账号。

  

第二个表格笔者召集各部门负责人以会议的方式进行审计，各部门负责人首先需要审查本部门相关岗位所持有的权限是否符合最小权限原则，再对其他各部门的岗位进行审查，特别是涉及财务、风控和其他比较敏感的权限，更加需要仔细审查。根据ISO27001体系的控制要求A.9.2.5，审计工作应该要形成记录，在体系认证审查时是需要检查的，因此笔者以会议签到表、会议纪要等作为审计工作的实施记录。

  

**权限审计这项工作在等级保护、ISO27001等信息安全体系中都有相关的合规要求，但是很多企业没有将这项工作落实到位。**下面笔者以两个基于真实案例改编的小剧场来体现权限审计的重要性：

  

1).A是某业务部门员工，B是某管理部门员工。在某个系统中，有一个权限本应该B所在岗位才能持有的，但是A却持有这个权限，并且利用该权限对某位客户的进行相关的业务操作。B登录系统查看该客户的记录发现被操作过，找到权限管理员通过查询操作日志发现是A操作的，但是A不应该有这个权限。于是B将这件事情向领导反馈要求问责，最后权限管理员由于未落实权限审计工作被问责处罚。

  

2).C是产品测试人员，其在系统中对应的权限组比较特殊。由于需要在生产环境中测试验收相关功能，因此每次上线新功能模块时，都需要为该权限组开通相关的权限。由于开通的权限没有在测试完毕后几时关闭，久而久之该权限组就拥有了非常多的权限。有一天，C在日常测试工作中在生产环境中进行了误操作，对业务造成了一定的影响，还惊动了高管。最后，权限管理员由于未及时关闭不必要的权限被问责处罚。

  

从以上两个小剧场的结局可看出，由于权限分配不当对业务造成影响，责任最后一般都会落到权限管理员身上。因此，落实权限审计工作，及时发现并收回分配不当的权限，一来可以避免由于误操作对业务造成影响，二来也是权限管理员应尽的职责。

  

  
  
  
**落地推动**  
  
  
  

  

在企业中，一名基层员工想要自下而上地推行一套制度、落实一套体制，会遇到很多阻力。

  

首先就是要获得领导的批准，发布制度。在领导的角度，他们会关注实施这套制度和体制的必要性、现有的制度和体制存在什么问题、拟推行的制度和体制能改进哪些地方、需要投入多少成本等等，

  

获得了领导批准发布了制度文件之后，接下来就是推动相关工作在各部门的落地实施。**这里关键是要得到审批流程中的各部门负责人的积极配合。**上文提到，Y公司原先就有权限开通相关的线下审批流程，但是相关负责人在审批时不一定能遵循最小权限原则。因此这里的重点就是要使相关负责人认同并遵循该原则，比较常见的做法是召开会议向相关负责人宣贯最小权限原则及基本的信息安全意识，为了引起负责人们的重视，可以深入介绍一下最小权限原则的重要性，并且举例说明违反该原则可能导致哪些后果，比如：因权限分配不当导致用户进行了误操作而对业务产生影响、个别用户私自获取公司内部信息谋取私利等等。然后再介绍权限管理制度里的问责条例，比如：因相关负责人未尽到审核义务而导致某用户被分配了不当的权限，且该用户利用这个权限进行了一些对影响公司业务运行的操作，此时就要追溯用户申请该权限时的相关审批负责人并进行问责。最后还需要由负责人们向部门同事传达相关的原则和意识。

  

笔者在跨部门的协调工作中比较困难的是与人力部门的协调。前面提到权限关闭的流程最合适的做法是附带在员工离职流程中，而当时人力部门不太乐意这样做，可能是认为员工离职流程不需要由一名基层技术员工来审批。为此，笔者通过网络上报导的一些离职员工利用系统权限进行报复性、破坏性操作，或者是窃取公司机密资料的案例，向人力部门强调离职员工账号及时关闭的重要性，然后传达了ISO27001体系认证中对员工离职流程方面的审查要求，最后才取得了人力部门的理解和认同。

  

  
  
  
**监督实施**  
  
  
  

  

经过上述提到的一系列措施，Y公司已经基本形成了一套相对标准化、规范化的权限管理体制，但身为一名安全工程师，笔者认为权限管理员并不能就此松懈。**权限管理员在整个体系中属于最终的执行者，**虽然上文中提到权限管理员在执行相关操作时，一般只需要照单办事。但是在实际审批流程中，难免会出现一些疏漏，比如某位负责人在执行审批时没有仔细审核，导致误审了不适当的权限。此时，作为权限管理员，就不能够照单办事，而是需要与申请人上级或相关业务负责人核实情况，必要时驳回审批单。

  

  
  
  
**总结**  
  
  
  

  

本文讲述了笔者对于权限管理工作的一些看法以及Y公司权限管理体制的改进过程。经过改进后，Y公司权限管理体制的结构可以概括为：制度依据、流程规范、权限审计和监督实施几个方面。其实Y公司的这套权限管理体制还不够完善，严格来讲一个系统中除了权限管理员外，还应该有安全管理员和审计管理员的角色，在等级保护中也有相关要求，但在一些中小型企业中并不能够严格落实。总而言之，**笔者认为在企业内部管理体系中，权限管理方面也值得重视，特别是互联网、金融、支付等类型企业的内部管理系统都是支撑业务运行的重要系统，**一旦由于权限管理相关措施落实不到位导致误操作、信息泄露等问题，都有可能对企业和业务造成影响。
