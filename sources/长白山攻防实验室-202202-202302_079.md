**姿势1:CSRF Token Tracker**  

CSRF Token Tracker是个插件,可以在BApp Store下载安装

![](../Images/9fc4abb573ed863e9544365dce893aa2.png)这种方式可以说是最简单的,但是不适用姿势2和姿势3中的案例，现有一个请求参数是user\_token  
![](../Images/9b130681c70ef727817d16ec73bddcb0.png)只需要在插件中添加  
![](../Images/c131297d9eab693547e85fec098e7970.png)

注意这里有个坑(搞了好久)

比如你想在repeater模块测试一下重新发送请求会不会修改密码

![](../Images/a0eb431dc72dadbbd4ba2885f490198a.png)

发现返回的结果仍然是302，这里是需要有一个有效的，没有使用过的user\_token去请求的!然后再去重放请求包就都会自动更新token了

  

总结一句就是你第一次用有效的token重放请求包就永远有效(自动更新token了)，你第一次用无效的token重放请求包就永远无效

  

**姿势2:定义宏**

在这个案例中使用CSRF Token Tracker无法成功自动更新token

![](../Images/b1f4fc3a2eaebbb1b24d068eb8a85d64.png)![](../Images/745ded3a382d1dad06a770e6bf0a7fde.png)

开始定义宏

![](../Images/ca91397b449db646b1c9c19b01d7ce12.png)![](../Images/50046963c064ab703d0ef3427d65da56.png)![](../Images/d8a017b95377beeea53d237851748f86.png)![](../Images/d9f6c83e59a0708b3edf5c9c126ec31d.png)![](../Images/2ecd4f4411b47838da77b01b1f759843.png)

一路OK回到这里

![](../Images/b03a0f553c1996526d23e467fd545db1.png)![](../Images/043bda0c1e401e2f2315daa07ce15bc6.png)![](../Images/54470a9e2cd5c4709210186e2842fcd0.png)

不懂就选择1,在所有请求前都运行宏

![](../Images/fea66a01340813bdaf7ac22b86177ffb.png)

来到repeater模块重新发送请求就不会说非法的csrftoken

![](../Images/fcbc8f02c73b1f8f6491183e3d574d0b.png)

来看日志发生了什么  

![](../Images/5f16a60e64e13d135f6ce3730df3603d.png)

我们使用repeater重放了登录的请求,也就是图中第71个请求

  
宏帮我们自动进行了了第70个请求获取了新的token让第71个带着新的token去登录

  

**姿势3:宏+Extractor**

在这个案例中前两种姿势均无效  
下载安装插件

![](../Images/6740b41c275efd77b5d4653772b2bd42.png)

先看下两个请求包  
第一个请求包就是获取token的

![](../Images/1f5f6f31b81b461ee0fce172038e5669.png)

第二个就是带着token去访问

![](../Images/03aac6d1dfbdb5da8109a63f7c85ec6f.png)

看过这两个请求包应该就明白了，这次token是在请求头中，而定义宏的时候会让你选择更新token的地方

  
这个地方却没有更新请求头的功能，所以姿势2在这里就失效了

![](../Images/997fe93d0c2a963db722dbc481581a5c.png)

首先定义宏获取token，这个宏只需要要确保在请求2之前会执行请求1，相比于姿势2的步骤简单一点

![](../Images/cf823abdc29f8a0599deb771484db9e1.png)![](../Images/fba5688bc013b50b9006f62552f5e43c.png)![](../Images/dc7e6175e607645e8702dc780a6ea500.png)

到这里宏就配置好了，在repeater重放请求2然后再logger+=里面查看  
确保每次都会在请求2前自动执行请求1就是正常的

![](../Images/cfe00588dcc031bf24a7e887631b3528.png)

然后配置插件Extractor  
把两个请求包都发送到Extractor

![](../Images/eeac4161d1d53020b389f32657096f35.png)![](../Images/5809a4b8fabd064726af2984b16871ed.png)![](../Images/2aadcb2a5a8394323efac7733d9eb664.png)

此时回到repeater模块重放发现token就有效了

![](../Images/b65386cd4f6677c93a240df007a9c42c.png)

再次回到logger++看发生了什么？看到第87个请求获取的token值为

407667d008b147199d174681a655aea0

![](../Images/14ddb6760614596427432faaa359c739.png)

第88个请求包的accessToken值也是

407667d008b147199d174681a655aea0

![](../Images/287919a06d1142c2c6b8423eceb7f448.png)

总结一下姿势3的思路：  
宏负责在请求2前发送请求1  
Extractor插件负责匹配和替换token
