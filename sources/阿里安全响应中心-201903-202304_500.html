概述

本文将介绍一个FackBook上的拒绝服务漏洞，我通过Semmle QL对Facebook的Fizz项目进行漏洞搜索，最终发现该漏洞。这是一个无限循环的缺陷，未授权的用户可以远程触发该漏洞。Fizz是Facebook TLS的实现框架，即https://facebook.com的“https”部分。在2018年8月6日，Facebook工程师Kyle Nekritz, Subodh Iyengar和 Alex Guzman联合发表了一篇博文，此博文是关于Facebook上大规模部署Fizz的一些介绍：

我们广泛地在我们的手机APP，Proxygen，均衡负载器和内部网络甚至是QUIC库，mvfst中部署使用Fizz和TLS 1.3。在我们的网络中流量，超过百分之50被TLS 1.3协议所保护。

Fizz是一个开源项目，因此其他的一些项目或组织可能也在使用它。

POC

我使用C语言写了该漏洞的一个简单POC，其主要功能是开启连接目标服务器的TCP套接字（socket），然后发送一个超过64KB的恶意流量包。只要发送完毕，这个程序就会关闭套接字，但是目标服务器并不会检测到异常，因为它已经陷入了无限的循环。我没有对任何真正的网站测试过该Payload，我只对使用了Fizz的一个样本服务器进行过测试。需要注意，这个漏洞触及到Fizz库的核心代码，所以其危害的不只是我的样本服务器。在我报告此漏洞之前，我认为*https://facebook.com* 一直都是处于风险之中。

Facebook已经更新了它们的系统，彻底修复了该漏洞，但是我将延缓几周分享POC代码，给其他的Fizz用户一些时间更新。

漏洞分析

这个漏洞的根源是一个+=导致的整形溢出，具体代码见PlaintextRecordLayer.cpp的42行：

auto length = cursor.readBE<uint16_t>();
if (buf.chainLength() < (cursor - buf.front()) + length) {
  return folly::none;
}
length +=
    sizeof(ContentType) + sizeof(ProtocolVersion) + sizeof(uint16_t);
buf.trimStart(length);
continue;

这段代码从输入的网络数据包中读取一个uint16_t，并且将它分配给length。换句话说，攻击者可以控制length的值。39行处的if语句看似在检查边界入口，但它实际上只判断了接受的数据是否足够用于下一步的解析。这就是为什么要发送64KB的数据才能利用该缺陷：42行处的代码表明了只有接收到length字节，它才会触发整形溢出。所以，我们把length设置为0xFFFB就可以实现利用。此时经过+=后，length的值又变为0。也就是说，经过43行代码的处理，然后调用trimStart函数却不会消耗任何数据，所以程序将一直循环迭代下去。这个漏洞的修复也非常简单：使用一个比uint_16更大的类型，从而杜绝整形溢出。

使用QL发现该漏洞

Facebook的工程师们在博文中经常把Fizz描述为“secure from the ground up（安全着陆）”，同时也分享一些使用C语言编写安全代码的经验，比如避免错误的state machine（状态机）转换。我也同意大部分的Fizz代码质量（安全性）都比较好。Fizz通常使用C++编写，这有效地避免了老C语言遗留下来的一些缺陷。尤其是它不进行任何手动的内存管理，所以基本上不存在缓冲溢出这类的漏洞。Facebook的安全人员告诉我，它们对Fizz做了fuzz测试，并且联系外部的公司对它进行了安全审查。总而言之，FB的Fizz是一个高质量的项目，安全团队已经做好了一切的安全措施。那么，这个漏洞为何还会存在，QL又是如何找到它的呢？

如果你去查看PlaintextRecordLayer.cpp的第42行，你也可以发现此处存在整形溢出。困难的是（面对如此多的代码），你不知道存在漏洞的是哪一行。Fuzzing能够自动高效地发现漏洞，但是它是基于随机数作为输入的，因此碰巧遇到特定代码的概率还是非常低的，此时Fuzzing不能发挥出很好的作用（正如我在前面提到过的，编写漏洞利用程序最难的一部分就是如何把输入与漏洞代码行联系起来）。但是QL不会被这一点约束。无论漏洞有多难触发，我都能够使用QL搜寻出所有潜在的整形溢出漏洞。有些结果实际可能无法确认，但是安全总比“遗憾”好。然而，我不能期望开发者们去修复成千上万个假设的“漏洞”，所以QL查询需要足够精准，返回的结果至少要是攻击者会认为是溢出的漏洞。

我刚开始搜寻该漏洞的查询有些小问题，我的同事Jonas Jensen帮助我改进了它，也就是我在这里用的。该查询比我原先的更加精准，它还可以提供C++中间展示，这个功能现在仍处于开发阶段。当相同操作具有多个源规则时，IR能够简化查询。举个例子，下面三行代码功能类似：

x = x+1;
x += 1;
x++;

如果不使用IR，在代码中搜寻附加内容的查询则需要为每一句子另添规则。但是如果使用，则只需为查询添加一个AddInstruction规则。

让我们使用IR来写一段查询来找出所有由大类型变为小类型的转换。这种转换可能会导致溢出。

import cpp
import semmle.code.cpp.ir.IR

from ConvertInstruction conv
where conv.getResultSize() < conv.getUnary().getResultSize()
select conv

如果你想尝试运行该查询，你可以下载QL for Eclipse和一个Fizz快照。这里有QL for Eclipse的说明文档。你也可以去LGTM的query console运行此查询，但是有个缺点是你只能查询最新版本的源码。由于Facebook已经修复了漏洞，所以你无法在查询控制台上找到该漏洞。

正如我们所期望的，上述代码会找出代码中由大至小的转化。这对刚开始搜寻潜在的溢出有点作用，但是我们需要的是一个更小的结果。如果攻击者能够有意触发整形溢出，那么这是一个安全漏洞。因此，我们需要增强查询（语句）转换过程中的上下文信息的部分，从而有效地搜寻出潜在的不受信输出点。通过使用新版的IR污染跟踪库来书写表达式，Jonas的查询很好的搜寻了不受信的输入点。但是不受信的输入又是从哪来？这取决于应用，因此这对建立目标应用攻击面的模型有所帮助。在Fizz这个例子，根源是Facebook上一个名为Folly的库，该库传输数据给IOBuf，然后Fizz跟进读取I0Buf。因此通过搜索Fizz中所有用到的I0Buf可以创建一个不受信数据源模型。但我们开发了不同的办法，对Fizz项目该方法即简单又不那么特别：当使用套接字发送数据时，通常是以网络字节顺序发送的。所以网络数据需要被转换为主机字节顺序，一般使用ntohs或ntohl实现。因此ntohs和ntoh1是“不受信输入”的绝佳代理人。有些遗憾Fizz并不使用ntohs或者ntoh1！而是Endian类来实现转化。QL类发现了Endian将网络字节顺序到主机字节顺序的转换方式：

class EndianConvert extends Function {
  EndianConvert() {
    (this.getName() = "big") and
    this.getDeclaringType().getName().matches("Endian")
  }
}

把所有东西结合起来，这是Jonas的查询，他使用污点跟踪来搜寻不安全的大小类型转化的代码，并且该转化依赖于不受信的输入：

/**
 * @name Fizz Overflow
 * @description Narrowing conversions on untrusted data could enable
 *              an attacker to trigger an integer overflow.
 * @kind path-problem
 * @problem.severity warning
 */

import cpp
import semmle.code.cpp.ir.dataflow.TaintTracking
import semmle.code.cpp.ir.IR
import DataFlow::PathGraph

/**
 * The endianness conversion function `Endian::big()`.
 * It is Folly's replacement for `ntohs` and `ntohl`.
 */
class EndianConvert extends Function {
  EndianConvert() {
    this.getName() = "big" and
    this.getDeclaringType().getName().matches("Endian")
  }
}

class Cfg extends TaintTracking::Configuration {
  Cfg() { this = "FizzOverflowIR" }

  /** Holds if `source` is a call to `Endian::big()`. */
  override predicate isSource(DataFlow::Node source) {
    source.(CallInstruction).getCallTarget().(FunctionInstruction).getFunctionSymbol() instanceof
      EndianConvert
  }

  /** Hold if `sink` is a narrowing conversion. */
  override predicate isSink(DataFlow::Node sink) {
    sink.getResultSize() < sink.(ConvertInstruction).getUnary().getResultSize()
  }
}

from
  Cfg cfg, DataFlow::PathNode source, DataFlow::PathNode sink, ConvertInstruction conv,
  Type inputType, Type outputType
where
  cfg.hasFlowPath(source, sink) and
  conv = sink.getNode() and
  inputType = conv.getUnary().getResultType() and
  outputType = conv.getResultType()
select sink, source, sink,
  "Conversion of untrusted data from " + inputType + " to " + outputType + "."

这个查询只能用来搜寻本文所述的漏洞。但目前该漏洞已经修复，查询已经无法找出有效结果。
