# 举个例子-什么是Kerberos委派?

某天，土豪A同学来到了他固定的K寄存中心取钱：1.A：您好，这是我的身份证，想进去取钱2.门卫：（验证身份），给你这个票据，去前台领号。A来到K寄存中心前台3.您好，这是我的身份证和门卫给的票据，要取点现金。4.前台：（验证身份），没问题，给你的号码，到柜台办理。5.6. A拿着身份证与号码，到柜台取了一个亿。以上就是一个简易的kerberos认证过程，用户使用自己的凭证获取了TGT（身份证换取的票据），再使用TGT得到了可以访问服务凭据ST（票据换取的号码），凭借ST请求服务，如下图：
![](../Images/0b0ac5a5a98c0a48c8ed898599591236.png)那么什么是委派呢，如果如果在一个域中，A使用Kerberos身份验证访问服务B，B再使用A的身份去访问C，这个过程就被称之为委派，委派分为非约束委派与约束委派：
**非约束委派**非约束委派在Kerberos中实现时，User会将从KDC处得到的TGT发送给访问的service1（可以是任意服务），service1拿到TGT之后可以通过TGT访问域内任意其他服务，所以被称为非约束委派。![](../Images/fbf2d3cc66d31599a19b7953d4cc5eca.png)A同学之前投资了点黄金,也放在了K寄存中心，但是中心对于黄金的存取管理更严格，必须由内部人员到金库操作。和取钱的流程一样，A同学分别在门卫和前台取了号，但是这次流程有所不同：A来到柜台前：(7)A：您好，这是我的身份证，请帮我取回我的黄金(8)(9)柜员拿着A的身份证，在系统中申请了去金库的凭证(10)(11) 使用A的身份，打开金库，运输了一吨黄金。(12)把黄金给了A。A通过身份验证去找柜员，柜员使用A的身份拿金子，这就是一个委派过程。但是华生，这里是不是有什么盲点！(13)(14)柜员拿着用户的身份证，不仅申请了去金库的凭证，还申请了去他保险柜、首饰箱。。。(15)(16)柜员顺利取走了属于A的物品。如果配置了非约束委派的Service1机器失陷，那么攻击者可以通过Service1拿到访问过此服务的用户TGT，以这些用户的身份访问其他服务。然后微软也发现了这种委派的不安全性，在windows2003中发布了约束委派的功能：**约束委派：**为了增加委派的安全性，在约束委派中，用户不能直接把TGT发给Service1，而是对发送给Service1的认证信息做了限制，**不允许service1代表User使用这个TGT去访问其他服务。**
这里包括一组名为S4U2Self（Service for User to Self）和S4U2Proxy（Service forUser to Proxy）的Kerberos协议扩展。Service1使用S4U2Self模拟用户向自己发送请求，并从KDC拿到了用于验证用户身份的ST（称为ST1），用ST完成用户的身份验证。完成认证后，Service1再使用S4U2Proxy协议，代表用户的身份请求去请求访问Service2的ST（称为ST2），通过认证后，代表用户使用ST2访问Service2。![](../Images/e6b2e35bdc9ebbd28ea3042fefbd8cbd.png)上次A的物品失窃后，整个K寄存中心改动了流程，并限制了柜台只能取钱以及被委托去金库，不能拿取其他的物品。那么A同学再来委托柜员取黄金时：
A来到柜台前（根据官方手册描述，用户在委派流程前，从kerberos以外的途径通过了身份认证，但Service1并没有A的身份信息）(1)A:您好，我想办理业务(2)柜员登录了系统(获得自身服务的TGT)，向系统（KDC）发起了一个是否能接待A同学的申请（S4U2Self）(3)申请通过，系统给柜员返回了A所需的信息(ST1）(4)柜员：您好，需要办理什么业务(5)A:我想取回我的黄金(6)(7)柜员用向系统提交了A同学访问金库的申请,得到了去金库的手续（ST2）。
(8)(9)(10)柜员受A的委托，代表A同学，拿着手续，去金库取了黄金，移交给了A。
是不是还觉得这个流程不太对？虽然柜员没有A同学的身份信息，也被限制了只能去往金库。但是他仍可以通过系统申请对A的接待和接受A的委派。如果柜员被人收买，那他可以在系统上发起去任何人金库的申请，并拿走他们的财产。
在实际环境中，如果Service1失陷，那么攻击者就可以伪造域内任意用户的身份，去请求被委派的服务Service2。
如果要配置约束委派，必须拥有SeEnableDelegation特权，该特权很敏感，通常仅授予域管理员。为了使用户/资源更加独立，Windows Server 2012中引入了基于资源的约束委派。
基于资源的约束委派与传统的约束委派不同，传统的约束委派是将Service2的SPN添加到Service1的msDS-AllowedToDelegateTo属性中，并且配置Service1的TrustedToAuthenticationForDelegation属性为true。基于资源的委派是将service1的SID添加到service2的msDS-AllowedToActOnBehalfOfOtherIdentity属性中，就可以达到相同目的。但是也因为这样，只要攻击者拿到具有修改msDS-AllowedToActOnBehalfOfOtherIdentity这个权限的账户，就可以进行上述的利用。
