前情提要：iOS Wi-Fi 格式串拒绝服务 0day 分析


移动安全公司 ZecOps 刚刚发了一篇关于 Wifi 格式化字符串的进一步漏洞分析，增加了一些新的内容，表示这个漏洞其实可以被利用！



在社交网络上被人踢爆漏洞的时间点是六月中，但早在 2021 年二月，这个点就已经被悄悄修复了一个同样的问题，但没给 CVE：



六月份 Carl Schou(@vm_call) 发现的问题需要连接上恶意名字的 Wi-Fi 热点。而毕竟一般人不会连接名字看上去有奇怪字符的热点。实际上在二月修复的这个问题严重的多，这个问题不需要用户交互，只要手机在热点覆盖范围，就会开始触发格式串漏洞。


我在前文写道，Objective-C 的格式串和 CTF 里用的 libc 不同，利用上也不同，不过没展开写。经典的 libc 格式串利用 %n 特性来向内存地址写入可控数据，从而构成利用原语。但 Objective-C 不支持 %n，而是引入了一个特殊的 %@ 符号。



写过 iOS 应用就会很熟悉这个用法，可以打印一个对象的描述信息（调用示例的 description 方法），如 <Object 0x1100000>。假如对象的指针可控，%@ 会尝试把这个数值当作内存地址解引用，传给 objc_msgSend。


早前任意地址的 objc_msgSend 多次被应用到漏洞利用场景。包括最早 nemo 的一系列文章介绍如何通过伪造的 isa 指针和 class 对象，实现 objc_msgSend 控制 pc 寄存器，结合 ROP 即可实现任意代码执行。后来引入 PAC 之后，Google Project Zero 利用这个原语，在通过 PAC 验证的情况下复用合法 isa 的方法，实现一种特殊的代码重用攻击，面向选择器编程（SeLector Oriented Programming，SLOP）。


针对这个点的可利用性，我之前的文章主要考虑两个方面。


第一这个格式串日志是打印到 syslog 里的，而没有远程回显。没办法用 %p 和 %x 打印栈上的内容。但这样一来用格式串做信息泄漏就没戏了。也许作为本地提权攻击可以通过 lockdown 访问日志，未做验证。另外本地提权的场景也不需要信息泄漏。


另一方面即使用了 %@ 做解引用，还要看具体堆栈和寄存器上的参数是否可控，也就是能不能引用到任意地址或者栈上的 buffer。


下的结论是不能利用，主要还是信息泄漏很困难，而且我分析的那个洞是之后需要用户主动连接的。


下面来看 ZecOps 这个分析。


首先在二月份被悄悄修复的漏洞里，用户交互是不需要的。不点也中招，即使不能执行代码，也会因为进程不断崩溃而导致 Wi-Fi 失灵和后台疯狂耗电。


到了参数控制的部分，这个骚操作是我没想过的：




通过特殊的设备可以喷射大量的 SSID。


SSID，也就是这里的格式化字符串最长支持到 32 个字符，因此最多可以插入 16 个 %@。具有格式化字符串漏洞的函数局部变量里有一个字符串指向 SSID 热点名。通过调整格式串，可以构成任意地址的解引用。


经过微调，ZecOps 发现这个字符串可以稳定控制 objc_msgSend 的 SELF 参数指针：


DDDD%x%x%x%@


文章到这里默认 objc_msgSend 可以控制 PC 指针，就没有再往下分析。


其实之前我有亲手调试过当前版本的 objc_msgSend 的实现，草稿箱里也丢了这篇 Objective-C 格式串利用的文章，但是发现了一处小问题。


在格式化函数里，%@ 最终输入了 description 方法的返回值。但在当作对象解引用时，会先发送 isProxy 等消息来检查对象的一些信息。


在运行时里，selector 会对应一个 IMP 指针，其实就是函数方法具体实现的机器码地址。漏洞利用时，SELF 指针指向一段内容受到攻击者控制的内存。objc_msgSend 函数会根据类和 selector 找到具体的 IMP 指针，然后当作函数执行之。通过伪造的 selector 和 IMP，就有机会让 __objc_msgSend_uncached_impcache 返回任意的地址。这个任意函数地址可以指向系统库已有的 ROP gadget，从而实现任意代码执行。


然而在当前的 mac / iOS 上测试时，我发现 Objective-C 运行时针对这种情况做了一个很恶心的检查。


在函数 lookUpImpOrForward 里多了一个 checkIsKnownClass 调用。这个 cls 参数就是我们需要伪造的运行时信息。


IMP lookUpImpOrForward(id inst, SEL sel, Class cls, int behavior){    const IMP forward_imp = (IMP)_objc_msgForward_impcache;    IMP imp = nil;    Class curClass;
    runtimeLock.assertUnlocked();
    if (slowpath(!cls->isInitialized())) {        // The first message sent to a class is often +new or +alloc, or +self        // which goes through objc_opt_* or various optimized entry points.        //        // However, the class isn't realized/initialized yet at this point,        // and the optimized entry points fall down through objc_msgSend,        // which ends up here.        //        // We really want to avoid caching these, as it can cause IMP caches        // to be made with a single entry forever.        //        // Note that this check is racy as several threads might try to        // message a given class for the first time at the same time,        // in which case we might cache anyway.        behavior |= LOOKUP_NOCACHE;    }
    // runtimeLock is held during isRealized and isInitialized checking    // to prevent races against concurrent realization.
    // runtimeLock is held during method search to make    // method-lookup + cache-fill atomic with respect to method addition.    // Otherwise, a category could be added but ignored indefinitely because    // the cache was re-filled with the old value after the cache flush on    // behalf of the category.
    runtimeLock.lock();
    // We don't want people to be able to craft a binary blob that looks like    // a class but really isn't one and do a CFI attack.    //    // To make these harder we want to make sure this is a class that was    // either built into the binary or legitimately registered through    // objc_duplicateClass, objc_initializeClassPair or objc_allocateClassPair.    checkIsKnownClass(cls);


看注释：


We don't want people to be able to craft a binary blob that looks like a class but really isn't one and do a CFI attack.


最后走到这个内联函数：


/************************************************************************ isKnownClass* Return true if the class is known to the runtime (located within the* shared cache, within the data segment of a loaded image, or has been* allocated with obj_allocateClassPair).** The result of this operation is cached on the class in a "witness"* value that is cheaply checked in the fastpath.**********************************************************************/ALWAYS_INLINEstatic boolisKnownClass(Class cls){    if (fastpath(objc::dataSegmentsRanges.contains(cls->data()->witness, (uintptr_t)cls))) {        return true;    }    auto &set = objc::allocatedClasses.get();    return set.find(cls) != set.end() || dataSegmentsContain(cls);}


上面做了三个检查：


  1. 类指针指向 dyld_shared_cache 的系统库的只读 data 段

  2. 类指针在全局变量 objc::allocatedClasses 里能找到

  3. 类指针指向可执行文件自身的只读 data 段


以上三个检查分别对应系统库的 class，动态使用 obj_allocateClassPair 创建的 class 和可执行文件自身的 class。我研究了一下发现并不好绕过。


首先第一和第三都是只读的页，只能复用到已有的 class，自然不能使用自定义的 IMP 指针。第二个检查在全局变量上做查找，需要一些内存读写操作才能插入新的类并实现利用。在这个漏洞里只能解引用，缺乏必要的原语。


不能使用恶意的自定义 class，意味着只能走 SLOP 的路线。一般来说 isProxy 和 description 方法在实现的时候都不会有副作用，更不要提触发 invoke 方法之类的骚操作，我反正看了一下就放弃了。


最后只会抛出一个冷冰冰的异常：


_objc_fatal("Attempt to use unknown class %p.", cls);


如果有读者能绕过这个 checkIsKnownClass 检查，欢迎留言！！


看完博客之后其实 ZecOps 也只是做了 POC，并没有做完整利用。很明显的两个问题没搞定：


  1. 没有信息泄漏，随机化没搞定。即使没有 PAC，还是需要算出 ROP gadgets 的地址

  2. objc_msgSend 的这个检查，他们没有亲测过（哈哈）


到这里说可利用性还是为时尚早，不过重要的是构造了两个之前未确认的关键条件：


  1. 无需交互的 0click 能力

  2. 任意地址解引用


能搞定完整利用的话这个漏洞就非常可怕了。
