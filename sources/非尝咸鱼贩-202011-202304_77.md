# 德国安全研究员公开智能汽车无接触攻击——TBONE

> 原文：[http://mp.weixin.qq.com/s?\_\_biz=Mzk0NDE3MTkzNQ==&mid=2247483861&idx=1&sn=cda2e5cddf12bf9914b5486234e29454&chksm=c329ff25f45e7633e3852b5016c6d1e65bffad4a5e4f4606ed14d5c5bece2d0a998d4d763b10&scene=126&sessionid=1681657511#rd](http://mp.weixin.qq.com/s?__biz=Mzk0NDE3MTkzNQ==&mid=2247483861&idx=1&sn=cda2e5cddf12bf9914b5486234e29454&chksm=c329ff25f45e7633e3852b5016c6d1e65bffad4a5e4f4606ed14d5c5bece2d0a998d4d763b10&scene=126&sessionid=1681657511#rd)

来自德国的安全研究员 Ralf-Philipp Weinmann 和 Benedikt Schmotzle 近日公开了他们在某知名电动汽车品牌上发现的漏洞“TBONE”。

  

具体是哪个品牌，你猜？

  

在接近汽车（但无需任何物理接触）的情况下，汽车会自动连上恶意的 Wi-Fi 热点，触发车载信息娱乐系统（infotainment）的远程代码执行漏洞，最终再通过其他 MCU 的漏洞解锁车门，使用一些原本需要面板才能触发的功能。漏洞不涉及 ECU，也就是**还不能控制驾驶**。

  

为了增强演示效果，他们把搭载攻击工具的硬件装到了无人机上。只要靠近汽车大约 100 米内即可。画风变的很像游戏 Watch\_Dogs 里的设定。在这个游戏里，主角的无人机无所不能，可以远程入侵包括汽车在内的多种设备。游戏剧情里正好有一个配角叫 T-Bone。

  

当然 T-Bone 也可以理解为该汽车厂商的 T 型 logo。至于这个名字到底是怎么来的，得问作者本人了。

  

他们组成了 Kunnapwn 团队，原本为 Pwn2Own 2020 准备了这项研究。在 2019 年，Amat Cama 和 Richard Zhu 组成的 fluoroacetate 队伍利用浏览器的漏洞拿到了车载操作系统的权限，当场开走了一辆 Model3 并拿走了 $35,000 奖金。

  
可惜 2020 年突如其来的疫情席卷全球，Pwn2Own 取消了汽车的项目，并把其他所有浏览器项目改成线上。之后 Kunnapwn 团队直接向厂商报告了问题，在 2020 年十月底得到修复。

  

漏洞来自于一个车载系统用到的开源组件 ConnMan。

  

ConnMan 是一个网络管理组件，用以连接 Wi-Fi 和管理 DNS、DHCP 等相关配置。Kunnapwn 通过 fuzz 很快找到一个栈溢出（CVE-2021-26675）：

  

![](../Images/e64bcdf9615398a484049aa083693cd4.png)

  

uptr 是来自上层调用的栈缓冲区，这里用了一个写死的长度 NS\_PREFIXEDSZ。

  

按理说 2020 年了，首先栈溢出漏洞属于比较“初级”的内存错误，代码质量好的项目很难再出现；其次当今的操作系统通过地址随机化、栈 cookie 和不可执行页阻断了相当一部分漏洞利用。

  

这个漏洞的触发方式是连接一个恶意的 Wi-Fi 热点。该品牌的车载娱乐系统内置了配置。当扫描到名为 Tesla Service，密码为特定字符串的热点就会自动连接。

  

不过有漏洞的代码默认情况下不能触发，需要车载系统使用 ConnMan 本地的 DNS，然后才能走到 DNS Proxy 当中存在漏洞的代码。Kunnapwn 使用 WPAD 协议，在 DHCP 给汽车分配好地址之后自动发起一个可控的 wpad.<domain> 查询，成功触发了漏洞。

  

这个车载信息娱乐系统使用了 Linux，当时的内核版本 4.14，运行在 Atom CPI（x86\_64 指令）上。用户态进程使用了 Kafel 和 AppArmor 对 syscall 过滤和沙箱限制。NX、ASLR 和 stack cookie 都是开启的状态。

  

不过这个栈溢出漏洞品相非常不错。这个 memcpy 在一个循环里，通过精心构造条件，可以让 memcpy 中的 uptr 自增可控的长度而不发生实际的写入。

  

![](../Images/d27c41ec15d4f9f6629fc2227f7118a4.png)

  

这样一来可以在不覆盖 stack cookie，而又部分覆盖栈上保存的返回地址，绕过了 canary 的检测。

![](../Images/4473e139e9395de5a0e3870dac16d768.png)

部分覆盖地址过随机化对于赛棍是基本操作。保存的返回地址有 8 字节，因为这个 CPU 是 little-endian 的，在从低地址开始向后覆盖时，随机化的部分最后才会被写入。因此可以直接覆盖指针的低比特位，跳转到当前进程内的任意指令。

  

这里提到的 ASLR 指的是当前进程。为了编写完整的 exploit 还需要获得 libc 的地址。不幸的是库的随机化和主程序所用的偏移还不一样。所以他们之后再找了另一个信息泄漏漏洞 CVE-2021-26676 用来获取栈上的指针。

  

这里没有直接用栈溢出漏洞执行 ROP 来读内存，笔者猜想可能是因为 ConnMan 里缺少必要的导入函数。他们在另一个处理 DHCP 的函数 listener\_event 里找到了一处可以重复触发的越界读，从栈上读取包括 libc 等库的返回地址在内的内容。

  

接下来就是开始 ROP。他们使用 mprotect 加载了一段较短的 shellcode，然后用 shellcode 反弹连接下载执行更长的攻击载荷（另一段 shellcode）。

  

Connman 进程使用独立的用户名（非 root）运行，还有沙箱策略，只能调用有限的 syscall 和部分系统资源，甚至不能启动 bash 进程。不过作为管理网络的进程，它可以有限地调用 modprobe 来加载具有原厂数字签名的内核驱动，关闭防火墙。
