谈谈 macOS 11.3 修复的 GateKeeper 绕过

这篇文章写完已经凌晨了，只能拖延到第二天再发。


苹果前晚发布了 BigSur 的 11.3 版本更新，修复了数个外部报告的安全问题。其中最有意思的是这个 GateKeeper 绕过，会让用户有下载安装恶意软件的风险，而且已经被发现野外利用。


说实在话这个漏洞属于安全特性绕过，倒不至于为之恐慌。实际上一些盗版软件用户甚至会主动关闭 GateKeeper，中招了也只能认了。


不过既然完整细节已经公开，况且确实有人已经在做攻击，还是赶紧升级系统到 Big Sur 11.3 吧。



GateKeeper 在 OS X Mountain Lion 被引入，旨在防止用户从网上被诱导下载运行未知的程序。Windows 上与之类似的功能有 SmartScreen。


两者的工作原理类似。浏览器从网上下载回来的文件会在属性中加上“来自 Internet”的标记；针对特定的文件类型，特别是可执行文件，会在打开之前弹出提示。


macOS 加上的文件属性是 com.apple.quarantine。经过疫情一年多的肆虐，相信大家对这个单词已经非常熟悉了……


$ xattr Downloads/PoC.zipcom.apple.maclcom.apple.metadata:kMDItemDownloadedDatecom.apple.metadata:kMDItemWhereFromscom.apple.quarantine


对于 mac 的应用软件，如果是直接提供软件包，一般有两种最流行的格式。第一种是 .pkg 格式，提供一套标准化的界面；另一种则是把 .app 打包成 .dmg 镜像，用户挂载 .dmg 之后直接运行或者复制到 /Applications 目录。


还有一种比较少见的就是直接把 .app 打包成 *.zip。Safari 默认有一个“下载后自动打开‘安全’文件格式”的功能，而压缩包默认关联的系统应用就是自动解压到当前目录。所以把 app 打包到 zip 里之后，用户感觉上是直接下载了一个 .app 回来，但实际上是系统自动做了解压的操作。


以上的集中情况都会受到 GateKeeper 限制。


macOS 虽然没有像 iOS 那样仅允许从应用市场下载程序，但这些年以安全为名实际上在逐步收紧生态。现在苹果提供了一个“公证”（notarization）机制，即使第三方软件自行提供安装包而不通过 App Store 分发，也要求将应用上传到苹果服务器，从而获得一个认证过的数字签名。




对带有“隔离”标记的 app，假如代码具有公证过的数字签名，就会弹出如图的对话框。假如没有，则会直接提示文件无效，不提供打开的选项（除非使用 control^ 单击在右键菜单中打开）。


回到恶意软件的场景。


作为恶意软件的传播者自然传播更广。使用浏览器 0day 太奢侈，诱骗下载运行才是最实惠的做法。制作一个虚假的 Flash 安装包或者恐吓用户安装所谓的杀毒软件来诱导下载一直都有人玩。


GateKeeper 至少能通过多个弹窗让用户运行之前想清楚再点，或者干脆没法执行。


这个野外被利用的漏洞的特点就是，使用了一个畸形的 .app 包，使得一个完全没有代码签名（更不要说公证）的脚本文件，即使有隔离标记也能被点开执行。


文章一开头我说这个漏洞其实没有特别严重，不是说漏洞品相不够好，而是很多人其实为了安装特别版的软件，照着网上的教程用 sudo spctl --master-disable  把 GateKeeper 直接关了。另外运行来历不明的盗版软件本身就是一件高风险的事情。



下面是这个漏洞的细节，主要参考了 Objective-See 的逆向。


正常情况下，一个 app 的结构包含如下文件：


  • Wonderful.app

    • Contents

      • Info.plist 元数据

      • MacOS

        • Wonderful 可执行文件


其中 Info.plist 定义了程序的基本信息，如图标、主程序的文件名等。主程序没有扩展名，必须带有 x（可执行）属性，可以是一个带有 shebang 的脚本文件，也可以是 macho 格式的二进制原生代码。


主程序的可以用任意文件名，只要在 Info.plist 的 CFBundleExecutable 里声明即可。


在这个漏洞里，攻击者构造的恶意 app 没有 Info.plist，而是直接在 Contents/MacOS 里放置了一个与 app（没有扩展名）同名的可执行文件 Wonderful。这似乎是非常老旧版本 OS X 的遗留格式。


这个畸形的 app 包并没有触发 GateKeeper 警告，只要确认打开就会直接运行里面的 shell 脚本。加上脚本天生的跨平台能力，一个 poc 可同时支持 Apple Silicon 和 Intel 的处理器。



虽然在我本地复现的环境里弹出了一次提示，但这个 app 仍然可以打开。目前 Safari 为了防止下载功能被滥用，还会额外询问一次是否允许网站下载文件。因此到这一步会有两个弹窗确认。


Objective-See 提供的录屏动画没有任何提示，应该是事前点过，记住了默认选择：



但无论怎样，按照 GateKeeper 正常的设计，这个程序应该被阻止运行。“打开”按钮根本不会显示，而是直接提示应用已损坏。


Objective-See 的分析里贴了很长的一段过程，从日志跟踪到单步调试定位具体的函数。有兴趣学习苹果平台逆向的可以移步原文参考。这里就长话短说，直接跳到根本原因。


GateKeeper 机制背后的实现其实挺复杂的，简单的一次点击会牵扯到多个用户态服务进程甚至内核驱动的协同。




“程序无法被打开，因为已损坏”的对话框来自 CoreServicesUIAgent 进程。


系统在显示弹窗之前会查询当前系统策略，是否关闭了特定安全措施，以及当前文件是否已经被用户放行过……这一通操作是由 syspolicyd 实现的。


关注过我以前发布过的技术演讲的读者可能对这个进程有点印象。除了实现 GateKeeper 的一部分功能，它还负责检查内核驱动的合法性。


syspolocyd 每次检查 app 包的合法性，会创建一个 PolicyScanTarget 对象，包含 isScript、isBundled 等属性。当 Info.plist 文件不存在时（本文的畸形文件），isBundled 为 false。


最终来到这个方法：


-[EvaluationPolicy determineGatekeeperEvaluationTypeForTarget:withResponsibleTarget:]


  // -[EvaluationPolicy determineGatekeeperEvaluationTypeForTarget:withResponsibleTarget:]  isAppWrapper = (unsigned int)objc_msgSend(target, "isAppWrapper");  isQuarantined = (unsigned int)objc_msgSend(target, "isQuarantined");  if ( !isQuarantined      || ((unsigned int)objc_msgSend(target, "isUserApproved") & 1) != 0      || (unsigned int)objc_msgSend(target, "isScript") &&       !(unsigned int)objc_msgSend(target, "isBundled") )  {      return 2;  }


仔细看这个逻辑。虽然 isQuarantined 和 isScript 都满足了，但程序缺少 Info.plist 导致 isBundled 返回 false，于是直接返回了 2，没有弹出警告也没有阻止运行。


当这个函数（错误地）返回 2 之后，上层的 -[EvaluationManager evaluateScanResult:withEvaluationArguments:withPolicy:withEvaluationType:withCodeEval:] 便误认为策略是放行，从 GateKeeper 眼皮底下溜了过去。



没有 Info.plist 的畸形 app 应该是具有相当年份的老旧 OS X 上的格式，在 GateKeeper 之前就有了。为了兼容，也可能苹果压根就没留意到，便被保留至今。


这是一个典型的 corner case 问题导致的程序错误，从而绕过系统的安全机制。


GateKeeper 绕过除了浏览器下载这个触发点之外，还有可能出现在即时聊天、邮件等传附件钓鱼，对 red team（蓝军）有一定程度的实战意义。
