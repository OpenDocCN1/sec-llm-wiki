过年之后好久没写文章了，灌水一篇。


大家在新闻或者短视频上可能都看到过“恶意充电宝盗取个人隐私”的说法，由于充电口往往具有数据传输功能，攻击者可以利用手机内置的数据同步甚至 App 安装功能来获取隐私、植入恶意程序。



那这是真的吗？


当然是真的。



以 iPhone 为例，在电脑端使用 iTunes 管理软件可以对手机当中的联系人、照片等数据进行访问。iTunes 内部使用的是 iOS 的 usbmux 协议[1]，目前支持 USB 和 Wi-Fi 两种方式访问。有大佬逆向协议之后实现了一个开源库 libimobiledevice[2]，并在此之上实现了数个和数据备份、App 调试相关的工具。


网上关于 usbmux 和 lockdown 的机制文章[3]很多，此处不再赘述。


“恶意充电宝”最简单的实现方式便是基于 usbmux 与手机交互。libimobiledevice 作为开源软件可以移植到 Android、树莓派等平台上，伪装成一个充电宝是可行的。



第一次访问 usb 时需要配对，在点击“信任”并输入锁屏密码之后才会正式允许访问。因此在连接陌生的设备时，永远不要点击信任。照片、通讯录等隐私信息可以立即访问，而其他 App 的敏感数据则可能要运行漫长的备份。不过考虑到诱骗充电这种场景，这个备份时间是可以接受的。


如果需要进一步安装程序，还需要用户主动在系统设置当中信任相关的证书，还需要再输入一次锁屏密码，然后点开 App，交互繁琐。如果这样还能中招，那就只能说……


iOS 11.4.1 引入了更严格的 USB 限制模式[4]，用以提高物理接触下数据提取的门槛。




前面这一串都是铺垫，攻击思路和技术细节在网上已经很多人写过了。


本文将分享这种攻击场景之上通过一些不起眼的小问题，直接拿到 iCloud 账号登录权限的案例。这个问题在去年 2 月份报给了苹果，然后他们偷偷摸摸修复了，别说给钱，连个致谢也没有。


We noticed your tweet about a possible flaw in the iCloud protocol design. We are interested in learning more about the issue you identified. Also, any report will be evaluated against the Apple Security Bounty criteria at https://developer.apple.com/security-bounty/.


本文提到的一些技术细节在之后的 iOS 版本上已无法复现。


正文开始。



之前提到的 USB 服务基本上都是通过 lockdownd 服务进程来管理，路径在 /usr/libexec/lockdownd（可以从 ipsw 固件中找到）。例如访问照片用的服务是 com.apple.afc，对应文件 /usr/libexec/afcd。服务名的注册信息以 property list 格式被写死到 lockdownd 的 __services 区段中。


安装 lief 库之后，通过如下 python 代码（或者使用 iOS 安全研究必备的 jtool）可以提取这个区段的内容：


import lief
lief.logging.disable()o = lief.parse('lockdownd')for sec in o.sections:    if sec.name == '__services':        print(bytes(sec.content).decode())


iOS 7 越狱工具通过攻击内置的 lockdown 服务来获取最初的用户态代码执行[5]，感兴趣的读者可以找当时这个越狱工具的技术分析来看。


而除了内置的服务之外，苹果将调试相关的功能通过 Xcode 提供。在 Xcode 的安装目录下有一个 DeviceSupport：


/Applications/Xcode.app/Contents/Developer/Platforms/iPhoneOS.platform/DeviceSupport


里面有多个版本对应的 DeveloperDiskImage。如果一台手机被用作真机调试，Xcode 会自动将对应版本的镜像安装到手机的 /Developer 下。这也会额外启用更多的 lockdown 服务。完整列表可以查看 DeveloperDiskImage/Library/Lockdown/ServiceAgents 下的文件。


Xcode 内置的 Instruments 工具便在 iOS 端安装了一个服务端 com.apple.instruments.remoteserver.DVTSecureSocketProxy。Instruments 可以在真机测试环境中收集调试版本的 App 的性能信息，具有一些特殊的功能。Instruments 对应的服务端进程是 DTServiceHub，协议的实现代码在 DVTInstrumentsFoundation 模块，感兴趣可以自行逆向。


之前有人逆向过 Instruments 的协议和实现细节[6]，发表在 RECON 上：


Discovering the iOS Instruments Server


https://recon.cx/2018/montreal/schedule/system/event_attachments/attachments/000/000/043/original/RECON-MTL-2018-Discovering_the_iOS_Instruments_Server.pdf


简单来说，Instruments 的协议基于 usbmux，其中使用 DTXMessage 类描述了跨设备的远程过程调用。


在 DTServiceHub 服务当中定义了数个 channels，以各自的 identifier 区分。部分列表如下：


$ strings Library/PrivateFrameworks/DVTInstrumentsFoundation.framework/DVTInstrumentsFoundation \    | grep com.apple.instruments.server.servicescom.apple.instruments.server.services.ultraviolet.renderercom.apple.instruments.server.services.assets.responsecom.apple.instruments.server.services.networkingcom.apple.instruments.server.services.networking.immediatecom.apple.instruments.server.services.networking.deferred...


获得对应的 channel 之后，Instruments（客户端）使用 DTXMessage 类封装远程过程调用请求。一个 DTXMessage 包含如下信息：


  • selector：远程方法的 selector 字符串

  • arguments：参数


为支持复杂对象结构，参数会使用 NSKeyedArchiver 序列化成二进制数据传输。


例如调用如下远程方法来启动一个 App：


-[DTSpringBoardProcessControlService launchSuspendedProcessWithDevicePath:bundleIdentifier:environment:arguments:options:]


伪代码如下


id channel = [device.connection makeChannelWithIdentifier:    @"com.apple.instruments.server.services.processcontrol.feature.deviceio"];DTXMessage *msg = [DTXMessage messageWithSelector:    @selector(launchSuspendedProcessWithDevicePath:bundleIdentifier:environment:arguments:options:)    objectArguments:nil, @"com.apple.Fitness", nil, @[], @{@"StartSuspendedKey": @NO}];[channel sendControlSync:msg replyHandler:^(id reply, void *arg2) {    id payload = reply.payloadObject;}];


这种消息格式看上去很危险，如果不对 selector 加以限制，可能造成远程代码执行。苹果自然意识到了这一点。远程过程调用要求 selector 必须在 @protocol DTXAllowedRPC 当中定义。可以通过如下的 frida 脚本在 DTServiceHub 进程中列举出所有可以远程调用的方法：


for (var name in ObjC.protocols) {  var protocol = ObjC.protocols[name]  if ('DTXAllowedRPC' in protocol.protocols) {    console.log('@protocol', name)    console.log('  ' + Object.keys(protocol.methods).join('\n  '))  }}


在知名的移动安全测试框架 frida 中也应用到了这个机制，用来实现免越狱的 App 信息枚举和杀进程[7]。可以参考其源代码的 DTX 等实现：


https://github.com/frida/frida-core/tree/8ed473d/src/fruity


顺便提一句，由于这个协议用到了 NSKeyedUnarchiver，而在历史上这个类是出过几个可以利用的漏洞的。如果有反序列化的安全漏洞，可以直接获取 DTServiceHub 进程当中的代码执行。


扯得有点远了。本文获取 iCloud 登录凭据，正是滥用了 Instruments 的协议。



刚才我们提到了一个可以启动 App 的方法：


-[DTSpringBoardProcessControlService launchSuspendedProcessWithDevicePath:bundleIdentifier:environment:arguments:options:]


正常情况下，Instruments 不允许对来自应用市场的 App 进行测试，因为大部分探针需要使用 task_for_pid 注入目标进程。如果没有越狱，只有通过 Xcode 运行的调试版应用才能满足条件。


这个方法默认的 StartSuspendedKey 为空或者 @YES，DTServiceHub 会调用 task_for_pid 调试目标进程。在之前的版本中，如果给这个参数传入 @NO，便可以直接启动任意 App，而不会走入调试的分支。


比较特别的是，正常情况下我们是从 URL Scheme 唤起应用的。而这个函数可以控制 App 的 argv 和环境变量——包括市场应用。


改了环境变量能干什么？



在 iOS 10 之后，系统内置的 SQLite3 开启了对环境变量 SQLITE_ENABLE_SQLLOG 的支持。这个环境变量可以设置一个目录，SQLite3 将所有的 SQL 操作写入文本日志，并给所有打开过的数据库创建一个副本。


例如在越狱设备上测试 App，加入 SQLLOG 参数之后启动，就会生成如下文件：


ios:/private/var/mobile/Containers/Data/Application/.../tmp root# lsWebKit      sqllog_05860_00000.sql  sqllog_05860_00003.sql  sqllog_05860_01.dbsqllog_05860.idx    sqllog_05860_00001.sql  sqllog_05860_00004.sql  sqllog_05860_02.dbsqllog_05860_00.db  sqllog_05860_00002.sql  sqllog_05860_00005.sql  sqllog_05860_03.db


05860 是 App 的进程 id，用 0 补足五位数。扩展名为 idx 的文件保存了数字编号和原始路径的对应关系，示例如下：


root# cat sqllog_05860.idx0 /private/var/mobile/Containers/Shared/AppGroup/21805C48-3DD1-4973-BDB8-F26441BE74B3/GIPPhenotype/phenotype.db1 /var/mobile/Containers/Data/Application/E89CEF28-30BA-41F8-BDB3-BD05E0598D32/Library/Application Support/data/johnsmith@outlook.com/sqlitedb2 /var/mobile/Containers/Data/Application/E89CEF28-30BA-41F8-BDB3-BD05E0598D32/Library/Application Support/data/johnsmith@outlook.com/imapsqlitedb3 /private/var/mobile/Containers/Data/Application/E89CEF28-30BA-41F8-BDB3-BD05E0598D32/Library/Caches/com.google.Gmail/Cache.d


好了，到这里可以用调试功能给任意 App 加环境变量，然后生成所有 SQLite3 数据库的副本。


由于沙箱机制，App 只能写入自身的容器路径内。如果为了信息提取而生成副本，原始文件我们也是可以通过 iTunes 备份之类的方式拿到的。这样有什么意义吗？



系统内置的 App 未必会有沙箱，或者规则限制比第三方应用宽松很多。例如内置浏览器 MobileSafari 拥有对如下目录的写入权限：


/var/mobile/media/iTunes_Control/iTunes


而这个目录可以通过 usbmux 的 AFC 服务直接读写。给 Safari 的 SQL 日志定向到这个目录，然后看看能读到什么：


➜  afcclient git:(master) ✗ ./afcclient cat iTunes_Control/iTunes/safari/sqllog_02343.idx0 /private/var/mobile/Containers/Data/Application/9210B36C-89E2-4728-9831-40CAA961C15E/Library/Image Cache/Favicons/Favicons.db1 /var/mobile/Containers/Data/Application/9210B36C-89E2-4728-9831-40CAA961C15E/Library/Safari/BrowserState.db2 /private/var/mobile/Containers/Data/Application/9210B36C-89E2-4728-9831-40CAA961C15E/Library/Image Cache/Touch Icons/TouchIconCacheSettings.db3 /private/var/mobile/Containers/Data/Application/9210B36C-89E2-4728-9831-40CAA961C15E/Library/Image Cache/Password Icons/TouchIconCacheSettings.db4 /var/mobile/Library/Safari/Bookmarks.db5 /private/var/mobile/Containers/Data/Application/9210B36C-89E2-4728-9831-40CAA961C15E/Library/Safari/History.db6 /var/mobile/Containers/Data/Application/9210B36C-89E2-4728-9831-40CAA961C15E/Library/WebKit/WebsiteData/LocalStorage/https_mobile.twitter.com_0.localstorage7 /private/var/mobile/Containers/Data/Application/9210B36C-89E2-4728-9831-40CAA961C15E/Library/Safari/PerSitePreferences.db8 /private/var/mobile/Containers/Data/Application/9210B36C-89E2-4728-9831-40CAA961C15E/Library/Caches/com.apple.mobilesafari/Cache.db


浏览器记录和 Cache.db 被提取出来了。正常情况下，iTunes 备份是不会包含 Cache.db 的，而这个文件会 inline 的形式保存一部分网络请求的原始报文。



用同样的方式启动 com.apple.Preferences。如果手机启用了 iCloud，系统设置应用会自动发起数个到 iCloud 网络服务的请求。


https://setup.icloud.com/setup/get_account_settings


在之前，这个 API 设置了一个匪夷所思的缓存策略：


Cache-Control: max-age=3600


这个 API 为什么要设置缓存……？


在打开应用之后，Cache.db 当中就会记录下多个访问 iCloud 后端的记录，包括用户登录态认证所需的如下 HTTP 头都被记录下来：


Authorization:X-Apple-I-MD: X-Apple-I-MD-M:


这时候用这个 Instruments 后门获取到数据库的副本，提取到这几个认证所需的参数。如果用户账户没有启用两步验证（Two-factor authentication），直接重放这些 token 便可以访问 iCloud 的各种后端功能，账号到手！


对于启用了 2FA 的账户，在每次请求时都会计算一个新的 X-Apple-I-MD 值。从历史的请求中无法简单计算出下一次所需的值，导致无法简单使用重放攻击来登录账号。


苹果收到报告后迅速调整了 iCloud 的后端，禁用了缓存策略并对登录认证进行了加固。


本文提到的攻击方式应该就失效了。不过由于我们有任意 App 启动的能力，仍然是可以曲线救国，让 MobileSafari 弹出恶意网页 URL，触发远程越狱来获得更高的权限。上一个已知在野外被利用的 iOS 远程越狱可以影响到 14.3，那可是相当新的版本。



本文介绍了一种在物理接触的情况下获取云端账号的攻击场景，不过限制很多：


  • 设备插入恶意的 USB 充电线

  • 受害者信任 USB 连接并输入了锁屏密码验证

  • 设备没有锁屏

  • 受害者的 iCloud 账户没有启用两步验证


基本上就只对数字取证这个场景有意义了。不过其中涉及到不少跨越幅度较大的知识，希望能给读者打开新的思路。


对于普通用户，还是要注意手机连接未知设备时的安全。保持操作系统更新到高版本，并记得启用云端账户的两步验证！
