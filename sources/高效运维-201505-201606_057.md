## 一、适用场景：

提到新浪微博，相信大家都不会陌生。而在日常“刷”微博的过程中，不知道大家是否 遇到过类似如下这些情况：

![](../Images/90a2b1edd68ff227b574c25c1dcf8981.png)

![](../Images/00dd105b46e20c4e8952b11bdae1018c.png)

![](../Images/c16093af3eb15abedb2f9974be09623c.png)

上述这些截图，全都来自于真实的用户投诉。这正是当时新浪 CDN 团队面临的一个首要问题。

为了便于理解，我们先来分析一下用户在“刷”微博图片时需经历的全链路。

![](../Images/24972e3e1c940d5c08d4f223ac7dbb18.png)

**1、从手机终端到网络接入点（如：4G/3G/2G 或 wifi 网关）**

> **注：**在这一环节，面临的主要挑战是网络信号随时都有可能出现不稳定的状况。

**2、从网络接入点到新浪 CDN 的边缘节点（通常来讲，该边缘节点会离用户“较近” ）**

> **注：**在实际中，这一环节可能会穿越各种“奇离古怪”的中间设备或代理节点。为便于叙述，下文将边缘节点统称为 L1 Cache。

**3、如果要访问的图片恰巧未在 CDN 边缘节点命中，就需要向源站发起连接。**

> **注：**通常来讲，边缘节点未命中的话，会首先回源到 CDN 系统内部的二级节点（即：L2 Cache），如果二级节点仍未命中的话，才会回到真正的源站（即：Source ）。

而具体到 CDN 内部 L1/L2 Cache 来看，又可细分为如下**三段链路**：

![](../Images/afe2af059c1ce5549f569cd39951e045.png)

显而易见，在这样一个长长的链条中，任何一个环节出现异常，都有可能导致用户端的访问异常。为进一步确认问题原因，我们对出现“白图”时，移动端上报的错误日志进行了分析，**并发现有两大明显特征：**

*   **特征一：**错误码集中于-1001、-1005 （IOS 平台） 和 8009 、8000（Andriod 平台）
    
*   **特征二：**移动端收到了 HTTP Response 的首包， 但后续报文没收完整。
    

## 二、传统的解决办法

1.  **借助手机客户端，不停地尝试刷微博，以期待问题再现。**
    
    这种方法最大的问题在于，“白 图”出现带有一定的偶发性，即便手工“刷”半小时，也有可能不曾复现。
    
2.  **对服务器端和客户端日志进行分析、分析再分析。**
    
    其中，服务端日志要覆盖 L4/L7 、L1 /L2 Cache 及 源站；客户端日志主要是移动端上报的错误日志。这种方法的主要问题在于，不同组件的日志是相互孤立的，要在海量日志中找到一次“白图”所对应的全部日志，如同大海捞针一般。
    
    **举个具体的例子来说：**假设我们现在从移动端上报的日志中发现一条与“白图”相关的日志，那么此时如何能顺藤摸瓜，找到该请求在 L4/L7、L1/L2 Cache 及源站上对应的记录呢？
    
3.  **联系用户请求协助。**
    
    虽然移动互联网时代提倡“用户的参与感”，但在问题定位和排查方 面，“参与感”很可能带来负面效果。
    

## 三、我们的思考

这个本质原因是，从“PC 端固网时代”到“移动互联网时代”。

移动互联网对于“服务质量管理”的要求，在本案例中总结出以下三条：

**1、用户从过去坐在电脑前，到现在无时无刻、随心所欲地移动着。**

这种使用场景的变化，决定了移动端网络的链路时时刻刻都有可能发生变化。

过一个桥、转一个弯，在屋 里移动一下位置…这都有可能会造成手机网络信号的变化。  
这种变化，这也使得每条连接、每次请求，都有它的唯一性和独特性。

因此，在这样的场景下，进行服务质量相关问题的诊断定位时，“对现场的还原” 更重于 “事后的复现”。

**2、流量的入口从浏览器变为了一个个的 APP。**

而开发这些 APP 时，通常都会使用 IOS 或 Andriod 系统高度封装好的开发库。这些开发库在带来便利的同时，也给后期服务质量 相关问题的诊断定位带来很多不利因素。

**例如:**\-1001、-1005 这些错误码代表的深层含 义究竟是什么？在什么情况下会报出这样的错误？

尽管在这些库的开发手册中，有相关 说明，但解释大多都比较含糊，没有暴露足够多的细节 。

因此，在这样的场景下，进行 服务质量相关问题的诊断定位时，需要对这些开发库报告的错误码或报错信息有足够深 的理解和掌握。

**3、APP 最终是运行在 IOS 或 Andriod 系统上的，出于手机用户的实际需要及安全性考虑， 默认都不会提供 tcpdump 等抓包、诊断工具。**

## 四、解决方法

综上，我们提出如下解决办法。

### **1、借助枚举法，化含糊的错误码为清晰**

![](../Images/8ad42069069d473e505eab789b1d3ca5.png)

我们在线下搭建了一套“移动端错误码枚举”的环境，如上图。

**首先**，中间这台笔记本电脑充当网关功能， 一方面，通过 wifi 热点共享，使得手机可以接入进来；另一方面，借助 WAN 口，接入 Internet。

这样，当手机开启 wifi“刷”微博时，所建立的 TCP 连接及其双向流量都会经过这台笔记本。

**其次**，开发一个 Linux 内核模块，用于精准控制丢包行为，并运行在笔记本电脑上。

借助该内核模块，可对手机端“刷”微博时产生的双向流量，精准设置丢包策略（如：丢 SYN 包、丢 SYN-ACK 包、丢 HTTP Response 的第 n 个包…..），甚至还可利用该模块触发 RST 包。

通过枚举丢包策略，我们就能在微博客户端上准确的看出其相应产生的错误码。籍此，我们对于-1001、-1005 等错误码有了较为清晰的理解。

当然，这只是迈出了第一步，仅停留于此，依然无法完全解开本案例的问题。

### **2、建立“现场还原”手段**

如上文所述，在移动互联场景下，进行服务质量相关问题的诊断定位时，“对现场的还原” 更重于“事后的复现”。

那么，是什么因素阻止了“对现场的还原”？是由于日志信息不够吗？在进一步回答之前，我们回顾当前系统日志的项目：

![](../Images/6ebeaaf8f649e24bd3090615743299a0.png)

可以看出，日志涵盖的“节点”已经不少了，那为何还是很难进行“现场还原”呢？是不是由于各节点中有些组件的日志还不够齐全呢？

对于这个问题的思考，我们给出的答案是：

> **日志不在于多和全，关键在于要能整合成 Supply Chain（供应链）。**

从前文的分析，已经能看出，只有全链路畅通，内容才能完整地交付给用户。

因此当出现内容交付问题时，首先需要锁定是链条中的哪个环节发生了问题。对“现场”的还原，首先要找出 Supply Chain 关系。

在这里，再次特意强调一下我们的观点：**对应用交付质量的管理及现场的“还原”，回归到对供应链(Supply Chain)的完整掌控 。**

### 3、小结

就本案例而言，要对 Supply Chain 有完整的掌握，涉及到两大因素：

**首先**，Supply Chain 不仅关注整个链条中各个节点（如：nginx、L1/L2 Cache …）的工作 状况，而且还格外关注节点间的“连接”，只有上游节点 与 下游节点 之间通过“挂钩” 连接起来，才能形成一条完整的“Chain”。

正如下图红色挂钩所示意的那样。

![](../Images/bb3b38ff47338b0717d1cea1113526b3.png)  
*注：配图来自网络搜索*

在本案例中，该以什么元素作为挂钩呢？

我们给出的答案是：“以 TCP 连接的 四元组。（源 IP 、源端口、目标 IP、目标端口）为挂钩”是最佳选择。

这基于两方面考虑：

*   一是因为所有的节点间的交互都是通过 TCP 来完成的，而该信息恰恰是传统日志最缺乏的；
    
*   二是每个节点的都可以通过上层函数库非常方便地获取到四元组信息。
    

![](../Images/8e6236ad6e0c921b4b701abbc3ce4101.png)

解决了挂钩问题后，另一个问题便凸显出来了，那就是，**如何把各个组件记录的四元组 信息提取出来呢？**

> 如果四元组信息不能被提取出来，也就无从使用了。

对此，我们给出的答案是：以“HTTP Response Header”为载体，同时充分发挥 APP 端的高可定制性。在具体实现时，分成两个步骤：

**步骤一：**各节点在返回 HTTP 响应头时，都附带一个叫做“Supply-Chain”的 Header。 该 Header 包含如下两方面信息：

> a. 节点的双边信息 : 记录了该节点“被动接受的连接” 和 “主动发起的连接” 所对应 的四元组信息；
> 
> b. 节点在处理请求时花在各阶段的时长： 例如：三次握手阶段耗时、发出/收到 HTTP Request 的时间间隔、对端/ 本地处理 HTTP 请求的耗时……

![](../Images/c55f1ee1cd16280d4ae465193c535149.png)

如上图所示，各节点逐层增加“Supply-Chain” 这个 HTTP Response Heder 后，势必会增大 带宽的消耗，对此可通过适当的编码及只在必要情况下在必要的节点上开启该功能，从而将带宽控制在可接受范围内。

同时为避免信息泄漏，需要对四元组的原始信息进行编码和特殊 处理。

**步骤二：**借助 APP 端的高可定制化，在发生“白图”错误，客户端进行错误日志上报时，将其已收到的“Supply-Chain” 这个 HTTP Response Heder 也同步上报回去，这样就形成了完整的“闭环”。 如下图所示：

![](../Images/4fc73ce47620bcdbc440f81b4116d965.png)

这样一来，我们只需对客户端回传的错误日志进行解码分析，就能够立刻还原出该“白图”当时对应的那条完整的“Supply-Chain”信息 及 当时 Supply-Chain 上各节点在各阶段的响应时间，由此做到了“对现场的还原”。

我们将这样的一种诊断方法，称为“基于 PerRequest 的诊断技术”。

### 五、PerRequest 诊断技术带来的变化

1.  问题诊断环节去“用户参与“，不是所有场景都需要”参与感“的；
    
2.  该技术所具备的神奇的“还原”功效，特别适用于复杂的“移动”网络环境；
    
3.  实现了问题诊断环节的去日志化。
    

经新浪 CDN 生产环境的真实运行检验，应用 PerRequest 诊断技术后，对于服务质量相关问题的诊断定位，不再象过去那样在海量日志中盲目分析了，转而重点分析客户端上报的错误日志，效率方面得到了很大的提升。

对此，这里指的“去日志化”不代表不使用日志，而是指问题定位环节所需要分析的日志范围和数量都得到了极大的减少。

1.  将“问题定位” 与 “定位后的更深层次分析” 相剥离，如下所示：  
    ![](../Images/4f4a6748a066dc8b0d99f854e75d4be1.png)
    
2.  PerRequest 诊断技术配合新浪自研发主的其它工具，进一步实现了定向化地精准优化，从而有效降低了“白图”出现的比例。
    

**案例实施前：** 衡量微博图片下载质量有若干指标，其中-1001、-1005、8009、8000    相关指标始终无法明确其成因，也因此无法在新浪 CDN 系统上进行相关优化。

**案例实施后：** 4项错误率指标的成因真相大白，并且通过精准定向优化，使得其中 2 项错误率分别降低了 50%、30% （限于新浪 CDN 系统提供的微博图片服务）。

### 六、案例启示

1.  回归到对“移动互联网”的思考，突破常规思路。有关这一点，已在前文案例分析中提 及，就不再赘述了。
    
2.  在进行系统优化和改进前，最理想的情况是借助一些工具或方法，精准定位到产生问题 的原因之处，再给予针对性的“精准”优化，可事半功倍。用“精准优化”替代“盲试” 也是我们团队所大力倡导的理念。
    
3.  架构设计之初，就要考虑到“交付质量的诊断”，而这一点，恰恰容易被忽视。
    
4.  以 Supply Chain 视角思考“应用交付质量”。
    

最后，还是想强调一点，世界上没有任何一种解决方案是包治百病的，PerRequest 诊断技术也不例外，它有相应的使用场景，也有它的不足和局限性。总之，希望能给大家带来一点思路上的启发。
