今天的分享的主要内容大致是这样的：

过去对于Mongodb的印象其实特别不爽，在11年就开始接触MongoDB，那时候还是1.9.x/2.0.x的版本：global lock和读写互相阻塞是非常让人崩溃的，举个例子：oplog需要设置的非常大，否则经常secondary就out-of-sync了；导致后来对使用Mongo的朋友特别鄙视（偷笑）。

后来MongoDB收购了WiredTiger(WT就不在这简介了)，它给MongoDB带来的变化是”行级锁，MVCC，高并发等”和更多可以tune的地方，WiredTiger是一个为了高并发而存在的引擎，且在之后的版本可能会有内存引擎。

这里看到有2个0，现在checkpoint/eviction的算法还是在持续改进中，mongo的工程师已经open了相关jira来review相关的算法，3.0.6再压已经稳定多了:)

很多朋友在纠结说Mongodb在机械盘上性能比较一般，我们PCIE基本是标配，效杠杠的。

Disk Space

之前提到了我们用PCIE卡，3.0WT的出现更是想睡觉就送上了枕头，WT引擎有了数据压缩功能，在2.6版本的时候1.18Billion条数据占大概3.12TB，而现在3.0之后 1.02Billion条数据仅占用270G，在条数差不多的情况下，数据量为原来的8%，极大了降低了使用SSD/PCIE的成本。

这是我们在选型的时候查看各个版本主要的一些jira上的Issues，我们本身没有什么历史包袱，之前只有一个应用是2.6版本，就在选择比较好的版本使用。

这里是3.0.2的部分lira issues。

WT-1941/SERVER-18629，fsync journal file的时候却fsync了data目录，造成了大量不必要的fsync，3.0.3中修复了，3.0.2的workaround是

log=(xxx,path=journal/,xxx)    journal后面加一个/

SERVER-18314 XFS 推荐XFS的文件系统

Issues-3.0.4

3.0.4修复了上述提到的issues，我们线上基本是跑的3.0.4，但是3.0.4也有如下的jira issues。

有关内存泄露，主要表现为cursor的内存泄露，其他的比较细，大家有需要可以直接去看看jira的讨论和进展。

Issues-3.0.6

3.0.6的issues，3.0.6没有之前4个版本那么严重的问题，这里的issues很多也在提出后很快就fix了，比如WT-2104在昨晚已经fix掉了。Mongo社区现在的反应还是很快的，我个人对MongoDB也非常有信心。

Issues-Driver

我们的一个业务使用了一个async 的driver，当时我们在测试环境功能测试都OK，但是在线上压测的时候我提出进行failover测试看看程序的波动，发现failover后，MongoDB 主从切换了，但是我们的driver无法发现新的主，后来我们定位到了bug，因此这里给大家的建议就是在使用新的Driver或者新特性时多测试，尤其是replicSet条件下的failover是非常必要的.

Issues-Application

虽然MongoDB 提倡schema free，但是这些点也是值得大家关注的。 我们有一个表，里面数据存储着一个add_time字段。却发现查出的数据有问题，最后发现是add_time的time format不一致。我们这些元数据还是要保持一致的。

还一个就是同一个字段同表中有不同type，这也是要避免的。

我们这边是这样考虑解决方案的。

  1. application schema constraint

  2. variety是一个开源工具，可以检查某个字段在表里有多少种type

  3. table level privileges

关于表级别权限这块儿主要是对业务一个把关，否则可能有一天发现多出几百个表都不知道什么意思，很被动.并且也可以提前了解到相关数据用mongodb是否是合适的存储，以及如何来设计。

Issues-Connection

原来也遇到过mongos half-open 连接泄露的问题，
这是我们的一些系统层面的设置，主要关于keepalive的时间方面。

我们的一些建议

  • 数据schema元数据要统一

  • 更新频繁时，尽可能避免indexed array使用groups{filed1:filed2:}来代替

  • 注意命名限制

  • 避免large document

  • 避免不必要的长filed名，因为存储的时候filed名也会存

  • TTL的时候时间也要注意。

MongoDB有一点非常强大，就是他的文档非常的详细，非常的全，建议尽可能多读文档，多跟进社区

最佳实践之 driver

  • 比如说如果服务端发一个长查询过来，没有设置timeout，那么可能一直hang住，而这个设置就类似于MySQL的Statment_timeout，可以对服务端有一个保护

  • 以前作为rdbms的dba有SQL可以tunning，但是对于nosql，没有sql，而相对都变成了code，因此这就要求我们更多深入到业务进行schema/architecure design,甚至需要code review。

最佳实践之 Application

  • 避免使用否定谓词(not in, != 等)

  • 更新document时只更新必要的字段：避免先读取document，更新fields然后save到collection

  • 开放/测试时通过explain 理解你的query

  • 依据业务场景合理设置合适的read preference

  • 对于enable sharding的业务，选取shard key的原则：在满足查询的基础上，尽量平衡写入负载

  • 合理使用mapreduce，每个mapreduce job 只会跑在一个core

Heterogeneous Replication

这几个slides主要是不同技术的组合应用
我们希望将mysql的数据复制到mongo中，以利用到mongo的高吞吐。
我们基于OR实现了VDP，可以非常方便解析binlog然后写入到相关目标端mysql/kafka/hbase/mongodb等等，也支持嵌入逻辑和元数据映射，使用方只需要在页面上拖拽即可。

另外一个场景

MongoDB上面的数据要进行一些报表或者即席查询，虽然Mongo可以跑，但是不是他的擅长，我们将MongoDB的数据抽取到HDFS上，再通过Hive/Presto来进行报表计算和查询，当然我们这里对于mongo的数据有一个要求要有一个lastupdatetime的字段，来好做增量抽取，这样可以减轻mongo的压力，我们要用最合适的方案去对应最合适的场景。

自动化与监控方面

mongodb 3.x 基本上有300多个监控项，我们使用zabbix来做数据搜集和展示，报警等，一些bug或问题我们通过数据很容易就定位到了。
