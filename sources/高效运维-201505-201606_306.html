如何看待？当你不能反抗的时候，就好好享受。

App 和 Docker 是真爱，上游将是一场场轰轰烈烈的水乳交融。

下游目前来看，IaaS 和 Docker是长期基友关系。只要这样的态势可以维持，皆大欢喜。

但凡出现任何一方越轨，可能行业要有血雨腥风。

张鑫问：容器怎么用更合适？作为传统VM（ IaaS ），还是以微服务为主的单进程？

容器用法的问题要两个角度看：容器本身和容器环境。

容器本身，其实没有所谓的姿势，怎么用都可以，当虚机跑也没问题。没有规则，可以胡搞，也允许胡搞。

容器环境，是基于容器交付的最佳实践 + 工具链。这就要守规矩，越守规矩，效能越大，是放大系数。

这个规矩，目前来看就是：单进程 + 微服务 + 无状态。

容器即进程，将容器回归其最初，而不是作为VM 虚拟机来搞。

如果不遵守这个最佳实践，那么，放大系数可能变成了衰减系数。

然后你就会因为体验不好，开始质疑并最后演化成讨伐容器，说这玩意是忽悠，被刻意夸大，甚至示威游行贴大字报，给自己贴上「反容器斗士」的标签。

张鑫再问：请再阐述下容器跟 IaaS 的关系？因为越界太容易了。

对于 App Centric 的部署，我也认为你讲的这个规矩是最佳实践。

我的问题还是，容器跟 IaaS ，是个什么关系？刚才你讲到，大家不越界都皆大欢喜。

对于 IaaS 来说，如果VM用法成为容器社区的主流，那么这个越界就会必然发生：

因为对于 IaaS 来说，存储、网络什么都有了，容器当VM用，集成起来水到渠成，一个星期的事情。

但如果主流用法是App Centric，那 IaaS 越界的难度就很大，因为设计思路完全变了。

“微服务 + 单进程 + 无状态”，每一个都对开发人员水平提出了极高要求，组合在一起，那就更甚，一般公司不见得有这个技术实力。

Netflix当年也是一团糟，他们自己也说，大家看到我们现在的微服务架构多么好，是因为我没告诉你我们填了多少坑（当然后来，Netflix开源了OSS，的确造福了不少创业公司，不用自己填坑了）。

利俊问：Docker技术尚在早期，贵司如何在企业市场推进Docker？

Docker 本身是工程师用脚投票的结果，现在脚差不多快把 CIO、CTO 的门槛踩塌了，然后 我司的电话就响了：「叔叔约不约？」这是目前我们企业市场推进的 90% case。

其他专家朋友观点：

李建业同学：

单进程模型是最佳实践，但也仅仅是最佳实践，不是强制要求。因此如果非要搞的像虚机也是可以的，只是未来可能会有技术债。

运气好的话，在未来花大力气能解决掉；运气不好的话，可能就要把这个债一直背到系统被淘汰了。

从最佳实践和十二因子来看，App 更适合Docker。

当容器状态和进程状态一致时，是可以避免很多问题的；但容器当VM用，仅在某些特殊场景有其发挥价值的地方。
