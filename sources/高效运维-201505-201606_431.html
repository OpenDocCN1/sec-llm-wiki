运维发展的趋势

整体的内容以围绕 Puppet 为主，之前大家也有讨论运维自动化的工具，而 Puppet 在这些工具当中，不管是对于使用，还是自己造，它的思想都有着很大的借鉴意义。《浪潮之巅》很好地诠释了互联网发展的几个时代，而目前我们处于“云”时代，而企业也以云计算、物互联网、大数据、人工智能息息相关。为此我们现在所维护的规模越来越庞大，早在十年前我们大多数人所维护的服务器不超过百台，千台。然而现在我们几乎都以千计。不管是物理机还是云主机，大规模的运维管理已成为大多数企业的挑战。这也是运维自动化如此火热的一个因素。

为此，工具，伴随着规模而诞生，刘宇同学并没有详细统计这 2 年到底冒出了多少个工具，但每个工具都有其自己的位置与侧重点，它们都是为了解决痛点而生。刘宇同学的团队也一直纠结在采用开源软件呢，还是自己造轮子当中。

刘宇同学认为：不管你用什么来实现，解决你现在的痛点，并把流程 Run 好，你就是功臣，否则，你就是一事无成。为了解决运维而面临的问题，可以采用构建不同的系统来解决问题，在很多时候，不管是单一的系统还是合并成平台的系统，能够解决问题，才是王道。但是，如今的时代，我们需要的是利刃，一把能解决所有问题的剑。所以在构建系统与平台时不得不思考更多。为此需要朝着一体化、快速、简单、有效的目标而设计。

Puppet 的地位

Puppet 在这里起着举足轻重的地位。它主要的功能就是配置管理，也就是下图中红色的标记。

通常我们做运维自动化平台都需要把这三块揉捏在一起，配置管理工具如此之多，为什么要选择 Puppet？刘宇同学总结了它的几大特性：

  • 幂等性

  • try-run (- -noop)

  • 社区活跃，使用者多，稳定，这也是众多朋友选择的理由，也算是刘宇同学喜欢的原因

什么是 Puppet

那么，Puppet 能做什么?

  • 定位：配置管理工具

  • 系统初始化

  • 软件安装、升级、删除

  • 配置更新、自适应硬件配置

  • 监控系统联动

  • Everything

  • 将这一切统统装进 Puppet （感觉它能一统江湖）

还是来看看概念吧：Puppet 是一个跨 Linux、Unix、Windows 平台的集中化配置管理系统，它使用自有的描述语言，可管理配置文件、用户、cron、软件包、系统服务等。Puppet 把这些统称为“资源”。Puppet 的设计目标是简化对这些资源的管理以及妥善处理资源间的依赖关系。

Puppet 采用 C/S 星状的结构。每个客户端周期的（默认半个小时）向服务器发送请求，获得其最新的配置信息，保证和该配置信息同步。跨平台是很多人选择的一大因素，尤其是国企。不过也有很多人因为 Windows 用它。

Puppet 的三板斧

接下来我们进入快速学习 Puppet 阶段。刘宇同学做了如下总结，简洁，准确。

  • 三板斧：一切皆资源，一切皆类，一切皆模块；

  • 二大魅：模板，Facter，五个基础；

  • 资源（Resource）：一个用户账户可以是一个资源，一个特定的文件，软件包，正在运行的服务，设定的 Cron 命令，这些都是资源；

  • 模块（Module），多个类的集合。一个应用实例一个模块；

  • 类（Class），多个资源的集合。对应用实例不同功能进行封装；

  • 模板（Template），ERB 模板。根据服务器硬件信息定制化不同配置文件。

Facter 是一个系统盘点工具，它返回每个 Agent 的 “fact”，其中包括主机运行的操作系统，主机名，IP 地址及其他配置项。

Puppet 的生态环境

接下来看一下 Puppetlabs 所构建的生态系统。如果大家有自己玩社区应该是知道这个生态系统打造的重要性。

Puppet 如何打造的呢？自我包围，外围发展，内外兼修。

具体如下：

  1. Puppetlabs 为懒人开发者提供了 doc 工具，方便生成 html 文档，即把代码注释转成文档；

  2. graph，生成内部的依赖关系图，这个功能也可以用在我们自己内部构建产品时的流程图讨论；

  3. puppet-lint 语法检查，不管是外部的如何好用，也顶不过原生态支持；

  4. geppetto 编辑器（备注：官网语法变过）；

  5. ENC，外部节点管理，Dashboard forman 等都依托它来管理节点，强大无比；

  6. Puppetdb，将数据存到了数据库，缺点是 Java，各种问题，尤其是性能；

  7. Hiera，诞生的目标是让 Puppet 更快，fast to fast。效果有待考验；

  8. Mcollective，又一大神器，比 Ansible 和 SaltStack 更灵活。大企业+传统企业推荐的方式。基于 MQ 的命令处理，也可以用它折腾 Puppet agent；

  9. Enterprise ，企业版本，这是 Puppetlabs 的收入，但是国内大多数使用 Foreman。至于这一点，官网也是任其发展。PE 其实国内也有很多公司购买；

  10. Foreman，大头。第三方开源的 Web UI ，强大到令人发紫。挡了 PE 好多财路；

说说流程，为什么这么快呢。

底层采用 Facter 采集系统的 facts，Report 到 Master 后，都会存储在本地，100 行以内的 py 进行读取，然后入库。其中还可以使用 puppetdb-api。然后 Django 读取 MySQL。CMDB 就此完成。

基础软件包我们也有一个自己的仓库，yum，更新快一些。目前抛弃了之前新浪的 fpm 打包的程序更新的做法。目前可以实现：游戏+Web 业务的研发自更新。不过这里也有很多规范，包括：tar 包，git 版本及 hook。目前大部分业务部门已遵守这个规范。

Puppet & Docker

最后，刘宇同学就 Puppet 和 Docker 发表了看法。

我们用 Puppet 来做什么？Docker 没那么火之前是这样的：

  1. 使用Puppet初始化操作系统，管理虚拟机；

  2. 安装软件包；

  3. 部署代码；

  4. 管理服务；

  5. 其他。

然而，dockerfile 也能实现部署，那是否能取代 Puppet 呢？当前推荐的做法是：使用 Puppet 初始化操作系统、 管理虚拟机、 安装 Docker、 运行 Containers、维护 dockerfile。

使用 Docker 安装软件包、部署代码、管理服务，将一部分的工作将给 Docker 来实现，利用 Puppet 来管理外围。

依靠 Puppet 是无法实现 Full-Stack 的。我们需要把环境创建自动化、软件安装、配置管理、应用部署、测试、监控、告警、故障检测、故障恢复、扩展等流程打通，才可以实现真正的“运维自动化“。
