## 1、OpenStack 在恒丰银行的现状

首先我们 OpenStack 一些数据看一下，我们搭建了两地三中心的多个 OpenStack 集群，我们在隔离业务能网络区域里面也部署了，再生产和测试都在使用，包括我们的多租户，资源隔离等等都有。

![](../Images/c2d5d4ea1f49caaf19bb51c0e69cd385.png)

我们现在数据库，以及大数据节点，我们的主要的业务应用系统都运行在  OpenStack 集群上。我们目前管理的两百个应用，超过六千个虚拟机，这个规模不太大，但是我们胆子比较大，我们的生产核心，包括短信银行等等主要业务除了数据库都在这个虚拟化的平台上，也比较跑了小半年了。所以我们算是胆子比较大。

![](../Images/cc0267ab1c4bebe8133d2ad6237af19d.png)

**我们几个特色：**

**第一个**就是我们在每一个网络区我们都有 OpenStack，这个和金融行业也有关，在这里面我们每一套 OpenStack 都是比较独立的。

**第二个**就是使用了这种超融合的架构，这里面考虑到成本更优化，同时这种计算访问也近距离，再有就是纯 SSD 的 Ceph 集群，就是我们的所有的系统盘，虚机用的都直接跑在我们的纯 SSD 的阵列上。

当时 SSD 的价格也在不断的下降，我们一些要求不高的应用，也是有 STAT CEPH  集群做，但是我们系统都是瘦分配，因为大量的操作系统没有大量的数据变化，所以还是可以节约很多的容量。

**第三个**就是全球比较领先的一个事情就是几乎是第一个，我们是和思科的 SDN 的控制集成，在国内应该是国际第一家，不是第一就是第二。我们这个实现了二三层的动态绑定，这些 Vxlan 标签的绑定都是动态完成的，同时端口迁移都是动态的。

![](../Images/b7d504fb5c6f313193900142079f38b0.png)

## 2、为什么选择OpenStack

**第一**，商业软件还是开源软件，我们不反对这种商业软件，开源或者说我们使用尤其是 OpenStack 扩充，就是他的闭源被厂商绑定，他不利于后续的发展以及我们自身技术的提升。

而这种开源的产品，实际上不属于任何一个公司，不一定说我开源代码我自己一定掌握，OpenStack 两千万代码我不可能了解，但是最关键的一点就是他不属于任何一个公司或者是厂商，它是开放的。

同时他不限制任何一个厂商再改，我们自己也可以改一些代码，我们有服务商也有厂商，我们不会因为厂商绑定死一个产品。我们就可以让A厂商做A部分的功能，我们自己做一个B部分，我们还可以找C再补充一些内容，这个都是可以的，这个就是做到自主可控。

**第二**，是我们的价值优势。因为他的软件不能商业 license，当然是订阅，那么往往收取的是服务费，这种服务随着规模的上升并不快。

还有就是开放的生态，这个也是我们未来非常看中的一点，就是说像任何一个产品，他很难说靠自己或者是靠一个公司够可以做到适配决大多数的硬件或者是软件。这是开源和生态的部分，在开源这个里面也有很多的工具，在提供。

![](../Images/12c2e48f75a7aeebbb11f3372c45ddf6.png)

我们为什么选择 OpenStack，可以看一下他的社区成熟度是非常高，他们有六万多个开发者，250多个国家的代码，这个社区的管理机制每年都有大会，管理的机制和理念也是非常成熟的。不管是国内还是国外都有非常多的做 OpenStack 的公司还有个人。

![](../Images/7f21df1a4db9a4c750d6320b49988422.png)

我们看下他的产品，第一社区好，产品稳定不稳定，但是 OpenStack 客观来说这六个核心的项目，已经是在五年以上的时间，就是发布到现在。

可以看到 NOVA 已经是六年，就是从第一个版本到现在已经六年，我们平时用到的功能，不特殊的新功能以外这些功能都运行很长的时间，该修复的漏洞都修复完了，因为在运行过程中，使用量还是很大的。

这几个核心模块可以说也经历过很多的考验，我们在使用他一年的时间，我们用的是L版本。

在L版本里面对我们的使用是几乎没有漏洞的，真正对我们造成影响就只是在 nova 有一个 BUG，在其它地方还没有看到，所以他的产品的成熟度已经达到了我们可以选择的程度，即使在金融行业我们认为也是可以选择的这样的一个程度。

![](../Images/e41db23a6c3e997f8a8e427c5c144570.png)

其次他的架构优势，看这个图比较乱，但是我们 OpenStack 架构是值得我们做软件开发值得学习的，它的所有的服务化，他的结构，全部都是用 API 调用，还有，比如他的 Plugin，都可以自己拓展，他有非常强大的拓展性，非常方便和灵活。

以至于这几个百个甚至是六百个公司贡献了两千个代码都可以在这样的架构下良好的运行。其实大家都可以换，这个时候就是简单的替换掉这个 plugin。

所以实际上可能不会用到两千行代码但是良好的架构想作拓展和想替换一些功能的时候是非常方便的，这个也是我们选择他一个很大的点。

![](../Images/d4cad0dd1a26dbaad9f389162b528ccd.png)

其次对厂商的支持就不说了，因特尔还构建了做一些虚拟化地层的技术和能力。这些都是在这里面。这些厂商对 OpenStack 社区贡献了很多一些硬件上面的对接和能力，因为企业应用很难说用纯软件实现，这个可能更不适了，你说互联网所有都是用软的来做了。

这些硬件怎么和这些 OpenStack 对接，其实靠的都是这些厂商自己贡献的代码，这里可以看到像 CISCO 这些公司，他们是要把自己的产品跟 OpenStack 适配起来。

各种各样的厂商都对 OpenStack 有比较好的兼容的方案，我们想换硬件的供应商我还不用换 OpenStack 还都可以对接上。这个也是很大的原因，所以我们最终选择了 OpenStack。

## 3、部署OpenStack

**3.1 恒丰如何部署OpenStack**

我们有两个节点，一个是控制节点，一个是计算节点，我们这里可以一些虚机把每一个都是放在虚机里面跑，有人是会用一个物理机跑，有的是使用容器这都可以，我们是把 API 等等东西都四在再一个独立的虚机上，我们做三个节点，我们还放了 DHCP Agent 和 Ceph Mon。

这两个为什么放在这里，因为本来是应该在控制节点的，因为我们控制节点和计算节点之前是三层的，二层是不通，这时候 DHCP 我们就不想让我们的控制节点的的二层延伸过去，所以我们在计算节点上放这个 DHCPAgent 的模式。Ceph Mon 是一样的道理，因为计算节点就是控制节点。

![](../Images/d40b37b28b53251edad8cdfaccfd74d3.png)

这个是我们的 OpenStack 部署架构，我们刚才说了，我们在多个网络区域里面，我们就可以看到一个数据中心，有两个机房，说白了这个都是为高可用考虑的，两个完全对对称的机房，我们这个还可以正常的提供服务，这个所有的都是双份的。我们有业务网和隔离网。我们是怎么摆放的。

首先我们业务网我们是一套 Openstack。我们用三个控制器，因为我们是三核结构，要选举必须是奇数，我们就不能放两个，一般是2和1，那最后就出现脑裂情况，所以就是需要有一个仲裁的节点。

我们找到一个网络机房放两个控制器，这个机器实际上他是三核节点中的一个，他也负责投票和仲裁。所有的计算节点，是对称的。这个要说一下，我们认证权限是一套 Keystone 管理。这样我们这里可以扩充更多的机房，但是原则上就是集群放在三个网络机房，这样来做的。

![](../Images/2b6b8fa1f494a039870411ddc78def7c.png)

3.2 高可用应用

我们专门讲一下控制节点高可用。我们说银行不能像做实验一样，就是有一个单节点的节点这个如果坏了就事就大了，我们做的是三活的方案。

![](../Images/1dc3a92365c605d345634d2ad5eb225a.png)

第一个，我们在三个控制节点里面都装 HA Proxy，我们选择一个主的，然后 VIP 选择一个主的来做，这个是我们所有的入口，这个是调用进来会分发给比如说我们的 NOVA 这样的 API 这些都是三个的结构，平均分发就可以了，这个数据库是一组两倍的，我们用了这个 Galera 方式来做这个三活，我们一个集群有三个DB节点，我们把它做成三活，但是我们真的用他们的了吗？这个还是有特殊的处理的。

**我们在 HAProxy 中配的是一主两备。我们把它做成三活，起码保证在任何终端的时候不需要人工去切换。但是我们为什么不分到三台数据库？**

因为我们有担心就是一致性的问题，我们现在这个方案，好处就在于当我晚上某一个数据库故障的时候，HA proxy 会自动把这个流量倒换到另外一个备机，这个时候是不需要人工干预的。如果主备是需要你起来去切换，我们目前的方案就是 HA proxy 切就可以了。

Memcache 都是主备，但是他有应用级的切换，这个都是三节点，就是我们能做三活都做三活，数据库做了一个特殊的处理，真正背后是三活，这样的一个高可用的架构，我们能够保证他在任何一个时间故障都是有自动切换的能力。

大家做运维就比较勤苦，至少 OpenStack 这个就不用夜里爬起来了。假设我们一个机房我用不用起来，我都不起来的，我这个B机房还在用，我的网络机房还可以正常提供服务。这个是我们一个主要的考虑，因为做金融行业自身最大的就是担心这个业务的高可用。

## 4、管理OpenStack

**4.1 我们如何管理OpenStack**

OpenStack 里面我们做的第一件事情就是我们怎么管理他，虽然 OpenStack 是一个可以管理上千上万的 OpenStack 管理集群的方案，我们目前都是单独的布置 OpenStack 进去。

### ![](../Images/be8e1a530cb1ccaea60255bf8971ceb8.png)

第一个就是隔离故障域，因为中间可能都是防火墙o，我的故障域，我们的网络故障都是不影响别人的，我们这一套 OpenStack 尽量不要影响另外一个网络区的集群。

还有一个就是性能的考虑，因为 OpenStack 只能说被验证的方案还是尽量不要超过一千个物理机，因为太大也不好，在这样的情况下，我们放多套 OpenStack，像我们一个DC可以容纳几万台这都是可以的，否则的话，你性能上不去。

我们做了多个 OpenStack 时候，我们用了一套 Keystone。比如说A租户在 OpenStackA 集群申请了一个资源，那同时也会在 OpenStackB 集群上申请资源。所以我们现在是一个 DC 用一套 Keystone 可以管理的。在这里还有一个比较有特色的地方，就是我们的 OpenStack 是两个同规格的 Ceph 的集群。

**为什么我们要做两个 Ceph 集群？**

我们第一套就是在A机房，我们第二套就是在B机房。如果只有一个 Ceph 集群，你就只能天天其早说这个集群都不要出问题，这个之前不是没有出过，所以 Ceph 不建议做太大的集群，所以你在里面可以切出小的 Ceph，这样就不会影响其他的节点。

![](../Images/d92eb943a9daf1051727ce0978ffeed1.png)

这是我们说故障率一定要尽可能的小。然后我们再讲资源的调度，因为其实 OpenStack 我们使用也不是很重度，我们在金融行业里面，最重要的就是我们要让这个应用的连续性，我们要保证我们的业务不中断，我们不放在一个篮子里就可以了。

我们把一个应用的一组应用的20个计算节点就可以放在不的 DC，不同的机房模块不同的机柜不同的宿主机上，这个是我们自己的写的 filter。

如果大家感兴趣可以找我们要代码，可能这个别的地方不需要这个东西。我们金融行业比较特殊，他就是要求连续性就比较大，他就要分散开，我们怎么做到的，就是上层的管理平台可以做到跨数据中心的，如果说同样一个应用十台放在A集群，十台放在B集群，他们可以放置在不同的 OpenStack。

我们会给每一个机房和机柜做 OpenStack 的标记，同样的一组节点比如说A应用的 servergroup 服务器，我们会标注这个 servergroup。

这十台机器可以尽量的分散在不同的机房模块和不同机柜的宿主机里。我们还有两地三中心，这是金融行业最大的特点，我认为就是我们在这个做的最多的事情就是这个，怎么样把鸡蛋放在不同的篮子里。尽可能的分散。

4.2 运维OpenStack

可能大家跟厂商交流的时候，我的虚拟机速度很快，我的技术怎么先进，这个是厂商会说得问题，对于我们来说我们作为 OpenStack 的用户，已经使用这么长时间，在这些时间里面，肯定会有不少的坑，不要听厂商说怎么样，我们在运维的时候还有很大的难度的。

![](../Images/8e9ba1af671757b7720e19328a26494a.png)

第一个就是要把 OpenStack 监控，我们一定要覆盖全，监控说我的网络监控本身原有的都是要做，我们在整个的 OpenStack 对于宿主机的故障会造成所有的虚拟机都故障。这个我们虚拟化还是比较高的，这个时候坏就是一大片几十台，这个时间风险很高，所以就是要尽早的发现宿主机上面的出现的一些问题，否则面对就是几十台机械坏了。

第二就是 smokeping 很可能一个简单的配置有一些地方又不同了这个时候我们就是用 smokeping 看我们的控制平面，我们的存储平面，还有我们的管理平面，就是有很多，每一段网络之间都是有问题的。

而且我们还做了一个比较有意思的，东西其实也不复杂，还是有点意思，就是模拟应用，我们搞了一个这么复杂的一个 OpenStack 的分散算法，我们就真的模拟网上银行就分别，我布一些最小的虚拟机，我们就是把这个模拟的应用布在我们每一个 OpenStack 上。

通过我们所有的基础设施，包括我们的 DNS，我们的负载均衡设备，一直到我们的虚拟机，我们到了这个虚拟机之后，又调一下数据库，看看行不行，看一下我们分布式的存储，探测一下像 Ceph 写入一下，我们IO能不能成功。

因为我上面的监控既是运动员又是裁判员，但是你真的相信他的报的问题吗？如果这个虚拟机已经写不下去了，有可能是网络问题。

我前面只有在 smokeping 是能够找到问题，如果模拟应用自己写不下去，有问题它的自己就会报，他报出来的就是简单的表征了我这个跟在同样的节点就是同样的 OpenStack，用同样的 Ceph 的节点可能都有问题。

我这个自己一般不会故障他要是坏了。这个代码写不了多少，但是很快的表示你这个东西有没有问题，所以我写了一些模拟应用，这些都是小技巧。

![](../Images/ce11b05b5d656444b283b8de59e07b40.png)

还有就是我们一要管理好 OpenStack 的这些标准化和基线。虽然你可以看到我们只做了两百多个节点，但是我的基线不整齐，我对这个升级或者是修改一下，那就是一个大工作，这一百个节点，我要用虚拟机升级这个就是多少个不眠夜就出来了。

我们可以用 puppet 做所有节点的部署，这样的所有的几十次的扩容，这个也是很容易就可以建成的。你推送下去所有的配置都是用管起来，我们是用两百个机器当一个来看，他所有的配置都是保持一致，他的服务都是在 puppet 管理之下，这样就不会很痛苦。

然后我们的源代码就是我们的 OpenStack 放在我们自己的 GitLab 上，我们没有用任何厂商的安装包，我们就直接同步社区的版本，我们就是这么做的。然后我们所有的代码都是直接从 GitHub 拉下来。

最后我们所有的虚拟机都用这个基线，就是这几种标准化的虚拟机，你来用，每一个都是用不同的格式不同的版本，这个对运维来说就是一个恶梦。

因此是一定要标准化，一定要自动化，否则你管理的机器就越来越大，大概就是几十台机器的配置，和我们主线不一致，下面的就是要全部拉平，拉平的时候是什么成本，我这几台宿主机上跑六七八个虚拟机，把每一个都热迁移走，然后打补丁申请速度机，一晚上也做不三十台。

一旦涉及到需要所有宿主机全体升级，这个活基本上就是几个晚上都干不完，是非常痛苦的事情，所以我也不能我就这样，就是这30台就是用老配置，我后面的100台就用新配置，这么多的例外，以后更难管理，这个漏洞不在这里出就在那里出，你的配置都不一样，谁可以记住。

所以对自己狠一点也要上这种标准化的工具。你要把标准化、自动化做好，自动化的 HA 做好，这个就是一切。

![](../Images/3b7dae14daa10e74a69a0e07290dfe03.png)

HA 是我一旦有故障，第一虚拟机热迁移这个都是自有的功能，你宿主机有问题，直接升级就迁走就好了，之后给他做修复这个活我们每天都干的。

然后虚拟机的 HA，这个就是自动做，这个你探测好像他有问题，但是他不一定真的坏了，我现在要做的事情就是他有问题，我就把它删掉，然后再另外一边再起一个，还有宿主机的 HA，这个所有的虚拟机都是要在另外一个起起来。

就是我要隔离掉，就是我不能说我探测的系统探测错了，这个时候网络都是乱掉了，这个备份就是运维最爱用的东西，就是时不时的备一下。

我可用A公司的A补丁，我可以用B公司的B补丁，这样说不定我们自己可以做，我们也可以回馈社区，这样我们不会被任何一个供应商锁定。

OpenStack 看上去是开源的，但是实际上你也可能被某一个供应商锁定。所**以奉劝大家用社区的版本，自己管理，没有变化是不可能的，因为你自己有一些特殊的要求。**这样你自己维护你自己的基线，这是我们最后的一个展望，希望大家做运维不忘初心，方得始终。

## Q & A

> **提问：**我们就是问一个 OpenStack 根据社区版本，我想问一下，自己的团队大家做 OpenStack 是多少人？

**潘文杰：**我们就是三五个小的点，我们有自己的特殊处理，这三五个点，就是三个人开发，真正的纯开发就是三个人。不需要太多的，因为客观说，咱们金融行业用不了他这些版本，你可能用的都是三年前的基本特性，你对于他的开发就是自己的定制。

所以这个东西是不多的，用不了太多的开发人员，如果想掌握整个 OpenStack，他有三百个项目，两千万的的代码，你需要多少人，但是这个思路我们应该这么坚持下去，那也是要自己管这个补丁比较好。

> **提问：**你做这个 OpenStack 碰到过比较典型的问题。

**潘文杰：**坑太多了，我们天天做虚拟机热迁移，就是一会儿配置有不一样的，一会儿就做补丁，尽量选择一样的CPU型号，这个在OpenStack L版本是已知的BUG，你现在用M版已经是没有漏洞的，但是你用L版本的时候热迁移是报错的。  

我讲一个通用的案例，就是出问题是肯定的，有就赶紧决定做变更，每天晚上把这个问题尽早的消灭，不能等。比如说我们遇到一个小的漏洞导致一个宿主机的漏洞，这个就是需要把所有的补丁打上，我们有过一个问题，让六台速度机挂了。还是有坑的，而且坑是不少的。
