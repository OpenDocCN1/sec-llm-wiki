## 正文：

7.24 运维日.上海站的活动圆满结束了，除了精彩的技术分享外，本次活动最大的亮点莫过于最后一个小时的技术辩论了。

> #### 本次辩论的主题是：Docker 是否一个革命性的技术

**正方观点是：** Docker 是一个革命性的技术

**反方观点是：** Docker just so so（Docker 不是一个革命性的技术）

我是反方一辩。

其实在活动工作人员找到我作为反方一辩的时候，我心里是有点拒绝的，因为在当前Docker 已经成为整个 IT 界茶余饭后的谈资的时候，我公然给这样一个被很多人奉为“神一样”存在的技术泼冷水真的是“逆势而为”。

从 2014 年开始，我就在测试Kubernetes了，也一直在追踪和研究有关Docker集群化、网络SDN等的新方案。

研究的越多，越发现 Docker 不是一个能够解决所有问题的神器，在诸多方面存在着不足（这个论断暂不展开论证了，后续在微信公众号“运维技术实践”中会有专门的文章论述）。

在商业和工程管理中，戴明环（Deming Circle）是指导业务推进的重要理论之一。戴明环的核心是 PDCA（Plan-Do-Check-Act），如下图所示：

![](../Images/45920e1165e9cc0117759c9df83188db.png)

以下结合 PDCA 的理论重点给大家分享下技术辩论中的一些注意事项。

#### 1、赛前本辩方团队内沟通（PDCA 之 Plan）。

> 《礼记·中庸》中有言“凡事豫则立，不豫则废”（豫，亦作“预”）。

作为预的重要部分，团队内沟通的内容包括：

*   知彼：和自己对立方的辩手可能会提出哪些观点，如何一一应对。
    
*   知己：
    

> 己方的观点内容
> 
> 如何有序提出
> 
> 对方可能会有哪些辩驳
> 
> 如何再应对对方对己方观点的质疑和挑战

#### 2、赛中的发挥（PDCA 之 Do）。

在辩论中，有以下的**策略和注意事项**：

*   每个辩手主要关注辩题的一个方面，切记一个人把本方的所有观点一次性全部说出来（最后总结陈词的辩手除外）。
    

每个人关注一个方面的好处是可以做到最深入细致的准备和分析，才能自信的说出自己的观点。

同时，不要一次性全部说完，才能让后面的队友“有话可说”，每个辩手都不想被观众认为是“猪一样的队友”。

*   主要观点熟记于心，不要拿打印稿或者手机等作为“讲稿”。
    

拿讲稿的目的是为了“面面俱到”和“不遗忘”，但这却会给观众留下不自信的感觉。同时，拿讲稿也会给自己的发挥造成阻碍，往往成了读“讲稿”，缺少临场发挥和“感情带入”。

辩论是一个思想碰撞的过程，很多情况下，对方并不按照你的套路出牌，甚至自己的队友在紧张的情况下也打乱了节奏，所以这个时候就需要随机应变，一方面给自己的队友做补充说明，一方面反驳对方的观点，一方面给出自己的论点论据。

*   使用金字塔原理推出自己的辩论内容。
    

> 金字塔原理来自《The Minto Pyramid Principle: Logic in Writing, Thinking, & Problem Solving》（Barbara Minto 著）。

这本书很厚，我总结其主要观点为“总分结构”或者“自上而下的结构”。

在工程项目管理里面，有个类似的概念叫“**Work Breakdown Structure**”（WBS，工作分解结构）。

这2个概念都在说一个事情，那就是，在写作（传记、小说等除外）、演讲或者工程规划时，一定要采用先说主要观点或者任务，然后在第二层对主要观点或者任务进行完整、不重复的有效分解（分论点或者论据，在工程中为任务）。

在我的实践中，特别是在辩论赛上，分解到第二层就可以了，再进行更多层次的划分会让观众感觉到信息量太大，反而起不到好效果。

另外，在辩论赛上，除了使用金字塔原理给出自己的观点外，在第二层分述完成后，需要再加入总结概况，这样才能让观众更加清晰你的观点。总结起来就是“总”-“分”-“总”。

有没有似曾相识的感觉，其实，这就是咱们初中论述文的写作方法了。

*   适当加入幽默成分，会让观众记住你和你的论点。
    

没有人会反对在技术辩论中加入幽默成分来提高观众的注意力。技术讨论，往往比较枯燥，很多观众听几分钟就没有兴趣了。

这个时候，适当引入一些小笑话能够有效的拉回观众的吸引力。技术是严谨的，但表达方式可以是多样的，“学究”在技术辩论上是吃亏的。

*   不要进行“人身攻击”。
    

技术辩论，主题是技术，不能质疑对方的“人品”、“人格”、“工作中的角色”等。技术人员往往容易激动，恨不得所有人都同意自己的观点，情急之下可能会说出不和谐的词句。

这个时候，可以深呼吸，让自己平静下来，或者暂时停止自己的发言，听听对方怎么说。

#### 3、赛后的总结（PDCA 之 Check&Act）。

人无完人，特别是第一次参加大型辩论的时候，我们总会存在表现的不好的地方。这个时候，可以通过观看录制的视频和向观看了辩论的亲友寻求建议来了解自己的不足之处。

下次辩论，针对自己的短处，可以进行有针对性的练习。赛后的总结是 PDCA 中的“C”，而持续的针对性练习则是“A”。由此可以实现 PDCA 的闭环，实现辩论能力的螺旋式提升。

> #### Practice makes perfect.

#### 附本次辩论的精彩观点集锦：

**正方：** Google、Intel、Microsoft、Huawei 等国内外互联网大型企业都纷纷加入了 Open Container Initiative（OCI），以支持 Docker，这个不就说明了 Docker 的创新性和革命性了吗？

**反方：**各家厂家加入这个组织的目的并不完全一致，各自向着不同的方向发力。这个组织成立这么长时间了，也没有像样的草案或者标准发布，说明 Docker 并没有实际像想象中那么受到支持啊。

**正方：** Docker 的应用，提高了服务器使用效率。

**反方：**在传统的应用中，有很多方法可以提高应用程序对服务器的资源使用率，如多进程、多线程及基于 EventPoll 的编程技术（如大家耳熟能详的 Nginx 服务器）。

在著名的C10K文章中有详细说明，在此不再展开。

使用了这些技术，完全可以充分利用服务器资源，一个程序跑满服务器资源的情况有很多。**这个时候还有必要使用容器做一层封装吗？**

**正方：**在开发测试部署流程中使用 Docker 加快了业务上线流程，提高了生产力，这是革命性的。

**反方：** Docker 只是加快了发布流程，但依然需要ITIL、流程和规范体系来支撑。ITIL、流程和规范体系没有变，Docker只是一个工具。

同时，如果有完备的ITIL、流程和规范体系，在传统业务上依然能够高质量、高效的发布业务。
