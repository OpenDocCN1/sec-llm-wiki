# 我有一招，更优雅的解决运维环境一致性问题

## 问题背景

在一个PaaS平台环境里，通常每台机器都运行着一个常驻进程agent，如图所示，

![](../Images/47734ef61753c0269d69cc60e96b4840.png)

  

PaaS Agent 需要每周进行迭代更新，当集群规模大到一定程度时， agent 的存活性和一致性会因为各种原因降低， 如图所示，

  

![](../Images/35db5ceccac864be83f90b0cac98dc1c.png)

  

经过统计，agent 版本一致性最低的时候低于99%，这意味着超过一万台机器的集群，有100+台机器的agent版本不一致，这会导致各种非预期情况，包括业务程序更新、数据传输、功能开关控制等功能的异常，最终对业务造成访问拒绝、数据错乱等稳定性故障，同时，修复这些不一致性问题，对运维人员的消耗也是很可观的。

基于此痛点，我们对日常各类运维场景进行整理，实现了运维环境一致性问题的解决方案，目标是将一致性保持在3个9以上。

![](../Images/5f86eca2c7152b416c67500e801a84ad.png)

## 解决思路

通过抽象上述表格所述场景，可以得到『实体』的定义，

**实体**，通常是各类文件，如二进制文件，系统配置文件，也可以是一个功能的组合设置，如网卡多队列功能。

**实体状态**，包括实体的版本、md5值、id 等状态信息。

下图展示了不一致问题从发生到解决的简化过程，

![](../Images/12db1e5e12eb24f47467f3b2d9b40633.png)

可以看出，不一致问题，就是不同类型的实体，因为各种原因，出现了不同的版本， 被发现后，通过种种手段解决的过程（重新部署，重新设置配置文件）。为了达到正确地自动修复的目标，我们定义了实体权威中心，这个中心定义了实体权威信息，如下表所示，描述了实体在什么状态才是正确的，

| 字段 || 含义 |
| --- | --- |
| Name || 实体名字 |
| --- | --- |
| Type || 实体类型，通常是file, 也可以是url |
| Path || 实体路径或者 url |
| Md5 || 实体的正确md5值，用于比对待检查实体md5是否一致 |
| Version || 实体版本信息，通常是业务程序使用 |
| Collect\_script || 规范化输出实体状态的采集信息，包含结果的md5值 |
| Repair\_script || 修复不一致实体的方法，可以是部署系统，作业系统等 |
| Entity\_set || 此实体部署的机器集合列表 |

## 自动修复流程

![](../Images/a18a7ec118b61fbc99a56063209477d8.png)

*   1、不一致故障因为各种原因发生了
*   2、StatusCollector 根据EntitySet 实体集合(通常是机器列表)，采集所有实体的状态信息
    
*   3、ConsistenCalculator根据采集到的信息，逐个与EntityCenter(实体权威中心)比对，找出与权威中心不一致的实体
*   4、输出不一致的实体列表
*   5、根据实体类型，发起维修任务
    
*   6、通常有几种，对于托管在部署系统里的业务程序，调用部署系统，以当前正确的svn或git version 重新部署；对于系统环境如网卡多队列或者QoS、limits.conf 这类，则调用作业系统(如ansible) 发起重新设置
*   7、经过修复后，集群恢复一致状态
    

另外，重点说下这个流程中比较关键的点，

**1、简化一致性计算逻辑**  
当要检测的对象是文本文件或者二进制文件的时候，比对很简单，直接比对md5值即可；

但对于一些复杂功能来说，比如网卡多队列，需要查看/proc/下一系列值，我们通过在Collect\_script规范化结果输出来简化计算逻辑，将 /proc/irq/\*/smp\_affinity 的整个结果取一个md5值，这样在计算是否一致时，直接比对 md5 值即可，而不用去逐个比对每个 irq 下的 smp\_affinity 值。**2、联动部署系统，实时获取实体的正确状态信息**  
在修复不一致的实体时，有可能相应的实体集合有部署任务正在执行，所以在发起修复任务之前，查询部署系统，分析此实体是否有上线、各个机房当前的程序版本等信息，保证修复正确。

## 应用效果

系统上线后，最直观的效果是，agent 的一致性提升到 99.5%，系统环境一致性提升到 99.9%，降低了由于环境不一致性引发的稳定性故障次数，同时节约了运维同学的人力消耗。
