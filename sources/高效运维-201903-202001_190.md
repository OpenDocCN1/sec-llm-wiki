# 没有透明度的封闭赛道不可能有DBA的未来

DBA这活呢反正差也差不到哪去，好呢也不会产生多少效益，给个行业均价招个行业平均水平的人就成了，真要来了大佛我这小庙也装不下。

如果你是DBA，你看到这种情况不会想吐血三升嘛？

DBA现在这个越来越缩紧的就业市场，只是上游数据库行业的趋势体现罢了。整个数据库生态在过去被一刀切，一侧是金融、电信等传统行业，它们资金充裕但稳定至上，是Oracle和IBM的供血人；另一侧是所谓「互联网企业」，它们求新求变轻装上阵，因此多在折腾MySQL、MongoDB之类的轻量化、免费甚至开源方案。但现在情况发生了变化，传统行业巨头们在市场竞争下也不得不动起来，于是开始「去IOE」。虽然这个过程仅仅只是个苗头，Oracle这些骆驼们也不会坐着等到瘦死，但DBA必须要现在就开始行动了。2009年也不过10年前，有多少当初以为不可能消失的工作现在已经消失了，比如路边卖电话卡和杂志的报刊亭。

DBA的就业市场已经初现端倪。或者说，DBA早就在不知不觉中踏入一个漫长周期了，而作为周期终点的寒武纪是在周期开始前就注定了的。DBA的市场价趋于稳定，但招人很难，升值更难。当你的职责就是「不出错」，企业哪会根据错误的「不存在」给你涨钱的呢？当问题发生时（根据统计学原理问题是一定会发生的），解决问题不仅是你份内的事，还证明了你之前的份内事没做好，企业又怎么可能因此而奖励你呢？

生物本质上是趋利避害的，把企业看作是生物的话，它也以类似的原则对待风险。DBA的工作属于「避害」类，性质决定了企业绝对不可能倾注多少关注在上面。而DBA属于运维角色，所涉及的系统层级多、外部层面广（要和各种工具与岗位角色打交道），因此门槛不低，企业做选择的偏差值很低；而如果DBA要想上发展，大多要往架构开发方向，所需要的精力非常非常多，而企业要付出的成本很高——真正需要数据库架构师的企业寥寥无几，但把这笔预算拨到开发那边，可是能招到创造实实在在价值的大牛啊。

这也是DBA工作经验要进行变现难度很高的原因。你还记得扁鹊三兄弟的故事吧？《鹖冠子·世贤》有记，魏文王问扁鹊，家中三兄弟谁医术最高明？答曰长兄可以在发病之前就治好，所以外人不知医术高明；中兄在发病初期就可以治好，只能以「治小病」传名乡里；而扁鹊在病重时下针放血、开药施膏，大动干戈才名冠天下的。这不就是活生生的DBA工作日常吗？数据库没问题的时候企业认为「没什么毛病用你作甚」，出小毛病的时候企业觉得「小打小闹水平了了」，只有出现删库跑路之类的大问题，企业才会紧紧握住DBA的手称赞真是人民的救火员啊！说到底，非专业人员根本无法区分数据库「在保障之下没出问题」和「因概率没遇到问题」啊。

而在未来，这一状况会进一步加剧。云将业务层与环境层剥离，将整个层抽象化为不可见的隔离，企业因此不必操心业务之外的事情。云计算的普及已经大大改变了中小企业的运行方式，带给运维工作形态巨大的变革，而作为运维末端的数据库也在被改革的范围之内。在未来，也许只有在数据出现重大问题的时候，企业才会以外包形式雇佣DBA进行故障专案处理，毕竟现在没有几个公司会养个电工在公司里了。而身为DBA，你有那个勇气放下心气像水电工一样跑现场吗？很多DBA在寻求向近年热门的大数据分析类岗位转移，但以统计学和数学为技术的分析岗且不说本身的发展前景如何、会不会被自动化与算法取代，学科之间的巨大鸿沟对担负着家庭重任的DBA来说是不可忽视的风险。

DBA行业的窄化来自于上游航道的封闭性，IBM、Oracle这些数据库巨头提供了无比完善的数据库产品及生态，同时也导致它们的产品成为巨大的黑箱，难以从外部了解情况。在实际工作中，DBA的工作有相当大一部分是和各个部门的人扯皮，是开发带来的bug，还是业务的逻辑问题，抑或是运维的保障不力？在语言无法互通的情况下不同的岗位自说自话，而决策者并无法作出客观的裁决和评估。这带来的结果就是「劣币驱逐良币」，市场无法区分水平一般的DBA和水平高超的DBA，最终只能一致给予类似的薪资待遇水平。

这个行业结构性问题，说实话单凭一己之力是难以解决的。要推动时间线向光明的那个分支发展，数据库行业的垄断性必须要被打破，而这需要数据库产品的透明性提升。对于DBA从业者来说，「不是数据库的问题肯定是应用没写好」是很好用的借口，但并不能真正解决已经出现的障碍（虽然双手合十祈祷问题自行消失也是解决办法之一）。能够以共通的语言与开发、业务、运维进行沟通，确认问题的真正根因并对症处理才是一劳永逸的法子。

而对于DBA需求方的企业来说，数据库在可见的未来（10年够企业活很久了！）还是一个必须要打交道的东西，因此打开数据库黑箱、让数据库性能和状态真正暴露在阳光下才是长久之道。对此，我们倒是能做点什么：
