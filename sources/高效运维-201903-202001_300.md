作为第一次参加类似的社区活动，确实感觉到 DevOps 是我们整个软件业的热度、感召力和影响力。上个星期我们在上海参加了移动通信大会，在现场可以非常清楚地感受到 5G 的热度也很厉害。这两个IT和CT最热门的热点结合起来，5G 网络来了以后运营商为什么要主动拥抱 DevOps 呢？

这里面有很重要的原因，就是在现有的运营维护工作中，我们感受到很大的痛点：**业务上线时间很长。**

以传统网络的业务上线流程为例，从通过ITU的标准、到厂家试验、工信部测试入网、再到网元测试部署等等，前后可能要8个月。比如说最近的高清语音业务，前后还要用上几年的时间。在全网的运营工作里，通信网里面存在很多厂家的网元，不同厂家之间的开发能力、测试能力不一，很容易影响运营商的业务。这个复杂度就决定上线的难度跟我们IT企业是完全不同的。

**这些痛点如何解决？**我觉得 5G 给我们带来一个新思路，设备商和运营商已经明确意识到我们的旧模式是不行的。![](../Images/c4272a8c67b2f5c0cf795096708322d1.png)

![](../Images/7b6ef856f7bf5d47b160f2a6035290f8.png)

**5G是一个契机。**

首先是硬件架构做了一个很大的改变，我们以后的硬件都是 X86 通用硬件，然后业务功能基本上是靠软件来实现了。我们作为 CT 运维，在 2/3/4G 的时候，每个厂家都是软硬一体的，我们作为运营商能够做的是有限的，只能做一些简单的监控，简单的操作维护，更多的故障是要依靠厂家。5G 来了以后，我们的目标就是要强化我们运营商的自研、自维能力。

其实广东移动也一直在做 DevOps 的尝试，信通院也给我们做了赋能（广东移动刚刚加入了企业级 DevOps 赋能（共促）计划）。最初我们先是在网管支撑系统做尝试，在信通院以及高效社区的指导下，用了两三年时间，参与到 DevOps 流水线的建设。但这个尝试不是我们的核心领域，在整个运营商领域也还没在核心领域上做尝试。![](../Images/317e988797b2af62e9fe0f985c3d3b9a.png)  

**现在我们讲的是在通信业的核心领域开展DevOps。**在墙的左边是一些设备厂商，他们慢慢在这个过程中自身也在转型，内部的研发过程中也逐渐的开源，在研发部署的阶段也采用了DevOps，对于墙的右边，我们运营商也做了一些探索，广东移动做好了DevOps流水线。但是两者之间是割裂的，它来升级也好，做软件升级部署也好，其实是带着普通的光盘或者USB到我们现场升级。

## 一、5G来了

我先简单介绍一下5G：6月6号的时候我们工信部已经对我们移动、电信、联通、广电发放了 5G 牌照，5G 时代正式来临了。

**5G 到底为我们带来了一些什么东西呢？**

总的来说就是三个点：大宽带高速率、低时延高可靠、大连接高灵活。当然，这是业务上的，我所在的部门是网络管理部门，我其实并不是特别关注业务的东西，我更关注它给运维带来了什么。在5G时代，有很多新的设备，有很多新的架构，有很多新的技术，还有很多新的需求，这些对我们运营商的运维来说是带来了一些很大的挑战跟困难。

5G的两个技术特点：一个是业务的虚拟化跟软件化，第二个是一个设备的云化，这两个再归结起来，总结一下就是 CT 变 IT ，我们 CT 业要向在座的IT业学习。

![](../Images/c4376f5469e0c1a6141e7f3787b1f391.png)

到了 5G ，我们网络上所有的专用设备都全部变成通用设备，全都是用 x86 服务器，在服务器上装一个虚拟层，通过虚拟层变成虚拟机资源后，在上面直接部署软件化的通信网的网络功能，这个就是 5G 带来的变化。我们通信业到 5G 的时候，基本上就是要维护一张规模庞大的IT网了，我们整个通信业运维工作从 CT 变成 IT 运维。

我这里总结了一句，**我认为 5G 是通信业的一个数字化转型。**

我们先后经历过金融业的数字化转型，经历过零售业的数字化转型。5G 对通信业来说如果也是数字化转型的化，那它会带来什么翻天覆地的变化，我觉得这是很值得大家去期待的，当然这个我也没有一个很好的结论，因为我也不知道。

但是，从运维的角度来说，我是认为在 5G 时代，我们电信网络很多的网络功能控制，还有一些管理运维，以后都会由云原生和 DevOps 来驱动。那么未来我们通信业运维应该学习 DevOps ，把 DevOps 的东西引进来，这样我们运营商才能够更好的走下去。上午有老师举例子，把我们通信网跟互联网做了一个比较，说我们是一个封闭的、求稳的，实际已经是技术的中后期了，但是我觉得在 5G 时代里面，我们会有这么一个机遇，让我们重新焕发生机。

## 二、电信业务云化

下面给大家介绍一下，在整个网络云场景下面，我们认为网络云跟IT环境下面的云会有哪些不同，以及对后续的运维会产生哪些挑战，把这一点跟大家解释一下。

在 5G 领域里面事实上真正能够做到云化的只有核心网，无线和承载网还是靠专用设备的。全云化网络架构主要是针对核心网的，向云化转型之后聚焦于什么？

第一点是多数据中心部署。

第二点是引入了我们传统的 KVM 这种虚拟化技术，目前来说是用 KVM 比较多一点。上传到业务处理单元都是采用我们传统的分布式的负载均衡架构，这种分布式负载均衡的算法一定是闭源的，永远不可能开源。

同时，我们推出我们的管理面、运维面，相当于我们理解的网管系统。VNFM 就是讲我们核心网，业务网元的网管系统，再上一层是做网络编排的，因为核心网业务处理的是大量网元信息的交换，以及内部媒体信赁的交集怎么处理。包括我们在大视频领域，处理视频流量，像 OGG 、IPTV这些场景都在这一层进行处理。

**最大的变化是什么？**在整个云化场景里面引入了 PaaS 的概念，通过微服务的这种理念来实现我们整套电信云的快速上云部署。

![](../Images/8de8c947b63db370e1e90a6f1e5d3e66.png)

**我们看一下电信云跟 IT 云到底有哪些不一样。最大的区别是什么？**

网络的演进，为什么？因为在 IT 云里面，我们发一个虚拟机或者是 VM 或者Guest OS，我们没法定义我的 OS 对外的路由指向。在我们电信云化的场景里面，我们所有电信云的网元都要大量的对外进行交互，尤其是跟我们的核心网、承载网进行交互，所以说最大的区别就是在这里。大家有一个概念就可以了，其实在 IT 云跟 CT 云里面还是有很大不一样的地方。

![](../Images/d992baae92e8da3e1f3351e61a74fa8e.png)

我们说全云化网络带来了整个运维体系的变化，我们传统的运维人员，要从 CT 向 IT 进行转型。

第二个是工具手段，之前我们在传统的电信云化场景下面，工具手段比较落后，每个厂家单独有一套，做的不是很好，永远达不到我们客户的期望。未来我们也是希望在这一块能够把所有厂家结同在一起，通过算法加大数据的能力做一些更好的运维尝试。

第三个讲可用性，大家都知道，云化引入了之后是有好处的，但是还是有一点坏处。比如说安全性、可靠性，做网元信息的隔离等方面都存在一些问题。目前来说比较好的解决方案，业内来说现在也没有一个好的标准。在VM上面引入了容器化的概念，容器化的内核是共享的，这种共享带来的隐患以及安全性，在电信里面风险系数是很高的，后面要靠大量的运维工具跟提前预测的手段来解决这些风险。

![](../Images/ee4818a907e77b17e51fe3b6a3427ff1.png)

## 三、具体实践

现在我就开始讲我们是怎么样通过 DevOps 把通信网元部署到现网上去。我们广东移动是具备了这样的条件：

**第一个现在的通信开发商，**比如说华为、中兴、爱立信等等，他们很多在内部的研发已经是敏捷开发的了，他们内部都有生产线。

**第二，现在上了 NFV ，所有的网元都是软件包了。**

**第三个，我们广东移动在去年就已经过了三级认证的 DevOps 生产线，**可以用来做持续部署。第四个，我们今年刚好也完成了我们的一个网络云资源池的搭建，具有基础环境的条件。

![](../Images/53f2da1d42b79b177144a1e77080b14f.png)

我们上午部门总经理孙总在介绍的时候也提到，我们现在面临的问题就是我们现在部署的方式很土，不管我们的开发商在他们的研发中心有多快，有多敏捷，甚至整个 DevOps 都有了，但是他们不能直接部署到我们线网。我们广东移动折腾了一个部署的生产线，但是也不能从华为拉到这里，存在一个鸿沟。其实把这个打通了之后，一切都可以解决。我们在三个月的时间内，做了这么一步，把最后这个拼图给拼起来。

![](../Images/081ad6a66746354bffaa6d2665fca813.png)

我们是怎么做的呢？我们当时用了三个月折腾了一把，通过图上的这个流程打通了：

**第一步，**网元的部署包的上传，目前我们通过公网来上传，当然如果是要真真正正走的话，直接这样通过公网我觉得是很不安全的，这只是我们的一个试点，做尝试的时候是这么做的。华为研发出来的制品包，跟它们的部署脚本，通过互联网，传到我们两个地方，一个是我们生产线的 nexus，一个是 gitlab，因为部署脚本有敏感信息，我们要加密，而且加密文件和解密key要分开存放，保证安全。

**第二步，**我们在 jenkins 上设置部署任务，任务执行时调用 docker 创建一个 ansible 的容器，然后在 nexus 和 gitlab 里面把它的那个 playbook 和解密文件，还有加密的 hosts 文件一起拉到 ansible 里面。

**第三步，**我们的 ansible 就开始调我们网络云的 openstack 的 API 接口，向 openstack 的控制节点发消息，我们要创建什么规格的虚拟机，创建完之后，从 nexus 把制品包拉到虚拟机，然后在这个虚拟机上安装，执行，启动。

![](../Images/de5b7dce9b063936d139055a0d532aed.png)

这是我们部署的结论：比传统的网元部署，通过 DevOps 生产线做可以大幅度降低时间。以前如果要部署，我先不管研发部分，只说现网部署，华为的驻场运维人员从他们的研发里面拿到要装的部署包，要手工登上去 MANO ，其他管理软件，VIM 也好，PIM 也好，创虚拟机、部署，然后传上去安装，怎么样也要花半天以上的时间，现在只有3分23秒，时间是大幅度降低的。

当然，这个做完之后我们觉得还不够，之后我们会往这四个方向去延伸。

**第一，制品 MD5 的校验。**

**第二，公网安全管控。**这个都是作为如果以后真的要自动的走这么一步，那我们怎么去验证华为通过互联网给我们的这个通讯网元的包是合规的？我们必须要做这些 MD5 的校验、安全管控，甚至以后还有一些扫描的事情。

**第三，我们也希望看一下能进一步的往CI，就是往他们研发里面去延伸，看实际能做到什么地步。**

**第四，现在我们这个网络云部署的通信网元全都是基于虚拟化的，**但是未来 5G 引入了很多一些微服务、切片这种概念，那这种概念能不能够直接用容器化去实现呢？这个暂时目前还没有一个很好的时间的结论，我们也跟各个厂商都是在摸索，就是看能不能虚拟化部署的，能不能改成容器化部署的，这是我们未来的四个方向。

![](../Images/39f6fee609762311952ada7d18832254.png)

## 四、畅想未来

让我们再扯远一点，之后还能怎么做？第一个我想到的是将 DevOps 引入我们 3GPP 的标准。因为 3GPP 的标准这个组织它现在给出来的 5G 的一个架构，还是很封闭、很落后，而且它只管这个业务功能，但实际上我们运营商拿到之后发现：

第一，我们运营可能不需要用到它很多功能、很多模块，它这么写，这个标准没用。但是 3GPP 是一个很通用的国际标准，很多通信网的开发商它肯定按这个标准弄一套东西过来。但我们运营商发现我们很多模块不用。

第二，它对我们的运维很不友好，它压根没考虑到运维是否需要用这些模块，还是说我们有更好的东西来替换它。如果是一个真正的未来 5G 或者以后的一个通信网的架构是怎样的，我能不能我直接用 jenkins+ansible+python ，就能够完成我整个通信网络的一个运维工具软件。用一些大中台的 python 脚本的这种方式，我们直接替换到我们所有的网管系统。

![](../Images/a3e294324df9fd3284e31783ea0752d5.png)

第二个对未来的一个想法就是我们 5G 来了，很多垂直应用是否也可以基于 DevOps 甚至是 AIOps 来做。因为 5G 过来之后，我相信会引入很多互联网或一些其它行业，会直接在我们的网络上直接叠加他们垂直应用的一些功能，然后那些公司基本上很多都会用 DevOps 来做的。

我们运营商要迎合 5G 的新浪潮，都是用 DevOps 来对接他们，直接就可以快速持续部署了，这样我们就能做到敏捷的把这些垂直应用直接部署到我们的 5G 的通信网里面。

![](../Images/1fe18bd235eba3a8e8a9125b7c8fb2d0.png)

**精彩问答**

  

**Q**

老师，我问一下，现在您做的是基于核心网的产品吗？

**佟得天：**对，是一个基于行业网关应用的，未来可能会慢慢去做一些其它核心网的比如说EPC、IMS，那些也会去做。但是我们认为只要他们都是软件的话，都是制品包，都是二进制的包，你是什么业务，对我这个DevOps生产线来说是不重要的。我之所以选行业网关来做这个尝试，只是因为刚好行业网关就是华为的，然后在广东移动，它正好也是计划部署在我们的网络云资源池里面，所以当时找了这个网元。我认为只要都是二进制包，你什么网元对我不重要，都可以用DevOps生产线来跑。

  

**Q**

老师，我第二个问题，其实那个度量指标如果没有的话，其实我就是想问一下，咱们日常的这种整个流水线上的发布的展示，就比如说如果是有度量指标的话，通常情况下它会选一个软件，然后进行从需求管理、从代码检查、再到流水线整个一个状态的展示，您这边如果是没有这个指标的话，从图形展示给大家的是只有那个DevOps的流水线吗？还是有其它的一些方式能够看到整体的运作状态？

**佟得天：**因为我们广东移动生产线，一开始是基于我们定制化软件系统的，这些定制化软件系统都是在我们的管控之下的，我们可以从需求就开始管它，所以可以从需求到部署，一套落地。但是，对于通信业来说，通信网元来说，这个壁垒相当大。你看华为、中兴、爱立信这些通信业的大厂，他们自己的研发，你说如果要让我们运营商从需求阶段或者CI开始来做，说实话CI我做不了，因为我作为一个通讯运营商的角度，我根本不可能让华为、爱立信，来，把你们研发做出来的东西源代码直接给我，放在我这边，这不可能。当然我们也会逐步去尝试。我们跟IT业不一样，我们运营商只能从通信业设备商去买东西，但买的是产品，而不是源代码，所以是行业的一个生态环境问题而导致我们做这个东西可能会跟在座各位IT或者互联网做的东西可能会有一些不一样。

  

**Q**

你们是一个公有云还是一个定制云，上面是不是有一些厂家提供定制文件？

**佟得天：**我们的这个网络云是两层结耦，就是硬件和它的Hypervisor层是一个厂家，上层应用是一个厂家。但是实际上我们可以做到三层结耦，就是硬件，你买任意一个，只要是X86的都行，Hypervisor层一个厂家，然后上层业务任意厂家，其实是一个比较通用的云。比如说我们这个网络云也是华为建的，它的Hypervisor层也是华为的，但是我们做这个DevOps部署，是直接通过ansible调用它底层的openstack的API，我们并没有通过华为的任何管理的网管来去做，完全绕开了他们的产品，实际上是可以继续解耦的。

  

**Q**

好的，因为刚才我听到那个介绍的时候，说为了后续的性能提升，可能会在这种硬件上加一些专有硬件，以提高这个性能，就类似于刚才提到了GPU，这是为了视频处理这一块的。那么是不是还会有一些其它别的硬件？这样子的话可能会导致虚拟层和业务层虽然云化了，但是并没有真正的结耦，这可能是听了刚刚PPT的一个疑问。

**佟得天：**对，的确是会有这个问题，因为对于通讯业来说，是不是所有功能都能够全部由虚拟层加上软件来做，这个其实也不见得是完全能做的。但是5G的确是提了这么一个标准，我们也是往这个方向去努力，我们也只能看一下未来会不会如我们所愿完全解耦，但是至少撇开通讯业，如果很多互联网企业在5G，想在通信业里面做垂直应用，我觉得绝对就是纯软，绝对可以DevOps来做的。

  

  

**Q**

我想了解一下，你们平时对厂商的制品的质量或者代码质量是怎么把控的？

**佟得天：**实际上我们通信网元是有一个跟DevOps没有任何关系的把控，就是我们所有买回来，从各个设备商买回来的通信网元，都要经过一个很长很严格的入网测试，然后拿到一个入网许可证的软件才能够部署到我们现网。因此我们这次行业网关的DevOps尝试部署的这个制品包，也是有入网许可证的。所以，我们认为入网许可证是可信的，只要它有入网许可证，我都可以让它部署到现网。

  

**Q**

只要他有这么一张证书，它后续任何迭代出来的制品都认为它是……

**佟得天：**迭代的版本也是要有入网许可证的，所以我刚刚提到一个现实的问题就是，我虽然打通了，但是你让我在现阶段，在有入网许可证这个政策的情况下，在这里每天跑一万次是不可能的，因为每个入网许可证可能都要两到三个月，就是这个问题，的确是不一样的。

  

**Q**

怎么去提高入网许可证的时间？

**佟得天：**对，但这可能就是我们整个行业的事情，我这边说了算也没用，可能真的是要一个很大很大的改变，整个CT业的东西才能做的到了。

  

**Q**

刚刚您提到网元的更新迭代其实周期并不会像互联网公司一样那么频繁，可能一个月到两个月，因为也受限于这个入网许可证。那我比较好奇，这么一种进度的话，敏捷上云的，或者说引入DevOps的这个理念的意义在哪儿？就是它的好处在哪里呢？

**佟得天：**我们做这么一个尝试，就是希望从技术上证明通信业也是可以走DevOps生产线的，剩下就是看一下能不能从管理上、制度上去推翻现有的政策，或者说把入网许可证的这个流程改成通过自动化测试、自动化手段来做。如果能的话，那我这个就更快了。从通信业来说要打通这个东西的话，是要推很长很长，要推很多座山才行，但是，我只能说我们现在目前正一步一步推，就看一下我们这个愚公移山到底最后能走多少了。
