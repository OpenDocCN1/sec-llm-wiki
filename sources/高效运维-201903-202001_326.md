## 1\. 背景——全国集中维护、全球最大

![](../Images/1e07f0b9d8430051f3c5ad8c02476ded.png)

我们是做10086客服系统，有多少人是移动的用户？有多少人给10086打过电话？有多少人关注过10086的微信、微博，在上面查过话费办理过业务的？上述这些服务都是我们公司提供的，可以自豪的讲，我们也是大家生活中必不可少的一部分。

我们公司是2014年10月注册成立，全集团集中化、专业化运营试验田。客服系统是总部统一建立，31个分公司使用。

![](../Images/f70e285a6b3e0db6891d5ccf0bfc9f6d.png)

传统呼叫中心是基于PBX、专用硬件排队机、硬件语音板卡等专用设备组成的客服系统。有很多缺点：

1.  软硬一体，不够灵活
    
2.  建设成本高、周期长、维护升级困难
    
3.  无法满足多渠道多媒体互联网相关增值业务的融合
    
4.  无法实现多客服中心坐席跨网协同
    
5.  无法快速响应业务需求
    

![](../Images/7da23ab2e8864af5ef7d36be51674051.png)

日益增加的用户请求，和互联网化的富媒体需求，驱动我们下定决心建设了一个新形态的呼叫中心，具有以下特征：

*   纯软件：全媒体CTI、IVR、互联网接入网关、软交换、中继网关、媒体加速服务、用户终端
    
*   富媒体：支持传统语音、文本、图片、视频、短语音、微信、微博
    
*   智能化：与人工智能（AI）、大数据技术结合，应用于IVR、机器人应答、质检、外呼等
    
*   集中化：接续、CRM、分析、质检、话务监控等集中化。
    

![](../Images/756777b4bc99e112e24b5609e31eec18.png)

新形态的呼叫平台对我们运维的挑战和压力很大，具体原因如下：

*   第一是用户多，IT规模接近一线互联网企业。我们中国移动最新的数据如下：
    

*   9亿用户，超1亿微信粉丝，月服务超亿次，微博矩阵粉丝3038万（居行业首位），10086APP超五千万用户量
    
*   20000+服务器
    
*   50000+Tomcat实例
    

*   第二是业务变化快，运维环境复杂，使用技术新。
    

*   支撑全国营销活动，总部、分公司、省公司多级协同
    
*   日均上线 87 次，日处理 206 例工单。
    
*   技术新：微服务、云计算、容器
    

*   第三是稳定性要求高，需要提供电信级服务。
    

*   99.999% 的可靠性
    
*   15秒接通要求
    
*   7\*24 小时保障
    

![](../Images/30b9536c2aedaab4303212d104748d8f.png)

监控是生产系统的眼睛，也是运维系统中第一个面临挑战的。因为现在系统集中化建设后，监控指标的量级、监控需求的复杂度也直线上升。因为我们对新监控系统也提出了4点要求，那就是敏捷、集中、自动和智能。

## 2\. 出路——选择开源

![](../Images/9f7b30efa8a705cba103efb0430ce8c1.png)

怎么改造现有的监控系统呢？我们选择了开源方案，现在业界有很多非常成熟的监控产品，有很优秀的数据采集能力。所以我们统一监控平台是使用了开源工具+二次开发的形式，快速形成了可以跨域、跨厂商、跨层次的融合监控能力，以及多样灵活的数据展现能力，可以灵活适配各种不同场景。

![](../Images/bce5898f1d5d0f9c5997c3fc05c912f8.png)

区别与之前的31分公司每个分公司一套监控的架构，为了更快速的建立标准监控能力，更全面的管控系统质量，在线服务公司统一监控平台采用了总部集中建设、统一管控，分公司标准化接入的建设模式。本部负责监控能力建设，前期在主机、操作系统、网络、应用等层面提供了80多个适配监控模板，给分公司提供了通过监控代理一键接入的能力。

![](../Images/17c44d71d9f30ec87537c989942b8748.png)

半年的时间，基于成熟的监控能力和集中化快捷接入的建设模式，我们基本完成了总部+31分公司99%的基础监控，2万台主机设备入网，200万监控项，一天产生30万报警。

![](../Images/59b0f8f1487ad4be7625be30d2c86b94.png)

监控系统已经支持业界主流的操作系统和中间件。

![](../Images/ff177e8cbfb2f2891292e7681c50bf2c.png)

网络设备上也做了很多兼容。

![](../Images/5ee81a3beb0a42419f952760bc5e1bd9.png)

监控数据依托于开源工具的能力，可以做多种灵活定制，针对不同的业务系统和场景，都可以进行分钟级配置生成。

![](../Images/2468aaa7cd32121deb57ebec4c330eb4.png)

接入31个分公司的全量主机，这对 Zabbix 系统是一种考验，200万监控指标，肯定要做优化的。比如说数据库方面，CPU、内存、IO、连接（最大连接数、超时时长）、数据一致性、强烈建议采用数据库SSD硬盘。主机参数、内核参数、TCP协议栈参数、信号量/IO（Zabbix启动失败不释放信号集）。还有 nginx、php 参数设置。以及 Zabbix 的优化，比如说视具体需求配置启动模块和进程数，禁用自动发现，采用脚本调用 api 实现，禁用 housekeeper，启用数据库表分区，禁用 server 直连 agent 等。

![](../Images/1fad4a9a34b27ffa01be37efd58eddcd.png)

下面给大家介绍2个真实案例，具体介绍一些 Zabbix 系统的优化点。第一个案例是当我们监控项超过150万时，第一次发生故障，Zabbix系统一直在重启。经过分析现象如下：

*   发现大量消息队列积压（超过20万），且呈现雪崩效应。
    
*   Preprocessing manager 负荷长期为100%。
    
*   Zabbix server主机反复重启，却无法启动成功。
    

右上图是 Zabbix 官网对于 pre-process 耗尽的说明。核心解决思路是要降低 preprocessing manamger 进程的负载，具体解决思路是：

解决方法：

1.  在 Zabbix server 所在主机再单独部署一个 proxy 节点。
    
2.  将之前由 Zabbix server 直接监控的所有proxy所在主机的 agent 节点，全部转到新增 proxy 管理。
    
3.  降低 server 的 pollers、java pollers、pingers、trappers 等进程数配置。
    
4.  增加 Zabbix server 的自监控项配置项及告警（ Pre-process进程占用率及 zabbix\_server.log的异常关键字告警）。
    

![](../Images/457310ebdd1b7de3bb98f663cb9b23f0.png)

第二个案例是在监控项到200万的时候，监控系统又出现一次问题，现象就是新增监控项，发现底层代理新增监控数据怎么都采集不上去并且代理还会积压消息。

Zabbix会定期查询server数据库相关信息，如监控项，触发器function，trigger等。并定期进行向相应的proxy进行同步，从而进行相应监控项的采集与告警触发。但如果max\_execution\_time时间设置过短，就会导致select的查询sql无法查询成功，导致新增监控项异常，如自动发现无法成功，监控项无法采集。因此需要将max\_execution\_time时间配置加长。并定期检查zabbix\_server.log的sql执行时长，避免出现sql查询异常情况。

建议如下：根据现网的数据库IO处理性能以及局点规模合理配置数据库超时相关参数，将max\_execution\_time设置为超过目前zabbix server同步配置sql执行时长的2倍以上，并定期检查zabbix\_server.log日志的相应执行时长，或者增加自监控告警。

## 3\. 转型—-几个问题

![](../Images/69adc69d1ac2ff987f46261b45dffe71.png)

即使做了上述这么多优化，统一监控平台依然存在问题。其中最尴尬的一个就是拥有200万监控指标，业务挂了依然不知道，用户报障比监控快。这时我们意识到这不是监控系统的技术问题，而是定位缺失。

我们发现在监控领域，以前只做好了基础设施和应用的管理，用户质量和用户体验却是空白，需要及时扭转思路。不为业务服务的系统不是好系统，不为业务服务的运维不是好运维。我们需要以业务质量和用户体验为核心，以可管控、可视化、可度量作为新一代监控系统的目标。以用户体验出发，补全端到端的全链路监控。

![](../Images/050ee0fd0992391d8d6aef5317d074fc.png)

左边是应用性能监控，可以提供用户体验、前端交互、网络切片等监控能力，但是在应用调用拓扑，代码定位追踪上只有 APM 是不够的。我们从框架和日志侧进行了补充。右边关注的是业务质量监控，我们根据谷歌的 SRE 五项黄金指标来一点点建立自己的业务质量衡量体系。

![](../Images/6b282e0e79f1258265dee2e6e8c7b007.png)

前面说到现在我司的IT设备体量是和一线互联网公司基本持平的。那么我们也拥有海量的日志，光业务日志单中心一天要处理220亿条。那么这些日志是否有进一步的利用价值，这是我们需要思考的问题。

那么答案是显然的，很多系统亚健康的状态都是提前在日志里体现的。所以我们不管是应用层面的日志还是设备层面的日志，都做了统一的考虑，利用大数据实时分析技术等做了统一日志平台，进行异常日志的分析、统计与报警推送。

![](../Images/1d2c87a3851680ad75fa4d22f539c02e.png)

上图是我们的一个业务场景。我们有 31 个分公司，每个分公司都要利用接口平台跟其省公司进行交互，每个接口平台大概跑3千个接口。如果统计这个接口的调用量、成功率、失败率和响应时间，用 Zabbix 做监控的话，需要加入约 2480 万的监控指标。

这个监控量单独使用一个 Zabbix 有点支撑不住。需要我们进一步对监控系统进行技术上的丰富和升级。prometheus 走进了我们的视野，其灵活的自定义标签功能非常适合这样的场景，只需要设置 4个 metrics 采集，利用不同的标签就能轻松完成。所以后续的业务监控采集，我们更多的倾向用 prometheus 来完成。

![](../Images/910955b9382aea4475cac7d8678b119c.png)

经过以上几个问题的解决，我们重新思考了监控平台的架构。对于底层的管控资源，我们通过多个底层开源监控系统进行全方位的数据采集。然后通过运维数据集市的建立，将监控数据进行分层处理，有实时数据处理，有离线数据处理，并结合资源数据以及一部分规则数据，为上层应用提供丰富的监控数据支撑。

![](../Images/d15ea896b4c238b9b93162ebb53152be.png)

前面一直讲的都是监控系统能力与架构方面的演进，下面想讲讲我们监控系统运营的历程。一个好的系统除了能力需要很优秀之外，还需要好的推广与运营。我们是集中支撑了总部+31分公司的所有监控需求，大家想一下，一个分公司每天提3个需求，一天就是100个需求。这可以说是相当的任务繁重。目前在线已经全面实现监控自动化、自助化，来减轻需求的压力，效果十分显著。之前需要15个厂商来全力支撑需求，现在只需要4个自有人员就可以解决。

![](../Images/43838c44c2822dbf314ea496308dce4e.png)

这里要说一句，要想实现监控自动化，必须要先做好监控标准化。在做标准化的路上，我们是摸着石头过河。刚开始监控推广的时候没有做标准化，只想着以速度和效力优先。后来发现搬起石头砸自己的脚，花了很大的力气进行返工，这是很大的教训。在这里建议大家，先做好需求分析和功能验证，制定好规范进行标准化，最后才能批量推广。

![](../Images/781b4d0692a7247ebf63f240095472f3.png)

最后总结一下现在的数字，截止目前我们实现了614万监控项，每天处理近500亿条日志，一天产生198万条报警。

## 4\. 蜕变——AIOPS在监控告警方面的尝试

![](../Images/2b020f6860ed2d6c234bf6a4dc1f112b.png)

但是一天198万条报警也会产生一个主要矛盾，那就是海量的告警与有限的专家之间的矛盾。领导说：监控要多而全，一个问题都不能放过。而苦逼的运维人员天天吐槽说：每天平均每人收4000条短信，完全看不过来。那么在多而全，少而精之间我们如何权衡，成为监控告警系统当前需要思考的问题。

![](../Images/5790daf6a8cfd43aad67bc6c9da7d403.png)

那么我们对海量的告警进行了数据化的分析，发现：

*   第一，正常告警缺乏压缩与关联；
    
*   第二，误告警中有80%的原因是因为阈值不合理；
    
*   第三，是漏报中有70%的原因是无法设定一个合理的告警阈值。可见合理的设置一个告警阈值能解决很大一部分问题。
    

![](../Images/cb9fffa7349e63389e09c14286ea6357.png)

在这里我们来回顾一下告警阈值设置发展的历程。以前依靠专家经验设定固定阈值，例如网络设备cpu利用率超过60%就应该报警了。后面有了大数据分析之后，我们可以根据历史三个月的数值来给出一个比较合理的告警阈值，但是这个阈值依然是固定的，不能随着业务系统的变化而自动变化。到了智能化时代，我们终于可以通过人工智能算法来给出一个智能动态阈值。

![](../Images/0a898ad247397b6d1fccfd6d71e64bf8.png)

通过单一监控指标历史数据的读取和清洗，我们把异常的毛刺检测剔除。然后使用人工智能算法LSTM，再结合其他数据分析算法，通过对监控指标历史数据的学习，来预测其未来的趋势。当预测趋势值与当前实际的监控指标值发生较大的差异时，就会产生异常告警，这样的告警比固定阈值要准确许多。

当然刚开始的时候可能有不准确的地方，但是告警值班人员可以利用正常告警通知的工作对告警进行人工标注。后续的标注结果可以持续不断的优化我们的算法模型，这样告警就会越来越准确，形成良性循环。

![](../Images/aa41c35860eb4021d98636f56b3cca5d.png)

其实我们运维智能化的道路才刚刚开始，推荐给大家主要是想告诉大家。运维智能化离我们并不遥远。大家都知道人工智能有三大要素，那就是数据、算法和计算。运维最不缺的就是数据，我们有监控、告警、资源等等各种数据。那么算法现在业界有 TensorFlow 成熟算法库，不需要你从零开始。

最后就是计算，我们是对结构化的数据进行计算，不像人工智能非常热门的领域，例如图像识别、语音识别等，我们不需要投入GPU服务器，其实简单的虚拟机就可以完成算法的计算过程。所以可以总结为我们是轻量级的人工智能应用。

![](../Images/edafd1568ff568ee4f3ca10e103407a8.png)

所以希望大家对智能化不要望而生畏，觉得那都是 BATJ 才能搞的东西。我们目前在日志异常检测、告警压缩与关联、告警规则挖掘、根因定位、容量管理等方面都在做进一步的智能化尝试，也希望更多有识之士加入我们。
