作者简介
付正全，京东物流研发架构师，国家认证信息系统项目管理师，监控系统领域资深专家。曾任浪潮集团系统架构师，对 DevOps/AIOPS 有比较深入的研究。
曾受邀在SACC、Qcon、GOPS、Gdevops 等平台分享过智能监控、AIOPS 等相关内容，取得了业界一致好评。目前负责京东物流监控体系的架构设计和规划工作。
京东拥有中国电商领域规模最大的物流基础设施。随着京东物流业务快速扩张和规模不断扩大，IT资源的监控规模与数量（系统，服务和业务监控项）越来越多。传统的运维工作方式已经不能满足京东物流目前的应用系统规模。
如何基于如此大规模的应用数量及服务器基础设施构建全方位的实时监控系统，保障京东物流 99.999% 的服务可用性、降低手工运维复杂度并大幅缩短线上故障处理时间，已经成为京东物流首要必须面对和解决的问题。
另一方面，当前 AIOps 已经成为运维行业新的趋势，AI 技术的日渐成熟以及智能运维业务的快速发展也让 AIOps 成为行业热点。如今业界已经在趋势预测、根因分析、告警收敛等方面取得较大的进展。
各大企业尤其是互联网企业都已经在 AIOps 落地方面形成了自己的实践方案，在这里我们可以将对 AIOps 的实践分为平台化、数据化、智能化三个阶段。
平台化：建设 CMDB、监控、运维等基础平台，将运维人员的工作方式由人肉运维向自动化运维转变。
数据化：将资产数据、监控数据、告警数据、故障处理数据等借助大数据处理平台进行数据化索引和存储，以便进行数据挖掘、机器学习等大数据分析
智能化：通过AI等智能算法和技术对数据化的运维数据进行大数据业务分析，最大限度的挖掘数据背后的价值
监控平台作为 AIOps 的基础设施之一，是进行数据化建设的必要条件也是 AIOps 落地的重要基础平台。
因此在监控平台建设方面，基于京东物流以上的特殊场景，我们有必要针对监控做一个专项探讨。

1. 面临的挑战

由于包含超大规模 IT 资源的京东物流仓储系统遍布全国各地，可以说对监控系统说能遇到的常见复杂问题，我们这里都有涉及。主要表现在以下几个方面：
  • 仓储库房分布地域广
京东物流在全国运营的超过 700 个仓库中运营着几百个库房的集群，此外还有一些国际化仓储系统分布在全球各地，对监控实时性提出了更高的要求。
  • 机器、应用数量多
IDC数据中心和全国各地的仓储系统中的IT资源和应用数量特别多，导致监控规模>300万。
  • 网络环境复杂
地域及网络运营环境的多样，以及复杂的系统间调用关系导致网络环境及其复杂
  • 监控对象种类杂
监控对象不仅包含了常规的系统资源监控，也要包含调用链、日志、业务等监控对象，
  • 资产变化频繁
特别是系统上云之后，资源的弹性伸缩导致云上资产变化非常频繁，因此如何保证适应资源频繁的变化，保证资产及监控的准确性非常重要。
  • 部署环境不一致
各种应用的技术架构及开发语言的差异，导致机器系统环境和部署环境不一致。

AIOps 趋势下的新挑战

AIOps 趋势下对智能监控又提出哪些新问题和新的要求呢？在回答这个问题前我们先分析下面这个问题：
AIOps 的概念提出已经有几年时间了，为什么现在落地的进展不是特别快呢？我觉得主要有两大方面原因：
第一、AIOps 简单来说就是 AI 加 OPS，需要我们同时具备这两方面的能力。那么能做到两方面都兼备是不容易的。
在实际推进过程中，运维人员比较懂业务，但是算法知识是其弱项；相反，在研究所、高校等科研机构的算法设计非常优秀，但是他们离实际运维业务场景有些距离，算法工程化较为困难，因此导致 AIOps 发展比较慢。
另一方面原因就是 AIOps 不像其他技术热点一样，能够很快形成业界统一的解决方案。该领域目前没有形成一个统一的通用解决方案或者统一的场景化落地方案。
因为 AIOps与的实际业务场景强相关，每个 AIOps 实践者内部的的业务场景都不一样，就导致了整个行业没法一起前进，这也阻碍了AIOps 的进一步发展。

2. 超大规模监控系统解决方案

对监控的认识

说到超大规模监控系统解决方案，大家也能很容易想到目前业界常见的解决方案，如Zabbix、Open-Falcon、Nagios、Prometheus、Shinken、CAT等。面对如此多的解决方案应该如何选择呢，如何整合其中的亮点特色呢？
在回答这个问题之前我们应该先追本溯源探讨一下对监控系统的认识、什么是监控、监控有哪些价值等等一系列的问题。这些问题搞清楚了，方案的选择就更加明确了。
我认为监控系统最大的价值和意义在于对整个数据中心和业务系统具有完全的可控性。
这种可控性包含：性能可控、容量可控、交付可控、变更可控、效率可控、生产可控、安全可控和故障可控。
不论系统出现何种问题，都在运维和管理人员的可控范围内，依据智能监控系统能够及时发现故障并及时进行故障止损，甚至通过智能算法预测故障的发生，进而从根本上避免故障发生，真正做到防患于未然。
对IT系统的完全可控性让我们对整个运维场景信息十足、了如指掌，所以我觉得这就是监控最大的核心价值。

监控运维体系规划

很多公司发展到一定的规模之后，由于前期运维体系的发展规划不足，可能导致运维或者监控平台的重复建设。平台繁多就容易形成数据孤岛，导致数据串不起来，无法做全面的数据分析。
因此，在介绍超大规模监控系统解决方案前有必要谈谈运维体系的规划（参考下图）。
总体上，我们将该规划分为资源层、平台化、数据化和智能化四个层次。
底层为资源层，包括物理资源、虚拟资源、应用、中间件以及数据库。
上层是平台层。在平台层，我们建立了维护基础数据的 CMDB 系统，在 ITSM 管理方面，集成了事件管理、问题管理、值班管理等运维流程化管理模块。
在 CMDB 系统基础上我们建设了大规模资源监控平台、网络监控平台以及多个运维平台。
京东物流在全国超过700个大型仓库中还运营着几百个库房的集群，针对库房运维管理我们建设了库房运维和数据库运维平台。
通过 DevOps 平台将 CMDB、监控、运维等多个平台数据关联起来，形成闭环，从而建立基础的运维体系。
平台层的上层是数据化层。在这一层，我们期望通过对监控和运维平台产生的大量数据进行处理并做趋势性的预测和智能分析，提供一些比较有价值的统计报表，来指导业务运营和决策。
最顶层是 AIOps 层，我们是从三个方面去规划和实施的：发现问题，解决问题，规避问题。
基于 AIOps，我们可以在异常检测、根因分析、故障预测、智能故障处理、智能运维机器人等方面继续发力探索。在解决问题方面，可以借助 KPI 聚类分析进行告警知识库自学习和故障自动处理等。
第三个层次就是避免问题，我们可以通过故障预测技术在故障没有发生之前预测故障信息并做相应的处理，比如扩容、业务迁移、重启等，从而达到避免问题的效果。只有前两个方面做好了，才能保证提前预估故障并进行预修复从而达到规避问题的效果，这是最理想的状态。

建设目标

下面谈谈监控系统的建设目标，怎样的监控系统才是比较好的比较优秀的系统呢？我认为一个好的监控系统解决方案必须要同时满足以下特点：
及时性，故障在第一时间告警并通知管理员；准确性，做到既不漏报也不误报；精确性，秒级监控、细粒度的监控支持；兼容性，兼容各服务器，应用、中间件；扩展性，监控组件插件式、易扩展；可用性，系统高可用、无单点故障。
从监控系统能力成熟度的角度看，最底层最基础的是当故障出现时能快速准确的定位故障点；第二层，提供简单的资产管理功能并以资产为基础为运维管理提供数据支持。
从本质上来说资产、监控和运维密不可分，资产说是监控的数据来源，监控又是运维的基础组件。
第三层，提供 cmdb 全生命周期管理，实时掌握数据中心整体资产配置使用情况、运行趋势和健康状况，为决策层提供数据支持。
第四层，以平台建立流程、以流程建立标准，推动规范化自动化的运维管理流程，提供完善的故障处理和快速修复机制；第五层，实现监控运维体系的数据化阶段，使用初步的 AIOps 技术和大数据分析技术挖掘监控数据价值，助力业务增值。
第六层，完全的 AIOps 落地阶段，使用 AI+OPS 的方案进行聚类分析，故障、性能、容量预测以及实现智能故障定位、根因分析等。

构建可靠的 CMDB

前面我们提到系统上云之后，资源的弹性伸缩导致云上资产变化非常频繁。那么就直接导致CMDB变得不可靠。频繁的扩容、缩容操作不仅导致了资产本身的变化，资产的业务关系也随之改变。
比如变更所属应用、应用下线、应用负责人、应用成员变化等都导致CMDB结构发生变化。为了应对资产的频繁变更，我们通过一下五种方式，能够有效的解决这个问题。
1、自动发现，自动发现是降低维护成本的一种有效方式，提供固定IP段、协议、参数等信息自动扫描资产信息以及资产配置信息
2、业务接口(消息)，资产配置信息变化频繁，在资产变更时发送广播消息(或通过接口)通知其他子系统同步变更，保证资产变化实时同步。
3、定时同步，一方面作为业务接口的补充方式，另一方面资产数据来源多样化，目前有来自j-one/cap/dbs/中间件等其他平台的资产配置信息，在没有提供业务接口的的情况下可以通过定时同步的方式作为补充手段。
4、流程化，结合具体京东物流的业务来讲，完善运维资产信息变更的场景化流程梳理，比如说开关仓，服务器开关机/断电，服务器下架等等，这些流程需要与相应的平台打通，建立标准化变更流程。
5、人工维护，结合现有的IT运维流程，在某些场景下通过人工变更把CMDB信息维护准确，比如主机所属负责人变更、人员异动、机器异动等，可以通过人工直接变更完成。

技术架构

监控数据处理流程分为采集、分析、决策、处理四个阶段。在监控数据采集方面，既有基于特定协议/接口的主动监控也有基于agent推送的被动监控。
在监控数据分析方面，首先要解决的问题就是数据处理性能问题。因为监控系统和其他业务系统在业务特点上有很大的区别。
普通业务系统的业务量大多与时间相关，在凌晨及夜间业务量少，白天业务量相对较高。但监控系统通常都是7*24小时全天候不间断的进行数据处理，其业务量压力一直很大。
所以这对我们数据处理架构的高性能、高可用设计提出更高的要求。
在技术架构方面，采用被动监控的方式，通过部署监控 Agent，把监控数据收集到 Kafka 消息队列里。
消费模块从 kafka 拿到数据后转存到 jimdb（京东内部的内存数据库中间件）中，jimdb 实际是一个内存的分布式消息队列。
这里加了一层 jimdb 的队列。为什么要加这层呢？因为我们如果直接消费 Kafka，Kafka 有分区的概念，不同的分区之间可以并发生产消息，但是 Kafka 的分区是消耗磁盘 IO 的，如果我们建的分区太多，这个磁盘 IO 可能就会是一个瓶颈，意味着我们要需要更多的硬件资源。
考虑到这一点，我们增加了 jimdb 层，它是一个生产者消费者模型的分布式消息队列，理论上可以有无数个 Consumer，这些 Consumer 之间并发消费数据，从而实现并发数据处理。
如果被监控机器宕机或者agent进程异常终止了，那么整个机器的状态就没法监控，它的存活状态我们也没法确定，那怎么办呢？我们的解决方案是提供一个心跳服务，心跳服务定时与agent进程通信，如果发现有两个监控周期后没有收到数据，就会给他主动发送消息，如果没有响应，我们就认为该节点已经失联。

兼容性设计

针对京东目前多个监控系统并存、监控数据没有互通的问题，我们把所有的监控平台的监控数据整合在一起，接入了京东目前主流的监控系统，包括 log 监控、Docker 监控，MDC 的监控，DBS 的数据库监控，UMP方法监控以及调用链监控等，把数据收集起来做统一的报警和分析。
一方面有助于对应用进行更加全方位的数据分析与监控状态评估，另一方面也有助于后期建立根因分析的时候结合分布式跟踪系统去构建业务拓扑。

调用链监控

据 Gartner 统计，APM 是整个 ITOM，甚至 ITSM 领域里增长最快的一个领域，有很广阔的市场前景，目前全球 APM 市场规模大大约为 60 亿美元，预计在 5 年内可以达到 90 亿美元。
目前国内外的 APM 厂商已经比较多，也出现了很多优秀的开源解决方案。在 APM 方面，我们基于 pinpoint 开发的 Jtrace 分布式跟踪系统拥有 7 大能力：
  1. 分布式事务跟踪
  2. 自动检测应用拓扑
  3. 水平扩展支持大规模服务集群
  4. 代码级别的可见性，这是相对于其他产品最大的不同，它可以跟踪方法堆栈，特别清晰
  5. 使用字节码增强
  6. 集成了 SQLAdvisor，在抓到 SQL 之后，我们会分析到哪些是比较慢的 SQL，慢的 SQL 到底慢在哪里，我们可以通过这个给出一些优化建议
  7. 智能化采样率，基于业务访问量自动调整采样率，大大降低了业务性能方面的开销。

事件处理引擎

监控平台产生的大量告警和故障事件依赖完善的事件处理引擎的支持。系统事前建立规则库，该规则库通过自学习和系统预设两种方式生成。
事件处理流程如下：首先告警事件发送至规则引擎，规则引擎匹配出合适的处理规则交由执行引擎处理；执行引擎分为人工处理和自动处理，对于高危以及无法确切评估影响的操作采用人工方式处理，人工处理方式与IT运维流程做无缝对接。最后，处理过程加入权限检查和审计日志，确保操作的安全性。

智能知识库

基于大量历史告警数据进行自学习，分析每个故障时间点应用和指标之间的关联关系汇总为知识库数据，并存储到知识库系统。这个不断完善的知识库系统可以作为研发定位问题的依据，也可以作为故障自动处理的依据，还可以作为运维机器人的知识来源。
同时，知识库也支持人工添加一些常见的故障以及故障原因并给予较高的分析权重。通过以上方法，我们可以得到一个相对完善的智能运维知识库。

3. 面向 AIOps 的智能监控最佳实践

故障快照

我们经常会面临这样一个场景；系统在凌晨发生突然的cpu飚高告警，这个时段未必能及时处理，即使立即登录系统查看，故障现场也可能已经消失。针对这个问题我们可以使用故障快照的方式解决这个问题。
使用快照机制在故障处理方面取得了很好的效果。当监测到异常时系统会在触发报警的时刻立即触发快照，在系统上抓一些现场信息，现场快照信息包含：占用 CPU 较高的线程排名、JVM 内存堆栈信息、网络信息以及磁盘 io 信息等。
在发出告警通知的同时提供该快照信息的访问链接。快照页面同时也会列出该告警前后半小时内各种指标的趋势情况，供研发去定位问题。
要注意的一点是我们在存储快照信息时没有把快照存到统一的服务端，而是直接存在机器里面。其原因是 JVM 内存堆栈通常较大，若将快照信息发送至远端统一存储那么势必增加网络压力，同时也会消耗过多的系统资源，让本来就负载过高的机器雪上加霜，进而影响到业务的正常运行。

网络检测模型

前文提到京东物流全国仓储库房分布地域广、网路环境极其复杂。复杂的网络环境很容易导致监控数据的漏报和连通性误报，这对任意一个监控平台而言都是不小的挑战。
针对京东物流特有的网络环境和业务特点，我们采用基于网络延时检测构建的网络检测拓扑，并根据网络检测拓扑逐级上报的方式上报数据。
该方案具体流程如下：
  1. 定义监控服务端为网络延时拓扑的根节点；
  2. 监控服务端的网络检测模块通过 ping 检测本机与其他所有被监控机器之间的网络延时情况，并将延时<10ms 的节点作为网络延时拓扑的叶子节点。
    若不存在 <10ms的节点则将延时 <20ms 的节点作为为网络延时拓扑的叶子节点，若仍不存在则依次将该值递加 10ms，直到找到叶子节点为止；
  3. 以上述叶子节点为新的根节点。该根节点的网络检测单元使用 ping 检测本机与其他所有机器之间的网络延时情况，并按照上述逻辑查找子节点，若延时阈值增加至100ms 仍未找到子节点则退出；
  4. 循环上述过程，直到所有节点均出现在网络延时拓扑中。若处理完成后出现一些离散的点，则将这些离散的点作为子节点添加至距离其网络延时最小的节点中。

要注意的是该拓扑不是一成不变的，当网络状况变化时，会触发自动构建新的网络检测拓扑，以保证数据上报的可靠性和实时性。

趋势预测

在这里我们使用的是基于 LSTM 的预测算法。在 AI 领域 LSTM（Long Short-Term Memory）是长短期记忆网络，是一种时间递归神经网络，非常适合预测时间序列数据。该算法最早由 Sepp Hochreiter 和 Jürgen Schmidhuber 于1997年提出。

4. 规划&展望

在建设规划方面，我们在技术架构、产品架构和组织架构方面进行持续深耕和优化。
在技术架构方面，AI算法和运维业务的整合是我们的核心技术方向，在这方面也会投入更多精力；在产品架构方面，目前我们的研发策略是聚焦业务和为业务服务，更多的以业务视角发现和解决问题，实现业务增值服务。
在组织架构方面，引入专业的算法和 AI 工程师提升 AI 能力，赋能运维行业。
AIOps 是互联网运维的必然趋势，也是当前IT运维未来的发展方向。
随着数字化转型的推进，京东物流业务快速扩张和规模不断扩大，监控规模与数量（系统，服务和业务监控项）越来越多，云计算的大力发展又导致更进一步的集中化。
这些因素使得物流行业信息系统运维工作复杂度超越人力所能管理的程度，必须通过自动决策方式辅助人来进行运维工作。而对于业务而言希望不通过增加运维团队规模的方式支持迅速扩张的业务。以上两点导致智能运维的必然性。
