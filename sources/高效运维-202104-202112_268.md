### 背景  

低代码不是什么新鲜事物，N年前微软的 VB 以及 IBM 的 Notes 代表 C/S 时代低代码的鼻祖曾经盛极一时。后来B/S开始流行，低代码工具沉寂了好多年，最近人气又猛增，支持B/S的各类低代码工具更加丰富，资本炒作也异常火爆，一时间“人人编码”、“公民开发者”的呼声越来越强烈。当然也有不同的声音，TW 的大牛就持相反观点。我们这里不去讨论孰对孰错，主要谈谈运维和低代码结合的实际使用场景，看看当运维遇到低代码会擦出什么样的火花。运维的同学其实挺苦的，要学的技术又多又杂，比如日常工作语言以前是shell 编写脚本，后来得学 Python 做自动化，容器时代又得掌握 Go，如今又在从黑屏到白屏运维趋势下，高高兴兴（bu de bu）地学习前端技术 JS、Vue 等。虽然操作便利和可视化是运维背锅侠的共同追求，但术业有专攻，后台写写没问题，但前端开发还得靠专门的开发团队，然鹅开发总是忙于实现业务价值，对于运维开发的优先级明显不足。那么有没有方法让运维人员可视化且快速地实现运维场景，并能随时根据需求变化自助进行应用更新和调整呢？这就得借助低代码的能力了。

### 需求和场景

当前低代码开发的范畴包括前端表单、后台数据、工作流编排等等。运维工程师一般都能写接口程序、批量处理程序、数据处理程序等，但对于写前端比较排斥。比如，我们有个很具券商特色的工作内容——每日开闭市操作和检查（又称运维值班检查），每天早上8点各个券商就开始对核心、机构、渠道等业务系统进行开市前的准备和检查，通常会由A岗执行操作，B岗进行复核。

开市检查的内容和步骤比较多，大的分类都有 120 多项，一般 AB 岗要协同完成早间开市工作。我们以前的做法是把上述步骤做成表格打印出来，手工填写更新表格的内容，完成开市检查后，对纸质的表格拍照上传到 ITIL 平台。

这种模式的缺点很明显：表单维护困难、信息展示不灵活、记录并查询历史困难、没有上下关联步骤的技术约束、没有关键时间窗口的提醒、AB 岗不能协作等等。其实早就想开发一个电子值班系统，但又不想做成一个工程类的系统，因为其中环节、步骤和功能会时不时增加、减少和更新，就需要开发人员通过硬编码去调整，运维又不想麻烦前端开发的同学，所以迟迟没有实现。现在有了低代码工具/平台，我们尝试通过它来搭建运维值班管理系统，满足对值班的定制化需求，同时验证低代码平台的开发能力，运维工程师通过可视化的设计器就可以完成表单的设计和步骤的编排，过程步骤的调整也可以自行完成。

### 低代码工具平台的应用

平台具备流程构建能力、标准化的应用管理能力和应用灵活扩展能力，既赋能运维人员在通过图形化拖拽完成应用的构建，做到业务友好，同时也面向专业技术开发人员，能通过全代码的方式进行复杂场景的能力开发。

低代码开发的基础概念这里就不做过多的赘述了，网上有很多定义。我们这个场景用到的低代码开发平台是一种模型驱动的图形化设计器，通过拖拉拽组件和配置即可完成应用系统的开发。简易的开发方式使应用后续的更新也十分灵活，当需求有变化时，调整页面组件和修改配置即可实现应用更新。

“模型驱动与复用”是我们使用低代码开发的一项原则。低代码开发具有抽象建模能力，能够将业务场景抽象为模型，模型的实体化就是能够可视化拖拽的各个组件。当低代码平台现有的内置功能和组件无法覆盖和满足我们的业务场景需求时，可以评估这类业务场景的通用性，定制相关组件或升级开发平台来支持该业务场景。随着更多的业务需求场景的锤炼，低代码的组件逐渐积累和完善，使得平台能够持续“进化”，对复杂业务场景的建模能力也将不断提升，对应的低代码支持的需求范围也会逐步扩大。在实现运维值班的场景过程中，我们定制了一批具有券商行业特点的低代码组件，比如新增了“不选、正常完成、异常结束”的“三态选择”组件，还有“证券表格组件”、“级联字段组件”等等，因为组件具有复用性，一次定制开发后，后续在此平台上的应用都可以复用该组件，从而提高开发效率。

### 效果和实际价值

通过项目实践我们收获了很多惊喜，在友好度方面，相较于传统硬编码方式，低代码对运维人员更友好，它屏蔽了技术实现的细节，将复杂代码逻辑封装到组件中，让我们直接从业务层开始可视化地设计应用，让运维人员快速上手。一般运维工程师需要大约 2-3 天就可以熟悉低代码开发平台应用构建的模式和开发方法。通过低代码平台构建的运维值班管理系统在上线后的使用效果还是很不错的，满足了用户的各种个性化需求，我们现在已经把频繁修改操作步骤、增加上下文依赖等功能给到运维团队自行配置和维护。目前低代码在协作表单和业务流程管理类场景的处理上已比较成熟，后续对于运维工作中的各类工单、运维文档的电子化管理可以通过低代码开发来实现，由于低代码平台的高效，有几个团队的新需求也主动提出通过低代码来实现。运维值班管理系统值班表单 ▼![](../Images/3ac4a080442428a776ea3d0964fc7341.png)

### 推广中遇到的问题和解决方法

通过低代码开发的运维值班管理系统在推广和使用过程中也遇到了一些问题，比如我们的办公网和交易网是完全隔离的。开市检查操作是在交易网段执行，而值班系统因为是非交易类应用，所以部署在了办公网内，这就使得运维人员需要在两套键盘鼠标、显示器之间来回切换，系统使用的便利性有所下降。

为此，我们专门配了 iPad 设备给运维人员，值班检查过程的操作通过笔/手指操作即可快速完成，一方面提升了效率，另一方面新增的 iPad 设备也降低了用户习惯改变带来的排斥心理，有助于系统的推广。实际上，这套系统上线后，因其易用性不错，大家的接受程度很好，不到两周使用该系统的核心运维的同学就发了阅件单宣布完全迁移到该系统。

### 未来展望

前面实现的运维值班管理系统是低代码结合运维场景的小试牛刀，更长期的规划是**通过构建“运维开发平台”打通各类运维工具平台的信息孤岛和操作限制，实现更复杂的运维业务场景。**

目前我们已经建设了集中监控、统一自动化、ITIL平台、RPA、运维大数据平台等各类运维工具和平台，但随着运维精细化要求的提升，需要各类工具平台之间的数据和执行的高效互动，所以我们正在建设运维的 API 网关，把各类工具平台的通用能力作为服务挂在这个 API 网关上，计划通过低代码平台连接 API网关对各种服务进行调用、控制和编排，从而快速实现更加复杂的运维业务场景。

例如，我们的数据团队有一些重要的跑批业务是在半夜执行的，因为处理海量数据的时间窗口非常宝贵，所以每天都有一位二线技术人员值夜班，数据团队希望通过语音电话形式有效通知（呼醒）当晚值班的同事。之前我们是通过硬编码的方式实现的，这个需求大概用了2周左右的时间上线，但如果用上“运维开发平台”，那么告警接入、语音通知等都会以通用服务的形式挂在 API 网关上，通过低代码平台将这几个服务快速组装起来，实现效率将会明显提升。当然，低代码不是万能的，它适合特定的业务场景和特定的使用团队，而运维应该是个比较合适的应用领域，大家可以尝试用低代码的思想、工具和平台来提高运维的效能。

最后，感谢我们核心运维团队的小伙伴，在创新的路上有你们的支持让基于低代码的本项目能够快速地实践和落地，提高了运维效能。
