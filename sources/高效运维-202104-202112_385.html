1 概述

Kubernetes 作为成熟的容器编排系统，已经作为各大云厂商，比如AWS、Google Cloud、阿里云等的标准服务，为软件企业提供了灰度发布、蓝绿发布功能，适应当前企业应用软件快速迭代、快速发布的节奏；支持企业应用的弹性伸缩，自动重启，保证高可用的服务；提供完整的应用管理、网络管理、存储管理解决方案，大大减少企业软件应用的运维成本。

Kubernetes 如何能够实现最大单个集群能够达到5000个节点，15 万个 Pod 的完全自动化管理，更多归功于声明式API编程与控制器模式的协作。在 Kubernetes 中运行了一系列控制器来确保集群的当前状态与期望状态保持一致，它们就是 Kubernetes 集群内部的管理控制中心或者说是”中心大脑”。例如，ReplicaSet 控制器负责维护集群中运行的 Pod 数量；Node控制器负责监控节点的状态，并在节点出现故障时，执行自动化修复流程，确保集群始终处于预期的工作状态。

2 控制器模式原理

在机器人设计和自动化领域，循环控制是一个控制系统状态的不终止的循环。在控制循环中，包含控制器、被控制的系统和观测系统的传感器三个逻辑组件，外界通过控制被控系统的期望（spec）,来声明系统要达到什么样的状态，通过观测传感器来上报当前系统的状态（status），控制器通过比较系统的期望（spec）与传感器的状态（status）的差值，来控制系统达到期望的状态，整个控制逻辑如图1所示。

图1. 循环控制系统逻辑

上图通过举例说明，例如房间里的温度自动调节器。当用户设置了温度，告诉了温度自动调节器的期望状态，房间的实际温度是当前状态。通过对设备的开关控制，温度自动调节器让其当前状态接近期望状态。控制器通过温度传感器感知室内的温度变化，并致力于将当前室内温度转变为期望的温度。
整个过程形成一个闭环的负反馈控制系统（如图2），其优势在于该系统可以从“负”上来理解，它主要通过输入、输出间的差值作用于控制系统的其他部分，这个差值反映了要求的输出和实际输出间的差别。控制器的控制策略是不停的减小这个差值。负反馈形式的系统，各个逻辑组件独立自主运行，不断使系统向终态趋近，控制精度高，系统运行稳定。


3 控制器模式在 Kubernetes 内的应用

3.1 Kubernetes 控制器组件

Kubernetes 借鉴了上述控制器模式的思想，包含一组内置控制器，例如Deployment、Service、StatefulSet等，运行在kube-controller-manager组件内。一种控制器至少追踪一种类型的Kubernetes资源，这些对象有一个代表期望状态的指定字段，控制器负责确保其追踪的资源对象的当前状态接近期望状态。在Kubernetes内部，可以认为”万物”皆是对象,所有资源对象可以抽象成如下格式：
type Object struct {         metav1.TypeMeta          metav1.ObjectMeta      Spec ObjectSpec       Status ObjectStatus }
所有的资源对象均包含对象元数据，Spec(期望)，Status(运行状态)。通过Kubernetes API创建/更新/删除资源对象，控制器会监听资源对象事件（创建/更新/删除），并通过循环控制来协调资源对象趋向期望状态。控制器最简单的实现方式如下：
for {  desired := getDesiredState()  current := getCurrentState()  makeChanges(desired, current)}
控制器逻辑结构如图3所示，主要由Reflector、Informer和Indexer三个组件构成。
Reflector组件通过List & Watch API Server来获取Kubernetes资源对象数据，List用来在控制器重启以及Watch中断的情况下进行资源对象的全量更新，而Watch则在多次List之间进行资源对象的增量更新。Reflector在获取新的资源对象更新后，会在一个Delta队列中添加一个包括资源对象信息本身以及资源对象事件类型的Delta记录，Delta队列中可以保证同一个资源对象在队列中仅有一条记录，从而避免Reflector重新List和Watch的时候产生重复的记录。
Informer组件不断的从Delta队列中弹出资源对象增量记录，每拿到一个增量，Informer 就会判断这个增量里的事件类型，触发事先注册好的Resource Event Handler，然后创建或者更新本地对象的缓存。比如，如果事件类型是 Add（添加对象），那么 Informer 就会通过一个叫作 Indexer 的库把这个增量里的 API 对象保存在本地缓存中，并为它创建索引。相反地，如果增量的事件类型是 Del（删除对象），那么 Informer 就会从本地缓存中删除这个对象。
Indexer 组件提供本地缓存的索引（生成索引的key格式如下/），创建索引的目的就是为了实现本地缓存的资源对象快速查找，缓存在默认设置下是用资源的命名空间来做索引的，并且可以被 Controller Manager 或多个 Controller 所共享。

图3 控制器内部结构

控制循环中的控制器组件主要由事件处理函数以及 worker 组成，事件处理函数之间会相互关注资源的新增、更新、删除的事件，并根据控制器的逻辑去决定是否需要处理。对需要处理的事件，会把事件关联资源的命名空间以及名字塞入一个工作队列中，并且由后续的 Process池中的一个 Worker 来处理，工作队列会对存储的对象进行去重，从而避免多个 Worker 处理同一个资源的情况。
Worker 在处理资源对象时，一般需要用资源的名字来重新获得最新的资源数据，用来创建或者更新资源对象，或者调用其他的外部服务，Worker 如果处理失败的时候，一般情况下会把资源的名字重新加入到工作队列中，从而方便之后进行重试。

3.2 控制器模式举例-ReplicaSet对象扩容

ReplicaSet 主要的作用是维持一组Pod副本的运行，用来描述无状态应用的扩缩容行为的资源，但是在实际部署的时候会使用Deployment 对象来管理无状态应用，本文只是为了举例说明控制器的工作过程。
ReplicaSet控制器会持续监听这些 Pod 的运行状态，假设ReplicaSet对象所在Namespace为default，对象名称为App，将原来的replicas=2 扩容为 replicas=3。
首先，Reflector 会 watch 到 ReplicaSet 和 Pod 两种资源的变化，发现ReplicaSet发生变化后，在 Delta 队列中塞入了资源对象App，而且事件类型是更新。Informer一方面把新的 ReplicaSet 更新到缓存中，并与 Namespace default作为索引。
另外一方面，调用 Update 的回调函数，ReplicaSet 控制器发现 ReplicaSet 发生变化后会把字符串的 default/App字符串塞入到工作队列中，工作队列后的一个 Worker 从工作队列中取到了 default/App 这个字符串的 key，并且从缓存中取到了最新的 ReplicaSet 数据。Worker 通过比较 ReplicaSet 中 spec 和 status 里的数值，发现需要对这个 ReplicaSet 进行扩容，因此 ReplicaSet 的 Worker 创建了一个 Pod，这个 pod 中的 ownerReference 指向了 ReplicaSet App，整个过程如图4所示。
然后，Reflector Watch 到的Pod新增事件，在Delta 队列中额外加入了 Add 类型的资源对象记录，一方面把新的 Pod 记录通过 Indexer 存储到了缓存中，另一方面调用ReplicaSet 控制器的 Add 回调函数通过检查Pod ownerReferences 找到了对应的ReplicaSet对象，并把包括 ReplicaSet 命名空间和字符串塞入到了工作队列中。ReplicaSet 的 Woker 在得到新的工作项之后，从缓存中取到了新的 ReplicaSet 记录，并得到了其所有创建的 Pod，因为 ReplicaSet 的状态不是最新的，也就是所有创建 Pod 的数量不是最新的。因此在此时 ReplicaSet 更新 status 使得 spec 和 status 达成一致，整个过程如图5所示。

4 控制器模式编程的思考

通过分析可知，Kubernetes实现“容器编排”的核心，在于一个叫做“控制器模式”的机制，即：通过对ETCD内存储的Kubernetes API资源对象的变化进行监视，然后控制器的组件里对这些变化进行响应。而无论是 Pod 等应用对象，还是 iptables、存储设备、网络等服务对象，任何一个API资源对象发生变化，接下来Kubernetes需要执行的响应逻辑，都是控制器里定义好的编排动作。该过程组合起来，可以称为声明式编程方式，另一种常见的编程方式是命令式编程方式。

4.1 两种编程方式对比

两种编程方式的差别可以通过生活中的例子来说明，命令式编程方式更像是老师与学生的交流方式。学生缺少目标意识，无法自我管理，老师通常会通过一些命令或者明确的行为来约束学生，比如上课要坐正，回家要写作业等命令。命令式编程，它要求开发者描述为了达到某一个效果或者目标所需要完成的指令，常见的编程语言 Java、Go、Ruby、C++ 等，其实都是命令式的编程方法，命令式编程方式更强调过程。

而声明式编程的方式更像是一种交互式的沟通方式，类似于老板与员工。老板一般不会给的员工下很明确的决定，更多是通过给员工设置可量化的业务目标的方式，来发挥员工自身的主观能动性。比如，老板会要求某个产品的市场占有率达到 50%，而不会指出要达到这个市场占有率，要做的具体操作细节。可知，声明式编程方式不会指定Kubernetes怎么去完成部署任务，只是描述任务目标的状态应该是什么样子。就如3.2章节所示，当给ReplicaSet对象扩容时，并不是通过向API Server发出“创建一个新Pod”的请求来创建新的pod3，而是通过修改ReplicaSet中的replicas属性来声明资源的变化。因此，声明式编程方式是一种更关注状态和结果声明式的编程方式。

理解两种编程方式的差别后，可以大概分析出命令式编程方式的缺陷。

1.应用系统错误处理的复杂性

在开发系统应用中，除了编写正常的逻辑外，更多的时间是在处理异常逻辑，各种边界条件都要考虑。即使在开发阶段考虑了异常情况，但是在系统运行时，错误也是无处不在的。一旦发出的命令没有响应，调用方只能通过反复重试的方式来试图恢复错误，然而盲目的重试可能会带来更大的问题。为了避免重试的问题，系统往往还需要在执行命令前，先记录一下需要执行的命令，并且在重启等场景下，重做待执行的命令，而且在执行的过程中，还需要考虑多个命令的先后顺序、覆盖关系等等一些复杂的逻辑情况。

2.巡检系统与后台系统逻辑不一致

为了修正命令处理超时、重试等一些场景造成数据不一致的问题，采用命令式编程方式开发的系统往往还会开发一个巡检系统；然而，因为巡检逻辑和日常操作逻辑是不一样的，往往在测试上覆盖不够，在错误处理上不够严谨，具有很大的操作风险，因此往往很多巡检系统都是人工来触发的。

3.并发访问问题频繁

命令式编程方式在处理多并发访问时，也很容易出现问题，假如有多方并发的对同一个资源的请求操作，如果其中有操作出现了错误，就需要重试，最后哪一个操作生效了是很难确认的，也无法保证。很多命令式系统往往在操作前会对系统资源进行加锁，从而保证整个系统最后生效行为的可预见性，但是加锁行为会降低整个系统的操作执行效率。

相对的，声明式编程方式会记录系统现在和最终的状态，不需要额外的操作数据。另外因为状态的幂等性，可以在任意时刻反复操作。在声明式系统运行的方式里，正常的操作实际上就是对资源状态的巡检，不需要额外开发巡检系统，系统的运行逻辑也能够在日常的运行中得到测试和锤炼，因此整个操作的稳定性能够得到保证。最后，因为资源的最终状态是明确的，因此可以合并多次对状态的修改，且不需要加锁，就支持多方的并发访问。

4.2 声明式实战

Prometheus是SoundCloud公司开源的监控系统，同时也是继Kubernetes之后，第二个加入CNCF的项目，目前是监控领域比较成熟的一站式方案。然而，Prometheus的配置文件都是通过YAML的方式配置的，对于没有YAML语法的开发人员来说，有一定的学习成本，如果开发人员想对运行在生产环境的应用设置告警规则，则需要了解Prometheus相关知识以及YAML语法。本文利用声明式编程方法，以开发一个可视化Prometheus配置系统（如图6所示）为例，来说明如何借鉴声明式编程方式开发应用系统。

图6 告警规则配置

一条告警规则主要由以下几部分组成：

  • alert：告警规则的名称。

  • expr：基于PromQL表达式告警触发条件，用于计算是否有时间序列满足该条件。

  • for：评估等待时间，可选参数。用于表示只有当触发条件持续一段时间后才发送告警。在等待期间新产生告警的状态为pending。

  • labels：自定义标签，允许用户指定要附加到告警上的一组附加标签。

  • annotations：用于指定一组附加信息，比如用于描述告警详细信息的文字等，annotations的内容在告警产生时会一同作为参数发送到AlertManager。

而告警规则表达式可以抽象成由[表达式1] <操作符> [表达式2] 组成，操作符可以是 (<,>,==, !=)等逻辑计算。可以借助关系型数据库比如MySQL创建两个表格rule和expr来存储用户的前端输入规则，来描述告警规则期望的最终状态，类似于Kubernetes API资源对象的声明。

开发的可视化Prometheus配置系统除了编写MySQL数据库的增删改查接口，还需要实现一个控制器来生成Prometheus告警规则文件。控制器内可定期检查期望生成的告警规则文件与当前Prometheus正在使用的告警规则文件是否有差异，如果有差异则生成期望的告警规则文件，用来替换当前Prometheus的告警规则配置文件，整个过程是一个幂等的操作，不会因为某一次服务不响应，而造成告警规则没有生效。

5 结束语

Kubernetes本身就是一个复杂的分布式系统，但是其被设计成声明式API资源对象来管理整个集群的状态，借助kube-controller-manager组件这个”中心大脑”来管理庞大的系统资源和异常情况。控制器将异步的控制系统向设置的终态驱近，这些控制器是自主运行的，使得系统的自动化和无人值守成为可能。整个逻辑过程可抽象为：

  • 观察：通过监控Kubernetes资源对象变化的事件来获取当前对象状态

  • 分析：确定当前状态和期望状态的不同

  • 执行：执行能够驱动对象当前状态变化的操作

由于 Kubernetes 的控制器和资源都是可以自定义的，因此可以很方便的扩展控制器模式，比如采用Operator方式扩展Kubernetes API资源。特别是对于有状态应用，往往通过自定义资源和控制器的方式，来自动化运维操作。这样针对MySQL，Kafka，ETCD等有状态应用，通过Operator方式以容器化的方式运行在 Kubernetes集群里，能够实现存储、缓存和分布式系统的全生命周期的管理，包括应用部署和配置的自动化管理，自动升级，数据备份和故障恢复，监控、告警和日志的可视化管理以及应用的自主扩缩容，故障检查和系统巡检。

而非运行在Kubernetes集群的分布式系统应用，也可以借鉴声明式API编程的思想并结合控制器模式，开发一个更稳定，更精确且容错性高的系统。可以认为除非是对实时性要求比较高的系统，其他均可借鉴Kubernetes 的设计哲学开发高效的系统。
