## 1 设计理念

DataBus诞生于陆金所整个去O场景下，以及其庞大的架构改造项目。我们知道去O不仅仅是把底层的 Oracle 数据库替换掉，也不仅仅是将 Oracle 进行数据迁移，更多是要对应用层进行一个从头到尾、从传统架构往微服务化架构的相关改造。在这个过程中我们会对应用和数据库进行一个细腻度的相关拆分，拆分完成后，数据库和应用的数量都会比以前多很多，甚至会呈现出以前的数倍。拆分之前，我们所有的数据和应用通通放在一起，在一个数据库内的很多的操作，包括事物、查询完全可以在事物内部实现出来；拆分完以后，由于应用和数据库的数量比以前多了很多，数据与应用/应用之间/应用到数据库，包括数据库到数据库之间的同步链路、同步要求会比以前要复杂很多。DataBus就是基于应用完成微服务化改造，包括数据库完成了去O以后做很细腻的水平拆分，怎么样解决这种多个源，这个源可以是应用/数据库/大数据存储引擎之间的数据同步工作。

![](../Images/e4767a23e866a89a849cc7b7dd29e77d.png)

### 去O的痛点

去O痛点在前面有提到，就是要把之前在 Oracle 里面各种复杂的大事务，甚至一些复杂的大关联查询有比较好的解决方案，因为在 Oracle 里会大量使用数据库的高级特性来解决一些相关业务场景。在去O过程中，我们怎么把这些在数据库层面实现的计算往应用层面去迁？这方面也是我们要面对的一个问题。第三就是在现有架构实现和落地以后，应用数量/数据库数量呈现出一个数倍的增加，同步链路呈现几何倍增的过程中，怎样通过一套产品很好地把数据的实时同步给处理掉。

![](../Images/891db672def8b4703a75e37a68a70cbe.png)

### DataBus 的设计理念

随着陆金所内部的去O、信创、微服务、数据中台等相关改造的需求大量出现，去O过程中/完成后出现的大量应用和数据库，怎样通过一套实时同步框架来建立起数据的实时同步机制，我们基于此研发了DataBus。

*   第一，我们会把 DataBus 作为一个相关服务，我们内部叫 DbaaS，我们会通过 DbaaS 很好的对源端和目标端进行实时接入。源端和目标端按照整个 DataBus 方式接入以后，就可以在 DataBus 里定义一条同步链路，很好地对数据进行实时同步，包括数据的实时处理、存量和增量的同步。
    
*   第二，我们会把 DataBus 作为一个同步数据，同时也提供一些就是流式计算场景的平台。

![](../Images/59b340a6c636e7f4483856b74fa01f50.png)

## 2 架构

### DataBus的架构

同步时效问题，怎样确保从源端出来，可以以秒级速度往目标端进行同步？在同步过程中，如果源端/DataBus某个组件/服务器出现故障，怎样很好地实现断点续传？在对数据端点续传的过程中，可能会有些数据会往前去提一提？这个时候怎么对相关的数据进行幂等性处理，确保数据无论在源端发了几份，目标端永远按照只有一份数据进行处理。

还有 DataBus 怎么实现 Source 和 Sink 端的数据一致性，就是在同步和传输过程中确保两边的数据是完全一致，传输过程中数据没有丢失，或者数据的格式/精度发生变化，怎样进行很好的校验，这块也是 DataBus 需要解决的问题。

同时也要做好资源隔离及任务监控，基于此，DataBus 的架构首先会有一个 Sync Center，Sync Center 更多是集中了各种主流的 CDC 组件，比如 Canal/Debezium等，这些都以插件的形式很好地与 DataBus 进行了整合。

在 Sync Center 后是 Process Center，Process Center 是一个处理平台，它更多的是按照 Flink 框架，把 Source 和 Sink 两个核心的模块在里面实现出来。Source 端更多的是把从 CDC 过来的数据进行一个非常好的处理和解析，在这个过程中，同时我们可以在 Process Center 中加入 SQL 相关的计算模块。就是在同步过程中，不仅可以做数据同步，同时还可以实时的对数据进行加工和处理，然后通过 Sink 端发往后台的各种数据库（HBase/ES/应用/关系数据库，按照数据库的格式，对之前处理过的数据进行整理和转换），最后发往目标端对数据进行一个传输和同步。

在这个过程中，通过 Monica Center 来监控于同步过程中的各个链路及每个链路上各个环节的同步情况，并将报警与监控中心进行绑定，生成各种报表，让用户能够对整个同步的性能、效率和报错进行全局的掌控。

![](../Images/a0a3802ebf627f5665b11350f229813e.png)

### DataBus 的 HA 方案

关于 DataBus 的高可用方案，这里需要说的就是 Sync Center 和 Process Center 原生支持高可用的相关模块。在这个过程中，如果某个模块某个节点，或某个模块上的某服务器出现了问题，Sync Center 和 Process Center 都能自动切换，并对用户基本上是不感知。

### DataBus 全量到增量方案

前面提到 DataBus 怎样通过 CDC 进行实时捕获及同步。我们知道在做实同步之前，还需要有一个全量同步模块和增量同步模块。DataBus 不仅可以做全量和增量，它还可以把两种数据库（包括数据字典、表结构、类型、长度/精度、索引/分区策略） 进行一个很好的自动转换，就是说只要定义好相关的同步链路，比如从 Oracle 往 MySQL/PostgreSQL/其他数据库同步，Databus 可以把这个数据字典转化，包括全量迁移，后续增量/实时同步等一趟全部实现掉。

在整个同步过程中不但可以做到表原封不动地从 Oracle 出来直接同步到各种异构数据库（存储引擎）里，同时可以做到就是按照字段级，比如说只想同步某些字段，或者想把某些字段工作的表同步到另外一张表；我们也可以进行一个相关字段级的切割和同步，同时我们也看到某个字段按照水平分片的方式进行同步，比如说取模或者范围，建立1到N的数据实时同步也没问题，甚至将一个库里面多张表同步到不同的数据库，进行一个垂直拆分的同步，DataBus 也可以支持。在这个过程中我们只要定义好源端和目标端的相关的数据源，后续的整个过程 DataBus 都会按照我们制定的策略来实时的完成。

![](../Images/2a7b3a174601e83cdf04e17c220ad84c.png)

### DataBus 分片方案

很多公司在去O过程中都会有数据库的分片改造，比如 Oracle  数据库有些表的数据量非常大，甚至是一张访问频度很高、很热的表，这个过程中我们会引入类似于 Shardingsphere 这种数据库的路由层，就是水平拆分、水平分片的相关中间件，DataBus 也支持类似 Shardingsphere 这种主流的数据路由层的定义好的分片策略，那我们可以到 Shardingspare 里面，把数据库的水平分片策略，给 DataBus 层面进行读取。后续 DataBus 会按照这个方式会自动建立起一个从1到n的水平分片的同步链路，这个时候可以配合一些数据路由层进行流量切换。

![](../Images/9a99c19723665f292c20585051d65f7f.png)

## 3 技术亮点

第三部分要跟大家介绍 DataBus 的技术亮点。

### 3.1 灵活可扩展的数据同步架构

首先 DataBus 可以支持很多同步/存储引擎，包括整个数据库的同步、数据库到数据库、数据库到应用、应用到应用之间的相关同步，在这个过程中它的同步量是非常大的，包括这个过程中，还要进行非常多的数据转化/校验，甚至数据库的计算/整个关联都在里面。

DataBus 框架有三个 Manager 节点，可以水平扩展多个相关的 worker 节点，所有的数据同步及计算任务都放在 worker 节点。Manager 节点更多是提供任务配置，包括管理及相关的监控功能。

基于这种架构可以实现一个非常好的水平过来。那同时所有的 worker 节点，它又可以把现在一些很主流的开源或商业数据同步框架，包括 datax、kettle、canal 等。这些框架可以作为插件完整的 worker 节点上面去做相关的配置。

后续就是整个 worker 节点可以很好地支持各种主流的可插拔式的同步插件，然后通过整个 Manager 节点进行一个比较好的有效的管理和监控。

![](../Images/05384e89a11d5d7a25a7dac2c7c3f23e.png)

### 3.2 高性能下支持多种异构存储引擎

DataBus 高性能的处理模式，就是它可以从数据源出来包括数据的采集、计算和处理，甚至可以对某些工作进行统计和分析，还可以把数据往各种的分布式存储里面去写，同时支持后端的各种数据库的相关的应用。这个过程中，整个链路过程的数据校验也是有相关支持。我们自己测试下来每个节点如果是32c，同步效率大概是每秒6万到8万行左右，这个同步效率应该说是非常快的。

DataBus 支持目前各种主流的国产/开源数据库，包括 Oracle/MySQL/PostgreSQL/TiDB/ES。

![](../Images/365678623a1493a4021654c954ef5678.png)

这一部分是 DataBus 的一个非常重要的工具操作页面。我们可以看到在整个 DataBus 操作页面，我们只要把源端和目标端进行一个相关的定义，定义完成以后，后续 DataBus 可以自动地将整个同步链路给建立起来，包括往生长环境信息相关发布。

发布到生产环境后 DataBus 的监控和实时同步，在后面也会通过一个强大的监控平台进行相关的监控，在这个过程中，我们可以精细化地选到表字段，包含各种同步策略，甚至可以往里面加一些计算模块，就是我不但做数据同步，还在数据同步的过程中，对数据进行计算和处理，我们可以把数据同步和流式计算这两块进行整合。

![](../Images/65c6ab7fcf297a6db4c1c2590155d2a0.png)

### 服务完善、简单易用

这一部分是 Databus 相关亮点总结，就不逐一展开了。

主要的特色是可以完全可视化的拖拽；然后是几乎不要写任何代码就可以把各种纷繁复杂的异构数据源，甚至是数据源到应用之间的同步统统建立起来，并且可以做到秒级同步。

## 4 应用场景

#### 解决分布式事物改造

首先是 DataBus 经常使用的一个应用场景：数据库分布式事务改造。在去O过程中，一个很大的 Oracle 数据库，可能它的一个事务非常大，同时要对几张甚至10张以上的表进行事务级别的增删改查。在去O之前可以利用 Oracle 数据库的事物一致性来保证这些表同时更新/回滚。

一旦完成去O，这些表可能是分布在几个不同的数据库，就需要在应用层建立起一个强大的分布式事务架构。在这个过程中，其实我们如果需要对每个应用场景，就是每个类似于这种分布事物的话，都在后台的话，通过这种应用来实现的话，对于应用层的侵入性，包括它的改造整个改造复杂性，是个非常大的挑战。那我们会通过 DataBus 来实现一套分布式事务的解决方案，在应用层还是去保持这几个很大的事务。我们会在 DataBus 上面实现，就是我的应用层不做改造，同时会去捕获大事务的相关变更操作，同时起一个分布式事务，把这个分布式事物上面对底层分布式数据库的一些相关的变更，通过整个 DataBus 来进行保证，就是通过 DataBus 来实现数据库层（事务）往应用层的分布事务做转化过程，然后替换应用层的分布式事务，很好的对各个已经拆分出来的子数据库进行一个分布式事物的变更。

![](../Images/9fdaae816883342da667066fe27185fe.png)

#### 适配多种存储引擎构建最优查询服务

我们刚才这边是有说到写，那读也会面临这个情况，比如做完去O之后（就像这张PPT里面展示的），它的账目库、用户库甚至整个交易库的表都是放在完全不一样的数据库里，怎么样用一个很好的方式，就是说在去O之前可能会有一些查询需要跨账户跨用户，包括跨相关交易，那在拆分完了以后，其实是没有办法在数据库层面再去保证跨库查询，或者如果想在数据库的层面去保证的话，这种查询的效率也会非常低。这个时候我们更多的是会引入一个数据中台服务，然后引入一些其他的存储引擎，包括 ES，HBase，ClickHouse，甚至 StarRokcksDB，就类似的新型存储引擎来构建一套中台数据查询图。那我们需要做的是这些前台拆分开来的比较小的数据库，需要跟后台的中台数据服务之间保持秒级的数据实时同步，那我才有可能是说把之前在 Oracle 里的某些查询任务（甚至是对时效性要求非常高的查询任务）往后面的数据中台服务来推，那我们会通过 DataBus 把这样一个秒级同步给建立起来。那可能我整个前台的数据库和对应的数据源都很多，整个数据中台这边要支撑的（就是通过各种存储引擎要支撑的中台服务的相关类型）也很多，那如果这些事情都需要通过相关的 ETL 去写代码来实现的话，这块的工作成本和投入会非常大的。现在通过 Databus 在源点和目标点之间的话进行勾选，可以马上对生产环境去发布一个实时同步的秒级的同步数据框架，可以做到前台数据库跟后台的数据中台服务器进行一个秒级的相关数据同步。

#### 单体架构向微服务转型

那同时整个应用场景里面，比如微服务改造，从现有的单体架构往微服务架构进行转型，在这个过程中我是逐步将这些服务，表，数据对象，从单体架构网络往微服务架构去迁，这个过程会持续很长时间，那我们会有一部分流量还是在老的单体架构上面提供服务，会有部分流量逐步迁到微服务架构里，在这个过程中我们会用 DataBus 来建立这新老两套架构之间从数据库应用甚至到应用下的微服务所对应的数据库之间的同步。

这个过程中，就是同时新老两套系统包括数据库统统都在，我们会通过 DataBus 建立起一套这样高效的数据实时同步服务。

![](../Images/7d1b3f272bd182463452a293cea3fcc3.png)

#### 实现数据中台

我们在上面的样例里面这边有提到，就是我们会构建一个实时的数据中台服务，通过 DataBus 把前端的数据库跟后端的各种大数据存储引擎通过秒级同步的方式关联起来，并且里面的同步链路会非常多、非常复杂。

通过 DataBus 可以高效的拖拽，这种自定义方式能快速地把这套中台同步模式给建立起来，然后这个时候很多应用又可以直接访问这套跟大数据相关的服务，可以将整个中台服务通过 DataBus 有效地提供出去。

![](../Images/43b11a4fed27cd9c446a26bdd137fbe8.png)

#### 实现多数据源的同步+关联+计算

刚才反反复复提到大量的数据同步，无论数据库到数据库/数据库到应用/数据库到到大数据的相关存储引擎都还是在进行数据同步。DataBus 除了数据同步以外，它还可以在同步过程进行实时计算，就比如说我们可以做到两个数据源通过 DataBus 进行一些关联 + 计算，后续往第三个目标数据源进行发布。这个过程中相当于把两个数据源之间的相关 Join/关联操作，不需要在全部同步到整个目标源后再进行关联，可以在同步的过程中把预处理的计算给实现掉，这样对后端整个目标存储引擎的处理压力就会小很多，这个也是 DataBus 经常支持的一个业务场景。

#### DataBus在陆金所的应用

那这一块就是整个 DataBus 在陆金所的相关应用，这个应用跟我们刚才说的数据中台服务这边是比较类似的。整个陆金所在两年前完成去O以后，我们自己的数据库拆分得非常细，这个时候我们也会引入各种新型的存储引擎，来对整个陆金所的业务进行一个比较好的支持。这个过程中，我们会发现就是会有一些很好的存储引擎比我们现有的大数据平台/MySQL 数据库对某些复杂关联查询的效率会提升10倍甚至百倍以上。这个过程中，我们就需要建立起一套能把整个 MySQL 数据库作为一个纯的金融级别的数据的事务提交引擎，把整个 StarRocksDB 作为后端的一个偏实时的数据的相关的计算引擎，这个过程中我需要把 MySQL 与 StartRocks 之间建立起一个快速的秒级同步，那甚至于 MySQL 这边有一些新表上线，可以自动地在新表上线过程中无需人工再介入开发，自动的在整个 StarRocks 上把这张新表给建立起来。那这个时候我们会通过整个 DataBus 自动的把这条链路配置好，后续在 MySQL 那边如果我新业务/表上线的话，整个 StartRocks 可以马上对这张表会进行一个实时的秒级同步，而不需要研发人员花大量的时间来维护这样一套复杂的框架。

#### DataBus在平安养老险的应用

那个这个样例的话是 DataBus 在平安养老险，平安养老险现在是在对全栈进行去O，养老险这边会有一些非常复杂和庞大的 Oracle 数据库，那它也要做一个很犀利的微服架构改造，在这个过程中 DataBus 会有两块使用场景。首先第一块就是从一个传统的单体架构往微服务架构，在转化过程中整个 DataBus 会做一个中间状态，就是把我的整个流量逐渐从传统架构往新的架构上去迁移/切换过程中，整个 DataBus 会保证传统架构的数据库的数据或说维c还没有切过来的相关流量，这些数据通过 DataBus ，往微服架构的应用和数据库存进行一个实时的同步和相关的写录操作，同时再通过 DataBus 来构建微服务以后的架构和后台的数据中台之间的数据同步服务。整个平安养老险在去O过程中大量应用 DataBus 来构建其一套可扩展/前滚/回滚的一套去O的数据实时同步框架。
