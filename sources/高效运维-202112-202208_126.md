> Kafka 是主流的消息流系统，其中的概念还是比较多的，下面通过图示的方式来梳理一下 Kafka 的核心概念，以便在我们的头脑中有一个清晰的认识。

## 01 基础

Kafka 是一套流处理系统（也可以叫消息队列），可以让后端服务轻松地相互沟通，是微服务架构中的常用组件。

![](../Images/a507b89dd4a6330140ace2bd515f944a.png)

## 02 生产者消费者

生产者服务 Producer 向 Kafka 发送消息，消费者服务 Consumer 监听 Kafka 接收消息。

![](../Images/ee7ee91daa906da82beaacac61132ab5.png)

一个服务可以同时为生产者和消费者。

![](../Images/27b96531b98084c9e77a64ed42417e8a.png)

## 03 Topics 主题

Topic 是生产者发送消息的目标地址，是消费者的监听目标。

![](../Images/9aac80e134b1fef6a4fb59c9abaf3b2e.png)

一个服务可以监听、发送多个 Topics。

![](../Images/c2de760754d5e02c477a0f3149c8a2e4.png)

Kafka 中有一个【consumer-group（消费者组）】的概念。

这是一组服务，扮演一个消费者。

![](../Images/d70cee43587d745cb7148624ebc5d0a1.png)

如果是消费者组接收消息，Kafka 会把一条消息路由到组中的某一个服务。

![](../Images/59a8e29de80d08fcf6880a0f467780d3.png)

这样有助于消息的负载均衡，也方便扩展消费者。

Topic 扮演一个消息的队列。首先，一条消息发送了。

![](../Images/70f2cc62b41a688ce7d19f72d018772d.png)

然后，这条消息被记录和存储在这个队列中，不允许被修改。

![](../Images/019bf557ee98d8de809ddd1966d5d1ff.png)

接下来，消息会被发送给此 Topic 的消费者。

但是，这条消息并不会被删除，会继续保留在队列中。

![](../Images/dd999486dc4ab57e2975bfbf92d3ef0b.png)

继续发送消息。

![](../Images/d782b07086be50d7802a04a8fb9117b3.png)

像之前一样，这条消息会发送给消费者，不允许被改动，一直呆在队列中（消息在队列中能待多久，取决于 Kafka 的配置）。

![](../Images/dbc9319936547f04bd9ce212fb10112f.png)

![](../Images/429da008354ac18d4cc3c3dfef675eef.png)

## 04  Partitions 分区

上面 Topic 的描述中，把 Topic 看做了一个队列，实际上，一个 Topic 是由多个队列组成的，被称为【Partition（分区）】。

这样可以便于 Topic 的扩展。

![](../Images/cb551494e00a7b85949b35be5016f2a7.png)

**生产者**发送消息的时候，这条消息会被路由到此 Topic 中的某一个分区（Partition）。

![](../Images/8c18687e2de307ed555dda59fc39028d.png)

**消费者**监听的是所有分区并消耗所有人的事件。

![](../Images/3251da994e837ceee474c67c6ed3685c.png)

生产者发送消息时，默认是面向 Topic 的，由 Topic 决定放在哪个 Partition，默认使用轮询策略。

![](../Images/56054903b8dd0b7336284cb078646601.png)

也可以配置 Topic，让同类型的消息都在同一个 Partition。

例如，处理用户消息，可以让某一个用户所有消息都在一个 Partition。

例如，用户 1 发送了 3 条消息：A、B、C，默认情况下，这 3 条消息是在不同的 Partition 中（如 P1、P2、P3）。

在配置之后，可以确保用户 1 的所有消息都发到同一个分区中（如 P1）。

![](../Images/330d43413faa086b6181cf067f5e8f78.png)

这个功能有什么用呢？这是为了提供消息的【**有序性**】。

消息在不同的 Partition 是不能保证有序的，只有一个 Partition 内的消息是有序的。

![](../Images/2c0791cadd829b69f03160fba626c961.png)

![](../Images/3d23d915a9a1f53fd18fed3d4159459f.png)

## 05 架构

Kafka 是集群架构的，ZooKeeper 是其重要组件。

![](../Images/ff1252d9e9decdeff50f9bb933388691.png)

ZooKeeper 管理着所有的 Topic 和 Partition。

Topic 和 Partition 存储在 Node 物理节点中，ZooKeeper 负责维护这些 Node。

![](../Images/e87e20e8e87d5c193981e465ba06bae7.png)

例如，有 2 个 Topic，各自有 2 个 Partition。

![](../Images/0e01e0d1d6402bc3ba22d660b06981a3.png)

这是逻辑上的形式，但在 Kafka 集群中的实际存储可能是这样的：

![](../Images/7edc41e614eb31a794c2bcdf27479d47.png)

Topic A 的 Partition **#1 **有 3 份，分布在各个 Node 上。

这样可以增加 Kafka 的可靠性和系统弹性。

3 个 Partition **#1** 中，ZooKeeper 会指定一个 Leader，负责接收生产者发来的消息。

![](../Images/8ab4324dd6efc487babb4561403f1d45.png)

其他 2 个 Partition #1 会作为 Follower，Leader 接收到的消息会复制给 Follower。

![](../Images/758ab707e2ffbc8297d5512a0e828f59.png)

这样，每个 Partition 都含有了全量消息数据。

![](../Images/9231997c7554951e269b9789d28d5c0c.png)

即使某个 Node 节点出现了故障，也不用担心消息的损坏。

Topic A 和 Topic B 的所有 Partition 分布可能就是这样的：

![](../Images/f40b089744423be28c6494a9355738e9.png)
