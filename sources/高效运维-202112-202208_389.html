本文主题是混沌工程在去哪儿网的落地实现，根本点是把概率性问题变成确定性问题，具体怎么做成确定性问题呢？这里会详细讲解一下。

作者简介

朱仕智，趣拿软件科技股份有限公司技术高级总监。2013年加入去哪儿网，负责过公共业务、国际机票、基础架构等团队，擅长高并发高可用高性能的系统设计和落地，多年的技术管理经验。目前主要负责去哪儿网的基础架构和基础平台，专注公司整体技术演进和云原生技术落地。

按照4个方向进行今天的主题：
  1. 做事情之前要先做一下价值探讨，什么样的公司适合落地混沌工程，混沌工程能得到什么样的收益.
  2. 作为一家中等体量的互联网公司，实践出来的混沌工程平台是什么样的架构。
  3. 怎样落地自动化闭环做演练，这个非常关键。
  4. 怎样让混沌工程和其他的服务领域结合起来，进而发生化学反应，产生更大的价值。

1.混沌工程价值研讨

首先，我列举了前段时间的几个重大的宕机事故。

  1. 10月25日，韩国三大通信供应商KT发生故障，导致韩国大面积断网，直接影响到民生。

  2. facebook 大面积系统故障。

  3. 携程系统出现问题，无法购票和下单。

大家看到这类新闻肯定是吃瓜心态，但技术人除了幸灾乐祸之外还有一点辛酸，因为不知道哪一天轮到你了。怎么解决这类事情呢？通过本次混沌工程的分享来解决这样的事情。

这里列举一些数据，以去哪儿网为例，线上跑着的活跃（近一年有过发布、功能迭代的）应用大概有3000多个，服务化的接口有18000多个，网关上注册的 HTTP 域名有3500多个，消息队列主题数超过13000多个，内网支持5种语言的技术栈。可以看到，支撑这样一个形态的公司需要的系统群和生态。

大规模的系统群和生态很难保证完全可靠。大家知道在分布式领域里经常面临一个问题，如果一个系统是4个9，但有10个系统出问题的概率会高得多，因为任意一个系统出问题都可能会影响最终的结果。
除了这种情况还有另外一种情况，基础设施也不是那么完美。这里贴了一些内网可能出现过的一些问题，有服务注册中心、消息队列、机房、网络等等，各种层面的故障都有可能会发生。

发生这些故障时，怎么能让面向C端的业务系统群能够更好地工作起来？这时需要有强有力的技术保障。

我们从类型、影响范围大小来将故障划分为以下几类。
  • IDC机房：机房断电了、网络不通，大家不要想这些不会出现。从我的职业生涯来看，这些问题我都碰到过。
  • 中间件问题：应用需要大量的中间件支撑，一旦中间件出现问题，可能应用无法访问。
  • 机器的资源：程序写得不够可靠，计算密集型，防护不够好，导致 CPU 高，load也高。其他的基础设施导致的，例如 JVM 的Bug或者并发编程不恰当，导致死循环而耗尽CPU等等。
  • 应用问题：FullGC，日志拖慢主线程，导致服务不可用。
  • 依赖问题：上下游的依赖，你的服务没问题，别人的服务有问题怎么办？
基于一系列背景，混沌工程诞生了，最早是 Netflix 为了保障他们的服务。因为 Netflix 的业务是跑在云上的，云基础设施对 Netflix 来说是无感的，即使这样的情况下还是发生了一个非常大的事故。这个事故之后他们就提出了混沌工程的理念和实践方式。我们来看一下这个混沌工程的概念。
这是一门什么样的学科呢？是一门通过主动演练，提前把可能会发生的问题让它真实发生出来，看看系统的真实反应，进而提前应对它。应对有很多种方式，可能提前把它修改掉，有可能是提前做好预案等等。
综合来看，混沌工程的目标有两个：
  • 通过混沌工程让我们建立系统工程抵御生产环境中发生失控的各类条件的能力和信心。做完之后说系统就是可靠的，不是靠概率、运气。
  • 把以前概率性问题变成确定性的问题，做到什么程度就知道可靠到什么程度。

混沌工程的收益是什么样的呢？这里分三个角度

  1. 人，对用户来说可以享受到更稳定的体验。以去哪儿网为例，系统挂了想买票、退票陷入焦虑的状态，可能是半小时后一趟火车，我想上系统里面买一张票，这个时候买不到会非常焦虑。对于测试和开发是一样的，能够提前发现这些隐患并把它修复，提升故障的应急响应效率。

  2. 流程：完善了故障处理体系，从被动发现变成主动发现，并且验证了以前收集的指标、设置的报警是否真实有效。

  3. 系统：提升了这个系统的韧性，在各种发生意外的情况下都不出问题，尽最大能力跑在线上。

2.去哪儿网混沌工程实践

从这个角度看，非常有必要将混沌工程落地到企业内部。去哪儿网从 2019年开始落地混沌工程平台，但是我们一路走过来也是分多阶段去落地实施。下面与大家深聊去哪儿网的混沌工程平台。
从应用架构来看有很多层次，有机房、中间件、服务器、应用、服务依赖层。层次间会显示出明显的关系：越往下概率越小，但是造成的影响是越大；越往上出概率的机会越大，但单次产生的影响越小。
这意味着当想要去落地混沌工程时面临一个选择，这个时候你希望先落地哪些类型呢？这需要针对企业内部做一个权衡。比如对去哪儿网来说，可能觉得下面三层是早期最希望能够解决的。

去哪儿网实践混沌工程的路径为以下几点：

1、优先做关机演练
关机的演练意味着机器或机房需要先宕掉，这会涉及到各个方面。例如演练去哪儿网多个IDC中的一个挂掉的场景。还有公司中间件的设施，服务注册的中心、消息队列都是公司级别的，假设这些中间件挂的时候怎么办？
所以，我们第一期基本覆盖了这四大的场景，这个是我认为收益最高的。当一个IDC挂掉时，如果没经过混沌工程演练过，我没办法保证一个IDC挂掉对线上业务有没有影响。
很多开发进行应用设计时不是能够自觉考虑系统可用性。举个例子，某个应用部署了两个实例放在两个机房甚至一个机房，这个机房发生断电或网络出现问题，有两种情况：第一种在机房布了两个实例两个都挂了，依赖这个服务提供的能力都不可用。
两个机房分开部署两个实例，一个机房挂掉意味一半的实例没有了。没有做好容量规划和提前评估，上来的流量会一下把它打爆掉。各种各样的原因导致我们最早做的是关机型的演练。
2、在基础设施保障下进行应用演练
有了底层基础设施的保障后，再去落地应用级别的演练。应用级别的演练主要解决的是应用资源的问题。可能会出现与关机演练不一样的是不会直接死掉，反而是半死不活的状态。应用不停地 FullGC，日志写入堵住主线程……请求一会儿能处理，一会儿不能处理，甚至以非常缓慢的速率在处理，这对分布式系统是最要命的。可能对它进行健康检测时是活着的，真实流量过去时大部分处理不了。
3、强弱依赖
什么是强弱依赖？一句话解释就是“死道友不死贫道”，“道友”全死掉都没关系，我能不死就行。通常会面临的问题是，比如调其他的服务，将超时时间设置成1秒、500毫秒、300毫秒，但超时时间跟吞吐量有关系。我们设置超时尽可能会保证请求能回来，会在最长时间的界限上留一定的 Buffer，当大量的响应时长都涨到阈值之下系统可能会被拖死，机器的资源都用于等待下游的响应导致不能服务新的请求。
这种情况意味着如果不好好处理，别人的服务可能出现状况，他没死掉，你反而是那个死掉的人。
4、容器化支持
现在是云原生时代，容器在云原生时代是非常好的载体。企业往云原生路上走，容器化是绕不开的东西。以前的落地演练基本上是针对虚拟机，在云原生时代，我们也做了容器化类型也做了支持。

下面从几个类型详细分述不同演练之间的能力和关键点。

2.1 关机演练

关机演练是同一个机房某个业务线所有服务节点全部关机，演练规模是单次有超过1千台。我们会做大批量真实的关机。为什么一定要这样？因为不仅要验证它出问题，还需要验证恢复的时间。如果是假装形式会恢复非常快。
关机演练有以下关键点：
  • 有非常完善 CMDB 或应用画像的平台，方便按照机房、业务将信息聚合起来。一些显而易见的问题，例如某些应用只在一个机房部署，不用演练就知道会出问题，这种信息可以提前聚合通知到对应负责人改造。
  • 演练过程中将沟通机制嵌入到流程里。帮助演练计划自动配套沟通群，包括所有进度周期等都会在内部IM里通知。
  • 真实的关机。
  • 接入告警。去哪儿网的机器指标和业务指标合起来大概5000万量级，指标和报警大了也会有区分度，当我们演练时需要接入最核心的业务指标的报警，核心的业务指标报警出现问题需要中断演练并自动化恢复。
  • 开关机之后服务自动恢复，这也是落地平台必须有的。比如大量虚拟机演练完不可能让公司的研发人员逐个将服务起起来，这在效率和人力上不可接受。

结构上来说有几个层次：
我们落地关机演练从底层来说实体机和虚拟机都有，2011、2012年上了Openstack，基于Openstack API 做到关机、重启等运维工作，但缺少了上层的编排服务和控制及流程的串通。

最后看一下演练效果，可以看到大概一两个月会做大型的关机房的演练，总共演练有49次，每次演练的机器和涉及到的应用也非常多，每次都能发现一定量的问题，前期发现的会更多。

我记得在2020年初有一次发现了30几个主流程上的问题。大家可能会疑惑，为什么有了演练还会发现新的问题？其实这跟架构是一样会自然地腐化，因为没有前置准入的控制，一段时间线上的时间会慢慢变糟糕掉。
可以从监控指标和告警上看到真正做机房关机的时候可能会有明显的异常波动。

2.2 应用演练

应用级别的演练会涉及到技术选型的问题，从机器资源层面说已经有 Openstack，应用级别的演练支持的场景非常多，例如需要不停地 FullGC、日志写入缓慢，需要有比较好的技术手段去支持。

当时基本上维护得比较好、用得比较多的大概只有三种选型：

  1. Netfilix 官方，支持平台是虚拟机，场景比较丰富的，问题是不开源。
  2. Chaosblade，阿里巴巴开源演练工具，特点是容器和VM都支持，场景相对丰富，好处是开源的。但是整体性比较差，什么叫整体性呢？当时只有 Agent 这一层，没有控制面，整个编排、安装等事情都是做不到的。
  3. Chaos Mesh，PingCAP开源出来，只支持K8s的模式。
这种情况下我们当时选择了 Choasblade 做执行面。
这里简单介绍一下 Choasblade，左边是执行面的架构，算是命令行和支持 HTTP 接口触发执行的 Agent 模式，支持多层面的故障演练：操作系统、语言技术栈，还有 K8s 层面的。

Choasblade 支持的场景非常丰富，基本上覆盖了需求的各个方面。但还有一些缺失的企业场景。例如：HTTP 超时、FullGC、日志拥堵；某个应用往下调用，不同点调用同一个接口之间的强弱依赖关系性不一样；调用点区分不支持；链路匹配，对于全链路Trace的以前也不支持。

在落地的过程中，公司内部支持了这些形态，我们将这些形态以 PR 的方式提交到社区里去，现在选择 Choasblade 以上特性都是天然支持的。

2.3 应用依赖关系

这里有一个特征就是想要呵护好应用程序的一个觉悟：就是别人的服务可以挂，我不可以挂，要尽最大努力提供服务。如果依赖关系不好会导致蝴蝶效应，最终传递到C端；强弱依赖判断不合理，熔断是不是预期，降级是不是合理，这些都需要演练才能保证。这些需求不好好治理最终只能运维来背锅。
针对强弱依赖型的演练做了支持，过程基本上是制定计划、选择对应的应用、需要生效的机器，将 Choasblade 的 Agent 注入到机器上并挂载到 JVM 里，进行选择策略的注入。
然后通过流量的触发，流量可能来源于各个方面，正常的流量或是人工触发的case等等，甚至是自动化等等。
最后把这些监控指标收起来，得到演练计划和集成结果的复盘，得出结论：演练下游接口出现问题应用是不是可靠的。

这是强弱依赖演练得到的效果。我们演练大量的接口依赖，能够找到很多以前难以发现的问题。

2.4 容器化支持

由于之前选择了Choasblade，我们希望继承技术的资产，不会一下子抛弃掉这个。这意味着在选型上有一个前提，基于Choasblade的场景下看演练去支持容器化的场景。
这里会有几个方案：
  1. Choasblade官方Operator方式，这种方式有个问题，控制端要全新实现一遍，控制端我们以前是自研的有完善的内部流程，怎么编排，怎么串流程，内部建群等一系列的东西都得推倒重来。
  2. 不通过Choasblade-operator，用Sidecar的模式，Sidecar的模式比较灵活，但只能解决Agent安装的问题，但是策略下发和控制都得重新做。
  3. Choasblade-operator+blade-server，要对Choasblade-operator做二次开发，最后选型是用Sidecar的模式。如果我们能够解决安装注入的问题，剩下基本上整个控制面已经有了，接下来控制面和Sidecar agent之间通信的问题就非常简单了。因为agent本身有HTTP接口的，我只需要把前面刚才提到的触发agent执行HTTP的接口调用一下就行。
这是支持完容器化之后比较简略的结构层次图，最上面是整个应用的管理平台，还有依赖信息（元数据）的平台。中间是演练的系统，包含了演练的生成、编排等各类支持功能。有多种技术手段需要触发，虚拟机可能用类似于Openstack的方式去触发，容器的就选择Choasblade。

建设完这项能力之后，当然希望生效面越大越好，有没有办法自动化执行并得到结论？下面提一下去哪儿网的实践。

3.自动化闭环演练策略

为什么做这个呢？
  • 常用常新：避免运动式，运动式面临人力成本高、覆盖面低；
  • 想要做到持续的可靠需要完善的应用元数据、自动化执行流量和自动化的断言。

3.1 应用元数据的采集

自动化演练需要所有的信息才可以提前编排，我们有完善的应用元数据的平台分析好所有底层资源，HTTP协议、Dubbo协议、数据库、应用本身暴露出来的各种接口的元数据，包括接口和数据类型；还有Trace的拓扑关联关系等，有了这些信息后聚合到一起分析，这个应用依赖谁？依赖的明晰数据是什么样的？A依赖B，B接口的Metric指标和数据结构是什么样的，有了这些数据我们可以自动化创建出来。

3.2 自动化流量和断言

注入进去没有流量怎么办？第一可以选择用线上流量，问题在于并不是有预期性的、提前控制好的影响面，这意味着用线上流量风险会非常大。这个时候需要有其他的流量帮助触发这些流程，并且保障能够得到结果。
比较好的是去哪儿内部有比较完善的接口自动化测试平台。依靠测试平台帮我拿到这些流量，执行到目标机器得到自动化测试的断言报告，知道对应用是否有影响。拿到这样的报告可以知道本次依赖断言，是成功还是失败，强依赖还是弱依赖。

有了这个机制后要周期性执行它，有两个：
  1. 增量演练，我们需要把之前产生的新增的依赖非常及时把它演练掉，这个依赖今天刚上线，第二天凌晨就把它全部演练一遍，这样能够保证我们东西上线可靠。
  2. 全量演练，这里有一个点依赖关系没变，但是调用点代码有变更，强依赖变成弱依赖等等，意味着我们要周期性把这个演练一遍。
演练的效果大出我的意料，我开始以为50%接口配置比较合理，真正执行下来发现73%是不符合预期的，不符合预期以前认为是弱依赖，真正把接口干掉以后应用真的出现问题了。

4.混沌工程和服务治理

最后一个混沌工程工程怎么和其他领域结合起来让它产生一个化学反应。大家前面看到这些能力之后，我们不满足于真的验证这个东西的可靠性，我会思考这个技术手段还有没有别的技术价值，我觉得我思考出来一个问题，其实可以和服务治理结合到一块。
怎么结合呢？我们服务治理配置的参数基本上具有很大的无效性靠开发人员脑测或者是配置出来的，比如说超时时间拿别人的往上加一个数，合不合理不知道，什么时候发现呢？故障的时候发现。我们不可能靠故障收敛超时，依赖会越来越多。必然会导致服务治理的无效性，配置超时、熔断、限流大概率有问题。
有问题的配置怎么改善呢？混沌工程的方式，帮所有业务人员配置超时的时候，可以用混沌工程先演练一遍，看是否符合它的预期，只有真正符合预期的时候，才认为超时、熔断、限流服务治理配置是有效的。
这里有一个难点，这些配置基本上不同环境可能不一样，这里面会面临一个问题，这些执行必然全部百分之百都需要在线上演练，这里会有一个难点，爆炸半径一定要控制得非常有效。举个例子来说，我有一个系统链路A调B调C，C挂掉的时候A和B会不会透传出去产生一系列的影响，甚至导致用户不下单，这是我们做自动规划的时候需要考虑的。
第二你的断言，前面提到自动演练需要依赖自动化测试的断言，但是如果你是线上去做断言很难做，你需要有第二种断言的方式，我们通过异常报警以及智能化的异常诊断做的。
第三需要有全链路压测平台，刚才提到了，限流的场景如果没有足够的流量是测不出来限流会不会被触发，只有比较完善的全链路压测平台给你足够多流量才能做好这个事情。

下面是爆炸半径控制的细节逻辑，我们有入口的系统，后面会有比较简单的ABC的系统，后面会接着往后调用。红色的线代表弱依赖，黑色的线代表强依赖。这条线上能够看到入口系统调用B系统、E系统、G系统、M系统这条链路是强依赖。比如说从E调到F这一层开始出现弱依赖的场景。

我们可以利用这种特性，我们在去选择要演练的系统的时候就可以去判断，当我这个系统挂掉合的时候，我去倒推中间有出现过弱依赖，进而能够保证我对线上没有产生影响，这个时候能够筛选出一大批系统，可以控制好爆炸的半径。

断言有两种类型，一种是人工型的核心面板和metric指标的报警配置，另外有偏AI形态的智能诊断和检测，发出一对应的报警。一系列的报警会放在一起，我们能不能发现Match指标，如果发现的话把演练中断掉。

演练过程第一个按照注入点选择注入，进行稳态的判断最后就是演练真正的生成，并且去执行这个演练。这样我们做完这一套流程下来，就能够得到线上这一些服务治理的指标到底是不是合理的一个结论。
