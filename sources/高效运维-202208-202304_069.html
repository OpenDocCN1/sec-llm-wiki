作者简介
李佩东，虎扑云平台架构师。2012年开始接触 VMwrare、Citrix 虚拟化，到后来的CloudStack、OpenStack，再到 Kubernetes、Container，在云计算岗位摸爬滚打了十年，积累了一定的专业技能和实践经验。

本文主要介绍虎扑业务场景、Flex扩缩容平台、问题与调优三个方面。其中将深入探讨虎扑的业务场景，介绍 Flex 扩缩容平台的架构与实现细节，并分享在使用过程中遇到的问题及调优。

一、虎扑业务场景特性

虎扑于2004年成立，已经发展了18年。目标是利用互联网技术为广大体育用户提供服务。目前，虎扑已经拥有超过1亿注册用户，日峰值访问量达到2.3亿，月活跃用户达到了1100万。这些数据大致能够反映出虎扑业务的规模和对可靠性要求。

关于业务

目前虎扑的在线生产应用约有500个，使用的语言包括 JAVA、Python、Go、PHP 和 Node 等，有四套环境，即本地、测试、预发和生产环境。
自2019年开始，虎扑逐渐将业务迁移到 Kubernetes（K8S）上，目前业务容器化率已达80%，高峰期 K8s 集群 node 节点平均使用率达 60 以上，云上资源成本降至50%。
在此过程中，我们建立了一套完善的系统，包括配置、构建、发布、工单、监控、日志、压测和费用管理等。目前，我们已在腾讯云和阿里云上部署了包括测试、预发、生产、运维和灾备等十几套集群。

关于流量

虎扑的流量基本上在夜间较低，白天比较稳定。在非赛季期间，流量比较正常，但在赛季期间流量会显著增加。同时也存在一部分无法预测的流量。比如在比赛期间，如果打得激烈出现热门话题或意外事件，就会突然产生大量流量，这些流量来得快去得也快，难以预测。

面临的问题

以下是面临的问题。在扩缩容方面，我们需要保证足够的备用资源量来满足各种业务场景。同时为了降低成本，在K8S生产集群中，只保留了 15%-20% 的常备资源池剩余量。我们需要在保证成本最低的同时，确保业务不挂、用户正常访问。同时需要进行多云部署，如何兼顾多个云平台的特性，并确保Pod和VM的兼容性也是一项挑战。
为了应对这些问题，我们开发了 Flex 扩缩容平台。

二、Flex扩缩容平台

Flex 概览

Flex 平台大屏主要分为两部分：左侧和右侧。右侧的大屏展示可分为两个维度：集群资源和应用资源。此外，还显示了场景调度的状态和热门比赛信息。运维人员可通过大屏及时发现热门比赛、异常流量等情况。

左侧为功能菜单，包括了扩缩容（Pod、云主机、Node），以及数据库扩缩容、场景开关、审计日志、用户权限设计等。

关于架构

Flex 是基于 CMDB 保存应用的各种元数据信息，包括应用名、项目名称、负责人、部门信息、资源配置信息和副本信息。当需要扩缩容时，Flex 会从 CMDB 中获取应用名和副本数，并保证应用实例的常备数量。
在缩容场景中，Flex 会确保缩容的数量不低于最低副本数量；在扩容场景中，Prometheus 将从 K8S 和云主机拉取数据，并通过 Rig 监控告警系统进行处理。处理后的数据将发送给 Flex 进行整理和分析，以决定是否需要扩容或缩容。
为了同时调用 K8S、腾讯云和阿里云的 API，Flex 引入了 API 层，从而实现对 Pod 和云主机的兼容性。

Flex核心功能

平台的核心功能包括资源统计、节点伸缩和场景调度。接下来，我将分别详细介绍这些功能。

资源统计

在大屏最上方一排可以看到节点数量。由于集群运行在云上，因此节点分为包年包月和按量计费两种。通过这两种节点，可以迅速知道当前集群是否处于扩容状态。我们发现，按量节点10小时相当于包年包月1天的时间。所以按量节点我们比较关注。如果按量节点运行时间超过8小时，我们会考虑是否需要增加包年包月节点来优化成本。

为了实现集群资源合理分配，通常会通过设置 Requests 参数来进行调整。如果集群的使用率接近阈值，在超出时则需要考虑扩容；反之，则可能存在多余的包年包月套餐数量，还有可能因为应用下线或经过调优而需要相应减少套餐的数量。此外，可进行 Pod 数量和规格的预留数量的管理。

资源统计 - 应用

在大屏下方的应用排行信息中，包括应用副本排行、资源用量排行和成本排行。当鼠标移悬停到界面上，会显示当前应用的使用费用情况。这三块可以帮助我们快速定位热点应用、可能出现故障的应用及需要进行调优的应用。通过这些最终反推业务部门做性能调优和成本压缩。
当然，财务每个月会通过费用管理平台与运维人员核对，以了解资源利用率为何下降、成本为何上升或下降等情况。

节点伸缩

在早期我们只有一个维度，即当 Pod 出现 Pending 事件后会扩容一个节点。而现在，我们发现仅仅依靠 Pending 是相对滞后的方式。因此，我们加入了一个新的维度——集群资源预留。一开始，我们预留了大约35%到40%的资源，但由于之后的成本问题，将其压缩至 15%-20%，这是经过长期压测得出来的结论。

后来发现，集群里预留的资源碎片过多。如果每个节点都预留了2C4G资源，那么整个集群的预留量可能会达到上千核。这时如果想要发布4C的 Pod 实例，它将无法正常创建。

基于此，我们加入了常用的规格预留，例如2C4G、8C16G等规格。以8C16G为例，集群中至少有10个实例能够正常创建。在经过虎扑K8S生产环境三年的投入后，我们的节点扩缩容已经达到20万次。

Pod、云主机伸缩

我们通过以下这几个维度来判断 Pod、云主机是否需要扩缩容。

常见的维度：

  • CPU

  • 内存

跟业务耦合：

  • QPS数

  • JVM线程数

分为实时和预测指标。在预测指标方面，我们会通过前10分钟的指标数据走势来预测后10分钟的指标走势。通过预测值，我们能够在很多情况下提前预测流量洪峰是否来袭，以便及时采取措施自动扩容。

Pod、云主机伸缩还有审计日志、副本明细、黑名单和阈值类型等等。其中，黑名单可以做到几个方向。首先，应用是否只允许扩容而不允许缩容，或者两者都禁止；在刚才的指标中，可以阻止它不使用内存、QPS等等；对于实时预测也可以分别做黑名单。

阈值类型一种基于百分比，另一种是基于固定数量。有些应用实例数量常备比较少，扩容的时候不能按照20%、30%的比例去扩，扩容时候第一时间至少以10台的标准来扩，以满足这类需求。

另外还提供了API，以便业务自身的特殊性需要自行控制 Pod 副本数量时使用。

场景调度

对于某些特定场景，如即将开始比赛，我们会预设一些策略以保证系统正常运行。比如NBA 开赛前 10 分钟，我们可能需要开启 NBA 场景的第一阶段，因为此时运维人员可能还没有上班，需要避免系统被比赛流量打垮。

当运维人员到达后，比赛可能已经开始。此时，运维人员会比较关注全局流量，如果出现异常或猜测即将有流量洪峰的情况，可以进行手动扩容。这样就可以提前将资源分配好，以应对即将到来的高峰期。

我们将这些场景分为活动和场景，并根据不同的活动和场景来实现不同的应用扩容和实例数量。对于每个活动，我们还会将其分为几个阶段。这些场景和阶段都是通过我们之前自己开发的流量录制压测平台得出的。

我们在高峰期平均每周进行 1-2 次压测，通过真实的线上流量进行测试，最终得出 NBA 比赛需要扩容哪些应用以及每个阶段需要放多少实例数量等信息。

其他伸缩

其他伸缩方面，我们还上线了一个 Alpha 版，主要对 MySQL/Redis 做配置伸缩，Redis 主要基于内存和分片数。MySQL 主要是CPU/内存/磁盘用量/连接数。通过这次 Alphas 发版后，可以猜想以后 Flex 平台不只是云主机/Pod的扩容，可能是全场景、全功能的扩容。

三、问题与调优

虽然 Flex 解决了扩缩容问题，但单纯的反应快并不足以解决问题。由于 Flex 要调用底层的 K8S 和云主机，如果下层运行慢，也可能无法达到预期效果。为了解决这个问题，我们做了大量的优化。现在，我们可以在 1 分钟之内将节点和 Pod 全部准备到位。

Node 加入集群缓慢

我们遇到的第一个问题是Node节点加入集群缓慢，一开始阿里云差不多2分钟加入一个节点，这个速度是我们没办法忍受的，后来研究了阿里云节点加入过程，发现是脚本，针对脚本做了调优，最终将节点join到开发集群时间，从2分钟降到最快10秒。

另外是节点异步添加，最高规格是50个节点批量创建，全部成功以后再加。后来我们发现有些主机创建快，有些创建慢，有些也会失败，谁先成功谁先 join，这样我们可以异步加入集群。

Pod 调度缓慢

在实践中，我们也遇到了阿里云的一些问题，刚进生产集群时，有些应用反应延迟高、CPU负载也不均衡，后来阿里云推出了 arms 进行链路分析。一次偶然的机会，我们创建200个Pod花了20秒左右，经过一系列排查以后，发现是 arms-pilot 组件的问题，移除之后，最终200个Pod 在1秒内就可以创建出来。

大家非常喜欢K8S的一些特性，比如 daemonset，它有好处也有坏处。我们扩容的时候是节点与 Pod 基本同时进行。并行后 daemonset pod 的调度、pull 也是一个问题。后面大量减少 daemonset 部署，把一些能集成的通过预埋到节点的方式去做。
另外，也增加了 Scale 步骤。早前 flex 通过patch hpa的 min达到扩容目的，后期在patch 的基础上增加 scale 步骤，减少HPA控制器的反应时间。

镜像拉取缓慢

镜像拉取缓慢问题。首先，我们要遵循 Docker 的最佳实践，统一基础镜像。分为四个层次：

  • 基础层：延续虎扑的传统用例，生成 CentOS 的基础镜像

  • 语言层：OpenJDK/Golang/Python

  • 中间层：比如 Python 等等，在构建过程中会拉取很多中间的包，这些中间包每次构建，一个是比较慢，二是时间长了会有些差异。我们对这些应用做了中间层镜像。

  • 业务层：在前面三层的基础上增加业务代码和 requestment 再次 build，pull 的时候基本只会 pull 业务层代码。

我们也实现了镜像预埋，早期采用了阿里的 Dragonfly 和 Uber Kraken，这种基于 P2P 的镜像分发技术，对于我们这种短时扩容 node 和 pod 场景不是特别理想，后来自己写了一个 NodeImage 插件，定时对核心应用镜像和基础设施设置镜像进行 pull，并清理早前的 Image。将镜像预埋到节点后，再做成云主机的节点镜像，后期就通过这个镜像来开设节点。

同时，Harbor 仓库也增加了 Proxy 功能，提升了扩容的时候并发 pull Image 的带宽。

Pod 启动缓慢

针对 Pod 启动缓慢，我们做了三个策略。

  1. Agent 懒加载，不影响应用类启动。
  2. 调整 HealthCheck，延迟 Liveness 检查，提前 Readiness 检查，这样可以让应用尽快启动并接受流量。
  3. postStart、preStop 核心功能与日志移到外部程序。直接发送信号给外部程序，由外部程序统一处理。


Master 性能

我们也分析了 Master 性能，大量扩缩容的时候，Master 节点应该是 32C64G，正常使用率也就 20% 以下。但是遇到弹性扩缩容场景的时候，CPU会瞬间达到 100%，内存直接爆掉。

通过火焰图我们分析了 Master 的性能，本来以为是策略不对，最终发现因为大量json对象的解编码造成资源开销，现在在赛期之前会对 Master 进行扩容，扩到 64C/128G，甚至是64C/256G，赛期结束之后，再把 Master 还原。这样基本都能在成本和弹性、稳定性之间做权衡。
