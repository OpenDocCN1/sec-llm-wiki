为什么叫披荆斩棘？

追溯到一开始探索的2018年，容器云技术欣欣向荣，各种配套技术都很成熟，但在我们下定决心要引进和转型时，在落地过程中却一次次陷入了困境。
首先要自力更生，当时我们没有经验、投资，也没有资深技术人员，从架构/设计/选型/落地，各个环节都需要自己摸索，整个过程非常考验心态。
我们用的是全开源技术，开源的特点之一是更迭十分频繁，这就要求有相应的技术储备；二是容器云建设存在技术门槛，你要考虑它是否稳定和可靠，监控体系建设等等；除了技术门禁，还有使用门禁，我们的容器云虽然是私有云，但用户大部分是厂商开发人员，水平参差不齐，这要求平台用起来要足够简单，不然可能用得不好，新技术可能会成为瓶颈，起到副作用。带着这些问题，我们开启了披荆斩棘的容器云建设之路。

从0到1建设容器云

介绍一下广东移动从0到1的容器云建设之路，以及在这个过程当中遇到哪些问题，是怎么解决的。

2017年-2018年我们刚开始接触容器云，觉得这个东西挺好用，搭建一个小型的集群，选择一个小项目开始试用。DevOps 平台上线后和容器云紧密结合，所以这会就利用机会把容器云一起上线。

但那时候集群比较简单，各种配套手段比较有限。2019年主要做的是运维经验积累，还有完善配套手段。到了2020年，重点变成容器云的推广，让更多的系统把业务转移到容器云上，对集群的能力进行增强，包括版本升级、扩容、架构优化、配置优化和可用性增强，最后是新技术的探索和落地。

CaaS初代上线

初代版本上线之时，docker+K8s 这种方案已经非常成熟，我们参照文档搭建了高可用 K8S 集群，那会我们手头硬件资源不多，所以就把 ETCD 以堆叠的形式部署在控制面上。好处是节省资源，缺点是集群高可用级别可能会降低，因为 ETCD 写入数据要求超过半数节点表决通过，三个控制面节点只能容纳一个节点发生故障。
官网还建议高可用控制集群要有一个统一的服务入口对外提供服务，我们使用 Nginx + Keeplived 方案搭建高可用负载均衡器，来代理 APIServer 的请求流量。
在容器网络实现上，主要考虑对 IPv6、网络策略的支持，选择 Calico 来实现。
后来还配套搭建 cephFS 集群，用于容器数据的共享和持久化存储。

集群搭建后，下一步要解决负载服务的暴露问题，试了3种方案后，最终选择了以 NodePort 为主的方案。因为当时域名和 IP池不是我们管理，如果大量使用 Ingress 或 LB 服务会带来管理上的问题。

CaaS监控体系

想要集群稳定，监控体系不可少。我们一开始知道用 Prometheus 来监控 K8s 集群，但是，

要监控什么指标？
指标的来源是什么？
哪些情况应该告警？
这些问题我们都不清楚。

当时就部署了一个 Prometheus，再找各种配置模版，但当时各种配置模版比较混乱，而且网上很多配置模版也不是特别完整，经常要等到问题出来才会发现哪些指标是错&漏了，后来也得益于开源技术快速发展，kube-prometheus 一统天下，所以 K8s 集群的监控就变得简单很多。

现在只要把 kube-prometheus 部署上去，基本上可以解决 80% 的监控场景，而且很多配置自动完成。
这里把 K8s 集群监控分成四个环节，第一环节是指标拉取，主要有四个指标来源，分别是 K8s 组件、node-exporter、kube-state-metrics、ServiceMonitor 和 PodMonitor 自定义指标来源。
第二是可视化监控，拉取到指标后存储到 Prometheus 时间序列数据库，通过 Grafana 对接 Prometheus 查询指标，定义一些可视化的监控面板进行监控。
有了监控后，接下来搞定告警产生。告警产生可以通过项目定义的 Prometheus CRD 定义一些告警规则，告警会发送给 Altermanger，由它进行告警的预处理，把告警通过邮件/短信/Webhook 的方式发送出去。
最后是告警闭环，这里用的是自主开发的智能运维平台，它可以接收 Altermanger 的告警进行闭环管控。

CaaS 指标源和告警列表

在一个监控体系中最重要还是要知道有哪些监控指标，指标来源是什么，哪些情况应该告警，这样在遇到问题才可以从容应对。

这里列举了 K8s 控制面指标来源&指标查看方式，一是各个控制面组件中的指标它可以用来监控组件的性能和健康状态等。二是 Cadvisor，可以用来监控容器的性能及资源使用情况；三是开源组件 kube-state-metrics，它可以用来监控应用的资源和应用的实时状态。最后一个是 node-exporter，可以用来监控主机的性能和资源使用情况。

上面介绍的这些都是 kube-promeheus 体系当中的部分，把 kube-prometheus 部署上去，以上功能都可以实现。

CaaS统一日志管理

监控只能发现问题，并不能避免出现问题。在问题的定位和解决上，要依靠日志的辅助。在检索日志过程中，发现 K8s 日志既有集群级，也有应用级，而且分散在不同的节点/容器/集群中，检索起来效率非常低，非常有必要进行统一管理。
后来参照社区的做法，在所有节点部署 Filebeat 采集各个节点上面的日志，日志主要有四个来源：

  • 服务形式运行的组件日志（docker/kubelet）；

  • APIServer 审计日志（可以审计集群哪个用户在什么时间做了什么操作）;

  • K8s事件（可以记录 K8S 集群在运行中产生的异常事件，事件对问题的定位也有帮助，但 K8S 为了考虑到节省内存，事件只保留最近一个小时，后来找了开源的 kube-event-exporter 组件，用来实现这个事件的持久化存储）；

  • 容器 stdout 和 stderr 日志（这里包括以容器形式运行的各个组件的日志、各个应用输出的日志）；

Filebeat 收集到日志推给中间件进行削峰限流，logstash 消费日志/解析，按照索引存储到 ES 集群，通过 Kibana 进行日志的集中检索/可视化分析，通过这种方式就提高了日志检索的效率，实现集群日志的统一管理。

异地两中心双活

集群运行一段时间后，更多系统把业务转移到容器云上的时候问题来了。集群比社区版本滞后比较多，有些系统需要的能力在新版 K8s 才具备，所以必须要升级 K8S 集群。

升级时候又慌了！

一开始搭建并没有生产系统，我们可以随便搞。但是现在不行了！！

而且我们对 K8s 版本升级也没有经验，要是升级失败，把集群搞崩了，影响就大了。
后来我们开了一个风险应对讨论会，干脆在另一个机房上新建 K8S 集群，让这两个集群同时承载生产的流量，当一个集群发生故障，另一个集群可以无缝衔接。
事不宜迟！在两个集群外建了一个高可用 Nginx 集群用于分发流量。让各个系统做应用架构改造，让应用同时部署到两个集群上。改造主要有两个部分，一是把一些有状态的应用从集群当中脱离出去，保证两个集群的状态是统一的，大部分是数据库/中间件/镜像仓库服务等等。
二是让应用减少对外服务的调用次数，现在两个集群在不同机房中，它在物理上的时延是不可取消的，如果频繁绑定外部服务，时延就会累积影响，最终影响可能会很大。做完双活改造之后，现在 K8s 版本升级的风险也不存在，成功通过走一换一的方式把版本升级上去。

CaaS扩容问题

下一步正式吹响规模化推广的号角，推广到一半又有问题了。

因为集群一开始建时资源比较少，现在资源已经到头了，各节点资源使用率很高，我们需要扩容。扩容本来是很简单的简单，我们第一次给集群增加一个新节点后，发现从外部访问这个节点的服务是正常的，但从这个节点访问它的外部服务是失败的。
原因在于我们内部网络架构有防火墙（一个网络策略），这个网络策略按最小化原则放通的，如果从外部访问新节点上的应用，我们先访问 Master 节点 Nodeport，再通过内网发到新的节点上去，这种情况下这些网络策略我们都放通过了，所以访问就没问题；如果从新节点访问外部服务的时候，K8s 的做法是直接把数据报给源 IP  NAT 成节点IP，因为新节点的 IP 策略还没放通，所以访问失败了。

后来把这个策略加上去就 OK 了，但又引出来新问题，要是每次扩容后都要重新放通一次策略显然是不可能的，因为策略数量这么多，放通一次又要花很多时间，所以我们开始找其他的方法解决这个问题。

一开始找的方法是通过集群内的 Nginx 或 Istio 出口网关把整个集群的出口流量固化到其中几个节点上面，这种方法虽然可以解决问题，但也有一个问题，它配置起来非常麻烦，要是每个系统每个应用模块都要做一个转发配置，这肯定会累死运维人员。

CaaS网络架构优化

后来跳出这个集群，瞄准它的出口防火墙。我们内部网络是这样的，集群的节点用的是内网的 IP，经过出口防火墙之后，源 IP 会换成网管 IP（另一个域），再访问一个外部服务。我们可以在出口防火墙上改一下策略，把 SNAT 改成 SPAT，这样整个集群所有数据包经过一个防火墙之后，它的源 IP 地址就会换成几个固定 IP 地址，而且这种方法增加新节点之后配置也很方便，直接改防火墙 ACL 策略组就行。

CaaS跨集群服务发现

我们建了两个业务双活集群，运行一段时间后发现虽然解决了问题，但又引进一个新问题 —— 异地故障转移（见图）。当集群1服务A发生故障或整个集群1发生故障，外置 Nginx 可以感知到，自动把流量切换到集群2（这种情况是正常的）。但是现在大部分应用基于微服务架构，要是集群1的服务B发生故障的时候，Nginx 无法感知到故障，还会继续将流量转发到集群1，这样一来业务就异常了。

我们想达到的效果是像下面这幅图，当集群1的服务B发生故障时，服务A也可以感知到故障，把流量转移到集群2服务B当中，现在这两个集群是一个整体，它们可以跨集群进行服务发现，也可以直接通过服务的名称进行访问。

那段时间刚好在做 Istio 探索落地，发现 Istio 多集群模式可以解决。

在多集群模式下，Istio 核心服务会同时向两个集群的 APIServer 查询服务&配置信息，下发到服务 A 的 Sidecar 容器中，当服务 A 访问服务 B，它可以先判断当前集群中有没有服务 B 健康的 Endpoint，有的话优先访问本集群，没有就通过另一个集群的 Istio 东西向网关把流量转移到另一个集群的服务 B 中。

也就是现在两个集群的服务在同一服务网格中，可以进行跨集群的服务发现，也可以通过服务名直接访问，而且配置起来也不难，直接给要访问的服务创建目标规则，定义好异地故障转移的方式就可以。

不断优化接入体验

关于容器云的建设阶段到这里告一段落，接下来想要推广容器云，改善用户使用体验，如果体验不好，可能会变成一个制造问题的平台。

CaaS接入现状

截至目前，广东移动O域的主要生产系统基本上已经接入容器云平台，还有不少系统已经完成100%的容器化改造。
这几年在应用体验的优化上主要做了两件事：
  • 简化应用的发布和管理方法，快速上云
  • 完善各种配套手段，让应用上云之后可以稳定可靠运行

自动CI/CD流水线

为了让应用快速上云，我们将 DevOps 平台和容器云平台进行打通，在 DevOps 平台上传代码后，端到端操作可以自动完成，最终应用可以自动化部署到容器云上。而且这个流水线可以给不同应用/不同环境设置一个开关，这样可以灵活控制部署范围。

应用编排

虽然应用的部署是一键完成，但应用的编排有优化的空间。
一开始是让用户提供 K8s 原生的 Yaml 文件给我们，但用了一段时间发现这种方式不可行。
因为一个系统有比较多的应用模块，每个应用模块中还有比较多的功能配置，每个功能配置又有比较多的功能特性。
这样用起来效率很低，而且对用户的水平要求又高。
用户觉得烦，我们更烦！

我们用 charts 包对应用进行封装，帮用户写好应用的基本部署框架，用户再把编排文件给到我们，最后用 HELM 部署应用。

这种方法可以解决大部分问题，有一个问题就是用户编排文件是以 Yaml 文件提供，有些开发商水平参差不齐容易写错（Yaml文件无执行/校验功能），我们进一步优化，开发一个界面提供可视化编排，在后台也基于 K8s 的 Go 客户端开发了一个服务，实现了应用的发布和管理。

应用上云

首先用户在一个流水线的编排页面做好流水线编排，其中包括 K8s 应用的配置，做完编排之后可以一键触发流水线，把应用自动部署到容器云上。最后转到容器应用管理平台上管理应用生命周期，这个平台以应用为中心，把应用关联的资源都显示出来，这样也比较符合用户的使用习惯。

业务高可用

应用上云之后，接下来关心的事情是应用能不能在容器云上稳定运行，我们也是基于 K8s 和 Istio 的原生能力提供四个级别的业务高可用。
  • 一是容器级的健康检查机制，K8s 可以给容器设置探针，当存活探针检查失败时，它会自动重启容器，就绪探针检查失败，就会屏蔽掉 Pod，让流量不要转发给这个 Pod；
  • 二是应用级多副本冗余设置，这样可以保证其中一个副本发生故障时不会影响业务；
  • 但即使有多个副本，在业务高峰期有可能因为资源紧缺而发生故障，我们也开启了 K8s 的 HPA 和 VPA 功能，实现应用动态伸缩；
  • 最后是地域级的业务高可用能力，这是在整个集群&服务发生故障的时候，可以实现异地故障转移。

HPA

HPA 主要针对无状态的应用开启，无状态应用可以创建多个副本，所以可以用 HPA 伸缩副本数量，它主要先调用 metric & custom.metrics 这两个 API 查询 Pod 指标，查询根据情况去伸缩副本的数量。

在使用过程中有比较深的感触，在它的扩缩容指标上建议用 HPA V2 的自定义指标（不要直接用资源类指标），一来自定义指标比较灵活，可以对接 Prometheus，用各种自定义指标扩缩容（比如 limit 资源使用率、QPS等）；二来当你用了 HPA 资源类指标，计算资源使用率时分母是 request 资源，但 K8s 可以使用的最大资源是 limit 资源，导致业务闲时扩容。

K8s 的算法对扩容很激进（缩容保守），它设了多个限制：冷却窗口/副本向上取整机制，最终这些 Pod 很难缩容，一直占用资源，导致集群资源利用率低。

VPA

对于有状态的应用，一般情况下只能运行一个副本，这时候你不能伸缩副本的数量，只能伸缩副本的资源，这是 VPA 的功能。
首先会调用 metric API 查询 Pod 资源历史使用，Recommender 组件生成 Pod 资源建议的设置，Updater 组件监控这个资源的设置，和 Pod 实际资源做对比，如果它们的资源相差比较大，它会驱逐这个 Pod 重新创建，在新创建会经过 K8s 的准入控制器，把资源配置替换成刚才生成的 VPA 资源建议值，实现 Pod 的资源扩缩容。
听下来会发现资源扩缩容不能热更新，这个过程需要驱逐 Pod 重新创建，而且这些应用有状态的应用（一般情况下只有一个副本），所以很危险。如果介意请用 Off 更新模式，只会生产资源建议配置，不会重启容器。如果需要热更新，可以自己扩展实现，直接到对应节点上修改这个容器的 cgroup 设置，更新资源设置而不重启容器。

地域故障转移

最后是地域级业务高可用能力，当集群 1 服务 B 发生故障的时候，由于开启了 Istio 多集群模式，所以服务 A 可以发现集群 2 的服务 B，把流量转移到集群 2 中。当整个集群 1 发生故障或者集群 1 服务 A 发生故障时，Nginx 会感知到故障，把流量自动切换到集群 2 中，业务也不会受影响。

应用运行监控

虽然有了高可用手段，但也并不代表万无一失，还是一样要做好监控，监控直接复用 Kube-prometheus 监控体系。如果开启 Istio 代理，顺便配置 ServiceMonitor，收集 Istio 代理的流量指标。应用指标有4个：

  • kube-state-metric：应用定义与资源状态；

  • cAdvisor模块：应用容器的性能与实时资源使用情况；

  • istio sidecar容器：代理的流量指标，可用于计算经典的黄金调用指标；

  • ServiceMonitor、PodMonitor：自定义指标来源；

应用日志统一管理

对于应用来说，监控重要，日志分析也很重要。应用日志和集群日志一样，存在日志分散、检索效率低。我们复用了集群日志统一管理体系，让各个用户把应用的日志以固定的格式输出到容器 stdout 里，docker 自动把 stdout 日志持久化到宿主机目录下，用 Filebeat 收集日志，推送 ES 解析、存储，从而实现应用日志的统一管理。

“欢快”的采坑之旅

最后我想补充一些常见的问题以及解决思路，在容器云建设过程中，可能会遇到相同的问题，也希望对大家提供帮助。

K8s升级注意

升级一直是运维头疼的问题，特别对开源产品，功能不是自己做的，很容易遇到意外，这几年我们累计升级了十多个 K8s 版本，正常的时候很正常，但不正常的时候特别不正常。

总结起来遇到比较多的问题主要有以下几个方面：
  • 一是在升级过程中，就算不驱逐容器，也会自动重启，因为升级到新版本之后，Pod 发生改变就会重启容器，在重启过程中可能会影响业务，但是因为有两个集群，我们升级前可以把流量切换到另一个集群，所以也不会有影响；
  • 二是不能跨多个大版本升级；
  • 三是升级前检查各个API使用的资源，看一下它们在新版本当中会不会被移除，如果会的话要提前做好迁移，否则升级后不能通过 APIServer 去操作，就只能通过ETCD修改，比较麻烦，但是现在已经有很多开源实现这个功能，例如Kubent直接下载使用就行了；
  • 四是关注第三方软件与 K8s 版本是否兼容，比如Traefik、kube-prometheus等；
  • 五是V1.24版本之后，K8s 正式移除了 Dockershim 模块，需要用 CRI-Dockerd 替代 Dockershim，或者用 Docker 迁移至其他容器运行时；

calico模式选择

集群是使用 Calico 实现容器网络，Calico 默认使用 IPIP 封装模式，当时为了提高数据转发效率改成 BGP 模式，数据包不用封装（效率确实高了）。
一开始用起来也没什么问题，直到有一天，集群扩容新增一个节点，新节点使用的IP子网跟之前节点不一样，问题就来了，新节点上的 Pod 全部访问不了。
后来定位后找路由表，发现在 BGP 模式下，Calico 生成的路由不正常，下一跳IP不是目的节点的IP，而是网关的IP（跨子网）。数据包到了网关后（没有封装），访问还是 Pod 的 IP，路由器上没有 Pod 的路由，数据包选择丢弃，导致访问失败。
正确的做法是选用 IPIP CrossSubnet 模式，可以动态地检测主机上的IP子网，如果主机跨子网，会自动启用IPIP封装（穿透子网），如果没跨子网，会继续使用 BGP 模式，提高转化效率。

还有一句题外话，现在很多企业内部也在做 IPV6 改造，Calico 也支持，但 IPv6 的封装上只支持 vxLAN（不支持IPIP），而且需要 3.23 及以上版本才支持，设置 IPv6POOL vxLAN 的封装模式为 CrossSubnet。

K8s与firewalld管理iptables引发冲突

很多企业内部可能要求对主机监管，要求开启 firewalld 服务。但是实践过程中发现 firewalld 很容易与 kube-policy 冲突。

有一次重启 firewalld 服务后，发现集群 NodePort、HostPort、HostNetwork 暴露方式访问不通，后来定位发现 firewalld 服务重启后会把 iptables 中 CNI 插件写入的 DNAT 规则删除，还会在 INPUT/FORWARD 链中写入默认拒绝所有规则。

这些规则组合作用下导致这些端口访问不通，所以有条件的话，建议关闭 firewalld 服务，使用管理防火墙，或者用 calico 的网络策略。

Istio多集群常见问题

开启多集群模式后，每个 Sidecar 容器要处理所有集群的服务&配置信息，规模翻倍势必会造成占用的 CPU/MEM 资源&处理的时延增加，可能会对业务造成影响。

Istio 官网提供一种解决方案，给工作负载创建 Sidecar 资源，在里面定义 Pod 需要访问的服务名称，这样后 Istio 只会下发这些服务信息给容器（不会全量下发），规模小了。还可以在 Istio pilot 中启动网关服务过滤开关，启用后 Istio 也只会下发需要的服务信息给各个网关（不会全量下发）。
但这个功能毕竟是手动配置，需要一定工作量，也容器错漏，所以建议服务上了规模后再使用。至于如何定义上了规模，可以通过sidecar容器的资源使用指标来反映。

在 Istio 多集群搭建模式下，由于跨集群的通信会用到 mTLS 加密，各个集群会互相验证证书，必须保证根证书是互信的。

Pod 不管有没有关联端口，都要创建 svc 并关联起来，Pod 不会算在服务网格中，不会感知到地域信息，异地的故障转移会失效。
