# DevOps 落地进行时，中国工商银行代码质量提升的6个实践

作者：中国工商银行软件开发中心珠海开发四部

本文介绍中国工商银行软件开发中心某项目组如何通过单元测试、代码扫描、变异测试、代码助手等手段提升入库代码质量，为快速研发、快速上线提供可能。

按业界定义，研发运营一体化（DevOps）是“研发（Development）”和“运营（Operations）”的组合缩写，是一组过程、方法与系统的统称。DevOps 的目标是提高科技团队对业务的响应力。

![](../Images/e3ee067c573cf5e4efcc57150200c67c.png)

  

从上图可以看出，在需求明确的情况下，提高业务响应力的关键是缩短测试和版本制作、部署所需时间。中国工商银行软件开发中心自2009年开启构建部署自动化的工具建设之路，时至今日，DevOps 工具链已经趋于成熟，版本制作、部署的自动化水平与效率提升明显。

超高速公路已经修好，限速600公里每小时。关键是：**你的车敢以这个速度上路吗？**因此，在 DevOps 成熟度提升的深水区，提升测试效能已成为重中之重。

Bug发现的越晚，需要付出的时间和经济成本越高，这已成为业界共识。在开发阶段尽可能排除问题是快速迭代、快速发布的基础。项目组开展单元测试增效、代码规范扫描等实践已近3年，取得一定实效，分享一些朴实无华的经验。

#### 1、以单元测试驱动开发（UTDD）代替单元测试（UT）

按传统做法，UT在代码编写完成后实施，设计过程相对弱化，系统代码可以运行的情况下，开发人员并不能即刻感受到UT代码的后期守护作用，容易理解为不产生实际效用的多余工作，从而产生抵触情绪。因此传统UT模式往往流于形式，难以对产出的代码质量产生实质影响，且代码返工次数依赖个人水平，功能完备性与可测性难以保证。

UTDD倡导“单元测试案例设计先于产品代码编写”，编写测试案例就是一个系统设计并实现的过程，同时UTDD流程天然倒逼开发人员思考产品代码的完整性和可测试性。

单元测试同样需要做案例设计，一个重要的问题是明确“什么是单元？”。按官方定义：单元测试（unit testing）是指对软件中的最小可测试单元进行检查和验证。如果完全按字面意思，最小可测试单元是单个方法（或函数）。按此推论，UTDD需要在案例设计阶段，提前明确所有方法（包括方法名、IO类型，处理逻辑），然后才能在此基础上设计案例。项目组实践后认识到这种方法导致程序设计过重，实际难以操作，也不符合UTDD倡导的“先实现功能，再重构代码结构”的精神（最终方法不是提前设计，而是在编码过程中重构出来的）。另外一种思路是完全以系统功能入口作为UTDD案例设计对象。这种方式优点是案例能直接体现业务需求。缺点是系统实现层次比较丰富的时候，难以精准测试，逻辑过多也导致mock复杂，单测案例编写复杂。同时粒度过大，几乎等同于自动化功能测试，不适用单元测试。最终我们采取的是根据代码结构，按系统分层、分模块进行UTDD案例设计。例如Spring框架下，根据Control/Service/Dao层功能定位，设想各个处理场景并分别整理单测案例清单。后续所有功能开发和测试代码编写以此为准。

#### 2、实施单元测试案例结对审核机制

为确保单元测试案例设计的完备性，项目组引入了功能测试人员结对审核机制。开发人员将自己整理的单测案例清单发给功能测试人员检查，提升案例设计完整性。同时，在项目组内达成共识：单元测试阶段的案例设计，也要从业务处理逻辑的角度进行描述。测试人员主要检查业务逻辑的完整性。

比如：不能直接描述某个方法输入1，返回2。应该描述为：查询范围为“本地区”（qryRang=1）并且数据库中本地区有2条记录时，返回记录总数2。

#### 3、实现单元测试初始代码自动生成，减轻单测编码工作量

开发人员使用统一的单元测试案例设计excel模板，填写测试场景、外部依赖，单元测试案例（英文）名称等信息。案例设计完成后，通过模板中简单的excel宏工具，根据测试案例清单直接生成单元测试起始代码，从而减轻编码量，有助于开发人员将注意力集中在案例设计的完备性和规范性上，便于结对审核人员查看。

#### 4、执行变异测试检测，确保单元测试的完备性

变异测试（Mutataion Testing）的思路是：测试工具修改已有系统代码（包括修改返回值，修改代码中的逻辑判断等），然后运行单元测试案例，如果单元测试案例仍显示测试通过，说明案例设计或断言并不完善。根据变异测试结果，开发人员可以在编码完成后、代码提交前再次检查和完善单元测试案例设计。

#### 5、实施代码规范扫描与门禁控制

单元测试可以保证代码的逻辑正确，代码的规范性则通过代码规范扫描来实现。依托中国工商银行代码规范扫描工具和门禁系统，开发人员在编码阶段可通过本地IDE实时扫描，发现规范性问题并获取修正方法；在代码提交阶段，通过 DevOps 流水线扫描和门禁控制系统阻止风险代码入库。

同时，门禁系统也会检测待提交程序的单元测试覆盖率、变异测试检查结果等信息，对于不满足最低指标的代码无法入库，实现了代码质量硬控制。

#### 6、建立模板代码共享机制

新增功能时，开发人员往往需要参考其他功能作为样例代码。但如果被参考的代码本身不够规范或存在潜在缺陷，往往导致缺陷扩散，降低系统整体质量。

为解决该问题，项目组充分利用中国工商银行代码助手工具，将典型业务代码作为模板上传至代码助手平台。开发人员编码时，在编码IDE中通过关键字灵活查询，找到需要的样例代码并直接引入，确保了新开发功能的规范性，同时提升了开发效率。

做好编码阶段的质量守护是一个长期的过程，需要我们时刻关注编码效能，发现改进点，及时提升。以上是我们在实践中的经验分享，欢迎小伙伴拍砖。
