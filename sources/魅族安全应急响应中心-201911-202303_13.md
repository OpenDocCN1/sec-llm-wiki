# 容器终端系统的威胁分析

*注：文中讨论的容器技术是指底层为Linux namespace+cgroups基础技术狭义相关;容器终端系统或容器系统是指基于此技术或包含此技术的广义相关系统*

  

**前言**

  

谈起容器，常联想到云原生、docker、k8s和微服务等互联网相关的场景、技术、产品和服务。容器技术是基于Linux操作系统级的隔离和分层，具有轻量化、虚拟化、原生化和一定程度安全性，所以众多企业基于此来构造产品和服务。容器技术不断发展，已广泛应用于各行各业，除了云计算，也在泛终端场景应用和发展，包含手机系统、车机系统、终端安全产品等。

  

云计算环境中的容器安全是一个非常庞大的话题和体系，行业也有较多研究，常见容器安全问题是容器逃逸。云相关的容器技术发展相对成熟，组件、工具、平台、产品和服务也在持续伴生一些安全问题，容器安全是当前安全行业投入和研究的热门领域。

  

**泛终端系统中的容器安全与云原生容器安全异同：**

  

**1.****底层基础技术一样**，存在同样的安全问题 ，主要在共享宿主机环境和资源，安全问题常来源于隔离 or 不隔离，或隔离的不彻底以及内核漏洞方面。

**2.****云原生容器安全发展较成熟**，复杂度高，体系化。

**3.****生命周期与应用场景不同**。云环境的容器在于弹性和灵活，生命周期短，而终端系统中的容器生命周期一般是常驻型。

**4.****技术栈和架构差异较大**，在构造完整商业产品中遇到的安全威胁有较大的差异。泛终端系统的OS常见的底层采用的是Linux、QNX和Android，系统架构一般表现为单个或组合形式(手机终端OS常见的是Linux+Android,车载OS常见的是Linux、Linux+QNX、QNX+Android）。

**5.****容器终端系统在某些场景是共享型**，如终端设备的硬件条件和性能、存储限制; 一些强依赖硬件而且需要独占的服务如音频、显示等;还有一些是产品层面设计所需，多个容器间是共享同一个服务及效果。

**6.**容器终端系统功能复杂繁多，系统层面的实现方案较多，厂商根据不同技术水平实现，**没有统一标准**，容易在使能安全隔离特性时有所疏忽，从而导致安全问题。

  

...

  

**所以，以Android系统为例，在Linux的底座之上，容器基础技术与Android或自研feature碰撞，在融合和设计的时候，存在不一样的安全风险，主要的威胁模型也存在较大的差异。本文主要从这方面并结合容器运行时安全角度挑选几个关键的场景进行分析与探索学习。**

  

  

**容器与虚拟化**

  

先来谈一下容器与虚拟化这两个概念及关系。

  

从技术角度来看，虚拟化像是一种技术泛称和实现目标，包括硬件虚拟化与软件虚拟化，容器更偏向具体的实现模型形式和综合完整性的技术体系。

  

以下引用《云原生安全：攻防实践与体系构建》中的一段描述及图1来说明其关系：

  

*虚拟化（Virtualization）和容器（Container）都是系统虚拟化的实现技术，可实现系统资源的“一虚多”共享。容器技术可以理解成一种“轻量的虚拟化”方式，此处的“轻量”主要是相比于虚拟化技术而言的。例如，虚拟化通常在Hypervisor层实现对硬件资源的虚拟化，Hypervisor为虚拟机提供了虚拟的运行平台，管理虚拟机的操作系统的运行，每个虚拟机都有自己的操作系统、系统库以及应用。而容器并没有Hypervisor层，每个容器是与主机共享硬件资源及操作系统。容器技术在操作系统层面实现了对计算机系统资源的虚拟化，在操作系统中，通过对CPU、内存和文件系统等资源的隔离、划分和控制，实现进程之间透明的资源使用。图1展示了虚拟机和容器在实现架构上的区别。*

**进程树**

  

从哪里开始？

  

容器运行时，负责容器的创建、运行和销毁的整个生命周期的管理工作。常见的容器运行时包括 runc、lxc、containerd、rkt、cri-o 等。这些不同的容器运行时和引擎代表着这方面技术在不同背景下的发展和成熟，也应用到不同场景中。

  

容器运行时规范（runtime-spec）是OCI(Open Container Initiative)标准中最重要部分之一。

  

容器运行时有标准的步骤和操作，这里只关心容器创建和运行、设置namespaces和cgroups等核心特性部分。  

  

在终端系统中引入容器,常见的需求表现是双系统或多系统，即在容器系统中一个宿主机伴随多个容器空间。在开始设计时最关键的一步便是考虑隔离的第一刀切在哪个地方。这通常与OS上层定义相关。这里以Android系统为例，Linux+Android的运行时环境，常见的Linux系统的运行时环境为单进程树结构，而Android系统我们熟悉的关键进程包括init，system\_server，zygote和App进程，并且相互间存在父子关系。在Android系统中引入容器特性并运行多个容器系统，主要考虑是从这几个关键进程开始。

**IPC/Binder**

  

Linux IPC Namespace不含Binder的隔离。

  

IPC（Inter-Process Communication，进程间通信）。进程间通信是指两个进程的数据之间产生交互。IPC是操作系统中数据流转依赖的基础，而交互的产生也伴随着安全问题，IPC通信安全是操作系统安全的基础之一。

  

在Linux 中有以下多种IPC通信机制：

*(1) 半双工Unix管道（PIPE)*

*(2) 命名管道(FIFOs)*

*(3) 消息队列(Message queues)*

*(4) 信号量(Semaphore)*

*(5) 共享内存(Share Memory)*

*(6) 套接字（Socket）*

*(7) 信号（Signal）*

*(8) 内存映射（Memory Map）*

  

从以下Linux 内核支持的 Namespaces 种类来看，其中IPC的隔离内容主要针对System V IPC,POSIX message queques,对应到上面多种IPC通信机制是指信号量（Semaphore）、共享内存（Share Memory）和消息队列（Message queues）这三种。

如不同空间相互间核心服务调用及监听。

  

如终端中不同容器之间安全性要求不相同，有的是普通空间，有的是对安全性要求较高的空间。如容器A感染了病毒，病毒软件通过技术方式影响到安全空间的安全性或任一空间通过漏洞方式获得提权都会影响到其它空间。

 

**提高安全性的一些方案**

禁止跨空间服务调用，通过命名空间标识与服务名称两者唯一确定服务，在注册和获取的时候判断并进行隔离返回。这种方案粒度较大，并不能解决某些服务是实际需要共享但又需要保证安全的场景。

  

**SELinux**

  

Linux namespace中不包含SElinux的隔离与虚拟化，容器与宿主共享安全策略与机制。

常见的安全问题是来自于容器与宿主不同的安全需求，如容器空间在安全产品中的安全要求与宿主空间不一样，在共享安全策略的场景下显得风险更高。

  

而在Android系统中，定制的应用进程域的安全策略和机制作为新增feature，在这种共享环境可能也会存在安全风险。

**提高安全性的一些目标和方向**

  

1.从系统调用关系和容器系统运行环境角度考虑，常见的漏洞提权行为都要通过一系列的调用逻辑和流程，而运行在容器系统中的恶意应用通过漏洞提权至root,也必然地需要调用一系列的操作。SELinux作为系统中最基础的安全方案之一，在众多关键调用和逻辑流程中都有安全的检查。

2.粒度需要更细，可以控制到接口层面，如LSM Hook中IPC调用，网络调用，文件操作调用等。

3.需要修改内核空间并保证安全可信，不被篡改或劫持

**UID/ GID**

  

Linux的安全基础是用户的权限模型，如果这部分存在安全问题，基于等于破防了整个系统安全。

  

回到图3进程树模型图，以Android系统为例，system\_server进程(UID分配规则及应用安装逻辑等位于system\_server进程，它是Android系统框架中的系统服务，里面也包括PMS,WMS等核心服务)是相互隔离的。但是容器系统存在非完全隔离的风险，并且存在共享服务的情况，而Android系统中UID是基本的应用安全及权限隔离单位，在某些场景处理不当，这会带来非常严重的安全问题。

**总结：**

  

操作系统安全常从隔离、混淆、控制、监视这几个方面进行设计和保障，容器技术是将隔离思想运用得比较极致的一种方案和特性。

  

本文单从从狭义容器的基础技术与广义的终端系统融合一小视角去探索可能存在的一些攻击面威胁情况及思路。挑选了一些主要的部分并结合项目的实践安全问题来介绍和研究，还有存储和网络等模块未展开。总的来说，终端容器安全的威胁来源包含运行的容器间的隔离是否充分、容器间的通信是否是安全的、容器内的恶意程序是否会影响到主机或者其他容器、容器的资源使用情况是否安全、容器与上层系统组件、服务的融合和定制衍生的安全风险等。

  

云原生的容器安全考虑的是容器环境基础设施的安全、镜像安全、运行时安全和整个容器生态和体系的安全性。也有有众多的防御建设思路和实践是值得借鉴到端侧的。容器沙盒化是行业上对容器安全增强较好的参考，代表有gVisor 和 Kata Containers。
