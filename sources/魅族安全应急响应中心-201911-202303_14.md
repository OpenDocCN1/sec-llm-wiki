## **前言**

Android平台安全设计在Root权限面前是否足够安全？哪些方面存在脆弱性？

  

#### **Android平台安全目标与关键安全功能**

Android操作系统安全目标：

*   保护应用程序和用户数据
    
*   保护系统资源（包括网络）
    
*   提供与系统、其他应用程序和用户的应用程序隔离
    

  

为实现这些目标，Android 提供了以下关键安全功能：

*   通过 Linux 内核在操作系统级别提供强大的安全性
    
*   强制性的应用程序沙箱
    
*   安全的进程间通信
    
*   应用签名
    
*   应用程序定义和用户授予的权限
    
      
    

#### **系统和内核安全**

##### **Linux 安全**

Android平台的基础是 Linux 内核。Linux的安全基础：

*   基于用户的权限模型
    
*   进程隔离
    
*   安全IPC的可扩展机制
    
*   移除内核中不必要且可能不安全的部分的能力
    

  

作为一个多用户操作系统，Linux内核的一个基本安全目标是将用户资源彼此隔离。Linux的安全理念是保护用户资源彼此不受影响：

*   阻止用户A读取用户B的文件
    
*   确保用户A不会耗尽用户B的内存
    
*   确保用户A不会耗尽用户B的CPU资源
    
*   确保用户A不会耗尽用户B的设备（例如，电话、GPS和蓝牙）
    
      
    

##### **应用程序沙箱**

Android 的应用程序安全性由应用程序沙箱强制执行，该沙箱将应用程序彼此隔离并保护应用程序和系统免受恶意应用程序的侵害。

##### **系统分区和安全模式**

系统分区包含 Android 的内核以及操作系统库、应用程序运行时、应用程序框架和应用程序。此分区设置为只读。当用户将设备启动到安全模式时，第三方应用程序可能会由设备所有者手动启动，但默认情况下不会启动。

##### **文件系统权限**

在 类UNIX 操作系统中，文件系统权限确保一个用户不能更改或读取另一个用户的文件。在 Android 的情况下，每个应用程序都作为自己的用户运行。除非开发人员明确与其他应用程序共享文件，否则由一个应用程序创建的文件不能被另一个应用程序读取或更改。

##### **安全增强的 Linux**

Android 使用 Security-Enhanced Linux (SELinux) 来应用访问控制策略并在进程上建立强制访问控制 (mac)。

**还有验证启动、密码库、文件系统加密、密码保护、设备管理等。**

  

## **Root与危害**

  

获得Root提权有什么危害？

  

默认情况下，在 Android 上，只有内核和一小部分核心应用程序以 root 权限运行。Android 不会阻止具有 root 权限的用户或应用程序修改操作系统、内核或任何其他应用程序。通常，root 对所有应用程序和所有应用程序数据具有完全访问权限。更改 Android 设备上的权限以授予对应用程序的 root 访问权限的用户会增加对恶意应用程序和潜在应用程序缺陷的安全风险。

**拥有root权限不仅仅在系统安全设计的原语中取得超级用户的特权，也可以绕过众多的防root的安全机制。**常用加密和可信存储等方式来保护数据免受root用户访问。

  

## **Capabilities 与CAP\_SETUID**

  

为什么需要SafeSetID？

  

Capabilities制是在Linux内核2.2版本之后引入的，参考了IEEE 1003.1e和IEEE1003.2c安全标准, 它的出现是为了对root权限进行更细粒度的控制，实现按需授权。从Capabilities机制关联的操作对象来看，主要分为进程（如cap\_setgid ）、文件（如cap\_chown ）、网络(如cap\_net\_admin）、IPC、  网络、系统、设备、审计和MAC。

常见的capability所允许的操作或行为如下表所示：

> ![](../Images/d034be2eb3e3ae3fa89975042429d6d3.png)

  

CAP\_SETUID属于Linux Capabilities中的一种特权，某个进程若想拥有CAP\_SETUID能力，一般有通过以下方法：

  

1.root权限的进程默认被系统赋予CAP\_SETUID能力  
2.通过系统调用接口动态赋予CAP\_SETUID能力  
3.执行了某个拥有CAP\_SETUID的可执行文件得到CAP\_SETUID能力

  

通过来说，CAP\_SETUID能力是受操作系统管控的，一般从进程创建的时候会拿掉(drop)。  
通过执行可执行文件的方式来获取的方式也是不建议和极少的场景，因为此种方式只要有该可执行文件的执行权限的进程都可以提权，容易管理不当带来系统安全漏洞。

拥有CAP\_SETUID能力特权的进程能切换到其它用户，在Linux系统中这是一种强大的能力，换言之，拥有此能力的进程能够提权到root用户。

  

这是非常危险的，总体来说，**CAP\_SETUID设计初衷是用来进一步细化和限制root权限的，而SafeSetID的出现则是进一步细化和限制CAP\_SETUID的能力。**

## **SafeSetID**

  

SafeSetID有哪些机制可参考用来防御提权漏洞？

  

Linux 5.1内核开始新增SafeSetID安全特性，SafeSetID作为一个LSM module被集成中到Linux中，它主要对setid系列的系统调用进行限制，通过allowlist系统名单的规则与机制控制进程UID/GID的转换能力(对 set up user namespace方面也有限制）。  
换句话说即是细分了Linux中CAP\_SET{U/G}ID的能力，进一步提高系统安全性。

  

**SafeSetID对setid系列的影响：**  
普通进程切换至其它进程用户仍然需要拥有CAP\_SETUID特权的能力，而SafeSetID增加了额外的限制，避免非root进程提权至root用户（uid为0)或创建或进入到其它命名空间(namespace)

##### **SafeSetID在内核提权漏洞防御方面的思考**

SafeSetID的机制有点类似MAC机制，以强制固定的规则控制UID的安全转换，比MAC不同之处在于它可以动态更新策略，并导出文件系统接口，这样可以和用户空间安全程序结合制定一些细化的策略。

Android系统一直在改善和完善安全能力，并且安全体系包罗万象，但系统攻击面也随着系统演进发展并没有缩小，漏洞修复与防御是贯穿整个Android系统架构层面与业务功能的方方面面，**而提权特别是root级别漏洞提权是漏洞攻击过程中最关键的一步，从系统角度来，如何识别漏洞提权行为而阻断，如何监控漏洞提权行为而感知入侵溯源追踪是防御方最关注的事情之一。**

## **漏洞提权的路径**

  

从通用提权路径中提取哪些作为漏洞防御要点？

  

需要总结提权漏洞的提权路径，常见的漏洞类型包括任意内核地址读、写，任意代码执行、UAF、 栈/堆缓冲区溢出等。

  

##### **提权途径路径的共通点：**

主要围绕着task\_struct结构中的cred安全指针内容进行，所有的前提是经过与操作系统一系列的调用和布局取得基址（偏移）或代码执行权限。

  

##### **方法一：通过篡改init\_cred结构提权**

篡改cred & real\_cred指针，将real\_cred和cred指针替换为init\_cred即可提权（任意内核读写这一类漏洞）

  

##### **方法二：通过执行commit\_creds代码提权**

这个函数会分配一个新的cred结构(uid=0, gid=0等)并且把它应用到调用进程中,此时就获得root权限了  
如：commit\_creds（prapare\_kernel\_cred(0));

  

##### **方法三：通过调用setid系列提权**

如setuid(0), setgid(0) ,setresgid(0, 0, 0)  ,setresuid(0, 0, 0)

## **基于行为特征的检测与防护方案**

如何轻量化汲取行业优秀思路至Android终端？

  

漏洞利用过程肯定在系统中留下痕迹，可以预设一些通用的行为作为特征库，并且在一些已知的攻击函数或常用攻击函数中加入HOOK逻辑，可以达到阻断攻击行为和追踪溯源的目的。

这方面可以借鉴云原生安全和主机安全防御体系的一些思路，业界也有非常多成熟或开源的方案(如Elkeid)，因为基座都是Linux系统，这些都可以轻量化地搬至Android终端并使能应用或参考其最核心的技术原理与逻辑，难点可能在于规则的精确运营（或机器学习）。

  

参考主机安全防御及入侵检测，常用的方案也包含基于Linux netlink机制，可以实现进程众多行为的安全审计，包含上述说到漏洞利用常经路径（setid系列），fork创建进程，exec执行文件等，而且对内核没有侵入性，又是原生特性。虽然Linux内核从2.6.15版本已支持此特性，不过在部分手机代码的kernel基本并没有打开，需要配置使能，因为此机制采集的事件较多，也需要进行部分精简和考虑一些性能方面的问题。

  

**当然对于定制系统来说，基于原生的特性在kernel再做一些优化工作，结合上层的产品思路会让整体安全方案跑在手机上比跑在资源丰富的主机上面更优。**

## **基于eBPF的检测与防护方案**

  

eBPF让内核具体有可编程性和观测性，并且具有内核与用户空间的双向编程通讯能力，可谓是系统上面的一把“瑞士jun dao”。这把“瑞士jun dao”本来可以承担深入探测漏洞进程的提权行为或异常行为，但安全行业上面的研究表明，已有恶意软件利用甚至应用到rootkit上面，不但能破解传统的主机防御行为检测体系，也给安全防御带多更高的挑战难度及思考（如基于eBPF的检测与防护方案如何防止基于eBPF的恶意绕过）。

这一类方案主要针对进程的运行时信息、安全指针、权限信息等进行监控，可能需要定制驱动或对内核有一定的侵入性。
