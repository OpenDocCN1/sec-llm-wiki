在之前的分析中，都是针对 CobaltStrike 整体通信流程的，也就忽略了中间的一些细节，其中一些细节对理解整个 CobaltStrike 也是非常重要的

  

  

0x01 基本校验与解析

先取了默认端口

  

![](../Images/497cc17143b631f7946f07e1b56a1ca4.png)

  

接着对 Java 环境及一些参数进行了验证，并校验了 license

  

![](../Images/f8744fe8093e6c7b53237d34a035b899.png)

  

这里重点看一下对于参数的检测，可以看到有校验两个参数是否存在，当你在跑 Controller 的时候，最好也一样将其参数加上，不然有可能会出现一些莫名其妙的问题

  

![](../Images/634b5f3e4b15c750f9e548e341901244.png)

  

对于 IP 等内容的判断就不重点关注了，看一下他在解析 C2Profile 时候的对比，如果有指定的话，会走下面那个流程，直接将地址传入 LoadProfile

  

![](../Images/dde6a618d609dae301ee92d5d07a46ff.png)

  

而在默认情况下，则调用了 LoadDefaultProfile，但它实际还是调用了 LoadProfile，然后直接加载了 resources 中的默认文件

  

![](../Images/70a73576ac657013e25ce06068c21b56.png)

  

之后就到了最关键的初始化环境的地方

  

  

0x02 初始化

先在 C2Profile 中增加了两项内容，license 认证中的水印与当前的路径，具体作用暂时也不清楚

  

![](../Images/2348364432c9fd24d28b57cc915154c0.png)

  

接着初始化 Resources 对象，并传入了 this.calls，它是一个 HashMap，对于后续所有的调用都至关重要

  

![](../Images/dce9400354b117ceac87b7bf51115b68.png)

  

在初始化 Resources 的时候，对两个内容进行了初始化，它们内部都创建了新线程，根据名字也可以明显的看出，ServerBus 是 TeamServer 所有运行内容的通道，所有的调用都是从这里走的，Archiver 属于日志类型的操作了，在调试的时候，时不时出现的 archiver 类型的数据包也就是从这里出来的

  

![](../Images/fee214f2db357562bc04aada55bab7d6.png)

  

在 ServerBus 中，除了将 calls 传入之外，就直接 new 线程了

  

![](../Images/9ad4c7686a300085dcd9cb1fa1805e12.png)

  

整个的逻辑也很明确，与 TeamQueue 等文件的处理方式是类似的，在接收到信息以后，从 calls 中获取到对应的类型，然后调用对应的 call 来完成后续的流程处理

  

![](../Images/f6111323b396d314b3f552979c2f5f8f.png)

  

再来看一下 Archiver 的相关处理，除了后面会 broadcast 信息之外，刚开始的 PersistentData 还是比较重要的

  

![](../Images/c97a065fe69fa7de0598a455508ecf97.png)

  

在中间直接创建了新线程

  

![](../Images/21fff1236005522e7d7a26f3c344d150.png)

  

处理逻辑跟前面也差不多，判断是否有数据，如果有处理

  

![](../Images/782cc61bc07da248d80c129444844d39.png)

  

大致也就猜出来是将数据存储到文件中

  

![](../Images/d1f2a0451f08155abd71de4a29c810e0.png)

  

回到主流程中，接着将 C2Profile、IP、密码等信息也存储到 this.resources 中

  

![](../Images/7f07adfcd6d9ebcbdd06f9c351131a74.png)

  

然后往 this.calls 中存入了几个测试数据

  

![](../Images/d221a15abcd049adebe4ee6960d13151.png)

  

对于这种 Test 的操作，在 CS 中也有很多，还有一个专门用来负责处理断言操作的类

  

![](../Images/ff0b2ecc80fc9dee4de99d0d9fe03288.png)

  

然后往 this.calls 中存入了数据

  

![](../Images/5b3830839f61c838c787492863c60f02.png)

  

这些实际上才是最关键的内容，根据上面 ServerHook 可以看到，在执行的时候，会根据这个类型来决定调用哪个类中的 call，也就决定了最终的处理流程

  

![](../Images/7e838aaee79c4c2392ac85cdf715d68b.png)

  

接下来的一众操作都是这个样子，为后续处理做了相当充足的工作

  

![](../Images/251ebcef95d443524ea03137c8e1b31b.png)

  

而且中间也能够看到很多东西了，发布任务时候的 beacons.task，启动监听的 listeners.go 都是在这里设置的，所以也就是说在 Controller 与 TeamServer 通信时，所传输的 beacons.task 等，最终都是在 ServerHook 中根据之前存储好的类型来最终决定处理流程的

  

![](../Images/a2446f27ae835747dcf44bf890d205fc.png)

  

经过这一波操作，this.calls 已经增加到了 64 个，接着又进行了一堆操作，增加了对数据的处理

  

![](../Images/0c9c891c6f2070b7184771f67c84454e.png)

  

所遍历的就是下面这些内容

  

![](../Images/82b87a99940917bf7cc7d2f32652cbd2.png)

  

然后通过如下的方式来进行了批量的添加，this.calls 最终达到了 106 个

  

![](../Images/a30f7b3cdbc365f22038587284b77de7.png)

  

接下来就是之前分析的与 Controller 进行通信的部分了

  

![](../Images/2ca0bc5f5dcaaf445c5786b477c15ea3.png)

  

  

0x03 启动 Listeners

为了验证前面所提到的流程，这里用启动监听来作为说明

  

![](../Images/bc22792814a7d23b36d457b87ed08a87.png)

  

跟入后可以发现，它在 ServerBus 中增加了一项

  

![](../Images/adb1c253835332ede7a31c36ed517f63.png)

  

所以就直接在 ServerBus 的处理线程中截取到

  

![](../Images/5745891fc301c91e3ae30a4d8237f027.png)

  

取出类型是 Listeners，就直接调用到了 Listeners 中的 call 方法，但是很明显它什么也没干，又用刚才的逻辑调用到了 beacons.start

  

![](../Images/dc89e1adcec7c0fb42f24b2b6cc58388.png)

  

一样通过刚才的逻辑进入相应的处理

  

![](../Images/80f1fd953a34ff152412f08f48c773b8.png)

  

在其中它根据 Listener 初始化了相对应的监听

  

![](../Images/f795c1bc02763dbbe36cb4f8a1144a4e.png)

  

这里用的是 HTTP

  

![](../Images/ed47b2ec763a028b697bdba4bb9102ec.png)

  

接着初始化了 RSA 公私钥

  

![](../Images/d604eec43a1db50f391f013cc59b7cfe.png)

  

如果文件存在的话，就不会再生成了，所以还是自己做一份为妙

  

![](../Images/1e9489693edba168d08fe82f08674a78.png)

  

然后也将这些信息存储到了 BeaconC2 当中

  

![](../Images/02504e5875f5690ea3f81251f607ba28.png)

  

接着就根据刚才初始化到信息启动相应的监听

  

![](../Images/a94b4b7dc3e775c5f63ed04352f5f01a.png)

  

然后将监听类与 Payload 存储到一个 HashMap 当中

  

![](../Images/7e349514e259a6005886a5f75f891d95.png)

  

就完成了监听的启动

  

![](../Images/caf49253f46ec147ff207d302811a936.png)

  

接着又用同样的逻辑调用了 listeners.set\_status，然后将信息存储到 Listeners 的 Map 当中

  

![](../Images/aa39301351fff652e5a2373482677740.png)

  

然后又调用了broadcast，通过 BroadcastWriter 将信息回传到 Controller

  

![](../Images/954e1619295bfbbd390ac49f448289c8.png)

  

这样也就完成了所有的操作
