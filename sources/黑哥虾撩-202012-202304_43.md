2、UMN VS Linux kernel 

首先我要说明下的是，前面我在朋友圈转发一篇文章：https://mp.weixin.qq.com/s/gAI4KswTiKS7DB6vXeNNrQ 因为我e文水平有限的问题，没有认真阅读原paper及相关文章，所以误解了当时UMN的测试提交是用的信任的官方账号去提交，如果按这个提交确实不是那么容易被人接受。随后在张超@THU老师朋友圈晒出了UMN论文当事人的一些说明，及Riatre的提醒并通过确认后实际当时测试提交的代码是新注册的一个人gmail（通过Riatre同学考古了下，找到一个找到一个疑似是当时的 patch 提交的邮件记录：https://lore.kernel.org/lkml/20200809221453.10235-1-jameslouisebond@gmail.com/ 代码跟论文 https://github.com/QiushiWu/QiushiWu.github.io/blob/main/papers/OpenSourceInsecurity.pdf 第九页的UAF case 2是对应的，另外可以留意下gmail地址为jameslouisebond@gmail.com ），也就是完全符合一个“攻击者”身份的模拟，而最后Linux kernel 开发维护者们看到这个论文后对应上UMN，瞬间“恼羞成怒”并迁怒于整个UMN。

实际上“恶意”开发者问题是整个开源社区必须面对的一个问题，这个“恶意”是一个主观色彩的词汇，比如你开发的代码有个“bug”，很难认定开发者是不是主观故意的！实际上攻击者主动融入安全社区在适当的时候适当的代码位置植入适当的“bug”是非常难防范的，当然这个如果要做得到而不发现可能也是要花点时间并对这个项目有足够深入的理解，其实好多年前我就有这个想法但是我对自己代码能力实在是没有啥太大的期望，就不了了之了～～（当然还有比如当年包括我都尝试过，一个漏洞的触发因为代码本身的bug而导致触发不了，就去尝试过提交修复这个bug的经历）

因为考虑到这种要求及“隐蔽战线”的隐忍力要求，所以现在比较流行相对“急功近利”的针对开发者的攻击模式，比如前面PHP的事情 https://news-web.php.net/php.internals/113838

我们回归到UMN VS Linux kernel 的事情上，归根到底是“业务 vs 安全”的问题，在历史上一些观点来看包括liunx本人在内的对待“安全”的态度及观点都不是那么友好及支持的，这个问题未来还会有继续 ...

\-------把攻击者放进威胁模型，而不是安全研究者-------

HardenedLinux 写道

"近日一篇于2021年2月公开的论文"On the Feasibility of Stealthily Introducing Vulnerabilities in Open-Source Software via Hypocrite Commits"和相关针对Linux内核社区故意投递恶意UAF漏洞的试验被内核维护者Greg Kroah-Hartman攻击而进入公共的视野，迫于媒体的压力明尼苏达大学宣布进行调查，Greg和一些内核维护者的指控在一些方面有失偏颇，首先，这是一项非常有趣的研究，真实世界的攻击者不论是否有相关公开的研究都会进行此类攻击和尝试，从这个角度，我们应该感谢明尼苏达大学的研究者。Greg单方面的“决定”封杀明尼苏达大学邮箱的提交和撤回之前所有的代码贡献是过度反应，如果撤回之前代码贡献的原因仅仅是因为此次试验的内容，那内核社区是否应该考虑代码审核的过程过于脆弱。Greg如果有权封杀所有他个人不喜欢的安全研究者，是否意味着Linux内核社区默认赋予他这样的权利，幸运的是，并不是所有人都赞同Greg和媒体的说辞 ,或许此举让Linux内核社区的行为准则成为了笑话。另外，其他自由开源软件社区也同样面临恶意植入的问题，而这些实际的问题大量引入媒体而非专业人士的建议是不明智的，我们应该把攻击者放进威胁模型，而不是安全研究者和明尼苏达大学。"
