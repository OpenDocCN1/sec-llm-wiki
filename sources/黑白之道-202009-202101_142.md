# **0x01 需求产生**

  

某聊天软件有已读回执功能，可以通过查看标记，判断对方是否读了你的消息：

  

![](../Images/db8f0a2010b38adf1b40d7a0940f0778.png)

  

经常出现这样一种情况，联系人发来几条消息，啊T.T，我好想看看他说了什么：

  

![](../Images/46ec9ab99b7c7ad939886d135212a12f.png)

  

  

然后点开看了一下，完蛋，又是借钱的：

  

![](../Images/7afc58d7125bf1bbf6a3d9db5ee1e2b9.png)

  

这个辩解苍白无力~

  

![](../Images/7bfceceffd13fa8d574763c6f6e2280a.png)

  

那么伟大的需求就此诞生:如何偷偷看他消息，而不让他知道我已读了？

  

# **0x02 探究原理**

盲猜原理一定是这样：

  

客户端查看了消息->客户端发送已读回执到服务器->服务器向消息发送者发送已读状态

  

那也就是说，只要我们使用的PC客户端不发送已读回执，服务器就永远不知道我们读了该条消息，对 放也就不会知道我们看过了。

  

一开始想看有没有人造过轮子，于是github上翻了翻，但没什么收获。不过在翻的过程中发现了一个有 意思的项目：dingtalk-interceptor，但该项目删除了，于是就去网上翻了翻，果然找到了相关的文章，针对的是老版的客户端（3.x），该版本就是Electron包装的一层网页，项目实现原理是通过拦截所有包含updateToRead的请求，从而实现永远未读消息的。

  

![](../Images/68858aa4953a8f6dc0f677bc8af9f0af.png)

  

因此我们要寻找的突破口就在这个关键字上：updateToRead

通过不断尝试，发现该聊天软件的核心逻辑都在MainFrame.dll中，因此只针对MainFrame.dll进行搜   索，关键字：updateToRead。

  

先定位到模块中:

  

  

![](../Images/a85b4e2c7dc0af68e55304f0d6a14d2c.png)

  

![](../Images/db2426bf73291d3837a127baa2dca618.png)

  

后在该模块中搜索updateToRead,并全部设置断点

  

发送两条消息并阅读测试，命中断点如下：

  

![](../Images/56ff5910af1ec3a66e0bb1d3f81d9def.png)

  

关闭其他断点，并用另一个号给调试的账号发送消息，并查看：

  

在第一个断点处，消息依然是未读状态

  

在第二个断点处，消息依然是未读状态

  

在第三个断点处，消息依然也是未读状态

  

在断到第四个断点处，消息依然是未读状态，但放过断点，消息就变成了已读：

  

![](../Images/aeae57a3cf9b3f4319802f75fa31063d.png)

![](../Images/a6e4cf4bab2be2d05aef2287c6083430.png)

  

**解决方案有几个**：

  

1. 破坏原有数据包,使其服务器无法正确更新状态

2. 在发送前拦截该数据包，使其不发送

3. 不进入检测消息是否未读状态

  

此处通过调用该接口“/r/IDLMessageStatus/updateToReadV2”向该接口发送请求，来告诉服务器，消息已经被读了。此处可以直接暴力将接口修改，修改成错误的地址，也可以实现看了消息不显示已读。  但直接通过该种方式修改，有两个弊端，

  

1.会向服务器发送一条数据，虽然服务器没能正确处理，但会返回一个异常。

  

2.客户端收到该错误响应后会认为自己与服务器断开连接，会经常认为自己掉线了从而发不出去消息

  

路线1走不通，因此继续寻找突破点，使用ida反编译该模块，查找该接口：

  

![](../Images/9975524529914efd380a74ca722bb5bc.png)

  

![](../Images/8f18733ab2150659ced2a1d08391d593.png)

  

发现该接口是出自sub\_1127B210函数：

  

![](../Images/6032a59b16281d2f047b15a11bbb42b5.png)

  

进入sub\_1127B210内容：

  

![](../Images/1a12f6263bb93074b0e07fae0cf8d33f.png)

  

往上跟踪，发现sub\_110BA580调用了sub\_1127B210

  

![](../Images/5f8be8a4ca044b97ab5bf7afa056499b.png)

  

往上跟踪，发现sub\_107269E0调用了sub\_110BA580

  

![](../Images/df78a54fe790b59c13c1f3c0a1961e06.png)

  

sub\_107269E0函数内容：

  

![](../Images/cef72aaef3bd4a3f61c97bac734d6183.png)

  

其中包含多个接口，作用是向服务器发送一个包含消息id的请求包，从而实现消息已读。

  

此时已经基本了解大概情况，继续用x64dbg调试，在调试过程中发现在执行完sub\_107269E0消息并未直接变成已读，而是继续向上层函数继续返回，直到返回了这样一个函数：

  

  

![](../Images/c2e106d7fd7532002f4c7e9504d6f8d9.png)

  

伪代码：

  

![](../Images/b69be143e3eed3ad0682ce95703dc60c.png)

  

该函数

sub\_10C77E70在if ( v3 )

处存在两个分支，一个分支调用sub\_10C785D0(i, &v4)，

另一个分支即已读分支sub\_10C77210(i)，也就是我们的call所调用的函数。因此，v3是一个关键判断点

v3所对应汇编代码为：jz short loc\_10C77EAC

偏移为：C77298

  

  

![](../Images/7a4c10f115f3636acf17ce5d470d41d4.png)

  

在C77298上下断点，通过修改寄存器zf标志位，使其进入sub\_10C785D0(i, &v4)

  

![](../Images/4815483f37359026c5db9f3d9feac4c2.png)

![](../Images/9d04f422b2352805a93a7a6b89f0f01a.png)

  

修改后发现，后续发送的消息均不显示已读，且不会再进入该判断，因此只要让v3永远=True,即可永不进入sub\_10C77210(i)分支，即修改该处条件跳转为jmp

  

![](../Images/34fb1dccce17f9f9455a727311209742.png)

  

![](../Images/842af2ee2cc11a2b1e9b3c222cda9a83.png)

  

修改后Patch到dll上即可。

  

特征码：

C0 75 33 8D 45 F0 8B CE 50 E8 CE F1 FF FF 80 7D F0 00 8B CE

  

修改后：

C0 EB 33 8D 45 F0 8B CE 50 E8 CE F1 FF FF 80 7D F0 00 8B CE
