# 通过供应链拿到目标后台权限的过程

**0x01 重要说明**

本文中涉及到的所有操作均得到了客户单位的授权，并且在漏洞修复后得以公开。请勿在未授权状态下进行任何形式的渗透测试！！！！  

  

**0x02 漫长的探索**

某天，接到一个任务，要求对某医院的信息系统做一次安全检测，看能否发现问题。经过初步的信息收集后，发现该医院并无官网，只有一个微信公众号提供了预约挂号，缴费等功能，看来只能把突破点放在这个公众号上了。  

  

下图是微信公众号的一些功能：

![](../Images/2ca5f4e080505b677748a6aac7b99269.png)  

当点击这些功能并抓包的时候，令我看到奇怪的是所有的请求都指向了a.test.com这个域名，如下图，原谅我的厚码...

![](../Images/e06faef507f373f613fe53c5471e4f46.png)  

test.com这个域名经过查找后发现是一家提供医疗信息系统的本地公司,但不解的是为什么医院的系统会放到供应商公司去呢？他们是如何进行数据同步的呢？带着这些问题我开始了对a.test.com这个域名的测试。

![](../Images/68891adf7ac8d118f13e9cc0abed9dc0.png)  

看到这个熟悉的页面，确定了此系统大概是由sping boot开发的，经过一系列常规操作后，只发现了一个swagger-ui页面。

![](../Images/8d5b9e1e37c9ced8121941dfb3b7b9f9.png)

  

由于我们的目标是拿权限，所以重点对此页面的接口进行了sql注入和越权等测试，无果，也没有任何的文件上传接口,开始卡到这里了。

  

回过来想，a.test.com这个域名是test.com的子域名，是否能够通过test.com进行突破呢？

  

访问test.com，打开的是供应商公司的官网。

![](../Images/30cbf696706004e4e02772842b1bffdd.png)  

对test.com的域名做信息收集后发现了几个子域均解析致某云服务器，但是ip不同。

![](../Images/ceff4fd3fb3ced335f3c86aabf95355e.png)  
首先git.test.com这个域名引起了我的注意，打开后是一个gitlab服务。![](../Images/09ff3704c61039763c1ee701725348e9.png)  

gitlab历史上是由几个漏洞的：

![](../Images/1576072e7226437562824f50a953a6cc.png)

  

但不幸的是此系统版本较高，漏洞均以修复。

  

那会不会由弱口令呢？使用几个常用的用户名和top密码进行爆破，无果，我又想办法加到了此公司的一个qq群中，尝试在群文件中获取一些有效信息。

![](../Images/b3fa7a8f8d07d3c9cab3fcebf1a1af11.png)

  

果不然，群文件中有一份表格，记录了员工的详细信息

![](../Images/7bacec6254bb7c2d61e578025a3e7982.png)![](../Images/75eeef6c587728b2563d9f7b9df19d0f.png)  

有了这些信息，我开始使用姓名和工号等组合成gitlab的用户名，使用常用弱口令定向爆破，期望能有一两个结果，但是还是无果，看来此gitlab对密码强度有要求，弱口令是走不通了。

  

**0x03 柳岸花明又一村**

当使用google hack 语法搜索此gitlab时发现了几处无需认证即可访问的公开仓库。  

![](../Images/9cd4ae2d6cdba81b1048bdf460fa7582.png)

  

我开始把希望寄托在了这些可公开访问的仓库上，仔细翻看这些仓库，大多数都是一些接口文档，对本次渗透没有啥用。

  

终于在rabbitmq安装介绍文档中发现了一个oracle数据库的连接用户名和密码：

![](../Images/842463bbe97a6890406f9acd79514089.png)  
在前面的信息收集过程中，已经发现了x.test.com这个子域名对应的ip地址开放了oracle数据库端口，我迅速连接了此数据库发现用户名密码正确，可以连接。![](../Images/426628efffc9a1fed93ac8fe2c0f0b4a.png)  
由于此数据库版本较低，并且时sysdba权限，我可以直接以system权限执行命令。![](../Images/0b791675558da611a69d5d163b4a399a.png)

  

然后就是添加用户登录拿下了这台oracle数据库的服务器。![](../Images/20720e16f1051771b62782300ddf9732.png)

  

并且在这个mysql文件夹中发现了mysql的配置文件。

![](../Images/45b292d95e4f9da37f47235510a67372.png)

  

由于test.com这台服务器是开放了mysql数据库的，利用此信息，我又成功登录了mysql数据库。![](../Images/09109e7a71696b9f5c7d8c61f1b6a5f8.png)  

  

在mysql数据库中成功获取了供应商官网test.com后台的用户名和密码。![](../Images/8348e3b6d7dd42a5e78666ea1e5ae22a.png)  

  

当我满怀欣喜的去登录时，发现确实可以登录，但登陆后的后台功能都已废弃，只有一个大大的thinkphp错误。

![](../Images/13f5302759469a0d4b4f524b08d320e1.png)  
怎么办，原想的通过后台getshell的想法也落空了。（也尝试过使用Thinkphp3的漏洞利用，但也全部失败了）

  

**0x04 绝处逢生**

到这里，我认为只能把希望放在这个mysql数据库上了，由于是windows系统，udf提权大概率成功不了，那就只能尝试写webshell了。写webshell的话需要知道绝对路径，我尝试使用各种办法让test.com报错，看报错信息中有没有包含绝对路径，一系列操作过后无果，只有404页面。  

  

没办法了，只有盲猜一波，我突然想到了mysql数据库表的表名是否就是网站的目录名呢？

![](../Images/1f53b8abf84bee4ee07c4aeb25de7368.png)

  

使用这两个表名构造了以下绝对路径

*   
*   
*   
*   

```
c:\\hs_webc:\\hswebd:\\hs_webd:\\hsweb
```

  
当尝试到c:\\\\hs\_web时，webshell提示已经写入成功了。![](../Images/ccb099e3d3f84bbc581706a103cb9774.png)

  

使用蚁剑连接成功：![](../Images/7f3617e42faf6caae947023f98dc20e7.png)

  

由于当前用户权限较小，使用potato成功提权：![](../Images/f24e927bcd33160a46738c6cca368e89.png)

  

添加用户成功登录远程桌面：![](../Images/544b3699f69167a5d4a791828fc4de2e.png)

  

在服务端的nginx配置文件中发现了代理规则，涉及到几十家医院：![](../Images/dc2a2a3934dbd1c0c2eccee30ed6530c.png)

  

原来这些医院的微信公众号业务都是先访问test.com这台服务器，然后再由这台服务器上的nginx转到到各个医院的真实服务器上。那这样也太不安全了吧，一旦供应商的这台服务器宕机、他们的业务也得跟着丢。

  

然后在这台服务器上发现了微信公众号后台源码，丢给同伴审计了一波，发现了后台登录绕过漏洞，可以直接登录后台。

![](../Images/07ff86b4a7e84b053b993105ac38a0af.png)  

然后就是随意改信息啦。

  

至此本次渗透就结束了，其实拿到医院的真实ip后也可以更深入的进行测试。
