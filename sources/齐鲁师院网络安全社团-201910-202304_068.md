**堆利用之off\_by\_one**  
  

  顾名思义就是溢出一个字节，当程序在缓冲区写入并溢出时，写入的字节数超过了这个缓冲区本身所申请的字节数且只越界了一个字节。

# 漏洞原理

其与整数溢出类似，往往都是对边界检测不严谨造成的溢出一字节情况，通常分为下面两种情况

##   

## 1、循环语句的循环次数设置不严谨

```

```

因为循环体是从0开始循环，而循环的结束语句确实当i小于等于指定size时才退出，程序员本身希望循环size次，却因为构造循环语句的不严谨多循环了一次，这就有可能造成off-by-one

**2、对字符串长度的错误判断  
**

*   

```

```

strlen函数是判断'\\x00'前一共有多少字符，并不包括'\\x00'，当我们使用strcpy函数将buf的内容复制到v1中时，'\\x00'会一同被拷贝过去，所以实际上v1中总共拷贝了9个字节，造成了溢出

**例题：Asis\_2016\_b00ks  
**

![](../Images/055c8f21a44a862b7f0b54a097d55354.png)

图书管理的菜单类型题，通过我们输入的数字来对书籍进行不同的操作

输入1：创建book

输入2：删除book

输入3：添加book的说明

输入4：输出所有book的信息  

输入5：更改作者名字  

这里我们着重看name函数与create函数

name函数

![](../Images/9c4af0514b0157213dbcca35195e7357.png)

![](../Images/355feede6d2c245ae9b89778aefa6e54.png)

在输入name的函数中发现了存在off\_by\_one漏洞，循环体共循环了33次，并且在其退出前name\_ptr指针执行了++操作，也就是说当我们输入的字符是32时，第33位会被置零

create函数

![](../Images/c8ad122cd09e87461ff7ea37fa0d1ad3.png)

在create函数中我们找到了book的结构体，其中依次存放了book\_id，指向book\_name的指针，指向book\_desc的指针，以及book\_desc的大小信息。然后指向book的结构体的指针通过id来存放每一个book结构体，跟进book\_struct\_ptr

![](../Images/9dd21573e15e4d7e7bfedd603c869b01.png)

在这里可以看出name\_ptr跟book\_struct\_ptr的距离正好是32，也就是说我们的off\_by\_one漏洞可以将book\_struct\_ptr的最低位置零，也可以利用这个漏洞将book\_struct\_ptr的地址泄露出来。

利用过程

1、泄露book\_struct\_ptr的地址  

![](../Images/7f29a2a2b6227e3316ba47ed3e842046.png)

程序开启了pie保护，所以我们首先需要做的便是泄露地址  

![](../Images/ef52e94d0ece35e29e356acecb27f096.png)

使用gdb调试，先输入32个字节的a触发off\_by\_one漏洞，再创建一个book1，然后ctrl+c  

![](../Images/8a09082d83bb2dc2f67fa954ebbf48cb.png)

这里我们用pwndbg的search命令寻找我们刚才输入的32个a，发现其在0x555555756040处  

![](../Images/63669ef94736566549e168ae6daf290a.png)

查看其中的内容，0x61是a的16进制表示，而正如我们先前看到的book\_struct\_ptr与name\_ptr的距离是32位，并且因为off-by-one的缘故现在它们的内容并没有'\\x00'进行隔离，也就是说当我们调用功能4print函数打印book信息时，book1\_struct\_ptr的地址会被打印出来（printf函数打印'\\x00'前的内容）  

![](../Images/12224d65a2d2208ffaa046cea020316c.png)

可以看到我们调用4来打印book的信息时32个a后面紧跟着一串乱码，这就是book1\_struct\_ptr的地址

2、利用off-by-one漏洞伪造book1&&泄露libc基地址

为什么需要创建这么大的内存呢，这里就涉及到堆申请内存的一些知识了，平时我们申请内存的时候系统都是通过控制brk的伸缩来完成的，但是当我们申请了过大的内存时，会通过mmap来分配虚拟内存空间，而mmap所申请的内存空间与libc的基地址之间的偏移是固定的，而我们的最终目的获得shell，那么获取libc的基地址就尤为重要了，这里我们申请book2的内存空间为0x21000，让book2\_name与book2\_desc的指针落在mmap申请的虚拟内存上，如下图所示

3、通过free\_hook获得shell

至此我们完成了所有准备工作，而要获得shell我们要利用free\_hook来完成，那么什么是free\_hook呢，我们来看一下函数原型

*   
*   
*   
*   
*   
*   
*   
*   
*   
*   

```
void __libc_free(void *mem) {    mstate    ar_ptr;    mchunkptr p; /* chunk corresponding to mem */
    void (*hook)(void *, const void *) = atomic_forced_read(__free_hook);    if (__builtin_expect(hook != NULL, 0)) {        (*hook)(mem, RETURN_ADDRESS(0));        return;    }}
```

在我们执行free函数的时候，会判断free\_hook中是否有函数，如果有就直接执行，而这也正是我们所需要的，如果我们令free\_hook等于system函数的真实地址，并且free了一个带有/bin/sh的堆块，那么程序就会执行system("/bin/sh")函数，这也正是我们想要的结果，首先我们先算出对应的基地址

*   
*   

```
free_hook = libc.symbols['__free_hook'] + libc_basesystem = libc.symbols['system'] + libc_base
```

binsh\_addr = libc.search('/bin/sh').next() + libc\_base  

![](../Images/45991dee9b0b4c881a1212a833cd813b.png)

然后我们通过edit函数将binsh和free\_hook写入book2的name指针和desc指针中，因为前面我们将fake\_book的desc指针也指向了book2的name指针处，所以我们这里通过调用edit函数修改fake\_book的desc，也就是book2的name指针中的内容

*   

```

```
